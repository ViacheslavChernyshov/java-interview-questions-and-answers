# If Two Objects Have the Same hashCode(), Are They Necessarily Equal by equals()?

---

## 🟢 Junior Level

**NO, absolutely not.**

When two distinct, non-equal objects produce the exact same `hashCode()`, it is known as a **Hash Collision**:

```
  The Invariable Asymmetry of the Contract:
  1. If a.equals(b) == true          ──► a.hashCode() == b.hashCode() (MANDATORY!)
  2. If a.hashCode() == b.hashCode() ──► a.equals(b) MAY BE TRUE OR FALSE (COLLISION!)
```

```java
String s1 = "Aa";
String s2 = "BB";

System.out.println(s1.hashCode()); // 2112
System.out.println(s2.hashCode()); // 2112 (Identical!)

System.out.println(s1.equals(s2)); // false — Completely different strings!
```

---

## 🟡 Middle Level

### Mathematical Proof: The Pigeonhole Principle

Why identical hash codes for unequal objects are impossible to prevent:
1. `hashCode()` returns a signed 32-bit primitive integer (`int`).
2. There are exactly **$2^{32} \approx 4.29 \times 10^9$** distinct integer hash codes.
3. The number of possible object states and string combinations is **infinite** (a 10-character ASCII string has $26^{10} \approx 141 \text{ trillion}$ combinations).
4. By the **Pigeonhole Principle**, mapping an infinite domain into 4.29 billion bins guarantees that distinct objects will share hash codes.

### 64-Bit Folding in `java.lang.Long`

```java
// OpenJDK Long.hashCode() folds 64 bits into 32 bits using XOR:
public static int hashCode(long value) {
    return (int)(value ^ (value >>> 32));
}
```

Because of this bit folding, `1L` and `4294967297L` ($1 + 2^{32}$) produce the **exact same `hashCode() == 1`**, yet `1L.equals(4294967297L)` is `false`.

## 🔴 Senior Level

### The 2-Tier Filtering Pipeline in `HashMap`

`HashMap` treats `hashCode()` and `equals()` as an asymmetric two-tier search pipeline:

```
  Incoming query: map.get(key)
         │
         ▼
  [Tier 1: hashCode()] ──► O(1) Fast Coarse Filter:
                           Computes array index = (n - 1) & hash.
                           Instantly eliminates 99.9% of all unrelated entries in RAM!
         │
         ▼
  [Tier 2: equals()]   ──► Fine-Grained Precision Matcher:
                           Traverses only the few collided nodes in that specific bucket.
                           Evaluates p.hash == hash && key.equals(p.key).
```

### Hash Flooding Vulnerability & Treeification Defense

Because unequal keys can easily share hash codes, attackers can generate thousands of distinct strings (e.g. `"AaAa"`, `"AaBB"`, `"BBAa"`, `"BBBB"`) that all hash to the same bucket:
- **Java 7 Vulnerability:** All items chained into a single 10,000-node linked list, causing $O(N^2)$ CPU starvation.
- **Java 8+ Defense:** When bucket collision length reaches 8 (and capacity $\ge 64$), `HashMap` converts the list into a Red-Black Tree, capping worst-case lookups at **$O(\log N)$**.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Truth:** Identical hash codes do NOT guarantee equality (this is a standard hash collision).
- **Pigeonhole Principle:** Finite 32-bit integer space ($4.29 \times 10^9$) vs infinite possible object instances.
- **String Collision Example:** `"Aa".hashCode() == "BB".hashCode() == 2112`.
- **Long Collision Example:** `1L` and `(1L + (1L << 32))` produce identical hash code 1.
- **Two-Tier Filtering:** `hashCode()` provides fast $O(1)$ bucket isolation; `equals()` performs exact key matching.
- **Java 8+ Defense:** Collision chains $\ge 8$ convert to Red-Black Trees ($O(\log N)$) to defend against hash flooding.

**Common Follow-up Questions:**
- *"What happens inside a HashMap when two unequal keys have the same hashCode?"* → Both entries are placed into the same bucket chain (as a linked list or Red-Black Tree) and differentiated via `equals()`.
- *"Can you design a custom class where every instance returns `hashCode() == 42`?"* → Yes, it is syntactically valid and preserves the contract, but it destroys `HashMap` performance by turning all operations into $O(\log N)$ tree searches.
- *"Why does String use multiplier 31 in its hashCode?"* → 31 is an odd prime, and `31 * h` is optimized by the CPU into a fast bit-shift and subtract: `(h << 5) - h`.

**Red Flags (DO NOT Say):**
- ❌ *"If two objects have the same hashCode, they are guaranteed to be equal."* (Equal hash codes only mean a collision occurred).
- ❌ *"A perfect hash function in Java should never produce collisions."* (Impossible due to the Pigeonhole Principle).
- ❌ *"If a collision occurs, the previous key in the map is overwritten."* (Values are overwritten only if `equals()` returns true).
