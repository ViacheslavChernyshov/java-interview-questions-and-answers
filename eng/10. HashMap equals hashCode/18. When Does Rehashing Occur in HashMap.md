# When Does Rehashing Occur in HashMap?

---

## 🟢 Junior Level

Rehashing (or table resizing) in a `HashMap` is triggered in **three distinct scenarios**:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Trigger Scenario                 │ Condition Evaluated in Source                                               │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Lazy Table Initialization**    │ Executed on the **first `put()`** when `table == null || table.length == 0` │
  │ 2 │ **Threshold Exceeded**           │ Executed when total elements exceed limit: **`++size > threshold`**         │
  │ 3 │ **Small Table Treeification**    │ Bucket reaches **$\ge 8$ elements**, but total table **capacity $< 64$**   │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
Map<String, Integer> map = new HashMap<>(); // table is initially null (0 bytes array)

map.put("First", 1); // 🚀 Trigger 1: Allocates initial array (capacity = 16, threshold = 12)

// ... After adding 11 more elements (size = 12):
map.put("Thirteenth", 13); // 🚀 Trigger 2: size (13) > threshold (12) -> Doubles capacity to 32
```

## 🟡 Middle Level

### Resizing Mechanics & Threshold Math

```java
// OpenJDK putVal() trigger check:
if (++size > threshold)
    resize();
```

$$\mathbf{threshold = (int)(capacity \times loadFactor)} = 16 \times 0.75 = 12$$

```
  What Happens When resize() Fires:
  1. Allocates a new array of double the previous size (newCap = oldCap << 1).
  2. Traverses all bins in the old array and relocates nodes to the new array.
  3. Updates threshold (newThr = oldThr << 1).
  4. Discards the old array reference for Garbage Collection.
```

### Preventing Resizing in Hot Paths

Resizing is an $O(N)$ stop-the-world-like operation for the executing thread that allocates a new array and relinks thousands of nodes. In high-frequency REST or Kafka consumer pipelines, unexpected resizes cause **P99 latency spikes**.

```java
// Pre-size map to avoid all resizing pauses for 10,000 entries:
Map<String, Order> orderMap = new HashMap<>((int) Math.ceil(10_000 / 0.75f));
```

## 🔴 Senior Level

### Trigger 3: Small-Table Treeification Fallback

```java
// OpenJDK treeifyBin() source logic:
final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY) // n < 64
        resize(); // 🚀 Resizes instead of treeifying!
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // Convert to Red-Black Tree
    }
}
```
> [!NOTE]
> When a table is small ($N < 64$), multiple keys sharing a bucket is considered a symptom of a cramped array rather than a bad hash code. Doubling the table redistributes the collided keys into distinct buckets at lower overhead than building tree nodes.

### Concurrency Dangers During Resizing

```
  Multi-Threaded Mutation Hazards:
  • Java 7: Concurrent resize() with head-insertion reversed list links, creating circular 
    references that locked CPU threads at 100% infinite loops during get().
  • Java 8+: Tail-insertion prevents circular loops, but concurrent resizing still causes
    silent data loss, broken trees, and race conditions. Always use ConcurrentHashMap.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The 3 Triggers:** (1) First `put()` lazy allocation, (2) `++size > threshold`, (3) Bucket count $\ge 8$ while capacity $< 64$.
- **Formula:** `threshold = capacity * loadFactor` (Default: $16 \times 0.75 = 12$).
- **Cost:** $O(N)$ time complexity + temporary heap memory allocation for both old and new arrays.
- **Lazy Initialization:** No memory is allocated for the bucket array until the first element is inserted.
- **Tail Insertion (Java 8+):** Preserves element order during migration, eliminating Java 7 circular loop bugs.

**Common Follow-up Questions:**
- *"Why does HashMap double its capacity ($2N$) rather than adding fixed increments ($+16$)?"* → Doubling ensures amortized $O(1)$ insertion cost and allows the Lo/Hi single-bit test without recomputing hash codes.
- *"What happens if capacity reaches `1 << 30` (maximum capacity)?"* → Resizing stops, and `threshold` is permanently set to `Integer.MAX_VALUE`.
- *"How can you size a map that expects 500 items?"* → $\lceil 500 / 0.75 \rceil = 667 \to$ rounds up to capacity **1024**.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap resizes on every single put() call."* (It only resizes when `++size > threshold`).
- ❌ *"Resize recalculates the hashCode() of every key in the map."* (Java 8+ uses a single bit check `(e.hash & oldCap) == 0` without recomputing hashes).
- ❌ *"Rehashing is completely safe across multiple threads in Java 8."* (It still suffers from data loss and race conditions; `ConcurrentHashMap` must be used).
