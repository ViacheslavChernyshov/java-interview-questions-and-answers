# What Happens If You Modify a Key After Adding It to HashMap?

---

## 🟢 Junior Level

If you modify a key's fields after inserting it into a `HashMap`, the key's hash code changes, making the entry **permanently unreachable via `map.get()` or `map.remove()`**:

```java
MutableKey key = new MutableKey(1);
map.put(key, "Initial Data"); // Stored in Bucket 1 (hash = 1)

key.setValue(2); // 💥 Mutated: Key hash is now 2

System.out.println(map.get(key)); // ❌ Returns null! (Searches Bucket 2)
```

```
  The Mechanical Breakdown:
  1. The Node physically remains in Bucket 1.
  2. map.get(key) dynamically computes hash(key.hashCode()) = 2 and searches Bucket 2.
  3. Bucket 2 is empty -> HashMap returns null!
```

## 🟡 Middle Level

### The Key-Reference Paradox & Iterator Anomaly

```
  ┌──────────────────────────────────────────────┬────────────────────────┬──────────────────────────────────────────────────┐
  │ Access Method                                │ Result                 │ Architectural Reason                             │
  ├──────────────────────────────────────────────┼────────────────────────┼──────────────────────────────────────────────────┤
  │ **Direct Lookup (`map.get(key)`)**           │ ❌ Returns `null`      │ Searches the wrong bucket based on new hash      │
  │ **Direct Deletion (`map.remove(key)`)**       │ ❌ Returns `null`      │ Cannot find node to unlink; entry remains in RAM │
  │ **Full Iteration (`map.entrySet()`)**         │ ✅ **Finds the entry!**│ Scans array slots 0 to $N-1$ physically          │
  └──────────────────────────────────────────────┴────────────────────────┴──────────────────────────────────────────────────┘
```

```java
// The iterator scans all physical table array slots, finding the trapped entry:
for (Map.Entry<MutableKey, String> entry : map.entrySet()) {
    System.out.println(entry.getKey() + " -> " + entry.getValue()); 
    // Prints: MutableKey(val=2) -> Initial Data
}
```

### Can the Element Be Recovered?

- **Yes, by Reversing the Mutation:** If the key's fields are restored to their exact original values, `key.hashCode()` returns to its original value, and `map.get(key)` successfully finds the entry again.
- **Yes, via Iterator Deletion:** `iterator.remove()` deletes the node from the bucket list without invoking `key.hashCode()`.

## 🔴 Senior Level

### The Ghost Entry Memory Leak

In high-throughput services with long-lived caches:

```java
// ❌ PRODUCTION ACCUMULATION LEAK:
Map<SessionKey, SessionData> sessionCache = new HashMap<>();

public void updateSession(SessionKey key, SessionData data) {
    key.setLastAccess(System.currentTimeMillis()); // Mutates hash field!
    sessionCache.put(key, data); // Adds a NEW node in new bucket slot!
}
```
```
  Result of Continuous Key Mutation:
  • Every update leaves the previous Node orphaned in its old bucket.
  • A single active user creates thousands of ghost entries in the table.
  • Memory fills Old Gen, triggering frequent Full GC pauses and OutOfMemoryError.
```

### Defensive Copying & Record Solutions

```java
// Pattern 1: Delete -> Modify -> Re-insert
String value = map.remove(key);
key.updateState();
map.put(key, value);

// Pattern 2: Immutable Records (Prevents mutations at compile-time)
public record SessionKey(UUID userId, long creationTimestamp) {}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Failure Cause:** Node remains in `oldBucket`, but `map.get()` searches `newBucket` based on updated `hashCode()`.
- **The Paradox:** Holding a direct pointer to the key object still results in `map.get(key)` returning `null`.
- **Iterator Behavior:** `map.entrySet()` will still find and display the item because it scans all buckets linearly.
- **Memory Leak:** `map.remove(key)` fails, creating un-removable "Ghost Entries".
- **Recovery:** Reverting fields back to their original values restores lookup capability.
- **Proper Pattern:** Always remove the key from the map before mutating it.

**Common Follow-up Questions:**
- *"Can you remove a mutated key from a HashMap?"* → Not via `map.remove(key)`. You must iterate using `map.entrySet().iterator()` and call `iterator.remove()`.
- *"What happens if the mutation does NOT change the hashCode?"* → If the mutated field is not part of `hashCode()` or `equals()`, lookups will continue to succeed, but it remains a dangerous architectural practice.
- *"Does copying the map via `new HashMap<>(oldMap)` fix broken keys?"* → Yes! `new HashMap<>(oldMap)` recalculates the bucket index for every key using its current `hashCode()`, correctly placing all items in their new buckets.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap automatically shifts nodes to their new buckets when key fields change."* (HashMap has no listeners or mechanism to track external mutations).
- ❌ *"The mutated entry is completely erased from the map."* (The node remains in memory, trapped in its old bucket).
- ❌ *"Mutating keys is safe if the map never resizes."* (Lookup fails immediately upon hash change, regardless of resizing).
