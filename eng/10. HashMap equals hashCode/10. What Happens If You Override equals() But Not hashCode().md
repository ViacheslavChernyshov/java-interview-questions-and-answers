# What Happens If You Override equals() But Not hashCode()?

---

## 🟢 Junior Level

If you override `equals()` but fail to override `hashCode()`, logically equal objects will inherit distinct default **Identity Hash Codes** from `Object.hashCode()`.

This **catastrophically breaks all Hash-based collections** (`HashMap`, `HashSet`, `ConcurrentHashMap`):

```java
public class Employee {
    private final Long id;
    public Employee(Long id) { this.id = id; }

    @Override
    public boolean equals(Object o) { // ❌ equals overridden, hashCode NOT overridden!
        if (this == o) return true;
        if (!(o instanceof Employee e)) return false;
        return Objects.equals(id, e.id);
    }
}
```

```java
Set<Employee> employees = new HashSet<>();
employees.add(new Employee(101L)); // Placed in Bucket A (Identity Hash 1)
employees.add(new Employee(101L)); // Placed in Bucket B (Identity Hash 2)

// 💥 BUG: HashSet contains duplicate elements!
System.out.println(employees.size()); // Returns 2!
```

## 🟡 Middle Level

### The 3 Production Failure Modes

```
  ┌───┬──────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Failure Mode             │ Mechanical Reason                                                           │
  ├───┼──────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **`map.get()` $\to$ `null`**│ `map.get()` calculates a different bucket index and never checks `equals()`.│
  │ 2 │ **`HashSet` Duplicates** │ `HashSet` checks `equals()` ONLY within the same bucket; never across bins. │
  │ 3 │ **Memory Leak (Zombies)**│ `map.remove()` searches the wrong bucket, leaving old entries in memory.    │
  └───┴──────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```
  Step-by-Step Failure Trace:
  1. map.put(new Employee(1L), "MANAGER") ──► Hash = 839219 ──► Stored in table[11]
  2. map.get(new Employee(1L))            ──► Hash = 192842 ──► Searches table[2] ──► Returns null!
```

### Static Analysis & Tooling Enforcement

Modern CI/CD quality gates treat this bug as a critical severity blocker:
- **SonarQube Rule `S1206`:** *"equals(Object obj) and hashCode() should be overridden in pairs"*.
- **SpotBugs Check `HE_EQUALS_USE_HASHCODE`:** Flags classes overriding equals without hashCode.

## 🔴 Senior Level

### The Cache Bypass & Stampede Hazard

In enterprise caching architectures (e.g. In-Memory Caffeine / Guava / Spring Cache):

```java
Map<UserCacheKey, UserProfile> cache = new HashMap<>();

public UserProfile getUser(Long userId) {
    UserCacheKey key = new UserCacheKey(userId); // Overrides equals, but NOT hashCode
    UserProfile cached = cache.get(key);        // 💥 ALWAYS returns null!
    if (cached == null) {
        cached = database.fetchUser(userId);    // Crushes database with duplicate queries!
        cache.put(key, cached);                 // Memory leaks with duplicate entries!
    }
    return cached;
}
```

### Lombok & Record Implementation Gotchas

```java
// ❌ LOMBOK HAZARD: Includes non-identity / transient cache fields in hash calculation
@EqualsAndHashCode
public class UserEntity {
    private Long id;
    private transient String temporaryCalculationCache; // Mutating this breaks hashCode consistency!
}

// ✅ EXPLICIT EXCLUSION:
@EqualsAndHashCode
public class UserEntity {
    private Long id;
    @EqualsAndHashCode.Exclude
    private transient String temporaryCalculationCache;
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Defect:** Equal objects inherit distinct identity hash codes and land in different buckets.
- **`HashSet` Impact:** Admits duplicate elements because `equals()` is never invoked across different buckets.
- **`HashMap` Impact:** `map.get()` returns `null` for valid stored keys; `map.remove()` fails, leaking memory.
- **Heisenbug Risk:** Unit tests on small tables may pass by coincidence if unequal hashes share lower bits.
- **Lombok Defense:** Use `@EqualsAndHashCode.Exclude` on transient or lazily computed fields.
- **Records:** Java `record`s guarantee safe, paired implementations automatically.

**Common Follow-up Questions:**
- *"Why does `HashSet.size()` equal 2 when adding two equal objects?"* → Because `HashSet` is backed by a `HashMap`. Two objects with different hash codes land in different bucket indices, so `HashSet` never calls `equals()` between them.
- *"What happens if a field is added to `equals()` but forgotten in `hashCode()`?"* → Equal objects will still share the same hash code (contract holds), but unequal objects will collide more often.
- *"What happens if `hashCode()` is overridden, but `equals()` is NOT?"* → Unequal instances may land in the same bucket, but `HashMap.get()` uses default reference equality (`==`), failing to match equal values.

**Red Flags (DO NOT Say):**
- ❌ *"Overriding only equals() is completely safe if you only use the class in Lists."* (It makes the entity dangerous for any future developer who uses it in a Set or Map).
- ❌ *"HashSet compares every element with every other element using equals()."* (It only compares elements sharing the same hash bucket).
- ❌ *"HashMap will fall back to equals() if it cannot find the hashCode."* (HashMap *never* falls back to full-table scans; it searches strictly by bucket index).
