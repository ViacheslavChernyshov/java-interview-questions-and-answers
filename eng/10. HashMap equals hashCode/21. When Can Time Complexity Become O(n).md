# When Can Time Complexity Become O(n)?

---

## 🟢 Junior Level

While `HashMap` operates in **average $O(1)$ constant time**, lookup operations (`get()`, `containsKey()`, `remove()`) can degrade to **$O(N)$ linear time** under specific architectural failure conditions:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Scenario                         │ Root Cause of $O(N)$ Performance Collapse                                   │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Broken / Constant `hashCode`** │ All keys return the same hash (e.g. `return 1;`), crowding one single bin.  │
  │ 2 │ **Small Table (Capacity $< 64$)**│ Treeification is suppressed; bucket collisions remain linked lists.         │
  │ 3 │ **Legacy Java 7 Runtimes**       │ Lacked Red-Black tree conversion entirely ($O(N)$ list chains).             │
  │ 4 │ **Map Iteration (`entrySet()`)** │ **$O(\text{Capacity} + N)$** by design (scans every allocated table slot).  │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// ❌ Pathological Key: Degrades HashMap into a linked list!
public class BrokenKey {
    private final String id;
    public BrokenKey(String id) { this.id = id; }
    
    @Override public int hashCode() { return 42; } // 💥 All keys collide into table[10]!
    @Override public boolean equals(Object o) { 
        return o instanceof BrokenKey k && Objects.equals(id, k.id); 
    }
}
```

## 🟡 Middle Level

### Scenario 1: Small Table Treeification Suppression (Capacity $< 64$)

```java
// OpenJDK treeifyBin() logic:
if (tab == null || tab.length < MIN_TREEIFY_CAPACITY) // length < 64
    resize(); // Table resizes instead of converting to a Red-Black Tree!
```

```
  How O(N) Occurs:
  • Default initial capacity is 16 (threshold = 12).
  • If 8 items land in bucket 2, the table capacity (16) is below MIN_TREEIFY_CAPACITY (64).
  • Treeification is aborted in favor of resizing.
  • Until capacity expands to >= 64, bucket lookups remain an O(K) linear linked list scan!
```

### Scenario 2: The Iteration Trap ($O(\text{Capacity} + N)$)

Iterating through a map is **not $O(1)$**:

```java
// Allocating 1,000,000 buckets for 5 elements:
Map<String, String> sparseMap = new HashMap<>(1_000_000);
sparseMap.put("A", "Val");

// 💥 Iteration must traverse 1,000,000 null slots in RAM:
for (Map.Entry<String, String> entry : sparseMap.entrySet()) {
    // Takes milliseconds instead of microseconds!
}
```

## 🔴 Senior Level

### Security: Algorithmic Complexity Attacks (CVE-2012-2743)

In Java 7, web application servers (like Apache Tomcat) decoded HTTP POST parameters into a standard `HashMap`:

```
  Hash Flooding Denial of Service:
  1. Adversaries generated 10,000 distinct parameter names sharing the same hashCode (e.g. "AaAa", "AaBB").
  2. All 10,000 parameters chained into a single linked list in table[index].
  3. Inserting 10,000 items took (10,000 * 10,001) / 2 = 50,000,000 equals() comparisons.
  4. Server CPU pegged at 100%, causing a complete Denial of Service (DoS).
```

**Java 8+ Defense:** Converting chains to Red-Black Trees (`TreeNode`) when bucket count reaches 8 bounds worst-case operations to **$O(\log N)$**.

### Comparison: $O(N)$ Linked List vs. $O(\log N)$ Red-Black Tree

Under a collision spike of **1,024 elements** in a single bucket:

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Data Structure               │ Comparisons Required     │ Physical Execution Time                          │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Singly-Linked List**       │ 1,024 comparisons        │ $\sim 5.0\ \mu\text{s}$ ($O(N)$)                 │
  │ **Red-Black Tree**           │ **10 comparisons**       │ **$\sim 0.1\ \mu\text{s}$** ($O(\log N)$)        │
  │ **Performance Advantage**    │ —                        │ **$\mathbf{50\times}$ faster!**                  │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Causes of $O(N)$:** Broken constant `hashCode()`, capacity $< 64$ suppressing treeification, or Java 7 runtimes.
- **Iteration Invariant:** Iterating over `entrySet()` or `keySet()` is strictly $O(\text{Capacity} + N)$.
- **Java 8+ Mitigation:** Treeification converts $O(N)$ linked lists into $O(\log N)$ balanced trees.
- **Security Attack:** Hash Flooding DoS (CVE-2012-2743) exploited Java 7's $O(N)$ lists to freeze web servers.
- **50x Speedup:** Red-Black trees reduce 1,024 comparisons down to 10 comparisons.

**Common Follow-up Questions:**
- *"Why does treeification require capacity $\ge 64$ before converting a list to a tree?"* → Because on small tables, table resizing is cheaper and more effective at redistributing keys across buckets than allocating memory-heavy tree nodes.
- *"What happens if keys with the same hashCode do NOT implement Comparable?"* → `HashMap` balances tree branches using `tieBreakOrder()` and `System.identityHashCode()`, keeping search at $O(\log N)$ with slight reflection/native overhead.
- *"How can you detect $O(N)$ degradation in production?"* → Profile CPU usage during `map.get()` calls using Java Flight Recorder (JFR) and check for elevated `HashMap.CollisionRate` events.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap iteration is O(N) where N is map.size()."* (It is $O(\text{Capacity} + N)$; oversized empty tables cause significant iteration overhead).
- ❌ *"Java 8 treeification makes worst-case lookup O(1)."* (It bounds worst case to $O(\log N)$, not $O(1)$).
- ❌ *"Fixing collisions requires increasing the load factor."* (Fixing collisions requires repairing the key's `hashCode()` implementation).
