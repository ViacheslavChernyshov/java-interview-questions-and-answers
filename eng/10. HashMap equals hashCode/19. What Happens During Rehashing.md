# What Happens During Rehashing?

---

## 🟢 Junior Level

During rehashing (resizing), `HashMap` allocates a new internal array **double the size ($2N$)** of the previous array and redistributes all existing elements into their new bucket positions:

```
  Old Array (Capacity = 16):
  table[4] ──► [Node: Key1] ──► [Node: Key2] ──► null

  Resizing occurs (Capacity doubles to 32):
  newTable[4]  ──► [Node: Key1] ──► null (Lo Partition: stays at index 4)
  newTable[20] ──► [Node: Key2] ──► null (Hi Partition: moves to index 4 + 16 = 20)
```

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Time Complexity                                        │ **$O(N)$** (Iterates across all elements)              │
  │ Hash Recalculation                                     │ **None!** (Uses a single-bit check)                    │
  │ Order Preservation (Java 8+)                           │ **Preserved** (Tail-insertion prevents infinite loops) │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

---

## 🟡 Middle Level

### The Lo/Hi Bit Partitioning Optimization

Because capacity is strictly a power of two, doubling the array adds exactly one higher bit to the index bitmask:

```
  Old Capacity = 16 -> Mask (15): 0000 1111
  New Capacity = 32 -> Mask (31): 0001 1111
                                     ^
                                     New Bit Exposed (Value = 16 / oldCap)
```

```java
// OpenJDK HashMap.java single-bit decision:
if ((e.hash & oldCap) == 0) {
    // 🟢 Lo-List: Stays at the exact same index 'i' in the new table
} else {
    // 🔵 Hi-List: Relocates to index 'i + oldCap' in the new table
}
```

```
  Why This is Ultra-Fast:
  • ZERO hash recalculations are performed (e.hash is stored in the Node).
  • A single bitwise AND (&) partitions the entire bucket into two clean sub-lists!
```

## 🔴 Senior Level

### Tree Splitting & Untreeification (`TreeNode.split()`)

When a bucket containing a Red-Black Tree is resized, `HashMap` executes `TreeNode.split()`:

```java
// OpenJDK TreeNode.split() untreeification logic:
if (lc <= UNTREEIFY_THRESHOLD) // lc <= 6
    tab[index] = loHead.untreeify(map); // 🚀 Reverts tree back to a linked list!
else {
    tab[index] = loHead;
    if (hiHead != null) loHead.treeify(tab); // Rebalances tree
}
```

```
  Tree Split Steps:
  1. Partitions tree nodes into 'lo' and 'hi' lists based on (e.hash & oldCap) == 0.
  2. If a partition contains <= 6 nodes, it unlinks tree pointers and converts back to a standard Node list.
  3. If a partition contains > 6 nodes, it constructs and balances a new Red-Black Tree.
```

### Transient Heap Allocation & GC Pressure

During a resize from capacity $1\text{M} \to 2\text{M}$:
- Old array: $\sim 8\text{ MB}$ (on 64-bit JVM with compressed OOPs).
- New array: $\sim 16\text{ MB}$.
- **Peak transient footprint:** $\sim 24\text{ MB}$ allocated concurrently until the old array is reclaimed by the Garbage Collector.

### Multi-Threaded Comparison: `ConcurrentHashMap`

Unlike `HashMap` (which corrupts data under concurrent resizing), `ConcurrentHashMap` supports **Parallel Cooperative Resizing**:
- Multiple threads assist in migrating buckets concurrently.
- Replaces processed buckets with a special `ForwardingNode` pointing to the new table, allowing concurrent reads to proceed without locking.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Array Doubling:** `newCap = oldCap << 1`.
- **Bitwise Split:** Elements are split into `Lo` (stays at `index`) and `Hi` (moves to `index + oldCap`) using `(e.hash & oldCap) == 0`.
- **No Hash Recomputation:** The precomputed `e.hash` is reused directly.
- **Tail Insertion (Java 8+):** Preserves element order, eliminating the circular list loops from Java 7.
- **Tree Splitting:** Trees split into two; partitions with $\le 6$ nodes revert to linked lists (`untreeify`).
- **Transient Memory:** Both old and new arrays exist simultaneously during the copy.

**Common Follow-up Questions:**
- *"Why does `(e.hash & oldCap) == 0` dictate whether an element moves?"* → Because `oldCap` is a single binary bit matching the newly exposed position in `newCap - 1`. If that bit is 0, the new index equals the old index; if 1, the new index equals `oldIndex + oldCap`.
- *"What happens if resizing occurs while an iterator is active?"* → `HashMap` detects the mutation via `modCount` and immediately throws `ConcurrentModificationException` (fail-fast behavior).
- *"How does ConcurrentHashMap improve resizing over HashMap?"* → It uses `ForwardingNode` markers and allows multiple concurrent worker threads to migrate bucket chunks in parallel.

**Red Flags (DO NOT Say):**
- ❌ *"Rehashing calls `key.hashCode()` on every key in the map."* (It checks the stored `e.hash` bitwise without recalculation).
- ❌ *"Rehashing randomly scatters elements across new buckets."* (It deterministically splits each bucket into at most two specific slots: `i` and `i + oldCap`).
- ❌ *"Java 8 makes resizing completely thread-safe in HashMap."* (It prevents circular loops, but concurrent resizing still corrupts data and loses entries).
