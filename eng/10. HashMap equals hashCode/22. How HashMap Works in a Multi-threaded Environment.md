# How HashMap Works in a Multi-threaded Environment

---

## 🟢 Junior Level

**`HashMap` is NOT thread-safe.**

Attempting to read or write to a `HashMap` concurrently across multiple threads without external synchronization leads to severe concurrency anomalies:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Concurrency Anomaly              │ Mechanical Symptom                                                         │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Silent Lost Updates**          │ Two threads writing to the same bucket overwrite and destroy each other.    │
  │ 2 │ **Stale Memory Visibility**      │ Thread reads stale values because internal fields lack memory barriers.     │
  │ 3 │ **Table Corruption on Resize**   │ Concurrent resizing corrupts bucket links, losing thousands of entries.     │
  │ 4 │ **`ConcurrentModificationException`**│ Iterating while another thread mutates the map aborts execution.        │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

> [!CAUTION]
> **Spring Framework Singleton Bug:**
> Storing a standard `HashMap` inside a Spring `@Service` or `@Component` singleton is a major production hazard. Hundreds of incoming Tomcat/Jetty worker threads mutate the map simultaneously, causing silent data corruption and erratic outages. Always use `ConcurrentHashMap`!

## 🟡 Middle Level

### The Lost Update Race Condition in `putVal()`

```java
// OpenJDK HashMap.java putVal() source:
if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null); // 💥 DATA RACE!
```

```
  Timeline of a Lost Update:
  Thread 1: Evaluates tab[i] == null (true) -> Suspended by OS scheduler.
  Thread 2: Evaluates tab[i] == null (true) -> Writes Node("Key2", 200) to tab[i].
  Thread 1: Resumes -> Writes Node("Key1", 100) directly over tab[i]!
  Result: Node("Key2") is completely deleted from the map and lost forever!
```

### The Fail-Fast Iterator & `modCount`

`HashMap` tracks structural mutations using an internal counter:

```java
transient int modCount; // Incremented on every put/remove/resize
```

When an iterator is created, it captures `expectedModCount = modCount`. If another thread mutates the map during iteration, the iterator detects `modCount != expectedModCount` and immediately throws **`ConcurrentModificationException`**.

> [!NOTE]
> Fail-fast iteration is a **best-effort debugging aid**, NOT a concurrency defense mechanism. It cannot guarantee detection under weak hardware memory models without synchronization.

## 🔴 Senior Level

### Safe Publication for Read-Only Maps

A standard `HashMap` can be safely read concurrently by millions of threads **IF AND ONLY IF** it is populated beforehand and published via **Safe Publication**:

```java
// ✅ SAFE PUBLICATION: Constructed completely before threads start, exposed via final field:
public class ImmutableConfigurationRegistry {
    private final Map<String, String> configMap;

    public ImmutableConfigurationRegistry(Map<String, String> rawData) {
        Map<String, String> temp = new HashMap<>(rawData);
        this.configMap = Collections.unmodifiableMap(temp); // JMM Final Freeze guarantees visibility!
    }

    public String getConfig(String key) {
        return configMap.get(key); // 100% thread-safe without locks!
    }
}
```

### Concurrency Options Compared

```
  ┌──────────────────────────────────┬──────────────────────────────────────┬──────────────────────────────────────────┐
  │ Implementation                   │ Concurrency Architecture             │ Performance & Scalability                │
  ├──────────────────────────────────┼──────────────────────────────────────┼──────────────────────────────────────────┤
  │ **`HashMap`**                    │ Zero synchronization / No locks      │ Not thread-safe (Data corruption)        │
  │ **`ConcurrentHashMap`**          │ Lock-free reads, CAS + Bin Locking   │ **Ultra-High Scalability (Industry Std)**│

```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Thread Safety:** `HashMap` is completely non-thread-safe.
- **Data Races:** Concurrent writes cause lost updates, stale reads, and table corruption during resize.
- **Java 7 vs Java 8+:** Java 7 head-insertion caused circular pointer loops (100% CPU infinite loops); Java 8+ tail-insertion eliminates loops, but data loss still occurs.
- **Safe Usage:** Safe for concurrent reads only after safe publication via `final`/`volatile` and with zero concurrent writes.
- **Fail-Fast:** `modCount` detects concurrent structural modifications on a best-effort basis (`ConcurrentModificationException`).
- **Primary Alternative:** `ConcurrentHashMap` using fine-grained bucket locks and CAS.

**Common Follow-up Questions:**
- *"Why does Spring Boot report random NullPointerExceptions when using HashMap in a @Service?"* → Because multiple HTTP request worker threads concurrently mutate the map, causing corrupted tree nodes and broken linked list references.
- *"Why is `ConcurrentHashMap` better than `Collections.synchronizedMap()`?"* → `synchronizedMap` locks the entire collection on every read and write; `ConcurrentHashMap` performs lock-free reads and locks only the individual bucket being modified.
- *"What is a TOCTOU race condition in HashMap?"* → Time-Of-Check to Time-Of-Use: `if (!map.containsKey(k)) map.put(k, v)` is non-atomic and allows another thread to insert a value in between.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap is thread-safe as long as threads write to different keys."* (Concurrent writes triggering `resize()` corrupt the entire table regardless of keys).
- ❌ *"Fail-fast iterators make HashMap thread-safe."* (Fail-fast is a debugging error trigger, not a concurrency synchronization mechanism).
- ❌ *"Collections.synchronizedMap() provides the same performance as ConcurrentHashMap."* (It forces single-threaded global lock contention).
