# What is the Time Complexity of get() and put() Operations in HashMap?

---

## 🟢 Junior Level

In `HashMap`, fundamental operations (`get()`, `put()`, `remove()`, `containsKey()`) execute in **average $O(1)$ constant time**:

```
  ┌──────────────────────────┬──────────────────────┬──────────────────────┬──────────────────────────────────────────────────┐
  │ Operation                │ Average Case         │ Worst Case (Java 7)  │ Worst Case (Java 8+)                             │
  ├──────────────────────────┼──────────────────────┼──────────────────────┼──────────────────────────────────────────────────┤
  │ **`get()`**              │ **$O(1)$**           │ $O(N)$ (Linked List) │ **$O(\log N)$** (Red-Black Tree)                 │
  │ **`put()`**              │ **$O(1)$** amortized │ $O(N)$ (Linked List) │ **$O(\log N)$** (Red-Black Tree)                 │
  │ **`remove()`**           │ **$O(1)$**           │ $O(N)$ (Linked List) │ **$O(\log N)$** (Red-Black Tree)                 │
  │ **`containsKey()`**      │ **$O(1)$**           │ $O(N)$ (Linked List) │ **$O(\log N)$** (Red-Black Tree)                 │
  │ **Map Iteration**        │ **$O(\text{Cap} + N)$**│ $O(\text{Cap} + N)$│ **$O(\text{Cap} + N)$**                          │
  └──────────────────────────┴──────────────────────┴──────────────────────┴──────────────────────────────────────────────────┘
```

```java
Map<String, Integer> map = new HashMap<>();

// Instant O(1) operations under well-distributed hash codes:
map.put("USD", 100);       // O(1)
Integer bal = map.get("USD"); // O(1)
```

## 🟡 Middle Level

### Why Operations Run in $O(1)$ Time

```
  1. Hash Spread Calculation: O(1) -> 2-3 CPU bitwise instructions.
  2. Bucket Index Mask:       O(1) -> 1 CPU bitwise AND (&) cycle.
  3. Direct Array Slot Jump:  O(1) -> Direct memory pointer dereference.
  4. Bucket Scan:             O(1) -> Under Poisson distribution (0.75 load factor), 
                                      average bucket length is <= 1.25 nodes.
```

### Amortized $O(1)$ for `put()`

While a single `put()` that triggers a table `resize()` takes $O(N)$ time, capacity grows geometrically ($16 \to 32 \to 64 \dots$). The total work across $N$ insertions sums to:

$$\sum_{i=0}^{\log_2 N} 2^i = 2N - 1 = O(N) \implies \frac{O(N)}{N} = \mathbf{O(1) \text{ amortized time per insertion}}$$

## 🔴 Senior Level

### Real-World CPU Latency: The Hidden Constant Factor

Asymptotic notation $O(1)$ hides the **hardware constant factor ($C$)**:

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Memory Hierarchy Level       │ Access Latency           │ Impact on HashMap                                │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **L1 CPU Cache Hit**         │ **$\sim 1$ ns**          │ Array slot in hot CPU cache                      │
  │ **L2 CPU Cache Hit**         │ **$\sim 4$ ns**          │ Bucket head node cached                          │
  │ **L3 CPU Cache Hit**         │ **$\sim 15$ ns**         │ Node located in shared CPU cache                 │
  │ **Main RAM Miss**            │ **$\sim 100$ ns**        │ Traversing scattered heap node pointers          │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

> [!TIP]
> A map with a broken `hashCode()` or an expensive `equals()` method (e.g. comparing 10KB strings) may run in $O(1)$ mathematically, but executes **100x slower** in practice due to constant memory cache misses and method execution overhead.

### When Worst-Case Degrades to $O(N)$ in Java 8+

Even with Java 8+ treeification, operations can still degrade to $O(N)$ under specific edge conditions:
1. **Total Capacity $< 64$:** When total table capacity is small, `HashMap` resizes instead of treeifying, leaving bucket chains as $O(K)$ linked lists.
2. **Non-Comparable Keys with Hash Collisions:** If thousands of keys produce the exact same `hashCode()` and do not implement `Comparable<K>`, `HashMap` must invoke `tieBreakOrder()` and perform full-branch tree scans.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Average Complexity:** $O(1)$ for get, put, remove, containsKey.
- **Worst Case Java 7:** $O(N)$ linear linked list scan.
- **Worst Case Java 8+:** $O(\log N)$ balanced Red-Black tree lookup.
- **Iteration Cost:** $O(\text{Capacity} + \text{Size})$ — traversing empty buckets adds overhead.
- **Amortization:** `put()` is amortized $O(1)$ because $O(N)$ resizes happen exponentially less frequently as size increases.
- **Hardware Latency:** RAM cache misses (~100 ns) dominate physical execution time over algorithmic steps.

**Common Follow-up Questions:**
- *"Why is map iteration NOT O(N)?"* → Because `HashMap` must inspect every slot in the `table` array from index 0 to `capacity - 1`, making iteration cost $O(\text{Capacity} + N)$.
- *"What is the difference in lookup speed between HashMap and ConcurrentHashMap?"* → `HashMap.get()` has zero synchronization overhead; `ConcurrentHashMap.get()` uses volatile reads on table nodes, which is nearly as fast (lock-free) on single threads with a minor memory barrier overhead.
- *"How does TreeMap compare to HashMap?"* → `TreeMap` is strictly $O(\log N)$ for all operations, but keeps keys ordered; `HashMap` is faster ($O(1)$), but unordered.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap operations are always guaranteed to execute in O(1) time."* (Worst case is $O(\log N)$ or $O(N)$ under heavy collisions).
- ❌ *"Iterating through HashMap keys is O(1)."* (It is $O(\text{Capacity} + \text{Size})$).
- ❌ *"Java 8 treeification makes worst-case lookup O(1)."* (Treeification reduces worst case to $O(\log N)$, not $O(1)$).
