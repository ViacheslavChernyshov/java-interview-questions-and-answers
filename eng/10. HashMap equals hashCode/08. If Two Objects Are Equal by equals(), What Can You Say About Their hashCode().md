# If Two Objects Are Equal by equals(), What Can You Say About Their hashCode()?

---

## 🟢 Junior Level

If two objects are equal according to `equals()`, their `hashCode()` values **MUST BE STRICTLY IDENTICAL**:

```java
Person p1 = new Person("Alice", 30);
Person p2 = new Person("Alice", 30);

if (p1.equals(p2)) {
    // 🚀 INVARIANT: This assertion MUST ALWAYS be true!
    assert p1.hashCode() == p2.hashCode(); 
}
```

```
  Why this is mandatory:
  1. HashMap locates the bucket index using hashCode(): index = (n - 1) & hash.
  2. If p1 and p2 have different hashCodes, HashMap looks in the WRONG bucket.
  3. map.get(p2) will return null even though p1 was previously stored with put(p1, value)!
```

---

## 🟡 Middle Level

### The Anatomy of Broken Retrieval

```
  Step 1: map.put(k1, "DATA")
  k1.hashCode() = 100 ──► Bucket Index: 4 ──► table[4] = [Node: k1 -> "DATA"]

  Step 2: map.get(k2) where k2.equals(k1) is true, but k2.hashCode() is 250:
  k2.hashCode() = 250 ──► Bucket Index: 10 ──► Searches table[10] ──► Returns null!
```

```
  Consequences of Violating the Contract:
  • Silent Data Loss: map.get() returns null for valid existing keys.
  • Duplicate Key Violations: HashSet allows multiple "identical" objects to be inserted.
  • Memory Leaks: map.remove(k2) searches the wrong bucket, leaving k1 permanently trapped in RAM.
```

## 🔴 Senior Level

### The Flaky Heisenbug Hazard

Failing to maintain identical hash codes for equal objects often produces **flaky, non-deterministic production bugs**:

```
  Why Tests Pass Locally but Crash in Production:
  • On small tables (capacity = 16), different hash codes (e.g. hash 36 and hash 68) 
    accidentally produce the same bucket index: (36 & 15 == 4) and (68 & 15 == 4).
  • Local unit tests pass because both objects land in bucket 4 by pure coincidence.
  • In production under heavy load, the map resizes to capacity = 32:
    (36 & 31 == 4), but (68 & 31 == 4 + 16 == 20).
  • The keys split into different buckets, causing instant, silent data lookup failures!
```

### Identity Hash Code & GC Mark Word Mechanics

By default, `Object.hashCode()` produces the **Identity Hash Code**:
- The identity hash code is lazily generated by the JVM (typically using a Marsaglia Xorshift or OpenJDK Park-Miller PRNG) upon first invocation.
- Once generated, it is stored directly in the object's 64-bit **Mark Word header**.
- **GC Relocation Immunity:** When a Garbage Collector (like G1 or ZGC) moves an object to a different memory address in Old Gen, the identity hash code in the Mark Word **remains unchanged**, guaranteeing consistency.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The Contract:** If `a.equals(b)` is true, `a.hashCode() == b.hashCode()` MUST be true.
- **Root Cause of Bugs:** Different hash codes cause `HashMap` to search the wrong bucket array index.
- **Failures Caused:** `map.get()` returns `null`, `HashSet` contains duplicates, `map.remove()` fails.
- **Heisenbug Risk:** Index collisions on small capacity tables can mask hash bugs in unit tests until resizing occurs.
- **Default Hash:** `System.identityHashCode()` is stored in the object header Mark Word and never changes during GC compaction.

**Common Follow-up Questions:**
- *"Is the reverse true: if two objects have the same hashCode, must they be equal?"* → No. Equal hash codes represent a hash collision; `equals()` must still confirm true equality.
- *"How do Lombok and Records protect against this bug?"* → `@EqualsAndHashCode` (Lombok) and Java `record`s construct both `equals()` and `hashCode()` using the exact same set of component fields.
- *"What happens if a field used in `equals()` is omitted from `hashCode()`?"* → The contract is technically preserved (equal objects will still have equal hashes), but unequal objects will collide more frequently, degrading performance.

**Red Flags (DO NOT Say):**
- ❌ *"If two objects are equal, their hash codes only need to be similar."* (They must be strictly identical integers).
- ❌ *"Overriding only equals() is fine as long as you don't use the class in a HashSet."* (It makes the class fragile and prone to catastrophic failure when another developer later places it in a Map).
- ❌ *"Default Object.hashCode() returns the object's current RAM memory address."* (It is a PRNG value generated once and preserved in the Mark Word; memory addresses change during GC).
