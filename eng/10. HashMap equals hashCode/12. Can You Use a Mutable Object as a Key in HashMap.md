# Can You Use a Mutable Object as a Key in HashMap?

---

## 🟢 Junior Level

Technically **yes**, Java allows any object to be used as a `HashMap` key, but **it is a severe anti-pattern**.

If you mutate the internal fields of a key object after inserting it into a `HashMap`, the key becomes **"broken"** and the stored entry becomes permanently inaccessible:

```java
public class MutableAccount {
    private int accountId; // ❌ Mutable field!

    public MutableAccount(int id) { this.accountId = id; }
    public void setAccountId(int id) { this.accountId = id; }

    @Override public int hashCode() { return accountId; }
    @Override public boolean equals(Object o) {
        return o instanceof MutableAccount a && this.accountId == a.accountId;
    }
}
```

```java
Map<MutableAccount, String> accounts = new HashMap<>();
MutableAccount acc = new MutableAccount(100);

accounts.put(acc, "VIP Customer"); // Stored in Bucket 4 (hash = 100)

acc.setAccountId(200); // 💥 MUTATION: Hash changes from 100 to 200!

// ❌ BROKEN: Searches Bucket 8 (hash = 200) -> Returns null!
System.out.println(accounts.get(acc)); 
```

## 🟡 Middle Level

### The "Ghost Entry" Memory Leak Pattern

```
  1. Insertion:
     put(key, val) ──► hash(100) ──► Stored in table[4]

  2. Mutation:
     key.setName("Updated") ──► hash changes to 250

  3. Lookup Failure:
     get(key) ──► hash(250) ──► Searches table[10] ──► Returns null!

  4. Deletion Failure (Memory Leak):
     remove(key) ──► Searches table[10] ──► Finds nothing!
     Result: Original Node in table[4] is permanently trapped in Old Gen memory.
```

### What if the Mutated Field is Omitted from `hashCode()` / `equals()`?

While mutating fields that are **not** part of `equals()` or `hashCode()` does not break bucket indexing, it is still considered **bad practice**:
- It violates the Principle of Least Surprise.
- A future refactoring might include that field in `@EqualsAndHashCode`, silently introducing catastrophic lookup bugs.

## 🔴 Senior Level

### Safe Mutation Pattern: Remove $\to$ Mutate $\to$ Re-insert

If an object's key property must be modified, strictly apply the **Extract-Mutate-Insert** cycle:

```java
public void updateAccountKey(Map<MutableAccount, String> map, MutableAccount key, int newId) {
    String value = map.remove(key); // 1. Remove while old hashCode is still valid
    if (value != null) {
        key.setAccountId(newId);    // 2. Mutate key state outside the map
        map.put(key, value);        // 3. Re-insert under new bucket index
    }
}
```

### `IdentityHashMap` as an Alternative

When mutable object references must serve as map keys without relying on object state:

```java
// Uses System.identityHashCode() and reference equality (==):
Map<MutableAccount, String> identityMap = new IdentityHashMap<>();
identityMap.put(acc, "VIP");
acc.setAccountId(200); // Does NOT break lookup because reference identity is unchanged!
```

> [!WARNING]
> `IdentityHashMap` alters equality semantics: two distinct object instances with identical field values are treated as **different keys**.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Rule:** Mutable keys are syntactically permitted, but mutating a key breaks `hashCode()` lookup.
- **The Failure:** `map.get()` searches the wrong bucket and returns `null`; `map.remove()` fails, leaking memory.
- **Ghost Entries:** Trapped, un-removable nodes in the hash table that cause memory leaks.
- **Golden Fix:** Use immutable types (`String`, `Integer`, `UUID`, Java `record`s) with `private final` fields.
- **Safe Mutation:** Always `remove()` from map before mutating, then `put()` back.

**Common Follow-up Questions:**
- *"Why is `StringBuilder` a terrible HashMap key while `String` is ideal?"* → `StringBuilder` is mutable and does not override `equals()` or `hashCode()` (inherits reference identity); `String` is strictly immutable and caches its content hash code.
- *"Why are JPA/Hibernate Entities risky as HashMap keys?"* → Entity primary keys change from `null` to assigned IDs upon `entityManager.persist()`, corrupting hash bucket locations if stored in a `Set` before saving.
- *"How can you enforce key immutability at compile time?"* → Declare classes as Java `record`s or ensure all fields are marked `final`.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap automatically recalculates bucket indices when a key is mutated."* (HashMap has zero knowledge of key field mutations).
- ❌ *"Mutable objects are fine as keys as long as you don't call remove()."* (Calling `get()` will also fail to find the item).
- ❌ *"IdentityHashMap is a drop-in replacement for HashMap when using mutable keys."* (It uses reference equality `==` instead of `equals()`, breaking logical equality).
