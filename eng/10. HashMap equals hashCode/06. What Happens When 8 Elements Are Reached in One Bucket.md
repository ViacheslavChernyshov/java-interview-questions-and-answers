# What Happens When 8 Elements Are Reached in One Bucket?

---

## 🟢 Junior Level

When a single bucket reaches **8 elements**, `HashMap` evaluates whether to optimize the bucket structure.

However, **it does NOT always convert to a tree**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Condition                                              │ Action Taken by `HashMap`                              │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ Bucket length $\ge 8$ **AND** Capacity $< 64$          │ **Resizes table** (Doubles capacity to spread keys)    │
  │ Bucket length $\ge 8$ **AND** Capacity $\ge 64$         │ **Treeifies bucket** (Converts list to Red-Black Tree) │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Why Table Resize is Preferred Over Treeification:**
> If the table capacity is small ($<64$), collisions are caused by a cramped table rather than a compromised hash code. Doubling the table redistributes elements into two distinct buckets based on a single bit check, resolving the collision at its root rather than optimizing search inside a crowded bucket.

## 🟡 Middle Level

### The 3 Core Treeification Constants

```java
static final int TREEIFY_THRESHOLD   = 8;  // Bucket count triggering treeifyBin()
static final int UNTREEIFY_THRESHOLD = 6;  // Bucket count triggering reversion to list
static final int MIN_TREEIFY_CAPACITY = 64; // Minimum table capacity before treeifying
```

```java
// OpenJDK treeifyBin() source logic:
final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)
        resize(); // 🚀 Capacity < 64: Resize table instead of treeifying!
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // Capacity >= 64: Transform linked list into Red-Black Tree (TreeNode)
    }
}
```

### The Hysteresis Principle (8 vs. 6)

```
  List State ──(Insert 8th item)──► Red-Black Tree State ($O(\log N)$)
      ▲                                   │
      │                                   │ (Remove until 6 items remain)
      └───────── Revert to List ──────────┘
```

If the threshold were symmetrical ($8 \leftrightarrow 7$), repeatedly adding and removing an 8th element would cause **structure thrashing** (continuous costly allocations and conversions between `Node` and `TreeNode`). The 2-element hysteresis gap stabilizes data structure transitions.

## 🔴 Senior Level

### Red-Black Tree Construction & `tieBreakOrder()`

When `treeifyBin()` executes, standard `Node<K,V>` instances are replaced with `TreeNode<K,V>` instances (doubly-linked to support ordered iteration + Red-Black balance pointers).

To construct a deterministic binary search tree when multiple keys share identical hash codes, `HashMap` applies the following precedence:
1. **Integer Hash Comparison:** `h1.compareTo(h2)`.
2. **`Comparable` Interface:** If `key implements Comparable<K>`, invokes `k1.compareTo(k2)`.
3. **`tieBreakOrder()` Fallback:** If keys do not implement `Comparable` or produce a tie (`compareTo == 0`), `HashMap` breaks ties using `System.identityHashCode()`:

```java
static int tieBreakOrder(Object a, Object b) {
    int d;
    if (a == null || b == null ||
        (d = a.getClass().getName().compareTo(b.getClass().getName())) == 0)
        d = (System.identityHashCode(a) <= System.identityHashCode(b) ? -1 : 1);
    return d;
}
```

### Production Implications: Treeification as an Anomaly Alert

Under normal production workloads with a well-behaved `hashCode()`, the mathematical probability of 8 collisions in a single bucket is approximately **$0.00000006$** (derived from the Poisson distribution).

> [!WARNING]
> If profiling reveals active `TreeNode` instances in production:
> 1. **Broken `hashCode()`:** Key entities likely return constant or poorly distributed hash values.
> 2. **Hash Flooding Attack:** The application may be under an external Algorithmic Complexity DoS attack.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Two Thresholds:** `TREEIFY_THRESHOLD = 8`, `MIN_TREEIFY_CAPACITY = 64`.
- **Resize vs. Treeify:** If capacity $< 64$, `HashMap` resizes; if capacity $\ge 64$, it converts the bucket to a Red-Black Tree.
- **Untreeify Threshold:** Reverts back from a tree to a linked list when element count drops to **6**.
- **Hysteresis:** The gap between 8 and 6 prevents rapid thrashing between tree and list structures.
- **Search Complexity:** Improves bucket lookup from $O(K)$ linear scan to $O(\log K)$ logarithmic tree search.
- **Tie-Breaking:** Uses `Comparable.compareTo()` or `System.identityHashCode()` via `tieBreakOrder()`.

**Common Follow-up Questions:**
- *"Why does treeification require capacity $\ge 64$?"* → Because on small tables, resizing is more effective at resolving collisions by distributing items across new buckets.
- *"Why not use trees for all buckets from the start?"* → `TreeNode` instances consume twice as much memory (~64–80 bytes vs ~32 bytes for `Node`), and list traversal is faster for $K \le 7$.
- *"Can a `null` key ever be part of a treeified bucket?"* → No. A map contains at most one `null` key, which always resides in `table[0]`.

**Red Flags (DO NOT Say):**
- ❌ *"Reaching 8 elements always turns the bucket into a tree immediately."* (Only if total capacity is at least 64; otherwise it resizes).
- ❌ *"The bucket untreeifies back to a list as soon as it drops to 7 elements."* (Untreeification occurs at 6 to provide hysteresis).
- ❌ *"Treeification is the normal, expected way HashMap stores elements."* (It is an emergency fallback for statistical anomalies or hash flooding attacks).
