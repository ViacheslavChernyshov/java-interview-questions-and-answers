# How HashMap Determines Which Bucket to Put an Element In

---

## 🟢 Junior Level

`HashMap` determines the target bucket index for any key in **two deterministic steps**:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Computation Step                 │ Mathematical Operation                                                      │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Bitwise Hash Spread**          │ `hash = (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16)`              │
  │ 2 │ **Power-of-Two Bitwise Mask**    │ `index = (capacity - 1) & hash`                                             │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// Example calculation for key = "hello" on default table capacity 16:
String key = "hello";
int rawHash = key.hashCode();            // e.g. 99162322 (binary: 00000101 11101001 00101110 11010010)
int spreadHash = rawHash ^ (rawHash >>> 16);
int index = (16 - 1) & spreadHash;       // 15 & spreadHash -> Bucket Index: 2
```

## 🟡 Middle Level

### Step 1: Why the Bitwise Spread (`>>> 16` XOR) Exists

```
  Key hashCode (32 bits):
  [ Higher 16 Bits: 0101 1110 1001 0010 ] [ Lower 16 Bits: 0010 1110 1101 0010 ]
                       │
                       ▼ (Shift right by 16 bits: >>> 16)
  [ Zero Fill:       0000 0000 0000 0000 ] [ Higher 16 Bits: 0101 1110 1001 0010 ]
                       │
                       ▼ (Bitwise XOR: ^)
  [ Perturbed Hash:  0101 1110 1001 0010 ] [ Blended Lower 16: 0111 0000 0100 0000 ]
```

- **Problem:** For typical table capacities ($N = 16, 32, 64$), the index mask `(N - 1)` only looks at the **lowest 4–6 bits**.
- **Solution:** Shifting the top 16 bits down and XOR-ing folds the entropy of the upper bits into the lower bits, preventing collisions when keys vary only in their higher bits (such as sequential memory addresses or timestamps).

### Step 2: Why Bitwise AND Replaces Modulo Division

$$\mathbf{index = hash \pmod N \iff index = (N - 1) \ \& \ hash} \quad (\text{when } N = 2^k)$$

```
  Bitwise AND Performance:
  • Modulo division (%) requires hardware integer division (10–50 CPU clock cycles).
  • Bitwise AND (&) executes as a single-cycle CPU logic instruction (~1 clock cycle).
```

## 🔴 Senior Level

### Mathematical Proof: Why Capacity MUST Be a Power of Two

If table capacity is **not** a power of two, bitmask indexing severely degrades bucket distribution:

```
  Case 1: Capacity = 16 (Power of 2)
  N - 1 = 15 -> Binary: 0000 1111 (All 4 lower bits are 1)
  Result: Every bucket index 0 through 15 can be reached uniformly.

  Case 2: Capacity = 15 (NOT a Power of 2)
  N - 1 = 14 -> Binary: 0000 1110 (Lowest bit is ALWAYS 0!)
  Result: Every odd-numbered bucket (1, 3, 5, 7, 9, 11, 13) is PERMANENTLY UNREACHABLE!
  50% of the allocated table array is wasted, doubling collision rates.
```

### Classic String Hash Collisions

Because Java's `String.hashCode()` computes $\sum_{i=0}^{n-1} s[i] \cdot 31^{n-1-i}$, known pairs produce identical 32-bit hash codes:

```java
// Identical hashCode = 2112:
System.out.println("Aa".hashCode()); // (65 * 31) + 97 = 2112
System.out.println("BB".hashCode()); // (66 * 31) + 66 = 2112

// Both land in the exact same bucket regardless of table size!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Two-Step Algorithm:** Spread function `h ^ (h >>> 16)` followed by bitmask `(n - 1) & hash`.
- **Bitwise AND Speed:** Bitwise `&` runs in 1 CPU cycle; modulo `%` takes 10–50 cycles.
- **Power of Two Invariant:** Ensures `(n - 1)` contains all binary 1s, making all bucket indices reachable.
- **`null` Key:** `hash(null) == 0`, placing `null` strictly in `table[0]`.
- **String Hash Caching:** `String` caches its 32-bit `hash` field after first calculation for $O(1)$ re-access.

**Common Follow-up Questions:**
- *"Why does `HashMap` not use `key.hashCode()` directly without spreading?"* → Because on small tables ($N=16$), only the lowest 4 bits are evaluated, causing massive collisions if keys differ only in high-order bits.
- *"What happens if a class returns a constant `hashCode()` (e.g. `return 42`)?"* → All keys map to the exact same bucket index, degrading `HashMap` into a linked list ($O(N)$) or Red-Black Tree ($O(\log N)$).
- *"How do Java 14+ Records generate hash codes?"* → The compiler synthesizes an invokedynamic `ObjectMethods.bootstrap` call that hashes all record components.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap finds the bucket by calling `key.hashCode() % table.length`."* (It uses bitwise `(capacity - 1) & hash`).
- ❌ *"The spread function makes `hashCode()` cryptographically secure."* (It is an internal distribution heuristic, not cryptographic hashing).
- ❌ *"Passing capacity 15 causes HashMap to use modulo arithmetic."* (HashMap rounds 15 up to 16).
