# How to Choose the Initial Capacity for HashMap?

---

## 🟢 Junior Level

When creating a `HashMap` where the approximate number of entries is known in advance, you should pre-calculate its **Initial Capacity** to prevent expensive runtime resizing pauses:

```java
// Golden Formula to eliminate all resize pauses:
int initialCapacity = (int) Math.ceil(expectedSize / 0.75f);
Map<String, Integer> map = new HashMap<>(initialCapacity);
```

```java
// Storing 100 entries:
int cap = (int) Math.ceil(100 / 0.75f); // 134 -> tableSizeFor() allocates capacity 256
Map<String, Integer> map = new HashMap<>(cap);
// threshold = 256 * 0.75 = 192 (100 items fit safely with ZERO resize operations!)
```

## 🟡 Middle Level

### The Classic Trap: Passing `expectedSize` Directly

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Instantiation Code           │ Internal Calculation     │ Result for 1,000 Elements                        │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ ❌ `new HashMap<>(1000)`     │ Cap = 1024, Thresh = 768 │ 💥 **Resizes to 2048 upon inserting 769th item!**│
  │ ✅ `new HashMap<>(1334)`     │ Cap = 2048, Thresh = 1536│ 🚀 **Zero resizes! 1000 items fit effortlessly** │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

```
  Why new HashMap<>(1000) Fails:
  1. tableSizeFor(1000) rounds up to the nearest power of two: 1024.
  2. The internal threshold is calculated as 1024 * 0.75 = 768.
  3. When inserting the 769th element, ++size > threshold evaluates to true,
     triggering an expensive O(N) resize() right in the middle of data loading!
```

### Google Guava / Commons Utility Helpers

```java
// Google Guava encapsulates the exact formula:
Map<String, Order> orders = Maps.newHashMapWithExpectedSize(1000);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Sizing Formula:** `initialCapacity = (int) Math.ceil(expectedSize / loadFactor)`.
- **The Pitfall:** `new HashMap<>(1000)` sets capacity to 1024 with threshold 768, triggering a resize on element 769.
- **`tableSizeFor()`:** Automatically rounds capacity up to the next power of two ($16, 32, 64, 128, \dots$).
- **Cost of Resizing:** Resizing during batch inserts causes GC allocation churn and P99 latency spikes.
- **Cost of Over-sizing:** Oversized arrays degrade iteration time ($O(\text{Capacity} + N)$) and waste heap RAM.
- **Small Collections:** Do not bother pre-sizing maps with $< 5$ elements.

**Common Follow-up Questions:**
- *"Why does Guava's `newHashMapWithExpectedSize(n)` add a small fudge factor for $n < 3$?"* → For $n < 3$, integer division gives small values where load factor thresholds would trigger premature resizing on the 1st or 2nd item.
- *"How does pre-sizing affect HashMap memory usage?"* → It allocates the target array once, preventing the allocation and subsequent garbage collection of all intermediate array sizes ($16, 32, 64, 128, 256, 512, 1024$).
- *"What is the formula for a custom load factor of 0.5?"* → For 1000 elements: $\lceil 1000 / 0.5 \rceil = 2000 \to$ rounds up to capacity **2048**.

**Red Flags (DO NOT Say):**
- ❌ *"Writing `new HashMap<>(1000)` ensures a map of capacity 1000 that never resizes for 1000 items."* (Capacity becomes 1024, threshold becomes 768, resizes at 769 items).
- ❌ *"Always set initial capacity to 100,000 just in case."* (Wastes RAM and severely degrades `entrySet()` iteration speeds).
- ❌ *"Initial capacity can be adjusted at runtime after creation."* (Capacity is fixed until automatic resizing occurs).
