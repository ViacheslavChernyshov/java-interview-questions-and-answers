# What Are the Requirements for a HashMap Key?

---

## 🟢 Junior Level

A class used as a `HashMap` key must satisfy **three fundamental requirements**:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Key Requirement                  │ Architectural Rationale                                                     │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Paired `equals()` & `hashCode`**│ Equal objects MUST produce identical hash codes (Contract Rule).            │
  │ 2 │ **Immutability**                 │ Key state must not change after insertion (Prevents broken bucket indices). │
  │ 3 │ **Deterministic Consistency**    │ Re-invoking `hashCode()` must return the exact same integer every time.     │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// ✅ IDEAL KEYS:
String s = "order-12345";         // Strictly immutable, cached hash code
Integer id = 42;                  // Primitive wrapper, immutable
public record UserKey(UUID id) {} // Java Record: Automatic immutability and contract compliance

// ❌ DANGEROUS KEYS:
StringBuilder sb = new StringBuilder("k"); // Mutable! No equals/hashCode implementation!
List<String> list = new ArrayList<>();     // Mutable! Modifying elements breaks map lookup!
```

## 🟡 Middle Level

### Key Suitability Matrix

```
  ┌──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Candidate Key Type       │ Suitability Status       │ Evaluation & Trade-offs                          │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **`String` / `UUID`**    │ 🌟 **Optimal**           │ Immutable, cached hash, uniform distribution     │
  │ **Java `record`**        │ 🌟 **Optimal**           │ Immutable components, clean compiler contracts   │
  │ **`Enum`**               │ ⚡ **Use `EnumMap`**      │ Excellent key; `EnumMap` is even faster ($O(1)$) │
  │ **`java.net.URI`**       │ ✅ **Safe**              │ Pure string syntax comparison                    │
  │ **`java.net.URL`**       │ 🚫 **DO NOT USE**        │ `equals()` triggers blocking network DNS queries │
  │ **Java Arrays (`byte[]`)**│ 🚫 **DO NOT USE**       │ `equals()` defaults to reference identity `==`   │
  └──────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

### The Performance Advantage of `Comparable<K>` Keys

```java
// 🚀 Implementing Comparable accelerates Red-Black Tree searches under heavy collisions:
public record OrderId(long id) implements Comparable<OrderId> {
    @Override
    public int compareTo(OrderId other) {
        return Long.compare(this.id, other.id);
    }
}
```

When a bucket treeifies ($\ge 8$ elements), `HashMap` orders `TreeNode` branches using `Comparable.compareTo()`. If keys do not implement `Comparable`, `HashMap` must fall back to the slower `tieBreakOrder()` mechanism using `System.identityHashCode()`.

## 🔴 Senior Level

### The Formal Specification Requirement

From the official Java `Map` interface specification:

> *"Great care must be exercised if mutable objects are used as map keys. The behavior of a map is not specified if the value of an object is changed in a manner that affects `equals` comparisons while the object is a key in the map."*

### Security Considerations: Hash Flooding & Timing Attacks

1. **Hash Flooding DoS:** Ensure custom key hash functions distribute entropy uniformly across all 32 bits to prevent malicious collision clustering.
2. **Timing Side-Channel Attacks:** When comparing cryptographic keys, standard `String.equals()` short-circuits on the first non-matching byte, leaking key length/prefix timing. Security tokens require constant-time comparison (`MessageDigest.isEqual()`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Requirements:** Paired `equals()`/`hashCode()`, immutability, deterministic consistency.
- **Top Key Choices:** `String`, `Integer`, `UUID`, Java `record`s.
- **Why Arrays Fail as Keys:** Arrays inherit `Object.equals()`, comparing memory addresses instead of contents (use `List.of()` or `ByteBuffer`).
- **The URL Trap:** Never use `java.net.URL` as a key because `equals()` makes blocking DNS network lookups.
- **`Comparable` Benefit:** Keys implementing `Comparable<K>` significantly speed up Red-Black tree bucket traversals.

**Common Follow-up Questions:**
- *"Why should you use EnumMap instead of HashMap when keys are Enums?"* → `EnumMap` uses a compact internal array indexed directly by `enum.ordinal()`, offering faster $O(1)$ operations with zero hashing and zero collision overhead.
- *"What happens if a key's `hashCode()` depends on `System.currentTimeMillis()`?"* → Every lookup fails because `get(key)` calculates a new, different hash value that maps to a random bucket.
- *"Can an interface be used as a HashMap key?"* → Yes, but the concrete implementing class must provide valid, consistent `equals()` and `hashCode()` implementations.

**Red Flags (DO NOT Say):**
- ❌ *"Any object can be used as a key without overriding equals() as long as it's small."* (Inherited `Object.equals()` uses reference identity, breaking logical lookups).
- ❌ *"Java Arrays are great keys for binary maps."* (Arrays do not override `equals()` or `hashCode()`; two arrays with identical bytes will fail `equals()`).
- ❌ *"It's safe to use URL as a key for web caches."* (URL performs blocking DNS resolution on every single map operation).
