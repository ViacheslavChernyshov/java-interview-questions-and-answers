# What is Load Factor in HashMap?

---

## 🟢 Junior Level

The **Load Factor** is a fill-ratio metric that determines how full the `HashMap` is allowed to get before its bucket array is automatically doubled in size:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Default Value                                          │ **`0.75f`** (75% full)                                 │
  │ Resizing Threshold Formula                             │ **`threshold = (int)(capacity * loadFactor)`**         │
  │ Default Initial Threshold                              │ $16 \times 0.75 = \mathbf{12}$ elements                │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// Default constructor uses capacity 16 and load factor 0.75:
Map<String, Integer> map = new HashMap<>(); 

// When the 13th element is inserted (size > threshold of 12),
// HashMap automatically resizes to capacity 32 with a new threshold of 24.
```

## 🟡 Middle Level

### Load Factor Trade-off Matrix

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Load Factor Setting          │ Memory Consumption       │ CPU & Collision Rate     │ Recommended Workload                             │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Low (`0.50f`)**            │ High (50% empty bins)    │ **Ultra-fast $O(1)$**    │ Ultra-low latency, read-heavy financial engines  │
  │ **Default (`0.75f`)**        │ **Optimal Balance**      │ **Optimal Balance**      │ General-purpose enterprise backend services      │
  │ **High (`0.90f - 1.0f`)**    │ Low (Minimal empty bins) │ Higher collisions        │ Memory-constrained environments (IoT, Embedded)  │
  │ **Overloaded (`> 1.0f`)**    │ Lowest                   │ Severe degradation       │ Anti-pattern (guarantees deep collision chains)  │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────────────────────────────┘
```

### Pre-calculating Initial Capacity to Prevent Resizing

To store $N$ elements without triggering an expensive runtime `resize()`:

$$\mathbf{initialCapacity = \left\lceil \frac{expectedSize}{loadFactor} \right\rceil} = \left\lceil \frac{1000}{0.75} \right\rceil = 1334 \implies \text{Rounds up to } \mathbf{2048}$$

```java
// Perfectly sized for 1000 items with zero resize pauses:
Map<String, User> map = new HashMap<>((int) Math.ceil(1000 / 0.75f));
```

## 🔴 Senior Level

### The Mathematical Rationale: Poisson Distribution

Why did the OpenJDK architects choose **`0.75`** instead of `0.5` or `1.0`?

Under a load factor of $0.75$, key distribution into buckets follows a **Poisson probability model** ($P(k) = \frac{e^{-\lambda} \lambda^k}{k!}$ with $\lambda = 0.5$):

```
  Probability of a bucket containing k items:
  • 0 items: ~60.65%
  • 1 item:  ~30.33%
  • 2 items: ~7.58%
  • 3 items: ~1.26%
  • 8 items: 0.00000006 (Near zero!)
```

```
  Statistical Conclusion:
  • 0.75 offers the mathematical sweet spot between RAM allocation and collision frequency.
  • An 8-element collision chain is practically impossible under standard workloads.
```

### CPU Cache Line Misses Under High Load Factor

When load factor exceeds $0.85$, collision lists grow longer:
- While asymptotic time remains $O(1)$ on paper, physically chasing `Node.next` heap pointers causes **L1/L2 CPU Cache Misses**.
- Traversing memory references from main RAM requires $\sim 100 \text{ ns}$ vs $\sim 1 \text{ ns}$ for an L1 cache hit, degrading real-world throughput by up to $300\%$.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** The ratio of elements to capacity that triggers table resizing (`threshold = capacity * loadFactor`).
- **Default:** `0.75f` (75%).
- **Calculation Formula:** `initialCapacity = (int) Math.ceil(expectedSize / loadFactor)`.
- **Low LF (0.5):** Fastest lookup speed, lowest collisions, but doubles heap memory overhead.
- **High LF (0.9):** Conserves heap memory, but increases collision chain lengths and CPU cache misses.
- **Poisson Model:** Threshold 8 treeification is derived from Poisson statistics under 0.75 load factor.

**Common Follow-up Questions:**
- *"Can you change the load factor after constructing the HashMap?"* → No, `loadFactor` is marked `final` and can only be set via the constructor.
- *"What happens if you set a load factor of 2.0?"* → The map will delay resizing until size is twice the capacity, guaranteeing multiple collisions per bucket and degrading performance towards $O(N)$.
- *"How does load factor affect iteration over entrySet()?"* → Lower load factors result in larger underlying array capacities, slightly slowing down full-table iteration because more empty buckets must be traversed.

**Red Flags (DO NOT Say):**
- ❌ *"Load factor 0.75 means 75% of buckets contain elements."* (It means total map `size` reaches 75% of total capacity before resizing; multiple elements may share buckets).
- ❌ *"Setting load factor to 1.0 is always optimal for memory."* (It causes severe collision chaining, increasing CPU cache misses and latency spikes).
- ❌ *"Load factor can be updated dynamically via a setter."* (It is immutable).
