# What Happens If You Override hashCode() But Not equals()?

---

## 🟢 Junior Level

If you override `hashCode()` but fail to override `equals()`, objects with identical fields will map to the **correct bucket index**, but `HashMap` will evaluate them as **completely different keys** because inherited `Object.equals()` performs strict **reference identity comparison (`==`)**:

```java
public class Product {
    private final String sku;
    public Product(String sku) { this.sku = sku; }

    @Override
    public int hashCode() { return sku.hashCode(); } // ✅ hashCode overridden!
    // ❌ equals() NOT overridden (Inherits Object.equals: this == obj)
}
```

```java
Map<Product, Integer> inventory = new HashMap<>();
inventory.put(new Product("SKU-100"), 50); // Stored in Bucket 5

// 💥 BUG: map.get() searches Bucket 5, but Object.equals fails on new heap instance!
Integer stock = inventory.get(new Product("SKU-100")); 
System.out.println(stock); // Returns null!
```

## 🟡 Middle Level

### The Two Symmetrical Contract Violations Compared

```
  ┌──────────────────────────────────────────────┬────────────────────────┬────────────────────────┬──────────────────────┬────────────────────────────┐
  │ Scenario                                     │ Bucket Search          │ In-Bucket Equals Check │ `map.get()` Result   │ `HashSet` Behavior         │
  ├──────────────────────────────────────────────┼────────────────────────┼────────────────────────┼──────────────────────┼────────────────────────────┤
  │ **Override `equals()`, forget `hashCode()`** │ ❌ **Wrong Bucket**    │ Never reached          │ `null`               │ Duplicates in **diff** bins│
  │ **Override `hashCode()`, forget `equals()`** │ ✅ **Correct Bucket**  │ ❌ **Fails (`==`)**    │ `null`               │ Duplicates in **same** bin │
  └──────────────────────────────────────────────┴────────────────────────┴────────────────────────┴──────────────────────┴────────────────────────────┘
```

### Trace of `map.get(new Product("SKU-100"))`

```java
// OpenJDK HashMap.java bucket search check:
if (first.hash == hash && ((k = first.key) == key || (key != null && key.equals(k))))
```
1. `first.hash == hash` $\to$ `true` (Hash codes match; searches correct bucket).
2. `(k = first.key) == key` $\to$ `false` (Different memory references in JVM heap: `0x100 != 0x200`).
3. `key.equals(k)` $\to$ Invokes `Object.equals()`, which evaluates `this == k` $\to$ `false`!
4. Result: `HashMap` scans the bucket chain and returns `null`.

## 🔴 Senior Level

### Production Catastrophe: Event Deduplication & Memory Leak

A common high-severity bug occurs in distributed message consumers (Kafka, SQS, REST webhooks):

```java
@Service
public class TransactionDeduplicator {
    // Set accumulates processed transaction DTOs:
    private final Set<TransactionId> processedIds = new HashSet<>();

    public void process(TransactionId txId) { // txId overrides hashCode, but NOT equals
        // 💥 txId is deserialized per request (new heap instance)!
        if (!processedIds.add(txId)) { // Always returns true!
            log.warn("Duplicate transaction: {}", txId);
            return;
        }
        executePayment(txId); // Duplicate payments charged repeatedly!
    }
}
```

```
  Catastrophic Impact:
  1. Duplicate Execution: Every transaction is processed as new, causing double-charges.
  2. Heap Exhaustion (OOM): Millions of duplicate TransactionId objects pile up inside 
     the SAME hash bucket in processedIds, eventually triggering java.lang.OutOfMemoryError.
```

### Bucket Crowding & `TreeNode` Degeneracy

Because all instances share identical hash codes:
- The bucket rapidly reaches `TREEIFY_THRESHOLD = 8` and converts to a **Red-Black Tree (`TreeNode`)**.
- Because the class does not implement `Comparable`, the tree must invoke the fallback `tieBreakOrder()` method, calling native `System.identityHashCode()` on every single lookup and insert.
- CPU cache locality is destroyed, degrading application throughput.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Defect:** Key lands in the correct bucket, but `Object.equals()` fails on reference identity (`this == obj`).
- **`map.get()` Failure:** `map.get(new Key("A"))` returns `null` because the new instance has a distinct heap address.
- **`HashSet` Failure:** `HashSet` accumulates duplicate elements inside the *same* bucket slot.
- **Production Hazard:** Deduplication sets in event processors fail, leading to duplicate processing storms and `OutOfMemoryError`.
- **Golden Rule:** Always override `equals()` and `hashCode()` together in pairs.

**Common Follow-up Questions:**
- *"What is the exact behavioral difference between forgetting equals vs forgetting hashCode?"* → Forgetting `hashCode` places equal items in different buckets; forgetting `equals` places equal items in the same bucket but treats them as distinct keys.
- *"What does `set.contains(new Product("SKU-100"))` return?"* → It returns `false`, because the newly instantiated `Product` fails reference identity comparison against the stored instance.
- *"How do you prevent this bug automatically?"* → Use Java `record` types, Lombok `@EqualsAndHashCode`, or IDE automated generation tools.

**Red Flags (DO NOT Say):**
- ❌ *"If hashCode is equal, Java skips the equals() check."* (Java always calls `equals()` to verify key identity after hash matching).
- ❌ *"Forgetting equals() is less damaging than forgetting hashCode()."* (Both cause identical functional failures: `get()` returning `null` and duplicate entries in Sets).
- ❌ *"HashMap uses reflection to compare fields if equals is missing."* (It strictly invokes `key.equals()`, which defaults to `this == obj`).
