# What is a Bucket in HashMap?

---

## 🟢 Junior Level

A **Bucket** (or bin) is an individual slot within the internal array (`table[]`) of a `HashMap`:

```
  HashMap Internal Storage (Array of Buckets):
  table[0]  ──► null (Empty bucket)
  table[1]  ──► [Node: "Alice"=30] ──► [Node: "David"=42] ──► null (Collision list)
  table[2]  ──► [TreeNode: Root] (Red-Black Balanced Tree)
  table[3]  ──► [Node: "Bob"=25] ──► null
  ...
  table[15] ──► null
```

```
  ┌──────────────────────────┬────────────────────────────────────────────────────────┐
  │ Physical Representation  │ Array element `table[index]`                           │
  │ Index Calculation        │ `index = (table.length - 1) & hash`                    │
  │ Default Initial Count    │ 16 buckets (table array slots)                         │
  │ Capacity Sizing Rule     │ Strictly constrained to **powers of two** ($2^n$)      │
  └──────────────────────────┴────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The 3 Structural States of a Bucket

```
  ┌───┬──────────────────────────┬─────────────────────────────────────────────┬───────────────────────────────────────────────┐
  │ # │ Bucket State             │ Internal Representation                     │ Search Complexity & Characteristics           │
  ├───┼──────────────────────────┼─────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ 1 │ **Empty**                │ `table[i] == null`                          │ **$O(1)$** (No elements present)              │
  │ 2 │ **Singly-Linked List**   │ Head `Node<K,V>` with `.next` pointers      │ **$O(K)$** where $K < 8$ bucket elements      │
  │ 3 │ **Red-Black Tree**       │ Root `TreeNode<K,V>` with left/right nodes  │ **$O(\log K)$** when $K \ge 8$ and cap $\ge 64$│
  └───┴──────────────────────────┴─────────────────────────────────────────────┴───────────────────────────────────────────────┘
```

### Power-of-Two Capacity Invariant

When configuring custom initial capacities, the JVM automatically rounds up to the next highest power of two via bitwise shifts (`tableSizeFor()`):

```java
// Providing capacity 10 allocates a table of size 16:
Map<String, String> map = new HashMap<>(10); // table.length = 16
```

## 🔴 Senior Level

### Memory Footprint: `Node` vs. `TreeNode`

```java
// Standard Singly-Linked Node (~32 bytes on 64-bit JVM with Compressed OOPs):
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;    // 4 bytes
    final K key;       // 4-8 bytes reference
    V value;           // 4-8 bytes reference
    Node<K,V> next;    // 4-8 bytes reference
}

// Red-Black TreeNode (~64-80 bytes on 64-bit JVM):
static final class TreeNode<K,V> extends LinkedHashMap.Entry<K,V> {
    TreeNode<K,V> parent; // 4-8 bytes
    TreeNode<K,V> left;   // 4-8 bytes
    TreeNode<K,V> right;  // 4-8 bytes
    TreeNode<K,V> prev;   // 4-8 bytes (needed to unlink upon removal)
    boolean red;          // 1 byte
}
```

### Statistical Basis: The Poisson Distribution

Why does treeification trigger specifically at **8 elements**? Under standard load factor ($0.75$), key placement follows a **Poisson distribution**:

$$P(k) = \frac{e^{-\lambda} \lambda^k}{k!} \quad (\text{with } \lambda = 0.5)$$

```
  Poisson Probability of Bucket Lengths:
  • 0 items: ~60.65%
  • 1 item:  ~30.33%
  • 2 items: ~7.58%
  • 3 items: ~1.26%
  • 8 items: 0.00000006 (~1 in 16,000,000 probability!)
```
> [!NOTE]
> Reaching 8 items in a single bucket under a well-distributed `hashCode()` is statistically near-impossible. A bucket reaching 8 indicates an adversarial **Hash Flooding Attack** or a broken `hashCode()` implementation, justifying the extra memory overhead of a Red-Black Tree.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** An individual array slot in `Node<K,V>[] table`.
- **3 States:** Empty (`null`), Singly-Linked List (`Node`), and Red-Black Tree (`TreeNode`).
- **Capacity Constraint:** Always sized to a power of two ($16, 32, 64, \dots$).
- **Memory Footprint:** Empty bucket = 4–8 bytes; `Node` = ~32 bytes; `TreeNode` = ~64–80 bytes.
- **Treeification:** Occurs when a bucket reaches 8 elements AND total capacity $\ge 64$.
- **Poisson Model:** Threshold 8 is derived mathematically from Poisson probabilities ($\sim 10^{-8}$).

**Common Follow-up Questions:**
- *"What happens if `new HashMap<>(100)` is constructed?"* → `tableSizeFor()` rounds 100 up to 128 (the nearest power of two).
- *"Why not use trees for all buckets from the start?"* → `TreeNode` instances consume more than double the memory of standard `Node` instances, and for $N \le 7$ linear list traversal is faster than tree traversal due to lower overhead and better CPU branch prediction.
- *"Why do long bucket chains degrade CPU cache locality?"* → Because nodes are individually allocated heap objects scattered non-contiguously in memory, each link traversal triggers an L1/L2/L3 cache miss.

**Red Flags (DO NOT Say):**
- ❌ *"A bucket can only ever hold one key-value entry."* (A bucket holds entire collision chains via linked lists or trees).
- ❌ *"A bucket always turns into a tree as soon as 8 elements are inserted, regardless of capacity."* (If total capacity is under 64, the table resizes instead of treeifying).
- ❌ *"Passing initial capacity 10 allocates an array of length 10."* (It rounds up to 16).
