# What is a Collision in HashMap?

---

## 🟢 Junior Level

A **Collision** occurs when two distinct keys ($k_1 \ne k_2$, where `!k_1.equals(k_2)`) map to the **exact same bucket index** in the internal `table[]` array:

```
  Collision Scenario:
  Key 1: "Aa" ──► hash = 2112 ──► index = 2 ──► table[2]
  Key 2: "BB" ──► hash = 2112 ──► index = 2 ──► table[2] (💥 Collision!)
```

> [!NOTE]
> **Collisions are normal and expected behavior, NOT a software bug.**
> Because there are infinitely many possible objects but only a finite number of buckets (e.g. 16, 32, 64), collisions are mathematically guaranteed. `HashMap` is specifically architected to handle collisions gracefully via **Separate Chaining**.

## 🟡 Middle Level

### The 2 Distinct Types of Collisions

```
  ┌───┬──────────────────────────┬─────────────────────────────────────────────────┬───────────────────────────────────────────────┐
  │ # │ Collision Type           │ Exact Cause                                     │ Architectural Solution                        │
  ├───┼──────────────────────────┼─────────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ 1 │ **HashCode Collision**   │ $k_1\text{.hashCode}() == k_2\text{.hashCode}()$│ Treeification into Red-Black Tree ($O(\log N)$│
  │ 2 │ **Index Mask Collision** │ Different hashes, but identical `(n-1) & hash`  │ Table Resizing ($N \to 2N$) spreads items out │
  └───┴──────────────────────────┴─────────────────────────────────────────────────┴───────────────────────────────────────────────┘
```

```java
// Example of an Index Mask Collision:
int hash1 = 100; // Binary: 0110 0100
int hash2 = 116; // Binary: 0111 0100

// In a table of capacity 16 (mask: 15 / 0000 1111):
int idx1 = 15 & hash1; // 4
int idx2 = 15 & hash2; // 4 -> Identical bucket index despite different hashCodes!
```

### Mathematical Inevitability

1. **Pigeonhole Principle:** The domain of 32-bit `hashCode()` values is $2^{32} \approx 4.29 \times 10^9$. The number of possible Strings/Objects is infinite.
2. **The Birthday Paradox:** In a hash table of size 16, the statistical probability of encountering at least one collision **exceeds 50% after inserting only 5 items**.

## 🔴 Senior Level

### 2-Tier Filtering Optimization

To minimize performance overhead during collision resolution, `HashMap` applies a two-tier evaluation inside `get()` / `put()`:

```java
// Fast-Path Hash Check before Slow-Path Object Equality:
if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k)))) {
    return p; // Key found!
}
```

```
  Filter Tier 1: Integer Equality (p.hash == hash)
  • Single-cycle CPU primitive comparison.
  • Discards 99.9% of non-matching nodes immediately without invoking object methods.

  Filter Tier 2: Reference & Equals Check (k == key || key.equals(k))
  • Evaluates reference identity (k == key) for fast true-match.
  • Invokes key.equals(k) ONLY if hashes match and references differ.
```

### Security: Hash Flooding DoS Attacks

In Java 7 and earlier, severe collisions degraded `HashMap` search into an $O(N)$ linear linked list scan. Malicious actors exploited this by sending thousands of crafted HTTP POST parameters sharing the same hash code, driving web servers to **100% CPU starvation** (Hash Flooding DoS).

**Java 8+ Mitigation:** Treeification converts bucket chains exceeding 8 items into Red-Black Trees, capping worst-case lookup at $O(\log N)$.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Two non-equal keys mapping to the same bucket index in `table[]`.
- **Expected Behavior:** Collisions are mathematically inevitable (Pigeonhole Principle + Birthday Paradox).
- **Two Collision Types:** HashCode collision (same hash) vs Index Mask collision (different hashes, same `(n-1) & hash`).
- **Resolution Strategy:** Separate Chaining using Singly-Linked Lists and Red-Black Trees (Java 8+).
- **Two-Tier Filtering:** Fast integer `p.hash == hash` check before invoking `key.equals()`.
- **Security Defense:** Treeification prevents Hash Flooding DoS attacks by capping search at $O(\log N)$.

**Common Follow-up Questions:**
- *"How does the Birthday Paradox apply to HashMap collisions?"* → In a table with 365 buckets, inserting 23 items yields a 50% probability of collision; in a 16-bucket HashMap, collisions start occurring around 5 items.
- *"Why does HashMap compare `p.hash == hash` before calling `equals()`?"* → Primitive `int` comparison is a single CPU clock cycle; `equals()` requires method dispatch, stack allocation, and multiple field comparisons.
- *"Can a HashMap function correctly if all keys have the same hashCode?"* → Yes, but performance degrades to $O(\log N)$ (or $O(N)$ if keys do not implement `Comparable`).

**Red Flags (DO NOT Say):**
- ❌ *"A collision means an error occurred and the key was overwritten."* (Values are overwritten only if keys are equal via `equals()`).
- ❌ *"Good hash functions completely eliminate collisions."* (Collisions can be minimized, but never eliminated due to the Pigeonhole Principle).
- ❌ *"Collisions only happen when two objects have the same hashCode."* (They frequently happen when different hashes share lower bits under `(n-1) & hash`).
