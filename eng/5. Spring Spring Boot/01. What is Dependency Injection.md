# What is Dependency Injection?

---

## 🟢 Junior Level

**Dependency Injection (DI)** is a software design pattern where an object receives its dependencies from an external assembler (the IoC container) rather than instantiating them internally via `new`.

DI is a concrete implementation of **Inversion of Control (IoC)** (often called the *Hollywood Principle*: *"Don't call us, we'll call you"*).

### Without DI vs. With DI

```java
// ❌ Without DI: High Coupling, Untestable
public class OrderService {
    private final OrderRepository repo = new SqlOrderRepository(); // Hardcoded dependency!
}

// ✅ With DI: Loose Coupling, 100% Testable
@Service
public class OrderService {
    private final OrderRepository repo;

    // Spring injects the configured OrderRepository implementation automatically:
    public OrderService(OrderRepository repo) {
        this.repo = repo;
    }
}
```

### Why Use Dependency Injection?
- **Loose Coupling:** Classes depend on interfaces rather than concrete implementations.
- **Testability:** Unit tests can pass mock or stub dependencies directly without booting a full database.
- **Lifecycle Management:** Spring handles instantiation, configuration, proxying, and destruction.

## 🟡 Middle Level

### The 3 Core Injection Types

| Injection Type | Syntax Example | Immutability | Testability | Recommended Use |
|---|---|---|---|---|
| **Constructor** | `public Service(Repo r) { this.r = r; }` | **Yes (`final`)** | **Highest (No Spring needed)** | **Production Standard (99%)** |
| **Setter** | `@Autowired public void setRepo(Repo r)` | No | Moderate | Optional / Reconfigurable dependencies |
| **Field** | `@Autowired private Repo r;` | No | Lowest (Requires reflection) | **Anti-Pattern (Avoid)** |

### Resolving Prototype Beans in Singletons

A common architectural bug occurs when a **`prototype`** scoped bean is injected into a **`singleton`** bean:
- Spring injects the prototype bean **only once during singleton initialization**, causing the prototype instance to remain stuck permanently as a pseudo-singleton.

```java
@Service
public class ReportService {
    // ❌ WRONG: Injected once; never receives fresh prototype instances!
    // @Autowired private ReportGenerator generator;

    // ✅ SOLUTION: Use ObjectProvider to fetch a fresh instance on demand:
    @Autowired
    private ObjectProvider<ReportGenerator> generatorProvider;

    public void generate() {
        ReportGenerator freshGen = generatorProvider.getObject(); // Fresh prototype instance!
        freshGen.run();
    }
}
```

## 🔴 Senior Level

### Under the Hood: The Spring DI Execution Pipeline

```
  1. Registration Phase:
     Classpath scanning -> ASM bytecode parsing -> `BeanDefinition` metadata registered.
     (Can be mutated globally via `BeanFactoryPostProcessor`).
                            │
                            ▼
  2. Instantiation Phase:
     Constructor selection -> Instantiated via reflection (`Constructor.newInstance()`) or CGLIB.
                            │
                            ▼
  3. Population Phase (Dependency Injection):
     `AutowiredAnnotationBeanPostProcessor` resolves dependencies and populates fields/setters.
                            │
                            ▼
  4. Initialization Phase:
     `BeanPostProcessor.postProcessBeforeInitialization`
     -> `@PostConstruct` / `InitializingBean.afterPropertiesSet()`
     -> `init-method`
     -> `BeanPostProcessor.postProcessAfterInitialization` (AOP Proxies created here!)
                            │
                            ▼
  5. Ready Phase:
     Bean cached in `DefaultSingletonBeanRegistry` (`singletonObjects` Level 1 cache).
```

### Circular Dependency Traps: Constructor vs. Field

- **Constructor Injection:** Spring cannot instantiate Bean A without Bean B, and cannot instantiate Bean B without Bean A. Fails fast during startup with `BeanCurrentlyInCreationException`.
- **Field / Setter Injection:** Spring resolves circular dependencies using a **3-Level Cache** (`singletonFactories` Level 3 cache exposes an uninitialized early reference). However, this creates hidden architectural coupling and can trigger `NullPointerException`s if beans invoke each other inside `@PostConstruct`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Design pattern where object dependencies are supplied externally by an IoC container rather than created internally with `new`.
- **IoC vs DI:** IoC is the broad architectural principle (inverting control flow); DI is the specific mechanism of injecting dependencies.
- **Recommended Strategy:** **Constructor Injection** (guarantees immutability with `final` fields, prevents NPEs, and enables pure POJO unit testing).
- **Prototype in Singleton Fix:** Use `ObjectProvider<T>`, `@Lookup`, or `Provider<T>` to request fresh instances lazily.
- **Field Injection Flaws:** Conceals dependencies, breaks immutability, violates Single Responsibility Principle, and requires reflection or Spring test runners for testing.

**Common Follow-up Questions:**
- *"What is a `BeanDefinition` in Spring?"* → The configuration metadata blueprint describing a bean (class name, scope, constructor arguments, autowiring mode, lazy initialization flag, init/destroy methods).
- *"How does Spring resolve dependencies under the hood?"* → `DefaultListableBeanFactory` scans `BeanDefinition`s, locates matching types, applies qualifiers/primary flags, and injects instances via `AutowiredAnnotationBeanPostProcessor`.
- *"Why is Field Injection considered an anti-pattern?"* → It allows creating uninitialized objects in tests (`new Service()` leaves fields `null`), hides the class's true dependency count, and prevents `final` immutable field declarations.

**Red Flags (DO NOT Say):**
- ❌ *"Field injection is the best and cleanest way to write Spring Boot code."* (It is a recognized anti-pattern; constructor injection is the industry standard).
- ❌ *"Dependency Injection and Service Locator are the same thing."* (Service Locator forces classes to depend directly on a locator registry; DI decouples the class completely from container APIs).
- ❌ *"Every single Java class in a project should be a Spring managed Bean."* (DTOs, Domain Entities, Value Objects, and utility functions should remain regular unmanaged POJOs).
