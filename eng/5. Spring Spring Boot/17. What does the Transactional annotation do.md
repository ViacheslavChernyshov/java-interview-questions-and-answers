# What does the Transactional annotation do?

---

## 🟢 Junior Level

**`@Transactional`** provides **declarative transaction management** in Spring applications:
- It instructs Spring to automatically begin a database transaction before the method starts and **commit** the transaction when the method returns.
- If an unhandled runtime error occurs, Spring automatically **rolls back** all database changes.

```java
@Service
public class BankTransferService {

    @Transactional
    public void transferMoney(Long fromAccount, Long toAccount, BigDecimal amount) {
        accountRepository.debit(fromAccount, amount);
        accountRepository.credit(toAccount, amount);
        // If an exception occurs -> Both operations roll back atomically!
    }
}
```

```
  Execution Lifecycle:
  Proxy ──> `BEGIN TRANSACTION` ──> Executes Business Method ──> `COMMIT`
                                               │
                                  (Throws RuntimeException)
                                               ▼
                                          `ROLLBACK`
```

## 🟡 Middle Level

### Transaction Propagation Behaviors

| Propagation Mode | Description | Behavior if Transaction Exists |
|---|---|---|
| **`REQUIRED` (Default)** | Standard mode; joins active transaction or starts a new one | Uses existing transaction |
| **`REQUIRES_NEW`** | **Suspends** active transaction; opens an independent new transaction | **Creates a 2nd transaction & connection** |
| **`NESTED`** | Uses JDBC **Savepoints** within the existing transaction | Creates a savepoint (Rolls back to savepoint) |
| **`MANDATORY`** | Must run within an active transaction | Joins existing (Throws Exception if none exists) |
| **`SUPPORTS`** | Executes non-transactionally if none exists; joins if active | Joins existing transaction |
| **`NOT_SUPPORTED`** | Suspends active transaction; executes non-transactionally | Suspends active transaction |
| **`NEVER`** | Must run non-transactionally | **Throws Exception** if transaction exists |

### The Checked Exception Rollback Trap

> [!WARNING]
> **Default Rollback Rules:** By default, Spring **ONLY rolls back on Unchecked Exceptions (`RuntimeException` and `Error`)**.
> - Checked exceptions (e.g. `IOException`, `SQLException`, custom business checked exceptions) **WILL NOT TRIGGER A ROLLBACK!**
> 
> ```java
> // ❌ DANGEROUS: Checked exception will commit corrupt data!
> @Transactional
> public void process() throws IOException { ... }
> 
> // ✅ PRODUCTION STANDARD: Explicitly declare rollback for all Exceptions:
> @Transactional(rollbackFor = Exception.class)
> public void process() throws IOException { ... }
> ```

### The `readOnly = true` Performance Optimization

```java
@Transactional(readOnly = true)
public UserDTO findUserById(Long id) {
    return userRepository.findById(id).map(UserDTO::fromEntity).orElseThrow();
}
```
**Benefits:**
1. **Hibernate Optimization:** Disables dirty-checking snapshot comparisons on entity objects, drastically saving CPU cycles and memory allocations.
2. **Database Routing:** Enables multi-datasource routing proxies to dispatch read queries to read-only database replicas.

## 🔴 Senior Level

### The `REQUIRES_NEW` Connection Pool Exhaustion Hazard

```
  HikariCP Pool Size = 10 Connections
  Thread 1 calls `outer()` [@Transactional] ───────────────> Holds Connection #1
    Thread 1 calls `inner()` [@Transactional(REQUIRES_NEW)] ──> Acquires Connection #2
```
If 10 concurrent requests execute `outer()`, all 10 pool connections are locked by outer transactions. When each thread attempts to call `inner()`, the pool is empty, and all 10 threads block waiting for each other, triggering an immediate **HikariCP Connection Pool Deadlock!**

### The Long-Running Transaction Anti-Pattern

```java
@Transactional
public void processPayment(Order order) {
    orderRepository.save(order);      // 1. Holds JDBC Connection (10ms)
    paymentClient.chargeCard(order);  // 2. ⚠️ SLOW HTTP I/O (3,000ms holding JDBC connection!)
    auditRepository.log(order);       // 3. Completes (10ms)
}
```
**Architecture Rule:** Never make external REST/gRPC network calls inside a `@Transactional` boundary. Network latency will monopolize database connections, quickly exhausting your connection pool.

### Transaction-Bound Events: `@TransactionalEventListener`

```java
@Component
public class OrderEventNotifier {

    // Ensures the Kafka event is published ONLY AFTER the database transaction commits successfully:
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onOrderCreated(OrderCreatedEvent event) {
        kafkaTemplate.send("order-topic", event);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Mechanism:** Dynamic proxy encloses method in a `TransactionInterceptor` coordinating with `PlatformTransactionManager`.
- **Default Rollback:** Only on `RuntimeException` and `Error`; checked exceptions require `rollbackFor = Exception.class`.
- **Propagation Modes:** `REQUIRED` (default), `REQUIRES_NEW` (independent connection), `NESTED` (JDBC savepoint).
- **`readOnly = true`:** Disables Hibernate dirty checking and routes to read replicas.
- **`REQUIRES_NEW` Risk:** Consumes a 2nd database connection, risking connection pool deadlocks.
- **Network I/O Rule:** Never execute slow external HTTP/RPC calls inside a transaction.
- **Distributed Safety:** Use `@TransactionalEventListener(phase = AFTER_COMMIT)` to emit messaging events after database commits.

**Common Follow-up Questions:**
- *"What happens if a `@Transactional` method calls another `@Transactional(REQUIRES_NEW)` method in the same class?"* → Self-invocation bypasses the proxy; the `REQUIRES_NEW` configuration is ignored and executes inside the parent transaction.
- *"How does `NESTED` differ from `REQUIRES_NEW`?"* → `NESTED` uses JDBC Savepoints within the same connection; `REQUIRES_NEW` opens a completely independent physical transaction on a separate database connection.
- *"Why does Spring not roll back checked exceptions by default?"* → The design follows standard EJB conventions where checked exceptions represent recoverable business conditions rather than system failures.

**Red Flags (DO NOT Say):**
- ❌ *"Spring rolls back all exceptions by default."* (Only `RuntimeException` and `Error` trigger rollbacks by default).
- ❌ *"Setting `readOnly = true` guarantees that no SQL INSERT statements will execute."* (`readOnly` is an optimization hint to Hibernate and JDBC drivers; native SQL inserts may still execute depending on driver capabilities).
- ❌ *"REQUIRES_NEW is identical to NESTED propagation."* (REQUIRES_NEW uses a separate connection; NESTED uses savepoints within the same connection).
