# What do PostConstruct and PreDestroy methods do?

---

## 🟢 Junior Level

**`@PostConstruct`** and **`@PreDestroy`** are standard Jakarta lifecycle annotations (`jakarta.annotation.*`) used to define initialization and cleanup logic for Spring-managed beans.

```java
import jakarta.annotation.PostConstruct; // Spring Boot 3+ (Jakarta EE standard)
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Service;

@Service
public class EmailNotificationService {

    private final SmtpClient smtpClient;

    public EmailNotificationService(SmtpClient smtpClient) {
        this.smtpClient = smtpClient;
    }

    @PostConstruct
    public void init() {
        // Runs ONCE after all dependencies are injected
        smtpClient.connect();
    }

    @PreDestroy
    public void cleanup() {
        // Runs ONCE before bean destruction during container shutdown
        smtpClient.disconnect();
    }
}
```

## 🟡 Middle Level

### Why Use `@PostConstruct` Instead of Class Constructors?

```java
@Service
public class CacheService {
    @Autowired private RedisClient redisClient; // Injected via Field Injection

    // ❌ FAILS: In the constructor, fields/setters are still NULL!
    public CacheService() {
        // redisClient.ping(); // Throws NullPointerException!
    }

    // ✅ SUCCEEDS: @PostConstruct runs after all properties are injected
    @PostConstruct
    public void init() {
        redisClient.ping(); // Fully safe!
    }
}
```

### Complete Execution Precedence

```
  Initialization Order:
  1. `@PostConstruct` (CommonAnnotationBeanPostProcessor)
         │
         ▼
  2. `InitializingBean.afterPropertiesSet()` (Spring interface callback)
         │
         ▼
  3. `@Bean(initMethod = "customInit")` (Explicit configuration)

  Destruction Order:
  1. `@PreDestroy` (CommonAnnotationBeanPostProcessor)
         │
         ▼
  2. `DisposableBean.destroy()` (Spring interface callback)
         │
         ▼
  3. `@Bean(destroyMethod = "customDestroy")` (Explicit configuration)
```

## 🔴 Senior Level

### The `@Transactional` Proxy Trap

```java
@Service
public class AccountService {

    @PostConstruct
    @Transactional // ❌ FAILS SILENTLY: No database transaction is opened!
    public void initDatabaseDefaults() {
        loadDefaultRoles(); // Runs on raw unproxied instance!
    }

    @Transactional
    public void loadDefaultRoles() { ... }
}
```

#### The Internal Reason:
AOP Dynamic Proxies (which intercept method calls to start transactions) are constructed inside **`BeanPostProcessor.postProcessAfterInitialization()`**, which runs **after** `@PostConstruct` has already executed.
- When `@PostConstruct` runs, Spring is executing code on the **raw unproxied target instance**.

#### The Production Solution:
```java
@Component
public class AccountBootstrap {

    @Autowired private AccountService accountService;

    @EventListener(ContextRefreshedEvent.class) // ✅ Runs after ALL proxies are active!
    @Transactional
    public void onApplicationStartup() {
        accountService.loadDefaultRoles(); // Wrapped properly in a transaction!
    }
}
```

### The Prototype Leak Hazard

```java
@Component
@Scope("prototype")
public class SocketSession {

    @PreDestroy
    public void close() {
        // ❌ NEVER CALLED BY SPRING!
        // Prototype beans are not tracked for destruction -> Sockets remain open!
    }
}
```
**Mandatory Rule:** Clients holding prototype beans must invoke cleanup methods manually or implement a custom `DestructionCallback`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`@PostConstruct`:** Executes once after constructor completion and dependency population; used for post-injection validation and cache warming.
- **`@PreDestroy`:** Executes once before bean destruction during graceful context shutdown; used to release sockets, threads, and I/O handles.
- **Package Standards:** Spring Boot 3+ uses `jakarta.annotation.*` (replaces legacy `javax.annotation.*`).
- **Initialization Order:** 1. `@PostConstruct` $\to$ 2. `InitializingBean.afterPropertiesSet()` $\to$ 3. `initMethod`.
- **Destruction Order:** 1. `@PreDestroy` $\to$ 2. `DisposableBean.destroy()` $\to$ 3. `destroyMethod`.
- **Proxy Trap:** AOP proxies are created *after* `@PostConstruct`, so `@Transactional` and `@Async` do not work inside `@PostConstruct`. Use `@EventListener(ContextRefreshedEvent.class)` instead.
- **Prototype Exemption:** `@PreDestroy` is **never** invoked automatically for prototype-scoped beans.

**Common Follow-up Questions:**
- *"What happens if an unhandled exception is thrown inside `@PostConstruct`?"* → The `ApplicationContext` aborts startup immediately (fail-fast behavior), preventing the application from serving requests in a corrupt state.
- *"Can a bean have multiple `@PostConstruct` methods?"* → While allowed, having multiple `@PostConstruct` methods in a single class is discouraged because the execution order between them is not guaranteed by the Jakarta specification.
- *"How do you handle background tasks that need retries during startup?"* → Implement `SmartLifecycle` with phase ordering instead of blocking `@PostConstruct`.

**Red Flags (DO NOT Say):**
- ❌ *"Field-injected dependencies are already available inside the constructor."* (They are `null` until the `populateBean` phase completes).
- ❌ *"@PreDestroy is called on prototype beans when they are garbage collected."* (Spring does not track prototype destruction; manual cleanup is mandatory).
- ❌ *"@Transactional works normally inside @PostConstruct."* (Dynamic proxies are generated after `@PostConstruct` finishes).
