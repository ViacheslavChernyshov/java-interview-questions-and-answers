# What is Bean Lifecycle?

---

## 🟢 Junior Level

The **Bean Lifecycle** encompasses all sequential stages a Spring-managed bean undergoes from initial instantiation to final container destruction.

```
  1. Instantiation     ──> Invokes Class Constructor
          │
          ▼
  2. Population        ──> Injects Dependencies (@Autowired)
          │
          ▼
  3. Initialization    ──> Executes `@PostConstruct` & Custom Init Hooks
          │
          ▼
  4. Ready for Use     ──> Servicing Business Logic in Application
          │
          ▼
  5. Destruction       ──> Executes `@PreDestroy` & Cleanup Callbacks
```

```java
import jakarta.annotation.PostConstruct; // Spring Boot 3+ (Jakarta standard)
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Service;

@Service
public class CacheWarmupService {

    public CacheWarmupService() {
        // Step 1: Instantiation
    }

    @PostConstruct
    public void init() {
        // Step 3: Initialization - executed after dependencies are wired
    }

    @PreDestroy
    public void cleanup() {
        // Step 5: Destruction - executed during ApplicationContext shutdown
    }
}
```

## 🟡 Middle Level

### Singleton vs. Prototype Lifecycle Invariant

| Lifecycle Stage | `singleton` Scope | `prototype` Scope |
|---|---|---|
| **Instantiation** | Once at context startup (Eager) | On every `getBean()` / injection |
| **Dependency Population** | Executed once by Spring | Executed on every new instance |
| **Initialization (`@PostConstruct`)** | Executed once | Executed on every new instance |
| **Destruction (`@PreDestroy`)** | **Executed on context shutdown** | **❌ NEVER EXECUTED BY SPRING!** |

> [!CAUTION]
> **Prototype Resource Leak Hazard:** Spring **does not track the lifecycle of prototype beans after handing them to the caller**. If a prototype bean opens network sockets, database connections, or file handles, you must invoke cleanup methods manually.

## 🔴 Senior Level

### The `@PostConstruct` Transaction Trap

A frequent production bug occurs when developers attempt to execute `@Transactional` database operations inside `@PostConstruct`:

```java
@Service
public class BootstrapDataService {

    @Autowired private UserRepository userRepository;

    @PostConstruct
    @Transactional // ❌ BUG: Transaction does NOT open!
    public void seedInitialAdmin() {
        userRepository.save(new User("admin", "secret"));
    }
}
```

#### Why it Fails:
AOP Dynamic Proxies (which handle `@Transactional`) are constructed inside **`BeanPostProcessor.postProcessAfterInitialization()`**, which occurs **after** `@PostConstruct` completes. Inside `@PostConstruct`, the call runs on the raw unproxied instance.

#### The Solution: `@EventListener(ContextRefreshedEvent.class)`
```java
@Component
public class BootstrapDataService {

    @Autowired private UserRepository userRepository;

    @EventListener(ContextRefreshedEvent.class) // ✅ Runs after ALL proxies are fully initialized!
    @Transactional
    public void seedInitialAdmin() {
        userRepository.save(new User("admin", "secret"));
    }
}
```

### The 3-Level Singleton Cache Architecture

To resolve circular dependencies during field/setter injection, `DefaultSingletonBeanRegistry` uses three internal caching tiers:

```
  Level 1 Cache: `singletonObjects` (ConcurrentHashMap<String, Object>)
  -> Stores fully constructed, wired, and initialized singleton beans.

  Level 2 Cache: `earlySingletonObjects` (HashMap<String, Object>)
  -> Stores early, raw bean instances (or early AOP proxy wrappers) exposed before initialization.

  Level 3 Cache: `singletonFactories` (HashMap<String, ObjectFactory<?>>)
  -> Stores lambdas producing early references, preventing premature proxy creation unless circularity is detected.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Phases:** Instantiation $\to$ Property Population $\to$ Initialization $\to$ Usage $\to$ Destruction.
- **Jakarta Transition:** Spring Boot 3+ / Spring 6+ uses `jakarta.annotation.PostConstruct` and `jakarta.annotation.PreDestroy` (not `javax.*`).
- **Prototype Destruction Invariant:** Spring never executes `@PreDestroy` on prototype beans; clients must manage their cleanup.
- **`@PostConstruct` & Proxies:** AOP proxies are created *after* `@PostConstruct`. Calling `@Transactional` methods from `@PostConstruct` will bypass the transaction manager.
- **Boot Event Alternative:** Use `@EventListener(ContextRefreshedEvent.class)` or `SmartLifecycle` for transactional bootstrap logic.
- **3-Level Cache:** Circular dependencies are resolved via `singletonObjects`, `earlySingletonObjects`, and `singletonFactories`.

**Common Follow-up Questions:**
- *"Why does `@PreDestroy` not execute for prototype scoped beans?"* → Because prototype beans are designed for short-lived client use; retaining references to them to manage destruction would create severe memory leaks in the container.
- *"What is the difference between `BeanFactoryPostProcessor` and `BeanPostProcessor`?"* → `BeanFactoryPostProcessor` operates on `BeanDefinition` metadata before any bean is instantiated; `BeanPostProcessor` operates on actual Java bean instances before and after initialization.
- *"How does `SmartLifecycle` differ from standard bean lifecycle?"* → `SmartLifecycle` allows defining start/stop phases (`getPhase()`) for clustered components, background worker loops, and network listeners after the entire container is fully loaded.

**Red Flags (DO NOT Say):**
- ❌ *"Spring automatically closes and cleans up resources inside prototype beans when they are garbage collected."* (Spring never calls destruction hooks on prototypes; manual cleanup is required).
- ❌ *"You can run transactional database migrations inside @PostConstruct."* (Proxies are not yet active during `@PostConstruct`; use `ContextRefreshedEvent` or Flyway/Liquibase).
- ❌ *"Bean instantiation and bean initialization are identical steps."* (Instantiation creates the raw Java object; initialization runs after dependencies are injected).
