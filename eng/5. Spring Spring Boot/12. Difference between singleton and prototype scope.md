# Difference between singleton and prototype scope

---

## 🟢 Junior Level

`singleton` and `prototype` are the two fundamental, non-web scopes in the Spring Framework.

### Core Differences at a Glance

| Feature | `singleton` Scope | `prototype` Scope |
|---|---|---|
| **Instance Count** | **Exactly 1 instance** per `ApplicationContext` | **New instance** created on every injection or request |
| **Creation Time** | Eagerly instantiated at container startup | Lazily instantiated on-demand |
| **Caching** | Stored permanently in Spring's Singleton Cache | **Not cached** by the container |
| **Statefulness** | Must be **Stateless** (Thread-safe) | Can be **Stateful** |
| **`@PreDestroy`** | **Invoked** on context shutdown | **❌ NEVER INVOKED BY SPRING** |

```java
// 1. Singleton Scope (Default):
@Service
public class OrderService {
    // Single shared instance across all worker threads
}

// 2. Prototype Scope:
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class DataExportTask {
    // Independent object allocated on each request
}
```

## 🟡 Middle Level

### The Prototype-in-Singleton Injection Hazard

```java
@Service // Singleton Bean (Instantiated once at startup)
public class NotificationService {

    @Autowired
    private EmailBuilder emailBuilder; // Prototype Bean!

    public void sendEmail(String recipient) {
        // ❌ BUG: `emailBuilder` was injected ONCE at startup.
        // It is reused across all invocations, behaving like a singleton!
        emailBuilder.build(recipient);
    }
}
```

### 3 Production Solutions

#### Option 1: `ObjectProvider<T>` (Recommended & Explicit)
```java
@Service
public class NotificationService {
    @Autowired private ObjectProvider<EmailBuilder> emailBuilderProvider;

    public void sendEmail(String recipient) {
        EmailBuilder freshBuilder = emailBuilderProvider.getObject(); // Fresh prototype instance!
        freshBuilder.build(recipient);
    }
}
```

#### Option 2: `@Lookup` Method Injection (Clean Annotation)
```java
@Service
public abstract class NotificationService {
    public void sendEmail(String recipient) {
        EmailBuilder freshBuilder = getEmailBuilder(); // Spring overrides this method via CGLIB!
        freshBuilder.build(recipient);
    }

    @Lookup
    protected abstract EmailBuilder getEmailBuilder();
}
```

#### Option 3: Scoped Proxy (`ScopedProxyMode.TARGET_CLASS`)
```java
@Component
@Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class EmailBuilder { ... }
```

## 🔴 Senior Level

### Circular Dependency Asymmetry

```
  Singleton Circular Dependency:
  [Bean A] <──────> [Bean B]
  -> Resolved safely via Level 3 `singletonFactories` cache!

  Prototype Circular Dependency:
  [Proto A] <─────> [Proto B]
  -> Triggers infinite recursive allocation loop!
  -> Container startup immediately crashes with `BeanCurrentlyInCreationException`.
```

### GC Allocation Pressure & Resource Leaks

```
  Prototype Scope Allocation Lifecycle:
  getBean() ──> Instantiation ──> BPP before ──> @PostConstruct ──> Handed to caller
                                                                           │
  Caller finishes work ────────────────────────────────────────────────────┘
  -> Spring DROPS all references immediately!
  -> If the prototype holds open JDBC connections/Sockets, @PreDestroy is NEVER called.
  -> Triggers severe database connection pool exhaustion!
```

> [!TIP]
> **Performance Guideline:** If you need an unmanaged, short-lived helper object without Spring `@Autowired` dependencies, use plain Java **`new MyHelper()`**. Requesting prototype beans through Spring incurs reflection and `BeanPostProcessor` execution overhead on every call.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Singleton:** 1 instance per container, cached in `DefaultSingletonBeanRegistry`, shared across all threads (must be stateless), full lifecycle with `@PreDestroy`.
- **Prototype:** New instance on every call, container drops tracking after initialization, `@PreDestroy` is **never** executed.
- **Prototype-in-Singleton Fixes:** Use `ObjectProvider<T>`, `@Lookup`, or `proxyMode = ScopedProxyMode.TARGET_CLASS`.
- **Circular Dependencies:** Solved for Singletons (3-level cache); impossible for Prototypes (throws `BeanCurrentlyInCreationException`).
- **Resource Management:** Prototype beans holding sockets or file handles must be cleaned up manually via `try-finally`.

**Common Follow-up Questions:**
- *"Why does Spring not call `@PreDestroy` on prototype beans?"* → Retaining references to every prototype instance to manage their destruction would cause severe memory leaks in the container.
- *"How does `@Lookup` work under the hood?"* → Spring dynamically subclasses the containing class using CGLIB and overrides the abstract `@Lookup` method to execute `context.getBean(TargetClass.class)`.
- *"When should you choose `new` over a Spring Prototype bean?"* → Use `new` if the object requires no dependency injection, lifecycle hooks, or aspect proxies.

**Red Flags (DO NOT Say):**
- ❌ *"Prototype beans are destroyed automatically by Spring when the method returns."* (Spring does not track prototype destruction).
- ❌ *"Injecting a prototype bean into a singleton automatically produces a new instance on every method call."* (It is injected once at startup and remains frozen).
- ❌ *"Prototype circular dependencies are resolved using the 3-level cache."* (The 3-level cache only works for singleton beans).
