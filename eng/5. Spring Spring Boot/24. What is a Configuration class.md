# What is a Configuration class?

---

## 🟢 Junior Level

A **`@Configuration` class** is a Spring configuration component containing one or more **`@Bean` methods** that programmatically instantiate, configure, and register objects into the Spring IoC container.

```java
@Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        // Registers BCryptPasswordEncoder as a Spring Bean:
        return new BCryptPasswordEncoder();
    }
}
```

### When to Use `@Configuration` with `@Bean`
- For **third-party libraries** (e.g. AWS S3 Client, Jackson `ObjectMapper`, Redis Client) where you cannot add `@Component` directly to source code.
- For **complex conditional instantiation logic** requiring dynamic configuration properties.

## 🟡 Middle Level

### Full Mode vs. Lite Mode (`proxyBeanMethods`)

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                 Full Configuration Mode                │                 Lite Configuration Mode                │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • `@Configuration(proxyBeanMethods = true)` (Default)  │ • `@Configuration(proxyBeanMethods = false)`           │
  │                                                        │   or `@Bean` methods inside `@Component` classes       │
  │ • Class is enhanced with a **CGLIB dynamic subclass**  │ • Class is instantiated as a standard POJO             │
  │ • Inter-bean `@Bean` method calls are intercepted to   │ • Inter-bean `@Bean` method calls execute **direct new │
  │   enforce **singleton caching**                        │   Java calls**, creating redundant duplicate instances │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// FULL MODE (Default):
@Configuration
public class FullConfig {
    @Bean public DatabaseClient db() { return new DatabaseClient(); }

    @Bean public UserService userService() {
        return new UserService(db()); // Intercepted by CGLIB -> Returns cached Singleton `db`!
    }

    @Bean public OrderService orderService() {
        return new OrderService(db()); // Intercepted by CGLIB -> Returns the SAME `db` instance!
    }
}
```

### Preferred Modern Pattern: Parameter Injection

Rather than relying on CGLIB method interception, the standard best practice is to pass dependencies as **`@Bean` method parameters**:

```java
@Configuration(proxyBeanMethods = false) // ✅ Safe, fast Lite Mode!
public class ModernAppConfig {

    @Bean
    public DatabaseClient db() { return new DatabaseClient(); }

    @Bean
    public UserService userService(DatabaseClient db) { // Spring automatically injects the singleton bean
        return new UserService(db);
    }
}
```

## 🔴 Senior Level

### Under the Hood: CGLIB Method Interception

```java
// Conceptual CGLIB Subclass generated by Spring:
public class FullConfig$$EnhancerBySpringCGLIB extends FullConfig {
    private BeanFactory beanFactory;

    @Override
    public DatabaseClient db() {
        if (beanFactory.containsSingleton("db")) {
            return (DatabaseClient) beanFactory.getSingleton("db");
        }
        DatabaseClient client = super.db();
        beanFactory.registerSingleton("db", client);
        return client;
    }
}
```

> [!CAUTION]
> **The `final` Modifier Hazard:** Because Full Mode relies on CGLIB subclassing, `@Configuration` classes and `@Bean` methods **cannot be declared as `final`**. Doing so causes Spring startup to fail with an `InvalidConfigurationException`.

### GraalVM Native Image & AOT Benefits
Disabling CGLIB proxies (`proxyBeanMethods = false`) avoids runtime bytecode generation and allows Ahead-Of-Time (AOT) compilers in Spring Boot 3 to generate fast, deterministic reflection-free code.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Source of bean definitions configured programmatically via `@Bean` methods.
- **Full Mode (`proxyBeanMethods = true`):** Generates CGLIB subclass to intercept inter-bean method calls and enforce singleton semantics.
- **Lite Mode (`proxyBeanMethods = false`):** Direct Java method invocation; zero CGLIB overhead.
- **Best Practice:** Pass dependencies as `@Bean` method parameters and configure `proxyBeanMethods = false`.
- **CGLIB Restriction:** `@Configuration` classes and methods cannot be marked `final`.
- **AOT / Native Image:** Lite mode accelerates startup and is native-image friendly.

**Common Follow-up Questions:**
- *"What happens if `@Bean` methods call each other inside a `@Component` class?"* → `@Component` operates in Lite Mode; calling another `@Bean` method directly executes a standard Java constructor call, creating a duplicate unmanaged instance rather than retrieving the singleton bean.
- *"Why should you not declare `@Configuration` classes as `final`?"* → CGLIB cannot create a runtime subclass of a `final` class.
- *"How does Spring process `@Configuration` classes internally?"* → `ConfigurationClassPostProcessor` (a `BeanFactoryPostProcessor`) parses the class, processes imports, and registers `BeanDefinition`s during context refresh.

**Red Flags (DO NOT Say):**
- ❌ *"A @Bean method inside a regular @Component behaves identically to one inside a @Configuration class."* (`@Component` runs in Lite mode without CGLIB singleton interception).
- ❌ *"Declaring proxyBeanMethods = false is always unsafe."* (It is completely safe as long as dependencies are injected via method parameters).
- ❌ *"You should use @Configuration to declare every domain service in your application."* (Use stereotype annotations like `@Service` and `@Repository` for application code; reserve `@Configuration` for infrastructure and 3rd-party beans).
