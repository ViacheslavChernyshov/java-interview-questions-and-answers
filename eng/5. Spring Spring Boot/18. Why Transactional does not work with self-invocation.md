# Why Transactional does not work with self-invocation

---

## 🟢 Junior Level

**Self-Invocation** occurs when a method inside a Spring bean calls another method **within the same class** (an internal `this.method()` call).

```java
@Service
public class OrderService {

    public void processOrder(Order order) {
        // ❌ SELF-INVOCATION: @Transactional on saveInternal() WILL NOT WORK!
        saveInternal(order);
    }

    @Transactional
    public void saveInternal(Order order) {
        orderRepository.save(order); // Executes WITHOUT an active transaction!
    }
}
```

### Why it Fails
Spring AOP works by wrapping your bean in a **Dynamic Proxy**.
- When `processOrder()` calls `saveInternal()`, the call is executed internally via **`this.saveInternal()`**, directly accessing the raw target object and **completely bypassing the outer Spring Proxy!**

---

## 🟡 Middle Level

### The Proxy Invocation Flow

```
  External Client Call:
  [Caller] ──> [Spring Dynamic Proxy] ──> [TransactionInterceptor] ──> [Target.processOrder()]
                                                                                 │
  Internal Self-Invocation:                                                     │
                                                                                 ▼
                                 [Target.saveInternal()] <── (Direct `this.saveInternal()`)
                                 (⭐ Completely Bypasses the Proxy & TransactionInterceptor!)
```

### All AOP Annotations Broken by Self-Invocation

Self-invocation disables **every declarative AOP feature** in Spring:
- **`@Transactional`:** Fails to open a transaction or change propagation (`REQUIRES_NEW` is ignored).
- **`@Async`:** Fails to offload to a thread pool; executes **synchronously on the caller thread**.
- **`@Cacheable` / `@CacheEvict`:** Bypasses cache lookups; executes the method directly every time.
- **`@PreAuthorize` / `@Secured`:** Bypasses security checks entirely.
- **`@Retryable`:** Fails to retry on exceptions.

## 🔴 Senior Level

### Why CGLIB Subclassing Does NOT Fix Self-Invocation

A frequent interview misconception is believing CGLIB subclassing solves self-invocation:

```java
// Conceptual CGLIB Generated Subclass:
public class OrderService$$EnhancerBySpringCGLIB extends OrderService {
    private MethodInterceptor interceptor;

    @Override
    public void processOrder(Order order) {
        // Intercepts external call
        interceptor.intercept(this, ..., () -> super.processOrder(order));
    }

    @Override
    public void saveInternal(Order order) {
        interceptor.intercept(this, ..., () -> super.saveInternal(order));
    }
}
```
- When `super.processOrder(order)` runs inside the target class, executing `saveInternal(order)` resolves to **`this.saveInternal(order)`** in the base class.
- Because `this` is bound to the target object instance, the call does **not** route back through the CGLIB subclass override.

### Diagnosing Self-Invocation at Runtime

You can verify whether a transaction is physically active using Spring's **`TransactionSynchronizationManager`**:

```java
@Transactional
public void saveInternal(Order order) {
    boolean isTxActive = TransactionSynchronizationManager.isActualTransactionActive();
    System.out.println("Transaction Active: " + isTxActive); 
    // Prints `false` if called via self-invocation!
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Calling a method in the same class via `this.method()` instead of through an injected proxy reference.
- **Root Cause:** Spring AOP is proxy-based. Internal `this` calls execute inside the target instance, bypassing the `TransactionInterceptor`.
- **Broad Impact:** Breaks `@Transactional`, `@Async`, `@Cacheable`, `@PreAuthorize`, and `@Retryable`.
- **CGLIB Myth:** CGLIB subclassing does NOT fix self-invocation because `this` inside the superclass points to the target object.
- **Diagnostic Tool:** Check `TransactionSynchronizationManager.isActualTransactionActive()`.

**Common Follow-up Questions:**
- *"What happens if a non-transactional `outer()` method calls a `@Transactional(propagation = REQUIRES_NEW)` method in the same class?"* → Self-invocation bypasses the proxy; no transaction is started, and `REQUIRES_NEW` is completely ignored.
- *"Does AspectJ suffer from the self-invocation problem?"* → No. AspectJ weaves bytecode directly into class files (Compile-Time or Load-Time Weaving), intercepting method executions directly inside the class without relying on dynamic proxies.
- *"What is the cleanest architectural solution for self-invocation?"* → Extracting the transactional/async method into a separate `@Service` bean (following Single Responsibility Principle).

**Red Flags (DO NOT Say):**
- ❌ *"CGLIB proxies fix the self-invocation problem in modern Spring Boot."* (Both JDK and CGLIB proxies fail on self-invocation).
- ❌ *"Declaring the internal method as public enables self-invocation proxying."* (Method visibility does not matter; calling via `this` always bypasses the proxy).
- ❌ *"Putting @Transactional on the class fixes self-invocation within that class."* (Class-level annotations only apply to calls arriving through the proxy from outside).
