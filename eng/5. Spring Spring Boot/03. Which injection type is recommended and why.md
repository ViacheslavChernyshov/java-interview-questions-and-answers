# Which injection type is recommended and why?

---

## 🟢 Junior Level

**Constructor Injection is the official industry and Spring Team standard** for all required dependencies.

```java
// ✅ Recommended Production Standard:
@Service
@RequiredArgsConstructor
public class PaymentProcessingService {
    private final PaymentGateway paymentGateway;
    private final AccountRepository accountRepository;
    private final AuditLogger auditLogger;
}
```

### The 3 Core Reasons
1. **Immutability:** Dependencies are declared `final` and cannot be modified after construction.
2. **Fail-Fast Safety:** Missing dependencies trigger a startup crash rather than a runtime `NullPointerException`.
3. **Pure POJO Testing:** You can test the class with `new Service(mockRepo)` without loading Spring test contexts.

---

## 🟡 Middle Level

### The 4 Architectural Pillars of Constructor Injection

```
  ┌─────────────────────────────────────────────────────────────────────────────────────────┐
  │ 1. Immutability (final Fields)                                                          │
  │    Guarantees thread safety and prevents accidental reassignment during runtime.       │
  ├─────────────────────────────────────────────────────────────────────────────────────────┤
  │ 2. Fail-Fast Startup Validation                                                         │
  │    Spring prevents incomplete object instantiation. Missing beans crash at boot time.   │
  ├─────────────────────────────────────────────────────────────────────────────────────────┤
  │ 3. 100% Decoupled Unit Testing                                                          │
  │    Zero reflection needed; test suites execute in microseconds without Spring runner.   │
  ├─────────────────────────────────────────────────────────────────────────────────────────┤
  │ 4. Single Responsibility Principle (SRP) Enforcer                                       │
  │    Constructor parameters make code smells and class bloat immediately visible (>5 args).│
  └─────────────────────────────────────────────────────────────────────────────────────────┘
```

### Constructor Resolution Rules in Spring

When Spring instantiates a bean:
1. **Single Constructor:** Automatically selected without needing `@Autowired` (Spring 4.3+ / 6.x+).
2. **Multiple Constructors:** Spring searches for an explicit `@Autowired` constructor. If none is found, it falls back to the default no-arg constructor; if absent, startup fails.

## 🔴 Senior Level

### Resolving Circular Dependencies

```
  Circular Dependency Scenario:
  [Service A] ──(Constructor Dependency)──> [Service B]
       ▲                                         │
       └────────(Constructor Dependency)─────────┘
```

When two beans require each other via Constructor Injection, Spring cannot construct either instance and throws `BeanCurrentlyInCreationException`.

#### Production Remediation Options:
1. **Architectural Refactoring (Recommended):** Extract the overlapping responsibilities into a new shared component `ServiceC`, or decouple the services using Spring's **`ApplicationEventPublisher`** (Event-Driven architecture).
2. **`@Lazy` Proxy Injection (Temporary Workaround):**
   ```java
   @Service
   public class ServiceA {
       private final ServiceB serviceB;
       public ServiceA(@Lazy ServiceB serviceB) {
           this.serviceB = serviceB; // Injects a CGLIB/JDK dynamic proxy stub
       }
   }
   ```
   *Mechanics:* Spring injects a dynamic proxy placeholder into `ServiceA`. When `serviceA.doWork()` first invokes a method on `serviceB`, the proxy resolves the real `ServiceB` singleton from the `ApplicationContext`.

### CGLIB Proxy Instantiation Warning

Because Spring Boot creates CGLIB subclasses for proxying (`@Transactional`, `@Async`), the superclass constructor is invoked during proxy generation.
- **Critical Rule:** Never perform heavy I/O, database queries, or external network calls inside a Spring Bean's constructor. Perform post-construction initializations inside **`@PostConstruct`** methods.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Primary Recommendation:** Constructor Injection for all mandatory dependencies.
- **Immutability:** Supports `private final` fields, guaranteeing thread-safe and unmodifiable references.
- **Fail-Fast Invariant:** Missing beans abort application startup with `NoSuchBeanDefinitionException`, eliminating production NPE risks.
- **Testability:** Allows direct POJO instantiation (`new OrderService(mockRepo)`) without requiring Mockito reflection or `@SpringBootTest`.
- **SRP Detection:** More than 4–5 constructor arguments immediately highlights an overloaded class that needs refactoring.
- **Circular Dependencies:** Constructor injection exposes cycles immediately at startup (unlike field injection which masks them).

**Common Follow-up Questions:**
- *"How does `@Lazy` resolve circular dependencies in constructor injection?"* → It instructs Spring to inject a lightweight dynamic proxy instead of the real bean, breaking the startup cycle. The actual bean is resolved from the context on the first method invocation.
- *"Why should you never write network initialization calls inside a bean constructor?"* → CGLIB proxy subclasses invoke the constructor during proxy generation, leading to duplicate network operations. Use `@PostConstruct` instead.
- *"When is Setter Injection preferred over Constructor Injection?"* → For truly optional dependencies (e.g. `@Autowired(required = false)`) or configuration properties that can be reloaded dynamically via JMX.

**Red Flags (DO NOT Say):**
- ❌ *"Field injection is better for small services because it looks cleaner."* (Constructor injection with Lombok `@RequiredArgsConstructor` is just as clean and far safer).
- ❌ *"Using @Lazy is the best long-term solution for circular dependencies."* (`@Lazy` is a temporary patch; circular dependencies indicate poor architectural design).
- ❌ *"Constructor injection is slower because Spring has to use reflection to inspect constructor arguments."* (The reflection overhead is negligible and occurs once at boot time).
