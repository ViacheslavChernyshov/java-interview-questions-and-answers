# What is deadlock?

---

## 🟢 Junior Level

A **Deadlock** occurs when two or more threads are permanently blocked because each holds a lock that the other needs, resulting in a **circular dependency**:

```
  The Deadlock Circle:
  Thread 1 ── holds ──► Lock A ── requested by ──► Thread 2
     ▲                                                │
     │                                                ▼
     └──────── requested by ── Lock B ◄─── holds ─────┘
```

```java
public class DeadlockDemo {
    private final Object lock1 = new Object();
    private final Object lock2 = new Object();

    // Thread 1 calls methodA():
    public void methodA() {
        synchronized(lock1) {
            sleep(100);
            synchronized(lock2) { // 💥 Blocked: Thread 2 holds lock2!
                doWork();
            }
        }
    }

    // Thread 2 calls methodB():
    public void methodB() {
        synchronized(lock2) {
            sleep(100);
            synchronized(lock1) { // 💥 Blocked: Thread 1 holds lock1!
                doWork();
            }
        }
    }
}
```

### Deadlock vs. Livelock vs. Starvation

```
  ┌──────────────────┬────────────────────────────────────────────────────┬────────────────────────────┐
  │ Failure Mode     │ Thread State & Behavior                            │ CPU Core Utilization       │
  ├──────────────────┼────────────────────────────────────────────────────┼────────────────────────────┤
  │ **Deadlock**     │ Threads enter **`BLOCKED`** / **`WAITING`** forever│ **0% CPU** (Dormant)       │
  │ **Livelock**     │ Threads continuously yield to each other in loops  │ **100% CPU** (Spinning)    │
  │ **Starvation**   │ Thread is ready but perpetually denied lock access │ Variable                   │
  └──────────────────┴────────────────────────────────────────────────────┴────────────────────────────┘
```

## 🟡 Middle Level

### The 4 Coffman Conditions (JMM Deadlock Prerequisites)

A deadlock can **ONLY** occur if all 4 conditions are satisfied simultaneously:

```
  ┌───┬──────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Condition                │ Architectural Contract                                                      │
  ├───┼──────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Mutual Exclusion**     │ Resources cannot be shared; held by one thread exclusively.                 │
  │ 2 │ **Hold and Wait**        │ A thread holding at least one resource waits to acquire additional resources.│
  │ 3 │ **No Preemption**        │ Locks cannot be forcibly taken from a holding thread.                       │
  │ 4 │ **Circular Wait**        │ A closed circular chain of threads where each waits for the next's lock.   │
  └───┴──────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

### Hidden Deadlock: Thread Pool Starvation

Deadlocks can occur without multiple lock objects via **Thread Pool Starvation**:

```java
// ❌ STARVATION DEADLOCK: Pool with 1 thread
ExecutorService singlePool = Executors.newSingleThreadExecutor();

singlePool.submit(() -> {
    // Parent task occupies the ONLY worker thread:
    Future<String> childFuture = singlePool.submit(() -> "Child Task Complete");
    
    // 💥 DEADLOCK! Parent blocks waiting on child, but child is queued waiting for worker!
    return childFuture.get(); 
});
```

## 🔴 Senior Level

### Diagnostic Analysis in Production

#### 1. Command-Line Thread Dumps (`jstack`)
```bash
jstack -l <pid>
```
```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x00007f (object 0x000000076af0c8d0), which is held by "Thread-2"
"Thread-2":
  waiting to lock monitor 0x00007f (object 0x000000076af0c8e0), which is held by "Thread-1"
```

#### 2. Programmatic Detection via `ThreadMXBean`
```java
ThreadMXBean mxBean = ManagementFactory.getThreadMXBean();
long[] deadlockedThreadIds = mxBean.findDeadlockedThreads(); // ⚠️ Expensive graph traversal!

if (deadlockedThreadIds != null) {
    ThreadInfo[] infos = mxBean.getThreadInfo(deadlockedThreadIds, true, true);
    for (ThreadInfo info : infos) {
        log.error("Deadlocked Thread: {} blocked on {}", info.getThreadName(), info.getLockName());
    }
}
```

### Core Prevention: Global Lock Ordering

Deadlocks are eliminated mathematically by breaking the **Circular Wait** condition through strict, global lock ordering:

```java
public void transferMoney(Account from, Account to, BigDecimal amount) {
    // 🚀 Order locks deterministically by account ID or identity hash:
    Account firstLock = from.getId() < to.getId() ? from : to;
    Account secondLock = from.getId() < to.getId() ? to : from;

    synchronized (firstLock) {
        synchronized (secondLock) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Two or more threads blocked permanently waiting on locks held by each other.
- **4 Coffman Conditions:** Mutual Exclusion, Hold & Wait, No Preemption, Circular Wait.
- **Deadlock vs Livelock:** Deadlock burns 0% CPU (`BLOCKED`); Livelock burns 100% CPU in active reaction loops.
- **Primary Prevention:** Global deterministic lock ordering (breaks Circular Wait) and `ReentrantLock.tryLock(timeout)`.
- **Diagnostics:** `jstack -l <pid>`, VisualVM, or `ThreadMXBean.findDeadlockedThreads()`.
- **Starvation Deadlock:** Parent tasks blocking on child tasks submitted to the same bounded thread pool.

**Common Follow-up Questions:**
- *"Does the JVM automatically resolve deadlocks like SQL database engines do?"* → No. Database engines detect circular waits and abort one transaction; the JVM detects deadlocks but cannot abort threads automatically.
- *"Why does `synchronized` carry higher deadlock risk than `ReentrantLock`?"* → `synchronized` blocks unconditionally and cannot be timed out or interrupted (`lockInterruptibly()`), whereas `ReentrantLock.tryLock(timeout)` allows backing off on contention.
- *"How does Static Class Initialization cause deadlocks?"* → If Class A's static initializer references Class B, and Class B's static initializer references Class A, concurrent class loading across two threads creates a circular lock in the ClassLoader.

**Red Flags (DO NOT Say):**
- ❌ *"Thread.interrupt() will instantly break a synchronized monitor deadlock."* (Monitors cannot be interrupted while in the BLOCKED state).
- ❌ *"Garbage collection will automatically unlock abandoned monitor locks."* (Held monitors remain locked until the owning thread explicitly unlocks or terminates).
- ❌ *"Livelock is the same as Deadlock."* (Livelock actively burns CPU in state-changing spin loops).
