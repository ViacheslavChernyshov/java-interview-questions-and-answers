# How to prevent deadlock?

---

## 🟢 Junior Level

Deadlock prevention relies on systematically eliminating at least one of the 4 Coffman conditions. In practice, the two most effective strategies are **Deterministic Lock Ordering** and **Timed Try-Locks**:

```
  ┌──────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ Prevention Strategy                  │ How It Breaks Coffman Conditions                                            │
  ├──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ **1. Global Lock Ordering**          │ **Breaks Circular Wait:** All threads acquire shared locks in identical    │
  │                                      │ ascending order (e.g. sorted by unique entity ID).                          │
  │ **2. `ReentrantLock.tryLock()`**     │ **Breaks Hold & Wait:** Releases earlier acquired locks if a subsequent    │
  │                                      │ lock cannot be obtained within a bounded timeout.                           │
  │ **3. Lock-Free Data Structures**     │ **Breaks Mutual Exclusion:** Replaces exclusive locks with hardware CAS.    │
  └──────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// Strategy 1: Deterministic Lock Ordering by Account ID
public void transferMoney(Account from, Account to, BigDecimal amount) {
    Account firstLock  = from.getId() < to.getId() ? from : to;
    Account secondLock = from.getId() < to.getId() ? to : from;

    synchronized(firstLock) {
        synchronized(secondLock) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
```

## 🟡 Middle Level

### Strategy 2: Bounded `tryLock()` with Exponential Back-off

```java
public boolean executeTransferWithTimeout(Account from, Account to, BigDecimal amount) 
        throws InterruptedException {
    long timeoutMs = 50;
    while (true) {
        if (from.getLock().tryLock(timeoutMs, TimeUnit.MILLISECONDS)) {
            try {
                if (to.getLock().tryLock(timeoutMs, TimeUnit.MILLISECONDS)) {
                    try {
                        from.debit(amount);
                        to.credit(amount);
                        return true; // Transfer completed successfully!
                    } finally {
                        to.getLock().unlock();
                    }
                }
            } finally {
                from.getLock().unlock(); // 🚀 Crucial: Relinquishes initial lock if target was busy!
            }
        }
        // Jittered back-off to prevent livelock collisions:
        Thread.sleep(ThreadLocalRandom.current().nextInt(10, 30));
    }
}
```

### The Golden Rule: Never Hold Locks Across Blocking I/O

```java
// ❌ DANGEROUS: Holding in-memory lock during external network / DB calls
synchronized(userLock) {
    restClient.postForObject("/payment-gateway", payload, Void.class); // 💥 500ms I/O latency!
    user.setPaid(true);
}

// ✅ SAFE: Execute I/O outside critical sections
PaymentResult result = restClient.postForObject("/payment-gateway", payload, PaymentResult.class);
synchronized(userLock) {
    user.setPaid(result.isSuccess()); // 0.001ms hold time!
}
```

## 🔴 Senior Level

### Lock Ordering vs. `tryLock()`: Architectural Decision Matrix

```
  ┌──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Workload Characteristic  │ Preferred Strategy       │ Architectural Rationale                          │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Known Fixed Entities** │ **Lock Ordering**        │ Zero performance overhead; mathematical immunity │
  │ **Dynamic Allocations**  │ **Timed `tryLock()`**    │ Adapts when entity ordering cannot be pre-sorted │
  │ **High Contention Web**  │ **Lock-Free / Sharded**  │ `ConcurrentHashMap`, `LongAdder`, actor models   │
  └──────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

### Static Analysis & Deadlock Linters

Modern CI/CD pipelines detect inverted lock acquisitions automatically before production deployments:
- **SonarQube Rule `S2143` / `S3067`:** Flags inconsistent ordering of nested `synchronized` blocks.
- **ThreadSanitizer (TSan):** OpenJDK dynamic race and lock order inversion detector (`-XX:+ThreadSanitizer`).

### Production Monitoring: Detecting Latency Spikes

```java
public class MonitoredLock {
    private final ReentrantLock lock = new ReentrantLock();

    public void executeCriticalSection(Runnable task) {
        long startTime = System.nanoTime();
        lock.lock();
        try {
            long waitDurationMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startTime);
            if (waitDurationMs > 500) {
                log.warn("High lock contention detected! Waited {} ms", waitDurationMs);
            }
            task.run();
        } finally {
            lock.unlock();
        }
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Principle:** Prevent deadlock by breaking any of the 4 Coffman conditions.
- **Lock Ordering:** Order lock acquisitions deterministically by unique identifier or `System.identityHashCode()`.
- **TryLock Pattern:** Always release the primary lock in a `finally` block if secondary locks cannot be acquired.
- **I/O Isolation:** Never invoke external HTTP APIs, database calls, or disk I/O while holding in-memory mutexes.
- **Lock-Free Concurrency:** Use `ConcurrentHashMap` and Atomic classes to eliminate mutual exclusion entirely.
- **Livelock Avoidance:** Add randomized back-off jitter to `tryLock()` retry loops.

**Common Follow-up Questions:**
- *"Why is lock ordering preferred over tryLock in high-throughput systems?"* → Because lock ordering has zero retry loop overhead and cannot cause CPU-wasting livelocks.
- *"What is a Tie-Breaker lock?"* → A static fallback lock acquired when two objects produce identical `System.identityHashCode()` values.
- *"Can Virtual Threads eliminate deadlocks in Java 21?"* → No. Virtual threads block on traditional monitor locks and `ReentrantLock` instances in the exact same manner as platform threads.

**Red Flags (DO NOT Say):**
- ❌ *"Using a single global synchronized lock on the entire application is a great production pattern."* (It destroys concurrency and turns a multi-threaded server into a single-threaded bottleneck).
- ❌ *"tryLock() without a back-off sleep is immune to concurrency issues."* (It can result in 100% CPU livelock where threads continuously acquire and drop locks without progressing).
- ❌ *"Deadlocks can be solved simply by increasing thread pool sizes."* (Adding more threads only increases the likelihood of lock contention).
