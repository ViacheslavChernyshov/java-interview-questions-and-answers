# How to avoid race condition?

---

## 🟢 Junior Level

Race conditions occur when multiple threads concurrently read and modify shared mutable state without synchronization. To eliminate race conditions, apply one of **4 core architectural strategies**:

```
  ┌──────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ Architectural Strategy               │ Core Mechanism & Java Implementation                                        │
  ├──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ **1. Mutual Exclusion (Locks)**      │ **Pessimistic:** `synchronized` or `ReentrantLock` enforce exclusive access.│
  │ **2. Lock-Free Atomics (CAS)**       │ **Optimistic:** `AtomicInteger`, `AtomicReference`, `LongAdder`.            │
  │ **3. Immutability**                  │ **Zero Mutation:** Java `record`s and `final` fields (Thread-safe by design)│
  │ **4. Thread Confinement**            │ **Zero Sharing:** Local stack variables and `ThreadLocal<T>`.               │
  └──────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// 1. Lock-Free Atomicity
public class SafeCounter {
    private final AtomicInteger count = new AtomicInteger(0);
    public void increment() { count.incrementAndGet(); } // Lock-free atomic increment
}

// 2. Immutability via Java Records
public record UserProfile(String username, String email) {
    // Immutable: State cannot be corrupted after construction!
}
```

## 🟡 Middle Level

### Strategy Comparison & Workload Suitability

```
  ┌──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Approach                 │ Key Strengths            │ Primary Trade-Offs                               │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **`synchronized`**       │ Atomic across 2+ fields  │ Thread contention causes OS context switches     │
  │ **Atomic Classes**       │ Fast (~5 ns), lock-free  │ Protects single variables only                   │
  │ **Immutability**         │ Scales infinitely across │ Memory allocation churn on frequent copy-updates │
  │ **`ThreadLocal`**        │ Zero lock contention     │ Memory leak risk in pooled worker threads        │
  └──────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

### The 4 Safe Publication Rules

Publishing an object reference to another thread without a memory barrier can expose partially constructed object state. Safe publication requires:

```java
// 1. Static Initializer (Guaranteed by JVM ClassLoader):
public static final AppConfig CONFIG = new AppConfig();

// 2. Final Fields (Guaranteed by JMM Freeze Action):
public class SecurityToken {
    private final String secret; // Safe publication without locks!
    public SecurityToken(String secret) { this.secret = secret; }
}

// 3. Volatile Reference Publishing:
private volatile ConnectionPool pool;
public void init() { pool = new ConnectionPool(); } // Flushes store buffer

// 4. Intrinsic Monitor Locking:
synchronized(lock) { sharedData = new Payload(); }
```

## 🔴 Senior Level

### Concurrent Collections: Internal Locking Evolution

```java
// ❌ VULNERABLE: Check-then-act race condition
if (!map.containsKey(key)) {
    map.put(key, computeValue(key)); // Window of vulnerability!
}

// ✅ ATOMIC: Atomic composite method on ConcurrentHashMap
map.computeIfAbsent(key, k -> computeValue(k));
```

```
  ConcurrentHashMap Internal Architecture (Java 8+):
  • get():       Lock-free (Direct volatile node traversal)
  • put():       CAS for empty bucket node; synchronized lock ONLY on the specific bucket head
  • resize():    Concurrent multi-threaded table transfer
```

### Thread Confinement: Stack vs. ThreadLocal

```java
// 1. Stack Confinement: Data never escapes local execution frame (100% thread-safe)
public int calculateTotal(List<Integer> numbers) {
    int localSum = 0; // Exists only in thread's private stack frame
    for (int n : numbers) localSum += n;
    return localSum;
}

// 2. ThreadLocal Confinement (Request Context):
public class RequestScope {
    private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

    public static void runInContext(UserContext user, Runnable task) {
        try {
            CTX.set(user);
            task.run();
        } finally {
            CTX.remove(); // 🚀 Crucial: Prevents thread pool cross-contamination
        }
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **4 Remedies:** Synchronized Mutexes, Lock-Free Atomics, Immutable Records, and Thread Confinement.
- **Atomic Compound Methods:** Use `map.computeIfAbsent()` / `map.putIfAbsent()` instead of `if (!map.containsKey()) map.put()`.
- **Safe Publication:** Static init, `final` fields (JMM Freeze), `volatile` pointers, or `synchronized` locks.
- **Stack Confinement:** Local primitive and object references inside method stacks are isolated per thread and cannot race.
- **`ThreadLocal` Cleanup:** Always remove `ThreadLocal` in a `finally` block when using thread pools.

**Common Follow-up Questions:**
- *"Why is `CopyOnWriteArrayList` inefficient for write-heavy workloads?"* → Because every mutation (`add`, `set`, `remove`) clones the entire backing array ($O(N)$ allocation penalty), making it suitable only for read-mostly scenarios like observer registries.
- *"How does `ConcurrentHashMap` achieve high write throughput?"* → By locking only the single bucket head node undergoing mutation, allowing concurrent writes to other hash buckets simultaneously.
- *"Why are Java `record`s inherently thread-safe?"* → Because all fields are declared `private final`, ensuring immutability and safe publication via JMM constructor freeze semantics.

**Red Flags (DO NOT Say):**
- ❌ *"Declaring a collection volatile makes its internal elements thread-safe."* (`volatile` only protects the reference pointer itself, not the list/map operations).
- ❌ *"ConcurrentHashMap locks the entire map during writes."* (It locks only the specific bucket undergoing mutation).
- ❌ *"ThreadLocal variables are automatically cleaned up when a task completes."* (Threads in a pool persist indefinitely; uncleaned `ThreadLocal` instances cause severe memory leaks).
