# What is race condition?

---

## 🟢 Junior Level

A **Race Condition** is a concurrency flaw that occurs when the correctness of a program depends on the **unpredictable timing or interleaving of concurrent threads**:

Unlike a Deadlock (which causes total system hang and is immediately visible), a Race Condition produces **silent data corruption** while the application continues to run without throwing exceptions:

```
  ┌──────────────────────────┬────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Characteristic           │ Race Condition                                         │ Deadlock                                               │
  ├──────────────────────────┼────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **Root Cause**           │ **Insufficient synchronization**                      │ **Excessive / Inverted lock synchronization**          │
  │ **Visible Symptom**      │ **Silent data corruption** (Incorrect calculations)    │ **Complete system freeze** (0% CPU utilization)        │
  │ **Reproducibility**      │ Non-deterministic (Timing and core count dependent)    │ Deterministic when circular lock graph is hit          │
  └──────────────────────────┴────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
public class UnsafeCounter {
    private int count = 0;

    public void increment() {
        count++; // ❌ NOT ATOMIC: 3 distinct CPU instructions
    }
}
```

```
  Thread Interleaving (Lost Update Anomaly):
  Thread 1: Read count (0) ──► Increment (1) ───────────────────────► Write count = 1
  Thread 2: ──────► Read count (0) ──► Increment (1) ──► Write count = 1 ──┘
  Result: count = 1 (Expected: 2!)
```

## 🟡 Middle Level

### The 3 Core Archetypes of Race Conditions

```
  ┌───┬──────────────────────────────┬─────────────────────────────────────────────────┬───────────────────────────────────────────────┐
  │ # │ Archetype                    │ Vulnerable Pattern                              │ Thread-Safe Solution                          │
  ├───┼──────────────────────────────┼─────────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ 1 │ **Read-Modify-Write**        │ `count++`                                       │ `AtomicInteger.incrementAndGet()`             │
  │ 2 │ **Check-Then-Act**           │ `if (!map.containsKey(k)) map.put(k, v);`       │ `map.putIfAbsent(k, v)` or `computeIfAbsent()`│
  │ 3 │ **Lazy-Initialization Race**│ Non-volatile Double-Checked Locking (DCL)       │ `volatile` instance field + class initializers│
  └───┴──────────────────────────────┴─────────────────────────────────────────────────┴───────────────────────────────────────────────┘
```

### The `volatile` Fallacy

> [!WARNING]
> Marking a variable **`volatile` does NOT fix race conditions** on compound operations:
> ```java
> private volatile int count = 0;
> public void increment() {
>     count++; // 💥 STILL BROKEN!
> }
> ```
> While `volatile` ensures every thread reads the freshest value from memory (Visibility), it provides **zero atomicity** for the multi-step `read -> modify -> write` sequence.

## 🔴 Senior Level

### Hardware Architecture Hazards: x86 vs. ARM / Graviton

Race conditions are notoriously difficult **Heisenbugs**:
- **x86 / x86-64 (Total Store Order - TSO):** Strong memory model; hardware prohibits Store-Store and Load-Load reorderings, frequently masking latent race conditions during local laptop testing.
- **ARM (Apple Silicon / AWS Graviton - Weak Memory Model):** Allows aggressive CPU out-of-order execution and instruction reordering. Code with missing memory barriers that passes all tests on x86 will **fail catastrophically on ARM Graviton cloud servers**.

### Verification via JCStress (Java Concurrency Stress Framework)

Unit tests cannot reliably assert thread interleavings. Production libraries verify race conditions using **OpenJDK JCStress**:

```java
@JCStressTest
@Outcome(id = "1", expect = Expect.ACCEPTABLE_INTERESTING, desc = "💥 Lost update detected!")
@Outcome(id = "2", expect = Expect.ACCEPTABLE,             desc = "✅ Correct atomic execution")
public class RaceConditionStressTest {
    int counter = 0;

    @Actor
    public void thread1() { counter++; }

    @Actor
    public void thread2() { counter++; }

    @Arbiter
    public void arbiter(I_Result r) {
        r.r1 = counter; // If r1 == 1, JCStress flags a data race violation
    }
}
```

### Deterministic Multi-Threaded Unit Testing

```java
@Test
void testConcurrentIncrement() throws InterruptedException {
    int threadCount = 32;
    CountDownLatch startGun = new CountDownLatch(1);
    CountDownLatch doneLatch = new CountDownLatch(threadCount);
    UnsafeCounter counter = new UnsafeCounter();

    for (int i = 0; i < threadCount; i++) {
        Thread.ofPlatform().start(() -> {
            try {
                startGun.await(); // 🚀 Synchronizes all 32 threads to fire simultaneously
                for (int j = 0; j < 1000; j++) counter.increment();
            } catch (InterruptedException ignored) {
            } finally {
                doneLatch.countDown();
            }
        });
    }

    startGun.countDown(); // BANG! All threads hit the counter simultaneously
    doneLatch.await();
    // Exposes race conditions consistently on multi-core systems:
    assertThat(counter.getCount()).isLessThan(32_000); 
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Concurrency flaw where system correctness depends on the non-deterministic scheduling and interleaving of threads.
- **3 Archetypes:** Read-Modify-Write (`count++`), Check-Then-Act (`if (!map.containsKey)`), Lazy-Initialization (DCL).
- **`volatile` Limitation:** `volatile` guarantees visibility, but does not provide atomicity for compound operations.
- **Race Condition vs Deadlock:** Race condition is missing synchronization (silent wrong answers); deadlock is broken lock ordering (system freeze).
- **Hardware Architecture:** Weak memory architectures (ARM / Graviton) expose races that stay hidden on x86.
- **Testing:** Use OpenJDK JCStress or `CountDownLatch` simultaneous-trigger harnesses.

**Common Follow-up Questions:**
- *"Why is `map.putIfAbsent()` superior to `if (!map.containsKey()) map.put()`?"* → Because `putIfAbsent()` executes the check and the insertion atomically inside the concurrent map's segment/bucket lock, eliminating the window for another thread to insert between the check and the act.
- *"What is a Benign Race Condition?"* → A deliberate race condition where approximate values are acceptable (such as high-volume metric telemetry or lossy statistical counters) to prioritize maximum throughput over exact precision.
- *"How does the CPU instruction pipeline cause race conditions?"* → Out-of-order execution, Store Buffers, and concurrent cache-line modifications lead to interleaved execution sequences.

**Red Flags (DO NOT Say):**
- ❌ *"Declaring a variable volatile makes `count++` thread-safe."* (`count++` is 3 instructions; volatile only ensures memory visibility).
- ❌ *"Race condition means two threads are deadlocked."* (Deadlock is permanent blocking; race condition is incorrect computation).
- ❌ *"Because my test passed on my laptop, the code is free of race conditions."* (Timing depends on CPU core counts, JIT compilation tier, and hardware architecture).
