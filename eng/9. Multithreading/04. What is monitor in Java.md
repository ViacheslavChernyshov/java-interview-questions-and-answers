# What is monitor in Java?

---

## 🟢 Junior Level

A **Monitor** (Intrinsic Lock) is a synchronization construct in Java that provides **mutual exclusion** and **thread coordination**. Every object created on the Java Heap possesses an intrinsic monitor "out of the box":

```java
public class Counter {
    private int count = 0;

    // synchronized acquires the intrinsic monitor of 'this' instance:
    public synchronized void increment() {
        count++; // Only one thread can execute inside this critical section
    }
}
```

```
  The Monitor Room Analogy:
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Monitor Room: [Running Thread executing synchronized critical section] │
  ├────────────────────────────────────────────────────────────────────────┤
  │ EntryList:    [BLOCKED Threads queued up waiting for the lock]         │
  │ WaitSet:      [WAITING Threads parked after calling wait()]            │
  └────────────────────────────────────────────────────────────────────────┘
```

### Thread Signaling: `wait()` & `notify()`

```java
// Producer / Consumer synchronization:
synchronized(lock) {
    while (!ready) {
        lock.wait(); // Releases the monitor lock and moves thread to WaitSet
    }
    // Wakes up and re-acquires lock when notified:
    processData();
}

// In Producer Thread:
synchronized(lock) {
    ready = true;
    lock.notify(); // Moves one waiting thread from WaitSet back to EntryList
}
```

> [!WARNING]
> Calling `wait()`, `notify()`, or `notifyAll()` outside a `synchronized` block throws an immediate **`IllegalMonitorStateException`**.

## 🟡 Middle Level

### The Mark Word & Lock State Hierarchy

Inside the JVM object header, the **Mark Word** stores the lock state:

```
  ┌─────────────────┬──────────────────────────────────────────────────┬───────────────────────────────┐
  │ Mark Word Tag   │ Lock State                                       │ Description                   │
  ├─────────────────┼──────────────────────────────────────────────────┼───────────────────────────────┤
  │ `01`            │ **Unlocked (No Lock)**                           │ Normal hash code and GC age   │
  │ `00`            │ **Lightweight Lock (Thin Lock)**                 │ Points to Stack `Lock Record` │
  │ `10`            │ **Heavyweight Lock (Fat Lock)**                  │ Points to JVM `ObjectMonitor` │
  │ `11`            │ **Marked for GC**                                │ Used during garbage collection│
  └─────────────────┴──────────────────────────────────────────────────┴───────────────────────────────┘
```

### The C++ `ObjectMonitor` Structure in HotSpot

When lock contention escalates to a Heavyweight Lock, the JVM allocates a C++ `ObjectMonitor` structure:

```cpp
// HotSpot ObjectMonitor implementation excerpt:
class ObjectMonitor {
    void*            _owner;       // Pointer to current owning thread
    ObjectWaiter*    _EntryList;   // Queue of BLOCKED threads contending for lock
    ObjectWaiter*    _WaitSet;     // Queue of WAITING threads that called wait()
    int              _recursions;  // Reentrant nesting recursion counter
};
```

```
  Thread Lifecycle in Monitor:
  New Thread ──► EntryList (BLOCKED) ──► Owner (RUNNING) ──► Complete (EXIT)
                                              │
                                              │ wait()
                                              ▼
                                         WaitSet (WAITING)
                                              │
                                              │ notify()
                                              ▼
                                         EntryList (BLOCKED)
```

## 🔴 Senior Level

### Lock Escalation Evolution (Java 21 Modern Pipeline)

> [!IMPORTANT]
> **Biased Locking was deprecated in Java 15 (JEP 374) and completely removed in Java 21 (JEP 416).**
> In modern Java runtimes, monitor locks follow a streamlined 2-tier escalation path:

```
  [Unlocked Object (01)] 
          │ 1. First Lock Acquisition (Single Thread)
          ▼
  [Thin Lock (00)] ──► Uses CAS to copy Mark Word into Thread Stack Lock Record
          │ 2. Contention Detected
          ▼
  [Adaptive Spinning] ──► Spins in a tight CPU loop before parking
          │ 3. Contention Persists
          ▼
  [Fat Lock (10)] ──► Inflates to native C++ ObjectMonitor; parks thread via OS kernel (futex)
```

### JIT Compiler Optimizations

#### 1. Lock Elision (Escape Analysis)
If Escape Analysis proves an object never escapes the local method stack, the JIT C2 compiler completely eliminates the synchronization overhead:
```java
public void process() {
    Object localLock = new Object();
    synchronized(localLock) {
        // 🚀 JIT C2 ELIDES THIS LOCK COMPLETELY! (Zero synchronization overhead)
        doWork();
    }
}
```

#### 2. Lock Coarsening
When the JIT compiler encounters consecutive synchronized blocks on the same monitor, it merges them into a single outer block to eliminate redundant lock/unlock cycles.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Intrinsic synchronization primitive tied to every Java heap object providing mutual exclusion.
- **Anatomy:** Composed of `_owner`, `_recursions`, `_EntryList` (BLOCKED), and `_WaitSet` (WAITING).
- **Lock Escalation:** Unlocked (`01`) $\to$ Thin Lock (`00` on stack) $\to$ Adaptive Spinning $\to$ Fat Lock (`10` native `ObjectMonitor`).
- **Java 21 Invariant:** Biased locking is completely removed in Java 21; modern locks transition directly from Unlocked to Thin Lock.
- **Signaling:** `wait()` releases the monitor and transitions thread to WAITING; `notify()` moves a thread to BLOCKED (`EntryList`).
- **JIT Optimizations:** Lock Elision (via Escape Analysis) and Lock Coarsening.

**Common Follow-up Questions:**
- *"What happens if `wait()` is called without acquiring the lock first?"* → Throws `IllegalMonitorStateException` at runtime.
- *"What is a Lock Record?"* → A memory slot allocated on the thread's execution stack containing a displaced Mark Word used during Thin Locking.
- *"Why is a Fat Lock expensive?"* → Because thread parking requires an OS kernel transition (`futex` syscall on Linux / `WaitForSingleObject` on Windows), costing ~1,000+ nanoseconds in context-switch latency.

**Red Flags (DO NOT Say):**
- ❌ *"A monitor is a separate object created in heap memory for every Java object."* (It is an intrinsic concept managed in the object header's Mark Word).
- ❌ *"Biased locking is the default lock state in Java 21."* (Biased locking was permanently removed in Java 21 via JEP 416).
- ❌ *"Calling `notify()` immediately transfers execution to the waiting thread."* (It only moves the thread to `EntryList`; the waking thread must still contend to acquire the lock).
