# How does synchronized work at monitor level?

---

## 🟢 Junior Level

At the language level, **`synchronized`** enforces mutual exclusion across concurrent threads by acquiring an object's intrinsic monitor before executing a critical section, and releasing it upon completion:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Syntax Usage                                           │ Target Lock Object Acquired                            │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ `public synchronized void method()`                    │ `this` (Current instance reference)                    │
  │ `public static synchronized void method()`             │ `ClassName.class` (Class object monitor)               │
  │ `synchronized(lock) { ... }`                           │ Specific explicit `lock` instance                      │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
public class SafeBankTransfer {
    private final Object transferLock = new Object();
    private double balance = 1000.0;

    public void withdraw(double amount) {
        synchronized(transferLock) { // Acquires transferLock monitor
            if (balance >= amount) {
                balance -= amount;
            }
        } // Automatically releases transferLock monitor
    }
}
```

## 🟡 Middle Level

### Bytecode Mechanics: Block vs. Method

There is a fundamental difference in how `javac` compiles synchronized blocks versus synchronized methods:

```
  ┌──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────┐
  │ Synchronized Construct           │ Bytecode Representation                                                 │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
  │ **`synchronized(obj) { ... }`**  │ Emits explicit **`monitorenter`** and dual **`monitorexit`** bytecodes. │
  │ **`synchronized void foo()`**    │ Sets method header flag **`ACC_SYNCHRONIZED`**; no explicit bytecodes.  │
  └──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────┘
```

#### Synchronized Block Bytecode
```bytecode
0: aload_1          // Load lock reference
1: dup              // Duplicate reference for exception handler
2: astore_2         // Store lock reference
3: monitorenter     // ──► ACQUIRE MONITOR LOCK
4: ...              // Critical section operations
8: aload_2
9: monitorexit      // ──► RELEASE MONITOR LOCK (Normal path)
10: goto 18
13: astore_3        // Catch all exceptions handler (Hidden finally)
14: aload_2
15: monitorexit      // ──► RELEASE MONITOR LOCK (Exception path)
16: aload_3
17: athrow
18: return
```

> [!NOTE]
> The compiler always generates **two `monitorexit` instructions** for every `monitorenter`: one for normal completion and one in a synthetic exception table handler to guarantee lock release even if an unhandled `RuntimeException` or `Error` occurs.

## 🔴 Senior Level

### Under the Hood: Lock State Escalation (Java 21)

Modern OpenJDK engines escalate lock states dynamically based on thread contention:

```
  1. Unlocked Object (01)
         │
         │ Thread executes synchronized block
         ▼
  2. Thin Lock (Lightweight Locking - 00)
         │ • Allocates a Lock Record on the thread's local execution stack
         │ • Uses hardware CAS to swap displaced Mark Word pointer
         │ • Cost: ~10-20 ns (Zero OS kernel interaction)
         │
         ▼ (Contention detected: Another thread attempts acquisition)
  3. Adaptive Spinning
         │ • Thread executes a tight heuristic spin-wait loop without sleeping
         │ • Skips OS context-switch overhead if lock is released quickly
         │
         ▼ (Spin limit exceeded: Persistent Contention)
  4. Fat Lock (Heavyweight Locking - 10)
         │ • Allocates native C++ ObjectMonitor in JVM heap
         │ • Parks thread via OS kernel syscall (Linux futex / Windows WaitForSingleObject)
         │ • Thread transitions to BLOCKED state (Context switch penalty: ~1,000-5,000 ns)
```

### JIT Compiler Optimizations

#### 1. Lock Elision (Escape Analysis)
If Escape Analysis determines that a locked object never escapes the declaring method scope, the JIT C2 compiler **completely eliminates the synchronization operations**:
```java
public String generateKey() {
    Object localLock = new Object();
    synchronized(localLock) { // 🚀 JIT C2 ELIDES THIS COMPLETELY (0 ns overhead)
        return UUID.randomUUID().toString();
    }
}
```

#### 2. Lock Coarsening
If multiple consecutive synchronized blocks operate on the same monitor, JIT C2 merges them into a single larger synchronized block:
```java
// What you wrote:
synchronized(lock) { append(a); }
synchronized(lock) { append(b); }

// JIT compiled machine code:
synchronized(lock) {
    append(a);
    append(b);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Bytecode Difference:** Synchronized blocks use `monitorenter`/`monitorexit`; synchronized methods use the `ACC_SYNCHRONIZED` method access flag.
- **Dual Exit Guarantee:** Every `monitorenter` has two `monitorexit` instructions (one normal, one in an exception handler).
- **Lock Escalation Path (Java 21):** Unlocked (`01`) $\to$ Thin Lock (`00` on stack) $\to$ Adaptive Spinning $\to$ Fat Lock (`10` native `ObjectMonitor`).
- **Fat Lock Cost:** Invokes OS kernel primitives (`futex`), descheduling threads and causing expensive context switches (~1,000–5,000 ns).
- **JIT Optimizations:** Lock Elision (removes unshared locks) and Lock Coarsening (merges adjacent blocks).

**Common Follow-up Questions:**
- *"Why does a synchronized method not contain monitorenter/monitorexit in its bytecode?"* → Because the JVM handles `ACC_SYNCHRONIZED` natively during method invocation and return, which is slightly more compact in bytecode size.
- *"How does reentrancy work inside the ObjectMonitor?"* → The `ObjectMonitor` increments a `_recursions` counter when the owning thread enters again, and decrements it on exit, releasing the lock when `_recursions == 0`.
- *"What is Adaptive Spinning?"* → A JVM heuristic where the thread spins in a CPU loop for a duration based on previous lock acquisition history on that specific monitor before falling back to OS parking.

**Red Flags (DO NOT Say):**
- ❌ *"Synchronized always creates a heavy C++ ObjectMonitor on the first acquisition."* (It starts as a lightweight Thin Lock on the thread stack).
- ❌ *"If an uncaught exception is thrown inside a synchronized block, the lock remains held forever."* (The JVM exception handler executes the second `monitorexit` before throwing).
- ❌ *"Biased locking is actively used in modern Java 21 applications."* (Biased locking was permanently removed in Java 21 via JEP 416).
