# What are Virtual Threads in Java 21?

---

## 🟢 Junior Level

**Virtual Threads** (finalized in Java 21 via **JEP 444 / Project Loom**) are lightweight, user-mode threads managed directly by the JVM runtime rather than the underlying operating system kernel:

```
  ┌──────────────────────────┬────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Characteristic           │ Platform Thread (Traditional OS Thread)                │ Virtual Thread (Java 21+)                              │
  ├──────────────────────────┼────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **Management**           │ OS Kernel Scheduler (1:1 Mapping)                      │ JVM Runtime Scheduler ($M:N$ Mapping)                  │
  │ **Memory Stack**         │ Fixed **~1 MB** native OS stack reserved upfront       │ Dynamic **~1 KB** stored in JVM Heap (`StackChunk`)    │
  │ **Creation Overhead**    │ Expensive (~1–10 ms; kernel context switch)            │ Ultra-fast (~microsecond range; zero syscall)          │
  │ **Scalability Limit**    │ Thousands before `OutOfMemoryError`                    │ **Millions** concurrently in a single JVM instance     │
  └──────────────────────────┴────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// 1. Spawning an ephemeral Virtual Thread:
Thread.ofVirtual().start(() -> {
    System.out.println("Executing on Virtual Thread: " + Thread.currentThread());
});

// 2. High-Throughput Thread-Per-Task Executor:
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> {
            Thread.sleep(1000); // Unmounts automatically without blocking OS threads!
            return fetchRemoteUserData();
        });
    }
} // Automatically awaits all subtasks upon exiting try-with-resources
```

## 🟡 Middle Level

### Continuation & Carrier Thread Architecture

Virtual threads do not run directly on CPU cores. They execute mounted on underlying OS **Carrier Threads** (backed by an internal `ForkJoinPool`):

```
  1. Virtual Thread mounted on Carrier Thread (Core 1)
  2. Blocking Operation Encountered (e.g. Socket Read, Thread.sleep, JDBC Query):
     ├──► JVM captures stack frame into Heap ('StackChunk' objects)
     └──► Virtual Thread UNMOUNTS from Carrier Thread
  3. Carrier Thread is now free to execute another Virtual Thread immediately!
  4. OS completes I/O (epoll / kqueue notification):
     └──► Virtual Thread re-MOUNTS to an available Carrier Thread and resumes execution.
```

```
  ┌────────────────────────────────────────────────────────────────────────┐
  │ 1,000,000 Virtual Threads (Heap Memory)                                │
  └──────────────────┬──────────────────┬──────────────────┬───────────────┘
                     │ (Mount/Unmount)  │                  │
                     ▼                  ▼                  ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Carrier Thread Pool (ForkJoinPool with ~8–16 OS Platform Threads)      │
  └──────────────────┬──────────────────┬──────────────────┬───────────────┘
                     ▼                  ▼                  ▼
  ┌────────────────────────────────────────────────────────────────────────┐
  │ Hardware CPU Cores (8 Physical Cores)                                  │
  └────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Pinning Hazard (Senior Concurrency Must-Know!)

**Thread Pinning** occurs when a virtual thread cannot unmount from its carrier thread during a blocking operation:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────┬───────────────────────────────────────────────┐
  │ Cause of Pinning             │ Problem Description                             │ Recommended Fix                               │
  ├──────────────────────────────┼─────────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ **`synchronized` blocks**    │ In Java 21, monitor holds pin the carrier thread│ Replace with **`ReentrantLock`**              │
  │ **Native Methods (JNI)**     │ JVM C/C++ frame cannot be copied to heap        │ Offload JNI calls to a dedicated thread pool  │
  └──────────────────────────────┴─────────────────────────────────────────────────┴───────────────────────────────────────────────┘
```

```java
// ❌ PINNING HAZARD: Carrier thread is held hostage for 5 seconds!
public synchronized void fetchOrder() {
    restClient.getForObject("https://api.com", String.class); // 💥 Stalls Carrier Thread
}

// ✅ IDIOMATIC FOR VIRTUAL THREADS: Unmounts smoothly
private final ReentrantLock lock = new ReentrantLock();
public void fetchOrder() {
    lock.lock();
    try {
        restClient.getForObject("https://api.com", String.class); // Unmounts carrier thread!
    } finally {
        lock.unlock();
    }
}
```

> [!TIP]
> Detect pinned threads in development by enabling the JVM diagnostic flag:
> `-Djdk.tracePinnedThreads=full`

### `ThreadLocal` Memory Hazard vs. `ScopedValue`

Storing large objects inside `ThreadLocal` when spawning 1,000,000 virtual threads causes massive heap exhaustion:

```java
// ❌ HEAP EXHAUSTION: 1,000,000 virtual threads allocate 1,000,000 separate buffer copies!
private static final ThreadLocal<byte[]> BUFFER = ThreadLocal.withInitial(() -> new byte[1024 * 64]);

// ✅ MODERN JAVA 21+: Scoped Values provide immutable, clean contextual sharing
private static final ScopedValue<UserContext> USER_CTX = ScopedValue.newInstance();

ScopedValue.runWhere(USER_CTX, new UserContext("alice"), () -> {
    handleRequest(); // Context is automatically bounded and cleaned up
});
```

### Spring Boot 3.2+ Native Activation

```yaml

    virtual:
      enabled: true
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Lightweight user-mode threads managed by the JVM runtime (JEP 444).
- **Stack Allocation:** Stored dynamically in JVM heap (`StackChunk`), starting at ~1 KB (vs ~1 MB OS static stack).
- **Mount/Unmount:** Virtual threads mount on OS Carrier Threads (`ForkJoinPool`); unmount on blocking I/O.
- **Ideal Workload:** High-throughput, I/O-bound web services and database clients.
- **Pinning:** Blocking inside `synchronized` blocks or native JNI pins the carrier thread; use `ReentrantLock`.
- **Do NOT Pool Virtual Threads:** Never use thread pools for virtual threads; create them per task.

**Common Follow-up Questions:**
- *"Why are Virtual Threads unsuitable for CPU-bound computations?"* → Because CPU-bound tasks never block on I/O, so virtual threads never unmount. Running CPU calculations on virtual threads only adds scheduling overhead without increasing concurrency.
- *"How do you debug pinned virtual threads?"* → Run the JVM with `-Djdk.tracePinnedThreads=full` or inspect `jdk.VirtualThreadPinned` events via Java Flight Recorder (JFR).
- *"How does Project Loom change the Reactive vs Imperative debate?"* → It allows writing straightforward synchronous, blocking code (thread-per-request) while achieving the massive scale previously only possible with reactive frameworks (WebFlux / RxJava).

**Red Flags (DO NOT Say):**
- ❌ *"Virtual Threads execute without any underlying OS threads."* (They mount onto OS platform Carrier Threads to execute bytecode on physical CPU cores).
- ❌ *"We should pool Virtual Threads using a fixed ThreadPoolExecutor."* (Virtual threads are ephemeral and designed to be created per task; pooling them is an anti-pattern).
- ❌ *"Virtual Threads speed up CPU-heavy operations like image rendering."* (They do not increase raw CPU compute speed; they increase I/O concurrency).
