# How do AtomicInteger, AtomicLong work?

---

## 🟢 Junior Level

**`AtomicInteger`** and **`AtomicLong`** are thread-safe, lock-free wrappers around primitive `int` and `long` values from the `java.util.concurrent.atomic` package.

They guarantee that compound read-modify-write operations are executed **atomically without using locks or thread blocking**:

```java
// ❌ UNSAFE: count++ consists of 3 distinct non-atomic bytecode instructions
int count = 0;
count++; // getfield -> iadd -> putfield (Causes data loss across threads)

// ✅ THREAD-SAFE & LOCK-FREE:
AtomicInteger counter = new AtomicInteger(0);
int newCount = counter.incrementAndGet(); // Atomic ++i executed via hardware CPU CAS
```

### Common Method Signatures

```
  ┌──────────────────────────────┬──────────────────────┬──────────────────────────────────────────────┐
  │ Method                       │ Equivalent Syntax    │ Return Value                                 │
  ├──────────────────────────────┼──────────────────────┼──────────────────────────────────────────────┤
  │ `incrementAndGet()`          │ `++count`            │ Returns the **updated (new)** value          │
  │ `getAndIncrement()`          │ `count++`            │ Returns the **previous (old)** value         │
  │ `addAndGet(delta)`           │ `count += delta`     │ Returns the **updated (new)** value          │
  │ `getAndAdd(delta)`           │ `old = count; +=`    │ Returns the **previous (old)** value         │
  │ `compareAndSet(exp, update)` │ Conditional swap     │ Returns `true` if swapped, `false` otherwise │
  └──────────────────────────────┴──────────────────────┴──────────────────────────────────────────────┘
```

## 🟡 Middle Level

### Internal Architecture: `volatile` + `VarHandle`

Inside OpenJDK (Java 9+), `AtomicInteger` holds a `volatile` value field manipulated via **`VarHandle`**:

```java
public class AtomicInteger extends Number implements java.io.Serializable {
    private volatile int value; // 1. Volatile field ensures visibility across CPU caches
    private static final VarHandle VALUE; // 2. VarHandle executes native atomic instructions

    static {
        try {
            MethodHandles.Lookup l = MethodHandles.lookup();
            VALUE = l.findVarHandle(AtomicInteger.class, "value", int.class);
        } catch (ReflectiveOperationException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    public final int incrementAndGet() {
        return (int) VALUE.getAndAdd(this, 1) + 1; // Translates to x86 'lock xadd'
    }
}
```

### Writing Semantics: `set()` vs. `lazySet()`

```java
AtomicInteger counter = new AtomicInteger(0);

// 1. Full Volatile Write:
counter.set(100);     // Inserts StoreStore + StoreLoad barriers (Immediate visibility)

// 2. Ordered / Release Write:
counter.lazySet(100); // Inserts StoreStore barrier only (Omits expensive StoreLoad barrier)
```
> [!NOTE]
> `lazySet()` provides **eventual consistency** with lower CPU overhead (~2-3 ns vs ~5-10 ns) because it does not flush hardware store buffers immediately. It is ideal for resetting state flags or cleaning queue references.

### 32-Bit JVM Word-Tearing Protection

On 32-bit JVM architectures, writing a 64-bit `long` primitive is performed in two separate 32-bit writes (high bits and low bits). Without synchronization, concurrent threads can read torn, corrupted values. **`AtomicLong` eliminates word-tearing** by executing atomic 64-bit hardware operations (`CMPXCHG8B` on x86).

## 🔴 Senior Level

### High-Throughput Optimization: ID Range Allocation

Under 100,000+ RPS, hammering a single `AtomicLong` as a global sequential sequence generator causes severe memory bus contention:

```java
// ❌ HIGH CONTENTION: Every single request hits the same AtomicLong
public long nextId() {
    return globalCounter.incrementAndGet(); // Millions of CAS retries/sec
}

// ✅ ID RANGE ALLOCATION: Batching increments amortizes CAS contention by 1000x
public class DistributedIdGenerator {
    private static final long BATCH_SIZE = 1000;
    private final AtomicLong sequenceRange = new AtomicLong(0);

    // ThreadLocal sub-allocator:
    private final ThreadLocal<LocalRange> localRange = ThreadLocal.withInitial(() -> allocateNewBatch());

    private LocalRange allocateNewBatch() {
        long start = sequenceRange.getAndAdd(BATCH_SIZE); // Hits shared AtomicLong only once every 1000 IDs!
        return new LocalRange(start, start + BATCH_SIZE);
    }
}
```

### Memory Footprint Reduction: `AtomicIntegerFieldUpdater`

In high-density domains storing millions of objects (e.g. 10,000,000 cached `UserSession` records):

```
  ┌────────────────────────────────────────────────────────┬──────────────────────────────────────────┐
  │ Approach                                               │ Heap Memory for 10,000,000 Objects       │
  ├────────────────────────────────────────────────────────┼──────────────────────────────────────────┤
  │ `AtomicInteger count = new AtomicInteger(0);`          │ **240 MB** (+24 bytes per instance)      │
  │ `volatile int count;` + `AtomicIntegerFieldUpdater`    │ **40 MB** (4 bytes primitive field only) │
  └────────────────────────────────────────────────────────┴──────────────────────────────────────────┘
```

```java
public class UserSession {
    // Plain volatile primitive field:
    private volatile int accessCount = 0;

    // Single static updater instance shared across all sessions:
    private static final AtomicIntegerFieldUpdater<UserSession> UPDATER =
        AtomicIntegerFieldUpdater.newUpdater(UserSession.class, "accessCount");

    public void incrementAccess() {
        UPDATER.incrementAndGet(this); // Atomic CAS directly on primitive field!
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Thread-safe wrappers for `int` and `long` providing lock-free atomic arithmetic and updates via CAS.
- **Hardware Mechanism:** Translates directly into native CPU atomic instructions (`LOCK XADD` / `LOCK CMPXCHG` on x86).
- **`incrementAndGet` vs `getAndIncrement`:** `incrementAndGet` returns the new value (`++i`); `getAndIncrement` returns the old value (`i++`).
- **`lazySet()`:** Fast ordered release write providing eventual consistency by skipping the expensive `StoreLoad` memory barrier.
- **Memory Optimization:** Use `AtomicIntegerFieldUpdater` to avoid creating wrapper objects across millions of entities.
- **Word-Tearing:** `AtomicLong` protects 64-bit variables from torn reads on 32-bit JVMs.

**Common Follow-up Questions:**
- *"What is the difference between `updateAndGet()` and `addAndGet()`?"* → `addAndGet()` performs simple addition; `updateAndGet()` accepts an arbitrary functional lambda expression (`IntUnaryOperator`), executing it inside an optimistic CAS retry loop.
- *"How does `AtomicInteger` differ from `synchronized`?"* → `AtomicInteger` is lock-free (no OS thread parking, no deadlocks); `synchronized` is a blocking mutex that transitions to an `ObjectMonitor` under contention.
- *"When does `AtomicLong` degrade in performance?"* → When hundreds of threads hammer the same variable simultaneously; under high contention, replace with `LongAdder`.

**Red Flags (DO NOT Say):**
- ❌ *"AtomicInteger acquires a monitor lock on each increment."* (It is lock-free and uses hardware CAS).
- ❌ *"lazySet() guarantees instant memory visibility across all cores."* (It provides eventual consistency and omits the StoreLoad fence).
- ❌ *"AtomicLong is unnecessary on modern 64-bit systems."* (It is still essential for lock-free multi-threaded compound atomicity).
