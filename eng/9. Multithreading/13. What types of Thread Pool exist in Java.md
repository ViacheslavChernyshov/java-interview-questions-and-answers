# What types of Thread Pool exist in Java?

---

## 🟢 Junior Level

Java provides factory methods inside **`java.util.concurrent.Executors`** to instantiate pre-configured thread pool architectures:

```
  ┌──────────────────────────────────────────────┬────────────────────────┬──────────────────────┬─────────────────────────────────────────────────┐
  │ Factory Method                               │ Pool Size              │ Work Queue Type      │ Primary Use Case                                │
  ├──────────────────────────────────────────────┼────────────────────────┼──────────────────────┼─────────────────────────────────────────────────┤
  │ **`newFixedThreadPool(n)`**                  │ Fixed `n`              │ Unbounded `Linked`   │ Predictable, steady production workloads        │
  │ **`newCachedThreadPool()`**                  │ Dynamic (0 to Max Int) │ `SynchronousQueue`   │ Bursty workloads with many short-lived tasks    │
  │ **`newSingleThreadExecutor()`**              │ Strictly 1             │ Unbounded `Linked`   │ Sequential FIFO task processing                 │
  │ **`newScheduledThreadPool(n)`**              │ Fixed `n`              │ `DelayedWorkQueue`   │ Periodic / Delayed cron-like task execution     │
  │ **`newWorkStealingPool()`** (Java 8)         │ Available CPU cores    │ Work-Stealing Deque  │ Recursive compute-heavy divide-and-conquer tasks│
  │ **`newVirtualThreadPerTaskExecutor()`** (21) │ Unbounded Virtual      │ Ephemeral per task   │ Modern massive I/O concurrency (Project Loom)   │
  └──────────────────────────────────────────────┴────────────────────────┴──────────────────────┴─────────────────────────────────────────────────┘
```

```java
// 1. Fixed thread pool
ExecutorService fixed = Executors.newFixedThreadPool(8);

// 2. Scheduled thread pool
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
scheduler.scheduleAtFixedRate(() -> heartbeat(), 0, 5, TimeUnit.SECONDS);

// 3. Modern Java 21 Virtual Thread executor (No pooling needed!)
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> fetchRemoteApi());
}
```

## 🟡 Middle Level

### Production Risks of Standard `Executors` Factories

> [!WARNING]
> High-traffic production services should avoid `Executors.newFixedThreadPool()` and `Executors.newCachedThreadPool()` because they lack back-pressure boundaries:

```
  1. Executors.newFixedThreadPool(n) Risk:
     Uses an UNBOUNDED LinkedBlockingQueue (Capacity: Integer.MAX_VALUE = 2.14 Billion tasks).
     If tasks arrive faster than worker threads can process, memory grows uncontrollably until
     💥 java.lang.OutOfMemoryError: Java heap space.

  2. Executors.newCachedThreadPool() Risk:
     Sets maximumPoolSize = Integer.MAX_VALUE with SynchronousQueue (Zero queue capacity).
     A traffic surge of 20,000 requests spawns 20,000 OS native threads simultaneously, triggering
     💥 java.lang.OutOfMemoryError: unable to create native thread.
```

### Production Best Practice: Explicit `ThreadPoolExecutor`

```java
// ✅ PRODUCTION SAFE: Bounded queue + CallerRuns back-pressure policy
ThreadPoolExecutor safeExecutor = new ThreadPoolExecutor(
    8,                                     // corePoolSize
    16,                                    // maximumPoolSize
    60L, TimeUnit.SECONDS,                 // keepAliveTime for burst threads
    new ArrayBlockingQueue<>(1000),        // Bounded capacity protection against OOM
    new CustomThreadFactory("order-svc-"), // Named daemon threads
    new ThreadPoolExecutor.CallerRunsPolicy() // Back-pressure on saturation
);
```

### Scheduling Policies: `FixedRate` vs. `FixedDelay`

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ `scheduleAtFixedRate(period = 5s)`                     │ `scheduleWithFixedDelay(delay = 5s)`                   │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ Measured from the **start** time of previous run       │ Measured from the **completion** time of previous run  │
  │ If task takes 7s, next execution starts **immediately**│ Waits the full 5s delay regardless of execution duration│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### `SingleThreadExecutor` vs. `newFixedThreadPool(1)`

`Executors.newSingleThreadExecutor()` wraps the internal pool in an unconfigurable **`FinalizableDelegatedExecutorService`**:
- Unlike `newFixedThreadPool(1)`, it **cannot be cast back to `ThreadPoolExecutor`** to mutate core/maximum sizes at runtime.
- If the single worker thread dies unexpectedly due to an uncaught `RuntimeException`, the pool automatically spawns a replacement worker thread to continue draining pending tasks.

### Mixed Workload Sizing Formula

```
  $N_{\text{threads}} = N_{\text{cores}} \times U_{\text{target}} \times \left(1 + \frac{\text{Wait Time}}{\text{Compute Time}}\right)$

  Example Calculation:
  - 8 CPU Cores
  - Target CPU Utilization = 80% (0.8)
  - Latency: 90ms Database I/O wait, 10ms CPU processing (Wait/Compute = 9)
  $N_{\text{threads}} = 8 \times 0.8 \times (1 + 9) = 6.4 \times 10 = \mathbf{64\ \text{Worker Threads}}$
```

### Java 21 Modern Paradigm: Virtual Threads

In Java 21+ applications handling I/O-bound workloads, native thread pools are largely replaced by **Virtual Threads**:

```java
// Spawns lightweight virtual threads on top of underlying ForkJoin carrier threads
ExecutorService virtualExecutor = Executors.newVirtualThreadPerTaskExecutor();
```
- **Zero Sizing Needed:** Virtual threads cost only a few kilobytes of RAM and are not bound by OS thread pool limits.
- **Do NOT Pool Virtual Threads:** Creating a fixed pool of virtual threads is an anti-pattern. Virtual threads are ephemeral and meant to be created per task.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The 5 Classic Types:** Fixed, Cached, SingleThread, Scheduled, WorkStealing.
- **Java 21 Modern Type:** `newVirtualThreadPerTaskExecutor()` for scalable I/O.
- **FixedThreadPool OOM Trap:** Backed by unbounded `LinkedBlockingQueue`, risking Heap OOM.
- **CachedThreadPool Thread Bomb Trap:** Max size is `Integer.MAX_VALUE`, risking OS Native Thread OOM.
- **`scheduleAtFixedRate` vs `scheduleWithFixedDelay`:** FixedRate starts from task beginning; FixedDelay waits from task end.
- **Production Standard:** Build explicit `ThreadPoolExecutor` with `ArrayBlockingQueue` and `CallerRunsPolicy`.

**Common Follow-up Questions:**
- *"Why does SonarQube flag `Executors.newFixedThreadPool()` as a major code smell?"* → Because it instantiates an unbounded queue with `Integer.MAX_VALUE` capacity, which leads to memory exhaustion during service degradations.
- *"How does `SingleThreadExecutor` maintain sequential execution if a task throws an Error?"* → It terminates the faulted thread and immediately spins up a fresh worker thread to resume processing subsequent queued tasks.
- *"Should we pool Virtual Threads in Java 21?"* → No. Virtual threads are lightweight, ephemeral resources; pooling them defeats their purpose and introduces unnecessary complexity.

**Red Flags (DO NOT Say):**
- ❌ *"CachedThreadPool is the ideal thread pool for heavy database queries."* (It will spawn hundreds of threads, exhausting DB connections and crashing the OS).
- ❌ *"scheduleAtFixedRate guarantees that tasks never overlap."* (A single thread in the pool will not overlap itself, but tasks will queue and execute back-to-back with zero delay if execution exceeds period).
- ❌ *"FixedThreadPool is completely safe from OutOfMemoryErrors."* (Its unbounded queue will consume all heap memory under sustained load).
