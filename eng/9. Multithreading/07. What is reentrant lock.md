# What is reentrant lock?

---

## 🟢 Junior Level

A **Reentrant Lock** (Recursive Mutex) is a synchronization mechanism that allows a thread that **already holds a lock to re-acquire it multiple times without deadlocking itself**.

Without reentrancy, a thread calling a synchronized method from inside another synchronized method would block indefinitely waiting for itself to release the lock.

```java
// 1. Built-in intrinsic synchronization is reentrant by default:
public class ReentrantDemo {
    public synchronized void outer() {
        inner(); // ✅ Does NOT deadlock! Same thread enters inner() smoothly
    }

    public synchronized void inner() {
        System.out.println("Executing inner critical section");
    }
}

// 2. Explicit ReentrantLock from java.util.concurrent.locks:
public class ExplicitLockDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void doWork() {
        lock.lock(); // Increment hold count (state = 1)
        try {
            lock.lock(); // Increment hold count again (state = 2)
            try {
                process();
            } finally {
                lock.unlock(); // Decrement hold count (state = 1)
            }
        } finally {
            lock.unlock(); // Released when state reaches 0!
        }
    }
}
```

## 🟡 Middle Level

### `synchronized` vs. `ReentrantLock` Comparison

```
  ┌──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Feature                  │ `synchronized`           │ `ReentrantLock`                                  │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Level**                │ Java Language Keyword    │ Library Class (`java.util.concurrent.locks`)     │
  │ **Reentrancy**           │ Automatic                │ Automatic via AQS `state` hold count             │
  │ **Try-Lock with Timeout**│ ❌ Not supported         │ ✅ `tryLock(100, TimeUnit.MILLISECONDS)`         │
  │ **Interruptible Lock**   │ ❌ Blocked indefinitely  │ ✅ `lockInterruptibly()`                         │
  │ **Fairness Option**      │ ❌ Unfair only           │ ✅ `new ReentrantLock(true)` (Strict FIFO)       │
  │ **Wait-Set Conditions**  │ 1 per object (wait/notify)│ Multiple independent `Condition` instances       │
  │ **Release Safety**       │ Automatic (JVM bytecode) │ **Manual:** Must use `try ... finally` block     │
  └──────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

### Multiple `Condition` Instances (Bounded Queue Example)

`ReentrantLock` allows binding multiple independent wait-sets to a single lock, avoiding the inefficiency of `notifyAll()` waking up unrelated threads:

```java
public class BoundedBuffer<T> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition(); // Producers wait here
    private final Condition notEmpty = lock.newCondition(); // Consumers wait here
    private final Object[] items = new Object[100];
    private int count, putptr, takeptr;

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await(); // Releases lock and waits for space
            }
            items[putptr] = x;
            if (++putptr == items.length) putptr = 0;
            count++;
            notEmpty.signal(); // Wakes up ONLY waiting consumers!
        } finally {
            lock.unlock();
        }
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await(); // Releases lock and waits for data
            }
            @SuppressWarnings("unchecked")
            T x = (T) items[takeptr];
            if (++takeptr == items.length) takeptr = 0;
            count--;
            notFull.signal(); // Wakes up ONLY waiting producers!
            return x;
        } finally {
            lock.unlock();
        }
    }
}
```

## 🔴 Senior Level

### Under the Hood: AbstractQueuedSynchronizer (AQS)

`ReentrantLock` delegates lock management to an internal implementation of **`AbstractQueuedSynchronizer` (AQS)**:

```
  AQS Lock State & CLH Wait Queue:
  ┌────────────────────────────────────────────────────────────────────────┐
  │ • volatile int state: 0 = Unlocked, 1+ = Reentrant Hold Count          │
  │ • Thread exclusiveOwnerThread: Reference to lock owner                 │
  └────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
  [Head Node] ◄──► [Node (Thread 1: Parked)] ◄──► [Node (Thread 2: Parked)] ◄──► [Tail]
```

### Fair vs. Non-Fair Sync Mechanics

```java
public class ReentrantLock implements Lock {
    public ReentrantLock() {
        sync = new NonfairSync(); // Default (High throughput)
    }
    public ReentrantLock(boolean fair) {
        sync = fair ? new FairSync() : new NonfairSync();
    }
}
```

#### Non-Fair Mode (Barging Permitted)
- When a lock is released, an incoming thread executing `lock()` immediately attempts a CAS swap on `state` from 0 to 1 (**Barging**).
- If successful, it bypasses the queued threads entirely, avoiding expensive CPU thread unparking and context switches. Throughput is **up to 50–100% higher** than Fair mode.

#### Fair Mode (Strict FIFO Queue)
- Enforces strict queue ordering via `!hasQueuedPredecessors()`.
- If threads are already waiting in the AQS queue, incoming threads are forced to enqueue at the tail, eliminating thread starvation at the expense of lower overall throughput.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Allows the owning thread to enter critical sections repeatedly without self-deadlock.
- **Hold Count:** Maintained via an internal counter (unlocked only when the hold count reaches 0).
- **AQS Foundation:** Built on `AbstractQueuedSynchronizer` using a `volatile int state` and a FIFO CLH queue.
- **Key Advantages:** `tryLock(timeout)`, `lockInterruptibly()`, fairness configuration, and multiple `Condition` wait-sets.
- **Critical Invariant:** Always call `unlock()` inside a **`finally` block** to prevent permanent deadlocks on unexpected exceptions.

**Common Follow-up Questions:**
- *"Why is Non-Fair locking the default in ReentrantLock?"* → Because allowing new threads to barge avoids thread parking and unparking latency, yielding significantly higher throughput.
- *"How does `Condition.await()` differ from `Object.wait()`?"* → `Condition.await()` allows binding multiple independent wait-sets (`notFull`, `notEmpty`) to the same lock, enabling targeted wakeups with `signal()`.
- *"What happens if `unlock()` is called more times than `lock()`?"* → Throws `IllegalMonitorStateException`.

**Red Flags (DO NOT Say):**
- ❌ *"ReentrantLock is always 10x faster than synchronized in Java 21."* (Modern `synchronized` is heavily optimized via Thin Locks; use `ReentrantLock` for advanced features, not raw speed).
- ❌ *"Forgetting `unlock()` inside finally is fine because garbage collection will free the lock."* (The lock remains permanently held, deadlocking all subsequent threads).
- ❌ *"Fair locks are always recommended in production."* (Fair locks introduce severe context-switching overhead and should only be used when starvation is a verified issue).
