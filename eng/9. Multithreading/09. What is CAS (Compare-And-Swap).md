# What is CAS (Compare-And-Swap)?

---

## 🟢 Junior Level

**CAS (Compare-And-Swap)** is an **atomic hardware instruction** supported by modern CPUs that enables **lock-free** concurrent updates:

```
  CAS Pseudo-Code:
  boolean compareAndSwap(MemoryAddress address, int expectedValue, int newValue) {
      if (memory[address] == expectedValue) {
          memory[address] = newValue; // Atomically written
          return true;  // Swap succeeded!
      }
      return false;     // Swap failed (value was mutated by another thread)
  }
```

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Optimistic Model (CAS / Atomics)                       │ Pessimistic Model (`synchronized` / Locks)             │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Proceed without acquiring a lock                     │ • Acquire lock before doing any work                   │
  │ • Attempt atomic swap; if collision occurs, retry loop │ • Block all other threads until lock is released       │
  │ • Ultra-fast under low to medium contention            │ • Prevents CPU spinning under heavy contention         │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// Inside AtomicInteger:
public final int incrementAndGet() {
    for (;;) {
        int current = get();
        int next = current + 1;
        if (compareAndSet(current, next)) { // Hardware CAS instruction
            return next; // Succeeded on first attempt!
        }
        // CAS failed: another thread updated value. Loop around and retry!
    }
}
```

## 🟡 Middle Level

### Hardware Translation Across Architectures

```
  ┌──────────────────┬──────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architecture     │ Hardware Machine Instruction         │ Concurrency Mechanism                            │
  ├──────────────────┼──────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **x86 / x86-64** │ `lock cmpxchg [memory], reg`         │ Single atomic instruction with cache line lock   │
  │ **ARM (AArch64)**│ `ldxr` / `stxr` Loop                 │ Load-Linked / Store-Conditional (LL/SC) pair     │
  │ **RISC-V**       │ `lr.w` / `sc.w` Loop                 │ Load-Reserved / Store-Conditional pair           │
  └──────────────────┴──────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Progress Guarantee Hierarchy

```
  ┌──────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Guarantee Tier           │ System-Wide Liveness Contract                                                   │
  ├──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Wait-Free**         │ **Every thread** is guaranteed to complete in a bounded number of steps         │
  │                          │ *(Example: `LongAdder.add()`)*                                                  │
  │ **2. Lock-Free**         │ **At least one thread** makes forward progress; individual threads may starve   │
  │                          │ *(Example: `AtomicInteger.incrementAndGet()`)*                                  │
  │ **3. Obstruction-Free**  │ A thread makes progress only if all other competing threads are suspended       │
  └──────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### CPU Spin Saturation & `Thread.onSpinWait()` (Java 9+)

Under moderate contention, spinning in a pure `for(;;)` loop burns CPU cycles and overheats cores. Java 9 introduced **`Thread.onSpinWait()`**:

```java
public int incrementWithBackoff() {
    for (;;) {
        int current = get();
        int next = current + 1;
        if (compareAndSet(current, next)) {
            return next;
        }
        // 🚀 Emits x86 PAUSE instruction: reduces CPU power consumption and memory pipeline stalls
        Thread.onSpinWait();
    }
}
```

## 🔴 Senior Level

### The ABA Problem & Memory Reclamation

The **ABA Problem** occurs when a memory location changes from $A \to B \to A$:
1. Thread 1 reads pointer `A` from the top of a concurrent lock-free stack.
2. Thread 2 pops `A`, modifies inner nodes, pops `B`, and pushes `A` back onto the stack.
3. Thread 1 resumes and executes `compareAndSet(A, newHead)`: CAS succeeds because memory address equals `A`, completely unaware that intermediate nodes (`B`) were corrupted or freed!

```
  The ABA Sequence:
  Thread 1 Reads:     [A]
  Thread 2 Mutates:   [A] ──► [B] ──► [A] (State mutated, but value looks identical)
  Thread 1 Executes:  CAS(A, C) ──► 💥 Succeeded erroneously!
```

#### The Solution: `AtomicStampedReference`
```java
// Stores both object reference AND an integer version stamp:
AtomicStampedReference<Node> top = new AtomicStampedReference<>(initialNode, 0);

int[] stampHolder = new int[1];
Node current = top.get(stampHolder);
int currentStamp = stampHolder[0];

// CAS succeeds ONLY if both reference pointer AND stamp match exactly:
boolean swapped = top.compareAndSet(current, newHead, currentStamp, currentStamp + 1);
```

### Contention Inversion: When `synchronized` Beats CAS

```
  ┌──────────────────────────────────────────┬────────────────────────┬────────────────────────────────────────┐
  │ Scenario                                 │ CAS (AtomicLong)       │ Mutex (`synchronized`)                 │
  ├──────────────────────────────────────────┼────────────────────────┼────────────────────────────────────────┤
  │ **Low Contention (1–4 Threads)**         │ 🟢 **Fastest (~5 ns)** │ 🟡 ~15 ns (Thin Lock)                  │
  │ **Ultra-High Contention (100+ Threads)** │ 🔴 Burns 100% CPU      │ 🟢 **Efficient:** Parks threads cleanly│
  └──────────────────────────────────────────┴────────────────────────┴────────────────────────────────────────┘
```
> [!NOTE]
> Under extreme multi-threaded contention on a single variable, CAS spin loops saturate memory bus bandwidth. A traditional mutex or a sharded accumulator (`LongAdder`) will outperform plain CAS loops.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Atomic hardware instruction that updates memory only if the current value matches the expected value.
- **Hardware Primitives:** `LOCK CMPXCHG` on x86, `LDXR`/`STXR` on ARM.
- **Concurrency Paradigm:** Optimistic Concurrency Control (OCC) vs Pessimistic Mutex Locking.
- **Liveness Hierarchy:** Wait-Free (strongest) $>$ Lock-Free (medium) $>$ Obstruction-Free (weakest).
- **ABA Problem:** Solved using `AtomicStampedReference` pairing references with version stamps.
- **CPU Hint:** Java 9 `Thread.onSpinWait()` emits hardware `PAUSE` instructions during spin loops.

**Common Follow-up Questions:**
- *"Why does CAS fail more often as thread count increases?"* → Because multiple cores attempt CAS on the same memory address simultaneously; only one core wins the cache line, forcing all other cores to fail and retry.
- *"What is the difference between Lock-Free and Wait-Free?"* → Lock-Free guarantees global forward progress (at least one thread wins); Wait-Free guarantees per-thread forward progress (every thread finishes in bounded steps).
- *"How does x86 `lock cmpxchg` maintain cache coherency?"* → It locks the target CPU cache line and broadcasts a bus invalidate signal to peer cores via the MESI protocol.

**Red Flags (DO NOT Say):**
- ❌ *"CAS is always faster than synchronized under all possible workloads."* (Under extreme contention, CAS burns 100% CPU in retry loops; mutexes park threads).
- ❌ *"CAS operations do not emit memory barriers."* (CAS enforces a full Acquire-Release / StoreLoad memory barrier).
- ❌ *"The ABA problem only occurs in Java."* (It is a fundamental hardware-level challenge in all lock-free architectures including C/C++ and Rust).
