# What are Atomic classes?

---

## 🟢 Junior Level

**Atomic Classes** in `java.util.concurrent.atomic` provide **lock-free, thread-safe operations** on single variables without incurring the performance penalty of thread blocking or monitor locks:

```java
// ❌ UNSAFE: count++ is 3 distinct operations (read -> modify -> write)
public class UnsafeCounter {
    private int count = 0;
    public void increment() { count++; } // Causes lost updates under concurrency
}

// ✅ THREAD-SAFE & LOCK-FREE:
public class SafeCounter {
    private final AtomicInteger count = new AtomicInteger(0);
    public void increment() { count.incrementAndGet(); } // Atomic CPU operation
}
```

## 🟡 Middle Level

### The Two Pillars: `volatile` + CAS (Compare-And-Swap)

Atomic classes achieve lock-free safety by pairing a `volatile` value field with native hardware CAS instructions:

```java
// Conceptual implementation of incrementAndGet():
public final int incrementAndGet() {
    for (;;) {
        int current = get();       // 1. Volatile read
        int next = current + 1;    // 2. Local compute
        if (compareAndSet(current, next)) { // 3. Atomic hardware swap
            return next;           // Success!
        }
        // CAS failed because another thread updated 'value'; spin and retry!
    }
}
```

### Memory Ordering Controls (Java 9+ `VarHandle`)

Under Java 9+ (JEP 193), atomic operations are routed through **`VarHandle`**, exposing fine-grained memory barriers:

```
  ┌──────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ Method               │ JMM Memory Ordering Guarantee                                               │
  ├──────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ **`set(v)`**         │ Full **Volatile Write** (Inserts `StoreStore` + `StoreLoad` barriers).      │
  │ **`lazySet(v)`**     │ **Release Write** (Skips expensive `StoreLoad` fence; eventual visibility). │
  │ **`compareAndSet()`**│ Full **Acquire-Release Fence** around the CAS instruction.                  │
  └──────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### High Contention: `AtomicLong` vs. `LongAdder`

Under heavy thread contention (e.g. 64 worker threads updating a single metric):
- **`AtomicLong` Contention Collapse:** All threads hammer a single memory address, causing continuous CAS retries, cache invalidation storms, and high CPU burn.
- **`LongAdder` Sharded Cells:** Distributes updates across an internal array of **`@Contended Cell`** structures. Each thread hashes to a separate CPU cache line; `sum()` aggregates values on demand.

```
  AtomicLong under 64 Threads:
  [Thread 1..64] ──► 💥 Heavy CAS Contention on [Single volatile long]

  LongAdder under 64 Threads:
  Thread 1..8   ──► [Cell 0 (@Contended)] ──┐
  Thread 9..16  ──► [Cell 1 (@Contended)] ──┼──► sum() combines all cells on demand
  Thread 17..32 ──► [Cell 2 (@Contended)] ──┘
```

### The ABA Problem & Version Stamps

A classic concurrency flaw in lock-free algorithms:
1. Thread 1 reads value `A`.
2. Thread 2 modifies `A -> B -> A`.
3. Thread 1 executes `compareAndSet(A, C)`: CAS succeeds because value is `A`, unaware that intermediate state mutations occurred.

#### The Solution: `AtomicStampedReference`
```java
// Binds an object reference to an integer version stamp:
AtomicStampedReference<Node> head = new AtomicStampedReference<>(initialNode, 0);

int[] stampHolder = new int[1];
Node current = head.get(stampHolder);
int currentStamp = stampHolder[0];

// CAS verifies BOTH object identity and version stamp:
boolean success = head.compareAndSet(current, newNode, currentStamp, currentStamp + 1);
```

### Memory Optimization: `AtomicIntegerFieldUpdater`

In applications storing millions of domain objects, allocating an `AtomicInteger` wrapper per instance incurs 24 bytes of heap overhead per entity. **Field Updaters** eliminate this overhead:

```java
public class Session {
    // Plain volatile primitive field (Takes only 4 bytes in Heap):
    private volatile int accessCount = 0;

    // Static singleton updater shared across all millions of Session instances:
    private static final AtomicIntegerFieldUpdater<Session> UPDATER =
        AtomicIntegerFieldUpdater.newUpdater(Session.class, "accessCount");

    public void recordAccess() {
        UPDATER.incrementAndGet(this); // Lock-free update directly on primitive field!
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Principle:** Lock-free thread-safety utilizing CPU hardware CAS (`LOCK CMPXCHG`) and `volatile` memory visibility.
- **Retry Loop:** Optimistic execution loop: reads value, calculates result, and retries if CAS detects concurrent modification.
- **ABA Problem:** Solved using `AtomicStampedReference` by attaching version numbers to reference updates.
- **High Contention:** Use `LongAdder` instead of `AtomicLong` for high-volume metrics to avoid CAS spin storms.
- **Memory Footprint:** Use `AtomicIntegerFieldUpdater` to perform lock-free operations directly on volatile fields across millions of entities.

**Common Follow-up Questions:**
- *"Why is `lazySet()` faster than `set()`?"* → Because `lazySet()` omits the expensive `StoreLoad` memory barrier, providing eventual consistency rather than immediate cross-thread visibility.
- *"Can Atomic classes guarantee atomicity across multiple variables?"* → No, an atomic class only protects a single variable. For multi-variable transactions, use `AtomicReference` holding an immutable DTO or use locks.
- *"What is the difference between `AtomicBoolean` and `volatile boolean`?"* → `volatile boolean` provides memory visibility; `AtomicBoolean` provides memory visibility plus atomic compound operations like `compareAndSet(expect, update)`.

**Red Flags (DO NOT Say):**
- ❌ *"Atomic classes use synchronized blocks under the hood."* (They are lock-free and use hardware CAS).
- ❌ *"AtomicInteger.incrementAndGet() is immune to thread contention."* (Under high contention, CAS spinning consumes significant CPU cycles; use `LongAdder`).
- ❌ *"AtomicReference prevents mutations to object fields inside the referenced instance."* (It only ensures atomic reassignment of the reference pointer itself).
