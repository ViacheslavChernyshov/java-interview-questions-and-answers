# What is the difference between synchronized method and synchronized block?

---

## 🟢 Junior Level

Both constructs enforce mutual exclusion using Java object monitors, but they differ fundamentally in **locking scope** and **lock target selection**:

```
  ┌──────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Characteristic       │ `synchronized` Method                    │ `synchronized` Block                             │
  ├──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Lock Target**      │ Strictly `this` (or `Class` if static)   │ Any designated object reference (`lock`)         │
  │ **Lock Scope**       │ **Entire method body**                   │ **Fine-grained custom section**                  │
  │ **Encapsulation**    │ Low (External code can lock `this`)      │ High (When using `private final Object lock`)    │
  │ **Flexibility**      │ Low (One lock per instance)              │ High (Multiple independent lock objects)         │
  └──────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

```java
public class Counter {
    private int count = 0;
    private final Object customLock = new Object();

    // 1. Synchronized Method: Locks the entire method on 'this'
    public synchronized void incrementMethod() {
        count++;
    }

    // 2. Synchronized Block: Locks ONLY the critical section on 'customLock'
    public void incrementBlock() {
        // Unsynchronized preparatory work...
        synchronized(customLock) {
            count++;
        }
        // Unsynchronized post-processing / logging...
    }
}
```

## 🟡 Middle Level

### Bytecode Architecture Comparison

```
  ┌──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────┐
  │ Syntax                           │ Bytecode Representation                                                 │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
  │ `public synchronized void foo()` │ Method flag: **`ACC_SYNCHRONIZED`** (No explicit monitor instructions)  │
  │ `synchronized(lock) { ... }`     │ Bytecode instructions: **`monitorenter`** and dual **`monitorexit`**   │
  └──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────┘
```

### The Private Lock Encapsulation Pattern

Using `synchronized(this)` or synchronized methods exposes your lock object to the outside world:

```java
// ❌ VULNERABLE: External code can interfere with class internals
public class Account {
    public synchronized void transfer() { /* critical section */ }
}

// Malicious / Accidental External Code:
Account acc = new Account();
synchronized(acc) {
    Thread.sleep(60_000); // 💥 FREEZES ALL Account synchronized methods across the app!
}
```

```java
// ✅ BEST PRACTICE: Private Lock Idiom prevents external interference
public class SecureAccount {
    private final Object internalLock = new Object(); // Inaccessible outside

    public void transfer() {
        synchronized(internalLock) {
            // Critical section fully protected against external locking attacks
        }
    }
}
```

### Fine-Grained Lock Striping

Synchronized blocks allow multiple independent locks inside the same class:

```java
public class UserCache {
    private final Map<Long, Profile> profiles = new HashMap<>();
    private final Map<Long, Image> avatars = new HashMap<>();

    private final Object profilesLock = new Object();
    private final Object avatarsLock = new Object();

    public Profile getProfile(Long id) {
        synchronized(profilesLock) { return profiles.get(id); }
    }

    public Image getAvatar(Long id) {
        synchronized(avatarsLock) { return avatars.get(id); } // Runs concurrently with profiles!
    }
}
```

## 🔴 Senior Level

### The Peril of `static synchronized`

```java
// ❌ CRITICAL BOTTLENECK: Locks the entire ClassLoader Class object
public class SystemConfig {
    public static synchronized void updateParam(String k, String v) {
        // Blocks ALL threads calling ANY static synchronized method in SystemConfig!
    }
}
```
> [!WARNING]
> `static synchronized` locks `SystemConfig.class`. In a high-throughput microservice, synchronizing on a Class object creates a global JVM-wide bottleneck. Replace with `ConcurrentHashMap` or a private static lock.

### Minimizing Lock Scope (Eliminating I/O Under Locks)

```java
// ❌ DISASTROUS: Blocking I/O inside synchronized hold
public synchronized void handleOrder(Order order) {
    validate(order);
    restTemplate.postForObject("/payment", order, Void.class); // 💥 Holds lock for 500ms!
    inventory.decrement(order.getItemId());
}

// ✅ IDIOMATIC: Lock strictly the in-memory mutation
public void handleOrder(Order order) {
    validate(order);
    restTemplate.postForObject("/payment", order, Void.class); // Non-blocking I/O outside lock
    synchronized(inventoryLock) {
        inventory.decrement(order.getItemId()); // 0.001ms hold time!
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Distinction:** Synchronized method locks `this` (or `Class`) across the entire method; synchronized block locks a specified object only for the enclosed block.
- **Bytecode:** Methods use the `ACC_SYNCHRONIZED` flag; blocks emit `monitorenter` and `monitorexit` instructions.
- **Private Lock Idiom:** `private final Object lock = new Object()` prevents external deadlocks and starvation.
- **Lock Scope:** Always extract blocking I/O, database calls, and network calls outside synchronized blocks.
- **Multiple Locks:** Synchronized blocks allow independent locks for disjoint shared resources.

**Common Follow-up Questions:**
- *"Why is `synchronized(this)` considered an architectural risk?"* → Because external callers holding a reference to the instance can lock it directly (`synchronized(instance)`), causing unexpected deadlocks or starvation.
- *"Why must a private lock object be declared `final`?"* → If the lock reference is not `final`, reassigning it while a thread is inside the synchronized block will allow other threads to acquire the new lock simultaneously, breaking mutual exclusion.
- *"How does the performance of an uncontended synchronized method compare to a synchronized block?"* → They have virtually identical performance (~10–20 ns); the real difference is in encapsulation and contention granularity.

**Red Flags (DO NOT Say):**
- ❌ *"Synchronized methods run 10x faster than synchronized blocks."* (Uncontended execution times are essentially identical).
- ❌ *"Synchronized blocks can lock primitive types like int."* (Monitors exist only on Java Heap objects; primitives cannot be locked).
- ❌ *"static synchronized locks all instances individually."* (It locks the single `Class` object, affecting all instances simultaneously).
