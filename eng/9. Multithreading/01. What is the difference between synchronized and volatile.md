# What is the difference between synchronized and volatile?

---

## 🟢 Junior Level

`synchronized` and `volatile` are two core keywords in Java for managing concurrent access to shared state:

```
  ┌──────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Feature              │ `volatile`                               │ `synchronized`                                   │
  ├──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Primary Guarantee**│ **Visibility & Ordering**                │ **Visibility + Atomicity + Mutual Exclusion**    │
  │ **Target Scope**     │ Variables (Fields only)                  │ Methods and Code Blocks                          │
  │ **Locking Model**    │ Non-blocking (Lock-free memory fences)   │ Blocking (Object Monitor acquisition)            │
  │ **Deadlock Risk**    │ **Impossible**                           │ **Possible**                                     │
  │ **Composite Ops**    │ ❌ Not atomic (`count++` causes races)   │ ✅ Fully atomic (Protected critical section)     │
  └──────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Basic `volatile` Example: State Flags
```java
public class TaskRunner {
    // volatile ensures any thread reading 'running' immediately sees writes from other threads
    private volatile boolean running = true;

    public void stop() {
        running = false; // Immediately flushed out of CPU cache to main memory
    }

    public void run() {
        while (running) {
            // Processing loop...
        }
    }
}
```

### Basic `synchronized` Example: Atomic Counter
```java
public class Counter {
    private int count = 0;

    // Mutex lock ensures only one thread executes increment at any given moment
    public synchronized void increment() {
        count++; // Atomic execution: read -> modify -> write
    }

    public synchronized int getCount() {
        return count;
    }
}
```

## 🟡 Middle Level

### The Java Memory Model (JMM) & Memory Barriers

Under JSR-133 (Java Memory Model), modern multi-core CPUs use multi-level hardware caches (L1/L2/L3) and execute instructions out-of-order.

#### How `volatile` Works Under the Hood
When accessing a `volatile` variable, the JVM inserts **Hardware Memory Barriers (Fences)**:

```
  Volatile Write Sequence:
    [Standard Reads & Writes]
    ──────── StoreStore Barrier ──────── (Flushes preceding writes before volatile store)
    [Volatile Write Instruction]
    ──────── StoreLoad Barrier ────────  (Prevents subsequent reads/writes from reordering above)

  Volatile Read Sequence:
    [Volatile Read Instruction]
    ──────── LoadLoad Barrier ────────   (Prevents subsequent reads from reordering above)
    ──────── LoadStore Barrier ────────  (Prevents subsequent writes from reordering above)
```

#### The `Happens-Before` Guarantee
A write to a `volatile` field **happens-before** every subsequent read of that same field. Any variable writes performed *before* the volatile write become visible to any thread that subsequent reads the volatile variable.

```java
int data = 0;
volatile boolean ready = false;

// Thread 1:
data = 42;
ready = true; // StoreStore + StoreLoad barrier flushes 'data' to RAM

// Thread 2:
if (ready) {
    System.out.println(data); // Guaranteed to print 42! (Never 0)
}
```

### The Double-Checked Locking (DCL) Trap

A classic senior interview question: **"Why is `volatile` strictly required in Double-Checked Locking?"**

```java
public class Singleton {
    // ⚠️ MUST BE volatile to prevent observing a partially initialized object!
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                         // 1st check (Lock-free)
            synchronized (Singleton.class) {
                if (instance == null) {                 // 2nd check (Thread-safe)
                    instance = new Singleton();         // Object construction & publication
                }
            }
        }
        return instance;
    }
}
```

#### The Instruction Reordering Hazard
Creating an object (`new Singleton()`) involves 3 steps in bytecode:
1. `allocate_memory()`
2. `invoke_constructor()` (Initialize fields)
3. `assign_reference(instance, pointer)`

Without `volatile`, the CPU/JIT compiler can reorder steps to `1 -> 3 -> 2`. If Thread B checks `instance != null` between steps 3 and 2, it receives a reference to an object whose constructor has not finished running! `volatile` forbids this reordering via the `StoreStore` barrier.

## 🔴 Senior Level

### Hardware Assembly & MESI Cache Coherency

On x86 / x86-64 architectures:
- Memory writes to `volatile` fields emit a **`lock addl $0, 0(%esp)`** or **`lock or`** instruction.
- The `lock` prefix locks the specific 64-byte CPU cache line and asserts the hardware **MESI (Modified, Exclusive, Shared, Invalid)** coherency broadcast, invalidating matching cache lines in all peer CPU cores.

```
  x86 Bytecode Translation:
  ┌─────────────────────────────────┬──────────────────────────────────────────┐
  │ Plain Field Write               │ Volatile Field Write                     │
  ├─────────────────────────────────┼──────────────────────────────────────────┤
  │ `movl $1, (%rax)`               │ `movl $1, (%rax)`                        │
  │                                 │ `lock addl $0, 0(%rsp)` (Full Fence)     │
  └─────────────────────────────────┴──────────────────────────────────────────┘
```

### Bytecode Anatomy: `monitorenter` & `monitorexit`

```java
synchronized(lock) {
    work();
}
```

Compiles into:
```bytecode
aload_1
monitorenter      // 1. Acquire object monitor lock
invokestatic #2   // 2. Execute work()
aload_1
monitorexit       // 3. Normal path monitor release
goto 14
astore_2
aload_1
monitorexit       // 4. Hidden exceptional finally path monitor release!
aload_2
athrow
```

> [!NOTE]
> `javac` always compiles **two `monitorexit` instructions** for every `monitorenter`: one for normal completion, and one inside a hidden synthetic exception table handler to guarantee lock release if exceptions occur.

### False Sharing & `@Contended` (JEP 142)

When multiple `volatile` variables reside inside the same 64-byte CPU cache line:
```java
public class MetricsCollector {
    @jdk.internal.vm.annotation.Contended // Pads cache line to isolate from counterB
    public volatile long counterA;
    public volatile long counterB;
}
```
Updating `counterA` forces the CPU to invalidate the entire cache line containing `counterB`, degrading multi-core throughput. `@Contended` adds 128 bytes of padding to eliminate false sharing.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Difference:** `volatile` guarantees visibility and ordering; `synchronized` guarantees visibility, atomicity, and mutual exclusion.
- **Scope:** `volatile` applies only to fields; `synchronized` applies to methods and code blocks.
- **Compound Operations:** `count++` is not safe with `volatile` because it decomposes into 3 bytecode operations (`getfield`, `iadd`, `putfield`).
- **Memory Barriers:** `volatile` inserts `StoreStore`, `StoreLoad`, `LoadLoad`, and `LoadStore` fences.
- **Double-Checked Locking:** `volatile` is mandatory on the singleton instance to prevent instruction reordering of constructor execution.
- **Deadlock:** Impossible with `volatile`, possible with `synchronized`.

**Common Follow-up Questions:**
- *"Can you use volatile for a multi-threaded counter?"* → No, use `AtomicInteger` or `LongAdder`; `volatile` does not provide atomicity for read-modify-write operations.
- *"What is the difference between volatile and AtomicBoolean?"* → `volatile boolean` only ensures visibility; `AtomicBoolean` provides visibility plus atomic lock-free CAS operations (`compareAndSet`).
- *"Why does synchronized have higher overhead than volatile?"* → `synchronized` involves monitor state checks, thread descheduling, OS parking, and context switches when contested.

**Red Flags (DO NOT Say):**
- ❌ *"volatile makes operations atomic."* (It only provides memory visibility; use Atomic classes or locks for atomicity).
- ❌ *"volatile and synchronized are completely interchangeable."* (They solve fundamentally different concurrency problems).
- ❌ *"Double-Checked Locking works safely without volatile in Java 8+."* (Without `volatile`, instruction reordering can publish half-initialized objects).
