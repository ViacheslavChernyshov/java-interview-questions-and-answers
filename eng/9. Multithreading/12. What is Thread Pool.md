# What is Thread Pool?

---

## 🟢 Junior Level

A **Thread Pool** is a managed collection of reusable worker threads that process asynchronous tasks from a shared work queue:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Without Thread Pool (Unbounded Thread Creation)        │ With Thread Pool (`ExecutorService`)                   │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ ❌ Allocates 1 MB native stack per thread              │ ✅ Fixed, bounded pool of persistent worker threads    │
  │ ❌ High OS context switching & instantiation latency   │ ✅ Tasks queue smoothly without crashing JVM memory    │
  │ ❌ Risk of `OOM: unable to create native thread`       │ ✅ Built-in task queueing, metrics, and back-pressure  │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// Production standard: Reuse 10 worker threads to process 1,000 tasks
ExecutorService pool = Executors.newFixedThreadPool(10);
for (int i = 0; i < 1_000; i++) {
    final int taskId = i;
    pool.submit(() -> processOrder(taskId));
}
```

## 🟡 Middle Level

### The 7 Parameters of `ThreadPoolExecutor`

```java
public ThreadPoolExecutor(
    int corePoolSize,                      // 1. Minimum baseline threads kept alive
    int maximumPoolSize,                   // 2. Maximum allowable thread burst capacity
    long keepAliveTime, TimeUnit unit,     // 3, 4. Idle time before terminating excess threads
    BlockingQueue<Runnable> workQueue,     // 5. Work queue holding pending tasks
    ThreadFactory threadFactory,           // 6. Factory for naming threads & setting daemon state
    RejectedExecutionHandler handler       // 7. Policy invoked when queue & threads saturate
);
```

### The Task Submission Algorithm (The Classic Interview Trap!)

```
  Incoming Task
       │
       ▼
  Running Threads < corePoolSize?
       ├─────► [YES] ──► Create new worker thread and execute immediately
       │
       ▼ [NO]
  Is workQueue full?
       ├─────► [NO]  ──► Enqueue task in workQueue (Threads pull from queue)
       │
       ▼ [YES]
  Running Threads < maximumPoolSize?
       ├─────► [YES] ──► Create new non-core worker thread
       │
       ▼ [NO]
  Trigger RejectedExecutionHandler (Saturated!)
```

> [!IMPORTANT]
> Non-core threads up to `maximumPoolSize` are **ONLY created AFTER the `workQueue` is completely full**. If an unbounded queue (`LinkedBlockingQueue`) is used, `maximumPoolSize` is completely ignored!

### The 4 Built-In Rejection Policies

```
  ┌──────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ Policy                               │ Saturation Behavior                                                         │
  ├──────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ **`AbortPolicy` (Default)**          │ Throws **`RejectedExecutionException`** immediately.                       │
  │ **`CallerRunsPolicy`**               │ Executes the task inside the **calling producer thread** (Back-Pressure!).  │
  │ **`DiscardPolicy`**                  │ Silently drops the task without throwing an exception.                      │
  │ **`DiscardOldestPolicy`**            │ Drops the oldest unhandled task from the queue head and retries submission. │
  └──────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Sizing Thread Pools (Goetz / Little's Law Formulas)

```
  1. CPU-Bound Tasks (Heavy computation, crypto, hashing):
     Pool Size = Number of CPU Cores + 1
     (The '+1' compensates for occasional page faults or OS interrupts)

  2. I/O-Bound Tasks (Database queries, HTTP REST clients, file systems):
     Pool Size = Number of CPU Cores × (1 + Wait Time / Compute Time)

     Example: If an average database query spends 90ms waiting on I/O and 10ms processing:
     Wait / Compute Ratio = 90 / 10 = 9
     On an 8-Core server: 8 × (1 + 9) = 80 Worker Threads!
```

### The `ThreadLocal` Memory Leak Danger

Worker threads in a pool never die during normal application lifecycles. If a task stores data in a `ThreadLocal` and fails to clear it, subsequent unrelated tasks executed by that same worker thread will **leak memory or read contaminated cross-tenant context**:

```java
// ❌ DANGEROUS: Contaminates pooled thread with stale user identity
pool.submit(() -> {
    SecurityContext.setTenantId("tenant-abc");
    handleRequest();
    // Missing cleanup!
});

// ✅ MANDATORY PATTERN: Always clear ThreadLocal in a finally block
pool.submit(() -> {
    try {
        SecurityContext.setTenantId("tenant-abc");
        handleRequest();
    } finally {
        SecurityContext.clear(); // 🚀 Crucial cleanup
    }
});
```

### Production Graceful Shutdown Protocol

```java
public void gracefulShutdown(ExecutorService executor) {
    executor.shutdown(); // 1. Reject new tasks; continue processing queued tasks
    try {
        if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
            executor.shutdownNow(); // 2. Cancel running tasks via Thread.interrupt()
            if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
                log.error("Worker pool did not terminate cleanly");
            }
        }
    } catch (InterruptedException ex) {
        executor.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Reusable pool of worker threads processing tasks from a thread-safe blocking queue.
- **7 Parameters:** `corePoolSize`, `maximumPoolSize`, `keepAliveTime`, `unit`, `workQueue`, `threadFactory`, `handler`.
- **Submission Order Trap:** `corePoolSize` $\to$ `workQueue` $\to$ `maximumPoolSize` $\to$ `RejectedExecutionHandler`.
- **Rejection Policies:** `CallerRunsPolicy` provides natural back-pressure by making the submitting thread execute the task.
- **Sizing:** CPU-bound: $N+1$; I/O-bound: $N \times (1 + W/C)$.
- **ThreadLocal Cleanup:** Always clean up `ThreadLocal` inside a `finally` block to prevent tenant data leakage.

**Common Follow-up Questions:**
- *"Why is `Executors.newCachedThreadPool()` dangerous in production?"* → It uses `SynchronousQueue` with `maximumPoolSize = Integer.MAX_VALUE`, creating unlimited native threads and causing out-of-memory crashes during traffic spikes.
- *"Why does `newFixedThreadPool` ignore `maximumPoolSize`?"* → Because it uses an unbounded `LinkedBlockingQueue`; the queue never fills up, so threads beyond `corePoolSize` are never spawned.
- *"What is the difference between `shutdown()` and `shutdownNow()`?"* → `shutdown()` stops accepting new tasks while draining existing queued tasks; `shutdownNow()` cancels queued tasks and sends `Thread.interrupt()` to running tasks.

**Red Flags (DO NOT Say):**
- ❌ *"A new thread is created up to maximumPoolSize before tasks are placed in the queue."* (Tasks are queued first; `maximumPoolSize` is reached only after the queue fills).
- ❌ *"Thread pools should be created as local variables inside method calls."* (Pools are expensive singletons; creating them in methods causes thread leaks).
- ❌ *"shutdownNow() forcibly kills OS threads immediately."* (It only sets the thread interrupt flag; tasks must handle `InterruptedException` gracefully).
