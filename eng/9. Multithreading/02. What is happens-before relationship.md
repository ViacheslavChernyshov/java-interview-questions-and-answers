# What is happens-before relationship?

---

## 🟢 Junior Level

The **Happens-Before (HB)** relationship is a formal **memory visibility guarantee** defined in JSR-133 (Java Memory Model).

> [!IMPORTANT]
> **Happens-before does NOT mean that action $A$ executes before action $B$ in chronological wall-clock time.**
> It strictly guarantees that **the memory writes produced by action $A$ are guaranteed to be visible to action $B$**, and the compiler/hardware is forbidden from reordering operations in a way that breaks this visibility.

```java
// Thread 1:
data = 42;             // Action A
ready = true;          // Action B (volatile write)

// Thread 2:
if (ready) {           // Action C (volatile read)
    System.out.println(data); // Guaranteed to print 42! (Never 0)
}
```

```
  Happens-Before Chain:
  Action A (data = 42) ──► Action B (ready = true)  [Program Order Rule]
                                  │
                                  ▼
  Action C (read ready) ──► Action D (read data)     [Volatile Rule + Transitivity]
```

## 🟡 Middle Level

### The 8 Formal JMM Happens-Before Rules (JSR-133)

```
  ┌───┬──────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ # │ JMM Rule                 │ Specification Contract                                                          │
  ├───┼──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Program Order**        │ In a single thread, each action HB every subsequent action in code order.       │
  │ 2 │ **Monitor Lock**         │ Unlocking a monitor (`monitorexit`) HB every subsequent lock on the SAME monitor│
  │ 3 │ **Volatile Variable**    │ A write to a `volatile` field HB every subsequent read of that same field.      │
  │ 4 │ **Thread Start**         │ Calling `thread.start()` HB all actions performed inside the started thread.    │
  │ 5 │ **Thread Termination**   │ All actions in a thread HB another thread successfully returning from `.join()`.│
  │ 6 │ **Interruption**         │ Calling `t.interrupt()` HB the target thread detecting it via `isInterrupted()`.│
  │ 7 │ **Finalizer**            │ Completion of an object constructor HB the invocation of its `finalize()`.      │
  │ 8 │ **Transitivity**         │ If $A \xrightarrow{hb} B$ and $B \xrightarrow{hb} C$, then $A \xrightarrow{hb} C$.│
  └───┴──────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Piggybacking on Happens-Before

Because of **Transitivity**, you can guarantee the visibility of multiple non-volatile fields using a single `volatile` write:

```java
int a = 0, b = 0, c = 0;
volatile boolean published = false;

// Producer Thread:
a = 10;
b = 20;
c = 30;
published = true; // Volatile write: flushes a, b, c to memory via StoreStore barrier

// Consumer Thread:
if (published) {  // Volatile read: pulls fresh cache lines via LoadLoad/LoadStore
    System.out.println(a + b + c); // Guaranteed to evaluate to 60!
}
```

## 🔴 Senior Level

### `final` Field Semantics & The Freeze Action

The JMM provides special memory visibility guarantees for `final` fields:
- When an object constructor finishes, the JVM executes an implicit **Freeze Action** on all `final` fields (equivalent to a `StoreStore` barrier).
- As long as the `this` reference is not leaked during construction (**Safe Publication**), any thread reading that object is guaranteed to observe the finalized values without needing `volatile` or `synchronized`.

```java
public class ImmutableConfig {
    private final String dbUrl; // JMM freeze guarantee ensures safe publication

    public ImmutableConfig(String host, int port) {
        this.dbUrl = "jdbc:postgresql://" + host + ":" + port;
        // Implicit JMM Freeze Barrier inserted before constructor exit
    }
}
```

### Hardware Translation: Memory Fences

Happens-Before is a high-level language specification. The JVM enforces it by inserting processor-specific **Memory Fences**:

```
  ┌─────────────────┬──────────────────────────────────────────────────┬───────────────────────────────┐
  │ Barrier Type    │ Reordering Prohibited                            │ x86/x64 Hardware Cost         │
  ├─────────────────┼──────────────────────────────────────────────────┼───────────────────────────────┤
  │ **LoadLoad**    │ Prohibits reordering of two consecutive reads    │ 🟢 Free (No-op on x86 TSO)    │
  │ **StoreStore**  │ Prohibits reordering of two consecutive writes   │ 🟢 Free (No-op on x86 TSO)    │
  │ **LoadStore**   │ Prohibits write from reordering before a read    │ 🟢 Free (No-op on x86 TSO)    │
  │ **StoreLoad**   │ Prohibits read from reordering before a write    │ 🔴 Expensive (`lock` / `mfence`)│
  └─────────────────┴──────────────────────────────────────────────────┴───────────────────────────────┘
```

### Empirical Verification: JCStress Framework

Unit tests cannot reliably detect memory ordering bugs. Production concurrency libraries (e.g. Netty, Caffeine) verify HB rules using **OpenJFX / OpenJDK JCStress (Java Concurrency Stress)**:

```java
@JCStressTest
@Outcome(id = {"42"}, expect = Expect.ACCEPTABLE, desc = "Properly published")
@Outcome(id = {"0"},  expect = Expect.FORBIDDEN,  desc = "Memory visibility bug!")
public class PublicationStressTest {
    int data = 0;
    volatile boolean ready = false;

    @Actor
    public void writer() {
        data = 42;
        ready = true;
    }

    @Actor
    public void reader(I_Result r) {
        if (ready) {
            r.r1 = data; // If data is 0, JCStress flags a fatal JMM violation
        }
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A formal memory visibility guarantee defined in JSR-133; ensures writes by action $A$ are visible to action $B$.
- **Not Wall-Clock Time:** HB specifies visibility and ordering constraints, not physical execution timestamps.
- **8 Rules:** Program Order, Monitor Lock, Volatile Variable, Thread Start, Thread Termination, Interruption, Finalizer, Transitivity.
- **Piggybacking:** Using transitivity to publish regular variables by writing a single `volatile` guard.
- **`final` Fields:** Automatically receive a JMM freeze guarantee upon constructor completion without synchronization.

**Common Follow-up Questions:**
- *"Does `Thread.start()` establish a happens-before relationship?"* → Yes. Everything written in the parent thread before calling `t.start()` is guaranteed to be visible to thread `t`.
- *"Why is StoreLoad the most expensive barrier on x86?"* → Because x86 CPUs allow Store-Load reordering (due to write buffers / store buffers); preventing it requires a CPU pipeline flush via `mfence` or a `lock` instruction.
- *"What happens if an object's `this` reference escapes during construction?"* → The JMM `final` field guarantee is completely voided, and other threads may observe uninitialized null or zero values.

**Red Flags (DO NOT Say):**
- ❌ *"Happens-before means that action A finished before action B started on the system clock."* (It is strictly a visibility guarantee).
- ❌ *"Every single variable in a class must be marked volatile to be visible."* (A single volatile write publishes all preceding writes via transitivity).
- ❌ *"All memory barriers have equal performance cost on x86 processors."* (StoreLoad is significantly more expensive than LoadLoad or StoreStore).
