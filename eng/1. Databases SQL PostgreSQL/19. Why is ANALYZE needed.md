# Why is ANALYZE needed?

---

## 🟢 Junior Level

**`ANALYZE`** is a PostgreSQL administrative command that inspects table data and populates internal statistical catalogs so the **Cost-Based Query Optimizer (Planner)** can accurately estimate query costs and select the fastest execution plan (e.g., deciding between an **Index Scan**, **Bitmap Scan**, or **Sequential Scan**).

**Simple analogy:** Before planning a road trip, GPS navigation software downloads real-time traffic speeds, road closures, and distance data. `ANALYZE` is the GPS survey that provides the database engine with accurate data maps.

**What `ANALYZE` collects:**
- Total row count estimates (`reltuples` in `pg_class`)
- Distinct value counts and uniqueness ratios (`n_distinct`)
- Most Common Values and their exact percentage frequencies (`most_common_vals`, `most_common_freqs`)
- Equi-depth histogram buckets for estimating range filters (`<`, `>`, `BETWEEN`)
- Physical disk vs logical sort correlation (`correlation`)

**Example:**
```sql
-- Analyze the entire database
ANALYZE;

-- Analyze a specific table and columns
ANALYZE users (email, country, status);

-- Run garbage collection + statistics collection in one command
VACUUM ANALYZE orders;
```

## 🟡 Middle Level

### Sampling Algorithm: Reservoir Sampling

`ANALYZE` **does not scan the entire table** (which would be too slow on Terabyte-scale datasets). Instead, it uses a two-stage **Reservoir Sampling** algorithm over randomized physical 8KB pages:

$$\text{Sample Row Count} = 300 \times \text{default\_statistics\_target}$$

- With default `default_statistics_target = 100`, PostgreSQL samples exactly **30,000 rows**, regardless of whether the table contains 100,000 rows or 500,000,000 rows!
- Sampling completes in milliseconds, providing a statistically sound bell-curve approximation.

### Catalog Exploration: Inspecting `pg_stats`

```sql
SELECT 
    attname AS column_name,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    ROUND(correlation::numeric, 2) AS correlation
FROM pg_stats
WHERE tablename = 'users' AND attname = 'status';
```

**How the Planner Uses `pg_stats`:**
- If `status = 'ACTIVE'` accounts for **90%** of rows (`most_common_freqs[1] = 0.90`), the planner chooses a **Sequential Scan** (avoiding costly random I/O index seeks).
- If `status = 'SUSPENDED'` accounts for **0.1%** of rows (`most_common_freqs[2] = 0.001`), the planner switches to an **Index Scan** for that exact same column!

### Common Pitfalls

#### 1. Bulk Data Ingestion without Immediate `ANALYZE`
```sql
-- Bulk insert 10,000,000 rows:
COPY orders FROM '/data/orders_dump.csv' WITH (FORMAT csv);

-- ❌ ANTI-PATTERN: Querying immediately causes disaster!
-- The planner still assumes the table has 0 rows, choosing disastrous Nested Loops!

-- ✅ MANDATORY PRODUCTION STEP:
ANALYZE orders;
```

#### 2. Temporary Tables Gotcha
The background `autovacuum` daemon **ignores temporary tables completely**. If you populate a large temporary table in a stored procedure or ETL pipeline, you **must run `ANALYZE temp_table` manually** before querying it.

## 🔴 Senior Level

### Extended Statistics: Cross-Column Correlation (`CREATE STATISTICS`)

By default, PostgreSQL evaluates single columns in total isolation, assuming mathematical independence:

$$P(\text{make} = \text{'Toyota'} \land \text{model} = \text{'Corolla'}) = P(\text{make} = \text{'Toyota'}) \times P(\text{model} = \text{'Corolla'})$$

In reality, knowing `make = 'Toyota'` means `model = 'Corolla'` is orders of magnitude more likely. The planner underestimates the result set size by 50x, inappropriately picking a Nested Loop instead of a Hash Join.

**Solution: Extended Multivariate Statistics**
```sql
-- 1. Functional Dependencies (knowing 'model' implies 'make')
CREATE STATISTICS s_cars_model_make (dependencies) 
ON make, model FROM cars;

-- 2. Multivariate Distinct Counts (joint n_distinct for multi-column grouping)
CREATE STATISTICS s_users_geo (ndistinct) 
ON country, state, city FROM users;

-- 3. Multivariate MCV Lists (PostgreSQL 13+: joint frequent combinations)
CREATE STATISTICS s_orders_status_priority (mcv) 
ON status, priority FROM orders;

-- Refresh catalog statistics:
ANALYZE cars, users, orders;
```

### Tuning Column-Level `statistics_target`

For columns exhibiting extreme data skew (e.g., status codes, tenant IDs, timestamps in time-series tables):

```sql
-- Increase histogram buckets from 100 to 1000 for a specific skewed column:
ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 1000;

-- ANALYZE now samples 300 * 1000 = 300,000 rows for this attribute
ANALYZE orders;
```

### Real-Time Statistics Collection Monitoring (PostgreSQL 13+)

Track running analyze operations on massive relations:
```sql
SELECT 
    p.pid,
    c.relname AS table_name,
    p.phase,
    p.sample_blks_total,
    p.sample_blks_scanned,
    ROUND(100.0 * p.sample_blks_scanned / NULLIF(p.sample_blks_total, 0), 2) AS sample_progress_pct
FROM pg_stat_progress_analyze p
JOIN pg_class c ON p.relid = c.oid;
```

### Expression Index Statistics

When creating a functional index, PostgreSQL automatically collects statistics on the **output expression**:
```sql
CREATE INDEX idx_users_lower_email ON users(LOWER(email));
ANALYZE users;
-- Planner now possesses accurate n_distinct and MCV histograms for LOWER(email)!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Purpose:** Gathers data distribution metrics (`n_distinct`, MCVs, histograms, correlation) into `pg_statistic` to guide cost-based query optimization.
- **Sampling:** Uses Reservoir Sampling ($300 \times \text{statistics\_target}$ rows; 30,000 rows by default), completing in $O(1)$ constant time regardless of table size.
- **Autovacuum Trigger:** Automatically runs when modified rows exceed $50 + (0.1 \times \text{n\_live\_tup})$.
- **Temporary Tables:** Autovacuum skips temp tables; manual `ANALYZE temp_table` is mandatory.
- **Bulk Load Best Practice:** Always execute `ANALYZE table` immediately after large `COPY` or `INSERT ... SELECT` batch operations.
- **Extended Statistics:** `CREATE STATISTICS ... (dependencies, ndistinct, mcv)` corrects multi-column correlation estimation errors.

**Common Follow-up Questions:**
- *"Why did our query performance collapse after importing 50 million rows with COPY?"* → The table statistics were not refreshed, so the optimizer assumed the table was empty and picked slow sequential scans or unindexed nested loops; running `ANALYZE` immediately resolves the issue.
- *"How does PostgreSQL estimate row counts for range queries like `WHERE age BETWEEN 25 AND 35`?"* → It evaluates the `histogram_bounds` array stored in `pg_stats` to compute the area under the equi-depth histogram buckets.
- *"What is the lock level of ANALYZE?"* → `ShareUpdateExclusiveLock`, which allows concurrent `SELECT`, `INSERT`, `UPDATE`, and `DELETE` queries to proceed without blocking.

**Red Flags (DO NOT Say):**
- ❌ *"ANALYZE scans every single row in the database table from start to finish."* (It uses randomized page reservoir sampling).
- ❌ *"Autovacuum will analyze temporary tables in stored procedures."* (Temporary tables are invisible to autovacuum).
- ❌ *"ANALYZE locks out readers and writers."* (It runs concurrently with read and write operations).
