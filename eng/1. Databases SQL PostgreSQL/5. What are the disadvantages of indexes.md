# What are the disadvantages of indexes?

---

## 🟢 Junior Level

**Indexes are not free:** they speed up read queries (`SELECT`) at the expense of slowing down write operations (`INSERT`, `UPDATE`, `DELETE`) and consuming disk and RAM.

**Simple analogy:** Think of an encyclopedia with multiple specialized indexes at the end (an index by subject, an index by chronological date, an index by geographic location, an index by author). Whenever a new article is added or edited, you must update not only the text of the article itself, but also find and update every single index. The more indexes you have, the more tedious and time-consuming every edit becomes.

**Core disadvantages:**
- ⚠️ **Write Performance Penalty:** Every `INSERT`, `UPDATE`, and `DELETE` must synchronize changes across every index on the table.
- ⚠️ **Disk Storage Consumption:** Indexes often consume more disk space than the actual table heap.
- ⚠️ **Maintenance Overhead:** Indexes suffer from fragmentation and bloat over time, requiring routine maintenance (`REINDEX`).

**Example:**
```sql
-- On a table with 5 indexes:
-- When inserting 1 new row:
-- 1. Insert row into the table heap
-- 2. Update Index #1 (Primary Key)
-- 3. Update Index #2 (email)
-- 4. Update Index #3 (customer_id)
-- 5. Update Index #4 (created_at)
-- 6. Update Index #5 (status)
-- Total: 6 distinct write operations and WAL entries instead of 1!
```

## 🟡 Middle Level

### 1. Write Amplification

Every index multiplies the physical I/O and Write-Ahead Log (WAL) operations required for mutations:

$$\text{1 INSERT Statement} = \text{1 Heap Block Write} + N \text{ Index Block Traversal Writes} + \text{WAL Logging}$$

| Index Count | Typical INSERT Latency | WAL Volume Multiplier |
|---|---|---|
| 1–2 | ~1 ms | 1x (Baseline) |
| 5–7 | 5–10 ms | 3x–5x |
| 10–15+ | 20–50+ ms | 10x–15x |

### 2. Disabling HOT (Heap-Only Tuple) Optimization

**HOT (Heap-Only Tuple)** is PostgreSQL's built-in optimization that allows `UPDATE` statements to avoid modifying any index pointers.

```sql
-- Index exists on 'status'
CREATE INDEX idx_orders_status ON orders(status);

-- ❌ This UPDATE modifies an indexed column -> Kills HOT, forces all indexes to update
UPDATE orders SET status = 'SHIPPED' WHERE id = 123;

-- ✅ This UPDATE modifies an unindexed column -> Can use HOT optimization
UPDATE orders SET notes = 'Deliver to front desk' WHERE id = 123;
```

**Requirements for HOT Optimization:**
1. The updated column must **not be part of any index definition**.
2. The new row version must fit inside the **same 8 KB heap page** as the previous version.

### 3. Index Bloat & Page Splits

Because B-tree indexes maintain strict sorting, inserting random values causes 8 KB pages to split when full. When rows are deleted or updated, pages are left with empty slots:
- Standard `VACUUM` marks slots as reusable for PostgreSQL, but **does not return physical disk space to the OS**.
- Bloated indexes require `REINDEX CONCURRENTLY` to restore compact leaf density.

### 4. RAM Cache Competition (`shared_buffers`)

Indexes compete directly with table data for cache space in RAM:
- If table size is 10 GB and indexes total 30 GB, an instance with 16 GB `shared_buffers` will experience high **Cache Misses**, forcing the OS and storage layer into continuous random disk seeks.

### 5. Increased Query Planning Time

Before executing a query, the cost-based optimizer must evaluate every available index candidate. Having dozens of indexes on a table noticeably inflates query compilation and planning latency.

## 🔴 Senior Level

### Write Amplification & Replica Lag

In high-throughput transactional systems with read replicas, index write amplification is a primary driver of **Physical Replication Lag**:
- Every index tuple insert, deletion, and B-tree page split generates WAL records.
- Standby replicas must replay WAL streams sequentially via a single recovery worker.
- Tables with 10+ indexes generate massive WAL volumes (e.g., hundreds of MBs per minute), saturating network bandwidth and causing read replicas to fall seconds or minutes behind the primary.

### Measuring HOT Update Efficiency

```sql
SELECT 
    schemaname,
    relname AS table_name,
    n_tup_hot_update AS hot_updates,
    n_tup_upd AS total_updates,
    ROUND(100.0 * n_tup_hot_update / NULLIF(n_tup_upd, 0), 2) AS hot_update_ratio_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 1000
ORDER BY hot_update_ratio_pct ASC;

-- Benchmark:
-- > 75%: Healthy OLTP application
-- < 20%: Severe issue; excessive indexing on updated columns or fillfactor too high (100)
```

### Diagnosing and Rebuilding Bloated Indexes

```sql
-- 1. Inspect leaf page fragmentation and density via pgstattuple
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT 
    index_name,
    avg_leaf_density,      -- Healthy: 70-90%. Below 50% indicates significant bloat
    leaf_fragmentation
FROM pgstatindex('idx_users_email');

-- 2. Zero-downtime online rebuild
REINDEX INDEX CONCURRENTLY idx_users_email;

-- 3. Zero-downtime full table and index repacking using pg_repack
-- Shell command: pg_repack -t orders -d production_db
```

### Measuring Cache Hit Ratio

```sql
SELECT 
    sum(heap_blks_read) AS disk_reads,
    sum(heap_blks_hit) AS cache_hits,
    ROUND(100.0 * sum(heap_blks_hit) / NULLIF(sum(heap_blks_read) + sum(heap_blks_hit), 0), 2) AS buffer_hit_ratio_pct
FROM pg_statio_user_tables;

-- Benchmark:
-- > 99%: Ideal in-memory working set
-- < 95%: Memory pressure caused by excessive index/table working sets
```

### Production Monitoring Queries

```sql
-- 1. Identify candidate indexes for removal (zero scans over past 30 days)
SELECT 
    s.schemaname,
    s.relname AS table_name,
    s.indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(s.indexrelid)) AS index_size,
    s.idx_scan AS scan_count
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0
  AND NOT i.indisunique
  AND NOT i.indisprimary
ORDER BY pg_relation_size(s.indexrelid) DESC;

-- 2. Inspect table fillfactor settings
SELECT 
    c.relname AS relation_name,
    c.relkind,
    c.reloptions
FROM pg_class c
WHERE c.reloptions IS NOT NULL;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Write Tax:** Every index adds write latency to `INSERT`/`UPDATE`/`DELETE` and expands WAL volume.
- **HOT Updates:** Updating an indexed column breaks Heap-Only Tuple optimization, requiring updates across all indexes and generating dead tuples.
- **Index Bloat:** B-tree page splits and dead tuples leave pages fragmented; standard `VACUUM` does not reclaim space to the OS (use `REINDEX CONCURRENTLY`).
- **Memory Pressure:** Indexes compete for `shared_buffers`; excess indexes evict hot table pages and trigger disk I/O bottlenecks.
- **Replication Lag:** High WAL generation caused by over-indexed tables directly increases read replica lag.

**Common Follow-up Questions:**
- *"Why is having 15 indexes on a table considered an anti-pattern?"* → It severely degrades write throughput, inflates WAL traffic causing replica lag, wastes RAM cache, and increases query planning time.
- *"What is a HOT update and how do indexes break it?"* → Heap-Only Tuple updates a row within the same page without updating index pointers. If any indexed column is modified, HOT is disabled.
- *"How do you diagnose index bloat in production?"* → Use `pgstatindex` from the `pgstattuple` extension; an `avg_leaf_density` under 50% indicates significant bloat requiring `REINDEX CONCURRENTLY`.

**Red Flags (DO NOT Say):**
- ❌ *"More indexes are always better because storage is cheap."* (Storage is cheap, but RAM cache and write I/O are expensive bottlenecks).
- ❌ *"Standard VACUUM shrinks index files on disk back to their original size."* (VACUUM only frees internal page slots; `REINDEX` or `VACUUM FULL` is needed to shrink the OS file).
- ❌ *"Indexes have no impact on SELECT query performance."* (Having too many indexes increases query planning time and pollutes `shared_buffers`).
