# What are Window Functions?

---

## 🟢 Junior Level

**Window functions** perform analytical calculations across a set of table rows that are related to the current row, **without collapsing** the rows into a single summary output (unlike `GROUP BY`).

**Core advantage:** Each row retains its individual identity and full column payload while displaying aggregate or ranking values computed across its partition.

**Simple analogy:** 
- **`GROUP BY`:** Sorting students into grade classrooms and reporting only the single class average on a whiteboard (individual student details vanish).
- **`Window Function`:** Handing each student their personal report card, showing their individual exam score alongside the class average.

**Example:**
```sql
-- Calculate both individual order amount and the customer's average order value
SELECT 
    user_id,
    order_id,
    amount,
    AVG(amount) OVER (PARTITION BY user_id) AS customer_avg_spent
FROM orders;

-- Output (Rows remain uncollapsed!):
-- user_id | order_id | amount | customer_avg_spent
-- 1       | 101      | 100    | 150
-- 1       | 102      | 200    | 150
-- 2       | 103      | 300    | 250
-- 2       | 104      | 200    | 250
```

**Common Categories:**
- **Ranking:** `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`
- **Aggregates:** `SUM() OVER()`, `AVG() OVER()`, `COUNT() OVER()`
- **Navigation (Offset):** `LAG()` (previous row), `LEAD()` (next row), `FIRST_VALUE()`, `LAST_VALUE()`

## 🟡 Middle Level

### Syntax and Clause Anatomy

```sql
FUNCTION() OVER (
    PARTITION BY department_id          -- 1. Divides table into distinct partitions
    ORDER BY hire_date ASC              -- 2. Orders rows within each partition
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW -- 3. Defines the sliding frame boundaries
)
```

### `GROUP BY` vs. Window Functions

| Feature | `GROUP BY` Aggregation | Window Functions (`OVER`) |
|---|---|---|
| **Row Multiplicity** | Collapses rows (1 output row per group) | Preserves all input rows (1:1 mapping) |
| **Mixing Granularity**| Cannot show raw details + aggregates | Seamlessly mixes row attributes and aggregates |
| **Pipeline Stage** | Evaluated **before** `HAVING` | Evaluated **after** `WHERE`, `GROUP BY`, `HAVING` |

### Framing Specifications: `ROWS` vs `RANGE` vs `GROUPS`

```sql
-- 1. ROWS: Physical row count (Fastest in-memory traversal)
-- Calculates 7-row moving average (current row + 6 preceding rows)
SELECT date, amount,
       AVG(amount) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7_rows
FROM sales;

-- 2. RANGE: Logical value intervals (Handles duplicate timestamps properly)
-- Calculates true 7-day interval moving sum
SELECT date, amount,
       SUM(amount) OVER (ORDER BY date RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW) AS weekly_sum
FROM sales;
```

> **Deep Dive: Default Framing Gotcha:** When you specify `ORDER BY` inside `OVER (...)` without an explicit frame, SQL defaults to `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. This can cause performance issues because Postgres must track duplicate key peers. Adding `ROWS UNBOUNDED PRECEDING` switches to physical pointer arithmetic, speeding up execution.

### Common Pitfalls

#### 1. Attempting to Filter Window Functions in `WHERE`
```sql
-- ❌ SYNTAX ERROR: Window functions execute in SELECT, after WHERE
SELECT user_id, amount,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY amount DESC) AS rn
FROM orders
WHERE rn = 1;

-- ✅ SOLUTION: Wrap in a CTE or Subquery
WITH ranked AS (
    SELECT user_id, amount,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY amount DESC) AS rn
    FROM orders
)
SELECT user_id, amount FROM ranked WHERE rn = 1;
```

#### 2. Running `COUNT(*) OVER()` Solely for UI Pagination
Adding `COUNT(*) OVER() AS total_count` to a `LIMIT 20` query forces the engine to scan and count the **entire** partition/table, negating the performance benefits of `LIMIT`. Use a separate asynchronous count query when possible.

## 🔴 Senior Level

### Execution Engine Internals: `WindowAgg` Node

In `EXPLAIN` query plans, window functions evaluate inside a **`WindowAgg`** plan node:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT department_id, salary,
       AVG(salary) OVER (PARTITION BY department_id ORDER BY hire_date)
FROM employees;
-- WindowAgg (cost=... actual rows=1000000)
--   -> Sort (Sort Key: department_id, hire_date)  <-- Expensive sort pass
--       -> Seq Scan on employees
```

#### Eliminating Sort Nodes via B-Tree Indexes
By building a composite index matching both `PARTITION BY` and `ORDER BY` keys in exact order:
```sql
CREATE INDEX idx_emp_dept_hire ON employees(department_id, hire_date);
-- Execution changes to: WindowAgg -> Index Only Scan (ZERO in-memory sorting!)
```

### Named Window Clause (`WINDOW w AS ...`)

Eliminate code duplication and ensure identical partition sorting structures across multiple window calculations:

```sql
SELECT 
    department_id,
    name,
    salary,
    AVG(salary) OVER w AS dept_avg,
    SUM(salary) OVER w AS dept_running_total,
    RANK() OVER w AS tenure_rank
FROM employees
WINDOW w AS (PARTITION BY department_id ORDER BY hire_date ASC);
```

### Advanced Framing: The `EXCLUDE` Clause (PostgreSQL 11+)

```sql
-- Calculate the average salary of all OTHER employees in the department (excluding self)
SELECT 
    name,
    department_id,
    salary,
    AVG(salary) OVER (
        PARTITION BY department_id 
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
        EXCLUDE CURRENT ROW
    ) AS peers_avg_salary
FROM employees;
```
- `EXCLUDE CURRENT ROW`: Omits the active row from accumulator totals.
- `EXCLUDE GROUP`: Omits the current row and all duplicate peers matching its sort key.
- `EXCLUDE TIES`: Retains the current row, but omits any duplicate peers.

### Incremental Sort Integration (PostgreSQL 13+)

If an index exists on `(department_id)`, but not on `(department_id, hire_date)`:
PostgreSQL 13+ leverages **Incremental Sort**, sorting only the small slices of `hire_date` within each pre-grouped `department_id` partition instead of running a monolithic $O(N \log N)$ sort across the entire table.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Concept:** Window functions calculate aggregates and rankings across partitions without collapsing individual input rows.
- **Pipeline Stage:** Evaluated in `SELECT`, strictly **after** `WHERE`, `GROUP BY`, and `HAVING`.
- **Filtering Rule:** You cannot filter window function results in `WHERE` or `HAVING`; you must wrap the query in a CTE or derived subquery.
- **Framing:** `ROWS` computes physical offsets (faster); `RANGE` computes logical value deltas (properly groups duplicate peers).
- **Index Optimization:** A composite index on `(PARTITION BY cols, ORDER BY cols)` allows `WindowAgg` to run streaming without a `Sort` node.
- **DRY Code:** The `WINDOW` clause declares named window specifications reusable across multiple expressions.

**Common Follow-up Questions:**
- *"Why does `WHERE ROW_NUMBER() OVER (...) = 1` throw an error?"* → `WHERE` executes before window calculations in the SQL logical query pipeline.
- *"What is the performance difference between `ROWS UNBOUNDED PRECEDING` and `RANGE UNBOUNDED PRECEDING`?"* → `ROWS` uses simple row index arithmetic; default `RANGE` evaluates peer row comparisons, adding CPU overhead.
- *"How can you calculate a 30-day moving average in PostgreSQL?"* → Use `AVG(amount) OVER (ORDER BY order_date RANGE BETWEEN INTERVAL '30 days' PRECEDING AND CURRENT ROW)`.

**Red Flags (DO NOT Say):**
- ❌ *"Window functions collapse rows like GROUP BY."* (They always maintain a 1:1 mapping with input rows).
- ❌ *"You can nest window functions inside each other like `AVG(SUM(...) OVER()) OVER()`."* (Window function nesting is forbidden; use CTE pipelines).
- ❌ *"Window functions cannot use indexes."* (Indexes matching `PARTITION BY` + `ORDER BY` enable streaming zero-sort execution).
