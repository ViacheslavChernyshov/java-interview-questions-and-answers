# When should you create an index?

---

## 🟢 Junior Level

You should create an index when **queries on a table are unacceptably slow** and you have identified specific columns frequently used for filtering, joining, or sorting.

**Simple analogy:** If you frequently look up contacts in a directory by phone number instead of person name, it makes sense to add a dedicated "reverse lookup by phone number" index. But adding an index for shoe size or eye color would be a waste of paper and effort.

**Core idea:**
- Indexes speed up data retrieval (`SELECT`) but slow down modifications (`INSERT`, `UPDATE`, `DELETE`).
- Create indexes for columns appearing in `WHERE`, `JOIN ... ON`, and `ORDER BY` clauses.
- **Never** create indexes "just in case" without analyzing actual query workloads.

**Example:**
```sql
-- Slow query performing a full table scan across millions of users
SELECT * FROM users WHERE email = 'test@example.com';

-- Create an index
CREATE INDEX idx_users_email ON users(email);

-- Fast query utilizing index lookup
SELECT * FROM users WHERE email = 'test@example.com';
```

**When to create an index:**
- A column is frequently filtered with high selectivity (e.g., `email`, `ssn`, `uuid`, `username`).
- A column is a **Foreign Key** referencing another table.
- A column is used in `ORDER BY` with `LIMIT` on large tables.
- The table contains more than 10,000 rows.

## 🟡 Middle Level

### How to Identify Indexing Needs

#### 1. Analyze Slow Query Logs
```ini
# postgresql.conf
log_min_duration_statement = 500  # Logs all queries taking longer than 500ms
```

#### 2. Query Statistics via `pg_stat_statements`
```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Find top 10 queries consuming the most total execution time
SELECT 
    query, 
    calls,
    mean_exec_time AS avg_time_ms,
    total_exec_time AS total_time_ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

### Core Criteria for Creating Indexes

#### 1. High Selectivity Filters in `WHERE`
```sql
-- ✅ High selectivity (almost every row has a unique value) -> Excellent index candidate
CREATE INDEX idx_users_email ON users(email);

-- ❌ Low selectivity (only 2 distinct values across millions of rows) -> Poor candidate
CREATE INDEX idx_users_gender ON users(gender); -- M / F
```

#### 2. Foreign Key Columns
```sql
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id) -- ⚠️ Always index foreign keys!
);

-- Index the FK column
CREATE INDEX idx_orders_user_id ON orders(user_id);
```
*Why?* When a parent row is deleted or updated in `users`, PostgreSQL must verify that no referencing rows exist in `orders`. Without an index on `orders.user_id`, PostgreSQL is forced to perform a full `Seq Scan` on `orders`, taking table-level locks and triggering massive performance degradation.

#### 3. Columns in `JOIN` Conditions
Foreign keys and join keys for **Nested Loop** joins require B-tree indexes on the inner table to achieve $O(N \log M)$ execution instead of $O(N \times M)$ cartesian loops.

#### 4. Pre-sorting for `ORDER BY` and `GROUP BY`
```sql
CREATE INDEX idx_orders_created ON orders(created_at DESC);

-- Query executes instantly without an in-memory Sort node
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
```

### Common Pitfalls

1. **Indexing Without Workload Verification:** Adding indexes proactively before measuring production access patterns.
2. **Redundant Duplicate Indexes:**
   ```sql
   CREATE INDEX idx_email_1 ON users(email);
   CREATE INDEX idx_email_2 ON users(email); -- Redundant duplicate
   ```
3. **Indexing Small Lookup Tables:** For tables under 1,000 rows, a sequential scan in memory is faster than navigating a B-tree and reading the heap.

## 🔴 Senior Level

### Workload Analysis and Diagnostics

#### 1. Disk I/O Bottlenecks in `pg_stat_statements`
```sql
SELECT 
    query,
    calls,
    mean_exec_time,
    total_exec_time,
    shared_blks_read,    -- Disk reads (high = cache miss bottleneck)
    shared_blks_hit      -- Buffer cache hits
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
ORDER BY total_exec_time DESC
LIMIT 20;

-- Key diagnostic metric: shared_blks_read / calls > 100
-- Indicates that each query execution reads over 100 pages from disk -> Missing index!
```

#### 2. Testing Virtual Indexes with `HypoPG`
`HypoPG` lets you evaluate whether PostgreSQL's query optimizer would actually choose an index before creating it on disk:
```sql
CREATE EXTENSION IF NOT EXISTS hypopg;

-- Create a hypothetical in-memory index (takes 0 disk space)
SELECT * FROM hypopg_create_index(
    'CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC)'
);

-- Run EXPLAIN to verify if the planner chooses it
EXPLAIN SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;
-- Plan will show: Index Scan using <hypothetical_index_name>...

-- Drop the hypothetical index
SELECT * FROM hypopg_drop_index(indexrelid);
```

### Architectural Trade-offs & Production Considerations

#### 1. Write Amplification & WAL Generation
Every additional index adds a write tax:
- `INSERT`: Inserts a new index tuple across every index on the table.
- `UPDATE`: Updates index entries unless HOT optimization applies.
- `WAL Volume`: Index page splits and updates generate heavy Write-Ahead Log volume, directly increasing **Physical Replication Lag** across read replicas.

| Number of Indexes | Typical INSERT Latency Overhead | WAL Generation Multiplier |
|---|---|---|
| 1–2 | +5–10% | Baseline |
| 5–7 | +50–100% | 2x–3x |
| 10–15+ | +200–500% | 5x–10x |

#### 2. Partial Indexes for Skewed Workloads
```sql
-- Target only unresolved error logs (5% of table)
CREATE INDEX idx_errors_unprocessed ON system_events(created_at)
WHERE status = 'UNPROCESSED';
-- Saves 95% disk space and WAL traffic while making hot queries instant
```

#### 3. Online Production Index Creation (`CONCURRENTLY`)
```sql
-- Never run bare CREATE INDEX on active production tables!
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
```

#### 4. Bulk Load Optimization Pattern
```sql
-- When inserting millions of rows:
-- 1. Drop non-essential indexes
DROP INDEX idx_orders_user_id;

-- 2. Bulk load data efficiently
COPY orders FROM '/data/orders.csv' WITH (FORMAT csv);

-- 3. Recreate indexes in parallel
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);
```

### Production Monitoring Queries

```sql
-- 1. Identify unindexed Foreign Keys (major source of Seq Scans and locking issues)
SELECT 
    conrelid::regclass AS child_table,
    conname AS fk_constraint_name,
    confrelid::regclass AS parent_table
FROM pg_constraint
WHERE contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index
    WHERE indrelid = conrelid
      AND indkey[0] = ANY(conkey)
  );

-- 2. Check for unused indexes in production
SELECT 
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan AS scan_count,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan ASC
LIMIT 20;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Decision Workflow:** Measure workload with `pg_stat_statements` → verify query plan with `EXPLAIN (ANALYZE, BUFFERS)` → test with `HypoPG` → create using `CONCURRENTLY`.
- **Always Index Foreign Keys:** Prevents full table locks and full table scans on child tables during parent row `DELETE`/`UPDATE`.
- **High Selectivity:** Indexes are most effective on columns matching a small percentage (< 5–10%) of the table.
- **Write Tax:** Every index increases `INSERT`/`UPDATE`/`DELETE` latency, WAL generation, and replica lag.
- **Bulk Loading:** For massive data loads, drop indexes, load data via `COPY`, and rebuild indexes afterwards.

**Common Follow-up Questions:**
- *"How do you diagnose which queries need an index?"* → Inspect `pg_stat_statements` for high `total_exec_time` and high `shared_blks_read / calls` ratio (> 100).
- *"Why must Foreign Keys almost always be indexed?"* → Because parent row updates/deletes check child table referential integrity via sequential scans if unindexed, taking shared locks and stalling writes.
- *"How can you test index effectiveness without creating it in production?"* → Use the `HypoPG` extension to create in-memory virtual indexes and inspect the query plan.

**Red Flags (DO NOT Say):**
- ❌ *"I create indexes on every single column just to be safe."* (Causes massive write amplification, storage bloat, and kills HOT updates).
- ❌ *"Running CREATE INDEX directly on production tables during business hours is fine."* (Blocks all writes with an `ACCESS EXCLUSIVE` lock; always use `CONCURRENTLY`).
- ❌ *"Small tables always run faster with indexes."* (Sequential scans are faster on tables with fewer than a few hundred to a thousand rows).
