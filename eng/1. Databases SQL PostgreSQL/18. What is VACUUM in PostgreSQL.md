# What is VACUUM in PostgreSQL?

---

## 🟢 Junior Level

**`VACUUM`** is PostgreSQL's built-in garbage collection and storage maintenance utility. Because PostgreSQL's MVCC architecture handles updates and deletes out-of-place, rows modified or removed are left behind as **dead tuples** inside database pages.

**Primary functions of VACUUM:**
1. **Reclaims dead tuple space:** Cleans up dead row versions so their space within 8KB heap pages can be reused by future `INSERT` and `UPDATE` operations.
2. **Prevents table bloat:** Stops database files from growing uncontrollably.
3. **Updates the Visibility Map:** Marks pages where all tuples are committed and visible to all transactions, accelerating **Index-Only Scans**.
4. **Freezes aging Transaction IDs:** Prevents fatal **XID Wraparound** database outages.

**Example:**
```sql
-- Standard background cleanup (Non-blocking, safe for production)
VACUUM users;

-- Rebuilds entire table, frees space to OS, but takes an exclusive lock
VACUUM FULL users;

-- Standard vacuum combined with optimizer statistics collection
VACUUM ANALYZE users;
```

## 🟡 Middle Level

### Standard `VACUUM` vs. `VACUUM FULL`

| Feature | Standard `VACUUM` | `VACUUM FULL` |
|---|---|---|
| **Lock Level** | `ShareUpdateExclusiveLock` (Allows concurrent reads and writes) | `AccessExclusiveLock` (Blocks ALL reads and writes) |
| **Frees Disk Space to OS** | ❌ No (Reclaims space internally inside the 8KB page Free Space Map) | ✅ Yes (Rewrites table into a brand new compact file) |
| **Execution Speed** | Fast / Throttled in background | Slow / Heavy I/O disk write overhead |
| **Index Handling** | Sweeps index pointers pointing to dead heap tuples | Completely rebuilds all table indexes from scratch |
| **Production Safety** | ✅ Safe to run 24/7 during business hours | ❌ Forbidden during peak hours; use **`pg_repack`** instead |

> **Exception:** In PostgreSQL 12+, standard `VACUUM` will truncate completely empty pages from the **very end (tail)** of a relation file back to the OS.

### Autovacuum Trigger Calculation

The background `autovacuum` daemon automatically triggers a vacuum sweep on a table when the number of dead tuples exceeds a calculated threshold:

$$\text{Trigger Threshold} = \text{autovacuum\_vacuum\_threshold} + (\text{autovacuum\_vacuum\_scale\_factor} \times \text{n\_live\_tup})$$

- **Default Parameters:** `threshold = 50`, `scale_factor = 0.2` (20%).

```sql
-- The Scale Factor Problem on Large Tables:
-- A table with 100,000,000 rows requires: 50 + (0.2 * 100,000,000) = 20,000,050 dead tuples!
-- Autovacuum runs far too late, causing massive bloat.

-- Production Solution: Lower scale factor for high-write tables:
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.02,  -- Trigger at 2% dead rows instead of 20%
    autovacuum_vacuum_cost_limit = 1000     -- Increase I/O budget for faster completion
);
```

## 🔴 Senior Level

### Cost-Based Vacuum Throttling Internals

To prevent background cleanup from saturating disk I/O and starving production client transactions, PostgreSQL enforces **Cost-Based Vacuum Throttling**:

```
Internal Action Cost Accounting:
  - Hit tuple in shared_buffers:   vacuum_cost_page_hit   = 1
  - Read page from OS cache/disk: vacuum_cost_page_miss  = 2 (or 10)
  - Dirty/Write page to disk:     vacuum_cost_page_dirty = 20
```

When the accumulated cost counter reaches `autovacuum_vacuum_cost_limit` (default: `200`), the worker process sleeps for `autovacuum_vacuum_cost_delay` (default: `2ms`).
*Modern NVMe SSD Tuning:* Set `autovacuum_vacuum_cost_limit = 2000` and `autovacuum_vacuum_cost_delay = 0` (or `2ms`) so vacuum finishes in minutes rather than throttling over days.

### Parallel Index Vacuuming (PostgreSQL 13+)

In PostgreSQL 13+, `VACUUM` can clean multiple B-tree indexes on a single table simultaneously in parallel:
```sql
VACUUM (PARALLEL 4, VERBOSE) large_table;
-- Uses 4 parallel worker processes to sweep 4 distinct B-tree indexes simultaneously!
```

### Real-Time Vacuum Progress Tracking

Monitor active vacuum jobs in production:
```sql
SELECT 
    p.pid,
    c.relname AS table_name,
    p.phase,
    p.heap_blks_total,
    p.heap_blks_scanned,
    p.heap_blks_vacuumed,
    ROUND(100.0 * p.heap_blks_scanned / NULLIF(p.heap_blks_total, 0), 2) AS scan_progress_pct
FROM pg_stat_progress_vacuum p
JOIN pg_class c ON p.relid = c.oid;
```

### Zero-Downtime Table Compaction: `pg_repack`

Because `VACUUM FULL` locks out all production traffic, high-availability PostgreSQL deployments rely on the **`pg_repack`** extension:

```bash
# Reclaims disk space and compacts the 'orders' table with zero read/write downtime:
pg_repack -h localhost -U postgres -d production_db -t orders
```
**Mechanism:**
1. Creates a compact shadow copy of the table.
2. Attaches a trigger to the original table to capture ongoing concurrent `INSERT`/`UPDATE`/`DELETE` operations into a log table.
3. Applies logged delta changes to the shadow table.
4. Acquires an instantaneous lock to swap the catalog names and drops the old bloated relation.

### Anti-Wraparound Emergency Freezing

When `age(datfrozenxid) > autovacuum_freeze_max_age` (default: **200,000,000 XIDs**), PostgreSQL spawns an **aggressive anti-wraparound autovacuum**.
- It ignores standard cost throttling.
- It **cannot be canceled** via `pg_cancel_backend()`.
- If neglected until `age = 2,000,000,000`, the PostgreSQL cluster will immediately halt and enter emergency single-user read-only mode to prevent silent data corruption.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Standard `VACUUM`:** Non-blocking (`ShareUpdateExclusiveLock`); reclaims dead tuple slots inside 8KB pages (Free Space Map) for future reuse, but does NOT shrink files.
- **`VACUUM FULL`:** Rewrites the entire table file to return space to the OS, but acquires an exclusive lock (`AccessExclusiveLock`) blocking all queries.
- **`pg_repack`:** Production standard for reclaiming disk space with zero downtime.
- **Trigger Formula:** $\text{dead\_tuples} > \text{threshold} + (\text{scale\_factor} \times \text{total\_rows})$.
- **Throttling:** Regulated by `vacuum_cost_limit` and `vacuum_cost_delay` to protect disk I/O.
- **Visibility Map:** VACUUM updates the VM, enabling Index-Only Scans and skipping clean pages during subsequent runs.
- **Anti-Wraparound:** Mandatory aggressive freeze triggered when transaction age passes 200M XIDs.

**Common Follow-up Questions:**
- *"Why didn't my database disk size decrease after running VACUUM on a table where I deleted 10 million rows?"* → Standard VACUUM only updates the internal Free Space Map (FSM) within existing page blocks for future inserts; to return space to the OS, you must use `VACUUM FULL` or `pg_repack`.
- *"How do you diagnose why autovacuum is failing to clean dead tuples?"* → Check `pg_stat_activity` for long-running open transactions, idle in transaction sessions, or abandoned replication slots holding back the `xmin` horizon.
- *"How do you speed up autovacuum on high-throughput NVMe SSD servers?"* → Lower table-level `autovacuum_vacuum_scale_factor` to `0.01`–`0.05` and increase `autovacuum_vacuum_cost_limit` to `1000`–`2000`.

**Red Flags (DO NOT Say):**
- ❌ *"Running VACUUM FULL every night in production is good practice."* (It takes an `AccessExclusiveLock`, causing major application outages).
- ❌ *"Standard VACUUM returns freed disk space back to the operating system."* (It only frees space inside the relation's internal 8KB pages).
- ❌ *"You should disable autovacuum globally to boost write speeds."* (Disabling autovacuum leads to catastrophic XID wraparound downtime).
