# What is a correlated subquery?

---

## 🟢 Junior Level

A **correlated subquery** is an inner SQL subquery that references one or more column values from the **outer query block**. 

Because of this cross-reference, the inner subquery cannot execute in isolation; logically, it must re-evaluate **for every single row** processed by the outer query (similar to a nested `for` loop in programming).

**Simple analogy:** Imagine a teacher grading a stack of exam papers. For each individual student's paper, the teacher must open a separate grade registry, search for that specific student's attendance records, and compute a custom bonus. For 100 students, the teacher opens and searches the registry 100 times.

**Example:**
```sql
-- For each user, retrieve the amount of their most recent order
SELECT 
    u.name,
    (SELECT o.total_amount 
     FROM orders o 
     WHERE o.user_id = u.id  -- ⚠️ References the outer row 'u.id'
     ORDER BY o.created_at DESC 
     LIMIT 1) AS last_order_amount
FROM users u;
```

**Why it matters:** While correlated subqueries are syntactically concise and intuitive to write, on large datasets (e.g., 1,000,000 users) an unoptimized correlated subquery will execute 1,000,000 distinct sub-queries, resulting in severe $O(N \times M)$ database performance bottlenecks.

## 🟡 Middle Level

### Logical vs. Physical Execution

#### Logical Execution Model: $O(N \times M)$
```
for outer_row in outer_table:           # N rows (e.g., 1,000,000)
    result = execute_inner_subquery(outer_row.key)  # Executes 1,000,000 times!
    emit(outer_row, result)
```

#### Physical Decorrelation (Unnesting to Semi-Join)
Whenever possible, PostgreSQL's query optimizer attempts to **decorrelate** the subquery into a set-based join:
```sql
-- Written as a Correlated EXISTS subquery:
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o 
    WHERE o.user_id = u.id AND o.total_amount > 500
);

-- Decorrelated by PostgreSQL into:
-- Plan: Hash Semi-Join (Executes in O(N + M) time via a single hash table pass!)
```

### Identifying `SubPlan` vs. `InitPlan` in Query Plans

- **`SubPlan` (Bad / Bottleneck):** The subquery remains correlated and executes iteratively for **every single outer row**.
  ```sql
  EXPLAIN SELECT u.name, (SELECT SUM(total_amount) FROM orders o WHERE o.user_id = u.id) FROM users u;
  -- Seq Scan on users u
  --   SubPlan 1 -> Aggregate -> Index Scan on orders o (user_id = u.id)  <-- Multiplied by N!
  ```
- **`InitPlan` (Good / Static):** The subquery is uncorrelated, evaluated **exactly once** before main execution, and cached as a parameter.
  ```sql
  EXPLAIN SELECT * FROM users WHERE salary > (SELECT AVG(salary) FROM employees);
  -- InitPlan 1 -> Aggregate -> Seq Scan on employees  <-- Evaluates ONCE
  -- Seq Scan on users (Filter: salary > $0)
  ```

### Optimized Alternatives to Correlated Subqueries

| Scenario | Anti-Pattern (Correlated Subquery) | Optimal Production Pattern |
|---|---|---|
| Per-Row Aggregation | Scalar Subquery in `SELECT` | `LEFT JOIN ... GROUP BY` or **Window Function** |
| Top-N Related Records | Correlated Subquery with `LIMIT 1` | `LEFT JOIN LATERAL` or `ROW_NUMBER()` Window Function |
| Existence Filter | `WHERE id IN (correlated subquery)` | `WHERE EXISTS (...)` (Compiles to **Semi-Join**) |
| Correlated `UPDATE` | `UPDATE ... WHERE col = (SELECT ...)` | `UPDATE ... FROM (CTE / JOIN)` |

## 🔴 Senior Level

### Deep Dive: PostgreSQL 14+ `Memoize` Optimization Node

In parameterized Nested Loops and `LATERAL` joins, PostgreSQL 14 introduced the **Memoize** execution node to cache subquery evaluation outputs in memory:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, recent_order.total_amount
FROM users u
LEFT JOIN LATERAL (
    SELECT total_amount FROM orders o
    WHERE o.user_id = u.id
    ORDER BY created_at DESC LIMIT 1
) recent_order ON true;

-- PostgreSQL 14+ Plan Output:
-- Nested Loop (cost=... actual rows=1000000)
--   -> Seq Scan on users u
--   -> Memoize (Hits: 850000, Misses: 150000, Evictions: 0, Cache Size: 8MB)
--       -> Limit
--           -> Index Scan on orders o (Index Cond: user_id = u.id)
```

**Diagnostic Analysis:**
- **Cache Hit Ratio:** $\frac{\text{Hits}}{\text{Hits} + \text{Misses}} = \frac{850,000}{1,000,000} = 85\%$ (Superb speedup!).
- If the outer dataset has nearly 100% unique IDs, `Hits` will be near 0, rendering Memoize ineffective.

### High-Performance Correlated `UPDATE` Pattern

Running correlated subqueries inside `UPDATE` or `DELETE` statements on millions of rows is a common cause of production outages:

```sql
-- ❌ CATASTROPHIC ANTI-PATTERN: Evaluates subquery for every order (100M executions)
UPDATE orders o 
SET status = 'ARCHIVED'
WHERE created_at < (
    SELECT MIN(created_at) + INTERVAL '1 year'
    FROM users u 
    WHERE u.id = o.user_id
);

-- ✅ OPTIMAL: Precompute threshold once via CTE and execute via UPDATE ... FROM
WITH user_cutoffs AS (
    SELECT id AS user_id, MIN(created_at) + INTERVAL '1 year' AS cutoff_date
    FROM users
    GROUP BY id
)
UPDATE orders o
SET status = 'ARCHIVED'
FROM user_cutoffs uc
WHERE o.user_id = uc.user_id
  AND o.created_at < uc.cutoff_date;
-- Compiles to Hash Join: 2 sequential/indexed passes instead of 100,000,000 subqueries!
```

### Window Functions vs. Correlated Aggregation

```sql
-- ❌ Correlated Subquery: O(N * M) nested scan overhead
SELECT o.id, o.user_id, o.total_amount,
       (SELECT AVG(total_amount) FROM orders o2 WHERE o2.user_id = o.user_id) AS user_avg
FROM orders o;

-- ✅ Window Function: O(N log N) single pass with in-memory WindowAgg
SELECT 
    o.id, o.user_id, o.total_amount,
    AVG(o.total_amount) OVER (PARTITION BY o.user_id) AS user_avg
FROM orders o;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A correlated subquery depends on outer query columns and logically evaluates once per outer row ($O(N \times M)$).
- **`SubPlan` vs `InitPlan`:** `SubPlan` runs per row (major bottleneck); `InitPlan` runs once ($O(1)$).
- **Decorrelation:** The optimizer converts correlated `EXISTS` and `IN` predicates into set-based **Semi-Joins** ($O(N + M)$).
- **`Memoize` (PG 14+):** Caches parameterized subquery results in a shared hash table, accelerating queries with duplicate parameter values.
- **Modern Replacements:** Replace scalar subqueries with **Window Functions** (`AVG() OVER (PARTITION BY ...)`), `JOIN ... GROUP BY`, or `UPDATE ... FROM`.

**Common Follow-up Questions:**
- *"What is the difference between `EXISTS (SELECT 1 ...)` and `EXISTS (SELECT * ...)` in a correlated subquery?"* → There is zero performance difference; the optimizer ignores the `SELECT` target list inside `EXISTS` and only checks for tuple existence.
- *"How do you optimize an UPDATE with a correlated subquery on 50 million rows?"* → Rewrite using `UPDATE ... FROM (CTE / subquery)` to convert row-by-row lookups into a single Hash Join pass.
- *"When does the optimizer fail to decorrelate a subquery?"* → When the inner subquery contains `LIMIT`, `OFFSET`, outer-correlated aggregate functions, or complex `UNION` branches.

**Red Flags (DO NOT Say):**
- ❌ *"Correlated subqueries in the SELECT list perform fine as long as there is an index."* (Even with indexes, $N$ index traversals for millions of rows will severely saturate disk I/O and CPU).
- ❌ *"SELECT * inside EXISTS is slower because it fetches all columns from disk."* (Postgres strips the target list in `EXISTS` nodes; it only checks index/page pointers).
- ❌ *"Memoize makes LATERAL joins faster in all scenarios."* (If outer parameter keys are distinct, cache hit rate is 0%, adding pure hash overhead).
