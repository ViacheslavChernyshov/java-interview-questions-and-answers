# What is an EXPLAIN plan?

---

## 🟢 Junior Level

An **EXPLAIN plan** is a diagnostic output generated by PostgreSQL that displays the **execution strategy chosen by the cost-based query optimizer** to execute an SQL statement.

- **`EXPLAIN`:** Generates the query plan based on statistical estimates **without executing the statement**.
- **`EXPLAIN ANALYZE`:** Actually **executes the query** and displays real execution times alongside estimated numbers.

**Simple analogy:** 
- `EXPLAIN` is like a GPS suggesting a route with estimated driving times before you start your car.
- `EXPLAIN ANALYZE` is driving the actual route, measuring exact stopwatch split times for every turn and traffic light.

**Basic Example:**
```sql
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';

-- Output:
-- Index Scan using idx_users_email on users (cost=0.42..8.44 rows=1 width=72)
--   Index Cond: (email = 'alice@example.com'::text)
```

**Interpreting the numbers:**
- `cost=0.42..8.44`: Estimated arbitrary cost units (`startup_cost`..`total_cost`).
- `rows=1`: Expected number of matching rows emitted.
- `width=72`: Average byte width of emitted rows.

## 🟡 Middle Level

### Essential Diagnostic Syntax: `EXPLAIN (ANALYZE, BUFFERS)`

In production troubleshooting, always invoke `EXPLAIN` with the `BUFFERS` parameter:

```sql
EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.city = 'Chicago'
GROUP BY u.name;
```

```
Execution Plan Output:
HashAggregate (cost=850.20..855.20 rows=500 width=40) (actual time=14.2..14.3 rows=500 loops=1)
  Buffers: shared hit=1250 read=50
  -> Hash Left Join (cost=220.00..810.00 rows=2000 width=40) (actual time=8.1..11.5 rows=2000 loops=1)
       Hash Cond: (o.user_id = u.id)
       -> Seq Scan on orders o (actual time=0.02..5.1 rows=10000 loops=1)
            Buffers: shared hit=400
       -> Hash (cost=150.00..150.00 rows=500 width=36) (actual time=2.8..2.8 rows=500 loops=1)
            Buffers: shared hit=850 read=50
            -> Index Scan using idx_users_city on users u (actual time=0.03..2.1 rows=500 loops=1)
                 Index Cond: (city = 'Chicago'::text)
                 Buffers: shared hit=850 read=50
Planning Time: 0.45 ms
Execution Time: 15.10 ms
```

### How to Read Query Plans: Bottom-Up Traversal

1. **Step 1 (Leaves):** The engine reads `users` via `Index Scan using idx_users_city`, fetching 500 rows matching Chicago.
2. **Step 2:** The `Hash` node builds an in-memory hash table of these 500 Chicago users in `work_mem`.
3. **Step 3:** The engine performs a `Seq Scan on orders`, streaming 10,000 orders against the in-memory hash table.
4. **Step 4:** The `Hash Left Join` combines matching pairs, emitting 2,000 joined tuples.
5. **Step 5 (Root):** `HashAggregate` computes the counts per user and returns the final 500 summary rows.

### Reading I/O Metrics via `BUFFERS`

- `shared hit=1250`: 1,250 pages (10 MB) were read directly from RAM (`shared_buffers`).
- `shared read=50`: 50 pages (400 KB) were not in cache and had to be fetched from physical disk.
- **Cache Hit Ratio:** $\frac{\text{shared hit}}{\text{shared hit} + \text{shared read}} = \frac{1250}{1300} = 96.1\%$.
- `temp read/written`: Indicates `work_mem` overflow; data spilled to disk during sorting/hashing.

## 🔴 Senior Level

### DML Safety Warning: `EXPLAIN ANALYZE` Modifies Data!

> [!CAUTION]
> Running `EXPLAIN ANALYZE` on a `DELETE`, `UPDATE`, or `INSERT` statement **actually executes the data modification** on disk! Always wrap testing in a transaction with `ROLLBACK`:

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) 
DELETE FROM audit_logs WHERE created_at < '2025-01-01';
ROLLBACK; -- Safely reverts the deletion after viewing the timing!
```

### The Prepared Statement Trap: Generic vs. Custom Plans

In Java (JDBC/Hibernate), frameworks default to parameterized Prepared Statements. This can create massive discrepancies between console speed and production speed:

1. **Custom Plan (Executions 1–5):** The planner evaluates the specific literal parameter (e.g., `id = 5`). If `id = 5` matches 1 row, it uses an **Index Scan**.
2. **Generic Plan (Execution 6+):** PostgreSQL generates a single reusable plan valid for any parameter (`id = $1`). If data is skewed, the planner may default to a safe **Seq Scan** across the board!

```sql
-- Diagnostic query to force custom plans for skewed parameters:
SET plan_cache_mode = 'force_custom_plan';
```

### JIT (Just-In-Time) LLVM Compilation Overhead

PostgreSQL compiles complex SQL expressions into native machine code via LLVM.
- **OLAP Benefit:** Speeds up queries evaluating millions of rows with heavy mathematical expressions.
- **OLTP Disaster:** In simple low-latency OLTP queries (`SELECT * FROM users WHERE id = 1`), JIT compilation overhead adds **5–15 ms** to a query that should take **0.2 ms**!

```sql
-- Disable JIT compilation for high-throughput OLTP workloads:
SET jit = off;
```

### Key Red Flags in EXPLAIN Output

| Plan Symptom | Root Cause | Remediation |
|---|---|---|
| `rows=100000` vs `actual rows=1` | Outdated statistics | Run `ANALYZE table_name` |
| `external merge Disk: 45MB` | `Sort` or `HashAggregate` exceeded memory | Increase `work_mem` for session |
| `Rows Removed by Filter: 990000` | Missing index on filtered column | Add dedicated or composite B-tree index |
| `JIT: Functions: 8, Timing: 12.5ms` | JIT compilation overhead in OLTP | Set `jit = off` |

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`EXPLAIN` vs `EXPLAIN ANALYZE`:** `EXPLAIN` estimates without running; `EXPLAIN ANALYZE` executes the query and measures actual wall-clock timing and row counts.
- **DML Safety:** Never run `EXPLAIN ANALYZE` on `UPDATE`/`DELETE` in production without wrapping in `BEGIN; ... ROLLBACK;`.
- **Cost Meaning:** `cost=startup..total` in arbitrary cost units (where 1 unit $\approx$ reading 1 sequential 8KB page).
- **`BUFFERS` Option:** Displays memory buffer hits vs physical disk reads and temp file spills.
- **Generic vs Custom Plans:** Prepared statements switch to generic plans after 5 executions, which can cause severe performance drops on skewed data.
- **JIT Overhead:** LLVM JIT compilation can severely penalize sub-millisecond OLTP queries.

**Common Follow-up Questions:**
- *"Why is a query fast in DBeaver/psql (2ms) but slow in Spring Boot / Hibernate (400ms)?"* → Hibernate uses prepared statements which switch to a Generic Plan, choosing a Seq Scan due to parameter average cost heuristics; set `plan_cache_mode = 'force_custom_plan'`.
- *"What does `Rows Removed by Filter: 500,000` inside a Seq Scan indicate?"* → The database read 500,000 rows off disk only to discard them in memory; a B-tree index on that column would allow seeking directly to matching tuples.
- *"How do you verify if a Hash Join spilled to disk in EXPLAIN?"* → Look for `Batches: > 1` and `Disk: X kB` under the Hash node.

**Red Flags (DO NOT Say):**
- ❌ *"The cost numbers in EXPLAIN represent execution time in milliseconds."* (They are dimensionless cost units relative to page reads).
- ❌ *"EXPLAIN ANALYZE only simulates queries without affecting table data."* (It executes all statements, including DELETE and UPDATE).
- ❌ *"JIT should always be enabled because machine code is faster."* (JIT compilation latency degrades OLTP response times).
