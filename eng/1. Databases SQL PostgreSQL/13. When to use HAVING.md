# When to use HAVING?

---

## 🟢 Junior Level

You should use **HAVING** when you need to filter query results based on the output of **aggregate functions** (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`) after grouping has occurred.

**Simple Rule:**
- Filtering raw row values (e.g., `status = 'ACTIVE'`, `created_at > '2026-01-01'`) $\longrightarrow$ Use **`WHERE`**.
- Filtering calculated group aggregates (e.g., `COUNT(*) > 5`, `AVG(salary) > 80000`) $\longrightarrow$ Use **`HAVING`**.

**Common Examples:**
```sql
-- 1. Identify high-volume customers (users with more than 5 orders)
SELECT user_id, COUNT(*) AS order_count
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 5;

-- 2. Identify departments with average salary exceeding $100,000
SELECT department_id, AVG(salary) AS avg_salary
FROM employees
GROUP BY department_id
HAVING AVG(salary) > 100000;

-- 3. Detect duplicate emails in a table
SELECT email, COUNT(*) AS occurrences
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```

## 🟡 Middle Level

### Architectural Best Practice: Dual-Stage Filtering (`WHERE` + `HAVING`)

High-performance SQL separates pre-aggregation row filtering from post-aggregation group qualification:

```sql
SELECT 
    customer_id, 
    AVG(total_amount) AS avg_order_val,
    SUM(total_amount) AS total_spent
FROM orders
WHERE status = 'DELIVERED'           -- 1. WHERE: Discards canceled/pending rows early (Uses Indexes!)
  AND created_at >= '2026-01-01'     -- 2. WHERE: Restricts input dataset to current year
GROUP BY customer_id                 -- 3. GROUP BY: Groups only active delivered orders
HAVING COUNT(*) >= 10                -- 4. HAVING: Filters for frequent buyers
   AND AVG(total_amount) > 200;      -- 5. HAVING: Filters for high average order value
```

**Why this separation is vital:**
- `WHERE` reduces the volume of rows fed into memory/sorting engines by 90%+.
- `HAVING` applies strictly to the remaining aggregated buckets.

### Common Pitfalls

#### 1. Placing Non-Aggregate Column Conditions in `HAVING`
```sql
-- ❌ BAD: Forces database to group all global cities before filtering
SELECT city, COUNT(*) 
FROM users 
GROUP BY city 
HAVING city = 'Chicago';

-- ✅ GOOD: Filters rows first, grouping only Chicago residents
SELECT city, COUNT(*) 
FROM users 
WHERE city = 'Chicago' 
GROUP BY city;
```

#### 2. SQL Portability Trap (SELECT Column Aliases in HAVING)
```sql
-- ⚠️ Allowed in PostgreSQL, but causes syntax errors in Oracle and Microsoft SQL Server:
SELECT city, COUNT(*) AS user_count
FROM users
GROUP BY city
HAVING user_count > 50;

-- ✅ Standard portable SQL:
SELECT city, COUNT(*) AS user_count
FROM users
GROUP BY city
HAVING COUNT(*) > 50;
```

## 🔴 Senior Level

### The Massive Group Explosion Bottleneck

A common production issue occurs when queries process millions of distinct groups, expecting `HAVING` to keep the query fast because the final output is small:

```sql
-- ⚠️ DANGEROUS QUERY: 100,000,000 orders across 15,000,000 distinct user_ids
SELECT user_id, SUM(total_amount)
FROM orders
WHERE created_at >= '2025-01-01'
GROUP BY user_id
HAVING SUM(total_amount) > 100000;
```

**Why it bottlenecks:**
1. `HAVING` filters the **output** of `GROUP BY`, not its input.
2. The `HashAggregate` executor must allocate 15,000,000 hash table buckets in memory.
3. When `work_mem` is exceeded, Postgres spills gigabytes of partitions to disk (`temp_files`), slowing execution from seconds to minutes.

**Engineering Solutions:**
1. **Pre-aggregation Filtering via CTE / Partial Indexes:**
   ```sql
   -- If orders > $1,000 are the only ones capable of reaching $100k:
   WITH qualifying_orders AS (
       SELECT user_id, total_amount 
       FROM orders 
       WHERE created_at >= '2025-01-01' AND total_amount > 1000
   )
   SELECT user_id, SUM(total_amount)
   FROM qualifying_orders
   GROUP BY user_id
   HAVING SUM(total_amount) > 100000;
   ```
2. **Materialized Views for Analytical Reporting:**
   ```sql
   CREATE MATERIALIZED VIEW mv_customer_annual_spend AS
   SELECT user_id, SUM(total_amount) AS total_spent, COUNT(*) AS order_count
   FROM orders
   WHERE created_at >= '2025-01-01'
   GROUP BY user_id;

   CREATE INDEX idx_mv_spend ON mv_customer_annual_spend(total_spent DESC);
   -- Instant indexed lookups:
   SELECT user_id, total_spent FROM mv_customer_annual_spend WHERE total_spent > 100000;
   ```

### Advanced Expressive Group Filtering with `FILTER`

Combine `HAVING` with aggregate `FILTER` clauses to express complex multi-condition group assertions:

```sql
-- Identify projects with at least 10 tasks where 80%+ are completed and NONE are blocked
SELECT project_id
FROM tasks
GROUP BY project_id
HAVING 
    COUNT(*) >= 10
    AND COUNT(*) FILTER (WHERE status = 'COMPLETED') >= (COUNT(*) * 0.8)
    AND COUNT(*) FILTER (WHERE status = 'BLOCKED') = 0
    AND MAX(due_date) >= CURRENT_DATE;
```

### `HAVING` with Correlated Subqueries

```sql
-- Find customer cohorts whose total spending exceeds the average cohort total
SELECT customer_segment, SUM(total_amount) AS segment_revenue
FROM orders
GROUP BY customer_segment
HAVING SUM(total_amount) > (
    SELECT AVG(cohort_sum) 
    FROM (
        SELECT SUM(total_amount) AS cohort_sum 
        FROM orders 
        GROUP BY customer_segment
    ) sub
);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Purpose:** `HAVING` filters aggregated group records; `WHERE` filters raw table rows.
- **Pipeline Stage:** `WHERE` (Pre-grouping -> Uses Indexes) $\longrightarrow$ `GROUP BY` $\longrightarrow$ `HAVING` (Post-grouping).
- **Aggregate Expressions:** Aggregates (`COUNT`, `SUM`, `AVG`) are valid in `HAVING`, forbidden in `WHERE`.
- **Memory Pressure:** `HAVING` does not prevent `HashAggregate` memory bloat or disk spills because all groups must be built before `HAVING` evaluates.
- **Window Functions:** Window functions evaluate after `HAVING`; filtering by window rank requires CTE wrapping.

**Common Follow-up Questions:**
- *"Why does a query with `HAVING city = 'Boston'` run significantly slower than `WHERE city = 'Boston'`?"* → `HAVING` aggregates all rows across the entire table into hash buckets before discarding non-Boston groups, whereas `WHERE` uses an index scan to read only Boston rows.
- *"How can you optimize a GROUP BY query with 10 million distinct groups and a restrictive HAVING filter?"* → Pre-filter rows in `WHERE`, increase `work_mem` to prevent disk spills, or pre-aggregate via Materialized Views.
- *"Can you use HAVING without a GROUP BY clause?"* → Yes, the entire table is treated as one summary group (e.g., `SELECT 'High Volume' FROM logs HAVING COUNT(*) > 100000`).

**Red Flags (DO NOT Say):**
- ❌ *"HAVING filters out rows before calculating SUM()."* (It filters calculated groups after aggregation).
- ❌ *"You can put aggregate functions in the WHERE clause if you use parentheses."* (Aggregates are strictly invalid in WHERE).
- ❌ *"HAVING speeds up GROUP BY by reducing group creation."* (All groups are created first; HAVING only filters output rows).
