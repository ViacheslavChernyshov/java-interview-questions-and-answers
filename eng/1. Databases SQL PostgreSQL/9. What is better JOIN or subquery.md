# What is better JOIN or subquery?

---

## 🟢 Junior Level

**There is no universal answer:** it depends on query semantics and optimizer capabilities. In modern relational database engines like PostgreSQL, the cost-based query optimizer frequently rewrites (unnests) subqueries into physical joins under the hood, yielding identical performance.

**Simple Rule of Thumb:**
- Use **JOIN** when you need to retrieve columns from **both** tables in the final `SELECT` list.
- Use a **Subquery (`EXISTS` / `IN`)** when you only need to filter or check for the **existence** of related records without displaying their payload columns.

**Example:**
```sql
-- 1. JOIN: Retrieve customer name AND order total
SELECT u.name, o.total_amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- 2. Subquery (EXISTS): Filter for users who have placed orders
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```

## 🟡 Middle Level

### Subquery Unnesting & Decorrelation

PostgreSQL implements **Subquery Unnesting** (flattening), translating subqueries in `WHERE` into physical join trees:

```sql
-- SQL Written with IN Subquery:
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total_amount > 100);

-- Optimizer's Internal Transformation:
SELECT users.*
FROM users
INNER JOIN (
    SELECT user_id FROM orders WHERE total_amount > 100
) o ON users.id = o.user_id;
-- Compiled to: Hash Semi-Join (Executes in O(N + M) time!)
```

### Why `EXISTS` Beats `JOIN + DISTINCT` (Join Amplification)

```sql
-- ❌ ANTI-PATTERN: Joining a 1-to-many relation duplicates parent rows,
-- requiring an expensive DISTINCT sort/hash to deduplicate:
SELECT DISTINCT u.* 
FROM users u
JOIN orders o ON u.id = o.user_id;

-- ✅ OPTIMAL: EXISTS compiles directly into a Semi-Join:
SELECT u.* 
FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
-- Stops scanning 'orders' for a given user immediately upon finding the FIRST match!
```

### Optimization Fences: When Unnesting Fails

Certain SQL constructs prevent PostgreSQL from unnesting a subquery into a join, forcing per-row execution (**SubPlan**):

| Optimization Fence | Optimizer Behavior | Recommended Solution |
|---|---|---|
| `LIMIT` / `OFFSET` inside subquery | Cannot be pulled up into a standard join | Use `LEFT JOIN LATERAL` |
| `DISTINCT` in correlated subquery | Subquery must execute independently | Rewrite via Window Functions or `GROUP BY` |
| `GROUP BY` / Aggregates in correlated subquery | Pre-aggregates or executes per row | Use `LEFT JOIN (SELECT ... GROUP BY)` |
| `UNION` / `INTERSECT` | Evaluated as an independent subplan | Rewrite using `OR` or separate CTEs |

### Scalar Subqueries in `SELECT`

```sql
-- ❌ SEVERE BOTTLENECK: Runs 1,000,000 independent index scans for 1,000,000 users!
SELECT 
    u.name, 
    (SELECT SUM(total_amount) FROM orders o WHERE o.user_id = u.id) AS total_spent
FROM users u;
-- Execution Plan: SubPlan (O(N * M))

-- ✅ OPTIMAL: Single Hash Join + HashAggregate pass!
SELECT 
    u.name, 
    COALESCE(SUM(o.total_amount), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;
-- Execution Plan: Hash Join + HashAggregate (O(N + M))
```

### CTE (Common Table Expressions) & Materialization

- **Prior to PostgreSQL 12:** CTEs (`WITH ... AS`) acted as hard optimization barriers. PostgreSQL was forced to evaluate and materialize every CTE into a temporary structure in memory/disk before executing the main query.
- **PostgreSQL 12+:** CTEs are **inlined by default** (`NOT MATERIALIZED`), allowing the planner to push predicates down into the CTE just like standard subqueries.

```sql
-- Force materialization when a heavy CTE is referenced multiple times:
WITH expensive_calc AS MATERIALIZED (
    SELECT user_id, SUM(total_amount) AS total FROM orders GROUP BY user_id
)
SELECT * FROM users u JOIN expensive_calc ec ON u.id = ec.user_id
UNION ALL
SELECT * FROM archived_users au JOIN expensive_calc ec ON au.id = ec.user_id;

-- Force inlining when the outer query has selective filters:
WITH active_orders AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE status = 'COMPLETED'
)
SELECT * FROM active_orders WHERE user_id = 42; -- Pushes 'user_id = 42' directly into the index scan
```

## 🔴 Senior Level

### Execution Nodes: `SubPlan` vs `InitPlan`

In `EXPLAIN` query plans, pay close attention to subquery node identifiers:

#### 1. `SubPlan` (Correlated Execution Penalty)
Evaluated once for **every outer row** ($O(N \times M)$). If an outer query scans 500,000 rows, the `SubPlan` executes 500,000 times:
```sql
EXPLAIN SELECT u.name, (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) FROM users u;
-- Seq Scan on users
--   SubPlan 1 -> Aggregate -> Index Scan on orders (user_id = u.id)
```

#### 2. `InitPlan` (Static Evaluation)
Evaluated **exactly once** prior to main query execution ($O(1)$) and stored as a constant parameter:
```sql
EXPLAIN SELECT * FROM orders WHERE total_amount > (SELECT AVG(total_amount) FROM orders);
-- InitPlan 1 -> Aggregate -> Seq Scan on orders
-- Seq Scan on orders (Filter: total_amount > $0)
```

### The `Memoize` Node (PostgreSQL 14+)

In PostgreSQL 14+, the engine introduced the **Memoize** execution node to optimize parameterized Nested Loops and `LATERAL` subqueries. Memoize caches subquery results in a hash table keyed by the parameter value (`user_id`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, recent_order.total_amount
FROM users u
LEFT JOIN LATERAL (
    SELECT total_amount FROM orders o
    WHERE o.user_id = u.id
    ORDER BY created_at DESC LIMIT 1
) recent_order ON true;

-- PostgreSQL 14+ Plan:
-- Nested Loop
--   -> Seq Scan on users
--   -> Memoize (Hits: 450000, Misses: 50000, Evictions: 0)
--       -> Limit
--           -> Index Scan on orders
```
*Impact:* If thousands of rows share duplicate parameter keys, cache hits approach 90%+, speeding up queries by 10x–50x without requiring query rewrites.

### DML Subqueries: `UPDATE ... FROM` vs Subqueries

```sql
-- ❌ Slow correlated subquery in UPDATE
UPDATE accounts 
SET balance = balance + 10
WHERE id IN (SELECT account_id FROM pending_bonuses WHERE processed = false);

-- ✅ Fast hash join execution via FROM syntax
UPDATE accounts a
SET balance = a.balance + 10
FROM pending_bonuses b
WHERE a.id = b.account_id AND b.processed = false;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Unnesting:** PostgreSQL automatically converts `WHERE id IN (...)` and `EXISTS (...)` into `Hash Semi-Join` or `Nested Loop Semi-Join` nodes.
- **`SubPlan` vs `InitPlan`:** `SubPlan` runs per row ($O(N \times M)$ bottleneck); `InitPlan` runs once ($O(1)$).
- **`EXISTS` vs `JOIN + DISTINCT`:** `EXISTS` stops at the first matching record (short-circuit evaluation), avoiding row duplication and expensive sorting.
- **`NOT IN` Trap:** `NOT IN` fails completely (returns 0 rows) if the subquery returns any `NULL`. Always use `NOT EXISTS`.
- **CTE Inlining (PG 12+):** CTEs are inlined by default; use `MATERIALIZED` only when reusing an expensive subquery across multiple query blocks.
- **`Memoize` (PG 14+):** In-memory cache node for parameterized subqueries and lateral joins.

**Common Follow-up Questions:**
- *"Why is `SELECT u.name, (SELECT COUNT(*) ...)` an anti-pattern in large tables?"* → It compiles to a `SubPlan`, invoking the subquery $N$ times instead of aggregating via a single Hash Join + Group By pass.
- *"How did CTE optimization change between PostgreSQL 11 and 12+?"* → Prior to PG 12, CTEs were optimization barriers (always materialized); PG 12+ inlines them by default unless explicitly declared `WITH cte AS MATERIALIZED (...)`.
- *"What is a Memoize node in PostgreSQL 14+?"* → A cache node placed above the inner relation of a parameterized nested loop that caches results for identical outer parameter keys.

**Red Flags (DO NOT Say):**
- ❌ *"Subqueries are always slower than joins because they execute row by row."* (Decorrelated subqueries compile to identical semi-joins).
- ❌ *"CTEs are always materialized into temporary tables on disk."* (In PostgreSQL 12+, CTEs are inlined by default).
- ❌ *"NOT IN is faster than NOT EXISTS."* (NOT IN cannot optimize easily and breaks when `NULL` values exist).
