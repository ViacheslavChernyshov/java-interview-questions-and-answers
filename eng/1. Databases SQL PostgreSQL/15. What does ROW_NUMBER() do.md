# What does ROW_NUMBER() do?

---

## 🟢 Junior Level

**`ROW_NUMBER()`** is a SQL window ranking function that assigns a **unique, sequential integer** (starting at 1) to each row within its partition, ordered according to the specified `ORDER BY` clause.

**Simple analogy:** Numbering raffle tickets or runner bibs at a marathon finish line: every person receives an exact, strictly unique number (1, 2, 3, 4...) based on their arrival sequence.

**Example:**
```sql
-- Rank orders from newest to oldest
SELECT 
    id,
    user_id,
    total_amount,
    created_at,
    ROW_NUMBER() OVER (ORDER BY created_at DESC) AS row_num
FROM orders;

-- Output:
-- id  | user_id | total_amount | created_at | row_num
-- 104 | 2       | 200          | 2026-04-01 | 1
-- 102 | 1       | 50           | 2026-03-25 | 2
-- 101 | 1       | 150          | 2026-02-10 | 3
```

**Common Use Cases:**
- Numbering report lines
- Extracting Top-N items per category/user
- Table deduplication (keeping the latest record per unique key)
- Page-number based offset pagination

## 🟡 Middle Level

### Syntax and Core Patterns

```sql
ROW_NUMBER() OVER (
    PARTITION BY user_id             -- Divides data into isolated user buckets (Optional)
    ORDER BY created_at DESC, id ASC -- Defines deterministic sort order (Mandatory!)
)
```

#### 1. Top-N Records per Group
```sql
-- Fetch the 3 most recent orders for EVERY user in a single pass
WITH ranked_orders AS (
    SELECT 
        user_id, order_id, total_amount, created_at,
        ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, order_id DESC) AS rn
    FROM orders
)
SELECT user_id, order_id, total_amount, created_at
FROM ranked_orders
WHERE rn <= 3;
```

#### 2. Deduplication (Batch Cleanup)
```sql
-- Remove duplicate email accounts, keeping only the most recently registered account
WITH ranked_users AS (
    SELECT id, email, created_at,
           ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at DESC, id DESC) AS rn
    FROM users
)
DELETE FROM users 
WHERE id IN (
    SELECT id FROM ranked_users WHERE rn > 1
);
```

### The Non-Determinism Trap

If the columns specified in `ORDER BY` contain duplicate values, PostgreSQL does not guarantee the relative ordering between duplicate rows across repeated query runs:

```sql
-- ❌ DANGEROUS: If two users registered at the exact same millisecond, rn is non-deterministic!
ROW_NUMBER() OVER (ORDER BY created_at DESC)

-- ✅ DETERMINISTIC: Append Primary Key as an unambiguous tie-breaker!
ROW_NUMBER() OVER (ORDER BY created_at DESC, id DESC)
```

### Comparing Ranking Functions

| Function | Numbering Sequence with Duplicate Values | Tie Handling |
|---|---|---|
| **`ROW_NUMBER()`** | `1, 2, 3, 4` | Assigns arbitrary unique integers to tied rows |
| **`RANK()`** | `1, 2, 2, 4` | Assigns identical rank to ties; leaves gaps in sequence |
| **`DENSE_RANK()`** | `1, 2, 2, 3` | Assigns identical rank to ties; leaves **no gaps** |

## 🔴 Senior Level

### Physical Optimization: Eliminating the `Sort` Node

Window aggregation normally requires a physical `Sort` node in the query plan:

```sql
-- By creating a composite index matching PARTITION BY + ORDER BY:
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC, id DESC);

-- Query plan optimization:
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, total_amount,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC, id DESC) AS rn
FROM orders;
-- WindowAgg (cost=... actual rows=5000000)
--   -> Index Only Scan using idx_orders_user_created on orders  <-- ZERO in-memory sort pass!
```

### Top-K Memory Optimization: Bounded Heap Sort

When calculating a global Top-K ranking with an outer `LIMIT` or `WHERE rn <= K`:
```sql
SELECT * FROM (
    SELECT id, total_amount,
           ROW_NUMBER() OVER (ORDER BY total_amount DESC) AS rn
    FROM orders
) sub
WHERE rn <= 10;
```
PostgreSQL optimizes the sort phase using a **Bounded Heap Sort**. Rather than sorting millions of records in `work_mem` ($O(N \log N)$), it maintains a fixed-size priority queue of only $K$ elements ($O(N \log K)$), reducing memory usage to $O(K)$.

### Large-Scale Pagination: Keyset vs. `ROW_NUMBER()`

For high-throughput APIs paginating large tables (> 1,000,000 rows):

```sql
-- ❌ INEFFICIENCY: ROW_NUMBER() must scan and rank all preceding rows up to OFFSET
SELECT * FROM (
    SELECT id, name, ROW_NUMBER() OVER (ORDER BY id ASC) AS rn
    FROM users
) sub WHERE rn BETWEEN 500001 AND 500020;
-- Scans 500,020 rows!

-- ✅ HIGH-PERFORMANCE: Keyset Pagination (Cursor-based)
SELECT id, name
FROM users
WHERE id > 500000  -- Last seen ID from previous page
ORDER BY id ASC
LIMIT 20;
-- Direct B-tree seek! Scans exactly 20 index tuples in 0.2ms.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** `ROW_NUMBER()` assigns a strictly unique, contiguous integer (`1, 2, 3...`) to every row in its window partition.
- **Filtering:** Cannot be filtered in `WHERE` directly; requires a CTE or subquery (`WHERE rn <= N`).
- **Determinism:** Always append a unique column (like the Primary Key) to `ORDER BY` to ensure consistent ordering across runs.
- **Index Elimination:** An index on `(PARTITION BY cols, ORDER BY cols)` allows `WindowAgg` to stream data directly without a `Sort` step.
- **Bounded Heap:** Queries filtering `WHERE rn <= K` use a bounded heap sort to cap memory usage at $O(K)$.
- **API Pagination:** Prefer Keyset pagination (`WHERE id > ? LIMIT 20`) over `ROW_NUMBER()` for deep pagination on large tables.

**Common Follow-up Questions:**
- *"How do you write a query to fetch the latest 5 transactions for each account?"* → Use `ROW_NUMBER() OVER (PARTITION BY account_id ORDER BY transaction_date DESC, id DESC)` in a CTE and filter `WHERE rn <= 5`.
- *"What happens if two rows have identical values in the ORDER BY clause of ROW_NUMBER()?"* → Both rows receive distinct incrementing integers (`1` and `2`), but the assignment order between them is arbitrary unless disambiguated with secondary sort keys.
- *"Why is Keyset Pagination faster than ROW_NUMBER() on page 5,000?"* → Keyset uses a direct B-tree search to locate the starting tuple in $O(\log N)$ time, whereas `ROW_NUMBER()` must read and sort all 50,000 preceding rows.

**Red Flags (DO NOT Say):**
- ❌ *"ROW_NUMBER() assigns the same number to duplicate rows."* (That is `RANK()` or `DENSE_RANK()`; `ROW_NUMBER()` is strictly unique).
- ❌ *"You can put `WHERE ROW_NUMBER() OVER (...) = 1` directly in the query without a subquery."* (Window functions execute after `WHERE`).
- ❌ *"ROW_NUMBER() is always non-deterministic."* (It is 100% deterministic when a unique column/PK is included in `ORDER BY`).
