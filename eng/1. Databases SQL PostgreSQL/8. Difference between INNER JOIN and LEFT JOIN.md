# Difference between INNER JOIN and LEFT JOIN

---

## 🟢 Junior Level

The core difference between **INNER JOIN** and **LEFT JOIN** lies in how they handle rows that have no matching counterparts in the joined table:
- **INNER JOIN:** Returns **only rows that have matching records in both tables**. Any unmatched rows from either side are discarded.
- **LEFT JOIN (LEFT OUTER JOIN):** Returns **all rows from the left table**, regardless of whether a match exists in the right table. If no match is found, columns from the right table are filled with `NULL`.

**Simple Example:**
```sql
-- Table users: Alice (id=1), Bob (id=2), Charlie (id=3)
-- Table orders: Alice has an order ($100), Bob has an order ($250), Charlie has NO orders

-- 1. INNER JOIN: Only users who placed orders
SELECT u.name, o.total_amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;
-- Result:
-- Alice   | 100
-- Bob     | 250

-- 2. LEFT JOIN: All users, with NULL for non-purchasers
SELECT u.name, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
-- Result:
-- Alice   | 100
-- Bob     | 250
-- Charlie | NULL
```

**When to use which:**
- Use **INNER JOIN** when you strictly require related data from both entities (e.g., "Show all shipped packages and their courier details").
- Use **LEFT JOIN** when you must preserve the complete primary list regardless of child entity existence (e.g., "Show all registered users and their last login timestamp, even if they never logged in").

## 🟡 Middle Level

### Optimizer Freedom & Join Reordering

#### INNER JOIN: Fully Associative & Commutative
```
(A ⋈ B) ⋈ C  ≡  A ⋈ (B ⋈ C)  ≡  (A ⋈ C) ⋈ B
```
The query planner possesses full freedom to reorder the join tree across all $N!$ permutations, allowing it to join the two most selective tables first to minimize intermediate row counts.

#### LEFT JOIN: Non-Associative
```
(A ⟕ B) ⟕ C  ≢  A ⟕ (B ⟕ C)
```
The optimizer's reordering freedom is strictly constrained. In a chain of `LEFT JOIN` operations, the leftmost table must act as the driving outer relation, restricting the planner from evaluating alternate join paths.

### Physical Execution Strategy Constraints

| Engine Metric | INNER JOIN | LEFT JOIN |
|---|---|---|
| **Hash Join** | Planner builds the hash table from whichever input is smaller | The right table is strictly used as the build relation |
| **Nested Loop** | Either table can serve as the outer driving loop | The left table must serve as the outer driving loop |
| **Merge Join** | Either table can determine merge sorting order | The left table dictates the primary stream order |

### The `WHERE` Clause Trap (Outer-to-Inner Transformation)

Placing a filter for the right table in the `WHERE` clause instead of the `ON` clause silently converts a `LEFT JOIN` into an `INNER JOIN`:

```sql
-- ❌ ACCIDENTAL INNER JOIN:
SELECT u.name, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.total_amount > 100;
-- Since o.total_amount is NULL for users without orders, NULL > 100 evaluates 
-- to UNKNOWN, filtering out all users without orders!

-- ✅ CORRECT: Filter placed inside the ON clause preserves unmatched users
SELECT u.name, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id AND o.total_amount > 100;
```

### Common Aggregation Pitfalls with LEFT JOIN

```sql
-- ❌ WRONG: COUNT(*) counts the row containing NULLs, returning 1 for users with 0 orders!
SELECT u.name, COUNT(*) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.name;

-- ✅ CORRECT: COUNT(o.id) ignores NULLs, returning 0 for users without orders
SELECT u.name, COUNT(o.id) AS order_count, COALESCE(SUM(o.total_amount), 0) AS total_spent
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.name;
```

## 🔴 Senior Level

### Deep Dive: Outer Join Removal (PostgreSQL 10+)

PostgreSQL features a sophisticated query rewrite optimization called **Outer Join Removal**. If a query contains a `LEFT JOIN`, but:
1. No columns from the right table appear in `SELECT`, `WHERE`, `GROUP BY`, or `ORDER BY`.
2. The join condition references a column in the right table that is guaranteed unique (`PRIMARY KEY` or `UNIQUE NOT NULL`).

Then the query optimizer **completely removes the right table from the physical execution plan**:

```sql
-- Left table: users, Right table: profiles (user_id is PRIMARY KEY in profiles)
SELECT u.id, u.name 
FROM users u
LEFT JOIN user_profiles p ON u.id = p.user_id;

-- EXPLAIN output will show:
-- Seq Scan on users u  <-- 'user_profiles' is completely eliminated from the plan!
```

> **Senior Gotcha:** Outer Join Removal fails if the unique constraint is declared as `DEFERRABLE`, because PostgreSQL cannot guarantee row uniqueness at the exact instant the join evaluates.

### Automatic Outer-to-Inner Transformation

When PostgreSQL's planner detects a null-rejecting predicate in the `WHERE` clause against the right-hand table of a `LEFT JOIN`, it formally rewrites the parse tree from an `Outer Join` to an `Inner Join`:

```sql
EXPLAIN (VERBOSE)
SELECT u.name, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 'COMPLETED';
-- Output displays: "Join Type: Inner"
```
This enables the optimizer to unlock full join reordering and hash table build swapping.

### Anti-Join Optimization Pattern

To find records in Table A that do not exist in Table B, a `LEFT JOIN ... WHERE right.id IS NULL` pattern compiles directly into an optimized **Hash Anti-Join** or **Merge Anti-Join**:

```sql
-- Finds users with zero orders using an Anti-Join
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;
-- Compiles to Hash Anti-Join: probes hash table and emits row ONLY if no match is found
```

### Performance Comparison Matrix

| Aspect | INNER JOIN | LEFT JOIN |
|---|---|---|
| **Query Planning Complexity** | Higher search space ($N!$), but finds optimal join tree | Lower search space, but often locked into suboptimal join trees |
| **Intermediate Memory Footprint** | Small (discards unmatched rows early) | Large (must preserve all left-side rows) |
| **Cascading Joins (5+ tables)** | Scalable; optimizer groups selective joins first | Dangerous; can cause severe Nested Loop bottlenecks if left table is large |

## 🎯 Interview Cheat Sheet

**Must Know:**
- **INNER JOIN:** Preserves rows matching both tables; discards unmatched records.
- **LEFT JOIN:** Preserves all rows from the left table; fills right-side non-matches with `NULL`.
- **Join Reordering:** INNER JOIN is commutative and associative ($A \bowtie B \equiv B \bowtie A$); LEFT JOIN restricts planner ordering.
- **`ON` vs `WHERE` Placement:** Filtering a LEFT JOIN's right table in `WHERE` implicitly converts it into an INNER JOIN unless checking `IS NULL`.
- **Outer Join Removal:** Postgres strips unreferenced unique `LEFT JOIN` relations out of the query plan entirely.
- **Aggregations:** Use `COUNT(right.id)` (not `COUNT(*)`) and `COALESCE(SUM(...), 0)` to handle `NULL` properly.

**Common Follow-up Questions:**
- *"What happens under the hood when you add `WHERE right_table.status = 'ACTIVE'` to a LEFT JOIN?"* → Outer-to-Inner Transformation: Postgres rewrites the query as an INNER JOIN because `NULL = 'ACTIVE'` evaluates to false/unknown.
- *"Why can a chain of 6 LEFT JOINs cause severe performance degradation?"* → Because non-associativity prevents the optimizer from rearranging join orders, forcing a fixed execution path that may perform millions of nested loops.
- *"How does Postgres execute `LEFT JOIN ... WHERE right.id IS NULL`?"* → As a Hash Anti-Join or Merge Anti-Join, stopping immediately upon verifying non-existence.

**Red Flags (DO NOT Say):**
- ❌ *"I always use LEFT JOIN just to be safe so I don't lose any data."* (LEFT JOIN restricts optimizer reordering and consumes significantly more memory).
- ❌ *"Putting a condition in ON vs WHERE produces the exact same result in a LEFT JOIN."* (Putting it in `WHERE` filters out rows where the right side is `NULL`, turning it into an INNER JOIN).
- ❌ *"SUM() on a LEFT JOIN automatically returns 0 if there are no matches."* (It returns `NULL`; you must wrap it in `COALESCE(SUM(...), 0)`).
