# What are indexes and why are they needed?

---

## 🟢 Junior Level

**Indexes** are auxiliary data structures in a relational database that speed up data retrieval at the cost of additional storage and slower write operations.

**Simple analogy:** Imagine a thick textbook without an index or table of contents. To find a specific topic, you would have to flip through every single page from beginning to end. An index is like the alphabetical index at the back of the book: you look up a keyword, get the exact page numbers, and jump straight to the relevant content.

**Core idea:**
- **Without an index:** The database scans the entire table row by row (**Sequential Scan / Seq Scan**), reading every data page from disk or memory.
- **With an index:** The database traverses a compact search tree or lookup structure to directly pinpoint the exact matching rows (**Index Scan**).

**Example:**
```sql
-- Without index: Slow full-table scan across 1,000,000 rows
SELECT * FROM users WHERE email = 'test@example.com';

-- Create an index on the email column
CREATE INDEX idx_users_email ON users(email);

-- With index: Fast index lookup
SELECT * FROM users WHERE email = 'test@example.com'; -- Uses index
```

**What changes internally:** The SQL query remains identical, but PostgreSQL's execution plan changes dramatically. Instead of reading thousands of 8 KB heap pages sequentially, PostgreSQL navigates 3–4 levels of the B-tree index (~0.01 ms) and retrieves the exact row from the heap table using its physical tuple pointer (**TID — Tuple Identifier**, formatted as `(block_number, tuple_offset)`).

**When to use:**
- Columns frequently filtered in `WHERE` clauses
- Join keys used in `JOIN ... ON` predicates (especially Foreign Keys)
- Columns used for sorting (`ORDER BY`) or grouping (`GROUP BY`)
- Tables with thousands to millions of rows where queries select a small percentage of total data

## 🟡 Middle Level

### How It Works Internally

An index stores indexed column values in a **sorted order** along with physical tuple identifiers (**TID / ItemPointer**), pointing to the exact page and offset of each row in the table's heap storage. By default, PostgreSQL creates **B-Tree** indexes.

### Index Types in PostgreSQL

| Type | Best Use Cases | Supported Operators | Internal Mechanism |
|---|---|---|---|
| **B-Tree** | General-purpose (default), unique constraints | `<`, `<=`, `=`, `>=`, `>`, `BETWEEN`, `IN`, `IS NULL` | Balanced multi-way search tree with sorted leaf pages |
| **Hash** | Exact equality lookups only | `=` | In-memory/disk hash table with bucket chains |
| **GIN** (Generalized Inverted) | Arrays, JSONB, Full-Text Search, composite documents | `@>`, `?`, `?&`, `?\|`, `@@` | Inverted index mapping element values to lists of TIDs |
| **GiST** (Generalized Search Tree) | Geometric, spatial (PostGIS), ranges, nearest-neighbor | `&&`, `@>`, `<@`, `<<`, `>>`, `<->` | Balanced tree allowing custom domain partitioning |
| **BRIN** (Block Range Index) | Huge append-only tables (>100 GB) with naturally ordered data | `<`, `<=`, `=`, `>=`, `>`, `BETWEEN` | Stores summary min/max metadata per physical block range |

**Why not use B-Tree for everything?**
- **Hash indexes** are slightly more compact for strict `=` searches, though modern B-Trees in Postgres 13+ with deduplication have largely closed this gap.
- **GIN indexes** are inverted indexes designed to index multi-valued items (e.g., searching if a JSONB document contains `{"role": "admin"}` or if an array contains an element), which B-Tree cannot do efficiently.
- **BRIN indexes** take 100x–1000x less disk space than B-Trees because they store only the minimum and maximum values for physical ranges of pages (typically 128 pages per entry). They are ideal for time-series and append-only audit logs.

### Scan Types in PostgreSQL Query Plans

| Scan Type | Execution Mechanism | When Selected by the Planner |
|---|---|---|
| **Index Scan** | B-Tree traversal → Direct Heap random I/O per matching TID | Small result sets (high selectivity, e.g., < 5–10% of table) |
| **Index Only Scan** | Reads only B-Tree pages without accessing Heap pages | All requested query columns exist in the index AND Visibility Map confirms pages are all-visible |
| **Bitmap Index Scan** | Index scan → In-memory TID Bitmap → Sorted physical Heap block reads | Moderate result sets where matches are scattered across many pages; avoids random I/O |
| **Seq Scan** | Direct sequential reading of all table blocks | Small tables (< 1000 rows), low selectivity filters, or unindexed queries |

> **Deep Dive: Bitmap Index Scan:** When a query matches hundreds or thousands of rows, individual Index Scans cause erratic random disk seeks. PostgreSQL builds an in-memory bitmap of matching page locations from the index, sorts them physically by block number, and then reads each affected heap page sequentially in order.

### Common Pitfalls and Anti-Patterns

1. **Over-indexing (Indexing Every Column)**
   - ❌ *Problem:* Every `INSERT`, `UPDATE`, and `DELETE` must synchronize across all indexes, causing write amplification and memory bloat.
   - ✅ *Solution:* Only index columns with high query frequency and strong selectivity.

2. **Applying Functions or Operations to Indexed Columns in `WHERE`**
   ```sql
   -- ❌ B-tree index on 'email' CANNOT be used (expression changes sorting)
   SELECT * FROM users WHERE LOWER(email) = 'test@example.com';

   -- ✅ Solution: Create an expression (functional) index
   CREATE INDEX idx_users_email_lower ON users(LOWER(email));
   ```

3. **Querying Trailing Columns of a Composite Index**
   ```sql
   -- Index created on (city, age)
   -- ❌ Cannot effectively use the index when filtering only by 'age'
   SELECT * FROM users WHERE age = 25;
   ```

### When NOT to Create an Index

- **Small tables (< 1000 rows):** Sequential scan is faster because reading a few contiguous pages in memory avoids the overhead of reading both the index tree and the heap.
- **Low cardinality columns without partial filters (e.g., boolean flags, gender `M`/`F`):** When a value matches 50% of the table, sequential scanning is cheaper than index lookups.
- **Write-heavy append/staging tables:** Where ingestion throughput is paramount and analytical reads happen elsewhere.

### Practical Example

```sql
-- Composite index for a common user-filtered ordered query
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, created_at DESC);

-- This query performs an Index Scan using both the filter and the sort order
SELECT order_id, total_amount, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 10;
```

## 🔴 Senior Level

### Internal Implementation & Concurrency

PostgreSQL B-Trees are based on the **Lehman & Yao high-concurrency B-link tree algorithm**. Rather than locking entire subtrees during page splits or traversals:
- Reader backends traverse downward taking short-term **shared buffer content latches** (released immediately after moving to the next node).
- Leaf pages contain **right-link pointers (`P_NEXT`)** and a **High Key** attribute representing the upper boundary value stored on that page.
- If a concurrent insert causes a page split while another transaction is reading, the reader recognizes that its target value exceeds the page's High Key and seamlessly traverses rightward via `P_NEXT` without backtracking to the root.

```
Page Structure:
Meta-page (Block 0: Root pointer, Fastroot, B-tree version)
  └── Root Page
       ├── Internal Nodes (Navigation routing keys)
       └── Leaf Nodes (Key value + TID pointers to Heap)
            └── P_NEXT / P_PREV links (Bidirectional horizontal scanning)
```

### Architectural Trade-offs

#### 1. Covering Indexes (`INCLUDE` Clause)
Introduced to enable **Index-Only Scans** without polluting the upper navigation layers of the B-Tree:
```sql
-- customer_id is in the B-Tree search key; total_amount is stored ONLY in leaf nodes
CREATE INDEX idx_orders_customer_include_total
ON orders(customer_id) INCLUDE (total_amount);

-- Index Only Scan: Reads customer_id and total_amount directly from index leaf pages
SELECT customer_id, total_amount
FROM orders
WHERE customer_id = 42;
```

#### 2. Partial Indexes
Index only a relevant subset of rows to save 90%+ storage and write overhead:
```sql
-- Index only active user sessions
CREATE INDEX idx_active_sessions
ON user_sessions(user_id)
WHERE status = 'ACTIVE';
```

#### 3. Production Index Creation (`CONCURRENTLY`)
Standard `CREATE INDEX` acquires an `ACCESS EXCLUSIVE` lock on the table, blocking all writes (`INSERT`, `UPDATE`, `DELETE`) until completion.
```sql
-- Non-blocking index creation for production 24/7 environments
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
-- ⚠️ Rules:
-- 1. Cannot run inside a transaction block (BEGIN...COMMIT)
-- 2. Scans the table twice and waits for all concurrent writing transactions to end
-- 3. If interrupted, leaves an INVALID index that must be dropped and recreated
```

### MVCC and HOT (Heap-Only Tuples) Interaction

In PostgreSQL, every `UPDATE` physically writes a new tuple version into the table heap. Normally, every single index on that table must also be updated to point to the new row's TID.

**HOT (Heap-Only Tuple)** optimization eliminates index write amplification:
- **Condition 1:** The `UPDATE` does **not modify any indexed column**.
- **Condition 2:** The new tuple version fits inside the **same 8 KB heap page** as the old version.
- **Outcome:** The index continues pointing to the old tuple, which acts as a root pointing to the new tuple via an intra-page pointer chain. Index updates are skipped entirely.

> **Senior Takeaway:** Adding an unnecessary index on an updated column immediately disables HOT optimization for that column, multiplying write I/O and accelerating index bloat.

### Edge Cases and Troubleshooting

#### 1. Diagnosing Invalid Indexes
If `CREATE INDEX CONCURRENTLY` fails or is cancelled, an invalid index remains, consuming write I/O without being usable by the planner:
```sql
SELECT indexrelid::regclass AS invalid_index, indrelid::regclass AS table_name
FROM pg_index
WHERE NOT indisvalid;

-- Remediation: Drop and rebuild
DROP INDEX CONCURRENTLY idx_name_invalid;
```

#### 2. Index Bloat & Fillfactor
Frequent `UPDATE` and random `INSERT` operations cause B-Tree page splits, leaving pages half-empty (bloated):
```sql
-- Set fillfactor to leave 20-30% free space per leaf page for in-place updates
CREATE INDEX idx_orders_status ON orders(status) WITH (fillfactor = 70);

-- Zero-downtime online rebuild to remove bloat
REINDEX INDEX CONCURRENTLY idx_orders_status;
```

### Production Monitoring Queries

```sql
-- 1. Measure index size, scan frequency, and tuple read efficiency
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan AS number_of_scans,
    idx_tup_read AS tuples_read_from_index,
    idx_tup_fetch AS tuples_fetched_from_table
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

-- 2. Identify unused indexes (candidates for removal, excluding unique constraints)
SELECT
    s.schemaname,
    s.relname AS table_name,
    s.indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(s.indexrelid)) AS index_size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0
  AND NOT i.indisunique
  AND NOT i.indisprimary
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- Indexes speed up `SELECT` at the cost of disk space and write penalties (`INSERT`, `UPDATE`, `DELETE`).
- **B-Tree** is the default general-purpose index supporting `<`, `<=`, `=`, `>=`, `>`, `BETWEEN`, `IN`, and prefix searches.
- **5 Core Index Types:** B-Tree (universal), Hash (`=`), GIN (JSONB/arrays/FTS), GiST (geometric/ranges), BRIN (large append-only time series).
- **4 Scan Types:** Index Scan, Index Only Scan (requires Visibility Map), Bitmap Index Scan, Sequential Scan.
- **Production Safety:** Always use `CREATE INDEX CONCURRENTLY` in production systems.
- **HOT Updates:** Indexes on frequently updated columns kill HOT optimization and cause severe write amplification.

**Common Follow-up Questions:**
- *"What happens when you create an index on every single column?"* → Massive write degradation, WAL bloat, high replication lag, and broken HOT optimizations.
- *"How do you verify if a query uses an index?"* → Run `EXPLAIN (ANALYZE, BUFFERS)` and check for `Index Scan` or `Index Only Scan` nodes and buffer hit metrics.
- *"Why does `WHERE UPPER(email) = ...` skip a regular index?"* → Standard B-Tree indexes store raw values; expressions require an expression index (`CREATE INDEX ... ON users(UPPER(email))`).
- *"What is the difference between `VACUUM` and `REINDEX` for indexes?"* → `VACUUM` marks dead tuples as reusable within existing pages; `REINDEX CONCURRENTLY` rebuilds the physical index structure from scratch to eliminate page bloat.

**Red Flags (DO NOT Say):**
- ❌ *"Indexes are always good, so we should index every column just in case."* (Indexes are a write tax; every index must be justified by workload metrics).
- ❌ *"Standard VACUUM returns unused index disk space to the OS."* (VACUUM only frees space internally for future Postgres writes; only `REINDEX` or `VACUUM FULL` compacts disk files).
- ❌ *"Hash indexes are always better for equality searches."* (B-Tree handles equality almost as fast, supports unique constraints, and handles multi-column ordering).
