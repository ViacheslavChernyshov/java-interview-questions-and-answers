# What JOIN types exist?

---

## 🟢 Junior Level

A **JOIN** is an SQL operation that combines rows from two or more tables based on a related column between them.

**Why:** Relational databases are normalized — data is separated across specialized tables (e.g., `users` and `orders`) to eliminate data redundancy and prevent update anomalies. JOIN operations stitch these rows back together dynamically during read queries.

**Simple analogy:** Imagine two spreadsheets:
- **Sheet A:** Students (`student_id`, `name`)
- **Sheet B:** Exam Scores (`student_id`, `score`)

A JOIN matches the `student_id` column between both sheets to generate a unified list showing student names alongside their exam scores.

### Logical JOIN Types

| Type | Description | Result Behavior |
|---|---|---|
| **INNER JOIN** | Returns only rows where there is a match in **both** tables | Non-matching rows from both sides are discarded |
| **LEFT JOIN** (LEFT OUTER) | Returns **all** rows from the left table + matching rows from the right | If no match exists on the right, right-side columns are filled with `NULL` |
| **RIGHT JOIN** (RIGHT OUTER) | Returns **all** rows from the right table + matching rows from the left | Rarely used; usually rewritten as a `LEFT JOIN` for readability |
| **FULL JOIN** (FULL OUTER) | Returns **all** rows when there is a match in either left or right table | Unmatched columns from either side contain `NULL` |
| **CROSS JOIN** | Cartesian product of both tables | Combines every row of Table A with every row of Table B ($N \times M$ rows) |

**Example:**
```sql
-- INNER JOIN: Returns only users who have placed at least one order
SELECT u.name, o.total_amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: Returns ALL users, even those with zero orders
SELECT u.name, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
-- If a user has no orders -> o.total_amount is NULL
```

## 🟡 Middle Level

### Physical Execution Strategies (PostgreSQL Engine)

PostgreSQL implements **three distinct physical algorithms** to execute relational joins:

#### 1. Nested Loop Join
```
For each row in Outer Table A:
    Search for matching rows in Inner Table B (ideally via an Index)
```
- **Best Use Case:** The outer table is small (or filtered to few rows) and the inner table has a B-tree index on the join key.
- **Time Complexity:** $O(N \log M)$ with an index; catastrophic $O(N \times M)$ without an index.

#### 2. Hash Join
```
Phase 1 (Build): Build an in-memory Hash Table using the smaller table's join keys.
Phase 2 (Probe): Scan the larger table and probe the in-memory Hash Table for matches.
```
- **Best Use Case:** Joining large, unsorted tables with equi-join predicates (`=`).
- **Memory Dependency:** Requires adequate `work_mem`. If the hash table exceeds `work_mem`, Postgres partitions it into multiple **batches** spilled to disk (temp files).
- **Time Complexity:** $O(N + M)$.

#### 3. Merge Join
```
1. Ensure both inputs are sorted by the join key (via index or explicit Sort node).
2. Advance two pointers simultaneously like merging two sorted lists.
```
- **Best Use Case:** Large datasets where inputs are already pre-sorted by existing B-tree indexes or range/inequality join predicates.
- **Time Complexity:** $O(N + M)$ after sorting ($O(N \log N + M \log M)$ if sorting is required).

### Advanced Logical JOIN Operations

#### Semi-Join (`EXISTS`)
Returns rows from the left table as soon as the **first match** is found in the right table without duplicating rows:
```sql
-- Returns users who have at least one order (no duplicate user rows)
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
-- Execution Plan: Hash Semi-Join (faster than INNER JOIN + DISTINCT)
```

#### Anti-Join (`NOT EXISTS`)
Returns rows from the left table where **no matching rows** exist in the right table:
```sql
-- Returns users who have NEVER placed an order
SELECT * FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
-- Execution Plan: Hash Anti-Join
```

#### LATERAL JOIN
Acts like a parameterized `flatMap` across rows, allowing the inner subquery to reference columns from the outer table row:
```sql
-- For each user, fetch their top 3 most recent orders
SELECT u.name, recent_orders.order_id, recent_orders.total_amount
FROM users u
LEFT JOIN LATERAL (
    SELECT o.id AS order_id, o.total_amount
    FROM orders o
    WHERE o.user_id = u.id
    ORDER BY o.created_at DESC
    LIMIT 3
) recent_orders ON true;
```

## 🔴 Senior Level

### Query Optimizer Mechanics & Join Reordering

#### 1. Join Associativity and Commutativity
- **INNER JOINs** are fully commutative and associative:
  $$(A \bowtie B) \bowtie C \equiv A \bowtie (B \bowtie C) \equiv (A \bowtie C) \bowtie B$$
  The optimizer freely permutes table join orders to evaluate the cheapest plan.
- **OUTER JOINs (LEFT/RIGHT/FULL)** are **NOT** associative:
  $$(A \leftouterjoin B) \leftouterjoin C \not\equiv A \leftouterjoin (B \leftouterjoin C)$$
  The optimizer's reordering freedom is constrained, which can prevent it from discovering cheaper join paths.

#### 2. Outer Join Removal (PostgreSQL 10+)
If a query contains a `LEFT JOIN`, but selects no columns from the right table and the join key on the right table is guaranteed unique (`PRIMARY KEY` or `UNIQUE NOT NULL`), the optimizer **removes the right table from the plan completely**:
```sql
-- Planner eliminates the 'orders' table scan entirely if orders.id is UNIQUE
SELECT u.id, u.name 
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
```

#### 3. Genetic Query Optimizer (GEQO)
When a query joins more than `geqo_threshold` tables (default: **12 tables**), exhaustive dynamic programming permutations become computationally prohibitive. PostgreSQL switches to a **Genetic Algorithm (GEQO)**, which can produce non-deterministic or suboptimal join trees:
```sql
-- Remedy for complex analytical queries:
SET geqo_threshold = 18; -- Allow exhaustive search for up to 18 tables
```

### Tuning Hash Join Memory (`work_mem`)

When `EXPLAIN (ANALYZE, BUFFERS)` reveals multi-batch Hash Joins:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM large_orders o JOIN large_users u ON o.user_id = u.id;
-- Hash Join (cost=...)
--   Batches: 16  Memory Usage: 4096kB  Disk Spill: 120MB  <-- DISK SPILL BOTTLENECK!
```

**Remediation:**
```sql
-- Increase work_mem for the current analytical session/transaction
SET work_mem = '256MB';
-- Note: work_mem is allocated PER operation per backend! 
-- 4 parallel workers doing a Hash Join could consume 1 GB RAM.
```

### Edge Case: LATERAL vs. Window Functions for Top-N per Group

While `LATERAL` is optimal for small outer datasets (e.g., retrieving top-3 orders for 50 specific users using index lookups), running `LATERAL` across 1,000,000 users triggers 1,000,000 nested index scans. 

For full-table Top-N aggregation, `ROW_NUMBER()` window functions combined with a single sequential pass are vastly superior:
```sql
-- Optimal for large batches: Single scan + WindowAgg
WITH ranked_orders AS (
    SELECT 
        user_id, total_amount, created_at,
        ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
    FROM orders
)
SELECT * FROM ranked_orders WHERE rn <= 3;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **5 Logical Types:** INNER, LEFT OUTER, RIGHT OUTER, FULL OUTER, CROSS JOIN.
- **3 Physical Strategies:**
  - **Nested Loop:** Best for small outer table + indexed inner table ($O(N \log M)$).
  - **Hash Join:** Best for large unsorted tables with equality join conditions ($O(N + M)$); depends on `work_mem`.
  - **Merge Join:** Best for large pre-sorted inputs ($O(N + M)$).
- **Semi-Join vs. Anti-Join:** `EXISTS` compiles to a Semi-Join (stops at first match); `NOT EXISTS` compiles to an Anti-Join.
- **`NOT IN` vs. `NOT EXISTS` Trap:** `NOT IN` returns zero rows if the subquery contains a single `NULL`. Always use `NOT EXISTS`.
- **GEQO:** Switches to genetic heuristics when joining $> 12$ tables.

**Common Follow-up Questions:**
- *"What physical strategy does PostgreSQL choose when joining two 50M-row tables on unindexed IDs?"* → Hash Join (or Merge Join if sorted), utilizing `work_mem` to build in-memory buckets.
- *"Why does `EXPLAIN` show `Batches: 8` for a Hash Join and how do you fix it?"* → The hash table exceeded `work_mem` and spilled to disk; fix by increasing `work_mem` for the query session.
- *"What is the difference between an INNER JOIN and a Semi-Join?"* → An INNER JOIN produces duplicate rows if multiple matches exist; a Semi-Join (`EXISTS`) emits the outer row once immediately upon finding the first match.

**Red Flags (DO NOT Say):**
- ❌ *"A JOIN is always faster than a subquery."* (Modern optimizers unnest correlated subqueries into identical Semi-Joins or Hash Joins).
- ❌ *"NOT IN and NOT EXISTS are 100% interchangeable."* (If the subquery returns even one `NULL`, `NOT IN` evaluates to `UNKNOWN` and returns zero results).
- ❌ *"CROSS JOIN is just a syntax error."* (It is a valid Cartesian product producing $N \times M$ rows, used in matrix generation).
