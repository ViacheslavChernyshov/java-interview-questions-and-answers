# Difference between WHERE and HAVING

---

## 🟢 Junior Level

Both **WHERE** and **HAVING** are SQL clauses used to filter data, but they operate at fundamentally different stages of the query processing pipeline:
- **`WHERE`:** Filters individual **rows** **before** any grouping or aggregation takes place.
- **`HAVING`:** Filters aggregated **groups** **after** `GROUP BY` has collapsed rows into summary buckets.

**Simple analogy:** Imagine sorting a bin of coins:
1. **WHERE:** You inspect the pile and remove all foreign currency tokens (filtering raw rows before grouping).
2. **GROUP BY:** You stack the remaining coins into piles by denomination (1¢, 5¢, 10¢, 25¢).
3. **HAVING:** You inspect the completed stacks and discard any pile containing fewer than 10 coins (filtering summary groups).

**Example:**
```sql
-- WHERE: Filters individual orders by status before grouping
-- HAVING: Filters resulting user groups where completed order count exceeds 5
SELECT user_id, COUNT(*) AS completed_orders
FROM orders
WHERE status = 'COMPLETED'  -- 1. Filter rows before aggregation (Uses Indexes!)
GROUP BY user_id
HAVING COUNT(*) > 5;        -- 2. Filter groups after aggregation
```

## 🟡 Middle Level

### Logical SQL Query Processing Pipeline

SQL queries are executed in a strict logical order that differs from their written syntax:

$$\text{1. FROM / JOIN} \longrightarrow \text{2. WHERE} \longrightarrow \text{3. GROUP BY} \longrightarrow \text{4. HAVING} \longrightarrow \text{5. SELECT} \longrightarrow \text{6. ORDER BY} \longrightarrow \text{7. LIMIT}$$

Because `WHERE` runs at Step 2 and `HAVING` runs at Step 4:
- **`WHERE`** can utilize table B-tree indexes, drastically reducing the volume of data fed into sorting and aggregation nodes.
- **`HAVING`** cannot use regular B-tree indexes on aggregate calculations (`COUNT`, `SUM`, `AVG`), as these values are computed on the fly.

### Performance Impact: The Misplaced Filter Anti-Pattern

```sql
-- ❌ CATASTROPHIC PERFORMANCE: Filters city AFTER aggregating the entire table!
SELECT city, COUNT(*) 
FROM users
GROUP BY city
HAVING city = 'London';  -- Forces HashAggregate across 50,000,000 global users!

-- ✅ OPTIMAL PERFORMANCE: Filters city BEFORE aggregation
SELECT city, COUNT(*) 
FROM users
WHERE city = 'London'    -- Index Scan isolates London rows immediately; aggregates only ~100k rows
GROUP BY city;
```

### Feature Comparison Matrix

| Feature / Behavior | `WHERE` Clause | `HAVING` Clause |
|---|---|---|
| **Filter Target** | Raw table / join rows | Summary groups (aggregated rows) |
| **Pipeline Stage** | Evaluated **before** `GROUP BY` | Evaluated **after** `GROUP BY` |
| **Aggregate Functions** | ❌ Forbidden (`WHERE COUNT(*) > 1` throws error) | ✅ Allowed (`HAVING COUNT(*) > 1`) |
| **B-Tree Index Usage** | ✅ Full index support (Index Scan) | ❌ No index support for aggregate expressions |
| **Memory Pressure** | Lowers memory usage by filtering early | Does not prevent `GROUP BY` memory bloat |

## 🔴 Senior Level

### Filter Push-down Optimization & Limitations

Starting in PostgreSQL 12+, the query planner attempts **Filter Push-down** to rewrite non-aggregate predicates from `HAVING` into `WHERE`:

```sql
-- Written Query:
SELECT department_id, AVG(salary)
FROM employees
GROUP BY department_id
HAVING department_id IN (1, 2, 3) AND AVG(salary) > 80000;

-- Planner's Internal Push-Down Rewrite:
SELECT department_id, AVG(salary)
FROM employees
WHERE department_id IN (1, 2, 3)  -- PUSHED DOWN to enable Index Scan!
GROUP BY department_id
HAVING AVG(salary) > 80000;
```

**Why you must NEVER rely on automatic Push-Down:**
- Push-down fails inside complex multi-level Views, `MATERIALIZED` CTEs, subqueries with volatile functions, and `WINDOW` function pipelines.
- Relying on optimizer heuristics risks catastrophic regressions during database upgrades or query refactoring.

### Memory Pressure: `work_mem` Spills

When non-aggregate filters are placed in `HAVING`, the `HashAggregate` executor must allocate hash buckets for every distinct grouping key across the entire table. If distinct groups exceed `work_mem`, Postgres spills partition batches to disk (`temp_files`):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT status, COUNT(*) FROM orders GROUP BY status;
-- HashAggregate (cost=... Memory Usage: 4096kB, Disk: 450MB)  <-- DISK SPILL!
```
Adding `WHERE created_at > NOW() - INTERVAL '30 days'` filters rows prior to aggregation, allowing the hash table to remain 100% in RAM.

### `WHERE` vs `HAVING` vs Window Functions

Window functions evaluate **after `HAVING`**. Therefore, filtering on a window function result (e.g., `ROW_NUMBER()`) cannot be performed in `WHERE` or `HAVING`:

```sql
-- ❌ SYNTAX ERROR: Window functions cannot appear in WHERE or HAVING
SELECT user_id, amount,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
FROM orders
HAVING rn = 1;

-- ✅ SOLUTION: Wrap in a CTE or Subquery
WITH ranked_orders AS (
    SELECT user_id, amount,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
    FROM orders
)
SELECT user_id, amount
FROM ranked_orders
WHERE rn = 1;
```

### PostgreSQL Aggregate `FILTER` Clause

```sql
-- Advanced aggregation filtering within the same group
SELECT 
    department_id,
    COUNT(*) AS total_employees,
    COUNT(*) FILTER (WHERE salary > 100000) AS high_earners_count,
    AVG(salary) FILTER (WHERE status = 'ACTIVE') AS active_avg_salary
FROM employees
GROUP BY department_id
HAVING COUNT(*) FILTER (WHERE salary > 100000) >= 5;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Execution Pipeline:** `FROM` -> `WHERE` -> `GROUP BY` -> `HAVING` -> `SELECT` -> `ORDER BY` -> `LIMIT`.
- **`WHERE`:** Filters rows before aggregation, leverages B-tree indexes, reduces `work_mem` pressure.
- **`HAVING`:** Filters summary groups after aggregation; aggregate functions (`COUNT`, `SUM`, `AVG`) are allowed.
- **Push-down:** Postgres 12+ pushes non-aggregate filters down, but explicit `WHERE` placement is mandatory in production code.
- **Window Functions:** Evaluated after `HAVING`; filtering by window functions requires subqueries/CTEs.

**Common Follow-up Questions:**
- *"Can you use HAVING without a GROUP BY clause?"* → Yes. The entire table is treated as a single group (e.g., `SELECT 'Exceeded' FROM orders HAVING COUNT(*) > 1000000`).
- *"Why does `WHERE AVG(salary) > 50000` throw a syntax error?"* → `WHERE` executes before rows are grouped, so aggregate averages do not yet exist.
- *"How does putting non-aggregate conditions in HAVING affect performance?"* → It forces Postgres to aggregate all table rows into memory/disk before filtering, whereas `WHERE` discards rows immediately via index scans.

**Red Flags (DO NOT Say):**
- ❌ *"HAVING is just an alternative syntax for WHERE."* (They operate at completely different pipeline stages).
- ❌ *"Postgres will always automatically fix misplaced filters in HAVING."* (Push-down fails across views, complex CTEs, and joins).
- ❌ *"You can filter ROW_NUMBER() in HAVING."* (Window functions evaluate after HAVING; requires a CTE/subquery).
