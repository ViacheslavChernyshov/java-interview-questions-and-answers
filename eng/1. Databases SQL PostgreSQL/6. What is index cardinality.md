# What is index cardinality?

---

## 🟢 Junior Level

**Cardinality** refers to the number of **unique (distinct) values** contained within a specific database table column.

**Why it matters:** The PostgreSQL cost-based query planner relies on cardinality estimates to determine whether executing an **Index Scan** is cheaper than scanning the entire table via a **Sequential Scan (Seq Scan)**.
- **High Cardinality:** A large number of unique values (e.g., `email`, `user_id`, `uuid`). An index is extremely effective because a lookup isolates one or very few rows.
- **Low Cardinality:** Very few unique values across millions of rows (e.g., `gender` with `M`/`F`, `is_active` with `true`/`false`). An index is usually ineffective because any single value matches a huge percentage of the table.

**Example:**
```sql
-- Table 'users' with 1,000,000 rows

-- High Cardinality (~1,000,000 distinct values) -> Index is highly effective ✅
SELECT COUNT(DISTINCT email) FROM users; 

-- Low Cardinality (2 distinct values) -> Index is ineffective ❌
SELECT COUNT(DISTINCT gender) FROM users; 
```

**Rule of Thumb:** Focus indexing efforts on columns with high cardinality or skewed low-cardinality distributions filtered via partial indexes.

## 🟡 Middle Level

### Cardinality vs. Selectivity

While frequently used interchangeably in conversation, they have precise distinct definitions in database engine architecture:

| Term | Definition | Formula / Example |
|---|---|---|
| **Cardinality** | The total number of distinct values in a column | `COUNT(DISTINCT city) = 500` |
| **Selectivity** | The fraction of rows in a table satisfying a specific query predicate | $\frac{\text{Matching Rows}}{\text{Total Table Rows}} = \frac{100}{1,000,000} = 0.0001$ (High Selectivity) |

> **Crucial Rule:** High selectivity means a query returns a **very small percentage** of the table. High cardinality generally produces high selectivity for equality filters (`WHERE id = 42`), making index access vastly cheaper than sequential scans.

### How PostgreSQL Estimates Cardinality

PostgreSQL collects column statistics via the `ANALYZE` command (executed automatically by the `autovacuum` daemon) and stores them in the `pg_statistic` system catalog (viewable via `pg_stats`):

```sql
SELECT 
    attname AS column_name,
    n_distinct,       -- Estimated distinct values
    correlation       -- Physical disk vs logical sort correlation
FROM pg_stats
WHERE tablename = 'users' AND attname = 'email';
```

**Interpreting `n_distinct`:**
- **Positive Number ($> 0$):** An exact estimated count of distinct values (e.g., `500` = exactly 500 distinct values).
- **Negative Number ($< 0$):** A distinct fraction relative to total table rows (e.g., `-1.0` indicates 100% unique values where every row is distinct; `-0.2` indicates 20% distinct values).

### Execution Plan Selection Thresholds

| Matching Rows (% of Total Table) | Execution Strategy Chosen by Planner |
|---|---|
| **< 1–5%** | **Index Scan** (Direct B-tree traversal to Heap TID) |
| **5–20%** | **Bitmap Index Scan** (Gathers TIDs into bitmap, sorts by physical block, reads heap sequentially) |
| **> 20–25%** | **Seq Scan** (Sequential block streaming is faster than random I/O index lookups) |

### Data Skew (Most Common Values - MCV)

A column may have low overall cardinality but strong **data skew**:
```sql
-- Table 'orders' with 1,000,000 rows
-- status = 'COMPLETED' (950,000 rows = 95%)
-- status = 'FAILED'    (10,000 rows = 1%)

-- Query 1: Planner chooses Seq Scan (95% of table)
EXPLAIN SELECT * FROM orders WHERE status = 'COMPLETED';

-- Query 2: Planner chooses Index Scan (1% of table)
EXPLAIN SELECT * FROM orders WHERE status = 'FAILED';
```
PostgreSQL stores the top frequent values in its **MCV (Most Common Values)** list along with their exact frequencies (`most_common_freqs`), allowing it to dynamically switch query plans depending on the literal constant supplied in the query!

## 🔴 Senior Level

### Deep Dive: Four Pillars of PostgreSQL Statistics

In `pg_stats`, PostgreSQL maintains 4 critical attributes for cardinality estimation:

1. **`n_distinct`:** Normalized distinct value ratio or absolute count.
2. **`most_common_vals` (MCV) & `most_common_freqs` (MCF):** Arrays of the top $N$ most frequent values and their exact relative percentages.
3. **`histogram_bounds`:** Equi-depth histogram buckets for non-MCV values, used to calculate selectivity for range predicates (`<`, `>`, `BETWEEN`).
4. **`correlation`:** Statistical correlation between physical disk ordering and logical index order (ranging from `-1.0` to `+1.0`):
   - `correlation ≈ 1.0`: Physical rows are sequentially ordered on disk matching the index. Index scans produce contiguous, sequential disk reads.
   - `correlation ≈ 0.0`: Physical rows are scattered randomly across pages. Index scans cause severe random I/O disk thrashing.

### Extended Statistics (`CREATE STATISTICS`)

**The Cross-Column Independence Fallacy:** By default, PostgreSQL assumes columns are completely independent when calculating joint selectivity:

$$P(\text{make} = \text{'Honda'} \land \text{model} = \text{'Civic'}) = P(\text{make} = \text{'Honda'}) \times P(\text{model} = \text{'Civic'})$$

In reality, if `make = 'Honda'`, `model = 'Civic'` is vastly more probable than random chance. The planner underestimates matching rows by orders of magnitude, choosing an inappropriate Nested Loop join instead of a Hash Join.

**Solution: Extended Statistics (PostgreSQL 10+)**
```sql
-- 1. Functional Dependencies (knowing 'model' determines 'make')
CREATE STATISTICS s_cars_make_model (dependencies)
ON make, model FROM cars;

-- 2. Multivariate Distinct Counts (computes joint n_distinct for multi-column grouping)
CREATE STATISTICS s_users_city_zip (ndistinct)
ON city, zip_code FROM users;

-- 3. Multivariate MCV Lists (PG 13+: joint MCV combinations)
CREATE STATISTICS s_orders_status_priority (mcv)
ON status, priority FROM orders;

-- Refresh catalog statistics
ANALYZE cars, users, orders;
```

### Tuning `default_statistics_target`

When dealing with heavily skewed distributions or large partitioned tables:
```sql
-- Default target is 100 histogram buckets
SHOW default_statistics_target;

-- Increase statistics target for specific skewed columns (creates up to 1000 histogram buckets)
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;
```

### Production Monitoring Queries

```sql
-- 1. Inspect column correlation and distinct value estimates
SELECT 
    attname AS column_name,
    n_distinct,
    ROUND(correlation::numeric, 3) AS physical_correlation,
    CASE 
        WHEN ABS(correlation) < 0.3 THEN 'LOW - Heavy Random I/O during Index Scan'
        WHEN ABS(correlation) < 0.7 THEN 'MEDIUM'
        ELSE 'HIGH - Sequential Heap Access'
    END AS io_pattern
FROM pg_stats
WHERE tablename = 'orders'
ORDER BY ABS(correlation) ASC;

-- 2. Inspect extended statistics definitions
SELECT 
    stxname AS stats_name,
    stxkeys AS attribute_numbers,
    stxkind AS enabled_statistics_types
FROM pg_statistic_ext
WHERE stxrelid = 'orders'::regclass;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Cardinality:** The count of unique values in a column; **Selectivity:** The ratio of matching rows to total table rows.
- **Planner Selection:** High selectivity (< 5%) -> `Index Scan`; Moderate selectivity (5–20%) -> `Bitmap Index Scan`; Low selectivity (> 25%) -> `Seq Scan`.
- **`n_distinct` Interpretation:** Negative values represent fractions (`-1.0` = 100% unique); positive values represent absolute distinct counts.
- **Physical Correlation:** `-1.0` to `+1.0`. Low correlation (< 0.3) means physical heap rows are scattered, making Index Scans suffer from random disk seek penalties.
- **Extended Statistics (`CREATE STATISTICS`):** Captures multi-column functional dependencies, multivariate `n_distinct`, and multi-column MCVs to prevent catastrophic plan miscalculations.

**Common Follow-up Questions:**
- *"Why does Postgres choose a Seq Scan even when an index exists on a filtered column?"* → If the filter matches > 15–20% of rows (low selectivity) or statistics indicate data skew, reading blocks sequentially in memory is faster than random index seeks.
- *"What does `n_distinct = -1` mean in `pg_stats`?"* → Every row has a unique value (100% uniqueness, e.g., a Primary Key).
- *"How do you fix planner row count underestimations when filtering by two correlated columns like `state` and `city`?"* → Create extended statistics using `CREATE STATISTICS ... (dependencies, ndistinct) ON state, city FROM table;` followed by `ANALYZE`.

**Red Flags (DO NOT Say):**
- ❌ *"An index on a boolean `is_deleted` column will always speed up queries looking for active records."* (If 99% of rows are `is_deleted = false`, Postgres will ignore the index and run a Seq Scan; use a partial index `WHERE is_deleted = false` instead).
- ❌ *"Negative `n_distinct` means the column has negative numbers."* (It represents a percentage ratio: `-1.0` = 100% unique).
- ❌ *"Postgres automatically detects correlations between different columns."* (Standard statistics evaluate single columns in isolation; extended statistics must be created explicitly).
