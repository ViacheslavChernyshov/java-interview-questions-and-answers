# How does B-tree index work?

---

## 🟢 Junior Level

**B-tree (Balanced Multi-way Tree)** is the default, general-purpose balanced index tree structure used by PostgreSQL.

**Why "Balanced"?** All leaf nodes in a B-tree reside at the exact same depth from the root. This guarantees consistent logarithmic search time $O(\log n)$ for every lookup, preventing pathological degeneration into $O(n)$ linked lists (a common issue in unbalanced binary search trees).

**Simple analogy:** Imagine the index in an encyclopedia:
- **Top level (Root):** Volume letters (A–D, E–H, I–P, Q–Z)
- **Middle level (Internal nodes):** Subject subheadings
- **Bottom level (Leaf nodes):** Exact page numbers and paragraph locations

To find an entry, you start at the root, compare your search key, follow the specific volume reference downward, and pinpoint the exact row without reading the rest of the book.

**Core idea:**
- Data is stored in **lexicographical sorted order**.
- Search is extremely fast: traversing 1,000,000+ entries requires reading only 3–4 eight-kilobyte index pages instead of scanning gigabytes of table heap.
- PostgreSQL automatically balances the tree during `INSERT`, `UPDATE`, and `DELETE` operations.

**Example:**
```sql
-- Creating a standard B-tree index (B-tree is used by default)
CREATE INDEX idx_users_email ON users(email);

-- Index lookup runs in O(log n) time
SELECT * FROM users WHERE email = 'test@example.com';
```

**When to use:**
- Equality comparisons: `WHERE id = 42`
- Range queries: `WHERE price BETWEEN 100 AND 500` or `WHERE created_at >= '2026-01-01'`
- Prefix string searches: `WHERE username LIKE 'alex%'`
- Pre-sorted ordering: `ORDER BY created_at DESC LIMIT 10`

## 🟡 Middle Level

### How It Works Internally

PostgreSQL B-trees are organized into standard **8 KB pages** (disk blocks) structured hierarchically:

```
Root Page (Level 2)
  ├── Internal Page (Level 1) ──► Leaf Pages (Level 0)
  └── Internal Page (Level 1) ──► Leaf Pages (Level 0)
```

**Internal 8 KB Page Structure:**
1. **Page Header:** Contains block LSN (*Log Sequence Number* for WAL replay and crash recovery) and checksums.
2. **Index Tuples:** Key values paired with downlink pointers (block numbers to child pages) in Internal nodes, or key values paired with **TID** `(block_num, offset)` pointers to table Heap rows in Leaf nodes.
3. **High Key:** The maximum boundary value allowed on this page.
4. **Special Area:** Opaque metadata containing bidirectional sibling pointers (`P_NEXT`, `P_PREV`) for horizontal range scans.

### Traversal and Search Algorithm

1. Begin at the **Root** page (cached in memory via the meta-page's `Fastroot`).
2. Perform binary search across index tuples on the page.
3. Follow the downlink block pointer to the child **Internal** page.
4. Repeat descent until reaching the target **Leaf** page (Level 0).
5. Read the matching key's TID and fetch the physical tuple from the table's heap storage.

### Why B-tree Instead of a Standard Binary Search Tree?

| Metric / Characteristic | Binary Search Tree (BST) | PostgreSQL B-Tree |
|---|---|---|
| **Branching Factor (Fan-out)** | 2 (left / right child) | 100–500+ child pointers per 8 KB page |
| **Height for 1,000,000 Records** | ~20 levels | **3–4 levels** |
| **Disk I/O Operations** | ~20 random disk reads | **3–4 page reads** (frequently hit in cache) |
| **Storage Locality** | Poor (nodes scattered across memory) | High (dense 8 KB pages match OS block I/O) |

### Common Pitfalls

1. **Ignoring Leftmost Prefix Rule in Composite Indexes**
   ```sql
   -- Composite index on (last_name, first_name)
   -- ✅ Uses index:
   WHERE last_name = 'Doe';
   WHERE last_name = 'Doe' AND first_name = 'John';

   -- ❌ Cannot effectively use index (skips leading column):
   WHERE first_name = 'John';
   ```

2. **Applying Functions to Indexed Columns**
   ```sql
   -- ❌ B-tree index on 'name' is ignored:
   WHERE UPPER(name) = 'ALEX';

   -- ✅ Solution: Build an expression index:
   CREATE INDEX idx_users_name_upper ON users(UPPER(name));
   ```

### When NOT to Use B-tree

- **Full-Text Search / JSONB / Arrays:** Use **GIN** (Generalized Inverted Index).
- **Geometric / Multidimensional Data:** Use **GiST** (R-Tree style bounding boxes).
- **Massive Append-Only Time Series (>100 GB):** Use **BRIN** for near-zero storage footprint.

## 🔴 Senior Level

### Internal Concurrency: Modified Lehman & Yao Algorithm

PostgreSQL implements high-concurrency B-trees using the **Lehman & Yao B-link tree algorithm**. 

Unlike naive tree implementations that acquire long-term locks from root to leaf:
- Traversals do **not lock the whole path**. A backend takes a short-term **shared buffer content latch** on a page, identifies the child pointer, pins the child buffer, and releases the parent latch immediately.
- **High Key & `P_NEXT` Invariant:** Every page holds a *High Key*. If a concurrent insert causes a **Page Split** while a reader is descending, the reader notices that `search_key > High_Key`. Instead of restarting at the root, the reader simply traverses rightward using the page's horizontal link pointer `P_NEXT`.

```
Page Split Mechanics:
Before Split (Full Page):       After Split (50/50 Allocation):
┌─────────────────────────┐     ┌──────────────┐       ┌──────────────┐
│ Key_A, Key_B, Key_C ... │ ──► │ Key_A, Key_B │ ────► │ Key_C, Key_D │
└─────────────────────────┘     └──────────────┘ P_NEXT└──────────────┘
                                       ▲
                         Parent Internal Node Updated
```

### Modern Engine Optimizations (PostgreSQL 13+)

#### 1. B-tree Deduplication
In PG 12 and below, duplicate keys stored duplicate `(Key, TID)` tuples, bloating the tree.
Starting with **PostgreSQL 13**, B-Tree deduplication collapses identical keys into posting lists:
```sql
-- PG 12: Stores (Key='ACTIVE', TID=1), (Key='ACTIVE', TID=2) ... (Key='ACTIVE', TID=1000000)
-- PG 13+: Stores Key='ACTIVE' once -> Posting List [TID_1, TID_2, ..., TID_N]
CREATE INDEX idx_orders_status ON orders(status);
-- Results in 70-90% disk space reduction for low/medium cardinality columns
```

#### 2. `LP_DEAD` Marking & Micro-Vacuuming
When a table heap row is deleted or updated, index entries cannot be deleted immediately due to active MVCC snapshots. 
- The index tuple pointer is flagged as `LP_DEAD`.
- Subsequent index scans notice `LP_DEAD` items and perform in-memory pruning (micro-vacuuming), avoiding re-reading dead heap pages before `VACUUM` runs.

### Edge Cases and Performance Tuning

#### 1. Index Bloat & `REINDEX CONCURRENTLY`
Random insertions and deletions cause leaf pages to split, leaving average leaf density low (< 50%).
```sql
-- Inspect index density via pgstattuple extension
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstatindex('idx_users_email');
-- If avg_leaf_density < 50% -> Index is bloated

-- Online zero-downtime rebuild
REINDEX INDEX CONCURRENTLY idx_users_email;
```

#### 2. Fillfactor Tuning for Heavy Update Workloads
```sql
-- Reserve 20-30% free space on each leaf page for local updates
CREATE INDEX idx_orders_status ON orders(status) WITH (fillfactor = 75);
```

### Production Monitoring Queries

```sql
-- 1. Inspect B-tree index statistics and leaf density
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'orders';

-- 2. Inspect physical B-tree tree level and leaf fragmentation
SELECT * FROM pgstatindex('idx_orders_id');
-- tree_level: 0 (single page), 1-2 (small table), 3-4 (large production table)
-- avg_leaf_density: percentage of usable space in leaf pages
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Structure:** Hierarchical multi-way balanced tree: Root → Internal Routing Nodes → Leaf Nodes with TIDs pointing to Heap blocks.
- **Fan-out:** 100–500+ child pointers per page, maintaining a shallow height of 3–4 levels even for billions of records.
- **Time Complexity:** $O(\log n)$ search, insert, and delete.
- **Concurrency Model:** Lehman & Yao algorithm with page-level latches, horizontal `P_NEXT` right-links, and High Key boundaries.
- **Deduplication (PostgreSQL 13+):** Groups identical keys into posting lists, slashing index bloat by 70–90%.
- **`REINDEX CONCURRENTLY`:** Online index rebuild without table write locks.

**Common Follow-up Questions:**
- *"Why is B-tree preferred over a Binary Search Tree in databases?"* → BSTs have a fan-out of 2, requiring ~20–30 random disk seeks for large datasets; B-trees have high fan-out (>100), keeping height to 3–4 disk reads.
- *"What is a Page Split and why is it dangerous?"* → When an 8 KB leaf page fills up, Postgres allocates a new page, moves half the items, and updates the parent. Frequent splits cause disk fragmentation (bloat) and WAL write spikes.
- *"How does PostgreSQL handle concurrent splits without locking the whole tree?"* → Lehman-Yao B-link tree: pages have High Keys and right-pointers (`P_NEXT`), allowing readers to traverse rightward if a split occurred mid-search.

**Red Flags (DO NOT Say):**
- ❌ *"B-tree is a binary tree with two children per node."* (No, it is a multi-way balanced search tree with hundreds of child pointers per page).
- ❌ *"Standard VACUUM shrinks bloated index files back to smaller sizes on disk."* (No, VACUUM only frees slots inside existing pages; only `REINDEX` or `VACUUM FULL` shrinks the OS file).
- ❌ *"Deduplication works for unique indexes."* (Unique indexes require distinct keys by definition; deduplication applies to non-unique B-tree indexes).
