# What does GROUP BY do?

---

## 🟢 Junior Level

The **GROUP BY** clause collapses multiple table rows sharing identical values across specified columns into distinct summary rows, allowing aggregate mathematical functions to be calculated across each bucket.

**Simple analogy:** Imagine you have a basket of mixed fruit. `GROUP BY fruit_type` sorts the fruits into distinct piles (Apples, Bananas, Oranges). Once separated into piles, you can run calculations like counting the number of fruits in each pile (`COUNT`) or calculating their average weight (`AVG`).

**Example:**
```sql
-- Table 'orders':
-- user_id | amount
-- 1       | 100
-- 1       | 200
-- 2       | 150

-- Group orders by user_id and calculate total expenditure per user
SELECT user_id, SUM(amount) AS total_spent
FROM orders
GROUP BY user_id;

-- Output:
-- user_id | total_spent
-- 1       | 300
-- 2       | 150
```

**Common Aggregate Functions:**
- `COUNT(*)` / `COUNT(col)` — Row count
- `SUM(col)` — Total sum
- `AVG(col)` — Arithmetic mean
- `MIN(col)` / `MAX(col)` — Smallest / largest value

## 🟡 Middle Level

### Physical Execution Engines: `HashAggregate` vs `GroupAggregate`

PostgreSQL implements two distinct execution algorithms for grouping:

```
                  ┌──────────────────────┐
                  │ GROUP BY user_id     │
                  └──────────┬───────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   ┌─────────────────┐               ┌─────────────────┐
   │  HashAggregate  │               │ GroupAggregate  │
   │ Unsorted Data   │               │ Sorted / Index  │
   │ Uses work_mem   │               │ Minimal Memory  │
   └─────────────────┘               └─────────────────┘
```

#### 1. `HashAggregate` (Default for Unsorted Inputs)
- Builds an in-memory hash table in `work_mem` where keys are grouping columns and values are aggregate accumulators.
- As rows stream in, Postgres computes `hash(group_key)` and updates accumulator states in place.
- **Complexity:** $O(N)$ execution time.

#### 2. `GroupAggregate` (For Sorted Inputs)
- Reads rows in strict sorted order by the grouping keys.
- Aggregates contiguous rows until the group key changes, then emits the summary row and resets accumulators.
- **Advantage:** Requires negligible memory because it only maintains state for the current active group.
- **Complexity:** $O(N)$ if pre-sorted via an Index Scan; $O(N \log N)$ if an explicit `Sort` node is required.

### Grouping by Primary Key (Functional Dependency)

In standard SQL-92, every non-aggregated column in `SELECT` was required in `GROUP BY`. In PostgreSQL (SQL:1999+ compliance), grouping by a table's **PRIMARY KEY** automatically satisfies functional dependency:

```sql
-- ✅ VALID in PostgreSQL: Grouping by Primary Key allows selecting any column from 'users'
SELECT u.id, u.name, u.email, COUNT(o.id) AS total_orders
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id; -- 'name' and 'email' do not need to be in GROUP BY!
```

### Handling `NULL` Values

In SQL grouping, all `NULL` values are grouped together into a **single distinct group**:
```sql
SELECT status, COUNT(*) 
FROM orders 
GROUP BY status;
-- Output:
-- 'COMPLETED' | 500
-- 'PENDING'   | 120
-- NULL        | 15   <-- All NULL rows aggregated into one group
```

## 🔴 Senior Level

### Deep Dive: `HashAggregate` Disk Spilling (PostgreSQL 13+)

- **Prior to PostgreSQL 13:** If the total size of unique hash groups exceeded `work_mem`, PostgreSQL aborted the query with an out-of-memory error or defaulted to an expensive disk-based external merge sort.
- **PostgreSQL 13+:** `HashAggregate` supports **disk spilling**. When `work_mem` fills up, hash table partitions are serialized to temporary files on disk and processed in batches.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT category_id, COUNT(*) FROM massive_catalog GROUP BY category_id;
-- HashAggregate (cost=... Memory Usage: 4096kB, Disk: 350MB, Batches: 8) <-- DISK SPILL!
```
*Tuning:* Increase `work_mem` for the session (`SET work_mem = '256MB'`) to keep large aggregations entirely in RAM.

### Multi-Dimensional Grouping: `ROLLUP`, `CUBE`, `GROUPING SETS`

Instead of running multiple expensive queries combined with `UNION ALL`, PostgreSQL computes multi-dimensional subtotals in a **single table pass**:

#### 1. `ROLLUP` (Hierarchical Subtotals)
```sql
SELECT department, region, SUM(sales)
FROM sales_data
GROUP BY ROLLUP (department, region);
-- Computes:
-- 1. (department, region) detail
-- 2. (department, NULL) department subtotals
-- 3. (NULL, NULL) grand total
```

#### 2. `CUBE` (All Dimensional Permutations)
```sql
SELECT department, region, SUM(sales)
FROM sales_data
GROUP BY CUBE (department, region);
-- Computes all 2^N combinations: (dept, reg), (dept, null), (null, reg), (null, null)
```

#### 3. `GROUPING SETS` (Custom Selected Aggregations)
```sql
SELECT department, region, SUM(sales)
FROM sales_data
GROUP BY GROUPING SETS (
    (department, region),
    (department),
    ()
);
```

### Parallel Aggregation Engine

```sql
EXPLAIN SELECT department_id, AVG(salary) FROM employees GROUP BY department_id;
-- Finalize GroupAggregate (Leader process combines worker outputs)
--   -> Gather (Collects partial streams)
--       -> Partial GroupAggregate (Workers aggregate local chunks in parallel)
--           -> Parallel Index Scan on employees
```
Workers compute partial states (`count` and `sum` locally), stream intermediate structures through `Gather`, and the leader process runs `Finalize` to compute exact grand totals (`sum / count`).

### The SQL Standard `FILTER` Clause

```sql
-- Clean aggregation without cumbersome CASE WHEN statements
SELECT 
    department_id,
    COUNT(*) AS total_headcount,
    COUNT(*) FILTER (WHERE salary > 120000) AS high_earners_count,
    AVG(salary) FILTER (WHERE tenure_years >= 5) AS senior_avg_salary
FROM employees
GROUP BY department_id;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **2 Physical Engines:** `HashAggregate` (in-memory hash table in `work_mem`) vs `GroupAggregate` (streaming sorted data with minimal RAM).
- **Index Optimization:** A B-tree index on grouping columns allows `GroupAggregate` to execute without sorting.
- **Disk Spilling (PG 13+):** `HashAggregate` spills to disk partitions when groups exceed `work_mem`.
- **Parallel Aggregation:** Executes via `Partial Aggregate` (workers) -> `Gather` -> `Finalize Aggregate` (leader).
- **Multi-Dimensional Grouping:** `ROLLUP` (hierarchical), `CUBE` (all combinations), and `GROUPING SETS` compute subtotals in a single pass.
- **Primary Key Grouping:** Grouping by Primary Key allows selecting any column from that table.

**Common Follow-up Questions:**
- *"When does the optimizer choose GroupAggregate over HashAggregate?"* → When the input data is already sorted by the group keys (e.g., via an index) or when `work_mem` is too small for HashAggregate.
- *"How do ROLLUP and CUBE differ from UNION ALL?"* → `ROLLUP`/`CUBE` scan the table once and aggregate intermediate states; `UNION ALL` scans the entire table $N$ times.
- *"How are NULL values handled in GROUP BY?"* → All `NULL` values are grouped together into a single summary row.

**Red Flags (DO NOT Say):**
- ❌ *"GROUP BY always sorts the data."* (HashAggregate uses an in-memory hash table and returns rows in arbitrary hash order).
- ❌ *"You must always include every selected column in the GROUP BY clause."* (Grouping by Primary Key satisfies functional dependency for all table attributes).
- ❌ *"Disk spilling in HashAggregate is acceptable for high-throughput OLTP."* (Disk spilling causes massive I/O degradation; increase `work_mem`).
