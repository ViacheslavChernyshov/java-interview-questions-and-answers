# How to optimize slow queries?

---

## 🟢 Junior Level

Query optimization in PostgreSQL is the systematic process of identifying, diagnosing, and accelerating slow-running database operations.

**The 4-Step Junior Optimization Loop:**
1. **Identify:** Detect the slow query via application metrics, slow query logs, or `pg_stat_statements`.
2. **Inspect:** Run `EXPLAIN (ANALYZE, BUFFERS)` to view the execution plan and locate the bottleneck.
3. **Diagnose:** Determine the root cause (e.g., a `Seq Scan` reading 1,000,000 rows, or disk spilling during a `Sort`).
4. **Remediate:** Implement the fix (e.g., adding an index on the filtered column, increasing `work_mem`, or rewriting the query).

**Example:**
```sql
-- Step 1 & 2: Inspect plan of slow query
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM users WHERE email = 'bob@example.com';
-- Output: Seq Scan on users (cost=0.00..18500.00 actual rows=1 actual time=45.2ms)
-- Rows Removed by Filter: 999,999  <-- Reading whole table for 1 row!

-- Step 4: Remediate with a B-tree Index
CREATE INDEX idx_users_email ON users(email);

-- Verified: Execution time drops from 45.2ms to 0.04ms (1000x faster)!
```

**Most Common Culprits:**
- Missing index on columns filtered in `WHERE` or joined in `ON`.
- Functions wrapping indexed columns (e.g., `WHERE LOWER(email) = ...`), which prevent standard B-tree lookups.
- Implicit type conversions (e.g., passing integer literals to a `varchar` column).
- Fetching unnecessary columns via `SELECT *`.

## 🟡 Middle Level

### Workload Discovery: `pg_stat_statements`

In production, never optimize blindly; identify the queries causing the highest cumulative database load:

```sql
-- Enable the official query analytics extension:
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 5 queries consuming the most cumulative database CPU/execution time:
SELECT 
    query,
    calls,
    ROUND(mean_exec_time::numeric, 2) AS avg_ms,
    ROUND(total_exec_time::numeric, 2) AS total_ms,
    shared_blks_hit,
    shared_blks_read,
    ROUND(100.0 * shared_blks_hit / NULLIF(shared_blks_hit + shared_blks_read, 0), 2) AS cache_hit_pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;
```

### Common Anti-Patterns and Direct Solutions

#### 1. Function Wrapping (Bypassing B-Trees)
```sql
-- ❌ ANTI-PATTERN: Standard B-tree index on 'created_at' is completely bypassed
SELECT * FROM orders WHERE DATE(created_at) = '2026-04-01';

-- ✅ SOLUTION A (Expression Index):
CREATE INDEX idx_orders_date ON orders(DATE(created_at));

-- ✅ SOLUTION B (Range Query - Best Practice):
SELECT * FROM orders 
WHERE created_at >= '2026-04-01 00:00:00' AND created_at < '2026-04-02 00:00:00';
```

#### 2. Implicit Type Mismatch
```sql
-- Column 'phone_number' is declared as VARCHAR(32)
-- ❌ Passing a raw integer forces PostgreSQL to CAST the entire table to numeric!
SELECT * FROM users WHERE phone_number = 18005550199; -- Forces Seq Scan

-- ✅ Passing exact string type allows instant B-tree Index Scan:
SELECT * FROM users WHERE phone_number = '18005550199';
```

#### 3. Disk Spilling during In-Memory Operations
```sql
-- EXPLAIN ANALYZE shows: Sort Method: external merge Disk: 45000kB
-- Remediate by granting adequate temporary work memory for the session:
SET work_mem = '128MB';
```

#### 4. The ORM N+1 Query Cascade
```sql
-- ❌ 1 query for users + 1,000 separate queries in a loop for orders:
-- for (User u : users) { orderRepo.findByUserId(u.getId()); }

-- ✅ Fetch via a single JOIN or batch IN-list query in 1 round-trip:
SELECT u.id, u.name, o.id AS order_id, o.total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.status = 'ACTIVE';
```

## 🔴 Senior Level

### The 4-Tier Architectural Optimization Framework

```
                          ┌───────────────────────────┐
                          │   Tier 1: SQL & Schema    │ Indexes, Covering, CTEs, De-correlation
                          ├───────────────────────────┤
                          │   Tier 2: Stats & Plan    │ ANALYZE, CREATE STATISTICS, Plan Cache
                          ├───────────────────────────┤
                          │   Tier 3: Engine Config   │ work_mem, random_page_cost, SSD Tuning
                          ├───────────────────────────┤
                          │   Tier 4: Architecture    │ PgBouncer, Partitioning, Materialized Views
                          └───────────────────────────┘
```

### 1. Function Volatility Tuning (`IMMUTABLE`, `STABLE`, `VOLATILE`)

When writing custom PL/pgSQL or SQL helper functions:
- **`VOLATILE` (Default):** The engine re-executes the function on every row and forbids index indexing.
- **`STABLE`:** Evaluated once per query scan if arguments are constant.
- **`IMMUTABLE`:** Can be pre-evaluated at query compilation time and indexed via functional indexes:

```sql
CREATE OR REPLACE FUNCTION sanitize_sku(text) RETURNS text AS $$
    SELECT UPPER(TRIM($1));
$$ LANGUAGE sql IMMUTABLE; -- Unlocks functional indexing & constant folding!
```

### 2. Resolving Parameterized Plan Cache Degenerations

In Java (Spring Boot / Hibernate), JDBC prepared statements switch to **Generic Plans** on the 6th execution. If table data is heavily skewed (e.g. status codes, tenant IDs), generic plans choose disastrous sequential scans:

```sql
-- Fix in application configuration or per-connection session:
SET plan_cache_mode = 'force_custom_plan';
```

### 3. Server Configuration for Modern NVMe SSD Storage

Default PostgreSQL configurations are tuned conservatively for legacy spinning HDDs:

```ini
# postgresql.conf optimization for modern SSD instances:
shared_buffers = 8GB                  # 25% of total system RAM
effective_cache_size = 24GB           # 75% of total system RAM
random_page_cost = 1.1                # Default 4.0 assumes spinning disks. 1.1 tells planner SSD random reads are nearly free!
work_mem = 64MB                       # Increases in-memory sort/hash budgets
maintenance_work_mem = 1GB            # Accelerates index creation and autovacuum
```

### 4. High-Scale Architecture: PgBouncer & Declarative Partitioning

- **Connection Pooling (PgBouncer in Transaction Mode):** PostgreSQL creates a dedicated OS process (~5–10 MB RAM) per client connection. 2,000 microservice connections thrash CPU caches via context switching. PgBouncer maps 2,000 client sockets to a pool of **50 backend PostgreSQL processes**, reclaiming 30%+ CPU capacity.
- **Declarative Partitioning:** For tables exceeding 100M rows, partition by range (e.g., date ranges). The optimizer uses **Partition Pruning** to eliminate unreferenced partition tables from the query plan entirely.
- **Materialized Views with Concurrent Refresh:**
  ```sql
  CREATE MATERIALIZED VIEW mv_daily_revenue AS
  SELECT date_trunc('day', created_at) AS day, SUM(total_amount) AS revenue
  FROM orders GROUP BY 1;
  CREATE UNIQUE INDEX idx_mv_revenue_day ON mv_daily_revenue(day);

  -- Zero read-downtime refresh:
  REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_revenue;
  ```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Systematic Approach:** Start with `pg_stat_statements` -> Profile with `EXPLAIN (ANALYZE, BUFFERS)` -> Fix at the lowest appropriate tier (SQL -> Stats -> Engine -> Architecture).
- **SSD Tuning:** `random_page_cost = 1.1` (down from 4.0) instructs the planner that random index reads on SSDs are not penalized.
- **B-tree Invalidation:** Avoid wrapping indexed columns in functions or mismatched types.
- **Generic vs Custom Plans:** Prepared statements can switch to generic plans; force custom plans if parameters have extreme data skew.
- **Memory Throttling:** Increase `work_mem` when `EXPLAIN` reports `external merge Disk` or multi-batch hash joins.
- **Architecture Tools:** Use PgBouncer for connection pooling, Declarative Partitioning for tables $> 100\text{M}$ rows, and Materialized Views for analytical aggregations.

**Common Follow-up Questions:**
- *"What is your step-by-step methodology when an API endpoint suddenly slows down from 50ms to 5s?"* → 1. Inspect `pg_stat_activity` for blocking locks. 2. Grab the query and run `EXPLAIN (ANALYZE, BUFFERS)`. 3. Check for Seq Scans or disk spills. 4. Check if `n_distinct` statistics are stale. 5. Verify if Hibernate is using a Generic Plan.
- *"Why is `random_page_cost = 1.1` important on cloud SSD instances?"* → The default `4.0` makes the planner assume random I/O is 4x more expensive than sequential scans, causing it to erroneously choose Seq Scans over Index Scans.
- *"How does PgBouncer improve database query throughput?"* → It multiplexes thousands of idle/active client connections into a small fixed pool of backend processes, eliminating CPU context-switching overhead and memory footprint.

**Red Flags (DO NOT Say):**
- ❌ *"I just add an index to every column in the WHERE clause."* (Causes massive write amplification and table bloat; only index selective filters and composite keys).
- ❌ *"Restarting PostgreSQL is the first step to fix slow queries."* (Destroys shared_buffers cache and resets metrics without solving the underlying bottleneck).
- ❌ *"Materialized Views should be used for real-time OLTP updates."* (They introduce data lag between refreshes and require maintenance overhead).
