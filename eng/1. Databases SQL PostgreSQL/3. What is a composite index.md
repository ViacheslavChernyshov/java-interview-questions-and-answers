# What is a composite index?

---

## 🟢 Junior Level

A **composite (compound / multi-column) index** is an index created across two or more columns of a single table simultaneously.

**Why:** A single well-designed composite index can satisfy queries that filter or sort by multiple columns, while replacing several redundant single-column indexes. This saves disk space, reduces RAM cache requirements, and minimizes write amplification during `INSERT`/`UPDATE` operations.

**Simple analogy:** Think of a telephone directory or contact book sorted first by `Last Name`, then by `First Name`. 
- You can easily find `"Smith, John"` because it is sorted by last name first, then first name.
- You can easily find all `"Smith"` entries (just using the last name).
- But if you only know the first name `"John"`, the book is useless — you would have to scan the entire directory from start to finish.

**Core idea:**
- One composite index can accelerate queries filtering on multiple columns.
- The **order of columns** in the index definition is **critically important**.
- It strictly enforces the **Leftmost Prefix Rule**.

**Example:**
```sql
-- Create a composite index on (city, age)
CREATE INDEX idx_users_city_age ON users(city, age);

-- ✅ Uses index: leading column 'city' is provided
SELECT * FROM users WHERE city = 'New York';

-- ✅ Uses index: both leading columns 'city' and 'age' are provided
SELECT * FROM users WHERE city = 'New York' AND age = 30;

-- ❌ CANNOT efficiently use index: leading column 'city' is skipped
SELECT * FROM users WHERE age = 30;
```

**When to use:**
- Queries frequently combining filters on the same 2–4 columns.
- Queries filtering on one column and ordering by another (e.g., `WHERE customer_id = 42 ORDER BY created_at DESC`).
- High-throughput tables where consolidating multiple single-column indexes reduces write overhead.

## 🟡 Middle Level

### How It Works Internally

A composite index sorts tuples **hierarchically (lexicographically)**:
1. Rows are sorted first by the 1st column.
2. For matching values of the 1st column, rows are sorted by the 2nd column.
3. For matching values of the 1st and 2nd columns, rows are sorted by the 3rd column, and so forth.

**The Leftmost Prefix Rule:** An index on `(A, B, C)` can accelerate queries filtering by:
- ✅ `WHERE A = ...`
- ✅ `WHERE A = ... AND B = ...`
- ✅ `WHERE A = ... AND B = ... AND C = ...`
- ❌ `WHERE B = ...` (Leading prefix `A` missing)
- ❌ `WHERE C = ...` (Leading prefixes `A` and `B` missing)
- ❌ `WHERE B = ... AND C = ...` (Leading prefix `A` missing)

### The Golden Rule of Column Ordering

$$\text{Equi-Filters } (=) \longrightarrow \text{Range-Filters } (<, >, \text{BETWEEN}) \longrightarrow \text{Sort/Covering Columns } (\text{ORDER BY} / \text{INCLUDE})$$

#### 1. Equality Before Range
```sql
-- Target Query: WHERE city = 'Chicago' AND age > 25

-- ✅ CORRECT: Equality column 'city' first, Range column 'age' second
CREATE INDEX idx_city_age ON users(city, age);

-- ❌ INCORRECT: Placing the range column first stops index traversal for subsequent columns
CREATE INDEX idx_age_city ON users(age, city);
```
*Why?* When the database encounters a range predicate (`age > 25`), it must scan all matching index leaf branches. Because `city` is nested under each distinct `age`, `city` values are no longer contiguous across the search range, rendering `city` index navigation ineffective.

#### 2. Filtering + Sorting (`ORDER BY`)
```sql
-- Target Query:
SELECT * FROM orders 
WHERE user_id = 123 
ORDER BY created_at DESC;

-- ✅ Index covers both the filter and the sort order:
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC);
```

### Common Mistakes

1. **Creating Redundant Prefix Indexes**
   ```sql
   -- ❌ Redundant: idx_users_a is entirely covered by idx_users_a_b
   CREATE INDEX idx_users_a ON users(a);
   CREATE INDEX idx_users_a_b ON users(a, b);
   ```

2. **Index Bloat from Excessive Columns**
   - PostgreSQL allows up to 32 columns in a composite index.
   - In production, having more than 3–5 indexed columns is an anti-pattern. Wide keys bloat internal B-Tree pages, reducing fan-out and driving up memory footprint.

### Composite Index vs. Multiple Single Indexes

| Query Filter | Single Indexes: `idx(A)` + `idx(B)` | Single Composite Index: `idx(A, B)` |
|---|---|---|
| `WHERE A = 1` | ✅ Fast Index Scan on `idx(A)` | ✅ Fast Index Scan on `idx(A, B)` |
| `WHERE B = 2` | ✅ Fast Index Scan on `idx(B)` | ❌ Cannot use `idx(A, B)` (Leftmost prefix) |
| `WHERE A = 1 AND B = 2` | ⚠️ Bitmap Index Scan combining both | ✅ Instant, direct Index Scan |

## 🔴 Senior Level

### Internal Representation: Lexicographical Key Encoding

In PostgreSQL B-Trees, composite keys are encoded as a single composite data tuple:
```
Leaf Page Tuple:
┌────────────────────────────────────────────────────────┐
│ Status: "ACTIVE" | City: "Berlin" | TID: (Block 4, Offset 12) │
├────────────────────────────────────────────────────────┤
│ Status: "ACTIVE" | City: "Madrid" | TID: (Block 4, Offset 13) │
├────────────────────────────────────────────────────────┤
│ Status: "PENDING"| City: "Berlin" | TID: (Block 5, Offset 1)  │
└────────────────────────────────────────────────────────┘
```

### Architectural Trade-offs: `INCLUDE` Clause vs. Index Key

Starting in PostgreSQL 11, the `INCLUDE` clause allows storing non-key payload attributes directly in the leaf pages without including them in B-tree navigation keys:
```sql
-- user_id is the B-Tree search key; amount and status are leaf-only payload columns
CREATE INDEX idx_orders_covering 
ON orders(user_id) INCLUDE (amount, status);

-- Enables Index-Only Scan without increasing internal tree height or key comparison cost
SELECT user_id, amount, status 
FROM orders 
WHERE user_id = 42;
```

### Emulating Index Skip Scan via Recursive CTE

Unlike Oracle or MySQL 8.0+, PostgreSQL currently lacks native **Index Skip Scan**. If an index is defined on `(status, user_id)` where `status` has very low cardinality (e.g., `'ACTIVE'`, `'INACTIVE'`, `'ARCHIVED'`), querying by `user_id` normally triggers a full table scan.

You can emulate Skip Scan in PostgreSQL using a **Recursive CTE**:
```sql
-- Fast Skip Scan emulation over low-cardinality leading column
WITH RECURSIVE skip_scan AS (
  (SELECT MIN(status) AS status FROM orders)
  UNION ALL
  SELECT (
    SELECT MIN(status) 
    FROM orders 
    WHERE status > s.status
  )
  FROM skip_scan s 
  WHERE s.status IS NOT NULL
)
SELECT o.*
FROM skip_scan s
JOIN LATERAL (
  SELECT * 
  FROM orders 
  WHERE status = s.status AND user_id = 42
) o ON true;
-- Converts a 30-second Seq Scan on 100M rows into a ~2 ms index hop!
```

### Multi-Column Directionality (Mixed Sorting)

```sql
-- Target Query: ORDER BY score DESC, created_at ASC
CREATE INDEX idx_leaderboard ON scores(score DESC, created_at ASC);
-- ⚠️ In Postgres, a standard (ASC, ASC) index can scan backwards for (DESC, DESC),
-- but CANNOT satisfy mixed directions (DESC, ASC) without explicit sorting in memory.
```

### Production Monitoring and Consolidation

```sql
-- 1. Inspect composite index columns and their key positions
SELECT 
    i.relname AS table_name,
    ix.indexrelid::regclass AS index_name,
    array_agg(a.attname ORDER BY k.n) AS indexed_columns
FROM pg_index ix
JOIN pg_class i ON i.oid = ix.indrelid
JOIN pg_class idx ON idx.oid = ix.indexrelid
JOIN generate_series(0, array_length(ix.indkey, 1) - 1) AS k(n) ON true
JOIN pg_attribute a ON a.attrelid = i.oid AND a.attnum = ix.indkey[k.n]
WHERE i.relname = 'orders'
GROUP BY i.relname, ix.indexrelid;

-- 2. Identify redundant index prefixes across tables
SELECT
    pg_size_pretty(pg_relation_size(indexrelid)) AS size,
    indexrelname,
    idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Leftmost Prefix Rule:** Query predicates must match the leading column(s) of the composite index in sequential order (`A` -> `A, B` -> `A, B, C`).
- **Ordering Rule:** `Equality (=) columns` first, `Range (<, >, BETWEEN)` columns second, `Payload (INCLUDE)` columns last.
- **Index Consolidation:** Replace redundant separate indexes `(a)` and `(a, b)` with a single composite index `(a, b)`.
- **Skip Scan:** PostgreSQL lacks native Skip Scan; emulate it for low-cardinality prefixes using Recursive CTEs.
- **Mixed Directionality:** If queries sort by `(a ASC, b DESC)`, the index must explicitly match `(a ASC, b DESC)`.

**Common Follow-up Questions:**
- *"Why can't `(city, age)` use the index for `WHERE age = 25`?"* → Because `age` is sorted only within each distinct `city`; without `city`, `age` values are scattered across the entire index tree.
- *"What is the difference between `CREATE INDEX (a, b)` and `CREATE INDEX (a) INCLUDE (b)`?"* → `(a, b)` includes `b` in the search tree (usable in `WHERE b = ...` when `a` is present and in `ORDER BY a, b`), whereas `INCLUDE (b)` stores `b` only on leaf pages for Index-Only Scans.
- *"How many columns should you put in a composite index?"* → Typically 2–4. Exceeding 5 columns increases leaf page bloat and harms caching efficiency.

**Red Flags (DO NOT Say):**
- ❌ *"Column order in a composite index doesn't matter because the database optimizer rearranges it."* (The optimizer cannot rearrange the physical B-tree order).
- ❌ *"It's better to create separate single-column indexes on every column so Postgres can just bitmap-join them."* (Bitmap Index Scans are significantly slower than a single composite Index Scan and multiply write overhead).
