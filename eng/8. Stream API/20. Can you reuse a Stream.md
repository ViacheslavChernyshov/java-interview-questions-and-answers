# Can you reuse a Stream?

---

## 🟢 Junior Level

**No, absolutely not.** In Java, a `Stream` is strictly a **single-use ephemeral pipeline**.

As soon as any **terminal operation** (e.g. `forEach`, `collect`, `count`, `reduce`, `findFirst`) is invoked on a stream, the stream is **consumed and permanently closed**.

```java
List<String> names = List.of("Alice", "Bob", "Charlie");
Stream<String> stream = names.stream();

// 1st terminal operation: Executes successfully
stream.forEach(System.out::println);

// 2nd terminal operation on the SAME stream instance:
long total = stream.count(); // ❌ THROWS EXCEPTION!
```

```
Exception in thread "main" java.lang.IllegalStateException: stream has already been operated upon or closed
```

### The Solution: Re-instantiate from Source

To perform multiple traversals, **create a fresh stream instance from the source collection each time**:

```java
// ✅ CORRECT: Re-creating the stream pipeline per operation
names.stream().forEach(System.out::println);
long total = names.stream().count();
```

## 🟡 Middle Level

### Under the Hood: `AbstractPipeline.linkedOrConsumed`

Inside OpenJDK (`java.util.stream.AbstractPipeline`), each pipeline stage manages its lifecycle using an internal state flag:

```java
// Simplified OpenJDK AbstractPipeline implementation:
private boolean linkedOrConsumed;

final <R> R evaluate(TerminalOp<E_OUT, R> terminalOp) {
    if (linkedOrConsumed) {
        throw new IllegalStateException("stream has already been operated upon or closed");
    }
    linkedOrConsumed = true; // ⚠️ Marks the stream pipeline as consumed!
    
    return isParallel()
        ? terminalOp.evaluateParallel(this, sourceSpliterator(terminalOp.getOpFlags()))
        : terminalOp.evaluateSequential(this, sourceSpliterator(terminalOp.getOpFlags()));
}
```

### Why Streams Are Single-Use by Design
1. **Unbuffered I/O Sources:** Streams can wrap network sockets (`SocketChannel`) or I/O channels that physically cannot be rewound.
2. **Zero-Copy Memory Efficiency:** Allowing replay would force the stream engine to buffer all intermediate items on the Heap, turning Streams into heavy Collections and destroying low-memory streaming benefits.
3. **Concurrency Safety:** A single-use lifecycle eliminates race conditions when work is divided across `ForkJoinPool` threads.

## 🔴 Senior Level

### The `Supplier<Stream<T>>` Factory Pattern

When designing APIs that require generating fresh streams on demand from an in-memory collection:

```java
Supplier<Stream<String>> streamFactory = () -> names.stream().filter(s -> s.startsWith("A"));

// Each .get() invocation yields a brand-new, unconsumed stream:
streamFactory.get().forEach(System.out::println);
long count = streamFactory.get().count();
```

### Resource Management with `AutoCloseable` Streams

Some streams hold underlying operating system file descriptors:
- `Files.lines(Path)`
- `Files.walk(Path)`
- `Files.list(Path)`

These streams implement **`java.lang.AutoCloseable`** and **must be enclosed in a Try-With-Resources block** to prevent native OS file descriptor leaks:

```java
// ✅ ESSENTIAL: Enclose I/O streams in Try-With-Resources
try (Stream<String> lines = Files.lines(Path.of("audit.log"))) {
    lines.filter(l -> l.contains("ERROR"))
         .forEach(System.out::println);
} // Automatically invokes lines.close(), releasing the OS file handle
```

### API Design Code Smell: `Stream<T>` as Method Parameter

> [!WARNING]
> Passing an open `Stream<T>` as a public method parameter is an architectural code smell. The receiving method cannot know if the stream has already been partially consumed, closed, or executed in parallel. Accept `Collection<T>`, `Iterable<T>`, or `Supplier<Stream<T>>` instead.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Single-Use Invariant:** A stream cannot be re-operated upon once a terminal operation has run.
- **Exception:** Reusing a consumed stream throws `IllegalStateException: stream has already been operated upon or closed`.
- **Internal Mechanism:** `AbstractPipeline` enforces this via the `linkedOrConsumed` boolean flag.
- **Factory Solution:** Use `Supplier<Stream<T>>` to generate fresh streams on demand.
- **I/O Streams:** `Files.lines()` streams implement `AutoCloseable` and require Try-With-Resources to release native OS file descriptors.

**Common Follow-up Questions:**
- *"What is the difference between `Stream` and `Iterable`?"* → `Iterable` can produce new `Iterator` instances repeatedly for multiple loops; `Stream` can only be traversed exactly once.
- *"Is it possible to reset or rewind a Stream?"* → No. There is no `reset()` or `rewind()` method in the Stream API.
- *"Why should you avoid passing `Stream<T>` as a method argument?"* → Because streams are single-use; the caller may pass an already consumed stream or a stream that cannot be read twice.

**Red Flags (DO NOT Say):**
- ❌ *"You can call `stream.reset()` to reuse an existing stream."* (No such method exists; streams are strictly single-use).
- ❌ *"parallelStream() allows reuse because it has multiple threads."* (Parallel streams obey the exact same single-use lifecycle).
- ❌ *"A stream caches all elements in memory so it can be re-read."* (Streams are unbuffered pipelines).
