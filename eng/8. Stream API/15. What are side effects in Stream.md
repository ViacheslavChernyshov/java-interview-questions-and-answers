# What are side effects in Stream?

---

## 🟢 Junior Level

A **Side Effect** in Java Stream API is any action performed by a lambda expression that **modifies state outside the scope of the operation** or interacts with the external runtime environment.

### Common Examples of Side Effects:
1. Mutating external collections or variables (`list.add()`, `map.put()`).
2. Mutating fields of objects traveling through the pipeline (`user.setStatus("ACTIVE")`).
3. Performing external I/O (console printing, file writes, database updates, HTTP calls).
4. Interacting with shared mutable singletons.

```java
// ❌ BAD: Pipeline relies on side-effects to populate an external list
List<String> upperNames = new ArrayList<>();
names.stream()
    .map(String::toUpperCase)
    .forEach(upperNames::add); // Side effect!

// ✅ GOOD: Pure functional pipeline returning a fresh immutable structure
List<String> upperNames = names.stream()
    .map(String::toUpperCase)
    .toList();
```

## 🟡 Middle Level

### The 3 Pillars of Functional Stream Contracts

According to the Java Specification (JLS), stream operations should satisfy three invariants:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Functional Invariant                                   │ Specification Requirement                              │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **1. Non-Interference**                                │ Never modify the backing source collection             │
  │ **2. Statelessness**                                   │ Result must not depend on state from prior elements    │
  │ **3. Side-Effect-Freedom**                             │ Lambdas must act as pure deterministic functions       │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Why Side Effects Break Parallel Execution

```
  Parallel Stream Execution:
  Worker 1 (Core 0) ──► Mutating shared memory ◄── Worker 2 (Core 1)
                                  │
                       💥 Race Condition / Data Loss
```
- **Race Conditions:** Unsynchronized access to non-thread-safe heap structures.
- **Non-Deterministic Ordering:** Side effects execute in unpredictable sequence across cores.
- **Memory Visibility Bugs:** Changes made by one CPU core may not be visible to others without volatile memory barriers.

## 🔴 Senior Level

### Highload Lock Contention via Logging (`peek(log::info)`)

A common production anti-pattern is adding logging inside stream operations:

```java
stream.parallel()
    .peek(item -> log.info("Processing entity id={}", item.getId()))
    .map(this::heavyTransform)
    .toList();
```
- Underlying logging frameworks (Logback, Log4j2) synchronize appenders using an internal `ReentrantLock` to prevent interleaved line fragments.
- When 16 ForkJoin worker threads contend for the logger lock, the application encounters massive **thread context-switching storms, causing a 50x throughput collapse**.

### The JIT Pipeline Elision Hazard (Java 9+)

In modern Java, the stream runtime can **eliminate intermediate operations** if the result can be determined directly:

```java
// In Java 9+, count() on SIZED collections queries size directly:
long count = users.stream()
    .peek(user -> auditService.recordAccess(user)) // ❌ ELIDED BY OPTIMIZER!
    .count();
```
> [!WARNING]
> Because streams are assumed to be side-effect-free, the JVM optimization engine is permitted to skip executing `peek()` entirely when computing `.count()`. The side effect is silently never executed.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Any operation modifying external state or performing I/O outside the function's return value.
- **Pure Functions:** Streams are architected around pure, deterministic functions without shared state.
- **Parallel Hazards:** Side effects in parallel streams cause race conditions, data loss, and deadlocks.
- **Logging Overhead:** Calling `log.info()` inside parallel streams causes severe appender lock contention.
- **Pipeline Elision:** Java 9+ optimizers can skip intermediate steps (like `peek()`) if computing operations like `.count()`.

**Common Follow-up Questions:**
- *"Where is the only legitimate place to perform side-effects in a Stream?"* → In the terminal `.forEach()` or `.forEachOrdered()` operations, which are explicitly designed for side-effect consumption.
- *"What happens if a stream operation modifies the source collection during execution?"* → The stream throws a `ConcurrentModificationException` (violation of the non-interference rule).
- *"How does side-effect elimination in `.count()` work?"* → If the source has the `SIZED` flag and intermediate stages are stateless, the runtime returns `source.size()` without traversing elements.

**Red Flags (DO NOT Say):**
- ❌ *"Using `map()` to write records to a database is good practice."* (`map()` is for pure data transformation; database writes belong in dedicated service layers or batch consumers).
- ❌ *"Side-effects in `peek()` are guaranteed to execute for every element in all Java versions."* (Optimizers can legally skip them in Java 9+).
- ❌ *"Side-effects are completely harmless in sequential streams."* (They still violate functional isolation and prevent refactoring to parallel mode).
