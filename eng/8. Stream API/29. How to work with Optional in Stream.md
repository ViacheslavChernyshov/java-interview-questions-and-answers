# How to work with Optional in Stream?

---

## 🟢 Junior Level

`Optional<T>` and the `Stream<T>` API are designed to work together seamlessly across two primary paradigms:

### 1. Unwrapping `Stream<Optional<T>>` into `Stream<T>`

```java
List<Long> userIds = List.of(1L, 2L, 3L, 4L);

// ✅ Modern Java 9+ Standard: Using flatMap(Optional::stream)
List<User> activeUsers = userIds.stream()
    .map(userRepository::findById) // Returns Stream<Optional<User>>
    .flatMap(Optional::stream)     // Unwraps present values and discards empty Optionals!
    .toList();
```

### 2. Streams Returning `Optional<T>`

Operations like `findFirst()`, `findAny()`, `min()`, `max()`, and 1-argument `reduce()` return `Optional<T>`:

```java
Optional<User> firstAdmin = users.stream()
    .filter(User::isAdmin)
    .findFirst();

// Safe extraction:
User admin = firstAdmin.orElseThrow(() -> new UserNotFoundException("Admin not found"));
```

> [!WARNING]
> Never invoke `.get()` on an `Optional` without verifying `.isPresent()`. In modern Java, prefer `.orElseThrow()`, `.orElse()`, or `.orElseGet()`.

## 🟡 Middle Level

### `orElse()` vs. `orElseGet()` (The Eager Evaluation Trap)

```
  ┌──────────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Method                   │ Evaluation Strategy                      │ Performance & Execution Risk                     │
  ├──────────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`orElse(defaultVal)`** │ **Eagerly evaluated** on EVERY execution │ ⚠️ Runs database queries / creates objects even  │
  │                          │                                          │    when the Optional is ALREADY PRESENT!         │
  │ **`orElseGet(Supplier)`**│ **Lazily evaluated** ONLY on empty       │ ✅ Executes fallback ONLY when value is missing  │
  └──────────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

```java
// ❌ CRITICAL WASTE: Hits the database EVERY TIME, even if user is present!
User user = optUser.orElse(userRepository.fetchDefaultUserFromDb());

// ✅ HIGH PERFORMANCE: Executes DB query ONLY if the Optional is empty:
User user = optUser.orElseGet(userRepository::fetchDefaultUserFromDb);
```

### Modern Java 9–11 Methods

```java
// 1. optional.or() -> Fallback chaining (Cache -> DB -> Remote API)
Optional<Config> config = loadFromCache(key)
    .or(() -> loadFromDatabase(key))
    .or(() -> loadFromRemoteService(key));

// 2. optional.ifPresentOrElse() -> Branching consumption
findUser(id).ifPresentOrElse(
    this::sendNotification,
    () -> log.warn("User with id={} not found", id)
);
```

## 🔴 Senior Level

### Structural Architectural Constraints for `Optional`

According to the OpenJDK design specification (Brian Goetz):
1. **Never use `Optional` as class fields (especially JPA Entities):**
   - `Optional` does **not** implement `java.io.Serializable`.
   - Adds 16–24 bytes of pointer indirection overhead per entity field.
2. **Never pass `Optional` as method arguments:**
   - Forces callers to wrap values: `service.update(Optional.of(name))` instead of cleaner method overloading.
3. **`Optional.of(null)` Trap:**
   - `Optional.of(null)` throws an immediate `NullPointerException`. Always use `Optional.ofNullable(val)`.

### High-Throughput GC Optimization
- In microsecond-critical loops, generating millions of heap-allocated `Optional` objects exerts Young Generation GC pressure.
- Use primitive specializations (`OptionalInt`, `OptionalLong`, `OptionalDouble`) to prevent object boxing.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Unwrapping in Java 9+:** Use `.flatMap(Optional::stream)` to filter out empty Optionals and unpack values.
- **Eager vs. Lazy Fallback:** `orElse()` evaluates eagerly every time; `orElseGet()` evaluates lazily only when empty.
- **Null Safety:** `Optional.of(null)` throws NPE; use `Optional.ofNullable()`.
- **Architectural Intent:** `Optional` is strictly designed as a **method return type**, never as a class field or method parameter.
- **Serialization:** `Optional` is not `Serializable` and should never be used in JPA entity fields.

**Common Follow-up Questions:**
- *"How does `flatMap(Optional::stream)` work under the hood?"* → `Optional.stream()` returns a single-element `Stream.of(val)` if present, or `Stream.empty()` if empty, which `flatMap()` flattens into the main stream.
- *"Why is calling `.get()` on an Optional considered an anti-pattern?"* → Calling `.get()` on an empty `Optional` throws a `NoSuchElementException`; use `.orElseThrow()` or `.orElseGet()` instead.
- *"Can you serialize a class containing an `Optional` field?"* → No, it will throw `java.io.NotSerializableException` because `Optional` does not implement `Serializable`.

**Red Flags (DO NOT Say):**
- ❌ *"Optional is a drop-in replacement for null on all class fields."* (It is an anti-pattern; use it only as a method return type).
- ❌ *"orElse() and orElseGet() have identical performance."* (`orElse()` executes eagerly regardless of presence).
- ❌ *"Optional.of(null) returns Optional.empty()."* (It throws `NullPointerException`).
