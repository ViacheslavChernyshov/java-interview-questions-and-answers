# What is peek() operation and when to use it?

---

## 🟢 Junior Level

The **`peek()`** operation is an **intermediate operation** in the Stream API that accepts a `Consumer<? super T>`, applies the action to each element as it passes through the pipeline, and **forwards the element unchanged downstream**.

According to official Java documentation:
> *"This method exists mainly to support debugging, where you want to see the elements as they flow past a certain point in a pipeline."*

```java
List<String> names = List.of("anna", "bob", "alexander", "clark");

List<String> result = names.stream()
    .filter(name -> name.length() > 3)
    .peek(e -> System.out.println("[DEBUG After filter]: " + e))
    .map(String::toUpperCase)
    .peek(e -> System.out.println("[DEBUG After map]: " + e))
    .toList();
```

```
[DEBUG After filter]: anna
[DEBUG After map]: ANNA
[DEBUG After filter]: alexander
[DEBUG After map]: ALEXANDER
[DEBUG After filter]: clark
[DEBUG After map]: CLARK
```

## 🟡 Middle Level

### `peek()` vs. `map()` vs. `forEach()`

```
  ┌──────────────────────┬──────────────────┬──────────────────────────────────────────┬────────────────────────────┐
  │ Operation            │ Operation Type   │ Core Purpose                             │ Return Type                │
  ├──────────────────────┼──────────────────┼──────────────────────────────────────────┼────────────────────────────┤
  │ **`peek(Consumer)`** │ Intermediate     │ Non-destructive debugging inspection     │ `Stream<T>` (Same type)    │
  │ **`map(Function)`**  │ Intermediate     │ Transforming values into a new shape     │ `Stream<R>` (New type)     │
  │ **`forEach(Consumer)`**│ **Terminal**   │ Consuming stream with final side-effects │ `void` (Closes stream)     │
  └──────────────────────┴──────────────────┴──────────────────────────────────────────┴────────────────────────────┘
```

### The Mutation Anti-Pattern

A common anti-pattern is using `peek()` to mutate object state:

```java
// ❌ CRITICAL ANTI-PATTERN: Mutating entities inside peek()
users.stream()
    .peek(user -> user.setActive(true)) // Side-effect!
    .toList();

// ✅ IDIOMATIC FUNCTIONAL APPROACH: Use map() to create clean transformed copies
List<User> activeUsers = users.stream()
    .map(User::toActiveState)
    .toList();
```

## 🔴 Senior Level

### The Java 9+ JIT Optimization Trap (JDK-8075056)

In Java 9+, the stream implementation optimizes the terminal `.count()` method:
- If the stream source is **`SIZED`** (such as an `ArrayList` or `List.of()`) and there are **no filtering operations in the pipeline**, the JVM computes the count directly from `collection.size()` and **completely elides (skips) intermediate pipeline steps**:

```java
List<String> list = List.of("a", "b", "c");

long total = list.stream()
    .peek(item -> auditService.recordEvent(item)) // ❌ SILENTLY SKIPPED IN JAVA 9+!
    .count(); // Evaluates size() directly; peek() is NEVER EXECUTED!
```
> [!WARNING]
> Never place essential business logic (e.g. audits, metrics, database writes) inside `peek()`. The JVM is legally permitted to optimize it away.

### Short-Circuiting Truncation

Short-circuiting operations (`findFirst()`, `limit()`, `anyMatch()`) terminate pipeline execution as soon as criteria are met, leaving remaining items unprocessed by `peek()`:

```java
List<String> items = List.of("A", "B", "C", "D", "E");

// peek() executes ONLY for "A" and "B"; "C", "D", "E" are NEVER passed to peek()!
items.stream()
    .peek(item -> metrics.increment("seen"))
    .filter("B"::equals)
    .findFirst();
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Primary Purpose:** Intermediate operation intended strictly for debugging and diagnostic pipeline tracing.
- **Contract:** Accepts `Consumer<T>`, passes elements downstream without modifying them, returns `Stream<T>`.
- **Laziness:** Executes nothing unless triggered by a terminal operation.
- **Optimization Trap (Java 9+):** The JVM skips `peek()` when evaluating `.count()` on `SIZED` collections.
- **Short-Circuiting:** `findFirst()` and `limit()` truncate evaluation, causing `peek()` to skip remaining items.

**Common Follow-up Questions:**
- *"Why should you never use `peek()` for business logic in production?"* → Because stream execution is lazy, prone to short-circuiting, and subject to optimizer elisions that silently drop `peek()` calls.
- *"How does `peek()` differ from `forEach()`?"* → `peek()` is intermediate (returns `Stream<T>` and keeps the pipeline open); `forEach()` is terminal (returns `void` and closes the stream).
- *"Does `peek()` alter stream performance in production?"* → Yes, every `peek()` adds virtual method invocation overhead per element, degrading throughput in high-volume pipelines.

**Red Flags (DO NOT Say):**
- ❌ *"peek() is the standard way to update entity database records in a stream."* (It is strictly a debugging utility; database updates belong in a repository or terminal `.forEach()`).
- ❌ *"peek() is guaranteed to execute for every element in the collection."* (Java 9+ optimizations and short-circuit operations skip `peek()`).
- ❌ *"peek() transforms elements into a new type like map()."* (It forwards the exact same elements without altering types).
