# When to use parallel streams?

---

## 🟢 Junior Level

You should use **`parallelStream()`** **ONLY when all 3 of the following conditions are simultaneously met**:

1. **Large Volume of Data:** The collection contains thousands to millions of elements.
2. **CPU-Bound Workload:** The operations perform heavy mathematical calculations, encryption, hashing, image processing, or complex parsing.
3. **Pure, Independent Operations:** Operations are completely stateless and free of side-effects (they do not mutate shared variables or rely on thread-local context).

```java
// ✅ EXCELLENT USE CASE: CPU-Bound, Large Array, Pure Function
List<BigInteger> probablePrimes = numbers.parallelStream()
    .filter(BigInteger::isProbablePrime)
    .toList();

// ❌ DISASTROUS ANTI-PATTERN: Blocking I/O inside parallelStream
List<User> users = userIds.parallelStream()
    .map(id -> restClient.getUser(id)) // 💥 Blocks ForkJoinPool.commonPool, freezing the JVM!
    .toList();
```

## 🟡 Middle Level

### The $N \times Q > 10{,}000$ Decision Matrix (Brian Goetz Model)

Before enabling parallelism, evaluate the $N \times Q$ rule:

$$\mathbf{N \times Q > 10{,}000}$$

- **$N$**: Total count of elements in the collection.
- **$Q$**: Number of CPU instructions required to process a single element.

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Scenario                                               │ Recommendation                                         │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ $N = 100$, Cheap Operation ($Q = 5$ instructions)      │ ❌ **Sequential:** $N \times Q = 500$ (Parallelism is 5x slower)│
  │ $N = 10{,}000$, Cheap Operation ($Q = 5$)              │ 🟡 **Marginal:** $N \times Q = 50{,}000$ (Minimal speedup)│
  │ $N = 500$, Heavy Cryptography ($Q = 2{,}000$)          │ 🟢 **Parallel:** $N \times Q = 1{,}000{,}000$ (Massive 4-8x speedup)│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Spliterator Partitioning Efficiency

- **Optimal ($O(1)$ direct index division):** `ArrayList`, primitive arrays (`int[]`), `IntStream.range()`.
- **Moderate ($O(\log N)$ tree splits):** `HashSet`, `TreeSet`.
- **Degraded ($O(N)$ sequential pointer walk):** `LinkedList`, `Stream.iterate()`.

## 🔴 Senior Level

### Modern Java Architectural Strategy: Parallel Stream vs. Virtual Threads

In modern Java (Java 21+), concurrency tools are strictly differentiated by workload profile:

```
  ┌──────────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Workload Profile         │ Recommended Tool                         │ Why NOT `parallelStream()`?                      │
  ├──────────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **CPU-Bound In-Memory**  │ 🟢 **`parallelStream()` / ForkJoinPool** │ Utilizes 100% of physical hardware CPU cores     │
  │ **I/O-Bound Blocking**   │ 🟢 **Virtual Threads (Java 21+)**        │ `parallelStream` starves `commonPool` workers    │
  │ **Async Reactive Flow**  │ 🟢 **`CompletableFuture` / Project Reactor**│ Handles non-blocking timeouts & error fallbacks  │
  └──────────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Senior Invariant: Verification via JMH

> [!IMPORTANT]
> Never assume parallel streams will improve throughput without benchmarking. Always verify speedups using **JMH (Java Microbenchmark Harness)** with proper JVM warmup phases, as the JIT C2 compiler applies SIMD vectorization and loop unrolling differently between sequential and parallel bytecodes.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **When to Use:** CPU-bound tasks, large datasets ($N \times Q > 10{,}000$), pure functional transformations.
- **When NOT to Use:** I/O operations (HTTP/JDBC), small collections ($N < 1{,}000$), `LinkedList`, stateful operations (`sorted`).
- **I/O Modern Standard:** Use Java 21+ Virtual Threads (`Executors.newVirtualThreadPerTaskExecutor()`) for I/O, not parallel streams.
- **Data Source:** Partitioning performance depends on `Spliterator`; arrays and `ArrayList` split instantly, while `LinkedList` incurs $O(N)$ traversal overhead.

**Common Follow-up Questions:**
- *"Why is `parallelStream()` ineffective on `LinkedList`?"* → Because `LinkedList` lacks indexed access; `Spliterator.trySplit()` must traverse $N/2$ pointers linearly, destroying any multi-threaded advantage.
- *"Why should you never use `parallelStream()` inside a Spring REST controller endpoint?"* → Because a single HTTP request executing a parallel stream monopolizes the global `ForkJoinPool.commonPool()`, degrading latency for all other concurrent web requests.
- *"What is the difference between CPU-bound and I/O-bound tasks in the context of streams?"* → CPU-bound tasks keep CPU cores at 100% compute load (ideal for ForkJoinPool); I/O-bound tasks block threads waiting for network/disk responses, idling the CPU core.

**Red Flags (DO NOT Say):**
- ❌ *"I add `.parallel()` to all streams in production to maximize performance."* (Causes severe common pool exhaustion and latency spikes).
- ❌ *"Parallel streams are great for batch inserting records into a database."* (I/O calls starve the CPU worker pool; use JDBC batching or Virtual Threads).
- ❌ *"Parallelism is always beneficial regardless of collection size."* (Small datasets execute slower due to thread coordination overhead).
