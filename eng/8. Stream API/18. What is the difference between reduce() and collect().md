# What is the difference between reduce() and collect()?

---

## 🟢 Junior Level

Both **`reduce()`** and **`collect()`** are **eager terminal operations** that aggregate all elements of a stream into a single final result.

The fundamental difference lies in **how the result is constructed**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ `reduce()` (Immutable Reduction)                       │ `collect()` (Mutable Reduction)                        │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Produces a **brand-new object on every step**        │ • Mutates a **single existing accumulator container**  │
  │ • Designed for scalars and primitives (`int`, `min`)   │ • Designed for collections (`List`, `Set`, `Map`)      │
  │ • Accumulator returns a new value: `BiFunction<U,T,U>` │ • Accumulator modifies in place: `BiConsumer<R,T>`     │
  │ • String concat via `reduce`: $O(N^2)$ GC thrashing    │ • String concat via `collect(joining())`: $O(N)$ buffer│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// 1. reduce(): Immutable scalar aggregation (Summing numbers)
int totalSum = numbers.stream().reduce(0, (acc, n) -> acc + n);

// 2. collect(): Mutable container accumulation (Packaging into List)
List<String> list = words.stream().map(String::toUpperCase).toList();
```

## 🟡 Middle Level

### Functional Signatures Comparison

```java
// reduce(): Functional Fold (Returns a new value on every element)
<U> U reduce(U identity, 
             BiFunction<U, ? super T, U> accumulator, 
             BinaryOperator<U> combiner);

// collect(): Mutable Container Sink (Mutates container via BiConsumer)
<R> R collect(Supplier<R> supplier, 
              BiConsumer<R, ? super T> accumulator, 
              BiConsumer<R, R> combiner);
```

### Why `reduce()` with an `ArrayList` is a Critical Anti-Pattern

Attempting to accumulate a collection using `reduce()` causes severe bugs:

```java
// ❌ CRITICAL ANTI-PATTERN: Using reduce() with mutable ArrayList
List<String> bad = words.parallelStream()
    .reduce(new ArrayList<>(), 
            (acc, w) -> { acc.add(w); return acc; }, 
            (l1, l2) -> { l1.addAll(l2); return l1; });
```
1. **Parallel Race Condition:** The `identity` instance (`new ArrayList<>()`) is shared across all threads in the ForkJoin pool. Parallel workers invoke `.add()` concurrently on the un-synchronized list, causing **data loss and `ArrayIndexOutOfBoundsException`**.
2. **$O(N^2)$ Complexity if Copying:** Attempting to return a new copy on every step (`new ArrayList<>(acc)`) incurs **quadratic time complexity and massive GC memory allocation**.

## 🔴 Senior Level

### Performance Benchmark: String Concatenation ($100{,}000$ Elements)

```
  ┌──────────────────────────────────────────┬──────────────────────┬──────────────────────────────────────────────┐
  │ Approach                                 │ Time Complexity      │ Garbage Collection Impact                    │
  ├──────────────────────────────────────────┼──────────────────────┼──────────────────────────────────────────────┤
  │ `reduce("", (a, b) -> a + b)`            │ $O(N^2)$             │ 💥 Allocates millions of ephemeral `String`s │
  │ `collect(Collectors.joining())`          │ $O(N)$               │ 🟢 Single contiguous resizable `byte[]` buffer│
  └──────────────────────────────────────────┴──────────────────────┴──────────────────────────────────────────────┘
```

### Collector Optimization: `Characteristics.CONCURRENT`

When collecting into thread-safe structures in parallel streams:

```
  Standard Collector in Parallel Stream:
  Thread 1 ──► Local Container A ──┐
                                   ├──► Combiner (l1.addAll(l2)) ──► Final List
  Thread 2 ──► Local Container B ──┘

  CONCURRENT Collector (ConcurrentHashMap) in Parallel Stream:
  Thread 1 ──┐
             ├──► SINGLE ConcurrentMap (Combiner is completely BYPASSED!)
  Thread 2 ──┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Distinction:** `reduce()` is immutable scalar folding; `collect()` is mutable container aggregation.
- **Accumulator Contract:** `reduce` accumulator returns a new value (`BiFunction`); `collect` accumulator returns `void` (`BiConsumer`).
- **Collection Hazard:** Never accumulate collections using `reduce()`; it causes data races in parallel streams or $O(N^2)$ copying overhead.
- **String Concatenation:** Always use `collect(Collectors.joining())` instead of `reduce()` to avoid $O(N^2)$ heap allocation.
- **Concurrent Optimization:** `Collector.Characteristics.CONCURRENT` allows parallel streams to bypass the `combiner` stage.

**Common Follow-up Questions:**
- *"Why does `reduce` require a BinaryOperator combiner while `collect` requires a BiConsumer combiner?"* → Because `reduce` merges two immutable values into a single new value, whereas `collect` merges the contents of the second mutable container into the first.
- *"Can `collect()` be implemented using `reduce()`?"* → In pure theory with immutable persistent data structures, yes, but in Java's memory model it causes severe GC allocation penalties ($O(N^2)$).
- *"Which is more memory efficient for summing primitive integers: `reduce()` or `mapToInt().sum()`?"* → `mapToInt().sum()` is vastly superior because it operates directly on primitive CPU registers with zero object allocations.

**Red Flags (DO NOT Say):**
- ❌ *"reduce() and collect() are identical and interchangeable."* (They have completely different memory and concurrency semantics).
- ❌ *"reduce() is faster than collect() because it has fewer arguments."* (Using `reduce` on collections degrades performance from $O(N)$ to $O(N^2)$).
- ❌ *"Mutating the identity object in `reduce()` is standard practice."* (It destroys thread safety in parallel streams).
