# How to Find Out How Much Memory a String Occupies

---

## 🟢 Junior Level

In modern Java (Java 9+ with 64-bit JVM and Compressed OOPs), calculating a String's physical memory footprint requires adding the **`String` object header** and its **backing `byte[]` array**:

```
  Total Memory Footprint = String Object (~24 bytes) + Backing byte[] Array (~16 bytes + data)
```

```java
// Exact Measurement using OpenJDK JOL (Java Object Layout):
import org.openjdk.jol.info.GraphLayout;

String s = "Hello";
System.out.println(GraphLayout.parseInstance(s).totalSize()); // Prints: 48 bytes
```

```
  Memory Footprint Examples (Java 9+ Latin-1 vs UTF-16):
  • `""` (Empty String)     ──► 40 bytes (24B String + 16B empty byte[] array)
  • `"Hello"` (5 Latin-1)   ──► 48 bytes (24B String + 16B header + 5B data + 3B padding)
  • `"Привет"` (6 UTF-16)   ──► 56 bytes (24B String + 16B header + 12B data + 4B padding)
```

## 🟡 Middle Level

### Memory Layout Breakdown (64-bit HotSpot JVM with Compressed OOPs)

```
  1. java.lang.String Object Instance (24 bytes):
  ├── Mark Word:                          8 bytes
  ├── Compressed Klass Pointer:           4 bytes
  ├── `byte[] value` reference:           4 bytes
  ├── `byte coder` flag:                  1 byte
  ├── `int hash` code:                    4 bytes
  └── Alignment Padding:                  3 bytes (Aligns to 8-byte boundary)
  └── TOTAL SHALLOW SIZE:                 24 bytes

  2. Backing `byte[]` Array (16 bytes + Data):
  ├── Mark Word:                          8 bytes
  ├── Compressed Klass Pointer:           4 bytes
  ├── Array Length `int`:                 4 bytes
  ├── Payload (N bytes Latin1 / 2N UTF16): N bytes
  └── Alignment Padding:                  to nearest multiple of 8 bytes
  └── TOTAL ARRAY SIZE:                   16 + N (Padded to 8B boundary)
```

### Shallow Size vs. Retained Size

```
  ┌──────────────────┬──────────────────────────────────┬────────────────────────────────────────────────┐
  │ Measurement Type │ Scope of Calculation             │ Size for `String s = "Hello"`                  │
  ├──────────────────┼──────────────────────────────────┼────────────────────────────────────────────────┤
  │ **Shallow Size** │ Just the `String` object itself  │ **24 bytes** (Excludes backing array)          │
  │ **Retained Size**│ `String` object + `byte[]` array │ **48 bytes** (Full memory reclaimed on GC)     │
  └──────────────────┴──────────────────────────────────┴────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The 32 GB Heap Cliff: Compressed OOPs Disabled

- **Heaps under 32 GB (`-XX:+UseCompressedOops`):** Reference pointers occupy **4 bytes**, resulting in a 24-byte `String` wrapper.
- **Heaps above 32 GB (`-XX:-UseCompressedOops`):** Pointers expand to full **8 bytes**, blowing up the `String` wrapper to **40 bytes** and increasing array headers from 16 to 24 bytes!

```
  Impact of Crossing 32 GB Heap Threshold:
  • 10,000,000 strings on 30 GB Heap ──► ~480 MB RAM
  • 10,000,000 strings on 34 GB Heap ──► ~720 MB RAM (+50% memory bloat due to uncompressed pointers!)
```

### Production Tooling for String Memory Profiling

```java
// 1. JOL Deep Inspection:
System.out.println(GraphLayout.parseInstance(myString).toPrintable());

// 2. Java Agent Instrumentation (Shallow Size Only):
long shallowBytes = instrumentation.getObjectSize(myString);

// 3. Command-Line Heap Inspection:
// jmap -histo:live <pid> | grep java.lang.String
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Two Components:** Total footprint = `String` object instance + backing `byte[]` array.
- **Base Footprint:** An empty string (`""`) occupies **40 bytes** (24 bytes object + 16 bytes array).
- **Short String Size:** `"Hello"` (5 Latin-1 chars) occupies **48 bytes** total.
- **Tooling:** Use OpenJDK **JOL (Java Object Layout)** (`GraphLayout.parseInstance().totalSize()`) for exact footprint analysis.
- **Shallow vs Retained:** Shallow size counts only the outer reference (24B); Retained size counts the backing array.
- **Compressed OOPs:** Heaps $<32\text{ GB}$ use 4-byte references; exceeding 32 GB increases string memory overhead by 30–50%.

**Common Follow-up Questions:**
- *"Why is there no `sizeof` operator in Java?"* → Java objects are abstracted away from direct memory management by the JVM, which applies alignment padding, compressed references, and garbage collection metadata transparently.
- *"How does the String Pool affect memory calculation?"* → If 1,000 references point to `"Hello"` in the String Pool, the total memory consumed is only 48 bytes (one shared instance), rather than 48,000 bytes.
- *"How can you inspect string memory in production heap dumps?"* → Load the `.hprof` file into Eclipse Memory Analyzer Tool (MAT) and inspect the **Dominator Tree** filtered by `java.lang.String`.

**Red Flags (DO NOT Say):**
- ❌ *"A 5-character string occupies 5 bytes in Java."* (This ignores the 40+ bytes of object headers and array metadata).
- ❌ *"You can use `Instrumentation.getObjectSize()` to calculate the full size of a String."* (`getObjectSize()` only returns shallow size [24B], ignoring the backing array).
- ❌ *"Compressed OOPs are always enabled regardless of Heap size."* (They are disabled when Heap exceeds 32 GB).
