# Why is StringBuffer Slower than StringBuilder?

---

## 🟢 Junior Level

**`StringBuffer` is significantly slower than `StringBuilder`** because every public method in `StringBuffer` is declared with the **`synchronized`** keyword:

```java
// StringBuffer (Synchronized on `this`):
StringBuffer sb1 = new StringBuffer();
for (int i = 0; i < 1_000_000; i++) {
    sb1.append("x"); // Incurs monitor lock acquisition on EVERY loop iteration! (~25ms)
}

// StringBuilder (Unsynchronized):
StringBuilder sb2 = new StringBuilder();
for (int i = 0; i < 1_000_000; i++) {
    sb2.append("x"); // Direct array write; zero locking overhead! (~15ms)
}
```

```
  Key Analogy:
  • StringBuilder is an unlocked door: Enter and exit freely.
  • StringBuffer is a locked door: You must unlock, open, enter, lock, unlock, and exit every single time, 
    even if you are the only person in the entire building.
```

## 🟡 Middle Level

### The Three Costs of `synchronized`

Even in a purely single-threaded execution context, `StringBuffer` incurs substantial overhead:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Overhead Factor                  │ Mechanism                                                                   │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Monitor Acquisition & CAS**    │ Evaluates atomic CAS instructions to update the object header's Mark Word.  │
  │ 2 │ **Hardware Memory Barriers**     │ Issues CPU memory fence instructions, flushing store buffers and L1 caches. │
  │ 3 │ **Compiler Optimization Limits** │ Synchronization boundaries inhibit JIT loop unrolling and reordering.      │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### JIT Compiler Optimizations: Lock Elision & Lock Coarsening

HotSpot C2 compiler attempts to optimize away unnecessary `StringBuffer` locks:

```java
public void buildLocalString() {
    // 1. Lock Elision via Escape Analysis:
    // If the JVM proves `sb` never escapes this method, JIT completely strips the `monitorenter` op!
    StringBuffer sb = new StringBuffer();
    sb.append("A");
    sb.append("B");
    
    // 2. Lock Coarsening:
    // If locks cannot be elided, JIT merges adjacent synchronized calls into a single outer monitor block.
}
```

> [!WARNING]
> Lock Elision and Lock Coarsening are **not guaranteed**. They depend on the C2 compilation budget, inlining depth, and whether the reference escapes to other methods. `StringBuilder` guarantees zero lock overhead out of the box.

### The Removal of Biased Locking (Java 15+ JEP 374)

- Prior to Java 15, **Biased Locking** allowed a single thread to acquire an uncontended monitor with almost zero CAS cost.
- **Java 15 (JEP 374)** permanently disabled and removed Biased Locking because of its complex synchronization handshake costs across containerized cloud environments.
- As a result, in modern Java 17/21, single-threaded `StringBuffer` monitor acquisition relies on **Atomic CAS instructions**, making the performance gap between `StringBuilder` and `StringBuffer` even wider.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Cause:** `StringBuffer` methods are `synchronized`, incurring monitor acquisition, atomic CAS operations, and memory barriers on every invocation.
- **Single-Thread Speed:** `StringBuilder` is ~1.5x–2.5x faster in single-threaded benchmarks.
- **Contended Multi-Threading:** Severe lock contention forces threads into kernel wait queues, increasing latency by over 1,000%.
- **Lock Elision:** HotSpot C2 uses Escape Analysis to remove locks on non-escaping instances, but it is not guaranteed.
- **Biased Locking Removal:** Java 15+ (JEP 374) eliminated biased locking, further increasing the uncontended cost of `StringBuffer`.

**Common Follow-up Questions:**
- *"What are the bytecode instructions generated for `synchronized` blocks?"* → `monitorenter` and `monitorexit`.
- *"What happens when threads contend for a `StringBuffer` monitor?"* → Threads fail the initial spin-lock and block, requiring an OS-level context switch ($1-10 \mu s$ latency penalty).
- *"Is `StringBuffer` still useful in modern Java?"* → Rarely; modern multi-threaded architectures use thread-local `StringBuilder` instances or lock-free concurrent data structures instead of sharing a mutable string buffer.

**Red Flags (DO NOT Say):**
- ❌ *"`StringBuffer` is faster than `StringBuilder` when only one thread is running."* (It is always slower due to monitor synchronization).
- ❌ *"The JVM completely eliminates all `StringBuffer` synchronization overhead in production."* (Lock elision only occurs if escape analysis successfully proves the instance never escapes).
- ❌ *"`StringBuffer` allocates less memory than `StringBuilder`."* (Both classes use the exact same `AbstractStringBuilder` byte array storage).
