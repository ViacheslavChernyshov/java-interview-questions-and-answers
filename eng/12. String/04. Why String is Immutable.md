# Why is String Immutable in Java?

---

## 🟢 Junior Level

In Java, **Immutability** means that once a `java.lang.String` object is created in memory, its character contents **can never be altered**:

```java
String greeting = "Hello";
greeting.toUpperCase(); // Creates and returns a BRAND NEW String ("HELLO")

System.out.println(greeting); // Prints "Hello" — the original string remains completely unchanged!
```

```
  Core Practical Reasons for Immutability:
  1. Security: File paths, network URLs, and database credentials cannot be corrupted in transit.
  2. Thread Safety: Strings can be safely shared across concurrent threads without locks.
  3. String Pool: Reusing identical string literals is only safe because no one can alter them.
  4. Hash Stability: Hash codes can be calculated once and cached forever for instant HashMap lookups.
```

### The Four Pillars of String Immutability

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Architectural Pillar             │ Technical Impact                                                            │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Security & TOCTOU Defense**    │ Prevents Time-of-Check to Time-of-Use tampering in ClassLoaders & OS calls. │
  │ 2 │ **Thread Safety by Design**      │ Zero synchronization overhead; immune to race conditions and memory leaks.  │
  │ 3 │ **String Pool Integrity**        │ Allows thousands of components to safely reference the exact same literal.  │
  │ 4 │ **Cached HashCode Performance**  │ `hash` is calculated once lazily; guarantees deterministic `HashMap` keys.  │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// HashCode Caching in java.lang.String:
Map<String, UserSession> sessionCache = new HashMap<>();
String sessionId = "sess_9921_x";
sessionCache.put(sessionId, session); 
// Because String is immutable, sessionId's hashCode will never change in memory!
```

## 🔴 Senior Level

### JDK Source Internals (Java 9+ Compact Strings)

```java
public final class String implements Serializable, Comparable<String>, CharSequence {

    @Stable // HotSpot C2 Compiler Intrinsic: Array contents never mutate after construction
    private final byte[] value;

    private final byte coder; // LATIN1 (0) or UTF16 (1)

    private int hash; // Lazily computed and cached hash code (Defaults to 0)
}
```

- **`public final class`**: Prevents malicious subclasses from overriding core methods like `charAt()` or `length()`.
- **`private final byte[] value`**: The memory reference to the backing byte array cannot be reassigned.
- **`@Stable` Annotation**: Informs the HotSpot JIT (C2) compiler that array elements are constant, enabling aggressive loop unrolling, SIMD vectorization, and constant folding.

### The TOCTOU (Time-of-Check to Time-of-Use) Security Threat

If `String` were mutable, an attacker could bypass filesystem authorization checks:

```
  Vulnerable Scenario (If String Were Mutable):
  1. Thread A passes String path = "/public/readme.txt" to SecurityManager.checkRead(path).
  2. SecurityManager inspects path and approves the read request.
  3. Concurrent Thread B mutates path in-place to "/etc/shadow" before the OS file descriptor opens.
  4. The JVM opens "/etc/shadow", completely bypassing the security check!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** String contents cannot be modified after construction; all mutation methods return new instances.
- **4 Reasons:** Security (ClassLoader/I/O), Thread Safety (lock-free sharing), String Pool (literal reuse), and HashMap stability (cached hash code).
- **Implementation:** `final` class, `private final byte[] value`, no mutator methods, defensive copying.
- **Performance Trade-off:** Immutability produces high allocation rates and GC churn under frequent concatenation loops (mitigate via `StringBuilder`).
- **JIT Optimization:** The `@Stable` annotation allows HotSpot C2 to treat string character bytes as compile-time constants.

**Common Follow-up Questions:**
- *"Why does String cache its `hashCode()`?"* → Since the character sequence is immutable, the hash code is guaranteed to remain identical throughout the object's lifetime, allowing instant $O(1)$ `HashMap` lookups.
- *"Can you modify a String's content using Java Reflection?"* → In Java 8 and earlier, `Field.setAccessible(true)` could modify `value`; in Java 9+ (and strictly enforced in Java 16+ JEP 396), the Java Module System strongly encapsulates `java.base`, throwing `InaccessibleObjectException`.
- *"What should you use if you need frequent string modifications?"* → Use `StringBuilder` (single-threaded) or pre-allocated `byte[]` buffers.

**Red Flags (DO NOT Say):**
- ❌ *"`String.replace()` modifies the string in-place."* (It returns a new `String` instance).
- ❌ *"Strings are thread-safe because the class methods are synchronized."* (String is thread-safe because it has no mutable state to synchronize).
- ❌ *"You can safely use mutable objects as HashMap keys as long as you implement `equals()`."* (Mutating a key after insertion corrupts HashMap bucket lookups).
