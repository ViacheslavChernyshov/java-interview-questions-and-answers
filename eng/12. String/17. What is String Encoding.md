# What is String Encoding?

---

## 🟢 Junior Level

A **Character Encoding** is a standardized set of rules that maps human-readable characters (letters, numbers, symbols, emojis) into binary byte sequences for storage in memory, disks, or network sockets, and vice versa:

```
  Text ("Hello")  ──►  Encoding (e.g. UTF-8)  ──►  Bytes: [0x48, 0x65, 0x6C, 0x6C, 0x6F]
  Bytes           ──►  Decoding (e.g. UTF-8)  ──►  Text ("Hello")
```

```java
String original = "Hello";

// 1. Encoding: Convert String to byte[]:
byte[] bytes = original.getBytes(StandardCharsets.UTF_8);

// 2. Decoding: Reconstruct String from byte[]:
String restored = new String(bytes, StandardCharsets.UTF_8);
```

> [!IMPORTANT]
> **Golden Rule:** ALWAYS explicitly specify the `Charset` (such as `StandardCharsets.UTF_8`). Never rely on default parameterless `getBytes()`, which historically varied between Windows (`windows-1252`/`windows-1251`) and Linux (`UTF-8`).

## 🟡 Middle Level

### Common Character Encodings Overview

```
  ┌──────────────────┬──────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Encoding         │ Bytes per Char   │ Character Coverage       │ Best Use Case                                    │
  ├──────────────────┼──────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **UTF-8**        │ **1 to 4 bytes** │ Full Unicode (1,114,112) │ ⭐️ **Global Web Standard** (JSON, REST, DB, Files)│
  │ **UTF-16**       │ **2 or 4 bytes** │ Full Unicode (Surrogates)│ JVM Internal non-Latin string representations    │
  │ **ISO-8859-1**   │ **1 byte**       │ Latin-1 (256 characters) │ Western European text & JVM Compact Strings      │
  │ **US-ASCII**     │ **1 byte**       │ 128 English characters   │ Legacy protocols & HTTP headers                  │
  │ **Windows-1251** │ **1 byte**       │ Cyrillic (256 chars)     │ Legacy Windows desktop files                     │
  └──────────────────┴──────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

### UTF-8 Default in Java 18+ (JEP 400)

- Prior to **Java 18**, `Charset.defaultCharset()` depended on the operating system locale.
- Starting in **Java 18 (JEP 400)**, the JVM default charset is standardized to **`UTF-8`** across all operating systems.
- However, explicitly passing `StandardCharsets.UTF_8` in application code remains mandatory for backward compatibility and clean architecture.

## 🔴 Senior Level

### Internal JVM Memory: Compact Strings (JEP 254)

Starting with Java 9, `java.lang.String` no longer stores characters as `char[]` (UTF-16 2-byte units). Instead, it uses an internal `byte[]` array paired with a `coder` flag:

```java
public final class String implements Serializable, Comparable<String>, CharSequence {
    @Stable
    private final byte[] value; // Raw bytes
    private final byte coder;   // LATIN1 (0) or UTF16 (1)
}
```

```
  • If all characters in the string fit within ISO-8859-1 (U+0000 to U+00FF):
    coder = LATIN1 (0) ──► Allocates 1 byte per character! (Saves 50% Heap memory!)

  • If any character requires > 1 byte (e.g. Cyrillic, Chinese, Emoji):
    coder = UTF16 (1)  ──► Allocates 2 bytes per character (UTF-16 encoding).
```

### Critical Encoding Edge Cases

```
  1. Byte Order Mark (BOM - \uFEFF):
     UTF-8 text exported from Windows Notepad starts with the 3-byte sequence [0xEF, 0xBB, 0xBF].
     Decoding with standard UTF_8 leaves '\uFEFF' as the first character, breaking string.startsWith("Hi")!
     Fix: Strip BOM manually or use Apache Commons IO `BOMInputStream`.

  2. Malformed Bytes & Replacement Characters:
     When decoding corrupted bytes, the JVM replaces invalid byte sequences with '\uFFFD' ().
     To reject invalid bytes immediately, configure a CharsetDecoder with CodingErrorAction.REPORT.

  3. Thread Safety Warning:
     `StandardCharsets.UTF_8` is a thread-safe singleton.
     `CharsetEncoder` and `CharsetDecoder` are MUTABLE and NOT THREAD-SAFE! Never share them across threads.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Rules mapping Unicode character code points to binary byte sequences.
- **UTF-8:** Variable-length (1–4 bytes), backward compatible with ASCII; standard for Web, JSON, and network I/O.
- **Java 18+ JEP 400:** Standardized the default charset to UTF-8 across all operating systems.
- **Compact Strings (Java 9+):** `byte[] value` + `coder` flag (`LATIN1` = 1 byte/char, `UTF16` = 2 bytes/char).
- **Encoding Safety:** Always use `StandardCharsets.UTF_8` over string literals (`"UTF-8"`) to avoid `UnsupportedEncodingException`.
- **Concurrency:** `CharsetEncoder`/`CharsetDecoder` are stateful and NOT thread-safe.

**Common Follow-up Questions:**
- *"Why does `"Привет".length()` return 6 while `"Привет".getBytes(StandardCharsets.UTF_8).length` returns 12?"* → `length()` returns the number of UTF-16 code units (6 chars), while UTF-8 encodes Cyrillic letters as 2 bytes each (12 bytes total).
- *"What happens if you decode a binary image or PDF into a `String`?"* → Binary byte sequences containing non-character patterns will be corrupted or replaced with `\uFFFD`, causing irreversible data loss when converted back to `byte[]`.
- *"How do surrogate pairs work in UTF-16?"* → Characters outside the Basic Multilingual Plane (BMP, code points $> \text{U+FFFF}$, such as emojis) require two 16-bit `char` units (High and Low surrogates) to represent a single Unicode glyph.

**Red Flags (DO NOT Say):**
- ❌ *"A Java `char` can represent every possible Unicode character."* (A `char` is 16-bit; supplementary Unicode code points and emojis require 2 `char` surrogate pairs).
- ❌ *"Calling `new String(bytes)` is always safe because Java defaults to UTF-8."* (Prior to Java 18, Windows defaulted to Windows-1252/1251, causing silent corruption).
- ❌ *"You can store raw binary files inside a `String` without data loss."* (Binary data must always remain in `byte[]` or `ByteBuffer`).
