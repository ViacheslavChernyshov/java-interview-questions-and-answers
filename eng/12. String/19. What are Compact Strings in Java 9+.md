# What are Compact Strings in Java 9+?

---

## 🟢 Junior Level

**Compact Strings (JEP 254)** is a JVM memory optimization introduced in **Java 9** that cuts the memory footprint of strings containing Western/ASCII characters **in half**:

```
  ┌──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Java Version             │ Storage Type             │ Memory per Character                             │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Java 8 and earlier**   │ `char[]` (UTF-16)        │ **2 bytes per character** (Always, even for 'a') │
  │ **Java 9+ (JEP 254)**    │ `byte[]` + `coder` flag  │ **1 byte per char** (Latin-1) / 2 bytes (UTF-16) │
  └──────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

```java
// Transparent Memory Savings in Java 9+:
String english = "Hello World"; // 11 bytes (Was 22 bytes in Java 8!) -> 50% RAM savings!
String cyrillic = "Привет Мир";   // 20 bytes (Requires UTF-16, identical to Java 8)
```

```
  Key Takeaway:
  • Compact Strings is enabled by default in Java 9, 11, 17, and 21.
  • Requires zero code changes from developers.
```

## 🟡 Middle Level

### Internal Structure: `byte[]` and the `coder` Flag

```java
public final class String implements Serializable, Comparable<String>, CharSequence {
    @Stable
    private final byte[] value; // Backing byte buffer
    private final byte coder;   // 0 = LATIN1, 1 = UTF16
}
```

```
  • coder = 0 (LATIN1): Characters in range U+0000 to U+00FF (ASCII, English, Spanish, German).
  • coder = 1 (UTF16):  Characters outside Latin-1 (Cyrillic, Arabic, Chinese, Emoji).
```

### Memory Footprint Comparison

```
  ┌──────────────────┬──────────────────────┬──────────────────────┬──────────────────────┐
  │ String Content   │ Java 8 (`char[]`)    │ Java 9+ (`byte[]`)   │ Memory Reduction     │
  ├──────────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
  │ `"admin"`        │ 10 bytes             │ **5 bytes**          │ 💥 **-50%**          │
  │ `"order_id_102"` │ 24 bytes             │ **12 bytes**         │ 💥 **-50%**          │
  │ `"Москва"`       │ 12 bytes             │ 12 bytes             │ 0% (UTF-16)          │
  │ `"User: Иван"`   │ 20 bytes             │ 20 bytes             │ 0% (Promoted to UTF) │
  └──────────────────┴──────────────────────┴──────────────────────┴──────────────────────┘
```

## 🔴 Senior Level

### High-Performance Bit-Shift Intrinsics

Methods inside `java.lang.String` use fast bitwise shifts against `coder` to calculate lengths and offsets without branch mispredictions:

```java
public int length() {
    // If coder == 0 (LATIN1): value.length >> 0 = value.length
    // If coder == 1 (UTF16):  value.length >> 1 = value.length / 2
    return value.length >> coder;
}

public char charAt(int index) {
    if (isLatin1()) {
        return (char)(value[index] & 0xff); // Zero-extension to 16-bit char
    }
    return StringUTF16.getChar(value, index);
}
```

### Architectural Trade-offs & Edge Cases

```
  1. Mixed Concatenation Widening:
     "Order: " (Latin1) + "Заказ" (UTF-16) ──► Entire resulting String becomes UTF-16!
     The ASCII prefix "Order: " expands from 1 byte/char to 2 bytes/char.

  2. Substring Coder Inheritance:
     String mixed = "Hello Москва"; // coder = UTF16
     String sub = mixed.substring(0, 5); // "Hello"
     ⚠️ `sub` inherits coder = UTF16! It occupies 10 bytes instead of 5 bytes.

  3. Hardware Cache Locality:
     Compacting strings doubles L1/L2 CPU cache density, significantly speeding up 
     JSON deserialization, HTTP routing, and database column parsing.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **JEP 254 (Java 9):** Replaced `char[]` with `byte[] value` and a `byte coder` flag.
- **`coder = 0` (LATIN1):** Encodes 1 byte per character for code points $\le \text{U+00FF}$.
- **`coder = 1` (UTF16):** Encodes 2 bytes per character for non-Latin scripts and emojis.
- **Memory Savings:** Saves ~50% of string heap memory in typical enterprise services (JSON, REST headers, SQL queries).
- **Bitwise Speed:** Calculates length via `value.length >> coder` for fast CPU evaluation.
- **Flag Control:** Enabled by default; can be disabled with `-XX:-CompactStrings`.

**Common Follow-up Questions:**
- *"Does Compact Strings compress text using algorithms like GZIP or Huffman encoding?"* → No; it is a direct 8-bit vs 16-bit storage representation, not an algorithmic compression codec.
- *"Why did Java choose Latin-1 instead of UTF-8 for internal storage?"* → Latin-1 allows constant-time $O(1)$ random character indexing (`charAt(i)` is just `value[i]`), whereas UTF-8 variable-width encoding requires $O(N)$ scanning.
- *"What happened to reflection code accessing `String.value` after Java 9?"* → The field type changed from `char[]` to `byte[]`, breaking legacy reflection code. Furthermore, Java 16+ strong encapsulation restricts reflective access to `java.base`.

**Red Flags (DO NOT Say):**
- ❌ *"Compact Strings compresses Cyrillic and Asian characters."* (Non-Latin characters require UTF-16; Compact Strings provides zero savings for them).
- ❌ *"You must pass `-XX:+CompactStrings` to enable this feature in Java 17."* (It is enabled by default in Java 9+).
- ❌ *"Compact Strings makes `charAt()` an $O(N)$ operation."* (It remains $O(1)$ because Latin-1 is a fixed 1-byte encoding).
