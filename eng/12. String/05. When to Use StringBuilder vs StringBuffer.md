# When to Use StringBuilder vs StringBuffer?

---

## 🟢 Junior Level

Both **`StringBuilder`** and **`StringBuffer`** are mutable companion classes for `String` that allow modifying text without creating intermediary garbage objects on every mutation:

```
  ┌──────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Class                    │ Thread Safety                    │ Recommended Use Case                             │
  ├──────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`StringBuilder`**      │ ❌ **Not Thread-Safe**           │ ⭐️ **Default Choice** (99% of single-thread use) │
  │ **`StringBuffer`**       │ ✅ **Thread-Safe** (Synchronized)│ Legacy code or rare cross-thread shared buffers   │
  └──────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

```java
// Standard Single-Threaded String Assembly (Fast & Efficient):
StringBuilder sb = new StringBuilder();
for (User user : users) {
    sb.append(user.getName()).append(", ");
}
String result = sb.toString();
```

## 🟡 Middle Level

### Memory Structure & Dynamic Buffer Growth

Both classes extend **`AbstractStringBuilder`** and operate on a mutable `byte[]` array:

```
  Default Initial Capacity = 16 characters

  Array Expansion Formula:
  newCapacity = (oldCapacity << 1) + 2  (Doubles the array size + 2)
```

```java
// Performance Tip: Pre-allocate capacity to eliminate resizing overhead!
// Avoids 10+ internal array allocations & System.arraycopy operations:
StringBuilder jsonBuilder = new StringBuilder(4096);
```

### Side-by-Side Architectural Comparison

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Parameter                    │ `StringBuilder`                  │ `StringBuffer`                                   │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Introduction Version**     │ Java 5 (JSR 133 / JDK 1.5)       │ Java 1.0 (Legacy)                                │
  │ **Method Synchronization**   │ None                             │ **`synchronized` on every public method**        │
  │ **Single-Thread Speed**      │ **1.5x - 2.5x Faster**           │ Slower due to monitor locks & memory barriers    │
  │ **Multi-Thread Concurrency** │ Race conditions / Index Corrupt  │ Thread-safe (atomic operations)                  │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Low-Level Synchronization & Lock Elision

```java
// StringBuffer methods require acquiring the object's monitor lock:
@Override
public synchronized StringBuffer append(String str) {
    toStringCache = null;
    super.append(str);
    return this;
}

// StringBuilder executes direct array manipulation without synchronization:
@Override
public StringBuilder append(String str) {
    super.append(str);
    return this;
}
```

### The Impact of Biased Locking Removal (Java 15+ JEP 374)

- In Java 8 and earlier, **Biased Locking** minimized the cost of uncontended synchronization on single-threaded `StringBuffer` instances by biasing the object header toward the active thread.
- In **Java 15+ (JEP 374)**, Biased Locking was **completely removed** from HotSpot JVM.
- Consequently, uncontended `StringBuffer` operations in modern Java are noticeably slower than `StringBuilder` due to atomic CAS (Compare-And-Swap) monitor locking instructions.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`StringBuilder`:** Mutable, unsynchronized, introduced in Java 5; default choice for all single-threaded code.
- **`StringBuffer`:** Mutable, synchronized on `this`, introduced in Java 1.0; legacy thread-safe alternative.
- **Underlying Structure:** Extends `AbstractStringBuilder` managing an expandable `byte[]` buffer (`LATIN1` / `UTF16`).
- **Initial Capacity:** Defaults to 16; resizing formula is `(oldCapacity << 1) + 2`.
- **Pre-allocation:** Always specify `new StringBuilder(estimatedCapacity)` when assembling large strings.
- **Modern JVMs:** Biased locking removal in Java 15 makes `StringBuffer` measurably slower even in single-threaded code.

**Common Follow-up Questions:**
- *"What happens if multiple threads invoke `StringBuilder.append()` concurrently?"* → Race conditions occur; `count` increments non-atomically, character data is overwritten, and `ArrayIndexOutOfBoundsException` or silent data corruption occurs.
- *"Can JIT compiler eliminate `StringBuffer` synchronization overhead?"* → Yes; via **Escape Analysis** and **Lock Elision** (`-XX:+EliminateLocks`), HotSpot can strip locks if it proves the instance never escapes the local method stack frame.
- *"Why should you instantiate `StringBuilder` outside of loops?"* → Instantiating inside the loop allocates a new buffer on every iteration; create it once before the loop and invoke `.append()` inside.

**Red Flags (DO NOT Say):**
- ❌ *"`StringBuffer` should be used by default just to be safe in case of multithreading."* (Use `StringBuilder` everywhere unless a single instance is explicitly shared across concurrent threads).
- ❌ *"`StringBuilder` is thread-safe as long as you do not call `delete()`."* (It is completely unsynchronized and unsafe across concurrent threads).
- ❌ *"Both `StringBuilder` and `StringBuffer` create new String objects on every append."* (They mutate an internal byte array in-place without creating intermediate String objects).
