# When to Use intern()?

---

## 🟢 Junior Level

The **`intern()`** method manually registers a string into the JVM **String Pool** and returns the canonical pooled reference:

```java
String s1 = new String("Ukraine"); // Allocated in regular Heap memory
String s2 = s1.intern();           // Adds to String Pool & returns pooled reference

String s3 = "Ukraine";             // Literal from String Pool
System.out.println(s2 == s3);      // true (Both point to the canonical pooled instance)
```

```
  When to use intern():
  • When loading millions of long-lived objects containing highly repetitive strings 
    (e.g., country codes, order statuses, currency symbols).
  • Replaces 1,000,000 duplicate String objects with 1 pooled object and 1,000,000 references!
```

---

## 🟡 Middle Level

### Database Ingestion Optimization

```java
// Batch loading users from a database:
List<UserRecord> users = new ArrayList<>();
while (resultSet.next()) {
    // Replaces duplicate strings with shared String Pool instances:
    String country = resultSet.getString("country").intern();
    String currency = resultSet.getString("currency").intern();
    users.add(new UserRecord(country, currency));
}
```

### `intern()` vs. `-XX:+UseStringDeduplication`

```
  ┌──────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Characteristic           │ `String.intern()`                │ G1 GC String Deduplication                       │
  ├──────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Execution Timing**     │ **Synchronous** (During call)    │ **Asynchronous** (During GC background passes)   │
  │ **Deduplication Target** │ Whole `String` objects           │ Backing `byte[]` arrays (String object remains)  │
  │ **Code Changes**         │ **Explicit Java code required**  │ **Zero code changes** (JVM flag only)            │
  │ **GC Dependency**        │ Works across all GC algorithms   │ Exclusive to **G1 GC** (and modern Shenandoah)   │
  │ **CPU Overhead**         │ Native JNI call & hashing cost   │ Minor background GC thread cost                  │
  └──────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### HotSpot JVM Native Interning Architecture

```cpp
// Native HotSpot OpenJDK implementation:
JVM_ENTRY(jstring, JVM_InternString(JNIEnv *env, jstring str))
  if (str == NULL) return NULL;
  oop string = JNIHandles::resolve_non_null(str);
  oop result = StringTable::intern(string, CHECK_NULL); // Queries/inserts into StringTable
  return (jstring) JNIHandles::make_local(env, result);
JVM_END
```

### Highload Hazards: Lock Contention & Table Saturation

```
  1. Multithreaded Contention:
     HotSpot's `StringTable` is a shared global resource. Concurrently calling `intern()` 
     from hundreds of worker threads introduces heavy lock contention and latency spikes.

  2. Unique Token Disaster (UUIDs, Hash Keys):
     Interning high-cardinality unique strings (e.g., UUIDs, authorization tokens, timestamps) 
     pollutes the StringTable with millions of non-reusable entries, degrading lookup times 
     from O(1) to O(n) and increasing GC pause times.
```

> [!TIP]
> **Modern Highload Alternative:** Use a bounded, application-level cache (e.g. `Caffeine` or `ConcurrentHashMap<String, String>`) with an LRU eviction policy to deduplicate strings without stressing the global JVM `StringTable`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Function:** `intern()` puts the string into the String Pool and returns the canonical pooled reference.
- **Primary Benefit:** Drastically reduces heap memory consumption for long-lived duplicate strings.
- **Top Use Cases:** Dictionary categories, status codes, country names, currencies loaded from I/O.
- **Top Anti-Patterns:** UUIDs, email addresses, order IDs, and short-lived strings (which die cheaply in Eden anyway).
- **Overhead:** Incurs JNI native call overhead (~50–100 ns) and global lock contention under heavy concurrency.
- **JVM Flag Alternative:** `-XX:+UseStringDeduplication` (transparent G1 GC background deduplication).

**Common Follow-up Questions:**
- *"What happens if you intern a string that already exists in the pool?"* → It returns the reference to the existing pooled instance, and the calling instance becomes eligible for garbage collection.
- *"Why is interning short-lived strings an anti-pattern?"* → Short-lived strings are efficiently collected in Young Generation (Eden); interning them forces global table lookups and prolongs their GC lifespan unnecessarily.
- *"How can you monitor StringTable health in production?"* → Run `jcmd <pid> VM.stringtable -verbose` to inspect bucket counts and maximum collision chain depths.

**Red Flags (DO NOT Say):**
- ❌ *"You should call `intern()` on all incoming HTTP request strings to optimize memory."* (Interning high-cardinality or short-lived strings harms CPU and memory).
- ❌ *"`intern()` is executed purely in Java bytecode without native calls."* (It is a native JNI call to HotSpot C++ `StringTable`).
- ❌ *"Strings added via `intern()` can never be garbage collected."* (Unreferenced interned strings in Java 7+ are garbage collected during standard GC cycles).
