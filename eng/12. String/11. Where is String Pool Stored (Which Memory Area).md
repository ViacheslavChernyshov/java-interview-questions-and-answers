# Where is the String Pool Stored (Which Memory Area)?

---

## 🟢 Junior Level

In modern Java, the **String Pool** is stored directly in the **Java Heap**:

```
  ┌──────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Java Version             │ Memory Area                      │ OutOfMemoryError Type                            │
  ├──────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Java 6 and earlier**   │ **PermGen** (Permanent Gen)      │ `java.lang.OutOfMemoryError: PermGen space`      │
  │ **Java 7+**              │ **Java Heap**                    │ `java.lang.OutOfMemoryError: Java heap space`    │
  │ **Java 8+ (Metaspace)**  │ **Java Heap** (NOT Metaspace!)   │ `java.lang.OutOfMemoryError: Java heap space`    │
  └──────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

```
  Key Takeaway:
  • The String Pool is NOT in Metaspace.
  • It resides in standard Java Heap memory, constrained only by the `-Xmx` heap limit.
```

## 🟡 Middle Level

### Memory Layout Across Java Versions

```
  JVM Memory Topology (Java 8, 11, 17, 21+):
  ┌─────────────────────────────────────────────────────────────────────────────┐
  │ JAVA HEAP (-Xmx)                                                            │
  │   ├── Young Generation (Eden, S0, S1)                                       │
  │   ├── Old / Tenured Generation                                              │
  │   └── ⭐️ STRING POOL (java.lang.String instances & byte[] arrays)           │
  └─────────────────────────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────────────────────────┐
  │ NATIVE MEMORY (Off-Heap)                                                    │
  │   ├── Metaspace (Class Metadata, Constant Pool Symbols)                     │
  │   ├── Code Cache (JIT Compiled Machine Code)                                │
  │   └── C++ StringTable (Native Hash Bucket Indexes)                          │
  └─────────────────────────────────────────────────────────────────────────────┘
```

### Why the String Pool was Moved in Java 7

1. **PermGen Elimination:** PermGen was slated for removal; moving the pool to the Heap paved the way for Metaspace in Java 8.
2. **Efficient Garbage Collection:** In PermGen, garbage collection was infrequent and expensive. In the Java Heap, unreferenced pooled strings are reclaimed during standard GC collection cycles.
3. **Dynamic Scalability:** Removed fixed `-XX:MaxPermSize` bottlenecks, allowing the pool to utilize the entire configured Heap.

## 🔴 Senior Level

### HotSpot JVM C++ `StringTable` vs. Java Heap Objects

In HotSpot source code, there is a clear distinction between the lookup table and the string data:

```cpp
// HotSpot OpenJDK internal architecture (C++ Native Memory):
class StringTable : public RehashableHashtable<oop, mtSymbol> {
    // The C++ hash buckets reside in Native C++ Heap memory.
    // The `oop` (Ordinary Object Pointer) points directly into the Java Heap.
};
```

- **Hash Bucket Pointers:** Stored off-heap in JVM C++ native memory.
- **`java.lang.String` Instances:** Stored in the **Java Heap**.
- **Backing `byte[]` Arrays:** Stored in the **Java Heap**.

### Garbage Collection of Pooled Strings

In Java 7+, strings in the pool **can be garbage collected**:
- When a class loader is unloaded, its compile-time string literals lose their root references.
- Dynamically interned strings (`s.intern()`) that are no longer strongly referenced by any live Java object are reclaimed during Young/Old GC cycles, and their corresponding entries in `StringTable` are pruned.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Location:** Stored in the **Java Heap** (since Java 7u6; NOT in Metaspace!).
- **Historical Context:** Resided in **PermGen** in Java 6 and earlier.
- **Metaspace Trap:** Java 8 replaced PermGen with off-heap Metaspace for class metadata, but the String Pool stayed in the Java Heap.
- **GC Behavior:** Unreferenced pooled strings in the heap are actively reclaimed by the Garbage Collector.
- **Error Type:** Over-interning in modern Java throws `OutOfMemoryError: Java heap space`.
- **Inspection:** Run `jcmd <pid> VM.stringtable -verbose` to inspect native table density.

**Common Follow-up Questions:**
- *"Why do people mistakenly believe the String Pool is in Metaspace?"* → Because PermGen held both class metadata and the String Pool in Java 6; when Java 8 introduced Metaspace to replace PermGen, developers assumed all PermGen contents moved to Metaspace.
- *"How does GC reclaim unreferenced strings from the String Pool?"* → During GC passes, the JVM scans the `StringTable`; any entry whose heap `oop` is marked as unreachable is cleared from the table.
- *"Can you configure an isolated memory limit for the String Pool?"* → No; it shares the general Java Heap memory pool with all other domain objects.

**Red Flags (DO NOT Say):**
- ❌ *"The String Pool is stored in Metaspace in Java 8 and later."* (It is in the Java Heap).
- ❌ *"Strings in the String Pool can never be garbage collected."* (In Java 7+, unreferenced pooled strings are collected by standard GC).
- ❌ *"The String Pool is stored in the JVM Stack."* (The Stack only stores local primitive variables and object references; objects live in the Heap).
