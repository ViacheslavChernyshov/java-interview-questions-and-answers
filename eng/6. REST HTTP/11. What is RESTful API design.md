# What is RESTful API design?

---

## 🟢 Junior Level

**RESTful API Design** is a set of engineering conventions and best practices for creating intuitive, scalable, and predictable web APIs based on REST principles.

### The 4 Foundational Design Rules

1. **Use Nouns, Not Verbs in URIs:**
   - ✅ `GET /api/v1/users` — Retrieve users
   - ❌ `GET /api/v1/getUsers` — Verbs are redundant; the HTTP method supplies the verb!
2. **Use Plural Nouns for Resource Collections:**
   - ✅ `/users`, `/orders`, `/products`
   - ❌ `/user`, `/order`, `/product`
3. **Use Standard HTTP Verbs for Operations:**
   - `GET` (read), `POST` (create), `PUT` (replace), `PATCH` (partial update), `DELETE` (remove).
4. **Return Meaningful HTTP Status Codes:**
   - `200 OK`, `201 Created` + `Location` header, `204 No Content`, `404 Not Found`, `422 Unprocessable Entity`.

```http
GET    /api/v1/orders        ──> Retrieve order list
GET    /api/v1/orders/42     ──> Retrieve order 42
POST   /api/v1/orders        ──> Create a new order
PUT    /api/v1/orders/42     ──> Replace order 42
PATCH  /api/v1/orders/42     ──> Update order 42 status
DELETE /api/v1/orders/42     ──> Delete order 42
```

## 🟡 Middle Level

### The Richardson Maturity Model

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ Level 3: HATEOAS (Hypermedia As The Engine Of Application State)                │
  │          Responses include dynamic navigation links (`_links`).                 │
  ├─────────────────────────────────────────────────────────────────────────────────┤
  │ Level 2: HTTP Verbs & Status Codes (⭐ Modern Industry Standard)                │
  │          Uses GET, POST, PUT, DELETE alongside 200, 201, 204, 400, 404.         │
  ├─────────────────────────────────────────────────────────────────────────────────┤
  │ Level 1: Discrete Resource URIs                                                 │
  │          Introduces discrete endpoints (`/orders`, `/users`), but uses POST/GET.│
  ├─────────────────────────────────────────────────────────────────────────────────┤
  │ Level 0: The Swamp of POX (RPC over HTTP)                                       │
  │          Single endpoint (`/api`) handling arbitrary XML/JSON RPC requests.     │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

### Design-First vs. Code-First API Development

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │              Design-First (OpenAPI 3.0 / YAML)         │             Code-First (SpringDoc OpenAPI)             │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Write OpenAPI YAML contract **before writing code**  │ • Write Java `@RestController` code first              │
  │ • Frontend & Backend develop in parallel against mocks │ • Annotations generate Swagger JSON automatically      │
  │ • **Best for:** Cross-team enterprise systems          │ • **Best for:** Rapid prototyping & single-team apps   │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### The REST Over-Fetching Problem: Resource Expansion

Unlike GraphQL, REST endpoints risk over-fetching or N+1 round trips. Use **resource inclusion/expansion parameters**:

```http
GET /api/v1/orders/42?include=items,customer,shippingAddress
```

## 🔴 Senior Level

### Under the Hood: Spring MVC `DispatcherServlet` & `HandlerMapping`

```
  HTTP Request (`GET /api/v1/users/42`)
                 │
                 ▼
        [DispatcherServlet]
                 │
                 ▼
  [RequestMappingHandlerMapping]
  (Matches HTTP Method + Path Pattern + Consumes/Produces MIME headers)
                 │
                 ▼
  [HandlerMethod: UserController.getUserById(Long id)]
```

### Trailing Slashes & URL Canonicalization

In HTTP specifications, `/users` (a resource representation) and `/users/` (a directory/collection index) are technically **two distinct URIs**.
- Ensure your API Gateway or Spring Boot routing enforces strict URI canonicalization (e.g. automatically redirecting `/users/` to `/users` via `301 Moved Permanently`).

### Traceability: Distributed Correlation IDs

Every enterprise REST API must inject and propagate distributed tracing headers:
```http
X-Correlation-ID: 1d9c4f72-9bb2-47e2-8924-d2e850b55ff8
Traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Design:** Plural nouns for URIs (`/users`), HTTP verbs for actions, standard status codes.
- **Richardson Maturity Model:** Level 2 (HTTP Verbs + Status Codes) is the global standard; Level 3 adds HATEOAS.
- **Nesting Limit:** Keep hierarchical URIs to $\le 2$ levels (`/departments/1/employees`). For deeper relationships, use query filters (`/projects?employeeId=42`).
- **Contract Strategies:** Design-First (OpenAPI YAML) enables parallel development; Code-First (SpringDoc) prioritizes rapid iteration.
- **Over-Fetching:** Solve with `?include=items,customer` expansion parameters.

**Common Follow-up Questions:**
- *"Why are nouns preferred over verbs in REST URIs?"* → Because URIs represent static *resources/nouns*, while the HTTP protocol provides the standardized *actions/verbs*.
- *"When should an endpoint return 201 Created vs. 200 OK?"* → Return `201 Created` for resource creation (`POST`), accompanied by a `Location` header; return `200 OK` when returning an updated entity or general read result.
- *"When is REST a bad architectural choice?"* → For high-frequency real-time streams (use WebSockets/gRPC), low-latency binary microservice IPC (use gRPC/Protobuf), or highly dynamic graph queries (use GraphQL).

**Red Flags (DO NOT Say):**
- ❌ *"Using verbs in URIs like `/createUser` is standard REST."* (Verbs belong in the HTTP method, not the URI).
- ❌ *"HATEOAS Level 3 is mandatory for all microservices."* (Level 3 adds significant payload overhead and is rarely used in internal microservices).
- ❌ *"Returning HTTP 200 OK with `{\"status\": 404}` inside the body is acceptable."* (Always use native HTTP status codes).
