# What is Content-Type header?

---

## 🟢 Junior Level

The **`Content-Type`** HTTP entity header indicates the **exact media format (MIME type)** of the data payload sent in the HTTP request or response body.

```http
POST /api/v1/users HTTP/1.1
Content-Type: application/json

{"name": "Alice", "age": 30}
```

Without `Content-Type`, the recipient (web server or browser) does not know how to deserialize the raw incoming byte stream into meaningful objects.

### Standard MIME Types

| MIME Media Type | Description | Typical Use Case |
|---|---|---|
| **`application/json`** | JSON data (Default standard) | Modern REST APIs |
| **`application/xml`** | XML formatted document | Enterprise SOAP / Legacy REST |
| **`multipart/form-data`** | Multi-part form payload with boundary | File uploads (`.pdf`, `.png`) |
| **`application/x-www-form-urlencoded`** | URL-encoded key-value pairs | HTML form submissions |
| **`text/plain`** | Plain raw text string | Simple status/log payloads |

## 🟡 Middle Level

### `Content-Type` in Spring MVC (`HttpMessageConverter`)

In Spring MVC, incoming request payloads are deserialized into Java objects using the **`HttpMessageConverter`** pipeline:

```
  Incoming Request (`Content-Type: application/json`)
                         │
                         ▼
  [DispatcherServlet] ──> Iterates registered `HttpMessageConverter` beans:
                         ├── 1. ByteArrayHttpMessageConverter   ──> canRead()? NO
                         ├── 2. StringHttpMessageConverter      ──> canRead()? NO
                         └── 3. MappingJackson2HttpMessageConverter ──> canRead()? YES!
                                │
                                ▼
                         Jackson `ObjectMapper` deserializes JSON bytes into `@RequestBody UserDTO`
```

- If the client sends an unsupported format (e.g. `Content-Type: application/yaml`), Spring automatically rejects the request with **`415 Unsupported Media Type`**.

### Security: MIME Sniffing & XSS Prevention

Legacy browsers sometimes ignore `Content-Type` and inspect (sniff) the initial bytes of a payload to infer its format.
- **Security Exploit:** An attacker uploads a malicious `.html`/`.js` file disguised as an image (`Content-Type: image/png`). The browser sniffs JavaScript and executes it in the victim's session (Cross-Site Scripting).
- **Protection:** Always send the security header:
  ```http
  X-Content-Type-Options: nosniff
  ```

## 🔴 Senior Level

### Multipart Boundaries & Streaming Uploads

When uploading binary files via `multipart/form-data`, the `Content-Type` header specifies a unique **boundary token** that demarcates discrete sub-payloads:

```http
POST /api/v1/documents HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="metadata"
Content-Type: application/json

{"title": "Quarterly Report"}
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="report.pdf"
Content-Type: application/pdf

<PDF Binary Bytes Stream>
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```

### High-Throughput Binary Serialization (Protobuf)

In ultra-high-throughput systems, replacing `application/json` with **`application/x-protobuf`** yields a $3\times\text{--}10\times$ improvement in serialization/deserialization throughput while cutting payload bandwidth by $50\%\text{--}80\%$:
- Zero lexical token parsing overhead.
- Compact integer field tags instead of verbose string keys.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Entity header specifying the MIME type of the payload in the request or response body.
- **Essential Formats:** `application/json`, `application/xml`, `multipart/form-data`, `application/x-www-form-urlencoded`.
- **Spring MVC:** Processed by `HttpMessageConverter` (e.g. `MappingJackson2HttpMessageConverter`).
- **Error Code:** Unsupported `Content-Type` triggers **`415 Unsupported Media Type`**.
- **Security:** Always configure `X-Content-Type-Options: nosniff` to eliminate MIME sniffing XSS attacks.
- **CharSet Standard:** UTF-8 is the RFC 8259 mandatory default for `application/json`; explicit `charset=utf-8` parameter is optional.

**Common Follow-up Questions:**
- *"What is the difference between `Content-Type` and `Accept`?"* → `Content-Type` informs the server what format is being *sent* in the body; `Accept` informs the server what format the client *wants to receive* in the response.
- *"Why is `Content-Type` unnecessary for standard `GET` requests?"* → Standard `GET` requests do not carry a body payload.
- *"What does `multipart/form-data; boundary=...` do?"* → The boundary string acts as a delimiter separating different form fields and binary file chunks within a single HTTP stream.

**Red Flags (DO NOT Say):**
- ❌ *"Content-Type tells the server what format to return in the response."* (That is the purpose of the `Accept` header).
- ❌ *"Servers should guess the body format if Content-Type is missing."* (Servers must return `415 Unsupported Media Type` or `400 Bad Request`).
- ❌ *"JSON payloads must always declare `charset=windows-1251`."* (JSON is standardized strictly on Unicode UTF-8).
