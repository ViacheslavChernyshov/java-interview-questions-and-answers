# How to properly name REST endpoints?

---

## 🟢 Junior Level

Clean REST URI naming establishes an intuitive, self-explanatory contract between clients and backend microservices.

### The 4 Foundational URI Naming Rules

1. **Use Nouns, Never Verbs:**
   - ✅ `GET /api/v1/users/42`
   - ❌ `GET /api/v1/getUser/42`
2. **Standardize on Plural Nouns for Collections:**
   - ✅ `/users`, `/orders`, `/products`
   - ❌ `/user`, `/order`, `/product`
3. **Use `kebab-case` for Multi-Word Segments (RFC 3986):**
   - ✅ `/api/v1/audit-logs`, `/api/v1/payment-methods`
   - ❌ `/audit_logs` (Underscores are hidden by URL hyperlinks), `/userProfiles` (Case-sensitivity bugs)
4. **Use Strictly Lowercase Characters:**
   - ✅ `/api/v1/customers/active`
   - ❌ `/api/v1/Customers/Active`

```http
GET    /api/v1/users              ──> Retrieve list of users
GET    /api/v1/users/42           ──> Retrieve user 42
POST   /api/v1/users              ──> Create new user
GET    /api/v1/users/42/orders    ──> Retrieve orders owned by user 42
GET    /api/v1/users?role=ADMIN   ──> Filter users by query parameter
```

## 🟡 Middle Level

### Path Hierarchy vs. Query Parameters

```
  Rule: Use Path Segments ONLY for strict parent-child ownership.
        Use Query Parameters for Filtering, Sorting, and Pagination.
```

- **✅ Proper Hierarchical Relationship (User owns Orders):**
  `GET /api/v1/users/42/orders`
- **❌ Anti-Pattern (Artificial Hierarchy):**
  `GET /api/v1/orders/status/shipped/page/2`
- **✅ Clean Query Parameter Filtering:**
  `GET /api/v1/orders?status=SHIPPED&page=2&size=20&sort=createdAt,desc`

### Modeling Non-CRUD Business Actions

When an operation does not cleanly fit standard CRUD (e.g. "Cancelling an Order", "Locking an Account"), use one of **3 approved industry patterns**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Approach                                               │ Pattern & URI                                          │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **1. Resource State Transition (Preferred REST)**      │ `PATCH /api/v1/orders/42` with payload:                │
  │                                                        │ `{"status": "CANCELLED"}`                              │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **2. Sub-Resource Entity Creation**                    │ `POST /api/v1/orders/42/cancellations`                 │
  │                                                        │ (Treats "Cancellation" as an immutable audit resource) │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **3. Pragmatic Action Verb (RPC-style)**               │ `POST /api/v1/orders/42/cancel`                        │
  │                                                        │ (Accepted for complex non-idempotent workflow engines) │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### IDOR (Insecure Direct Object Reference) Prevention

Allowing clients to pass arbitrary user IDs in paths (`/users/123/profile`) exposes the system to IDOR attacks (where malicious users enumerate `/users/124`, `/users/125`).

```http
// ✅ SECURE PATTERN: Uses the authenticated caller's identity from JWT
GET /api/v1/users/me/profile
GET /api/v1/users/me/orders
```
- For administrative access to other users, retain `/api/v1/users/{id}/profile` guarded by explicit `@PreAuthorize("hasRole('ADMIN')")` checks.

### Correct HTTP Error Semantics: `404` vs. `405`

If a client sends `POST /api/v1/users/42` when only `GET`, `PUT`, `PATCH`, and `DELETE` are supported for that individual resource:
- **❌ Error:** Returning `404 Not Found` (Misleading; implies the resource does not exist).
- **✅ Standard:** Return **`405 Method Not Allowed`** with the header:
  ```http
  HTTP/1.1 405 Method Not Allowed
  Allow: GET, PUT, PATCH, DELETE
  ```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Grammar:** Plural nouns (`/orders`), `kebab-case` (`/audit-logs`), strict lowercase, no verbs in standard CRUD URIs.
- **Hierarchy Boundary:** Use path segments strictly for parent-child ownership (`/authors/1/books`); use query params for filtering (`/books?genre=scifi&sort=title,asc`).
- **Non-CRUD Actions:** Model as state transitions (`PATCH`), sub-resources (`POST /cancellations`), or pragmatic action verbs (`POST /cancel`).
- **Security (IDOR):** Use `/users/me` to read the authenticated caller's own context.
- **Method Not Allowed:** Return `405 Method Not Allowed` + `Allow` header if a verb is unsupported on an existing URI.

**Common Follow-up Questions:**
- *"Why is `kebab-case` preferred over `camelCase` or `snake_case` in URIs?"* → RFC 3986 specifies hyphens as preferred word separators for URIs; search engines treat hyphens as distinct word boundaries, whereas underscores are often obscured by hyperlink underlines.
- *"How should search queries be formatted if they exceed URL length limits?"* → Use `POST /api/v1/users/_search` with a JSON query body.
- *"What is the difference between `/users/42` and `/users/42/`?"* → Technically distinct URIs; Spring Boot redirects trailing slashes to canonical non-slash paths via `308 Permanent Redirect`.

**Red Flags (DO NOT Say):**
- ❌ *"Using verbs in URIs like `/getAllProducts` is standard REST design."* (HTTP methods already supply the action; URIs should be nouns).
- ❌ *"Filter parameters should always be encoded as deep path segments like `/orders/status/shipped`."* (Use query strings for non-hierarchical filtering).
- ❌ *"Return 404 when a client uses an unsupported HTTP method on an existing endpoint."* (Must return `405 Method Not Allowed`).
