# What is the difference between PUT and PATCH?

---

## 🟢 Junior Level

Both **`PUT`** and **`PATCH`** are HTTP verbs used to update an existing resource on the server, but they operate under completely different architectural semantics:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                        PUT                             │                        PATCH                           │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • **Complete Replacement** of the resource             │ • **Partial Update** of specific fields                │
  │ • Client must send **all fields**                      │ • Client sends **only the fields being changed**       │
  │ • Missing fields are **reset to `null` or defaults**   │ • Omitted fields **remain untouched**                  │
  │ • **Always Idempotent**                                │ • **Conditionally Idempotent**                         │
  │ • SQL Analogy: `UPDATE users SET name=?, age=?, ...`   │ • SQL Analogy: `UPDATE users SET age = 31`             │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```http
// 1. PUT Example (Full Replacement):
PUT /api/v1/users/42
Content-Type: application/json

{"name": "Alice", "age": 30, "email": "alice@example.com"}

// 2. PATCH Example (Partial Modification):
PATCH /api/v1/users/42
Content-Type: application/json

{"age": 31}
// `name` and `email` remain completely unchanged in the database!
```

## 🟡 Middle Level

### The 2 Official IETF Standards for `PATCH`

```
                                  ┌─── 1. JSON Merge Patch (RFC 7386)
                                  │      `Content-Type: application/merge-patch+json`
                                  │      Declarative JSON object containing only changed fields.
  IETF PATCH Specifications ──────┤
                                  └─── 2. JSON Patch (RFC 6902)
                                         `Content-Type: application/json-patch+json`
                                         Sequential array of atomic mutation operations.
```

#### RFC 7386: JSON Merge Patch
```json
{
  "email": "alice.new@example.com",
  "phoneNumber": null // Null explicitly instructs the server to delete this field!
}
```

#### RFC 6902: JSON Patch
```json
[
  { "op": "test", "path": "/version", "value": 3 },
  { "op": "replace", "path": "/email", "value": "alice.new@example.com" },
  { "op": "remove", "path": "/phoneNumber" },
  { "op": "add", "path": "/roles/1", "value": "ADMIN" }
]
```

## 🔴 Senior Level

### Handling `null` vs. Omitted Fields in Spring Boot (Jackson `JsonNullable`)

In Java DTOs, distinguishing between *"the client omitted the field"* and *"the client explicitly sent `"field": null` to clear it"* is a classic challenge:

```java
// Using org.openapitools.jackson.nullable.JsonNullable:
public class UserPatchRequest {
    private JsonNullable<String> email = JsonNullable.undefined();

    // email.isUndefined() -> Client omitted the field -> Do not update
    // email.isPresent() && email.get() == null -> Client sent `null` -> Set DB field to NULL
    // email.isPresent() && email.get() != null -> Client sent new value -> Update DB field
}
```

### Optimistic Locking & The Lost Update Problem

```
  User A reads User 42 (ETag: "v1", age: 30) ──> Submits PUT /users/42 (age: 31)
  User B reads User 42 (ETag: "v1", age: 30) ──> Submits PUT /users/42 (age: 35)
```
- Without concurrency protection, User B's update silently overwrites User A's update.
- **Solution:** Clients supply `If-Match: "v1"`. When User B submits with `"v1"`, the server detects that the current database version is `"v2"` and rejects the request with **`412 Precondition Failed`**.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`PUT`:** Complete replacement; omitted fields must be erased/reset to defaults; always idempotent.
- **`PATCH`:** Partial update; modifies only specified attributes; bandwidth-efficient.
- **RFC Standards:** RFC 7386 (JSON Merge Patch) vs. RFC 6902 (JSON Patch array of operations: `add`, `remove`, `replace`, `move`, `copy`, `test`).
- **Idempotency Contrast:** `PUT` is guaranteed idempotent; `PATCH` is non-idempotent if operations are non-deterministic (e.g. array append operations).
- **Concurrency:** Guarded via `ETag` and `If-Match` (`412 Precondition Failed`).

**Common Follow-up Questions:**
- *"Why is PATCH not automatically guaranteed to be idempotent?"* → If a PATCH request contains an instruction to append an item to an array (`{"op": "add", "path": "/tags/-", "value": "premium"}`), repeating the request adds multiple duplicate tags.
- *"How do you implement partial PATCH mapping cleanly in Spring?"* → Use MapStruct with `@BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)` or Jackson `JsonNullable<T>`.
- *"When should you choose PUT over PATCH?"* → Use `PUT` for small entities where replacing the full object representation is clean and unambiguous.

**Red Flags (DO NOT Say):**
- ❌ *"PUT only updates the fields sent in the request body."* (That describes `PATCH`; `PUT` replaces the entire resource representation).
- ❌ *"PATCH is an unofficial non-standard HTTP extension."* (It is standardized in RFC 5789, RFC 7386, and RFC 6902).
- ❌ *"PUT and PATCH have identical performance characteristics."* (`PATCH` saves substantial network bandwidth on large models with hundreds of attributes).
