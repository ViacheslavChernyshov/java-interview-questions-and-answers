# What does Stateless mean in REST context?

---

## 🟢 Junior Level

In REST architecture, **Statelessness** means that **the server stores zero client conversational session state between requests**.

Every incoming HTTP request must be completely self-contained, supplying all parameters, credentials, and context required for the server to authenticate and process it.

```
  [Client] ─── Request 1: "Get User Profile" (Token: ABC) ───> [Server Node A]
  [Client] ─── Request 2: "Get Orders List"   (Token: ABC) ───> [Server Node B]
                                                                (Any node can process!)
```

### Core Advantages
1. **Horizontal Scalability:** Load balancers can route any request from any client to any backend pod or server instance.
2. **High Reliability:** If a server node crashes, active client sessions are not lost because no session state resides on that server.

## 🟡 Middle Level

### Session State vs. Resource State

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                 Session State (Client-Side)            │               Resource State (Server-Side)             │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Stored **strictly on the client**                    │ • Stored **on the server in databases / disk**         │
  │ • ❌ **Forbidden on the server** in REST               │ • ✅ **Standard & expected**                           │
  │ • Examples: Active JWT token, current wizard step,     │ • Examples: PostgreSQL database records, persistent    │
  │   selected UI pagination offset, unsubmitted form state│   order records, inventory item counts                 │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Stateful (`HttpSession`) vs. Stateless (JWT Bearer Token)

```http
// ❌ STATEFUL (Anti-pattern in REST): Requires Sticky Sessions & Heap Memory
POST /login
<-- Set-Cookie: JSESSIONID=node0198273645.node01

GET /cart
--> Cookie: JSESSIONID=node0198273645.node01 (Must route to node01!)
```

```http
// ✅ STATELESS REST STANDARD: Self-contained Bearer Token
POST /api/v1/auth/login
<-- {"accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."}

GET /api/v1/cart
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9... (Any node can verify!)
```

## 🔴 Senior Level

### The Stateless Token Revocation Paradox

Pure stateless JWT tokens cannot be invalidated immediately upon user password change or compromise without checking a centralized revocation registry.

```
                       ┌─────────────────────────┐
                       │  Stateless REST Server  │
                       └────────────┬────────────┘
                                    │ On EVERY request:
                                    ▼
                       ┌─────────────────────────┐
                       │   Redis Token Blacklist │ ◄── Centralized state check!
                       └─────────────────────────┘
```

**Production Architectural Pattern:**
1. Issue **Short-Lived Access Tokens** (5–15 minute TTL) verified purely through cryptographic signature without database lookups.
2. Issue **Long-Lived Refresh Tokens** (7–30 days) stored and validated in Redis/DB only during token refresh cycles.

### Optimistic Concurrency Control (`ETag` + `If-Match`)

Without server-side session locks, concurrent updates to shared resources are handled using HTTP Conditional Headers:

```http
// 1. Client fetches entity:
GET /api/v1/products/42
<-- 200 OK
<-- ETag: "v1.4"

// 2. Client submits update with optimistic precondition:
PUT /api/v1/products/42
If-Match: "v1.4"
--> If another user updated it to "v1.5", server returns: 412 Precondition Failed
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** The server retains zero client conversational context; every request contains all authentication and payload metadata.
- **State Distinction:** Session State is strictly client-owned; Resource State is persistent on server databases.
- **Scaling Power:** Eliminates sticky sessions, enabling effortless Kubernetes HPA auto-scaling and multi-region Anycast routing.
- **JWT Standard:** JWT Bearer tokens provide stateless claims verification.
- **Concurrency:** Handled via `ETag` and `If-Match` conditional headers (`412 Precondition Failed`).

**Common Follow-up Questions:**
- *"Why are Sticky Sessions an anti-pattern in cloud microservices?"* → Sticky sessions bind users to individual server instances, preventing balanced workload distribution and causing dropped sessions during pod restarts or auto-scaling.
- *"How do you handle immediate JWT revocation in a stateless architecture?"* → Use short-lived access tokens combined with a Redis-backed token blacklist or token introspection (RFC 7662) for sensitive endpoints.
- *"Does stateless mean the server cannot use a database?"* → No. Databases store *Resource State*, which is permanent domain data. Statelessness strictly forbids storing *Client Session State* on the application server.

**Red Flags (DO NOT Say):**
- ❌ *"Stateless means the application server does not connect to a database."* (Resource data in databases is fully supported; only conversational session state is avoided).
- ❌ *"REST APIs store client state in standard Tomcat `HttpSession` objects."* (`HttpSession` creates stateful server-bound sessions, violating REST).
- ❌ *"Stateless services cannot handle user authentication."* (Authentication is passed statelessly via Bearer tokens on every request).
