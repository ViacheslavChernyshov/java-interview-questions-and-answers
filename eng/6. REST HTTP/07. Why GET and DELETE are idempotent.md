# Why GET and DELETE are idempotent?

---

## 🟢 Junior Level

Both **`GET`** and **`DELETE`** are idempotent HTTP methods, but they achieve idempotency through completely different mechanisms:

### `GET`: Idempotency Through Safety (Read-Only)
`GET` requests **do not alter the server's resource state**. Requesting the same URI $1$ time or $100$ times leaves the target resource identical.

```http
GET /api/v1/users/42 ──> Returns User 42 representation
GET /api/v1/users/42 ──> Returns identical User 42 representation
```

### `DELETE`: Idempotency Through State Invariance
The first `DELETE` request removes the resource. Subsequent `DELETE` requests confirm that the resource is already absent.
- The **final state of the server ("Resource is absent") remains unchanged** whether you execute `DELETE` once or ten times.

```http
DELETE /api/v1/users/42 ──> 204 No Content (Resource deleted)
DELETE /api/v1/users/42 ──> 404 Not Found  (Resource is still absent!)
DELETE /api/v1/users/42 ──> 404 Not Found  (Resource remains absent!)
```

```
  Summary Mental Model:
  • GET is idempotent because it changes nothing.
  • DELETE is idempotent because after the first call, there is nothing left to change.
```

---

## 🟡 Middle Level

### The Status Code Independence Invariant

> [!IMPORTANT]
> **RFC 9110 Specification Rule:** Idempotency guarantees **server-side resource state consistency**, NOT identical HTTP response status codes.
> - Call 1: `204 No Content`
> - Call 2: `404 Not Found`
> 
> Because the server's database state is identical after both calls (User 42 does not exist), `DELETE` is **100% idempotent**.

### Soft Deletion (`is_deleted = true`)
In modern enterprise architectures where records are never physically dropped:
```sql
-- Executed on DELETE /api/v1/users/42:
UPDATE users SET is_deleted = TRUE, deleted_at = NOW() WHERE id = 42;
```
Repeating this query multiple times results in `is_deleted = TRUE` every time, remaining completely idempotent.

### Technical Side-Effects vs. Domain Safety
A `GET` request may write to an access log, increment Prometheus latency metrics, or update a Redis cache.
- These **infrastructure side-effects do not violate REST safety** because they do not alter the domain representation of the requested resource.

## 🔴 Senior Level

### Distributed Event-Driven Architecture (Kafka / Outbox Pattern)

When a `DELETE` endpoint triggers asynchronous domain events (e.g. `OrderCancelledEvent` published to Kafka):

```
  Client DELETE Retry ──> [Order Service]
                                │
                                ├─> 1. Check if Order exists in DB:
                                │      • Exists: Mark CANCELLED & Write Event to Outbox Table.
                                │      • Already Cancelled: Skip Event Emission! (Returns 204 / 404)
                                │
                                └─> Prevents duplicate downstream Kafka events!
```
- **Senior Design Rule:** Never emit duplicate domain events on subsequent duplicate `DELETE` network retries.

### Cache Invalidation on `DELETE`

RFC 9110 mandates that intermediate caching proxies (Cloudflare, Fastly, Nginx) **must invalidate any cached representations** associated with the URI upon receiving a successful `DELETE` request:

```
  DELETE /api/v1/products/42 (204 No Content)
         │
         ▼
  [CDN Cache Invalidator] ──> Purges cached `GET /api/v1/products/42`
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`GET` Idempotency:** Guaranteed by safety; read-only operations cause zero domain state mutations.
- **`DELETE` Idempotency:** Guaranteed by state invariance; resource is absent after the first call, and repeated calls produce no additional state mutations.
- **Status Code Rule:** Changing status codes (`204` $\to$ `404`) does **not** break idempotency.
- **Soft Deletes:** `UPDATE SET is_deleted = true` is fully idempotent.
- **Event-Driven Guardrail:** Ensure network retries of `DELETE` do not emit duplicate Kafka/RabbitMQ events.
- **Cache Invalidation:** Successful `DELETE` purges intermediate CDN caches for that URI.

**Common Follow-up Questions:**
- *"Why is `GET /users/1/delete` considered dangerous?"* → Web crawlers, search bots, and browser URL pre-fetchers execute `GET` requests speculatively; treating `GET` as a delete action causes catastrophic accidental data loss.
- *"How should batch deletions be modeled in REST?"* → Use `DELETE /api/v1/users?ids=10,11,12` (idempotent) rather than `POST /api/v1/users/delete-batch` (non-idempotent).
- *"Can a GET request return different data over time and still be idempotent?"* → Yes. If other processes update the database, subsequent `GET` requests reflect the new state. Idempotency means the `GET` request itself did not cause the state change.

**Red Flags (DO NOT Say):**
- ❌ *"DELETE is not idempotent because the second request returns a 404 error instead of 200."* (Idempotency pertains to server state, not response status codes).
- ❌ *"GET requests cannot write anything to logs or metrics."* (Infrastructure telemetry does not violate domain safety).
- ❌ *"Soft delete makes DELETE non-idempotent."* (Setting a flag to `true` repeatedly produces the exact same final state).
