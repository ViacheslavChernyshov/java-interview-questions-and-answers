# How to organize REST API versioning?

---

## 🟢 Junior Level

**API Versioning** is the practice of managing changes to an API contract so that existing client applications (mobile apps, third-party integrations, SPAs) do not break when new features or breaking changes are introduced.

### Breaking vs. Non-Breaking Changes

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                 ⚠️ Breaking Changes                    │                ✅ Non-Breaking Changes                 │
  │              (Requires Version Bump)                   │             (Safe to Deploy in Place)                  │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Removing or renaming existing JSON fields            │ • Adding new **optional** response fields              │
  │ • Changing field data types (`Integer` ──> `String`)   │ • Adding new **optional** query parameters             │
  │ • Adding new **mandatory** request fields              │ • Adding brand-new endpoints (`/api/v1/promotions`)    │
  │ • Altering HTTP status code contracts (`200` ──> `404`)│ • Performance optimizations & internal bug fixes       │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The 4 Versioning Strategies Compared

```
  ┌────────────────────────┬────────────────────────────────────────────┬─────────────────────────────┬─────────────────────────────┐
  │ Strategy               │ Example Syntax                             │ Pros                        │ Cons                        │
  ├────────────────────────┼────────────────────────────────────────────┼─────────────────────────────┼─────────────────────────────┤
  │ **1. URI Path**        │ `GET /api/v1/users`                        │ ⭐ Industry standard        │ Violates URI permanence;    │
  │ (Most Popular)         │ `GET /api/v2/users`                        │ Trivial caching & routing   │ multiple endpoints in code  │
  ├────────────────────────┼────────────────────────────────────────────┼─────────────────────────────┼─────────────────────────────┤
  │ **2. Query Parameter** │ `GET /api/users?version=2`                 │ Easy fallback to default v1 │ CDN cache key fragmentation │
  ├────────────────────────┼────────────────────────────────────────────┼─────────────────────────────┼─────────────────────────────┤
  │ **3. Custom Header**   │ `GET /api/users`                           │ Clean, semantic URIs        │ Requires `Vary: Header`;    │
  │                        │ `X-API-Version: 2`                         │                             │ Harder to test in browser   │
  ├────────────────────────┼────────────────────────────────────────────┼─────────────────────────────┼─────────────────────────────┤
  │ **4. Content / Media** │ `GET /api/users`                           │ Pure REST constraint        │ Complex cURL testing;       │
  │ (Vendor MIME Type)     │ `Accept: application/vnd.app.v2+json`      │ (Content Negotiation)       │ Swagger documentation pain  │
  └────────────────────────┴────────────────────────────────────────────┴─────────────────────────────┴─────────────────────────────┘
```

## 🔴 Senior Level

### RFC 8594 Sunset & Deprecation Lifecycle

When deprecating legacy API versions, inform consumers programmatically using standardized HTTP response headers:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1767225600
Sunset: Wed, 11 Nov 2026 00:00:00 GMT
Link: <https://api.example.com/v1-to-v2-migration>; rel="sunset"

{"id": 101, "name": "Legacy User Payload"}
```

### Database Evolution: The Expand and Contract Pattern

API versioning often fails at the database layer. Senior engineers use the **Expand and Contract (Parallel Run)** database migration pattern:

```
  Phase 1 (Expand): Add `full_name` column to DB. Keep `first_name` & `last_name`.
  Phase 2 (Dual-Write): Application writes to both old and new columns.
  Phase 3 (Backfill): Migrate historical rows to populate `full_name`.
  Phase 4 (Read Switch): Release v2 API reading from `full_name`.
  Phase 5 (Contract): Deprecate v1, drop `first_name` and `last_name` columns without downtime.
```

### Consumer-Driven Contract Testing (Pact / Spring Cloud Contract)

In microservice ecosystems, prevent versioning churn by using **Contract Testing**:
1. Downstream consumer defines exact JSON schema requirements in a Pact contract.
2. Upstream provider's CI pipeline runs contract tests on every pull request, preventing accidental breaking changes from ever reaching staging or production.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Strategies:** URI Path (`/v1/orders` - Industry Standard), Query Param (`?v=2`), Custom Header (`X-API-Version`), Content Negotiation (`Accept: application/vnd.company.v2+json`).
- **Breaking Changes:** Removing fields, renaming fields, altering data types, adding required request parameters.
- **Deprecation Standards:** `Sunset` (RFC 8594) and `Deprecation` response headers.
- **Database Migrations:** Expand and Contract pattern prevents database lockup and downtime during version transitions.
- **Contract Testing:** Tools like Pact ensure consumer compatibility without requiring aggressive major version bumps.

**Common Follow-up Questions:**
- *"Why is URI Path versioning preferred by Stripe, GitHub, and AWS over Header versioning?"* → URI versioning is explicit, easy to bookmark, visible in access logs, and integrates seamlessly with L7 reverse proxy routing (Nginx/Kong) and CDN edge caching.
- *"What headers should you send when deprecating an API version?"* → Send `Deprecation: true`, `Sunset: <HTTP-Date>`, and `Link: <url>; rel="sunset"`.
- *"How do you handle breaking database changes across two API versions?"* → Use the Expand and Contract pattern: add new schema elements alongside old ones, dual-write during transition, and drop deprecated columns only after sunsetting v1.

**Red Flags (DO NOT Say):**
- ❌ *"Adding a new optional field to a JSON response is a breaking change."* (Modern JSON parsers ignore unknown fields; it is backward-compatible).
- ❌ *"URI Path versioning is strictly forbidden in REST."* (It is the dominant pragmatic industry standard used by 90%+ of cloud companies).
- ❌ *"We can immediately shut down v1 API endpoints without warning clients."* (APIs must follow structured deprecation and sunset schedules with telemetry tracking).
