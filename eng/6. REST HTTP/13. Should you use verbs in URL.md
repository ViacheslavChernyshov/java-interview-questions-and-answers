# Should you use verbs in URL?

---

## 🟢 Junior Level

**In strict REST architecture, verbs should NOT be used in URIs.**

The HTTP protocol already supplies the action (the verb); the URI must represent the entity (the noun):

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                 ❌ Anti-Pattern (RPC Style)            │                 ✅ Clean REST Standard                 │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ `POST /saveOrder`                                      │ `POST /api/v1/orders`                                  │
  │ `GET  /getUserById?id=42`                              │ `GET  /api/v1/users/42`                                │
  │ `POST /deleteUser/42`                                  │ `DELETE /api/v1/users/42`                              │
  │ `GET  /searchProducts?query=shoes`                     │ `GET  /api/v1/products?query=shoes`                    │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

> [!CAUTION]
> **The `GET /logout` or `GET /deleteUser` Catastrophe:** If you use `GET` for destructive actions, web crawlers (Googlebot) and browser URL pre-fetchers will speculatively crawl those links, triggering accidental bulk account deletions!

## 🟡 Middle Level

### Turning Complex Actions into Resources (Reification)

When a business process cannot be expressed as simple CRUD, Senior architects apply **Reification (Turning the Action into a First-Class Domain Resource)**:

```
  Business Need: "Cancel an Order"
```

1. **Option 1: State Mutation via `PATCH` (Good for simple changes)**
   ```http
   PATCH /api/v1/orders/42
   Content-Type: application/json

   {"status": "CANCELLED"}
   ```

2. **Option 2: Sub-Resource Reification (Best for auditability)**
   ```http
   POST /api/v1/orders/42/cancellations
   Content-Type: application/json

   {"reason": "Customer requested refund", "authorizedBy": "Agent-007"}
   ```
   *Advantage:* Creates an immutable cancellation record with audit metadata, timestamp, and refund references.

## 🔴 Senior Level

### Pragmatic Controller Endpoints (When Verbs are Allowed)

While pure REST requires noun-based resources, industry leaders (GitHub, Stripe, AWS, Kubernetes) accept **controller-style action endpoints** for complex, multi-stage workflows:

```http
// Real-World Pragmatic Exceptions:
POST /api/v1/repos/octocat/Hello-World/forks
POST /api/v1/payment-intents/pi_123/confirm
POST /api/v1/calculators/tax-estimator
```

### State Machine Transitions via HATEOAS

Instead of exposing arbitrary verb endpoints (`/approve`, `/reject`, `/refund`), a HATEOAS-compliant API returns **permissible hypermedia transitions** based on the entity's current lifecycle state:

```json
// GET /api/v1/orders/42 (Order is in PENDING state)
{
  "orderId": 42,
  "status": "PENDING",
  "_links": {
    "self": { "href": "/api/v1/orders/42" },
    "cancel": { "href": "/api/v1/orders/42/cancellations", "method": "POST" },
    "payment": { "href": "/api/v1/orders/42/payments", "method": "POST" }
  }
}
```
*When the order transitions to `SHIPPED`, the server dynamically removes the `cancel` link, preventing illegal state transitions at the network layer!*

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Rule:** URIs must be nouns; HTTP methods supply the verbs.
- **Reification Pattern:** Model complex operations as noun sub-resources (`POST /orders/42/cancellations` rather than `POST /orders/42/cancel`).
- **State Changes:** Use `PATCH` with state payloads (`{"status": "CANCELLED"}`).
- **Pragmatic Compromise:** Controller-style endpoints (`POST /confirm`, `POST /fork`) are acceptable in production for non-CRUD business actions.
- **HATEOAS State Machine:** Dynamic `_links` guide clients through legal lifecycle transitions without hardcoding action endpoints.

**Common Follow-up Questions:**
- *"Why should you never use `GET /api/logout`?"* → `GET` is a Safe method; browsers and antivirus scanners pre-fetch `GET` links, causing users to be logged out unexpectedly. Use `POST /api/logout`.
- *"What is Reification in REST API design?"* → Converting an abstract business verb/action into a concrete noun resource (e.g. turning "cancel order" into the resource "Cancellation").
- *"How does HATEOAS eliminate the need for custom action URIs?"* → The server advertises permitted action endpoints inside `_links` depending on the current state of the resource.

**Red Flags (DO NOT Say):**
- ❌ *"Putting verbs in URIs like `/getAllUsers` or `/updateUser` is standard REST."* (That is RPC, not REST).
- ❌ *"It is fine to use `GET` for actions like `/users/1/activate` as long as it takes no body."* (`GET` must be safe and read-only).
- ❌ *"Verbs are completely forbidden under every circumstance in production APIs."* (Pragmatic action endpoints like `POST /calculate` or `POST /fork` are widely used in enterprise architectures).
