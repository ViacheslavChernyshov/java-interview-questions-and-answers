# What HTTP status codes do you know?

---

## 🟢 Junior Level

**HTTP Status Codes** are standardized 3-digit numeric responses returned by a web server to indicate the outcome of an HTTP request.

### The 5 Status Code Categories

| Category | Range | Meaning | Common Examples |
|---|---|---|---|
| **`1xx`** | 100–199 | **Informational** | `100 Continue`, `101 Switching Protocols` |
| **`2xx`** | 200–299 | **Success** | `200 OK`, `201 Created`, `204 No Content` |
| **`3xx`** | 300–399 | **Redirection** | `301 Moved Permanently`, `304 Not Modified`, `307 Temporary Redirect` |
| **`4xx`** | 400–499 | **Client Error** | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` |
| **`5xx`** | 500–599 | **Server Error** | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` |

```
  Rule of Thumb:
  • 2xx: Everything worked as expected.
  • 4xx: The CLIENT made a mistake (invalid input, missing token, forbidden).
  • 5xx: The SERVER failed (unhandled exception, database outage, network timeout).
```

## 🟡 Middle Level

### Essential 2xx, 3xx, 4xx, and 5xx Codes in REST

#### 2xx Success
- **`200 OK`:** General successful read/update request with response payload.
- **`201 Created`:** Resource successfully created. Returns the `Location: /api/v1/orders/101` header pointing to the new resource.
- **`202 Accepted`:** Asynchronous processing acknowledged; job queued but not yet finished.
- **`204 No Content`:** Successful operation returning **no body** (ideal for `DELETE` and `PUT`).

#### 3xx Redirection
- **`304 Not Modified`:** Returned during **Conditional GET** (`If-None-Match`). Informs client to use local browser cache, saving 100% of payload bandwidth.
- **`307 Temporary Redirect` & `308 Permanent Redirect`:** Modern standards that **strictly preserve the HTTP method** (`POST` remains `POST`), unlike legacy `301/302` which allowed browsers to mutate `POST` into `GET`.

#### 4xx Client Errors
- **`400 Bad Request` vs. `422 Unprocessable Entity`:**
  - `400`: Syntactic error (malformed JSON, invalid characters).
  - `422` (RFC 4918 / 9110): Semantic validation error (JSON is well-formed, but `email` lacks `@` or `age < 0`).
- **`401 Unauthorized` vs. `403 Forbidden`:**
  - `401`: Unauthenticated (Missing/expired token; "Who are you?").
  - `403`: Authenticated but Unauthorized (Identity verified, but lacking required role/permissions; "You cannot access this").
- **`409 Conflict`:** Unique constraint collision (duplicate email) or optimistic lock mismatch.
- **`429 Too Many Requests`:** Rate limiter triggered; returns `Retry-After: 60`.

#### 5xx Server Errors
- **`500 Internal Server Error`:** Unhandled Java runtime exception (`NullPointerException`).
- **`502 Bad Gateway`:** Reverse proxy (Nginx / Cloudflare) failed to establish a connection to the backend JVM application.
- **`503 Service Unavailable`:** Server overloaded or down for maintenance.
- **`504 Gateway Timeout`:** Reverse proxy connected, but backend JVM took too long to respond.

## 🔴 Senior Level

### Structured Error Responses: RFC 9457 Problem Details

Modern Spring Boot 3 applications reject ad-hoc custom error maps in favor of the **RFC 9457 (formerly RFC 7807) standard**:

```java
@ExceptionHandler(AccountBalanceException.class)
public ProblemDetail handleInsufficientFunds(AccountBalanceException ex) {
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(
        HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage()
    );
    problem.setType(URI.create("https://api.bank.com/errors/insufficient-funds"));
    problem.setTitle("Insufficient Account Funds");
    problem.setProperty("currentBalance", ex.getBalance());
    problem.setProperty("timestamp", Instant.now());
    return problem;
}
```

```json
{
  "type": "https://api.bank.com/errors/insufficient-funds",

  "instance": "/accounts/acc-99/transfers",
  "currentBalance": 120.00,

}
```

### Highload Infrastructure Patterns
- **Negative Caching:** CDNs cache `404` and `410 Gone` responses for a short duration (e.g. 5–30s) to protect backend microservices from DDoS request storms targeting non-existent URIs.
- **Circuit Breaker Integration:** Upstream services monitor `5xx` error rates; if threshold exceeds 50%, the Circuit Breaker trips immediately to prevent cascading thread pool exhaustion.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Status Families:** `1xx` (Info), `2xx` (Success), `3xx` (Redirect), `4xx` (Client error), `5xx` (Server error).
- **Core Success:** `200` (OK), `201` (Created + `Location` header), `202` (Accepted async job), `204` (No Content).
- **Redirection:** `307/308` strictly preserve HTTP methods (`POST` stays `POST`); `304` indicates cached resource validity.
- **Client Errors:** `400` (malformed syntax) vs. `422` (validation failure); `401` (unauthenticated) vs. `403` (unauthorized); `409` (conflict); `429` (rate limited).
- **Server Errors:** `500` (application bug), `502` (proxy can't reach backend), `503` (overloaded), `504` (backend timeout).
- **Error Standard:** RFC 9457 `ProblemDetail` is the modern industry standard for API error payloads.

**Common Follow-up Questions:**
- *"When should an API return 202 Accepted?"* → When processing a heavy background job (video encoding, batch export). The response returns a tracking ID or polling status URL.
- *"Why are 307 and 308 preferred over 301 and 302 in REST APIs?"* → Because `307/308` explicitly forbid clients from mutating the HTTP request method during redirection.
- *"What is the difference between 502 Bad Gateway and 504 Gateway Timeout?"* → `502` means the proxy (Nginx) could not connect or received an invalid response from the upstream Java service; `504` means the upstream service connected but failed to return a response before the timeout deadline.

**Red Flags (DO NOT Say):**
- ❌ *"Returning 200 OK with `{\"error\": \"User not found\"}` in the JSON body is standard REST practice."* (Violates REST Level 2; use appropriate `4xx` status codes).
- ❌ *"401 and 403 are identical synonyms."* (`401` is authentication identity failure; `403` is authorization permission failure).
- ❌ *"500 Internal Server Error is a good response for business validation failures."* (Business errors are client issues and must return `4xx`).
