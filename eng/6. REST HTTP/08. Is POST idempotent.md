# Is POST idempotent?

---

## 🟢 Junior Level

**No, by HTTP specification (RFC 9110), the `POST` method is officially NON-IDEMPOTENT.**

Each time a client executes a `POST` request, the server performs a **new, distinct business action or subordinate resource creation**:

```
  POST /api/v1/orders ──> Creates Order #101 (Database record created)
  POST /api/v1/orders ──> Creates Order #102 (Second database record created!)
  POST /api/v1/orders ──> Creates Order #103 (Third database record created!)
```

### Real-World Implications
- **Network Retries are Dangerous:** If a network timeout occurs while waiting for a `POST` response, browser or proxy automated retries can cause duplicate credit card charges or double order placements.
- **Form Resubmissions:** Web browsers pop up a warning dialog ("Confirm Form Resubmission") when users refresh a page loaded via `POST`.

---

## 🟡 Middle Level

### Why `POST` is Designed to be Non-Idempotent

In REST semantics:
- `PUT /orders/101` replaces the exact resource at `/orders/101`.
- `POST /orders` instructs the collection `/orders` to **generate and append a new subordinate resource** with a server-assigned identifier.

### When Non-Idempotency is Desirable
Non-idempotency is the intended behavior when:
1. Posting comments on an article.
2. Appending telemetry audit log events.
3. Sending notifications or chat messages.

### The Post/Redirect/Get (PRG) Pattern

```
  [User Browser] ──(1. POST /checkout)──────────────────> [Server] (Charges card)
  [User Browser] <──(2. 303 See Other: /order/42)──────── [Server]
  [User Browser] ──(3. GET /order/42)────────────────────> [Server]
  [User Browser] <──(4. 200 OK: Renders Confirmation)─── [Server]
```
If the user presses `F5` to refresh the page, the browser re-executes the safe, idempotent **`GET /order/42`**, preventing double-charging!

## 🔴 Senior Level

### Enterprise Pattern: Making `POST` Idempotent via `Idempotency-Key`

Payment processors (Stripe, Adyen) and microservices convert non-idempotent `POST` endpoints into **Idempotent Operations** using an `Idempotency-Key` header:

```http
POST /api/v1/charges HTTP/1.1
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
Content-Type: application/json

{"amount": 5000, "currency": "USD"}
```

```
  Step 1: Check Redis distributed lock: `SET charge:{user_id}:{idempotency_key} "PROCESSING" NX EX 120`
          ├── Key Exists with status "PROCESSING" ──> Returns `409 Conflict` (Prevents race condition!)
          └── Key Exists with status "COMPLETED"  ──> Returns cached original `201/200` JSON response!
  Step 2: If Key is new, execute database transaction and charge payment gateway.
  Step 3: Update Redis entry to status "COMPLETED" with serialized response payload (24h TTL).
```

### The `POST /search` Pragmatic Exception

While resource retrieval should theoretically use `GET`, complex enterprise search queries with 50+ nested filters exceed web server and proxy URI length limits ($8\text{KB}$).
- **Industry Convention:** Use `POST /api/v1/search` with a JSON filter payload in the request body. Although semantically a `POST`, it functions as a safe, read-only query. (The IETF is developing the standard HTTP `QUERY` method for this use case).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Rule:** `POST` is officially non-idempotent by RFC 9110 specification.
- **Semantic Role:** Appends new subordinate resources under a collection URI or executes an unconstrained processing action.
- **Safety Hazard:** Network retries on `POST` risk duplicate transactions.
- **Browser Protection:** PRG (Post/Redirect/Get) pattern redirects `POST` to `GET` via `303 See Other`.
- **Enterprise Solution:** `Idempotency-Key` header + Redis distributed lock + Database unique constraints enable safe `POST` retries.
- **Complex Queries:** `POST /search` is a pragmatic industry standard for large JSON filter queries that exceed URI length limits.

**Common Follow-up Questions:**
- *"How does Stripe guarantee that a customer is never double-charged during a network drop?"* → The client generates a unique UUID `Idempotency-Key`. If a retry arrives with that key, Stripe returns the original cached result without re-executing the payment.
- *"What HTTP status code should you return if a second request arrives with the same `Idempotency-Key` while the first is still processing?"* → Return `409 Conflict` or `425 Too Early`.
- *"Why is `POST /search` used instead of `GET`?"* → When search filter criteria are large or complex, URL encoding in a `GET` query string exceeds web server/CDN URI buffer limits ($8\text{KB}$).

**Red Flags (DO NOT Say):**
- ❌ *"POST is idempotent if you only update one record."* (That is the semantic domain of `PATCH` or `PUT`).
- ❌ *"Service meshes automatically retry failed POST requests."* (Envoy/Istio strictly forbids auto-retrying `POST` by default due to duplicate execution hazards).
- ❌ *"Using POST for complex search violates all REST principles."* (It is a recognized pragmatic pattern due to URI buffer limitations).
