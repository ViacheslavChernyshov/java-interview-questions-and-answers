# Which HTTP methods are idempotent?

---

## 🟢 Junior Level

In REST and HTTP architecture (RFC 9110), methods are divided into **Idempotent** (can be repeated safely without extra side-effects) and **Non-Idempotent**:

### Idempotent HTTP Methods

| HTTP Method | Idempotent? | Why |
|---|---|---|
| **`GET`** | ✅ **Yes** | Read-only; causes zero state changes on the server |
| **`HEAD`** | ✅ **Yes** | Identical to `GET` but returns headers only |
| **`OPTIONS`** | ✅ **Yes** | Read-only metadata query (e.g. CORS permissions) |
| **`PUT`** | ✅ **Yes** | Complete replacement; setting state to `'ACTIVE'` $N$ times results in `'ACTIVE'` |
| **`DELETE`** | ✅ **Yes** | 1st call deletes resource; subsequent calls confirm it remains deleted |

### Non-Idempotent HTTP Methods

| HTTP Method | Idempotent? | Why |
|---|---|---|
| **`POST`** | ❌ **No** | Typically creates a new resource on every invocation |
| **`PATCH`** | ⚠️ **Conditionally** | Depends on whether the patch operation is deterministic |

```
  GET    /api/v1/orders/101  ──> Idempotent (Safe read)
  PUT    /api/v1/orders/101  ──> Idempotent (State replacement)
  DELETE /api/v1/orders/101  ──> Idempotent (Deletion)
  POST   /api/v1/orders      ──> Non-Idempotent (Creates order #102, #103, #104...)
```

## 🟡 Middle Level

### Safe vs. Modifying Idempotent Methods

```
                                  ┌─── Safe Idempotent (Read-Only, Zero Mutations):
                                  │      `GET`, `HEAD`, `OPTIONS`
                                  │
  Idempotent HTTP Methods ────────┤
                                  └─── Modifying Idempotent (State Mutating, Repeat-Safe):
                                         `PUT` (Full replacement)
                                         `DELETE` (Resource removal)
```

### The `PATCH` Idempotency Nuance

Whether a `PATCH` request is idempotent depends strictly on the operations inside its payload:

```json
// ✅ IDEMPOTENT PATCH (Sets value deterministically):
{ "op": "replace", "path": "/status", "value": "CANCELLED" }

// ❌ NON-IDEMPOTENT PATCH (Appends to array on every call):
{ "op": "add", "path": "/auditLogs/-", "value": "Attempted update" }
```

## 🔴 Senior Level

### Service Mesh (Istio / Envoy) Automatic Retry Policies

Cloud-native infrastructure relies on HTTP method idempotency to implement automated network fault tolerance:

```
  Incoming Request
         │
         ▼
  [Envoy Sidecar Proxy] ──> [Target Microservice Pod] (Returns 503 / Drops TCP)
         │
         ├─> If GET, HEAD, PUT, DELETE:
         │   ✅ Automatically retries with Exponential Backoff & Jitter!
         │
         └─> If POST:
             ❌ FORBIDDEN to auto-retry (Unless configured with `Idempotency-Key`)!
```

### The Retry Storm Hazard & Jitter Mitigation

When a downstream database suffers a momentary slowdown, hundreds of clients auto-retrying idempotent requests simultaneously can trigger a catastrophic **Retry Storm**:

$$\text{Retry Delay} = \min(\text{Cap}, \text{Base} \times 2^{\text{Attempt}}) + \text{Full Jitter Randomness}$$

Adding **Jitter** decorrelates retry spikes, allowing degraded databases to recover safely.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Idempotent Set:** `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`.
- **Non-Idempotent Set:** `POST`.
- **Conditional:** `PATCH` (deterministic replace is idempotent; relative append/increment is non-idempotent).
- **Service Mesh Policies:** Envoy/Istio automatically retries failed `GET`, `PUT`, and `DELETE` requests; `POST` retries are blocked by default.
- **Side-Effects Rule:** Creating technical database audit records does not violate domain idempotency.

**Common Follow-up Questions:**
- *"Why is `PUT` idempotent but `POST` is not?"* → `PUT` specifies the exact target URI and state representation to store; repeating it replaces the same URI with the same data. `POST` instructs the server to generate a new subordinate resource under a collection URI on each call.
- *"How does a Service Mesh know which requests to retry?"* → Sidecar proxies inspect the HTTP request verb; idempotent methods (`GET`, `PUT`, `DELETE`) are retried on `503` or network dropouts according to retry policies.
- *"What is a Retry Storm?"* → A cascading failure where thousands of clients retry failed requests simultaneously without exponential backoff or jitter, overwhelming an already struggling backend service.

**Red Flags (DO NOT Say):**
- ❌ *"All HTTP methods except GET are non-idempotent."* (`PUT`, `DELETE`, `HEAD`, and `OPTIONS` are fully idempotent).
- ❌ *"DELETE is non-idempotent because the first call returns 200/204 and the second returns 404."* (Idempotency measures server state side-effects, not HTTP response codes).
- ❌ *"PATCH is strictly forbidden in RESTful APIs."* (PATCH is an official standard under RFC 5789).
