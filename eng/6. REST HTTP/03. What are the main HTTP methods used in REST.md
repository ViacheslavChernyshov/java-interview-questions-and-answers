# What are the main HTTP methods used in REST?

---

## 🟢 Junior Level

**HTTP Methods (HTTP Verbs)** are standardized protocol verbs that inform the server **what action** to perform on the target resource identified by a URI.

| HTTP Method | CRUD Equivalent | Semantic Purpose | Example Request |
|---|---|---|---|
| **`GET`** | **R**ead | Retrieve resource representation | `GET /api/v1/users/42` |
| **`POST`** | **C**reate | Create a new subordinate resource / execute action | `POST /api/v1/users` |
| **`PUT`** | **U**pdate (Replace) | Completely **replace** the target resource | `PUT /api/v1/users/42` |
| **`PATCH`** | **U**pdate (Partial) | **Partially update** specific fields of a resource | `PATCH /api/v1/users/42` |
| **`DELETE`** | **D**elete | Remove the specified resource | `DELETE /api/v1/users/42` |

```
  Core REST Rule:
  • URIs are NOUNS representing entities (`/orders`, `/customers`).
  • HTTP Verbs are ACTIONS operating on those nouns (`GET`, `POST`, `DELETE`).
```

## 🟡 Middle Level

### Method Taxonomy: Safe & Idempotent (RFC 9110)

Under the **RFC 9110 (HTTP Semantics)** specification, HTTP methods are strictly classified by their safety and idempotency guarantees:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │                               HTTP METHOD MATRIX                                │
  ├──────────────┬──────────────┬──────────────┬──────────────┬─────────────────────┤
  │ Method       │ Request Body │ Safe?        │ Idempotent?  │ Default Cacheable?  │
  ├──────────────┼──────────────┼──────────────┼──────────────┼─────────────────────┤
  │ **`GET`**    │ ❌ No        │ ✅ **Yes**   │ ✅ **Yes**   │ ✅ **Yes**          │
  │ **`HEAD`**   │ ❌ No        │ ✅ **Yes**   │ ✅ **Yes**   │ ✅ **Yes**          │
  │ **`OPTIONS`**│ ❌ No        │ ✅ **Yes**   │ ✅ **Yes**   │ ❌ No               │
  │ **`POST`**   │ ✅ Yes       │ ❌ No        │ ❌ **No**    │ ⚠️ Only with header │
  │ **`PUT`**    │ ✅ Yes       │ ❌ No        │ ✅ **Yes**   │ ❌ No               │
  │ **`PATCH`**  │ ✅ Yes       │ ❌ No        │ ⚠️ Depends   │ ❌ No               │
  │ **`DELETE`** │ ⚠️ Rare      │ ❌ No        │ ✅ **Yes**   │ ❌ No               │
  └──────────────┴──────────────┴──────────────┴──────────────┴─────────────────────┘
```

- **Safe Methods (`GET`, `HEAD`, `OPTIONS`):** Cause **zero state mutations** on the server. Safe for search engine crawlers and browser prefetching.
- **Idempotent Methods (`GET`, `PUT`, `DELETE`, `HEAD`):** Making $N > 1$ identical requests leaves the server's resource state identical to making 1 request.

### Utility Methods: `HEAD` and `OPTIONS`

- **`HEAD`:** Returns the exact headers that a `GET` would return, but **suppresses the response body**. Used to inspect file size (`Content-Length`) or cache validity (`ETag`) before initiating heavy network downloads.
- **`OPTIONS`:** Executed automatically by web browsers during **CORS Preflight** checks to inspect supported methods (`Access-Control-Allow-Methods: GET, POST, PUT, DELETE`).

## 🔴 Senior Level

### Network Retry Policies in Cloud Service Meshes (Envoy / Istio)

Cloud infrastructure depends on HTTP method semantics to execute automated network retries:

```
  Client Call ──> [Envoy Sidecar Proxy] ──> [Backend Service] (Returns 503 / Drops TCP)
                         │
                         ├─> If GET, PUT, DELETE: ✅ AUTOMATICALLY RETRIES (Safe / Idempotent)
                         └─> If POST: ❌ FORBIDDEN TO RETRY (Risk of duplicate charges/orders!)
```

### Method Tunneling (`X-HTTP-Method-Override`)

Legacy corporate firewalls, API proxies, and strict WAFs sometimes block `PUT`, `PATCH`, and `DELETE` requests.
- **Solution:** Clients send a standard `POST` request with an override header:
  ```http
  POST /api/v1/orders/102 HTTP/1.1
  X-HTTP-Method-Override: PATCH
  Content-Type: application/json

  {"status": "CANCELLED"}
  ```
  Spring Boot supports this transparently by configuring `HiddenHttpMethodFilter`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **5 Core Verbs:** `GET` (read), `POST` (create/process), `PUT` (full replace), `PATCH` (partial update), `DELETE` (remove).
- **Safe vs. Idempotent:** Safe methods never modify state (`GET`, `HEAD`); Idempotent methods can modify state, but $N$ executions yield identical server state (`PUT`, `DELETE`).
- **`POST` is Non-Idempotent:** Executing $N$ POST requests creates $N$ distinct resources.
- **`HEAD`:** Headers-only representation for metadata inspection without downloading payloads.
- **`OPTIONS`:** Used for CORS Preflight permission checks.

**Common Follow-up Questions:**
- *"Why is `DELETE` considered idempotent if the second request returns 404?"* → Idempotency refers to **the state of the resource on the server**, not the HTTP status code. After both the 1st and 100th call, the resource is deleted from the database.
- *"Why should you never use `GET` to delete records?"* → `GET` must be safe; browser URL pre-fetching, search crawlers, and caching proxies will trigger unintended database deletions.
- *"What is the difference between `PUT` and `PATCH`?"* → `PUT` replaces the entire resource representation (missing fields are reset to `null` or defaults); `PATCH` modifies only the supplied subset of fields.

**Red Flags (DO NOT Say):**
- ❌ *"GET and POST are the only two methods supported in modern REST."* (REST relies heavily on `PUT`, `PATCH`, `DELETE`).
- ❌ *"PUT and PATCH are identical synonyms."* (`PUT` is full replacement and idempotent; `PATCH` is partial mutation).
- ❌ *"DELETE is not idempotent because the status code changes from 200 to 404."* (Idempotency measures server state side-effects, not response codes).
