# Which exceptions must be handled?

---

## 🟢 Junior Level

In the Java language specification, **only Checked Exceptions are MANDATORY to handle at compile-time**.

```
  ┌────────────────────────┬────────────────────────────────────────────┬───────────────────────────────────────────┐
  │ Exception Type         │ Handling Requirement                       │ Enforced By                               │
  ├────────────────────────┼────────────────────────────────────────────┼───────────────────────────────────────────┤
  │ **Checked Exceptions** │ **MANDATORY**                              │ **`javac` Compiler**                      │
  │ (`IOException`, etc.)  │ Must enclose in `try-catch` OR `throws`    │ (Code will not compile if omitted)        │
  ├────────────────────────┼────────────────────────────────────────────┼───────────────────────────────────────────┤
  │ **Unchecked (Runtime)**│ **OPTIONAL / ARCHITECTURAL**               │ **Application Architecture**              │
  │ (`NullPointerException`│ Handled at centralized global controllers  │ (Compiler imposes zero rules)             │
  ├────────────────────────┼────────────────────────────────────────────┼───────────────────────────────────────────┤
  │ **JVM Errors**         │ ❌ **DO NOT CATCH**                        │ **JVM Internal Subsystem**                │
  │ (`OutOfMemoryError`)   │ JVM state is corrupted; recovery is unsafe │ (Let thread terminate or process restart) │
  └────────────────────────┴────────────────────────────────────────────┴───────────────────────────────────────────┘
```

```java
// Compilation succeeds: Compiler forces handling of checked IOException
public void processFile(Path path) {
    try {
        Files.readString(path);
    } catch (IOException e) {
        log.error("Unable to read file: {}", e.getMessage());
    }
}
```

## 🟡 Middle Level

### The "Catch or Specify" Contract

A checked exception is a formal contract between a method and its caller. The method declares: *"I may encounter an external environmental contingency $X$, and you must write explicit logic to address it."*

### Architectural Boundary Exception Translation

Propagating raw checked exceptions across application layers breaks encapsulation and pollutes interface contracts:

```java
public interface OrderStorage {
    // Clean interface: Does not leak JDBC/SQL dependencies
    Order save(Order order); 
}

public class PostgresOrderStorage implements OrderStorage {
    @Override
    public Order save(Order order) {
        try {
            return jdbcTemplate.queryForObject(...);
        } catch (DataAccessException e) {
            // Translate checked/infrastructure exception into semantic domain runtime exception
            throw new OrderStorageException("Failed to persist order: " + order.id(), e);
        }
    }
}
```

## 🔴 Senior Level

### The JVM Uncaught Exception Safety Net

When an unchecked exception (or a checked exception bypassed via `@SneakyThrows`) escapes the top of a thread's call stack, the JVM invokes the thread's **`UncaughtExceptionHandler`**:

```java
// Production Best Practice: Configure global safety net for worker threads
Thread.setDefaultUncaughtExceptionHandler((thread, throwable) -> {
    log.error("FATAL: Uncaught exception in thread [{}]", thread.getName(), throwable);
    Metrics.counter("jvm.threads.uncaught_exceptions", "thread", thread.getName()).increment();
    if (throwable instanceof VirtualMachineError) {
        System.exit(1); // Initiate container pod restart for OOM
    }
});
```

### Why You Must Never Catch `java.lang.Error`

```java
// ❌ CRITICAL ANTI-PATTERN: Attempting to catch and continue after OOM
try {
    processHeavyBatch();
} catch (Throwable t) { // Catches OutOfMemoryError and ThreadDeath!
    log.error("Error occurred, continuing...", t);
}
```
*When `OutOfMemoryError` occurs, the JVM's object references, locks, and internal state are in an undefined corrupted state. Continuing execution risks writing corrupted data to disks and databases.*

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Mandatory Set:** Checked exceptions (`Exception` subclasses excluding `RuntimeException`).
- **Compiler Rule:** Catch locally via `try-catch` or specify in signature via `throws`.
- **Unchecked Set:** `RuntimeException` subclasses (optional; handled globally via `@ControllerAdvice`).
- **Never Catch:** `java.lang.Error` (`OutOfMemoryError`, `StackOverflowError`); indicates irrecoverable JVM memory corruption.
- **Exception Translation:** Always wrap low-level infrastructure checked exceptions into unchecked domain exceptions at repository boundaries.
- **Safety Net:** Set `Thread.setDefaultUncaughtExceptionHandler` to log unhandled thread exceptions and trigger container restarts.

**Common Follow-up Questions:**
- *"What happens if you catch `java.lang.Error` in a background worker thread?"* → The thread may continue running in an unstable, memory-corrupted JVM state where locks or half-allocated objects cause data corruption.
- *"Why is `catch (Throwable t)` considered a dangerous code smell?"* → Because `Throwable` catches `OutOfMemoryError`, `StackOverflowError`, and `ThreadDeath`, preventing the JVM from shutting down gracefully. Catch `Exception` instead.
- *"How do unchecked exceptions reach the client if not caught locally?"* → They unwind the call stack to the top-level framework dispatcher (e.g. Spring MVC's `DispatcherServlet`), which delegates to `@ExceptionHandler` methods.

**Red Flags (DO NOT Say):**
- ❌ *"Catching `OutOfMemoryError` in a try-catch block is a valid way to free memory."* (OOM corrupts JVM state; the pod should crash and restart).
- ❌ *"All exceptions must be caught in the exact method where they are thrown."* (Exceptions are designed to bubble up to architectural layers that possess the context to handle them).
- ❌ *"Swallowing checked exceptions with an empty `catch (Exception e) {}` fulfills the handling requirement."* (It satisfies the compiler syntactically while introducing catastrophic silent failures).
