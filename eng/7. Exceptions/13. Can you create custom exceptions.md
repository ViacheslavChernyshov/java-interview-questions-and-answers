# Can you create custom exceptions?

---

## 🟢 Junior Level

**Yes. You can create custom exceptions in Java by defining a class that extends `java.lang.Exception` or `java.lang.RuntimeException`.**

```java
// 1. Custom Checked Exception (Checked by compiler)
public class InsufficientInventoryException extends Exception {
    public InsufficientInventoryException(String message) {
        super(message);
    }
}

// 2. Custom Unchecked Exception (Recommended for modern business domain logic)
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) {
        super(message);
    }
}
```

```java
public User getUser(Long id) {
    return userRepository.findById(id)
        .orElseThrow(() -> new UserNotFoundException("User not found with id: " + id));
}
```

## 🟡 Middle Level

### The 4 Standard Constructors Rule (Effective Java)

To ensure your custom exception integrates seamlessly with exception chaining and diagnostic tools, implement all **4 canonical constructors**:

```java
public class PaymentProcessingException extends RuntimeException {
    private static final long serialVersionUID = 1L;

    public PaymentProcessingException() {
        super();
    }

    public PaymentProcessingException(String message) {
        super(message);
    }

    public PaymentProcessingException(String message, Throwable cause) {
        super(message, cause);
    }

    public PaymentProcessingException(Throwable cause) {
        super(cause);
    }
}
```

### Rich Domain Context Pattern

Rather than concatenating diagnostic strings, modern domain exceptions store structured metadata:

```java
public class OrderDomainException extends RuntimeException {
    private final ErrorCode errorCode;
    private final String orderId;
    private final Map<String, Object> details = new LinkedHashMap<>();

    public OrderDomainException(ErrorCode errorCode, String orderId, String message) {
        super(message);
        this.errorCode = errorCode;
        this.orderId = orderId;
    }

    public OrderDomainException withDetail(String key, Object value) {
        this.details.put(key, value);
        return this;
    }

    public ErrorCode getErrorCode() { return errorCode; }
    public String getOrderId() { return orderId; }
    public Map<String, Object> getDetails() { return Collections.unmodifiableMap(details); }
}
```

## 🔴 Senior Level

### Microservice Boundary Translation (RFC 9457)

Custom Java exception classes must **never leak across network API boundaries**:
- If Service A throws `OrderDomainException`, an external client or Service B lacking that class in its classpath will fail to deserialize it.
- **Production Solution:** Catch domain exceptions at the Spring Web layer and translate them into RFC 9457 `ProblemDetail` JSON payloads:

```java
@RestControllerAdvice
public class DomainExceptionHandler {

    @ExceptionHandler(OrderDomainException.class)
    public ProblemDetail handleOrderException(OrderDomainException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            ex.getErrorCode().getHttpStatus(), ex.getMessage()
        );
        problem.setTitle(ex.getErrorCode().getTitle());
        problem.setProperty("orderId", ex.getOrderId());
        problem.setProperty("details", ex.getDetails());
        return problem;
    }
}
```

### Security & PII Protection (GDPR / PCI-DSS)

> [!CAUTION]
> Never include Personally Identifiable Information (PII), raw passwords, API keys, or credit card numbers in exception messages. Exception messages are written to unencrypted log aggregators (ELK/Datadog) and error monitoring dashboards (Sentry).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Creation:** Extend `RuntimeException` (unchecked domain errors) or `Exception` (checked environmental conditions).
- **4 Canonical Constructors:** Provide no-arg, message, message + cause, and cause constructors.
- **Rich Context:** Store structured domain attributes (`errorCode`, `entityId`, `timestamp`) as typed fields rather than building unparseable formatted strings.
- **Serialization:** Always declare `private static final long serialVersionUID = 1L;`.
- **API Boundaries:** Map custom exceptions to RFC 9457 `ProblemDetail` responses via `@RestControllerAdvice`.
- **Security:** Sanitize messages to exclude PII, passwords, and sensitive tokens.

**Common Follow-up Questions:**
- *"When should you NOT create a custom exception?"* → When an existing standard JDK exception clearly expresses the condition (`IllegalArgumentException`, `IllegalStateException`, `NoSuchElementException`, `UnsupportedOperationException`).
- *"Why is `serialVersionUID` needed on custom exceptions?"* → Because `Throwable` implements `Serializable`, altering the class definition without declaring `serialVersionUID` causes `InvalidClassException` during remote RPC deserialization.
- *"How can you optimize custom exceptions that are thrown thousands of times per second?"* → Create stackless exceptions by passing `writableStackTrace = false` to `super()`.

**Red Flags (DO NOT Say):**
- ❌ *"Custom exceptions should inherit directly from `Throwable`."* (Always inherit from `Exception` or `RuntimeException`).
- ❌ *"Create a new custom exception class for every single validation error in the app."* (Leads to class explosion; use parameterized domain exceptions or standard exceptions).
- ❌ *"Include user passwords in exception messages for easier debugging."* (Violates security compliance standards and leaks credentials to logs).
