# What is exception wrapping?

---

## 🟢 Junior Level

**Exception Wrapping** (also known as *Exception Translation* or *Chaining*) is the practice of catching a low-level or checked exception and throwing a higher-level semantic exception that encapsulates the original failure as its **`cause`**.

```java
try {
    // Low-level database call that may throw a checked SQLException
    jdbcTemplate.queryForObject(sql, mapper);
} catch (DataAccessException e) {
    // ✅ Wrapping: Embeds the root cause into a domain runtime exception
    throw new UserLookupException("Failed to retrieve user for id: " + userId, e);
    //                                                                        ^-- Root Cause
}
```

```
com.bank.UserLookupException: Failed to retrieve user for id: 42
    at com.bank.UserService.getUser(UserService.java:28)
Caused by: org.postgresql.util.PSQLException: Connection refused (Connection timed out)
    at org.postgresql.core.v3.ConnectionFactoryImpl.openConnection(ConnectionFactoryImpl.java:82)
```

### Why We Wrap Exceptions
1. **Enrich Context:** Adds domain business parameters (`userId=42`) to raw technical messages.
2. **Encapsulate Infrastructure:** Prevents low-level vendor dependencies (`PSQLException`, `StripeException`) from polluting service interfaces.
3. **Preserve Root Cause:** Preserves the complete original stack trace via the `Caused by:` chain.

## 🟡 Middle Level

### The Lost Cause Anti-Pattern

```java
// ❌ CRITICAL ANTI-PATTERN: Completely destroys the original stack trace and exception type!
try {
    processPayment();
} catch (PaymentProviderException e) {
    throw new OrderException(e.getMessage()); // ⚠️ Cause is NOT attached!
}

// ✅ CORRECT: Chains the entire exception object
try {
    processPayment();
} catch (PaymentProviderException e) {
    throw new OrderException("Payment failed for orderId=" + orderId, e);
}
```

### Under the Hood: The `cause` Field in `Throwable`

Inside `java.lang.Throwable`, the root cause is managed via an internal reference:

```java
private Throwable cause = this; // Default self-sentinel
```
- Passing `cause` into `super(message, cause)` invokes **`initCause(cause)`**.
- Calling `initCause()` more than once on the same `Throwable` instance throws an **`IllegalStateException`**.

## 🔴 Senior Level

### Reflection & Dynamic Proxies: `InvocationTargetException`

When invoking methods via Java Reflection (`Method.invoke()`) or dynamic proxies, the JVM **always wraps any exception thrown by the target method inside an `InvocationTargetException`**:

```java
try {
    Method method = targetClass.getMethod("process");
    method.invoke(instance);
} catch (InvocationTargetException e) {
    // Extract the ACTUAL exception thrown by the underlying method:
    Throwable actualException = e.getCause();
    log.error("Underlying method execution failed", actualException);
}
```

### Programmatic Root Cause Traversal

To traverse an arbitrary exception causal chain down to the physical root cause:

```java
// Native Java Root Cause Extractor:
public static Throwable getRootCause(Throwable throwable) {
    Objects.requireNonNull(throwable);
    Throwable rootCause = throwable;
    while (rootCause.getCause() != null && rootCause.getCause() != rootCause) {
        rootCause = rootCause.getCause();
    }
    return rootCause;
}

// Or using Apache Commons Lang:
Throwable root = ExceptionUtils.getRootCause(throwable);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Creating a higher-level exception that stores the lower-level original exception as its `cause`.
- **Purpose:** Decouples layer abstractions, adds domain context, and preserves root cause stack traces.
- **Log Appearance:** Chained causes appear as `Caused by:` lines in application log outputs.
- **Lost Cause Trap:** Never write `new MyException(e.getMessage())`; always pass the exception object `e` directly.
- **Reflection:** `Method.invoke()` wraps all target exceptions inside `InvocationTargetException.getCause()`.
- **Root Cause Extraction:** Traverse using `while (t.getCause() != null) t = t.getCause()`.

**Common Follow-up Questions:**
- *"What happens if you invoke `initCause()` twice on the same exception?"* → The JVM throws an `IllegalStateException` because an exception's cause can only be established once.
- *"Why should intermediate service layers wrap checked `SQLException` into unchecked `DataAccessException`?"* → To maintain clean architectural decoupling so changes in persistence technologies (e.g. switching from SQL to MongoDB) do not break service interface signatures.
- *"What is the difference between an exception's `cause` and its `suppressed` exceptions?"* → A `cause` represents the underlying causal failure that triggered the exception; `suppressed` exceptions are secondary failures occurring during resource cleanup (Try-With-Resources).

**Red Flags (DO NOT Say):**
- ❌ *"I wrap exceptions by passing `e.getMessage()` to the new exception constructor."* (Destroys the entire causal stack trace and original exception type).
- ❌ *"Wrapping exceptions is bad because it creates too many lines in logs."* (Root causes are indispensable for diagnosing production database, network, and timeout bugs).
- ❌ *"You can call `initCause()` as many times as you want to update the cause."* (`initCause()` can only be called once).
