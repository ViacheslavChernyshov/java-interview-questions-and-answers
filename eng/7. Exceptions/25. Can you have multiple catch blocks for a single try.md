# Can you have multiple catch blocks for a single try?

---

## 🟢 Junior Level

**Yes. A single `try` block can be followed by multiple sequential `catch` blocks** to apply distinct handling logic to different exception types.

```java
public String readConfigFile(String path) {
    try {
        return Files.readString(Path.of(path));
    } catch (NoSuchFileException e) {
        log.warn("Configuration file missing, applying defaults");
        return "{}";
    } catch (AccessDeniedException e) {
        log.error("Permission denied reading configuration at {}", path);
        throw new SecurityException("Cannot access config", e);
    } catch (IOException e) {
        log.error("Generic I/O failure", e);
        throw new UncheckedIOException(e);
    }
}
```

### The Ordering Rule: Specific to General
Catch blocks must be arranged **from the most specific subclass to the most general superclass**:

```java
// ❌ COMPILATION ERROR: Exception has already been caught!
try {
    process();
} catch (IOException e) {
    // Intercepts all IOExceptions, including FileNotFoundException!
} catch (FileNotFoundException e) {
    // ❌ javac fails: "Unreachable code: FileNotFoundException has already been caught"
}
```

## 🟡 Middle Level

### Under the Hood: The Bytecode Exception Table

In the JVM bytecode specification, `try-catch` blocks are compiled into an **Exception Table**:

```
  Exception Table:
  from    to    target    type
     0    12        15    Class java/io/FileNotFoundException
     0    12        28    Class java/io/IOException
     0    12        42    Class java/lang/Exception
```

```
  JVM Exception Resolution (First-Match-Wins):
  Step 1: Code in range [0, 12] throws an exception instance.
  Step 2: JVM scans Exception Table sequentially from top to bottom.
  Step 3: First entry whose class matches (or is a supertype of) the thrown object gains control.
  Step 4: Execution jumps directly to the `target` bytecode address.
```

### Zero-Cost Exception Handling in the JVM
> [!NOTE]
> Entering a `try` block has **zero runtime execution cost** in modern JVMs. The Exception Table exists purely as static class metadata. No CPU instructions are executed unless an exception is actually thrown.

## 🔴 Senior Level

### Catch Block Ladder Smell & Java 17/21 Pattern Matching

Having 6+ sequential catch blocks is an architectural code smell indicating a violation of the Single Responsibility Principle (SRP).
- **Alternative 1 (Multi-Catch):** Combine catches with identical handling into `catch (IOException | SQLException e)`.
- **Alternative 2 (Pattern Matching for instanceof / switch in Java 21):**

```java
try {
    executeComplexBatch();
} catch (Exception e) {
    // Modern Java pattern matching switch:
    switch (e) {
        case FileNotFoundException fnf -> log.warn("Missing file: {}", fnf.getMessage());
        case TimeoutException te       -> triggerRetry(te);
        case SecurityException se      -> alertSecurityTeam(se);
        default                        -> log.error("Unhandled execution error", e);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Language Support:** A `try` block can have multiple `catch` blocks evaluated top-down.
- **Ordering Mandate:** Specific subclasses must be declared **before** broader superclasses (`FileNotFoundException` before `IOException`).
- **First Match Wins:** The JVM executes only the first matching `catch` block; remaining blocks are skipped.
- **Zero-Cost Try:** `try` blocks execute with zero CPU overhead when no exception occurs (Exception Table is static bytecode metadata).
- **Multi-Catch (Java 7+):** Use `catch (A | B e)` when multiple exception types share identical handling.

**Common Follow-up Questions:**
- *"What happens if an exception matches two different catch blocks?"* → Only the first matching catch block in declaration order executes.
- *"Why does `javac` produce a compile error if `catch (Exception e)` is placed above `catch (IOException e)`?"* → Because `IOException` is a subclass of `Exception`, making the second block permanently unreachable code.
- *"Can a `finally` block execute if none of the catch blocks match the thrown exception?"* → Yes. The `finally` block executes before the unhandled exception propagates up the call stack.

**Red Flags (DO NOT Say):**
- ❌ *"Catch block order does not matter in Java."* (Superclasses must always be placed after subclasses; otherwise code fails compilation).
- ❌ *"Having 10 catch blocks slows down normal happy-path method execution."* (Exception tables have zero CPU overhead during normal execution).
- ❌ *"The JVM executes all matching catch blocks sequentially."* (Only the first matching block executes).
