# How to properly log exceptions?

---

## 🟢 Junior Level

In enterprise Java applications, always use a logging framework (such as **SLF4J with Logback**) instead of `System.out.println()` or `e.printStackTrace()`.

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderProcessor {
    private static final Logger log = LoggerFactory.getLogger(OrderProcessor.class);

    public void process(Long orderId) {
        try {
            executePayment(orderId);
        } catch (PaymentException e) {
            // ✅ CORRECT: Exception is passed as the LAST argument with domain context
            log.error("Failed to process payment for orderId={}", orderId, e);
        }
    }
}
```

### The SLF4J Formatting Trap

```java
// ❌ CRITICAL MISTAKE: Passes `e` into `{}` placeholder (invokes e.toString(); STACK TRACE IS LOST!)
log.error("Payment failed: {}", e);

// ❌ CODE SMELL: Only logs the message, completely losing the root cause and line numbers
log.error(e.getMessage());

// ✅ CORRECT: `{}` consumes orderId; the trailing `e` is automatically extracted as a stack trace!
log.error("Payment failed for orderId={}", orderId, e);
```

## 🟡 Middle Level

### The "Log Once OR Rethrow" Invariant

A common architectural anti-pattern is logging an exception at every layer of the call stack before rethrowing it:

```java
// ❌ ANTI-PATTERN: "Log and Rethrow" duplicates the error 4 times in ELK/Datadog
try {
    dao.save(order);
} catch (SQLException e) {
    log.error("DAO error", e); // Log entry #1
    throw new ServiceException(e);
}
```

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Correct Pattern 1: Handle & Log                        │ Correct Pattern 2: Wrap & Rethrow                      │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ `try { ... } catch (Exception e) {`                    │ `try { ... } catch (SQLException e) {`                 │
  │ `    log.error("Handled error for id={}", id, e);`     │ `    throw new OrderPersistenceException("Fail", e);`  │
  │ `    return fallbackValue;`                            │ `}`                                                    │
  │ `}`                                                    │ *(Let top-level `@RestControllerAdvice` log it once!)* │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Context Enrichment with MDC (Mapped Diagnostic Context)

In distributed microservices, stack traces require correlation IDs (`traceId`, `spanId`, `userId`):

```java
try {
    MDC.put("traceId", UUID.randomUUID().toString());
    MDC.put("userId", String.valueOf(user.getId()));
    orderService.submit(order);
} finally {
    // ⚠️ CRITICAL: Always clear MDC in finally to prevent leaking context across thread pools!
    MDC.clear();
}
```

## 🔴 Senior Level

### High-Throughput Log Optimization (Logback / Log4j2)

Logging full 200-line stack traces at $50{,}000$ RPS can saturate disk I/O and choke application throughput.
1. **Asynchronous Appenders:** Decouple disk I/O from request worker threads using `AsyncAppender`:
   ```xml
   <appender name="ASYNC_FILE" class="ch.qos.logback.classic.AsyncAppender">
       <appender-ref ref="FILE" />
       <queueSize>1024</queueSize>
       <discardingThreshold>0</discardingThreshold>
       <neverBlock>true</neverBlock>
   </appender>
   ```
2. **Shortened Throwable Converters:** Truncate deep repetitive framework frames (Spring AOP, Hibernate proxies) while preserving application frames:
   ```xml
   <!-- Outputs at most 20 frames, packaging info, and root causes -->
   <pattern>%d{ISO8601} [%thread] %-5level %logger - %msg%n%rEx{20}%n</pattern>
   ```

### PII Data Scrubbing (Security Compliance)

> [!CAUTION]
> Never log raw Personally Identifiable Information (PII), unmasked credit card PANs, passwords, or authorization bearer tokens. Configure log scrubbers at the Logback encoder layer to sanitize sensitive keys before writing to disk.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **SLF4J Trailing Arg:** Always pass the exception as the last argument (`log.error("context {}", id, e)`); do NOT put a `{}` placeholder for it.
- **Log OR Rethrow:** Never log an exception AND rethrow it; log it once at the handling layer or bubble it up to `@RestControllerAdvice`.
- **MDC Tracking:** Enrich logs with distributed `traceId` via `MDC.put()`, and always clear in `finally`.
- **Async Logging:** Use `AsyncAppender` in high-throughput microservices to prevent disk I/O from blocking request threads.
- **PII Protection:** Sanitize sensitive user data to maintain GDPR and PCI-DSS compliance.

**Common Follow-up Questions:**
- *"What happens if you write `log.error(\"Failed: {}\", e.getMessage(), e)`?"* → SLF4J binds `e.getMessage()` to `{}` and correctly attaches `e`'s stack trace because `e` is the last parameter.
- *"Why is MDC cleanup mandatory when using thread pools?"* → Thread pools (e.g. Tomcat/HikariCP) reuse worker threads; failing to call `MDC.clear()` will cause subsequent unrelated requests to inherit stale `traceId` and `userId` metadata.
- *"What log level should be used for expected business exceptions (e.g. `UserNotFoundException`)?"* → Use `log.warn()` or `log.info()`; reserving `log.error()` strictly for system failures prevents alert fatigue in SRE dashboards.

**Red Flags (DO NOT Say):**
- ❌ *"I log exceptions using `log.error(e.getMessage())`."* (Completely drops the stack trace, class name, and causal chain).
- ❌ *"I always log the error in the catch block and then rethrow it to the caller."* (Creates duplicate log pollution across every service layer).
- ❌ *"Calling `MDC.clear()` is unnecessary because threads clean themselves up."* (Thread pool reuse causes severe diagnostic data leaks).
