# What is the order of catch blocks?

---

## 🟢 Junior Level

The golden rule for ordering `catch` blocks in Java is: **Most Specific Subclasses MUST Come First, Broad Superclasses MUST Come Last**.

```java
try {
    processLocalFile("data.bin");
} catch (FileNotFoundException e) {
    // 1. Most specific subclass first
    log.warn("File missing, using fallback: {}", e.getMessage());
} catch (IOException e) {
    // 2. Intermediate superclass
    log.error("I/O communication error", e);
} catch (Exception e) {
    // 3. Broadest application root last
    log.error("Unexpected application failure", e);
}
```

### What Happens If You Reverse the Order?
If you place a broader superclass before a narrower subclass, **the Java compiler rejects the code with a compilation error**:

```java
// ❌ COMPILATION ERROR: Unreachable Code
try {
    process();
} catch (Exception e) {
    // Catches all Exceptions, making subsequent catch blocks unreachable!
} catch (IOException e) {
    // ❌ Error: "Exception IOException has already been caught"
}
```

## 🟡 Middle Level

### The "First-Match-Wins" Runtime Search

When an exception is thrown, the JVM consults the method's **Exception Table** from top to bottom:

```
  ┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ Exception Table (Scanned Top-to-Bottom by JVM during unwind):                                   │
  │   [Entry 1] if thrown instanceof FileNotFoundException ──> Jump to Handler 1 (Target: L1)      │
  │   [Entry 2] if thrown instanceof IOException           ──> Jump to Handler 2 (Target: L2)      │
  │   [Entry 3] if thrown instanceof Exception             ──> Jump to Handler 3 (Target: L3)      │
  └─────────────────────────────────────────────────────────────────────────────────────────────────┘
```
- The **very first handler** whose declared class matches the thrown instance (or is a supertype of it) gains execution control.
- All subsequent catch handlers in the table are bypassed.

### Unrelated Sibling Exceptions
Exceptions that share no direct parent-child relationship (e.g. `SQLException` and `IOException`) can be declared in **any relative order**:

```java
// ✅ Both are valid and compile cleanly:
catch (SQLException e) { ... } catch (IOException e) { ... }
catch (IOException e) { ... }  catch (SQLException e) { ... }
```

## 🔴 Senior Level

### Placement of `catch (Throwable t)`

Catching `Throwable` is strictly reserved for the **outermost boundary of a thread root**:

```java
// Outermost thread worker loop:
public void run() {
    while (running) {
        try {
            processTask();
        } catch (DomainException e) {
            log.warn("Task rejected: {}", e.getMessage());
        } catch (Exception e) {
            log.error("Task failed unexpectedly", e);
        } catch (Throwable t) {
            // ⚠️ SENIOR GUARD: Catch Throwable ONLY at thread root to log fatal JVM crashes
            log.error("FATAL: JVM crash condition in worker thread", t);
            System.exit(1); // Force pod restart
        }
    }
}
```

### Micro-Optimization: Frequency Ordering for Disjoint Types
Because the JVM evaluates Exception Table entries with linear $O(N)$ complexity upon unwinding, ordering disjoint catch blocks by **highest anticipated failure probability** minimizes table scan times in high-throughput error scenarios.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Ordering Rule:** Specific subclasses must be declared before broader superclasses (`FileNotFoundException` before `IOException`).
- **Compiler Invariant:** Inverted ordering results in compile-time rejection (*"Exception X has already been caught"*).
- **Execution Model:** First match wins; the JVM stops searching upon finding the first valid entry in the Exception Table.
- **Disjoint Types:** Sibling exceptions without parent-child inheritance can be listed in any arbitrary order.
- **Throwable Rule:** `catch (Throwable t)` should only exist at thread boundary roots.

**Common Follow-up Questions:**
- *"Does the order of types inside a single multi-catch block `catch (A | B e)` matter?"* → No. Types inside a multi-catch statement are disjoint siblings pointing to the same target handler address.
- *"Why does `javac` forbid placing `catch (Exception e)` above `catch (RuntimeException e)`?"* → Because `RuntimeException` extends `Exception`, making the second catch block dead, unreachable code.
- *"Can a `catch (Error e)` block precede a `catch (Exception e)` block?"* → Yes. `Error` and `Exception` are sibling subclasses of `Throwable`, so either order compiles cleanly.

**Red Flags (DO NOT Say):**
- ❌ *"Catch blocks are evaluated in random order by the JVM."* (They are strictly evaluated in top-down source order).
- ❌ *"Putting `catch (Exception e)` first is fine because the compiler will figure out the right handler."* (It causes an immediate compile error).
- ❌ *"Sibling exceptions must be sorted alphabetically."* (Disjoint exceptions have no compiler-enforced ordering constraints).
