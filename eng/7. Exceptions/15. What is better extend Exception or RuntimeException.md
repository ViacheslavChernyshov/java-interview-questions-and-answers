# What is better: extend Exception or RuntimeException?

---

## 🟢 Junior Level

The decision to extend **`Exception` (Checked)** versus **`RuntimeException` (Unchecked)** comes down to a single question: **Can the immediate caller meaningfully recover from this failure programmatically?**

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │              Extend Exception (Checked)                │          Extend RuntimeException (Unchecked)           │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Use when failure is **expected and recoverable**     │ • Use for **business domain errors** and bug defenses  │
  │ • Compiler **forces caller to handle or declare**      │ • Compiler **imposes zero boilerplate**                │
  │ • Best for **low-level libraries & external I/O**      │ • Best for **Spring Boot, microservices & DDD**        │
  │ • Examples: `InterruptedException`, `TimeoutException` │ • Examples: `OrderNotFoundException`, `NPE`            │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// 1. Extend Exception (Checked): Forces caller to implement retry/fallback logic
public class QuotaExhaustedException extends Exception {
    public QuotaExhaustedException(String message) { super(message); }
}

// 2. Extend RuntimeException (Unchecked - Modern Standard): Bubbles to global error handler
public class InsufficientFundsException extends RuntimeException {
    public InsufficientFundsException(String message) { super(message); }
}
```

## 🟡 Middle Level

### The Architectural Decision Framework

```
                          Encountered Failure Condition
                                        │
             Is it an unrecoverable bug or programming mistake?
             (e.g., null argument, invalid array index)
                                        │
                       ┌────────────────┴────────────────┐
                       ▼ YES                             ▼ NO
            [RuntimeException]             Can caller RECOVER immediately?
            (`IllegalArgumentException`)   (e.g. retry, choose fallback)
                                                         │
                                        ┌────────────────┴────────────────┐
                                        ▼ YES                             ▼ NO
                             [Checked Exception]                [RuntimeException]
                             (`ConnectionTimeoutException`)     (`UserNotFoundException`)
```

### The Abstraction Leak Problem with Checked Exceptions

When lower layers throw checked exceptions, implementation details bleed through interface boundaries:

```java
// ❌ LEAKY ABSTRACTION: Exposes underlying database technology to business layers!
public interface UserRepository {
    User findById(Long id) throws SQLException; // Leaks JDBC detail!
}

// ✅ CLEAN ARCHITECTURE: Uses unchecked domain exceptions
public interface UserRepository {
    User findById(Long id); // Throws unchecked UserNotFoundException on missing records
}
```

## 🔴 Senior Level

### Why the Industry Moved to `RuntimeException`

Checked exceptions were Java's pioneering 1995 language experiment, but modern software engineering has largely abandoned them:
1. **Language Evolution:** C#, Kotlin, Scala, Go, and Rust deliberately omitted checked exceptions.
2. **Framework Alignment:** Spring, Hibernate, and Jakarta EE translate checked exceptions (like `SQLException`) into unchecked hierarchies (`DataAccessException`, `PersistenceException`).
3. **Reactive & Stream Compatibility:** Project Reactor (`Mono`/`Flux`) and Java Stream API lambdas (`Function<T, R>`) cannot throw checked exceptions without cumbersome boilerplate wrappers.

### When Checked Exceptions are Still Justified

Extend `java.lang.Exception` only in **public standalone SDKs and core utility libraries** where:
- The error represents a critical, unavoidable lifecycle event (e.g. thread interruption via `InterruptedException`).
- Forcing compile-time handling prevents silent data corruption in mission-critical hardware or financial transaction protocols.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Standard Rule:** Extend `RuntimeException` for 95%+ of application code (business domain errors, validation failures, REST APIs).
- **Checked Rule:** Extend `Exception` only when the caller can programmatically recover (e.g. retry, fallback) in low-level library code.
- **Abstraction Leaks:** Checked exceptions leak low-level technology concerns (`SQLException`) across interface layers.
- **Modern Ecosystem:** Spring, Kotlin, and Reactive Streams standardly use `RuntimeException`.
- **Performance Equality:** Both checked and unchecked exceptions have identical bytecode execution and stack trace capture overhead (~$1\text{--}5\,\mu\text{s}$).

**Common Follow-up Questions:**
- *"Why does Spring convert all JDBC `SQLException` instances into `DataAccessException`?"* → To insulate business logic from database vendor dependencies and eliminate repetitive `try-catch` boilerplate across service layers.
- *"Why do Kotlin and C# not have checked exceptions?"* → Language designers found that checked exceptions led to catch-and-ignore anti-patterns, interface signature pollution, and functional programming friction.
- *"If you convert a checked exception to an unchecked exception, what must you do?"* → Always preserve the original root cause by passing it to the constructor: `new ServiceException("Operation failed", cause)`.

**Red Flags (DO NOT Say):**
- ❌ *"Always extend `Exception` because checked exceptions are safer and better for business code."* (Causes signature pollution and abstraction leaks).
- ❌ *"Checked exceptions run slower in the JVM than unchecked exceptions."* (Both execute identical `athrow` bytecode instructions and have identical runtime overhead).
- ❌ *"Never create custom runtime exceptions; only use standard JDK exceptions."* (Domain-Driven Design requires semantic domain runtime exceptions).
