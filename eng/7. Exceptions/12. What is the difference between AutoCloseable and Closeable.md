# What is the difference between AutoCloseable and Closeable?

---

## 🟢 Junior Level

**`Closeable` is an I/O-specific sub-interface of `AutoCloseable`**:

```
                   java.lang.AutoCloseable (Java 7)
                             │
                             ▼
                   java.io.Closeable (Java 5, retrofitted in Java 7)
                             │
                 ┌───────────┴───────────┐
                 ▼                       ▼
          FileInputStream         BufferedReader
```

### Direct Comparison

| Feature | `java.io.Closeable` | `java.lang.AutoCloseable` |
|---|---|---|
| **Introduced In** | Java 5 | Java 7 |
| **Package** | `java.io` | `java.lang` (No imports needed) |
| **Exception Thrown** | `throws IOException` | `throws Exception` |
| **Domain Scope** | **Strictly I/O Streams** (`InputStream`, `Reader`) | **Universal Resources** (DB, Sockets, Locks) |
| **Idempotency** | **MANDATORY** by specification | **STRONGLY RECOMMENDED** by specification |

```java
// 1. Closeable: Restricted strictly to IO operations
public interface Closeable extends AutoCloseable {
    void close() throws IOException;
}

// 2. AutoCloseable: General-purpose language-level abstraction
public interface AutoCloseable {
    void close() throws Exception;
}
```

---

## 🟡 Middle Level

### The Idempotency Contract Nuance

- **`Closeable.close()` (Strict Invariant):** The Javadoc mandates: *"If the stream is already closed, then invoking this method has no effect."*
- **`AutoCloseable.close()` (Recommendation):** The Javadoc states: *"While this interface method is declared to throw Exception, implementers are strongly advised to declare more specific exceptions, or to throw no exception at all if the close operation cannot fail. It is also strongly advised to make the close operation idempotent."*

### Why `AutoCloseable` Throws `Exception`

`AutoCloseable` was designed to accommodate any resource in the Java ecosystem. For instance:
- `java.sql.Connection.close()` throws `SQLException`.
- If `AutoCloseable` had restricted `close()` to `IOException`, JDBC connections could not have implemented it without wrapping `SQLException`.

### Exception Narrowing in Custom Implementations

When implementing `AutoCloseable`, **always narrow or eliminate the `throws Exception` clause**:

```java
// ❌ BAD PRACTICE: Forces callers to catch generic Exception
public class SecurityContextResource implements AutoCloseable {
    @Override
    public void close() throws Exception { ... }
}

// ✅ CLEAN & IDIOMATIC: Omitting throws eliminates try-catch boilerplate!
public class SecurityContextResource implements AutoCloseable {
    @Override
    public void close() {
        SecurityContextHolder.clearContext();
    }
}
```

## 🔴 Senior Level

### Flushable Interaction & Buffered Streams

Many `Closeable` stream decorators (`BufferedWriter`, `BufferedOutputStream`, `GZIPOutputStream`) also implement **`java.io.Flushable`**:

```java
public class BufferedOutputStream extends FilterOutputStream implements Closeable, Flushable {
    @Override
    public void close() throws IOException {
        try {
            flush(); // Flushes internal byte buffer to disk/socket before closing
        } finally {
            out.close(); // Guarantees native handle disposal even if flush() fails
        }
    }
}
```
*Because Try-With-Resources closes streams in LIFO order, wrapping streams inside TWR guarantees that `flush()` executes before the underlying socket or physical file channel is severed.*

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Hierarchy:** `Closeable` extends `AutoCloseable` (introduced in Java 5, retrofitted in Java 7).
- **Package Location:** `Closeable` is in `java.io`; `AutoCloseable` is in `java.lang`.
- **Exception Signature:** `Closeable` throws `IOException`; `AutoCloseable` throws generic `Exception`.
- **Domain Scope:** `Closeable` is strictly for byte/char I/O; `AutoCloseable` is for any system resource (JDBC, locks, native memory).
- **Idempotency Rule:** `Closeable` strictly mandates idempotency; `AutoCloseable` strongly encourages it.
- **Exception Narrowing:** Always remove or narrow `throws Exception` when writing custom `AutoCloseable` implementations.

**Common Follow-up Questions:**
- *"Which interface should you implement when creating a custom transactional resource?"* → Implement `AutoCloseable`, narrowing `throws` to your specific domain exception or omitting it entirely.
- *"Why can a `Closeable` object be used inside a Try-With-Resources statement?"* → Because `Closeable` extends `AutoCloseable`, satisfying TWR's compiler type check.
- *"Is every `AutoCloseable` object an instance of `Closeable`?"* → No. For example, `java.sql.Connection` implements `AutoCloseable`, but does NOT implement `Closeable`.

**Red Flags (DO NOT Say):**
- ❌ *"AutoCloseable and Closeable are completely unrelated interfaces."* (`Closeable` is a direct sub-interface of `AutoCloseable`).
- ❌ *"AutoCloseable can only throw unchecked RuntimeExceptions."* (The interface method explicitly declares `throws Exception`).
- ❌ *"Closeable was created after AutoCloseable to fix its design flaws."* (`Closeable` was created in Java 5; `AutoCloseable` was added in Java 7 to generalize resource management).
