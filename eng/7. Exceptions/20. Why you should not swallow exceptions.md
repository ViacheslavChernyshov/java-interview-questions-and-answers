# Why you should not swallow exceptions?

---

## 🟢 Junior Level

**"Exception Swallowing"** (the Empty Catch Block anti-pattern) occurs when code intercepts an exception and performs no action—neither logging, rethrowing, rolling back state, nor alerting.

```java
// ❌ CATASTROPHIC ANTI-PATTERN: Exception Swallowing
try {
    paymentService.charge(order);
} catch (Exception e) {
    // Empty block: The system silently swallows the error!
}
// Execution proceeds as if payment succeeded, shipping unpaid goods!
```

### Why Exception Swallowing is Catastrophic
1. **Silent Data Inconsistency:** Partial operations commit, corrupting database records.
2. **Invisible Production Bugs:** Zero traces appear in ELK/Datadog logs; SRE teams cannot diagnose why orders fail.
3. **Wasted CPU Cycles:** The JVM still executes the expensive native `fillInStackTrace()` method on every exception.

## 🟡 Middle Level

### The 3 Severe Architecture Traps

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Architecture Layer                                     │ Impact of Swallowing Exceptions                        │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **1. Database Transactions**                           │ Catching `SQLException` prevents transaction rollback; │
  │                                                        │ half-updated records are committed to storage!         │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **2. Asynchronous Pipelines (`CompletableFuture`)**   │ Swallowing errors prevents completion stages like      │
  │                                                        │ `.exceptionally()` or `.handle()` from executing.      │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **3. Java Stream API Pipelines**                       │ Returning `null` on error corrupts stream downstream   │
  │                                                        │ collections with silent null pointer vulnerabilities.  │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### The Only Legitimate Exceptions to the Rule

If an exception is intentionally ignored, it **must adhere to strict coding invariants**:

#### 1. Restoring Thread Interruption
```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // ⚠️ MANDATORY: Restore the interrupted status flag!
    Thread.currentThread().interrupt();
    log.debug("Worker thread sleep interrupted, exiting loop.");
}
```

#### 2. Optional Best-Effort Caches (With Debug Logging)
```java
try {
    redisTemplate.opsForValue().set(key, value);
} catch (RedisConnectionException e) {
    // Cache failure is non-fatal to core business; log at DEBUG level:
    log.debug("Redis cache write bypassed due to connection glitch", e);
}
```

## 🔴 Senior Level

### Production Defense: Automated CI/CD Quality Gates

In enterprise engineering organizations, empty catch blocks should be **blocked at build time**:
- **SonarQube Quality Gate:** Enforce rule **`java:S1166`** (*"Exception handlers should preserve the original exception"*) and **`java:S2486`** (*"Generic exceptions should not be swallowed"*).
- **Metric-Driven Safety Nets:** If an optional exception must be swallowed, increment a Micrometer metric to detect hidden outages:

```java
try {
    metricService.push(metric);
} catch (Exception e) {
    Metrics.counter("telemetry.errors.swallowed", "type", e.getClass().getSimpleName()).increment();
    log.debug("Telemetry push dropped", e);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Catching an exception without logging, rethrowing, or handling state rollback.
- **Dangers:** Corrupted database state, silent system degradation, and phantom HTTP 200 responses.
- **CPU Waste:** Swallowed exceptions still incur full `fillInStackTrace()` CPU costs.
- **InterruptedException:** Swallowing `InterruptedException` destroys thread cancellation signals; always restore via `Thread.currentThread().interrupt()`.
- **CI/CD Quality Gates:** Use SonarQube (`java:S1166`) and Checkstyle to fail builds containing empty catch blocks.

**Common Follow-up Questions:**
- *"What happens if you swallow an exception inside a Spring `@Transactional` method?"* → Spring's transaction interceptor never intercepts the exception, causing the transaction to commit dirty, partially modified entity state!
- *"How should you handle an ignored exception in a test or cleanup method?"* → Name the catch parameter `ignored` (e.g. `catch (IOException ignored) {}`) to signal deliberate intent to IDE static analyzers, and include a comment explaining why.
- *"Why is swallowing exceptions in Java Streams particularly dangerous?"* → Catching and returning `null` inside `.map()` pollutes the stream with `null` references that trigger downstream `NullPointerException`s far away from the root cause.

**Red Flags (DO NOT Say):**
- ❌ *"I use empty catch blocks because I know the error won't happen."* (If it couldn't happen, the exception would never be thrown).
- ❌ *"Swallowing exceptions improves system performance by skipping error logs."* (Exception creation already burned CPU; hiding logs prevents diagnosing performance bottlenecks).
- ❌ *"Swallowing `InterruptedException` is safe as long as the loop exits."* (It resets thread state and breaks thread pool shutdown protocols).
