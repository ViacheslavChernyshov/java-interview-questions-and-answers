# What is an unchecked exception (Runtime Exception)?

---

## 🟢 Junior Level

An **Unchecked Exception** is any exception class extending from **`java.lang.RuntimeException`** (or `java.lang.Error`).

The Java compiler does **NOT enforce handling**: methods are not required to catch them or declare them via `throws`.

```
  java.lang.Throwable
    └── java.lang.Exception
          └── java.lang.RuntimeException  (⭐ Unchecked)
                ├── NullPointerException
                ├── IllegalArgumentException
                ├── IllegalStateException
                ├── IndexOutOfBoundsException
                ├── ArithmeticException
                └── ClassCastException
```

### Core Semantic Roles
1. **Programmer Defect:** Violations of API contracts, invalid arguments, division by zero, or null dereferences.
2. **Domain Business Conditions:** High-level application errors (`InsufficientFundsException`, `UserNotFoundException`) that bubble up to global handlers.

```java
// 1. Parameter validation violation
public void setDiscount(double discount) {
    if (discount < 0 || discount > 1.0) {
        throw new IllegalArgumentException("Discount must be between 0.0 and 1.0");
    }
    this.discount = discount;
}

// 2. Business domain runtime exception
public Order getOrder(Long id) {
    return orderRepository.findById(id)
        .orElseThrow(() -> new OrderNotFoundException("Order " + id + " does not exist"));
}
```

## 🟡 Middle Level

### The Fail-Fast Architectural Principle

Unchecked exceptions are the primary tool for implementing **Fail-Fast** software design:
- Rather than allowing a `null` or invalid argument to propagate across multiple service layers and silently corrupt database rows, fail immediately at the system boundary:

```java
public void transferMoney(AccountId source, AccountId target, BigDecimal amount) {
    Objects.requireNonNull(source, "Source account cannot be null");
    Objects.requireNonNull(target, "Target account cannot be null");
    if (amount.compareTo(BigDecimal.ZERO) <= 0) {
        throw new IllegalArgumentException("Transfer amount must be strictly positive");
    }
    // Safe to proceed with ledger operations
}
```

### Centralized Exception Handling in Spring Boot (`@RestControllerAdvice`)

Modern enterprise architectures never catch unchecked exceptions at intermediate Service layers. Instead, exceptions propagate up to a centralized global handler:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    public ProblemDetail handleNotFound(OrderNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Order Not Found");
        return problem;
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ProblemDetail handleBadRequest(IllegalArgumentException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, ex.getMessage());
    }
}
```

## 🔴 Senior Level

### Anti-Pattern: Exceptions as Control Flow

Using exceptions for regular business branching logic is a severe anti-pattern:

```java
// ❌ HORRIBLE ANTI-PATTERN: 100x-1000x slower due to JVM stack walking
public boolean isUserActive(Long userId) {
    try {
        User user = userService.getUser(userId); // Throws UserNotFoundException if missing
        return user.isActive();
    } catch (UserNotFoundException e) {
        return false;
    }
}

// ✅ CLEAN & HIGH-PERFORMANCE: Returns Optional or explicit boolean
public boolean isUserActive(Long userId) {
    return userService.findUser(userId)
        .map(User::isActive)
        .orElse(false);
}
```

### High-Throughput Optimization: Pre-Instantiated Stackless Singletons

In low-latency systems (e.g. rate limiters rejecting $50{,}000$ RPS), you can eliminate GC allocation and CPU stack-walking overhead by using pre-instantiated stackless singletons:

```java
public class RateLimitExceededException extends RuntimeException {
    public static final RateLimitExceededException INSTANCE = 
        new RateLimitExceededException("Rate limit quota exceeded");

    private RateLimitExceededException(String message) {
        // (message, cause, enableSuppression, writableStackTrace = false)
        super(message, null, false, false);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Subclass of `RuntimeException`; compiler does not require `try-catch` or `throws`.
- **Primary Uses:** Programming bugs (`NullPointerException`, `IndexOutOfBoundsException`) and domain exceptions (`UserNotFoundException`).
- **Fail-Fast:** Unchecked exceptions immediately halt invalid operations before state corruption occurs.
- **Enterprise Pattern:** Bubbles up to `@RestControllerAdvice` for RFC 9457 structured JSON error generation.
- **Control Flow Anti-Pattern:** Never use exceptions for normal conditional logic (use `Optional<T>` or boolean checks).
- **Performance Cost:** `fillInStackTrace()` is the main CPU bottleneck; use `writableStackTrace = false` for high-frequency signal exceptions.

**Common Follow-up Questions:**
- *"Why does Spring Data convert checked `SQLException` into unchecked `DataAccessException`?"* → To decouple business and service layers from JDBC-specific infrastructure dependencies and eliminate boilerplate `try-catch` blocks.
- *"Why is using exceptions for control flow bad?"* → Creating an exception forces the JVM to walk the entire thread stack frames (`fillInStackTrace()`), making it $100\times\text{--}1000\times$ slower than standard `if-else` branching.
- *"Can you declare an unchecked exception in a method's `throws` clause?"* → Yes. It is syntactically valid and serves as documentation (e.g. `public void parse() throws IllegalArgumentException`), but the compiler does not enforce caller handling.

**Red Flags (DO NOT Say):**
- ❌ *"Unchecked exceptions cannot be caught in a try-catch block."* (They can be caught like any other `Throwable`).
- ❌ *"Catching `RuntimeException` and doing nothing is fine for unhandled cases."* (Swallowing exceptions obscures catastrophic application bugs).
- ❌ *"Throwing an exception is just as fast as returning an `Optional`."* (Stack trace capture makes exception creation orders of magnitude slower).
