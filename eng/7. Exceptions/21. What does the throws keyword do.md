# What does the throws keyword do?

---

## 🟢 Junior Level

The **`throws`** keyword is declared in a method signature to specify which **Checked Exceptions** the method might propagate to its callers.

It enforces the compiler's **"Catch or Specify"** requirement: any code calling this method must either handle the exception inside a `try-catch` block or re-declare `throws` in its own signature.

```java
// Method specifies that it may throw checked exceptions:
public String readConfigFile(Path path) throws IOException, TimeoutException {
    return Files.readString(path);
}

// Calling method handles it:
public void init() {
    try {
        readConfigFile(Path.of("app.yml"));
    } catch (IOException | TimeoutException e) {
        log.warn("Using fallback configuration: {}", e.getMessage());
    }
}
```

### `throw` vs. `throws`
- **`throw` (Verb / Action):** Used inside a method body to instantiate and throw a specific exception object (`throw new IllegalArgumentException("Invalid");`).
- **`throws` (Noun / Clause):** Used in the method declaration header to declare the exception types that may escape (`public void run() throws IOException`).

## 🟡 Middle Level

### Method Overriding & The Liskov Substitution Principle (LSP)

When overriding a superclass method, the `throws` clause must strictly adhere to LSP:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Subclass Overriding Method Signature                   │ Compiler Result                                        │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ Declares the **same checked exceptions**               │ ✅ Allowed                                             │
  │ Declares **narrower / subclass checked exceptions**    │ ✅ Allowed (e.g. `FileNotFoundException` for `IOException`)│
  │ **Omits** checked exceptions completely                │ ✅ Allowed (Safer implementation)                      │
  │ Declares **new or broader checked exceptions**         │ ❌ COMPILATION ERROR (Violates LSP polymorphism)       │
  │ Declares any **unchecked exceptions** (`Runtime`)      │ ✅ Allowed (Compiler ignores unchecked exceptions)     │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Under the Hood: The `Exceptions` Bytecode Attribute

In compiled `.class` files, the `throws` list is stored in the method's metadata table as the **`Exceptions` attribute**:
- This attribute is parsed exclusively by the `javac` compiler during static compilation.
- The JVM runtime engine and bytecode verifier **completely ignore this attribute at runtime**; any method can execute the `athrow` bytecode opcode for any `Throwable` regardless of whether `throws` was declared.

## 🔴 Senior Level

### Generic Exception Signatures (`<E extends Throwable>`)

Java Generics allow defining methods that dynamically declare the exact exception type thrown by an underlying lambda parameter:

```java
@FunctionalInterface
public interface ThrowingCallable<T, E extends Throwable> {
    T call() throws E;
}

public class TransactionHelper {
    // Dynamically propagates whatever checked exception E the lambda throws:
    public static <T, E extends Throwable> T executeInTx(ThrowingCallable<T, E> action) throws E {
        startTransaction();
        try {
            return action.call();
        } finally {
            commitOrRollback();
        }
    }
}
```

### Binary Compatibility & Library API Evolution

> [!WARNING]
> Adding a checked exception to an existing public method signature is a **major breaking change**:
> - It breaks **Source Compatibility** (all downstream consumer projects fail to compile).
> - It breaks **Binary Compatibility** (compiled client `.jar` bytecode fails during dynamic linkage with `IncompatibleClassChangeError`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Declares checked exceptions in a method signature to enforce compile-time handling.
- **throw vs throws:** `throw` fires an exception instance; `throws` declares exception types in a signature.
- **LSP Rules:** Overriding methods can narrow or remove declared exceptions, but cannot introduce new or broader checked exceptions.
- **Bytecode Storage:** Stored in `.class` metadata as the `Exceptions` attribute (enforced only by `javac`, ignored by JVM runtime).
- **Public API Rule:** Never declare `throws Exception` in public libraries; it destroys type safety and forces clients to catch broad exceptions.

**Common Follow-up Questions:**
- *"Can you declare an unchecked `RuntimeException` in a `throws` clause?"* → Yes. It compiles and serves as documentation (JavaDoc), but the compiler does not enforce caller handling.
- *"Why does Reflection (`Method.invoke()`) bypass the compile-time `throws` requirement?"* → Because reflection operates dynamically at runtime, where the JVM executes `athrow` directly and wraps checked exceptions inside `InvocationTargetException`.
- *"Can an interface method declare no exceptions while an implementing class declares `throws IOException`?"* → No. That violates polymorphism; the subclass method would be wider than the interface contract.

**Red Flags (DO NOT Say):**
- ❌ *"The JVM throws an error at runtime if a method throws an exception not listed in its `throws` clause."* (The JVM has no runtime checks for checked exceptions; `throws` is enforced purely by `javac`).
- ❌ *"Subclasses can declare any new checked exceptions they want when overriding methods."* (Violates Liskov Substitution Principle).
- ❌ *"Using `throws Exception` on every method is a clean way to handle errors."* (Defeats the purpose of exception safety and pollutes caller code).
