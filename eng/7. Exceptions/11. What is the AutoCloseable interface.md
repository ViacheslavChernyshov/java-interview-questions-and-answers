# What is the AutoCloseable interface?

---

## 🟢 Junior Level

**`java.lang.AutoCloseable`** is a core functional interface introduced in Java 7 to support **Try-With-Resources (TWR)**.

It contains a single method contract:

```java
package java.lang;

public interface AutoCloseable {
    void close() throws Exception;
}
```

```java
// Example Custom Resource Implementation
public class FileProcessor implements AutoCloseable {
    @Override
    public void close() {
        System.out.println("File handles closed.");
    }
}

// Automatic cleanup upon block exit:
try (FileProcessor fp = new FileProcessor()) {
    fp.process();
} // close() invoked automatically!
```

### Why It Resides in `java.lang`
`AutoCloseable` is placed in `java.lang` (available globally without imports) because it is a **universal language-level abstraction** for any disposable resource (I/O streams, database pools, thread locks, native JNI pointers), not just I/O streams.

## 🟡 Middle Level

### The 3 Core Implementation Best Practices

1. **Narrow the Exception Signature:**
   The interface declares `throws Exception` to permit any implementation failure. Specific classes should narrow this to specific exceptions (e.g. `throws IOException`) or omit `throws` entirely if closing cannot fail:
   ```java
   public class ThreadLockResource implements AutoCloseable {
       @Override
       public void close() { // Omits `throws Exception`; callers require no try-catch!
           lock.unlock();
       }
   }
   ```
2. **Make `close()` Strictly Idempotent:**
   Calling `close()` multiple times must be completely safe:
   ```java
   private final AtomicBoolean isClosed = new AtomicBoolean(false);
   @Override
   public void close() {
       if (isClosed.compareAndSet(false, true)) {
           doRelease();
       }
   }
   ```
3. **Safe Sub-Resource Closing:**
   When a class encapsulates multiple inner resources, close them inside independent `try-finally` blocks to guarantee that failure in the first does not prevent disposal of the second.

## 🔴 Senior Level

### Garbage Collection vs. Native Operating System Descriptors

> [!IMPORTANT]
> The Java Garbage Collector only reclaims **JVM Heap Memory**. It has **zero awareness of native operating system resources** (file descriptors, sockets, epoll handles, GPU memory buffers).

If an application instantiates $2{,}000$ unclosed `FileInputStream` objects, the JVM may have gigabytes of free heap, but the operating system will crash with **`java.io.IOException: Too many open files`**.

### Safety Nets: `finalize()` Deprecation vs. `java.lang.ref.Cleaner` (Java 9+)

`Object.finalize()` was deprecated in Java 9 and marked for removal due to unpredictable execution, thread locking, and object resurrection hazards. Modern Java uses **`java.lang.ref.Cleaner`** as a non-blocking safety net:

```java
public class NativeBufferWrapper implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    // Static cleanup state must NOT hold a reference to the outer instance!
    private record CleanState(long nativePointer) implements Runnable {
        @Override
        public void run() {
            NativeMemory.free(nativePointer);
        }
    }

    private final Cleaner.Cleanable cleanable;

    public NativeBufferWrapper(long size) {
        long pointer = NativeMemory.allocate(size);
        this.cleanable = CLEANER.register(this, new CleanState(pointer));
    }

    @Override
    public void close() {
        cleanable.clean(); // Executes cleanup immediately and unregisters phantom ref
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Java 7 interface in `java.lang` enabling Try-With-Resources; single method `void close() throws Exception`.
- **Package Location:** In `java.lang` so any library component can implement it without dependencies.
- **Idempotency:** Javadoc strongly recommends that multiple `close()` calls produce no additional side-effects.
- **Native Handles:** GC cannot reclaim native OS descriptors; failing to call `close()` triggers `Too many open files` errors.
- **Signature Narrowing:** Always narrow `throws Exception` to specific checked exceptions or omit it entirely.
- **Safety Net:** `java.lang.ref.Cleaner` (Java 9+) is the modern phantom-reference fallback replacing deprecated `finalize()`.

**Common Follow-up Questions:**
- *"Why is `finalize()` deprecated in favor of `Cleaner`?"* → `finalize()` caused thread starvation, deadlocks, object resurrection vulnerabilities, and unpredictable GC delays; `Cleaner` uses clean phantom references with isolated cleaning threads.
- *"Why should you avoid throwing `Exception` from custom `close()` methods?"* → Declaring `throws Exception` forces callers using manual `try-catch` to handle generic `Exception`, defeating compile-time checked exception safety.
- *"Can an `AutoCloseable` resource be used across multiple threads?"* → Yes, but its `close()` implementation must be made thread-safe and idempotent using atomic state primitives (`AtomicBoolean`).

**Red Flags (DO NOT Say):**
- ❌ *"The Garbage Collector will close files automatically when objects are garbage collected."* (GC reclaims heap memory, leaving OS file descriptors open).
- ❌ *"AutoCloseable was introduced in Java 5."* (It was introduced in Java 7; `Closeable` was introduced in Java 5).
- ❌ *"Custom `close()` methods must always throw `Exception`."* (Subclasses should narrow or eliminate the `throws` clause).
