# Can you rethrow an exception?

---

## 🟢 Junior Level

**Yes. An exception caught inside a `catch` block can be rethrown to calling methods using the `throw e;` statement.**

```java
public void executeOrder(Long orderId) {
    try {
        paymentService.charge(orderId);
    } catch (PaymentException e) {
        log.error("Payment failure for orderId={}, alerting operations", orderId, e);
        // Rethrows the exact same exception up the call stack:
        throw e; 
    }
}
```

### Why Rethrow an Exception?
1. **Side-Effect Interception:** Logging error diagnostics or updating metrics before bubbling up.
2. **Transaction Rollback:** Triggering manual cleanups or rollbacks (`connection.rollback()`).
3. **Exception Translation:** Wrapping low-level errors into high-level business domain exceptions.

---

## 🟡 Middle Level

### Stack Trace Preservation Guarantee

When you execute `throw e;`, **the Java Virtual Machine does NOT modify the original stack trace**:
- The stack trace still points to the exact class, file, and line number where the exception was originally instantiated.

```java
// Original point of error:
public void step1() {
    throw new IllegalStateException("Crash at line 10"); // Instantiated here
}

public void step2() {
    try {
        step1();
    } catch (IllegalStateException e) {
        throw e; // Rethrown at line 18: Stack trace STILL points to line 10!
    }
}
```

### Overwriting the Stack Trace: `fillInStackTrace()`

If you explicitly want the stack trace to reflect the rethrow location instead of the origin:

```java
catch (RuntimeException e) {
    // ⚠️ Overwrites the call stack frames, erasing the original origin point!
    throw (RuntimeException) e.fillInStackTrace();
}
```

## 🔴 Senior Level

### Java 7+ Precise Rethrow

Prior to Java 7, catching `Exception` and rethrowing it forced the enclosing method to declare `throws Exception`:

```java
// Java 7+ Precise Rethrow:
public void process() throws IOException, SQLException { // Precise checked types declared!
    try {
        executeDatabaseAndNetworkWork();
    } catch (Exception e) {
        // javac compiler statically analyzes the `try` block and infers
        // that `e` can ONLY be IOException or SQLException:
        log.warn("Intercepting failure during execution");
        throw e; // Compiles without requiring `throws Exception`!
    }
}
```

### Spring Framework `@Transactional` Rollback Trap

> [!CAUTION]
> By default, Spring's `@Transactional` interceptor **rolls back ONLY for unchecked exceptions (`RuntimeException` and `Error`)**.
> - If you catch and rethrow a **checked exception** (`throw new IOException()`), Spring commits the transaction!
> - To force rollback on checked exceptions:
>   `@Transactional(rollbackFor = Exception.class)`

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Catching an exception, performing intermediate actions (logging/rollback), and propagating it via `throw e;`.
- **Stack Trace:** `throw e;` preserves the original instantiation line and frame history unchanged.
- **Precise Rethrow:** Java 7+ type inference allows catching `Exception` and rethrowing without widening the method's `throws` clause.
- **Spring Transactions:** By default, Spring rolls back transactions only on unchecked `RuntimeException`; configure `rollbackFor = Exception.class` for checked exceptions.
- **fillInStackTrace:** Calling `e.fillInStackTrace()` resets the stack trace to the rethrow site, discarding the original failure origin.

**Common Follow-up Questions:**
- *"What is the difference between `throw e;` and `throw new ServiceException(e);`?"* → `throw e;` propagates the identical exception instance without changing its type; `throw new ...` wraps it into a new domain exception layer attaching the original as `cause`.
- *"Is an empty catch-and-rethrow `catch (Exception e) { throw e; }` bad practice?"* → Yes. It adds zero value, consumes extra CPU cycles for Exception Table lookups, and clutters the codebase.
- *"What happens if a method inside the `catch` block throws a new exception before `throw e;` executes?"* → The new exception is thrown, completely masking and dropping the original exception `e`.

**Red Flags (DO NOT Say):**
- ❌ *"Executing `throw e;` updates the exception's stack trace to the current line."* (`throw e;` preserves the original origin; only `fillInStackTrace()` updates it).
- ❌ *"Spring `@Transactional` rolls back on all checked and unchecked exceptions by default."* (Default rollback occurs only on `RuntimeException` and `Error`).
- ❌ *"Rethrowing an exception creates a new object in heap memory."* (It rethrows the exact same object reference).
