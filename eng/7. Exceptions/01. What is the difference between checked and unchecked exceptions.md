# What is the difference between checked and unchecked exceptions?

---

## 🟢 Junior Level

In the Java platform, all exceptional events extend from **`java.lang.Throwable`**. They are fundamentally categorized into two categories:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │              Checked Exceptions                        │             Unchecked Exceptions (Runtime)             │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Subclasses of `Exception` (except `RuntimeException`)│ • Subclasses of `RuntimeException` and `Error`         │
  │ • **Compiler ENFORCES handling** via `try-catch`       │ • **Compiler DOES NOT enforce handling**               │
  │   or `throws` method signature declaration             │                                                        │
  │ • Represents **recoverable external failures**         │ • Represents **programmer bugs** or domain violations  │
  │ • Examples: `IOException`, `SQLException`,             │ • Examples: `NullPointerException`,                    │
  │   `ClassNotFoundException`, `InterruptedException`     │   `IllegalArgumentException`, `ArithmeticException`    │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// 1. Checked Exception: Compilation fails without `throws` or `try-catch`
public void readFile(String path) throws IOException {
    Files.readAllLines(Path.of(path));
}

// 2. Unchecked Exception: Handled or thrown optionally
public int calculateTax(int income) {
    if (income < 0) {
        throw new IllegalArgumentException("Income cannot be negative");
    }
    return income / 10;
}
```

## 🟡 Middle Level

### The Compile-Time Illusion: JVM Runtime Mechanics

> [!IMPORTANT]
> The JVM runtime has **zero concept of checked vs. unchecked exceptions**. 
> - The distinction is purely a compile-time syntactic rule enforced by `javac`.
> - In Java bytecode, every exception is thrown via the exact same opcode: **`athrow`**.

### Architectural Evolution: Why Modern Frameworks Prefer Unchecked

1. **Functional Programming & Streams Incompatibility:** Java's standard functional interfaces (`Function<T, R>`, `Predicate<T>`, `Supplier<T>`) do not declare `throws Exception`. Checked exceptions cannot be thrown inside Stream pipelines or `CompletableFuture` stages without messy wrapping.
2. **Signature Pollution:** Adding a checked exception to a low-level DAO requires modifying method signatures across every intermediate Service and Controller layer up the call stack.
3. **Layer Boundary Exception Translation:** Best practice dictates catching infrastructure checked exceptions at DAO/adapter boundaries and rethrowing semantic unchecked domain exceptions:

```java
public User findById(Long id) {
    try {
        return jdbcTemplate.queryForObject("SELECT * FROM users WHERE id = ?", rowMapper, id);
    } catch (DataAccessException e) {
        // Translate low-level checked/data exception into high-level domain runtime exception
        throw new UserNotFoundException("User not found for id: " + id, e);
    }
}
```

## 🔴 Senior Level

### Sneaky Throws via Generic Type Erasure

Because the JVM does not verify checked exception signatures at runtime, generic type erasure allows throwing checked exceptions **without declaring `throws`**:

```java
public class SneakyThrower {
    @SuppressWarnings("unchecked")
    public static <E extends Throwable> void sneakyThrow(Throwable t) throws E {
        throw (E) t; // javac erases type parameter `E` to `Throwable` at runtime!
    }

    public static void runUnchecked() {
        // Throws checked IOException without needing a `throws IOException` signature!
        sneakyThrow(new IOException("Disk read failed"));
    }
}
```
*Lombok's `@SneakyThrows` annotation generates this exact bytecode transformation under the hood.*

### High-Throughput Optimization: Stackless Exceptions

In high-frequency low-latency systems (e.g. trading engines, 100k+ RPS gateways), the most computationally expensive operation in throwing an exception is **`Throwable.fillInStackTrace()`**, which walks the JVM execution call frames:

```java
public class FastSignalException extends RuntimeException {
    public FastSignalException(String message) {
        // (message, cause, enableSuppression, writableStackTrace = false)
        super(message, null, false, false);
    }
}
```
*Disabling `writableStackTrace` speeds up exception instantiation by $10\times\text{--}50\times$, generating near-zero GC memory pressure.*

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Checked:** Subclasses of `Exception` (excluding `RuntimeException`); compiler enforces `try-catch` or `throws`.
- **Unchecked:** Subclasses of `RuntimeException` (and `Error`); compiler enforces nothing.
- **JVM Level:** All exceptions are identical in bytecode (`athrow`); checked enforcement is strictly a `javac` compiler feature.
- **Language Design:** Kotlin, Scala, C#, and Go abandoned checked exceptions due to signature pollution and FP/lambda incompatibility.
- **Sneaky Throws:** Bypasses `javac` checks via generic type erasure (`<E extends Throwable>`).
- **Highload Performance:** `fillInStackTrace()` is the primary CPU cost of exceptions; disable it via `super(msg, null, false, false)` for high-frequency control flow signals.

**Common Follow-up Questions:**
- *"Why can't you throw a checked exception directly inside a Java 8 Stream `map()`?"* → Because `java.util.function.Function` does not declare `throws Throwable` in its `apply()` method signature.
- *"What is Exception Translation?"* → The pattern of catching low-level infrastructure exceptions (`SQLException`) at layer boundaries and wrapping them into semantic unchecked domain exceptions (`DatabaseConnectionException`).
- *"How does Lombok's `@SneakyThrows` work?"* → It uses generic type erasure to trick the `javac` compiler into emitting an `athrow` instruction for checked exceptions without generating compilation errors.

**Red Flags (DO NOT Say):**
- ❌ *"The JVM verifies checked exception types at runtime during bytecode execution."* (Only the `javac` compiler checks them; the JVM treats all `Throwable` objects identically).
- ❌ *"Checked exceptions should be used for all custom business errors."* (Modern enterprise architecture uses unchecked domain exceptions handled via `@ControllerAdvice`).
- ❌ *"Unchecked exceptions are slower than checked exceptions."* (Both execute identical bytecode and have identical runtime performance characteristics).
