# What is a checked exception and when to use it?

---

## 🟢 Junior Level

A **Checked Exception** is any subclass of `java.lang.Exception` (excluding `java.lang.RuntimeException`).

The Java compiler enforces the **"Catch or Specify" requirement**: any method that can encounter a checked exception must either:
1. Handle it locally inside a **`try-catch`** block, OR
2. Declare it explicitly in its method signature using the **`throws`** keyword.

```java
// 1. Specify via `throws`
public String readConfigFile(Path path) throws IOException {
    return Files.readString(path);
}

// 2. Catch locally
public void loadConfig() {
    try {
        String content = readConfigFile(Path.of("app.json"));
    } catch (IOException e) {
        log.warn("Config file missing, falling back to defaults: {}", e.getMessage());
        useDefaultConfig();
    }
}
```

### When to Use Checked Exceptions
According to standard Java design philosophy, use a checked exception when a condition is:
1. **Anticipated & Environmental:** External failure outside program control (file missing, database unavailable, network timeout).
2. **Actionable & Recoverable:** The calling code can take a meaningful corrective action (fall back to cache, retry with exponential backoff).

## 🟡 Middle Level

### Method Overriding & The Liskov Substitution Principle (LSP)

In Java inheritance, method overriding rules for checked exceptions strictly follow LSP:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Overriding Method in Subclass                          │ Compiler Validity                                      │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ Declares the **same checked exception**                │ ✅ **Allowed** (`throws IOException`)                  │
  │ Declares a **narrower subclass exception**             │ ✅ **Allowed** (`throws FileNotFoundException`)        │
  │ **Omits** the checked exception completely             │ ✅ **Allowed** (Subclass method is strictly safer)     │
  │ Declares **new or broader checked exceptions**         │ ❌ **COMPILATION ERROR** (Violates LSP polymorphism)   │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Functional Programming Friction (Lambdas & Stream API)

Standard Java functional interfaces (`Function<T, R>`, `Predicate<T>`, `Supplier<T>`) do not declare checked exceptions in their method signatures:

```java
// ❌ Compilation Error: Unhandled exception type IOException
List<String> lines = filePaths.stream()
    .map(path -> Files.readString(path))
    .toList();

// ✅ Solution: Wrap in a standard Unchecked Exception (e.g. UncheckedIOException)
List<String> lines = filePaths.stream()
    .map(path -> {
        try {
            return Files.readString(path);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    })
    .toList();
```

## 🔴 Senior Level

### Binary Compatibility & Library API Evolution

In enterprise library design, **adding a checked exception to an existing public method is a breaking change**:
- It breaks **Source Compatibility:** All client code calling that method will fail to compile.
- It breaks **Binary Compatibility:** Existing compiled `.jar` bytecode running on newer runtime versions will throw `IncompatibleClassChangeError` during link-time verification.

### The Special Case of `InterruptedException`

`InterruptedException` is one of the few universally praised checked exceptions in the standard library because it prevents concurrent threads from ignoring cancellation requests:

```java
public void runWorkerTask() {
    try {
        blockingQueue.take();
    } catch (InterruptedException e) {
        // ⚠️ CRITICAL SENIOR RULE: Restore the thread's interrupted status!
        Thread.currentThread().interrupt();
        log.info("Worker thread interrupted during task polling, initiating clean shutdown...");
        cleanupAndExit();
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Subclass of `Exception` (except `RuntimeException`); compiler enforces `try-catch` or `throws`.
- **Criteria for Use (Effective Java):** Condition is environmental, anticipated, recoverable, and actionable by the caller.
- **LSP Overriding Rules:** Overriding methods can omit or narrow checked exceptions, but cannot declare broader or new checked exceptions.
- **Lambda Incompatibility:** Functional interfaces cannot throw checked exceptions; wrap them in `UncheckedIOException` or domain runtime exceptions.
- **Library Impact:** Adding a checked exception to an existing public API is a breaking change.
- **Thread Interruption:** Always restore interrupt status via `Thread.currentThread().interrupt()` when catching `InterruptedException`.

**Common Follow-up Questions:**
- *"Why does `Files.lines()` throw `UncheckedIOException` instead of `IOException`?"* → Because `Files.lines()` returns a `Stream<String>`, and Streams evaluate lazily inside functional interfaces that cannot declare checked exceptions.
- *"Can a subclass method remove a `throws IOException` declared in the parent interface?"* → Yes. Removing or narrowing exceptions makes the implementation more specific and safer, which adheres to Liskov Substitution.
- *"Why did modern languages (Kotlin, Scala, C#) discard checked exceptions?"* → Checked exceptions cause severe signature pollution across architectural layers and introduce immense friction with functional and reactive programming.

**Red Flags (DO NOT Say):**
- ❌ *"I declare `throws Exception` on all my methods so I never have to write try-catch."* (Destroys method contracts and forces callers to catch generic `Exception`).
- ❌ *"Subclasses can throw any checked exception they want."* (Violates polymorphic contracts; subclasses cannot add new checked exceptions).
- ❌ *"Swallowing `InterruptedException` with an empty catch block is safe."* (Silently destroys thread cancellation signals, causing thread pool leaks).
