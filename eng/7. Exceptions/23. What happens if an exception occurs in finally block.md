# What happens if an exception occurs in finally block?

---

## 🟢 Junior Level

If an exception is thrown inside a `finally` block while an exception from the `try` block is already in flight, **the `finally` exception completely overwrites and masks the original `try` exception**.

The original `try` exception is permanently discarded and will not appear anywhere in logs or stack traces:

```java
public void demonstrateShadowing() {
    try {
        throw new SQLException("Database connection timed out"); // Original primary failure
    } finally {
        throw new NullPointerException("NPE during resource cleanup"); // Secondary failure
    }
}
```

```
Exception in thread "main" java.lang.NullPointerException: NPE during resource cleanup
    at com.example.Demo.demonstrateShadowing(Demo.java:6)
    (The SQLException is completely GONE!)
```

---

## 🟡 Middle Level

### The JVM Stack Frame Mechanism (Why Shadowing Happens)

1. The `try` block throws Exception $A$ (`SQLException`).
2. The JVM sets Exception $A$ in the thread's pending exception register and pauses stack unwinding to execute the `finally` block.
3. The `finally` block encounters an error and throws Exception $B$ (`NullPointerException`).
4. The JVM **overwrites the pending exception register with Exception $B$**.
5. The thread resumes unwinding using Exception $B$. Exception $A$ becomes unreachable and is garbage collected.

### The Return Masking Variant

A similar silent masking bug occurs if a `finally` block executes a `return` statement:

```java
public int calculate() {
    try {
        throw new IllegalStateException("Calculation failed");
    } finally {
        return 42; // ⚠️ SILENTLY SWALLOWS the exception and returns 42!
    }
}
```

## 🔴 Senior Level

### Cascade Resource Leaking in Legacy `finally` Blocks

Prior to Java 7, sequentially closing multiple resources inside a single `finally` block was a major source of production memory and file descriptor leaks:

```java
// ❌ DANGEROUS LEGACY ANTI-PATTERN:
finally {
    if (res1 != null) res1.close(); // If this throws IOException...
    if (res2 != null) res2.close(); // ...this line is NEVER REACHED! res2 LEAKS!
    if (res3 != null) res3.close(); // ...this line is NEVER REACHED! res3 LEAKS!
}
```

### The Solution: Try-With-Resources (`addSuppressed`)

In modern Java, **Try-With-Resources eliminates exception shadowing**:
- The `try` block exception remains the **Primary Exception**.
- Any exceptions thrown during `.close()` are attached as **Suppressed Exceptions**:

```java
try (Connection conn = dataSource.getConnection();
     Statement stmt = conn.createStatement()) {
    throw new SQLException("Primary Query Failure");
}
```
```
java.sql.SQLException: Primary Query Failure
    at com.bank.Service.query(Service.java:24)
    Suppressed: java.sql.SQLException: Socket closed during cleanup
        at com.bank.Connection.close(Connection.java:88)
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Primary Effect:** Exception from `finally` overwrites and destroys the original exception from `try` (Exception Shadowing).
- **Return Masking:** A `return` statement in `finally` completely swallows any active exception thrown in `try`.
- **Resource Leaks:** An exception in `finally` halts execution of remaining cleanup lines, leaking native resources.
- **Java 7 Solution:** Use Try-With-Resources; it preserves the `try` error as primary and attaches closing errors via `addSuppressed()`.

**Common Follow-up Questions:**
- *"How can you inspect suppressed exceptions in Java code?"* → Call `e.getSuppressed()`, which returns an array of `Throwable[]` objects.
- *"If you must use legacy `finally`, how should multiple resources be closed safely?"* → Enclose every `.close()` invocation in its own isolated `try-catch` block inside `finally`.
- *"Does a `return` in `finally` trigger a compile error in `javac`?"* → No, it compiles cleanly, but static analyzers (SonarQube rule `java:S1143`) flag it as a critical blocker.

**Red Flags (DO NOT Say):**
- ❌ *"The JVM combines both exceptions into a single compound exception automatically in finally."* (Only Try-With-Resources does this via suppressed exceptions; raw `finally` obliterates the first).
- ❌ *"Throwing an exception in `finally` is a good way to signal cleanup errors."* (It permanently wipes out the root cause that triggered cleanup).
- ❌ *"Putting a return statement in `finally` is standard practice for setting default return values."* (It silently suppresses unhandled exceptions).
