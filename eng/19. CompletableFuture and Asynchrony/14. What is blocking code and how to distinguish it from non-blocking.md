# What is Blocking Code and How to Distinguish It from Non-Blocking?

---

## 🟢 Junior Level

The distinction between **blocking** and **non-blocking** code centers on what happens to the underlying **OS worker thread** while waiting for a response:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🛑 BLOCKING CODE (Thread-Parking)                        │ 🚀 NON-BLOCKING CODE (Event-Driven / Reactive)          │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • The OS thread is **frozen / parked** in kernel space. │ • The OS thread **immediately returns** after initiating│
  │ • Consumes ~1MB of RAM while doing **0% CPU work**.     │   the operation.                                        │
  │ • Cannot process any other requests until data arrives. │ • Freely processes thousands of other concurrent tasks. │
  │ • Examples: `Thread.sleep()`, `future.get()`, JDBC.     │ • Examples: `sendAsync()`, NIO, `CompletableFuture`.    │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
// 🛑 BLOCKING: Thread freezes until HTTP response finishes:
HttpResponse<String> response = httpClient.send(request, BodyHandlers.ofString());

// 🚀 NON-BLOCKING: Thread immediately continues; callback executes when packets arrive:
httpClient.sendAsync(request, BodyHandlers.ofString())
    .thenAccept(res -> System.out.println("Payload: " + res.body()));
```


## 🔴 Senior Level

### OS-Level Kernel Mechanics: Blocking vs. Non-Blocking I/O

```
  1. BLOCKING I/O (Linux `read()` Syscall):
     [Java OS Thread] ──(Syscall `read()`)──► [Linux Kernel] ──(Thread enters TASK_UNINTERRUPTIBLE / sleep)
                                                    │
                                             (Data arrives on NIC)
                                                    │
     [Java OS Thread] ◄──(Context Switch / Wakeup)──┘

  2. NON-BLOCKING I/O (Linux `epoll` / Java NIO):
     [Java Event Loop] ──(Registers socket with `epoll_ctl`)──► Returns immediately!
                                                                     │
     [Java Event Loop] ◄──(Pulls ready events via `epoll_wait`)──────┘ (Processes 10,000 sockets on 1 thread!)
```

#### The Java 21 Virtual Threads Transformation

In **Java 21 Virtual Threads (Project Loom)**, when a virtual thread performs a blocking I/O operation (like `InputStream.read()` or JDBC), the JVM automatically **unmounts** the virtual thread from its underlying OS carrier thread, allowing the carrier thread to execute other virtual threads. This provides non-blocking throughput with simple blocking imperative syntax!

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Blocking:** The OS thread enters a waiting state (`BLOCKED`/`WAITING`), consuming memory and unable to process other tasks until an external I/O event finishes.
- **Non-Blocking:** The thread registers a completion handler and immediately returns to process other work, handled by OS event loops (`epoll`/`kqueue`).
- **Classic Blocking Culprits:** `Thread.sleep()`, `Future.get()`, `CompletableFuture.join()`, standard JDBC queries, `RestTemplate`, and `InputStream.read()`.
- **Non-Blocking Tools:** Java NIO, `CompletableFuture` callback pipelines, Java 11 `HttpClient.sendAsync()`, R2DBC, Spring `WebClient`.
- **Automated Detection:** Use **BlockHound** in test suites to catch accidental blocking calls on event loops.

**Common Follow-up Questions:**
- *"Is calling `.join()` inside a CompletableFuture pipeline considered blocking?"* → Yes! Calling `.join()` blocks the worker thread that is executing the pipeline; always use `.thenApply` or `.thenCompose` to process results non-blockingly.
- *"How does Java 21 Project Loom change the blocking vs non-blocking equation?"* → Virtual threads allow writing standard blocking code while the JVM transparently unmounts them from carrier threads, achieving reactive scalability without complex asynchronous callback chains.
- *"Is CPU-intensive code considered blocking?"* → No, CPU-intensive code is *active computation*, not blocked waiting on I/O. However, long CPU tasks should be isolated to a dedicated thread pool to avoid starving event-driven dispatchers.

**Red Flags (DO NOT Say):**
- ❌ *"Non-blocking code always runs faster on a single request than blocking code."* (Non-blocking code provides higher concurrent *throughput*, but may have slightly higher individual latency due to event loop scheduling).
- ❌ *"CompletableFuture makes any blocking JDBC query automatically non-blocking."* (Wrapping a blocking call in `supplyAsync()` just offloads the block to another thread; the thread still blocks!).
- ❌ *"Thread.sleep() is fine inside CompletableFuture callbacks."* (Freezes the worker thread; use a scheduled executor or non-blocking delays).
