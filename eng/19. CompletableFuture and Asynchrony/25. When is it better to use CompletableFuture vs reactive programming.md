# When is It Better to Use CompletableFuture vs Reactive Programming?

---

## 🟢 Junior Level

The core difference between `CompletableFuture` and Reactive Programming (e.g. **Project Reactor / WebFlux** or **RxJava**) comes down to **cardinality (how many items are produced)**:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 📦 `CompletableFuture` — Discrete Single-Value Promise  │ 🌊 Reactive Programming (`Flux` / `Flowable`) — Stream  │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Produces **0 or 1 value** (Scalar result).            │ • Produces **0 to $\mathbf{N}$ (unbounded)** items.     │
  │ • Ideal for **discrete RPC / HTTP calls** and           │ • Ideal for **continuous event streams** (WebSockets,   │
  │   point-to-point scatter-gather tasks.                  │   Kafka feeds, SSE, real-time telemetry).               │
  │ • **Zero external dependencies** (Standard JDK).        │ • Requires reactive libraries & reactive drivers (R2DBC)│
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
// 1. CompletableFuture (1 Request -> 1 Response):
CompletableFuture<User> userFuture = userClient.fetchUserAsync(userId);

// 2. Project Reactor (Continuous Stream of Events):
Flux<StockPrice> stockStream = stockMarketClient.streamLivePrices("GOOG");
stockStream.subscribe(price -> System.out.println("Live Price: " + price));
```

## 🟡 Middle Level

### The 5 Architectural Dimensions

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Dimension                    │ `CompletableFuture`          │ Reactive Programming (Reactor / WebFlux)         │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. Data Cardinality**      │ Single item ($0 \dots 1$)    │ Stream of items ($0 \dots \infty$)               │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **2. Backpressure Support**  │ 🔴 **NONE** (Buffer/OOM risk)│ 🟢 **NATIVE** (`request(n)` push-pull flow)      │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **3. Operator Richness**     │ ~50 basic pipeline methods   │ ~300+ operators (`window`, `buffer`, `sample`)   │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **4. Learning Curve**        │ 🟢 Low (Standard Java 8)     │ 🔴 Steep (Reactive mindset shift)                │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **5. Debugging & Tracing**   │ 🟢 Standard stack traces     │ 🔴 Inverted stacks; requires `Hooks.onOperator`  │
  └──────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### Why Backpressure Dictates the Choice

In `CompletableFuture`, if an upstream producer pushes 10,000 tasks/second into a thread pool and the downstream consumer only processes 1,000 tasks/second, the task queue grows unbounded until the JVM crashes with **`OutOfMemoryError`**.

In **Reactive Streams (`Flux`)**, the consumer signals its demand (`request(100)`), preventing the fast producer from overwhelming system memory:

```java
// Reactive Backpressure: Consumer only requests 5 items at a time:
eventFlux.subscribe(new BaseSubscriber<>() {
    @Override protected void hookOnSubscribe(Subscription s) { request(5); }
    @Override protected void hookOnNext(Event value) {
        process(value);
        request(1); // 👈 Pulls 1 more item as capacity becomes available!
    }
});
```

## 🔴 Senior Level

### The Java 21 Virtual Threads Paradigm Shift

Before Java 21, teams adopted reactive frameworks primarily to avoid OS thread starvation during high-concurrency I/O.

With **Java 21 Virtual Threads (Project Loom)**, the need for complex reactive code is drastically reduced for 90% of standard web services:

```
  ┌──────────────────────────────────────────────────────────┬──────────────────────────────────────────────────────────┐
  │ ❌ Complex Reactive WebFlux (Java 8 - 17)                │ 🏆 Java 21 Virtual Threads + CompletableFuture           │
  ├──────────────────────────────────────────────────────────┼──────────────────────────────────────────────────────────┤
  │ • Must rewrite entire stack (R2DBC, WebFlux, Mono/Flux). │ • Write simple imperative code or standard               │
  │ • Stack traces are unreadable across thread hops.        │   `CompletableFuture` pipelines.                         │
  │ • ThreadLocal contexts (MDC/Security) break easily.      │ • Millions of cheap virtual threads unmount on I/O.      │
  └──────────────────────────────────────────────────────────┴──────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`CompletableFuture`:** Use for **single-value** asynchronous tasks ($0 \dots 1$), microservice scatter-gather, and discrete RPCs. No external dependencies.
- **Reactive (Reactor/RxJava):** Use for **multi-value event streams** ($0 \dots \infty$), WebSockets, Server-Sent Events, and scenarios requiring **Backpressure**.
- **Backpressure:** `CompletableFuture` has NO backpressure; Reactive Streams enforces consumer-driven rate regulation.
- **Java 21 Impact:** Virtual Threads make standard imperative/CF code as scalable as Reactive for standard CRUD and REST aggregation.

**Common Follow-up Questions:**
- *"Can you convert a `CompletableFuture` to a Project Reactor `Mono`?"* → Yes: `Mono.fromFuture(completableFuture)` and `mono.toFuture()`.
- *"Why is debugging Reactive code harder than CompletableFuture?"* → Reactive pipelines separate assembly time from execution time; exceptions thrown on Netty event loops produce detached stack traces with hundreds of internal reactor frames.
- *"When is Reactive programming still mandatory in Java 21?"* → For continuous streaming protocols (WebSocket live feeds, SSE, Kafka streaming) and complex event processing operators (time-windowed tumbling aggregations).

**Red Flags (DO NOT Say):**
- ❌ *"CompletableFuture is obsolete; always use Spring WebFlux and Project Reactor for everything."* (WebFlux adds immense complexity; CF + Virtual Threads is preferred for discrete RPCs).
- ❌ *"CompletableFuture supports backpressure natively."* (CompletableFuture has zero backpressure mechanisms).
- ❌ *"Reactive streams are always faster than CompletableFuture."* (Reactive frameworks add object allocation and operator overhead; their advantage is high concurrency under I/O bottlenecks).
