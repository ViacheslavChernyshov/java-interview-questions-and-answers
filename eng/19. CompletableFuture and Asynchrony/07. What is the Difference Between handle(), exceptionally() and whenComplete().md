# What is the Difference Between handle(), exceptionally() and whenComplete()?

---

## 🟢 Junior Level

`handle()`, `exceptionally()`, and `whenComplete()` are the three core methods for processing errors and lifecycle completions in `CompletableFuture`:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 1. `exceptionally()` ➔ CATCH block (Executes ONLY on error; returns fallback of SAME type $T$).   │
  │ 2. `handle()`        ➔ TRY/CATCH transformation (ALWAYS executes; can return a NEW type $U$).      │
  │ 3. `whenComplete()`  ➔ FINALLY block for telemetry (ALWAYS executes; CANNOT alter value or error). │
  └───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

```java
CompletableFuture<Integer> cf = CompletableFuture.supplyAsync(() -> 10 / 0);

// 1. exceptionally: Catches ArithmeticException and returns fallback 0:
cf.exceptionally(ex -> 0); // Returns CompletableFuture<Integer> (value: 0)

// 2. handle: Always executes; can transform error or result into a String:
cf.handle((res, ex) -> ex != null ? "Failed: " + ex.getMessage() : "Success: " + res); // Returns CF<String>

// 3. whenComplete: Side-effect observer (logging); error continues down the pipeline:
cf.whenComplete((res, ex) -> {
    if (ex != null) log.error("Calculation failed", ex);
}); // Returns CompletableFuture<Integer> (still in EXCEPTION state!)
```

## 🟡 Middle Level

### The Definitive Comparison Matrix

```
  ┌──────────────────────────────┬────────────────────────┬────────────────────────┬────────────────────────┬────────────────────────┐
  │ Method                       │ When Does It Run?      │ Input Functional Type  │ Can It Change Type?    │ Can It Swallow Errors? │
  ├──────────────────────────────┼────────────────────────┼────────────────────────┼────────────────────────┼────────────────────────┤
  │ **`exceptionally`**          │ **Only on Error**      │ `Function<Throwable, T>`│ 🔴 No (Returns $T$)   │ 🟢 **Yes** (Recovers)  │
  ├──────────────────────────────┼────────────────────────┼────────────────────────┼────────────────────────┼────────────────────────┤
  │ **`handle`**                 │ **Always**             │ `BiFunction<T, Th, U>` │ 🟢 **Yes** ($T \to U$) │ 🟢 **Yes** (Recovers)  │
  ├──────────────────────────────┼────────────────────────┼────────────────────────┼────────────────────────┼────────────────────────┤
  │ **`whenComplete`**           │ **Always**             │ `BiConsumer<T, Th>`    │ 🔴 No (Returns $T$)   │ 🔴 **No** (Error stays)│
  └──────────────────────────────┴────────────────────────┴────────────────────────┴────────────────────────┴────────────────────────┘
```

### 1. `exceptionally`: Classical Fallback

```java
public CompletableFuture<String> fetchUserBio(String userId) {
    return remoteBioClient.getBioAsync(userId)
        .exceptionally(ex -> {
            log.warn("Bio service failed for user {}, using default bio", userId, ex);
            return "Standard Profile User"; // 🛡️ Fallback value
        });
}
```

### 2. `handle`: Full Control & Type Transformation

`handle()` receives both the result and the exception (one of them will be `null`). It can return a completely different type:

```java
// Transforms both success and error into a unified HTTP ResponseDTO:
public CompletableFuture<ResponseDTO> handleUserRequest(String userId) {
    return remoteBioClient.getBioAsync(userId)
        .handle((bio, ex) -> {
            if (ex != null) {
                return new ResponseDTO(HttpStatus.INTERNAL_SERVER_ERROR, "Service error: " + ex.getMessage());
            }
            return new ResponseDTO(HttpStatus.OK, bio);
        });
}
```

### 3. `whenComplete`: Pure Side-Effects (Finally)

`whenComplete()` is an **observer**. It lets you inspect the outcome (e.g. for metrics, logging, or closing resources) without interrupting or altering the pipeline flow:

```java
// Observes execution for telemetry, then passes raw result/exception downstream:
userService.fetchUserAsync(userId)
    .whenComplete((user, ex) -> {
        if (ex != null) {
            metricsRegistry.counter("users.fetch.errors").increment();
        } else {
            metricsRegistry.counter("users.fetch.success").increment();
        }
    })
    .thenAccept(user -> renderProfile(user)); // 👈 Receives the original user (or skipped if error)!
```

## 🔴 Senior Level

### The `whenComplete` Exception Precedence Hazard

> [!WARNING]
> If the action inside `whenComplete` itself throws an unexpected runtime exception:
> - The **new exception** replaces or suppresses the original exception!
> - The downstream future completes with the *new* exception, potentially masking the root cause error.

```java
// ⚠️ DANGEROUS: Exception inside whenComplete overrides the original error!
CompletableFuture.supplyAsync(() -> {
    throw new DatabaseException("Original DB Timeout");
})
.whenComplete((res, ex) -> {
    throw new NullPointerException("NPE in logging callback!"); // 💥 MASKS ORIGINAL ERROR!
})
.exceptionally(ex -> {
    // 💥 `ex` is NullPointerException, NOT DatabaseException!
    return null;
});
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`exceptionally`:** Runs only on exception; catches error and returns fallback of same type $T$.
- **`handle`:** Always runs; takes `(res, ex)` and returns new type $U$, with full power to recover or transform.
- **`whenComplete`:** Always runs; takes `(res, ex)` for side-effects (logging/metrics); does NOT change value or swallow errors.
- **Analogy:** `exceptionally` $\approx$ `catch`; `whenComplete` $\approx$ `finally`; `handle` $\approx$ `try/catch/finally` with return.
- **Gotcha:** Any exception thrown inside `whenComplete` will overwrite the original pipeline exception.

**Common Follow-up Questions:**
- *"When should you choose `handle` over `exceptionally`?"* → Choose `handle` when you want to execute logic on both success and failure, or when you need to transform the return type (e.g. returning `HTTP 200` on success and `HTTP 500` DTO on error).
- *"How do you handle async fallbacks in Java 12+?"* → Use `exceptionallyCompose()`, which allows the fallback function to return a `CompletableFuture<T>` instead of a blocking synchronous value.
- *"Why is `whenComplete` preferred for logging over `handle`?"* → Because `whenComplete` preserves the original future's type and error state automatically without needing to manually re-return `res` or re-throw `ex`.

**Red Flags (DO NOT Say):**
- ❌ *"whenComplete can be used to return a default fallback string."* (whenComplete takes a `BiConsumer` which returns `void`; it cannot return fallback values).
- ❌ *"handle only executes if an exception is thrown."* (handle executes unconditionally on both success and failure).
- ❌ *"exceptionally can change the return type from `String` to `Integer`."* (exceptionally must return the same type $T$; use `handle` to change types).
