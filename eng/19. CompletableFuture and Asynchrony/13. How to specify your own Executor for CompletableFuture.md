# How to Specify Your Own Executor for CompletableFuture?

---

## 🟢 Junior Level

Every asynchronous method in `CompletableFuture` has an overloaded variant that accepts a custom **`java.util.concurrent.Executor`**:

```java
// 1. Create a dedicated thread pool:
ExecutorService customExecutor = Executors.newFixedThreadPool(10);

// 2. Pass the custom executor as the 2nd argument to supplyAsync:
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("Running in custom thread: " + Thread.currentThread().getName());
    return "Data";
}, customExecutor);

// 3. Pass the custom executor to downstream async transformation stages:
future.thenApplyAsync(data -> data.toUpperCase(), customExecutor)
      .thenAccept(System.out::println);
```

```
  Why use a Custom Executor?
  • 🛡️ Isolation: Isolates slow database/HTTP queries from other critical parts of your system.
  • 🛑 Starvation Prevention: Prevents exhausting the shared JVM-wide `ForkJoinPool.commonPool()`.
  • 🏷️ Observability: Named threads (`order-io-1`, `payment-worker-2`) make thread dumps easy to debug.
```

## 🟡 Middle Level

### The Executor Non-Propagation Gotcha

> [!WARNING]
> Specifying an `Executor` in `supplyAsync()` **DOES NOT propagate** to downstream `*Async` stages!
>
> If you call `.thenApplyAsync(fn)` without an explicit executor, it **silently reverts to `ForkJoinPool.commonPool()`**!

```java
// ❌ SILENT FALLBACK TRAP:
CompletableFuture.supplyAsync(() -> fetchFromDb(), myCustomIoExecutor)
    .thenApplyAsync(data -> transform(data)); // 💥 Silently executes on ForkJoinPool.commonPool()!

// 🟢 SOLUTION 1: Use synchronous `thenApply` (runs inline on the worker thread that fetched DB data):
CompletableFuture.supplyAsync(() -> fetchFromDb(), myCustomIoExecutor)
    .thenApply(data -> transform(data)); // 🚀 Zero context switch, stays on custom thread!

// 🟢 SOLUTION 2: Explicitly pass the custom executor to each async stage:
CompletableFuture.supplyAsync(() -> fetchFromDb(), myCustomIoExecutor)
    .thenApplyAsync(data -> transform(data), myCustomIoExecutor);
```

## 🔴 Senior Level

### Enterprise Spring Boot Configuration with Custom Thread Pool

```java
@Configuration
@EnableAsync
public class AsyncThreadPoolConfig {

    @Bean(name = "orderProcessingExecutor")
    public Executor orderProcessingExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(16);
        executor.setMaxPoolSize(64);
        executor.setQueueCapacity(500);
        executor.setThreadNamePrefix("order-async-");
        // 🛡️ Backpressure Policy: If queue is full, calling Tomcat thread executes task directly:
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.setAwaitTerminationSeconds(30);
        executor.initialize();
        return executor;
    }
}
```

```java
@Service
public class OrderService {

    @Autowired
    @Qualifier("orderProcessingExecutor")
    private Executor orderExecutor;

    public CompletableFuture<OrderReceipt> processOrderAsync(Order order) {
        return CompletableFuture.supplyAsync(() -> executeOrder(order), orderExecutor);
    }
}
```

### Advanced JDK: `ForkJoinPool.ManagedBlocker`

If your system *must* execute blocking operations inside a `ForkJoinPool`, implement **`ForkJoinPool.ManagedBlocker`**. When a thread blocks inside a managed blocker, the pool dynamically spawns a temporary compensation worker thread to maintain full parallelism:

```java
ForkJoinPool.managedBlock(new ForkJoinPool.ManagedBlocker() {
    private boolean done = false;
    @Override public boolean block() {
        blockingSocketRead();
        done = true;
        return true;
    }
    @Override public boolean isReleasable() { return done; }
});
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **How to Specify:** Pass the custom `Executor` as the 2nd argument to `supplyAsync`, `runAsync`, `thenApplyAsync`, etc.
- **Non-Propagation Rule:** An `Executor` specified in `supplyAsync` does **NOT** propagate to `.thenApplyAsync()`; it reverts to `commonPool()` unless explicitly passed again or using inline `.thenApply()`.
- **Backpressure:** Always configure a bounded queue (`ArrayBlockingQueue` or `LinkedBlockingQueue(cap)`) and a `CallerRunsPolicy` on production `ThreadPoolExecutor`s.
- **Java 21 Standard:** Use `Executors.newVirtualThreadPerTaskExecutor()` for high-concurrency non-blocking I/O.
- **Naming:** Always name threads via a custom `ThreadFactory` for readable stack traces.

**Common Follow-up Questions:**
- *"What happens if the custom Executor's queue is full and rejected execution handler is triggered?"* → The `RejectedExecutionException` causes `CompletableFuture.supplyAsync()` to fail immediately or triggers the rejection policy (e.g. `CallerRunsPolicy`).
- *"Why should you avoid `Executors.newCachedThreadPool()` in production?"* → It creates an unbounded number of OS threads with an integer max of $2^{31}-1$, which can easily cause an `OutOfMemoryError: unable to create native thread` under traffic spikes.
- *"How should you manage the lifecycle of custom executors in Spring?"* → Define them as `@Bean` instances or manage graceful shutdown via `@PreDestroy` and `executor.shutdown()`.

**Red Flags (DO NOT Say):**
- ❌ *"If you pass an Executor to `supplyAsync()`, all subsequent `*Async` methods in the chain automatically use that same executor."* (Each `*Async` stage defaults back to `commonPool()` unless explicitly provided).
- ❌ *"Use an unbounded queue (`Integer.MAX_VALUE`) on your production ThreadPoolExecutor."* (Causes silent memory exhaustion during downstream service outages).
- ❌ *"Never shut down your custom ExecutorService."* (Leaks native OS threads and prevents clean container pod termination).
