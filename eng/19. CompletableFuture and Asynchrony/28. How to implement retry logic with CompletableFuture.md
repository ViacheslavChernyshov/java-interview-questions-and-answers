# How to Implement Retry Logic with CompletableFuture?

---

## 🟢 Junior Level

Implementing retry logic with `CompletableFuture` requires **asynchronously re-executing the operation** when an error occurs, without blocking worker threads with `Thread.sleep()`:

```java
// Recursive asynchronous retry using exceptionallyCompose (Java 12+):
public static <T> CompletableFuture<T> retryAsync(
        Supplier<CompletableFuture<T>> supplier, int maxRetries) {
    
    return supplier.get().exceptionallyCompose(ex -> {
        if (maxRetries > 0) {
            log.warn("Operation failed ({} retries left). Retrying...", maxRetries);
            return retryAsync(supplier, maxRetries - 1); // 🔄 Asynchronous recursive retry!
        }
        // Exceeded retries: propagate original failure
        return CompletableFuture.failedFuture(ex);
    });
}
```

```
  Golden Rule:
  • Never call `Thread.sleep()` inside an asynchronous retry lambda!
  • Use non-blocking scheduled delays (`delayedExecutor` or `ScheduledExecutorService`).
```

## 🟡 Middle Level

### Asynchronous Exponential Backoff with `CompletableFuture.delayedExecutor()` (Java 12+)

In production, retries must incorporate an **increasing exponential delay** ($1\text{s} \to 2\text{s} \to 4\text{s}$) to give failing services time to recover:

```java
public class AsyncRetryUtils {

    public static <T> CompletableFuture<T> retryWithBackoff(
            Supplier<CompletableFuture<T>> supplier,
            int maxRetries,
            long initialDelayMs,
            Predicate<Throwable> retryPredicate) {

        return supplier.get().exceptionallyCompose(ex -> {
            Throwable rootCause = (ex instanceof CompletionException) ? ex.getCause() : ex;

            // 1. Verify remaining retries and check if error is transient (e.g. Timeout):
            if (maxRetries > 0 && retryPredicate.test(rootCause)) {
                log.warn("Transient failure: {}. Retrying in {}ms...", rootCause.getMessage(), initialDelayMs);

                // 2. Schedule non-blocking delayed re-execution (Java 9+ delayedExecutor):
                Executor delayedExecutor = CompletableFuture.delayedExecutor(initialDelayMs, TimeUnit.MILLISECONDS);

                return CompletableFuture.supplyAsync(() -> null, delayedExecutor)
                    .thenCompose(v -> retryWithBackoff(supplier, maxRetries - 1, initialDelayMs * 2, retryPredicate));
            }

            // 3. Non-retryable error or retries exhausted:
            return CompletableFuture.failedFuture(rootCause);
        });
    }
}
```

```java
// Production Usage: Only retry network timeouts up to 3 times:
CompletableFuture<UserDTO> result = AsyncRetryUtils.retryWithBackoff(
    () -> userClient.fetchUserAsync("101"),
    3,
    500, // Initial delay: 500ms
    ex -> ex instanceof TimeoutException || ex instanceof ConnectException
);
```

## 🔴 Senior Level

### Enterprise Standard: Resilience4j Asynchronous Retry

In mission-critical enterprise microservices, implement asynchronous retries using **Resilience4j** (`Retry.decorateCompletionStage`), which integrates with **Micrometer metrics**, **Circuit Breakers**, and **Randomized Jitter**:

```java
@Service
@RequiredArgsConstructor
public class ResilientPaymentService {

    private final PaymentClient paymentClient;
    private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();

    private final Retry retry = Retry.of("paymentServiceRetry", RetryConfig.custom()
        .maxAttempts(3)
        .waitDuration(Duration.ofMillis(500))
        .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(500, 2.0, 0.5)) // Exponential Jitter!
        .retryExceptions(TimeoutException.class, SocketTimeoutException.class)
        .ignoreExceptions(InvalidCardException.class) // Fail-fast on 4xx business errors
        .build());

    public CompletableFuture<PaymentReceipt> chargeCustomerAsync(PaymentRequest request) {
        // Decorate Supplier<CompletionStage<T>> with non-blocking resilience:
        Supplier<CompletionStage<PaymentReceipt>> decoratedSupplier = 
            Retry.decorateCompletionStage(retry, scheduler, () -> paymentClient.chargeAsync(request));

        return decoratedSupplier.get().toCompletableFuture();
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Asynchronous Retry:** Re-execute the supplier recursively using `.exceptionallyCompose()` and `CompletableFuture.delayedExecutor()`.
- **Zero-Blocking Invariant:** Never use `Thread.sleep()`; always use non-blocking scheduled executors.
- **Enterprise Tool:** Use **Resilience4j** (`Retry.decorateCompletionStage`) for production-grade retry with jitter and circuit breaking.
- **Idempotency:** Only retry idempotent operations with unique idempotency keys to prevent duplicate billing/mutations.
- **Transient-Only:** Never retry 4xx client/validation errors.

**Common Follow-up Questions:**
- *"Why is `exceptionallyCompose` (Java 12) required instead of `exceptionally` for retries?"* → Because `exceptionally` only returns a synchronous value $T$, whereas `exceptionallyCompose` can return a new `CompletableFuture<T>`, allowing the retry itself to be asynchronous.
- *"How does Exponential Jitter prevent cascading microservice outages?"* → Jitter randomizes the backoff interval across thousands of concurrent clients so they do not all hit the recovering database at the exact same millisecond (Thundering Herd).
- *"How do you combine Retry with a Circuit Breaker in CompletableFuture?"* → Order the decorators: `CircuitBreaker(Retry(RateLimiter(AsyncCall)))`.

**Red Flags (DO NOT Say):**
- ❌ *"Put a loop with `Thread.sleep(1000)` inside `supplyAsync()` to implement retries."* (Blocks worker threads and exhausts thread pools; use non-blocking schedulers).
- ❌ *"Retry every failed request 10 times unconditionally."* (Retrying invalid input or fatal errors exhausts server capacity; only retry transient network errors).
- ❌ *"Retries don't require idempotency keys on payment endpoints."* (Causes duplicate charges on network timeouts; idempotency is mandatory).
