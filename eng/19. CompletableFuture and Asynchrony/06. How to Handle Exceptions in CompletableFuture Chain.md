# How to Handle Exceptions in CompletableFuture Chain?

---

## 🟢 Junior Level

In `CompletableFuture`, exceptions propagate down the pipeline and **skip normal stages** (such as `.thenApply` or `.thenAccept`) until they hit an error-handling operator.

There are **3 primary methods** for handling exceptions:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 1. `exceptionally(ex -> fallback)`                                                                │
  │    • Acts like a `catch` block; provides a fallback value if an error occurs.                     │
  │ 2. `handle((result, ex) -> transform)`                                                            │
  │    • Always executes (success or failure); can transform results or recover from errors.          │
  │ 3. `whenComplete((result, ex) -> { log(); })`                                                    │
  │    • Acts like a `finally` block for side-effects (logging/metrics); does NOT modify the result.  │
  └───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

```java
// 1. exceptionally() — Return a fallback on failure:
CompletableFuture.supplyAsync(() -> {
    if (true) throw new RuntimeException("Database timeout!");
    return "Real Data";
})
.exceptionally(ex -> "Cached Fallback Data") // 🛡️ Recovers from exception!
.thenAccept(System.out::println);            // Prints: "Cached Fallback Data"
```

## 🟡 Middle Level

### The Error Handling Operator Matrix

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────┬────────────────────────┐
  │ Method                       │ When Does It Execute?        │ Can It Modify the Value?     │ Can It Swallow Errors? │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────┼────────────────────────┤
  │ **`exceptionally(fn)`**      │ **Only on Exception**        │ 🟢 Yes (Returns fallback)    │ 🟢 Yes (Recovers)      │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────┼────────────────────────┤
  │ **`handle(biFn)`**           │ **Always** (Success & Error) │ 🟢 Yes (Transforms $T \to U$)│ 🟢 Yes (Recovers)      │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────┼────────────────────────┤
  │ **`whenComplete(biConsumer)`**│ **Always** (Success & Error) │ 🔴 No (Passes through)       │ 🔴 No (Error persists) │
  └──────────────────────────────┴──────────────────────────────────────────────────────────────┴────────────────────────┘
```

### The `CompletionException` Unwrapping Gotcha

Any checked or unchecked exception thrown inside a `CompletableFuture` lambda is automatically wrapped inside a **`java.util.concurrent.CompletionException`**:

```java
CompletableFuture.supplyAsync(() -> {
    throw new UserNotFoundException("User 404");
})
.exceptionally(ex -> {
    // ⚠️ `ex` is a CompletionException, NOT UserNotFoundException!
    Throwable actualCause = (ex instanceof CompletionException) ? ex.getCause() : ex;
    
    if (actualCause instanceof UserNotFoundException) {
        log.warn("User missing: {}", actualCause.getMessage());
        return "GUEST_USER";
    }
    throw new RuntimeException(actualCause); // Re-throw fatal errors
});
```

## 🔴 Senior Level

### Asynchronous Fallback Recovery: `exceptionallyCompose()` (Java 12+)

Before Java 12, recovering from an error by calling a *secondary asynchronous service* was awkward. Java 12 introduced **`exceptionallyCompose()`** (the async flatMap for exceptions):

```java
// Java 12+: Asynchronous fallback to secondary microservice if primary fails:
public CompletableFuture<PriceDTO> getProductPrice(String productId) {
    return primaryPricingService.fetchPriceAsync(productId)
        .exceptionallyCompose(ex -> {
            log.warn("Primary pricing service down, calling backup service...", ex);
            return backupPricingService.fetchPriceAsync(productId); // 🚀 Returns CompletableFuture<PriceDTO>!
        });
}
```

### Exception Skipping Flow (Pipeline Short-Circuiting)

```
  [supplyAsync: THROWS ERROR]
            │
            ├──► (SKIPPED) ➔ [.thenApply(transformData)]
            ├──► (SKIPPED) ➔ [.thenCompose(fetchAddress)]
            ├──► (SKIPPED) ➔ [.thenAccept(saveToCache)]
            │
            ▼
  [exceptionally: RECOVERS WITH FALLBACK] ──► [.thenAccept(sendConfirmation)] (RESUMES NORMAL FLOW!)
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **3 Operators:** `exceptionally` (catch & fallback), `handle` (process result or error), `whenComplete` (finally block for telemetry).
- **Wrapping:** Exceptions thrown in asynchronous stages are wrapped in **`CompletionException`**; unwrap via `ex.getCause()`.
- **Short-Circuiting:** When a stage throws an error, all downstream `thenApply`/`thenAccept` stages are skipped until an error handler is reached.
- **Java 12+ Feature:** `exceptionallyCompose` allows returning a fallback `CompletableFuture` asynchronously.
- **`whenComplete` Invariant:** `whenComplete` cannot alter the result or swallow exceptions; it is strictly for side-effects (metrics, cleanup).

**Common Follow-up Questions:**
- *"What happens if an exception is thrown inside `handle()` or `exceptionally()`?"* → The newly thrown exception wraps in a new `CompletionException` and continues propagating downstream to any subsequent error handlers.
- *"How does `join()` behave when an exception occurs?"* → `join()` throws unchecked `CompletionException`, while `get()` throws checked `ExecutionException`.
- *"Can you chain multiple `exceptionally()` blocks?"* → Yes; you can place `exceptionally()` at different stages of the pipeline to provide localized fallbacks for specific operations.

**Red Flags (DO NOT Say):**
- ❌ *"Wrap `.supplyAsync()` inside a standard Java `try/catch` block to catch asynchronous exceptions."* (The `try/catch` only catches errors thrown during submission; runtime async exceptions must be caught via `.exceptionally()` or `.handle()`).
- ❌ *"whenComplete can return a default fallback value to swallow the exception."* (`whenComplete` takes a `BiConsumer` and cannot modify the result or stop error propagation; use `handle` or `exceptionally`).
- ❌ *"Exceptions in CompletableFuture are silently lost if you don't call `join()`."* (The future remains completed exceptionally, and any downstream stage or `join()` call will encounter the error).
