# Can You Reuse a Single CompletableFuture in Multiple Chains?

---

## 🟢 Junior Level

**YES, absolutely!** A single `CompletableFuture` can serve as the root source for multiple independent downstream chains simultaneously. This pattern is known as **Fan-Out** (one producer, multiple consumers):

```
                       ┌──► Chain 1: [.thenAccept(sendConfirmationEmail)]
                       │
  [userFuture (ROOT)] ─┼──► Chain 2: [.thenApply(extractOrders) ➔ .thenAccept(saveToCache)]
                       │
                       └──► Chain 3: [.thenRun(incrementMetricsCounter)]
```

```java
// 1. The root asynchronous task executes EXACTLY ONCE:
CompletableFuture<User> userFuture = userService.fetchUserAsync(userId);

// 2. Attach multiple independent pipelines:
userFuture.thenAccept(user -> notificationService.sendWelcome(user));
userFuture.thenAccept(user -> auditLogger.recordLogin(user));
userFuture.thenRun(() -> metricsRegistry.counter("users.loaded").increment());
```

```
  Key Invariants:
  • The underlying computation (`fetchUserAsync`) runs **only once**.
  • All registered chains receive the **exact same completed result**.
  • If a chain is attached *after* `userFuture` is already completed, its callback executes immediately.
```

## 🟡 Middle Level

### Production Pattern: Asynchronous Request De-duplication (Thundering Herd Defense)

You can cache `CompletableFuture` instances in a `ConcurrentHashMap` to deduplicate identical concurrent database queries:

```java
@Service
@RequiredArgsConstructor
public class DeduplicatingProductService {

    private final ProductClient productClient;
    private final Map<String, CompletableFuture<ProductDTO>> inFlightRequests = new ConcurrentHashMap<>();

    public CompletableFuture<ProductDTO> getProductAsync(String productId) {
        // If 50 concurrent requests arrive simultaneously for "prod-101",
        // only 1 HTTP call is made; all 50 callers subscribe to the SAME future!
        return inFlightRequests.computeIfAbsent(productId, id ->
            productClient.fetchProduct(id)
                .whenComplete((res, ex) -> {
                    // Evict from map when request finishes so future queries fetch fresh data:
                    inFlightRequests.remove(id);
                })
        );
    }
}
```

## 🔴 Senior Level

### Critical Architectural Hazards & Gotchas

#### 1. The Mutable Shared State Corruption Hazard

> [!CAUTION]
> All downstream chains receive a reference to the **exact same memory object**.
> If Chain 1 mutates a field on the shared object, Chain 2 will observe the corrupted mutation!

```java
CompletableFuture<User> userFuture = userService.fetchUserAsync(userId);

// ❌ DANGEROUS: Chain 1 mutates the shared instance:
userFuture.thenAccept(user -> user.setRole("ADMIN"));

// 💥 Chain 2 reads the illegally mutated role:
userFuture.thenAccept(user -> auditService.checkPermissions(user)); // Observed "ADMIN"!
```
**Senior Rule:** Any object shared across multiple asynchronous `CompletableFuture` chains **MUST BE IMMUTABLE** (use **Java 16+ Records** or defensive copies).

#### 2. Non-Deterministic Execution Ordering

The JDK **does not guarantee the order** in which independent chains execute:
- Do not assume Chain 1 finishes before Chain 2 starts.
- If sequential ordering is required, chain them explicitly via `.thenCompose()`.

#### 3. Unbounded DAG Memory Leaks

Each chained method (`.thenApply()`, `.thenAccept()`) allocates a `Completion` node pushed onto the root future's internal Treiber stack. Continuously attaching chains to a long-lived or uncompleted future retains the entire object graph in memory, preventing GC.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Answer:** Yes, a single `CompletableFuture` can be reused across multiple independent chains (Fan-Out).
- **Execution Invariant:** The root computation executes **only once**; all subscribers receive the cached result.
- **Top Pattern:** **Request De-duplication (Promise Caching)** using `ConcurrentHashMap.computeIfAbsent()` to collapse concurrent redundant queries.
- **Top Danger:** **Shared Mutable State**; always use immutable objects (Java Records) when fanning out.
- **Execution Order:** Independent chains execute in non-deterministic order.

**Common Follow-up Questions:**
- *"What happens if you cancel the root future?"* → Cancelling the root future marks it as `CancellationException`, which causes all downstream subscriber chains to fail with `CancellationException`.
- *"What happens if one child chain fails with an exception?"* → The exception is isolated to that specific child chain; other sibling chains attached to the root future continue executing unaffected.
- *"Can you attach a callback to a future that finished 10 minutes ago?"* → Yes; `CompletableFuture` retains its completed result indefinitely in memory until garbage collected, allowing late subscribers to immediately retrieve the result.

**Red Flags (DO NOT Say):**
- ❌ *"Attaching 3 `.thenAccept()` calls causes the root `supplyAsync()` task to re-run 3 times."* (The root task executes only once; the result is shared).
- ❌ *"CompletableFuture guarantees that the first `.thenAccept()` finishes before the second `.thenAccept()` begins."* (Independent chains run concurrently without sequential ordering guarantees).
- ❌ *"Child chains can mutate shared domain entities safely because each chain gets an independent deep copy."* (All chains share the exact same reference; immutability is required).
