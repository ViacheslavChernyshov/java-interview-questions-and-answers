# How to Properly Execute Multiple Parallel Requests to Microservices?

---

## 🟢 Junior Level

When a modern web backend or **BFF (Backend for Frontend)** must aggregate data from multiple independent microservices, executing requests **sequentially** causes severe latency accumulation:

```
  1. ❌ SEQUENTIAL HTTP CALLS (Slow & Blocking):
     [User Service (200ms)] ➔ [Order Service (300ms)] ➔ [Loyalty Service (150ms)] ➔ Total = 650ms

  2. 🚀 PARALLEL ASYNCHRONOUS CALLS (`CompletableFuture` Scatter-Gather):
     ┌──► [User Service (200ms)] ────┐
     ├──► [Order Service (300ms)] ───┼──► Aggregate Dashboard ➔ Total = 300ms (max)
     └──► [Loyalty Service (150ms)] ─┘
```

```java
// 🚀 Parallel Microservice Scatter-Gather with CompletableFuture:
CompletableFuture<UserDTO> userFuture = userServiceClient.getUserAsync(userId);
CompletableFuture<List<OrderDTO>> ordersFuture = orderServiceClient.getOrdersAsync(userId);
CompletableFuture<LoyaltyDTO> loyaltyFuture = loyaltyServiceClient.getLoyaltyAsync(userId);

// Wait for all 3 microservices to respond in parallel:
CompletableFuture<DashboardDTO> dashboardFuture = CompletableFuture.allOf(userFuture, ordersFuture, loyaltyFuture)
    .thenApply(v -> new DashboardDTO(
        userFuture.join(),
        ordersFuture.join(),
        loyaltyFuture.join()
    ));
```

## 🟡 Middle Level

### The 5 Pillars of Enterprise Microservice Aggregation

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────┐
  │ # │ Pillar                           │ Why It Is Mandatory in Production                              │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 1 │ **Dedicated I/O Thread Pool**    │ Never use `ForkJoinPool.commonPool()` for network HTTP calls.   │
  │ 2 │ **Non-Blocking HTTP Client**     │ Use `HttpClient.sendAsync()` or Spring `WebClient`.             │
  │ 3 │ **Strict Per-Call Timeouts**     │ Enforce `.orTimeout()` so 1 slow service doesn't hang the app.  │
  │ 4 │ **Partial Failure Degradation**  │ Use `.exceptionally()` fallback so secondary failures don't 500.│
  │ 5 │ **Trace Context Propagation**    │ Propagate MDC / OpenTelemetry trace IDs across async threads.   │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────┘
```

### Production Implementation with Fallbacks and Timeouts

```java
@Service
@RequiredArgsConstructor
public class DashboardAggregatorService {

    private final UserClient userClient;
    private final OrderClient orderClient;
    private final RecommendationClient recommendationClient;
    private final Executor microserviceExecutor; // Custom dedicated thread pool

    public CompletableFuture<DashboardDTO> getAggregatedDashboard(String userId) {
        // 1. Mandatory Service (Fail-fast if user does not exist):
        CompletableFuture<UserDTO> userCF = userClient.fetchUserAsync(userId, microserviceExecutor)
            .orTimeout(500, TimeUnit.MILLISECONDS);

        // 2. Secondary Service with Timeout & Fallback:
        CompletableFuture<List<OrderDTO>> ordersCF = orderClient.fetchOrdersAsync(userId, microserviceExecutor)
            .orTimeout(800, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> {
                log.warn("Order service timed out/failed for user {}: {}", userId, ex.getMessage());
                return Collections.emptyList(); // 🛡️ Graceful fallback!
            });

        // 3. Non-critical Service with Fallback:
        CompletableFuture<List<PromoDTO>> promoCF = recommendationClient.fetchPromosAsync(userId, microserviceExecutor)
            .orTimeout(300, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> Collections.emptyList());

        // 4. Scatter-Gather Barrier:
        return CompletableFuture.allOf(userCF, ordersCF, promoCF)
            .thenApply(v -> new DashboardDTO(userCF.join(), ordersCF.join(), promoCF.join()));
    }
}
```

## 🔴 Senior Level

### Distributed Tracing & Security Context Propagation

In asynchronous multithreaded pipelines, `ThreadLocal` contexts (such as **SLF4J MDC** and **Spring SecurityContextHolder**) do **not** automatically transfer to background worker threads.

#### Senior Solution: Context-Propagating Executor Wrapper

```java
public class ContextAwareExecutor implements Executor {
    private final Executor delegate;

    public ContextAwareExecutor(Executor delegate) { this.delegate = delegate; }

    @Override
    public void execute(Runnable command) {
        // 1. Capture calling thread's MDC context map and SecurityContext:
        Map<String, String> mdcContext = MDC.getCopyOfContextMap();
        SecurityContext securityContext = SecurityContextHolder.getContext();

        delegate.execute(() -> {
            // 2. Install context on the worker thread:
            if (mdcContext != null) MDC.setContextMap(mdcContext);
            SecurityContextHolder.setContext(securityContext);
            try {
                command.run();
            } finally {
                // 3. Clean up worker thread state:
                MDC.clear();
                SecurityContextHolder.clearContext();
            }
        });
    }
}
```

### Modern Java 21 Virtual Threads Architecture

With **Java 21 Virtual Threads**, you can combine non-blocking parallel throughput with simpler code via Structured Concurrency or Virtual Thread executors:

```java
// Java 21+: Millions of parallel microservice calls with zero thread pool tuning:
ExecutorService virtualExecutor = Executors.newVirtualThreadPerTaskExecutor();

CompletableFuture<DashboardDTO> future = CompletableFuture.supplyAsync(() -> fetchUser(id), virtualExecutor)
    .thenCombine(CompletableFuture.supplyAsync(() -> fetchOrders(id), virtualExecutor), DashboardDTO::new);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Pattern:** **Scatter-Gather** (Fan-out requests concurrently ➔ wait via `allOf` / `thenCombine` ➔ Fan-in results).
- **Latency Equation:** Reduces total latency from $\sum T_i$ to $\max(T_i)$.
- **Crucial Rules:**
  1. Always isolate microservice calls into a **dedicated `Executor`** (or Java 21 Virtual Threads).
  2. Always attach **Timeouts** (`.orTimeout(ms, TimeUnit)`) and **Fallbacks** (`.exceptionally(...)`).
  3. Propagate **MDC & Security tokens** across thread boundaries via custom Executor wrappers.
- **Graceful Degradation:** A failure in a non-critical widget (e.g. recommendations) should never crash the main user dashboard.

**Common Follow-up Questions:**
- *"What happens if one of the parallel microservices hangs indefinitely without a timeout?"* → The `allOf()` stage will wait forever, leaking memory and leaving the HTTP request open until client connection timeout; always configure `.orTimeout()`.
- *"How do you pass OpenTelemetry traceparent headers in asynchronous HTTP calls?"* → Use an HTTP client interceptor configured with OpenTelemetry's `W3CTraceContextPropagator` to inject `traceparent` headers into outgoing requests.
- *"What is the difference between CompletableFuture scatter-gather and Spring WebClient `Mono.zip()`?"* → Both perform asynchronous aggregation; `CompletableFuture` is standard JDK concurrency, while `WebClient / Mono.zip` is part of Project Reactor's reactive stream ecosystem.

**Red Flags (DO NOT Say):**
- ❌ *"Execute parallel microservice calls on `ForkJoinPool.commonPool()` to avoid configuring thread pools."* (Blocks commonPool threads and starves Parallel Streams system-wide).
- ❌ *"If any single microservice fails, let the entire dashboard API return a 500 error."* (Violates graceful degradation; non-critical dependencies should fall back to cached or empty data).
- ❌ *"Call `.join()` after each microservice line in sequence."* (Turns parallel code into blocking sequential code).
