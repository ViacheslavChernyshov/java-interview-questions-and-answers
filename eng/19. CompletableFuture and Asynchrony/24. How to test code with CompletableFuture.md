# How to Test Code with CompletableFuture?

---

## 🟢 Junior Level

Testing asynchronous code requires ensuring that the JUnit test runner **waits for background threads to complete** before evaluating assertions:

```java
@Test
void shouldCalculateDiscountSuccessfully() {
    PricingService service = new PricingService();
    
    CompletableFuture<Double> priceFuture = service.calculateDiscountAsync(100.0, 0.2);

    // 🛑 Block and retrieve the value in the test:
    Double finalPrice = priceFuture.join();

    assertEquals(80.0, finalPrice);
}
```

> [!TIP]
> Use **`join()`** instead of `get()` in simple unit tests to avoid boilerplate checked `try/catch` blocks for `InterruptedException` and `ExecutionException`.

### 1. Mockito Stubs with Immediate Futures

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock private PaymentClient paymentClient;
    @InjectMocks private OrderService orderService;

    @Test
    void shouldProcessOrderWithMockedAsyncDependency() {
        // 🚀 Return immediate synchronous future (0 thread delay):
        when(paymentClient.authorizeAsync(any()))
            .thenReturn(CompletableFuture.completedFuture(new AuthReceipt("AUTH-999")));

        CompletableFuture<OrderConfirmation> confirmationFuture = 
            orderService.submitOrderAsync(new Order(101L));

        OrderConfirmation result = confirmationFuture.join();
        assertThat(result.authCode()).isEqualTo("AUTH-999");
    }

    @Test
    void shouldHandlePaymentFailureProperly() {
        // 💥 Stub with an exceptional future:
        when(paymentClient.authorizeAsync(any()))
            .thenReturn(CompletableFuture.failedFuture(new InsufficientFundsException("Card declined")));

        CompletableFuture<OrderConfirmation> confirmationFuture = 
            orderService.submitOrderAsync(new Order(101L));

        // Verify exceptional completion unwrapping:
        assertThatThrownBy(confirmationFuture::join)
            .isInstanceOf(CompletionException.class)
            .hasCauseInstanceOf(InsufficientFundsException.class)
            .hasMessageContaining("Card declined");
    }
}
```

## 🔴 Senior Level

### Advanced Testing: SameThreadExecutor & Awaitility

#### 1. Injecting `Runnable::run` for 100% Synchronous Unit Testing

By injecting a direct same-thread executor (`Runnable::run`) during tests, you eliminate all multithreading non-determinism:

```java
@Test
void shouldExecuteInSameThreadForDeterministicTesting() {
    // 🎯 Runs async tasks synchronously on the test thread:
    Executor sameThreadExecutor = Runnable::run;

    UserService service = new UserService(userRepository, sameThreadExecutor);
    CompletableFuture<UserDTO> future = service.getUserAsync("user-1");

    // The future is ALREADY COMPLETED immediately with zero waiting!
    assertThat(future).isCompletedWithValueMatching(u -> u.id().equals("user-1"));
}
```

#### 2. Eventual Consistency with Awaitility

For testing asynchronous fire-and-forget side effects (e.g. background audit logging or metrics publishing), use **Awaitility**:

```java
@Test
void shouldEventuallyRecordAuditLogInBackground() {
    orderService.processOrderAsync(new Order(500L));

    // 🕒 Polling assertion without sleeping:
    org.awaitility.Awaitility.await()
        .atMost(2, TimeUnit.SECONDS)
        .pollInterval(50, TimeUnit.MILLISECONDS)
        .untilAsserted(() -> {
            verify(auditRepository).save(argThat(log -> log.orderId() == 500L));
        });
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Unit Test Mocking:** Stub async methods using `CompletableFuture.completedFuture(data)` (success) or `failedFuture(ex)` (error).
- **Integration Rule:** Never call bare `.get()` without a timeout in integration tests; always pass `.get(3, TimeUnit.SECONDS)` to prevent hanging test suites.
- **Same-Thread Injection:** Pass `Runnable::run` as the `Executor` in unit tests to make async code run completely deterministically on the calling test thread.
- **Exception Assertions:** Use AssertJ's `assertThatThrownBy(future::join).isInstanceOf(CompletionException.class).hasCauseInstanceOf(...)`.
- **Side-Effects:** Use **Awaitility** to poll for background fire-and-forget assertions.

**Common Follow-up Questions:**
- *"Why is `Thread.sleep()` an anti-pattern in async unit tests?"* → `Thread.sleep()` makes test suites slow, non-deterministic, and flaky across different CI/CD hardware speeds; use `.join()`, `get(timeout)`, or Awaitility instead.
- *"How do you test `allOf()` failure handling?"* → Pass a mix of `completedFuture()` and `failedFuture()` mocks, and assert that the composite future resolves with expected fallback objects or completes exceptionally.
- *"How does AssertJ support CompletableFuture natively?"* → AssertJ provides `assertThat(future).isCompleted()`, `isNotCompleted()`, `isCompletedWithValue(expected)`, and `isCompletedExceptionally()`.

**Red Flags (DO NOT Say):**
- ❌ *"Put a `Thread.sleep(2000)` at the end of every async test to wait for background threads."* (Extremely slow and flaky; always synchronize via `.join()` or Awaitility).
- ❌ *"You cannot unit test code that returns a CompletableFuture."* (Easily tested by mocking dependencies with `completedFuture`).
- ❌ *"Async tests should never throw exceptions."* (Test exceptional paths by asserting on `CompletionException` and its `cause`).
