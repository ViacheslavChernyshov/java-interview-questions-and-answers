# What is the Difference Between persist() and merge()?

---

## 🟢 Junior Level

In JPA, **`persist()`** and **`merge()`** are two primary `EntityManager` methods used to move entity objects into the **Managed** state, but they are designed for completely different lifecycle states and have fundamentally different behaviors:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🆕 `persist(entity)`                                    │ 🔄 `merge(entity)`                                      │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Designed for **NEW / TRANSIENT** entities.            │ • Designed for **DETACHED** entities.                   │
  │ • Transitions the input object directly to **Managed**. │ • Copies state onto a managed copy; **input stays Det**!│
  │ • Returns `void`.                                       │ • **Returns the Managed instance**.                     │
  │ • Generates SQL `INSERT` on flush.                      │ • Executes SQL `SELECT` + `UPDATE` (or `INSERT`).       │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
// 1. Using persist():
User newUser = new User("Alice");
entityManager.persist(newUser); // newUser is now MANAGED!
newUser.setName("Alicia");      // Changes tracked directly by dirty checking!

// 2. Using merge():
User detachedUser = new User(1L, "Bob");
User managedUser = entityManager.merge(detachedUser); // MUST capture return value!

detachedUser.setName("Bobby"); // ❌ NOT SAVED! (detachedUser is still detached)
managedUser.setName("Bobby");  // 🛡️ SAVED! (managedUser is managed)
```

## 🟡 Middle Level

### Feature Comparison Matrix

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Feature              │ `em.persist(entity)`         │ `em.merge(entity)`                               │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Target State**     │ Transient (New)              │ Detached (or Transient)                          │
  │ **Return Value**     │ `void`                       │ Managed entity instance ($T$)                    │
  │ **Input Parameter**  │ Becomes **Managed**          │ **Remains Detached** (Unchanged)                 │
  │ **SQL Executed**     │ SQL `INSERT` on flush        │ SQL `SELECT` (to hydrate) + SQL `UPDATE`         │
  │ **If Detached**      │ 💥 Throws `Exception`        │ ✅ Copies state onto managed entity              │
  │ **Primary Use Case** │ Creating brand new rows      │ Updating rows from REST DTOs / detached sessions │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Under the Hood: The 5 Steps of `merge()`

When you invoke `entityManager.merge(detachedEntity)`:

```
  [Detached Entity: ID=42, Name="Updated"]
                    │
                    ▼
  Step 1: Checks L1 Cache for Entity with ID=42.
          • If NOT in L1 Cache ──► Executes SQL `SELECT * FROM users WHERE id = 42;`
          • Hydrates and places a new `ManagedUser` instance into the L1 Cache.
                    │
                    ▼
  Step 2: Copies all property values from `Detached Entity` onto `ManagedUser`.
                    │
                    ▼
  Step 3: Returns the `ManagedUser` instance to the caller.
                    │
                    ▼
  Step 4: During next flush, Dirty Checking compares `ManagedUser` with initial snapshot 
          and generates: `UPDATE users SET name = 'Updated' WHERE id = 42;`.
```

### The Redundant SELECT Overhead (Why Not Use `merge()` for Everything?)

Intermediate developers often use `merge()` for creating new entities because it "handles both new and detached". **This is a severe performance trap!**

```java
// ⚠️ ANTI-PATTERN: Calling merge() on new entities:
User brandNewUser = new User(); // No ID assigned
entityManager.merge(brandNewUser);
```
- If an ID is manually assigned or passed in, `merge()` **always executes an initial SQL SELECT** to check if the row exists before inserting, doubling database round-trip latency!

### How Spring Data JPA `save()` Works Under the Hood

```java
// Spring Data SimpleJpaRepository implementation:
@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        entityManager.persist(entity); // 1. Fast direct INSERT
        return entity;
    } else {
        return entityManager.merge(entity); // 2. SELECT + UPDATE copy
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`persist()`:** For Transient entities; mutates input object to Managed; returns `void`; schedules SQL `INSERT`.
- **`merge()`:** For Detached entities; returns a new Managed copy; input object remains Detached; schedules `UPDATE`.
- **The Golden Rule:** Always capture the return value of `merge()` (`User u = em.merge(detached)`).
- **Redundant Query Trap:** Calling `merge()` on entities with assigned IDs fires a redundant SQL `SELECT` before `INSERT`.
- **Spring `save()`:** Uses `persist()` if `id == null`, otherwise uses `merge()`.

**Common Follow-up Questions:**
- *"What exception is thrown if you pass a Detached entity to `em.persist()`?"* → Throws `org.hibernate.PersistentObjectException: detached entity passed to persist`.
- *"What happens if you call `em.persist()` on an entity that is already Managed?"* → It is a no-op; Hibernate simply ignores the redundant call.
- *"How does Spring Data know whether an entity is 'new' when calling `repository.save()`?"* → By default, it checks if the `@Id` property is `null` (or 0 for primitive types). If using custom assigned IDs, the entity can implement `Persistable<ID>` and override `isNew()`.

**Red Flags (DO NOT Say):**
- ❌ *"`em.persist()` and `em.merge()` do the exact same thing."* (`persist()` transitions the original object; `merge()` returns a separate clone).
- ❌ *"Calling `merge()` updates the detached object in memory so it becomes managed."* (The detached argument remains detached).
- ❌ *"Always use `merge()` for inserts and updates because it is universal."* (Using `merge()` for inserts fires unnecessary SELECT queries).
