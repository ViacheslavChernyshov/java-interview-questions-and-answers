# What is Projection in JPA?

---

## 🟢 Junior Level

A **Projection** in JPA and Spring Data JPA is a query mechanism that fetches **only a specific subset of columns/attributes** directly from the database into a lightweight data structure (such as a Java Record, DTO, or Interface), rather than loading full managed entity objects:

```
  Document Printing Analogy:
  • Full Entity: Printing a 200-page employee dossier when you only needed their email address 
    (Wasted paper, heavy binder, slow printing).
  • Projection: Printing a single business card with just their name and email address 
    (Fast, lightweight, zero wasted resources!).
```

```java
// 1. Immutable Java 17/21 Record DTO:
public record UserSummaryDTO(Long id, String name, String email) {}

// 2. Repository JPQL Constructor Expression:
public interface UserRepository extends JpaRepository<User, Long> {

    @Query("SELECT new com.example.dto.UserSummaryDTO(u.id, u.name, u.email) FROM User u WHERE u.status = :status")
    List<UserSummaryDTO> findSummariesByStatus(@Param("status") String status);
}
```

```sql
-- Generated SQL sent to the database (Fetches ONLY 3 columns!):
SELECT u.id, u.name, u.email FROM users u WHERE u.status = 'ACTIVE';
```

## 🟡 Middle Level

### The 4 Types of Projections in Spring Data JPA

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Projection Type              │ Mechanism & Syntax               │ Evaluation & Recommendation                      │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. Class / Record DTO**    │ `SELECT new com.dto.UserDTO(...)`│ 🏆 **Best Practice**: Fast, type-safe, immutable,│
  │ (Constructor Expression)     │ Returns clean Java instances.    │ zero proxy overhead.                             │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **2. Closed Interface**      │ Spring Data interface with       │ 🟢 Convenient: Spring generates SQL selecting    │
  │ (Interface-based)            │ getters (`String getName();`).   │ only requested getter columns.                   │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **3. Open Interface**        │ Interface using Spring SpEL:     │ 🔴 ⚠️ **Hazard**: Queries **ALL COLUMNS** from   │
  │ (SpEL Expressions)           │ `@Value("#{target.first + ' '}")`│ database, then computes expression in Java RAM!  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **4. Dynamic Projection**    │ Generic repository method:       │ 🚀 Flexible: Caller specifies desired projection │
  │ (Generic Type Parameter)     │ `<T> List<T> findBy(Class<T> cls)`│ class dynamically.                               │
  └──────────────────────────────┴──────────────────────────────────────────────────────────────────────────────────┘
```

### 1. Closed vs. Open Interface Projections

```java
// ✅ Closed Interface Projection (Queries ONLY id and email):
public interface UserEmailView {
    Long getId();
    String getEmail();
}

// ⚠️ Open Interface Projection (SpEL causes full entity loading from DB!):
public interface UserFullNameView {
    @Value("#{target.firstName + ' ' + target.lastName}")
    String getFullName(); // Jackson/Spring fetches all columns from Postgres!
}
```

### 2. Dynamic Generic Projections

```java
public interface UserRepository extends JpaRepository<User, Long> {
    // Dynamic projection:
    <T> List<T> findByDepartment(String department, Class<T> type);
}

// Usage in Service:
List<UserSummaryDTO> summaries = userRepository.findByDepartment("Engineering", UserSummaryDTO.class);
List<UserEmailView> emails = userRepository.findByDepartment("Engineering", UserEmailView.class);
```

## 🔴 Senior Level

### Performance Benchmark: Entities vs. Record Projections

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Managed Entity Query (`SELECT u FROM`)   │ DTO Record Projection (`SELECT new UserDTO`)     │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Loads all 40 columns into RAM.         │ • Transmits only 3 requested columns over wire.  │
  │ • Allocates Entity in L1 Cache.          │ • Bypasses L1 Cache completely.                  │
  │ • Takes snapshot copy for Dirty Checking.│ • Zero snapshot memory overhead.                 │
  │ • Checks/initializes ByteBuddy proxies.  │ • Zero proxy allocation.                         │
  │ • **p99 Latency: ~45ms (High Memory)**   │ • ⚡ **p99 Latency: ~4ms (80% Memory Reduction)**│
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Projections with Joined Aggregates and Window Functions

Projections can directly aggregate relational child rows without entity mapping overhead:

```java
public record CustomerOrderStatsDTO(
    Long customerId,
    String customerName,
    Long totalOrders,
    BigDecimal totalSpent
) {}
```

```java
public interface CustomerRepository extends JpaRepository<Customer, Long> {

    @Query("""
        SELECT new com.example.dto.CustomerOrderStatsDTO(
            c.id, c.name, COUNT(o.id), COALESCE(SUM(o.totalAmount), 0)
        )
        FROM Customer c
        LEFT JOIN c.orders o
        GROUP BY c.id, c.name
    """)
    List<CustomerOrderStatsDTO> findCustomerSpendingStats();
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Querying a specific subset of database columns directly into lightweight DTOs or Interfaces.
- **Top Choice:** **Java 17/21 Record Constructor Expressions** (`SELECT new com.dto.Record(...)`).
- **Performance:** Bypasses L1 Cache, Dirty Checking snapshots, and proxy overhead; slashes memory and latency.
- **Interface Projections:** Spring Data creates dynamic proxy wrappers for interface getter definitions.
- **Open Projection Trap:** SpEL `@Value` interface projections force Hibernate to load all columns into memory.

**Common Follow-up Questions:**
- *"Are Projection objects managed by the EntityManager?"* → No; projections are plain, unmanaged Java objects (DTOs/Records); modifications to their fields are **never** tracked or saved by dirty checking.
- *"How do Interface Projections work under the hood in Spring Data?"* → Spring uses JDK Dynamic Proxies (`java.lang.reflect.Proxy`) wrapping a property map backed by the database row columns.
- *"Can you use Native SQL queries with DTO constructor expressions?"* → No, JPQL constructor expressions (`new com.dto...`) are parsed by JPQL only; for Native SQL, use `@SqlResultSetMapping` with `@ConstructorResult` or Spring Data interface projections.

**Red Flags (DO NOT Say):**
- ❌ *"Modifying a DTO projection updates the database on transaction commit."* (Projections are not managed entities and have zero dirty checking).
- ❌ *"Open Interface Projections with SpEL are the fastest way to project data."* (SpEL open projections load full entities and execute slow runtime reflection).
- ❌ *"Projections cannot be used with JPQL aggregate functions like `SUM()` or `COUNT()`."* (Projections are the ideal target for aggregate queries).
