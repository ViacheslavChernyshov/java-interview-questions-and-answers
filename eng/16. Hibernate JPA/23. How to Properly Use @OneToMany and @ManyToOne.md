# How to Properly Use @OneToMany and @ManyToOne?

---

## 🟢 Junior Level

The **`@OneToMany`** and **`@ManyToOne`** relationship is the most common association in relational domain modeling. To use them correctly, you must understand the distinction between the **Owning Side** and the **Inverse (Mapped) Side**:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 👑 OWNING SIDE (`@ManyToOne`)                           │ 🪞 INVERSE SIDE (`@OneToMany`)                          │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Holds the physical Foreign Key (`@JoinColumn`).       │ • Points to the owner via `mappedBy = "..."`.          │
  │ • **Dictates what is written to the database!**         │ • Read-only view in the persistence context.            │
  │ • Example: `Order` table contains `customer_id`.        │ • Example: `Customer` has `List<Order>`.                │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
// 1. OWNING SIDE (Holds the Foreign Key):
@Entity
public class OrderItem {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false) // Rule 1: Always LAZY!
    @JoinColumn(name = "order_id")                      // Rule 2: Defines FK column!
    private Order order;
}

// 2. INVERSE SIDE (Mirrors the relationship):
@Entity
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Rule 3: mappedBy points to the field name in OrderItem:
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();
}
```

## 🟡 Middle Level

### The 5 Golden Rules of One-to-Many Mapping

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Rule                            │ Architectural Rationale                                                         │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Always `fetch = LAZY`**    │ `@ManyToOne` defaults to EAGER; always override to LAZY to prevent N+1 queries. │
  │ **2. Owning Side on ManyToOne** │ The Foreign Key column lives in the "Many" table; place `@JoinColumn` there.    │
  │ **3. Use `mappedBy` on One**    │ Prevents Hibernate from creating an unnecessary join table.                     │
  │ **4. Sync Helper Methods**      │ Maintain bidirectional integrity in Java RAM (`addItem` / `removeItem`).        │
  │ **5. Avoid Unidirectional One** │ Unidirectional `@OneToMany` creates join tables and fires extra SQL `UPDATE`s!  │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Why Bidirectional Helper Methods are Mandatory

Because Hibernate only inspects the **Owning Side** (`OrderItem.order`), modifying only the inverse collection in memory fails to save the foreign key:

```java
// ❌ CRITICAL BUG (Inverse side updated, but owner NOT set):
Order order = orderRepository.findById(1L).orElseThrow();
OrderItem item = new OrderItem("Laptop", 1200.00);

order.getItems().add(item); // Modifies List in RAM
// On commit: item is saved, but `order_id` in database is NULL!

// ✅ THE CORRECT PATTERN: Use Synchronization Helper Methods:
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this); // 🛡️ Sets foreign key on the OWNING side!
    }

    public void removeItem(OrderItem item) {
        items.remove(item);
        item.setOrder(null); // 🛡️ Unlinks foreign key!
    }
}
```

## 🔴 Senior Level

### The Unidirectional `@OneToMany` Performance Disaster

If you define a unidirectional `@OneToMany` without a matching `@ManyToOne` on the child:

```java
// ⚠️ ANTI-PATTERN: Unidirectional @OneToMany:
@Entity
public class Order {
    @OneToMany(cascade = CascadeType.ALL) // No mappedBy, no child reference
    private List<OrderItem> items = new ArrayList<>();
}
```

```
  Why Unidirectional @OneToMany is Terrible for Performance:
  1. Default Schema: Hibernate creates a separate JOIN TABLE: `order_order_items (order_id, item_id)`!
  2. If using `@JoinColumn(name = "order_id")` on `@OneToMany`:
     • Step 1: Executes `INSERT INTO order_items (id, name) VALUES (1, 'Book');` (Foreign key is NULL!).
     • Step 2: Executes a SECOND query: `UPDATE order_items SET order_id = 10 WHERE id = 1;`!
     • 💥 Doubles the number of SQL statements written to the database!
```

#### Senior Solution:
Always prefer **Bidirectional `@ManyToOne` / `@OneToMany`** or a **Unidirectional `@ManyToOne`** on the child side.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Owning Side:** The `@ManyToOne` side containing `@JoinColumn(name = "fk_id")`; controls DB foreign keys.
- **Inverse Side:** The `@OneToMany` side using `mappedBy = "fieldName"`.
- **Always LAZY:** Always explicitly add `fetch = FetchType.LAZY` to `@ManyToOne`.
- **Helper Methods:** Implement `addItem()` and `removeItem()` inside the parent entity to synchronize both sides.
- **Unidirectional Penalty:** Unidirectional `@OneToMany` causes separate join tables or secondary SQL `UPDATE`s.

**Common Follow-up Questions:**
- *"What happens if you only call `order.getItems().add(item)` without calling `item.setOrder(order)`?"* → The foreign key column in the child table will remain `NULL` in the database (or throw a `NOT NULL` constraint violation).
- *"How should `equals()` and `hashCode()` be implemented for `@OneToMany` entities?"* → Implement `equals()` and `hashCode()` based on **Business Keys (Natural IDs)** or constant equality, never on mutable generated `@Id` or lazy collections (to prevent `HashSet` corruption).
- *"Why is `List` preferred over `Set` for `@OneToMany`?"* → `List` allows maintaining order and avoids forcing immediate initialization of child entity properties during `equals()` checks in sets.

**Red Flags (DO NOT Say):**
- ❌ *"The `@OneToMany` side is the owner of the relationship."* (The `@ManyToOne` child side is the owning side).
- ❌ *"`@ManyToOne` defaults to Lazy loading in JPA."* (`@ManyToOne` defaults to EAGER).
- ❌ *"You don't need helper methods if you use `CascadeType.ALL`."* (Cascading navigates from parent to child, but the child still requires its back-reference populated to write the FK).
