# What is JPQL and How Does It Differ from SQL?

---

## 🟢 Junior Level

**JPQL (Java Persistence Query Language)** is an object-oriented query language defined by the JPA specification. Instead of querying physical database tables and columns, JPQL queries **Java entity classes and their properties**:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ ☕ JPQL (Object-Oriented)                                │ 🗄️ SQL (Relational)                                     │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Operates on **Entity Class Names** (`User`).          │ • Operates on **Database Tables** (`users`).            │
  │ • References **Java Field Properties** (`u.email`).     │ • References **Physical Column Names** (`email_address`).│
  │ • Uses **Path Navigation** (`o.customer.city`).         │ • Requires explicit relational `JOIN ... ON ...`.       │
  │ • Database-Agnostic (Translated via Hibernate Dialect). │ • Bound to specific database dialects (Postgres/Oracle).│
  │ • Returns **Managed Entities or DTOs**.                 │ • Returns raw tabular `ResultSet` rows.                 │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
// JPQL Example (Queries the Java Class "User" and field "age"):
String jpql = "SELECT u FROM User u WHERE u.age >= :minAge ORDER BY u.name ASC";
List<User> users = entityManager.createQuery(jpql, User.class)
                                .setParameter("minAge", 21)
                                .getResultList();

// Translated SQL sent to database (PostgreSQL):
// SELECT u.id, u.user_name, u.user_age FROM app_users u WHERE u.user_age >= 21 ORDER BY u.user_name ASC;
```

  │ **Polymorphism**     │ 🏆 **Automatic**: Querying a  │ ❌ Manual: Requires complex table `UNION`s or   │

  │                      │                              │ CTE `WITH RECURSIVE`, JSONB operators).          │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘

```java
// Automatic Polymorphic Querying in JPQL:
// If CreditCardPayment and CryptoPayment extend Payment:
List<Payment> payments = em.createQuery("SELECT p FROM Payment p", Payment.class).getResultList();
// Hibernate automatically queries the entire hierarchy and instantiates the correct subclasses!
```

## 🔴 Senior Level

### The Bulk Update / Delete Cache Invalidation Trap

JPQL supports bulk mutation queries (`UPDATE` / `DELETE`). However, **bulk JPQL queries execute directly against the database, bypassing the First-Level Cache (L1 Cache)**:

```java
// ❌ CATASTROPHIC STALE CACHE TRAP:
User user = userRepository.findById(1L).orElseThrow(); // user.status is "PENDING" (In L1 Cache)

// Bulk JPQL UPDATE:
userRepository.updateStatusForInactiveUsers("SUSPENDED"); 
// Database row is updated to "SUSPENDED", BUT entity in L1 Cache STILL SAYS "PENDING"!

System.out.println(user.getStatus()); // 💥 Prints STALE "PENDING"!
```

#### Senior Solution in Spring Data JPA:
Always annotate bulk JPQL mutations with `@Modifying(clearAutomatically = true)` to evict the persistence context after execution:

```java
public interface UserRepository extends JpaRepository<User, Long> {

    @Modifying(clearAutomatically = true) // 🛡️ Clears L1 Cache to prevent stale entity reads!
    @Query("UPDATE User u SET u.status = :status WHERE u.lastLoginDate < :cutoff")
    int updateStatusForInactiveUsers(@Param("status") String status, @Param("cutoff") LocalDate cutoff);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Object-oriented query language targeting Java entities and properties, not DB tables.
- **Dialect Translation:** Hibernate parses the JPQL AST and compiles it to database-specific SQL.
- **Polymorphism:** Automatically queries all subclasses when querying an inheritance root.
- **Path Navigation:** Allows traversing associations with dot notation (`o.customer.address.city`).
- **Bulk Mutation Trap:** Bulk `UPDATE`/`DELETE` queries bypass the L1 cache; use `@Modifying(clearAutomatically = true)`.

**Common Follow-up Questions:**
- *"When should you choose Native SQL over JPQL?"* → Use Native SQL for database-specific optimizations, PostgreSQL `JSONB` operators, Common Table Expressions (`WITH RECURSIVE`), complex window functions (`ROW_NUMBER() OVER (...)`), or bulk ETL scripts.
- *"Can you map Native SQL query results to DTOs in JPA?"* → Yes; using `@SqlResultSetMapping` with `@ConstructorResult` or Spring Data JPA interface/record projections.
- *"What is HQL?"* → Hibernate Query Language (HQL) is the precursor and superset of JPQL; all valid JPQL queries are valid HQL queries, but HQL supports additional Hibernate-specific operators.

**Red Flags (DO NOT Say):**
- ❌ *"JPQL uses physical database table and column names in its query string."* (JPQL strictly uses Java entity and field names).
- ❌ *"JPQL queries are validated by the database engine at compile time."* (JPQL is validated at runtime when the EntityManager factory bootstraps or query executes).
- ❌ *"Executing a JPQL bulk UPDATE updates all managed entities in the First-Level Cache automatically."* (Bulk queries bypass L1 cache; persistence context must be cleared).
