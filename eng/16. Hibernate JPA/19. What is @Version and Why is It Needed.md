# What is @Version and Why is It Needed?

---

## 🟢 Junior Level

The **`@Version`** annotation in JPA is used to enable **Optimistic Locking** on an entity, automatically tracking modification revisions to prevent concurrent transactions from silently overwriting each other's changes (Lost Update problem):

```
  Document Revision Stamp Analogy:
  • You print a contract marked "Revision 1".
  • Another colleague prints the same contract marked "Revision 1", edits Clause A, 
    and submits it to legal ──► The contract becomes "Revision 2".
  • You later submit your edits based on "Revision 1":
  • Legal immediately rejects your submission because you are submitting against an outdated revision!
```

```java
@Entity
@Table(name = "products")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Managed exclusively by Hibernate; incremented on every SQL UPDATE:
    @Version
    private Long version;

    private String name;
    private int stockQuantity;
}
```

## 🟡 Middle Level

### Supported Types for `@Version`

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Version Data Type            │ Evaluation & Recommendation                                                     │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`Long` / `long`**          │ 🏆 **Recommended Standard**: Monotonically increments ($0, 1, 2...$).           │
  │                              │ Immune to overflow ($2^{63}-1$ capacity).                                       │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`Integer` / `int`**        │ 🟢 Standard: Monotonically increments. Suitable for standard entity lifecycles. │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`Short` / `short`**        │ 🟡 Usable, but risks overflow ($32,767$ limit) on heavily updated entities.     │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`Timestamp` / `Instant`**  │ 🔴 ⚠️ **Not Recommended**: Clock skew across distributed cloud servers and low  │
  │                              │ millisecond precision can cause undetected collisions.                          │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### The Lost Update Prevention Walkthrough

```
  1. Initial Database State:
     Product(id=42, stock=10, version=1)

  2. Transaction A (User 1) and Transaction B (User 2) read simultaneously:
     Tx A: Reads stock=10, version=1
     Tx B: Reads stock=10, version=1

  3. Transaction B completes checkout (Buys 2 items):
     SQL: UPDATE products SET stock = 8, version = 2 WHERE id = 42 AND version = 1;
     Result: ✅ 1 row updated. Database version is now 2!

  4. Transaction A completes checkout (Buys 3 items):
     SQL: UPDATE products SET stock = 7, version = 2 WHERE id = 42 AND version = 1;
     Result: ❌ 0 rows updated! (Because DB version is 2, not 1).
     Hibernate immediately throws `jakarta.persistence.OptimisticLockException`!
```

## 🔴 Senior Level

### REST API Detached Versioning Pattern

In modern decoupled microservices, the `@Version` property enables **End-to-End Optimistic Locking across disconnected HTTP requests**:

```
  1. Frontend fetches Product:
     GET `/api/products/42` ──► Returns JSON: `{"id": 42, "stock": 10, "version": 1}`

  2. User edits product in web browser for 2 minutes.

  3. Frontend submits update with version payload:
     PUT `/api/products/42` ──► Body: `{"id": 42, "stock": 8, "version": 1}`

  4. Backend Controller / Service:
     `Product managed = entityManager.merge(productDto.toEntity());`
     • If someone else modified the product during those 2 minutes (DB version is now 2):
     • `em.merge()` detects `detached.version (1) != database.version (2)`!
     • 🛡️ Throws `OptimisticLockException` ──► Returns HTTP 409 Conflict to the user!
```

### The Collection Modification Gotcha (Aggregate Versioning)

By default, adding or removing elements in a child collection (`@OneToMany List<OrderItem>`) **does NOT increment the parent entity's `@Version` column**:

```java
// ⚠️ Problem: Modifying order items does not update orders.version!
Order order = orderRepository.findById(orderId).orElseThrow();
order.getItems().add(new OrderItem("Book", 20.00));
// On commit: INSERT INTO order_items executes, but Order version remains unchanged!

// ✅ Solution: Force version increment on the aggregate root:
Order order = entityManager.find(Order.class, orderId, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
order.getItems().add(new OrderItem("Book", 20.00));
// On commit: Hibernate forces UPDATE orders SET version = version + 1 WHERE id = ?;
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Declares an optimistic locking field that increments automatically on every SQL `UPDATE`.
- **Purpose:** Prevents Lost Updates in concurrent transactions without acquiring physical DB locks.
- **Data Types:** Use `Long` or `Integer`; avoid `Timestamp` due to distributed clock skew.
- **REST APIs:** Pass `version` in JSON DTOs to detect conflicts across disconnected web sessions (HTTP 409).
- **Rule:** Never mutate the `@Version` property in application business code.

**Common Follow-up Questions:**
- *"What happens if an entity does not have a `@Version` field?"* → Hibernate performs no optimistic lock verification by default; the last transaction to commit silently overwrites previous writes (Last-Commit-Wins).
- *"Can you use optimistic locking without a `@Version` column in Hibernate?"* → Yes; Hibernate supports `@OptimisticLocking(type = OptimisticLockType.ALL / DIRTY)`, which validates all/dirty columns in the `WHERE` clause, though this has higher CPU overhead.
- *"How many `@Version` fields can an entity have?"* → Strictly at most **one** `@Version` property per entity hierarchy.

**Red Flags (DO NOT Say):**
- ❌ *"I write `product.setVersion(product.getVersion() + 1)` manually in my service class."* (Mutating the version manually breaks Hibernate's internal dirty tracking).
- ❌ *"Placing `@Version` on an entity locks the table with an exclusive PostgreSQL lock."* (Zero DB locks are acquired; it is purely an SQL `WHERE version = ?` predicate check).
- ❌ *"Timestamps are better than Longs for `@Version` because they show when the update happened."* (Clock skew between multiple Kubernetes nodes can cause false-positive conflicts or missed collisions; use `Long` for versioning and `@UpdateTimestamp` for audit dates).
