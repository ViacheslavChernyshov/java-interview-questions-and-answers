# Describe the Entity Lifecycle in Hibernate

---

## 🟢 Junior Level

In JPA and Hibernate, an entity instance transitions through a formal **4-state lifecycle** based on its relationship with the database and the active **Persistence Context (`EntityManager` / `Session`)**:

```
                          ┌───────────────────────────┐
                          │     NEW / TRANSIENT       │ (Created via `new User()`)
                          └─────────────┬─────────────┘
                                        │
                         `em.persist()` │ `em.merge()`
                                        ▼
    ┌─────────────────────►┌───────────────────────────┐◄─────────────────────┐
    │                      │    MANAGED / PERSISTENT   │                     │
    │                      └──────┬─────────────┬──────┘                     │
    │                             │             │                            │
    │             `em.detach()` / │             │ `em.remove()`              │ `em.merge()`
    │             Session closes  │             │                            │
    │                             ▼             ▼                            │
    │  ┌───────────────────────────┐   ┌───────────────────────────┐         │
    └──┤         DETACHED          │   │          REMOVED          │─────────┘
       └───────────────────────────┘   └─────────────┬─────────────┘
                                                     │ (SQL DELETE on flush)
                                                     ▼
                                                   [DB 🗑️]
```

```java
// 1. TRANSIENT: In-memory Java object only; not tracked:
User user = new User("Alice");

// 2. MANAGED: Bound to Persistence Context; tracked by Dirty Checking:
entityManager.persist(user);
user.setEmail("alice@example.com"); // Automatically saved on transaction commit!

// 3. DETACHED: Session closes or detached explicitly:
entityManager.detach(user);
user.setEmail("new@example.com"); // Will NOT be saved to database!

// 4. REMOVED: Scheduled for SQL DELETE on next flush:
User managedUser = entityManager.find(User.class, 1L);
entityManager.remove(managedUser);
```

## 🟡 Middle Level

### Entity State Transition Matrix

```
  ┌──────────────────────┬──────────────────────┬──────────────────────┬───────────────────────────────────────────┐
  │ Current State        │ Method Called        │ New State            │ Action Performed                          │
  ├──────────────────────┼──────────────────────┼──────────────────────┼───────────────────────────────────────────┤
  │ **Transient**        │ `em.persist(e)`      │ **Managed**          │ Scheduled for SQL `INSERT` on flush.      │
  │ **Transient**        │ `em.merge(e)`        │ **Managed (Copy)**   │ Queries DB, copies state, returns Managed.│
  ├──────────────────────┼──────────────────────┼──────────────────────┼───────────────────────────────────────────┤
  │ **Managed**          │ `em.detach(e)`       │ **Detached**         │ Evicted from First-Level Cache.           │
  │ **Managed**          │ `em.clear()`         │ **Detached**         │ Evicts ALL entities from cache.           │
  │ **Managed**          │ `em.remove(e)`       │ **Removed**          │ Scheduled for SQL `DELETE` on flush.      │
  │ **Managed**          │ `em.refresh(e)`      │ **Managed**          │ Re-reads state from DB, overwriting RAM.  │
  ├──────────────────────┼──────────────────────┼──────────────────────┼───────────────────────────────────────────┤
  │ **Detached**         │ `em.merge(e)`        │ **Managed (Copy)**   │ Loads/updates DB, returns managed clone.  │
  │ **Detached**         │ `em.persist(e)`      │ ❌ **ERROR**          │ Throws `PersistentObjectException`!       │
  └──────────────────────┴──────────────────────┴──────────────────────┴───────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Critical `merge()` Reference Invariant

One of the most frequent concurrency bugs occurs when developers assume `merge()` converts the existing object reference into a managed entity:

```java
// ❌ CRITICAL BUG:
User detachedUser = new User(1L, "Bob");
entityManager.merge(detachedUser); // Merges state, but `detachedUser` REMAINS DETACHED!

detachedUser.setName("Robert");
// 💥 "Robert" is NEVER saved to the database because `detachedUser` is not managed!

// ✅ THE CORRECT PATTERN:
User detachedUser = new User(1L, "Bob");
User managedUser = entityManager.merge(detachedUser); // MUST capture returned reference!

managedUser.setName("Robert"); // 🛡️ Saved to database automatically via Dirty Checking!
```

### Dirty Checking Mechanics on Managed Entities

When an entity is in the **Managed** state:
1. **Snapshots:** Upon entering the Persistence Context, Hibernate creates a hidden snapshot copy of all entity property values.
2. **Comparison on Flush:** During transaction commit or before query execution, Hibernate compares the current entity values against the initial snapshot.
3. **Automatic SQL Update:** If any property has changed, Hibernate automatically generates and executes an SQL `UPDATE` statement. Developers **never need to call `repository.save()`** for managed entities!

## 🎯 Interview Cheat Sheet

**Must Know:**
- **4 States:** Transient (new in RAM), Managed (in L1 cache & tracked), Detached (session closed), Removed (marked for delete).
- **Dirty Checking:** Managed entities automatically sync field modifications to the database without calling `save()` or `update()`.
- **`merge()` Invariant:** `em.merge(e)` returns a **new managed instance**; the original input argument remains detached.
- **Detach Triggers:** Closing the session, committing transaction, calling `detach()`, or calling `clear()`.
- **`persist()` Restriction:** Calling `persist()` on a detached entity throws an exception.

**Common Follow-up Questions:**
- *"What happens if you modify a detached entity's properties and commit a transaction?"* → Nothing happens in the database; detached entities are not tracked by the Persistence Context. You must call `em.merge()` to sync changes.
- *"What is the difference between `em.clear()` and `em.close()`?"* → `clear()` evicts all entities from the current persistence context while keeping the `EntityManager` open for subsequent queries; `close()` completely closes the `EntityManager` and releases the database connection.
- *"Can a Removed entity be transitioned back to Managed?"* → Yes; calling `em.persist(removedEntity)` transitions it back to the Managed state before `flush()` is executed.

**Red Flags (DO NOT Say):**
- ❌ *"You must always call `userRepository.save(user)` inside `@Transactional` methods to save changes to a managed entity."* (Managed entities are automatically updated via Dirty Checking).
- ❌ *"`merge()` mutates the original object reference to make it managed."* (`merge()` creates and returns a separate managed copy).
- ❌ *"Transient entities already exist in the database table."* (Transient entities have never been stored in the database).
