# What Are the Peculiarities of Bidirectional Relationships?

---

## 🟢 Junior Level

A **Bidirectional Relationship** in JPA exists when both entities maintain an explicit Java reference to each other, allowing navigation in either direction (e.g. `User ➔ List<Order>` and `Order ➔ User`):

```
  Two-Way Bridge Analogy:
  • Physical Database Table: There is only ONE physical foreign key column (`orders.user_id`).
  • Java Memory: There are TWO separate object pointers (`user.orders` and `order.user`).
  • If you cross the bridge in Java, you must ensure both ends of the bridge stay connected!
```

```java
// 1. Inverse Side (Points to field in Order):
@Entity
public class User {
    @Id private Long id;

    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();
}

// 2. Owning Side (Manages the foreign key):
@Entity
public class Order {
    @Id private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    private User user;
}
```

## 🟡 Middle Level

### The 3 Core Peculiarities and Hazards

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Peculiarity / Hazard            │ Technical Impact & Solution                                                     │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. In-Memory De-sync**        │ Modifying one side does not update the other in Java RAM. Must implement        │
  │                                 │ **bidirectional helper methods** (`addOrder` / `removeOrder`).                  │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. `toString()` StackOverflow**│ Printing an entity causes infinite circular reflection:                        │
  │                                 │ `User.toString()` ➔ `Order.toString()` ➔ `User.toString()` ➔ 💥 `StackOverflow`!│
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. JSON Serialization Loop**  │ Jackson serializer gets trapped in an infinite recursive JSON nesting loop.     │
  │                                 │ Fix using **DTO Projections** or `@JsonBackReference` / `@JsonIgnore`.          │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Defensive Synchronization Helper Methods

```java
@Entity
public class User {
    @Id private Long id;

    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();

    // 🛡️ Guarantees both in-memory pointers stay synchronized:
    public void addOrder(Order order) {
        orders.add(order);
        order.setUser(this);
    }

    public void removeOrder(Order order) {
        orders.remove(order);
        order.setUser(null);
    }
}
```

## 🔴 Senior Level

### Preventing Lombok `toString()`, `equals()`, and `hashCode()` Traps

Using `@Data` or `@ToString` on both sides of a bidirectional relationship will immediately crash the application with **`StackOverflowError`** during logging or debugging:

```java
// ❌ CRITICAL BUG (Lombok @Data on bidirectional entities):
@Entity
@Data // 💥 Generates toString(), equals(), hashCode() traversing all fields!
public class User {
    @OneToMany(mappedBy = "user")
    private List<Order> orders;
}

@Entity
@Data // 💥 Calls user.toString(), which calls orders.toString() infinitely!
public class Order {
    @ManyToOne(fetch = FetchType.LAZY)
    private User user;
}
```

#### Senior Solution:
Exclude the relationship from `@ToString` and `@EqualsAndHashCode`:

```java
// ✅ THE PRODUCTION STANDARD:
@Entity
@Getter
@Setter
@ToString(exclude = "orders") // Exclude lazy collections from toString!
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
public class User {
    @Id
    @EqualsAndHashCode.Include
    private Long id;

    @OneToMany(mappedBy = "user")
    private List<Order> orders = new ArrayList<>();
}
```

### Unidirectional vs. Bidirectional Architectural Choice

Senior architects design aggregates around transactional boundaries:
- **Default to Unidirectional `@ManyToOne`** when child entities rarely need to be retrieved as an entire collection (e.g. A `User` with 50,000 `AuditLog` rows should **never** have a `@OneToMany List<AuditLog>` collection!).
- Use **Bidirectional `@OneToMany`** only when the child collection is small (< 100 items) and lifecycle-bound to the aggregate root (`Order` and `OrderItem`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Asymmetric Reality:** Database has 1 foreign key; Java has 2 object references.
- **Owning Side:** The `@ManyToOne` side controls the database foreign key.
- **Helper Methods:** `addX()` and `removeX()` must maintain both sides in Java RAM.
- **`StackOverflowError`:** Prevent by excluding bidirectional associations from `toString()` and `hashCode()`.
- **Large Collections:** Never use bidirectional `@OneToMany` for high-cardinality collections (10,000+ items); query via repository pagination instead.

**Common Follow-up Questions:**
- *"Why does `equals()` on a bidirectional entity risk `StackOverflowError`?"* → If `equals()` compares child collections and the child compares the parent, evaluating `user1.equals(user2)` triggers infinite mutual recursion.
- *"How should you handle a User with 100,000 Orders?"* → Remove the `@OneToMany List<Order>` collection from `User` entirely. Model it as a unidirectional `@ManyToOne User user` on `Order`, and query orders via `orderRepository.findByUserId(userId, pageable)`.
- *"What is the difference between `@JsonManagedReference` and `@JsonBackReference`?"* → `@JsonManagedReference` is serialized normally into JSON; `@JsonBackReference` is omitted from serialization to prevent JSON circular nesting.

**Red Flags (DO NOT Say):**
- ❌ *"Hibernate automatically synchronizes the in-memory Java collection when you set `order.setUser(user)`."* (Hibernate does NOT update the Java collection in memory; you must write helper methods).
- ❌ *"Use Lombok `@Data` on all JPA entity classes."* (`@Data` creates recursive `toString()` and breaks `equals/hashCode` for lazy proxies).
- ❌ *"Every `@ManyToOne` relationship in an enterprise system must have a corresponding `@OneToMany` collection."* (High-cardinality associations should remain unidirectional to avoid loading thousands of items into memory).
