# What Fetch Strategies Exist in Hibernate?

---

## 🟢 Junior Level

In Hibernate and JPA, fetching strategies are governed by two distinct concepts: **WHEN** the data is fetched (JPA `FetchType`) and **HOW** the physical SQL is structured (Hibernate `@Fetch(FetchMode)`):

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ ⏳ JPA `FetchType` (WHEN to load)                       │ 🛠️ Hibernate `FetchMode` (HOW to load via SQL)          │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • **`LAZY`**: On first method access.                   │ • **`SELECT`**: Executes separate secondary SELECT.    │
  │ • **`EAGER`**: Immediately upon entity load.            │ • **`JOIN`**: Fetches via SQL `LEFT OUTER JOIN`.        │
  │                                                         │ • **`SUBSELECT`**: Fetches collections via subquery.    │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
@Entity
public class Order {
    @Id
    private Long id;

    // Hibernate FetchMode configuration:
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @Fetch(FetchMode.SUBSELECT)
    private List<OrderItem> items;
}
```

## 🟡 Middle Level

### The 3 Core Hibernate `FetchMode` Strategies

```
  ┌──────────────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Hibernate `FetchMode`        │ Generated SQL Pattern                    │ Primary Impact & Gotchas                         │
  ├──────────────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`FetchMode.SELECT`** (Def) │ `SELECT * FROM items WHERE order_id = ?` │ Separate query per parent entity (N+1 hazard).   │
  ├──────────────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`FetchMode.JOIN`**         │ `SELECT o.*, i.* FROM orders o           │ ⚠️ **Overrides `LAZY` to EAGER** during          │
  │                              │  LEFT JOIN items i ON o.id = i.order_id` │ `em.find()`. **Ignored by JPQL queries!**        │
  ├──────────────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`FetchMode.SUBSELECT`**    │ `SELECT * FROM items WHERE order_id IN   │ 🚀 Loads all child collections for all parents   │
  │                              │  (SELECT id FROM orders WHERE ...)`      │ in **1 single additional subquery**!             │
  └──────────────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Deep Dive: `FetchMode.SUBSELECT`

`SUBSELECT` is an elegant solution when loading collections for multiple parent entities returned by a query:

```java
// 1. Initial Parent Query:
List<Order> orders = em.createQuery("SELECT o FROM Order o WHERE o.status = 'SHIPPED'", Order.class)
                       .getResultList();
// SQL: SELECT * FROM orders WHERE status = 'SHIPPED'; (Returns 50 orders)

// 2. Accessing child items in loop:
for (Order order : orders) {
    order.getItems().size(); // Triggers SUBSELECT on first iteration!
}
// SQL: SELECT * FROM order_items WHERE order_id IN (SELECT id FROM orders WHERE status = 'SHIPPED');
// Result: Exactly 2 queries executed instead of 51!
```

## 🔴 Senior Level

### The Dynamic JPA Fetching Landscape

Hibernate `@Fetch` annotations are **static metadata** compiled into entity classes. Senior architects prefer **Dynamic JPA Fetching** configured at runtime per query:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Dynamic Strategy             │ Mechanism & Code Example                                                        │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **JPQL `JOIN FETCH`**        │ Injects an explicit inner/left join into the JPQL abstract syntax tree.         │
  │                              │ `SELECT o FROM Order o JOIN FETCH o.items`                                      │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **JPA 2.1 `@EntityGraph`**   │ Overrides fetch plans dynamically without rewriting JPQL queries.               │
  │                              │ `@EntityGraph(attributePaths = {"customer", "items.product"})`                  │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Batch Fetching**           │ Configured via `@BatchSize(size = 50)` or `default_batch_fetch_size=50`.        │
  │                              │ Batches lazy queries using SQL `IN (?, ?, ...)`.                                │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

```
  ⚠️ The JPQL Override Invariant:
  • If an entity field is annotated with `@Fetch(FetchMode.JOIN)`, Hibernate ignores it when 
    executing JPQL queries (`SELECT o FROM Order o`).
  • JPQL queries ALWAYS default to `FetchMode.SELECT` unless you explicitly declare `JOIN FETCH`!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **FetchType vs FetchMode:** `FetchType` (JPA) defines *when* (LAZY/EAGER); `FetchMode` (Hibernate) defines *how* (SELECT/JOIN/SUBSELECT).
- **`FetchMode.SELECT`:** 1 query per association (default).
- **`FetchMode.JOIN`:** SQL Outer Join on `em.find()`; forces eager loading; ignored by JPQL.
- **`FetchMode.SUBSELECT`:** Fetches all child collections across all queried parents using an embedded SQL subquery (exactly 2 total queries).
- **Dynamic Standard:** Always use `FetchType.LAZY` on entities and override dynamically via `JOIN FETCH` or `@EntityGraph`.

**Common Follow-up Questions:**
- *"Why does `@Fetch(FetchMode.JOIN)` fail to eliminate N+1 queries in JPQL?"* → JPQL queries build their own execution plan based strictly on the JPQL query string; they ignore Hibernate's `@Fetch` annotations and require explicit `JOIN FETCH`.
- *"When should you choose `FetchMode.SUBSELECT` over `@BatchSize`?"* → `SUBSELECT` re-executes the original query's `WHERE` clause inside an SQL subquery in a single round-trip (ideal for large unpaginated query results); `@BatchSize` works on arbitrary batches of entities loaded through multiple independent points in the session.
- *"What is a Fetch Profile in Hibernate?"* → A named configuration (`@FetchProfile`) defined at the package or entity level that allows enabling specific fetch join overrides dynamically on the active `Session`.

**Red Flags (DO NOT Say):**
- ❌ *"FetchMode and FetchType are identical terms for the same JPA annotation."* (`FetchType` is JPA standard; `FetchMode` is a proprietary Hibernate extension).
- ❌ *"Setting `@Fetch(FetchMode.JOIN)` ensures all JPQL queries execute with SQL joins automatically."* (JPQL completely ignores `@Fetch(FetchMode.JOIN)`).
- ❌ *"SUBSELECT can be applied to `@ManyToOne` single entity associations."* (`SUBSELECT` is valid only for collection mappings: `@OneToMany` and `@ManyToMany`).
