# What is the N+1 Problem and How to Solve It?

---

## 🟢 Junior Level

The **N+1 Query Problem** is a notorious database performance anti-pattern where an ORM (like Hibernate) executes **1 initial query** to fetch $N$ parent entities, followed by **$N$ additional queries** (one per parent) to fetch associated child entities:

```
  Shopping Cart Analogy:
  • Efficient Method: You load 10 boxes onto 1 flatbed cart and push them to your car in 1 trip.
  • N+1 Problem: You walk to your car with the empty cart (Query 1), then make 10 separate round-trips 
    carrying each box one by one (10 queries = 11 total trips for 10 items!).
```

```java
// ❌ The N+1 Trap:
List<Order> orders = em.createQuery("SELECT o FROM Order o", Order.class).getResultList();
// 1 Initial Query: SELECT * FROM orders; (Returns 100 orders)

for (Order order : orders) {
    // Triggers 100 individual queries: SELECT * FROM order_items WHERE order_id = ?;
    System.out.println(order.getItems().size());
}
// TOTAL: 1 + 100 = 101 SQL queries sent to the database!
```

## 🟡 Middle Level

### The 4 Production Solutions to Eliminate N+1 Queries

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Solution                     │ Mechanism & Code Example                                                        │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. `JOIN FETCH` (JPQL)**   │ Forces an inner/left join in SQL to load parent and child in a **single query**.│
  │                              │ `@Query("SELECT o FROM Order o JOIN FETCH o.items")`                            │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. `@EntityGraph`**        │ JPA 2.1 declarative fetch plan; overrides lazy loading dynamically per method.  │
  │                              │ `@EntityGraph(attributePaths = {"items", "customer"})`                          │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. `@BatchSize`**          │ Groups lazy queries into SQL `IN (?, ?, ...)` clauses.                          │
  │                              │ `@BatchSize(size = 50)` flattens 100 queries into **2 queries**!                │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **4. DTO Projections**       │ Directly maps relational columns to a Java Record/DTO, bypassing entities.      │
  │                              │ `SELECT new com.dto.OrderSummary(o.id, c.name) FROM ...`                        │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### 1. JPQL `JOIN FETCH`

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    // Generates 1 single SQL JOIN query:
    @Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.status = :status")
    List<Order> findAllByStatusWithItems(@Param("status") String status);
}
```

### 2. Spring Data JPA `@EntityGraph`

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    // Loads Order along with items and customer in a single SQL LEFT OUTER JOIN:
    @EntityGraph(attributePaths = {"items", "customer"})
    List<Order> findByStatus(String status);
}
```

## 🔴 Senior Level

### The EAGER Fetching Trap (Why EAGER Does NOT Prevent N+1)

A common misconception among intermediate developers is that changing `@ManyToOne(fetch = FetchType.EAGER)` solves the N+1 problem. **It actually makes it worse!**

```java
@Entity
public class Order {
    // ⚠️ ANTI-PATTERN: EAGER loading on ManyToOne
    @ManyToOne(fetch = FetchType.EAGER)
    private Customer customer;
}
```

- When calling `orderRepository.findAll()` (JPQL: `SELECT o FROM Order o`), Hibernate parses the JPQL query for `Order` first, executes `SELECT * FROM orders`, and then **fires $N$ separate queries to eagerly fetch each `Customer`**!
- Furthermore, you can no longer disable the secondary queries on endpoints that don't need `Customer`.

### The MultipleBagFetchException & Cartesian Product Hazard

Attempting to `JOIN FETCH` multiple collections (`List<OrderItem>` and `List<Payment>`) in a single query triggers Hibernate's `MultipleBagFetchException`:

```
  Cartesian Product Problem:
  • 10 Orders with 10 Items each and 5 Payments each:
  • Row count in result set = 10 * 10 * 5 = 500 rows returned over network!
```

#### Senior Architectural Remedy:
1. Fetch the first collection via `JOIN FETCH` (`JOIN FETCH o.items`).
2. Fetch the second collection via **Global Batch Fetching**:
   ```properties
   spring.jpa.properties.hibernate.default_batch_fetch_size=50
   ```
   (Hibernate loads all 50 `Payment` collections in 1 batch query: `WHERE order_id IN (?, ?, ...)`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** 1 initial query to fetch $N$ parents + $N$ secondary queries for lazy/eager child associations.
- **Top Solutions:** JPQL `JOIN FETCH`, Spring Data `@EntityGraph`, Batch fetching (`@BatchSize`), DTO Projections.
- **EAGER Myth:** `FetchType.EAGER` does **not** solve N+1 in JPQL queries; it makes lazy loading impossible.
- **Global Batch Size:** `hibernate.default_batch_fetch_size=50` is the safest global defense against N+1 queries across the entire application.
- **Multiple Collections:** Never `JOIN FETCH` multiple child `List` collections in a single query (Cartesian product).

**Common Follow-up Questions:**
- *"What is the difference between `JOIN` and `JOIN FETCH` in JPQL?"* → `JOIN` applies SQL join filtering in the `WHERE` clause but only populates the root entity fields in Java memory; `JOIN FETCH` initializes and populates the child collection/association into the persistent context.
- *"How do you detect N+1 queries automatically in automated tests?"* → Use libraries like `datasource-proxy` or `QuickPerf` (`@ExpectSelect(1)`), or enable `spring.jpa.show-sql=true` with `org.hibernate.stat` metrics logging.
- *"What is the difference between `jakarta.persistence.fetchgraph` and `jakarta.persistence.loadgraph`?"* → `fetchgraph` treats only specified attributes as EAGER and all others as LAZY; `loadgraph` treats specified attributes as EAGER and respects the pre-configured entity mapping for all others.

**Red Flags (DO NOT Say):**
- ❌ *"Changing all associations to `FetchType.EAGER` eliminates N+1 query issues."* (EAGER still fires N+1 queries in JPQL and creates permanent memory overhead).
- ❌ *"The N+1 problem only happens when using `FetchType.LAZY`."* (It happens on EAGER associations when queries are executed via JPQL or Criteria API).
- ❌ *"Always `JOIN FETCH` all 5 entity collections in a single query for maximum performance."* (Causes massive Cartesian products and `MultipleBagFetchException`).
