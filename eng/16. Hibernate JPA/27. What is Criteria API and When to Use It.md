# What is Criteria API and When to Use It?

---

## 🟢 Junior Level

The **JPA Criteria API** is a programmatic, strongly-typed Java API used to dynamically construct database queries as an object graph in code, rather than concatenating hardcoded string literals:

```
  Lego Brick Query Analogy:
  • JPQL / SQL: Writing a complete fixed story on paper (Rigid; difficult to add/remove paragraphs dynamically).
  • Criteria API: Building a structure out of modular Lego bricks (`CriteriaBuilder`, `Root`, `Predicate`). 
    You snap in search filter bricks only when the user fills out specific search fields!
```

```java
// 1. Obtain CriteriaBuilder:
CriteriaBuilder cb = entityManager.getCriteriaBuilder();
CriteriaQuery<User> query = cb.createQuery(User.class);

// 2. Define FROM clause:
Root<User> root = query.from(User.class);

// 3. Assemble SELECT and WHERE clauses:
query.select(root)
     .where(cb.greaterThan(root.get("age"), 18))
     .orderBy(cb.asc(root.get("name")));

// 4. Execute type-safe query:
List<User> users = entityManager.createQuery(query).getResultList();
```

## 🟡 Middle Level

### Dynamic Multi-Filter Search Queries

The primary production use case for Criteria API is building dynamic search screens with optional filters:

```java
public List<Product> searchProducts(String title, BigDecimal minPrice, BigDecimal maxPrice, String category) {
    CriteriaBuilder cb = entityManager.getCriteriaBuilder();
    CriteriaQuery<Product> query = cb.createQuery(Product.class);
    Root<Product> product = query.from(Product.class);

    List<Predicate> predicates = new ArrayList<>();

    // Conditionally attach filter predicates:
    if (title != null && !title.isBlank()) {
        predicates.add(cb.like(cb.lower(product.get("title")), "%" + title.toLowerCase() + "%"));
    }
    if (minPrice != null) {
        predicates.add(cb.greaterThanOrEqualTo(product.get("price"), minPrice));
    }
    if (maxPrice != null) {
        predicates.add(cb.lessThanOrEqualTo(product.get("price"), maxPrice));
    }
    if (category != null) {
        predicates.add(cb.equal(product.get("category"), category));
    }

    // Combine all predicates with boolean AND:
    query.where(cb.and(predicates.toArray(new Predicate[0])));

    return entityManager.createQuery(query).getResultList();
}
```

## 🔴 Senior Level

### True Compile-Time Type Safety: The JPA Static Metamodel

Using string property names (`product.get("title")`) is vulnerable to typo bugs and breaks during code refactoring. Generating the **JPA Static Metamodel** via `hibernate-jpamodelgen` provides 100% compile-time safety:

```xml
<!-- pom.xml: Generates Metamodel classes (e.g. Product_.java) at build time -->
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jpamodelgen</artifactId>
    <scope>provided</scope>
</dependency>
```

```java
// ✅ True Compile-Time Type-Safe Query using Generated Metamodel:
query.where(
    cb.greaterThanOrEqualTo(product.get(Product_.price), new BigDecimal("100.00")),
    cb.equal(product.get(Product_.status), ProductStatus.ACTIVE)
);
// If a developer renames 'price' to 'cost' in Product.java, the code fails at COMPILE TIME!
```

### Spring Data JPA `Specification<T>` (The Clean Architecture Standard)

In enterprise Spring Boot microservices, developers wrap Criteria API logic into composable **`Specification`** building blocks:

```java
public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> {
}

// Reusable business specifications:
public class ProductSpecs {
    public static Specification<Product> hasCategory(String category) {
        return (root, query, cb) -> category == null ? null : cb.equal(root.get(Product_.category), category);
    }

    public static Specification<Product> priceBetween(BigDecimal min, BigDecimal max) {
        return (root, query, cb) -> {
            if (min == null && max == null) return null;
            if (min != null && max != null) return cb.between(root.get(Product_.price), min, max);
            return min != null ? cb.ge(root.get(Product_.price), min) : cb.le(root.get(Product_.price), max);
        };
    }
}
```

```java
// Composing dynamic search queries cleanly:
Specification<Product> spec = Specification.where(ProductSpecs.hasCategory("Electronics"))
                                           .and(ProductSpecs.priceBetween(min, max));

Page<Product> results = productRepository.findAll(spec, pageable);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Programmatic, strongly-typed API for dynamically building queries in Java code.
- **Core Building Blocks:** `CriteriaBuilder` (factory), `CriteriaQuery<T>` (structure), `Root<T>` (FROM), `Predicate` (WHERE).
- **Primary Use Case:** Complex dynamic filtering and search screens with optional parameters.
- **Metamodel:** `Product_.title` provides compile-time property validation during Java compilation.
- **Spring Abstraction:** `JpaSpecificationExecutor` + `Specification<T>` provides modular, reusable Criteria predicates.

**Common Follow-up Questions:**
- *"How does Criteria API compare to QueryDSL?"* → QueryDSL has a much cleaner, fluent SQL-like syntax (`QProduct.product.price.gt(100)`), but is a third-party library; Criteria API is built into the official JPA standard.
- *"Why not just concatenate JPQL query strings for dynamic searches?"* → String concatenation is verbose, error-prone, fragile during refactoring, and vulnerable to SQL injection if parameters are not parameterized properly.
- *"Can Criteria API perform `JOIN FETCH` operations?"* → Yes; `root.fetch(Product_.items, JoinType.LEFT)` injects a join fetch into the criteria query.

**Red Flags (DO NOT Say):**
- ❌ *"You should write all standard static CRUD queries using Criteria API."* (Criteria API is excessively verbose; use standard Spring Data repository methods or JPQL for static queries).
- ❌ *"Criteria API queries run faster in PostgreSQL than identical JPQL queries."* (Both compile to the exact same SQL statement under the hood).
- ❌ *"Criteria API automatically validates database column names against Postgres at compile time."* (It validates Java entity properties via the JPA Metamodel).
