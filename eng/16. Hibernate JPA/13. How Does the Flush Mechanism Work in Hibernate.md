# How Does the Flush Mechanism Work in Hibernate?

---

## 🟢 Junior Level

The **Flush** mechanism in Hibernate synchronizes the state of the in-memory **Persistence Context** (`EntityManager` / L1 Cache) with the underlying relational database by executing pending SQL `INSERT`, `UPDATE`, and `DELETE` statements over the active JDBC connection:

```
  Document Draft vs. Save Analogy:
  • Working on Draft: You type text in your word processor (In-memory entity changes).
  • Flush (`em.flush()`): The word processor writes your changes to the temp file on disk 
    (Sends SQL statements to database; transaction remains open and uncommitted).
  • Commit (`tx.commit()`): You finalize the file and send it to the client 
    (Database `COMMIT` command executed; locks released; changes made permanent).
```

```java
@Transactional
public void updateUser() {
    User user = entityManager.find(User.class, 1L);
    user.setName("New Name"); // In-memory mutation

    // 1. Explicit Flush:
    entityManager.flush(); // Sends SQL UPDATE to DB immediately; transaction still open!

    // 2. Method Exit:
    // Spring executes COMMIT on the active database transaction.
}
```

## 🟡 Middle Level

### The 3 Triggers of the Flush Mechanism

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Flush Trigger                │ When & Why It Occurs                                                            │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Transaction Commit**    │ Triggered automatically before `transaction.commit()` completes.                │
  │ **2. Prior to JPQL Queries** │ In `FlushModeType.AUTO`, flushes pending writes to ensure the query returns     │
  │                              │ fresh, up-to-date data instead of stale database rows.                          │
  │ **3. Explicit Invocation**   │ When the developer explicitly calls `entityManager.flush()`.                    │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### FlushMode Options

```java
// 1. FlushModeType.AUTO (Default):
// Flushes before transaction commit AND before executing queries on modified tables:
entityManager.setFlushMode(FlushModeType.AUTO);

// 2. FlushModeType.COMMIT:
// Flushes ONLY during transaction commit. Queries do NOT trigger flushes:
entityManager.setFlushMode(FlushModeType.COMMIT);
```

```
  ⚠️ The Auto-Flush Query Behavior:
  1. `user.setStatus("VIP");` (Dirty in memory)
  2. `entityManager.createQuery("SELECT u FROM User u WHERE u.status = 'VIP'").getResultList();`
  3. Hibernate detects that the query targets `users` ──► Executes `flush()` FIRST, 
     then runs the SELECT so the modified user is included in the result set!
```

## 🔴 Senior Level

### Under the Hood: Hibernate `ActionQueue` Execution Order

When `flush()` runs, Hibernate does **not** execute statements in the order your Java code ran. It groups and executes all pending actions in the internal **`ActionQueue`** using a strict deterministic order:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ HIBERNATE ACTIONQUEUE EXECUTION ORDER:                                                        │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 1. `OrphanRemovalAction`                                                                      │
  │ 2. `EntityInsertAction` (All SQL INSERTs)                                                     │
  │ 3. `EntityUpdateAction` (All SQL UPDATEs)                                                     │
  │ 4. `CollectionRemoveAction`                                                                   │
  │ 5. `CollectionUpdateAction`                                                                   │
  │ 6. `CollectionRecreateAction`                                                                 │
  │ 7. `EntityDeleteAction` (All SQL DELETEs executed LAST!)                                      │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

### The Unique Constraint Collision Hazard (Why Deletes Run Last)

```java
// ❌ THE UNIQUE CONSTRAINT TRAP:
// Assume table `users` has a UNIQUE constraint on `username`.
User oldUser = userRepository.findByUsername("alice").orElseThrow();
userRepository.delete(oldUser); // Marks for DELETE

User newUser = new User("alice");
userRepository.save(newUser); // Queues INSERT

// 💥 CRASH on flush! 
// Because ActionQueue runs INSERT before DELETE:
// 1. Executes INSERT INTO users (username='alice') ──► UNIQUE CONSTRAINT VIOLATION!
// 2. DELETE was never reached!

// ✅ THE PRODUCTION FIX:
userRepository.delete(oldUser);
entityManager.flush(); // Force DELETE to execute on DB FIRST!
userRepository.save(newUser);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Flush vs Commit:** `flush()` writes SQL statements to the database connection; `commit()` finalizes the database transaction permanently.
- **Triggers:** Auto-flush runs before transaction commit and before JPQL queries touching dirty tables.
- **`ActionQueue` Order:** `INSERT` statements are executed **before** `DELETE` statements during flush.
- **Unique Constraint Trap:** Deleting a row and inserting a replacement with the same unique key requires an explicit `em.flush()` between the operations.
- **Read-Only Speed:** Setting `@Transactional(readOnly = true)` switches flush mode to `MANUAL`, skipping flush comparisons.

**Common Follow-up Questions:**
- *"Does calling `em.flush()` commit the transaction?"* → No; `flush()` only executes the SQL statements against the open database transaction; if an exception occurs later, the transaction can still be rolled back completely.
- *"Can an uncommitted flushed change be seen by other concurrent database transactions?"* → In standard `READ_COMMITTED` isolation, other transactions **cannot** see flushed uncommitted changes until the transaction executes `COMMIT`.
- *"What happens to the First-Level Cache when you call `flush()`?"* → Entities remain in the First-Level Cache (Managed state); their dirty checking snapshots are simply updated to match the database.

**Red Flags (DO NOT Say):**
- ❌ *"Calling `em.flush()` makes changes permanent and impossible to roll back."* (A transaction rollback undoes flushed changes).
- ❌ *"Hibernate executes SQL statements in the exact order you wrote them in Java."* (Hibernate re-orders statements via `ActionQueue`: Inserts first, Deletes last).
- ❌ *"`em.clear()` flushes changes to the database before clearing."* (`clear()` discards all un-flushed changes without saving them).
