# When to Use Lazy vs Eager Loading?

---

## 🟢 Junior Level

In modern enterprise Java development, the universal best practice is: **Always default to `FetchType.LAZY` for 100% of entity relationships**:

```
  Buffet Dining Analogy:
  • EAGER Loading: The waiter forces 25 full dishes onto your table the second you sit down, 
    even if you only came for a cup of coffee (Wasted food, full table, slow service).
  • LAZY Loading + Dynamic Fetching: You sit down, drink your coffee, and only walk to the 
    buffet to pick up specific dishes when you are actually hungry!
```

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ THE GOLDEN RULE OF MODERN JPA:                                                  │
  │ • Set `fetch = FetchType.LAZY` on ALL mappings (@ManyToOne, @OneToOne, etc.).   │
  │ • Fetch associations dynamically per use case using `JOIN FETCH` or EntityGraph!│
  └─────────────────────────────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### Why Static `FetchType.EAGER` is an Anti-Pattern

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Architectural Hazard            │ Technical Consequence                                                           │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Cannot be Overridden**        │ Once mapped as EAGER, no JPQL query or hint can turn it off for that request!   │
  │ **Cascading Graph Explosion**   │ If Order ➔ Customer (EAGER) and Customer ➔ Address (EAGER), loading 1 Order     │
  │                                 │ loads the entire relational database graph into memory!                         │
  │ **N+1 Query Amplification**     │ JPQL `SELECT o FROM Order o` still executes $N$ secondary queries for EAGER.    │
  │ **Severe Memory Waste**         │ REST endpoints that only need `orderId` and `totalAmount` wastefully load       │
  │                                 │ megabytes of unneeded child objects into the JVM heap.                          │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Static Mapping vs. Dynamic Query-Time Fetching

```java
// 1. Static Entity Mapping (Always LAZY!):
@Entity
public class Order {
    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY) // Override default EAGER!
    private Customer customer;

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<OrderItem> items;
}
```

```java
// 2. Dynamic Fetching tailored to specific business use cases:
public interface OrderRepository extends JpaRepository<Order, Long> {

    // Use Case A: Lightweight dashboard list (Loads ONLY Order columns):
    @Query("SELECT o FROM Order o WHERE o.status = :status")
    List<Order> findLightweightOrders(@Param("status") String status);

    // Use Case B: Full invoice generation (Loads Order + Customer + Items in 1 query):
    @Query("SELECT o FROM Order o JOIN FETCH o.customer JOIN FETCH o.items WHERE o.id = :id")
    Optional<Order> findOrderForInvoice(@Param("id") Long id);
}
```

## 🔴 Senior Level

### The Dynamic Fetching Decision Matrix

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Business Scenario            │ Recommended JPA Pattern      │ Performance Impact                               │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Read-Only REST APIs**      │ **DTO Projections** / Record │ ⚡ **Fastest**: Bypasses entity lifecycle & L1   │
  │ (Displaying tables/grids)    │ `SELECT new OrderDTO(...)`   │ cache snapshots entirely. 0% proxy overhead.     │
  │ **Transactional Mutations**  │ `JOIN FETCH` / `@EntityGraph`│ 🚀 **High**: Fetches aggregate root and children │
  │ (Modifying order & items)    │                              │ in 1 query for atomic state modification.        │
  │ **Batch Processing (ETL)**   │ `default_batch_fetch_size`   │ ⚖️ **Predictable**: Flattens $N$ lazy loads into │
  │ (Iterating 10,000 records)   │                              │ SQL `WHERE id IN (?, ?, ...)` batches.           │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### The Only Legitimate Exceptions for EAGER
- Value Objects and Components mapped via `@Embedded` / `@Embeddable` (part of the same database row).
- Strictly mandatory single-column foreign key relationships where the child is mapped with `optional = false` and accessed in literally 100% of all queries across the entire codebase.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The Rule:** Always use `FetchType.LAZY` for all relationships in entity class mappings.
- **Dynamic Fetching:** Decide what to fetch dynamically at the repository query level (`JOIN FETCH`, `@EntityGraph`).
- **EAGER Trap:** Static EAGER cannot be disabled per query and triggers cascading database queries.
- **DTO Optimization:** Use Java Record DTO projections for read-only query endpoints.
- **Batch Safety:** Use `hibernate.default_batch_fetch_size=50` to mitigate unexpected lazy queries.

**Common Follow-up Questions:**
- *"Why does JPA specify EAGER as the default for `@ManyToOne` if it is an anti-pattern?"* → Historical legacy from the early EJB/JPA 1.0 specification (2006); modern high-performance architectures always override it to `LAZY`.
- *"How does `@EntityGraph` differ from `JOIN FETCH`?"* → `JOIN FETCH` is hardcoded directly inside JPQL/HQL queries; `@EntityGraph` can be applied declaratively as an annotation over Spring Data derived query methods or injected dynamically via EntityManager query hints.
- *"What happens if you use `JOIN FETCH` with pagination (`Pageable`)?"* → Hibernate issues a warning (`HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!`) and fetches the **entire table into memory** before paginating in Java RAM!

**Red Flags (DO NOT Say):**
- ❌ *"I always use Eager loading because it prevents `LazyInitializationException`."* (This is the worst possible fix; it destroys performance. Fix the transaction boundary or use `JOIN FETCH` instead).
- ❌ *"Eager loading is fine if the database has only 1,000 rows."* (Applications grow; static Eager loading creates massive technical debt).
- ❌ *"You can easily disable an `@ManyToOne(fetch=EAGER)` mapping dynamically when executing a light query."* (EAGER cannot be turned off per query).
