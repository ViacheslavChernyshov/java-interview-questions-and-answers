# How to Implement Optimistic Locking in JPA?

---

## 🟢 Junior Level

**Optimistic Locking** is a concurrency control strategy that assumes conflicting data modifications are rare. Instead of locking database rows with physical database locks, transactions read data freely and verify at update time that no other transaction has modified the data in the interim:

```
  Wiki Article Edit Analogy:
  • Two editors (Tx 1 and Tx 2) open the same article at Version 1.
  • Editor 1 finishes first and saves their changes ──► Article becomes Version 2.
  • Editor 2 clicks "Save" 5 seconds later attempting to overwrite Version 1:
  • The system rejects Editor 2 with an edit conflict (💥 OptimisticLockException!), 
    asking them to refresh and merge changes!
```

```java
@Entity
@Table(name = "orders")
public class Order {
    @Id
    private Long id;

    // Hibernate automatically increments and validates this version field on every UPDATE:
    @Version
    private Long version;

    private String status;
}
```

## 🟡 Middle Level

### The Under-the-Hood SQL Mechanism

When updating an entity annotated with `@Version`:

```sql
-- Generated SQL UPDATE:
UPDATE orders 
SET status = 'SHIPPED', version = 2 
WHERE id = 100 AND version = 1;
```

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ EVALUATION OF JDBC ROW COUNT:                                                                 │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ • **If 1 row updated:** Success! Transaction progresses normally.                             │
  │ • **If 0 rows updated:** Another transaction already incremented the version to 2!            │
  │   Hibernate immediately aborts and throws `jakarta.persistence.OptimisticLockException`!     │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### LockModeType: `OPTIMISTIC` vs. `OPTIMISTIC_FORCE_INCREMENT`

```
  ┌──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Lock Mode                        │ Operational Behavior & Use Case                                                 │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`OPTIMISTIC`**                 │ Verifies at commit time that the entity's version hasn't changed. Guarantees   │
  │ (Read Lock)                      │ repeatable reads across long transactions without physical DB locks.            │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`OPTIMISTIC_FORCE_INCREMENT`** │ Forces an unconditional version increment even if the parent entity's scalar    │
  │ (Aggregate Root Lock)            │ fields didn't change (e.g. when adding an item to a child collection).          │
  └──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

```java
// Example: Bumping parent Order version when adding a child OrderItem:
@Transactional
public void addItemToOrder(Long orderId, OrderItem item) {
    Order order = entityManager.find(Order.class, orderId, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
    order.getItems().add(item);
    item.setOrder(order);
    // On commit, Hibernate increments Order's version, preventing concurrent child modifications!
}
```

### Spring Boot Automated Retry Blueprint

In high-concurrency systems, optimistic lock collisions should be retried automatically with exponential backoff:

```java
@Service
@RequiredArgsConstructor
public class OrderProcessingService {

    private final OrderRepository orderRepository;

    @Retryable(
        retryFor = {ObjectOptimisticLockingFailureException.class, OptimisticLockException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 100, multiplier = 2.0)
    )
    @Transactional
    public void updateOrderStatus(Long orderId, String newStatus) {
        Order order = orderRepository.findById(orderId)
            .orElseThrow(() -> new EntityNotFoundException("Order not found: " + orderId));

        order.setStatus(newStatus);
        // If conflict occurs, Spring catches exception, rolls back, and retries automatically!
    }

    @Recover
    public void handleLockFailure(OptimisticLockException e, Long orderId, String newStatus) {
        log.error("Failed to update order {} after 3 attempts due to concurrent edits.", orderId);
        throw new BusinessConflictException("Concurrent edit conflict. Please refresh the page.");
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Non-blocking concurrency control using a version check during SQL `UPDATE`.
- **`@Version`:** Placed on `Long`, `Integer`, `Short`, or `Timestamp` fields.
- **SQL Condition:** Uses `WHERE id = ? AND version = ?`; throws exception if row count is 0.
- **Exception Thrown:** `jakarta.persistence.OptimisticLockException` (Spring: `ObjectOptimisticLockingFailureException`).
- **`FORCE_INCREMENT`:** Used on Aggregate Roots to increment version when child collections change.

**Common Follow-up Questions:**
- *"Can you have multiple `@Version` properties on a single entity?"* → No; JPA strictly enforces at most one `@Version` field per entity.
- *"What happens if the application manually modifies the `@Version` getter/setter?"* → Application code should **never mutate version properties**; Hibernate exclusively manages version increments.
- *"When should you choose Optimistic Locking over Pessimistic Locking?"* → Choose Optimistic Locking for read-heavy workloads with low collision rates and web user interactions; choose Pessimistic Locking for high-contention financial ledger writes.

**Red Flags (DO NOT Say):**
- ❌ *"Optimistic locking places an exclusive row lock on the database table during the entire transaction."* (Optimistic locking places zero database locks; it only checks the version column on update).
- ❌ *"You should manually write `WHERE version = :version` in all your JPQL queries."* (Hibernate automatically appends the version check to all generated SQL UPDATE/DELETE statements).
- ❌ *"Optimistic locking prevents dirty reads during the initial SELECT query."* (Dirty reads are governed by the database transaction isolation level, not optimistic locking).
