# How to Implement Pessimistic Locking in JPA?

---

## 🟢 Junior Level

**Pessimistic Locking** is a concurrency control strategy that assumes data conflicts are frequent. It acquires **physical database-level row locks** at the exact moment an entity is read, blocking all other concurrent transactions from modifying or locking those rows until the transaction finishes (`COMMIT` or `ROLLBACK`):

```
  Single-Stall Restroom Analogy:
  • You walk into the restroom and physically turn the deadbolt lock (PESSIMISTIC_WRITE).
  • Anyone else who arrives must wait outside the door in line until you finish and unlock the door.
  • Prevents two people from using the room at the same time, completely eliminating race conditions!
```

```java
// Spring Data JPA Pessimistic Write Lock:
public interface AccountRepository extends JpaRepository<Account, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") Long id);
}
```

```sql
-- Generated SQL statement sent to database:
SELECT id, balance, owner FROM accounts WHERE id = 1 FOR UPDATE;
```

## 🟡 Middle Level

### The 3 Pessimistic Lock Modes

```
  ┌──────────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ LockModeType                     │ Generated SQL Syntax         │ Operational Behavior & Concurrency               │
  ├──────────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`PESSIMISTIC_READ`**           │ `SELECT ... FOR SHARE`       │ Shared Read Lock: Others can read, but cannot    │
  │                                  │ (or `LOCK IN SHARE MODE`)    │ update or delete the locked rows.                │
  ├──────────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`PESSIMISTIC_WRITE`**          │ `SELECT ... FOR UPDATE`      │ 🛡️ Exclusive Lock: Blocks all concurrent read/  │
  │                                  │                              │ write locks until transaction commits.           │
  ├──────────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`PESSIMISTIC_FORCE_INCREMENT`**│ `SELECT ... FOR UPDATE` +    │ Exclusive Lock + automatically increments the    │
  │                                  │ `UPDATE ... SET version=v+1` │ entity's `@Version` property upon commit.        │
  └──────────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Lock Timeouts: `NOWAIT` and `SKIP LOCKED`

Indefinite blocking on database locks degrades throughput and causes connection pool exhaustion. Configure lock timeouts using JPA query hints:

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Timeout Value / Hint         │ Generated SQL (Postgres/Ora) │ Behavior                                         │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`timeout = 0`**            │ `SELECT ... FOR UPDATE NOWAIT`│ Fails immediately with `PessimisticLockException`│
  │                              │                              │ if the row is already locked by another worker.  │
  │ **`timeout = 5000`**         │ `SELECT ... FOR UPDATE WAIT 5`│ Blocks up to 5 seconds before failing.           │
  │ **`SKIP LOCKED`** (Hint)     │ `SELECT ... SKIP LOCKED`     │ 🚀 Skips locked rows and returns unlocked rows   │
  │                              │                              │ (Standard pattern for DB message queues / jobs). │
  └──────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

```java
// Example: High-Throughput Background Job Polling using SKIP LOCKED:
public interface TaskQueueRepository extends JpaRepository<TaskQueue, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({
        @QueryHint(name = AvailableHints.HINT_SPEC_LOCK_TIMEOUT, value = "-2") // -2 maps to SKIP LOCKED
    })
    @Query("SELECT t FROM TaskQueue t WHERE t.status = 'PENDING' ORDER BY t.priority DESC")
    List<TaskQueue> fetchNextAvailableTasks(Pageable pageable);
}
```

### Deadlock Prevention in High-Concurrency Financial Transfers

When two transactions lock the same resources in reverse order, a **Database Deadlock** occurs:

```
  Tx 1: Locks Account #10 ──► Attempts to lock Account #20 (Blocked by Tx 2!)
  Tx 2: Locks Account #20 ──► Attempts to lock Account #10 (Blocked by Tx 1!)
  💥 RESULT: Database deadlock detector kills one transaction with `DeadlockLoserDataAccessException`!
```

#### Senior Architectural Solution: Deterministic Lock Ordering
Always sort resource IDs before acquiring pessimistic locks:

```java
@Transactional
public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
    // 1. Sort IDs to enforce global deterministic lock order:
    Long firstId = fromId < toId ? fromId : toId;
    Long secondId = fromId < toId ? toId : fromId;

    // 2. Acquire locks in strict numerical ascending order:
    Account firstAccount = accountRepository.findByIdForUpdate(firstId).orElseThrow();
    Account secondAccount = accountRepository.findByIdForUpdate(secondId).orElseThrow();

    Account from = fromId.equals(firstId) ? firstAccount : secondAccount;
    Account to = toId.equals(secondId) ? secondAccount : firstAccount;

    from.debit(amount);
    to.credit(amount);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Physical database-level row locking (`SELECT ... FOR UPDATE`) acquired during the initial read.
- **`PESSIMISTIC_WRITE`:** Exclusive row lock; prevents concurrent updates and shared locks.
- **`PESSIMISTIC_READ`:** Shared read lock (`FOR SHARE`); permits concurrent reads, blocks updates.
- **`NOWAIT` / `SKIP LOCKED`:** Eliminates thread blocking; `SKIP LOCKED` powers transactional message queues.
- **Deadlock Mitigation:** Always acquire multiple locks in strict deterministic ascending ID order.

**Common Follow-up Questions:**
- *"What happens if a transaction holding a pessimistic lock crashes or loses its network connection?"* → The database connection drops, and the relational database automatically rolls back the uncommitted transaction and releases all row locks.
- *"How does Pessimistic Locking affect database connection pool sizing?"* → Long-running transactions with pessimistic locks hold database connections open, rapidly exhausting the HikariCP pool; keep pessimistic transactions strictly under 100ms.
- *"What exception is thrown when a lock acquisition times out?"* → Throws `jakarta.persistence.PessimisticLockException` or `jakarta.persistence.LockTimeoutException` (Spring: `CannotAcquireLockException`).

**Red Flags (DO NOT Say):**
- ❌ *"Pessimistic locks are held in Java memory by the JVM."* (Pessimistic locks are physical database engine row locks).
- ❌ *"Use Pessimistic Locking on all database queries for safety."* (Creates severe database lock contention and destroys system throughput).
- ❌ *"Pessimistic locking works across disconnected web sessions."* (Pessimistic locks require an active, open database connection and cannot span disconnected HTTP requests).
