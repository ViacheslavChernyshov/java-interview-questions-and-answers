# What are the Main Instructions Used in Dockerfile?

---

## 🟢 Junior Level

A Dockerfile uses a set of standardized instructions to define how an image is built:

```
  ┌──────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Instruction  │ Category                                 │ Primary Purpose                                  │
  ├──────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ `FROM`       │ Environment                              │ Sets the base image (e.g. `eclipse-temurin:21`). │
  │ `WORKDIR`    │ Environment                              │ Sets working directory for subsequent commands.  │
  │ `COPY`       │ Filesystem                               │ Copies local files/directories into the image.   │
  │ `ADD`        │ Filesystem                               │ Copies files, auto-extracts `.tar.gz` archives.  │
  │ `RUN`        │ Build-Time                               │ Executes commands and creates a new image layer. │
  │ `CMD`        │ Runtime                                  │ Default arguments/command for container startup. │
  │ `ENTRYPOINT` │ Runtime                                  │ Fixed executable binary that runs on startup.    │
  │ `ENV`        │ Environment                              │ Sets persistent environment variables.           │
  │ `ARG`        │ Environment                              │ Sets build-time-only variables.                  │
  │ `EXPOSE`     │ Network                                  │ Documents container listening port (Metadata).   │
  │ `USER`       │ Security                                 │ Sets UID/user for non-root execution.            │
  └──────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

```dockerfile
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

## 🟡 Middle Level

### Crucial Instruction Comparisons

#### 1. `COPY` vs. `ADD`
- **`COPY` (Best Practice):** Straightforward, predictable file copying from local build context.
- **`ADD`:** Can automatically extract compressed `.tar.gz` archives on the fly. Avoid using `ADD` to fetch remote URLs (use `RUN curl` or `wget` instead to control caching and verification).

#### 2. `ARG` vs. `ENV`

```
  ┌──────────────────────┬──────────────────────────┬──────────────────────────┬───────────────────────────────────────┐
  │ Variable Type        │ Available at Build Time? │ Available at Runtime?    │ Security Hazard                       │
  ├──────────────────────┼──────────────────────────┼──────────────────────────┼───────────────────────────────────────┤
  │ **`ARG`**            │ ✅ **Yes**               │ ❌ **No**                │ ⚠️ **Visible in `docker history`!**   │
  │ **`ENV`**            │ ✅ **Yes**               │ ✅ **Yes** (Container)   │ ⚠️ **Visible in `docker inspect`!**   │
  └──────────────────────┴──────────────────────────┴──────────────────────────┴───────────────────────────────────────┘
```

> [!CAUTION]
> **Never pass passwords or API tokens via `ARG` or `ENV`!** Use Docker BuildKit secret mounts (`RUN --mount=type=secret`) instead.

#### 3. Single-Layer Cleanup Rule for `RUN`
In Overlay2 filesystem layers, deleting a file in a separate `RUN` step creates a "whiteout" marker but **leaves the physical bytes trapped in the underlying layer**:

```dockerfile
# ❌ BAD: Leaves 50MB of apt-cache in lower layer:
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# ✅ GOOD: Cleans cache in the SAME atomic layer:
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*
```

## 🔴 Senior Level

### Exec Form vs. Shell Form: The PID 1 Graceful Shutdown Problem

Instructions (`RUN`, `CMD`, `ENTRYPOINT`) can be written in two syntactic forms:

```
  1. Exec Form (Canonical & Mandatory for Production):
     ENTRYPOINT ["java", "-jar", "app.jar"]
     • Spawns the `java` process directly as PID 1.
     • Receives OS signals (`SIGTERM`, `SIGINT`) immediately, enabling 
       Spring Boot Graceful Shutdown within Kubernetes termination grace periods.

  2. Shell Form (Anti-Pattern):
     ENTRYPOINT java -jar app.jar
     • Spawns `/bin/sh -c "java -jar app.jar"`.
     • The shell becomes PID 1 and drops `SIGTERM` signals!
     • When Kubernetes deletes the pod, Java never receives `SIGTERM`; 
       after 30 seconds, K8s forcefully kills the container with `SIGKILL` (Exit 137), 
       corrupting in-flight database transactions!
```

### BuildKit Secret Mounts

```dockerfile
# Secure Maven build without leaking ~/.m2/settings.xml to Docker history:
RUN --mount=type=secret,id=mvn_settings,target=/root/.m2/settings.xml \
    mvn clean package -DskipTests
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`RUN` vs `CMD` vs `ENTRYPOINT`:** `RUN` executes at build-time to create layers; `ENTRYPOINT` defines the runtime process; `CMD` provides default overrideable parameters.
- **Exec Form:** Always use JSON array format `["executable", "param"]` to ensure the process runs as PID 1 and receives `SIGTERM` for graceful shutdown.
- **`EXPOSE`:** Purely documentary; does not map or publish host ports (requires `-p 8080:8080` at runtime).
- **Layer Optimization:** Combine `apt-get install` and cache cleanup in a single `RUN` line to prevent image bloat.
- **Secret Safety:** `ARG` values are visible in plain text via `docker history`; use BuildKit secret mounts for credentials.

**Common Follow-up Questions:**
- *"What is the difference between `WORKDIR /app` and `RUN cd /app`?"* → `RUN cd /app` only changes the directory for that single temporary layer; `WORKDIR /app` persists the working directory for all subsequent instructions and runtime container execution.
- *"Why does `EXPOSE 8080` not make the container accessible from the host browser?"* → `EXPOSE` is metadata; host port binding requires runtime flag `-p <host_port>:<container_port>`.
- *"How do you pass environment variables dynamically when launching a container?"* → Use `docker run -e DB_URL="jdbc:..."` or load an env file with `docker run --env-file .env`.

**Red Flags (DO NOT Say):**
- ❌ *"Using `RUN cd /app` changes the working directory for the rest of the Dockerfile."* (Each `RUN` runs in a new subshell; you must use `WORKDIR`).
- ❌ *"Shell form `ENTRYPOINT java -jar app.jar` is identical to exec form."* (Shell form wraps execution in `/bin/sh`, breaking signal propagation and graceful shutdown).
- ❌ *"`EXPOSE 8080` automatically opens port 8080 on the host machine."* (It is documentation only; port mapping requires `-p`).
