# What is Ingress in Kubernetes?

---

## 🟢 Junior Level

An **Ingress** is an API object that manages external Layer 7 (HTTP/HTTPS) access to internal cluster Services, providing host-based and path-based routing, SSL/TLS termination, and centralized traffic entry:

```
  Airport Reception Analogy:
  • External Visitors arrive at a single airport main gate (Public Ingress IP).
  • Receptionist (Ingress) checks boarding passes (Host/Path):
    - "api.company.com" ──► Gate A (Order Service)
    - "store.company.com" ──► Gate B (Web Frontend)
```

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 80
      - path: /payments
        pathType: Prefix
        backend:
          service:
            name: payment-service
            port:
              number: 80
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls-cert
```

## 🟡 Middle Level

### The Ingress Resource vs. Ingress Controller

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Component                       │ Architectural Responsibility                                                    │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Ingress Resource**            │ Declarative YAML storing rules, hosts, paths, and TLS secrets in `etcd`.        │
  │ **Ingress Controller**          │ Active reverse proxy (NGINX, Traefik, HAProxy, Envoy) that watches the K8s API │
  │                                 │ and continuously updates its internal routing table.                            │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> Creating an Ingress YAML manifest does **nothing** by itself. You must have an active **Ingress Controller** deployed in your cluster!

### Complete Network Ingestion Path

```
  [Internet User]
        │
        ▼
  [Cloud Load Balancer] (Single Public IP: 198.51.100.1)
        │
        ▼
  [Ingress Controller Pod (NGINX)] ──► Terminates HTTPS SSL/TLS
        │ (L7 Host/Path Matching)
        ▼
  [Internal Service (ClusterIP)]
        │ (L4 Routing / iptables)
        ▼
  [Backend Spring Boot Pod]
```

## 🔴 Senior Level

### SSL Automation (`cert-manager`) & The Gateway API Evolution

1. **Automated TLS Lifecycle via `cert-manager`:**
   - In production, Ingress annotations trigger `cert-manager` to solve ACME HTTP-01 or DNS-01 challenges, obtaining and automatically renewing Let's Encrypt X.509 certificates into Kubernetes TLS Secrets.

2. **The Modern Successor: Gateway API (v1.0+ GA):**
   - The classic Ingress API suffered from vendor-specific annotation bloat (e.g. `nginx.ingress.kubernetes.io/*`).
   - The **Kubernetes Gateway API** replaces Ingress with clean, role-oriented CRDs:
     - **`GatewayClass`:** Managed by Infrastructure Team (Defines Envoy/Cilium controllers).
     - **`Gateway`:** Managed by Cluster Ops (Defines IP, Port 443, TLS listeners).
     - **`HTTPRoute`:** Managed by Application Developers (Defines path routing, header matching, canary weight splits).

```yaml
# Next-Gen Canary Deployment using Gateway API HTTPRoute:
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-route
spec:
  parentRefs:
  - name: main-gateway
  rules:
  - matches:
    - path: { type: PathPrefix, value: /orders }
    backendRefs:
    - name: order-service-v1
      port: 80
      weight: 90 # 90% traffic to stable version
    - name: order-service-v2
      port: 80
      weight: 10 # 10% traffic to canary version
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Layer 7 Routing:** Ingress routes based on HTTP Host headers (`api.example.com`) and URL path prefixes (`/orders`).
- **Resource vs Controller:** Ingress is the YAML declaration; Ingress Controller (NGINX/Envoy) is the running proxy that executes routing.
- **Cost Efficiency:** Consolidates hundreds of internal microservices behind a single cloud LoadBalancer IP.
- **TLS Termination:** Decrypts HTTPS traffic at the cluster perimeter and passes unencrypted HTTP inside the private cluster network.
- **Modern Standard:** The Kubernetes **Gateway API** (`HTTPRoute`) is the next-generation standard replacing classic Ingress.

**Common Follow-up Questions:**
- *"What happens if you deploy an Ingress manifest without an Ingress Controller?"* → The Ingress resource is saved successfully in `etcd`, but no routing occurs and the Ingress never receives an external IP address.
- *"What is the difference between PathType `Prefix` and `Exact`?"* → `Prefix` matches URL paths based on URL segments split by `/` (`/v1` matches `/v1/users`); `Exact` requires a 100% literal match.
- *"How do you handle sticky sessions (session affinity) in Ingress?"* → By adding controller-specific annotations (e.g., `nginx.ingress.kubernetes.io/affinity: "cookie"`).

**Red Flags (DO NOT Say):**
- ❌ *"An Ingress is a hardware router installed in the data center."* (It is a Kubernetes software Layer 7 reverse proxy).
- ❌ *"Creating an Ingress YAML manifest automatically provisions a load balancer without any controller installed."* (Ingress requires an active Ingress Controller daemon).
- ❌ *"Ingress is designed for low-level TCP/UDP socket traffic like raw database queries."* (Ingress is strictly Layer 7 HTTP/HTTPS; use Layer 4 Services for raw TCP/UDP).
