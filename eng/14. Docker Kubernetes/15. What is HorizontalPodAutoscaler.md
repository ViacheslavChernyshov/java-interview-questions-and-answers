# What is HorizontalPodAutoscaler?

---

## 🟢 Junior Level

The **HorizontalPodAutoscaler (HPA)** is a built-in Kubernetes controller that automatically scales the number of Pod replicas up or down based on real-time resource utilization (CPU, memory) or custom application metrics:

```
  Traffic Surge Analogy:
  • High CPU Spike (>70%) ──► HPA scales out replicas from 2 to 8 Pods.
  • Traffic Returns to Normal ──► HPA gradually scales in back to 2 Pods.
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

```
  2 Mandatory Prerequisites:
  1. Metrics Server: Must be installed in the cluster to supply CPU/Memory telemetry.
  2. Resource Requests: The target container MUST define `resources.requests.cpu`.
```

## 🟡 Middle Level

### The 4 Metric Types Supported in `autoscaling/v2`

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Metric Type          │ Data Provider                │ Real-World Example                               │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Resource**         │ Kubernetes Metrics Server    │ Average CPU / RAM utilization across pods.       │
  │ **Pods**             │ Custom Metrics API (Prom)    │ Average HTTP requests per second per pod.        │
  │ **Object**           │ Custom Metrics API           │ Ingress Controller throughput / HTTP 5xx error %.│
  │ **External**         │ External Metrics API / KEDA  │ AWS SQS queue depth, Kafka consumer lag.         │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### Why Autoscaling Java Applications on Memory is Dangerous

```
  ⚠️ The JVM Memory Allocation Trap:
  • Java JVM allocates memory up to `-Xmx` (or `MaxRAMPercentage`) and does NOT immediately 
    release free heap memory back to the Linux OS after garbage collection.
  • HPA sees container memory at 85% constantly (even when the app is completely idle!).
  • Result: HPA scales the Deployment out to `maxReplicas` and NEVER scales back down!

  ✅ Production Rule: Scale Java workloads primarily on CPU, HTTP RPS, or Queue Lag.
```

## 🔴 Senior Level

### Advanced Scaling Policies & Anti-Flapping Stabilization Windows

To prevent rapid scale oscillation (flapping) during erratic traffic bursts, declare granular scaling behaviors:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: billing-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: billing-service
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 65
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0 # React to traffic spikes immediately!
      policies:
      - type: Percent
        value: 100 # Double capacity every 15 seconds if needed
        periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300 # Wait 5 minutes before scale-down (Anti-Flapping)
      policies:
      - type: Percent
        value: 10 # Only remove max 10% of pods per minute
        periodSeconds: 60
```

### Event-Driven Autoscaling with KEDA (Kafka / SQS / RabbitMQ)

For asynchronous worker pods consuming message brokers, standard CPU scaling is ineffective because idle consumers show 0% CPU even with 1,000,000 unconsumed messages in the topic.
- **KEDA (Kubernetes Event-driven Autoscaling):** Intercepts Kafka partition lag metrics and feeds them into HPA, scaling worker pods from **0 to N replicas** based directly on queue depth.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Autoscaling controller that dynamically adjusts Deployment replica count based on metrics.
- **Formula:** $\text{DesiredReplicas} = \left\lceil \text{CurrentReplicas} \times \left( \frac{\text{CurrentMetric}}{\text{TargetMetric}} \right) \right\rceil$.
- **Hard Prerequisite:** Requires **Metrics Server** and defined `resources.requests`.
- **Memory Scaling Hazard:** Java heap retention keeps container memory elevated, causing permanent max-replica scale out.
- **Stabilization Window:** `behavior.scaleDown.stabilizationWindowSeconds` prevents pod flapping.

**Common Follow-up Questions:**
- *"How frequently does the HPA loop evaluate metrics?"* → Every **15 seconds** by default (configured via `kube-controller-manager` flag `--horizontal-pod-autoscaler-sync-period`).
- *"Can HPA scale a Deployment down to 0 replicas?"* → Standard K8s HPA supports `minReplicas: 1`; scaling to `0` requires **KEDA** (Kubernetes Event-driven Autoscaling).
- *"What happens if multiple metrics (e.g. CPU and Custom RPS) are specified in the same HPA?"* → HPA calculates the desired replica count for **each** metric independently and scales to the **highest** calculated replica count.

**Red Flags (DO NOT Say):**
- ❌ *"HPA scales individual worker nodes when the cluster runs out of memory."* (HPA only scales Pods; Cluster Autoscaler or Karpenter scales Nodes).
- ❌ *"Setting HPA target to 99% CPU is best practice for cost optimization."* (High targets leave no headroom for traffic spikes, leading to 504 Gateway Timeouts).
- ❌ *"HPA calculates memory usage based on the container's `resources.limits`."* (HPA evaluates metrics against `resources.requests`).
