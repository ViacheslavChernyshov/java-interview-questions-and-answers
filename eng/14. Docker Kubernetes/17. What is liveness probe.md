# What is Liveness Probe?

---

## 🟢 Junior Level

A **Liveness Probe** is a health check configured in Kubernetes and executed periodically by `kubelet` to verify whether an application container is alive and operating normally:

```
  Heartbeat Analogy:
  • `kubelet` taps the container on the shoulder every 10 seconds: "Are you still alive?"
  • If the container fails to respond (e.g. frozen by an internal deadlock), `kubelet` 
    kills the container and restarts it.
```

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 45 # Grace period while Spring Boot boots
  periodSeconds: 10       # Check every 10 seconds
  timeoutSeconds: 3       # Timeout after 3 seconds
  failureThreshold: 3     # Restart container after 3 consecutive failures
```

```
  Action on Failure:
  Container KILLED and RESTARTS (Incrementing Pod restart count).
```

## 🟡 Middle Level

### The 4 Probe Mechanisms

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Probe Type           │ Checking Mechanism           │ Standard Production Use Case                     │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`httpGet`**        │ HTTP GET (Expects 200–399)   │ REST APIs, Spring Boot Actuator endpoints.       │
  │ **`tcpSocket`**      │ Successful TCP 3-way Handshk │ Non-HTTP TCP daemons (Postgres, Redis, Kafka).   │
  │ **`exec`**           │ Shell command exits with `0` │ Checking internal lock files (`test -f /tmp/ok`).│
  │ **`grpc`** (v1.24+)  │ gRPC Health Checking Protocol│ High-performance gRPC microservices.             │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Critical Anti-Pattern: The Cascading Death Spiral

```
  ❌ THE DISASTER SCENARIO (Checking DB in Liveness Probe):
  1. Your PostgreSQL database experiences temporary latency or connection pool exhaustion.
  2. All 50 backend pods query the DB inside their `/actuator/health` liveness probe.
  3. The liveness probe fails across ALL 50 pods simultaneously.
  4. `kubelet` kills and restarts all 50 pods at once!
  5. 50 restarting pods flood the recovering database with hundreds of new connection requests, 
     crashing the database permanently!

  ✅ PRODUCTION RULE:
  • Liveness Probes must ONLY verify internal application health (threads, memory, local deadlock).
  • NEVER check external databases or downstream third-party services in a Liveness Probe!
```

## 🔴 Senior Level

### Modern Spring Boot 3.x Actuator & Startup Probe Architecture

Slow JVM cold-starts (45–90 seconds) historically forced developers to set huge `initialDelaySeconds: 90`. This delayed deadlock detection during normal runtime.

Modern architecture pairs **Startup Probes** with **Liveness Probes**:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: billing-service
spec:
  template:
    spec:
      containers:
      - name: app
        image: billing-service:1.0
        # 1. Startup Probe: Disables Liveness/Readiness until Spring Boot completes boot
        startupProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          failureThreshold: 30 # 30 * 3s = 90s max boot window
          periodSeconds: 3

        # 2. Liveness Probe: Fast 5-second loop during steady state
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          periodSeconds: 5
          failureThreshold: 3
          timeoutSeconds: 2
```

In `application.yml`:
```yaml
management:
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true
  endpoint:
    health:
      probes:
        enabled: true
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Primary Function:** Determines if the container is alive; triggers a **container restart** on failure.
- **Key Use Cases:** Deadlocks, memory leaks, frozen event loops.
- **Probe Types:** `httpGet`, `tcpSocket`, `exec`, `grpc`.
- **The Golden Invariant:** **Never check external databases or remote microservices in a Liveness Probe!**
- **Startup Probe:** Use `startupProbe` to handle slow Spring Boot initializations without compromising runtime responsiveness.

**Common Follow-up Questions:**
- *"What is the difference between Liveness and Readiness Probes?"* → Liveness restarts the container if it fails; Readiness temporarily removes the container from the Service load balancer without restarting it.
- *"Why does Spring Boot expose separate `/actuator/health/liveness` and `/actuator/health/readiness` endpoints?"* → Liveness checks only the local JVM state; Readiness evaluates database connectivity and message broker consumers.
- *"What happens if `initialDelaySeconds` is too short?"* → The container will fail the probe during JVM startup and enter an endless `CrashLoopBackOff` restart cycle before the application can finish booting.

**Red Flags (DO NOT Say):**
- ❌ *"Liveness probe failure removes the Pod from the Service endpoint without killing it."* (That is the definition of a Readiness Probe; Liveness actively restarts the container).
- ❌ *"A Liveness Probe should test if PostgreSQL and Redis are reachable."* (This triggers catastrophic cascading cluster restarts during DB maintenance).
- ❌ *"Setting `initialDelaySeconds: 0` is recommended for fast startup."* (JVM applications will be killed instantly before classes load).
