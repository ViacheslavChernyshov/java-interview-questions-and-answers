# How Does Scaling Work in Kubernetes?

---

## 🟢 Junior Level

Scaling in Kubernetes is the ability to adjust compute capacity to match application traffic demands across two distinct dimensions:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ ↔️ HORIZONTAL SCALING (Scale Out / In)                   │ ↕️ VERTICAL SCALING (Scale Up / Down)                   │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Adds or removes **Pod replicas** (`replicas: 1 ➔ 5`)  │ • Increases/decreases **CPU & RAM per Pod**             │
  │ • Handled automatically by **HPA**                      │ • Handled automatically by **VPA**                      │
  │ • Best for stateless REST APIs & web workers            │ • Best for monolithic services & database workloads     │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```bash
# Manual horizontal scaling of a Deployment:
kubectl scale deployment order-service --replicas=5
```

## 🟡 Middle Level

### The 3 Dimensions of Kubernetes Autoscaling

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Autoscaler           │ Managed Level                │ Trigger Mechanism                                │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **HPA**              │ Number of Pods               │ CPU, Memory, HTTP RPS, or Queue Depth metrics    │
  │ **VPA**              │ CPU / Memory per Pod         │ Pod memory starvation or underutilization        │
  │ **Cluster Autoscaler**│ Number of Worker Nodes (VMs) │ Pods stuck in `Pending` due to lack of capacity  │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### The HPA Target Formula

The Horizontal Pod Autoscaler controller periodically queries the **Metrics Server** (every 15s by default) and applies the formula:

$$\text{DesiredReplicas} = \left\lceil \text{CurrentReplicas} \times \left( \frac{\text{CurrentMetricValue}}{\text{TargetMetricValue}} \right) \right\rceil$$

```
  Example:
  • Current Replicas = 2
  • Target CPU Utilization = 50%
  • Current CPU Utilization = 100%
  • Desired Replicas = ceil[2 * (100 / 50)] = 4 Pods!
```

> [!IMPORTANT]
> **HPA Invariant:** For HPA to function, all containers **must** define `resources.requests.cpu` (and/or memory). Without requests, HPA cannot calculate target utilization percentages and fails.

## 🔴 Senior Level

### Modern Scaling Architecture: HPA + Cluster Autoscaler vs. Karpenter

```
  [Spike in Traffic] ──► [HPA Spawns 50 Pods]
                                │
                                ▼
  [Cluster Full] ──► [Pods Stuck in "Pending" State (Insufficient CPU/RAM)]
                                │
                                ▼
  ┌───────────────────────────────────────────────────────────────┐
  │ NODE AUTOSCALER TRIGGERS:                                     │
  │ • Classic Cluster Autoscaler: Scales cloud Node AutoScalingGrps│
  │ • Karpenter (Next-Gen): Directly launches right-sized EC2 VMs │
  │   in sub-45 seconds without pre-defined node groups!          │
  └───────────────────────────────────────────────────────────────┘
```

### Critical Production Anti-Pattern: HPA vs. VPA Conflict

- **The Race Condition:** Never configure HPA on CPU/memory and VPA on CPU/memory for the **same Deployment**.
  - As CPU increases, HPA tries to scale out pods, while VPA simultaneously tries to scale up pod CPU by killing and restarting pods. This creates cascading deployment thrashing.
- **Architectural Rule:** Use HPA for stateless apps (REST APIs); use VPA in `Off` / recommendation mode to tune resource requests.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **3 Scaling Layers:** HPA (horizontal pods), VPA (vertical pod resources), Cluster Autoscaler / Karpenter (worker nodes).
- **HPA Metric Sources:** Resource metrics (CPU/RAM from Metrics Server), Custom metrics (Prometheus), External metrics (AWS SQS / Kafka lag).
- **Request Prerequisite:** Pods must declare `resources.requests` for HPA percentage calculations.
- **Node Scale-Out Trigger:** Worker nodes are added when Pods enter `Pending` state due to insufficient cluster allocatable resources.
- **Node Scale-In Safety:** CA drains and evicts nodes only when node utilization remains below threshold without violating `PodDisruptionBudgets`.

**Common Follow-up Questions:**
- *"What happens if HPA triggers pod creation but the cluster has no remaining CPU capacity?"* → New pods are placed in `Pending` state until the Cluster Autoscaler provisions new worker nodes.
- *"How do you prevent HPA from scaling down too quickly during temporary traffic dips (flapping)?"* → Configure `spec.behavior.scaleDown.stabilizationWindowSeconds: 300` (5-minute cooldown period).
- *"How does Karpenter improve upon the classic Kubernetes Cluster Autoscaler?"* → Karpenter bypasses fixed cloud node groups, directly provisioning bare-metal and spot VM instances tailored to exact pending pod requirements in seconds.

**Red Flags (DO NOT Say):**
- ❌ *"HPA can autoscale pods based on CPU even if `resources.requests.cpu` is omitted."* (HPA requires `requests` as the 100% baseline).
- ❌ *"VPA and HPA on CPU should be configured together to maximize resilience."* (They conflict and crash workloads; use HPA for horizontal workloads).
- ❌ *"Cluster Autoscaler provisions nodes based on average cluster CPU load."* (It provisions nodes when Pods are in `Pending` state due to resource scheduling failure).
