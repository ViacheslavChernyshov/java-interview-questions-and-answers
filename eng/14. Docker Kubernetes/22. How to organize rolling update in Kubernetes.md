# How to Organize Rolling Update in Kubernetes?

---

## 🟢 Junior Level

A **Rolling Update** is the default deployment strategy in Kubernetes that incrementally replaces instances of the previous application version with the new version, ensuring **Zero Downtime** for active users:

```
  Tire Replacement Analogy:
  • Recreate Strategy: Stopping the car, removing all 4 tires simultaneously (Downtime: 15 min).
  • Rolling Update: Replacing one wheel at a time while the remaining 3 keep the car supported (Downtime: 0 sec).
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Max 1 extra temporary Pod created during rollout (4 + 1 = 5)
      maxUnavailable: 0  # Guarantees exactly 4 healthy pods always available!
  template:
    spec:
      containers:
      - name: app
        image: order-service:2.0 # Updated image tag
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          periodSeconds: 5
```

```bash
# Check real-time rollout progression:
kubectl rollout status deployment/order-service

# Instant one-command rollback if errors occur:
kubectl rollout undo deployment/order-service
```

## 🟡 Middle Level

### Tuning `maxSurge` and `maxUnavailable`

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Parameter            │ Definition & Defaults        │ Zero-Downtime Recommendation                     │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`maxSurge`**       │ How many Pods can be created │ Set to **`25%`** or **`1`** (Allows K8s to spawn │
  │                      │ *above* `spec.replicas`.     │ new pods before terminating old ones).           │
  │ **`maxUnavailable`** │ How many Pods can be missing │ Set to **`0`** (Guarantees capacity is never     │
  │                      │ *below* `spec.replicas`.     │ degraded during high-traffic updates).           │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### The 6-Step Rollout Lifecycle

```
  1. Deployment creates a new child ReplicaSet (v2).
  2. Deployment spawns 1 new Pod in RS v2 (Cluster has 4 old + 1 new = 5 Pods).
  3. Kubelet executes the Readiness Probe on the new Pod v2.
  4. Once Readiness passes, Pod v2 is added to the Service `EndpointSlice`.
  5. Deployment terminates 1 old Pod from RS v1 (`SIGTERM` ➔ Graceful Shutdown).
  6. Cycle repeats until RS v2 has 4 active Pods and RS v1 is scaled to 0.
```

## 🔴 Senior Level

### Graceful Termination & The In-Flight Request Trap

When Kubernetes terminates an old Pod, a race condition occurs between `kube-proxy` removing iptables rules and the application shutting down:

```
  ┌───────────────────────────────────────────────────────────────┐
  │ TIMELINE OF A ROLLING UPDATE POD TERMINATION:                 │
  ├───────────────────────────────────────────────────────────────┤
  │ T+0s:  API server sends `SIGTERM` to Spring Boot process.     │
  │ T+0s:  Endpoint Controller notifies `kube-proxy` across nodes.│
  │ T+1s:  `kube-proxy` is still updating iptables on Worker B... │
  │        (Active HTTP requests continue hitting the old Pod!)   │
  │ T+2s:  If Spring Boot exits instantly ──► 💥 Users get 502!  │
  └───────────────────────────────────────────────────────────────┘
```

#### The Production Solution: `preStop` Hook + Spring Graceful Shutdown

```yaml
# 1. Kubernetes Manifest: Inject preStop hook delay
spec:
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["sh", "-c", "sleep 10"] # Wait for kube-proxy iptables to drain!
```

```yaml
# 2. application.yml: Spring Boot Graceful Shutdown
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```

### Database Schema Backwards Compatibility (Expand/Contract)

During a rolling update, **Version 1.0 and Version 2.0 Pods run concurrently against the database for several minutes**:
- **Rule:** Never drop or rename database columns in a single step!
- Use the **Expand/Contract (Parallel Run) Pattern**:
  1. *Step 1 (Expand):* Add new nullable column. Deploy v2.0 (writes to both old and new).
  2. *Step 2 (Migrate):* Backfill historical data via batch job.
  3. *Step 3 (Contract):* Deploy v3.0 (reads only from new column). Drop old column.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Default zero-downtime deployment strategy replacing old Pods incrementally.
- **Rollout Controls:** `maxSurge` (extra pods allowed) and `maxUnavailable` (allowed capacity drop).
- **Readiness Dependency:** A rolling update **will stall and freeze** if new pods fail their Readiness Probes.
- **Rollout CLI:** `rollout status`, `rollout history`, `rollout undo`, `rollout pause/resume`.
- **Graceful Termination:** Combine `preStop: sleep 10` with Spring Boot `server.shutdown: graceful` to eliminate 502 Bad Gateway errors.

**Common Follow-up Questions:**
- *"What happens if a new application image crashes upon startup during a rolling update?"* → The new Pod enters `CrashLoopBackOff` and fails its readiness probe; Kubernetes halts the rollout at `maxSurge`, keeping all existing healthy v1 Pods running without user disruption.
- *"How do you revert a bad deployment in production?"* → Execute `kubectl rollout undo deployment/<name>` to instantly scale the previous ReplicaSet back up.
- *"Why must database migrations be backwards-compatible during rolling updates?"* → Because both old and new application versions query the database concurrently during the rollout window.

**Red Flags (DO NOT Say):**
- ❌ *"A Rolling Update deletes all old pods before creating any new pods."* (That is the `Recreate` strategy, which causes complete downtime).
- ❌ *"Setting `maxUnavailable: 100%` is recommended for fast production deployments."* (This kills all production pods simultaneously).
- ❌ *"Rollbacks in Kubernetes require rebuilding the previous Docker container image."* (Kubernetes simply re-scales the existing preserved previous ReplicaSet in etcd).
