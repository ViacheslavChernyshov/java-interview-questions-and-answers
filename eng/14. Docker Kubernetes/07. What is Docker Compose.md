# What is Docker Compose?

---

## 🟢 Junior Level

**Docker Compose** is a declarative tool for defining and running multi-container Docker applications using a single `compose.yaml` (or `docker-compose.yml`) configuration file:

```yaml
# compose.yaml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      - SPRING_DATASOURCE_URL=jdbc:postgresql://postgres-db:5432/orders_db
    depends_on:
      postgres-db:
        condition: service_healthy

  postgres-db:
    image: postgres:16-alpine
    environment:
      - POSTGRES_DB=orders_db
      - POSTGRES_USER=admin
      - POSTGRES_PASSWORD=secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin -d orders_db"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pgdata:
```

```bash
# Start all containers in background:
docker compose up -d

# View live aggregate logs across all services:
docker compose logs -f

# Stop and remove containers and internal networks:
docker compose down
```

## 🟡 Middle Level

### Embedded DNS & Service Discovery

When Docker Compose spins up an application, it automatically creates a dedicated bridge network:
- Containers can reach each other by their **service names** as hostnames (e.g. `http://postgres-db:5432`).
- No hardcoded IP addresses or manual host `/etc/hosts` configurations required.

### The Startup Order Hazard: `depends_on` vs. Healthchecks

```
  ❌ The Naive `depends_on: [postgres-db]` Problem:
  • Docker starts the database container process, then IMMEDIATELY starts the Java app.
  • Postgres takes 3–5 seconds to initialize data catalogs; Spring Boot fails on startup with 
    `Connection refused: localhost:5432`!

  ✅ The Production Solution:
  • Define a `healthcheck` on the database (`pg_isready`).
  • In the app service, use `depends_on: { postgres-db: { condition: service_healthy } }`.
```

## 🔴 Senior Level

### Architectural Comparison: Docker Compose vs. Kubernetes

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architectural Feature        │ Docker Compose                   │ Kubernetes                                       │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Target Environment**       │ Local Development / Single-Node  │ Production Multi-Node Clusters                   │
  │ **Scaling & Autoscaling**    │ Manual (`--scale app=3`)         │ **Automated Horizontal (HPA) & Cluster (CA)**   │
  │ **Self-Healing & Restarts**  │ Simple container restart policy  │ Pod evictions, Node drain, Liveness probes       │
  │ **Zero-Downtime Deployments**│ ❌ No (Port conflicts on 1 host) │ ✅ Native Rolling Updates, Blue/Green, Canary    │
  │ **Service Discovery**        │ Embedded Docker DNS daemon       │ CoreDNS + `kube-proxy` IPVS / eBPF (Cilium)      │
  │ **Secret Management**        │ Local `.env` files               │ Kubernetes `Secret` & Vault CSI drivers          │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Production Local Setup: Profiles & Resource Constraints

```yaml
# Modular developer stack with Profiles:
services:
  backend:
    image: myapp:local
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 1024M
    restart: unless-stopped

  # Starts ONLY when explicitly requested: docker compose --profile telemetry up
  prometheus:
    image: prom/prometheus:v2.45.0
    profiles: ["telemetry"]
    ports: ["9090:9090"]

  grafana:
    image: grafana/grafana:10.0.0
    profiles: ["telemetry"]
    ports: ["3000:3000"]
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Multi-container definition tool managing services, networks, and persistent volumes in a single YAML file.
- **Service Discovery:** Automatic internal DNS resolution allows services to communicate via service names (e.g. `http://db:5432`).
- **Healthcheck Synchronization:** Always pair `depends_on` with `condition: service_healthy` to prevent Spring Boot startup crashes.
- **Primary Use Case:** Local development, automated integration testing (Testcontainers), and single-node staging environments.
- **Production Limit:** Compose lacks cluster-wide scheduling, automated pod autoscaling, and zero-downtime rolling updates (use Kubernetes).

**Common Follow-up Questions:**
- *"What is the difference between `docker-compose` (with hyphen) and `docker compose` (with space)?"* → `docker-compose` is the legacy Python v1 tool; `docker compose` is the modern Go-based v2 plugin embedded directly in Docker CLI.
- *"How do environment variables work in Docker Compose?"* → Compose automatically reads values from a local `.env` file in the same directory and substitutes `${VARIABLE_NAME}` references in the YAML file.
- *"What does `docker compose down -v` do?"* → It stops and deletes all containers and networks, and the `-v` flag additionally **wipes all named persistent volumes** (deleting database data).

**Red Flags (DO NOT Say):**
- ❌ *"`depends_on: [db]` waits until PostgreSQL has completed initialization and is ready to accept queries."* (It only waits until the container process starts; you must use healthchecks).
- ❌ *"Docker Compose is designed for orchestrating large 100-node production clusters."* (Compose only runs on a single Docker host; Kubernetes is required for multi-node clusters).
- ❌ *"Hardcoding production passwords inside `docker-compose.yml` is acceptable because Docker encrypts the file."* (YAML files are plain text; use `.env` files omitted from Git or Secret managers).
