# What is Namespace?

---

## 🟢 Junior Level

A **Namespace** in Kubernetes is a virtual cluster partition that provides a **logical boundary** for organizing, isolating, and managing resources within a single physical Kubernetes cluster:

```
  Office Building Analogy:
  • The physical building ──► The Kubernetes Cluster.
  • Floor 1, Floor 2, Floor 3 ──► Namespaces (`development`, `staging`, `production`).
  • Both Floor 1 and Floor 2 can have a conference room named "Room 101" (Pod `web-service`) 
    without causing naming collisions!
```

```bash
# View all active namespaces:
kubectl get namespaces

# List pods in a specific namespace:
kubectl get pods -n production

# Switch default namespace context:
kubectl config set-context --current --namespace=production
```

```
  4 Default Built-in Namespaces:
  1. `default`         ──► Standard destination for objects created without an explicit namespace.
  2. `kube-system`     ──► System pods and control plane components (CoreDNS, kube-proxy).
  3. `kube-public`     ──► Publicly readable cluster discovery data.
  4. `kube-node-lease` ──► High-frequency node heartbeats for availability monitoring.
```

## 🟡 Middle Level

### Resource Scoping: Namespace-Scoped vs. Cluster-Scoped

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ 🏢 Namespace-Scoped Resources            │ 🌐 Cluster-Scoped Resources (Global)             │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • **Pod**, **Deployment**, **ReplicaSet**│ • **Node** (Worker machines)                     │
  │ • **Service**, **Ingress**               │ • **PersistentVolume** (Underlying storage disks)│
  │ • **ConfigMap**, **Secret**              │ • **StorageClass** (Storage provisioners)        │
  │ • **PersistentVolumeClaim (PVC)**        │ • **Namespace** (The partition itself)           │
  │ • **Role**, **RoleBinding**              │ • **ClusterRole**, **ClusterRoleBinding**        │
  │ • **ServiceAccount**                     │ • **CustomResourceDefinition (CRD)**             │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Cross-Namespace Communication & DNS Syntax

Namespaces do **not** block network traffic by default; Pods in `staging` can reach Services in `production` unless restricted by NetworkPolicies.

```
  Cross-Namespace DNS Resolution (FQDN):
  http://<service-name>.<namespace>.svc.cluster.local:<port>

  Example:
  http://payment-service.production.svc.cluster.local:8080
```

## 🔴 Senior Level

### Multi-Tenancy Governance: ResourceQuotas, LimitRanges & RBAC

Enterprise clusters enforce strict multi-tenant boundaries via three governance mechanisms:

```yaml
# 1. ResourceQuota: Caps maximum CPU/RAM footprint for the entire namespace
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: team-billing
spec:
  hard:
    requests.cpu: "16"
    requests.memory: 32Gi
    limits.cpu: "32"
    limits.memory: 64Gi
    pods: "50"
---
# 2. LimitRange: Enforces default and min/max constraints per container
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: team-billing
spec:
  limits:
  - default: # Default limits if omitted by developer
      cpu: "500m"
      memory: 512Mi
    defaultRequest: # Default requests if omitted
      cpu: "250m"
      memory: 256Mi
    type: Container
```

```yaml
# 3. RBAC Role: Restricts junior developers to viewing logs and pods in dev-ns only
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: development
  name: dev-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Virtual cluster slice providing logical isolation for names, access control (RBAC), and compute quotas.
- **Resource Boundary:** Pods, Services, and ConfigMaps are namespace-scoped; Nodes and PersistentVolumes are cluster-scoped.
- **DNS Syntax:** `<service-name>.<namespace>.svc.cluster.local`.
- **Default Namespaces:** `default`, `kube-system`, `kube-public`, `kube-node-lease`.
- **Resource Governance:** `ResourceQuota` limits total namespace consumption; `LimitRange` sets per-pod defaults.

**Common Follow-up Questions:**
- *"Do Namespaces provide secure network isolation out of the box?"* → No; by default, Kubernetes uses a flat network where any Pod in any namespace can send packets to any other Pod; network isolation requires explicit **NetworkPolicies**.
- *"What happens if you delete a Namespace?"* → Kubernetes triggers cascade deletion, forcefully terminating and deleting **all** Pods, Services, ConfigMaps, and PVCs contained inside that namespace.
- *"Can a PersistentVolumeClaim in `namespace-a` bind to a PersistentVolumeClaim in `namespace-b`?"* → No; PVCs are strictly namespace-scoped, though both can bind to cluster-scoped `PersistentVolumes`.

**Red Flags (DO NOT Say):**
- ❌ *"Namespaces physically isolate containers onto separate dedicated worker nodes."* (Namespaces are purely logical; pods from different namespaces run side-by-side on the same worker node unless Node Affinity or Taints are configured).
- ❌ *"Namespaces encrypt network traffic between different teams."* (Namespaces have no relation to encryption; mTLS requires a Service Mesh like Istio or Cilium WireGuard).
- ❌ *"Nodes are assigned to a specific Namespace."* (Nodes are cluster-scoped infrastructure resources shared across all namespaces).
