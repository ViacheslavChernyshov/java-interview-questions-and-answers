# What is the Difference Between CMD and ENTRYPOINT?

---

## 🟢 Junior Level

Both `ENTRYPOINT` and `CMD` define what command executes when a container starts, but they serve distinct purposes:

```
  Function Analogy:
  • ENTRYPOINT ──► The Fixed Executable Command (e.g. `java -jar app.jar`)
  • CMD        ──► The Default Arguments/Flags  (e.g. `--server.port=8080`)
```

```dockerfile
# Standard Spring Boot Production Pattern:
ENTRYPOINT ["java", "-jar", "/app.jar"]
CMD ["--server.port=8080"]
```

```bash
# 1. Default Run: Executes: java -jar /app.jar --server.port=8080
docker run myapp

# 2. Overriding default arguments: Executes: java -jar /app.jar --server.port=9090
docker run myapp --server.port=9090
```

## 🟡 Middle Level

### Interaction Matrix & Override Rules

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Scenario                     │ Dockerfile Configuration         │ Resulting Command on `docker run myapp -v`       │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Only `CMD`**               │ `CMD ["java", "-jar", "app.jar"]`│ 💥 `-v` completely **replaces** `CMD`!           │
  │ **Only `ENTRYPOINT`**        │ `ENTRYPOINT ["java", "-jar"]`    │ `java -jar -v` (Appends argument)                │
  │ **`ENTRYPOINT` + `CMD`**     │ `ENTRYPOINT ["java", "-jar"]`    │ `java -jar -v` (Replaces default `CMD` cleanly)  │
  │                              │ `CMD ["app.jar"]`                │                                                  │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Overriding at Runtime

```bash
# Overriding CMD: Pass arguments directly at the end of the command:
docker run myapp --spring.profiles.active=prod

# Overriding ENTRYPOINT: Requires the explicit `--entrypoint` flag:
docker run --entrypoint /bin/sh -it myapp
```

## 🔴 Senior Level

### Kubernetes Mapping & Invariant Translation

When running Docker images inside Kubernetes Pods, manifest fields map to Docker instructions as follows:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Dockerfile Instruction       │ Kubernetes Pod Spec Field        │ Override Behavior                                │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`ENTRYPOINT`**             │ `command:`                       │ `command` in YAML overrides Docker `ENTRYPOINT`  │
  │ **`CMD`**                    │ `args:`                          │ `args` in YAML overrides Docker `CMD`            │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-service
spec:
  containers:
  - name: app
    image: payment-service:1.0
    command: ["java"]             # Overrides ENTRYPOINT
    args: ["-jar", "/app.jar"]    # Overrides CMD
```

### The PID 1 Zombie Reaping & Signal Trap

```
  1. Exec Form (`ENTRYPOINT ["java", "..."]`):
     • Java runs as PID 1 directly.
     • Receives `SIGTERM` from Docker/Kubernetes on shutdown.
     • Initiates Spring Boot `GracefulShutdown` (completes active HTTP requests).

  2. Shell Form (`ENTRYPOINT java -jar app.jar`):
     • `/bin/sh -c` becomes PID 1; Java is PID 7.
     • `/bin/sh` ignores `SIGTERM`.
     • After timeout (default 30s), Kubernetes issues `SIGKILL` (Exit Code 137), 
       killing the app mid-transaction!

  3. Init Systems (Tini):
     • For complex containers spawning sub-processes, use `tini` to forward signals 
       and reap zombie child processes:
       ENTRYPOINT ["/sbin/tini", "--", "java", "-jar", "app.jar"]
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Role:** `ENTRYPOINT` sets the immutable binary/executable; `CMD` provides default overrideable parameters.
- **Combined Best Practice:** `ENTRYPOINT ["java", "-jar", "app.jar"]` + `CMD ["--server.port=8080"]`.
- **CLI Overrides:** Passing arguments to `docker run` replaces `CMD`; changing `ENTRYPOINT` requires `--entrypoint`.
- **Kubernetes Translation:** `ENTRYPOINT` = `command`, `CMD` = `args`.
- **Exec vs Shell Form:** Always use Exec Form (`["..."]`) so the application receives `SIGTERM` as PID 1.

**Common Follow-up Questions:**
- *"What happens if a Dockerfile contains multiple `CMD` instructions?"* → Only the very last `CMD` in the Dockerfile takes effect; all preceding `CMD` instructions are ignored.
- *"Why does shell form prevent graceful shutdown in Kubernetes?"* → Shell form starts `/bin/sh` as PID 1; the shell does not propagate the `SIGTERM` termination signal to the child Java process.
- *"How does `tini` help containers?"* → `tini` runs as a tiny init process (PID 1) that properly forwards OS signals to child processes and reaps defunct zombie processes.

**Red Flags (DO NOT Say):**
- ❌ *"Both `CMD` and `ENTRYPOINT` are executed sequentially one after another."* (`CMD` provides arguments appended to `ENTRYPOINT`).
- ❌ *"In Kubernetes, `command` corresponds to `CMD` and `args` corresponds to `ENTRYPOINT`."* (It is the exact opposite: `command` = `ENTRYPOINT`, `args` = `CMD`).
- ❌ *"Shell form is preferred because it supports environment variable expansion."* (Shell form breaks OS signal handling; use exec form or an entrypoint wrapper script).
