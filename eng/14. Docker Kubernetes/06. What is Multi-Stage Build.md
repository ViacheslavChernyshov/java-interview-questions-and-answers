# What is Multi-Stage Build?

---

## 🟢 Junior Level

A **Multi-Stage Build** is a Docker technique that uses multiple `FROM` statements in a single Dockerfile to separate the **build environment** from the **runtime environment**:

```
  Cake Baking Analogy:
  • Build Stage (Kitchen): Uses ovens, mixers, spatulas, and raw flour (Maven, JDK, Git).
  • Runtime Stage (Delivery Box): Contains ONLY the baked cake (The final `.jar` file + minimal JRE). 
    You never deliver the oven and mixer to the customer!
```

```dockerfile
# ==========================================
# Stage 1: The Builder (Compiles source code)
# ==========================================
FROM maven:3.9-eclipse-temurin-21-alpine AS builder
WORKDIR /build

COPY pom.xml .
RUN mvn dependency:go-offline -B

COPY src ./src
RUN mvn clean package -DskipTests -B

# ==========================================
# Stage 2: The Production Runtime (Minimal)
# ==========================================
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Copy ONLY the compiled jar from the 'builder' stage:
COPY --from=builder /build/target/*.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

```
  Key Result:
  • Single-Stage Image Size: ~850 MB (Full JDK + Maven + Source Code + Build Cache)
  • Multi-Stage Image Size:  ~180 MB (Lightweight Alpine JRE + `.jar` only)
```

## 🔴 Senior Level

### Deep-Dive Optimization Matrix: From JDK to GraalVM Native

```
  ┌──────────────────────────────┬────────────┬──────────────────┬─────────────────────────────────────────────────────┐
  │ Approach                     │ Image Size │ Startup Time     │ Production Trade-Offs                               │
  ├──────────────────────────────┼────────────┼──────────────────┼─────────────────────────────────────────────────────┤
  │ **Single-Stage JDK**         │ ~850 MB    │ ~2–4 seconds     │ ❌ High CVE attack surface; exposes source code.    │
  │ **Multi-Stage JRE Slim**     │ ~220 MB    │ ~1.5–3 seconds   │ 🛡️ Standard enterprise baseline; full glibc support.│
  │ **Multi-Stage Alpine JRE**   │ ~170 MB    │ ~1.5–3 seconds   │ ⚠️ Lightweight musl libc; watch out for JNI crashes.│
  │ **Multi-Stage + `jlink`**    │ ~60 MB     │ ~1.0–2 seconds   │ 🚀 Stripped custom modular JRE; complex dependency. │
  │ **Google Distroless**        │ ~90 MB     │ ~1.5–3 seconds   │ 🔒 Zero shell (`/bin/sh`), zero package managers.   │
  │ **GraalVM Native Image**     │ ~35 MB     │ **< 50 ms**      │ ⚡ Instant startup; high compile CPU/RAM overhead.   │
  └──────────────────────────────┴────────────┴──────────────────┴─────────────────────────────────────────────────────┘
```

### Custom Modular JRE with `jlink`

```dockerfile
# Step 1: Build Custom Stripped JRE
FROM eclipse-temurin:21-jdk-jammy AS jre-builder
RUN $JAVA_HOME/bin/jlink \
    --add-modules java.base,java.logging,java.sql,java.net.http,java.desktop \
    --strip-debug \
    --no-man-pages \
    --no-header-files \
    --compress=2 \
    --output /custom-jre

# Step 2: Build Application
FROM maven:3.9-eclipse-temurin-21-alpine AS app-builder
WORKDIR /workspace
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests

# Step 3: Ultra-Minimal Production Image
FROM debian:bookworm-slim
ENV JAVA_HOME=/opt/jre
ENV PATH="${JAVA_HOME}/bin:${PATH}"

COPY --from=jre-builder /custom-jre /opt/jre
COPY --from=app-builder /workspace/target/*.jar /app/app.jar

RUN useradd -u 10001 -m appuser
USER appuser
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **What is It:** Using multiple `FROM` stages to isolate compilation tools from the final production runtime.
- **The Invariant:** Only the layers declared in the **final `FROM` stage** are retained in the published image.
- **Core Benefits:** Drastically reduced image size (from ~850MB to <180MB), reduced attack surface, and faster network pull times in Kubernetes.
- **`COPY --from=stage`:** Syntax used to import artifacts between stages.
- **Distroless & Non-Root:** Standard senior practice to prevent container shell execution.

**Common Follow-up Questions:**
- *"How does Docker handle caching across different stages?"* → BuildKit analyzes the dependency graph between stages; if a stage is unchanged, its layers are retrieved from cache; unneeded stages can even be skipped entirely.
- *"What is `jlink` and how does it relate to multi-stage builds?"* → `jlink` is a JDK tool that bundles only the specific Java modules required by your application into a custom lightweight JRE (~40–60MB).
- *"Can you copy files from an arbitrary Docker image without defining a local stage?"* → Yes; `COPY --from=nginx:alpine /etc/nginx/nginx.conf /etc/nginx/nginx.conf` extracts files directly from public images.

**Red Flags (DO NOT Say):**
- ❌ *"All files created in previous stages are packaged into the final Docker image unless deleted with `rm`."* (Previous stages are discarded entirely; only files explicitly copied via `COPY --from` are included).
- ❌ *"Multi-stage builds require multiple separate Dockerfiles and bash orchestration scripts."* (Everything is declared cleanly in a single `Dockerfile`).
- ❌ *"Multi-stage builds are only useful for compiled languages like Go and Java."* (Frontend Node.js builds also use multi-stage builds to discard `node_modules` after webpack compilation).
