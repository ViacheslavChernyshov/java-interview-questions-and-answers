# What Types of Service Exist (ClusterIP, NodePort, LoadBalancer)?

---

## 🟢 Junior Level

Kubernetes offers **four core types of Services** that control how and from where network traffic can reach your application Pods:

```
  ┌──────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Service Type         │ Accessibility Scope      │ Primary Use Case                                 │
  ├──────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **`ClusterIP`** (Def)│ Internal Cluster Only    │ Inter-service microservice REST / gRPC calls.    │
  │ **`NodePort`**       │ External via Node IP:Port│ Quick local debugging / non-cloud environments.  │
  │ **`LoadBalancer`**   │ Public Internet IP       │ Production public-facing services in Cloud.      │
  │ **`ExternalName`**   │ Internal DNS Alias       │ Mapping internal calls to external databases.    │
  └──────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

```
  The Russian Nesting Doll Hierarchy:
  LoadBalancer ──► wraps a NodePort ──► wraps a ClusterIP ──► routes to Pods
```

## 🟡 Middle Level

### Practical Declarations & Mechanics

#### 1. ClusterIP (Default Internal Networking)
```yaml
spec:
  type: ClusterIP
  selector: { app: order-api }
  ports:
  - port: 80
    targetPort: 8080
```

#### 2. NodePort (Exposes Port 30000–32767 on Every Node)
```yaml
spec:
  type: NodePort
  selector: { app: web-ui }
  ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080 # Accessible at http://<Node-IP>:30080
```

#### 3. LoadBalancer (Cloud Managed VIP)
```yaml
spec:
  type: LoadBalancer
  selector: { app: api-gateway }
  ports:
  - port: 443
    targetPort: 8443
```

#### 4. ExternalName (CNI CNAME Redirection)
```yaml
spec:
  type: ExternalName
  externalName: production-postgres.rds.amazonaws.com
```

### Cost Optimization: Ingress vs. Multiple LoadBalancers

```
  ❌ Costly Anti-Pattern:
  20 Microservices ──► 20 Cloud LoadBalancers ──► ~$500 / month in AWS/GCP fees!

  ✅ Production Architecture:
  20 Microservices (ClusterIP) ──► 1 Ingress Controller ──► 1 Cloud LoadBalancer ($25/mo)
```

## 🔴 Senior Level

### Under the Hood: Cloud Controller Manager & On-Premises Bare-Metal (MetalLB)

1. **Cloud LoadBalancer Provisioning:**
   - When a `LoadBalancer` service is applied, `cloud-controller-manager` calls cloud APIs (e.g. AWS ELB/NLB, GCP Cloud Load Balancing) to provision physical external load balancers and configure target health checks.
2. **On-Premise Bare-Metal Clusters:**
   - Bare-metal Kubernetes clusters (lacking cloud providers) leave `LoadBalancer` IPs stuck in `<pending>` state.
   - Solution: Deploy **MetalLB** in **Layer 2 mode** (ARP responses) or **BGP mode** (Border Gateway Protocol peering with top-of-rack data center routers).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **4 Service Types:** `ClusterIP` (internal default), `NodePort` (ports 30000-32767), `LoadBalancer` (cloud public IP), `ExternalName` (DNS CNAME).
- **Hierarchy:** `LoadBalancer` builds on top of `NodePort`, which builds on top of `ClusterIP`.
- **Production Pattern:** Expose internal microservices via `ClusterIP`; route all external HTTP traffic through a single **Ingress Controller** backed by one `LoadBalancer`.
- **Bare-Metal:** Use MetalLB to support `LoadBalancer` services on on-premise hardware.

**Common Follow-up Questions:**
- *"What is the standard NodePort port range in Kubernetes?"* → `30000–32767` (configurable via API server flag `--service-node-port-range`).
- *"Why should you avoid using NodePort directly in production?"* → It requires exposing worker node public IPs, lacks Layer 7 SSL termination/path routing, and creates port conflict management overhead.
- *"How does ExternalName work under the hood?"* → CoreDNS returns a DNS `CNAME` record directly to the client Pod; traffic bypasses `kube-proxy` netfilter routing entirely.

**Red Flags (DO NOT Say):**
- ❌ *"Every microservice in production should have its own public `LoadBalancer` Service."* (Extremely expensive and insecure; use Ingress with ClusterIP services).
- ❌ *"NodePort only opens a port on the specific node where the Pod is running."* (NodePort opens the port on **every worker node** in the entire cluster and forwards traffic across the cluster overlay network).
- ❌ *"ExternalName proxies database TCP traffic through kube-proxy."* (It is pure DNS CNAME redirection without any proxying).
