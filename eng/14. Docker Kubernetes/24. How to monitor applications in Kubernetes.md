# How to Monitor Applications in Kubernetes?

---

## 🟢 Junior Level

Monitoring in Kubernetes provides full visibility into the health, performance, and resource consumption of the cluster, nodes, containers, and applications:

```
  The Car Dashboard Analogy:
  • Speedometer (Metrics) ──► Prometheus & Grafana (Tracking CPU, memory, requests/sec).
  • Black Box (Logs)      ──► Loki / Elasticsearch (Diagnostic log streams).
  • GPS Journey (Traces)  ──► OpenTelemetry & Jaeger (Tracking request latency across microservices).
```

```
  The Complete Observability Stack:
  • Prometheus: Scrapes and stores time-series metric data via a pull model.
  • Grafana: Visualizes metrics and log dashboards.
  • Alertmanager: Dispatches high-priority alerts to Slack, PagerDuty, or Email.
```

```yaml
# Spring Boot Actuator: pom.xml dependencies
# <artifactId>spring-boot-starter-actuator</artifactId>
# <artifactId>micrometer-registry-prometheus</artifactId>

# application.yml: Exposing the Prometheus metrics endpoint
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  metrics:
    export:
      prometheus:
        enabled: true
```

### Prometheus Scrape Architecture & Core Exporters

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Component                       │ Metrics Provided & Collection Mechanism                                         │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Spring Boot Actuator**        │ JVM Heap, GC pauses, HikariCP connections, HTTP Latency (`/actuator/prometheus`)│
  │ **cAdvisor** (In `kubelet`)     │ Per-container CPU throttling, Memory usage, Network RX/TX bytes.                │
  │ **Node Exporter** (DaemonSet)   │ Physical host hardware stats (CPU, RAM, Disk I/O, OS load).                     │
  │ **kube-state-metrics**          │ Kubernetes API object stats (Pod crash counts, Deployment replica status).      │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### The Prometheus Operator: `ServiceMonitor`

Rather than manually configuring Prometheus scrape targets, the **Prometheus Operator** uses custom resources:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: payment-service-monitor
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: payment-api
  endpoints:
  - port: http
    path: /actuator/prometheus
    interval: 15s
```

## 🔴 Senior Level

### Google SRE 4 Golden Signals & Alerting Rules

```
  ┌──────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Golden Signal        │ PromQL Metric Query                      │ Critical Alert Threshold                         │
  ├──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. Latency**       │ `histogram_quantile(0.99, ...)`          │ p99 latency > 800ms for > 5 minutes              │
  │ **2. Traffic**       │ `sum(rate(http_requests_total[5m]))`     │ Sudden 80% drop in normal request rate           │
  │ **3. Errors**        │ `rate(http_requests_5xx[5m]) / rate(...)`│ HTTP 5xx error rate > 1.0%                       │
  │ **4. Saturation**    │ Container memory vs Cgroup limit         │ Memory > 90% or CPU Throttling > 25%             │
  └──────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Production Alerting Rule (PrometheusRule CRD)

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: payment-alerts
  namespace: monitoring
spec:
  groups:
  - name: payment.rules
    rules:
    - alert: PaymentServiceHigh5xxRate
      expr: |
        sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
        /
        sum(rate(http_server_requests_seconds_count[5m])) > 0.05
      for: 2m
      labels:
        severity: critical
      annotations:
        summary: "Payment API 5xx error rate exceeded 5% for 2 minutes"

    - alert: PodCrashLooping
      expr: rate(kube_pod_container_status_restarts_total[5m]) * 60 > 2
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.pod }} is restarting frequently (CrashLoopBackOff)"
```

### Full Distributed Tracing: OpenTelemetry & Grafana Tempo

For microservice call chains ($A \to B \to C \to DB$), log inspection is insufficient:
- **OpenTelemetry Java Agent:** Injects `traceparent` W3C headers across HTTP/gRPC boundaries without modifying application code.
- **Grafana Tempo / Jaeger:** Renders timeline flame graphs pinpointing the exact microservice causing p99 latency spikes.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The 3 Pillars of Observability:** Metrics (Prometheus/Grafana), Logs (Loki/Fluentbit), Traces (OpenTelemetry/Jaeger).
- **The 4 Golden Signals:** Latency, Traffic, Errors, Saturation.
- **Prometheus Model:** Pull-based metric scraping (every 15–30s) from `/metrics` or `/actuator/prometheus`.
- **Infrastructure Metrics:** `cAdvisor` (container CPU/memory) + `kube-state-metrics` (K8s API object state).
- **Spring Boot Standard:** `spring-boot-starter-actuator` + `micrometer-registry-prometheus`.

**Common Follow-up Questions:**
- *"What is the difference between cAdvisor and kube-state-metrics?"* → `cAdvisor` collects raw runtime resource metrics (CPU, RAM, network) from the container runtime; `kube-state-metrics` listens to the Kubernetes API server to report cluster object states (pod status, replica counts, node conditions).
- *"How does the Prometheus pull model discover new Pods automatically?"* → Prometheus connects to the `kube-apiserver` to watch Pod/Service endpoints dynamically via Kubernetes Service Discovery (SD).
- *"What is CPU Throttling and how do you detect it?"* → When a container exceeds its `resources.limits.cpu`, Linux CFS throttles CPU cycles rather than killing the pod; monitor `container_cpu_cfs_throttled_periods_total`.

**Red Flags (DO NOT Say):**
- ❌ *"Monitoring only requires checking `kubectl top pods` periodically."* (`kubectl top` only provides momentary snapshots without historical graphing or alerting).
- ❌ *"Prometheus pushes metrics from applications to a central collector."* (Prometheus uses a **pull model**, scraping HTTP endpoints).
- ❌ *"CPU throttling triggers the OOMKiller."* (CPU throttling slows execution; exceeding memory limits triggers the OOMKiller).
