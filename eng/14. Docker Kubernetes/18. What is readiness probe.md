# What is Readiness Probe?

---

## 🟢 Junior Level

A **Readiness Probe** is a health check configured in Kubernetes to determine whether an application Pod is fully prepared to accept and process incoming network traffic:

```
  Restaurant Opening Analogy:
  • The kitchen is lit and the ovens are on (The container process is running).
  • But the chef is still slicing vegetables and pre-heating the grill (Warming up caches/DB pool).
  • The host (Readiness Probe) keeps the front doors locked until the kitchen signals: "Ready for customers!"
```

```yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 5
  failureThreshold: 3
```

```
  Action on Failure:
  • Container is NOT killed or restarted!
  • Pod IP is IMMEDIATELY removed from the Service's Endpoints / EndpointSlice.
  • Traffic stops routing to this Pod until the probe succeeds again.
```

## 🟡 Middle Level

### Side-by-Side Comparison: Liveness vs. Readiness Probe

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Characteristic               │ Liveness Probe                   │ Readiness Probe                                  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Primary Objective**        │ Detect unrecoverable deadlocks   │ Gate incoming traffic until warmup is complete   │
  │ **Action on Failure**        │ 💥 **Kills and Restarts** Pod    │ 🛡️ **Removes Pod from Service Endpoints**       │
  │ **Pod Restart Count**        │ Increments on every failure      │ Stays unchanged (`0/1 READY` in `kubectl get`)   │
  │ **Target Dependencies**      │ Internal JVM threads only        │ DB pool, cache warmup, broker connections        │
  │ **Zero-Downtime Role**       │ Recovers frozen production nodes │ Blocks traffic switchover during Rolling Updates │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Zero-Downtime Rolling Update Synchronization

```
  [Rolling Update Triggered: Deployment v1 ➔ v2]
  1. K8s spawns new Pod v2.
  2. Pod v2 boots in ~20 seconds (Status: `Running 0/1 READY`).
  3. K8s holds traffic routing to old Pod v1.
  4. Pod v2 passes Readiness Probe (Status: `Running 1/1 READY`).
  5. Service adds Pod v2 IP to `EndpointSlice` ──► Traffic routes to v2!
  6. K8s sends `SIGTERM` to old Pod v1 and gracefully terminates it.
```

## 🔴 Senior Level

### Spring Boot 3.x Dynamic Readiness State Management

Spring Boot provides programmatic control over the `ReadinessState` event bus. Under extreme load, a service can temporarily mark itself unready to shed load:

```java
@Service
@RequiredArgsConstructor
public class OrderBatchProcessingService {

    private final ApplicationEventPublisher eventPublisher;

    public void processMassiveNightlyBatch() {
        try {
            // 1. Temporarily pull this instance out of the Kubernetes Load Balancer:
            AvailabilityChangeEvent.publish(eventPublisher, this, ReadinessState.REFUSING_TRAFFIC);

            executeHeavyCalculations();

        } finally {
            // 2. Restore healthy status to resume receiving user HTTP requests:
            AvailabilityChangeEvent.publish(eventPublisher, this, ReadinessState.ACCEPTING_TRAFFIC);
        }
    }
}
```

```
  Under the hood:
  • `/actuator/health/readiness` automatically returns HTTP 503 Service Unavailable when 
    `ReadinessState.REFUSING_TRAFFIC` is active.
  • Kubelet detects the 503 and removes the pod from the Service VIP in <5 seconds.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Role:** Determines if the Pod can accept traffic; failures **remove the Pod from Service Endpoints** without restarting it.
- **Zero-Downtime Key:** Rolling updates depend on Readiness Probes to prevent traffic from hitting uninitialized pods.
- **`kubectl get pods` Status:** A failed readiness probe displays `0/1 READY`, but the status remains `Running`.
- **Target Checks:** Cache preloading, Flyway migrations, connection pools, and downstream dependency verification.
- **Dynamic Gating:** Applications can programmatically refuse traffic via Spring Boot `AvailabilityChangeEvent`.

**Common Follow-up Questions:**
- *"What happens if a Deployment has no Readiness Probe configured?"* → Kubernetes immediately considers new pods ready as soon as the container process starts (`PID` launched), forwarding user traffic to Spring Boot before it has finished booting, causing widespread HTTP 502/503 errors during deployments!
- *"How quickly does Kubernetes remove an unready Pod from receiving traffic?"* → Within `periodSeconds * failureThreshold` (typically 5–15 seconds); `kube-proxy` / CNI updates iptables/IPVS rules across worker nodes.
- *"Why should you never omit Readiness Probes on stateful microservices?"* → Because DB connection initialization and cache hydration take time; without readiness probes, unhydrated pods return errors to active users.

**Red Flags (DO NOT Say):**
- ❌ *"If the Readiness Probe fails, Kubernetes restarts the container."* (Liveness restarts containers; Readiness only detaches the Pod from Service routing).
- ❌ *"You only need a Liveness Probe; Readiness Probes are redundant."* (Liveness without Readiness guarantees downtime during rolling deployments).
- ❌ *"Readiness Probes should only check if port 8080 is open via TCP."* (TCP port checks succeed before Spring Boot finishes initializing the Spring ApplicationContext).
