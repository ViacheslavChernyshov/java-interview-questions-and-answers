# What Happens If You Override Getter in Subclass of Immutable Class?

---

## 🟢 Junior Level

If an immutable class is **not marked `final`**, a subclass can override its getter accessors and return dynamically mutating values, **completely destroying immutability guarantees**:

```java
// ❌ FLAWED BASE CLASS (Not final):
public class Money {
    private final long amount;

    public Money(long amount) { this.amount = amount; }
    public long getAmount() { return amount; }
}

// 💥 Subclass overrides getter with mutable field:
public class FraudulentMoney extends Money {
    private long dynamicAmount;

    public FraudulentMoney(long initial) {
        super(initial);
        this.dynamicAmount = initial;
    }

    public void setAmount(long amount) { this.dynamicAmount = amount; }

    @Override
    public long getAmount() {
        return this.dynamicAmount; // 💥 Hijacked getter returns mutated state!
    }
}
```

```java
Money wallet = new FraudulentMoney(100);
System.out.println(wallet.getAmount()); // Prints 100

((FraudulentMoney) wallet).setAmount(999);
System.out.println(wallet.getAmount()); // 💥 Prints 999 (Even though variable type is Money!)
```

---

## 🟡 Middle Level

### Violation of the Liskov Substitution Principle (LSP)

This is a textbook violation of the **Liskov Substitution Principle**:
- **Parent Contract:** Declares that the return value of `getAmount()` is immutable and deterministic across all threads forever.
- **Subclass Reality:** The subclass introduces volatile dynamic state, causing unpredictable bugs for downstream consumers.

### Catastrophic Downstream Impact

```
  ┌──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Vulnerable Area                  │ Failure Impact                                                                  │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`HashMap` / `HashSet` Keys**   │ Mutating the child field changes the key's `hashCode()`, stranding the entry in │
  │                                  │ the wrong bucket and causing permanent memory leaks.                            │
  │ **Thread Safety & Visibility**   │ Base fields have JMM `final` freeze guarantees; child fields lack memory fences,│
  │                                  │ causing data races and reading stale CPU cache line values.                     │
  └──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Bytecode Mechanics: `invokevirtual` & Dynamic Dispatch

In Java bytecode, calling a non-static, non-private method compiles to **`invokevirtual`**:

```
invokevirtual #4 // Method Money.getAmount:()J
```

- At runtime, the JVM performs a **`vtable` (virtual method table)** lookup using the actual runtime heap instance (`FraudulentMoney`).
- Even though the variable is typed as `Money`, the JVM dispatches execution to `FraudulentMoney.getAmount()`.
- **Senior Takeaway:** The Java Memory Model guarantees field immutability in memory, but **cannot prevent polymorphic method hijacking**.

```
  3 Architectural Defenses:
  1. Declare the Class `final`: `public final class Money { ... }`
  2. Private Constructors + Static Factory: `private Money(...)` + `public static Money of(...)`
  3. Java 16+ Records: Records are implicitly `final` and component getters cannot be overridden via inheritance.
```

---

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Hazard:** Polymorphic dynamic dispatch (`invokevirtual`) routes method execution to the subclass's overridden getter.
- **LSP Violation:** Subclasses break the invariant contract of the parent class.
- **HashMap Destruction:** Altering getter return values alters `hashCode()`, losing map entries.
- **Concurrency Danger:** Subclass mutable fields lack JMM `final` freeze barriers, introducing data races.
- **Solution:** Always declare immutable classes as `final`, or use private constructors with static factories.

**Common Follow-up Questions:**
- *"Why didn't `final` on the parent field prevent this bug?"* → The parent's `final amount` field remained untouched in memory, but the overridden getter bypassed that field entirely to read the subclass's mutable field.
- *"Can a subclass override a getter if the method itself is marked `final`?"* → No; marking the method `public final long getAmount()` prevents method overriding, but marking the whole class `final` is cleaner.
- *"How do Java 16+ Records protect against this?"* → Records are implicitly `final` and cannot be extended.

**Red Flags (DO NOT Say):**
- ❌ *"Declaring fields as `final` prevents subclasses from overriding getters."* (Method overriding is a polymorphic feature independent of field modifiers).
- ❌ *"Polymorphism is disabled when a method returns a primitive value."* (Primitive return types follow standard virtual dispatch).
- ❌ *"Overridden getters are thread-safe as long as the parent class is thread-safe."* (Child classes introduce non-final mutable fields that lack thread-safety guarantees).
