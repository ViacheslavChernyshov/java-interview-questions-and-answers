# How Does String Pool Work and How is It Related to Immutability?

---

## 🟢 Junior Level

The **String Pool** is a specialized area in the Java Heap that stores unique instances of string literals by implementing the **Flyweight Pattern**:

```java
String s1 = "Hello";
String s2 = "Hello"; // Reuses the existing instance from String Pool

System.out.println(s1 == s2); // true (Both variables point to the EXACT same memory address!)

String s3 = new String("Hello"); // Explicitly allocates a new instance in the general Heap
System.out.println(s1 == s3); // false (Different memory addresses)
```

```
  💥 Why String Pool is IMPOSSIBLE Without Immutability:
  • If strings were mutable, calling `s1.setCharAt(0, 'J')` would mutate the shared pool instance.
  • `s2` and every framework in the JVM referencing `"Hello"` would silently become `"Jello"`!
  • Global sharing across threads is safe ONLY because strings can never be modified.
```

## 🟡 Middle Level

### Bytecode Resolution: The Constant Pool & `ldc` Opcode

During compilation, javac places string literals into the `.class` Constant Pool. At runtime, the JVM executes the **`ldc` (load constant)** instruction:

```
0: ldc           #2                  // Loads reference from native StringTable
2: astore_1
3: new           #3                  // Allocates new String object on Heap
6: dup
7: ldc           #2                  // Loads "Hello" literal to pass to constructor
9: invokespecial #4                  // Method java/lang/String."<init>":(Ljava/lang/String;)V
```

### Memory Location History: PermGen vs. Java Heap

```
  ┌────────────────────────┬──────────────────────────────────┬────────────────────────────────────────────────┐
  │ Java Version           │ Storage Location                 │ GC & OutOfMemory Behavior                      │
  ├────────────────────────┼──────────────────────────────────┼────────────────────────────────────────────────┤
  │ **Java 6 & Earlier**   │ **PermGen** (Fixed size, 64MB)   │ Calling `intern()` caused `OOM: PermGen space` │
  │ **Java 7+ & Modern**   │ **Standard Java Heap**           │ Unreferenced pooled strings collected by GC    │
  └────────────────────────┴──────────────────────────────────┴────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### HotSpot Internals: The Native C++ `StringTable`

Under the hood, the String Pool is implemented inside the HotSpot JVM as a native C++ hash table (`StringTable`):
- **Collision Resolution:** Open hashing with linked bucket chaining.
- **Bucket Size Tuning:** `-XX:StringTableSize=65536` (Default in modern Java 11/17/21).
- **The Highload UUID Anti-Pattern:** Interning millions of high-cardinality strings (e.g. random UUIDs) creates massive bucket collisions, degrading `intern()` from $O(1)$ to a CPU-intensive $O(N)$ linked list search.

### `String.intern()` vs. G1 GC String Deduplication

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Feature                      │ `String.intern()`                │ G1 String Deduplication (`-XX:+UseStringDedup`) │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Mechanism**                │ Adds reference to `StringTable`  │ Merges backing `byte[]` arrays during GC passes  │
  │ **Invocation**               │ Synchronous code call            │ Low-priority background GC thread                │
  │ **Reference Identity (`==`)**│ Evaluates to **`true`**          │ Evaluates to **`false`** (Wrappers are distinct) │
  │ **Native Table Pollution**   │ Pollutes C++ `StringTable`       │ Off-heap native memory table (~20MB)             │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A JVM heap cache storing unique string literals via the Flyweight Pattern.
- **Immutability Dependency:** Sharing instances globally is only safe because characters cannot be mutated in place.
- **Memory Evolution:** Moved from PermGen (Java 6) to the regular Java Heap (Java 7+), allowing standard GC reclamation.
- **Bytecode:** Loaded at runtime via the `ldc` instruction.
- **Highload Hazard:** Avoid calling `intern()` on dynamic random data (UUIDs) to prevent `StringTable` collision bottlenecks.
- **Modern Alternative:** Use G1 GC String Deduplication (`-XX:+UseStringDeduplication`) for zero-code memory optimization.

**Common Follow-up Questions:**
- *"How many objects does `new String("abc")` create?"* → Two objects: one in the String Pool (if `"abc"` wasn't loaded already) and one in the general Java Heap.
- *"Can pooled strings be garbage collected?"* → Yes; in Java 7+, unreferenced dynamically interned strings are swept during standard GC cycles.
- *"What is the time complexity of `intern()`?"* → $O(1)$ average; degrades to $O(N)$ if the `StringTable` is saturated with millions of colliding entries.

**Red Flags (DO NOT Say):**
- ❌ *"The String Pool is located in Metaspace / PermGen in Java 17."* (It lives in the standard Java Heap).
- ❌ *"Calling `intern()` on all user inputs improves application throughput."* (It causes lock contention and bucket saturation in `StringTable`).
- ❌ *"`new String("text") == "text"` returns true."* (`new` always creates a distinct heap instance; returns `false`).
