# Can You Use Immutable Objects as Keys in HashMap?

---

## 🟢 Junior Level

**Not only can you, but you absolutely should!** Immutable objects are the **strongly recommended, ideal keys** for `HashMap`, `HashSet`, and `ConcurrentHashMap`:

```java
Map<String, Integer> scores = new HashMap<>();
scores.put("Alice", 100); // String is immutable
scores.put("Bob", 95);

System.out.println(scores.get("Alice")); // 100 (Safe, reliable lookup)
```

```
  Why Immutable Keys are Best Practice:
  1. Invariant `hashCode()`: The hash code is constant forever; the key never lands in the wrong bucket.
  2. Invariant `equals()`: Value equality checks remain 100% deterministic.
  3. Zero Ghost Entries: Keys cannot mutate and become lost in memory.
```

---

## 🟡 Middle Level

### The HashMap Bucket Mechanics

`HashMap` locates entries in two steps:
1. **`put(key, value)`:** Computes `key.hashCode()`, derives the bucket index `(capacity - 1) & hash`, and places the entry in that bucket.
2. **`get(key)`:** Re-computes `key.hashCode()` and searches that exact bucket.

```
  Immutable Key Lookup (Guaranteed Success):
  put("user_1", val) ──► hash("user_1") = 42 ──► Stored in Bucket 10
  get("user_1")      ──► hash("user_1") = 42 ──► Found in Bucket 10!
```

### Pre-Cached `hashCode()` Optimization

Because immutable objects cannot mutate, classes like `String` compute their hash code lazily once and cache it in a private field:

```java
// java.lang.String internal caching:
private int hash; // 0 by default

public int hashCode() {
    int h = hash;
    if (h == 0 && !value.isEmpty()) {
        h = computeHash(); // Computed exactly ONCE
        hash = h;          // Cached permanently!
    }
    return h; // Subsequent calls return cached integer in 0 ms!
}
```

## 🔴 Senior Level

### Composite Keys with Java 16+ Records

Java `record`s are the ultimate modern tool for composite multi-field map keys:

```java
// Clean, boilerplate-free composite key:
public record TenantOrderKey(String tenantId, UUID orderId) {}

Map<TenantOrderKey, OrderStatus> orderMap = new HashMap<>();

TenantOrderKey key = new TenantOrderKey("US-EAST", UUID.randomUUID());
orderMap.put(key, OrderStatus.PROCESSING);

// Fast, deterministic lookup:
OrderStatus status = orderMap.get(key);
```

### Fallback Strategies If a Key MUST Be Mutable

If legacy constraints force you to work with mutable keys:
1. **Extract Immutable Identifiers:** Use `Long id` or `UUID` as the map key instead of the whole entity.
2. **Delete-Modify-Insert Pattern:**
   ```java
   map.remove(key);       // 1. Remove from old bucket
   key.setStatus("ACTIVE"); // 2. Mutate in isolation
   map.put(key, value);   // 3. Insert into new bucket
   ```
3. **`IdentityHashMap`:** Compares keys purely by memory address reference (`==`) and `System.identityHashCode(k)`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Verdict:** Immutable objects are the gold standard for `HashMap` keys.
- **Why Required:** Guarantees that `hashCode()` and `equals()` remain completely invariant across the lifetime of the application.
- **Top Key Choices:** `String`, `UUID`, `Integer`/`Long`, `LocalDate`, and Java **`record`** types.
- **Hash Caching:** Immutability allows lazy one-time evaluation and caching of `hashCode()` in a private field.
- **Mutable Key Bug:** Mutating a key shifts its hash code, losing the entry in the old bucket and causing logical memory leaks.

**Common Follow-up Questions:**
- *"Why is `String` the most popular key in Java?"* → It is immutable, pre-caches its `hashCode()`, has fast SIMD string equality checks, and reuses literals via the String Pool.
- *"What happens if you use `ArrayList` as a HashMap key?"* → Adding an item (`list.add("X")`) alters the list's `hashCode()`; subsequent `map.get(list)` searches the wrong bucket and returns `null`.
- *"Can a `record` be used as a composite key?"* → Yes; records are implicitly `final`, immutable, and automatically generate correct `equals()` and `hashCode()` methods over all components.

**Red Flags (DO NOT Say):**
- ❌ *"Using mutable objects like `ArrayList` or custom JavaBeans as map keys is fine as long as they aren't modified concurrently."* (Even single-threaded modifications corrupt hash bucket indexing).
- ❌ *"HashMap automatically recalculates bucket positions if a key's fields are modified."* (HashMap has no listeners and is completely unaware of internal key mutations).
- ❌ *"`IdentityHashMap` solves all problems with mutable keys."* (`IdentityHashMap` uses reference identity `==` instead of `.equals()`, which breaks standard value equality).
