# What is an Immutable Object?

---

## 🟢 Junior Level

An **Immutable Object** is an object whose observable state **cannot be modified** after its construction has finished. Once created, all internal data remains permanently fixed for the lifetime of the object:

```java
// Standard Immutable Class:
public final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }
    // No mutator methods (setters) exist!
}
```

```
  Key Characteristics of Immutable Objects:
  1. No Setters / Mutators: No methods alter internal fields.
  2. `final` Class: Subclasses cannot override methods to introduce mutable state.
  3. `private final` Fields: Memory references cannot be reassigned after construction.
```

## 🟡 Middle Level

### The 5 Golden Rules of Immutability

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Immutability Rule                │ Why It Is Required                                                          │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Declare the Class `final`**    │ Prevents subclasses from overriding getters or introducing mutable fields.  │
  │ 2 │ **Make All Fields `final`**      │ Enforces single initialization and JMM safe publication guarantees.         │
  │ 3 │ **Make All Fields `private`**    │ Prevents direct external field modification.                                │
  │ 4 │ **Zero Mutator Methods**         │ No `setX()`, `clear()`, `add()`, or in-place modification methods.          │
  │ 5 │ **Defensive Copying on Objects** │ Deep-copy all mutable fields (Lists, Dates, Arrays) in constructors/getters. │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// Modern Java 16+ Record (Built-in Immutability):
public record UserProfile(String username, List<String> roles) {
    // Compact constructor with defensive copy:
    public UserProfile {
        roles = List.copyOf(roles); // Replaces mutable list with unmodifiable copy
    }
}
```

## 🔴 Senior Level

### Java Memory Model (JMM §17.5) Final Field Semantics

The Java Memory Model provides special thread-safety guarantees for `final` fields:

```
  Thread A (Constructs Object)                  Thread B (Reads Object)
  ┌─────────────────────────────────┐           ┌─────────────────────────────────┐
  │ 1. Allocates memory on Heap     │           │ 1. Receives object reference    │
  │ 2. Writes field values          │           │ 2. Reads `final` fields         │
  │ 3. [FREEZE BARRIER (StoreStore)]│ ────────► │ 🛡️ GUARANTEED: Sees initialized │
  │ 4. Publishes object reference   │           │    field values without locks!  │
  └─────────────────────────────────┘           └─────────────────────────────────┘
```

- **Freeze Action:** At the end of the constructor, the JVM inserts a memory fence that "freezes" all `final` fields.
- **Safe Publication:** Any thread reading an immutable object's reference after construction is guaranteed to see fully initialized field values without needing `synchronized` or `volatile` keywords.

### The Constructor Escape Hazard (`this` Leak)

```java
public final class LeakyImmutable {
    private final int id;

    public LeakyImmutable(int id) {
        this.id = id;
        EventListener.register(this); // 💥 CRITICAL ERROR: `this` escapes before freeze barrier!
    }
}
```

> [!CAUTION]
> If `this` is published to another thread (via event listeners, callbacks, or static collections) inside the constructor, concurrent threads may read uninitialized default values (`id = 0`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** An object whose state cannot be changed after instantiation.
- **5 Rules:** `final` class, `private final` fields, no setters, defensive copying on mutable references, no constructor escape.
- **Thread Safety:** Naturally thread-safe without locks due to lack of mutable shared state.
- **JMM Guarantee:** Section 17.5 guarantees safe publication of `final` fields across threads.
- **Modern Idiom:** Use Java 16+ **`record`** components for clean, boilerplate-free immutable data transfer objects.
- **Collections:** Always use `List.copyOf()` or `Collections.unmodifiableList()` to prevent backing list mutations.

**Common Follow-up Questions:**
- *"Is an object immutable if all its fields are marked `final`?"* → Not necessarily; if a `final` field points to a mutable object (e.g. `final List<String> items`), callers can still modify the list's contents (`items.add("new")`).
- *"Why must an immutable class be declared `final`?"* → To prevent malicious or buggy subclasses from extending the class, adding mutable fields, or overriding getters to return modified state.
- *"How does HotSpot optimize immutable objects?"* → Bump-the-pointer allocation in Young Gen (Eden) makes short-lived immutable allocations nearly free, and immutability eliminates GC Old-Gen write barriers.

**Red Flags (DO NOT Say):**
- ❌ *"An immutable object is simply any class that doesn't have setter methods."* (If getters return direct references to mutable internal lists or arrays, callers can mutate it externally).
- ❌ *"Immutability always makes applications slower due to object allocation."* (In multi-threaded environments, eliminating lock contention and synchronization barriers makes immutable architectures significantly faster).
- ❌ *"Records are fully immutable by default even if they contain mutable objects."* (Records are shallowly immutable; you must still defensively copy mutable fields like `List` or `Date`).
