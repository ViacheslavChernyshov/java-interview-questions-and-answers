# What Happens If You Modify a Mutable Key in HashMap?

---

## 🟢 Junior Level

If you mutate an object that is currently used as a key in a `HashMap`, that entry **becomes lost and completely unlocatable** ("Ghost Entry"):

```java
// ❌ DANGEROUS ANTI-PATTERN: Using a mutable ArrayList as a Map key:
List<String> roles = new ArrayList<>(List.of("USER"));

Map<List<String>, String> permissions = new HashMap<>();
permissions.put(roles, "READ_ONLY_ACCESS");

System.out.println(permissions.get(roles)); // "READ_ONLY_ACCESS" (Works initially)

// 💥 DISASTER: Mutate the key in-place:
roles.add("ADMIN"); 

// Lookups fail completely:
System.out.println(permissions.get(roles));         // ❌ Returns null!
System.out.println(permissions.containsKey(roles)); // ❌ Returns false!
System.out.println(permissions.size());              // ⚠️ Returns 1 (The entry is STILL pinned in RAM!)
```

```
  Luggage Lockers Analogy:
  • You store a blue suitcase in Locker #5 (derived from color "Blue").
  • Overnight, someone repaints the suitcase "Red".
  • In the morning, the system searches Locker #10 (derived from "Red"), finds it empty, 
    and reports "Luggage Not Found". Your suitcase is trapped in Locker #5 forever!
```

## 🟡 Middle Level

### The Dual Point of Failure in `HashMap.getNode()`

To understand why key mutation breaks lookups, observe the internal logic of `HashMap.getNode()`:

```java
final Node<K,V> getNode(Object key) {
    Node<K,V>[] tab; Node<K,V> first, e; int n, hash; K k;
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (first = tab[(n - 1) & (hash = hash(key))]) != null) { // 1. Target Bucket Index
        
        // 2. Hash & Equality Verification:
        if (first.hash == hash && // ⚠️ COMPARES CACHED HASH!
            ((k = first.key) == key || (key != null && key.equals(k))))
            return first;
        
        // 3. Bucket Chaining / Tree Traversal...
    }
    return null;
}
```

```
  Failure 1: Bucket Index Mismatch
  • Inserted at Bucket 5 (Old Hash).
  • Lookup searches Bucket 12 (New Hash). Bucket 12 is empty ──► Returns null!

  Failure 2: Cached Node Hash Mismatch (Even on Index Collision!)
  • Even if Bucket 5 matches, `Node<K,V>` holds `cachedHash` computed during `put()`.
  • The check `first.hash == hash` evaluates to `false`, discarding the node even if `first.key == key` is `true`!
```

### HashSet Duplication Bug

Because `HashSet` is backed internally by a `HashMap<E, Object>`, mutating a set element allows adding the **exact same instance a second time**:

```java
Set<List<String>> set = new HashSet<>();
List<String> list = new ArrayList<>(List.of("A"));
set.add(list);

list.add("B"); // Mutate list
set.add(list); // 💥 Successfully adds the same object twice!

System.out.println(set.size()); // Prints 2 duplicate elements in a Set!
```

## 🔴 Senior Level

### Memory Leak Mechanics & The `resize()` Trap

1. **Logical Memory Leak (Zombie Entry):**
   - The orphaned entry is retained by a strong reference in `table[bucket]`.
   - The Garbage Collector **cannot free either key or value**, causing memory bloat.
   - The entry can only be recovered or deleted by iterating through `map.entrySet()` in $O(N)$ time.
2. **Rehashing Disasters on `resize()`:**
   - When table capacity expands, `HashMap` redistributes nodes using `node.hash` (the original cached hash).
   - The ghost node is moved to a new bucket derived from its *old* hash, cementing its permanently unlocatable status.

### 3 Architectural Solutions

```
  ┌───┬──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ # │ Pattern                      │ Implementation                                                                  │
  ├───┼──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Immutable Records**        │ `public record UserKey(String tenant, UUID userId) {}` (Default Rule)           │
  │ 2 │ **Delete-Modify-Insert**     │ `map.remove(key); key.modify(); map.put(key, val);`                             │
  │ 3 │ **`IdentityHashMap`**        │ Compares references via `==` and `System.identityHashCode(k)` (Bypasses hash).   │
  └───┴──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Outcome:** The entry is lost; `get()` and `containsKey()` return `null`/`false`, while `size()` still counts it.
- **Dual Cause:** Searches the wrong bucket, and fails the `first.hash == hash` cached hash comparison.
- **Memory Leak:** Strong references in `table` prevent GC collection of orphaned keys and values.
- **HashSet Duplication:** Mutating items breaks set uniqueness, allowing duplicate entries.
- **Recovery:** Orphaned entries can only be located by a full $O(N)$ scan of `map.entrySet()`.

**Common Follow-up Questions:**
- *"Why does `map.get(key)` fail even if `key1.equals(key2)` is true?"* → `HashMap` checks `hash == node.hash` first as a fast-path filter; if hashes differ, `.equals()` is never even called.
- *"How can you safely mutate a map key?"* → Remove the key first (`map.remove(key)`), perform the mutation, and re-insert (`map.put(key, value)`).
- *"How does `IdentityHashMap` behave with mutable keys?"* → It uses `System.identityHashCode(key)` (memory address), which never changes when object fields are mutated.

**Red Flags (DO NOT Say):**
- ❌ *"HashMap automatically updates bucket positions when a key is modified."* (HashMap has no listeners and cannot detect mutations).
- ❌ *"Mutating a key causes HashMap to throw a ConcurrentModificationException."* (No exception is thrown; lookups simply return `null` silently).
- ❌ *"The Garbage Collector automatically reclaims lost keys from HashMap."* (The strong reference in the internal array prevents GC).
