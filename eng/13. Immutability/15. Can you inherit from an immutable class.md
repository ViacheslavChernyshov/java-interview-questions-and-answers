# Can You Inherit From an Immutable Class?

---

## 🟢 Junior Level

Technically in Java, you **can** inherit from a class if it lacks the `final` keyword; however, doing so is a **dangerous architectural anti-pattern** that completely destroys immutability guarantees:

```java
// ❌ ARCHITECTURAL FLAW: Forgot the `final` keyword on the parent class:
public class Money {
    private final long amount;

    public Money(long amount) { this.amount = amount; }
    public long getAmount() { return amount; }
}

// 💥 Malicious/buggy subclass injects mutable state:
public class FraudulentMoney extends Money {
    private long stolenAmount;

    public FraudulentMoney(long amount) { super(amount); }
    public void setStolenAmount(long stolen) { this.stolenAmount = stolen; }

    @Override
    public long getAmount() {
        return super.getAmount() + stolenAmount; // 💥 Dynamic mutable state returned!
    }
}
```

```
  Core Invariant:
  • An immutable class MUST prevent subclassing.
  • Otherwise, subclasses can override accessors or introduce mutable state!
```

---

## 🟡 Middle Level

### Violation of the Liskov Substitution Principle (LSP)

The **Liskov Substitution Principle (LSP)** requires that objects of a subclass must be substitutable for objects of a superclass without altering program correctness.

```
  Parent Contract (Immutable Money):
  • `getAmount()` is 100% deterministic and invariant forever.
  • Safe for lock-free caching in `ConcurrentHashMap`.
  • `hashCode()` is constant and safe for `HashSet`.

  Subclass Reality (`FraudulentMoney`):
  • `getAmount()` changes dynamically at runtime.
  • Concurrency data races and corrupted cache entries occur.
```

### 2 Architectural Solutions to Prevent Subclassing

#### 1. Composition Over Inheritance (*Effective Java Item 18*)
```java
public final class LabeledMoney {
    private final Money money;       // Encapsulates the immutable object
    private final String currency;

    public LabeledMoney(Money money, String currency) {
        this.money = money;
        this.currency = currency;
    }
}
```

#### 2. Private Constructors with Static Factories (*Effective Java Item 17*)
```java
public class SecureMoney {
    private final long amount;

    // Private constructor blocks external subclasses from calling super():
    private SecureMoney(long amount) {
        this.amount = amount;
    }

    public static SecureMoney of(long amount) {
        return new SecureMoney(amount);
    }
}
```

## 🔴 Senior Level

### Modern Java Standard: Sealed Hierarchies (Java 17+ JEP 409)

When your domain architecture genuinely requires a **closed polymorphism hierarchy**, use **`sealed` types with immutable `record`s**:

```java
// Bounded type hierarchy:
public sealed interface TransactionResult permits Success, Failure {}

// All implementations are inherently final and immutable:
public record Success(String txId, long timestamp) implements TransactionResult {}
public record Failure(String errorCode, String reason) implements TransactionResult {}
```

```java
// 🚀 Exhaustive Pattern Matching in Java 21+ (No default branch required!):
String status = switch (result) {
    case Success s -> "Completed: " + s.txId();
    case Failure f -> "Failed: " + f.reason();
};
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Verdict:** Subclassing an immutable class is an anti-pattern that destroys thread safety and violates LSP.
- **Root Danger:** Subclasses can override getters to return dynamic mutable state or add mutable fields.
- **Protection Techniques:** Mark class `final`, use `private` constructors with static factories, or use Java 17 `sealed` hierarchies.
- **JDK Standard:** All foundational JDK immutable classes (`String`, `Integer`, `LocalDate`, `BigDecimal`) are declared `final`.
- **Modern Solution:** Use Java 17+ `sealed interface` combined with `record` components for safe Algebraic Data Types (ADTs).

**Common Follow-up Questions:**
- *"How can you extend the functionality of an immutable class without inheritance?"* → Wrap it using the **Composition Pattern** (`private final ImmutableClass delegate`).
- *"Can a `record` inherit from a class?"* → No; all records implicitly extend `java.lang.Record` and are implicitly `final`.
- *"Why are Sealed Classes better than package-private constructors?"* → Sealed classes provide compile-time exhaustive pattern matching in `switch` expressions and enforce strict type boundaries across packages and modules.

**Red Flags (DO NOT Say):**
- ❌ *"Subclassing an immutable class is safe as long as the child class doesn't define setters."* (The child class can still override getters to compute values dynamically).
- ❌ *"Declaring a class `final` violates good OOP design and polymorphism."* (For value objects and domain data carriers, `final` is essential for correctness and security).
- ❌ *"Records can be extended by other classes."* (Records are implicitly `final` and cannot be subclassed).
