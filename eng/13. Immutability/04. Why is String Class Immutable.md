# Why is String Class Immutable?

---

## 🟢 Junior Level

In Java, the **`java.lang.String` class is strictly Immutable**: once created in memory, its character sequence can **never be changed**:

```java
String original = "Java";
original.concat(" Developer"); // Creates a new String, but the return value is ignored!

System.out.println(original); // Prints "Java" (The original string is completely unchanged)

// To preserve the modification, assign the new reference:
String updated = original.concat(" Developer");
System.out.println(updated);  // Prints "Java Developer" (A brand new object in the Heap)
```

```
  The 4 Core Reasons for String Immutability:
  1. String Pool: Reuses identical string literals across the entire JVM to save RAM.
  2. Security: Prevents file paths, class loaders, and network sockets from being tampered with.
  3. Thread Safety: Strings can be shared across multiple threads without locks or synchronization.
  4. Cached HashCode: Pre-computed hash codes make HashMap lookups fast and deterministic.
```

---

## 🟡 Middle Level

### 1. The String Pool (Flyweight Pattern)

Because strings are immutable, thousands of components can safely reference the exact same literal:

```java
String s1 = "interview";
String s2 = "interview";

System.out.println(s1 == s2); // true (Both variables point to the same String Pool instance)
```

If strings were mutable, calling `s1.setCharAt(0, 'I')` would silently corrupt `s2` and every third-party library referencing `"interview"`.

### 2. Protection Against TOCTOU Security Exploits

Strings are passed as security parameters into OS system calls and filesystem APIs:

```java
public void deleteUserFile(String filePath) {
    if (!securityManager.isPathAllowed(filePath)) { // 1. Time-of-Check (Security validation)
        throw new SecurityException("Access Denied");
    }

    // If String were mutable, a malicious concurrent thread could mutate filePath here!
    fileSystem.deleteFile(filePath); // 2. Time-of-Use (Execution)
}
```

### 3. Why Passwords Should NEVER Be Stored in String

Because strings are immutable, plain-text passwords remain pinned in Heap memory until an unpredictable Garbage Collector cycle occurs. If a server takes an emergency Heap Dump (`.hprof`), attackers can extract passwords in clear text.

```java
// ✅ RECOMMENDED: Store secrets in mutable char[] and zero it out immediately:
char[] password = readPasswordFromInput();
authenticate(password);
Arrays.fill(password, '0'); // Wipes plaintext password from RAM immediately!
```

## 🔴 Senior Level

### Internal Storage Evolution: Java 8 vs Java 9+ Compact Strings

```java
// Java 8 and earlier:
public final class String {
    private final char[] value; // UTF-16, always 2 bytes per char
    private int hash;
}

// Java 9+ Compact Strings (JEP 254):
public final class String {
    @Stable
    private final byte[] value; // 1 byte/char for Latin-1, 2 bytes/char for UTF-16
    private final byte coder;   // 0 = LATIN1, 1 = UTF16
    private int hash;           // Lazily computed and permanently cached hash
}
```

- **JMM Safe Publication (§17.5):** The JVM inserts a memory freeze barrier at constructor exit, guaranteeing that any thread reading a `String` reference sees fully initialized byte contents without `synchronized` locks.
- **Hardware SIMD Acceleration:** HotSpot C2 recognizes `String` immutability and compiles `equals()` and `indexOf()` loops into vectorized **AVX-2 / AVX-512** assembly instructions.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Pillars:** String Pool literal sharing, Thread Safety by design, TOCTOU security defense, and cached `hashCode`.
- **Implementation:** `public final class`, `@Stable private final byte[] value`, `private final byte coder`.
- **Security Rule:** Store passwords in `char[]` (not `String`) to zero out memory after use.
- **Hash Caching:** `hashCode()` is computed once lazily and cached permanently in `private int hash`.
- **G1 Deduplication:** G1 GC safely merges identical `byte[]` arrays in the background because strings are immutable.

**Common Follow-up Questions:**
- *"What is a TOCTOU attack?"* → Time-of-Check to Time-of-Use exploit where a concurrent thread mutates a security-checked string argument before the OS executes the action.
- *"Why does String cache its `hashCode` lazily instead of in the constructor?"* → To avoid wasting CPU cycles calculating hashes for strings that are never inserted into hash-based collections (`HashMap`, `HashSet`).
- *"Can string contents be changed via Java reflection?"* → In Java 8 yes; in modern Java (Java 16+ JEP 396), the Java Module System blocks reflection into `java.base`, throwing `InaccessibleObjectException`.

**Red Flags (DO NOT Say):**
- ❌ *"Calling `s.toUpperCase()` modifies `s` in place."* (It returns a brand new `String` object).
- ❌ *"The String Pool is stored in PermGen."* (PermGen was removed in Java 8; String Pool lives in the standard Java Heap).
- ❌ *"Storing passwords in `String` is completely secure if the variable is marked private."* (Plaintext strings stay in Heap RAM until GC; use `char[]` and zero it out).
