# How to Implement Builder Pattern for an Immutable Class

---

## 🟢 Junior Level

The **Builder Pattern** solves the "Telescoping Constructor" anti-pattern when instantiating complex immutable objects with multiple optional parameters:

```java
// ❌ TELESCOPING CONSTRUCTOR ANTI-PATTERN:
new User("Alice");
new User("Alice", 25);
new User("Alice", 25, "alice@work.com");
new User("Alice", 25, "alice@work.com", true, "ADMIN"); // Confusing boolean and null arguments!

// ✅ CLEAN IMMUTABLE BUILDER PATTERN:
UserProfile user = new UserProfile.Builder("Alice") // Mandatory field
    .age(25)                                        // Optional field
    .email("alice@work.com")                        // Optional field
    .role("ADMIN")                                  // Optional field
    .build();                                       // Returns immutable instance
```

## 🟡 Middle Level

### The Canonical Implementation Blueprint

```java
public final class UserProfile {
    // 1. All fields are private and final:
    private final String username; // Mandatory
    private final String email;    // Optional
    private final int age;         // Optional

    // 2. Private constructor: Enforces creation solely through the Builder:
    private UserProfile(Builder builder) {
        this.username = builder.username;
        this.email = builder.email;
        this.age = builder.age;
    }

    public String getUsername() { return username; }
    public String getEmail() { return email; }
    public int getAge() { return age; }

    // 3. Helper to create modified immutable clones:
    public Builder toBuilder() {
        return new Builder(this.username).email(this.email).age(this.age);
    }

    // 4. Static nested Builder:
    public static class Builder {
        private final String username; // Mandatory
        private String email;          // Default null
        private int age;               // Default 0

        public Builder(String username) {
            this.username = Objects.requireNonNull(username, "Username required");
        }

        public Builder email(String email) {
            this.email = email;
            return this; // Fluent method chaining
        }

        public Builder age(int age) {
            this.age = age;
            return this;
        }

        public UserProfile build() {
            // Cross-field validation before instantiation:
            if (email != null && !email.contains("@")) {
                throw new IllegalArgumentException("Invalid email format");
            }
            return new UserProfile(this);
        }
    }
}
```

## 🔴 Senior Level

### Lombok Integration: `@Builder`, `@Value`, and `@Singular`

In modern Spring Boot enterprise architectures, Lombok simplifies builders while maintaining strict immutability:

```java
@Value // Generates final class, private final fields, getters, equals/hashCode
@Builder(toBuilder = true)
public class Order {
    String orderId;
    String customerId;

    // @Singular automatically creates defensive unmodifiable List snapshots in build():
    @Singular
    List<String> items;
}
```

```java
// Fluent Usage:
Order order = Order.builder()
    .orderId("ORD-99")
    .customerId("CUST-1")
    .item("Laptop")
    .item("Mouse") // Adds to internal collection cleanly
    .build();

// Non-destructive partial update via toBuilder():
Order updatedOrder = order.toBuilder().customerId("CUST-2").build();
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Purpose:** Clean, fluent instantiation of complex immutable objects with optional fields.
- **Architecture:** `public final class`, `private final` fields, `private` constructor accepting the Builder, and a `public static class Builder`.
- **Validation:** Execute cross-field validation inside `build()` **before** allocating the immutable instance.
- **`toBuilder()`:** Allows creating updated copies of immutable objects easily (`order.toBuilder().age(30).build()`).
- **Lombok Tools:** Combine `@Value` with `@Builder` and `@Singular` to handle collections defensively.

**Common Follow-up Questions:**
- *"Why should the immutable class constructor be private?"* → To prevent external code from bypassing the builder and validation logic via direct constructor calls.
- *"What does Lombok `@Singular` do?"* → It allows adding collection elements one-by-one via fluent methods and wraps the collection in `Collections.unmodifiableList()` during `.build()`.
- *"When is a Builder over-engineering?"* → For small data classes with only 1–3 mandatory fields; use standard Java **`record`** types instead.

**Red Flags (DO NOT Say):**
- ❌ *"The Builder class must also be immutable."* (The Builder is a transient mutable helper used to assemble fields; only the resulting constructed object is immutable).
- ❌ *"Validation should be performed inside setter methods of the Builder."* (Cross-field validation must be performed in `build()` because setters can be called in any arbitrary order).
- ❌ *"Builders make objects slower in multithreaded systems."* (Builders are local to a single thread; the resulting published object is completely thread-safe).
