# How to Properly Work with Collections in Immutable Classes

---

## 🟢 Junior Level

Handling collections in immutable classes requires strict enforcement of the **3 Core Rules**:

```
  ┌───┬──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ # │ Golden Rule                  │ Implementation                                                                  │
  ├───┼──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Snapshot on Ingress**      │ Never store raw collection references; take an unmodifiable snapshot.           │
  │ 2 │ **Safe Egress**              │ Return direct references to unmodifiable lists, or return unmodifiable views.   │
  │ 3 │ **Zero Aliases**             │ Never expose raw internal arrays or mutable collections to external callers.    │
  └───┴──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

```java
// ✅ CORRECT IMMUTABLE PATTERN:
public final class StudentGroup {
    private final String groupName;
    private final List<String> studentNames;

    public StudentGroup(String groupName, List<String> studentNames) {
        this.groupName = groupName;
        // 1. Take an isolated, unmodifiable snapshot on ingress:
        this.studentNames = (studentNames == null) ? List.of() : List.copyOf(studentNames);
    }

    public String getGroupName() { return groupName; }

    // 2. Safe to return directly because studentNames is already unmodifiable:
    public List<String> getStudentNames() { return studentNames; }
}
```

## 🟡 Middle Level

### The Shallow Immutability Trap with Mutable Elements

`List.copyOf()` freezes the **collection container**, but does **not** protect mutable objects stored inside it:

```java
// ⚠️ SHALLOW IMMUTABILITY HAZARD:
public record Team(String name, List<MutableMember> members) {
    public Team {
        members = List.copyOf(members); // Container is frozen, but items are NOT!
    }
}

// 💥 EXPLOIT: Mutating elements via getter:
team.members().get(0).setName("Hacked"); // Allowed! Mutates member internal state!
```

```java
// 🛡️ DEEP COPY SOLUTION (Copy constructors):
public record DeepTeam(String name, List<MutableMember> members) {
    public DeepTeam {
        members = (members == null) ? List.of() : members.stream()
            .map(MutableMember::new) // Clones each element via copy constructor
            .toList();
    }
}
```

## 🔴 Senior Level

### Architectural Comparison: Live Wrapper vs. Immutable Snapshot

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Feature                      │ `Collections.unmodifiableList()` │ `List.copyOf()` (Java 10+)                       │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Nature**                   │ **Decorator Wrapper (View)**     │ **True Immutable Snapshot**                      │
  │ **Source List Modification** │ ⚠️ Reflected in view             │ 🛡️ Completely isolated from changes             │
  │ **Creation Overhead**        │ **$O(1)$**                       │ **$O(N)$** (Short-circuits to $O(1)$ if immut.)  │
  │ **Null Element Policy**      │ Permitted                        │ **Strictly Banned (NPE)**                        │
  │ **Concurrency Risk**         │ `ConcurrentModificationException`│ Lock-free thread-safe reading                    │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Highload Architecture: Persistent Collections (Vavr)

When dealing with large collections that undergo frequent single-item modifications, copying $N$ items via `List.copyOf()` creates high GC churn. Use **Vavr Persistent Collections** with **Structural Sharing**:

```java
// Updates take O(1) for prepending and O(log32 N) for Maps via HAMT:
io.vavr.collection.List<String> listV1 = io.vavr.collection.List.of("A", "B");
io.vavr.collection.List<String> listV2 = listV1.prepend("Z"); // Reuses tail!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **3 Rules:** Snapshot in constructor, safe access in getter, zero raw alias retention.
- **Java 10+ Standard:** Use `List.copyOf(input)`, `Set.copyOf(input)`, `Map.copyOf(input)`.
- **Shallow by Default:** `List.copyOf()` only protects collection structure; contained mutable elements must be cloned individually.
- **Records Pattern:** Always add defensive copies inside the compact constructor (`public RecordName { items = List.copyOf(items); }`).
- **Null Safety:** `List.copyOf()` rejects `null` values; if `null`s are permitted, use `Collections.unmodifiableList(new ArrayList<>(input))`.

**Common Follow-up Questions:**
- *"Why is `List.copyOf()` safe to return directly from a getter?"* → Because `List.copyOf()` produces an immutable collection; callers attempting to call `.add()` or `.clear()` receive an `UnsupportedOperationException`.
- *"When should you choose `unmodifiableList` over `List.copyOf`?"* → In performance-critical getters of private classes where internal state is never mutated, saving the $O(N)$ allocation overhead of `List.copyOf()`.
- *"How does Vavr solve collection copying overhead?"* → It uses Persistent Data Structures with Structural Sharing, executing updates in $O(1)$ or $O(\log N)$ time by reusing unchanged subtrees.

**Red Flags (DO NOT Say):**
- ❌ *"`List.copyOf()` makes all objects inside the list immutable."* (It only makes the container unmodifiable; mutable elements can still be altered).
- ❌ *"`Collections.unmodifiableList(list)` in a constructor prevents callers from modifying internal state."* (The caller retains the original list reference and can mutate it).
- ❌ *"Records automatically copy collection arguments without needing a compact constructor."* (Records only store references; you must explicitly invoke `List.copyOf()`).
