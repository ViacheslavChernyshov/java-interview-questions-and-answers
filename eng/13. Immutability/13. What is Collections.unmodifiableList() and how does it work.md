# What is Collections.unmodifiableList() and How Does It Work?

---

## 🟢 Junior Level

`Collections.unmodifiableList()` is a utility method from `java.util.Collections` that wraps an existing list in a **read-only Decorator**:

```java
List<String> original = new ArrayList<>();
original.add("Java");

List<String> readOnly = Collections.unmodifiableList(original);

System.out.println(readOnly.get(0)); // Prints "Java"

readOnly.add("Python"); // 💥 Throws UnsupportedOperationException!
```

```
  Key Trait:
  • `Collections.unmodifiableList()` does NOT copy the underlying data!
  • It is merely a "Live View" wrapper over the original collection.
```

---

## 🟡 Middle Level

### Internal Architecture: The Decorator Pattern

Under the hood, `Collections.unmodifiableList()` instantiates a private nested class `UnmodifiableList<E>`:

```java
// Simplified JDK implementation:
static class UnmodifiableList<E> extends UnmodifiableCollection<E> implements List<E> {
    final List<? extends E> list; // Retains reference to original list

    UnmodifiableList(List<? extends E> list) {
        super(list);
        this.list = list;
    }

    public E get(int index) { return list.get(index); } // Delegated read

    public boolean add(E e) { 
        throw new UnsupportedOperationException();      // Mutating call blocked!
    }
    public E remove(int index) { 
        throw new UnsupportedOperationException(); 
    }
}
```

### The "Live View" Mutation Hazard

Because the wrapper delegates reads directly to the underlying list, mutations made to the underlying list are **immediately reflected in the unmodifiable wrapper**:

```java
List<String> mutable = new ArrayList<>(List.of("Alice"));
List<String> unmodifiable = Collections.unmodifiableList(mutable);

mutable.add("Bob"); // Mutates source list

System.out.println(unmodifiable); // Prints [Alice, Bob]! (Wrapper was NOT immune to change!)
```

---

## 🔴 Senior Level

### Concurrency Hazards: The Illusion of Thread Safety

Senior engineers know that wrapping a list in `Collections.unmodifiableList()` **does NOT make it thread-safe**:

```
  Multi-Threaded Failure Scenario:
  1. Thread A iterates through `unmodifiableList` using an enhanced for-loop or Iterator.
  2. Thread B executes `mutableList.add("New Item")` on the underlying list.
  3. 💥 Thread A crashes with `ConcurrentModificationException`!

  Senior Fix:
  Use `List.copyOf(mutable)` (Java 10+) to take a truly isolated, unmodifiable snapshot 
  that has zero memory connection to the source collection.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Design Pattern:** Implements the **Decorator Pattern**, delegating read calls and throwing `UnsupportedOperationException` on write calls.
- **Nature:** It is a **Live View**, not an independent snapshot; changes to the backing list are visible through the wrapper.
- **Time/Space Complexity:** Construction is $O(1)$ time and allocates only one small wrapper object.
- **Concurrency Danger:** Iterating through the wrapper while another thread mutates the backing list throws `ConcurrentModificationException`.
- **Modern Alternative:** Use `List.copyOf()` (Java 10+) for true data isolation.

**Common Follow-up Questions:**
- *"Is `Collections.unmodifiableList()` thread-safe?"* → No; if the underlying list is modified by another thread, iterating through the unmodifiable wrapper will throw `ConcurrentModificationException`.
- *"How does `Collections.unmodifiableList()` compare to `List.copyOf()`?"* → `unmodifiableList()` is a live view ($O(1)$) that reflects changes; `List.copyOf()` is an independent snapshot ($O(N)$) immune to subsequent mutations.
- *"Can you modify elements inside an `unmodifiableList`?"* → If elements are mutable objects, you can call setter methods on those elements (`list.get(0).setName(...)`).

**Red Flags (DO NOT Say):**
- ❌ *"`Collections.unmodifiableList()` creates a deep copy of the collection."* (It is a shallow wrapper around the existing list).
- ❌ *"Wrapping a list in `unmodifiableList` protects it from being modified anywhere in the application."* (Anyone holding a reference to the original mutable list can still modify it).
- ❌ *"`unmodifiableList` is safe for concurrent reads and writes across threads."* (Concurrent writes to the backing list cause `ConcurrentModificationException` in reading threads).
