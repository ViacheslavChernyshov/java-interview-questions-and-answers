# Why Should an Immutable Class Be final?

---

## 🟢 Junior Level

An immutable class must be declared with the **`final`** modifier to **strictly prohibit inheritance**:

```java
// ❌ VULNERABLE: Omitting `final` invites subclassing exploits:
public class GeoCoordinate {
    private final double latitude;
    private final double longitude;

    public GeoCoordinate(double lat, double lon) {
        this.latitude = lat;
        this.longitude = lon;
    }

    public double getLatitude() { return latitude; }
    public double getLongitude() { return longitude; }
}

// 💥 Subclass breaks immutability by overriding getters:
public class MutableGeoCoordinate extends GeoCoordinate {
    private double dynamicLat;

    public MutableGeoCoordinate(double lat, double lon) { super(lat, lon); }
    public void setLatitude(double lat) { this.dynamicLat = lat; }

    @Override
    public double getLatitude() { return dynamicLat; } // 💥 Dynamic mutation!
}
```

```
  │ Vulnerability                    │ Production Failure Mechanism                                                    │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **TOCTOU Security Bypass**       │ Security validator checks `GeoCoordinate`, but subclass mutates values before   │
  │                                  │ persisting to database.                                                         │
  │ **`HashMap` Bucket Corruption**  │ Subclass computes `hashCode()` using mutable fields; entries become unlocatable.│
  │ **Thread Safety Invalidation**   │ Parent fields have JMM `final` freeze guarantees, but subclass fields do not,   │

```

### JDK Precedents & Testing with Modern Mockito

- **JDK Foundations:** All core immutable JDK classes are declared `final` (`String`, `Integer`, `Double`, `BigDecimal`, `LocalDate`, `Instant`, and all `record` types).
- **Mocking `final` Classes:** In older Mockito 2/3, `final` classes could not be mocked. In **Mockito 5+** (Spring Boot 3), mocking `final` classes and methods works out-of-the-box via the `mock-maker-inline` ByteBuddy agent.

## 🔴 Senior Level

### HotSpot JIT Optimizations: Devirtualization & Monomorphic Inlining

Declaring an immutable class `final` provides critical optimization hints to the HotSpot C2 JIT compiler:

```
  1. Class Hierarchy Analysis (CHA) & Devirtualization:
     • The JVM analyzes the class hierarchy and proves that no subclasses exist.
     • Bytecode `invokevirtual` instructions on getters are converted directly 
       into static native CPU jumps, completely bypassing `vtable` lookups.

  2. Monomorphic Inlining:
     • Small getter methods (`getLatitude()`) are inlined directly into caller assembly, 
       reducing method call overhead to 0 clock cycles (direct register reads).

  3. Escape Analysis & Scalar Replacement:
     • C2 easily proves that the immutable object does not escape the local method scope, 
       decomposing its fields into CPU registers and eliminating Heap allocation!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Purpose:** Prohibits subclassing to prevent child classes from injecting mutable fields or overriding getters.
- **LSP Preservation:** Ensures all instances satisfy the immutable Liskov Substitution Principle invariant.
- **JIT Wins:** Enables Class Hierarchy Analysis (CHA), devirtualization of `invokevirtual`, monomorphic inlining, and scalar replacement.
- **JDK Consistency:** `String`, wrappers, `java.time.*`, `BigDecimal`, and Java `record`s are all strictly `final`.
- **Alternative:** Private constructors with `public static` factory methods (`Class.of(...)`).

**Common Follow-up Questions:**
- *"Is making all methods `final` equivalent to making the class `final`?"* → Making all methods `final` prevents method overriding, but a subclass can still introduce new mutable methods, causing confusion and design violations; marking the class `final` is cleaner and more explicit.
- *"How does HotSpot optimize calls to methods in `final` classes?"* → It bypasses virtual method table (`vtable`) pointer dispatch and inlines the method body directly into the calling machine code.
- *"Can you mock a `final` class in Spring Boot 3 unit tests?"* → Yes; Mockito 5+ uses the inline mock maker by default to safely mock `final` classes.

**Red Flags (DO NOT Say):**
- ❌ *"Making a class `final` is optional as long as all its fields are marked `final`."* (Subclasses can still override getters or add mutable fields).
- ❌ *"The `final` keyword degrades performance because of additional JVM checks."* (It actually accelerates runtime execution via JIT devirtualization and inlining).
- ❌ *"You should avoid `final` classes because they break unit testing frameworks."* (Modern testing libraries like Mockito 5+ mock `final` classes seamlessly).
