# What are design patterns?

---

## 🟢 Junior Level

**Design patterns** are battle-tested, standardized architectural templates that solve recurring software engineering problems in object-oriented programming.

**Why they matter:** You do not need to invent software architecture from scratch. Applying established patterns saves hours of debugging, avoids known design flaws, and establishes a **shared vocabulary** across engineering teams (e.g., *"Let's use a Strategy pattern here"* instantly conveys the entire structural intent).

**Simple analogy:** When constructing a house, architects do not reinvent how doors, foundations, or roof trusses function; they use proven blueprints with standardized building codes. Design patterns are architectural blueprints for your codebase.

**Minimal Example (Classic Singleton):**
```java
// Guarantees only one instance exists across the application
public class AppLogger {
    private static final AppLogger INSTANCE = new AppLogger();

    // Private constructor prevents direct instantiation via 'new'
    private AppLogger() {}

    public static AppLogger getInstance() {
        return INSTANCE;
    }

    public void log(String message) {
        System.out.println("[LOG] " + message);
    }
}

// Usage:
AppLogger.getInstance().log("System initialized successfully.");
```

**When to use patterns:**
- When encountering standard engineering problems (object creation complexity, dynamic algorithm switching, decoupled event listening).
- When a codebase begins suffering from code smells (deep conditional nesting, tight coupling, code duplication).

## 🟡 Middle Level

### Architectural Hierarchy: Idioms vs. Patterns vs. Enterprise Architecture

| Level | Scope & Abstraction | Typical Examples |
|---|---|---|
| **Language Idioms** | Low-level, language-specific syntax techniques | `try-with-resources`, `Optional`, Stream pipelines, Record constructors |
| **GoF Design Patterns** | Mid-level class and object interactions | Strategy, Decorator, Observer, Abstract Factory, Proxy |
| **Enterprise Patterns** | Domain and data access architecture | Repository, Data Mapper, Unit of Work, Service Layer |
| **Distributed / Cloud Patterns** | Microservice resilience and data consistency | Circuit Breaker, Saga, CQRS, Outbox Pattern, Sidecar |

> **GoF Context:** Established in 1994 by the *"Gang of Four"* (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides) in their seminal book *Design Patterns: Elements of Reusable Object-Oriented Software*.

### Evolution in Modern Java (Java 8–21+)

Modern Java features have eliminated the boilerplate of many classic Gang of Four patterns:

```java
// ❌ CLASSIC GoF STRATEGY (Requires multiple boilerplate interface & class declarations)
public interface DiscountStrategy {
    BigDecimal applyDiscount(BigDecimal total);
}
public class BlackFridayDiscount implements DiscountStrategy { ... }
public class VipMemberDiscount implements DiscountStrategy { ... }

// ✅ MODERN JAVA (Functional Interfaces & Lambdas)
public class OrderService {
    public BigDecimal calculateTotal(BigDecimal basePrice, UnaryOperator<BigDecimal> discountRule) {
        return discountRule.apply(basePrice);
    }
}

// Usage with zero class boilerplate:
orderService.calculateTotal(price, p -> p.multiply(BigDecimal.valueOf(0.80)));
```

### Pitfalls & Pattern Smells

1. **Golden Hammer (Maslow's Hammer):** Forcing a complex pattern where a simple 3-line `if-else` or `switch` statement is cleaner and faster.
2. **Overengineering & Indirection:** Creating 15 interfaces, factories, and adapters for simple CRUD operations, making stack traces impossible to debug.
3. **Cargo Cult Programming:** Blindly copying pattern templates (like implementing `Cloneable` or manual singletons) without understanding modern runtime consequences.

## 🔴 Senior Level

### Patterns as Architectural Contracts & SOLID Foundations

At the senior level, design patterns are not merely code templates; they are explicit contracts enforcing the **SOLID** principles:
- **Open/Closed Principle (OCP):** Strategy, Decorator, and Template Method allow extending behavior without modifying existing tested classes.
- **Single Responsibility Principle (SRP):** Builder and Factory separate object construction logic from operational domain logic.
- **Dependency Inversion Principle (DIP):** Abstract Factory and Bridge decouple high-level modules from low-level concrete implementations.

### JIT Compiler Inlining: Monomorphic vs. Megamorphic Call Sites

Applying dynamic polymorphism (e.g. Strategy, State) affects the HotSpot JVM's JIT compiler performance in critical execution paths:

```java
public interface PaymentProcessor {
    void process(Order order);
}

// Runtime Execution Call Sites:
// 1. Monomorphic (1 concrete implementation loaded at runtime):
//    The JIT compiler performs Direct Method Inlining (0 vtable lookup overhead, fastest).
//
// 2. Bimorphic (Exactly 2 concrete implementations):
//    The JIT uses an inline cache with a conditional branch (very fast).
//
// 3. Megamorphic (> 2 concrete implementations active in the same call site):
//    The JIT aborts direct inlining and falls back to indirect vtable lookup dispatch.
```

*Senior Optimization:* In ultra-low-latency hot paths, if you have a known closed set of algorithms, prefer an **`enum` with abstract methods** or **Java 17+ Sealed Interfaces with pattern matching** over open dynamic polymorphs to aid compiler branch prediction and inlining.

```java
public sealed interface OrderState permits PendingState, PaidState, ShippedState {
    OrderState next();
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Standardized, reusable solutions to recurring object-oriented design challenges.
- **3 GoF Categories:**
  - **Creational:** Object instantiation mechanisms (Singleton, Factory, Builder, Prototype).
  - **Structural:** Composition of classes and objects (Adapter, Decorator, Proxy, Composite, Facade).
  - **Behavioral:** Communication and delegation of algorithms (Strategy, Observer, State, Command).
- **Modern Java Evolution:** Functional interfaces (`Function`, `Predicate`, `Consumer`) replace Strategy/Command classes; Records replace manual DTO Prototypes; Spring DI replaces manual Singletons.
- **Principle of Sufficiency:** Never add a pattern unless it directly solves an existing or immediate scaling problem.

**Common Follow-up Questions:**
- *"When should you NOT use a design pattern?"* → In simple CRUD services, throwaway prototypes, or where a standard `switch` statement provides sufficient clarity without class explosion.
- *"How does the Strategy pattern impact JVM performance?"* → Monomorphic call sites are inlined directly by JIT; megamorphic call sites (>2 strategies at the same call site) force indirect vtable lookups.
- *"What is the difference between a design pattern and an architectural pattern?"* → Design patterns govern class and object relationships inside a single application; architectural patterns (MVC, CQRS, Saga) govern entire subsystems and multi-service systems.

**Red Flags (DO NOT Say):**
- ❌ *"I try to use design patterns everywhere in my code to make it look professional."* (Indicates severe overengineering and Golden Hammer anti-pattern).
- ❌ *"Design patterns always make an application run faster."* (They add layers of indirection and memory allocations; their goal is maintainability, not raw CPU speed).
- ❌ *"Singleton is always the best way to share global state in Java."* (Manual singletons introduce hidden global state, break unit testing mocks, and create concurrency hazards).
