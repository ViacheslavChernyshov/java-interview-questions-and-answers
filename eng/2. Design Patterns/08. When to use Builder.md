# When to use Builder?

---

## 🟢 Junior Level

The **Builder pattern** is a Creational design pattern that allows the **step-by-step construction of complex objects**, separating the construction logic from the object's final representation.

**The Problem:** When an entity contains multiple attributes (some mandatory, many optional), class constructors rapidly degenerate into the **Telescoping Constructor anti-pattern**:

```java
// ❌ TELESCOPING CONSTRUCTORS: Unreadable and error-prone!
User user = new User("Alice", "Smith", "alice@example.com", 
                     "+18005550199", "Seattle", 28, true, false);
```

**The Solution (Fluent Builder):**
```java
// ✅ CLEAN, SELF-DOCUMENTING, IMMUTABLE
User user = User.builder()
    .firstName("Alice")
    .lastName("Smith")
    .email("alice@example.com")
    .city("Seattle")
    .age(28)
    .active(true)
    .build();
```

**When to use Builder:**
- A class constructor accepts **4 or more parameters**.
- Several parameters are **optional** or have sensible defaults.
- You need the constructed object to be **strictly immutable (`final` fields)** without exposing public setters.

## 🟡 Middle Level

### Problems Solved by the Builder Pattern

#### 1. Eliminating Telescoping Constructors
Without Builder, supporting different combinations of optional parameters requires writing $2^N$ constructor overloads. Builder handles all parameter permutations with a single fluent interface.

#### 2. Eliminating the JavaBeans Anti-Pattern
```java
// ❌ JAVABEANS HAZARD: Object exists in an invalid, half-initialized state!
User user = new User();
user.setFirstName("Alice");
user.setEmail("alice@example.com");
// What if another thread reads 'user' right here before age/city are set?
user.setAge(28);
```
**Builder guarantees atomicity:** The domain object is instantiated only when `build()` is invoked, ensuring that half-constructed or invalid objects are never exposed.

### Standard Manual Implementation

```java
public final class HttpRequest {
    private final String url;          // Mandatory
    private final String method;       // Mandatory
    private final Map<String, String> headers; // Optional
    private final byte[] body;         // Optional

    private HttpRequest(Builder builder) {
        this.url = builder.url;
        this.method = builder.method;
        this.headers = Map.copyOf(builder.headers);
        this.body = builder.body;
    }

    public static Builder builder() { return new Builder(); }

    public static final class Builder {
        private String url;
        private String method = "GET"; // Default value
        private Map<String, String> headers = new HashMap<>();
        private byte[] body;

        public Builder url(String url) { this.url = url; return this; }
        public Builder method(String method) { this.method = method; return this; }
        public Builder header(String key, String value) { 
            this.headers.put(key, value); 
            return this; 
        }
        public Builder body(byte[] body) { this.body = body; return this; }

        public HttpRequest build() {
            // Validation at construction boundary
            if (url == null || url.isBlank()) {
                throw new IllegalStateException("URL is mandatory");
            }
            return new HttpRequest(this);
        }
    }
}
```

## 🔴 Senior Level

### Compile-Time Enforcement: The Step Builder (Staged Builder)

Standard Builders validate mandatory parameters at runtime inside `.build()`. A **Step Builder** forces callers to supply all mandatory fields in a strict sequence **at compile time**:

```java
public class Account {
    private final String id;
    private final String owner;
    private final BigDecimal balance;

    private Account(String id, String owner, BigDecimal balance) {
        this.id = id;
        this.owner = owner;
        this.balance = balance;
    }

    // Step 1: Force ID
    public interface IdStep {
        OwnerStep id(String id);
    }
    // Step 2: Force Owner
    public interface OwnerStep {
        BuildStep owner(String owner);
    }
    // Step 3: Optional fields + Final Build
    public interface BuildStep {
        BuildStep balance(BigDecimal balance);
        Account build();
    }

    public static IdStep builder() {
        return new AccountBuilder();
    }

    private static class AccountBuilder implements IdStep, OwnerStep, BuildStep {
        private String id;
        private String owner;
        private BigDecimal balance = BigDecimal.ZERO;

        public OwnerStep id(String id) { this.id = id; return this; }
        public BuildStep owner(String owner) { this.owner = owner; return this; }
        public BuildStep balance(BigDecimal balance) { this.balance = balance; return this; }
        public Account build() { return new Account(id, owner, balance); }
    }
}

// Usage (Compiler guarantees no step is skipped):
Account account = Account.builder()
    .id("ACC-101")    // Compile error if skipped!
    .owner("Alice")   // Compile error if skipped!
    .balance(BigDecimal.valueOf(500))
    .build();
```

### Functional Immutability: The Copy Builder (`toBuilder`)

In event-driven architectures, immutable domain state is updated by generating new copies with modified fields (the Wither pattern):

```java
@Builder(toBuilder = true)
public record Order(String id, BigDecimal amount, String status) {}

// Updating status without mutating original instance:
Order activeOrder = new Order("ORD-1", BigDecimal.valueOf(100), "PENDING");
Order paidOrder = activeOrder.toBuilder()
    .status("PAID")
    .build();
```

### Inheritance with Lombok `@SuperBuilder`

Standard `@Builder` fails when extending classes because the parent builder cannot return the child builder type. Lombok provides `@SuperBuilder` using recursive generic type bounds:

```java
@SuperBuilder
public abstract class BaseEntity {
    private final Instant createdAt;
}

@SuperBuilder
public class Product extends BaseEntity {
    private final String sku;
}

// Fluent assembly of both parent and child fields:
Product p = Product.builder()
    .createdAt(Instant.now())
    .sku("SKU-999")
    .build();
```

### Hot-Path Performance & GC Allocation Overhead

> [!WARNING]
> In ultra-high-throughput hot paths (e.g. allocating 1,000,000 DTOs per second in a financial matching engine), each `Builder` invocation allocates a temporary heap object, creating significant **GC allocation pressure**. In critical hot paths, favor direct static factory methods or standard constructors.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Purpose:** Replaces telescoping constructors and mutable JavaBeans with a fluent, immutable object assembly pipeline.
- **Atomicity:** Objects are instantiated only upon calling `build()`, preventing invalid intermediate states.
- **Step Builder:** Enforces mandatory parameters at compile time using chained interface types.
- **Copy Builder (`toBuilder`):** Generates modified copies of immutable objects without mutating existing state.
- **Performance Trade-Off:** Introduces short-lived heap allocations; avoid builders in extreme high-frequency hot-path loops.

**Common Follow-up Questions:**
- *"When should you NOT use a Builder?"* → For small value objects with 1–2 fields (e.g. `Point(x, y)`), or in high-frequency hot-paths where temporary builder heap allocation triggers GC pressure.
- *"How does Lombok `@SuperBuilder` solve the inheritance problem?"* → It generates an abstract generic builder class (`B extends BaseEntityBuilder<C, B>`) using self-referential type bounds, allowing subclasses to inherit and return the correct builder type.
- *"Why are instance fields in the target class declared as `final` when using Builder?"* → To guarantee thread safety and strict immutability once `build()` completes.

**Red Flags (DO NOT Say):**
- ❌ *"I add getters and setters to classes that use the Builder pattern."* (Setters defeat the core purpose of Builder, which is immutability and thread safety).
- ❌ *"Builder should be used on every single class in the application."* (Overengineering for simple 2-attribute classes).
- ❌ *"Step Builder is just a regular Builder with more methods."* (Step Builder uses interface typing to enforce compile-time mandatory parameter ordering).
