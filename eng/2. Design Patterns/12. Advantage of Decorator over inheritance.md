# Advantage of Decorator over inheritance

---

## 🟢 Junior Level

The **Decorator pattern** is a Structural design pattern that allows you to **attach new behaviors and responsibilities to objects dynamically at runtime** by placing them inside special wrapper objects.

**The Inheritance Problem:** Subclassing is static. If you need to support multiple optional features, inheritance causes a **combinatorial explosion of subclasses**:

```java
// ❌ INHERITANCE EXPLOSION: 2^N subclasses required for N features!
class Coffee {}
class MilkCoffee extends Coffee {}
class SugarCoffee extends Coffee {}
class MilkSugarCoffee extends Coffee {}
class WhipMilkSugarCoffee extends Coffee {} // Becomes unmaintainable!
```

**The Solution (Decorator):**
```java
// Common Component Interface
public interface Coffee {
    BigDecimal getCost();
    String getDescription();
}

// Base Concrete Component
public class SimpleCoffee implements Coffee {
    public BigDecimal getCost() { return BigDecimal.valueOf(2.00); }
    public String getDescription() { return "Simple Coffee"; }
}

// Abstract Base Decorator
public abstract class CoffeeDecorator implements Coffee {
    protected final Coffee decoratedCoffee;
    public CoffeeDecorator(Coffee coffee) { this.decoratedCoffee = coffee; }
    public BigDecimal getCost() { return decoratedCoffee.getCost(); }
    public String getDescription() { return decoratedCoffee.getDescription(); }
}

// Concrete Decorator A
public class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) { super(coffee); }
    @Override
    public BigDecimal getCost() { return super.getCost().add(BigDecimal.valueOf(0.50)); }
    @Override
    public String getDescription() { return super.getDescription() + ", Milk"; }
}

// Concrete Decorator B
public class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee coffee) { super(coffee); }
    @Override
    public BigDecimal getCost() { return super.getCost().add(BigDecimal.valueOf(0.25)); }
    @Override
    public String getDescription() { return super.getDescription() + ", Sugar"; }
}

// Usage: Arbitrary dynamic nesting at runtime!
Coffee myOrder = new MilkDecorator(new SugarDecorator(new SimpleCoffee()));
System.out.println(myOrder.getDescription() + " -> $" + myOrder.getCost());
// Output: Simple Coffee, Sugar, Milk -> $2.75
```

## 🟡 Middle Level

### Architectural Comparison: Inheritance vs. Decorator

| Dimension | Class Inheritance | Decorator Pattern |
|---|---|---|
| **Binding Time** | Compile-Time (Static) | Runtime (Dynamic) |
| **Number of Classes** | $2^N$ combinatorial subclasses | $N$ linear decorator classes |
| **Coupling** | High (tightly coupled to parent implementation) | Low (loosely coupled via interface) |
| **SOLID Compliance**| Violates Single Responsibility (SRP) | Adheres strictly to SRP and OCP |

### Canonical Example: The `java.io` Stream Library

The standard Java I/O library is the quintessential real-world demonstration of the Decorator pattern:

```java
InputStream inputStream = 
    new BufferedInputStream(            // Layer 4: Adds 8KB memory buffering
        new CipherInputStream(          // Layer 3: Adds AES decryption
            new GZIPInputStream(        // Layer 2: Adds GZIP decompression
                new FileInputStream(file) // Layer 1: Reads raw physical disk bytes
            ), cipher
        )
    );
```
Each wrapper implements `InputStream` while enhancing the underlying stream's read behavior.

## 🔴 Senior Level

### Structural Triad: Decorator vs. Adapter vs. Proxy

Candidates frequently confuse these three Structural Gang of Four patterns:

```
  ┌───────────────┐   ┌───────────────────────────┐   ┌───────────────────────────────┐
  │    Pattern    │   │      Interface Status     │   │         Core Intent           │
  ├───────────────┤   ├───────────────────────────┤   ├───────────────────────────────┤
  │   Decorator   │   │  Preserves same interface │   │ Adds new responsibilities     │
  │    Adapter    │   │  Converts to NEW interface│   │ Makes incompatible APIs work  │
  │     Proxy     │   │  Preserves same interface │   │ Controls / intercepts access  │
  └───────────────┘   └───────────────────────────┘   └───────────────────────────────┘
```

### Spring Framework Interceptor Chains (Decorator Architecture)

In Spring Web development, request and response processing chains function on the Decorator principle:

```java
// Spring REST Client Interceptor (Decorator on ClientHttpRequestExecution)
@Component
public class BearerTokenAuthInterceptor implements ClientHttpRequestInterceptor {
    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body, 
                                        ClientHttpRequestExecution execution) throws IOException {
        request.getHeaders().add("Authorization", "Bearer " + SecurityContext.getToken());
        // Delegates to next decorator in the execution chain:
        return execution.execute(request, body);
    }
}
```

### Performance & Debugging Trade-offs

1. **Stack Trace Obfuscation:** Deeply nested decorator chains (10+ layers) produce long stack traces that complicate debugging.
2. **Object Identity Issues:** A decorated object does not have the same reference identity (`this != decoratedObject`), which can break collections relying on reference equality (`==`).
3. **Transient Memory Allocations:** Instantiating 8 wrapper objects per request incurs small heap allocation overhead compared to a single monolithic class.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Principle:** **Composition over Inheritance** — adds dynamic capabilities at runtime instead of static subclassing at compile time.
- **Class Explosion:** Solves the $2^N$ combinatorial explosion problem, reducing required classes to $N$.
- **Java I/O:** `BufferedInputStream` wrapping `FileInputStream` is the classic JDK implementation.
- **Structural Triad Distinction:**
  - **Decorator:** Same interface, adds behavior.
  - **Proxy:** Same interface, controls/guards access.
  - **Adapter:** Changes interface to bridge incompatible APIs.
- **Spring Examples:** `ClientHttpRequestInterceptor`, `HandlerInterceptor`, `ResponseBodyAdvice`.

**Common Follow-up Questions:**
- *"Why not use inheritance instead of Decorator?"* → Inheritance is fixed at compile time, applies to all instances of the subclass, and causes exponential class explosion when features can be combined arbitrarily.
- *"How does Decorator adhere to the Open/Closed Principle?"* → You can introduce new decorators without altering the base component or existing decorator classes.
- *"What is a drawback of using deeply nested decorators?"* → Debugging stack traces is harder and reference equality (`==`) checks fail between the wrapper and the inner component.

**Red Flags (DO NOT Say):**
- ❌ *"Decorator changes the interface of the wrapped object."* (That is the Adapter pattern; Decorators must implement the exact same interface).
- ❌ *"Decorator and Proxy are the exact same pattern with different names."* (Proxy controls access without adding business features; Decorator adds new business functionality).
- ❌ *"Inheritance is always faster and better than composition."* (Inheritance creates brittle, tightly-coupled hierarchies that break under evolving requirements).
