# What is the Prototype pattern?

---

## 🟢 Junior Level

The **Prototype pattern** is a Creational design pattern that allows you to **produce new objects by copying an existing instance (the prototype)** without making your code dependent on their concrete classes or repeating expensive initialization workflows.

**Why it is needed:** When direct instantiation via `new` is computationally expensive (e.g. requires loading large database configurations, parsing remote schemas, or complex mathematical transforms), cloning a pre-configured template is significantly faster.

**Simple analogy:** A photocopier. Instead of typing a 10-page document by hand every time, you copy an existing template and modify only the recipient name.

**Modern Java Implementation (Copy Constructor):**
```java
public class UserPermissions {
    private final String role;
    private final List<String> permissions;

    public UserPermissions(String role, List<String> permissions) {
        this.role = role;
        this.permissions = new ArrayList<>(permissions);
    }

    // Copy Constructor (The Prototype Mechanism)
    public UserPermissions(UserPermissions source) {
        this.role = source.role;
        // Deep copy of the mutable collection!
        this.permissions = new ArrayList<>(source.permissions);
    }

    public void addPermission(String perm) {
        this.permissions.add(perm);
    }
}

// Usage:
UserPermissions adminTemplate = new UserPermissions("ADMIN", List.of("READ", "WRITE"));
UserPermissions customUser = new UserPermissions(adminTemplate); // Instant clone!
customUser.addPermission("DELETE");
```

## 🟡 Middle Level

### Why `java.lang.Cloneable` and `Object.clone()` are Broken

In Java, the built-in `Cloneable` mechanism is widely acknowledged as a **flawed language design** (as documented by Joshua Bloch in *Effective Java*):

1. **Marker Interface Flaw:** `Cloneable` does not declare a public `clone()` method. The method is defined as `protected native Object clone()` on `java.lang.Object`.
2. **Bypasses Class Constructors:** `Object.clone()` creates an object by copying raw memory directly without invoking constructors, bypassing class invariant validation.
3. **Incompatible with `final` Fields:** You cannot assign values to `final` fields inside `clone()`, making deep cloning impossible for immutable objects.
4. **Shallow Copy by Default:** Copies only primitive values and object references. Both original and clone share mutable internal references!
5. **Checked Exception:** Forces callers to catch `CloneNotSupportedException`.

### The Preferred Approach: Copy Constructors & Static Copy Factories

```java
public final class OrderItem {
    private final String sku;
    private final int quantity;
    private final BigDecimal price;

    // Copy Constructor
    public OrderItem(OrderItem other) {
        this(other.sku, other.quantity, other.price);
    }

    // Static Copy Factory
    public static OrderItem copyOf(OrderItem other) {
        return new OrderItem(other);
    }
}
```

### Deep vs. Shallow Cloning

```
         Shallow Copy                                 Deep Copy
 ┌──────────┐     ┌──────────┐              ┌──────────┐     ┌──────────┐
 │ Original │     │  Clone   │              │ Original │     │  Clone   │
 └────┬─────┘     └────┬─────┘              └────┬─────┘     └────┬─────┘
      │                │                         │                │
      └───────┬────────┘                         ▼                ▼
              ▼                            ┌───────────┐    ┌───────────┐
      ┌───────────────┐                    │ Addresses │    │ Addresses │
      │ Shared List   │                    │ (List A)  │    │ (List B)  │
      │ (Mutations    │                    └───────────┘    └───────────┘
      │ affect both!) │
      └───────────────┘
```

## 🔴 Senior Level

### Spring Framework Prototype Scope (`@Scope("prototype")`)

In Spring, beans with `prototype` scope return a **brand new instance on every request** from the container:

```java
@Component
@Scope("prototype")
public class ReportGenerator {
    private final UUID generationId = UUID.randomUUID();
}
```

#### ⚠️ The Prototype-in-Singleton Injection Trap
If you inject a `prototype` bean into a standard `singleton` bean using `@Autowired`, Spring initializes the prototype **only once** during application startup!

```java
@Service // Singleton Scope
public class InvoiceService {
    @Autowired
    private ReportGenerator generator; // ❌ BUG: Only one instance ever injected!
}
```

#### ✅ Proper Solutions for Dynamic Prototype Resolution

```java
// Option 1: ObjectProvider (Cleanest in Modern Spring)
@Service
public class InvoiceService {
    private final ObjectProvider<ReportGenerator> generatorProvider;

    public InvoiceService(ObjectProvider<ReportGenerator> generatorProvider) {
        this.generatorProvider = generatorProvider;
    }

    public void processInvoice() {
        ReportGenerator freshInstance = generatorProvider.getObject(); // Fresh instance!
    }
}

// Option 2: @Lookup Method Injection
@Service
public abstract class InvoiceService {
    public void processInvoice() {
        ReportGenerator freshInstance = getReportGenerator(); // CGLIB generates fresh bean!
    }

    @Lookup
    protected abstract ReportGenerator getReportGenerator();
}
```

### Spring Prototype Lifecycle Gotcha: `@PreDestroy` is Ignored!

> [!WARNING]
> Spring manages the complete creation lifecycle of prototype beans (calling `@PostConstruct`), but **does NOT manage their destruction lifecycle**. Spring **never executes `@PreDestroy`** on prototype beans! The client code must manually close any open connections or files.

### Deep Cloning Complex Object Graphs (JSON vs Serialization)

For massive arbitrary object graphs where manual copy constructors would be too complex:

```java
// Deep cloning via Jackson JSON Serialization:
public static <T> T deepCloneViaJson(T object, Class<T> targetClass, ObjectMapper mapper) {
    try {
        byte[] bytes = mapper.writeValueAsBytes(object);
        return mapper.readValue(bytes, targetClass);
    } catch (IOException e) {
        throw new UncheckedIOException("Deep copy failed", e);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Intent:** Creates new instances by cloning a pre-existing prototype, bypassing expensive reconstruction workflows.
- **`Cloneable` is Flawed:** Avoid `implements Cloneable`; use **Copy Constructors** or **Static Copy Factories** (`Class.copyOf(other)`).
- **Shallow vs Deep Copy:** Shallow copy duplicates references (mutations affect both objects); deep copy recursively allocates independent copies of all nested mutable objects.
- **Spring Prototype Scope:** Produces a new instance on every call, but requires `ObjectProvider<T>` or `@Lookup` when injected into a Singleton.
- **Spring Prototype Lifecycle:** Spring **never** invokes `@PreDestroy` on prototype beans.

**Common Follow-up Questions:**
- *"Why does `super.clone()` violate object encapsulation?"* → It bypasses standard constructors and copies raw heap bytes, meaning invariants checked in constructors can be bypassed and `final` fields cannot be deep-copied.
- *"What happens if a Prototype bean opens a database connection?"* → Because Spring does not run `@PreDestroy` on prototype beans, connections will leak unless the caller manually cleans up resources.
- *"How fast is a Copy Constructor compared to JSON deep cloning?"* → A Copy Constructor is direct native Java bytecode execution (~50ns); JSON cloning involves reflection and byte serialization overhead (~500–1000ns).

**Red Flags (DO NOT Say):**
- ❌ *"I always implement `Cloneable` and override `clone()` to copy objects in Java."* (Indicates unawareness of `Cloneable`'s fundamental design defects).
- ❌ *"Injecting a Prototype bean into a Singleton bean generates a new instance on every method call."* (It is injected once at startup unless `ObjectProvider` or `@Lookup` is used).
- ❌ *"Spring will automatically call `@PreDestroy` on all my prototype beans when the app shuts down."* (Spring explicitly delegates prototype cleanup to the caller).
