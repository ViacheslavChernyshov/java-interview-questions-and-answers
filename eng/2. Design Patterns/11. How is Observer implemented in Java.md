# How is Observer implemented in Java?

---

## 🟢 Junior Level

The **Observer pattern** is a Behavioral design pattern where an object (known as the **Subject** or **Publisher**) maintains a list of dependents (**Observers** or **Subscribers**) and notifies them automatically of any state changes or events.

**Simple analogy:** Subscribing to a newsletter or YouTube channel. Whenever the creator publishes new content, all registered subscribers receive an instant alert without polling the server repeatedly.

**Basic Implementation:**
```java
// Observer Interface
public interface OrderEventListener {
    void onOrderCreated(String orderId, BigDecimal amount);
}

// Subject (Publisher)
public class OrderService {
    private final List<OrderEventListener> listeners = new CopyOnWriteArrayList<>();

    public void subscribe(OrderEventListener listener) {
        listeners.add(listener);
    }

    public void unsubscribe(OrderEventListener listener) {
        listeners.remove(listener);
    }

    public void createOrder(String orderId, BigDecimal amount) {
        System.out.println("Order created: " + orderId);
        // Broadcast notification to all subscribers:
        for (OrderEventListener listener : listeners) {
            listener.onOrderCreated(orderId, amount);
        }
    }
}

// Usage with Lambdas:
OrderService service = new OrderService();
service.subscribe((id, amt) -> System.out.println("Email sent for order " + id));
service.subscribe((id, amt) -> System.out.println("Stock updated for amount " + amt));
service.createOrder("ORD-101", BigDecimal.valueOf(99.50));
```

## 🟡 Middle Level

### The Deprecation of `java.util.Observer` (Java 9+)

> [!WARNING]
> `java.util.Observer` and `java.util.Observable` were **deprecated in Java 9** due to severe architectural shortcomings:
> 1. `Observable` was a concrete class rather than an interface, preventing classes that already extended another parent from using it.
> 2. It was not thread-safe and lacked generic type parameters (`Object arg`).
> 3. It had no mechanism for error propagation or asynchronous backpressure.

### Three Crucial Production Resilience Rules

#### 1. Exception Isolation (Preventing Notification Halts)
```java
// ❌ WRONG: If listener 1 throws RuntimeException, listeners 2 and 3 NEVER run!
for (OrderEventListener l : listeners) {
    l.onOrderCreated(orderId, amount);
}

// ✅ CORRECT: Catch and log exceptions per observer
for (OrderEventListener l : listeners) {
    try {
        l.onOrderCreated(orderId, amount);
    } catch (Exception ex) {
        log.error("Failed to notify observer: {}", l.getClass().getSimpleName(), ex);
    }
}
```

#### 2. Avoiding `ConcurrentModificationException`
If an observer attempts to unregister itself during the callback execution, iterating over a standard `ArrayList` throws a `ConcurrentModificationException`. Always use a **`CopyOnWriteArrayList`** or iterate over a shallow snapshot copy (`new ArrayList<>(listeners)`).

#### 3. Preventing Memory Leaks (The Lapsed Listener Problem)
If a short-lived listener registers with a long-lived publisher, the publisher holds a strong reference in heap memory, preventing the listener from being garbage collected. Always implement explicit unsubscription hooks or use **`WeakReference`** observer wrappers.

## 🔴 Senior Level

### Enterprise Event-Driven Architecture: Spring Application Events

In Spring Boot, the Observer pattern is realized through decoupled, transaction-aware event publishing:

```java
// 1. Immutable Domain Event
public record OrderPlacedEvent(String orderId, String customerEmail, BigDecimal total) {}

// 2. Event Publisher Service
@Service
public class OrderProcessingService {
    private final ApplicationEventPublisher eventPublisher;

    public OrderProcessingService(ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    @Transactional
    public void completeOrder(Order order) {
        saveToDatabase(order);
        // Publishes event synchronously inside the transaction:
        eventPublisher.publishEvent(new OrderPlacedEvent(order.getId(), order.getEmail(), order.getTotal()));
    }
}

// 3. Decoupled Listeners
@Component
public class NotificationEventHandler {

    // Runs ONLY AFTER the database transaction commits successfully!
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Async // Runs asynchronously in a background thread pool
    public void handleOrderNotification(OrderPlacedEvent event) {
        sendConfirmationEmail(event.customerEmail(), event.orderId());
    }
}
```

### Modern Java 9+ Reactive Streams (Flow API)

The official high-performance Java implementation of the Observer pattern is the **`java.util.concurrent.Flow` API**, supporting non-blocking asynchronous streaming with **Backpressure**:

```java
public class MarketDataPublisher implements Flow.Publisher<BigDecimal> {
    private final List<Flow.Subscriber<? super BigDecimal>> subscribers = new CopyOnWriteArrayList<>();

    @Override
    public void subscribe(Flow.Subscriber<? super BigDecimal> subscriber) {
        subscribers.add(subscriber);
        subscriber.onSubscribe(new Flow.Subscription() {
            @Override
            public void request(long n) {
                // Backpressure: Publisher sends at most 'n' items requested by subscriber
            }
            @Override
            public void cancel() {
                subscribers.remove(subscriber);
            }
        });
    }

    public void updatePrice(BigDecimal newPrice) {
        subscribers.forEach(s -> s.onNext(newPrice));
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Concept:** 1-to-N dependency where state changes in a Subject are broadcast to all registered Observers.
- **Java 9 Deprecation:** `java.util.Observer` is deprecated; use **Spring Events**, **Flow API**, or **Functional Interfaces (`Consumer<T>`)**.
- **Resilience:** Wrap observer loops in `try-catch` to isolate failures; use `CopyOnWriteArrayList` to prevent `ConcurrentModificationException`.
- **Lapsed Listener Problem:** Failure to unsubscribe listeners causes memory leaks; resolved via `WeakReference` or explicit lifecycle hooks.
- **Spring `@TransactionalEventListener`:** Ensures listeners only execute after the surrounding database transaction successfully commits.

**Common Follow-up Questions:**
- *"What is the difference between synchronous and asynchronous observers?"* → Synchronous observers block the publisher thread during notification; asynchronous observers (`@Async` / Flow API) dispatch notifications onto worker thread pools, protecting publisher response times.
- *"Why is `CopyOnWriteArrayList` ideal for storing observers?"* → Observers are registered rarely (at startup) but iterated frequently on every event emission; `CopyOnWriteArrayList` provides lock-free reads and safe mutation iteration.
- *"What is Backpressure in the Flow API?"* → A mechanism allowing a slow consumer to signal how many items it can process (`Subscription.request(n)`), preventing fast publishers from overwhelming consumer memory.

**Red Flags (DO NOT Say):**
- ❌ *"I still use `java.util.Observer` in modern Java projects."* (Deprecated since Java 9).
- ❌ *"If an observer throws an exception, it is fine to let it crash the entire event loop."* (Crashes subsequent independent observers and potentially the main business transaction).
- ❌ *"All observers in Spring must run in the exact same thread as the caller."* (Spring supports `@Async` background execution).
