# What anti-patterns do you know?

---

## 🟢 Junior Level

An **anti-pattern** is a commonly used software development practice or architectural structure that initially appears to be a viable solution, but ultimately produces **severe negative consequences**, code rot, and maintenance gridlock.

**Common Code-Level Anti-Patterns:**

1. **God Object (The Blob):** A single monolithic class that knows too much and does everything, violating the Single Responsibility Principle (SRP).
   ```java
   // ❌ THE GOD OBJECT: Responsible for database, validation, email, analytics, and billing!
   public class ApplicationManager {
       public void saveToDb() { ... }
       public void validateUser() { ... }
       public void sendEmail() { ... }
       public void generatePdfReport() { ... }
   }
   ```
2. **Spaghetti Code:** Code with no clear structure, characterized by deeply nested loops, convoluted conditional jumps, and tangled execution flows.
3. **Copy-Paste Programming:** Duplicating code blocks across multiple services instead of refactoring into shared reusable components (violates DRY).

## 🟡 Middle Level

### High-Yield Architectural & Design Anti-Patterns

#### 1. The Golden Hammer (Maslow's Hammer)
Assuming that a single favorite pattern, framework, or technology solves every problem (*"If all you have is a hammer, everything looks like a nail"*).
- *Example:* Using microservices and Kafka event streams for a simple 100-user internal CRUD admin panel.

#### 2. Cargo Cult Programming
Blindly copying code snippets, annotations, or architectural patterns without understanding *why* they are needed or how they work under the hood.
- *Example:* Slapping `@Transactional` on every method in the project (including `private` methods and pure read-only getters) "just to be safe".

#### 3. Lava Flow (Dead / Zombie Code)
Dead, outdated, or undocumented code segments that nobody on the current team understands, but everyone is terrified of deleting because *"it might break production"*.

#### 4. Poltergeist (Gypsy Wagon)
Short-lived, stateless classes whose sole existence is to invoke another class, adding meaningless architectural indirection:
```java
// ❌ POLTERGEIST: Useless pass-through layer
public class OrderHelper {
    public void executeOrder(Order o) {
        new OrderProcessor().process(o);
    }
}
```

#### 5. Sequential Coupling
Enforcing an implicit, undocumented method invocation order at runtime that causes runtime exceptions if executed out of sequence:
```java
// ❌ SEQUENTIAL COUPLING: Calling process() before configure() crashes!
ReportEngine engine = new ReportEngine();
engine.init();
engine.configure();
engine.process(); // Fix: Enforce ordering via Builder pattern!
```

## 🔴 Senior Level

### Enterprise Architecture Anti-Patterns

#### 1. Big Ball of Mud
A system lacking any recognizable modular architecture, where classes, database tables, and presentation layers are tangled in circular dependency graphs.
- *Remediation:* Enforce package boundary encapsulation using **ArchUnit** tests and modular domain layers (Hexagonal / Clean Architecture).

#### 2. Anemic Domain Model vs. Rich Domain Model
Entities contain only raw fields with public getters and setters (dumb data holders), while all business invariants and business logic are scattered across massive 2,000-line `@Service` procedural classes.
- *Remediation:* Move domain invariants and validation logic directly into the Domain Entity (Domain-Driven Design).

#### 3. Inner-Platform Effect
Re-implementing a primitive, poorly tested version of existing database or operating system capabilities inside your application layer (e.g. building an ad-hoc in-memory query engine on top of nested HashMaps instead of using PostgreSQL).

### Anti-Pattern Triage & Prevention Matrix

| Anti-Pattern | Root Cause Code Smell | Preventive Tooling & Technique |
|---|---|---|
| **God Object** | Class $> 500$ lines, $> 30$ methods | Static Analysis (SonarQube), Single Responsibility refactoring |
| **Big Ball of Mud** | Circular package dependencies | **ArchUnit** automated architecture verification |
| **Cargo Cult** | Annotation copy-pasting | Strict Code Review, Technical Design Documents (TDD) |
| **Lava Flow** | Unused dead code branches | Code coverage analysis (JaCoCo), regular technical debt sprints |
| **Sequential Coupling** | Runtime temporal dependencies | **Step Builder** pattern enforcing compile-time order |

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A recurring software pattern that seems beneficial initially but results in severe technical debt and maintenance fragility.
- **Top Anti-Patterns:**
  - **God Object (The Blob):** Monolithic class violating SRP.
  - **Golden Hammer:** Forcing one familiar tool/pattern onto every problem.
  - **Cargo Cult:** Blindly applying annotations/patterns without understanding their mechanics.
  - **Lava Flow:** Legacy dead code retained out of fear of breaking unknown dependencies.
  - **Poltergeist:** Useless pass-through classes adding meaningless indirection.
  - **Anemic Domain Model:** Entities with only getters/setters while procedural services hold all business logic.
- **Remediation:** Adhere to **SOLID**, **KISS**, **YAGNI**, **DRY**, and use automated architecture linters like **ArchUnit** and **SonarQube**.

**Common Follow-up Questions:**
- *"What is the Anemic Domain Model and why is it considered an anti-pattern by Martin Fowler?"* → It reduces object-oriented design to procedural programming: entities are just passive data structures with getters/setters, violating encapsulation because business rules are duplicated across multiple services.
- *"How do you eliminate Sequential Coupling?"* → Use the Step Builder pattern to enforce method ordering at compile time, or pass all required configuration into the constructor.
- *"What automated tools prevent architectural erosion?"* → ArchUnit (unit tests for architecture rules), SonarQube (cognitive complexity and code duplication), and JaCoCo (uncovering dead lava flow code).

**Red Flags (DO NOT Say):**
- ❌ *"A God Object is fine as long as it is well-commented."* (Violates SRP, prevents parallel teamwork, and causes daily git merge conflicts).
- ❌ *"I put `@Transactional` on every method just in case a database call is added later."* (Classic Cargo Cult programming; adds transactional and proxy overhead to non-database operations).
- ❌ *"We never delete old code because nobody knows what it does."* (Lava Flow anti-pattern; dead code must be validated via tests and deleted).
