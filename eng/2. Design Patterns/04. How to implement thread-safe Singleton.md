# How to implement a thread-safe Singleton?

---

## 🟢 Junior Level

When multiple threads execute lazy initialization simultaneously, a race condition occurs: both threads evaluate `instance == null` as true, and both call `new Singleton()`, resulting in **two distinct objects** in heap memory.

**The Race Condition:**
```java
// ❌ BROKEN in Multithreaded Environments:
if (instance == null) {
    // Thread 1 & Thread 2 interleave here, creating duplicate instances!
    instance = new Singleton(); 
}
```

### The Safest Solution: Enum Singleton

```java
public enum AppConfig {
    INSTANCE;

    private String environment = "PRODUCTION";

    public String getEnvironment() {
        return environment;
    }
}

// Usage:
String env = AppConfig.INSTANCE.getEnvironment();
```

**Why Enum is the Best Default:**
- **Thread-safe by default:** The JVM guarantees that enum values are initialized atomically upon class loading.
- **Reflection-proof:** The JVM explicitly throws an `IllegalArgumentException` if reflection attempts to instantiate an enum.
- **Serialization-safe:** Native JVM serialization handles enum singletons without duplicating objects.

## 🟡 Middle Level

### The 3 Core Thread-Safe Implementation Patterns

#### 1. Bill Pugh Initialization-on-Demand Holder Idiom
```java
public class BillPughSingleton {
    private BillPughSingleton() {}

    // Static nested class is NOT loaded until getInstance() is invoked:
    private static class InstanceHolder {
        private static final BillPughSingleton INSTANCE = new BillPughSingleton();
    }

    public static BillPughSingleton getInstance() {
        return InstanceHolder.INSTANCE;
    }

    protected Object readResolve() {
        return getInstance();
    }
}
```
**How it works:** Under the Java Language Specification (JLS §12.4.1), inner static classes are loaded **lazily** only when referenced. The JVM's internal class loading lock guarantees thread safety without any explicit `synchronized` keywords or runtime overhead.

#### 2. Double-Checked Locking (DCL) with `volatile`
```java
public class DclSingleton {
    // volatile is mandatory to enforce memory barriers!
    private static volatile DclSingleton instance;

    private DclSingleton() {
        if (instance != null) {
            throw new IllegalStateException("Instance already created!");
        }
    }

    public static DclSingleton getInstance() {
        DclSingleton localRef = instance; // Local variable optimization
        if (localRef == null) {
            synchronized (DclSingleton.class) {
                localRef = instance;
                if (localRef == null) {
                    instance = localRef = new DclSingleton();
                }
            }
        }
        return localRef;
    }
}
```

### Comparison Matrix

| Approach | Lazy Loading | Thread Safety | Performance | Resistance to Attacks |
|---|---|---|---|---|
| **Enum** | ❌ Eager | ✅ JVM Guaranteed | ⚡ Ultra-fast | 🛡️ Immune (Reflection + Ser.) |
| **Bill Pugh** | ✅ Lazy | ✅ ClassLoader Lock | ⚡ Ultra-fast | ⚠️ Needs `readResolve()` |
| **DCL + volatile** | ✅ Lazy | ✅ Memory Barrier | ⚡ Fast (1 volatile read) | ⚠️ Needs `readResolve()` |
| **synchronized method**| ✅ Lazy | ✅ Monitor Lock | 🐢 Slow (Contention) | ⚠️ Needs `readResolve()` |

## 🔴 Senior Level

### The Java Memory Model & The Need for `volatile`

Instantiating an object (`instance = new Singleton()`) is **not an atomic bytecode operation**. It consists of three distinct steps:
1. `allocate`: Allocate heap memory block for the object.
2. `ctor`: Execute the constructor and initialize object fields.
3. `assign`: Assign the allocated memory address to the static `instance` reference.

```
Without 'volatile' (Instruction Reordering by CPU / JIT Compiler):
  Step 1: Allocate Memory  ──>  Step 3: Assign Reference  ──>  Step 2: Run Constructor
                                        │
                                        ▼ (Thread B observes instance != null)
                             Thread B receives a PARTIALLY INITIALIZED object!
```

**The `volatile` Fix:**
- Inserting `volatile` emits CPU memory fences (`StoreStore` and `StoreLoad` on x86/ARM).
- It creates a strict **Happens-Before** relationship: all constructor writes are guaranteed to be flushed to main memory **before** the reference assignment becomes visible to other threads.

### High-Performance DCL via `VarHandle` (Java 9+)

For high-throughput systems, Java 9 introduced `VarHandle` with `getAcquire()` and `setRelease()` semantics, which omit heavier full volatile memory fences:

```java
public class VarHandleSingleton {
    private static VarHandleSingleton instance;
    private static final VarHandle VH;

    static {
        try {
            VH = MethodHandles.lookup().findStaticVarHandle(
                VarHandleSingleton.class, "instance", VarHandleSingleton.class
            );
        } catch (ReflectiveOperationException e) {
            throw new ExceptionInInitializerError(e);
        }
    }

    private VarHandleSingleton() {}

    public static VarHandleSingleton getInstance() {
        VarHandleSingleton local = (VarHandleSingleton) VH.getAcquire();
        if (local == null) {
            synchronized (VarHandleSingleton.class) {
                local = (VarHandleSingleton) VH.getAcquire();
                if (local == null) {
                    local = new VarHandleSingleton();
                    VH.setRelease(local);
                }
            }
        }
        return local;
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Enum Singleton:** Best choice when lazy loading is not needed; natively immune to serialization and reflection attacks.
- **Bill Pugh (Holder Idiom):** Best choice when lazy loading is required; zero lock overhead via JLS §12.4.1 classloader initialization guarantees.
- **Double-Checked Locking:** Requires `volatile` to prevent CPU out-of-order instruction reordering (where memory is assigned before constructor completion).
- **Local Variable Optimization:** Storing `instance` in a local variable inside `getInstance()` reduces expensive volatile reads to a single access in the common path.
- **Spring Framework:** Never write manual singletons in Spring; declare beans with `@Component` / `@Service` (Singleton scope by default).

**Common Follow-up Questions:**
- *"Why does DCL check `localRef == null` twice?"* → The first check avoids expensive synchronization when the instance is already initialized; the second check inside the `synchronized` block ensures that only one thread creates the instance if multiple threads passed the first check simultaneously.
- *"Why is `java.lang.Enum` protected from reflection attacks?"* → `Constructor.newInstance()` explicitly checks the `ENUM` modifier and throws an `IllegalArgumentException("Cannot reflectively create enum objects")`.
- *"How does Bill Pugh achieve thread safety without `synchronized`?"* → The JVM class loader holds an internal initialization lock when loading the nested static holder class, ensuring atomic single-threaded execution of static initializers.

**Red Flags (DO NOT Say):**
- ❌ *"DCL works fine without the `volatile` keyword in modern Java versions."* (Without `volatile`, instruction reordering can publish partially constructed objects).
- ❌ *"I use `synchronized` on `public static synchronized getInstance()` in production."* (Causes severe thread contention bottlenecks in hot code paths).
- ❌ *"Enum singletons support lazy initialization on first method call."* (Enums are loaded eagerly as soon as any member of the enum class is referenced).
