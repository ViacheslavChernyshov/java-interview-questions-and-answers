# Difference between Factory Method and Abstract Factory

---

## 🟢 Junior Level

Both patterns solve the problem of object instantiation without coupling business logic to concrete classes, but they operate at different structural scopes:

- **Factory Method:** Creates a **single product** using inheritance. A parent class defines a template method, delegating the instantiation of that one product to subclasses.
- **Abstract Factory:** Creates a **family of related/dependent products** using composition. A single factory interface produces multiple matching objects (e.g. Buttons, Checkboxes, Menus) designed to work together consistently.

```
       Factory Method                      Abstract Factory
   ┌────────────────────┐              ┌───────────────────────────┐
   │    Dialog Class    │              │    GUIFactory Interface   │
   ├────────────────────┤              ├───────────────────────────┤
   │ + createButton()   │              │ + createButton(): Button  │
   └─────────┬──────────┘              │ + createCheckbox(): Check │
             │                         │ + createMenu(): Menu      │
             ▼                         └─────────────┬─────────────┘
   ┌────────────────────┐                            │
   │ WinDialog / Mac... │              ┌─────────────┴─────────────┐
   │ (Returns 1 Button) │              ▼                           ▼
   └────────────────────┘      ┌───────────────┐           ┌───────────────┐
                               │ WinGUIFactory │           │ MacGUIFactory │
                               └───────────────┘           └───────────────┘
```

**Simple analogy:**
- **Factory Method:** Ordering a single coffee from a barista (subclass decides whether you get Latte, Espresso, or Cappuccino).
- **Abstract Factory:** Ordering a full modular furniture set (Victorian Sofa + Victorian Chair + Victorian Table vs Modern Sofa + Modern Chair + Modern Table). You never mix a Victorian chair with a Modern table!

## 🟡 Middle Level

### 1. Factory Method in Detail (Inheritance-Based)

```java
public abstract class DocumentParser {
    // Template Method defining parsing workflow
    public Document parse(File file) {
        Reader reader = createReader(); // Factory method call
        return reader.read(file);
    }

    // Subclasses override this single factory method
    protected abstract Reader createReader();
}

public class CsvDocumentParser extends DocumentParser {
    @Override
    protected Reader createReader() {
        return new CsvReader();
    }
}
```

### 2. Abstract Factory in Detail (Composition-Based)

```java
// Abstract Factory Interface
public interface CloudInfrastructureFactory {
    ComputeInstance createCompute();
    StorageBucket createStorage();
    DatabaseInstance createDatabase();
}

// AWS Concrete Family
public class AwsInfrastructureFactory implements CloudInfrastructureFactory {
    public ComputeInstance createCompute() { return new Ec2Instance(); }
    public StorageBucket createStorage() { return new S3Bucket(); }
    public DatabaseInstance createDatabase() { return new RdsDatabase(); }
}

// Client service accepts the factory via Dependency Injection (Composition)
public class CloudDeployer {
    private final CloudInfrastructureFactory factory;

    public CloudDeployer(CloudInfrastructureFactory factory) {
        this.factory = factory;
    }

    public void deployEnvironment() {
        ComputeInstance vm = factory.createCompute();
        StorageBucket storage = factory.createStorage();
        // Guaranteed: Ec2Instance and S3Bucket belong to the same cloud vendor!
    }
}
```

### Architectural Comparison

| Dimension | Factory Method | Abstract Factory |
|---|---|---|
| **Instantiation Target** | 1 standalone product | A cohesive family of related products |
| **Coupling Mechanism** | Class inheritance (subclassing) | Object composition (interface injection) |
| **Implementation Complexity**| Low (1 abstract method) | High (interface with multiple factory methods) |
| **New Product Types** | Trivial (create 1 subclass) | High breaking risk (modifies interface for all factories) |

## 🔴 Senior Level

### The Open/Closed Principle (OCP) Asymmetry

There is a fundamental design trade-off regarding the Open/Closed Principle between these patterns:

1. **Factory Method adheres strictly to OCP:** Adding a new concrete product variant requires adding a new subclass without modifying any existing classes.
2. **Abstract Factory exhibits asymmetric OCP compliance:**
   - **Adding a new Product Family (e.g. `GcpInfrastructureFactory`):** Fully adheres to OCP.
   - **Adding a new Product Type (e.g. adding `createKubernetesCluster()`):** **Violates OCP**. You must edit the `CloudInfrastructureFactory` root interface and rewrite every single existing concrete factory (`Aws`, `Azure`, `Local`) across the codebase.

### Modern Java Refactoring: Functional Interfaces & Records

In modern Java (17+), heavy class hierarchies can be replaced with `Supplier<T>` and compact Java Records:

```java
// Abstract Factory represented as a Java Record:
public record UIThemeFactory(
    Supplier<Button> buttonSupplier,
    Supplier<Checkbox> checkboxSupplier
) {}

// Concrete Factory instances assembled with Method References:
public static final UIThemeFactory DARK_THEME = new UIThemeFactory(
    DarkButton::new,
    DarkCheckbox::new
);

public static final UIThemeFactory LIGHT_THEME = new UIThemeFactory(
    LightButton::new,
    LightCheckbox::new
);
```

### Spring Framework as a Dynamic Meta-Factory

In enterprise architectures, Spring's `@Configuration` and `@Profile` annotations replace manual Abstract Factories:

```java
@Configuration
public class StorageConfig {
    @Bean
    @Profile("prod")
    public StorageService s3StorageService() {
        return new S3StorageService();
    }

    @Bean
    @Profile("local")
    public StorageService localStorageService() {
        return new LocalDiskStorageService();
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Distinction:** Factory Method uses inheritance to create **one** product; Abstract Factory uses composition to create a **family** of compatible products.
- **OCP Trap:** Abstract Factory makes adding new product families easy, but adding new product types breaks all existing factory implementations.
- **Modern Java:** Use `Supplier<T>` and constructor method references (`MyClass::new`) to implement lightweight Factory Methods without subclassing.
- **Spring Integration:** Spring `@Configuration` with `@Profile` / conditional beans acts as an enterprise Abstract Factory at runtime.

**Common Follow-up Questions:**
- *"Why not use Abstract Factory when there is only one product to create?"* → It creates unnecessary architectural indirection and interface boilerplate; a simple Factory Method or static factory method (`Class.of()`) is cleaner.
- *"What is a Simple Factory vs Factory Method?"* → A Simple Factory is a non-extensible static helper class with an `if/switch` block (`PaymentFactory.create("STRIPE")`); a Factory Method is an overridable method inside an abstract class hierarchy.
- *"How does Abstract Factory prevent incompatible component mixing?"* → Client code interacts exclusively with the abstract interface, making it impossible to accidentally instantiate a Windows button inside a macOS rendering context.

**Red Flags (DO NOT Say):**
- ❌ *"Factory Method and Abstract Factory are basically identical."* (They use completely different mechanisms: inheritance vs composition).
- ❌ *"Abstract Factory never violates the Open/Closed Principle."* (Adding a new creation method to the factory interface breaks all implementors).
- ❌ *"A static method with a switch case is the Gang of Four Factory Method."* (That is the non-GoF Simple Factory idiom).
