# What is Singleton?

---

## 🟢 Junior Level

**Singleton** is a Creational design pattern that guarantees a class has **only one instance throughout the runtime lifecycle** of an application and provides a global access point to that instance.

**Why it is needed:** When a resource is fundamentally shared (e.g. logging facility, hardware driver interface, application configuration registry) and creating multiple conflicting instances would cause resource contention or state corruption.

**Simple analogy:** A country has only one head of state (President). Whenever citizens inquire *"Who is the President?"*, everyone receives a reference to the exact same person.

**Core Mechanics:**
1. **Private constructor:** Prevents external instantiation via the `new` operator.
2. **Private static field:** Holds the unique single instance.
3. **Public static factory method (`getInstance()`):** Provides global access to the instance.

```java
public class AppConfig {
    // 1. Eagerly instantiated static instance
    private static final AppConfig INSTANCE = new AppConfig();

    // 2. Private constructor prevents 'new AppConfig()'
    private AppConfig() {}

    // 3. Global accessor
    public static AppConfig getInstance() {
        return INSTANCE;
    }

    public String getProperty(String key) {
        return System.getProperty(key);
    }
}

// Usage:
AppConfig config1 = AppConfig.getInstance();
AppConfig config2 = AppConfig.getInstance();
System.out.println(config1 == config2); // true (Identical heap reference!)
```

### Singleton vs. Static Utility Class

| Feature | Singleton Pattern | Static Class (`Math`, `Collections`) |
|---|---|---|
| **Polymorphism** | Can implement interfaces and extend classes | Cannot implement interfaces |
| **Object Passing** | Can be passed as a parameter (`Method(Config c)`) | Cannot be passed as an object reference |
| **Lazy Loading** | Supports lazy on-demand initialization | Loaded eagerly when class is referenced |
| **Mockability** | Easy to mock via interfaces in unit tests | Very difficult to mock without ByteBuddy/PowerMock |

## 🟡 Middle Level

### Common Implementation Strategies

#### 1. Eager Initialization (Thread-Safe, Non-Lazy)
```java
public class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() {}
    public static EagerSingleton getInstance() { return INSTANCE; }
}
// ✅ Thread-safe (guaranteed by JVM class loading)
// ❌ Not lazy (allocated in memory even if never requested)
```

#### 2. Synchronized Lazy Initialization (Thread-Safe, High Contention)
```java
public class SynchronizedSingleton {
    private static SynchronizedSingleton instance;
    private SynchronizedSingleton() {}
    
    public static synchronized SynchronizedSingleton getInstance() {
        if (instance == null) {
            instance = new SynchronizedSingleton();
        }
        return instance;
    }
}
// ✅ Thread-safe & Lazy
// ❌ High overhead: Synchronized lock acquisition penalty on every single read call!
```

#### 3. Enum Singleton (Effective Java Item 3 — The Gold Standard)
```java
public enum EnumSingleton {
    INSTANCE;
    
    public void execute(String command) {
        System.out.println("Executing: " + command);
    }
}

// Usage:
EnumSingleton.INSTANCE.execute("START_BATCH");
// ✅ Thread-safe & Clean
// ✅ Built-in immunity to Reflection & Serialization attacks
```

### Three Ways a Classical Singleton Can Be Broken

#### 1. Reflection Attack (`setAccessible(true)`)
```java
Constructor<EagerSingleton> constructor = EagerSingleton.class.getDeclaredConstructor();
constructor.setAccessible(true);
EagerSingleton rogueInstance = constructor.newInstance(); // ❌ Second instance created!
```
*Defense:* Throw an `IllegalStateException` from the constructor if an instance already exists, or use an `enum` (the JVM explicitly forbids reflective instantiation of enums).

#### 2. Serialization Attack
```java
// Deserializing a singleton creates an entirely new heap object!
byte[] serialized = serialize(EagerSingleton.getInstance());
EagerSingleton deserialized = deserialize(serialized);
System.out.println(deserialized == EagerSingleton.getInstance()); // false!
```
*Defense:* Implement the `readResolve()` hook:
```java
protected Object readResolve() {
    return getInstance(); // Returns the canonical singleton instance
}
```

#### 3. Multiple ClassLoaders
In application servers (e.g. Tomcat, OSGi), each web application runs in an isolated `ClassLoader`. If two classloaders load the same class, **two distinct singleton instances** will exist in memory.

## 🔴 Senior Level

### Scope & Contextuality: Singleton in Distributed & Spring Systems

> [!IMPORTANT]
> A Java Singleton is **only unique per ClassLoader within a single JVM process**. It is **not** a cluster-wide singleton.

```
       Cluster Architecture (3 Nodes)
 ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
 │ Node 1 (JVM)  │   │ Node 2 (JVM)  │   │ Node 3 (JVM)  │
 │ ┌───────────┐ │   │ ┌───────────┐ │   │ ┌───────────┐ │
 │ │ Singleton │ │   │ │ Singleton │ │   │ │ Singleton │ │
 │ └───────────┘ │   │ └───────────┘ │   │ └───────────┘ │
 └───────────────┘   └───────────────┘   └───────────────┘
  (3 completely independent instances operating in parallel!)
```
*Production Rule:* In distributed cloud systems, do not use in-memory Singletons for global coordination or sequence generation; use **Redis (`INCR`, Redlock)**, **ZooKeeper**, or a **Database Sequence**.

### Spring Framework Singleton vs. GoF Singleton

- **GoF Singleton:** Enforces exclusivity via `private` constructors and `static` references. Tightly coupled, untestable, hardcoded lifecycle.
- **Spring Singleton Scope (`@Component`):** Exclusivity is managed by the **IoC Container (`ApplicationContext`)**. The class itself remains a standard POJO with a public constructor, making it 100% testable and injectable.

```java
// Spring manages lifecycle cleanly without static state:
@Service // Singleton scope by default in Spring Context
public class PaymentService {
    private final PaymentGateway gateway;
    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway; // Fully mockable in Unit Tests!
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Concept:** Ensures exactly one instance exists and provides a global access point via a private constructor and static accessor.
- **Best Implementations:**
  - **Enum Singleton:** Preferred for libraries/SDKs; immune to serialization and reflection attacks.
  - **Bill Pugh (Holder Idiom):** Preferred for lazy initialization without synchronization overhead.
  - **Spring DI:** Preferred in enterprise applications (managed bean lifecycle).
- **Vulnerabilities of Classic Singletons:**
  1. Reflection (`setAccessible(true)` bypasses private constructor).
  2. Serialization (`readObject()` creates a duplicate instance unless `readResolve()` is implemented).
  3. Multiple ClassLoaders create duplicate instances in modular environments.
- **Cluster Warning:** Singletons are local to a single JVM/ClassLoader, never across distributed nodes.

**Common Follow-up Questions:**
- *"Why is manual Singleton often considered an anti-pattern?"* → It introduces hidden global state, violates Single Responsibility and Dependency Inversion principles, and prevents unit test isolation and mocking.
- *"How does `readResolve()` protect against serialization duplicates?"* → The JVM serialization engine checks for `readResolve()` and substitutes the deserialized instance with the object returned by the method.
- *"What happens if a Singleton holds mutable state across HTTP requests?"* → Under concurrent access from Tomcat worker threads, unsynchronized mutations cause critical race conditions and data corruption.

**Red Flags (DO NOT Say):**
- ❌ *"A Singleton ensures only one instance exists across my entire Kubernetes cluster."* (It is strictly local to one ClassLoader in one JVM).
- ❌ *"I use manual Singletons with public static methods inside Spring Boot services."* (Breaks Dependency Injection and testability).
- ❌ *"Double-Checked Locking works fine without the `volatile` keyword."* (Causes partial object construction bugs due to CPU memory reordering).
