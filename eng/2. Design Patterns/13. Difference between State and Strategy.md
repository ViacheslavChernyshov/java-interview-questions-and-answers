# Difference between State and Strategy

---

## 🟢 Junior Level

While both **State** and **Strategy** share nearly identical UML class diagrams (a Context delegating execution to a polymorphic interface), their **architectural intent and control flow are completely different**:

- **Strategy Pattern (External Control):** The client code actively chooses and injects which algorithm to execute. The strategies are completely independent and unaware of each other.
- **State Pattern (Internal Control):** The context object changes its behavior dynamically as its **internal lifecycle state changes**. The state transitions occur automatically as a **Finite State Machine (FSM)**.

```
       Strategy Pattern                             State Pattern
 (Client Injects Algorithm)                  (Internal State Transition FSM)
┌────────┐    ┌──────────────┐             ┌────────┐    ┌─────────────┐
│ Client │───>│   Context    │             │ Client │───>│   Context   │
└────────┘    └──────┬───────┘             └────────┘    └──────┬──────┘
                     │ delegates                                │ delegates
                     ▼                                          ▼
             ┌───────────────┐                          ┌───────────────┐
             │PaymentStrategy│                          │  OrderState   │
             └───────┬───────┘                          └───────┬───────┘
          ┌──────────┴──────────┐                    ┌──────────┴──────────┐
          ▼                     ▼                    ▼                     ▼
    ┌───────────┐         ┌───────────┐        ┌───────────┐         ┌───────────┐
    │CreditCard │         │  PayPal   │        │ NewOrder  │ ──────> │ PaidOrder │
    └───────────┘         └───────────┘        └───────────┘ (Next)  └───────────┘
    (Completely Independent of each other)    (Aware of Transition Pipeline & Invariants)
```

**Simple analogy:**
- **Strategy:** You choose whether to travel by Car, Train, or Airplane.
- **State:** A traffic light cycles automatically through Red $\to$ Yellow $\to$ Green based on internal timer transitions.

## 🟡 Middle Level

### Strategy: Client-Driven Execution

```java
// Strategy: Algorithms are isolated and swappable at will
public interface CompressionStrategy {
    byte[] compress(byte[] data);
}

public class ZipCompression implements CompressionStrategy { ... }
public class GzipCompression implements CompressionStrategy { ... }

// Client decides:
DataArchiver archiver = new DataArchiver();
archiver.setStrategy(new GzipCompression());
archiver.archive(payload);
```

### State: Self-Transitioning State Machine

```java
public interface OrderState {
    void next(OrderContext ctx);
    void cancel(OrderContext ctx);
    String getStatus();
}

public class NewOrderState implements OrderState {
    @Override
    public void next(OrderContext ctx) {
        // Enforces valid business state transition:
        ctx.setState(new PaidOrderState());
    }

    @Override
    public void cancel(OrderContext ctx) {
        ctx.setState(new CancelledOrderState());
    }

    @Override
    public String getStatus() { return "NEW"; }
}

public class PaidOrderState implements OrderState {
    @Override
    public void next(OrderContext ctx) {
        ctx.setState(new ShippedOrderState());
    }

    @Override
    public void cancel(OrderContext ctx) {
        throw new IllegalStateException("Cannot cancel an order that is already paid!");
    }

    @Override
    public String getStatus() { return "PAID"; }
}
```

### Direct Comparison Matrix

| Dimension | Strategy Pattern | State Pattern |
|---|---|---|
| **Control of Change** | **External:** Client injects strategy explicitly | **Internal:** Context/State transitions itself automatically |
| **Inter-Class Awareness**| None: Strategies are 100% unaware of each other | High: States know about valid predecessor/successor states |
| **Execution Lifetime** | Usually stays constant for a specific operation | Changes continuously across the entity's lifecycle |
| **Primary Goal** | Avoid procedural `if-else` algorithm switches | Model a Finite State Machine and enforce valid state rules |

## 🔴 Senior Level

### Modern Java 17+ Implementation: Sealed Interfaces & Pattern Matching

In modern Java, state machines are implemented cleanly using **Sealed Interfaces** and exhaustive pattern matching, eliminating mutable state pointers:

```java
// Sealed State Hierarchy (Java 17+)
public sealed interface OrderState permits DraftState, PaidState, ShippedState, CancelledState {}

public record DraftState(BigDecimal amount) implements OrderState {}
public record PaidState(BigDecimal amount, Instant paidAt, String txId) implements OrderState {}
public record ShippedState(String trackingNumber) implements OrderState {}
public record CancelledState(String reason) implements OrderState {}

// Pure Functional State Machine Dispatcher (Java 21 Pattern Matching):
public class OrderWorkflowEngine {
    public OrderState transitionToNext(OrderState currentState, String eventPayload) {
        return switch (currentState) {
            case DraftState draft -> new PaidState(draft.amount(), Instant.now(), eventPayload);
            case PaidState paid   -> new ShippedState(eventPayload);
            case ShippedState _   -> throw new IllegalStateException("Order is already final!");
            case CancelledState _ -> throw new IllegalStateException("Cannot advance cancelled order!");
        };
    }
}
```

### Avoiding State Tight-Coupling: State Registry vs Direct Instantiation

> [!CAUTION]
> Direct instantiation of next states (`new PaidState()`) creates tight coupling between state classes. In Spring, use a **State Registry** or **Spring Statemachine**:

```java
@Component
public class StateRegistry {
    private final Map<OrderStep, OrderState> stateMap;

    public StateRegistry(List<OrderState> states) {
        this.stateMap = states.stream()
            .collect(Collectors.toMap(OrderState::getStep, Function.identity()));
    }

    public OrderState getState(OrderStep step) {
        return stateMap.get(step);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Difference:** Strategy is algorithm selection from the **outside** (client); State is behavior adaptation from the **inside** (lifecycle FSM).
- **Coupling:** Strategies are completely decoupled from each other; States are connected via a directed transition graph.
- **Modern Java 17/21:** Implement state transitions using **Sealed Interfaces** and exhaustive `switch` pattern matching for compile-time validation.
- **Enterprise Spring:** Use Spring Statemachine or a State Registry to decouple state transition classes from direct constructor coupling.

**Common Follow-up Questions:**
- *"How do you prevent invalid state jumps (e.g. from Shipped directly back to Draft)?"* → In the State pattern, `ShippedState` explicitly throws an `IllegalStateException` on invalid transition requests.
- *"Why is Strategy called Dependency Injection for algorithms?"* → The client injects the strategy instance into the context at construction or runtime without the context knowing the concrete algorithm.
- *"What is the difference between State and Template Method?"* → State alters behavior dynamically via composition across multiple states; Template Method alters invariant algorithm steps via class inheritance.

**Red Flags (DO NOT Say):**
- ❌ *"State and Strategy are identical patterns with no real difference."* (Their architectural intent, control flow, and inter-class coupling are completely distinct).
- ❌ *"The client should manually call `order.setState(new ShippedState())` in production."* (Defeats the State pattern; the context and state machine must govern valid transitions).
- ❌ *"Sealed classes cannot be used for state machines in Java."* (Sealed interfaces provide exhaustive compile-time verification for state machines).
