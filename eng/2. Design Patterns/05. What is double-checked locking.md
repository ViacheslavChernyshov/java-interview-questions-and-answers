# What is double-checked locking?

---

## 🟢 Junior Level

**Double-Checked Locking (DCL)** is a software concurrency optimization pattern designed to reduce the overhead of acquiring a lock by testing the initialization criteria twice: **once without locking** and **once with locking**.

**The Problem:** Using `synchronized` on an entire method incurs a 10–50ns locking overhead on *every single invocation*, even after the instance has already been created.

```java
// ❌ HIGH CONTENTION: Every read thread waits for a monitor lock!
public static synchronized DatabaseConnection getInstance() {
    if (instance == null) {
        instance = new DatabaseConnection();
    }
    return instance;
}
```

**The DCL Solution:**
```java
public class DatabaseConnection {
    // ⚠️ 'volatile' is MANDATORY to prevent CPU instruction reordering!
    private static volatile DatabaseConnection instance;

    private DatabaseConnection() {}

    public static DatabaseConnection getInstance() {
        // Check 1: Fast-path (No locking)
        if (instance == null) {
            synchronized (DatabaseConnection.class) {
                // Check 2: Thread-safe check under lock
                if (instance == null) {
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance; // Lock-free read on subsequent calls!
    }
}
```

---

## 🟡 Middle Level

### Why Two Checks Are Required

1. **First Check (`if (instance == null)`):** Fast-path filter. Once initialized, 100% of concurrent threads return the instance immediately without acquiring any monitor locks.
2. **Second Check (`if (instance == null)` inside `synchronized`):** Thread-safety guard. If two threads pass the first check simultaneously, Thread 1 acquires the lock, creates the object, and releases the lock. When Thread 2 acquires the lock, the second check prevents it from creating a redundant second instance.

### The Critical Need for `volatile` (JSR-133 Java Memory Model)

Object construction in Java bytecode is broken down into three discrete operations:

```
  1. allocate:  Allocate raw heap memory for the DatabaseConnection object.
  2. ctor:      Execute <init>() constructor to populate instance fields.
  3. assign:    Assign the heap memory address to the static 'instance' variable.
```

**Without `volatile`:** Out-of-order execution by the CPU or JIT compiler can legally reorder instructions to `1 -> 3 -> 2`:

```
 Thread A                              Thread B
 ────────                              ────────
 1. Allocates Memory
 3. Assigns reference to 'instance'
                                       1. Checks 'instance == null' (Evaluates FALSE!)
                                       2. Uses uninitialized object fields -> CRASH / NPE!
 2. Executes Constructor
```

**With `volatile`:** The Java compiler and CPU are forbidden from reordering reads and writes across the volatile access.

## 🔴 Senior Level

### Memory Barriers and Happens-Before Semantics

The `volatile` modifier enforces synchronization at the CPU hardware level by emitting **Memory Barriers (Fences)**:

```
  [Constructor writes: fieldA = x, fieldB = y]
  ────── StoreStore Barrier ────── (Ensures constructor writes flush to cache BEFORE reference write)
  [PUTSTATIC instance = reference]
  ────── StoreLoad Barrier ──────  (Ensures write is visible to all CPU cores)
```

```
  [GETSTATIC reference = instance]
  ────── LoadLoad Barrier ──────   (Ensures subsequent field reads see updated main memory)
  [Read object fields: fieldA, fieldB]
```

Under JSR-133 (Java 5+), a write to a `volatile` variable **happens-before** every subsequent read of that same `volatile` variable.

### Performance Optimization: Local Variable Caching

```java
public static DatabaseConnection getInstance() {
    DatabaseConnection localRef = instance; // Read volatile field exactly once
    if (localRef == null) {
        synchronized (DatabaseConnection.class) {
            localRef = instance;
            if (localRef == null) {
                instance = localRef = new DatabaseConnection();
            }
        }
    }
    return localRef; // Return local CPU register reference
}
```
**Why this matters:** Volatile reads bypass CPU L1/L2 caches to guarantee memory synchronization. Caching the reference in a local register variable (`localRef`) avoids reading the volatile memory address twice in the common fast path, yielding a **~25% performance improvement** in high-throughput microbenchmarks.

### DCL Beyond Singleton: Lazy Field Caching (`String.hashCode()`)

DCL is also used to lazily cache immutable computed properties:

```java
public final class ImmutableDocument {
    private final byte[] content;
    private volatile String checksum; // Lazily computed hash

    public ImmutableDocument(byte[] content) {
        this.content = content;
    }

    public String getChecksum() {
        String result = checksum;
        if (result == null) {
            synchronized (this) {
                result = checksum;
                if (result == null) {
                    checksum = result = computeSha256(this.content);
                }
            }
        }
        return result;
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Goal:** Lock-free reads after a one-time synchronized initialization.
- **Why Two Checks:** Check 1 avoids lock acquisition; Check 2 avoids duplicate creation if multiple threads raced past Check 1.
- **Why `volatile` is Mandatory:** Prevents CPU instruction reordering ($1 \to 3 \to 2$), which would expose a partially constructed object to other threads.
- **Happens-Before Guarantee:** `volatile` write creates memory barriers ensuring constructor execution completes before the reference is published.
- **History:** DCL was fundamentally broken prior to Java 5 (pre-JSR-133 memory model).

**Common Follow-up Questions:**
- *"What happens if you run DCL without `volatile` on modern multi-core ARM/x86 processors?"* → On x86 (strong memory model), it might pass tests but fail intermittently under load; on ARM (weak memory model), instruction reordering will cause frequent NPEs or reading uninitialized default field values (`0` or `null`).
- *"Why is `Bill Pugh Singleton` often preferred over DCL?"* → Bill Pugh uses classloader locks, eliminating the need for `volatile` memory barriers and manual synchronization code altogether.
- *"Why do we assign `localRef = instance` at the start of `getInstance()`?"* → It caches the volatile reference in a local register, reducing expensive volatile read instructions.

**Red Flags (DO NOT Say):**
- ❌ *"DCL is completely safe without `volatile` in Java 8+."* (It is undefined behavior and causes subtle race conditions).
- ❌ *"DCL locks the class on every single read operation."* (The synchronized block is only entered once during the very first invocation).
- ❌ *"DCL is only used for implementing Singletons."* (It is used for any lazy calculation/caching of expensive immutable values).
