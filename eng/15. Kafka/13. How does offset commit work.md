# How Does Offset Commit Work?

---

## 🟢 Junior Level

**Offset Committing** is the mechanism by which a Kafka Consumer Group records its reading progress back to the cluster so that if a consumer crashes or restarts, it can resume processing from where it left off:

```
  Reading Bookmark Analogy:
  • You finish reading page 10 of a textbook.
  • You write down in your study journal: "Next page to read is Page 11." (Committed Offset = 11).
  • If your phone rings and you close the book, you reopen directly to Page 11 tomorrow.
```

```
  The +1 Offset Invariant:
  • If you successfully process a record at Offset 5:
  • You must commit Offset 6!
  • The committed offset ALWAYS points to the NEXT unread record!
```

```java
// Basic Manual Synchronous Commit:
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processOrder(record.value());
    }
    // Block until the broker confirms offset has been written to disk:
    consumer.commitSync();
}
```

## 🟡 Middle Level

### Under the Hood: The `__consumer_offsets` Topic

When a consumer commits an offset, it sends an `OffsetCommitRequest` to the **Group Coordinator** broker:
- The coordinator writes a message into the internal system topic **`__consumer_offsets`**.
- **Record Key:** `[Group_ID, Topic_Name, Partition_ID]`
- **Record Value:** `[Committed_Offset, Leader_Epoch, Metadata_String, Timestamp]`
- **Compaction:** Because `__consumer_offsets` has `cleanup.policy=compact`, Kafka retains only the latest committed offset per group/topic/partition, preventing unbounded disk growth.

### Synchronous vs. Asynchronous Commit

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Commit Method        │ Thread Behavior & Retries    │ Trade-Off & Production Use Case                  │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`commitSync()`**   │ **Blocking** (5–30ms latency)| 🛡️ Safe & Deterministic. Retries transient       │
  │                      │ Retries until ACK or fatal.  │ errors automatically. Lower throughput.          │
  │ **`commitAsync()`**  │ **Non-Blocking** (Fire & For)| ⚡ High Throughput. **Never retries** to prevent │
  │                      │ Continues loop immediately.  │ out-of-order offset regression!                  │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

```
  ⚠️ Why `commitAsync()` Never Retries:
  • Request 1 (Commit Offset 10) experiences a network timeout.
  • Request 2 (Commit Offset 20) succeeds immediately.
  • If Request 1 were retried, it would succeed AFTER Request 2, 
    incorrectly regressing the committed offset back to 10!
```

## 🔴 Senior Level

### Production Hybrid Commit Pattern

Senior engineers combine `commitAsync()` inside the high-throughput loop with `commitSync()` inside the shutdown handler:

```java
try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> record : records) {
            processRecord(record);
        }
        
        // Fast non-blocking commit during steady-state processing:
        consumer.commitAsync((offsets, exception) -> {
            if (exception != null) {
                log.warn("Async offset commit failed for offsets: {}", offsets, exception);
            }
        });
    }
} catch (WakeupException e) {
    // Expected during graceful container termination
} finally {
    try {
        // Guaranteed synchronous commit during shutdown before releasing partitions:
        consumer.commitSync();
    } finally {
        consumer.close();
    }
}
```

### Fine-Grained Partial Batch Commits

For high-throughput large batches (`max.poll.records=500`), committing every 50 records limits the blast radius of duplicate processing upon crash:

```java
Map<TopicPartition, OffsetAndMetadata> currentOffsets = new HashMap<>();
int count = 0;

for (ConsumerRecord<String, String> record : records) {
    processRecord(record);
    currentOffsets.put(
        new TopicPartition(record.topic(), record.partition()),
        new OffsetAndMetadata(record.offset() + 1, "App Version 2.1")
    );

    if (++count % 50 == 0) {
        consumer.commitAsync(currentOffsets, null);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Function:** Persists the consumer group's reading position to the cluster.
- **Destination:** Stored in the internal compacted topic `__consumer_offsets`.
- **The +1 Rule:** The committed offset is always $\text{processed\_offset} + 1$.
- **`commitSync()`:** Blocks, retries transient errors, throws `CommitFailedException` on rebalance.
- **`commitAsync()`:** Non-blocking, maximum throughput, never retries to prevent out-of-order regressions.
- **Production Standard:** Combine `commitAsync()` in the poll loop with `commitSync()` in the `finally` close block.

**Common Follow-up Questions:**
- *"What causes `CommitFailedException` when calling `commitSync()`?"* → The time taken to process the batch exceeded `max.poll.interval.ms` (default 5 minutes), causing the Group Coordinator to consider the consumer dead and trigger a rebalance that revoked its partitions.
- *"How does Spring Kafka handle offset commits by default?"* → Spring Kafka uses an `AckMode` (default `BATCH` or `RECORD`), executing manual commits behind the scenes after the `@KafkaListener` method returns.
- *"Can a consumer commit arbitrary metadata alongside an offset?"* → Yes; `new OffsetAndMetadata(offset, "metadata-payload")` allows storing custom tracking data (such as processing timestamps or version tags) in `__consumer_offsets`.

**Red Flags (DO NOT Say):**
- ❌ *"The committed offset is the exact offset of the last processed record."* (It is $\text{offset} + 1$, indicating the *next* message to read).
- ❌ *"`commitAsync()` automatically retries until it succeeds."* (It never retries to avoid overwriting newer offsets with older ones).
- ❌ *"Offsets are stored in memory on the broker and lost on broker restart."* (Offsets are written as durable commit log messages to disk in `__consumer_offsets`).
