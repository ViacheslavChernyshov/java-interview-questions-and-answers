# Can You Read Messages from a Specific Partition?

---

## 🟢 Junior Level

**Yes, absolutely!** In Apache Kafka, a consumer can read directly from specific partitions using the **`consumer.assign()`** API instead of the standard `consumer.subscribe()`:

```
  Dining Hall Table Analogy:
  • `subscribe()` (General Seating): You sit anywhere the host directs you. 
    If a table breaks, the host moves you to another table (Dynamic Group Rebalance).
  • `assign()` (Reserved Private Table): You walk directly to Table 0 and sit down. 
    No host needed, no group coordination, but if you leave, nobody takes over your table.
```

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);

// Manually assign Partition 0 and Partition 2 of "orders-topic":
TopicPartition p0 = new TopicPartition("orders-topic", 0);
TopicPartition p2 = new TopicPartition("orders-topic", 2);

consumer.assign(List.of(p0, p2)); // Bypasses Consumer Group Rebalances!

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        System.out.printf("Partition: %d, Offset: %d, Value: %s%n", 
                          record.partition(), record.offset(), record.value());
    }
}
```

## 🟡 Middle Level

### `subscribe()` vs. `assign()` Comparison Matrix

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Feature                      │ `consumer.subscribe()`           │ `consumer.assign()`                              │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Consumer Group Protocol**  │ ✅ Full Group Coordination       │ ❌ **Bypasses Consumer Groups completely**       │
  │ **Automated Rebalancing**    │ ✅ Yes (Handles crashes/scaling) │ ❌ **No Rebalancing** (Zero failover if crashed) │
  │ **Offset Tracking**          │ Stored in `__consumer_offsets`   │ Manual offset management or local state          │
  │ **Mutual Exclusivity**       │ Cannot call with `assign()`      │ Cannot call with `subscribe()` (Throws Error)    │
  │ **Primary Target**           │ Standard Production Microservices│ Diagnostics, Replays, Pinned Caches, Stream Apps │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Spring Kafka Partition-Pinned Listeners

In Spring Boot, developers can bind specific partitions directly using `@KafkaListener`:

```java
@Component
public class PartitionSpecificOrderListener {

    // Dedicated listener reading exclusively from Partitions 0 and 1 starting from beginning:
    @KafkaListener(
        topicPartitions = @TopicPartition(
            topic = "orders-topic",
            partitions = {"0", "1"},
            partitionOffsets = @PartitionOffset(partition = "0", initialOffset = "0")
        )
    )
    public void listenToSpecificPartitions(ConsumerRecord<String, String> record) {
        log.info("Received from Partition {}: {}", record.partition(), record.value());
    }
}
```

### Primary Enterprise Use Cases for `assign()`

1. **Atomic Dual-Store Offsets:** Store partition offsets inside the same local relational database transaction alongside business records (`BEGIN; UPDATE accounts ...; UPDATE kafka_offsets SET offset=100 WHERE partition=0; COMMIT;`), achieving true Exactly-Once without distributed 2PC.
2. **Deterministic Local State Stores:** When building stateful stream applications (e.g. Kafka Streams or Flink), each worker task pins its local RocksDB embedded database to a dedicated partition (`Partition 0 ➔ RocksDB-0`).
3. **Emergency SRE Incident Diagnostic Replays:** SREs spin up a standalone diagnostic pod to seek to offset $N$ on a broken partition, replaying events to isolate bugs without disturbing the production consumer group.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Direct Answer:** Yes, via `consumer.assign(Collection<TopicPartition>)`.
- **No Rebalancing:** `assign()` completely disables dynamic group coordination and rebalancing.
- **Mutual Exclusivity:** Calling `subscribe()` and `assign()` on the same consumer throws `IllegalStateException`.
- **Failover Risk:** If an assigned consumer dies, no other consumer will automatically take over its partitions.
- **Primary Use Case:** Debugging, time-travel replays, local state stores, and transactional database offset storage.

**Common Follow-up Questions:**
- *"Can you use `consumer.seek()` with `assign()`?"* → Yes; `assign()` paired with `seek()` is the standard pattern for replaying records from specific offsets or timestamps on target partitions.
- *"Does a consumer using `assign()` require a `group.id`?"* → No; `group.id` is optional when using `assign()`, though setting it allows committing offsets to `__consumer_offsets` if desired.
- *"What happens if you invoke `consumer.subscribe()` after `consumer.assign()`?"* → The client throws `IllegalStateException: Subscription to topics, partitions and pattern are mutually exclusive`.

**Red Flags (DO NOT Say):**
- ❌ *"Reading from a specific partition is impossible in Kafka because consumer groups randomize everything."* (You can manually assign partitions using `assign()`).
- ❌ *"If a consumer with `assign()` crashes, Kafka automatically reassigns that partition to another pod."* (`assign()` has zero automated failover).
- ❌ *"You should use `assign()` for all standard production web microservices."* (`subscribe()` is standard for elasticity and automated crash recovery).
