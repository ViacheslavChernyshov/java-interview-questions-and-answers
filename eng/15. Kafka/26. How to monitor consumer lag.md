# How to Monitor Consumer Lag?

---

## 🟢 Junior Level

**Consumer Lag** is the numerical difference between the latest message written to a partition by producers (**Log End Offset - LEO**) and the last message committed by the consumer group (**Committed Offset**):

```
  Supermarket Checkout Line Analogy:
  • Log End Offset = Total number of customers who entered the checkout queue (e.g. 100).
  • Committed Offset = Total number of customers who have finished paying (e.g. 80).
  • Consumer Lag = 100 - 80 = 20 customers waiting in line!
  • If the line grows from 20 to 500, the cashier is falling severely behind!
```

$$\text{Consumer Lag} = \text{Log End Offset (LEO)} - \text{Committed Offset}$$

```bash
# Checking Consumer Lag via Kafka CLI:
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-billing-group

# Output:
# GROUP                 TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# order-billing-group   orders-topic   0          1000            1250            250
# order-billing-group   orders-topic   1          850             900             50
```

## 🟡 Middle Level

### Why Consumer Lag is the #1 Kafka SLA Metric

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Lag Trend Pattern            │ Root Cause & System State                                                       │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Lag $\approx 0$**          │ 🟢 **Healthy Real-Time Processing**: Consumer keeps up with producers.          │
  │ **Lag Spikes, then Drains**  │ 🟡 **Traffic Burst**: Normal momentary backlog; drained within minutes.         │
  │ **Lag Monotonically Rises**  │ 🔴 **Capacity Deficit**: Consumers are too slow; need horizontal pod scaling.   │
  │ **Lag Flat & Unchanging**    │ ☠️ **Consumer Dead**: Pod crashed, deadlocked, or stuck in rebalance storm!     │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Production Alerting Rules (PromQL)

```yaml
# Prometheus Alertmanager Rule:
groups:
- name: kafka.consumer.alerts
  rules:
  # Alert 1: Absolute Lag Threshold Exceeded
  - alert: KafkaConsumerLagHigh
    expr: sum(kafka_consumergroup_lag{topic="orders-topic"}) by (consumergroup) > 5000
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "Consumer group {{ $labels.consumergroup }} lag exceeded 5,000 for 5 minutes"

  # Alert 2: Consumer Dead / Zero Consumption with Growing Backlog
  - alert: KafkaConsumerStalled
    expr: |
      (rate(kafka_consumergroup_current_offset[5m]) == 0)
      and
      (kafka_consumergroup_lag > 100)
    for: 3m
    labels:
      severity: critical
    annotations:
      summary: "Consumer group {{ $labels.consumergroup }} has STALLED. Zero records consumed!"
```

### Dynamic Autoscaling with KEDA (Kubernetes Event-driven Autoscaling)

Instead of scaling on CPU, modern cloud-native Kubernetes workloads use **KEDA** to autoscale consumer pods based directly on real-time Consumer Lag:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-consumer-scaler
spec:
  scaleTargetRef:
    name: order-consumer-deployment
  minReplicaCount: 2
  maxReplicaCount: 12 # Cannot exceed topic partition count!
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka:9092
      consumerGroup: order-billing-group
      topic: orders-topic
      lagThreshold: "100" # Scales up 1 pod for every 100 messages of lag
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Numerical backlog of unread records ($\text{LEO} - \text{CommittedOffset}$).
- **Single Source of Truth:** Queried from partition log end offsets and `__consumer_offsets`.
- **Primary Tooling:** CLI (`kafka-consumer-groups.sh`), Prometheus Kafka Exporter, Grafana, and Micrometer.
- **KEDA Autoscaling:** Scales Kubernetes consumer pods dynamically based on lag thresholds.
- **Stall Detection:** Alert when lag is growing while consumption rate is zero.

**Common Follow-up Questions:**
- *"What is the difference between message lag (record count) and time lag (milliseconds)?"* → Record lag measures the number of unprocessed records (e.g. 5,000 records); time lag measures how old the oldest unprocessed record is (e.g. 15 minutes old). Tools like Lightbend Kafka Lag Exporter calculate time lag for strict SLAs.
- *"Why might consumer lag appear negative in some monitoring dashboards?"* → If a consumer commits an offset before the metadata scraper updates the broker LEO, temporary negative math can occur momentarily; proper scrapers clamp minimum lag to 0.
- *"How can you reduce consumer lag rapidly during a production emergency?"* → 1) Scale consumer pods up to the partition count ceiling; 2) Increase consumer batch sizes; 3) Route records to internal worker thread pools; 4) Temporarily increase partition counts.

**Red Flags (DO NOT Say):**
- ❌ *"Consumer lag is monitored by counting rows inside the client JVM memory heap."* (Lag is calculated from the broker's Log End Offset and committed offsets in `__consumer_offsets`).
- ❌ *"You can scale a consumer group from 10 pods to 50 pods to clear lag on a 10-partition topic."* (Excess consumers beyond the 10 partitions will sit completely idle).
- ❌ *"Consumer lag of 1,000 always means the system is failing."* (For a system processing 100,000 msg/sec, 1,000 lag is cleared in 10 milliseconds).
