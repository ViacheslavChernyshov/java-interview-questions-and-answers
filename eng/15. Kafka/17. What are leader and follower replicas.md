# What are Leader and Follower Replicas?

---

## 🟢 Junior Level

In Kafka's replication model, each partition has one **Leader Replica** and zero or more **Follower Replicas**:

```
  Master & Scribe Analogy:
  • Leader Replica = The Master Author (Takes orders, writes new chapters, speaks to customers).
  • Follower Replicas = The Scribes (Sit quietly in the back copying every page written by the Master).
  • If the Master falls ill ──► The fastest, most up-to-date Scribe is instantly promoted to Master!
```

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 👑 LEADER REPLICA                                       │ 📋 FOLLOWER REPLICA                                     │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Receives all Producer write requests.                 │ • Does NOT accept client write requests.                │
  │ • Serves standard Consumer read requests.               │ • Continuously pulls log batches from the Leader.       │
  │ • Tracks and maintains the In-Sync Replicas (ISR) list. │ • Stands by to take over as Leader during a crash.      │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

---

## 🟡 Middle Level

### The Leader Failover Lifecycle

```
  1. Normal State:
     Broker 1 (Leader: Offset 100) ──► Broker 2 (Follower: Offset 100 - in ISR)

  2. Broker 1 Crashes (Hardware / Network failure):
     • Kafka Controller detects missing heartbeat from Broker 1.
     • Controller queries the active ISR list and elects Broker 2 as the NEW LEADER.
     • Controller broadcasts updated metadata to all brokers in the cluster.

  3. Client Re-Routing:
     • Producers and Consumers receive a `NOT_LEADER_OR_FOLLOWER` error.
     • Clients refresh metadata and redirect traffic to Broker 2 in < 500ms!
```

## 🔴 Senior Level

### Availability vs. Consistency: `unclean.leader.election.enable`

What happens if the Leader crashes and **ALL remaining Followers are out-of-sync** (lagging behind)?

```
  Leader (Crashed):  Offset 100
  Follower A (Dead): Offset 100 (In ISR)
  Follower B (Alive):Offset 85  (Out of ISR - Lagging behind)
```

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ `unclean.leader.election.enable=false`   │ `unclean.leader.election.enable=true`            │
  │ (Default & Production Standard)          │ (Dangerous Availability Mode)                    │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ 🛡️ **Guarantees Zero Data Loss (CP)**    │ ⚠️ **Favors Availability over Consistency (AP)** │
  │ • Rejects electing Follower B as leader. │ • Promotes lagging Follower B to Leader.         │
  │ • Partition remains unavailable until    │ • Partition stays writeable, BUT:                │
  │   Broker 1 or Follower A recovers.       │   💥 **Messages 86..100 are PERMANENTLY LOST!**  │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Modern Follower Fetching (KIP-392: Cross-AZ Cloud Cost Optimization)

Historically, all consumer reads hit the Leader, causing high cross-Availability-Zone data transfer charges in AWS/GCP:
- **KIP-392 (Kafka 2.4+):** Consumers configure `client.rack=us-east-1b`.
- The consumer fetches data directly from the **In-Sync Follower located in the same local AZ**, eliminating cloud network egress costs while maintaining strict consistency.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Leader:** Single authoritative replica handling writes, reads, and High Watermark tracking.
- **Follower:** Passive replica fetching data to maintain in-sync standby status.
- **Failover:** The Controller promotes an in-sync follower to Leader when the active Leader dies.
- **`unclean.leader.election`:** Must remain `false` in production to prevent permanent data loss.
- **Follower Fetching:** KIP-392 allows reading from local AZ followers to eliminate cloud egress costs.

**Common Follow-up Questions:**
- *"How does a Follower replica know which messages to fetch?"* → Followers periodically send `FetchRequest` RPCs containing their current local Log End Offset (LEO); the Leader responds with subsequent unread batches.
- *"What is a Preferred Leader Election?"* → A background rebalancing optimization where Kafka restores leadership to the partition's primary designated broker (`preferred-replica`) after it recovers from a reboot.
- *"How long can a Follower lag behind the Leader before being kicked out of the ISR?"* → Configured via `replica.lag.time.max.ms` (default 30,000ms / 30 seconds).

**Red Flags (DO NOT Say):**
- ❌ *"Follower replicas accept writes from producers to balance cluster CPU load."* (Only Leaders accept writes).
- ❌ *"Setting `unclean.leader.election.enable=true` is recommended for financial payment pipelines."* (This destroys data consistency and silently drops transactions).
- ❌ *"Leader election is performed by voting among all consumers."* (Leader election is performed by the Kafka Controller broker / KRaft Quorum).
