# What is Retention Policy?

---

## 🟢 Junior Level

The **Retention Policy** in Apache Kafka defines the rules for how long or how large partition commit logs are preserved on disk before older data is automatically purged or compacted:

```
  Security DVR Analogy:
  • Time Retention (`retention.ms=7d`): The security camera system keeps video for 7 days. 
    On Day 8, the oldest day's footage is deleted automatically.
  • Size Retention (`retention.bytes=50GB`): If the hard disk reaches 50 GB per camera, 
    the oldest video files are deleted regardless of age.
  • Log Compaction (`cleanup.policy=compact`): The camera system only keeps the latest snapshot 
    of each room, overwriting previous frames when something moves.
```

```properties
# Topic-level retention settings:
retention.ms=604800000        # 7 days (Time-based retention)
retention.bytes=53687091200   # 50 GB per partition (Size-based retention)
cleanup.policy=delete         # Purge old segments (Default)
```

## 🟡 Middle Level

### The 3 Log Cleanup Policies

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Cleanup Policy               │ Operational Behavior & Target Data Type                                         │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`delete`** (Default)       │ Deletes entire closed log segments older than `retention.ms` or when partition  │
  │                              │ size exceeds `retention.bytes`. Used for event streams, logs, and metrics.      │
  │ **`compact`**                │ Retains only the latest value for each unique message key. Discards historical  │
  │                              │ overwrites. Used for user profile tables, account balances, and changelogs.     │
  │ **`compact,delete`**         │ Combines both: compacts keys while enforcing an absolute time-to-live ceiling.  │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Log Segment Unit Invariant (Senior Gotcha)

Senior distributed systems engineers know that **Kafka never deletes individual messages from disk**:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ THE LOG SEGMENT BOUNDARY RULE:                                                                │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ • Partitions are split into physical segment files on disk (`.log`, default 1 GB each).       │
  │ • Kafka evaluates retention strictly on **CLOSED SEGMENTS**, never individual records!        │
  │ • A segment is eligible for deletion ONLY when the HIGHEST timestamp in that segment is older│
  │   than `retention.ms`.                                                                        │
  │ • ⚠️ The **ACTIVE SEGMENT** (currently receiving writes) is NEVER deleted, regardless of age! │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

```
  Partition Directory on Broker Disk:
  ├── 00000000000000000000.log  (Max timestamp: 8 days ago) ──► 🗑️ PURGED by Retention!
  ├── 00000000000005829100.log  (Max timestamp: 4 days ago) ──► 🛡️ RETAINED
  └── 00000000000009940200.log  (ACTIVE SEGMENT - Open)      ──► 🛡️ RETAINED (Never deleted)
```

### Tombstone Deletion Protocol (`delete.retention.ms`)

To completely delete a key from a compacted topic, producers send a **Tombstone record** (`key != null`, `value == null`):
1. **Write:** The tombstone is appended to the partition log as a regular record.
2. **Compaction:** Log cleaner purges all older values for that key, keeping only the tombstone marker.
3. **Purge:** The tombstone marker itself is deleted once `delete.retention.ms` (default 24 hours / 86,400,000 ms) elapses, allowing slow consumers time to observe the deletion event.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Rules dictating log segment pruning based on time (`retention.ms`), size (`retention.bytes`), or key compaction (`cleanup.policy=compact`).
- **Segment Deletion:** Deletion operates at the granularity of **entire closed log segments**, never individual records.
- **Active Segment Rule:** The active log segment is never purged or deleted by retention policies.
- **Log Compaction:** Retains only the most recent record per message key.
- **Tombstone:** A null-value record that triggers permanent key removal after `delete.retention.ms`.

**Common Follow-up Questions:**
- *"What happens if a producer writes at a very low volume and the active segment never reaches `segment.bytes` (1 GB)?"* → The active segment will remain open indefinitely; to enforce time-based rolling of quiet topics, configure `segment.ms` (default 7 days) to force closing inactive segments.
- *"Can you set different retention policies for different topics in the same cluster?"* → Yes; retention properties configured at the topic level override broker-wide defaults (`log.retention.ms`).
- *"What is `min.cleanable.dirty.ratio` in log compaction?"* → The percentage of uncompacted (dirty) records required in a partition (default 0.5 / 50%) before the background Log Cleaner thread begins compacting the segment.

**Red Flags (DO NOT Say):**
- ❌ *"Kafka traverses every individual record on disk and deletes it the exact second it turns 7 days old."* (Kafka deletes entire closed segment files based on the newest timestamp in the file).
- ❌ *"Setting `retention.bytes=10GB` limits the total storage of the entire topic across all partitions."* (`retention.bytes` applies **per individual partition**, not globally across the whole topic).
- ❌ *"Log compaction immediately destroys old values the microsecond a new key arrives."* (Compaction is executed asynchronously in the background by `LogCleaner` threads).
