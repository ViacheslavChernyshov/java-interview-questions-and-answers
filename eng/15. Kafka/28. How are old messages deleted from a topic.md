# How are Old Messages Deleted from a Topic?

---

## 🟢 Junior Level

Kafka deletes old messages by pruning **entire closed Log Segment files from disk** rather than deleting individual records one by one:

```
  Office Filing Cabinet Analogy:
  • Each drawer (Partition) contains numbered folders (Log Segments: Folder 1, Folder 2, Folder 3).
  • When Folder 1 is full of old paperwork older than 7 days, the clerk removes and shreds 
    the ENTIRE Folder 1 in one motion!
  • The clerk never wastes time opening individual envelopes to shred single pages.
```

```
  Partition Directory on Disk (`/var/lib/kafka/data/orders-0/`):
  ├── 00000000000000000000.log        # Segment 0 (Offsets 0 - 500k) ──► 🗑️ DELETED (Older than retention)
  ├── 00000000000000000000.index
  ├── 00000000000000000000.timeindex
  ├── 00000000000000500001.log        # Segment 1 (Offsets 500k - 1M) ──► 🛡️ RETAINED
  ├── 00000000000000500001.index
  └── 00000000000001000001.log        # Active Segment (Currently Writing) ──► 🛡️ RETAINED (Never deleted)
```

## 🟡 Middle Level

### The 3 Stages of the Log Deletion Pipeline

```
  STAGE 1: Segment Rolling (Active ➔ Closed)
  The Active Segment closes and a new one is created when:
  • Size reaches `segment.bytes` (Default: 1 GB), OR
  • Time reaches `segment.ms` (Default: 7 days).

  STAGE 2: Retention Pruning Scan
  Every `log.retention.check.interval.ms` (Default: 5 minutes), the `LogManager` background thread:
  • Evaluates the NEWEST (maximum) timestamp in each closed segment file.
  • If `max_timestamp < (Current_Time - retention.ms)` ──► Marks segment as `.deleted`.

  STAGE 3: Physical OS Disk Removal
  • Waits for `log.segment.delete.delay.ms` (Default: 60 seconds) to ensure any active consumer 
    reading the file completes its I/O transfer.
  • Calls the OS `unlink()` syscall to free the physical disk space.
```

## 🔴 Senior Level

### Under the Hood: Log Segment Filesystem Triplet

Every segment on disk consists of four associated files sharing the identical base offset:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ File Extension               │ Contents & Role                                                                 │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`.log`**                   │ Binary stream of compressed record batches with payload headers.                │
  │ **`.index`**                 │ Sparse memory-mapped index: Maps Logical Offset ➔ Physical Byte Position.       │
  │ **`.timeindex`**             │ Timestamp index: Maps Event Timestamp ➔ Logical Offset (for time seeks).       │
  │ **`.txnindex`** (Optional)   │ Transaction index: Tracks aborted transaction ranges for `read_committed`.     │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### The "Quiet Topic" Disk Leak Trap (Why Size Never Shrinks)

```
  ❌ THE TRAP (Low-Throughput Inactive Topic):
  • A microservice publishes 1 event per day to `audit-events` (1 KB/day).
  • `segment.bytes=1GB` (Default).
  • `retention.ms=7 days`.
  • At 1 KB/day, the active segment takes **2,700 YEARS** to reach 1 GB!
  • Because the active segment NEVER rolls and is NEVER deleted, records from 3 years ago 
    are STILL retained on disk!

  ✅ SOLUTION:
  • Configure `segment.ms=86400000` (Force active segment to roll every 24 hours).
  • Once rolled, closed 24-hour segments become eligible for retention purging!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Granularity:** Deletion occurs at the **Log Segment level** (typically 1 GB files), never per message.
- **Timestamp Evaluation:** Pruned based on the **maximum timestamp** in the segment file (.timeindex).
- **Active Segment Exemption:** The active segment currently receiving writes is never deleted.
- **Roll Triggers:** Segments roll based on `segment.bytes` (1 GB) or `segment.ms` (7 days).
- **File Types:** Each segment consists of `.log`, `.index`, and `.timeindex`.

**Common Follow-up Questions:**
- *"What happens if a consumer is actively reading a segment when retention deletes it?"* → The file is renamed to `<offset>.log.deleted` and held open; after `log.segment.delete.delay.ms` (60s) and once open file descriptors close, the OS deletes the file.
- *"How does size-based retention (`retention.bytes`) decide which segment to delete first?"* → It deletes the oldest closed segment first (lowest base offset), repeating until total partition size drops below `retention.bytes`.
- *"Can you immediately reclaim disk space in emergency out-of-disk situations?"* → Yes; decrease topic `retention.ms` or `retention.bytes` via `kafka-configs.sh` and set `log.segment.delete.delay.ms=1000` to trigger immediate segment purge.

**Red Flags (DO NOT Say):**
- ❌ *"Kafka rewrites the `.log` file every time a single record expires."* (Rewriting files would destroy disk I/O performance; Kafka unlinks entire segment files).
- ❌ *"The active segment is deleted if the topic is older than `retention.ms`."* (The active segment is protected from deletion).
- ❌ *"Old messages are moved to a temporary swap partition before deletion."* (Files are marked `.deleted` and unlinked directly by the OS).
