# What is Consumer Group?

---

## 🟢 Junior Level

A **Consumer Group** is a set of consumers configured with the same `group.id` that cooperatively share the work of reading messages from one or more subscribed Kafka topics:

```
  Warehouse Workers Analogy:
  • Topic = A warehouse with 4 delivery bays (Partitions 0, 1, 2, 3).
  • Consumer Group = A team of 4 loaders (`group.id="order-processors"`).
  • Each worker is assigned to unload exactly 1 bay so they never bump into each other 
    or duplicate work!
```

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ THE CONSUMER GROUP INVARIANT:                                                   │
  │ • Each individual partition is assigned to EXACTLY ONE consumer within a group! │
  │ • One consumer can read from MULTIPLE partitions.                               │
  │ • If there are more consumers than partitions, the extra consumers sit IDLE.   │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```java
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "billing-service-group"); // Defines group membership
props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("order-events"));
```

## 🟡 Middle Level

### The Duality: Queue vs. Publish-Subscribe

By adjusting `group.id`, Kafka seamlessly switches between classic messaging patterns:

```
                               ┌───────────────────────────────┐
                               │     TOPIC: "order-events"     │
                               │   (Partition 0, 1, 2, 3)      │
                               └───────┬───────────────┬───────┘
                                       │               │
                 ┌─────────────────────┘               └─────────────────────┐
                 ▼                                                           ▼
  ┌──────────────────────────────┐                            ┌──────────────────────────────┐
  │ CONSUMER GROUP A             │                            │ CONSUMER GROUP B             │
  │ `group.id="fraud-service"`   │                            │ `group.id="email-service"`   │
  │ • Consumer 1 (P0, P1)        │                            │ • Consumer 1 (P0, P1, P2, P3)│
  │ • Consumer 2 (P2, P3)        │                            │                              │
  │ ➔ Receives 100% of all events│                            │ ➔ Receives 100% of all events│
  └──────────────────────────────┘                            └──────────────────────────────┘
```

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Messaging Pattern            │ Kafka Configuration          │ Behavior                                         │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Point-to-Point Queue**     │ All consumers share same ID  │ Partitions divided across instances; each record │
  │                              │ (`group.id="order-workers"`) │ processed by exactly 1 consumer instance.        │
  │ **Publish-Subscribe**        │ Each service has a unique ID │ Every consumer group gets a full copy of every   │
  │                              │ (`group.id="billing"`, ...)  │ record in the topic independently.               │
  └──────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Under the Hood: Group Coordinator & Group Leader Protocol

```
  1. Finding Coordinator:
     Consumer calculates `Math.abs("my-group".hashCode()) % 50` ──► Finds partition in `__consumer_offsets`.
     The broker hosting the Leader replica of that partition becomes the **Group Coordinator**.

  2. JoinGroup Phase:
     All consumers send `JoinGroup` RPCs to the Group Coordinator.
     The Coordinator elects the first responding consumer as the **Group Leader**.

  3. SyncGroup Phase:
     • The Coordinator sends partition metadata to the Group Leader.
     • The Group Leader runs the client-side partition assignment algorithm 
       (`RangeAssignor`, `CooperativeStickyAssignor`) and returns the plan to the Coordinator.
     • The Coordinator responds to each consumer with its assigned partition subset.
```

### Partition Assignment Strategies

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Strategy                     │ Execution Model & Trade-Off                                                     │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`RangeAssignor`** (Def)    │ Assigns contiguous ranges per topic. Can cause skew when subscribing to         │
  │                              │ multiple topics with identical partition counts.                                │
  │ **`RoundRobinAssignor`**     │ Interleaves partitions across all consumers uniformly.                          │
  │ **`CooperativeSticky`**      │ (KIP-429) **Incremental rebalancing**: Only revokes reassigned partitions;     │
  │                              │ unimpacted consumers continue processing without "Stop-the-World" pauses!       │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Group of consumers sharing the partitions of subscribed topics under a common `group.id`.
- **Partition Ratio Rule:** 1 partition = max 1 consumer per group; extra consumers remain idle.
- **Pattern Duality:** Same `group.id` = Point-to-Point Queue; Distinct `group.id`s = Pub/Sub Broadcast.
- **Group Coordinator:** Broker managing membership and offset storage in `__consumer_offsets`.
- **Modern Rebalancing:** Use `CooperativeStickyAssignor` to avoid Stop-the-World group rebalances.

**Common Follow-up Questions:**
- *"What happens if a consumer in a group crashes?"* → The Group Coordinator detects a missed heartbeat (`session.timeout.ms`), marks the consumer dead, and triggers a group **rebalance** to reassign its partitions to remaining active members.
- *"Where does Kafka store committed offsets for a Consumer Group?"* → In an internal, highly compacted system topic named **`__consumer_offsets`** (50 partitions by default).
- *"Can two different consumers in the same group read from the same partition at the same time?"* → Never; this is an absolute architectural invariant in Kafka to preserve sequential consumption.

**Red Flags (DO NOT Say):**
- ❌ *"Two consumers with the same `group.id` can read from Partition 0 simultaneously to speed up processing."* (Strictly prohibited by Kafka protocol).
- ❌ *"Committed offsets are stored in ZooKeeper in modern Kafka."* (ZooKeeper offset storage was deprecated years ago; offsets are stored in `__consumer_offsets`).
- ❌ *"A Consumer Group can only subscribe to a single topic."* (A Consumer Group can subscribe to multiple topics simultaneously using regex patterns or list subscriptions).
