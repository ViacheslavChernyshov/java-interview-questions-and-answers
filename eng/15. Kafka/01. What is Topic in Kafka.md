# What is Topic in Kafka?

---

## 🟢 Junior Level

A **Topic** in Apache Kafka is a named logical category, feed, or stream to which producers publish records and from which consumers read data:

```
  Television Channel Analogy:
  • Topic = A specific TV channel (e.g. "orders-stream", "user-events").
  • Producers = News anchors broadcasting video segments to the channel.
  • Consumers = Viewers tuning their TV sets to watch the stream.
  • Unlike traditional queues, multiple independent viewers can watch the same channel 
    at different times and speeds without consuming or deleting the broadcast!
```

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🐰 Traditional Queue (RabbitMQ / SQS)                   │ 📨 Apache Kafka Topic                                   │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • **Destructive:** Message is deleted once read/acked.  │ • **Persistent:** Append-only immutable log on disk.    │
  │ • 1 Consumer Group typically deletes the item.          │ • Many independent Consumer Groups read the same stream.│
  │ • Cannot replay historical events.                      │ • Replayable from any historical offset (Time-travel).  │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```bash
# Creating a topic using the Kafka CLI:
kafka-topics.sh --create \
  --bootstrap-server localhost:9092 \
  --topic order-events \
  --partitions 6 \
  --replication-factor 3
```

## 🟡 Middle Level

### Logical vs. Physical Architecture

```
  LOGICAL VIEW:
  Topic: "payment-events"

  PHYSICAL DISK STORAGE (Distributed across Cluster):
  Broker 1 ──► [Partition 0 Log Segments: .log, .index, .timeindex]
  Broker 2 ──► [Partition 1 Log Segments: .log, .index, .timeindex]
  Broker 3 ──► [Partition 2 Log Segments: .log, .index, .timeindex]
```

### Topic Cleanup Policies

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Cleanup Policy               │ Mechanism                        │ Production Use Case                              │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`delete`** (Default)       │ Purges segments after age        │ Audit logs, telemetry metrics, clickstreams.     │
  │                              │ (`retention.ms=604800000` / 7d). │                                                  │
  │ **`compact`**                │ Retains only the latest value    │ User profile state, account balance snapshots,   │
  │                              │ for each unique message key.     │ Kafka Streams KTable changelogs.                 │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Fundamental Ordering Rule

- **Within a Single Partition:** Strict deterministic FIFO ordering is guaranteed.
- **Across the Entire Topic ($>1$ Partitions):** There is **no global ordering guarantee**; records across different partitions are consumed concurrently.

## 🔴 Senior Level

### Under the Hood: Log Segment Storage & Zero-Copy I/O

On the broker filesystem (e.g. `/var/lib/kafka/data/order-events-0/`), each partition is split into immutable **Log Segments** (default 1 GB each):

```
  order-events-0/
  ├── 00000000000000000000.log        # Raw sequential binary record batch payload
  ├── 00000000000000000000.index      # Sparse memory-mapped index (Offset ➔ Physical File Byte Position)
  ├── 00000000000000000000.timeindex  # Timestamp-to-Offset index for time-based lookups
  └── leader-epoch-checkpoint         # Prevents log divergence during leader elections
```

1. **Sequential Disk I/O:** Kafka achieves multi-gigabyte throughput because appending to a segment file is a purely sequential disk write ($>600\text{ MB/s}$ on NVMe/SATA), bypassing expensive random disk seeks.
2. **OS PageCache & Zero-Copy (`sendfile`):** When consumers fetch data, the Linux kernel transfers bytes directly from OS PageCache to the network socket via the `sendfile()` syscall, bypassing JVM heap memory allocations entirely.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Logical stream name backed by one or more physical distributed commit log partitions.
- **Non-Destructive:** Messages are retained on disk for `retention.ms` regardless of consumer reads.
- **Ordering Guarantee:** Strict FIFO ordering is guaranteed **only within a single partition**, never globally across multiple partitions.
- **Cleanup Policies:** `delete` (time/size retention) vs. `compact` (keeps latest record per key).
- **Zero-Copy Engine:** Leverages Linux PageCache and `sendfile()` for high-throughput reads without JVM heap overhead.

**Common Follow-up Questions:**
- *"How does Kafka differ from RabbitMQ or ActiveMQ?"* → Traditional brokers push messages to consumers and delete them upon acknowledgment; Kafka is an append-only log where consumers pull records and track their own read position (offset).
- *"Can you change the number of partitions of an existing topic?"* → You can increase partitions (`kafka-topics --alter --partitions 10`), but you can **never decrease** partitions.
- *"What happens to message key hashing when you increase topic partitions?"* → Increasing partitions breaks the hash modulo formula ($hash(key) \pmod N$), causing new messages with existing keys to route to different partitions!

**Red Flags (DO NOT Say):**
- ❌ *"Kafka guarantees global FIFO ordering across all topic partitions simultaneously."* (Ordering is strictly per-partition).
- ❌ *"A message is deleted from the topic as soon as a consumer reads it."* (Messages persist according to retention configuration).
- ❌ *"You can easily decrease topic partitions from 10 to 4 when traffic drops."* (Kafka does not support decreasing partitions).
