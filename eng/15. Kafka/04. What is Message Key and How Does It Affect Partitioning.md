# What is Message Key and How Does It Affect Partitioning?

---

## 🟢 Junior Level

A **Message Key** is an optional metadata attribute attached to a Kafka `ProducerRecord` that acts as the routing identifier for determining which partition receives the message:

```
  Airport Flight Boarding Analogy:
  • Flight Number = Message Key (`key="BA-104"`).
  • Gate Number = Partition (`Partition 2`).
  • All passengers for flight BA-104 board at Gate 2 in strict arrival order.
  • Passengers for flight AA-200 board at Gate 0.
```

```java
// Producing an order event with a deterministic routing key:
ProducerRecord<String, String> record = 
    new ProducerRecord<>("orders-topic", "user-8492", "{\"status\":\"PAID\"}");
//                         topic             key                 value
```

```
  2 Primary Rules:
  1. Same Key = Same Partition: All events for `user-8492` land in the same partition.
  2. Strict Causal Ordering: Preserves sequential order (Created ➔ Paid ➔ Shipped) for that key.
```

## 🟡 Middle Level

### The Two Critical Roles of a Message Key

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Architectural Role              │ Purpose & Behavior                                                              │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Deterministic Routing**    │ Hashes the key via `MurmurHash2` to guarantee all records for an aggregate root │
  │                                 │ (e.g. `orderId`, `accountId`) land on the exact same partition.                 │
  │ **2. Log Compaction**           │ In topics configured with `cleanup.policy=compact`, Kafka retains only the      │
  │                                 │ latest value for each unique key, deleting older historical updates.            │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Key Selection Matrix

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Candidate Key        │ Distribution Quality         │ Recommended Production Use Case                  │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ `orderId` / `uuid`   │ 🟢 **High Uniformity**       │ E-commerce lifecycle events, payment gateways.   │
  │ `userId`             │ 🟢 **High Uniformity**       │ User activity tracking, session event streams.   │
  │ `null` (No Key)      │ 🟢 **Sticky Batching**       │ High-throughput telemetry where order is moot.   │
  │ `countryCode` (EU)   │ 🔴 **Severe Skew (Anti-Pat)**│ ⚠️ Creates massive Hot Partitions on large tiers.│
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Partition Mutation Invariant (Hash Modulo Breakage)

Senior distributed systems engineers know that changing the partition count of an active topic permanently corrupts key-based ordering:

```
  Initial State (3 Partitions):
  MurmurHash2("user-123") = 100
  100 % 3 = Partition 1  ──► All events (v1, v2, v3) wrote to Partition 1.

  Topic Altered to 4 Partitions:
  MurmurHash2("user-123") = 100
  100 % 4 = Partition 0  ──► New event (v4) writes to Partition 0!

  💥 RESULT:
  • Consumer reading Partition 1 processes (v1, v2, v3).
  • Consumer reading Partition 0 processes (v4) CONCURRENTLY!
  • Causal ordering for `user-123` is completely broken!
```

### Tombstone Records in Log Compaction

To delete a key from a compacted topic, producers send a **Tombstone record** (`key != null`, `value == null`):
- Kafka writes the tombstone record to the partition log.
- During the next log cleaner compaction cycle, Kafka purges all historical values for that key and eventually removes the tombstone after `delete.retention.ms` (default 24 hours).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Role:** Dictates partition assignment via `MurmurHash2(key) % numPartitions`.
- **Causal Consistency:** All events with identical keys are guaranteed to be processed in strict sequential order.
- **Log Compaction Key:** Compacted topics use the key as the primary key to maintain current state snapshots.
- **The Partition Change Trap:** Increasing topic partitions alters modulo arithmetic and breaks sequential ordering for existing keys.
- **Tombstone:** A record with a non-null key and a `null` value instructs Kafka to delete that key during compaction.

**Common Follow-up Questions:**
- *"What happens if a message has no key (`key == null`)?"* → Kafka uses the Sticky Partitioner to fill a batch for one partition before rotating to the next, maximizing network compression.
- *"How do you prevent hot partition skew when a single customer generates millions of messages?"* → Use **Key Salting**: append a random modulo suffix to the key (e.g. `customerId + "_" + random(1..4)`).
- *"Can you use complex objects (JSON / Protobuf) as message keys?"* → Yes, but any modification to field order or serialization formats will produce different byte arrays and change the hash destination!

**Red Flags (DO NOT Say):**
- ❌ *"Kafka message keys are required for every message published."* (Keys are optional; `key=null` enables high-throughput sticky batching).
- ❌ *"Kafka automatically rebalances historical messages across partitions when you increase partition count."* (Kafka never moves existing log segments; only new messages follow the new hash calculation).
- ❌ *"Using a hardcoded static string like `key='EVENT'` is good for grouping."* (This forces 100% of topic traffic onto a single partition, bottlenecking the cluster).
