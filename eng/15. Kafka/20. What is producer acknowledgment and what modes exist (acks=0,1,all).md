# What is producer acknowledgment and what modes exist?

## 🟢 Junior Level

**Producer Acknowledgment (acks)** is a producer configuration parameter that determines how many acknowledgments from broker replicas the producer must receive to consider a message write successful. It is the main lever for balancing **Durability** vs **Latency**.

| Mode | Acknowledgment | Speed | Reliability |
|---|---|---|---|
| `acks=0` | None (Fire & Forget) | Maximum | Zero |
| `acks=1` | Leader replica only | Medium | Medium |
| `acks=all` (`-1`) | Leader + all ISR replicas | Low | Maximum |

### Simple analogy

- **acks=0** — sent a letter and walked away without checking if it arrived
- **acks=1** — sent a letter and waited for the post office to accept it
- **acks=all** — sent a letter and waited for confirmation that copies are stored in multiple offices

---

## 🟡 Middle Level

### Detailed breakdown of ACKS modes

#### acks = 0 (Fire and Forget)
The producer does not wait for any acknowledgment from the broker. The message is considered successfully sent as soon as it hits the network buffer.
- **Latency**: Minimal.
- **Reliability**: Zero. If the broker crashed or a network failure occurred — data is lost forever.
- **Use Case**: Log or metrics collection where 1-2% data loss is acceptable.

#### acks = 1 (Leader Only)
The producer waits for acknowledgment only from the partition Leader. The Leader writes data to its local log and immediately responds to the producer.
- **Latency**: Medium.
- **Reliability**: Medium. If the Leader crashes **right after** responding to the producer, but **before** Followers replicated the data — it will be lost.
- **Use Case**: General business events not requiring extreme reliability.
- *Note: Default before Kafka 3.0. Starting from Kafka 3.0 (KIP-316) default changed to acks=all.*

#### acks = all (or -1)
The producer waits for acknowledgment from the Leader and **all in-sync replicas (ISR)**.
- **Latency**: Maximum (limited by the slowest replica in ISR).
- **Reliability**: Maximum. Data is guaranteed to be stored on multiple nodes.
- **Use Case**: Financial transactions, critical data.

### Connection with min.insync.replicas

The `acks=all` parameter alone does not guarantee writing to multiple nodes. If only the Leader remains in ISR, `acks=all` effectively becomes `acks=1`. To guarantee real redundancy, you need `min.insync.replicas >= 2`.

```java
// Producer configuration for maximum reliability
Properties props = new Properties();
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
// At topic level: min.insync.replicas=2, replication.factor=3
```

## 🔴 Senior Level

### Impact on Retries

With `acks=1` or `all`, the producer may receive errors (e.g., `NotLeaderForPartitionException`). In this case, it will automatically retry (`retries`). With `acks=0`, retries are impossible since the producer does not know about the error.

### acks=all + min.insync.replicas: Reliability Formula

```
Guarantee = acks=all + min.insync.replicas >= 2 + replication.factor >= 3
```

If ISR < min.insync.replicas → `NotEnoughReplicasException`, write is rejected. This protects from silent data loss but reduces availability.

### Production Best Practices

| Scenario | acks | min.insync.replicas | replication.factor |
|---|---|---|---|
| Logs/metrics | 0 or 1 | 1 | 2 |
| Business events | 1 | 1 | 3 |
| Finance/critical | all | 2 | 3 |
| Audit/compliance | all | 2 | 3 + rack awareness |

### Monitoring

```
# Key producer metrics
kafka.producer:type=producer-metrics,client-id=*
  record-error-rate          # Write errors → if growing, check ISR
  request-latency-avg        # Average latency → compare acks=1 vs acks=all
  record-retry-rate          # Retry rate → if high, cluster issues
```

### Senior Summary

- `acks=0`: Speed at any cost.
- `acks=1`: Balance (dangerous on leader failure).
- `acks=all`: Maximum reliability, but higher latency and lower availability.
- Always use `acks=all` with `min.insync.replicas >= 2` for critical data.
- `acks=all` protects from data loss but not from duplicates (idempotency needed).

## 🎯 Interview Cheat Sheet

**Must know:**
- `acks=0` — fire and forget, minimum latency, zero reliability
- `acks=1` — leader acknowledgment, medium reliability; data lost on leader failure
- `acks=all` — acknowledgment from all ISR, maximum reliability; higher latency
- `acks=all` without `min.insync.replicas>=2` = `acks=1` if ISR=1
- Default changed: before Kafka 3.0 — acks=1; from Kafka 3.0 (KIP-316) — acks=all
- Retries possible with acks=1/all; with acks=0 producer does not know about errors
- `acks=all` protects from loss but not from duplicates (idempotency needed)

**Common follow-up questions:**
- *Why is acks=all without min.insync.replicas insufficient?* — If ISR=1, acks=all = acks=1
- *What is the default in Kafka 3.0+?* — acks=all (KIP-316), previously acks=1
- *What happens with acks=all and ISR < min.insync.replicas?* — NotEnoughReplicasException

**Red flags (do NOT say):**
- "acks=0 for production data" — zero delivery guarantee
- "acks=all guarantees write to multiple nodes without min.insync.replicas" — if ISR=1, only one
- "acks=0 supports retries" — producer does not know about errors
- "acks=all protects from duplicates" — no, idempotency needed
