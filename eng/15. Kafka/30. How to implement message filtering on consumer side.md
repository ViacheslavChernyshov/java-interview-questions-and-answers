# How to Implement Message Filtering on Consumer Side?

---

## 🟢 Junior Level

Unlike traditional message brokers (such as RabbitMQ or JMS selectors), **Apache Kafka brokers do not filter messages on the server side**. All records are streamed to consumers, and filtering is executed entirely on the client side:

```
  Dumb Broker / Smart Consumer Philosophy:
  • Traditional JMS/RabbitMQ (Smart Broker): Broker inspects message headers and routes 
    to specific queues (High broker CPU load; ruins zero-copy throughput).
  • Apache Kafka (Smart Consumer): Broker serves raw sequential bytes at line rate via Zero-Copy; 
    the consumer decides which messages to process and which to skip!
```

```java
// 1. Basic In-Code Consumer Filtering:
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        if (shouldProcess(record)) {
            processBusinessLogic(record.value());
        }
        // Skipped records still have their offsets committed to maintain stream progress!
    }
    consumer.commitSync();
}
```

## 🟡 Middle Level

### Spring Kafka Declarative Filtering: `RecordFilterStrategy`

In Spring Boot, instead of polluting business methods with `if/else` checks, configure a **`RecordFilterStrategy`**:

```java
@Configuration
public class KafkaConsumerFilterConfig {

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, OrderEvent> filteredKafkaListenerContainerFactory(
            ConsumerFactory<String, OrderEvent> consumerFactory) {

        var factory = new ConcurrentKafkaListenerContainerFactory<String, OrderEvent>();
        factory.setConsumerFactory(consumerFactory);

        // Discards records where return value is TRUE; passes records when FALSE:
        factory.setRecordFilterStrategy(record -> {
            OrderEvent order = record.value();
            // Filter out small test transactions or cancelled orders:
            return order == null || "CANCELLED".equals(order.getStatus()) || order.getAmount() < 10.0;
        });

        // Automatically acknowledges/commits the offset of discarded records:
        factory.setAckDiscarded(true);

        return factory;
    }
}
```

```java
@Service
public class HighValueOrderListener {

    // Only receives pre-filtered high-value orders!
    @KafkaListener(
        topics = "orders-topic", 
        groupId = "high-value-group",
        containerFactory = "filteredKafkaListenerContainerFactory"
    )
    public void handleFilteredOrder(OrderEvent order) {
        log.info("Processing VIP order: {}", order.getOrderId());
    }
}
```

## 🔴 Senior Level

### High-Performance Header-Based Filtering (Pre-Deserialization Bypass)

Parsing heavy JSON or Avro payloads consumes significant CPU. Senior engineers filter based on **Kafka Record Headers** *before* deserializing the body:

```java
public class HeaderFilteringInterceptor<K, V> implements ConsumerInterceptor<K, V> {

    @Override
    public ConsumerRecords<K, V> onConsume(ConsumerRecords<K, V> records) {
        Map<TopicPartition, List<ConsumerRecord<K, V>>> filteredMap = new HashMap<>();

        for (ConsumerRecord<K, V> record : records) {
            Header tenantHeader = record.headers().lastHeader("X-Tenant-Id");
            
            // Fast byte check before object deserialization:
            if (tenantHeader != null && "EU_TENANT".equals(new String(tenantHeader.value(), StandardCharsets.UTF_8))) {
                filteredMap.computeIfAbsent(
                    new TopicPartition(record.topic(), record.partition()), 
                    tp -> new ArrayList<>()
                ).add(record);
            }
        }
        return new ConsumerRecords<>(filteredMap);
    }

    @Override public void onCommit(Map<TopicPartition, OffsetAndMetadata> offsets) {}
    @Override public void close() {}
    @Override public void configure(Map<String, ?> configs) {}
}
```

### Pre-Filtering Topologies (Kafka Streams & ksqlDB)

When multiple downstream microservices only need specific sub-streams, use an upstream **Kafka Streams filter topology**:

```java
@Bean
public KStream<String, OrderEvent> buildFilterPipeline(StreamsBuilder builder) {
    KStream<String, OrderEvent> rawStream = builder.stream("raw-orders-stream");

    // Creates dedicated sub-topics, eliminating consumer network waste:
    rawStream.filter((k, v) -> v.getAmount() >= 1000.0)
             .to("vip-orders-topic");

    rawStream.filter((k, v) -> "FRAUD_SUSPECTED".equals(v.getStatus()))
             .to("fraud-review-topic");

    return rawStream;
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Zero Broker Filtering:** Kafka brokers do not filter messages on the server; all filtering is performed client-side.
- **Dumb Broker Architecture:** Offloading filtering preserves broker CPU and enables Linux zero-copy `sendfile` speed.
- **Offset Progression:** Skipped/filtered records **must still have their offsets committed** to advance the consumer's position.
- **Spring Filter Strategy:** `RecordFilterStrategy` with `setAckDiscarded(true)` provides clean declarative filtering.
- **Header Optimization:** Filter using record headers to avoid expensive JSON/Avro payload deserialization.

**Common Follow-up Questions:**
- *"Why didn't the creators of Kafka include server-side JMS-style message selectors?"* → Server-side filtering requires the broker to uncompress, deserialize, and inspect every record header/payload, destroying broker throughput and preventing zero-copy network caching.
- *"What happens to the committed offset when `RecordFilterStrategy` discards a message in Spring Kafka?"* → When `ackDiscarded=true`, Spring acknowledges the discarded message and commits its offset, ensuring the consumer does not get stuck.
- *"When should you filter in the consumer versus creating separate topics via Kafka Streams?"* → If 90% of topic traffic is discarded by multiple consumers, use Kafka Streams to route data into dedicated sub-topics to save consumer network bandwidth.

**Red Flags (DO NOT Say):**
- ❌ *"You can configure the Kafka broker to only send messages matching a SQL `WHERE` clause to specific consumers."* (Brokers stream raw partition bytes without inspection).
- ❌ *"Discarding a message means its offset is ignored and not committed."* (Offset must be committed; otherwise, the consumer will re-read the discarded record upon restart).
- ❌ *"Filtering on the consumer creates memory leaks in Kafka brokers."* (Filtering is purely local to client memory and has zero effect on the broker).
