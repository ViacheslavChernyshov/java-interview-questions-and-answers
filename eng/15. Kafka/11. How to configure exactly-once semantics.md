# How to Configure Exactly-Once Semantics?

---

## 🟢 Junior Level

**Exactly-Once Semantics (EOS)** in Kafka guarantees that across a "Consume ➔ Process ➔ Produce" stream pipeline, every input message is processed and its output/offsets are committed **exactly once**, even in the event of producer, broker, or consumer crashes:

```
  Bank Transfer Analogy:
  • An atomic transaction moves $100 from Account A to Account B.
  • Both the withdrawal (Input Topic offset commit) and the deposit (Output Topic write) 
    commit together atomically.
  • If the server crashes mid-flight, the entire transaction aborts, leaving ZERO duplicate entries.
```

```
  3 Essential Configuration Pillars:
  1. Producer: `enable.idempotence=true`, `acks=all`, `transactional.id="unique-tx-id"`
  2. Consumer: `isolation.level=read_committed`, `enable.auto.commit=false`
  3. Broker: `transaction.state.log.replication.factor=3`, `transaction.state.log.min.isr=2`
```

## 🟡 Middle Level

### The Canonical "Consume-Process-Produce" Transaction API

In pure Java client code, offsets are committed **inside the producer's transaction** via `sendOffsetsToTransaction`:

```java
Properties prodProps = new Properties();
prodProps.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
prodProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
prodProps.put(ProducerConfig.ACKS_CONFIG, "all");
prodProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-stream-processor-01");

Properties consProps = new Properties();
consProps.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
consProps.put(ConsumerConfig.GROUP_ID_CONFIG, "order-group");
consProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
consProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed"); // Crucial!

KafkaProducer<String, String> producer = new KafkaProducer<>(prodProps);
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consProps);

// 1. One-time transaction initialization (Registers with Transaction Coordinator):
producer.initTransactions();
consumer.subscribe(List.of("incoming-orders"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    if (records.isEmpty()) continue;

    try {
        // 2. Begin Atomic Transaction:
        producer.beginTransaction();

        for (ConsumerRecord<String, String> record : records) {
            String processedValue = enrichOrder(record.value());
            producer.send(new ProducerRecord<>("processed-orders", record.key(), processedValue));
        }

        // 3. Attach consumer group offsets to this exact transaction:
        Map<TopicPartition, OffsetAndMetadata> offsetsToCommit = calculateOffsets(records);
        producer.sendOffsetsToTransaction(offsetsToCommit, consumer.groupMetadata());

        // 4. Atomic Two-Phase Commit:
        producer.commitTransaction();

    } catch (ProducerFencedException | InvalidProducerEpochException e) {
        log.error("Fatal transaction error. Another producer instance took over!", e);
        producer.close();
        break;
    } catch (KafkaException e) {
        log.warn("Transient error. Aborting transaction and re-polling...", e);
        producer.abortTransaction();
    }
}
```

## 🔴 Senior Level

### Under the Hood: The 2PC Transaction Coordinator & Zombie Fencing

```
  [Producer] ──► 1. InitTransactions (Registers transactional.id)
                      │
                      ▼
  [Transaction Coordinator Broker] (Backing topic: `__transaction_state`)
  • Bumps `producer.epoch` to fence out older crashed/zombie producer instances!
  • Writes `BEGIN` marker to `__transaction_state`.
                      │
  [Producer Writes] ──► 2. Writes data records to target topic partitions.
                      │
  [Producer Commits] ──► 3. Writes `PREPARE_COMMIT` marker.
                      │
  [Coordinator] ──► 4. Writes `COMMIT MARKER` into all affected partition logs!
                      │
  [Consumer] ──► 5. `read_committed` reader encounters Commit Marker ──► Emits records!
```

### Spring Boot 3.x / Spring Kafka Integration

In modern Spring Boot applications, configure `KafkaTransactionManager`:

```yaml
spring:
  kafka:
    producer:
      acks: all
      transaction-id-prefix: tx-order-
      properties:
        enable.idempotence: true
    consumer:
      enable-auto-commit: false
      isolation-level: read_committed
```

```java
@Service
@RequiredArgsConstructor
public class TransactionalOrderProcessor {

    private final KafkaTemplate<String, String> kafkaTemplate;

    @Transactional("kafkaTransactionManager")
    @KafkaListener(topics = "raw-orders", groupId = "order-group")
    public void processAndForward(String orderJson) {
        String enrichedOrder = applyBusinessLogic(orderJson);
        // Automatically participates in the active Kafka transaction:
        kafkaTemplate.send("validated-orders", enrichedOrder);
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Pillars of EOS:** Idempotent Producer + Transaction Coordinator + `read_committed` Consumer.
- **Transactional ID:** `transactional.id` identifies the producer across restarts and enforces **Zombie Fencing** via producer epochs.
- **Consumer Isolation:** Consumers **must** declare `isolation.level=read_committed` or they will read aborted/uncommitted transactional records.
- **`sendOffsetsToTransaction`:** Offset commits are packaged inside the producer transaction to ensure atomic rollback.
- **EOS Boundary:** Native Kafka Transactions guarantee EOS **only for Kafka-to-Kafka streams**.

**Common Follow-up Questions:**
- *"What happens if a consumer configured with `isolation.level=read_uncommitted` (default) reads from a transactional topic?"* → It immediately reads all messages as soon as they are written, including records from transactions that are later aborted!
- *"What is a Commit Marker?"* → A specialized non-data control record written into the partition log by the broker to indicate whether preceding transactional records were committed or aborted.
- *"How does Zombie Fencing work in Kafka Transactions?"* → If Producer Instance A hangs (e.g. long GC pause) and Producer Instance B starts with the same `transactional.id`, the coordinator increments the `epoch`; when Instance A wakes up and attempts a write, it is rejected with `ProducerFencedException`.

**Red Flags (DO NOT Say):**
- ❌ *"Setting `enable.idempotence=true` alone gives you full Exactly-Once Transactions across multiple topics."* (Idempotence only prevents duplicates on a single partition; transactions require `transactional.id` and 2PC markers).
- ❌ *"Kafka transactions allow atomic rollbacks in external PostgreSQL databases."* (Kafka transactions only coordinate with Kafka topics; external databases require the Transactional Outbox pattern).
- ❌ *"Consumers automatically hide uncommitted records by default."* (Default `isolation.level` is `read_uncommitted`; you must explicitly set `read_committed`).
