# How is Data Distributed Across Partitions?

---

## 🟢 Junior Level

When a producer publishes a message to a Kafka topic, the client's internal **Partitioner** determines which partition receives the record based on whether a **message key** is provided:

```
  Mail Sorting Analogy:
  • Letters with a Street Address (Key Present) ──► Always delivered to the exact same mail slot.
  • Letters with NO Address (Key Absent) ──► Bundled into a bag and sent to the next available mail carrier.
```

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Message Attribute    │ Routing Mechanism            │ Primary Consequence                              │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Key Present**      │ **MurmurHash2(key) % N**     │ All records with the same key go to the SAME     │
  │                      │                              │ partition, guaranteeing strict chronological FIFO│
  │ **Key Absent**       │ **Sticky Partitioning**      │ Batches messages into one partition at a time    │
  │ (`key == null`)      │                              │ to maximize batch compression and throughput.    │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The Default Partitioner Algorithm

In `DefaultPartitioner`, the routing decision follows a strict three-tier hierarchy:

```
  1. Did the developer explicitly specify a partition index?
     ├── YES ──► Route directly to that exact partition.
     └── NO  ──► Check if `key != null`?
                  ├── YES ──► Calculate `toPositive(murmur2(keyBytes)) % numPartitions`
                  └── NO  ──► Use Sticky Batching (Fill batch on current partition, then rotate)
```

### Evolution of Unkeyed Messages: Round-Robin vs. Sticky Partitioner

```
  ❌ Legacy Round-Robin (Kafka < 2.4):
  • msg 1 ➔ P0, msg 2 ➔ P1, msg 3 ➔ P2, msg 4 ➔ P0...
  • Disadvantages: Produces tiny 1-message network packets; destroys compression ratios and increases latency.

  ✅ Modern Sticky Partitioner (Kafka 2.4+):
  • msg 1..64 ➔ P0 (Fills 16 KB batch buffer) ──► Sends 1 single compressed network request!
  • msg 65..128 ➔ P2 (Fills next batch buffer)
  • Result: Drastically reduces broker CPU utilization and cuts p99 producer latency by up to 50%!
```

## 🔴 Senior Level

### Custom Partitioner Implementation

When standard hashing is insufficient (e.g., routing VIP customers or geographical regions to dedicated partitions):

```java
public class RegionAwarePartitioner implements Partitioner {

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
        int numPartitions = partitions.size();

        if (key == null) {
            return ThreadLocalRandom.current().nextInt(numPartitions);
        }

        String userKey = (String) key;
        if (userKey.startsWith("EU_")) {
            return 0; // Dedicated European partition
        } else if (userKey.startsWith("US_")) {
            return 1; // Dedicated US partition
        }

        // Fallback Murmur2 hashing for remaining partitions (2..N-1):
        int hash = Utils.toPositive(Utils.murmur2(keyBytes));
        return 2 + (hash % (numPartitions - 2));
    }

    @Override
    public void configure(Map<String, ?> configs) {}

    @Override
    public void close() {}
}
```

### The Hot Partition Problem (Data Skew)

- **The Danger:** If $80\%$ of messages share the same key (e.g., `key="AMAZON_ORDERS"`), $80\%$ of traffic floods a single partition/broker while other brokers sit idle.
- **Senior Mitigation (Key Salting):**
  - Append a random salt suffix to high-cardinality keys: `key = orderId + "_" + ThreadLocalRandom.current().nextInt(1, 5)`.
  - Distributes the load across 4 partitions while grouping smaller sub-batches.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **With Key:** Hashed via `MurmurHash2(key) % numPartitions` to guarantee ordering for that key.
- **Without Key (`null`):** Handled via **Sticky Partitioning** to maximize batching efficiency.
- **Partitions Ceiling:** Adding partitions to an existing topic changes hash modulo results, breaking key-to-partition routing for future messages!
- **Ordering Reality:** Kafka guarantees strict FIFO ordering **only per partition**, never globally across a topic.
- **Custom Partitioner:** Implement `org.apache.kafka.clients.producer.Partitioner` for tenant/region-based routing.

**Common Follow-up Questions:**
- *"What happens if you increase the number of partitions on a topic from 3 to 6?"* → Existing messages remain in partitions 0..2; however, new messages with existing keys will hash against modulo 6, landing on different partitions and breaking sequential consumption ordering!
- *"Why did Kafka replace Round-Robin with Sticky Partitioning for null keys?"* → Round-robin created fragmented single-record batches across all partitions, increasing network TCP overhead and ruining Snappy/zstd compression.
- *"How do you guarantee that all updates for a specific `customerId` are processed strictly in order?"* → Set `customerId` as the record key; this guarantees all updates route to the same partition and are consumed by the same consumer instance sequentially.

**Red Flags (DO NOT Say):**
- ❌ *"Kafka uses Java's standard `String.hashCode()` for partition calculation."* (Kafka uses a custom 32-bit `MurmurHash2` implementation for cross-language compatibility).
- ❌ *"Messages without keys are dropped or rejected by Kafka."* (They are batched and distributed via the Sticky Partitioner).
- ❌ *"Adding partitions to an active topic preserves key ordering guarantees seamlessly."* (It alters the hash modulo, splitting an entity's history across multiple partitions).
