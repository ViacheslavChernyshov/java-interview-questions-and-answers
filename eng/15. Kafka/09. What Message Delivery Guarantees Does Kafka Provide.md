# What Message Delivery Guarantees Does Kafka Provide?

---

## 🟢 Junior Level

Apache Kafka provides **three distinct levels of message delivery semantics** depending on how producers and consumers are configured:

```
  ┌──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Delivery Guarantee               │ Operational Definition                                                          │
  ├──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. At-Most-Once** (Loss Toler) │ Messages may be lost in transit, but are **never duplicated**.                  │
  │ **2. At-Least-Once** (Def Stand) │ Messages are **never lost**, but may be **duplicated** upon retries.           │
  │ **3. Exactly-Once** (EOS)        │ Every message is delivered and processed **exactly once** end-to-end.           │
  └──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

```
  Real-World Trade-Offs:
  • At-Most-Once ──► High-frequency IoT metrics & telemetry (Dropping 1 GPS point is harmless).
  • At-Least-Once ──► Standard enterprise default (Requires idempotent consumer database writes).
  • Exactly-Once ──► Financial ledger transfers, payment settlement, billing event pipelines.
```

## 🟡 Middle Level

### End-to-End Configuration Matrix

Delivery guarantees require coordinated configuration across both Producer and Consumer:

```
  ┌──────────────────────┬──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Semantic Tier        │ Producer Configuration                   │ Consumer Configuration                           │
  ├──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **At-Most-Once**     │ `acks=0`, `retries=0`                    │ `enable.auto.commit=true` (Auto-commits offset   │
  │                      │ (Fire-and-forget; ignores failures)      │ *before* business processing completes).         │
  ├──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **At-Least-Once**    │ `acks=all`, `retries=MAX_VALUE`,         │ `enable.auto.commit=false` (Manual commit        │
  │ (Enterprise Standard)│ `enable.idempotence=true`                │ `commitSync()` *after* business logic succeeds). │
  ├──────────────────────┼──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Exactly-Once**     │ `enable.idempotence=true`, `acks=all`,   │ `isolation.level=read_committed`,                │
  │ (Kafka-to-Kafka EOS) │ `transactional.id="tx-order-01"`         │ `sendOffsetsToTransaction(...)` API.             │
  └──────────────────────┴──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Boundaries of Exactly-Once Semantics (The Dual-Write Problem)

Senior architects understand that native Kafka Transactions **only guarantee Exactly-Once within the Kafka boundary** (Kafka-to-Kafka streams):

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ THE DUAL-WRITE REALITY:                                                                       │
  │ [Kafka Topic] ──► [Consumer Java App] ──► [PostgreSQL Database]                               │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ • Kafka transactions cannot coordinate a 2PC distributed commit with an external SQL database!│
  │ • If the DB commit succeeds, but the Kafka consumer crashes before committing its offset:    │
  │   The new consumer will RE-READ the message and duplicate the SQL insert!                     │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Production Solution for End-to-End External System Exactly-Once:
1. **Idempotent Upserts:** Execute database writes with `INSERT ... ON CONFLICT (order_id) DO UPDATE` or unique idempotency key constraints.
2. **Transactional Outbox Pattern:** Save domain business state and outgoing events atomically inside the same local relational database transaction (`BEGIN ... INSERT INTO orders ... INSERT INTO outbox ... COMMIT;`), and let Debezium / CDC stream events to Kafka.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **3 Semantics:** At-Most-Once (loss allowed), At-Least-Once (duplicates allowed, no loss), Exactly-Once (no loss, no duplicates).
- **At-Least-Once Standard:** Industry standard baseline (`acks=all` + manual offset commits + idempotent consumer).
- **EOS Scope:** Native Kafka Transactions provide EOS **strictly for Kafka-to-Kafka workflows**.
- **External DB Solution:** Combine At-Least-Once with **Idempotent Consumer** or **Transactional Outbox**.
- **Idempotent Producer:** `enable.idempotence=true` eliminates producer retry network duplicates via sequence numbers.

**Common Follow-up Questions:**
- *"Why does `acks=0` cause message loss?"* → The producer writes to the network socket and immediately assumes success without waiting for the broker to write to disk or replicate; if the broker crashes, the record is lost permanently.
- *"How does a consumer achieve At-Least-Once processing?"* → Disable auto-commit (`enable.auto.commit=false`) and invoke `consumer.commitSync()` only after all database writes or business operations have completed successfully.
- *"What is the performance overhead of Exactly-Once Transactions in Kafka?"* → Approximately $10\%–20\%$ latency and throughput overhead due to Two-Phase Commit transaction coordinator markers written to the `__transaction_state` topic.

**Red Flags (DO NOT Say):**
- ❌ *"Kafka provides Exactly-Once delivery to external databases out of the box without any special consumer design."* (External database writes require idempotency or the Outbox pattern).
- ❌ *"At-Least-Once is slow and dangerous, so production systems always use At-Most-Once."* (At-Most-Once drops financial records; At-Least-Once is the enterprise standard).
- ❌ *"Setting `enable.auto.commit=true` guarantees At-Least-Once delivery."* (Auto-commit runs on a timer and commits offsets before processing, risking message loss).
