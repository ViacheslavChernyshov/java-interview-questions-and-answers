# What is Producer Acknowledgment and What Modes Exist (acks=0, 1, all)?

---

## 🟢 Junior Level

The **Producer Acknowledgment (`acks`)** setting in Apache Kafka dictates how many partition replicas must write a message to their local log before the broker responds with a success confirmation back to the Producer:

```
  Registered Post Analogy:
  • `acks=0` (Drop in Street Mailbox): You drop the letter and walk away. Zero receipt; if the box burns down, letter is lost.
  • `acks=1` (Postal Clerk Stamp): The counter clerk stamps your receipt. Fast, but if the local post office burns down before shipping to the hub, letter is lost.
  • `acks=all` (Multi-Signature Vault Confirmation): The central vault and all regional security branches sign receipt of the parcel. Maximum security!
```

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ `acks` Mode          │ Confirmation Source          │ Durability vs. Latency Trade-Off                 │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`acks=0`**         │ None (Local socket write)    │ ⚡ **Lowest Latency (~0.5ms)**, ⚠️ High Loss Risk │
  │ **`acks=1`** (Legacy)│ Leader Replica Disk only     │ 🚀 **Fast (~2ms)**, ⚠️ Data Loss on Leader Crash │
  │ **`acks=all`** (Def) │ Leader + **All ISR Replicas**│ 🛡️ **Guaranteed Durability**, ⚖️ Latency (~5–15ms)│
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

```java
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.ACKS_CONFIG, "all"); // Production standard for zero data loss
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```

## 🟡 Middle Level

### Architectural Comparison & Kafka 3.0 Defaults

```
  1. `acks=0` Flow:
     Producer ──► [OS Network Buffer] ──► Immediate Success (No broker confirmation!)

  2. `acks=1` Flow:
     Producer ──► Leader Replica (Appends to Log) ──► Responds Success!
                  (Followers replicate asynchronously in background)

  3. `acks=all` Flow:
     Producer ──► Leader Replica
                  ├── Replicated to Follower 1 (ACK)
                  └── Replicated to Follower 2 (ACK)
                  ▼
                  Leader waits for ALL ISR members to confirm ──► Responds Success!
```

```
  KIP-316 Evolution (Kafka 3.0+):
  • Kafka < 3.0: Default was `acks=1` (Optimized for raw speed over safety).
  • Kafka >= 3.0: Default is `acks=all` + `enable.idempotence=true` ("Durable and Safe by Default").
```

## 🔴 Senior Level

### The Critical Coupling: `acks=all` + `min.insync.replicas`

Senior architects know that `acks=all` **is meaningless on a degraded cluster without `min.insync.replicas`**:

```
  Scenario: Topic has `replication.factor=3`, `acks=all`, but `min.insync.replicas=1` (Default).

  1. Brokers 2 and 3 crash. The ISR pool shrinks to `ISR=[Broker 1 (Leader)]`.
  2. Producer publishes message with `acks=all`.
  3. The Leader checks the ISR list: Since ISR only has Broker 1, it writes locally and returns SUCCESS!
  4. Broker 1 immediately crashes.
  5. 💥 DISASTER: The record was lost despite `acks=all`!

  🛡️ THE BULLETPROOF PRODUCTION TRIAD:
  • `replication.factor=3`
  • `min.insync.replicas=2` (Rejects writes with `NotEnoughReplicasException` if ISR drops to 1)
  • `acks=all`
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`acks=0`:** Fire-and-forget; retries are disabled; maximum speed for telemetry/logs.
- **`acks=1`:** Waits only for Leader disk write; risks data loss during un-replicated leader crash.
- **`acks=all` (or `-1`):** Waits for Leader AND all active In-Sync Replicas (ISR).
- **Default Shift (Kafka 3.0):** Default changed from `acks=1` to `acks=all` + `enable.idempotence=true`.
- **Durability Invariant:** `acks=all` requires `min.insync.replicas=2` to prevent single-broker fallback.

**Common Follow-up Questions:**
- *"Why are retries ineffective when `acks=0`?"* → Because the client never receives error responses from the broker; the producer always marks the send as successful the moment bytes hit the local network buffer.
- *"Does `acks=all` wait for dead or lagging replicas outside the ISR?"* → No; it only waits for replicas currently registered in the active **ISR** pool.
- *"How can you optimize throughput when using `acks=all`?"* → Enable message batching (`linger.ms=20`, `batch.size=65536`) and compression (`compression.type=lz4` or `zstd`) to amortize network round-trips over thousands of records.

**Red Flags (DO NOT Say):**
- ❌ *"`acks=all` means the write will fail if even one follower in the entire cluster of 50 brokers is offline."* (It only waits for replicas assigned to that specific partition's ISR).
- ❌ *"`acks=all` is too slow for production banking systems."* (Combined with producer batching, `acks=all` handles hundreds of thousands of transactions per second).
- ❌ *"`acks=1` guarantees zero data loss."* (If the Leader crashes before followers fetch the record, the message is permanently lost).
