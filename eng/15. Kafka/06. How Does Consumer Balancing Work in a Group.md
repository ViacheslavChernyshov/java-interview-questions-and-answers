# How Does Consumer Balancing Work in a Group?

---

## 🟢 Junior Level

**Consumer Balancing** is the automated mechanism in Kafka that dynamically assigns and redistributes topic partitions among all active consumers within a Consumer Group:

```
  Cake Slicing Analogy:
  • 6 Slices of Cake (6 Partitions) & 3 Friends (3 Consumers):
    - C1 gets Slices 0 & 1
    - C2 gets Slices 2 & 3
    - C3 gets Slices 4 & 5
  • If a 4th friend arrives ──► Kafka rebalances slices: C1 (0, 1), C2 (2), C3 (3), C4 (4, 5).
```

```
  The Core Rule:
  • Partitions are divided as evenly as possible across active consumers.
  • No partition is ever assigned to more than one consumer in the same group.
```

## 🟡 Middle Level

### The 4 Partition Assignment Strategies

Configured via `props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG, ...)`:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Strategy                     │ Execution Mechanism & Trade-Off                                                 │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`RangeAssignor`** (Def)    │ Divides numeric partition ranges on a per-topic basis.                         │
  │                              │ ⚠️ Severe imbalance when subscribing to multiple topics!                        │
  │ **`RoundRobinAssignor`**     │ Interleaves all topic partitions evenly across all consumers.                   │
  │ **`StickyAssignor`**         │ Balances partitions evenly while maximizing preservation of current assignments.│
  │ **`CooperativeSticky`**      │ 🚀 **Incremental Cooperative Rebalancing (KIP-429)**: Reassigns only migrating   │
  │                              │ partitions without stopping healthy consumers!                                  │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### The Multi-Topic RangeAssignor Imbalance Trap

```
  Scenario: Group subscribes to 10 Topics (Each topic has 3 partitions: P0, P1, P2).
  Group has 2 Consumers (C1, C2).

  RangeAssignor Calculation per Topic:
  • Topic 1..10: C1 gets P0, P1 (2 partitions); C2 gets P2 (1 partition).

  💥 TOTAL DISASTER:
  • Consumer 1 is overloaded with 20 partitions!
  • Consumer 2 sits underutilized with only 10 partitions!

  ✅ SOLUTION: Use `CooperativeStickyAssignor` (Each gets exactly 15 partitions).
```

## 🔴 Senior Level

### Cooperative Rebalancing vs. Eager Rebalancing Protocol

```
  1. Eager Rebalance Protocol (Legacy):
     [Rebalance Triggered] ──► All consumers REVOKE 100% of their partitions.
     "Stop-the-World" Pause: Zero messages processed across the entire group for 5–30 seconds!
     [SyncGroup Completes] ──► Consumers re-open connections and resume reading.

  2. Incremental Cooperative Rebalancing (Kafka 2.4+ / CooperativeSticky):
     • Phase 1: Group identifies that only Partition 3 needs to move from C1 to C3.
     • C1 revokes ONLY Partition 3; C1 continues processing Partitions 0, 1 uninterrupted!
     • C2 processes Partitions 2, 4 with ZERO interruption!
     • Phase 2: C3 joins and begins reading Partition 3.
```

### Safe State Commit via `ConsumerRebalanceListener`

```java
consumer.subscribe(List.of("orders-topic"), new ConsumerRebalanceListener() {

    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        log.warn("Partitions being revoked: {}. Committing in-flight offsets...", partitions);
        // 1. Flush local database transactions
        // 2. Synchronously commit offsets to avoid duplicate processing:
        consumer.commitSync();
    }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        log.info("New partitions assigned: {}. Initializing cache...", partitions);
    }

    @Override
    public void onPartitionsLost(Collection<TopicPartition> partitions) {
        log.error("Partitions lost to coordinator heartbeat timeout: {}. Discarding buffer!", partitions);
    }
});
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Function:** Assigns partitions among group consumers and triggers rebalances on member changes.
- **Assignment Strategies:** `Range` (per-topic slices), `RoundRobin` (uniform interleaving), `CooperativeSticky` (incremental non-blocking).
- **Multi-Topic Skew:** `RangeAssignor` causes massive load skew across multiple topics; always prefer `CooperativeStickyAssignor`.
- **Eager vs Cooperative:** Eager revokes all partitions and stops processing; Cooperative only revokes moving partitions.
- **`ConsumerRebalanceListener`:** Essential hook to commit offsets and flush buffers before losing a partition.

**Common Follow-up Questions:**
- *"What is the difference between `onPartitionsRevoked` and `onPartitionsLost`?"* → `onPartitionsRevoked` is called during normal graceful rebalances allowing you to commit offsets; `onPartitionsLost` is called when the coordinator has already reassigned your partitions due to heartbeat timeouts (offsets should NOT be committed to prevent overwriting).
- *"How do you configure Cooperative Sticky Rebalancing in Spring Kafka?"* → Set `spring.kafka.consumer.properties.partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor`.
- *"What triggers a consumer rebalance in production?"* → Adding a consumer, scaling down pods, network heartbeat timeouts (`session.timeout.ms`), or long-running message processing exceeding `max.poll.interval.ms`.

**Red Flags (DO NOT Say):**
- ❌ *"During a rebalance, Kafka brokers re-route messages in memory to different queues."* (Brokers do nothing to messages; the client-side consumers simply reassign which partition log offsets they read).
- ❌ *"RangeAssignor is optimal when consuming from dozens of topics simultaneously."* (It causes severe partition count imbalance on the first consumer).
- ❌ *"Rebalances always pause all message consumption across the entire consumer group."* (Modern `CooperativeStickyAssignor` allows unimpacted consumers to process uninterrupted).
