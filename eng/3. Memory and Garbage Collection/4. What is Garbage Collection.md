# What is Garbage Collection?

---

## 🟢 Junior Level

**Garbage Collection (GC)** is the JVM's automated memory management subsystem responsible for dynamically discovering and reclaiming heap memory occupied by **unreachable objects** (objects no longer referenced by any active thread).

**Why it is needed:** In low-level languages like C/C++, developers must manually invoke `free()` or `delete`. Forgetting to free memory creates **Memory Leaks**, while freeing too early causes fatal **Dangling Pointers** or **Segmentation Faults**. Java eliminates these manual memory hazards.

```
       [ Active Thread Stack ] ──(GC Root)──> [ Object A (Live) ] ──> [ Object B (Live) ]
                                                                                
       [ Object X (Dead) ] <──── (Cyclic unreferenced island) ────> [ Object Y (Dead) ]
       (Both X and Y are reclaimed automatically by the Garbage Collector!)
```

### Tracing Reachability vs. Reference Counting

> [!IMPORTANT]
> The JVM **never uses simple Reference Counting** because reference counters cannot detect cyclic references ($A \to B \to A$). Instead, Java uses **Tracing Garbage Collection (Root Reachability Analysis)**: starting from known **GC Roots**, it traverses the object graph. Any object that cannot be reached along a chain of live references is marked as garbage.

## 🟡 Middle Level

### The Weak Generational Hypothesis

Decades of enterprise workload telemetry establish two empirical axioms:
1. **Most allocated objects die shortly after creation** (over 90% are short-lived DTOs, method parameters, and lambdas).
2. **Objects that survive multiple collection cycles tend to remain alive for a long time** (singletons, caches, thread pools).

This hypothesis dictates dividing the JVM Heap into distinct **Generations**:
- **Young Generation (Eden + Survivors S0/S1):** Collected frequently via high-speed **Copying collectors** (Minor GC).
- **Old Generation (Tenured):** Collected infrequently via **Mark-Sweep-Compact collectors** (Major/Mixed GC).

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                   GC Algorithm                         │                  Primary Use Case                      │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **Copying (Evacuation)**                               │ Young Gen: Copies live objects to a clean space        │
  │ **Mark-Sweep**                                         │ Old Gen: Marks live objects; reclaims dead slots       │
  │ **Mark-Compact**                                       │ Full GC: Defragments memory by sliding objects together│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### The Garbage Collection Trilemma

Engineers cannot maximize all three dimensions simultaneously; prioritizing one compromises another:

```
                      [ Latency ] (Pause times)
                         / \
                        /   \
                       /     \
    [ Throughput ] ───────────── [ Footprint ] (RAM overhead)
    (CPU time for app)            (Extra memory metadata)
```

- **Parallel GC:** Maximizes **Throughput** at the cost of longer multi-second STW pauses.
- **ZGC / Shenandoah:** Minimizes **Latency** (<1ms pauses) at the cost of 5–15% lower raw throughput due to Load Barriers.
- **G1 GC:** Provides an engineered **Balance** (targeting ~200ms predictable pauses).

## 🔴 Senior Level

### Safepoints & TTSP (Time To Safepoint) Mechanics

The JVM cannot halt application threads arbitrarily at any instruction; doing so would leave registers and heap references in inconsistent states.

1. **Safepoint Poll:** The JIT compiler inserts safepoint checks into method returns, exception handlers, and loop edges.
2. **Safepoint Trigger:** When a GC phase requires a Stop-The-World (STW) pause, the JVM unmaps a memory guard page. When application threads read this page, a hardware page fault traps the thread into a suspended waiting state.
3. **TTSP (Time To Safepoint):** The delay between when the GC requests a pause and when the *slowest* application thread reaches a safepoint.

> [!CAUTION]
> **The Counted Loop TTSP Trap:** Historically, HotSpot omitted safepoints from finite `for (int i=0; i<1_000_000_000; i++)` counted loops. If a background thread was stuck in a long counted loop, **the entire JVM would freeze for seconds** waiting for that single thread to reach a safepoint. Modern JVMs resolve this via `-XX:+UseCountedLoopSafepoints`.

### Cross-Generational Tracking: Card Tables & Write Barriers

To collect the Young Generation without scanning gigabytes of Old Generation memory, the JVM maintains a **Card Table** (where 1 byte represents a 512-byte block of Old Gen memory).
Whenever an Old Gen object field is updated to reference a Young Gen object (`oldObj.field = youngObj`), the JIT compiler executes a **Write Barrier**:

$$\text{card\_table}[\text{address} \gg 9] = \mathbf{DIRTY}$$

During Minor GC, the collector scans *only* the dirty cards rather than the entire Old Generation.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Concept:** Automatic discovery and reclamation of unreachable heap memory via Root Reachability Analysis (Tracing GC).
- **Weak Generational Hypothesis:** The heap is partitioned into Young (Eden, S0, S1) and Old generations because most objects die young.
- **Core Algorithms:** Copying (Young Gen), Mark-Sweep (Old Gen), Mark-Compact (Full GC).
- **Stop-The-World (STW):** Pauses all application mutator threads at Safepoints to ensure heap reference consistency during critical GC phases.
- **Card Tables & Write Barriers:** Tracks Old-to-Young references, avoiding whole-heap scans during Minor GCs.
- **Major Collectors:** G1 (default balanced), ZGC (<1ms pauses), Parallel (maximum batch throughput).

**Common Follow-up Questions:**
- *"Why doesn't Java use Reference Counting like Python or Swift?"* → Reference counting cannot detect circular reference graphs ($A \to B \to A$) and adds heavy synchronization overhead to every pointer write.
- *"What is an Allocation Stall in concurrent collectors?"* → Occurs when application threads allocate memory faster than the concurrent GC can sweep/evacuate it, forcing the JVM to freeze mutator threads until memory is freed.
- *"What causes a high Time-To-Safepoint (TTSP)?"* → Long uncounted loops, heavy JNI native calls, or disk I/O blocking threads from checking the safepoint poll guard page.

**Red Flags (DO NOT Say):**
- ❌ *"Garbage Collection is based on counting references to an object."* (Java uses Root Reachability Analysis, not reference counting).
- ❌ *"Calling `System.gc()` is a good way to improve application performance."* (Triggers a heavy, synchronous Stop-The-World Full GC).
- ❌ *"ZGC is always superior to Parallel GC in every workload."* (Parallel GC yields higher raw CPU throughput for batch analytics and big data workloads).
