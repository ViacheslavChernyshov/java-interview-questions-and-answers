# What is stored in Stack?

---

## 🟢 Junior Level

The **JVM Stack** is a private, thread-isolated region of memory created whenever a new thread is spawned. It stores active method execution contexts structured as a Last-In, First-Out (**LIFO**) sequence of **Stack Frames**.

**Why each thread requires its own Stack:** Threads execute independent call graphs concurrently. If threads shared a single stack, local variables from one thread would corrupt the calculations of another.

**What is stored in the Stack:**
1. **Local Primitive Variables:** `int`, `double`, `boolean`, `char`, `long`, `byte`, `short`, `float`.
2. **Object Reference Handles:** The memory address pointer referencing an object instance located in the Heap.
3. **Execution Control Frames:** Return addresses, operand stacks, and exception dispatch records.

```java
public void executeWorkflow() {
    int count = 10;                     // Primitive value stored directly in the Stack frame
    User user = new User("Alice");      // 'user' pointer resides in Stack; User instance lives in Heap
    calculateTax(count);                // Pushes a new Stack Frame onto the call stack
}
```

- **Thread Configuration:** Controlled via `-Xss` (default is 1MB per thread on 64-bit JVMs).
- **Failure Mode:** Deep or infinite recursion exhausts stack depth, throwing `java.lang.StackOverflowError`.

## 🟡 Middle Level

### Internal Structure of a JVM Stack Frame

Whenever a method is invoked, the JVM allocates a stack frame whose exact memory size is **pre-calculated at compile time**:

```
  Stack Frame Components:
  ┌────────────────────────────────────────────────────────┐
  │ 1. Local Variable Table (LVT)                          │
  │    • Slot [0] = `this` reference (for instance methods)│
  │    • Slot [1..N] = Method parameters and local vars    │
  │    • 32-bit slots (`long` & `double` take 2 slots)     │
  ├────────────────────────────────────────────────────────┤
  │ 2. Operand Stack                                       │
  │    • LIFO bytecode workspace for mathematical ops      │
  │    • e.g. `iload_1`, `iload_2`, `iadd`, `istore_3`     │
  ├────────────────────────────────────────────────────────┤
  │ 3. Frame Data & Dynamic Linking                        │
  │    • Reference to Runtime Constant Pool for the class  │
  │    • Normal method return PC address                   │
  │    • Exception Dispatch Table references               │
  └────────────────────────────────────────────────────────┘
```

### Modern Stack Inspection: `StackWalker` API (Java 9+)

Legacy stack inspection (`new Throwable().getStackTrace()`) eagerly captures the entire stack trace as an expensive array of strings, imposing heavy CPU overhead.

The modern **`java.lang.StackWalker`** provides lazy, high-performance stream traversal:

```java
// Lazy, zero-overhead stack frame filtering:
String callerClass = StackWalker.getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE)
    .walk(frames -> frames
        .skip(1) // Skip current method frame
        .findFirst()
        .map(StackWalker.StackFrame::getClassName)
        .orElse("UnknownCaller")
    );
```

## 🔴 Senior Level

### Virtual Threads Memory Model (Java 21+ Project Loom)

The stack architecture fundamentally diverges between OS Platform Threads and Java 21 Virtual Threads:

```
  Platform Thread vs. Virtual Thread Stack Architecture:

  Platform Thread (1:1 OS Thread mapping):
  ┌────────────────────────────────────────────────────────┐
  │ Fixed 1 MB Contiguous Virtual Memory Stack in OS RAM   │
  │ • Cannot shrink or grow dynamically                    │
  │ • 10,000 active threads = ~10 GB RAM consumed!         │
  └────────────────────────────────────────────────────────┘

  Virtual Thread (M:N Carrier Thread mapping):
  ┌────────────────────────────────────────────────────────┐
  │ Chunked Stack allocated on the JVM HEAP (~2 KB start)   │
  │ • Grows and shrinks dynamically based on call depth    │
  │ • Mount: Copies heap frame into Carrier Thread stack   │
  │ • Unmount (on I/O block): Freezes frame back to Heap   │
  │ • 10,000 active threads = ~20 MB RAM consumed!         │
  └────────────────────────────────────────────────────────┘
```

> [!WARNING]
> Virtual threads excel at **I/O-bound tasks** (HTTP calls, DB queries). For **CPU-bound calculations**, virtual threads provide no throughput gain and introduce unnecessary frame mounting/unmounting overhead.

### Tail Call Optimization (TCO) vs. JIT Method Inlining

Java does **not** natively support Tail Call Optimization (TCO) in bytecode because preserving full stack traces for security checks (`SecurityManager` / stack inspection) historically required intact frames.

However, the HotSpot C2 JIT compiler optimizes self-recursive tail calls via **Method Inlining & Loop Unrolling**, transforming recursive methods into iterative hardware loops:

```java
// Written as Tail Recursion:
public int sum(int n, int accumulator) {
    if (n <= 0) return accumulator;
    return sum(n - 1, accumulator + n);
}

// C2 JIT Inlines this into a single hardware loop (0 new stack frames allocated!):
public int sum(int n, int accumulator) {
    while (n > 0) {
        accumulator += n;
        n--;
    }
    return accumulator;
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Stack Contents:** Method call frames, primitive local variables, reference pointers to Heap objects.
- **Thread Isolation:** Every thread has an independent Stack; Stack memory is never shared across threads.
- **Frame Lifecycle:** Created upon method entry, popped deterministically upon return (zero Garbage Collection involvement).
- **Stack Frame Anatomy:** **Local Variable Table (LVT)** + **Operand Stack** + **Dynamic Linking / Frame Data**.
- **Virtual Threads (Java 21):** Stack frames live on the **Heap** as lightweight chunked objects (~2KB initial footprint), enabling millions of concurrent threads.
- **Stack Inspection:** Use `java.lang.StackWalker` instead of `Throwable.getStackTrace()` for high-performance lazy traversal.

**Common Follow-up Questions:**
- *"Why do `long` and `double` variables occupy two slots in the Local Variable Table?"* → The JVM local variable table is structured as an array of 32-bit slots; 64-bit primitive data types require two contiguous 32-bit slots.
- *"What is slot 0 in the Local Variable Table of an instance method?"* → Slot 0 always stores the hidden `this` pointer reference to the current object instance. In `static` methods, slot 0 is assigned to the first method parameter.
- *"Can a `StackOverflowError` be caught with a `try-catch` block?"* → Yes, it extends `java.lang.Error`, but catching it is dangerous because the thread stack may be left in an unstable state.

**Red Flags (DO NOT Say):**
- ❌ *"Objects created inside a method are stored on the Stack."* (Only the reference pointer resides on the Stack; the actual object is on the Heap, unless eliminated by JIT Scalar Replacement).
- ❌ *"Java natively supports Tail Call Optimization for recursive methods."* (Java bytecode does not support TCO; HotSpot relies on JIT method inlining).
- ❌ *"Virtual Threads allocate a 1MB native stack just like Platform Threads."* (Virtual thread stacks are chunked heap objects starting at ~2KB).
