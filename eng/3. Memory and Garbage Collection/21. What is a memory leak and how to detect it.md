# What is a memory leak and how to detect it?

---

## 🟢 Junior Level

In Java, a **Memory Leak** occurs when objects that are **no longer needed by application business logic** remain unintentionally anchored to a live **GC Root** via active strong references, preventing the Garbage Collector from freeing their memory.

**Visual Warning Sign: The Rising Sawtooth Pattern**
In healthy JVMs, memory graphs resemble a sawtooth with a constant floor. In leaking applications, the minimum floor creeps upward after every GC cycle until an `OutOfMemoryError` occurs.

```
  Healthy JVM (Constant Floor):       Memory Leak (Rising Baseline Floor):
  Memory                               Memory
   |   /\    /\    /\    /\             |     /\      /\      /\      / \  [OOM!]
   |  /  \  /  \  /  \  /  \            |    /  \    /  \    /  \    /   \
   |_/____\/____\/____\/____\           |___/____\__/____\__/____\__/_____
   +-------------------------> Time     +---------------------------------> Time
     (Floor remains flat)                  (Floor rises steadily -> Leak!)
```

## 🟡 Middle Level

### The 4-Step Delta Analysis Methodology

Do not inspect a single static heap dump in isolation. Use **Heap Delta Analysis**:

```
  1. Boot JVM & Warm-up ──> 2. Baseline Dump T0 ──> 3. Apply Load Test ──> 4. Snapshot Dump T1
                                                                                  │
                                                                                  ▼
                                        5. Compare T0 vs T1 in Eclipse MAT (Delta Diff)
```

1. Capture **Baseline Dump $T_0$** after initial startup and warm-up.
2. Subject the application to load/stress testing.
3. Capture **Snapshot Dump $T_1$**.
4. Open both dumps in **Eclipse MAT** and generate a **Class Histogram Diff**: the leaking objects appear at the top of the delta count!

### Shallow Heap vs. Retained Heap

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                       Shallow Heap                     │                      Retained Heap                     │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • The physical memory consumed by the object itself    │ • The total heap memory that would be **freed** if this│
  │   (Header + Primitive Fields + Reference Pointers)     │   specific object were collected by GC                 │
  │ • Example: A `HashMap` node is only **32 bytes**       │ • Example: The same `HashMap` node holds **500 MB** of │
  │   shallow heap.                                        │   cached payload in its retained subtree!              │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```
> [!IMPORTANT]
> When hunting memory leaks in Eclipse MAT, **always sort by Retained Heap**, never Shallow Heap!

## 🔴 Senior Level

### Eclipse MAT Power Tools: Dominator Tree & GC Root Paths

```
  Dominator Tree ──> Select Top Retained Node ──> Path to GC Roots ──> Exclude Weak/Soft References
```

1. **Dominator Tree:** Reorganizes the object graph into a strict hierarchy: An object $A$ dominates object $B$ if every reference path from a GC Root to $B$ must pass through $A$. Top dominators pinpoint the ultimate root cause.
2. **Path to GC Roots (Excluding Weak/Soft):** Traces the exact chain of strong reference fields (e.g. `AppConfig.INSTANCE -> static registry -> ConcurrentHashMap.table -> LeakingObject`).

### Object Query Language (OQL)

Query the heap dump like a SQL database to discover rogue collections and oversized payloads:

```sql
-- Find all HashMaps holding more than 50,000 entries:
SELECT m 
FROM java.util.HashMap m 
WHERE m.size > 50000

-- Find all String instances consuming over 1 MB of memory:
SELECT s 
FROM java.lang.String s 
WHERE s.value.@length > 1000000
```

### Low-Overhead Production Profiling: JFR `OldObjectSample`

> [!WARNING]
> Triggering a 64GB+ Heap Dump in production causes a **30–60 second Stop-The-World pause**, causing Kubernetes Liveness Probes to fail and killing the container!

#### ✅ The Zero-Pause Production Alternative:
Use **Java Flight Recorder (JFR)** to sample long-lived objects with **$<1\%$ CPU overhead**:

```bash
# Record 10 minutes of low-overhead memory allocations:
jcmd <PID> JFR.start duration=600s filename=leak_profile.jfr settings=profile
```
Open `leak_profile.jfr` in **JDK Mission Control (JMC)** and inspect the `Old Object Sample` tab to see allocation stack traces and reference paths without ever pausing the JVM!

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Unintentional strong object retention preventing GC reclamation.
- **Visual Tell:** Rising baseline floor on memory telemetry graphs (Sawtooth Pattern).
- **Delta Analysis:** Compare Baseline Dump $T_0$ vs Post-Load Dump $T_1$ to isolate growing object counts.
- **Shallow vs Retained:** Shallow = object's own bytes; Retained = total memory liberated if object is collected. Always sort by Retained Heap!
- **Dominator Tree & Path to GC Roots:** Primary Eclipse MAT views to find the root reference holding the leak.
- **JFR `OldObjectSample`:** Safe production leak profiling for massive heaps (>32GB) without STW heap dump pauses.

**Common Follow-up Questions:**
- *"Why is triggering `jcmd GC.heap_dump` risky on a 128GB production heap?"* → The JVM must freeze in a Stop-The-World pause while writing 128GB of data to disk (taking 30–90 seconds), which causes load balancer timeouts and Kubernetes container restarts.
- *"What is a Dominator in Eclipse MAT?"* → Node $X$ dominates node $Y$ if every execution path from the GC Roots to $Y$ must traverse through $X$; deleting $X$ guarantees $Y$ is also garbage collected.
- *"How do you diagnose off-heap memory leaks?"* → Heap dumps cannot inspect off-heap memory; use **Native Memory Tracking (NMT)** via `jcmd <pid> VM.native_memory detail.diff`.

**Red Flags (DO NOT Say):**
- ❌ *"Sorting by Shallow Heap in Eclipse MAT shows which object is causing the leak."* (Shallow heap only shows the tiny 32-byte header; Retained Heap reveals the gigabytes of held data).
- ❌ *"Memory leaks are impossible in Java because it has an automatic Garbage Collector."* (GC only reclaims unreferenced objects; logic errors that retain strong references cause leaks).
- ❌ *"I take heap dumps directly in production on high-traffic nodes during peak hours."* (Freezes the JVM; use JFR `OldObjectSample` or route traffic away from the replica first).
