# What happens on OutOfMemoryError?

---

## 🟢 Junior Level

An **`OutOfMemoryError` (OOME)** is a critical JVM runtime error (extending `java.lang.VirtualMachineError`) thrown when the Java Virtual Machine **cannot allocate sufficient physical or virtual memory for an object**, and no more memory can be made available by the Garbage Collector.

```
  Allocation Request ──> Out of Memory ──> Full GC Runs ──> Still Out of Memory ──> Throws OOME!
```

**Common Manifestations:**
- `java.lang.OutOfMemoryError: Java heap space` (Heap is full).
- `java.lang.OutOfMemoryError: Metaspace` (Class metadata is full).
- `java.lang.OutOfMemoryError: GC overhead limit exceeded` (GC spends 98%+ CPU time reclaiming <2% memory).

---

## 🟡 Middle Level

### The Internal OOM Escalation Sequence

```
  1. Mutator thread requests memory allocation -> Eden / TLAB fails
                               │
                               ▼
  2. JVM executes emergency Stop-The-World Full GC
                               │
                               ▼
  3. All `SoftReference` instances are forcefully purged
                               │
                               ▼
  4. Heuristic Check: Did GC spend >98% CPU time freeing <2% RAM?
     ├── YES ──> Throws `OutOfMemoryError: GC overhead limit exceeded`
     └── NO  ──> Free memory still insufficient?
                  └── YES ──> Throws `OutOfMemoryError: Java heap space`
```

### The "Zombie State" Danger of Partial Thread Death

> [!CAUTION]
> **OOME does NOT terminate the JVM process by default!**
> Only the specific thread that requested memory throws the error and terminates. The rest of the application threads **continue running**, often leaving the system in an unstable, corrupted **Zombie State**:
> 1. **Orphaned Synchronization Locks:** If a thread dies while holding an explicit lock (or before completing a `try-finally` block), the lock is never released, causing permanent **Deadlocks** for all other worker threads.
> 2. **Corrupted Data Structures:** In-flight modifications to shared collections (`ConcurrentHashMap`) or database caches remain partially updated.

## 🔴 Senior Level

### JVM OOME vs. Linux Kernel OOM-Killer (Docker / Kubernetes)

Engineers frequently confuse an internal JVM error with an operating system kernel kill:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                 Internal JVM OOME                      │             Linux Kernel OOM-Killer (Exit 137)         │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Triggered by: Java Heap, Metaspace, or Direct Buffer │ • Triggered by: Total Process RSS > Container Cgroup   │
  │ • Emits a full Java stack trace in application logs   │ • Emits **zero Java logs**; process vanishes instantly │
  │ • Can generate an automatic `.hprof` Heap Dump        │ • Linux Kernel logs event to `dmesg` (`SIGKILL 9`)     │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Production Fail-Fast Configuration

Never attempt to catch `OutOfMemoryError` in business logic (`try-catch (Throwable t)`). Configure the JVM to crash cleanly and emit an HPROF dump so orchestrators (Kubernetes) can immediately spawn a healthy replacement pod:

```bash
# Recommended Production Flags for Kubernetes Pods:
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/dumps/oom_dump.hprof \
     -XX:+ExitOnOutOfMemoryError \
     -jar app.jar
```

- **`-XX:+HeapDumpOnOutOfMemoryError`:** Captures heap memory snapshot at the exact moment of failure.
- **`-XX:+ExitOnOutOfMemoryError`:** Forces immediate JVM termination, preventing corrupted Zombie States.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Thrown when the JVM cannot satisfy an object allocation even after a Full GC and purging SoftReferences.
- **Zombie State:** OOME terminates *only the allocating thread*, leaving other threads running with potential deadlocks and corrupted shared structures.
- **GC Overhead Limit:** Specific OOME triggered when the JVM spends $>98\%$ of CPU time on GC while reclaiming $<2\%$ of heap space.
- **JVM OOME vs OS OOM-Killer:** JVM OOME writes stack traces and dumps; Kernel OOM-Killer sends `SIGKILL (Exit Code 137)` with zero Java logs when total RSS exceeds container cgroup limits.
- **Production Standard:** Configure `-XX:+HeapDumpOnOutOfMemoryError` and `-XX:+ExitOnOutOfMemoryError`.

**Common Follow-up Questions:**
- *"Why should you never catch `OutOfMemoryError` in application code?"* → Because JVM invariants, synchronization locks, and data structures may be in a corrupted, half-initialized state.
- *"What should you do if your container is terminated with Exit Code 137 but no OOM heap dump is generated?"* → The process was killed by the OS Kernel OOM-Killer because native off-heap memory (Metaspace, thread stacks, direct buffers) exceeded the container cgroup limit. Check `dmesg | grep -i oom` and lower `-Xmx` or increase container RAM.
- *"Can a `finally` block fail to execute during an OutOfMemoryError?"* → Yes, if the OOM occurs while allocating stack frame memory or instantiating an exception object during the unwind process.

**Red Flags (DO NOT Say):**
- ❌ *"Catching `OutOfMemoryError` and retrying the request is standard error-handling practice."* (Leaves the JVM in a corrupt, unpredictable Zombie State).
- ❌ *"An OutOfMemoryError automatically terminates the entire Java process."* (Only the thread requesting memory terminates; the JVM remains running unless configured with `-XX:+ExitOnOutOfMemoryError`).
- ❌ *"The Linux OOM-Killer is triggered when `-Xmx` is exceeded."* (OOM-Killer triggers when total OS process RSS exceeds the cgroup container limit).
