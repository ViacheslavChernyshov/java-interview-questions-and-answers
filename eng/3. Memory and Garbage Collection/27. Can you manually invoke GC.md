# Can you manually invoke GC?

---

## 🟢 Junior Level

**Yes, you can request a collection** by calling `System.gc()` or `Runtime.getRuntime().gc()`. 

However, calling `System.gc()` is considered an **architectural anti-pattern in production application code**:

```java
// ❌ ANTI-PATTERN in production business logic:
public void processBatch() {
    executeHeavyCalculations();
    System.gc(); // "Please JVM, run a full Garbage Collection now"
}
```

**Why it is a request, not a command:**
- In the JVM specification, `System.gc()` is a non-binding hint.
- When executed, HotSpot defaults to triggering an immediate, synchronous **Stop-The-World Full GC**, halting all application threads for hundreds of milliseconds or seconds.

**Legitimate Use Cases:**
- Microbenchmarking fixtures (e.g. JMH warmup loops).
- Test suites asserting reference cleanup (`WeakReference`).
- Manually purging dead objects prior to capturing a Heap Dump.

---

## 🟡 Middle Level

### Why Calling `System.gc()` Degrades Performance

1. **Monolithic Full GC Stop:** Halts all application threads to perform whole-heap marking and compaction.
2. **Disrupts Adaptive GC Heuristics:** Modern collectors (G1, ZGC) dynamically calculate Eden expansion and IHOP based on observed allocation rates; manual calls discard these statistical models.
3. **Premature Evacuation:** Collects Eden when it might be 80% empty, wasting CPU cycles on premature young generation sweeps.

### The Direct Memory (`DirectByteBuffer`) Conundrum

```java
// Allocates native OS RAM outside the JVM Heap:
ByteBuffer direct = ByteBuffer.allocateDirect(100 * 1024 * 1024);
```

#### The Internal NIO Trigger:
1. Native off-heap allocations via `DirectByteBuffer` rely on `PhantomReference` / `Cleaner` instances to deallocate native memory.
2. If application heap churn is low, the JVM Heap never fills up, and the GC does not run.
3. When native direct memory is exhausted, the JDK internal memory allocator (`jdk.internal.misc.Bits`) **explicitly calls `System.gc()`** to force phantom cleanup and reclaim native buffers!

## 🔴 Senior Level

### Production JVM Configuration Flags

```bash
# 1. Completely ignore all System.gc() calls (Silently discarded):
-XX:+DisableExplicitGC

# 2. Transform System.gc() into a non-blocking background concurrent cycle:
-XX:+ExplicitGCInvokedConcurrent
```

> [!CAUTION]
> **The `-XX:+DisableExplicitGC` Trap:** Disabling explicit GC completely can cause **native off-heap memory exhaustion (`OutOfMemoryError: Direct buffer memory`)** in high-throughput Netty / gRPC applications because `Bits.reserveMemory()` can no longer trigger emergency phantom reference cleanup!
> In production, **always prefer `-XX:+ExplicitGCInvokedConcurrent`**.

### External On-Demand Invocations via `jcmd`

Never add `System.gc()` into Java source code. If you need to trigger a collection on a running production JVM for diagnostic purposes, invoke it externally via the JDK CLI:

```bash
# Triggers a garbage collection externally without modifying code:
jcmd <PID> GC.run
```

### Diagnosing Rogue `System.gc()` Invocations

If your production monitoring alerts you to periodic Full GC pauses, verify whether a third-party library is invoking explicit GC:

```bash
# Enable unified GC logging to track explicit GC triggers:
-Xlog:gc*

# Look for this diagnostic tag in the log:
# [gc,start] GC(12) Pause Full (System.gc())
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Mechanism:** `System.gc()` and `Runtime.getRuntime().gc()` submit a hint to the JVM, which defaults to triggering a Stop-The-World Full GC.
- **Production Rule:** Never invoke `System.gc()` in business application logic.
- **Direct Memory Exception:** NIO `DirectByteBuffer` internally calls `System.gc()` when native off-heap memory is exhausted to trigger `Cleaner` deallocation.
- **`-XX:+DisableExplicitGC`:** Ignores `System.gc()`, but can cause native memory leaks with direct buffers.
- **`-XX:+ExplicitGCInvokedConcurrent`:** Production best practice — turns explicit GC requests into non-blocking background concurrent cycles.
- **Diagnostic Trigger:** Use `jcmd <pid> GC.run` to trigger on-demand diagnostic collections externally.

**Common Follow-up Questions:**
- *"Why is `-XX:+ExplicitGCInvokedConcurrent` preferred over `-XX:+DisableExplicitGC`?"* → It prevents Stop-The-World Full GC pauses while still allowing Direct Memory allocators (NIO / Netty) and RMI Distributed Garbage Collection to trigger concurrent background cleanup.
- *"How can you find which library in your project is calling `System.gc()`?"* → Run Java Flight Recorder (JFR) and filter for the `System GC` event, which captures the exact calling thread and stack trace.
- *"Can the JVM ignore a `System.gc()` call?"* → Yes, if `-XX:+DisableExplicitGC` is set, or if the underlying collector implementation chooses not to prioritize explicit requests.

**Red Flags (DO NOT Say):**
- ❌ *"Calling `System.gc()` forces the JVM to instantly free all memory on the current line."* (It is an asynchronous/synchronous hint, not an instantaneous memory eraser).
- ❌ *"Setting `-XX:+DisableExplicitGC` is 100% safe for all Java applications."* (It can break direct byte buffer deallocation, causing native memory OOMs).
- ❌ *"I add `System.gc()` after heavy database batch jobs to keep memory clean."* (This is an anti-pattern that creates severe latency spikes and disrupts GC heuristics).
