# What is ZGC?

---

## 🟢 Junior Level

The **Z Garbage Collector (ZGC)** is an ultra-low-latency, scalable Garbage Collector designed to manage heaps ranging from a few megabytes to **16 Terabytes** while maintaining **sub-millisecond (< 1.0 ms) Stop-The-World pause times**, regardless of total heap size.

**Where it is used:** High-Frequency Trading (HFT), real-time financial clearing engines, gaming servers, and ultra-strict SLA microservices (<10ms p99 latency).

```
  ┌────────────────────────────────────────────────────────┐
  │                 G1 GC vs. ZGC Latency                  │
  ├────────────────────────────────────────────────────────┤
  │ G1 GC Pause:  [ 20ms ................. 200ms ] (STW)   │
  │ ZGC Pause:    [ < 1ms ] (Constant across 16 TB Heaps!) │
  └────────────────────────────────────────────────────────┘
```

**The Trade-off:** ZGC achieves <1ms pauses by running almost all phases concurrently, which trades away **5%–10% of raw throughput** compared to G1 or Parallel GC due to **Load Barriers**.

## 🟡 Middle Level

### The Three Architectural Pillars of ZGC

```
  ┌─────────────────────────────────────────────────────────────────────────────────────────┐
  │ 1. Colored Pointers                                                                     │
  │    Encodes GC metadata directly into the upper bits (42–45) of 64-bit reference pointers│
  ├─────────────────────────────────────────────────────────────────────────────────────────┤
  │ 2. Load Barriers & Self-Healing                                                         │
  │    Intercepts reference reads; if an object was relocated, automatically heals pointer  │
  ├─────────────────────────────────────────────────────────────────────────────────────────┤
  │ 3. Concurrent Evacuation (Relocation)                                                   │
  │    Copies live objects to clean pages in parallel while application threads execute     │
  └─────────────────────────────────────────────────────────────────────────────────────────┘
```

### Colored Pointers Explained

On 64-bit CPU architectures, ZGC utilizes the reference pointer's upper bits as metadata tags:

```
  64-Bit Reference Pointer in ZGC:
  +-------------------+-------------+-----------------------------------------------+
  | 16 Unused Bits    | 4 Color Bits| 44 Address Bits (Addresses up to 16 Terabytes)|
  +-------------------+-------------+-----------------------------------------------+
                      | | | |
                      | | | +-- Finalizable
                      | | +---- Remapped (Pointer is clean and points to new address)
                      | +------ Marked1
                      +-------- Marked0
```

Because metadata is embedded in the pointer itself, ZGC determines whether an object is alive or relocated **without dereferencing the object in heap memory**.

## 🔴 Senior Level

### Load Barriers & Self-Healing Mechanism

Unlike G1 (which uses Write Barriers on assignment), ZGC uses **JIT-compiled Load Barriers** on reference dereferences (`Object ref = container.field`):

```
  Thread reads reference: `Person p = company.ceo;`
                            │
                            ▼
  1. Load Barrier checks the `Remapped` bit on the pointer
                            │
              ┌─────────────┴─────────────┐
              ▼ (Bit is set)              ▼ (Bit is NOT set)
      [ Return immediately ]     [ Object has moved! ]
      (Zero latency path)                 │
                                          ▼
                                 2. Lookup new address in Forwarding Table
                                          │
                                          ▼
                                 3. Update `company.ceo` pointer via atomic CAS
                                          │
                                          ▼
                                 4. Return new address to caller (Self-Healed!)
```

The next thread reading `company.ceo` finds the `Remapped` bit already set and proceeds with zero delay.

### Virtual Memory Multi-Mapping

To allow the CPU hardware to dereference 64-bit colored pointers without masking off the metadata bits in hardware registers, ZGC uses **OS Page Multi-Mapping**:
- The same physical memory page is mapped into **3 distinct virtual address spaces** (corresponding to `Marked0`, `Marked1`, and `Remapped`).
- Regardless of which color bit is active, the CPU memory controller points to the exact same physical RAM cell.

### Generational ZGC (Java 21+ JEP 439)

Prior to Java 21, ZGC was single-generational, requiring whole-heap concurrent marking and triggering **Allocation Stalls** under high churn.

**Generational ZGC (Java 21+)** separates Young and Old generations:
- Runs high-frequency, ultra-lightweight Young GC cycles concurrently.
- Reduces CPU overhead by **~50%**, virtually eliminating Allocation Stalls.

```bash
# Enable Generational ZGC in Java 21+:
java -XX:+UseZGC -XX:+ZGenerational -jar app.jar
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Primary Feature:** Sub-millisecond (<1ms) pause times on heaps up to **16 Terabytes**.
- **Colored Pointers:** Embeds GC metadata (Marked0, Marked1, Remapped) directly into the pointer bits (42–45).
- **Load Barriers:** Intercepts reference reads, performing atomic **Self-Healing** pointer updates when objects are relocated.
- **Concurrent Evacuation:** Relocates objects concurrently without Stop-The-World application freezes.
- **Generational ZGC (Java 21):** Adds generational separation to ZGC, halving CPU consumption and eliminating allocation stalls.
- **Platform Constraint:** Requires 64-bit OS architectures (x86_64, AArch64).

**Common Follow-up Questions:**
- *"Why does ZGC use Load Barriers instead of Write Barriers?"* → Because ZGC moves objects concurrently while application threads are reading them; a Load Barrier ensures that a thread reading a relocated object is immediately redirected to the new address.
- *"What is an Allocation Stall in ZGC?"* → A state where application allocation rate exceeds the speed of concurrent GC marking/relocation, forcing threads to block until memory is freed.
- *"Why is ZGC not ideal for CPU-bound batch workloads?"* → Load Barriers add ~5–10% CPU overhead to reference reads, reducing raw batch computation throughput compared to Parallel GC.

**Red Flags (DO NOT Say):**
- ❌ *"ZGC uses Write Barriers just like G1 GC."* (ZGC fundamentally relies on Load Barriers on pointer read).
- ❌ *"ZGC pause times increase linearly as the Heap grows from 10GB to 10TB."* (Pause times remain constant at <1ms because STW phases only scan root thread stacks).
- ❌ *"ZGC works on 32-bit JVMs."* (Colored Pointers strictly require 64-bit virtual address architectures).
