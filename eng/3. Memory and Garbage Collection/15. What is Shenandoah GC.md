# What is Shenandoah GC?

---

## 🟢 Junior Level

**Shenandoah GC** is an ultra-low-latency Garbage Collector originally developed by Red Hat for the OpenJDK community, designed to achieve **sub-millisecond (< 1.0 ms) Stop-The-World pause times** by performing **Concurrent Evacuation (Compaction)** alongside live application threads.

**Core Innovation:** Unlike G1 GC (where live object evacuation halts all mutator threads in a Stop-The-World pause), Shenandoah moves and compacts live objects **concurrently while the application continues processing user requests**.

```
  Collector Pause Mechanics Comparison:
  ┌────────────────────────────────────────────────────────┐
  │ G1 GC:        [ Marking (Conc) ] ──> [ Evacuation (STW Pause: 50-200ms) ]
  │ Shenandoah:   [ Marking (Conc) ] ──> [ Evacuation (CONCURRENT: 0ms STW) ]
  └────────────────────────────────────────────────────────┘
```

- **Primary Flag:** `-XX:+UseShenandoahGC`
- **When to Choose:** Real-time low-latency systems where ZGC is unavailable or when deploying lightweight containers built on **Alpine Linux (`musl libc`)**.

## 🟡 Middle Level

### From Brooks Pointers to Modern Load-Reference Barriers (LRB)

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │              Legacy Brooks Pointers (Historic)         │          Modern Load-Reference Barriers (LRB)          │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Added an 8-byte forwarding pointer to EVERY header   │ • No object header memory bloat                        │
  │ • Wasted 8 bytes per object (~15–20% heap footprint)   │ • JIT-inserted barrier intercepts reference reads/writes│
  │ • Obsolete in modern JDKs                              │ • Uses CAS to safely resolve forwarded object addresses│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### Shenandoah Operational Lifecycle

```
  1. Init Mark (STW: ~0.5ms) ──> Scans initial GC Roots
                                   │
                                   ▼
  2. Concurrent Marking ──> Traverses live object graph in background
                                   │
                                   ▼
  3. Final Mark (STW: ~0.5ms) ──> Completes marking and selects Collection Set (C-Set)
                                   │
                                   ▼
  4. Concurrent Evacuation ──> Copies live objects to clean regions concurrently!
                                   │
                                   ▼
  5. Concurrent Update References ──> Updates remaining pointers to new addresses concurrently
```

## 🔴 Senior Level

### The 3 Degradation Tiers of Shenandoah

When memory allocation pressure spikes beyond the collector's evacuation capacity, Shenandoah degrades gracefully through three distinct operational modes:

```
  [ Normal Concurrent Mode ] ──(<1ms Pauses)──> Lowest Latency
             │ (Allocation rate outpaces concurrent evacuation)
             ▼
  [ Degenerated GC Mode ] ──(STW Pause)──> Pauses mutators to finish evacuation fast
             │ (Heap is completely exhausted before evacuation completes)
             ▼
  [ Full GC Mode ] ──(Multi-Second STW)──> Monolithic single-threaded compact
```

> [!TIP]
> If logs report frequent `Degenerated GC` cycles, increase concurrent GC thread allocations via `-XX:ConcGCThreads` or expand maximum heap headroom (`-Xmx`).

### Shenandoah vs. ZGC: Architectural Comparison

| Dimension | Shenandoah GC | ZGC |
|---|---|---|
| **Pointers & Metadata** | Standard uncolored pointers (in-memory LRB) | **Colored Pointers** (metadata in pointer bits) |
| **Virtual Memory Engine** | Standard OS memory pages | **Multi-Mapping** (3 virtual pages per physical page) |
| **C-Library Compatibility** | Excellent on **Alpine Linux (`musl libc`)** | Historically tailored for `glibc` |
| **Generational Support** | Generational mode (Java 21+) | Generational ZGC (Java 21+) |

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Intent:** Open-source ultra-low-latency collector (Red Hat / OpenJDK) achieving <1ms pause times via **Concurrent Evacuation**.
- **Load-Reference Barrier (LRB):** Intercepts pointer reads/writes, returning the forwarded address if an object has moved without requiring extra header words.
- **Concurrent Update References:** Pointer addresses are rewired concurrently while application threads run.
- **3 Operating Tiers:** Concurrent Mode $\to$ Degenerated GC (STW fallback) $\to$ Full GC.
- **Alpine Compatibility:** Highly stable and performant in minimal container base images using `musl libc`.

**Common Follow-up Questions:**
- *"What is the main difference between Shenandoah and G1 GC?"* → G1 evacuates objects during a Stop-The-World pause; Shenandoah evacuates and compacts objects concurrently with live mutator execution.
- *"What is Degenerated GC in Shenandoah?"* → A fallback mode where Shenandoah halts mutator threads (STW) to quickly finish an active evacuation cycle before the heap runs out of space.
- *"Why did Shenandoah move away from Brooks Pointers?"* → Brooks Pointers required adding an extra 8-byte pointer to every object header, creating a 10–20% RAM memory penalty. Modern Load-Reference Barriers eliminate this overhead.

**Red Flags (DO NOT Say):**
- ❌ *"Shenandoah uses Colored Pointers just like ZGC."* (ZGC uses Colored Pointers; Shenandoah uses standard pointers with Load-Reference Barriers).
- ❌ *"Shenandoah has no Stop-The-World pauses at all."* (It still requires micro-pauses for Init Mark, Final Mark, and Init Update References, but each takes $<0.5\text{ms}$).
- ❌ *"Degenerated GC is a normal, healthy operating state."* (It indicates allocation pressure is outpacing GC throughput).
