# When does an object become eligible for GC?

---

## 🟢 Junior Level

An object in Java becomes **eligible for Garbage Collection** the exact moment it becomes **unreachable from any GC Root** along any active reference chain in the application.

**The Golden Rule:** If there is no live path connecting a known **GC Root** to the object in heap memory, the object is considered dead and will be reclaimed during a future GC cycle.

```java
public void executeTask() {
    User user1 = new User("Alice"); // user1 is reachable from the Stack frame
    user1 = null;                    // Alice instance is now unreachable -> GC Eligible!

    User user2 = new User("Bob");
    // When executeTask() returns, user2's stack frame pops -> Bob instance becomes GC Eligible!
}
```

### The "Islands of Isolation" Rule

Even if two or more objects reference each other strongly, if the entire group is disconnected from all GC Roots, the entire **island of isolation** is eligible for collection:

```
  [ GC Roots ] (No live references pointing to Island)
       │
       ✕
  ┌──────────┐   references   ┌──────────┐
  │ Object A │ ─────────────> │ Object B │
  │          │ <───────────── │          │
  └──────────┘   references   └──────────┘
  (Both A and B are collected together despite referencing each other!)
```

## 🟡 Middle Level

### Reference Strength Hierarchy (`java.lang.ref`)

Java provides 4 distinct tiers of object reachability:

| Reference Type | When It Is Reclaimed by GC | Primary Use Case |
|---|---|---|
| **Strong Reference** | **Never**, as long as reachable from a GC Root | Core application business domain entities |
| **Soft Reference (`SoftReference<T>`)** | Only when JVM encounters **memory pressure** before OOM | Memory-sensitive caches (e.g. image buffers) |
| **Weak Reference (`WeakReference<T>`)** | On the **very next GC cycle**, regardless of free RAM | Canonical mappings, `WeakHashMap`, metadata tags |
| **Phantom Reference (`PhantomReference<T>`)** | After finalization; `.get()` always returns `null` | Post-mortem native resource cleanup (`Cleaner`) |

```java
// Soft Reference Usage:
SoftReference<HeavyReport> softReport = new SoftReference<>(new HeavyReport());
HeavyReport report = softReport.get(); // Returns null if JVM freed it under memory pressure!

// Weak Reference Usage:
Map<SessionKey, UserMetadata> registry = new WeakHashMap<>();
// When SessionKey is no longer strongly referenced elsewhere, the entry is evicted automatically!
```

## 🔴 Senior Level

### JIT Early Reachability & `Reference.reachabilityFence()`

Under aggressive C2 JIT optimization, **an object can become GC-eligible before its enclosing method has finished executing**:

```java
public void processNativeFile() {
    NativeFileReader reader = new NativeFileReader("/data.bin");
    long handle = reader.getNativeHandle();
    
    // The JIT compiler detects that 'reader' is never accessed again in this method!
    // -> GC can collect 'reader' and trigger its Cleaner WHILE nativeRead() is still running!
    executeLongNativeRead(handle); // 💥 CRASH: Native Segfault if native memory was closed early!
}
```

#### ✅ Modern Fix (Java 9+ `reachabilityFence`):
```java
public void processNativeFile() {
    NativeFileReader reader = new NativeFileReader("/data.bin");
    long handle = reader.getNativeHandle();
    try {
        executeLongNativeRead(handle);
    } finally {
        // Guarantees 'reader' remains strongly reachable until this line completes:
        Reference.reachabilityFence(reader);
    }
}
```

### The Death of `finalize()` and Object Resurrection

In legacy Java, overriding `protected void finalize()` allowed an object to execute cleanup before collection. However:
1. **Object Resurrection:** An object could assign `this` to a static collection inside `finalize()`, resurrecting itself into a live GC Root chain!
2. **GC Thread Bottlenecks:** Objects with finalizers must survive at least one extra GC cycle and are queued into a single-threaded `Finalizer` queue, causing massive memory leaks.

> [!IMPORTANT]
> `finalize()` was **deprecated in Java 9** and is slated for removal. Modern applications must use **`java.lang.ref.Cleaner`** or **`AutoCloseable`** with `try-with-resources`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Eligibility Trigger:** An object is eligible for GC when it cannot be reached by traversing reference pointers starting from any **GC Root**.
- **Islands of Isolation:** Circular references ($A \to B \to A$) do not prevent collection if the cluster is unreachable from GC Roots.
- **Reference Tiers:** Strong (never cleared if reachable), Soft (cleared on low memory), Weak (cleared on next GC), Phantom (enqueued after death).
- **JIT Liveness:** JIT compilers can treat a local variable as dead *before* the method returns if it is no longer dereferenced.
- **`reachabilityFence`:** Prevents premature collection and native resource cleanup during long JNI executions.
- **Deprecation:** `finalize()` is deprecated; use `java.lang.ref.Cleaner` or `try-with-resources`.

**Common Follow-up Questions:**
- *"When exactly does `SoftReference` clear objects?"* → Based on the formula: $\text{FreeMemory (MB)} \times \text{-XX:SoftRefLRUPolicyMSPerMB}$ (default is 1000ms per MB of free heap).
- *"Why does `PhantomReference.get()` always return `null`?"* → To prevent resurrecting a dying object that has already been scheduled for memory reclamation.
- *"How does `WeakHashMap` clean up its keys?"* → Its internal `Entry` class extends `WeakReference<K>`; when keys are collected, references are enqueued to a `ReferenceQueue` and polled on subsequent map operations.

**Red Flags (DO NOT Say):**
- ❌ *"An object is collected immediately when you assign `obj = null`."* (Setting a variable to null makes the instance *eligible*; actual collection happens during the next GC cycle).
- ❌ *"Cyclic references between two objects will always cause a memory leak in Java."* (Tracing GC easily collects unreferenced cyclic islands).
- ❌ *"Overriding `finalize()` is the standard way to clean up database connections."* (Deprecated since Java 9 due to performance hazards and thread blocking; use `AutoCloseable`).
