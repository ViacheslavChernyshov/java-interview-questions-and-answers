# What are generations in GC?

---

## 🟢 Junior Level

The JVM partitions heap memory into **Generations** based on the expected **lifespan of objects**, applying optimized collection algorithms to each area.

**Simple analogy:**
- **Young Generation:** Disposable paper napkins — used once and discarded immediately.
- **Old Generation:** Heavy winter coats — kept and reused for years.
- **Metaspace:** Architectural blueprints — stored in native OS memory to describe how things are built.

```
  ┌────────────────────────────────────────────────────────┐
  │                    JVM HEAP MEMORY                     │
  ├────────────────────────────────────┬───────────────────┤
  │      Young Generation (1/3)        │  Old Gen (2/3)    │
  │  ┌──────────┬──────────┬─────────┐ │  ┌──────────────┐ │
  │  │   Eden   │ Survivor │Survivor │ │  │   Tenured    │ │
  │  │  (80%)   │ S0 (10%) │S1 (10%) │ │  │ (Long-Lived) │ │
  │  └──────────┴──────────┴─────────┘ │  └──────────────┘ │
  └────────────────────────────────────┴───────────────────┘
```

| Memory Generation | What It Stores | Collection Frequency & Algorithm |
|---|---|---|
| **Young Generation** | Freshly created objects (`new`) | Frequent Minor GC (Copying / Evacuation) |
| **Old Generation** | Long-lived survivors and singletons | Infrequent Major/Mixed GC (Mark-Sweep-Compact) |
| **Metaspace** | Class metadata, method bytecodes | Native RAM; collected on ClassLoader unload |

## 🟡 Middle Level

### The Weak Generational Hypothesis

Decades of enterprise workload telemetry demonstrate two core principles:
1. **Infant Mortality:** Over 95% of allocated objects die within milliseconds of creation (transient DTOs, method local strings, stream buffers).
2. **Longevity Clustering:** Objects that survive multiple collection passes have high probability of remaining referenced indefinitely (caches, connection pools, Spring singletons).

### Object Progression Lifecycle

```
  1. `new User()` ──> Allocated in Eden Space via thread-local TLAB
                           │
                           ▼ (Minor GC runs)
  2. Live Objects ──> Copied to Survivor Space S0 (Tenuring Age = 1)
                           │
                           ▼ (Subsequent Minor GCs: ping-pong S0 <-> S1)
  3. Surviving Objects ──> Age increments on each cycle (Age 1 -> 2 -> ... -> 15)
                           │
                           ▼ (Age exceeds `-XX:MaxTenuringThreshold`)
  4. Promoted ──> Tenured into Old Generation!
```

### Premature Promotion Hazards

If Survivor spaces (S0/S1) are undersized relative to allocation spikes, short-lived objects are forced into the **Old Generation prematurely**, triggering frequent, expensive **Full GC pauses**.

## 🔴 Senior Level

### Cross-Generational Reference Tracking: Card Tables & Write Barriers

A Young GC must not scan the entire Old Generation to discover references pointing from Old Gen into Young Gen:

```
  Old Generation Memory (Divided into 512-byte Cards):
  [ Card 0 ] [ Card 1 ] [ Card 2 (DIRTY) ] [ Card 3 ] ...
                               │
                               ▼
        points to ──> [ Young Gen Object in Eden ]
```

1. Whenever an application thread executes `oldObject.field = youngObject`, the JIT compiler triggers a hardware-level **Write Barrier**:
   $$\text{CardTable}[\text{Address} \gg 9] = \mathbf{DIRTY}$$
2. During Minor GC, the collector scans **only dirty cards**, reducing root discovery time from seconds to milliseconds.

### Modern Evolution: Generational ZGC (Java 21+ JEP 439)

Originally, ZGC was single-generational (collecting the entire heap concurrently). In Java 21, **Generational ZGC** introduced separate Young and Old generation partitions:
- Collects Young Gen frequently with ultra-fast concurrent evacuated marking.
- Reduces CPU overhead by **~50%** compared to non-generational ZGC while preserving **sub-millisecond (<1ms) pause guarantees**.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Intent:** Leverage the Weak Generational Hypothesis (most objects die young) to run fast Copying algorithms on Young Gen and compact algorithms on Old Gen.
- **Young Gen Structure:** Eden (80%) + Survivor 0 (10%) + Survivor 1 (10%).
- **Tenuring Age:** Incremented each time an object survives a Minor GC; promoted to Old Gen at `-XX:MaxTenuringThreshold` (max 15).
- **Card Table & Write Barrier:** 512-byte dirty card tracking that eliminates the need to scan Old Gen during Minor GCs.
- **Metaspace:** Native off-heap memory storing loaded class metadata (replaces legacy PermGen).
- **Generational ZGC (Java 21):** Extends ZGC with generational collection, halving CPU consumption.

**Common Follow-up Questions:**
- *"Why are there two Survivor spaces (S0 and S1)?"* → To execute compaction by evacuation: live objects from Eden and the active Survivor space are copied to the empty Survivor space, leaving the previous areas completely clean without fragmentation.
- *"Why does an object bypass Survivor spaces and go directly to Old Gen?"* → If an object is larger than the Survivor space capacity or exceeds $50\%$ of a G1 region (Humongous Object), it is allocated directly in Old Gen.
- *"What is the difference between Minor GC, Major GC, and Full GC?"* → Minor GC collects only Young Gen; Major GC collects Old Gen; Full GC collects the entire Heap (Young + Old + Metaspace defragmentation).

**Red Flags (DO NOT Say):**
- ❌ *"Metaspace is located inside the JVM Heap."* (Metaspace is allocated in native OS RAM outside `-Xmx`).
- ❌ *"Objects in Java never move in memory once allocated."* (Copying collectors in Young Gen relocate surviving objects between Eden and Survivors on every Minor GC).
- ❌ *"Minor GC must scan the entire Old Generation to find live references."* (Card Tables and Write Barriers isolate Old-to-Young references efficiently).
