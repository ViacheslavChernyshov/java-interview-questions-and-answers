# What is a memory leak in Java?

---

## 🟢 Junior Level

In Java, a **Memory Leak** is not the physical loss of memory addresses (as in C/C++), but **unintentional object retention**: objects that are logically dead and no longer needed by application logic remain **strongly reachable from a GC Root**, preventing the Garbage Collector from reclaiming their memory.

**Simple analogy:** Forgetting to remove items from a shared company shopping cart. Even though the team has moved on to other projects, the cart retains all old items indefinitely, eventually exhausting the company budget.

```
  [ Live GC Root (e.g. Static Map) ]
                 │
                 ▼ (Accidental Strong Reference)
  [ Logically Dead Object (100 MB Payload) ] ──> GC Cannot Reclaim!
```

**Common Symptoms:**
- The application gradually consumes more RAM over days or weeks.
- GC pause times increase and CPU spikes to 100% as the collector struggles to find free space.
- The JVM inevitably crashes with `java.lang.OutOfMemoryError`.

## 🟡 Middle Level

### The Three Leak Domains in JVM Architecture

```
  ┌────────────────────────┬────────────────────────────────────────────────────────┐
  │      Memory Area       │                  Common Leak Mechanism                 │
  ├────────────────────────┼────────────────────────────────────────────────────────┤
  │ **1. On-Heap Leak**    │ Static collections, `ThreadLocal` without `.remove()`  │
  │ **2. Metaspace Leak**  │ ClassLoader leaks during dynamic code reload / deploy  │
  │ **3. Off-Heap Leak**   │ Unclosed `DirectByteBuffer` or native C/JNI allocations│
  └────────────────────────┴────────────────────────────────────────────────────────┘
```

### Diagnostic Patterns: The Sawtooth Baseline Creep

```
  Healthy JVM Heap (Sawtooth Pattern):
  Memory |   /\    /\    /\    /\    /\
         |  /  \  /  \  /  \  /  \  /  \
         | /    \/    \/    \/    \/    \  ──> Stable Memory Baseline
         └───────────────────────────────── Time

  JVM with a Memory Leak (Baseline Creep):
  Memory |               /\    /\   [ OOM Crash! ]
         |         /\   /  \  /  \      ▲
         |   /\   /  \ /    \/    \     │
         |  /  \ /    \                 │
         | /    \ ─────────────────────┴─ Rising Memory Baseline Floor!
         └───────────────────────────────── Time
```

In a healthy application, Full GC returns heap usage to a flat baseline. In a leaking application, the **post-GC baseline floor climbs continuously** until an `OutOfMemoryError` occurs.

## 🔴 Senior Level

### Memory Analysis: Shallow Heap vs. Retained Heap

When diagnosing heap dumps in **Eclipse MAT (Memory Analyzer Tool)**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                     Shallow Heap                       │                     Retained Heap                      │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • The physical memory consumed by the object ITSELF   │ • The total memory that would be FREED if this object  │
  │   (Object header + immediate primitive/pointer fields)│   were garbage collected.                              │
  │ • e.g. A `HashMap` instance shallow size = **48 bytes**│ • e.g. That same `HashMap` retaining **2.5 GB** of data│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> When investigating memory leaks, **always inspect the Dominator Tree by Retained Heap size**, not Shallow Heap size!

### ClassLoader & Metaspace Leaks

In enterprise application servers (e.g. Tomcat, OSGi containers), deploying updated WAR files without restarting the JVM can leak entire ClassLoaders:
1. `AppClassLoader` loads 2,000 application classes (`InstanceKlass` in Metaspace).
2. A single static reference or un-deregistered JDBC driver in `DriverManager` holds a reference to one class from that `ClassLoader`.
3. Because every class holds a reference to its `ClassLoader`, and the `ClassLoader` holds references to *all* classes it loaded, **the entire ClassLoader tree and all 2,000 classes remain pinned in Metaspace**, resulting in `OutOfMemoryError: Metaspace`.

### Production Crash Remediation in Kubernetes

In cloud-native microservice clusters, a node suffering an OOM leak can enter a "zombie state" (failing requests while health checks pass):

```bash
# Recommended Production Flags for Kubernetes Pods:
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/dumps/heapdump.hprof
-XX:+CrashOnOutOfMemoryError   # Immediately terminates pod, forcing K8s to restart it!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Unintentional retention of unused objects that remain strongly reachable from a GC Root.
- **Java vs C++:** C++ leaks unreferenced lost memory addresses; Java leaks unneeded objects pinned by live references.
- **Shallow vs Retained Heap:** Shallow is the object's own size; Retained is the total cascade of memory freed if the object is collected (use Dominator Tree in MAT).
- **Baseline Creep:** The post-GC memory baseline steadily drifts upward over time.
- **Top 3 Causes:** Unbounded static maps, `ThreadLocal` in thread pools, and ClassLoader leaks in application servers.
- **Production Best Practice:** Configure `-XX:+HeapDumpOnOutOfMemoryError` and `-XX:+CrashOnOutOfMemoryError`.

**Common Follow-up Questions:**
- *"Why does increasing `-Xmx` fail to solve a memory leak?"* → It merely delays the inevitable crash and prolongs Stop-The-World pause times as the heap fills with more garbage.
- *"How do you diagnose Off-Heap native memory leaks?"* → Enable Native Memory Tracking (`-XX:NativeMemoryTracking=detail`) and run `jcmd <pid> VM.native_memory baseline / detail.diff`.
- *"Why are ClassLoader leaks particularly dangerous?"* → A single leaked object can pin an entire `ClassLoader`, keeping thousands of classes, static fields, and metadata structures in Metaspace.

**Red Flags (DO NOT Say):**
- ❌ *"Memory leaks are impossible in Java because the Garbage Collector exists."* (GC only reclaims *unreachable* objects; objects pinned by unintentional references still leak).
- ❌ *"To fix a memory leak, simply double the maximum heap size (`-Xmx`)."* (Masks the underlying defect and causes longer GC pauses before crashing).
- ❌ *"Shallow Heap is the most important metric when analyzing memory dumps in Eclipse MAT."* (Retained Heap reveals the actual memory held hostage).
