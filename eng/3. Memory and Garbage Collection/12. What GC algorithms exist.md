# What GC algorithms exist?

---

## 🟢 Junior Level

A **Garbage Collection Algorithm** defines the strategy and mechanics used by the JVM to discover unreachable objects, reclaim their memory, and reorganize the remaining live objects to avoid heap fragmentation.

### 3 Core Algorithmic Building Blocks

| Strategy | Operational Mechanism | Best Suited For |
|---|---|---|
| **Copying (Evacuation)** | Evacuates live objects to an empty space and wipes the source in bulk. | **Young Generation** (where 95%+ of objects are dead). |
| **Mark-Sweep** | Traverses live objects and adds dead object addresses to a **Free List**. | **Old Generation** when minimizing relocation overhead. |
| **Mark-Compact** | Traverses live objects and **slides them contiguously** to heap start. | **Full GC** to completely eliminate memory fragmentation. |

```
  ┌────────────────────────────────────────────────────────┐
  │                 THE GC TRADEOFF TRIANGLE               │
  │                      [ Latency ]                       │
  │                         / \                            │
  │                        /   \                           │
  │    [ Throughput ] ───────────── [ Footprint ]          │
  └────────────────────────────────────────────────────────┘
```
- **Throughput:** Maximizing CPU time spent on business logic rather than GC.
- **Latency:** Minimizing Stop-The-World (STW) pause times.
- **Footprint:** Minimizing extra RAM allocated for GC barriers and metadata.

## 🟡 Middle Level

### Production Garbage Collector Comparison Matrix

| Collector Flag | Target Workload | Typical Pause SLA | Heap Overhead |
|---|---|---|---|
| **Serial GC** (`-XX:+UseSerialGC`) | Single-core, small CLI tools (<512MB RAM) | 100ms – 1000ms | Extremely Low |
| **Parallel GC** (`-XX:+UseParallelGC`) | Batch computing, ETL pipelines, Big Data | 200ms – 5000ms | Low |
| **G1 GC** (`-XX:+UseG1GC`, Default) | General enterprise web apps, Spring Boot | **20ms – 200ms** | Medium (~5–10%) |
| **ZGC** (`-XX:+UseZGC`) | Real-time APIs, financial systems, massive heaps | **< 1.0 ms** | Medium (~10–15%) |
| **Shenandoah** (`-XX:+UseShenandoahGC`) | Ultra-low latency alternative for OpenJDK | **< 2.0 ms** | Medium (~10–15%) |
| **Epsilon GC** (`-XX:+UseEpsilonGC`) | Performance benchmarks, ephemeral lambdas | **0 ms** (No-Op) | None |

### Allocation Stall (The Hidden Latency Killer)

If application mutator threads allocate memory faster than a concurrent collector (like G1 or ZGC) can mark and sweep, free memory runs out completely:
- The allocating thread is forced to **freeze and wait** until GC worker threads free memory (**Allocation Stall**).
- If stalling persists, the JVM falls back to a catastrophic **Stop-The-World Full GC**.

## 🔴 Senior Level

### Barrier Mechanics: Write Barriers vs. Load Barriers

Concurrent garbage collectors enforce memory safety during live application execution using JIT-inserted hardware barriers:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │              Write Barrier (G1 Collector)              │               Load Barrier (ZGC Collector)             │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Triggered on: `obj.field = newRef` (Pointer Write)   │ • Triggered on: `ref = obj.field` (Pointer Read)       │
  │ • Updates Card Table or logs reference to SATB buffer  │ • Inspects **Colored Pointer bits** in the reference   │
  │ • Minimal CPU cost (~1–2ns per write)                  │ • If reference is un-relocated, triggers **Self-Healing│
  │ • Keeps GC informed of cross-region updates            │   relocation** before returning pointer to caller      │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### SATB (Snapshot-At-The-Beginning) vs. Incremental Update

- **SATB (G1 GC):** Preserves a logical snapshot of live objects at the start of concurrent marking. Any reference destroyed during the phase is logged to a buffer. 
  - *Trade-off:* Produces **Floating Garbage** (objects that die mid-cycle are collected on the *next* cycle), but mark convergence is deterministic.
- **Incremental Update (CMS legacy):** Re-marks objects whenever a new pointer is written to a black (already scanned) object.

### Epsilon GC: The No-Op Collector (JEP 318)

`-XX:+UseEpsilonGC` handles memory allocation via Bump-the-Pointer, but **never frees a single byte of memory**:
- When the heap fills up, the JVM immediately throws `OutOfMemoryError` and crashes.
- *Use cases:* Isolating memory allocation overhead during microbenchmarks (JMH) or running ultra-short ephemeral functions in AWS Lambda where the container is destroyed immediately after handling a single request.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **3 Fundamental Algorithms:** Copying (fast, zero fragmentation, used in Young Gen), Mark-Sweep (in-place free lists, fragmentation), Mark-Compact (defragments memory via sliding).
- **Default Collector:** **G1 GC** (default since Java 9), balances throughput and pause targets (20ms–200ms).
- **Low-Latency Standard:** **ZGC** achieves sub-millisecond pauses (<1ms) up to 16TB using Colored Pointers and Load Barriers.
- **Batch Processing Standard:** **Parallel GC** yields maximum CPU throughput where multi-second pauses are acceptable.
- **Barriers:** G1 uses **Write Barriers** (Card Tables / SATB); ZGC uses **Load Barriers** (Self-healing pointer updates on read).
- **Allocation Stall:** Occurs when allocation rate exceeds GC reclamation speed, freezing threads.

**Common Follow-up Questions:**
- *"Why is ZGC's throughput slightly lower than Parallel GC?"* → ZGC executes Load Barriers on every object reference read instruction (~5–10% CPU overhead) to achieve concurrent sub-millisecond pause times.
- *"What is Floating Garbage in G1 GC?"* → Objects that become unreachable *after* the initial SATB concurrent marking snapshot; they are safely swept in the subsequent collection cycle.
- *"When would you choose Serial GC over G1?"* → In tiny containerized microservices or CLI tools with $<512\text{MB}$ RAM and single-core CPUs where G1's multi-threaded overhead and region structures consume too much memory.

**Red Flags (DO NOT Say):**
- ❌ *"ZGC is always faster than Parallel GC in every scenario."* (Parallel GC delivers higher raw throughput for non-interactive batch workloads).
- ❌ *"Epsilon GC is a high-performance garbage collector for production web servers."* (Epsilon never reclaims memory and crashes immediately upon filling the heap).
- ❌ *"Mark-Sweep is faster than Copying in the Young Generation."* (Copying is significantly faster when 95%+ of objects are dead because work scales strictly with live objects).
