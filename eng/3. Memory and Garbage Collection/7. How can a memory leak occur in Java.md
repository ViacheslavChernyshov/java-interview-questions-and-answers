# How can a memory leak occur in Java?

---

## 🟢 Junior Level

A **Memory Leak** in Java occurs whenever an object is **no longer needed by application logic**, but a **strong reference path from a GC Root** remains intact, preventing the Garbage Collector from freeing its memory.

### Top 3 Common Leak Causes

1. **Static Collections Without Eviction:**
   ```java
   // ❌ LEAK: Static list grows indefinitely across the entire application lifetime!
   public class AuditLogger {
       private static final List<String> auditLogs = new ArrayList<>();
       public static void log(String msg) { auditLogs.add(msg); } // Never pruned!
   }
   ```
2. **`ThreadLocal` in Thread Pools:**
   ```java
   // ❌ LEAK: Forgetting to remove context in worker thread pools
   private static final ThreadLocal<SecurityContext> ctx = new ThreadLocal<>();
   public void doFilter() {
       ctx.set(loadUser());
       // Missing ctx.remove() in finally block!
   }
   ```
3. **Unclosed Native / I/O Streams:**
   ```java
   // ❌ LEAK: Unclosed streams pin file descriptors and native OS memory buffers
   InputStream is = new FileInputStream("large_data.bin");
   // Fixed via try-with-resources!
   ```

## 🟡 Middle Level

### 1. `ThreadLocal` Leak & Cross-Request Data Pollution

In web servers (e.g. Tomcat, Netty, Undertow), worker threads are **pooled and reused** across thousands of HTTP requests:

```java
// ❌ CRITICAL DEFECT: Memory Leak + Security Vulnerability!
public class UserFilter implements Filter {
    private static final ThreadLocal<UserSession> userContext = new ThreadLocal<>();

    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        userContext.set(authenticate(req));
        chain.doFilter(req, res);
        // If an exception occurs, or if remove() is omitted:
        // 1. UserSession remains pinned to the pooled thread forever (Memory Leak).
        // 2. Next request handled by this thread accesses the PREVIOUS user's session (Security Breach)!
    }
}

// ✅ PROPER PRODUCTION REMEDIATION:
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
    try {
        userContext.set(authenticate(req));
        chain.doFilter(req, res);
    } finally {
        userContext.remove(); // GUARANTEED CLEANUP!
    }
}
```

### 2. Non-Static Inner Classes & Anonymous Classes

Every non-static inner class holds an implicit synthetic field (`this$0`) pointing to its outer enclosing instance:

```java
public class HeavyReportGenerator {
    private final byte[] heavyData = new byte[50 * 1024 * 1024]; // 50 MB

    public Runnable createTask() {
        // ❌ Non-static inner class implicitly captures HeavyReportGenerator.this!
        return new Runnable() {
            @Override
            public void run() { System.out.println("Processing..."); }
        };
    }
}

// In another service:
Runnable task = reportGenerator.createTask();
backgroundQueue.submit(task); 
// HeavyReportGenerator (50 MB) CANNOT be garbage collected as long as 'task' sits in the queue!

// ✅ REMEDIATION: Use a static nested class or a lambda that does not reference outer fields!
public static class CleanTask implements Runnable {
    @Override public void run() { System.out.println("Processing..."); }
}
```

### 3. Unbounded Static Caching

```java
// ❌ WRONG: Simple HashMap as a cache
private static final Map<String, Report> CACHE = new ConcurrentHashMap<>();

// ✅ CORRECT: Bounded Cache with TTL & Maximum Size (Caffeine)
private static final Cache<String, Report> CACHE = Caffeine.newBuilder()
    .maximumSize(5_000)
    .expireAfterWrite(Duration.ofMinutes(15))
    .build();
```

## 🔴 Senior Level

### 4. ClassLoader & Metaspace Leaks (Dynamic Bytecode)

Dynamic code generators (CGLIB proxies, runtime Groovy scripts, un-cached `Proxy.newProxyInstance()`) compile bytecode directly into **Metaspace**:

```
  Dynamic Proxy Generator ──> Emits `Proxy$123.class` ──> Stored in Metaspace
```

- Each dynamic class loader allocates metadata in Metaspace.
- If classes are generated in a loop without caching, or if `AppClassLoader` holds references across redeployments, **Metaspace grows continuously until `OutOfMemoryError: Metaspace`**.
- *Diagnosis:* Monitor via `jcmd <pid> VM.metaspace` and enable `-Xlog:class+load=info,class+unload=info`.

### 5. Off-Heap Direct Memory Leaks (`DirectByteBuffer`)

```java
// Allocates memory directly from native OS RAM (outside JVM Heap):
ByteBuffer directBuffer = ByteBuffer.allocateDirect(100 * 1024 * 1024); // 100 MB Native RAM
```

#### The "Empty Heap" Native OOM Hazard:
1. `DirectByteBuffer` relies on a Java `PhantomReference` / `Cleaner` to free native memory when the Java wrapper object is garbage collected.
2. If application heap churn is low, **the JVM Heap remains mostly empty**, meaning the Garbage Collector **never triggers**.
3. Direct memory allocation continues in native OS RAM until the OS Kernel OOM-Killer violently kills the Java process!
- *Remediation:* Limit direct memory with `-XX:MaxDirectMemorySize=2g` and use pooled byte buffers (e.g. Netty `PooledByteBufAllocator`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`ThreadLocal` in Thread Pools:** Causes memory leaks and cross-request data leaks; **must always call `threadLocal.remove()` in a `finally` block**.
- **Non-Static Inner Classes:** Hold hidden strong references to `Outer.this`, keeping large enclosing classes alive.
- **Unbounded Static Maps:** Never use raw `HashMap` as a cache; use **Caffeine / Guava** with `maximumSize` and TTL.
- **Off-Heap Direct Memory:** `ByteBuffer.allocateDirect()` leaks native RAM if the heap is idle; configure `-XX:MaxDirectMemorySize`.
- **Metaspace Leaks:** Un-cached dynamic proxies or hot-reloading leaking `ClassLoader` references.
- **Listeners / Callbacks:** Registering listeners without unregistering causes the Lapsed Listener leak.

**Common Follow-up Questions:**
- *"Why is an anonymous `Runnable` dangerous when submitted to a long-lived ExecutorService?"* → If declared inside an instance method, it silently retains the outer instance, preventing the entire outer object from being garbage collected until the task finishes.
- *"How does `String.intern()` cause memory issues?"* → Interning unbounded unique strings (like UUIDs or logs) pollutes the native JVM `StringTable`, causing high hash collision chains and memory growth.
- *"Why does a thread pool prevent `ThreadLocal` variables from being collected?"* → In a pool, worker threads never terminate; their internal `ThreadLocalMap` entries remain reachable from the active thread GC Root.

**Red Flags (DO NOT Say):**
- ❌ *"Static collections are automatically cleaned up when memory is low."* (Static fields are permanent GC Roots; objects in static collections are never collected unless explicitly removed).
- ❌ *"Inner classes in Java are completely decoupled from their outer classes."* (Non-static inner classes retain an implicit strong pointer to the outer instance).
- ❌ *"Calling `System.gc()` is the best way to clean up unclosed streams."* (Streams must be deterministically closed via `try-with-resources`).
