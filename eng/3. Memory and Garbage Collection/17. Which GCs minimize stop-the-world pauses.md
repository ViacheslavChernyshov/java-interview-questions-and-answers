# Which GCs minimize stop-the-world pauses?

---

## 🟢 Junior Level

**Low-Latency Garbage Collectors** are specialized JVM engines designed to minimize or eliminate application Stop-The-World (STW) pauses by executing memory marking and object relocation **concurrently with live application threads**.

### The Big Three Low-Latency Collectors

1. **ZGC (`-XX:+UseZGC`):** Industry benchmark for low latency; guarantees **sub-millisecond (< 1.0 ms)** pauses on heaps up to 16TB.
2. **Shenandoah (`-XX:+UseShenandoahGC`):** OpenJDK alternative delivering **< 1.0 ms** pauses via concurrent evacuation.
3. **G1 GC (`-XX:+UseG1GC`):** Default balanced collector delivering predictable soft pause targets (**20ms – 200ms**).

```
  Stop-The-World Pause Time Comparison:
  ┌────────────────────────────────────────────────────────┐
  │ Parallel GC:  ████████████████████████ (500ms - 5000ms)│
  │ G1 GC:        ████ (20ms - 200ms)                      │
  │ Shenandoah:   ▌ (< 1.0ms)                              │
  │ ZGC:          ▌ (< 1.0ms)                              │
  └────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### Architectural Strategy Comparison

| Dimension | G1 GC | Shenandoah GC | ZGC (Java 21+) |
|---|---|---|---|
| **Max Pause Target** | 20ms – 200ms | < 1.0 ms | **< 1.0 ms** |
| **Marking Phase** | Concurrent (SATB) | Concurrent | Concurrent |
| **Evacuation Phase** | **Stop-The-World** | **Concurrent** | **Concurrent** |
| **Barrier Strategy** | Write Barrier (on pointer assign) | Load-Reference Barrier | Load Barrier + Colored Pointers |
| **Throughput Penalty** | Baseline (~0%) | -5% to -10% | -5% to -10% |
| **Max Supported Heap** | ~64 GB | ~100 GB+ | **Up to 16 Terabytes** |

### The Allocation Stall Threat

If a low-latency concurrent collector (like ZGC or Shenandoah) cannot evacuate regions as fast as high-throughput mutator threads allocate new objects, the JVM encounters an **Allocation Stall**:
- Application threads block and wait for the concurrent GC workers to finish sweeping.
- Under sustained memory starvation, pause times spike, degrading throughput worse than Parallel GC.

### Why Generational ZGC (Java 21+) is a Game Changer

In earlier Java versions, ZGC collected the entire heap concurrently, causing high CPU consumption. **Generational ZGC (JEP 439 in Java 21)**:
- Applies concurrent collection to young and old generations independently.
- **Reduces CPU barrier overhead by ~50%**, matching G1's throughput while keeping pause times firmly below 1 millisecond.

```bash
# Recommended Low-Latency Command Line (Java 21+):
java -XX:+UseZGC -XX:+ZGenerational -XX:ConcGCThreads=4 -Xms16g -Xmx16g -jar app.jar
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Lowest Latency Collectors:** **ZGC** and **Shenandoah** achieve sub-millisecond (<1ms) max pauses.
- **Concurrent Evacuation:** The secret to <1ms pauses is relocating/compacting objects *concurrently* while mutators read and write memory.
- **G1 Limitation:** G1 performs concurrent marking, but its evacuation/compaction phase is Stop-The-World (20ms–200ms).
- **Throughput Trade-off:** ZGC and Shenandoah trade 5–10% of raw throughput due to JIT Load Barriers.
- **Generational ZGC (Java 21):** Cuts CPU overhead in half, combining G1-like throughput with sub-millisecond latency.

**Common Follow-up Questions:**
- *"Why is G1 still the default collector instead of ZGC in modern Java?"* → G1 delivers higher raw CPU throughput for standard enterprise CRUD applications and small heap sizes (<4GB) where 50ms pauses are completely imperceptible.
- *"What happens if you run ZGC on a system with 95% CPU utilization?"* → Performance collapses because concurrent GC worker threads and Load Barriers compete with application mutator threads for saturated CPU cores.
- *"How do Load Barriers achieve concurrent evacuation?"* → When an application thread reads a reference to an object currently being evacuated, the Load Barrier intercepts the read, directs the thread to the new copy, and heals the pointer via CAS.

**Red Flags (DO NOT Say):**
- ❌ *"ZGC has zero performance trade-offs compared to Parallel GC."* (ZGC consumes 5–10% more CPU due to Load Barriers and concurrent GC worker threads).
- ❌ *"G1 GC moves objects concurrently without Stop-The-World pauses."* (G1's evacuation phase requires a Stop-The-World pause).
- ❌ *"You should always use ZGC for offline batch analytics jobs."* (Parallel GC is far superior for batch jobs because it maximizes raw CPU throughput).
