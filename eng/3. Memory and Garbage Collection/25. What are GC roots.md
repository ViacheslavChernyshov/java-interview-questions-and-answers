# What are GC roots?

---

## 🟢 Junior Level

A **GC Root (Garbage Collection Root)** is an initial, always-reachable anchor object from which the JVM's Tracing Garbage Collector begins traversing the live object graph during reachability analysis.

**Simple analogy:** A massive family tree. The roots at the top are the starting ancestors (GC Roots). Any branch or leaf connected to an ancestor is considered alive. Any disconnected fallen branch is garbage and is cleared away.

```
  [ GC ROOTS ] ──> [ Live Object 1 ] ──> [ Live Object 2 ]
                        │
                        ▼
                  [ Live Object 3 ]
                  
  [ Disconnected Object X ] <──> [ Disconnected Object Y ]  (Reclaimed by GC!)
```

**Core GC Roots Categories:**
1. **Thread Stack Variables:** Local variables and method parameters inside active stack frames.
2. **Static Variables:** Fields declared on loaded classes.
3. **Active Threads:** All running `java.lang.Thread` instances.
4. **JNI Handles:** Object references created by native C/C++ code.

## 🟡 Middle Level

### Complete Classification of JVM GC Roots

```
  JVM GC Root Anchors:
  ┌────────────────────────────────────────────────────────┐
  │ 1. Stack Local Variables & Method Parameters           │
  │    (All reference slots in active thread stack frames) │
  ├────────────────────────────────────────────────────────┤
  │ 2. Static Fields of Loaded Classes (System Dictionary) │
  ├────────────────────────────────────────────────────────┤
  │ 3. Active Running Thread Objects                       │
  ├────────────────────────────────────────────────────────┤
  │ 4. JNI Global & Local References (Native C Code)       │
  ├────────────────────────────────────────────────────────┤
  │ 5. Objects Used as Synchronization Monitors            │
  │    (Objects locked via `synchronized` or `wait()`)     │
  ├────────────────────────────────────────────────────────┤
  │ 6. JVM Internal System References                      │
  │    (Built-in ClassLoaders, OutOfMemory pre-allocations)│
  └────────────────────────────────────────────────────────┘
```

### JIT OopMaps: High-Speed Root Scanning

The JVM does not scan every raw byte of a thread's stack looking for pointers (which would be slow and might mistake an integer primitive for a memory address).

Instead, the JIT compiler produces **OopMaps (Ordinary Object Pointer Maps)** at each Safepoint:
- An **OopMap** is a compact bitmask detailing exactly which CPU registers and stack slots contain genuine object pointers at that execution instruction.
- When a GC pause begins, the collector reads the OopMap and inspects **only** the designated pointer slots, completing root scanning in sub-millisecond time.

## 🔴 Senior Level

### Thread-Local Handshakes (Java 10+ JEP 312)

Historically, scanning stack roots required halting **all application threads simultaneously** in a global Stop-The-World pause.

Modern JVMs leverage **Thread-Local Handshakes**:
- The Garbage Collector pauses and scans thread stacks **individually and asynchronously**.
- While Thread A is paused for stack scanning, Threads B, C, and D continue executing normal business transactions, dramatically reducing global application latency.

### Diagnosing Leaks via Eclipse MAT: Path to GC Roots

When debugging an `OutOfMemoryError` heap dump in Eclipse Memory Analyzer:

```
  Dominator Tree ──> Select Leaking Object ──> [ Path to GC Roots ] 
                                                   │
                                                   └──> Exclude Weak/Soft References
```

> [!TIP]
> Always **exclude Weak and Soft references** when inspecting the Path to GC Roots. Doing so isolates the exact **Strong Reference chain** (usually a static singleton, thread-pool `ThreadLocalMap`, or active cache) keeping the memory leak alive.

### JNI Global Reference Leaks (The Native Blind Spot)

If native C code allocates a global reference via `(*env)->NewGlobalRef(env, javaObj)` and forgets to execute `(*env)->DeleteGlobalRef()`, the Java object becomes a **permanent JNI Global GC Root**. 
- Eclipse MAT identifies these as `JNI Global` roots.
- *Blind Spot:* Local references created inside active native C functions are transient and cannot be tracked once the native method frame finishes without a heap dump.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** The fundamental starting nodes for Tracing Garbage Collection reachability analysis.
- **Top Root Categories:** Stack local variables, static class fields, active thread instances, JNI native handles, and synchronization monitor locks.
- **OopMaps:** JIT bitmasks mapping register and stack slot pointer offsets, avoiding full stack scans and false-pointer errors.
- **Thread Handshakes:** Allows HotSpot to scan individual thread roots independently without global STW stops.
- **Eclipse MAT:** Use *"Path to GC Roots (excluding soft/weak references)"* to uncover the strong reference chain causing a leak.

**Common Follow-up Questions:**
- *"Can an object become a GC Root temporarily?"* → Yes. An object locked inside a `synchronized (obj)` block or waiting in a `Finalizer` queue acts as a temporary GC Root until released.
- *"How do static variables act as GC Roots?"* → Static fields belong to the `java.lang.Class` instance, which is pinned by its `ClassLoader` in the JVM System Dictionary.
- *"Why does having 10,000 platform threads degrade GC performance?"* → Root scanning duration scales with the number of active threads; 10,000 thread stacks require scanning thousands of stack frames and OopMaps during GC pauses.

**Red Flags (DO NOT Say):**
- ❌ *"GC Roots are only static variables."* (Stack locals, active threads, and JNI handles are also primary GC Roots).
- ❌ *"The Garbage Collector scans every single byte of RAM from address 0 to find references."* (It uses OopMaps and Card Tables to scan only valid pointer slots).
- ❌ *"An object referenced by a WeakReference is considered a GC Root."* (Weak and Soft references do not prevent collection and are excluded from root reachability).
