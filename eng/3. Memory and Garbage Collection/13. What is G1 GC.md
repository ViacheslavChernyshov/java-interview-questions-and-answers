# What is G1 GC?

---

## 🟢 Junior Level

The **Garbage-First (G1) Garbage Collector** is the default, server-class Garbage Collector in Java (enabled by default since Java 9), designed for multi-gigabyte heaps with predictable, user-configurable pause time targets.

**The "Garbage-First" Concept:** Unlike legacy collectors that manage young and old spaces as contiguous physical memory blocks, G1 divides the heap into thousands of small **Regions** and prioritizes collecting the regions containing the **most garbage first** (maximizing reclaimed memory per millisecond of pause time).

```
  G1 Heap Partitioning (2,048 Dynamic Regions):
  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
  │ Eden │ Old  │ Free │ Eden │ Surv │ Old  │ Hum  │ Free │
  ├──────┼──────┼──────┼──────┼──────┼──────┼──────┼──────┤
  │ Old  │ Eden │ Surv │ Free │ Old  │ Free │ Eden │ Hum  │
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
  (Regions dynamically change roles: Eden, Survivor, Old, Humongous, Free)
```

**Key Advantages:**
- **Soft Real-Time Pause Target:** Configurable via `-XX:MaxGCPauseMillis=200` (default 200ms).
- **Incremental Compaction:** Continuously compacts memory by region evacuation, avoiding memory fragmentation.

## 🟡 Middle Level

### G1 Region Taxonomy & Sizing

The JVM dynamically sizes regions to yield approximately **2,048 regions** across the heap (region sizes range from **1MB to 32MB**, always a power of 2):
1. **Eden Regions:** Houses fresh allocations.
2. **Survivor Regions:** Houses objects surviving early Minor GCs.
3. **Old (Tenured) Regions:** Houses promoted long-lived objects.
4. **Humongous Regions:** Contiguous sequences of regions reserved for objects exceeding **50% of a single region size**.
5. **Free Regions:** Available pool awaiting allocation.

### The Two Core Internal Data Structures

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │                 Remembered Sets (R-Sets)               │                  Collection Sets (C-Sets)              │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Maintained **per region** ("Who points to me?")      │ • The dynamic list of regions chosen to be EVACUATED   │
  │ • Tracks cross-region reference pointers               │   in the current GC pause                              │
  │ • Eliminates the need to scan other regions during GC  │ • Young GC: C-Set = All Young Regions                  │
  │ • Updated asynchronously via concurrent Write Barriers │ • Mixed GC: C-Set = All Young + Highest-Yield Old Regs │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### G1 Operational Cycle

```
  1. Young GC (STW) ──> Evacuates all Eden/Survivor regions into clean regions
                             │
                             ▼ (Old Gen occupancy crosses IHOP = 45%)
  2. Concurrent Marking ──> SATB background scan calculates garbage density per region
                             │
                             ▼
  3. Remark (STW) ──> Finalizes SATB buffers and cleans empty regions
                             │
                             ▼
  4. Mixed GC (STW) ──> Evacuates all Young regions + selected dirtiest Old regions
```

## 🔴 Senior Level

### Evacuation Failure (To-Space Exhaustion)

When G1 performs region evacuation, it must copy surviving live objects into clean target regions:
- **The Failure:** If no free regions are available to receive surviving objects, G1 reports **To-space exhausted (Evacuation Failure)**.
- **The Consequence:** G1 aborts concurrent execution and falls back to a **monolithic, single-threaded Stop-The-World Full GC**, causing multi-second latency spikes.
- *Remediation:* Enlarge total heap (`-Xmx`), increase `-XX:G1ReservePercent=15` (reserve buffer), or lower `-XX:InitiatingHeapOccupancyPercent=35` to start concurrent marking earlier.

### Transparent G1 String Deduplication

G1 provides automated background deduplication of `byte[]` arrays inside `java.lang.String` instances:

```bash
# Enable background string deduplication:
-XX:+UseStringDeduplication
```
During region evacuation, G1 inspects candidate strings and points identical string values to a single shared `byte[]` array on the heap, typically saving **5%–15% total heap memory**.

### Production Sizing Rules for G1

1. **Never Hardcode `-Xmn`:** Setting a fixed young generation size completely disables G1's ability to expand or contract Young Gen to achieve `-XX:MaxGCPauseMillis`.
2. **Handle Humongous Objects:** If application logs show frequent `G1 Humongous Allocation` triggers, increase region size (e.g. `-XX:G1HeapRegionSize=16m`) to prevent direct Old Gen pollution.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Architecture:** Divides heap into ~2,048 dynamic regions (1MB–32MB: Eden, Survivor, Old, Humongous, Free).
- **Core Intent:** Garbage-First collects the regions with the highest proportion of garbage first to maximize throughput within the pause target (`-XX:MaxGCPauseMillis=200`).
- **R-Sets (Remembered Sets):** Per-region card tables recording incoming cross-region references, enabling isolated regional evacuation.
- **C-Sets (Collection Sets):** The set of regions evacuated in a single GC pause.
- **Mixed GC:** Evacuates all Young regions plus the most reclaimable Old Gen regions.
- **To-Space Exhausted:** Evacuation failure occurring when target free regions run out, triggering a fallback Full GC.
- **String Deduplication:** `-XX:+UseStringDeduplication` consolidates duplicate string byte arrays during GC.

**Common Follow-up Questions:**
- *"What is a Humongous Object in G1 and why is it dangerous?"* → Any object larger than 50% of a region size. It is allocated directly into contiguous Old Gen regions, causing heap fragmentation and early GC triggers.
- *"Why should you not set `-XX:MaxGCPauseMillis` to an unrealistic value like 5ms?"* → G1 will drastically shrink Young Gen to meet the pause SLA, causing hyper-frequent collections, throughput collapse, and eventual evacuation failure.
- *"How does SATB (Snapshot-At-The-Beginning) work in G1?"* → It captures the live object graph at marking start; any pointer modifications during concurrent marking are recorded via write barriers to prevent dropping live objects.

**Red Flags (DO NOT Say):**
- ❌ *"G1 allocates Young and Old generations in fixed, separate physical memory blocks."* (Regions are uniform and dynamically change generational roles).
- ❌ *"Setting `-Xmn2g` is a great way to optimize G1 GC."* (Hardcoding `-Xmn` disables G1's dynamic pause-time adjustment heuristics).
- ❌ *"G1 never experiences Full GC pauses."* (If evacuation fails or concurrent marking falls behind allocation rates, G1 falls back to an expensive Full GC).
