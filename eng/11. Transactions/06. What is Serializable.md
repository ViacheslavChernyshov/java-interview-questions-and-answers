# What is Serializable?

---

## 🟢 Junior Level

**Serializable** is the highest and strictest transaction isolation level defined by ANSI SQL.

It guarantees that the final state produced by concurrently executing transactions is mathematically equivalent to **some strictly sequential (serial) execution order**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Dirty Reads                                            │ ✅ **Strictly Prevented**                              │
  │ Non-Repeatable Reads                                   │ ✅ **Strictly Prevented**                              │
  │ Phantom Reads                                          │ ✅ **Strictly Prevented**                              │
  │ Write Skew & Read-Write Anomalies                      │ ✅ **Strictly Prevented**                              │
  │ Primary Trade-off                                      │ Requires **Automated Application Retry Logic**         │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
// Spring Declarative Serializable Configuration:
@Transactional(isolation = Isolation.SERIALIZABLE)
public void executeCriticalLedgerSettlement(SettlementOrder order) {
    // Completely immune to race conditions, phantom inserts, and write skew!
    ledgerRepository.process(order);
}
```

## 🟡 Middle Level

### Concurrency Engines: Strict 2PL vs. SSI

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Concurrency Approach         │ Strict Two-Phase Locking (2PL)   │ Serializable Snapshot Isolation (SSI)            │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Used In**                  │ Microsoft SQL Server (Default)   │ **PostgreSQL (9.1+)**                            │
  │ **Locking Behavior**         │ **Pessimistic:** Readers block   │ **Optimistic:** Non-blocking reads/writes        │
  │                              │ writers; writers block readers   │ via MVCC snapshots                               │
  │ **Conflict Resolution**      │ Threads stall in OS lock queues  │ Detects dependency cycles & **aborts with 40001**│
  │ **Throughput Under Contention│ Severely degraded by deadlocks   │ High throughput; requires application retry logic│
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Mandatory Requirement: Automated Retry Logic

Under Serializable isolation, database engines do not guarantee that every transaction will succeed on its first attempt. When a serialization conflict is detected, the database aborts the transaction with `SQLSTATE 40001`:

```java
// ✅ Mandatory Enterprise Pattern: Retry with Randomized Backoff (Jitter)
@Service
public class TreasuryService {

    @Retryable(
        retryFor = {CannotSerializeTransactionException.class},
        maxAttempts = 5,
        backoff = @Backoff(delay = 50, maxDelay = 1000, multiplier = 2.0, random = true)
    )
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public void transferTreasuryFunds(Long sourceId, Long targetId, BigDecimal amount) {
        accountRepository.debit(sourceId, amount);
        accountRepository.credit(targetId, amount);
    }
}
```

## 🔴 Senior Level

### PostgreSQL SSI Architecture: Predicate Locks & Dependency Cycles

PostgreSQL achieves full Serializability without read/write blocking using **Serializable Snapshot Isolation (SSI)**:

```
  1. Predicate Locks (SIREAD Locks):
     • Tracks what data a transaction has READ (tuple, page, or relation predicate).
     • Stored entirely in shared RAM memory (zero disk I/O).

  2. Anti-Dependency Tracking (rw-antidependencies):
     • When Transaction T1 reads data that Transaction T2 subsequently updates,
       an edge T1 ──► T2 is registered in the in-memory Dependency Serialization Graph.

  3. Dangerous Structure Detection:
     • A cycle in the dependency graph (e.g. T1 ──► T2 ──► T1) proves that no serial
       execution order exists that could produce this result.
     • PostgreSQL immediately aborts the incoming transaction with:
       "ERROR: could not serialize access due to read/write dependencies among transactions (40001)"
```

### Edge Cases and Production Traps

```
  1. Database Sequences (nextval):
     • Sequences are non-transactional. If a Serializable transaction generates an ID 
       via nextval() and subsequently aborts, the sequence ID is PERMANENTLY GAPPED.

  2. Read-Only Transaction Aborts:
     • Even pure SELECT queries running under Serializable can be aborted with 40001 
       if they read intermediate data participating in an active dependency cycle.
     • Fix: Declare @Transactional(isolation = Isolation.SERIALIZABLE, readOnly = true).

  3. Long-Running Transaction Hazard:
     • Long transactions expand the conflict window, exponentially increasing the 
       probability of serialization aborts and preventing dead tuple VACUUM cleanup.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Highest isolation level; mathematically equivalent to strict sequential execution.
- **Anomalies:** Prevents 100% of concurrency anomalies (Dirty, Non-Repeatable, Phantom, Write Skew).
- **PostgreSQL SSI:** Non-blocking MVCC using in-memory Predicate Locks (`SIREAD`) and Dependency Graph cycle detection.
- **Mandatory Retries:** Applications **must** implement retry logic (`@Retryable`) to handle `SQLSTATE 40001`.
- **Performance Cost:** 2x-10x lower throughput under heavy write contention due to abort rates.
- **Sequences:** `nextval()` increments are never rolled back upon transaction serialization failure.

**Common Follow-up Questions:**
- *"What is the difference between Two-Phase Locking (2PL) and Serializable Snapshot Isolation (SSI)?"* → 2PL blocks concurrent readers and writers using physical locks; SSI allows non-blocking execution via MVCC and detects dependency cycles at commit time, aborting conflicting transactions.
- *"Why can a read-only query abort under Serializable isolation?"* → If a read-only query reads state from an uncommitted cycle of transactions, it could observe non-serializable states; PostgreSQL aborts it to maintain global consistency.
- *"When should you avoid Serializable isolation?"* → On high-concurrency write-heavy tables, hot-spot counters, or batch jobs lasting longer than a few seconds.

**Red Flags (DO NOT Say):**
- ❌ *"Setting Serializable isolation means transactions will never fail or throw errors."* (Serializable transactions fail frequently with `CannotSerializeTransactionException` and require retries).
- ❌ *"PostgreSQL uses table-level locks for Serializable transactions."* (PostgreSQL uses non-blocking SSI with fine-grained in-memory predicate locks).
- ❌ *"Serializable isolation completely eliminates the need for database indexing."* (Without indexes, predicate locks promote to full-table locks, causing massive serialization conflict aborts).
