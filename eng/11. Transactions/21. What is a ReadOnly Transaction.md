# What is a ReadOnly Transaction?

---

## 🟢 Junior Level

A **ReadOnly Transaction** is a transaction marked with **`@Transactional(readOnly = true)`**, which signals to Spring, Hibernate, and the underlying database that the method executes **pure read operations**:

```java
@Service
public class UserService {

    @Autowired private UserRepository userRepository;

    @Transactional(readOnly = true) // Disables dirty checking & enables DB optimizations!
    public UserProfile getUserProfile(Long userId) {
        return userRepository.findProfileById(userId);
    }
}
```

```
  Core Benefits of readOnly = true:
  1. Performance: Hibernate completely disables dirty checking on managed entities.
  2. Safety: Database rejects accidental INSERT/UPDATE/DELETE queries.
  3. Routing: Enables dynamic routing to read-only database replicas.
```

## 🟡 Middle Level

### The Three Optimization Layers

```
  ┌──────────────────┬──────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Layer            │ Action Taken When `readOnly = true`  │ Performance Benefit                              │
  ├──────────────────┼──────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Hibernate**    │ Sets `FlushMode.MANUAL`              │ **Completely disables entity dirty checking!**   │
  │ **JDBC Driver**  │ Calls `connection.setReadOnly(true)` │ Disables locks and optimizes query plans         │
  │ **Infrastructure│ `AbstractRoutingDataSource` check    │ Routes queries to **Read Replicas (Slaves)**     │
  └──────────────────┴──────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Hibernate Dirty Checking Elimination

In standard transactions (`readOnly = false`), Hibernate must inspect every loaded entity upon transaction commit, comparing its current field values against its initial hydration snapshot. 

When loading 10,000 entities in `readOnly = true`:
- Hibernate **skips snapshot comparison entirely**.
- Saves significant CPU cycles and avoids garbage collector churn.

## 🔴 Senior Level

### Dynamic Read-Replica Routing (`AbstractRoutingDataSource`)

Modern enterprise architectures use `readOnly = true` to automatically offload query traffic to Read Replicas:

```java
public class DynamicReplicaRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        // Inspects thread-local transaction status:
        boolean isReadOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return isReadOnly ? "REPLICA_POOL" : "PRIMARY_POOL";
    }
}
```

```
  HTTP Request (@Transactional readOnly=true) ──► RoutingDataSource ──► Read-Only Replica
  HTTP Request (@Transactional readOnly=false) ──► RoutingDataSource ──► Primary Database
```

### Common Edge Cases & Traps

```
  1. Entity Modification Silent Ignore:
     If code executes user.setName("Updated") inside a readOnly transaction, 
     NO exception is thrown! Hibernate simply skips the flush, and the change is lost.

  2. Direct DML Modification Throws Exception:
     Executing em.createQuery("UPDATE User SET active = false").executeUpdate() 
     immediately throws: "SQLException: cannot execute UPDATE in a read-only transaction".

  3. Joining Read-Only Transactions:
     If a readOnly method calls a write method with Propagation.REQUIRED, the write 
     method joins the read-only transaction and fails when trying to write!
     Fix: Give the write method @Transactional(propagation = Propagation.REQUIRES_NEW).
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Purpose:** Optimizes read-only methods by disabling Hibernate dirty checking and setting JDBC read-only flags.
- **Hibernate Optimization:** Sets `FlushMode.MANUAL`, skipping snapshot comparisons on entity commit.
- **Database Enforcement:** PostgreSQL and Oracle reject `INSERT`/`UPDATE`/`DELETE` in read-only transactions with `PSQLException`.
- **Replica Routing:** Powers dynamic routing via `AbstractRoutingDataSource` to distribute traffic to read replicas.
- **Entity Mutation:** Mutating entity fields inside a read-only method does not throw an exception; changes are silently discarded upon method exit.
- **Propagation Hazard:** Calling a write method (`REQUIRED`) from a `readOnly = true` method causes write failure due to transaction inheritance.

**Common Follow-up Questions:**
- *"Why does `@Transactional(readOnly = true)` improve memory and CPU efficiency in Hibernate?"* → It allows Hibernate to avoid creating snapshot copies of loaded entities and bypasses dirty checking loops across the entire persistence context on commit.
- *"What happens if you execute a Spring Data `@Modifying` query inside a `@Transactional(readOnly = true)` method?"* → Spring throws `TransactionRequiredException` or the database throws a read-only transaction violation error.
- *"Is it better to omit `@Transactional` completely for read-only methods rather than using `readOnly = true`?"* → No; `readOnly = true` provides a consistent transaction snapshot across multiple queries, prevents dirty checking, and enables read replica routing.

**Red Flags (DO NOT Say):**
- ❌ *"Setting `readOnly = true` makes all loaded Java entity objects completely immutable in memory."* (Java getters/setters still work; Hibernate simply skips flushing changes to the database).
- ❌ *"Calling `user.setName("New")` inside a read-only transaction immediately throws an UnsupportedOperationException."* (No exception is thrown; the mutation is silently omitted during commit).
- ❌ *"Spring automatically routes queries to read replicas without requiring any custom DataSource configuration."* (You must configure an `AbstractRoutingDataSource` to inspect the read-only flag).
