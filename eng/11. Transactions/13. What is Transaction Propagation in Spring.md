# What is Transaction Propagation in Spring?

---

## 🟢 Junior Level

In Spring Framework, **Transaction Propagation** defines how transaction boundaries behave when one `@Transactional` method calls another `@Transactional` method:

```
  ┌───┬──────────────────────────────┬───────────────────────────────────────┬────────────────────────────────────────┐
  │ # │ Propagation Mode             │ If Transaction Already Exists         │ If No Transaction Exists               │
  ├───┼──────────────────────────────┼───────────────────────────────────────┼────────────────────────────────────────┤
  │ 1 │ **`REQUIRED`** (Default)     │ **Joins current transaction**         │ **Creates a new transaction**          │
  │ 2 │ **`REQUIRES_NEW`**           │ **Suspends current; creates new**     │ **Creates a new transaction**          │
  │ 3 │ **`NESTED`**                 │ **Creates a nested JDBC Savepoint**   │ **Creates a new transaction**          │
  │ 4 │ **`MANDATORY`**              │ **Joins current transaction**         │ ❌ **Throws Exception** (`Illegal...`) │
  │ 5 │ **`SUPPORTS`**               │ **Joins current transaction**         │ Executes non-transactionally           │
  │ 6 │ **`NOT_SUPPORTED`**          │ **Suspends current transaction**      │ Executes non-transactionally           │
  │ 7 │ **`NEVER`**                  │ ❌ **Throws Exception** (`Illegal...`)│ Executes non-transactionally           │
  └───┴──────────────────────────────┴───────────────────────────────────────┴────────────────────────────────────────┘
```

```java
@Service
public class OrderService {

    private final AuditService auditService;
    private final OrderRepository orderRepository;

    @Transactional // Defaults to Propagation.REQUIRED
    public void placeOrder(Order order) {
        orderRepository.save(order);
        auditService.logAuditRecord(order); // Calls REQUIRES_NEW
    }
}
```

## 🟡 Middle Level

### Practical Scenarios for Common Propagation Types

```java
@Service
public class AuditService {

    // 1. Independent Audit Logging (Must survive outer transaction rollback):
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAuditRecord(Order order) {
        auditRepository.save(new AuditLog("ORDER_PLACED", order.getId()));
    }
}

@Service
public class SecurityValidator {

    // 2. Strict Architectural Enforcement (Must only be called from an active transaction):
    @Transactional(propagation = Propagation.MANDATORY)
    public void verifyDebitAuthorization(Long accountId) {
        // Guaranteed to run within a surrounding transaction
    }
}
```

### The Rollback-Only Trap with `Propagation.REQUIRED`

When Method A (`REQUIRED`) calls Method B (`REQUIRED`) and Method B throws an unchecked exception caught by Method A:

```java
@Transactional
public void methodA() {
    try {
        serviceB.methodB(); // Throws RuntimeException!
    } catch (RuntimeException e) {
        log.warn("Recovered from inner error");
    }
    // 💥 When methodA attempts to COMMIT, Spring throws:
    // UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only!
}
```

```
  Why this happens:
  • Method A and Method B share the SAME physical database transaction.
  • When Method B throws an exception, Spring's TransactionAspect marks the 
    underlying transaction as "Rollback-Only".
  • Method A's try-catch cannot unmark the transaction!
```

## 🔴 Senior Level

### Spring AOP Proxy Mechanics & ThreadLocal Context

```
  Caller ──► Spring CGLIB / JDK Proxy ──► TransactionInterceptor ──► Target Bean Method
```

Spring manages transaction state via **`TransactionSynchronizationManager`**, binding connections and resources to the active thread using `ThreadLocal`:
- When `REQUIRES_NEW` is invoked, Spring executes `AbstractPlatformTransactionManager.suspend()`.
- The outer `ConnectionHolder` is unbound from `ThreadLocal` and saved in a `SuspendedResourcesHolder`.
- A brand new `Connection` is fetched from the pool, bound to `ThreadLocal`, and committed independently.
- Upon completion, the suspended outer connection is restored.

### Production Highload Hazard: Connection Pool Exhaustion Deadlock

Using `Propagation.REQUIRES_NEW` inside a high-concurrency service can cause a catastrophic **HikariCP Connection Pool Deadlock**:

```
  Disaster Scenario:
  • HikariCP Pool Size = 10 connections.
  • 10 concurrent HTTP requests invoke placeOrder() (Method A: REQUIRED).
  • All 10 threads acquire Connection 1 from the pool (10/10 connections checked out).
  • All 10 threads simultaneously invoke logAuditRecord() (Method B: REQUIRES_NEW).
  • Each thread requests a SECOND connection from HikariCP while holding Connection 1.
  • Pool is EMPTY! All 10 threads block indefinitely waiting for a connection!
  💥 Result: Complete service deadlock and HTTP timeout storm!
```

> [!IMPORTANT]
> **Formula for HikariCP Pool Sizing with `REQUIRES_NEW`:**
> $$\text{PoolSize} \ge \text{MaxActiveThreads} \times (\text{MaxNestedRequiresNew} + 1)$$

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Propagation defines transaction boundary inheritance between calling methods.
- **Default:** `Propagation.REQUIRED` (joins existing, creates new if absent).
- **7 Types:** REQUIRED, REQUIRES_NEW, NESTED, MANDATORY, SUPPORTS, NOT_SUPPORTED, NEVER.
- **Rollback-Only:** Catching an exception from an inner `REQUIRED` method still results in an `UnexpectedRollbackException`.
- **REQUIRES_NEW Cost:** Suspends outer transaction and consumes an additional physical JDBC connection.
- **Pool Deadlock:** High concurrency with nested `REQUIRES_NEW` can exhaust the connection pool and deadlock the JVM.

**Common Follow-up Questions:**
- *"What is the difference between REQUIRES_NEW and NESTED?"* → `REQUIRES_NEW` uses two separate physical database transactions with independent commits; `NESTED` uses a single physical transaction with JDBC Savepoints.
- *"Why does calling an inner `@Transactional` method via `this.method()` ignore propagation?"* → Internal `this` method invocations bypass the Spring AOP proxy wrapper, executing plain Java code without transaction interception.
- *"When should you use `Propagation.MANDATORY`?"* → When writing low-level repository or domain services that must never be executed outside an established transactional unit of work.

**Red Flags (DO NOT Say):**
- ❌ *"Catching an exception from an inner `REQUIRED` method in a try-catch block allows the outer transaction to commit successfully."* (Spring marks the transaction as rollback-only; committing throws `UnexpectedRollbackException`).
- ❌ *"REQUIRES_NEW shares the database connection with the outer transaction."* (It opens a separate physical connection from the pool).
- ❌ *"NESTED propagation works out of the box with all JPA/Hibernate configurations."* (Hibernate L1 cache does not track savepoint rollbacks; NESTED is natively supported by `JdbcTemplate` / `DataSourceTransactionManager`).
