# What Transaction Isolation Levels Exist?

---

## 🟢 Junior Level

ANSI SQL defines **four standard transaction isolation levels**, arranged in order from weakest isolation (highest concurrency) to strictest isolation (lowest concurrency):

```
  ┌───┬──────────────────────────┬──────────────────────┬────────────────────────────────────────────────────────┐
  │ # │ Isolation Level          │ Default Database     │ Primary Guarantee                                      │
  ├───┼──────────────────────────┼──────────────────────┼────────────────────────────────────────────────────────┤
  │ 1 │ **Read Uncommitted**     │ None (Obsolete/Rare) │ Reads raw uncommitted in-flight dirty data.            │
  │ 2 │ **Read Committed**       │ **PostgreSQL, Oracle**│ Reads only committed data; new snapshot per query.     │
  │ 3 │ **Repeatable Read**      │ **MySQL (InnoDB)**   │ Data read once remains unchanged throughout transaction│
  │ 4 │ **Serializable**         │ Explicit Opt-In      │ Strict sequential execution without anomalies.         │
  └───┴──────────────────────────┴──────────────────────┴────────────────────────────────────────────────────────┘
```

### The Standard ANSI SQL Anomaly Matrix

```
  ┌──────────────────────────────┬──────────────────┬────────────────────────┬────────────────────────┐
  │ Isolation Level              │ Dirty Read       │ Non-Repeatable Read    │ Phantom Read           │
  ├──────────────────────────────┼──────────────────┼────────────────────────┼────────────────────────┤
  │ **Read Uncommitted**         │ ❌ Allowed       │ ❌ Allowed             │ ❌ Allowed             │
  │ **Read Committed**           │ ✅ **Prevented** │ ❌ Allowed             │ ❌ Allowed             │
  │ **Repeatable Read**          │ ✅ **Prevented** │ ✅ **Prevented**       │ ❌ Allowed (ANSI)*     │
  │ **Serializable**             │ ✅ **Prevented** │ ✅ **Prevented**       │ ✅ **Prevented**       │
  └──────────────────────────────┴──────────────────┴────────────────────────┴────────────────────────┘
```

> [!NOTE]
> *\* Engine Extension:* In MySQL InnoDB, Repeatable Read also prevents Phantom Reads using **Next-Key Locking (Record + Gap Locks)**.

## 🟡 Middle Level

### Database Defaults & MVCC Mechanics

```
  PostgreSQL Default (Read Committed):
  • Evaluates a NEW MVCC snapshot before EVERY SQL statement.
  • Prevents Dirty Reads at zero locking cost, but allows Non-Repeatable Reads between statements.
  • PostgreSQL lacks a physical "Read Uncommitted" mode; it silently promotes it to Read Committed.

  MySQL InnoDB Default (Repeatable Read):
  • Evaluates ONE MVCC snapshot at the START of the transaction.
  • Employs Next-Key Locks (Gap Locks) on indexed ranges to block concurrent phantom inserts.
```

```java
// Spring Declarative Isolation Configuration:
@Transactional(isolation = Isolation.REPEATABLE_READ)
public FinancialReport generateMonthlyReport(Long companyId) {
    // Reads consistent snapshot of ledger balances throughout method execution
    return reportService.compile(companyId);
}
```

## 🔴 Senior Level

### Serializable Snapshot Isolation (SSI) vs. Strict 2-Phase Locking (2PL)

Traditional relational databases achieved Serializability via **Strict Two-Phase Locking (S2PL)**:
- Shared locks ($S$) on all reads and Exclusive locks ($X$) on all writes held until transaction `COMMIT`.
- Heavy locking caused pervasive thread blocking and deadlock storms.

**Modern PostgreSQL (SSI Architecture):**
- Does not block readers or writers!
- Constructs an in-memory **Serialization Conflict Dependency Graph** tracking `Read-Write (rw-antidependencies)` between active transactions.
- If the database detects a cyclic dependency indicating non-serializable interleaving, it aborts one of the transactions with `ERROR: could not serialize access (SQLSTATE 40001)`.

```java
// Mandatory Production Pattern for Serializable Transactions:
@Retryable(
    retryFor = {CannotSerializeTransactionException.class, SQLException.class},
    maxAttempts = 3,
    backoff = @Backoff(delay = 100, multiplier = 2.0)
)
@Transactional(isolation = Isolation.SERIALIZABLE)
public void executeCriticalLedgerSettlement(SettlementOrder order) {
    ledgerRepository.settle(order);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **4 Levels:** Read Uncommitted $\to$ Read Committed $\to$ Repeatable Read $\to$ Serializable.
- **Defaults:** PostgreSQL, Oracle, SQL Server default to **Read Committed**; MySQL InnoDB defaults to **Repeatable Read**.
- **PostgreSQL Quirk:** Automatically treats `READ UNCOMMITTED` as `READ COMMITTED` because MVCC never reads uncommitted dirty tuples.
- **MySQL Quirk:** Repeatable Read eliminates Phantom Reads via **Next-Key Locks** (Record Lock + Gap Lock).
- **Serializable Cost:** Requires application-level retry logic to handle `SQLSTATE 40001` serialization failure aborts.

**Common Follow-up Questions:**
- *"Why does Read Committed allow Non-Repeatable Reads?"* → Because Read Committed generates a fresh MVCC snapshot for every separate `SELECT` query within the transaction. If another transaction commits an `UPDATE` in between, the second query sees the new value.
- *"What is a Gap Lock in MySQL?"* → A lock placed on the empty gap between index records (or before the first / after the last record) that prevents other transactions from inserting new rows into that range.
- *"Why should long-running batch jobs avoid Serializable isolation?"* → Long-running transactions hold historical snapshots open, creating large serialization dependency graphs and drastically increasing the probability of serialization failure rollbacks.

**Red Flags (DO NOT Say):**
- ❌ *"Repeatable Read works identically across all databases."* (MySQL uses Gap Locks; PostgreSQL uses MVCC snapshot isolation without gap locks).
- ❌ *"Serializable mode completely eliminates the need for error handling in the application."* (Serializable transactions regularly fail with serialization conflicts and require automated retry loops).
- ❌ *"PostgreSQL Read Uncommitted allows dirty reads."* (PostgreSQL does not support uncommitted reads; it promotes to Read Committed).
