# What is Lost Update?

---

## 🟢 Junior Level

A **Lost Update** is a concurrency anomaly that occurs when two transactions read the same initial record state, calculate new values in application memory, and write their updates back sequentially, causing the second transaction to **silently overwrite and obliterate the changes made by the first**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Root Cause Pattern                                     │ **Read-Modify-Write** in application code              │
  │ Concurrency Impact                                     │ **Silent permanent data destruction** without error    │
  │ Common Vulnerabilities                                 │ Account balance updates, inventory counters, views     │
  │ Default Spring Protection                              │ ❌ `@Transactional` **DOES NOT protect against this!**│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```
  Lost Update Destruction Timeline:
  Initial Database State: account_1.balance = $1,000

  Time   Transaction 1 (Deposit $500)                 Transaction 2 (Withdraw $200)
  ────────────────────────────────────────────────────────────────────────────────────────────────────────
  T1     SELECT balance FROM accounts WHERE id = 1;   SELECT balance FROM accounts WHERE id = 1;
         ──► Reads $1,000                             ──► Reads $1,000
  T2     Computes: 1000 + 500 = $1,500                Computes: 1000 - 200 = $800
  T3     UPDATE accounts SET balance = 1500; COMMIT;  
  T4                                                  UPDATE accounts SET balance = 800; COMMIT;
  ────────────────────────────────────────────────────────────────────────────────────────────────────────
  Final Database State: balance = $800! 💥 (The $500 deposit was completely destroyed!)
```

## 🟡 Middle Level

### The Four Industry Defenses Against Lost Updates

```
  ┌───┬──────────────────────────────────┬────────────────────────────┬────────────────────────────────────────┐
  │ # │ Defense Strategy                 │ Mechanism                  │ Best For                               │
  ├───┼──────────────────────────────────┼────────────────────────────┼────────────────────────────────────────┤
  │ 1 │ **Atomic Database SQL**          │ `SET balance = balance + ?`│ Simple counters, credits, balance adjustments│
  │ 2 │ **Optimistic Locking (`@Version`)│ `WHERE version = ?` check  │ Web CRUD forms, low/medium contention  │
  │ 3 │ **Pessimistic Locking**          │ `SELECT ... FOR UPDATE`    │ Complex business logic with invariants │
  │ 4 │ **Append-Only Event Sourcing**   │ `INSERT` ledger entries    │ Financial ledgers, highload audits     │
  └───┴──────────────────────────────────┴────────────────────────────┴────────────────────────────────────────┘
```

### 1. Atomic Database SQL (Highest Performance)

```java
// ✅ Eliminates the read-modify-write window at the database engine level:
@Modifying
@Query("UPDATE Account a SET a.balance = a.balance - :amount WHERE a.id = :id AND a.balance >= :amount")
int deductBalanceSafely(@Param("id") Long id, @Param("amount") BigDecimal amount);
```

### 2. Optimistic Locking (`@Version`)

```java
@Entity
public class Account {
    @Id
    private Long id;
    private BigDecimal balance;

    @Version
    private Long version; // Hibernate automatically appends: WHERE version = :oldVersion
}
```

## 🔴 Senior Level

### Deep Dive: Why `@Transactional` Alone Does Not Prevent Lost Updates

A common senior developer interview mistake is assuming that wrapping a method in `@Transactional` prevents Lost Updates:

```java
// 💥 VULNERABLE PRODUCTION CODE:
@Transactional // Uses default Read Committed!
public void applyDiscount(Long productId, BigDecimal discount) {
    Product p = productRepo.findById(productId).orElseThrow(); // Step 1: Read
    p.setPrice(p.getPrice().subtract(discount));              // Step 2: Modify
    productRepo.save(p);                                      // Step 3: Write
}
```

```
  Why this fails under Read Committed:
  1. Transaction 1 reads price = $100.
  2. Transaction 2 reads price = $100 concurrently in its own statement snapshot.
  3. Transaction 1 saves price = $90 and commits.
  4. Transaction 2 saves price = $80 and commits.
  5. Transaction 2's write executes cleanly, overwriting Transaction 1's price change!
```

### The Architectural Choice: Optimistic vs. Pessimistic Locking

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Characteristic               │ Optimistic (`@Version`)  │ Pessimistic (`FOR UPDATE`)                       │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Database Locking**         │ None (Lock-free)         │ Row-level exclusive lock ($X$)                   │
  │ **High-Contention Behavior** │ **Severe Retry Storms**  │ **Threads queue cleanly** (Waits on lock)        │
  │ **Deadlock Risk**            │ Zero                     │ Present (if locking order is inconsistent)       │
  │ **Throughput (100 threads)** │ Low (Aborts on conflicts)│ High (Sequential processing)                     │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Two concurrent transactions perform a read-modify-write cycle on the same record; the second write overwrites the first, losing data.
- **Root Cause:** Application-level read-modify-write patterns executed without row-level locks or version checking.
- **Spring Fallacy:** `@Transactional` alone **does NOT** prevent lost updates.
- **Defense 1 (Atomic SQL):** Execute direct single-statement SQL (`UPDATE t SET col = col + 1`).
- **Defense 2 (Optimistic):** Use JPA `@Version` column checking to throw `OptimisticLockException` on concurrent modifications.
- **Defense 3 (Pessimistic):** Use `SELECT ... FOR UPDATE` to block concurrent transactions during the calculation.
- **Defense 4 (Event Sourcing):** Use append-only immutable ledger tables.

**Common Follow-up Questions:**
- *"What happens when Hibernate detects an OptimisticLockException?"* → The current transaction is marked as rollback-only; the application must catch the exception and retry the entire transaction.
- *"Why does Atomic SQL outperform Optimistic Locking on hot-spots?"* → Atomic SQL updates the value in a single CPU cycle inside the engine without application round-trips or retry loops.
- *"What is Write Skew?"* → A multi-row generalized variant of Lost Update where two transactions read overlapping datasets, make decisions, and update disjoint records, violating a global business invariant.

**Red Flags (DO NOT Say):**
- ❌ *"Adding `@Transactional` to a Spring service method automatically prevents lost updates."* (It only provides transaction boundaries; lost updates will still occur under Read Committed).
- ❌ *"Optimistic locking with `@Version` physically locks database rows."* (It is lock-free; it uses version condition matching in the `UPDATE ... WHERE version = ?` clause).
- ❌ *"Lost updates only occur in NoSQL databases."* (Lost updates occur in all relational databases executing unprotected read-modify-write code).
