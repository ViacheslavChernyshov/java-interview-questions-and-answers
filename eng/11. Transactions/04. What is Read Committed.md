# What is Read Committed?

---

## 🟢 Junior Level

**Read Committed** is the most widely used transaction isolation level and the default setting for **PostgreSQL, Oracle, and Microsoft SQL Server**.

It guarantees that a transaction will only read data that has been **officially committed** before the query began:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Dirty Reads                                            │ ✅ **Strictly Prevented** (No dirty reads)             │
  │ Non-Repeatable Reads                                   │ ❌ **Permitted** (Data can change between statements)  │
  │ Phantom Reads                                          │ ❌ **Permitted** (New rows can appear in range queries)│
  │ Snapshot Creation Rule                                 │ **A fresh MVCC snapshot per individual SQL statement** │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```
  Non-Repeatable Read Example on Read Committed:
  Transaction A:
  1. BEGIN;
  2. SELECT price FROM products WHERE id = 1; ──► Returns $100

  Transaction B:
  3. UPDATE products SET price = $150 WHERE id = 1;
  4. COMMIT;

  Transaction A:
  5. SELECT price FROM products WHERE id = 1; ──► Returns $150! (Value changed!)
  6. COMMIT;
```

## 🟡 Middle Level

### The Per-Statement MVCC Snapshot Model

The defining architectural characteristic of Read Committed is **Statement-Level MVCC Snapshots**:

```
  ┌──────────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ `Read Committed` (Statement MVCC)            │ `Repeatable Read` (Transaction MVCC)             │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ Generates a **NEW snapshot** for EVERY query │ Generates **ONE snapshot** at transaction start  │
  │ Sees mutations committed between queries     │ Ignores all mutations committed after start      │
  │ Never throws serialization conflict aborts   │ Aborts if concurrent transaction updates row     │
  └──────────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Targeted Protection: `SELECT ... FOR UPDATE`

When working in Read Committed, developers can prevent Non-Repeatable Reads and Lost Updates for specific critical rows without locking the entire table or switching isolation levels:

```java
// Spring Data JPA Pessimistic Lock:
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM BankAccount a WHERE a.id = :id")
Optional<BankAccount> findByIdForUpdate(@Param("id") Long id);
```

```sql
-- Emits explicit row-level exclusive lock:
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
```

## 🔴 Senior Level

### PostgreSQL Engine Internals: MVCC Snapshot Structure

In PostgreSQL, every SQL statement creates an active `SnapshotData` struct containing:
- `xmin`: The lowest transaction ID that is still active/uncommitted.
- `xmax`: The highest transaction ID assigned so far $+ 1$.
- `xip_list`: The list of active in-progress transaction IDs.

```
  Visibility Rule:
  A table row (tuple) is visible to the statement snapshot if:
  1. tuple.xmin is committed AND tuple.xmin < snapshot.xmin (or committed before snapshot).
  2. tuple.xmax is either not set, aborted, or belongs to a transaction not yet committed.
```

### PostgreSQL `EvalPlanQual` (EPQ) Re-evaluation

When an `UPDATE` or `DELETE` executes under Read Committed on a row being concurrently modified by another transaction:
1. Transaction B blocks until Transaction A commits or rolls back.
2. If Transaction A commits, Transaction B **does NOT abort**!
3. PostgreSQL invokes **`EvalPlanQual`**: it fetches the newly committed version of the row and re-evaluates the query's `WHERE` clause. If the row still matches the filter, the update is applied to the new version.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Status:** Default isolation level in PostgreSQL, Oracle, and SQL Server.
- **Anomalies:** Prevents Dirty Reads; permits Non-Repeatable Reads and Phantom Reads.
- **Snapshot Timing:** Generates a fresh MVCC snapshot before **every separate SQL statement**.
- **No Reader-Writer Blocking:** In MVCC engines, readers never block writers, and writers never block readers.
- **Pessimistic Locking:** Use `SELECT ... FOR UPDATE` to secure specific rows against concurrent modifications.
- **PostgreSQL EPQ:** Concurrently modified rows are re-evaluated rather than aborted.

**Common Follow-up Questions:**
- *"Why do two identical SELECT queries return different results inside the same Read Committed transaction?"* → Because each `SELECT` generates its own new snapshot. If another transaction commits an update in between, the second query's snapshot reflects that commit.
- *"Why is Read Committed the standard default for enterprise applications?"* → It provides the best trade-off between consistency and performance: zero dirty reads, zero serialization aborts, and high concurrent throughput.
- *"How does SQL Server handle Read Committed differently from PostgreSQL?"* → SQL Server historically uses shared locks on reads (readers block writers); enabling `READ_COMMITTED_SNAPSHOT` (RCSI) switches SQL Server to PostgreSQL-style MVCC.

**Red Flags (DO NOT Say):**
- ❌ *"Read Committed guarantees that queries inside the same transaction will always read the same data."* (Non-Repeatable Reads can change values between statements).
- ❌ *"Read Committed places shared read locks on every table row."* (MVCC implementations read snapshot versions lock-free).
- ❌ *"Read Committed transactions abort with serialization failure errors on conflicts."* (They wait on row locks and re-evaluate via EPQ).
