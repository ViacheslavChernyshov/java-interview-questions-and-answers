# What Does Propagation NESTED Do?

---

## 🟢 Junior Level

**`Propagation.NESTED`** executes within a nested transaction using **JDBC Savepoints** if an active transaction exists. If no transaction exists, it creates a new one (behaving like `REQUIRED`):

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Underlying Mechanism                                   │ **JDBC Savepoints (`connection.setSavepoint()`)**      │
  │ Physical Database Transactions                         │ **1 Single Database Transaction & 1 Connection**       │
  │ Inner Exception Behavior                               │ Rolls back **ONLY to Savepoint**; outer continues     │
  │ Outer Rollback Behavior                                │ **Rolls back EVERYTHING** (including nested changes)   │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
@Service
public class BatchProcessingService {

    private final SubTaskProcessor subTaskProcessor;

    @Transactional
    public void processBatch(List<BatchItem> items) {
        for (BatchItem item : items) {
            try {
                // Each item executes within its own Savepoint:
                subTaskProcessor.processItem(item); // Propagation.NESTED
            } catch (Exception e) {
                // Only this single item's savepoint is rolled back!
                log.warn("Failed item {}, continuing batch...", item.getId());
            }
        }
        // One unified COMMIT persists all successful items!
    }
}
```

## 🟡 Middle Level

### `Propagation.NESTED` vs. `Propagation.REQUIRES_NEW`

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architectural Property       │ `Propagation.NESTED`             │ `Propagation.REQUIRES_NEW`                       │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Physical Connections**     │ **1 JDBC Connection**            │ **2 JDBC Connections** (Outer suspended)         │
  │ **Commit Timing**            │ Delayed until outer `COMMIT`     │ **Immediate & Independent** upon method exit     │
  │ **Outer Rollback Impact**    │ **Rolls back nested work**       │ **Nested work remains committed permanently**    │
  │ **JTA / Distributed Support**│ ❌ **Unsupported**               │ ✅ **Fully Supported**                           │
  │ **Primary Use Case**         │ Partial-failure batch loops      │ Independent audit logs, token generations        │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Hibernate / JPA L1 Cache Inconsistency Hazard

When using `Propagation.NESTED` in JPA/Hibernate environments:

```java
@Service
public class OrderService {

    @Autowired private EntityManager entityManager;
    @Autowired private PaymentProcessor paymentProcessor;

    @Transactional
    public void placeOrder(Order order) {
        orderRepo.save(order); // Entity enters Hibernate L1 Persistence Context

        try {
            paymentProcessor.chargeCard(order); // NESTED method throws exception!
        } catch (PaymentException e) {
            // ⚠️ CRITICAL HAZARD: The JDBC Savepoint rolls back SQL state in the DB,
            // but Hibernate's L1 Cache still holds the modified/dirty entity in JVM RAM!
            entityManager.clear(); // Mandatory: Clear persistence context to prevent dirty flush!
        }
    }
}
```

> [!WARNING]
> Rolling back a JDBC Savepoint modifies database state, but does not notify Hibernate's in-memory Persistence Context. If you do not invoke `entityManager.clear()`, Hibernate may flush corrupted in-memory entity states during the final commit.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Mechanism:** Implemented via **JDBC 3.0 Savepoints** (`setSavepoint()`, `rollback(savepoint)`).
- **Single Connection:** Uses only **1 physical database connection** (unlike `REQUIRES_NEW` which requires 2).
- **Partial Rollback:** Allows an inner failure to roll back to its savepoint without marking the outer transaction as `rollback-only`.
- **Outer Dependency:** If the outer transaction rolls back, all nested savepoints are completely undone.
- **JPA Trap:** Hibernate's L1 cache does not automatically reset after a savepoint rollback; call `entityManager.clear()`.
- **JTA Limitation:** `NESTED` is not supported in distributed JTA environments.

**Common Follow-up Questions:**
- *"Why should you use NESTED instead of REQUIRES_NEW for batch processing?"* → `NESTED` uses only 1 connection and permits a single atomic commit at the end, whereas `REQUIRES_NEW` commits each item permanently even if the entire batch later fails.
- *"What happens if a method annotated with `@Transactional(propagation = Propagation.NESTED)` is called without an active transaction?"* → It creates a new standard top-level transaction (identical to `REQUIRED`).
- *"Can you nest multiple savepoints within each other?"* → Yes, Spring supports arbitrary savepoint nesting within the same physical transaction.

**Red Flags (DO NOT Say):**
- ❌ *"NESTED opens a second independent database transaction."* (It opens a Savepoint inside the existing transaction).
- ❌ *"If the outer transaction rolls back, changes committed by the NESTED transaction remain in the database."* (Nested changes are rolled back with the outer transaction; use `REQUIRES_NEW` to survive outer rollback).
- ❌ *"NESTED works seamlessly with Hibernate without needing to clear the EntityManager."* (Savepoints desynchronize the database from Hibernate's L1 cache).
