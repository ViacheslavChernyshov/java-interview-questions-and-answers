# What is Dirty Read?

---

## 🟢 Junior Level

A **Dirty Read** is a database concurrency anomaly where a transaction reads uncommitted modifications made by another concurrent in-flight transaction that are **subsequently aborted via `ROLLBACK`**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Anomaly Type                                           │ Reading uncommitted, non-existent database state       │
  │ Permitted Isolation Level                              │ **Read Uncommitted ONLY**                              │
  │ Prevented Isolation Levels                             │ **Read Committed**, **Repeatable Read**, **Serializable│
  │ Engine Default Status                                  │ **Eliminated by default** in all modern RDBMS engines  │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```
  Dirty Read Timeline:
  Time   Transaction A (Writer)                     Transaction B (Reader)
  ────────────────────────────────────────────────────────────────────────────────────────────────────────
  T1     BEGIN;                                     BEGIN; (Read Uncommitted)
  T2     UPDATE accounts SET balance = 500 WHERE id = 1;
  T3                                                SELECT balance FROM accounts WHERE id = 1; ──► Sees 500!
  T4     ROLLBACK; (Restores balance to 100)
  T5                                                Approves transfer based on phantom $500!
```

## 🟡 Middle Level

### Dirty Read vs. Non-Repeatable Read vs. Phantom Read

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Concurrency Anomaly          │ Mutation State Observed  │ Root Cause                                       │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Dirty Read**               │ **Uncommitted**          │ Reads dirty data later discarded by `ROLLBACK`   │
  │ **Non-Repeatable Read**      │ **Committed**            │ Value of an existing row changes between reads   │
  │ **Phantom Read**             │ **Committed**            │ New rows matching a `WHERE` range query appear   │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

### Why MVCC Prevents Dirty Reads at Zero Cost

In traditional lock-based databases (2PL), preventing dirty reads required acquiring **Shared Read Locks ($S$)**, which blocked writers ($X$) and harmed concurrency.

In **MVCC (Multi-Version Concurrency Control)**, dirty read prevention is completely free:
- Writers do not overwrite existing data in place; they write a new row version tagged with their in-progress transaction ID (`t_xmin`).
- Readers inspect snapshots containing only **committed transaction IDs**.
- Uncommitted tuple versions are automatically ignored without locking!

## 🔴 Senior Level

### Low-Level PostgreSQL Visibility Logic (`t_xmin`)

```c
// PostgreSQL internal tuple visibility evaluation:
bool HeapTupleSatisfiesSnapshot(HeapTupleHeader tuple, Snapshot snapshot) {
    TransactionId xmin = HeapTupleHeaderGetXmin(tuple);

    // If the inserting transaction is still in-progress -> INVISIBLE (Prevents Dirty Read!)
    if (TransactionIdIsInProgress(xmin, snapshot))
        return false;

    // If the inserting transaction aborted -> INVISIBLE
    if (!TransactionIdDidCommit(xmin))
        return false;

    return true; // Tuple was committed before snapshot start
}
```

### The Perils of SQL Server `WITH (NOLOCK)`

In SQL Server, using `SELECT ... WITH (NOLOCK)` bypasses lock acquisition, introducing severe physical anomalies beyond simple dirty reads:
- **Index B-Tree Page Splits:** If a concurrent writer splits an index page while a `NOLOCK` scan progresses, the reader can **skip rows entirely** or **read identical rows twice**.
- **Inconsistent Aggregate Totals:** `SUM()` or `COUNT()` queries yield corrupted financial numbers.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Reading data modified by an uncommitted transaction that later aborts (`ROLLBACK`).
- **Isolation Scope:** Occurs **only** in `Read Uncommitted`.
- **Zero-Cost MVCC:** MVCC engines (PostgreSQL, Oracle) filter out in-progress transaction IDs (`t_xmin`), making dirty reads impossible by design with zero locking overhead.
- **Silent Corruption:** Dirty reads cause silent, cascading application data corruption without raising database errors.
- **SQL Server NOLOCK:** `WITH (NOLOCK)` produces dirty reads, duplicate rows, and dropped rows during page splits.

**Common Follow-up Questions:**
- *"Why is a Dirty Read more dangerous than a Non-Repeatable Read?"* → A Dirty Read observes data that *never legally existed* in the database (discarded by rollback), whereas a Non-Repeatable Read observes valid, committed data that simply changed over time.
- *"How does PostgreSQL prevent dirty reads if you explicitly set `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`?"* → PostgreSQL silently elevates the transaction to `Read Committed`.
- *"Can dirty reads happen during read-only reporting queries?"* → Yes, if executed under Read Uncommitted or with `NOLOCK`, reporting queries will aggregate uncommitted, erroneous values.

**Red Flags (DO NOT Say):**
- ❌ *"Dirty reads happen when two transactions read the same row at the same time."* (Dirty read is reading uncommitted modifications that may rollback).
- ❌ *"PostgreSQL allows dirty reads under heavy system load."* (PostgreSQL's MVCC strictly prevents dirty reads across all settings).
- ❌ *"Dirty reads throw a database exception to alert the application."* (Dirty reads return normal query results silently with invalid data).
