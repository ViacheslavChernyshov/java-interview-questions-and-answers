# Which Exceptions Trigger Rollback by Default?

---

## 🟢 Junior Level

By default, Spring Framework automatically triggers transaction rollback **ONLY for Unchecked Exceptions**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Exception Type                                         │ Default Spring Rollback Behavior                       │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **`RuntimeException`** (and all subclasses)            │ ✅ **ROLLBACK**                                        │
  │ **`Error`** (and all subclasses)                       │ ✅ **ROLLBACK**                                        │
  │ **Checked Exceptions** (`extends Exception`)           │ ❌ **COMMITS** (Transaction commits successfully!)     │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) throws IOException {
        orderRepo.save(order);

        // 1. Throws RuntimeException -> ROLLBACK!
        if (order.getAmount().signum() <= 0) {
            throw new IllegalArgumentException("Invalid amount"); 
        }

        // 2. Throws Checked Exception -> COMMITS! (Order is saved permanently!)
        if (externalApiFailed()) {
            throw new IOException("Remote disk failure"); 
        }
    }
}
```

## 🟡 Middle Level

### The Philosophical Rationale: Unchecked vs. Checked

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Category                     │ Semantic Meaning         │ Default Spring Action                            │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **`RuntimeException`**       │ **Unrecoverable Bug**    │ **Rollback** (System state is corrupted/unknown) │
  │ **`Error`**                  │ **JVM Hardware/VM Fault**│ **Rollback** (Out of memory, stack overflow)     │
  │ **Checked `Exception`**      │ **Expected Business Flow**│ **Commit** (Caller handles flow; commit partial) │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

### Spring's `DataAccessException` Translation

Although raw JDBC throws checked `java.sql.SQLException`, Spring repositories automatically translate JDBC errors into the unchecked **`DataAccessException`** hierarchy:

```
  java.sql.SQLException (Checked)
         │  (Translated by Spring PersistenceExceptionTranslationPostProcessor)
         ▼
  org.springframework.dao.DataAccessException (RuntimeException) ──► ✅ Triggers Automatic Rollback!
```

## 🔴 Senior Level

### Rule Resolution Engine: `RuleBasedTransactionAttribute`

When an exception escapes a `@Transactional` method, Spring evaluates `RuleBasedTransactionAttribute.rollbackOn()`:

```java
// Spring Framework source logic:
public boolean rollbackOn(Throwable ex) {
    // 1. Check user-defined rollbackRules (rollbackFor / noRollbackFor)
    for (RollbackRuleAttribute rule : this.rollbackRules) {
        int depth = rule.getDepth(ex);
        if (depth >= 0) {
            return (rule instanceof RollbackRuleAttribute); // Most specific rule wins!
        }
    }
    // 2. Fallback to default policy:
    return (ex instanceof RuntimeException || ex instanceof Error);
}
```

### The Silent Catch-and-Swallow Trap

```java
// 💥 HAZARDOUS PRODUCTION TRAP:
@Transactional
public void processBatch(List<Order> orders) {
    for (Order order : orders) {
        try {
            orderRepo.save(order);
            throw new RuntimeException("Database timeout");
        } catch (Exception e) {
            // Swallowing exception without re-throwing!
            log.error("Failed to save order", e);
        }
    }
    // 💥 Spring's TransactionInterceptor sees normal method return -> COMMITS corrupt partial data!
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Default Rule:** Spring rolls back on **`RuntimeException` and `Error`**, and **COMMITS** on checked `Exception`.
- **Customization:** Add `@Transactional(rollbackFor = Exception.class)` to force rollback on all checked exceptions.
- **Exception Swallowing:** Catching an exception in a `try-catch` without re-throwing or calling `setRollbackOnly()` results in a successful `COMMIT`.
- **Spring Data Exceptions:** `DataAccessException` is a `RuntimeException` and triggers automatic rollback.
- **Exclusion:** Use `noRollbackFor = SpecificException.class` to prevent rollbacks on designated exceptions.

**Common Follow-up Questions:**
- *"Why does Spring not roll back on checked exceptions by default?"* → Spring followed EJB design conventions where checked exceptions represented recoverable business conditions (e.g. `InsufficientFundsException`) that the calling code might want to commit alongside compensatory ledger records.
- *"How does Spring decide whether to rollback when both `rollbackFor` and `noRollbackFor` match the exception?"* → Spring computes the inheritance depth (`getDepth()`); the rule closest to the thrown exception's concrete class wins.
- *"What happens if an exception is thrown in a separate thread spawned by `@Async`?"* → The exception cannot cross thread boundaries to the parent transaction; it will not trigger rollback in the caller's transaction.

**Red Flags (DO NOT Say):**
- ❌ *"Spring rolls back for all exceptions by default."* (Checked exceptions commit by default).
- ❌ *"Custom business exceptions extending `Exception` automatically trigger rollback."* (They extend `Exception`, so they commit unless `rollbackFor` is specified).
- ❌ *"Catching an exception in a try-catch block still triggers transaction rollback."* (If swallowed, Spring observes a normal method exit and commits).
