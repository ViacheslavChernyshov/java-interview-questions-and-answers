# What is the Default Isolation Level in PostgreSQL?

---

## 🟢 Junior Level

The default transaction isolation level in **PostgreSQL** is **`Read Committed`**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Default Isolation Level                                │ **Read Committed**                                     │
  │ Concurrency Mechanism                                  │ **MVCC (Multi-Version Concurrency Control)**           │
  │ Snapshot Creation Frequency                            │ **A new MVCC snapshot for EVERY separate statement**   │
  │ Dirty Read Protection                                  │ ✅ **Strictly Prevented**                              │
  │ Non-Repeatable Read Protection                         │ ❌ **Permitted** (Values can change between queries)   │
  │ Phantom Read Protection                                │ ❌ **Permitted** (New rows can appear between queries) │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```sql
-- Checking the active default isolation level in PostgreSQL:
SHOW default_transaction_isolation; -- Returns 'read committed'
```

## 🟡 Middle Level

### How PostgreSQL Implements Read Committed via MVCC

In PostgreSQL, table rows are stored as multi-version tuples containing internal transaction header metadata:
- `t_xmin`: The Transaction ID (XID) that inserted this version.
- `t_xmax`: The Transaction ID that deleted or updated this version ($0$ if currently active).

```
  PostgreSQL Statement-Level Snapshot Lifecycle:
  1. Transaction T1 begins.
  2. Query 1 (SELECT): Allocates Snapshot A. Reads tuples where xmin was committed before T2.
  3. Concurrent Transaction T2 commits an UPDATE on row 1.
  4. Query 2 (SELECT): Allocates Snapshot B! 
     Snapshot B sees T2's committed changes because Snapshot B was created AFTER T2's commit.
```

```java
// Overriding default for financial reporting:
@Transactional(isolation = Isolation.REPEATABLE_READ)
public FinancialReport generateConsistentAuditReport(LocalDate date) {
    // Freezes a single snapshot for the entire method execution
    return reportService.calculate(date);
}
```

## 🔴 Senior Level

### PostgreSQL Isolation Matrix & Engine Quirks

```
  ┌──────────────────────────────┬──────────────────┬────────────────────────┬────────────────────────┬────────────────────────┐
  │ PostgreSQL Isolation Level   │ Dirty Read       │ Non-Repeatable Read    │ Phantom Read           │ Serialization Aborts?  │
  ├──────────────────────────────┼──────────────────┼────────────────────────┼────────────────────────┼────────────────────────┤
  │ **Read Uncommitted**         │ 🛡️ Prevented*    │ ❌ Allowed             │ ❌ Allowed             │ ❌ No                  │
  │ **Read Committed (Default)** │ 🛡️ **Prevented** │ ❌ **Allowed**         │ ❌ **Allowed**         │ ❌ **No**              │
  │ **Repeatable Read**          │ 🛡️ Prevented     │ 🛡️ Prevented           │ 🛡️ **Prevented** (MVCC)│ ⚠️ Yes (on write clash)│
  │ **Serializable (SSI)**       │ 🛡️ Prevented     │ 🛡️ Prevented           │ 🛡️ Prevented           │ 💥 Yes (`40001` aborts)│
  └──────────────────────────────┴──────────────────┴────────────────────────┴────────────────────────┴────────────────────────┘
```

> [!NOTE]
> *\* PostgreSQL Architectural Fact:* PostgreSQL lacks a physical `Read Uncommitted` engine. Issuing `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` **silently promotes the transaction to `Read Committed`**.

### Performance & Dead Tuple Garbage Collection (`VACUUM`)

Under high-update workloads:
- Every `UPDATE` in PostgreSQL creates a new heap tuple and marks the old tuple as dead (`xmax = updating_xid`).
- Under default `Read Committed`, short queries allow `autovacuum` to quickly clean up dead tuples.
- Under `Repeatable Read` or `Serializable`, long-running transactions prevent `VACUUM` from reclaiming dead tuples, causing severe **table and index bloat**.

```sql
-- Tuning aggressive autovacuum for high-throughput update tables:
ALTER TABLE accounts SET (
    autovacuum_vacuum_threshold = 100,
    autovacuum_vacuum_scale_factor = 0.05
);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Default Level:** PostgreSQL defaults to **`Read Committed`**.
- **Snapshot Timing:** Allocates a fresh MVCC snapshot before **every individual SQL statement**.
- **No Dirty Reads:** PostgreSQL MVCC completely eliminates dirty reads at zero locking cost.
- **Elevation Quirk:** Requesting `READ UNCOMMITTED` silently executes as `READ COMMITTED`.
- **Phantom Reads on RR:** PostgreSQL's `Repeatable Read` prevents phantom reads automatically via transaction snapshots.
- **Reporting Fix:** Use `Repeatable Read` for multi-query reporting to prevent drifting balance calculations.

**Common Follow-up Questions:**
- *"Why does PostgreSQL default to Read Committed instead of Repeatable Read?"* → Read Committed offers maximum throughput with zero serialization aborts and minimum table bloat, fitting 90%+ of OLTP application needs.
- *"What happens if two concurrent UPDATE statements hit the same row under Read Committed?"* → The second transaction blocks on the row lock; once the first commits, PostgreSQL uses **`EvalPlanQual` (EPQ)** to re-evaluate the `WHERE` clause on the new version without aborting.
- *"How can you detect long-running transactions holding back VACUUM in PostgreSQL?"* → Query `pg_stat_activity` for `backend_xid` and `now() - xact_start > interval '5 minutes'`.

**Red Flags (DO NOT Say):**
- ❌ *"PostgreSQL uses shared read locks for Read Committed transactions."* (PostgreSQL uses lock-free MVCC snapshots).
- ❌ *"PostgreSQL permits dirty reads under the Read Uncommitted setting."* (PostgreSQL promotes Read Uncommitted to Read Committed).
- ❌ *"Repeatable Read in PostgreSQL allows phantom reads."* (PostgreSQL's MVCC snapshot isolation prevents phantom reads on Repeatable Read).
