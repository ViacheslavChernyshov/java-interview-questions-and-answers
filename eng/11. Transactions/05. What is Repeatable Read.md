# What is Repeatable Read?

---

## 🟢 Junior Level

**Repeatable Read** is an isolation level guaranteeing that if a transaction reads a row once, **all subsequent reads of that exact same row will return the identical values**, regardless of concurrent modifications committed by other transactions:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Dirty Reads                                            │ ✅ **Strictly Prevented**                              │
  │ Non-Repeatable Reads                                   │ ✅ **Strictly Prevented** (Values remain unchanged)    │
  │ Phantom Reads                                          │ ⚖️ **Engine-Dependent** (Prevented in MySQL/PostgreSQL)│
  │ Default Database Engine                                │ **MySQL (InnoDB Engine)**                              │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```
  Repeatable Read Invariance Trace:
  Transaction A (Repeatable Read):
  1. BEGIN;
  2. SELECT price FROM products WHERE id = 1; ──► Returns $100

  Transaction B:
  3. UPDATE products SET price = $150 WHERE id = 1;
  4. COMMIT;

  Transaction A:
  5. SELECT price FROM products WHERE id = 1; ──► STILL Returns $100! (Consistent Snapshot)
  6. COMMIT;
```

## 🟡 Middle Level

### Database Engine Architectural Divergence

Although sharing the same name in ANSI SQL, **MySQL InnoDB** and **PostgreSQL** implement Repeatable Read using completely different underlying concurrency mechanics:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architectural Aspect         │ PostgreSQL Repeatable Read       │ MySQL InnoDB Repeatable Read                     │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Core Mechanism**           │ **Transaction-Level MVCC**       │ **MVCC + Next-Key Locking (Gap Locks)**          │
  │ **Phantom Read Protection**  │ Snapshot-level protection        │ Strict Index Gap Locking                         │
  │ **Concurrent Update Conflict**│ Aborts with **`SQLSTATE 40001`** │ **Blocks** on row lock (waits for commit)        │
  │ **Deadlock Frequency**       │ Low                              │ **Higher** (Due to range Gap Locks)              │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Next-Key Locking in MySQL InnoDB

```sql
-- MySQL InnoDB on index range [5, 10, 15]:
SELECT * FROM orders WHERE order_id BETWEEN 5 AND 10 FOR UPDATE;
```
- **Record Locks:** Locks existing rows `id = 5` and `id = 10`.
- **Gap Locks:** Locks the open interval gaps `(0, 5)`, `(5, 10)`, and `(10, 15)`.
- Blocks other transactions from executing `INSERT INTO orders (order_id) VALUES (7)`!

## 🔴 Senior Level

### The Write Skew Anomaly: Why Repeatable Read $\ne$ Serializable

Repeatable Read prevents Dirty and Non-Repeatable reads, but **permits Write Skew anomalies**:

```
  The On-Call Doctor Write Skew Puzzle:
  Invariant Rule: At least ONE doctor must remain on call (count >= 1).
  Initial State: Dr. Alice and Dr. Bob are BOTH on call (count = 2).

  Transaction A (Dr. Alice requests off):
  1. SELECT COUNT(*) FROM on_call; -- Sees 2 (Rule satisfied!)
  2. UPDATE doctors SET on_call = false WHERE name = 'Alice';

  Transaction B (Dr. Bob requests off concurrently):
  1. SELECT COUNT(*) FROM on_call; -- Sees 2 in its own snapshot!
  2. UPDATE doctors SET on_call = false WHERE name = 'Bob';

  Both transactions COMMIT under Repeatable Read!
  💥 DISASTER: Both doctors go off call simultaneously (count = 0), violating the invariant!
```

> [!CAUTION]
> To eliminate Write Skew, you must use **`Serializable` isolation** (or explicit locking via `SELECT ... FOR UPDATE`).

### PostgreSQL Snapshot Life Cycle & Table Bloat

Under PostgreSQL Repeatable Read:
- The snapshot is created on the **first query statement**, capturing active transaction IDs (`xmin`/`xmax`).
- **Table Bloat Hazard:** As long as a long-running Repeatable Read transaction remains active, PostgreSQL's `VACUUM` worker is **prohibited from cleaning dead row tuples** created after the transaction's `xmin`. Prolonged RR transactions cause severe disk bloat and memory degradation.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Ensures rows read once retain their exact values across all subsequent reads in the transaction.
- **MySQL Default:** MySQL InnoDB uses Repeatable Read as its default isolation level.
- **PostgreSQL Conflict:** If two concurrent transactions attempt to update the same row under RR, PostgreSQL aborts the second with `ERROR: could not serialize access (40001)`.
- **MySQL Gap Locks:** Next-Key Locks combine record locks with gap locks to prevent phantom inserts.
- **Write Skew:** Repeatable Read does NOT prevent Write Skew anomalies (requires `Serializable`).
- **Table Bloat:** Long-running RR transactions prevent `VACUUM` from removing dead tuples.

**Common Follow-up Questions:**
- *"Why does MySQL use Repeatable Read as its default instead of Read Committed?"* → Historically, MySQL relied on Statement-Based Replication (SBR). Under Read Committed, non-repeatable reads caused master and replica binlogs to execute transactions in different orders, desynchronizing data.
- *"How should an application handle a PostgreSQL 40001 serialization failure?"* → Implement an automated retry mechanism using Spring `@Retryable` with exponential backoff.
- *"What is the difference between a Snapshot in Read Committed vs Repeatable Read?"* → Read Committed allocates a new snapshot for each query statement; Repeatable Read reuses a single snapshot for the entire transaction.

**Red Flags (DO NOT Say):**
- ❌ *"Repeatable Read is 100% equivalent to Serializable."* (Repeatable Read allows Write Skew anomalies).
- ❌ *"PostgreSQL uses Gap Locks on Repeatable Read."* (PostgreSQL does not use gap locks; it uses MVCC and conflict aborts).
- ❌ *"Repeatable Read prevents write conflicts without throwing errors."* (In PostgreSQL, concurrent updates on the same row trigger an immediate transaction abort).
