# At What Level Can @Transactional Be Used?

---

## 🟢 Junior Level

In Spring Framework, the `@Transactional` annotation can be placed at the **Method Level**, **Class Level**, or **Interface Level**:

```
  ┌──────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Placement Level          │ Recommendation           │ Behavioral Impact                                │
  ├──────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **Method Level**         │ ⭐️ **Best Practice**     │ Precise control per operation (propagation, etc.)│
  │ **Class Level**          │ ✅ **Acceptable**        │ Sets defaults for all `public` methods in class  │
  │ **Interface Level**      │ 🚫 **Discouraged**       │ Ignored by CGLIB subclass proxies (Spring Boot)  │
  │ **Controller Level**     │ ❌ **Strict Anti-Pattern**│ Holds DB connections open during JSON responses  │
  └──────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

```java
// Method-Level Customization (Recommended):
@Service
public class OrderService {

    @Transactional(readOnly = true)
    public Order findById(Long id) { ... }

    @Transactional // readOnly = false (Overrides read-only)
    public void createOrder(Order order) { ... }
}
```

## 🟡 Middle Level

### Annotation Resolution & Precedence

Spring determines transaction attributes using **`AbstractFallbackTransactionAttributeSource`**:

```
  Method-Level Annotation (Class Implementation)  [HIGHEST PRIORITY]
         │
         ▼ (If absent)
  Class-Level Annotation (Class Implementation)
         │
         ▼ (If absent)
  Method-Level Annotation (Interface Declaration) [JDK Proxy only]
         │
         ▼ (If absent)
  Interface-Level Annotation                      [JDK Proxy only] [LOWEST PRIORITY]
```

### Class-Level Default with Method-Level Override

```java
@Service
@Transactional(readOnly = true) // Baseline for all query methods
public class CustomerService {

    public Customer getCustomer(Long id) { // Inherits readOnly = true
        return customerRepo.findById(id).orElseThrow();
    }

    @Transactional // Overrides baseline to readOnly = false!
    public void updateAddress(Long id, Address address) {
        Customer c = getCustomer(id);
        c.setAddress(address);
    }
}
```

## 🔴 Senior Level

### The CGLIB vs. JDK Proxy Interface Trap

Because Spring Boot defaults to **CGLIB Class Subclassing Proxies** (`spring.aop.proxy-target-class = true`):
- Annotations declared on **Interfaces** are not inherited by CGLIB subclass bytecode!
- If `@Transactional` is placed on the interface and the service class lacks the annotation, transactions are **silently omitted**!

```java
// ❌ SILENT TRANSACTION FAILURE (with CGLIB proxying):
public interface PaymentService {
    @Transactional // CGLIB ignores this!
    void process(Payment p);
}

@Service
public class PaymentServiceImpl implements PaymentService {
    public void process(Payment p) { ... } // Executes NON-TRANSACTIONALLY!
}
```

### The Open Session in View (OSIV) Anti-Pattern

```
  HTTP Request ──► OSIV Filter (Opens DB Session) ──► Controller ──► Service (@Transactional)
                                                                            │
  HTTP Response ◄── Jackson JSON Serialization (Triggers Lazy Queries!) ◄───┘
```

> [!WARNING]
> By default, `spring.jpa.open-in-view = true` keeps the database session open throughout the entire HTTP request lifecycle. Any uninitialized lazy-loaded relationships accessed during Jackson JSON serialization trigger **silent N+1 query storms**, exhausting database connections.
>
> **Production Fix:** Set `spring.jpa.open-in-view = false` in `application.yml` and use DTO projections with explicit `JOIN FETCH` queries in the service layer.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Best Practice:** Place `@Transactional` on **implementation classes and individual methods** in the service layer.
- **Precedence:** Method-level annotations strictly override class-level annotations.
- **Interface Trap:** Placing `@Transactional` on interfaces fails under CGLIB proxying (Spring Boot's default).
- **Public Methods Only:** Only `public` methods can be intercepted by Spring's AOP proxy.
- **Controllers:** Never place `@Transactional` on Controller classes (wastes connection pool slots during HTTP I/O).
- **OSIV:** Disable `spring.jpa.open-in-view` to prevent hidden N+1 queries during JSON response serialization.

**Common Follow-up Questions:**
- *"What happens if a class has `@Transactional(readOnly = true)` and a method within it executes a repository `@Modifying` query without overriding `@Transactional`?"* → Spring throws a `TransactionRequiredException` or `InvalidDataAccessApiUsageException` because write operations are forbidden within a read-only transaction context.
- *"Why does Spring Boot use CGLIB proxying by default instead of JDK Dynamic Proxies?"* → CGLIB can proxy concrete classes directly without requiring interface definitions, enabling seamless dependency injection by class type.
- *"How does `@Transactional` interact with Spring Data JPA repository interfaces?"* → Spring Data repositories come pre-annotated with `@Transactional(readOnly = true)` at the implementation level (`SimpleJpaRepository`); service-level `@Transactional` declarations join or override these boundaries.

**Red Flags (DO NOT Say):**
- ❌ *"Placing `@Transactional` on an interface is the recommended enterprise pattern."* (It fails silently under CGLIB proxies).
- ❌ *"Class-level `@Transactional` applies to `private` and `protected` methods."* (Spring AOP proxies only intercept `public` methods).
- ❌ *"Controllers should be marked `@Transactional` so the view can lazy-load database entities."* (This is the OSIV anti-pattern that leads to severe connection starvation).
