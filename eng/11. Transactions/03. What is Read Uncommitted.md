# What is Read Uncommitted?

---

## 🟢 Junior Level

**Read Uncommitted** is the lowest transaction isolation level in the ANSI SQL standard. At this level, a transaction can read modifications made by other concurrent transactions **before they are committed**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Primary Concurrency Anomaly                            │ **Dirty Read** (Reading uncommitted, rolled-back data) │
  │ Secondary Concurrency Anomalies                        │ **Non-Repeatable Reads** and **Phantom Reads**         │
  │ Production Recommendation                              │ 🚫 **Anti-Pattern** (Avoid for business logic)         │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```
  Dirty Read Scenario:
  Transaction A (Wants to transfer funds):
  1. BEGIN;
  2. UPDATE accounts SET balance = 500 WHERE id = 1; -- Uncommitted!

  Transaction B (Read Uncommitted):
  3. SELECT balance FROM accounts WHERE id = 1; ──► Sees balance = 500!

  Transaction A (Encounters Error):
  4. ROLLBACK; -- Balance restored to original $100!

  Transaction B:
  5. Approves credit decision based on phantom $500 balance that never existed!
```

## 🟡 Middle Level

### Database Engine Behaviors

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ Database Engine              │ Behavior Under `READ UNCOMMITTED`                                           │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ **PostgreSQL**               │ **Silent Elevation:** Automatically treats as `READ COMMITTED`.             │
  │ **Oracle**                   │ **Silent Elevation:** Forbids levels below `READ COMMITTED`.                │
  │ **MySQL (InnoDB)**           │ Reads in-flight buffer pool pages directly without consulting undo logs.   │
  │ **Microsoft SQL Server**     │ Bypasses shared read locks; activated via `SELECT ... WITH (NOLOCK)`.       │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

> [!NOTE]
> **Why Modern MVCC Engines Suppress Read Uncommitted:**
> In PostgreSQL and Oracle, Multi-Version Concurrency Control (MVCC) guarantees that readers only see committed tuple versions. Preventing dirty reads is an architectural zero-cost default, rendering Read Uncommitted unnecessary.

## 🔴 Senior Level

### The Severe Risks of SQL Server `NOLOCK`

In Microsoft SQL Server, developers frequently add `WITH (NOLOCK)` to avoid blocking locks during reporting queries:

```sql
-- ⚠️ HAZARDOUS PRODUCTION QUERY:
SELECT COUNT(*), SUM(amount) FROM transactions WITH (NOLOCK);
```

```
  Hidden Dangers of NOLOCK:
  1. Dirty Reads: Aggregates numbers from failed transactions that are later aborted.
  2. Page Allocation Corruption: If an active transaction causes an index B-tree page split 
     while a NOLOCK query scans pages, the query can SKIP rows or READ DUPLICATE rows!
  3. Non-Deterministic Data: Financial totals will not balance across successive runs.
```

### Production Alternatives to Read Uncommitted

When query throughput must be maximized without locking active write transactions:
1. **Read Committed MVCC:** Use standard Read Committed with optimal composite indexes.
2. **Read Replicas:** Route heavy reporting queries to asynchronous read-only database replicas.
3. **Materialized Views:** Precompute aggregate statistics asynchronously.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Weakest isolation level; allows reading uncommitted data from active transactions.
- **Primary Hazard:** **Dirty Read** — reading temporary data that is subsequently rolled back.
- **Engine Elevation:** PostgreSQL and Oracle do not support dirty reads; they silently elevate to **Read Committed**.
- **MS SQL Server:** Implemented via `WITH (NOLOCK)` query hints.
- **Production Stance:** Prohibited for financial or business logic; acceptable only for approximate analytics or telemetry dashboards.

**Common Follow-up Questions:**
- *"Why does PostgreSQL not support Read Uncommitted?"* → Because PostgreSQL's MVCC tuple visibility rules (`xmin`/`xmax`) check commit status by default; enabling uncommitted reads would require extra logic and add zero performance benefit.
- *"Can a Read Uncommitted transaction cause data corruption in the database?"* → The read itself does not corrupt the database schema, but application code taking actions based on dirty uncommitted data will write corrupt business records back into the database.
- *"What anomalies are possible under Read Uncommitted?"* → All standard anomalies: Dirty Reads, Non-Repeatable Reads, and Phantom Reads.

**Red Flags (DO NOT Say):**
- ❌ *"Read Uncommitted is 10x faster than Read Committed in PostgreSQL."* (In PostgreSQL, both execute identically as Read Committed with zero performance difference).
- ❌ *"NOLOCK is completely safe for read-only reporting queries."* (It can read duplicate rows and skip records during page splits).
- ❌ *"Dirty reads only happen if the database crashes."* (They happen whenever an active transaction rolls back or fails).
