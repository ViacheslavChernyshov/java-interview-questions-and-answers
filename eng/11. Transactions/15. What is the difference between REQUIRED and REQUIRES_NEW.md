# What is the Difference Between REQUIRED and REQUIRES_NEW?

---

## 🟢 Junior Level

`REQUIRED` and `REQUIRES_NEW` are the two most frequently used transaction propagation modes in Spring Framework:

```
  ┌──────────────────────────┬─────────────────────────────────────────────┬───────────────────────────────────────────────┐
  │ Characteristic           │ `Propagation.REQUIRED` (Default)            │ `Propagation.REQUIRES_NEW`                    │
  ├──────────────────────────┼─────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ **Transaction Creation** │ **Joins existing**; creates new only if none│ **Always suspends existing** & creates new    │
  │ **Physical DB Sessions** │ **1 Shared Transaction & 1 Connection**     │ **2 Separate Transactions & 2 Connections**   │
  │ **Commit Timing**        │ Single atomic `COMMIT` at end of outer method│ Inner method `COMMITS` immediately on exit    │
  │ **Outer Rollback Effect**│ **Rolls back all inner & outer operations** │ **Inner commit remains permanently saved**    │
  │ **Inner Exception Result**│ **Marks entire transaction as Rollback-Only**│ Outer can catch and proceed with its own `COMMIT`│
  └──────────────────────────┴─────────────────────────────────────────────┴───────────────────────────────────────────────┘
```

```java
// REQUIRED: If order creation fails, audit log ALSO rolls back (Shared atomicity)
@Transactional(propagation = Propagation.REQUIRED)
public void createOrder(Order order) { ... }

// REQUIRES_NEW: If order creation fails, audit log SURVIVES (Independent persistence)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logAuditAttempt(Order order) { ... }
```

## 🟡 Middle Level

### The Inner Exception Handling Trap

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Calling Context                                        │ Result When Inner Method Throws Exception              │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ **Outer (REQUIRED) ──► Inner (REQUIRED)**              │ 💥 Spring marks transaction as **Rollback-Only**!      │
  │                                                        │ Even if outer catches exception in a `try-catch`,      │
  │                                                        │ outer `COMMIT` throws **`UnexpectedRollbackException`**│
  │ **Outer (REQUIRED) ──► Inner (REQUIRES_NEW)**          │ 🛡️ Inner rolls back independently. Outer catches       │
  │                                                        │ exception and successfully commits its own changes!    │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
@Service
public class PaymentService {

    @Autowired private AuditService auditService;
    @Autowired private PaymentRepository paymentRepo;

    @Transactional // REQUIRED
    public void processPayment(Payment payment) {
        paymentRepo.save(payment);

        try {
            // REQUIRES_NEW: If audit logging fails, payment still commits cleanly!
            auditService.logPaymentAttempt(payment);
        } catch (AuditLoggingException e) {
            log.warn("Non-critical audit failure; proceeding with payment processing", e);
        }
    }
}
```

## 🔴 Senior Level

### Low-Level Spring Suspension Mechanics

When entering a `REQUIRES_NEW` method:

```
  1. AbstractPlatformTransactionManager.suspend():
     • Unbinds outer ConnectionHolder from ThreadLocal (TransactionSynchronizationManager.unbindResource).
     • Suspends active transaction synchronizations (Hibernate Session, JTA callbacks).
     • Packages active state into a SuspendedResourcesHolder object.

  2. New Transaction Execution:
     • Acquires a SECOND physical connection from HikariCP pool.
     • Starts a fresh JDBC transaction (connection.setAutoCommit(false)).
     • Binds new ConnectionHolder to ThreadLocal.

  3. Cleanup & Resume:
     • Commits/rolls back inner transaction and releases the second connection back to pool.
     • Re-binds original ConnectionHolder to ThreadLocal and resumes synchronizations.
```

### HikariCP Connection Pool Exhaustion Formula

Because `REQUIRES_NEW` checks out a second connection from the pool while holding the first:

```
  Connection Pool Sizing Invariant:
  If MaxConcurrentThreads = N and each thread executes REQUIRES_NEW:
  Minimum Pool Size >= N * 2

  If pool size is less than N * 2, all N threads will acquire Connection 1, 
  and all N threads will deadlock waiting for Connection 2 from the exhausted pool!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`REQUIRED`:** Reuses the existing transaction; creates a new one only if absent.
- **`REQUIRES_NEW`:** Always suspends the current transaction and opens a brand new physical database transaction.
- **Connection Usage:** `REQUIRED` uses 1 connection; `REQUIRES_NEW` holds **2 connections simultaneously**.
- **Rollback-Only:** An uncaught exception in an inner `REQUIRED` method marks the shared transaction as rollback-only; outer `try-catch` cannot prevent `UnexpectedRollbackException`.
- **Surviving Rollback:** Use `REQUIRES_NEW` when inner operations (e.g. security audits, credit checks) must commit regardless of outer transaction success.
- **Deadlock Warning:** Nested `REQUIRES_NEW` under heavy concurrent load can exhaust HikariCP connection pools.

**Common Follow-up Questions:**
- *"What exception is thrown when an outer method tries to commit a transaction marked rollback-only by an inner REQUIRED method?"* → Spring throws `org.springframework.transaction.UnexpectedRollbackException`.
- *"How does Spring manage transaction suspension in a multi-threaded environment?"* → Spring stores the active transaction context in a `ThreadLocal` variable via `TransactionSynchronizationManager`, unbinding and re-binding connections during suspension.
- *"Why should you not use `REQUIRES_NEW` for related business entities (e.g. Order and OrderItems)?"* → Because if the outer order creation rolls back, the inner order items will remain committed, causing orphaned, inconsistent data.

**Red Flags (DO NOT Say):**
- ❌ *"Catching an exception from an inner `REQUIRED` method allows the outer transaction to commit normally."* (The transaction is already marked rollback-only; commit will throw an exception).
- ❌ *"REQUIRES_NEW executes asynchronously in a separate thread."* (It executes synchronously on the same thread, suspending the outer connection).
- ❌ *"REQUIRED and REQUIRES_NEW consume the exact same number of database connections."* (REQUIRES_NEW holds 2 connections per thread during inner execution).
