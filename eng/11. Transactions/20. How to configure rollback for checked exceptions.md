# How to Configure Rollback for Checked Exceptions?

---

## 🟢 Junior Level

By default, Spring does not roll back transactions when a **Checked Exception** (`extends Exception`) is thrown.

To configure Spring to roll back for checked exceptions, use the **`rollbackFor`** attribute:

```java
// 1. Rollback on ANY exception (Checked or Unchecked):
@Transactional(rollbackFor = Exception.class)
public void processOrder(Order order) throws BusinessException {
    orderRepository.save(order);
    if (!order.isValid()) {
        throw new BusinessException("Order validation failed"); // Triggers ROLLBACK!
    }
}
```

```java
// 2. Rollback for specific checked exceptions:
@Transactional(rollbackFor = {IOException.class, SQLException.class})
public void importData(File file) throws IOException, SQLException {
    dataImporter.read(file);
}
```

## 🟡 Middle Level

### The Three Architectural Approaches

```
  ┌───┬──────────────────────────────────┬────────────────────────────┬────────────────────────────────────────┐
  │ # │ Approach                         │ Syntax                     │ When to Use                            │
  ├───┼──────────────────────────────────┼────────────────────────────┼────────────────────────────────────────┤
  │ 1 │ **Declarative `rollbackFor`**    │ `rollbackFor = Exc.class`  │ Standard approach when using checked   │
  │ 2 │ **Unchecked Hierarchy Design**   │ `extends RuntimeException` │ ⭐️ **Modern Best Practice** in Spring  │
  │ 3 │ **Programmatic `setRollbackOnly`│ `txStatus.setRollbackOnly` │ Conditional rollback without throwing  │
  └───┴──────────────────────────────────┴────────────────────────────┴────────────────────────────────────────┘
```

### Combining `rollbackFor` and `noRollbackFor`

```java
@Transactional(
    rollbackFor = Exception.class,
    noRollbackFor = {EntityNotFoundException.class, ValidationWarningException.class}
)
public void processPayment(Payment p) throws Exception {
    // Exception -> ROLLBACK
    // EntityNotFoundException -> COMMITS (Excluded by noRollbackFor)
}
```

## 🔴 Senior Level

### Rule Resolution Priority & Inheritance Depth

Spring resolves rollback rules inside **`RuleBasedTransactionAttribute`** by computing the inheritance depth (`getDepth()`):

```
  Thrown Exception: FileNotFoundException
  
  Rule A: rollbackFor = Exception.class         (Depth = 3: FileNotFoundException -> IOException -> Exception)
  Rule B: noRollbackFor = IOException.class     (Depth = 1: FileNotFoundException -> IOException)
  
  Resolution: Rule B has smaller depth (closer in inheritance hierarchy) -> NO ROLLBACK wins!
```

### The String-Based `rollbackForClassName` Hazard

```java
// ⚠️ HAZARDOUS ANTI-PATTERN:
@Transactional(rollbackForClassName = "PaymentExceptoin") // Typo in string!
public void executeTransfer() throws PaymentException { ... }
```

> [!WARNING]
> `rollbackForClassName` resolves string names lazily at runtime. Spring performs **no compile-time validation or startup checking**. If a typo exists, the rule fails silently, and the transaction will unexpectedly **`COMMIT`** during exceptions!
> Always use type-safe Class literals: `rollbackFor = PaymentException.class`.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The Problem:** Checked exceptions (`extends Exception`) commit by default in Spring.
- **The Fix:** Add `@Transactional(rollbackFor = Exception.class)`.
- **Modern Best Practice:** Inherit all custom domain exceptions from `RuntimeException` to enable automatic rollback without annotation clutter.
- **Exclusion:** Use `noRollbackFor` to exclude specific exceptions from rollback.
- **String Danger:** Avoid `rollbackForClassName` due to silent runtime typo failures.
- **Programmatic Fallback:** Call `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`.

**Common Follow-up Questions:**
- *"What happens if a method is annotated with `@Transactional(rollbackFor = Exception.class)` and throws an `Error` (e.g. `OutOfMemoryError`)?"* → It still rolls back because `Error` is covered by Spring's built-in default rollback rule.
- *"How does Spring decide between conflicting `rollbackFor` and `noRollbackFor` rules?"* → Spring traverses the exception's superclass hierarchy; the rule that matches the exception with the shortest inheritance distance (depth) takes precedence.
- *"Why do modern Java and Spring frameworks favor RuntimeExceptions over checked Exceptions?"* → RuntimeExceptions eliminate throws-clause pollution across service layers, integrate cleanly with functional Lambdas/Streams, and trigger automatic transaction rollbacks.

**Red Flags (DO NOT Say):**
- ❌ *"Checked exceptions automatically roll back if you add `@Transactional`."* (They commit unless `rollbackFor` is specified).
- ❌ *"Using `rollbackForClassName` is safer because it avoids class-loading dependencies."* (It is error-prone and fails silently on typos).
- ❌ *"You cannot combine `rollbackFor` and `noRollbackFor` on the same method."* (You can combine them; Spring resolves priority via inheritance depth).
