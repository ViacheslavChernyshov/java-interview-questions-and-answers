# What is Non-Repeatable Read?

---

## 🟢 Junior Level

A **Non-Repeatable Read** is a concurrency anomaly where a transaction reads the same existing row multiple times and observes **different column values**, because another concurrent transaction updated or deleted the row and committed the change in between:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Anomaly Description                                    │ Existing row data changes between two `SELECT` queries │
  │ Permitted In                                           │ **Read Uncommitted**, **Read Committed**               │
  │ Prevented In                                           │ **Repeatable Read**, **Serializable**                  │
  │ Mutation Type                                          │ `UPDATE` or `DELETE` on existing records               │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```
  Non-Repeatable Read Timeline:
  Transaction A (Read Committed)              Transaction B (Writer)
  ────────────────────────────────────────────────────────────────────────────────────────────────────────
  1. BEGIN;
  2. SELECT price FROM items WHERE id = 1; ──► Returns $100
  3.                                          UPDATE items SET price = $150 WHERE id = 1;
  4.                                          COMMIT;
  5. SELECT price FROM items WHERE id = 1; ──► Returns $150! (Value changed mid-transaction!)
```

## 🟡 Middle Level

### Non-Repeatable Read vs. Phantom Read

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Parameter                    │ Non-Repeatable Read          │ Phantom Read                                     │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Target Rows**              │ **Existing rows**            │ **New / non-existent rows**                      │
  │ **Triggering SQL**           │ Concurrent `UPDATE` / `DELETE`│ Concurrent `INSERT`                              │
  │ **Query Type Affected**      │ Single-row lookups (`id = ?`)│ **Range & aggregate queries** (`WHERE age > 20`) │
  │ **Business Vulnerability**   │ Corrupts read-modify-write   │ Corrupts summary totals and billing reports      │
  └──────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### Architectural Cause: Per-Statement MVCC Snapshots

In PostgreSQL under **Read Committed**, each `SELECT` creates a fresh MVCC snapshot. Between statements 2 and 5, Transaction B committed its changes; hence, statement 5's new snapshot includes Transaction B's committed updates.

## 🔴 Senior Level

### Remediation Strategies in Production

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │ # │ Pattern                          │ Implementation & Mechanics                                                  │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 1 │ **Repeatable Read Isolation**    │ `@Transactional(isolation = Isolation.REPEATABLE_READ)` (Freezes snapshot)  │
  │ 2 │ **Pessimistic Row Locking**      │ `SELECT ... FOR UPDATE` (Acquires exclusive row lock, blocking writers)    │
  │ 3 │ **Optimistic Locking**           │ JPA `@Version` (Validates version timestamp on commit; fails on conflict)   │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘
```

```java
// Production Pattern: Locking critical rows to guarantee repeatable reads
@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT o FROM Order o WHERE o.id = :id")
    Optional<Order> findByIdForUpdate(@Param("id") Long id);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A re-read of the same record within a single transaction returns different values due to a concurrent committed `UPDATE`/`DELETE`.
- **Occurrence:** Occurs in `Read Committed`; prevented in `Repeatable Read` and `Serializable`.
- **Contrast with Phantom:** Non-Repeatable Read modifies *existing* rows; Phantom Read inserts *new* rows.
- **Root Cause:** In Read Committed, each separate query allocates a new MVCC snapshot reflecting freshly committed updates.
- **Fixes:** Upgrade transaction isolation to `Repeatable Read`, use `SELECT ... FOR UPDATE`, or apply JPA `@Version` optimistic locking.

**Common Follow-up Questions:**
- *"Why does Repeatable Read prevent Non-Repeatable Reads?"* → Under Repeatable Read, the transaction reuses the initial MVCC snapshot taken at the start of the transaction for all subsequent queries, ignoring all later commits.
- *"How does a Non-Repeatable Read break business logic?"* → If Step 1 verifies that `user.accountBalance >= 100` and Step 2 executes a debit without row locking, a concurrent update could have emptied the account in between, resulting in overdrafts.
- *"Can Non-Repeatable Reads happen in MySQL InnoDB?"* → Not under MySQL's default isolation level (`Repeatable Read`), but they will occur if the isolation level is changed to `Read Committed`.

**Red Flags (DO NOT Say):**
- ❌ *"Non-Repeatable Read is caused by uncommitted dirty writes."* (It is caused by committed transactions; uncommitted changes cause Dirty Reads).
- ❌ *"Non-Repeatable Read and Phantom Read are identical concepts."* (Non-Repeatable affects existing rows; Phantom affects new rows in range queries).
- ❌ *"PostgreSQL Read Committed prevents Non-Repeatable Reads."* (PostgreSQL Read Committed permits Non-Repeatable Reads by design).
