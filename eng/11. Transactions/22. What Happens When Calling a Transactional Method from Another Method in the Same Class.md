# What Happens When Calling a @Transactional Method from Another Method in the Same Class?

---

## 🟢 Junior Level

When a method calls another `@Transactional` method **within the same class**, the `@Transactional` annotation on the inner method is **completely ignored**:

```java
@Service
public class OrderService {

    public void processOrder(Order order) {
        // Direct internal call: bypasses Spring AOP Proxy!
        saveToDatabase(order); 
    }

    @Transactional // ⚠️ SILENTLY IGNORED! Executes without a database transaction!
    public void saveToDatabase(Order order) {
        orderRepository.save(order);
    }
}
```

```
  Why this happens (The Self-Invocation Problem):
  • Spring transaction management relies on AOP Proxy wrappers.
  • External callers invoke methods on the Proxy wrapper.
  • Internal method calls evaluate to `this.saveToDatabase()`, which talks 
    directly to the raw underlying Java instance, bypassing the proxy!
```

---

## 🟡 Middle Level

### Visualizing the Proxy Bypass

```
  External Client Call:
  Client ──► OrderService Proxy (CGLIB) ──► TransactionInterceptor (Opens Tx) ──► Target Bean Method
                                                                                         │
  Internal Self-Invocation:                                                              │
  Method A ──► this.methodB() ──► Executes directly on Target Instance (NO PROXY / NO TX!) ◄┘
```

## 🔴 Senior Level

### Four Architectural Solutions

#### 1. Extract to a Dedicated Service Bean (⭐️ Recommended Best Practice)

Adheres to the **Single Responsibility Principle (SRP)** and maintains clean architectural boundaries:

```java
@Service
public class OrderService {
    @Autowired private OrderPersistenceService persistenceService;

    public void processOrder(Order order) {
        persistenceService.saveOrder(order); // Intercepted by proxy cleanly!
    }
}

@Service
public class OrderPersistenceService {
    @Transactional
    public void saveOrder(Order order) {
        orderRepo.save(order);
    }
}
```

#### 2. Self-Injection with `@Lazy`

```java
@Service
public class OrderService {
    @Autowired @Lazy private OrderService self; // Injects the CGLIB proxy bean

    public void processOrder(Order order) {
        self.saveToDatabase(order); // Calls through proxy!
    }

    @Transactional
    public void saveToDatabase(Order order) {
        orderRepo.save(order);
    }
}
```

#### 3. Programmatic `TransactionTemplate`

```java
@Service
public class OrderService {
    @Autowired private TransactionTemplate transactionTemplate;

    public void processOrder(Order order) {
        transactionTemplate.executeWithoutResult(status -> {
            saveToDatabase(order); // Runs transactionally without proxy tricks!
        });
    }

    public void saveToDatabase(Order order) {
        orderRepo.save(order);
    }
}
```

#### 4. AspectJ Bytecode Weaving

- Replaces Spring's runtime dynamic proxying with **AspectJ Compile-Time Weaving (CTW)** or **Load-Time Weaving (LTW)**.
- Injects transaction bytecode directly into the `.class` file, enabling transaction interception on `this.method()`, `private`, and `protected` calls.

---

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The Issue:** Self-invocation (`this.method()`) completely bypasses Spring AOP dynamic proxies, disabling `@Transactional`.
- **Root Cause:** Spring's AOP proxy wraps the bean; internal `this` method calls execute on the raw target JVM instance without passing through `TransactionInterceptor`.
- **Top Solution:** Refactor internal transactional logic into a separate `@Service` bean.
- **Alternative 1:** Inject the bean into itself via `@Autowired @Lazy private MyService self;`.
- **Alternative 2:** Use programmatic transaction management via `TransactionTemplate`.
- **AspectJ:** AspectJ compile-time / load-time bytecode weaving solves self-invocation natively.

**Common Follow-up Questions:**
- *"Why is `@Lazy` required when self-injecting a bean?"* → Without `@Lazy`, Spring encounters a circular dependency error during bean instantiation (`BeanCurrentlyInCreationException`).
- *"Can you use `AopContext.currentProxy()` to resolve self-invocation?"* → Yes, if `@EnableAspectJAutoProxy(exposeProxy = true)` is configured, but it tightly couples domain code to the Spring AOP runtime API.
- *"Does self-invocation also bypass other Spring annotations like `@Async`, `@Cacheable`, and `@Secured`?"* → Yes; all proxy-based Spring annotations (`@Async`, `@Cacheable`, `@PreAuthorize`, `@Retryable`) fail silently during self-invocation.

**Red Flags (DO NOT Say):**
- ❌ *"Spring CGLIB proxies can intercept `this` internal method calls."* (CGLIB subclass proxies still evaluate `this` against the target instance).
- ❌ *"Making the method `public` is enough to fix self-invocation inside the same class."* (Visibility does not solve proxy bypass; the call must pass through the proxy bean).
- ❌ *"TransactionTemplate requires proxy configuration to function."* (TransactionTemplate is purely programmatic and executes directly on the database transaction manager).
