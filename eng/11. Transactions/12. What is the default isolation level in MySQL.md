# What is the Default Isolation Level in MySQL?

---

## 🟢 Junior Level

The default transaction isolation level in **MySQL (InnoDB storage engine)** is **`Repeatable Read`**:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Default Isolation Level                                │ **Repeatable Read**                                    │
  │ Default Storage Engine                                 │ **InnoDB**                                             │
  │ Concurrency Mechanism                                  │ **MVCC (Undo Log) + Next-Key Locking (Gap Locks)**     │
  │ Dirty Read Protection                                  │ ✅ **Strictly Prevented**                              │
  │ Non-Repeatable Read Protection                         │ ✅ **Strictly Prevented** (Values frozen in snapshot)  │
  │ Phantom Read Protection                                │ ✅ **Prevented** (via Next-Key Locks on indexed ranges)│
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```sql
-- Checking the active transaction isolation level in MySQL:
SELECT @@GLOBAL.transaction_isolation, @@SESSION.transaction_isolation;
-- Returns 'REPEATABLE-READ'
```

## 🟡 Middle Level

### Why MySQL Defaults to Repeatable Read (Historical SBR Context)

```
  Historical Statement-Based Replication (SBR) Requirement:
  • Early MySQL versions copied raw SQL statements across master-replica replication streams.
  • Under Read Committed, non-repeatable reads caused transactions to commit in different 
    orders on replicas, causing massive data divergence between master and replica!
  • Repeatable Read was mandated to enforce deterministic statement replication.
```

### Next-Key Locking: Record Locks + Gap Locks

In addition to MVCC read snapshots, InnoDB uses **Next-Key Locks** on locking queries (`FOR UPDATE`, `LOCK IN SHARE MODE`, `UPDATE`, `DELETE`):

```sql
-- InnoDB locks index intervals:
SELECT * FROM orders WHERE order_id BETWEEN 10 AND 20 FOR UPDATE;
```
- **Record Locks:** Locks rows with `order_id` values $10, 11, \dots, 20$.
- **Gap Locks:** Locks the unallocated key intervals `(0, 10)`, `(10, 20)`, and `(20, 30)`.
- Prevents concurrent transactions from inserting new rows into the gap, eliminating phantom reads at the cost of **higher deadlock risks**.

## 🔴 Senior Level

### MySQL (InnoDB) vs. PostgreSQL MVCC Architecture

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architectural Parameter      │ MySQL InnoDB                     │ PostgreSQL                                       │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Default Isolation Level**  │ **`Repeatable Read`**            │ **`Read Committed`**                             │
  │ **MVCC Version Storage**     │ **Undo Log Tablespace**          │ **Main Table Heap Tuples** (with `xmin`/`xmax`)  │
  │ **Table File Bloat**         │ Minimal (Undo purged by threads) │ High (Dead tuples require `VACUUM` cleanup)      │
  │ **Phantom Read Defense**     │ **Next-Key Gap Locks**           │ **MVCC Snapshot Isolation**                      │
  │ **Deadlock Frequency**       │ **Higher** (Due to Gap Locks)    │ **Lower** (Zero gap locking on standard updates) │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Modern Enterprise Recommendation: Switch MySQL to `Read Committed`

In modern MySQL 8.0+ architectures utilizing **Row-Based Replication (`binlog_format = ROW`)**:
- Statement-based replication constraints no longer apply.
- Switching to `Read Committed` **completely disables Gap Locking** for non-locking queries, reducing database deadlocks by **80% to 95%** under high-concurrency write workloads.

```ini
# Production /etc/my.cnf optimization for highload microservices:
[mysqld]
transaction-isolation = READ-COMMITTED
binlog_format = ROW
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Default Level:** MySQL InnoDB defaults to **`Repeatable Read`**.
- **Historical Reason:** Enforced deterministic Statement-Based Replication (SBR) before Row-Based Replication became standard.
- **Next-Key Locking:** Combines Record Locks with **Gap Locks** to eliminate phantom reads on indexed ranges.
- **MVCC Mechanism:** Stores previous row versions inside the **Undo Log** (`DB_ROLL_PTR`), unlike PostgreSQL which leaves dead tuples in the heap table.
- **Deadlock Trade-off:** Gap locks significantly increase deadlock frequencies compared to PostgreSQL.
- **Production Tuning:** High-throughput microservices should switch MySQL to `READ-COMMITTED` alongside `binlog_format = ROW`.

**Common Follow-up Questions:**
- *"What is the difference between an InnoDB Record Lock and a Gap Lock?"* → A Record Lock locks an existing index row; a Gap Lock locks the empty interval between two index records to prevent concurrent `INSERT` statements into that space.
- *"Why do long-running Repeatable Read transactions cause undo log bloat in MySQL?"* → Active Read Views prevent InnoDB's background Purge threads from freeing old transaction records from the undo tablespace.
- *"How does MySQL deadlock resolution work?"* → InnoDB builds an in-memory wait-for graph, detects cycles, and automatically rolls back the transaction with the fewest undo log records.

**Red Flags (DO NOT Say):**
- ❌ *"MySQL and PostgreSQL use the exact same default isolation level."* (MySQL defaults to `Repeatable Read`; PostgreSQL defaults to `Read Committed`).
- ❌ *"Gap Locks are only used in Serializable isolation in MySQL."* (Gap Locks are actively used in MySQL's default `Repeatable Read` level).
- ❌ *"PostgreSQL uses Undo Logs just like MySQL."* (PostgreSQL stores multi-version tuples directly in the heap table; MySQL stores version deltas in the Undo Log).
