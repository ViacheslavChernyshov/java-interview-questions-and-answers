# What is Phantom Read?

---

## 🟢 Junior Level

A **Phantom Read** is a database concurrency anomaly where a transaction executes a range search query (e.g. `WHERE status = 'PENDING'`), and upon repeating the exact same query later in the transaction, discovers **new rows that did not exist previously** (or finds that previously matched rows have disappeared):

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Anomaly Type                                           │ New rows appearing in range / aggregate queries        │
  │ Triggering SQL Command                                 │ Concurrent **`INSERT`** (or `DELETE`) committed by T2  │
  │ ANSI SQL Permitted Levels                              │ **Read Uncommitted**, **Read Committed**, **Repeatable │
  │                                                        │ Read** (Allowed in standard, prevented in MySQL/PG)    │
  │ Prevented Under                                        │ **Serializable**                                       │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```sql
-- Transaction 1:
BEGIN;
SELECT COUNT(*) FROM orders WHERE status = 'PENDING'; -- Returns 5

-- In the meantime, Transaction 2 executes concurrently:
-- INSERT INTO orders (id, status) VALUES (99, 'PENDING'); COMMIT;

-- Transaction 1 repeats the query:
SELECT COUNT(*) FROM orders WHERE status = 'PENDING'; -- Returns 6 (Phantom row appeared!)
COMMIT;
```

## 🟡 Middle Level

### Phantom Read vs. Non-Repeatable Read

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Characteristic               │ Non-Repeatable Read          │ Phantom Read                                     │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Target Mutation**          │ **Existing rows**            │ **New / Non-existent rows**                      │
  │ **Triggering Operation**     │ Concurrent `UPDATE`          │ Concurrent `INSERT` (or `DELETE`)                │
  │ **Query Focus**              │ Specific row (`WHERE id = 1`)│ Range / Set queries (`WHERE amount > 1000`)      │
  │ **System Impact**            │ Value corruption             │ Aggregate count & financial total desynchrony    │
  └──────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### Engine Handling Comparison on `Repeatable Read`

```
  ┌──────────────────────────────┬──────────────────────────┬──────────────────────────────────────────────────┐
  │ Database Engine              │ Phantoms on Repeatable R.│ Underlying Concurrency Defense                   │
  ├──────────────────────────────┼──────────────────────────┼──────────────────────────────────────────────────┤
  │ **PostgreSQL**               │ 🛡️ **Prevented**        │ Frozen MVCC snapshot excludes higher `t_xmin`    │
  │ **MySQL (InnoDB)**           │ 🛡️ **Prevented**        │ **Next-Key Locks (Record Lock + Gap Lock)**      │
  │ **Oracle**                   │ 🛡️ **Prevented**        │ Transaction-level MVCC snapshot isolation        │
  │ **Microsoft SQL Server**     │ ❌ **Allowed**           │ Allowed unless elevated to `SERIALIZABLE`        │
  └──────────────────────────────┴──────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Production Financial Discrepancy Hazard

```java
// 💥 HAZARDOUS FINANCIAL REPORT UNDER READ COMMITTED:
@Transactional // Default: Read Committed (New snapshot per query)
public DailyAuditReport generateDailyAudit(LocalDate today) {
    int totalCount = orderRepo.countByDate(today);        // Query 1: Snapshot sees 10,000 orders
    BigDecimal totalSum = orderRepo.sumAmountByDate(today); // Query 2: In-flight inserts commit! Sees 10,050 orders ($5.25M)
    List<Order> orderList = orderRepo.findAllByDate(today); // Query 3: Sees 10,050 orders

    // Disaster: totalCount (10,000) does NOT match orderList.size() (10,050) or totalSum!
    return new DailyAuditReport(totalCount, totalSum, orderList);
}
```

> [!TIP]
> **Production Fix:** Elevating this method to `@Transactional(isolation = Isolation.REPEATABLE_READ)` in PostgreSQL freezes the MVCC snapshot across all three queries, guaranteeing 100% mathematical consistency without table locking.

### Concurrency Mechanics: Gap Locks vs. Predicate Locks

```
  1. MySQL InnoDB Next-Key Locking:
     • Locks physical key gaps between index entries (e.g. gap between ID 10 and ID 20).
     • Blocks other threads from executing INSERT into the gap, eliminating phantoms 
       at the expense of potential range deadlocks.

  2. PostgreSQL SSI Predicate Locks (SIREAD):
     • Does NOT lock physical gaps.
     • Registers an in-memory lock on the query condition (WHERE status = 'PENDING').
     • If an incoming INSERT overlaps with an active predicate lock, it flags a 
       rw-antidependency in the SSI serialization graph and aborts on conflict.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A re-executed range query (`WHERE condition`) returns a different row set or count due to concurrent committed `INSERT`/`DELETE` operations.
- **Contrast:** Non-Repeatable Read = `UPDATE` on existing row; Phantom Read = `INSERT` of new matching rows.
- **PostgreSQL RR:** MVCC snapshot freezes visible transaction IDs (`t_xmin`), preventing phantoms in pure reads.
- **MySQL RR:** Uses **Next-Key Locks (Record + Gap Locks)** to physically block range insertions.
- **SQL Server RR:** Permits phantom reads; requires `SERIALIZABLE` Range-S locks to prevent them.
- **Report Hazards:** Multi-query reporting under Read Committed frequently yields desynchronized aggregate totals due to phantom inserts.

**Common Follow-up Questions:**
- *"Why does ANSI SQL allow Phantom Reads under Repeatable Read if MySQL and PostgreSQL prevent them?"* → The ANSI SQL-92 standard was formulated around locking protocols (where Repeatable Read only acquired row locks). Modern MVCC and Next-Key locking exceed the minimum baseline of the ANSI standard.
- *"How does a Gap Lock in MySQL prevent phantom reads?"* → It places a shared lock over the unallocated space between index entries, causing concurrent `INSERT` statements attempting to write into that key range to wait.
- *"What is the performance overhead of Predicate Locks in PostgreSQL Serializable mode?"* → Predicate locks (`SIREAD`) are stored purely in shared RAM (zero disk I/O); their overhead comes from graph traversal and serialization conflict aborts under heavy write contention.

**Red Flags (DO NOT Say):**
- ❌ *"A phantom read is when a query returns corrupted data that failed database validation."* (It is the arrival of valid, committed new rows in a search range).
- ❌ *"Using `SELECT ... FOR UPDATE` on a single ID prevents phantom reads across the whole table."* (`FOR UPDATE` on a specific key locks only that record; range queries require gap locks or table-level predicates).
- ❌ *"All database engines prevent phantom reads at the Repeatable Read isolation level."* (SQL Server permits phantom reads at Repeatable Read).
