# What is Rollback in Transactions?

---

## 🟢 Junior Level

A **Rollback** is an operation that aborts the current database transaction, completely undoing all uncommitted modifications and restoring the database to its exact state prior to transaction initiation:

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │ Core ACID Property Guaranteed                          │ **Atomicity (A)** (All-or-nothing execution)           │
  │ Spring Trigger Condition                               │ Unhandled **`RuntimeException`** or **`Error`**        │
  │ Checked Exception Default                              │ ⚠️ **COMMITS** (Unless `rollbackFor` is specified)     │
  │ Sequence Increments (`nextval`)                        │ ❌ **NEVER rolled back** (Leaves gaps by design)       │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

```java
@Service
public class AccountTransferService {

    @Transactional
    public void transferFunds(Long fromId, Long toId, BigDecimal amount) {
        accountRepo.debit(fromId, amount);   // Mutation 1
        accountRepo.credit(toId, amount);   // Mutation 2

        // If an unexpected RuntimeException occurs here:
        // Spring instructs the database to execute ROLLBACK, undoing Mutation 1 and 2!
    }
}
```

## 🟡 Middle Level

### Spring Rollback Mechanics: Declarative vs. Programmatic

```java
// Method 1: Declarative Rollback via Exception
@Transactional(rollbackFor = Exception.class)
public void executeSettlement(Order order) throws BusinessException {
    if (!order.isValid()) {
        throw new BusinessException("Invalid settlement order"); // Triggers rollback!
    }
    orderRepo.save(order);
}

// Method 2: Programmatic Rollback (Without throwing exceptions)
@Transactional
public void processWithManualRollback(Order order) {
    orderRepo.save(order);
    if (externalPaymentFailed(order)) {
        // Marks the transaction for rollback without raising an exception:
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    }
}
```

### The `UnexpectedRollbackException` Flow

```
  Caller ──► Outer Method (@Transactional REQUIRED) ──► Inner Method (@Transactional REQUIRED)
                                                                 │
                                                       Throws RuntimeException!
                                                                 │
                                                       TransactionAspect sets:
                                                       txStatus.setRollbackOnly(true)
                                                                 │
  Catches Exception in try-catch ◄───────────────────────────────┘
  Method returns normally...
  Attempts COMMIT on Outer exit ──► 💥 Spring discovers Rollback-Only flag!
                                    Executes physical ROLLBACK and throws:
                                    org.springframework.transaction.UnexpectedRollbackException
```

## 🔴 Senior Level

### Database Engine Internals: PostgreSQL vs. MySQL InnoDB Rollback

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Database Engine              │ Rollback Mechanism               │ Physical Execution                               │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **PostgreSQL**               │ **Logical Rollback**             │ Writes `XACT_ABORT` to WAL. Tuples are marked    │
  │                              │                                  │ aborted (`xmin = aborted_xid`); physical dead    │
  │                              │                                  │ tuple removal is deferred to **`VACUUM`**.       │
  │ **MySQL (InnoDB)**           │ **Physical Active Rollback**     │ Re-reads **Undo Log** segments in reverse order, │
  │                              │                                  │ physically restoring data pages in buffer pool.  │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Non-Transactional Side Effects

```java
// 💥 PRODUCTION HAZARD: Non-Transactional Side Effects
@Transactional
public void processOrder(Order order) {
    orderRepository.save(order);
    emailService.sendConfirmationEmail(order); // Network I/O!
    paymentGateway.chargeCard(order);          // 💥 If this fails:
    // Database rolls back, BUT the user ALREADY received the confirmation email!
}
```

> [!TIP]
> **Production Fix:** Use Spring's **`TransactionSynchronizationManager.registerSynchronization()`** to defer external side effects (emails, message queue events) until `afterCommit()` has successfully completed.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Reverts all modifications of an uncommitted transaction to enforce ACID Atomicity.
- **Spring Defaults:** Automatically rolls back on `RuntimeException` and `Error`; commits on checked `Exception`.
- **`rollback-only`:** Inner `REQUIRED` methods mark the shared transaction context as rollback-only; outer `try-catch` cannot prevent `UnexpectedRollbackException`.
- **Manual Rollback:** Use `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`.
- **PostgreSQL vs MySQL:** PostgreSQL uses logical aborts (vacuumed later); MySQL actively restores pages via Undo Logs.
- **Sequence Gaps:** Sequence increments (`nextval`) are monotonic and **never rolled back**.

**Common Follow-up Questions:**
- *"Why does Spring not roll back on checked exceptions by default?"* → Historically in EJB/Spring design, checked exceptions represent expected business flow conditions that the caller is expected to handle, whereas unchecked exceptions indicate unrecoverable programmatic faults.
- *"How do you safely dispatch a Kafka event only if a transaction commits?"* → Use `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` or `TransactionSynchronizationManager.registerSynchronization()`.
- *"Can you roll back to a specific checkpoint without aborting the entire transaction?"* → Yes, use `Propagation.NESTED` which creates a JDBC Savepoint.

**Red Flags (DO NOT Say):**
- ❌ *"Catching a RuntimeException from an inner REQUIRED method allows the outer method to commit."* (The transaction is already marked rollback-only; committing will throw `UnexpectedRollbackException`).
- ❌ *"Database sequences are rolled back to their previous value if a transaction aborts."* (Sequences are non-transactional and retain their incremented values).
- ❌ *"PostgreSQL actively rewrites data files back to their original bytes during a rollback."* (PostgreSQL writes an abort record to WAL and leaves tuple cleanup to `VACUUM`).
