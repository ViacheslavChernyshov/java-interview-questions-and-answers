# When to use synchronized collections?

---

## 🟢 Junior Level

**Synchronized Collections** are decorator wrappers created via `java.util.Collections` helper methods that serialize access by placing a **`synchronized` mutex on every single method call**.

```java
List<String> syncList = Collections.synchronizedList(new ArrayList<>());
Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
```

### The Core Problem

Synchronized collections use a **single, coarse-grained lock for the entire collection**:
- If Thread A is reading `get(0)`, Thread B **cannot read** `get(10)` and Thread C **cannot write** `add("X")`.
- All multi-threaded operations are serialized into a single line, causing severe CPU lock contention.

**Modern Production Recommendation:**
- For Maps $\to$ Use **`ConcurrentHashMap`** (Lock-free reads + per-bucket locks).
- For Read-Heavy Lists $\to$ Use **`CopyOnWriteArrayList`** (Lock-free snapshot reads).
- For FIFO Queues $\to$ Use **`ConcurrentLinkedQueue`** or **`ArrayBlockingQueue`**.

---

## 🟡 Middle Level

### The 2 Critical Traps of Synchronized Collections

#### 1. Compound Operations Are NOT Atomic (Check-Then-Act Race Condition)
Synchronizing individual methods does **not** make multi-step transactions atomic:

```java
// ❌ RACE CONDITION: Thread B can insert between contains() and add()!
if (!syncList.contains(targetUser)) {
    syncList.add(targetUser); 
}

// ✅ MANDATORY: Must explicitly synchronize on the wrapper:
synchronized (syncList) {
    if (!syncList.contains(targetUser)) {
        syncList.add(targetUser);
    }
}
```

#### 2. Iteration Requires Manual Synchronization
Calling `syncList.iterator()` or running an enhanced `for-each` loop is **not internally synchronized**:

```java
// ❌ FAILS: Throws ConcurrentModificationException if another thread modifies the list!
for (String item : syncList) {
    process(item);
}

// ✅ MANDATORY: Must manually lock on the collection during full iteration:
synchronized (syncList) {
    for (String item : syncList) {
        process(item);
    }
}
```

## 🔴 Senior Level

### Under the Hood: The Synchronized Decorator Pattern

Inside `java.util.Collections`, synchronized collections wrap the original backing collection and synchronize all delegated calls on a shared `mutex`:

```java
static class SynchronizedList<E> implements List<E> {
    final List<E> list;
    final Object mutex; // Coarse monitor lock

    public E get(int index) {
        synchronized (mutex) { return list.get(index); }
    }
    public boolean add(E e) {
        synchronized (mutex) { return list.add(e); }
    }
    public Iterator<E> iterator() {
        return list.iterator(); // Returns raw unsynchronized iterator!
    }
}
```

### Production Workload Selection Matrix

| Scenario / Requirement | Recommended Collection | Rationale |
|---|---|---|
| **High-Throughput Key-Value Storage** | **`ConcurrentHashMap`** | Lock-free reads, CAS writes, independent bucket locks |
| **Listener / Observer Registries** | **`CopyOnWriteArrayList`** | Zero-lock reads, snapshot iterations without CME |
| **Multi-Threaded Work Queues** | **`LinkedBlockingQueue`** | Dual-lock producer/consumer parallelism |
| **Atomic Multi-Statement Batch Operations** | **`Collections.synchronizedList`** | Allows locking the entire collection via `synchronized (list)` |
| **Legacy Codebases (pre-Java 5)** | **`Collections.synchronized*`** | Backward compatibility |

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Decorator wrapper synchronizing every method on a single shared `mutex` lock.
- **Lock Contention:** Serializes all operations (even simultaneous reads), crippling throughput under concurrency.
- **Compound Operations:** `if (!list.contains(x)) list.add(x)` is NOT atomic; requires manual `synchronized (list) { ... }`.
- **Iteration Invariant:** Iterators are fail-fast and unsynchronized; iterating without an external `synchronized` block throws `ConcurrentModificationException`.
- **Modern Replacements:** `ConcurrentHashMap`, `CopyOnWriteArrayList`, `ConcurrentLinkedQueue`.

**Common Follow-up Questions:**
- *"Why does iterating over `Collections.synchronizedList()` throw `ConcurrentModificationException`?"* → The `iterator()` method returns an unsynchronized iterator. If another thread invokes `add()` while an iteration is in progress, the backing array's `modCount` changes, triggering a CME on the next `it.next()` call.
- *"What happens if code mutates the underlying `ArrayList` directly instead of via the `synchronizedList` wrapper?"* → Thread safety is completely broken because raw direct calls bypass the wrapper's `synchronized` block.
- *"When are synchronized collections still justified in modern Java?"* → When you explicitly need to lock the entire collection to perform an atomic batch update across all elements without allowing any concurrent reads or writes.

**Red Flags (DO NOT Say):**
- ❌ *"Collections.synchronizedList makes all compound check-then-act operations thread-safe."* (Individual methods are synchronized, but multi-step sequences require external locking).
- ❌ *"Synchronized collections allow multiple threads to read simultaneously."* (They acquire a mutex on every read, serializing all readers).
- ❌ *"Iterating through a synchronizedList using a for-each loop is thread-safe by default."* (Requires wrapping the entire loop in a manual `synchronized (list)` block).
