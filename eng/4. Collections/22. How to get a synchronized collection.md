# How to get a synchronized collection?

---

## 🟢 Junior Level

You can obtain a synchronized collection using the static factory methods provided in **`java.util.Collections`**.

### The Primary Factory Methods

```java
// Synchronized List wrapper:
List<String> syncList = Collections.synchronizedList(new ArrayList<>());

// Synchronized Set wrapper:
Set<String> syncSet = Collections.synchronizedSet(new HashSet<>());

// Synchronized Map wrapper:
Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
```

> [!IMPORTANT]
> **Manual Synchronization During Iteration is MANDATORY:**
> ```java
> // ❌ DANGEROUS: Throws ConcurrentModificationException if another thread modifies the list!
> for (String item : syncList) {
>     process(item);
> }
> 
> // ✅ PROPER USAGE: Must manually wrap iteration in a synchronized block:
> synchronized (syncList) {
>     for (String item : syncList) {
>         process(item);
>     }
> }
> ```

## 🟡 Middle Level

### The Decorator Architecture

`Collections.synchronized*` methods implement the classic **Decorator Pattern**:
- They wrap the target backing collection and forward each method call inside a `synchronized (mutex)` block.

```java
// Inside JDK Collections.java:
static class SynchronizedCollection<E> implements Collection<E> {
    final Collection<E> c;  // Backing collection
    final Object mutex;     // Lock monitor (defaults to 'this')

    SynchronizedCollection(Collection<E> c) {
        this.c = Objects.requireNonNull(c);
        this.mutex = this;
    }

    public int size() {
        synchronized (mutex) { return c.size(); }
    }
    public boolean add(E e) {
        synchronized (mutex) { return c.add(e); }
    }
    public Iterator<E> iterator() {
        return c.iterator(); // Must be manually synchronized by caller!
    }
}
```

### Complete Factory Method Taxonomy

- **Collections:** `synchronizedCollection(Collection<T> c)`
- **Lists:** `synchronizedList(List<T> list)`
- **Sets:** `synchronizedSet(Set<T> s)`, `synchronizedSortedSet(SortedSet<T> s)`, `synchronizedNavigableSet(NavigableSet<T> s)`
- **Maps:** `synchronizedMap(Map<K, V> m)`, `synchronizedSortedMap(SortedMap<K, V> m)`, `synchronizedNavigableMap(NavigableMap<K, V> m)`

## 🔴 Senior Level

### The "Backing Collection Reference Leak" Bug

A frequent concurrency hazard occurs when developers retain a reference to the raw backing collection:

```java
List<String> rawList = new ArrayList<>();
List<String> threadSafeList = Collections.synchronizedList(rawList);

// ❌ THREAD-SAFETY DESTROYED:
// Thread A modifies through raw reference (bypasses synchronized wrapper lock!):
rawList.add("unprotected_item");

// Thread B reads through wrapper:
threadSafeList.get(0); // Race condition and memory visibility corruption!
```

> [!TIP]
> **Defensive Coding Rule:** Never retain a reference to the raw collection instance. Always construct the backing collection inline:
> ```java
> List<String> list = Collections.synchronizedList(new ArrayList<>());
> ```

### Comparison with Modern Concurrent Collections

```
  ┌────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────┐
  │              Collections.synchronized*                 │                java.util.concurrent (CHM / COWAL)      │
  ├────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────┤
  │ • Coarse single-mutex locking (`this`)                 │ • Lock-free CAS, volatile fields, partitioned locks    │
  │ • Readers block other readers                          │ • Unlimited concurrent lock-free readers               │
  │ • Iterators throw `ConcurrentModificationException`    │ • Iterators are Weakly Consistent or Snapshot-based    │
  │ • Best for: Legacy code or atomic multi-step locks     │ • Best for: High-throughput production applications   │
  └────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Factory Methods:** `Collections.synchronizedList()`, `synchronizedSet()`, `synchronizedMap()`, etc.
- **Pattern:** Decorator pattern wrapping all delegated methods in `synchronized (mutex)` blocks.
- **Iteration Invariant:** Iterators are **not synchronized**; developers must manually synchronize on the wrapper (`synchronized (syncCol) { ... }`).
- **Backing Collection Leak:** Do not retain or expose the raw backing collection; instantiate it inline inside the factory call.
- **Modern Alternatives:** Prefer `ConcurrentHashMap` and `CopyOnWriteArrayList` for scalable multi-threading.

**Common Follow-up Questions:**
- *"Why does `Collections.synchronizedList()` not synchronize its `iterator()` method?"* → Synchronizing `iterator()` would only protect the instantiation of the iterator, not the subsequent sequence of `hasNext()` and `next()` calls across the iteration loop.
- *"What is the `mutex` object in synchronized collections?"* → The monitor lock used by the decorator. By default, it points to `this` (the wrapper object itself).
- *"Can you pass a custom mutex object to `Collections.synchronizedList()`?"* → Package-private constructors allow custom mutexes, but the public API sets `mutex = this`.

**Red Flags (DO NOT Say):**
- ❌ *"Synchronized collections protect against ConcurrentModificationException during for-each loops automatically."* (You must manually wrap the loop in a `synchronized` block).
- ❌ *"Mutating the raw backing collection after creating a synchronized wrapper is thread-safe."* (Direct access bypasses the mutex and causes data corruption).
- ❌ *"Collections.synchronizedMap is just as fast as ConcurrentHashMap."* (SynchronizedMap serializes all reads and writes through a single mutex).
