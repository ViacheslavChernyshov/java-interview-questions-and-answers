# How does HashSet work internally?

---

## 🟢 Junior Level

**`HashSet`** is an adapter wrapper built directly on top of **`HashMap`**. Every element added to the set becomes a **Key** in an internal `HashMap`, while the **Value** is set to a constant dummy singleton object.

### The Internal JDK Implementation

```java
public class HashSet<E> extends AbstractSet<E> implements Set<E>, Serializable {
    // Backing HashMap instance:
    private transient HashMap<E, Object> map;

    // Shared dummy value associated with all keys in the backing map:
    private static final Object PRESENT = new Object();

    public HashSet() {
        map = new HashMap<>();
    }

    public boolean add(E e) {
        // Returns true if the key was newly inserted (put returned null)
        return map.put(e, PRESENT) == null;
    }

    public boolean contains(Object o) {
        return map.containsKey(o);
    }

    public boolean remove(Object o) {
        return map.remove(o) == PRESENT;
    }
}
```

## 🟡 Middle Level

### Bucket Allocation & Collision Resolution (Java 8+)

```
  1. Calculate Hash:   h = key.hashCode() ^ (h >>> 16)
  2. Compute Bucket:   index = (table.length - 1) & h
  3. Collision Strategy:
     ├── Bucket Count < 8: Singly-Linked List (O(n) search within bucket)
     └── Bucket Count >= 8 AND Total Capacity >= 64:
         Treeified into Red-Black Tree (TreeNode) -> O(log n) search!
```

- **`TREEIFY_THRESHOLD = 8`:** If collisions in a single bucket reach 8 entries and total table capacity $\ge 64$, the bucket converts to a Red-Black Tree.
- **`UNTREEIFY_THRESHOLD = 6`:** During resizing or deletions, if the tree shrinks to $\le 6$ nodes, it untreeifies back into a simple linked list.

### Memory Overhead Breakdown

Because `HashSet` wraps `HashMap`, each stored element is enclosed in a `HashMap.Node` object:

```
  HashMap.Node Heap Footprint (64-bit JVM with Compressed OOPs):
  ┌─────────────────────────────────────────┐
  │ Object Header                   12 Bytes│
  │ int hash                         4 Bytes│
  │ K key Reference                  4 Bytes│
  │ V value Reference (PRESENT)      4 Bytes│
  │ Node next Reference              4 Bytes│
  │ Padding (8-byte boundary)        4 Bytes│
  ├─────────────────────────────────────────┤
  │ Total Overhead per Element:    32 Bytes │
  └─────────────────────────────────────────┘
```
Storing 1,000,000 `Long` wrappers in a `HashSet<Long>` requires **$\sim 56\text{ MB}$ of RAM**, compared to just **$8\text{ MB}$** in a primitive `long[]` array.

## 🔴 Senior Level

### Custom Serialization Architecture

In `HashSet`, the backing map field is explicitly marked **`transient`**:
```java
private transient HashMap<E, Object> map;
```

> [!NOTE]
> **Why `map` is not serialized directly:**
> The distribution of keys across hash buckets depends on the JVM architecture, bitness, and identity hash generation. Deserializing a raw bucket array across different JVM implementations could cause corrupt lookups.
> Instead, `HashSet` overrides `writeObject()` and `readObject()` to write the raw stream of elements and capacity settings sequentially, rebuilding the `HashMap` cleanly during deserialization.

### High-Volume Primitive Optimization: Open Addressing

For high-throughput systems processing millions of primitive numbers (e.g. IDs or timestamps), standard `HashSet` introduces excessive GC pressure and memory waste.

**Recommended Solution:** Use an open-addressing primitive collection (e.g. `fastutil`'s `LongOpenHashSet` or `IntOpenHashSet`):
- Eliminates `HashMap.Node` wrappers and object headers.
- Stores primitive keys directly in a flat `long[]` table using linear/quadratic probing.
- **Memory footprint drops by $4-5\times$** with zero GC overhead.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Architecture:** `HashSet` is an adapter wrapping `HashMap<E, Object>`, mapping elements as keys and using `PRESENT = new Object()` as the dummy value.
- **Complexity:** $O(1)$ amortized for `add()`, `remove()`, and `contains()`.
- **Treeification:** In Java 8+, single-bucket collisions $\ge 8$ (with table capacity $\ge 64$) convert from linked lists to Red-Black Trees ($O(\log n)$).
- **Memory Footprint:** Heavy ($\sim 32\text{ bytes}$ per element for `HashMap.Node`).
- **Serialization:** Backing map is `transient`; elements are written sequentially via custom `writeObject()` / `readObject()`.
- **Mutable Elements:** Never mutate fields that participate in `hashCode()` after inserting an element into a `HashSet`.

**Common Follow-up Questions:**
- *"Why does `HashSet.add()` return a boolean?"* → Because `map.put(e, PRESENT)` returns `null` when a key is newly added (returning `true`), and returns the previous value (`PRESENT`) if the key already existed (returning `false`).
- *"Why is the default load factor 0.75?"* → It represents the mathematical sweet spot (Poisson distribution) balancing memory utilization against collision frequency.
- *"What happens if two distinct elements produce the exact same `hashCode()`?"* → They land in the same hash bucket; `HashSet` resolves the collision by chaining them in a linked list and checking `equals()` on lookup.

**Red Flags (DO NOT Say):**
- ❌ *"HashSet maintains its own independent hashing algorithm separate from HashMap."* (It delegates 100% of hashing logic to `HashMap`).
- ❌ *"HashSet is thread-safe for concurrent read/write operations."* (It is unsynchronized; use `ConcurrentHashMap.newKeySet()`).
- ❌ *"Treeification happens immediately whenever 8 collisions occur anywhere in the set."* (Treeification only occurs if the bucket has $\ge 8$ nodes AND total capacity $\ge 64$; otherwise, it simply resizes the table).
