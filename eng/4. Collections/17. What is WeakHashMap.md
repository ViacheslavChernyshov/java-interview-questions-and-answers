# What is WeakHashMap?

---

## 🟢 Junior Level

**`WeakHashMap`** is a specialized `Map` implementation where **Keys** are stored as **Weak References (`WeakReference`)**.

When a key is no longer strongly referenced anywhere else in the application, the Garbage Collector collects the key, and `WeakHashMap` **automatically evicts the corresponding entry**.

```java
WeakHashMap<Object, String> map = new WeakHashMap<>();

Object sessionKey = new Object();
map.put(sessionKey, "Active User Session");

// Dereference the strong pointer:
sessionKey = null;

// Suggest GC sweep (for illustration):
System.gc();

// Entry is automatically purged from the map:
System.out.println(map.size()); // 0
```

---

## 🟡 Middle Level

### Internal Architecture: `ReferenceQueue` & Lazy Eviction

```
  1. Internal Entry wraps Key: Entry<K, V> extends WeakReference<K>
  2. Strong Key reference lost -> GC sweeps Key on next Minor GC
  3. JVM enqueues dead Entry into WeakHashMap's internal ReferenceQueue
  4. On NEXT map operation (get, put, size):
     -> expungeStaleEntries() drains ReferenceQueue
     -> Unlinks and frees stale Entry nodes from the hash table!
```

```java
// Inside JDK WeakHashMap:
private void expungeStaleEntries() {
    for (Object x; (x = queue.poll()) != null; ) {
        // Unlinks dead key's bucket entry from internal table
    }
}
```

> [!IMPORTANT]
> **Eviction is Lazy:** Dead entries are not cleaned up in the background by a dedicated thread. They are purged **only when map methods (`get()`, `put()`, `size()`) are actively invoked**.

---

## 🔴 Senior Level

### The Two Critical Memory Leak Traps

#### 1. The Value-to-Key Reference Loop (Circular Leak)
If a stored `Value` holds a strong reference back to its `Key` (either directly or via an inner class / lambda closure), the entry will **never be garbage collected**:

```
  GC Root ──> WeakHashMap ──> Entry ──(Strong)──> Value
                                 │                  │
                             (Weak)             (Strong)
                                 │                  │
                                 └───> Key <────────┘
```
Because the `Key` is strongly reachable from the `Entry` via `Value`, the `WeakReference` is never cleared, creating a **permanent silent memory leak**.

#### 2. String Literals & Interned Keys
```java
// ❌ CRITICAL BUG: String literals reside in the JVM String Pool!
WeakHashMap<String, Metadata> map = new WeakHashMap<>();
map.put("constant_key", metadata); // "constant_key" is rooted by the ClassLoader forever!
```

### Why `WeakHashMap` is an Anti-Pattern for Caching

| Feature | `WeakHashMap` | Production Cache (e.g. Caffeine) |
|---|---|---|
| **Eviction Mechanism** | **Cleared on EVERY Minor GC** | LRU, W-TinyLFU, TTL, Size bounds |
| **Survival Duration** | **Milliseconds / Seconds** | Predictable based on SLA policies |
| **Thread Safety** | Non-thread-safe | Fully concurrent |
| **Best Application** | **Object Metadata Association** | Application Data & Computed Caches |

> [!WARNING]
> Because `WeakReference`s are cleared unconditionally during Minor GCs in the Young Generation, using `WeakHashMap` as a cache results in **violent cache thrashing** and severe CPU overhead from repeated re-computations.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Hash table where keys are wrapped in `WeakReference`. When a key loses strong reachability, its entry is automatically discarded.
- **Lazy Eviction:** `expungeStaleEntries()` cleans dead entries during active method invocations (`get()`, `put()`, `size()`).
- **Circular Leak Hazard:** If `Value` holds a strong reference back to `Key`, the key is never collected $\implies$ memory leak.
- **String Literals:** String literals and boxed primitives are rooted permanently in JVM pools and will never be collected.
- **Not a Cache:** Weak references are wiped on every Minor GC; use **Caffeine** or `SoftReference` for caching.

**Common Follow-up Questions:**
- *"What is the difference between `WeakHashMap` and `SoftReference` caches?"* → `WeakReference` objects are collected on *every* GC pass regardless of heap pressure; `SoftReference` objects survive until the JVM approaches an `OutOfMemoryError`.
- *"Why does `WeakHashMap.size()` return 0 only after some operations?"* → `WeakHashMap` cleans up dead entries lazily; calling `size()` triggers `expungeStaleEntries()`, clearing the pending queue before returning the count.
- *"How should you store metadata for an object without modifying its class?"* → Store the metadata in a `WeakHashMap<TargetObject, Metadata>`. When the target object is dereferenced by the business logic, its metadata is cleanly evicted.

**Red Flags (DO NOT Say):**
- ❌ *"WeakHashMap is the best way to implement a fast in-memory cache."* (It is cleared too aggressively on every Minor GC).
- ❌ *"WeakHashMap cleans up dead entries in a background daemon thread."* (It cleans up lazily inside method calls).
- ❌ *"WeakHashMap removes entries based on whether the Value is weakly referenced."* (Only the **Key** is weakly referenced; values are strongly held).
