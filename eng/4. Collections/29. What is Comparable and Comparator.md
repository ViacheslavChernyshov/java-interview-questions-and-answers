# What is Comparable and Comparator?

---

## 🟢 Junior Level

**`Comparable`** and **`Comparator`** are the two standard Java interfaces used to define sorting order for objects.

| Dimension | `Comparable<T>` | `Comparator<T>` |
|---|---|---|
| **Package** | `java.lang` | `java.util` |
| **Method** | `int compareTo(T other)` | `int compare(T o1, T o2)` |
| **Concept** | **Internal "Natural Ordering"** (Implemented by the class itself) | **External "Custom Strategy"** (Separate standalone comparator) |
| **Number of Strategies** | Exactly **one** natural order per class | **Infinite** customizable sorting strategies |
| **Usage** | `Collections.sort(list)` / `list.sort(null)` | `list.sort(comparator)` |

```java
// 1. Comparable: Class defines its own natural sort order
record User(int id, String name, int age) implements Comparable<User> {
    @Override
    public int compareTo(User other) {
        return Integer.compare(this.id, other.id); // Natural order by ID
    }
}

// 2. Comparator: External customized sorting strategies
Comparator<User> byName = Comparator.comparing(User::name);
Comparator<User> byAgeDesc = Comparator.comparingInt(User::age).reversed();

List<User> users = new ArrayList<>(...);
users.sort(byName);    // Sorted alphabetically
users.sort(byAgeDesc); // Sorted by age descending
```

## 🟡 Middle Level

### Fluent Modern Comparator Combinators (Java 8+)

Java 8 transformed `Comparator` into a powerful functional interface with declarative builder methods:

```java
Comparator<User> complexComparator = Comparator
    .comparing(User::name, String.CASE_INSENSITIVE_ORDER)
    .thenComparingInt(User::age)
    .thenComparing(User::id, Comparator.reverseOrder());

// Safe Null Handling:
Comparator<User> nullSafeComparator = Comparator
    .comparing(User::name, Comparator.nullsLast(String::compareTo));
```

### The Integer Subtraction Overflow Vulnerability

> [!CAUTION]
> Never implement comparison logic using raw integer subtraction:

```java
// ❌ CRITICAL BUG: Integer Overflow!
Comparator<User> bad = (u1, u2) -> u1.id() - u2.id();

// If u1.id = -2_000_000_000 and u2.id = 2_000_000_000:
// -2_000_000_000 - 2_000_000_000 = -4_000_000_000 (Wraps around to +294,967,296!)
// Result: Comparator reports u1 > u2, breaking sorting completely!

// ✅ ALWAYS USE STATIC WRAPPER COMPARATORS:
Comparator<User> good = (u1, u2) -> Integer.compare(u1.id(), u2.id());
```

## 🔴 Senior Level

### The 3 Mathematical Invariants & Timsort Contract

The Java sorting engine (`java.util.TimSort` for reference types) relies on strict mathematical ordering properties:

1. **Antisymmetry:** $\text{sgn}(\text{compare}(x, y)) == -\text{sgn}(\text{compare}(y, x))$
2. **Transitivity:** $\text{compare}(x, y) > 0 \land \text{compare}(y, z) > 0 \implies \text{compare}(x, z) > 0$
3. **Equivalence Congruence:** $\text{compare}(x, y) == 0 \implies (\text{compare}(x, z) == \text{compare}(y, z))$

> [!WARNING]
> If a custom comparator violates transitivity (e.g. returning non-deterministic random values or inconsistent fallback paths), `TimSort` will throw a runtime **`IllegalArgumentException: Comparison method violates its general contract!`**.

### Consistency with `equals()` for `TreeSet` & `TreeMap`

While not strictly enforced by the compiler, `compareTo()` should be **consistent with `equals()`**:
$$\forall x, y: (x.\text{compareTo}(y) == 0) \iff x.\text{equals}(y)$$

Because `TreeSet` and `TreeMap` use `compareTo() == 0` instead of `equals()` to identify duplicate entries, inconsistent implementations will silently drop distinct elements:
- *Example:* If two `BigDecimal` objects `new BigDecimal("2.0")` and `new BigDecimal("2.00")` are added to a `HashSet`, both are stored (`equals` is false due to scale differences). In a `TreeSet`, the second is discarded (`compareTo` returns 0).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **`Comparable`:** Natural ordering within the target class (`compareTo`); single default sorting strategy.
- **`Comparator`:** External standalone sorting strategy (`compare`); allows multiple independent sorting rules.
- **Fluent API:** `Comparator.comparing()`, `thenComparing()`, `reversed()`, `nullsFirst()`, `nullsLast()`.
- **Never Subtract Integers:** `a - b` overflows around `Integer.MIN_VALUE` / `Integer.MAX_VALUE`; always use `Integer.compare(a, b)` or `Long.compare(a, b)`.
- **Timsort Contract:** Comparators must satisfy antisymmetry and transitivity; violations throw `IllegalArgumentException`.
- **`TreeSet` / `TreeMap` Equality:** Determined by `compareTo() == 0`, **not `equals()`**.

**Common Follow-up Questions:**
- *"Why does `Collections.sort()` sometimes throw `IllegalArgumentException` in production?"* → The supplied `Comparator` violates transitivity or antisymmetry, breaking `TimSort`'s internal binary merge assumptions.
- *"How do `Comparable` and `Comparator` differ when used with `TreeSet`?"* → If no `Comparator` is passed to the `TreeSet` constructor, elements must implement `Comparable`; otherwise, `TreeSet` throws a `ClassCastException`.
- *"Why does `BigDecimal.compareTo()` behave differently from `BigDecimal.equals()`?"* → `equals()` requires both value and decimal scale to match (`2.0` != `2.00`), while `compareTo()` ignores scale (`2.0` == `2.00`).

**Red Flags (DO NOT Say):**
- ❌ *"Comparable allows defining multiple sorting orders for a class."* (`Comparable` defines only one natural order; `Comparator` is used for multiple orders).
- ❌ *"Subtracting integers `(o1, o2) -> o1.id - o2.id` is safe as long as IDs are positive."* (Negative numbers or boundary overflows corrupt the comparison; use `Integer.compare()`).
- ❌ *"TreeSet uses equals() to check whether an element is a duplicate."* (`TreeSet` uses `compareTo()` or `Comparator.compare()`).
