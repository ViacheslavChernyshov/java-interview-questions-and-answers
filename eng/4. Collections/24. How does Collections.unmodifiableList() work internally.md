# How does Collections.unmodifiableList() work internally?

---

## 🟢 Junior Level

**`Collections.unmodifiableList()`** implements the **Decorator (Wrapper) Pattern**:
- It creates a thin wrapper object that holds a direct reference to the original backing list.
- **Read methods** (`get()`, `size()`, `contains()`) delegate directly to the underlying list.
- **Mutator methods** (`add()`, `set()`, `remove()`, `clear()`) throw **`UnsupportedOperationException`** immediately.

```java
List<String> list = new ArrayList<>(List.of("A", "B"));
List<String> unmod = Collections.unmodifiableList(list);

unmod.get(0);   // ✅ Direct delegation -> Returns "A"
unmod.add("X"); // ❌ Throws UnsupportedOperationException!
```

## 🟡 Middle Level

### JDK Source Code Architecture

```java
// Inside java.util.Collections:

public static <T> List<T> unmodifiableList(List<? extends T> list) {
    return (list instanceof RandomAccess ?
            new UnmodifiableRandomAccessList<>(list) :
            new UnmodifiableList<>(list));
}

static class UnmodifiableList<E> extends UnmodifiableCollection<E> implements List<E> {
    final List<? extends E> list; // Direct reference to backing list

    UnmodifiableList(List<? extends E> list) {
        super(list);
        this.list = list;
    }

    // 1. All Mutators Throw UnsupportedOperationException:
    public E set(int index, E element) { throw new UnsupportedOperationException(); }
    public void add(int index, E element) { throw new UnsupportedOperationException(); }
    public E remove(int index) { throw new UnsupportedOperationException(); }
    public void replaceAll(UnaryOperator<E> operator) { throw new UnsupportedOperationException(); }
    public void sort(Comparator<? super E> c) { throw new UnsupportedOperationException(); }

    // 2. Read Methods Delegate Directly to Backing List:
    public E get(int index) { return list.get(index); }
    public int indexOf(Object o) { return list.indexOf(o); }
    public int lastIndexOf(Object o) { return list.lastIndexOf(o); }

    // 3. SubList Returns Nested Unmodifiable View:
    public List<E> subList(int fromIndex, int toIndex) {
        return new UnmodifiableList<>(list.subList(fromIndex, toIndex));
    }
}
```

### Iterator Protection: `UnmodifiableListIterator`

Calling `listIterator()` does not expose raw mutable list iterators:
- It returns an **`UnmodifiableListIterator`** wrapper that intercepts and blocks `set()`, `add()`, and `remove()`:

```java
ListIterator<String> it = unmod.listIterator();
it.next();   // ✅ OK
it.set("Z"); // ❌ Throws UnsupportedOperationException!
```

## 🔴 Senior Level

### `UnmodifiableRandomAccessList` Specialization

```java
static class UnmodifiableRandomAccessList<E> extends UnmodifiableList<E> implements RandomAccess {
    UnmodifiableRandomAccessList(List<? extends E> list) {
        super(list);
    }
    @Override
    public List<E> subList(int fromIndex, int toIndex) {
        return new UnmodifiableRandomAccessList<>(list.subList(fromIndex, toIndex));
    }
}
```
**Algorithmic Value:** If the backing list implements `RandomAccess` (e.g. `ArrayList`), the JDK ensures the unmodifiable wrapper preserves the marker interface, enabling downstream algorithms (such as `Collections.binarySearch()`) to select $O(1)$ index looping rather than $O(n)$ iterator traversal.

### JIT Inlining & Performance Overhead

Because `UnmodifiableList.get(index)` consists of a single method delegation line (`return list.get(index)`), the **HotSpot C2 JIT Compiler** trivially **inlines the call**:
- The runtime overhead of the unmodifiable wrapper is **effectively 0 nanoseconds** in compiled production code.

### The Reflection Bypass Vulnerability

Because `UnmodifiableList` is a wrapper holding a private reference field `list`, unauthorized code with reflection privileges can bypass the protection:

```java
List<String> raw = new ArrayList<>(List.of("Secret"));
List<String> unmod = Collections.unmodifiableList(raw);

// ⚠️ Reflection Bypass:
Field listField = unmod.getClass().getDeclaredField("list");
listField.setAccessible(true);
List<String> leaked = (List<String>) listField.get(unmod);
leaked.add("Corrupted"); // Bypasses wrapper!

// ✅ Complete Immunity (Java 10+):
List<String> immune = List.copyOf(raw); // No backing reference exists to leak!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Design Pattern:** Decorator Pattern; holds reference to backing list and overrides mutators to throw `UnsupportedOperationException`.
- **Performance:** $O(1)$ wrapper allocation; JIT compiler inlines delegation methods to achieve near-zero runtime overhead.
- **`RandomAccess` Support:** Returns `UnmodifiableRandomAccessList` if source list implements `RandomAccess`.
- **Iterators:** Wraps `Iterator` and `ListIterator` into read-only proxies blocking `remove()`, `set()`, `add()`.
- **View Semantics:** Changes to the original backing list are immediately reflected in the wrapper.
- **Java 10+ Alternative:** Use `List.copyOf()` when you require an independent defensive snapshot decoupled from the source.

**Common Follow-up Questions:**
- *"What is the memory overhead of `Collections.unmodifiableList()`?"* → It allocates a single wrapper object containing one reference field (24 bytes on 64-bit JVM with Compressed OOPs), regardless of list size.
- *"What does `subList()` return on an unmodifiable list?"* → It returns a new unmodifiable wrapper enclosing the underlying list's subList view.
- *"Why does `Collections.unmodifiableList()` not defend against concurrent modification exceptions?"* → Because it is an unsynchronized view. If another thread mutates the backing list while an iteration is active on the unmodifiable view, the iterator's `modCount` check will fail and throw `ConcurrentModificationException`.

**Red Flags (DO NOT Say):**
- ❌ *"Collections.unmodifiableList makes a defensive copy of all elements."* (It only allocates a 24-byte wrapper holding a reference to the original list).
- ❌ *"UnmodifiableList is thread-safe for concurrent read and write operations."* (It provides no synchronization locks).
- ❌ *"Iterating through an unmodifiableList allows you to safely call `iterator.remove()`."* (`iterator.remove()` throws `UnsupportedOperationException`).
