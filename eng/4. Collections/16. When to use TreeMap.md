# When to use TreeMap?

---

## 🟢 Junior Level

**`TreeMap`** is a Red-Black Tree implementation of `NavigableMap` that maintains its keys in **strictly sorted order**.

### When to Choose `TreeMap`

| Choose `TreeMap` When: | Choose `HashMap` When: | Choose `LinkedHashMap` When: |
|---|---|---|
| • You need continuous sorting by key | • You need highest-speed lookups | • You need to preserve **insertion order** |
| • You need **nearest-neighbor queries** (`floorKey`, `ceilingKey`) | • Key ordering is irrelevant | • You need an **LRU Cache** |
| • You need **range-bounded submaps** (`subMap`, `headMap`, `tailMap`) | • Performance must be strictly **$O(1)$** | • Performance must be **$O(1)$** |

```java
TreeMap<Integer, String> map = new TreeMap<>();
map.put(100, "Platinum");
map.put(20, "Bronze");
map.put(50, "Silver");

System.out.println(map); // {20=Bronze, 50=Silver, 100=Platinum} (Sorted!)

// Nearest-neighbor lookups:
Integer tier = map.floorKey(45); // Returns 20 (Highest key <= 45)
```

## 🟡 Middle Level

### Production Use Cases for `TreeMap`

#### 1. Tiered Tax / Billing Calculation (Nearest Bound Matching)
```java
NavigableMap<Double, Double> taxBrackets = new TreeMap<>();
taxBrackets.put(0.0, 0.00);      // 0% for income starting at 0
taxBrackets.put(15_000.0, 0.10); // 10% for income starting at 15k
taxBrackets.put(50_000.0, 0.22); // 22% for income starting at 50k
taxBrackets.put(100_000.0, 0.32); // 32% for income starting at 100k

// Retrieve the applicable marginal tax rate for a $65,000 salary:
Double marginalRate = taxBrackets.floorEntry(65_000.0).getValue(); // Returns 0.22
```

#### 2. Time-Series Windowing & Metric Aggregation
```java
NavigableMap<Instant, MetricPoint> metrics = new TreeMap<>();

// Extract all telemetry events recorded in the last 15 minutes:
Instant fifteenMinutesAgo = Instant.now().minus(15, ChronoUnit.MINUTES);
SortedMap<Instant, MetricPoint> recentWindow = metrics.tailMap(fifteenMinutesAgo);
```

#### 3. Key Prefix Slicing
```java
// Extract all keys starting with prefix "user:session:"
NavigableMap<String, Session> store = new TreeMap<>();
SortedMap<String, Session> sessionKeys = store.subMap("user:session:", "user:session{");
```

## 🔴 Senior Level

### Performance Trade-offs & The "Sort-on-Read" Pattern

```
  Algorithmic Complexity Comparison:
  ┌────────────────────────────────────────────────────────┬────────────────────────┐
  │ Map Class                                              │ Cost per Mutation/Read │
  ├────────────────────────────────────────────────────────┼────────────────────────┤
  │ **`HashMap`**                                          │ **$O(1)$ Amortized**   │
  │ **`TreeMap`**                                          │ **$O(\log n)$**        │
  └────────────────────────────────────────────────────────┴────────────────────────┘
```

> [!WARNING]
> In high-throughput write workloads ($>100{,}000\text{ writes/sec}$), `TreeMap`'s Red-Black tree rebalancing and pointer chasing can run **$20-50\times$ slower** than `HashMap`.

**The "Sort-on-Read" Optimization:**
If sorting is only needed occasionally (e.g. rendering a periodic dashboard report), **do not store data in a `TreeMap`**. Store data in a fast `HashMap` ($O(1)$ writes) and sort the key set only when reading:

```java
// ✅ FAST WRITES + ON-DEMAND SORT:
Map<String, Data> fastStore = new HashMap<>(); // O(1) writes!

public List<Data> getSortedReport() {
    List<String> sortedKeys = new ArrayList<>(fastStore.keySet());
    Collections.sort(sortedKeys); // O(k log k) executed only during report generation
    return sortedKeys.stream().map(fastStore::get).toList();
}
```

### Thread-Safe Sorted Alternative: `ConcurrentSkipListMap`

`TreeMap` is **not thread-safe**. When concurrent multi-threaded sorted access is required, use **`ConcurrentSkipListMap`**:
- Backed by a concurrent **Skip List** with multi-level express pointer lanes.
- Delivers $O(\log n)$ performance with **lock-free CAS operations**, eliminating coarse synchronization bottlenecks.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **When to Use:** When you require sorted iteration, range windowing (`subMap`), or closest-match lookups (`floorKey`, `ceilingKey`).
- **Complexity:** $O(\log n)$ for `get()`, `put()`, `remove()`.
- **`null` Restriction:** Throws `NullPointerException` (keys must be comparable).
- **Sort-on-Read Alternative:** If sorted output is rarely requested, use `HashMap` ($O(1)$ writes) and sort the keys on-demand.
- **Thread-Safe Alternative:** Use `ConcurrentSkipListMap` for concurrent sorted maps.

**Common Follow-up Questions:**
- *"Why is `TreeMap.subMap()` faster than filtering a `HashMap` using streams?"* → `TreeMap.subMap()` is an $O(1)$ metadata slice that bounds tree pointer traversal, whereas filtering a `HashMap` requires scanning every entry in $O(n)$ time.
- *"How does `floorKey()` differ from `lowerKey()`?"* → `floorKey(k)` returns the greatest key $\le k$; `lowerKey(k)` returns the greatest key strictly $< k$.
- *"Why does `TreeMap` not implement `ConcurrentMap`?"* → `TreeMap` is non-concurrent; use `ConcurrentSkipListMap` instead.

**Red Flags (DO NOT Say):**
- ❌ *"TreeMap is the default choice for implementing key-value maps."* (`HashMap` is the default; `TreeMap` is specialized for sorted ranges).
- ❌ *"TreeMap preserves the order in which keys were added."* (`LinkedHashMap` preserves insertion order; `TreeMap` sorts by key value).
- ❌ *"TreeMap is thread-safe."* (`TreeMap` is unsynchronized).
