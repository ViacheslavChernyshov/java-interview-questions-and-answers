# What is ConcurrentHashMap?

---

## 🟢 Junior Level

**`ConcurrentHashMap` (CHM)** is a high-throughput, thread-safe implementation of `ConcurrentMap` designed for concurrent multi-threaded applications.

### Primary Advantage over `Collections.synchronizedMap`

| Feature | `Collections.synchronizedMap(new HashMap<>())` | `ConcurrentHashMap` |
|---|---|---|
| **Locking Granularity** | **Single global lock on the entire Map** | **Fine-grained per-bucket locking & CAS** |
| **Concurrent Reads** | Serialized (Threads block each other) | **100% Lock-Free** (Unlimited parallel readers) |
| **Concurrent Writes** | Serialized (One write at a time) | **High Concurrency** (Writes to different buckets run in parallel) |
| **`null` Keys / Values** | Allowed | **Prohibited (Throws NPE)** |

```java
Map<String, Integer> cache = new ConcurrentHashMap<>();

// Safe for simultaneous multi-threaded reads and writes:
cache.put("user_101", 42);
Integer val = cache.get("user_101"); // Lock-free read!
```

## 🟡 Middle Level

### Architectural Evolution: Java 7 vs. Java 8+

```
  Java 7: Segment Locking (16 ReentrantLocks)
  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐
  │ Segment 0 │ │ Segment 1 │ │ Segment 2 │ │ Segment 3 │ ... (Max concurrency capped at 16)
  └───────────┘ └───────────┘ └───────────┘ └───────────┘

  Java 8+: Node-Level Locking + CAS
  [Bucket 0] -> Empty? Use atomic CAS (Zero Locks!)
  [Bucket 1] -> Collision? Synchronize strictly on this single bucket HEAD node!
  [Bucket 2] -> Concurrent read? Lock-free volatile read!
```

- **Java 7:** Partitioned the table into 16 discrete `Segment` objects (each extending `ReentrantLock`).
- **Java 8+ Modern Standard:** Eliminated `Segment` overhead. Uses **CAS on empty buckets** and **`synchronized` strictly on the collision head node**, providing virtually unlimited concurrent write channels.

### Atomic Compound Operations

`ConcurrentHashMap` provides atomic methods to prevent check-then-act race conditions:

```java
// 1. Compute and insert atomically:
cache.computeIfAbsent("metrics", k -> new ArrayList<>()).add("event_1");

// 2. Atomic counter increment:
cache.merge("requestCount", 1, Integer::sum);

// 3. Conditional put:
cache.putIfAbsent("lock_token", "acquired");
```

## 🔴 Senior Level

### Lock-Free Read Architecture

In `ConcurrentHashMap`, the `get()` method acquires **zero locks**:
- The internal `Node<K, V>[] table` reference is `volatile`.
- `Node.val` and `Node.next` are declared **`volatile`**.
- Under the Java Memory Model (JMM), reading a volatile reference establishes a formal **Happens-Before relationship**, guaranteeing that reader threads immediately observe the latest writes without thread synchronization overhead.

### Distributed Multi-Threaded Resizing (`ForwardingNode`)

When resizing from $N$ to $2N$ buckets:
1. `ConcurrentHashMap` places a special **`ForwardingNode`** with hash `-1` (`MOVED`) into migrated buckets.
2. If another thread attempts to write to a migrating bucket, it detects the `ForwardingNode` and invokes **`helpTransfer()`**.
3. **Result:** Instead of blocking, writing threads cooperate in parallel to transfer chunks of the table, completing large resizes in milliseconds.

### Scalable Size Tracking: `CounterCell` Array

Instead of bottlenecking on a single shared volatile counter, `ConcurrentHashMap` uses a **`CounterCell[]` striped array** (identical to `LongAdder`):
- Concurrent threads increment independent counter cells based on thread probe hashes.
- `mappingCount()` computes the sum across all cells, supporting maps with over $2^{31}$ entries:

```java
// ✅ Recommended for large concurrent maps:
long totalEntries = map.mappingCount(); // Returns long (unlike map.size() which caps at Integer.MAX_VALUE)
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Design:** High-throughput thread-safe map using CAS for empty buckets and fine-grained `synchronized` locks on bucket heads.
- **Lock-Free Reads:** `get()` uses `volatile` fields without acquiring any locks.
- **Java 8+ Evolution:** Replaced coarse `Segment` locks with per-node synchronization and TreeBins.
- **`null` Prohibition:** Throws `NullPointerException` on `null` keys or values to eliminate concurrency ambiguity.
- **Iterators:** **Weakly Consistent** (reflects state at iterator creation, tolerates concurrent updates, never throws `ConcurrentModificationException`).
- **Parallel Resizing:** Employs `ForwardingNode` allowing writer threads to help transfer buckets in parallel.

**Common Follow-up Questions:**
- *"Why does `ConcurrentHashMap` forbid `null` values?"* → If `map.get(k)` returned `null`, a multi-threaded application could not distinguish between "the key does not exist" and "the key is mapped to `null`". Calling `containsKey(k)` to check would introduce an un-synchronized check-then-act race condition.
- *"What is the difference between `map.size()` and `map.mappingCount()`?"* → `size()` returns a 32-bit `int` (clamped to `Integer.MAX_VALUE`), whereas `mappingCount()` returns a 64-bit `long` reflecting distributed `CounterCell` sums.
- *"What risk exists when running heavy logic inside `computeIfAbsent()`?"* → The computation runs while holding the bucket head lock; long-running operations or network I/O will block all other threads accessing that bucket. Recursive map calls will trigger a **deadlock**.

**Red Flags (DO NOT Say):**
- ❌ *"ConcurrentHashMap locks the entire map during writes."* (It only synchronizes on the specific bucket being updated).
- ❌ *"ConcurrentHashMap still uses 16 Segments in modern Java."* (Segment locking was deprecated and replaced in Java 8).
- ❌ *"Iterating over ConcurrentHashMap requires a synchronized block to prevent ConcurrentModificationException."* (CHM iterators are weakly consistent and never throw CME).
