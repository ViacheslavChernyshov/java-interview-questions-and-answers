# What is Retry Pattern and How to Use It Correctly?

---

## 🟢 Junior Level

The **Retry Pattern** enables an application to automatically re-attempt a failed remote network call, assuming that the failure was caused by a **temporary, transient glitch** that will resolve itself in a fraction of a second:

```
  Transient Glitch vs. Permanent Error:
  • Transient Blip (RETRY!): Pod is rolling over during a zero-downtime deployment; connection dropped for 200ms.
  • Permanent Error (DO NOT RETRY!): You sent a bad request with invalid JSON (`400 Bad Request`) or a wrong 
    password (`401 Unauthorized`). Retrying 10 times will NEVER fix a bad password!
```

```
  1. Call Attempt #1 ──► 💥 Network Timeout!
  2. Wait 500ms...
  3. Call Attempt #2 ──► 💥 Connection Reset!
  4. Wait 1000ms...
  5. Call Attempt #3 ──► 🟢 HTTP 200 OK (Success!)
```

## 🟡 Middle Level

### The 4 Golden Rules of Production Retries

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Rule                            │ Why It Is Critical                                                              │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Retry Transient ONLY**     │ Retry: `503 Service Unavailable`, `504 Gateway Timeout`, `SocketTimeout`.       │
  │                                 │ ❌ NEVER RETRY: `400 Bad Request`, `401 Unauthorized`, `404 Not Found`.         │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. Mandatory Idempotency**    │ Retrying a non-idempotent `POST /charge` can charge the customer's card 3 times!│
  │                                 │ Must supply a unique **`Idempotency-Key`** header!                              │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. Exponential Backoff**      │ Double the wait time between attempts ($500\text{ms} \to 1\text{s} \to 2\text{s}$)│
  │                                 │ to allow struggling backends time to recover.                                   │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **4. Add Random Jitter**        │ Adds randomized noise to backoff delays to prevent synchronized **Retry Storms**│
  │                                 │ (Thundering Herd problem).                                                      │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Production Implementation with Resilience4j

```java
@Service
@Slf4j
public class InventoryServiceClient {

    @Retry(name = "inventoryService", fallbackMethod = "inventoryFallback")
    public InventoryStatusDTO checkStock(Long productId) {
        // Remote HTTP REST call:
        return restTemplate.getForObject("http://inventory-svc/api/v1/stock/" + productId, InventoryStatusDTO.class);
    }

    // Fallback invoked when all 3 retry attempts are exhausted:
    public InventoryStatusDTO inventoryFallback(Long productId, Throwable ex) {
        log.error("Inventory Service unreachable after retries. Returning unknown status. Error: {}", ex.getMessage());
        return new InventoryStatusDTO(productId, "UNKNOWN_OFFLINE");
    }
}
```

```yaml
# application.yml: Resilience4j Retry Configuration
resilience4j.retry:
  instances:
    inventoryService:
      max-attempts: 3
      wait-duration: 500ms
      enable-exponential-backoff: true
      exponential-backoff-multiplier: 2
      enable-randomized-wait: true
      randomized-wait-factor: 0.5      # Jitter: Delays vary between 50% and 150% of base
      retry-exceptions:
        - java.io.IOException
        - java.net.SocketTimeoutException
        - org.springframework.web.client.HttpServerErrorException.ServiceUnavailable # 503
      ignore-exceptions:
        - org.springframework.web.client.HttpClientErrorException.BadRequest # 400
        - org.springframework.web.client.HttpClientErrorException.NotFound   # 404
```

## 🔴 Senior Level

### The "Retry Storm" (Thundering Herd) Disaster & Jitter Fix

When a downstream database slows down, thousands of client requests fail simultaneously. Without **Jitter (randomization)**, all 10,000 clients retry at the exact same synchronized millisecond, creating a destructive wave:

```
  Synchronized Retries (Destructive Wave):
  Second 0.0:  10,000 requests fail!
  Second 1.0:  💥 10,000 retries hit the server at the exact same instant $\to$ Downstream CRASHES!
  Second 3.0:  💥 10,000 retries hit again at the exact same instant!
```

#### The Jitter Mathematical Solution:
$$\text{Delay} = \text{random_between}(0, \text{base_delay} \times 2^{\text{attempt}})$$
Instead of all requests hitting at second 1.0, Jitter disperses the 10,000 retries evenly across a wide time window (between 0.5s and 2.5s), smoothing out traffic spikes and allowing the server to drain its queues.

### Retrying Non-Idempotent Operations with Idempotency Keys

```java
public PaymentResponse chargeCreditCard(PaymentRequest request) {
    String idempotencyKey = UUID.randomUUID().toString(); // Consistent across retries!

    HttpHeaders headers = new HttpHeaders();
    headers.set("Idempotency-Key", idempotencyKey);
    HttpEntity<PaymentRequest> entity = new HttpEntity<>(request, headers);

    // If attempt #1 times out over the wire, attempt #2 sends the SAME idempotency key.
    // The payment gateway detects the duplicate key and returns the original transaction result!
    return restTemplate.postForObject("/api/v1/charge", entity, PaymentResponse.class);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Automatically re-executing an operation that failed due to a transient, temporary glitch.
- **Retry Scope:** Retry **only transient 5xx/network errors**; never retry deterministic 4xx client errors.
- **Idempotency Requirement:** Never retry state mutations (`POST`) without an **Idempotency Key**.
- **Backoff & Jitter:** Always combine Exponential Backoff with Random Jitter to prevent **Retry Storms**.
- **Cap Retries:** Limit attempts to 3 (maximum 5) before failing fast or executing a Fallback.

**Common Follow-up Questions:**
- *"What is the difference between `@Retryable` (Spring Retry) and Resilience4j `@Retry`?"* → Spring Retry uses standard Spring AOP proxies and blocks the thread; Resilience4j is modular, functional, integrates with Micrometer metrics, and supports non-blocking reactive / virtual thread execution.
- *"How should you handle an HTTP 429 Too Many Requests response during retries?"* → Inspect the `Retry-After: 30` HTTP response header and pause execution for the duration specified by the server before making the next attempt.
- *"Should you put Circuit Breaker inside Retry, or Retry inside Circuit Breaker?"* → Put **Retry inside Circuit Breaker**; if Retry wraps Circuit Breaker, 1 failed user action retrying 3 times counts as 3 separate failures in the Circuit Breaker sliding window, tripping the breaker prematurely.

**Red Flags (DO NOT Say):**
- ❌ *"Configure Retry to retry every failed request infinitely until it succeeds."* (Causes infinite thread blocking and severe server overload).
- ❌ *"Retry `404 Not Found` errors with exponential backoff."* (404 is a permanent deterministic error; retrying wastes CPU and network bandwidth).
- ❌ *"Retrying a `POST /checkout` request without idempotency keys is completely safe."* (Will create duplicate orders and charge credit cards multiple times).
