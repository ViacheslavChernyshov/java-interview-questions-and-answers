# How to Implement Authentication and Authorization in Microservices?

---

## 🟢 Junior Level

In a microservices architecture, **Authentication (AuthN)** and **Authorization (AuthZ)** handle security across distributed services:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🔑 AUTHENTICATION (AuthN) — "Who are you?"              │ 🛡️ AUTHORIZATION (AuthZ) — "What can you do?"           │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Verifies user identity via credentials, MFA, or SSO.  │ • Determines if the authenticated user has permission to│
  │ • Performed once at login by an **Identity Provider**   │   execute an action (e.g. `ROLE_ADMIN`, `orders:write`).│
  │   (IdP: Keycloak, Auth0, Okta).                         │ • Evaluated at the **API Gateway** & internal services. │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```
  1. Login:   [User Browser] ────(User/Pass)────► [Auth Server (Keycloak)]
                             ◄──(Returns JWT)─────┘
  2. Access:  [User Browser] ────(Bearer JWT)───► [API Gateway (Verifies Signature)]
                                                         │ (Injects `X-User-Id: 42`)
                                                         ▼
                                                  [Order Service (Checks Role)]
```

## 🟡 Middle Level

### The Edge Token Verification Pattern

Validating cryptographic RSA/ECDSA signatures on every single internal microservice creates massive CPU overhead. The enterprise standard verifies tokens at the **API Gateway** and propagates clean trusted headers downstream:

```
  [External Client]
         │ (HTTP Request with `Authorization: Bearer eyJhbGci...`)
         ▼
  ┌─────────────────────────────────────────────────────────────────────────┐
  │                           API GATEWAY                                   │
  │ 1. Fetches public keys from IdP (`/jwks.json`).                         │
  │ 2. Validates cryptographic signature & expiration (`exp`).              │
  │ 3. Injects trusted user context into internal headers:                  │
  │    • `X-User-Id: 1042`                                                  │
  │    • `X-User-Roles: ROLE_USER,ROLE_ADMIN`                               │
  │    • `X-Tenant-Id: acme_corp`                                           │
  └───────────────────────────────────┬─────────────────────────────────────┘
                                      │ (Internal Fast Network)
                                      ▼
                        [INTERNAL ORDER SERVICE]
           (Reads `X-User-Id` header directly without crypto overhead!)
```

### Spring Security 6 Resource Server Configuration

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity // Enables @PreAuthorize on service methods
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/public/**").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
            .build();
    }
}
```

## 🔴 Senior Level

### Service-to-Service Security: Zero-Trust & mTLS

Treating the internal network as "trusted" is a fatal security flaw (a single compromised pod allows lateral movement). Senior architectures enforce **Zero-Trust Security**:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Security Mechanism           │ Implementation Architecture                                                     │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. mTLS (Mutual TLS)**     │ **Service Mesh (Istio / Linkerd)**: Envoy sidecars automatically establish      │
  │ (Identity & Wire Encryption) │ encrypted TLS connections, validating short-lived x509 SPIFFE certificates.     │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. OAuth2 Client           │ Microservices authenticate with Keycloak using `client_id` + `client_secret`    │
  │ Credentials Grant**          │ to obtain machine-to-machine (M2M) JWT tokens for cross-service calls.          │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

```
  [Order Service Pod]                             [Payment Service Pod]
  ┌────────────────────────┐                      ┌────────────────────────┐
  │ [Java Container]       │                      │ [Java Container]       │
  │           │            │                      │           ▲            │
  │  (Plaintext Localhost) │                      │  (Plaintext Localhost) │
  │           ▼            │                      │           │            │
  │ [Envoy Sidecar Proxy]  │ ──(mTLS Encrypted)─► │ [Envoy Sidecar Proxy]  │
  │ (SPIFFE: spiffe://...) │                      │ (Validates Cert & SAN) │
  └────────────────────────┘                      └────────────────────────┘
```

### JWT Revocation & The Stateless Invalidation Dilemma

Because JWTs are stateless and self-contained, a compromised token remains valid until its `exp` timestamp expires.

#### Senior Solution: Short-Lived Access Tokens + Refresh Tokens
1. **Short Lifespan:** Set Access Token expiration to **5–15 minutes**.
2. **Refresh Token Flow:** When the Access Token expires, the client uses a long-lived **Refresh Token** (stored in an `HttpOnly` secure cookie) to obtain a new token from the IdP.
3. **Emergency Revocation Blocklist:** For immediate account locks (e.g. lost phone), store revoked `token_id` (JTI) entries in **Redis** with a TTL matching the token lifespan; the API Gateway checks Redis on incoming requests.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **AuthN vs AuthZ:** AuthN verifies identity; AuthZ evaluates permissions and roles.
- **Edge Verification:** API Gateway validates JWT signatures against IdP (Keycloak/Auth0) and forwards parsed `X-User-Id` / `X-User-Roles` headers downstream.
- **Stateless Standard:** Use OAuth2 / OpenID Connect (OIDC) JWT tokens with Spring Security 6 Resource Server.
- **Zero-Trust Internal Network:** Use **mTLS via Service Mesh** (Istio Envoy sidecars) for service-to-service encryption and authentication.
- **Token Invalidation:** Mitigate stateless JWT revocation using short 15-min lifespans + Refresh Tokens + Redis blacklists.

**Common Follow-up Questions:**
- *"What is the difference between OAuth 2.0 and OpenID Connect (OIDC)?"* → OAuth 2.0 is a framework for **Authorization** (delegated access via Access Tokens); OpenID Connect is an identity layer built on top of OAuth 2.0 for **Authentication** (providing identity verification via `id_token`).
- *"Why should you never pass JWTs in URL query parameters?"* → Query parameters are logged in plaintext across browser histories, API Gateway access logs, and proxy servers. Always transmit tokens via the `Authorization: Bearer <token>` header.
- *"What is a JWKS endpoint?"* → JSON Web Key Set (`/.well-known/jwks.json`) is an HTTP endpoint hosted by Keycloak/Auth0 exposing public cryptographic keys used by API Gateways to verify JWT digital signatures.

**Red Flags (DO NOT Say):**
- ❌ *"Store user passwords in the local microservice database in plaintext."* (Passwords must be managed by dedicated IdPs using Argon2 or BCrypt).
- ❌ *"Let every microservice connect to the LDAP/Active Directory database on every HTTP request."* (Creates severe database bottlenecks; use JWT claims).
- ❌ *"Internal microservice traffic does not need encryption or authentication because it is behind a firewall."* (Violates Zero-Trust; a single compromised container exposes the entire platform).
