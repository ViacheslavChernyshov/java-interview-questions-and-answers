# What is the Difference Between Sharding and Partitioning?

---

## 🟢 Junior Level

The core difference between **Partitioning** and **Sharding** comes down to **WHERE** the physical data is stored—on a **single machine** or across **multiple physical servers**:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🗄️ PARTITIONING (Single Database Server)                │ 🌐 SHARDING (Distributed Multi-Node Architecture)       │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Splits a large table into smaller physical sub-tables │ • Splits a table horizontally across **multiple         │
  │   within the **same database server instance**.         │   independent physical database servers**.              │
  │ • Full ACID transactions and Foreign Keys preserved.    │ • No cross-node foreign keys; requires 2PC for trans.   │
  │ • Purpose: **Query Optimization & Fast Pruning**.       │ • Purpose: **Horizontal Scale & High Write Capacity**.  │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```
  1. PARTITIONING (1 Server, 1 DB Engine):
     Database Server:
     └── Table `orders`
         ├── `orders_2023` (Partition Table 1 on local disk)
         ├── `orders_2024` (Partition Table 2 on local disk)
         └── `orders_2025` (Partition Table 3 on local disk)

  2. SHARDING (3 Separate Physical Servers):
     [Server 1 (IP: 10.0.1.1)] ──► Holds Shard 1 (Users 1..1M)
     [Server 2 (IP: 10.0.1.2)] ──► Holds Shard 2 (Users 1M..2M)
     [Server 3 (IP: 10.0.1.3)] ──► Holds Shard 3 (Users 2M..3M)
```

## 🟡 Middle Level

### Feature Comparison Matrix

```
  ┌──────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Technical Aspect     │ Table Partitioning (Single DB)   │ Database Sharding (Multi-Server)                 │
  ├──────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Server Count**     │ Exactly **1 physical server**.   │ **$N$ physical servers** across the network.     │
  │ **ACID Transactions**│ 🟢 **100% Native ACID**: Standard│ 🔴 **Distributed**: Requires 2PC / Sagas.        │
  │                      │ single-database transactions.    │                                                  │
  ├──────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Foreign Keys**     │ 🟢 Supported across partitions.  │ 🔴 **No Cross-Shard Foreign Keys**.              │
  ├──────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **SQL Joins**        │ ⚡ **Full Local Join Speed**.    │ 🔴 Complex **Scatter-Gather** network joins.     │
  ├──────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Total Capacity**   │ Limited to single machine's disk.│ 🚀 **Unlimited Horizontal Storage & Write IOPS**.│
  │ **Complexity**       │ Low (Built into Postgres/MySQL). │ High (Requires routing, rebalancing, proxies).   │
  └──────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### PostgreSQL Declarative Partitioning in Action

```sql
-- 1. Create Partitioned Root Table:
CREATE TABLE orders (
    id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    created_at DATE NOT NULL
) PARTITION BY RANGE (created_at);

-- 2. Create Specific Partition Sub-Tables:
CREATE TABLE orders_2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE orders_2025 PARTITION OF orders
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

-- 3. Default Fallback Partition (Prevents insert errors):
CREATE TABLE orders_default PARTITION OF orders DEFAULT;
```

## 🔴 Senior Level

### The 2 Superpowers of Table Partitioning: Pruning & Instant Drops

1. **Partition Pruning (Query Optimization):**
   ```sql
   -- When executing this query:
   SELECT * FROM orders WHERE created_at = '2025-06-15';
   ```
   - The PostgreSQL query optimizer inspects table constraints, **skips 100% of all other partition tables**, and scans ONLY `orders_2025` from disk!
2. **Instant Archiving / Purging (`DROP TABLE` vs `DELETE`):**
   ```sql
   -- ❌ ANTI-PATTERN: Deleting 50 million old rows (Locks table, causes massive WAL/Vacuum churn):
   DELETE FROM orders WHERE created_at < '2023-01-01';

   -- ✅ THE SENIOR STANDARD: Instant metadata drop in 2 milliseconds:
   DROP TABLE orders_2022;
   ```

### When to Partition vs. When to Shard Decision Framework

```
                       ┌───────────────────────────────┐
                       │  Is table size/traffic high?  │
                       └───────────────┬───────────────┘
                                       │
                                       ▼
                       ┌───────────────────────────────┐
                       │ Can 1 high-spec server handle │──► [YES] ──► 🏆 Use Single-Node Table
                       │  storage and write IOPS?      │              PARTITIONING + Read Replicas!
                       └───────────────┬───────────────┘
                                       │
                                     [NO] (Writes > 50k/s or DB > 10 TB)
                                       │
                                       ▼
                             🚀 Use Database SHARDING
                           (Citus, Vitess, or CockroachDB)
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Rule:** Partitioning is on **1 database server**; Sharding is across **multiple independent servers**.
- **All Sharding is Horizontal Partitioning**, but not all partitioning is sharding.
- **Partition Pruning:** Database optimizer skips unneeded partition tables during `WHERE` clauses.
- **Instant Drop:** Old data can be purged in milliseconds by dropping the partition table (`DROP TABLE`).
- **Architectural Rule:** Always exhaust Table Partitioning, Vertical Scaling, and Read Replicas before introducing the immense operational complexity of Sharding!

**Common Follow-up Questions:**
- *"What is Vertical Partitioning?"* → Splitting a wide table by columns (e.g. moving rarely accessed `user_profile_description` text columns into a separate `user_details` table to keep the main `users` table cache-friendly).
- *"Can a Sharded database also use Table Partitioning?"* → Yes (Composite Partitioning); each physical shard database server can internally partition its local tables by date ranges!
- *"What happens if an SQL INSERT doesn't match any partition range in PostgreSQL?"* → If no `DEFAULT` partition is defined, PostgreSQL throws an error (`no partition of relation "orders" found for row`).

**Red Flags (DO NOT Say):**
- ❌ *"PostgreSQL partitioning splits data across 10 AWS cloud servers automatically."* (Standard PostgreSQL partitioning operates strictly on a single database instance).
- ❌ *"Sharding is easier to maintain than table partitioning."* (Sharding is vastly more complex due to distributed routing, backup management, and lack of cross-shard foreign keys).
- ❌ *"You can never drop partitions without deleting the parent table."* (`DROP TABLE <partition_name>` safely drops the partition while keeping the parent table intact).
