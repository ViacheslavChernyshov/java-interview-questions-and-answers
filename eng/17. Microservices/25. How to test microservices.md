# How to Test Microservices?

---

## 🟢 Junior Level

Testing microservices requires testing components at different boundaries—from individual Java classes up to cross-network contracts—using the **Microservices Test Pyramid**:

```
                              /\
                             /  \      1. End-to-End (E2E) Tests (~5%)
                            / E2E\     (Slowest, high fragility, full cluster)
                           /------\
                          /Contract\   2. Consumer-Driven Contract Tests (~15%)
                         / & Integ. \  (Pact / WireMock / Testcontainers)
                        /------------\
                       /  Unit Tests  \ 3. Unit Tests (~80%)
                      /________________\ (Sub-second execution, JUnit 5 + Mockito)
```

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Test Category                │ What It Tests                    │ Typical Tooling                                  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. Unit Tests**            │ Pure Java business logic methods │ **JUnit 5, Mockito, AssertJ** (Runs in $< 50\text{ms}$)│
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **2. Component / DB Tests**  │ Real database queries & Kafka    │ **Testcontainers** (PostgreSQL, Kafka, Redis)    │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **3. Contract Tests**        │ API schema compatibility         │ **Pact, Spring Cloud Contract**                  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **4. Outbound Mocking**      │ Simulates external REST APIs     │ **WireMock**                                     │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### Modern Spring Boot 3.1+ Integration Testing with Testcontainers (`@ServiceConnection`)

In modern Spring Boot 3, `@ServiceConnection` automatically discovers container ports and binds them to Spring environment properties without boilerplate `@DynamicPropertySource` code:

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class OrderServiceIntegrationTest {

    // Automatically spins up a real PostgreSQL container and configures Datasource URL/Credentials:
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    // Automatically spins up real Apache Kafka in Docker:
    @Container
    @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.5.0"));

    @Autowired
    private OrderRepository orderRepository;

    @Test
    void shouldCreateOrderAndPersistToDatabase() {
        Order order = new Order("item-101", new BigDecimal("49.99"), "CONFIRMED");
        Order saved = orderRepository.save(order);

        assertThat(saved.getId()).isNotNull();
        assertThat(saved.getTotalAmount()).isEqualByComparingTo("49.99");
    }
}
```

## 🔴 Senior Level

### Consumer-Driven Contract Testing (Pact / Spring Cloud Contract)

In a microservices ecosystem with 50 services, deploying a full test environment with all 50 services running is slow, expensive, and constantly broken by environmental flakiness. 

Senior teams use **Consumer-Driven Contract (CDC) Testing**:

```
  1. Consumer Side (User Service):
     • Writes a contract definition: "I expect `GET /orders/1` to return JSON with `id` and `total`."
     • Pact generates a `.json` contract file (Pact file) and uploads it to the central **Pact Broker**.

  2. Provider Side (Order Service CI/CD Pipeline):
     • Runs in isolation (no live User Service needed).
     • Pulls the Pact contract from the Broker and replays it against `OrderController`.
     • 🛡️ If an Order Service developer renames `total` to `totalAmount`, the Provider CI pipeline 
       **FAILS INSTANTLY BEFORE DEPLOYMENT!**
```

```java
// Provider Contract Verification Test:
@Provider("order-service")
@PactFolder("pacts")
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
public class OrderServiceProviderContractTest {

    @LocalServerPort
    private int port;

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void pactVerificationTestTemplate(PactVerificationContext context) {
        context.verifyInteraction(); // Validates that controller matches consumer expectations!
    }

    @BeforeEach
    void before(PactVerificationContext context) {
        context.setTarget(new HttpTestTarget("localhost", port));
    }
}
```

### Why Heavy End-to-End (E2E) Staging Environments Are an Anti-Pattern

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ ❌ The Staging E2E Testing Trap          │ 🏆 Contract Testing + Testcontainers Standard    │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Tests fail due to unrelated services   │ • Each service is tested 100% independently in CI│
  │   being down or out of sync (Flakiness). │   using ephemeral Docker containers.             │
  │ • Staging database data becomes polluted.│ • Zero shared staging environmental flakiness.   │
  │ • Test suite takes 3+ hours to execute.  │ • Complete CI test suite runs in under 4 minutes.│
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Test Pyramid:** 80% Unit Tests, 15% Component/Contract Tests, 5% E2E Smoke Tests.
- **Testcontainers:** The modern standard for integration testing with real PostgreSQL, Kafka, and Redis instances in Docker.
- **Spring Boot 3.1+:** Use `@ServiceConnection` for zero-boilerplate Testcontainer property injection.
- **Contract Testing:** **Pact** verifies API schema compatibility between Consumer and Provider in CI/CD without running live multi-service clusters.
- **WireMock:** Used to stub third-party external HTTP APIs during integration tests.

**Common Follow-up Questions:**
- *"What is the difference between `@MockBean` and WireMock?"* → `@MockBean` replaces a Spring bean inside the JVM using Mockito reflection; WireMock spins up a lightweight mock HTTP server listening on a local TCP port, testing the entire HTTP networking stack (`RestClient`, serializers, error handling).
- *"How do you test asynchronous Kafka event flows in isolation?"* → Use **Testcontainers Kafka** combined with **Awaitility** (`await().atMost(5, SECONDS).untilAsserted(...)`) to assert asynchronous message delivery and consumption deterministically.
- *"What is a Pact Broker?"* → A centralized repository where consumers publish JSON API contracts, and providers verify them during pull request builds (`can-i-deploy` CLI tool).

**Red Flags (DO NOT Say):**
- ❌ *"We don't need unit tests; we only write 500 end-to-end tests across all microservices in staging."* (E2E tests are slow, brittle, and create immense release bottlenecks).
- ❌ *"Integration tests should connect to a shared staging PostgreSQL database on the office network."* (Shared test databases create race conditions, dirty data, and network flakiness; use Testcontainers).
- ❌ *"Use H2 in-memory database for all integration tests instead of PostgreSQL."* (H2 has different SQL dialects, locking semantics, JSONB support, and indexing than Postgres, causing production bugs).
