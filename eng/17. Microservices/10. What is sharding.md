# What is Sharding?

---

## 🟢 Junior Level

**Database Sharding** (Horizontal Partitioning across nodes) is an architectural technique of splitting a single logical database across **multiple independent physical database servers (shards)**, where each server holds a unique, disjoint subset of the total rows:

```
                                [SHARDED DATABASE]
                                        │
           ┌────────────────────────────┼────────────────────────────┐
           ▼                            ▼                            ▼
      [Shard 1]                    [Shard 2]                    [Shard 3]
   Users A – H                  Users I – P                  Users Q – Z
 (DB Server 1: 2 TB)          (DB Server 2: 2 TB)          (DB Server 3: 2 TB)
```

```
  26-Volume Encyclopedia Analogy:
  • Single Server: A massive 10,000-page book. Only 1 person can read/write at a time; too heavy to lift.
  • Sharded Database: Splitting the book into 26 individual volumes (A, B, C... Z). 
    26 readers and writers can access different volumes simultaneously without blocking each other!
```

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Scaling Technique    │ Data Distribution            │ What Does It Scale?                              │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Read Replication** │ Every node stores **100%**   │ 🟢 Scales **Read Throughput** (`SELECT`).        │
  │                      │ of the entire database.      │ 🔴 Does NOT scale Write throughput or disk size. │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Sharding**         │ Each node stores **a unique  │ 🚀 Scales **BOTH Write Throughput and Total Disk │
  │                      │ slice** of data rows.        │ Storage Capacity** linearly across $N$ servers!  │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The 3 Shard Key Strategies

A **Shard Key** is an entity attribute (e.g. `user_id`, `tenant_id`, or `country_code`) used by the routing layer to determine which physical shard server holds a given row:

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Strategy                     │ Routing Formula              │ Trade-offs & Hotspot Risks                       │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. Range-Based**           │ `ID 1..1M ➔ Shard 1`         │ 🟢 Fast range queries (`BETWEEN`).               │
  │                              │ `ID 1M..2M ➔ Shard 2`        │ 🔴 **Hotspotting**: All new auto-increment writes│
  │                              │                              │ hammer the newest shard server!                  │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **2. Hash-Based** (Default)  │ `hash(user_id) % num_shards` │ 🟢 **Perfect Uniform Distribution** of writes.   │
  │                              │                              │ 🔴 Range queries require scattering to ALL shards│
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **3. Directory-Based**       │ Central Lookup Table:        │ 🟢 Flexible (Can isolate VIP tenants to dedicated│
  │                              │ `Tenant_A ➔ Shard 3`         │ hardware). 🔴 Lookup directory is a SPOF/bottlene│
  └──────────────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### The 3 Inherent Penalties of Sharded Databases

```
  1. Cross-Shard Joins (Scatter-Gather):
     • A query without a shard key (`SELECT * FROM orders WHERE status = 'PENDING'`) must execute 
       on ALL 100 shards simultaneously (Scatter), merging results in application memory (Gather).

  2. Loss of Foreign Key Referential Integrity:
     • Relational databases cannot enforce `FOREIGN KEY` constraints across physical server boundaries 
       (`orders` on Shard 1 cannot reference `users` on Shard 2). Integrity must be enforced in Java!

  3. Cross-Shard Transactions:
     • Atomic updates across two shards require heavy **Two-Phase Commit (2PC)**, multiplying 
       latency by 10x–50x.
```

## 🔴 Senior Level

### The Re-Sharding Crisis & Consistent Hashing

With naive modulo hashing (`hash(key) % N`):
- If you scale from $N=3$ to $N=4$ shards, **75% of all keys in the database change shard destinations**, requiring days of massive data migration downtime!

#### The Senior Solution: Consistent Hashing (Virtual Nodes)

```
                                 [0 / 2^32 - 1]
                              .----------------.
                           .'     Shard A        '.
                         .'                        '.
                   Shard C                           Shard B
                         '.                        .'
                           '.                    .'
                              '----------------'
```
- Both shard servers and data keys are mapped onto a logical circular **Hash Ring** ($0 \dots 2^{32}-1$).
- Adding a new shard server takes over keys from only its immediate neighbor, moving only **$\frac{1}{N+1}$ of the total database** without full re-indexing!
- **Virtual Nodes:** Each physical shard maps to multiple points on the ring (e.g. `ShardA-1`, `ShardA-2`), ensuring uniform load distribution.

### Modern Distributed SQL (NewSQL) vs. Application-Level Sharding

In modern enterprise architectures, manual Java-level sharding logic is replaced by transparent distributed database engines:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Technology                   │ Architecture & Mechanism                                                        │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Citus Data (PostgreSQL)**  │ Extends PostgreSQL into a distributed cluster; automatically shards tables      │
  │                              │ based on `tenant_id` while preserving SQL semantics.                            │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Vitess (YouTube MySQL)**   │ Proxy clustering layer providing transparent horizontal sharding for MySQL.    │

  │ **Distributed NewSQL**       │ **CockroachDB**, **YugabyteDB**, **Google Cloud Spanner**: Built-in automatic   │

  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Splitting a single logical database across multiple physical database servers.
- **Scaling Purpose:** Scales **Write Throughput** and **Disk Capacity** beyond the physical limits of a single machine.
- **Shard Key:** The routing attribute (e.g. `user_id`); choosing high-cardinality keys is critical.
- **Downsides:** No cross-shard foreign keys, slow cross-shard joins (Scatter-Gather), complex distributed transactions.
- **Consistent Hashing:** Eliminates massive data migrations when adding new shard servers.

**Common Follow-up Questions:**
- *"What is a 'Hot Shard' (Hotspotting)?"* → When one shard receives a disproportionate amount of read/write traffic (e.g. a celebrity user's account or a single date range), overloading that specific server while other shards sit idle.
- *"What is Scatter-Gather querying?"* → A query without a shard key is broadcast to all shards in parallel (Scatter), and the application or gateway merges, sorts, and paginates the returned subsets (Gather).
- *"How does Sharding differ from Vertical Partitioning?"* → Sharding splits rows horizontally across multiple servers; Vertical Partitioning splits columns of a table into separate tables (e.g. moving large BLOBs/descriptions to a separate table).

**Red Flags (DO NOT Say):**
- ❌ *"Sharding and Read Replication are the exact same thing."* (Replication duplicates 100% of data for read scaling; Sharding splits data for write/storage scaling).
- ❌ *"You should shard your database on day 1 of a new startup project."* (Sharding adds immense architectural complexity; scale vertically and use read replicas first).
- ❌ *"Foreign keys work automatically between different PostgreSQL shard servers."* (Relational engines cannot enforce cross-node foreign keys).
