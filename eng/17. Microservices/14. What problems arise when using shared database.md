# What Problems Arise When Using Shared Database?

---

## 🟢 Junior Level

The **Shared Database Anti-Pattern** occurs when multiple independent microservices connect directly to the same physical or logical database instance and read/write the same tables via SQL:

```
        ┌──────────────────┐           ┌──────────────────┐
        │  Order Service   │           │   User Service   │
        └────────┬─────────┘           └────────┬─────────┘
                 │ (Direct SQL)                 │ (Direct SQL)
                 └──────────────┐       ┌───────┘
                                ▼       ▼
                        ┌───────────────────────┐
                        │    SHARED DATABASE    │ ⚠️ (CATASTROPHIC ANTI-PATTERN!)
                        │ (users, orders, ...)  │
                        └───────────────────────┘
```

```
  Communal Kitchen Analogy:
  • If 5 independent chefs share a single spice rack and refrigerator without talking to each other, 
    one chef throws away an ingredient (drops a column) thinking it is unused, instantly ruining 
    all 4 other chefs' dishes!
```

```
  The Result: A "Distributed Monolith"
  • You suffer all the operational pain of microservices (network latency, distributed tracing, complex deployments) 
    with NONE of the benefits (no autonomous deployments, no fault isolation, no independent scaling).
```

## 🟡 Middle Level

### The 5 Catastrophic Failures of Shared Databases

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Failure Mechanism               │ Technical Breakdown & Real-World Impact                                         │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Schema Tight-Coupling**    │ `UserService` runs `ALTER TABLE users DROP COLUMN phone;`.                      │
  │                                 │ `OrderService` instantly crashes in production with `SQLException`!             │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. Connection Starvation**    │ `AnalyticsService` executes a heavy report, grabbing all 300 database           │
  │                                 │ connections in HikariCP. `AuthService` can get 0 connections $\to$ 💥 **HTTP 503**!│
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. Lock Contention & Deadlock**│ Service A opens a long transaction updating 10,000 rows. Database escalates to a│
  │                                 │ **Table Lock**, blocking Service B's fast `SELECT ... WHERE id = ?` queries!   │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **4. Single Point of Failure**  │ If the shared database runs out of disk or restarts, **100% of all microservices│
  │ (Total Cluster Blackout)        │ in the company crash simultaneously**.                                          │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **5. Migration Conflicts**      │ Multiple services run Flyway/Liquibase migrations simultaneously against the    │
  │                                 │ same `schema_version` metadata table, triggering deadlock migration failures.   │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Zero-Downtime Migration: Strangler Fig + Debezium CDC

Migrating from a legacy Shared Database to [Database per Service](13.%20What%20is%20Database%20per%20Service%20Pattern.md) without customer downtime is an advanced architectural initiative:

```
  Step 1: Shared DB ──► Step 2: CDC Sync ──► Step 3: Shadow Reads ──► Step 4: Cutover & Isolate
```

```
                             [CLIENT TRAFFIC]
                                    │
                                    ▼
                         [USER SERVICE CONTAINER]
                         ┌──────────┴──────────┐
                         │ (Writes to Old DB)  │ (Shadow Reads from New DB)
                         ▼                     ▼
               ┌───────────────────┐ ┌───────────────────┐
               │  LEGACY SHARED DB │ │  NEW ISOLATED DB  │
               └─────────┬─────────┘ └───────────────────┘
                         │                     ▲
                         │ (Tail Postgres WAL) │ (Stream Inserts)
                         ▼                     │
               [Debezium CDC + Kafka Connect] ─┘
```

#### Step-by-Step Migration Protocol:
1. **Enforce API Boundaries:** Forbid all other microservices from querying `users` table directly; force them to call `UserService` via REST / gRPC.
2. **Provision Dedicated Database:** Spin up a new, isolated PostgreSQL RDS instance (`user_db`).
3. **Real-Time CDC Replication:** Deploy **Debezium + Kafka Connect** to tail the Write-Ahead Log (WAL) of the old shared database and replicate all row mutations to `user_db` in real-time ($< 10\text{ms}$ replication lag).
4. **Dark Launch / Shadow Reads:** Configure `UserService` to execute dual-reads from both databases in background threads to verify data integrity and compare latencies.
5. **Traffic Cutover:** Point `UserService` write connections to `user_db`, decommission the Debezium replication pipeline, and drop the legacy tables from the shared database!

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Multiple microservices sharing a single database instance and directly accessing tables.
- **The Core Danger:** Transforms your architecture into a **Distributed Monolith** (tight coupling, fragile releases).
- **5 Traps:** Schema coupling, connection pool starvation, lock contention/deadlocks, single point of failure, migration collisions.
- **Remedy:** Migrate to [Database per Service](13.%20What%20is%20Database%20per%20Service%20Pattern.md) using **Strangler Fig Pattern** and **Debezium CDC**.

**Common Follow-up Questions:**
- *"Is a shared database ever acceptable?"* → Only in early-stage startups/prototypes where the team has 1–2 developers and business domain boundaries are not yet known. Once multiple teams exist, it becomes a severe bottleneck.
- *"How do you prevent connection starvation if you are forced to share a database temporarily?"* → Enforce strict connection caps in HikariCP per service and deploy **PgBouncer** / AWS RDS Proxy to manage connection pooling globally.
- *"Why is dropping a column in a shared database so dangerous?"* → In Java Hibernate, if an entity has `@Column(name = "phone")` mapped and the database column is dropped by another team, all queries (`SELECT u FROM User u`) immediately fail with `Column not found` exceptions.

**Red Flags (DO NOT Say):**
- ❌ *"Shared database is good because it lets you execute fast SQL JOINs across all company microservices."* (Defeats the entire purpose of microservice autonomy and isolation).
- ❌ *"You can fix shared database problems by having developers tell each other in Slack before modifying database tables."* (Human communication cannot prevent runtime connection starvation or lock escalation).
- ❌ *"Database migrations should run in all microservices against the same shared database simultaneously."* (Triggers Liquibase/Flyway schema version lock collisions).
