# How to Implement Horizontal Scaling of Microservices?

---

## 🟢 Junior Level

**Horizontal Scaling (Scale Out)** is the practice of increasing system capacity by adding **more identical instances (replicas)** of a microservice behind a load balancer, rather than making a single server larger (Vertical Scaling / Scale Up):

```
  Supermarket Cashier Analogy:
  • Vertical Scaling (Scale Up): Hiring 1 super-cashier who types twice as fast. 
    Eventually, human limits are reached, and if they take a lunch break, the store closes.
  • Horizontal Scaling (Scale Out): Opening 10 checkout lanes side-by-side with 10 cashiers. 
    You can dynamically open 5 more lanes during holiday surges and close them when quiet!
```

```
                                [LOAD BALANCER]
                                        │
           ┌────────────────────────────┼────────────────────────────┐
           ▼                            ▼                            ▼
  [Order Service #1]           [Order Service #2]           [Order Service #3]
  (Pod @ 10.244.1.5)           (Pod @ 10.244.2.8)           (Pod @ 10.244.3.12)
```

## 🟡 Middle Level

### The #1 Prerequisite: Enforcing Strict Statelessness

A microservice **cannot be scaled horizontally** if it maintains state in local JVM memory or local disk:

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Local Stateful Trap             │ Production Stateless Remedy                                                     │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. In-Memory User Sessions**  │ Offload HTTP sessions to a centralized **Redis Cluster**, or use **Stateless    │
  │ (`HttpSession` in JVM memory)   │ Cryptographic JWT Tokens** verified at the API Gateway.                         │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. Local Disk File Uploads**  │ Never save uploads to `/tmp/uploads`; stream directly to S3 / MinIO buckets.    │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. Scheduled Background Jobs**│ Use distributed schedulers (**ShedLock**, Quartz, or Kubernetes `CronJob`) so   │
  │ (`@Scheduled` running on all)   │ only 1 instance executes the cron task instead of all 10 replicas!              │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Kubernetes Horizontal Pod Autoscaler (HPA v2) Configuration

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 20
  metrics:
  # Metric 1: CPU Utilization
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  # Metric 2: Custom Prometheus Request Rate (Throughput)
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: 500
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300 # Prevent flapping during intermittent traffic drops
```

## 🔴 Senior Level

### Autoscaling on Message Queue Lag (KEDA)

Scaling microservices based purely on CPU is ineffective for event-driven workers. When 100,000 messages hit a Kafka topic, CPU might remain at 10% while messages pile up. Senior architects use **KEDA (Kubernetes Event-Driven Autoscaling)**:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-consumer-scaler
spec:
  scaleTargetRef:
    name: order-worker-deployment
  minReplicaCount: 2
  maxReplicaCount: 30
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka-cluster:9092
      consumerGroup: order-processing-group
      topic: order-events
      lagThreshold: "1000" # Add 1 worker pod for every 1,000 lag messages
```

### The Database Connection Pool Exhaustion Ceiling

The hidden risk of horizontal scaling is overwhelming the downstream database:

```
  1. Each Spring Boot pod configures HikariCP with `maximumPoolSize = 30`.
  2. Traffic surges ➔ HPA scales pods from 5 to 50 replicas!
  3. Total Open JDBC Connections = $50 \times 30 = 1,500$ Connections!
  4. 💥 PostgreSQL reaches `max_connections = 500` ➔ Rejects connections with fatal errors!
```

#### Senior Solution:
Deploy a database connection pooler (**PgBouncer** for PostgreSQL, **ProxySQL** for MySQL, or **AWS RDS Proxy**) between the scaled microservice fleet and the database server to multiplex thousands of microservice sockets into a fixed set of database connections.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Adding identical stateless microservice instances behind a load balancer to increase capacity.
- **Scale Out vs Scale Up:** Scale Out provides high availability, fault tolerance, and near-infinite elasticity.
- **Statelessness Rule:** Microservices must store zero persistent session/file state in JVM memory or local disk.
- **Kubernetes HPA:** Automatically scales pod replicas based on CPU, memory, HTTP request rates, or custom metrics.
- **KEDA:** Scales event-driven Kafka/RabbitMQ consumer workers based on queue lag.
- **Database Hazard:** Always guard against database connection pool exhaustion using **PgBouncer** / RDS Proxy.

**Common Follow-up Questions:**
- *"Why is JVM Heap Memory a dangerous metric for HPA autoscaling?"* → The JVM allocates memory from the OS and delays releasing it until Major GC cycles; HPA may see 90% memory usage and continuously scale out pods even when actual heap occupancy is low.
- *"What is Flapping / Thrashing in autoscaling?"* → Rapid oscillating between scaling up and scaling down caused by spiky traffic. Prevent this by configuring `stabilizationWindowSeconds: 300` on scale-down behavior.
- *"How does Node Autoscaling (Karpenter) work with HPA?"* → When HPA creates new pods that cannot fit on existing Kubernetes worker nodes (Pending state), Karpenter provisions new physical/cloud VM instances in seconds to host the pods.

**Red Flags (DO NOT Say):**
- ❌ *"Horizontal scaling means upgrading your server from 16 GB of RAM to 64 GB of RAM."* (That is Vertical Scaling; Horizontal Scaling means adding more independent instances).
- ❌ *"Store user login sessions in `HttpSession` JVM RAM and enable sticky sessions on the load balancer."* (Sticky sessions break elasticity and load balancing; use Redis or stateless JWTs).
- ❌ *"You can scale horizontally to 100 instances without worrying about database connection limits."* (Uncapped connection pooling will crash the database; connection poolers are required).
