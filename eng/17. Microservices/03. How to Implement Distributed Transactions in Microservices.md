# How to Implement Distributed Transactions in Microservices?

---

## 🟢 Junior Level

In a microservices architecture where each service has its own dedicated database (**Database per Service**), traditional monolithic ACID transactions (`@Transactional`) cannot span across multiple services:

```
  Multi-Bank Wire Transfer Analogy:
  • Monolithic Transaction (1 Bank): Transferring money between Account A and Account B within the same bank 
    is handled in 1 atomic database transaction (ACID).
  • Distributed Transaction (Different Banks): Bank 1 debits Account A, but Bank 2's network drops before 
    crediting Account B. You cannot use a local database rollback; you need distributed coordination!
```

```
  The 3 Primary Solutions for Distributed Consistency:
  1. 🏆 Saga Pattern: Asynchronous chain of local transactions with Compensating Rollbacks.
  2. 📦 Transactional Outbox Pattern: Solves the "Dual-Write" problem between DB and Message Broker.
  3. ⚠️ Two-Phase Commit (2PC / XA): Legacy synchronous distributed locking (largely avoided today).
```

## 🟡 Middle Level

### The Dual-Write Disaster (Why Simple Kafka Publishing Fails)

The most common mistake when implementing distributed transactions is publishing an event directly after saving to the database:

```java
// ❌ CATASTROPHIC DUAL-WRITE BUG:
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order); // Step 1: Writes to PostgreSQL
    
    // Step 2: Publish to Kafka:
    kafkaTemplate.send("order-events", new OrderCreatedEvent(order.getId()));
    // 💥 IF APP CRASHES OR NETWORK DIES HERE:
    // Postgres committed the order, but Kafka NEVER received the event!
    // Downstream Payment Service will NEVER charge the customer!
}
```

### The Production Solution: Transactional Outbox + Debezium CDC

```
  [Order Service Application]
  1. Atomic Local Transaction (Postgres):
     • `INSERT INTO orders (...) VALUES (...);`
     • `INSERT INTO outbox_table (event_id, payload) VALUES (...);`
     • `COMMIT;` (100% Guaranteed consistency via single local ACID transaction!)
          │
          ▼
  [PostgreSQL Write-Ahead Log (WAL)]
          │
          ▼
  [Debezium CDC Connector / Kafka Connect]
  2. Tails Postgres WAL directly from disk and streams event to Kafka!
          │
          ▼
  [Kafka Topic: "order-events"]
          │
          ▼
  [Payment Service Consumer]
```

### Idempotency & TCC (Try-Confirm-Cancel) Pattern

For financial and payment integrations where compensating transactions are complex, senior systems use the **TCC (Try-Confirm-Cancel)** pattern:

```
  1. TRY Phase (Reserve Resources):
     • Check account balance.
     • Move $100 from `available_balance` to `frozen_balance`.
  
  2. CONFIRM Phase (Finalize):
     • Deduct $100 from `frozen_balance`.
     • Mark transaction as COMPLETED.

  3. CANCEL Phase (Rollback on Failure):
     • Release $100 from `frozen_balance` back to `available_balance`.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The Core Problem:** Microservices with isolated databases cannot use single-database `@Transactional` boundaries.
- **Why 2PC Fails:** Two-Phase Commit is synchronous, holds distributed database locks, and creates a coordinator SPOF.
- **The Standard:** **Saga Pattern** + **Transactional Outbox Pattern** (via Debezium CDC) is the modern industry standard.
- **Dual-Write Defense:** Never write to a database and publish to Kafka in the same method without an outbox table.
- **Architectural Rule #1:** The best distributed transaction is the one you design away (co-locate tightly coupled domain models).

**Common Follow-up Questions:**
- *"What is the difference between Saga and TCC (Try-Confirm-Cancel)?"* → Saga executes actual business state changes ($T_k$) and undoes them via compensation ($C_k$); TCC reserves resources in the "Try" phase and finalizes them in the "Confirm" phase, avoiding visible intermediate business mutations.
- *"How does Debezium ensure zero message loss in Transactional Outbox?"* → Debezium reads PostgreSQL's low-level binary Write-Ahead Log (WAL) directly using logical replication slots, guaranteeing every committed outbox row is published to Kafka.
- *"What happens if a consumer receives the same Saga event twice?"* → Every consumer **must implement idempotency** (e.g. checking a processed `event_id` table) to prevent duplicate processing.

**Red Flags (DO NOT Say):**
- ❌ *"We use Spring `@Transactional` across 4 REST microservices."* (`@Transactional` only manages a single local JDBC connection).
- ❌ *"Two-Phase Commit is the recommended default for cloud Kubernetes microservices."* (2PC destroys availability and scalability).
- ❌ *"Publishing to Kafka inside `@Transactional` is completely safe because Spring handles rollback."* (Kafka messages cannot be rolled back after transmission).
