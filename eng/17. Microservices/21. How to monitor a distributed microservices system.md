# How to Monitor a Distributed Microservices System?

---

## 🟢 Junior Level

Monitoring a distributed microservices system requires tracking the health, performance, and resource usage of dozens or hundreds of independent services in real-time using the **Observability Triad**:

```
                               ┌─────────────────────────┐
                               │   OBSERVABILITY TRIAD   │
                               └────────────┬────────────┘
                                            │
                ┌───────────────────────────┼───────────────────────────┐
                ▼                           ▼                           ▼
        [1. METRICS]                  [2. LOGS]                   [3. TRACES]
    Numeric time-series data      Structured JSON event records  End-to-end request journeys
    (Prometheus & Grafana)        (Loki / ELK / OpenSearch)      (OpenTelemetry & Jaeger)
```

```
  Google SRE 4 Golden Signals:
  1. ⏱️ Latency: How long requests take to execute (p50, p95, p99 percentiles).
  2. 🚦 Traffic: Demand placed on the service (Requests Per Second / RPS).
  3. 💥 Errors: Rate of requests that fail with HTTP 5xx or exceptions.
  4. 📈 Saturation: Resource constraints (CPU %, Memory %, Thread pool queue depth).
```

## 🟡 Middle Level

### The RED & USE Monitoring Methodologies

Senior SREs structure dashboards around two standard monitoring frameworks:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Methodology                  │ Target Scope                     │ Core Telemetry Metrics                           │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **RED Method**               │ **Request-Driven Web Services**  │ • **Rate**: Requests processed per second.       │
  │ (Tom Wilkie)                 │ (Microservice API endpoints)     │ • **Errors**: Failed requests per second.        │
  │                              │                                  │ • **Duration**: Latency distribution histogram.  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **USE Method**               │ **Hardware & Infrastructure**    │ • **Utilization**: % time resource was busy.     │
  │ (Brendan Gregg)              │ (CPUs, Disks, DB Connections)    │ • **Saturation**: Queue length of pending work.  │
  │                              │                                  │ • **Errors**: Hardware / OS packet drop count.   │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Spring Boot 3 Actuator + Micrometer Metric Instrumentation

```java
@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    private final Counter orderCounter;
    private final Timer orderLatencyTimer;
    private final OrderService orderService;

    public OrderController(MeterRegistry registry, OrderService orderService) {
        this.orderService = orderService;
        // 1. Monotonic Counter tracking total successful checkouts:
        this.orderCounter = Counter.builder("orders.placed.total")
            .description("Total number of successfully placed orders")
            .tag("region", "us-east-1")
            .register(registry);

        // 2. Timer tracking execution latency histograms (p95, p99):
        this.orderLatencyTimer = Timer.builder("orders.processing.latency")
            .description("Order creation execution time")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
    }

    @PostMapping
    public OrderResponseDTO createOrder(@RequestBody OrderRequestDTO request) {
        return orderLatencyTimer.record(() -> {
            OrderResponseDTO response = orderService.processOrder(request);
            orderCounter.increment();
            return response;
        });
    }
}
```

### Eliminating "Alert Fatigue" (The Actionable Alert Rule)

The #1 failure in enterprise monitoring is **Alert Fatigue**, where engineers receive 100 non-critical alerts a day and begin muting PagerDuty:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ THE ACTIONABLE ALERT GOLDEN RULES:                                                            │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 1. **Alert on Symptoms, Not Causes:** Alert if "Order checkout p99 latency > 2s for 5 mins"   │
  │    (Symptom hurting users), NOT "Pod CPU temporarily hit 85%" (Noise).                        │
  │ 2. **Every Alert Must Be Actionable:** If an alert fires at 3:00 AM and the on-call engineer  │
  │    does not need to take immediate corrective action, that alert MUST be deleted!             │
  │ 3. **Use Multi-Window Burning Rates:** Alert based on SLO Error Budget Burn Rates to detect  │
  │    rapid catastrophic outages without triggering on momentary blips.                          │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Observability Triad:** Metrics (numbers), Logs (events), Traces (request journeys).
- **4 Golden Signals:** Latency, Traffic, Errors, Saturation.
- **RED Method:** Rate, Errors, Duration (standard for microservice APIs).
- **USE Method:** Utilization, Saturation, Errors (standard for infrastructure/databases).
- **Spring Stack:** **Spring Boot Actuator + Micrometer** scraped by **Prometheus** and visualized in **Grafana**.
- **Actionable Alerts:** Only alert on user-impacting SLO breaches; avoid alert fatigue.

**Common Follow-up Questions:**
- *"What is the difference between p95 and Average (Mean) latency?"* → Average hides extreme outliers (e.g. 99 users get 10ms responses, but 1 user waits 30 seconds; the average is 310ms, but p99 reveals the critical 30s bottleneck).
- *"How do Pull-based (Prometheus) and Push-based (StatsD/Datadog) monitoring differ?"* → In Pull-based, Prometheus scrapes target `/metrics` HTTP endpoints on a schedule; in Push-based, applications send UDP/HTTP packets to an agent collector.
- *"What is a Gauge in Micrometer?"* → A metric representing a value that can arbitrarily go up and down over time (e.g. active HTTP connections, available memory, or thread pool size).

**Red Flags (DO NOT Say):**
- ❌ *"Monitoring just means logging errors to a local log file on the container's hard drive."* (Container disks are ephemeral; logs and metrics must be shipped to centralized monitoring clusters).
- ❌ *"Configure PagerDuty to page developers whenever a single HTTP 500 error occurs."* (Creates severe alert fatigue; alert on error rates and SLO breaches).
- ❌ *"Average response time is the only latency metric you need to look at."* (Averages mask severe p99 tail-latency anomalies).
