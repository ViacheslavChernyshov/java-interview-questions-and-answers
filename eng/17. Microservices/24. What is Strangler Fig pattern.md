# What is Strangler Fig Pattern?

---

## 🟢 Junior Level

The **Strangler Fig Pattern** (coined by Martin Fowler) is an architectural migration strategy that **incrementally decomposes a legacy monolithic application into microservices** by gradually replacing specific features piece-by-piece behind an API Gateway, avoiding the catastrophic risk of a "Big Bang Rewrite":

```
  Botanical Analogy:
  • The Strangler Fig vine seeds in the upper branches of a host tree, slowly grows roots downward, 
    gradually envelops the original trunk, and eventually replaces the old tree entirely!
```

```
  Phase 0: [=== 100% LEGACY MONOLITH ===]
  Phase 1: [=== 80% Monolith ===] + [User Microservice]
  Phase 2: [=== 50% Monolith ===] + [User Microservice] + [Order Microservice]
  Phase 3: [=== 20% Monolith ===] + [User Svc] + [Order Svc] + [Payment Svc]
  Phase 4: [User Svc] + [Order Svc] + [Payment Svc] + [Catalog Svc] (Monolith DECOMMISSIONED!)
```

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ ❌ Big Bang Rewrite (Massive Anti-Pattern)│ 🏆 Strangler Fig Pattern (Industry Standard)     │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Freeze feature development for 2 years │ • Continues shipping new features every sprint.  │
  │   to rewrite the entire system.          │ • Delivers value to production every 2–4 weeks.  │
  │ • High rate of total project failure.    │ • Low risk; rollback is trivial via API Gateway. │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The 4-Step Migration Lifecycle

```
                       ┌───────────────────────────────┐
                       │     API GATEWAY / INGRESS     │
                       └───────┬───────────────┬───────┘
                               │               │
            /api/v1/orders/**  │               │  /api/v1/users/** (STRANGLED ROUTE!)
                               ▼               ▼
                      ┌─────────────────┐ ┌─────────────────┐
                      │ LEGACY MONOLITH │ │  USER SERVICE   │
                      │  (Deprecated)   │ │ (New Container) │
                      └─────────────────┘ └─────────────────┘
```

```
  1. INTERCEPT (The Routing Facade):
     • Place an **API Gateway** (Spring Cloud Gateway, Kong, Envoy) in front of the Monolith. 
     • 100% of all client traffic enters through the Gateway.

  2. TRANSFORM (Build New Service):
     • Carve out a distinct Bounded Context (e.g. `User Service`) and build it with its own 
       isolated database ([Database per Service](13.%20What%20is%20Database%20per%20Service%20Pattern.md)).

  3. COEXIST (Dual Running & Cutover):
     • The Gateway routes `/api/v1/users/**` to the new User Service while continuing to proxy 
       all other requests (`/orders`, `/payments`) to the Monolith.

  4. ELIMINATE (Decommissioning):
     • Safely delete the legacy user code and tables from the Monolith. Repeat for the next domain!
```

## 🔴 Senior Level

### Data Synchronization: Why Dual-Writing Fails & CDC Wins

During the Coexist phase, data must remain synchronized between the Monolith's database and the new Microservice's database.

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ ❌ Application Dual-Writing (Fragile)    │ 🏆 Change Data Capture / CDC (Zero-Loss Standard)│
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Monolith updates local DB and makes an │ • **Debezium + Kafka Connect** tails the low-    │
  │   HTTP/Kafka call to the new service.    │   level Write-Ahead Log (WAL) of the Monolith DB │
  │ • Network drops and app crashes cause    │   and streams mutations to Kafka.                │
  │   permanent data divergence & race conds.│ • Guarantees sub-second, zero-loss replication!  │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

```
  [Monolith PostgreSQL] ──(WAL Binary Stream)──► [Debezium CDC] ──► [Kafka] ──► [New User Service DB]
```

### Traffic Shadowing (Dark Launching) & Diff Verification

Before routing real users to the new microservice, senior architects validate performance and accuracy using **Traffic Shadowing**:

```
  [API Gateway]
        │
        ├── (1. Primary Synchronous Call) ────────► [Legacy Monolith] ──► Returns HTTP 200 to User
        │
        └── (2. Asynchronous Shadow Copy) ───────► [New Microservice]
                                                           │
                                                           ▼
                                               [Diff Comparison Engine]
```
1. **Shadow Copy:** The API Gateway clones 100% of live production requests in the background, firing them at the new microservice asynchronously.
2. **Diff Engine:** Compares the JSON responses and HTTP status codes between Monolith and Microservice across 1,000,000 requests.
3. **Canary Cutover:** Once accuracy reaches 100%, real traffic is shifted gradually via Feature Flags ($1\% \to 10\% \to 50\% \to 100\%$).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Incrementally migrating features out of a monolith into microservices behind an API Gateway.
- **Why It Wins:** Eliminates the catastrophic failure rate of 2-year "Big Bang Rewrites".
- **4 Phases:** **Intercept** (Gateway), **Transform** (Build service), **Coexist** (Route traffic), **Eliminate** (Delete legacy code).
- **Data Synchronization:** Use **Change Data Capture (CDC / Debezium)** rather than application-level dual-writes.
- **Verification:** Use **Traffic Shadowing (Dark Launching)** to test the new service with real production load before cutover.

**Common Follow-up Questions:**
- *"Which domains should you strangle first?"* → Start with low-risk, loosely coupled boundary services (e.g. Email/SMS notifications, PDF generation, or read-heavy catalogs) to build team confidence and CI/CD pipelines before tackling the core transactional billing engine.
- *"How do you handle shared database foreign keys during Strangler Fig migration?"* → Replicate necessary data via Kafka events to denormalize the new service's database, removing cross-database foreign key constraints.
- *"What happens if a newly strangled microservice fails in production?"* → Instant rollback in 1 second by toggling the API Gateway route or Feature Flag back to the Monolith endpoint.

**Red Flags (DO NOT Say):**
- ❌ *"The best way to modernize a monolith is to stop all company feature development for 18 months and rewrite everything from scratch."* (Classic anti-pattern that frequently leads to bankruptcy or cancelled projects).
- ❌ *"Synchronize data during migration by making synchronous HTTP REST calls from inside database triggers."* (Disastrous latency and deadlock hazard).
- ❌ *"A strangled microservice should continue sharing the monolith's database tables."* (Every carved-out service must own its private database).
