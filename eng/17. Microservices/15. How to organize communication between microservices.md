# How to Organize Communication Between Microservices?

---

## 🟢 Junior Level

In a microservices architecture, services communicate using **two primary communication styles**:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 📞 SYNCHRONOUS (Request / Response)                     │ 📬 ASYNCHRONOUS (Event / Message Driven)                │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • The caller sends a request and **waits for an         │ • The producer publishes a message to a **Message       │
  │   immediate response** (e.g. HTTP REST, gRPC).          │   Broker** (Kafka/RabbitMQ) and moves on immediately.   │
  │ • Real-Time Phone Call Analogy.                         │ • Sending an Email / Text Message Analogy.              │
  │ • Best for: Immediate queries (`GET /user/123`).        │ • Best for: Multi-step background workflows & events.   │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```
  1. Synchronous Communication:
     [Order Service] ────(HTTP / gRPC Request)────► [Payment Service]
                     ◄───(Immediate HTTP 200 OK)────┘

  2. Asynchronous Communication:
     [Order Service] ────(Publish: "OrderPlaced")────► [Kafka Topic: "order-events"]
                                                               │
                                                       (Consumes when ready)
                                                               ▼
                                                       [Shipping Service]
```

## 🟡 Middle Level

### The 4 Major Protocols in Modern Systems

```
  ┌──────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Communication Type   │ Protocol / Technology        │ Production Use Case                              │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. HTTP / REST**   │ JSON over HTTP/1.1 or HTTP/2 │ Public API endpoints, browser/mobile clients,    │
  │                      │ (Spring `RestClient`)        │ simple external integrations.                    │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **2. gRPC / Protobuf**│ Binary Protobuf over HTTP/2 │ ⚡ **Internal Service-to-Service High-Speed RPC**:│
  │                      │ Multiplexed TCP streams      │ 7x–10x faster serialization than JSON!           │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **3. Event Streams** │ **Apache Kafka**             │ High-throughput event-carried state transfer,    │
  │ (Pub-Sub)            │ Distributed commit log       │ data replication, and event sourcing.            │
  ├──────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **4. Message Queues**│ **RabbitMQ / AWS SQS**       │ Task distribution, AMQP routing, dead-letter     │
  │ (Point-to-Point)     │ Smart broker / Dumb consumer │ retry queues, and command processing.            │
  └──────────────────────┴──────────────────────────────┴──────────────────────────────────────────────────┘
```

### Modern Spring Boot 3 Declarative HTTP Client (`@HttpExchange`)

Spring 6 introduced **HTTP Interfaces**, providing clean, declarative client code similar to OpenFeign without heavy third-party dependencies:

```java
// 1. Declarative Interface:
public interface UserClient {
    @GetExchange("/api/v1/users/{id}")
    UserDTO getUserById(@PathVariable("id") Long id);
}

// 2. Client Bean Configuration:
@Configuration
public class ClientConfig {
    @Bean
    public UserClient userClient(RestClient.Builder builder) {
        RestClient restClient = builder.baseUrl("http://user-service").build();
        HttpServiceProxyFactory factory = HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(restClient))
            .build();
        return factory.createClient(UserClient.class);
    }
}
```

## 🔴 Senior Level

### Parallel API Composition with Virtual Threads / CompletableFuture

When a user opens a dashboard requiring data from 3 separate microservices, executing synchronous calls sequentially ($100\text{ms} + 150\text{ms} + 200\text{ms} = 450\text{ms}$) creates severe latency. Senior architects execute parallel composition:

```java
@RestController
@RequiredArgsConstructor
public class UserDashboardController {

    private final UserClient userClient;
    private final OrderClient orderClient;
    private final NotificationClient notificationClient;

    @GetMapping("/api/v1/dashboard/{userId}")
    public DashboardDTO getDashboard(@PathVariable Long userId) {
        // Parallel non-blocking execution across services:
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var userFuture = executor.submit(() -> userClient.getUserById(userId));
            var ordersFuture = executor.submit(() -> orderClient.getRecentOrders(userId));
            var notifsFuture = executor.submit(() -> notificationClient.getUnread(userId));

            // Latency = Max(User, Orders, Notifications) ~ 200ms (55% Latency Reduction!):
            return new DashboardDTO(userFuture.get(), ordersFuture.get(), notifsFuture.get());
        } catch (Exception e) {
            throw new ResponseStatusException(HttpStatus.INTERNAL_SERVER_ERROR, "Failed to aggregate dashboard", e);
        }
    }
}
```

### The Architectural Decision Framework

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ 🟢 WHEN TO USE SYNCHRONOUS (gRPC/REST)   │ 📬 WHEN TO USE ASYNCHRONOUS (KAFKA/RABBITMQ)     │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Real-time user queries (`SELECT`).     │ • State-changing business workflows (`INSERT`).  │
  │ • Operations where caller cannot proceed │ • High-traffic data replication and syncing.     │
  │   without an immediate response          │ • Background notifications (Email, SMS, Push).   │
  │   (e.g. Real-time Payment Authorization).│ • Systems requiring resilience against downstream│
  │ • Simple CRUD read-aggregations.         │   outages (Broker buffers messages safely).      │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Synchronous:** Caller waits for response (HTTP/REST, gRPC); simple, but vulnerable to cascading latency and outages.
- **Asynchronous:** Producer publishes to broker (Kafka, RabbitMQ) and disconnects; fault-tolerant and decoupled.
- **gRPC:** Preferred protocol for internal synchronous microservice RPC due to HTTP/2 binary efficiency.
- **Spring 6 Client:** Use `RestClient` and `@HttpExchange` HTTP interfaces for modern Spring Boot 3 HTTP clients.
- **Parallel Aggregation:** Use Java 21 Virtual Threads / `CompletableFuture` to parallelize multiple independent backend calls.

**Common Follow-up Questions:**
- *"What is Event-Carried State Transfer?"* → Including all necessary entity state inside the event payload (e.g. `OrderPlacedEvent` with customer name, items, and address) so consumers do not need to make synchronous back-channel HTTP calls to query missing fields.
- *"Why is gRPC faster than REST?"* → gRPC uses compact binary Protobuf serialization (no JSON text parsing overhead), single persistent TCP connection multiplexing via HTTP/2, and strongly typed schema contracts.
- *"How do you prevent cascading failures in synchronous call chains?"* → Apply strict HTTP connection/read timeouts and wrap remote calls with a **Circuit Breaker** (Resilience4j).

**Red Flags (DO NOT Say):**
- ❌ *"Synchronous REST is always better because you don't need to run a message broker like Kafka."* (Synchronous chains create tight coupling and cascading system outages).
- ❌ *"Execute 5 sequential REST calls in a single HTTP request handler."* (Causes cumulative latency; parallelize independent calls).
- ❌ *"Use asynchronous messaging for user password login verification."* (Login authentication requires an immediate synchronous response).
