# What is API Gateway and What Problems Does It Solve?

---

## 🟢 Junior Level

An **API Gateway** is a reverse-proxy server that serves as the **single public entry point** for all external clients (Web browsers, iOS/Android mobile apps, and third-party partner integrations) into an internal microservices cluster:

```
  Airport Customs Analogy:
  • No Gateway: International travelers bypass customs and walk directly into individual city buildings, 
    requiring every single store and house to check passports and inspect baggage (Chaotic and insecure).
  • API Gateway: An international airport terminal. All travelers pass through security, passport control 
    (Auth), and customs (Rate Limiting) before taking connecting flights to their final destinations!
```

```
  [Mobile App / Web Browser]
              │ (Single Public Endpoint: `https://api.company.com`)
              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │                       API GATEWAY                           │
  │ • TLS Termination   • JWT Auth Validation   • Rate Limiting │
  │ • Reverse Routing   • Request Aggregation   • CORS Policy   │
  └───────┬─────────────────────┬─────────────────────┬─────────┘
          │ (gRPC / HTTP)       │ (gRPC / HTTP)       │ (gRPC / HTTP)
          ▼                     ▼                     ▼
   [User Service]        [Order Service]       [Payment Service]
```

## 🟡 Middle Level

### The 5 Problems Solved by an API Gateway

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Problem Without Gateway         │ How the API Gateway Solves It                                                   │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Exposed Internal Topology**│ Hides internal pod IPs, ports, and microservice boundaries behind public paths. │
  │ **2. Chatty Mobile Network**    │ Aggregates 5 backend microservice calls into 1 optimized single client response.│
  │ **3. Duplicate Security Code**  │ Validates JWTs, OAuth2 tokens, and CORS once at the edge, offloading backends.  │
  │ **4. Protocol Mismatches**      │ Translates external HTTP/JSON into high-speed internal **gRPC / Protobuf**.     │
  │ **5. DDoS & Traffic Surges**    │ Enforces global **Rate Limiting** via Redis token buckets before hitting DBs.   │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Spring Cloud Gateway Non-Blocking Reactive Route Definition

```java
@Configuration
public class GatewayRouteConfig {

    @Bean
    public RouteLocator customRouteLocator(RouteLocatorBuilder builder, RedisRateLimiter redisRateLimiter) {
        return builder.routes()
            // Route 1: Users Service with JWT Auth Filter & Rate Limiting:
            .route("user-service", r -> r
                .path("/api/v1/users/**")
                .filters(f -> f
                    .stripPrefix(2)
                    .requestRateLimiter(c -> c.setRateLimiter(redisRateLimiter))
                    .circuitBreaker(c -> c.setName("userBreaker").setFallbackUri("forward:/fallback/users")))
                .uri("lb://user-service"))

            // Route 2: Orders Service:
            .route("order-service", r -> r
                .path("/api/v1/orders/**")
                .filters(f -> f.stripPrefix(2))
                .uri("lb://order-service"))
            .build();
    }
}
```

## 🔴 Senior Level

### The BFF Pattern (Backend for Frontend)

As client variety grows, a single "One-Size-Fits-All" API Gateway becomes a bloated, cross-team deployment bottleneck. Senior architects deploy the **Backend for Frontend (BFF)** pattern:

```
                          ┌───────────────────────────┐
                          │   EXTERNAL CLIENT APPS    │
                          └─────┬───────────────┬─────┘
                                │               │
              Mobile API Traffic│               │Desktop Web Traffic
                                ▼               ▼
                    ┌─────────────────┐   ┌─────────────────┐
                    │   MOBILE BFF    │   │     WEB BFF     │
                    │ (Lightweight,   │   │ (Rich payloads, │
                    │  compressed JSON│   │  full tables,   │
                    │  aggregated)    │   │  paginated)     │
                    └────────┬────────┘   └────────┬────────┘
                             │                     │
                             └──────────┬──────────┘
                                        │ (Internal gRPC / Event Mesh)
                                        ▼
                           [INTERNAL MICROSERVICES]
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Centralized reverse-proxy entry point handling routing, security, and edge policies.
- **Key Responsibilities:** Routing, JWT Authentication, Rate Limiting, SSL Termination, CORS, Protocol Translation.
- **BFF Pattern:** Deploying specialized gateways per frontend type (Mobile BFF vs Web BFF).
- **Non-Blocking Architecture:** Modern gateways (Spring Cloud Gateway, Kong, Envoy) use asynchronous non-blocking event loops (Netty/NGINX) to handle 50,000+ concurrent connections.
- **Security Offload:** Verifies digital signatures on JWTs at the edge, passing clean parsed user headers (`X-User-Id`, `X-User-Roles`) to internal services.

**Common Follow-up Questions:**
- *"How do you prevent the API Gateway from becoming a bottleneck and SPOF?"* → Scale gateway instances horizontally behind an AWS Network Load Balancer (NLB) or Cloudflare Anycast IP, and keep gateway logic strictly stateless (offloading state to Redis).
- *"Should business logic be placed inside an API Gateway?"* → Never; an API Gateway should only handle routing, security, and protocol mediation. Embedding business validation creates a monolithic gateway anti-pattern.
- *"What is the difference between an API Gateway and an Ingress Controller in Kubernetes?"* → A Kubernetes Ingress Controller is a specialized API Gateway (e.g. NGINX or Envoy) that configures routing dynamically based on Kubernetes `Ingress` or `HTTPRoute` YAML resources.

**Red Flags (DO NOT Say):**
- ❌ *"Clients should call internal microservice IP addresses directly over the public internet."* (Severe security vulnerability and high network latency).
- ❌ *"Every microservice should re-implement its own JWT public key signature validation from scratch."* (Validate JWTs once at the API Gateway and pass verified identity headers downstream).
- ❌ *"API Gateways must execute database transactions to save user data."* (Gateways must remain strictly stateless reverse proxies).
