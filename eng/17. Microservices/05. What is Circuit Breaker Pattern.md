# What is Circuit Breaker Pattern?

---

## 🟢 Junior Level

The **Circuit Breaker Pattern** is a resilience design pattern in distributed systems that stops an application from repeatedly attempting to execute an operation that is likely to fail, preventing **Cascading System Outages**:

```
  Home Electrical Fuse Analogy:
  • When a power surge occurs or an appliance short-circuits, the physical electrical fuse trips (OPENS), 
    cutting off the current to protect the house from catching fire.
  • In software, if the Payment Service goes down, the Circuit Breaker trips immediately, preventing 
    thousands of user requests from hanging indefinitely and crashing the Web Gateway!
```

```
  The 3 Circuit Breaker States:
  ┌──────────────┬─────────────────────────────────────────────────────────────────┐
  │ State        │ Behavior                                                        │
  ├──────────────┼─────────────────────────────────────────────────────────────────┤
  │ **CLOSED**   │ 🟢 Normal state: Requests pass through to downstream service.   │
  │ **OPEN**     │ 🔴 Tripped state: Fails fast immediately (returns Fallback).    │
  │ **HALF_OPEN**│ 🟡 Trial state: Lets limited probe requests through to test.    │
  └──────────────┴─────────────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The Problem: Cascading System Failures (Thread Starvation)

Without a Circuit Breaker, a single slow downstream dependency can take down an entire microservices cluster:

```
  1. [Recommendation Service] develops a database bottleneck (Responses take 30 seconds).
  2. [Order Gateway Service] has 200 Tomcat request threads.
  3. 200 concurrent users visit the store ──► All 200 threads become BLOCKED waiting for Recommendations!
  4. Incoming requests for Checkout and Login cannot obtain a free Tomcat thread!
  5. 💥 RESULT: The ENTIRE website crashes because of a minor non-critical recommendation widget!
```

### Production Implementation with Resilience4j & Spring Boot 3

In the modern Java ecosystem, **Resilience4j** is the enterprise standard (completely replacing deprecated Netflix Hystrix):

```yaml
# application.yml: Resilience4j CircuitBreaker configuration
resilience4j:
  circuitbreaker:
    instances:
      recommendationService:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 20             # Evaluate last 20 requests
        minimum-number-of-calls: 10         # Minimum calls before calculating error rate
        failure-rate-threshold: 50          # Trip to OPEN if 50%+ fail
        slow-call-rate-threshold: 50        # Trip to OPEN if 50%+ take > 2 seconds
        slow-call-duration-threshold: 2000ms
        wait-duration-in-open-state: 10000ms# Wait 10s before testing recovery (HALF_OPEN)
        permitted-number-of-calls-in-half-open-state: 5
```

```java
@Service
@Slf4j
public class ProductRecommendationClient {

    @CircuitBreaker(name = "recommendationService", fallbackMethod = "getFallbackRecommendations")
    public List<ProductDTO> fetchRecommendations(Long customerId) {
        // Remote HTTP REST / gRPC call:
        return restTemplate.getForObject("http://recommendation-svc/api/v1/" + customerId, List.class);
    }

    // 🛡️ Fallback method executed immediately when breaker is OPEN or call fails:
    public List<ProductDTO> getFallbackRecommendations(Long customerId, Throwable throwable) {
        log.warn("Recommendation service unavailable (Breaker OPEN). Returning default cached items.", throwable);
        return List.of(new ProductDTO("Popular Item 1"), new ProductDTO("Popular Item 2"));
    }
}
```

## 🔴 Senior Level

### Sliding Window Evaluation: Count-Based vs. Time-Based

Resilience4j tracks metrics using high-performance, ring-buffer sliding windows:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Window Type                  │ Tracking Metric                  │ Best Use Case                                    │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`COUNT_BASED`** (Default)  │ Evaluates the last $N$ calls     │ High-traffic endpoints with steady request rates.│
  │                              │ (e.g. 100 calls ring buffer).    │                                                  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **`TIME_BASED`**             │ Evaluates calls made in the last │ Low/variable traffic endpoints where old errors  │
  │                              │ $T$ seconds (e.g. last 60s).     │ from hours ago should not trip the breaker today.│
  └──────────────────────────────┴──────────────────────────────────────────────────────────────────────────────────┘
```

### Advanced Architectural Strategies: Fallback Graceful Degradation

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Fallback Strategy            │ Production Implementation Pattern                                               │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Cached Snapshot**       │ Return stale data from local Redis cache (ideal for product catalogs/news).     │
  │ **2. Static Default**        │ Return pre-configured generic defaults (e.g. standard product recommendations). │
  │ **3. Asynchronous Buffering**│ Queue the action into local disk/Kafka for delayed processing (e.g. Analytics). │
  │ **4. Fail Fast (HTTP 503)**  │ Return immediate HTTP `503 Service Unavailable` with `Retry-After: 10` header.  │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Resilience pattern that wraps remote calls, tripping OPEN to fail fast and prevent cascading thread starvation.
- **3 States:** `CLOSED` (traffic flows), `OPEN` (fails fast immediately), `HALF_OPEN` (trial probes to test recovery).
- **Modern Standard:** **Resilience4j** is the modern lightweight standard in Spring Boot (Hystrix is dead).
- **Trigger Metrics:** Trips based on `failure-rate-threshold` (e.g. 50% errors) or `slow-call-rate-threshold` (e.g. timeouts).
- **Fallback Rule:** Always provide a graceful fallback method matching the original signature + `Throwable`.

**Common Follow-up Questions:**
- *"What is the difference between Circuit Breaker and Retry pattern?"* → Retry repeatedly resends a request assuming a momentary glitch; Circuit Breaker prevents sending requests entirely when the downstream service is known to be failing.
- *"Why should Circuit Breakers and Retries be combined carefully?"* → If Circuit Breaker wraps a Retry, a single customer action that retries 3 times counts as 3 failures in the sliding window, tripping the breaker prematurely! (Proper order: Circuit Breaker outside, Retry inside).
- *"How do you monitor Circuit Breaker state transitions in production?"* → Resilience4j exports Prometheus metrics (`resilience4j_circuitbreaker_state{state="open"}`) scraped by Grafana and Alertmanager.

**Red Flags (DO NOT Say):**
- ❌ *"Circuit Breakers fix bugs in broken downstream microservices automatically."* (Circuit Breakers only isolate failures and protect the caller from thread starvation).
- ❌ *"Netflix Hystrix is the recommended circuit breaker for new Spring Boot 3 projects."* (Hystrix has been in maintenance mode since 2018; use Resilience4j).
- ❌ *"When a circuit breaker is OPEN, it waits 10 seconds before attempting to send the user's original request."* (It fails fast in 0ms; it only tests trial probes during `HALF_OPEN`).
