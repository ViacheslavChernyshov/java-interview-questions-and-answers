# What is Saga Pattern and When to Use It?

---

## 🟢 Junior Level

The **Saga Pattern** is an architectural design pattern for managing **distributed business transactions** across multiple independent microservices without holding long-lived distributed database locks:

```
  Travel Booking Analogy:
  • You book a vacation package consisting of 3 steps: Flight Ticket ➔ Hotel Room ➔ Rental Car.
  • Step 1: Flight booked successfully ($T_1$).
  • Step 2: Hotel booked successfully ($T_2$).
  • Step 3: Rental car booking fails (Sold out!) ($T_3$ Fails).
  • Rollback: The system cancels the Hotel ($C_2$) and cancels the Flight ($C_1$), 
    issuing a full refund!
```

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ THE SAGA FORMULA:                                                               │
  │ • Forward Execution: $T_1 \longrightarrow T_2 \longrightarrow T_3 \longrightarrow T_n$ │
  │ • Failure at $T_3$:  $T_1 \longrightarrow T_2 \longrightarrow T_3\text{ (Fail)} \longrightarrow C_2 \longrightarrow C_1$ │
  │   ($C_k$ is the Compensating Transaction that semantically undos $T_k$).         │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

### Forward vs. Compensating Transactions Flow

```
  [Order Service]      ──► 1. Create Order (Status: PENDING)
                                │
  [Payment Service]    ──► 2. Charge $100 ($T_1$ Success)
                                │
  [Inventory Service]  ──► 3. Reserve Stock ($T_2$ FAILS: Out of Stock!)
                                │
                                ▼ (TRIGGER COMPENSATING CHAIN)
  [Payment Service]    ──► 4. Refund $100 ($C_1$ Compensating Action)
                                │
  [Order Service]      ──► 5. Update Order (Status: CANCELLED)
```

## 🔴 Senior Level

### The Lack of Isolation (ACID vs. BASE) & Semantic Countermeasures

The most critical challenge in Saga architectures is that **Sagas lack Isolation (the "I" in ACID)**:

```
  Why Sagas Lack Isolation:
  • In Step 1, Payment Service deducts $100 and COMMITS to PostgreSQL immediately.
  • In Step 2, Inventory Service fails.
  • For 500 milliseconds, another service or customer reads the bank balance and sees the deduction 
    BEFORE the compensation refund arrives (Dirty Read / Anomalous State)!
```

#### Senior Architectural Countermeasures:
1. **Semantic Lock (Pending States):** Set aggregate state to `PENDING_RESERVATION` during intermediate steps to prevent other transactions from modifying or treating the entity as finalized.
2. **Idempotent Compensations:** Every compensating transaction ($C_k$) **must be strictly idempotent**. If a network timeout occurs while refunding, retrying the refund must not deduct or credit money twice!
3. **Pessimistic View:** In user-facing UI dashboards, display intermediate states as "Processing" rather than confirmed.

### When to Use vs. When to Avoid Sagas

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ 🟢 PRIME USE CASES FOR SAGAS             │ 🔴 SCENARIOS TO AVOID SAGAS                      │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Cross-service e-commerce checkout.     │ • Single-database CRUD operations (Use ACID).    │
  │ • Multi-step asynchronous bookings.      │ • High-frequency banking ledger balancing where  │
  │ • Workflows involving external REST APIs │   intermediate visibility violates strict laws.  │
  │   (Stripe, Twilio, FedEx) with no 2PC.   │ • Operations where rollback cannot be formulated │
  │ • Systems requiring high availability.   │   (e.g. Sending a printed physical envelope).    │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Sequence of local transactions where each step updates a local DB and triggers the next step; rollbacks are handled via **Compensating Transactions**.
- **Alternative to 2PC:** Replaces blocking Two-Phase Commit with asynchronous, non-blocking eventual consistency.
- **Flavors:** **Choreography** (event-driven pub-sub) vs. **Orchestration** (central coordinator).
- **Isolation Absence:** Sagas lack ACID isolation; use **Semantic Locks** (Pending states) to mitigate dirty reads.
- **Idempotency Mandate:** All forward and compensating actions must be idempotent to survive retries.

**Common Follow-up Questions:**
- *"What happens if a Compensating Transaction itself fails?"* → The Saga coordinator/participant must retry the compensation with exponential backoff; if retries fail permanently, an alert is sent to an SRE Dead Letter Topic for manual human intervention.
- *"Why is 2PC (Two-Phase Commit) deprecated in microservices architectures?"* → 2PC is a synchronous, blocking protocol; if one database or coordinator hangs, locks are held indefinitely across all nodes, destroying cluster availability ($CAP$ theorem).
- *"What frameworks implement the Saga pattern in the Java ecosystem?"* → **Axon Framework**, **Temporal.io**, **Camunda BPM**, and **Eventuate Tram**.

**Red Flags (DO NOT Say):**
- ❌ *"Sagas use database rollbacks (`ROLLBACK;`) to undo changes across all microservices."* (Local transactions are already committed; Sagas execute *compensating business operations*, like refunds).
- ❌ *"Saga provides strict ACID isolation across microservices."* (Sagas are BASE: Basically Available, Soft state, Eventual consistency).
- ❌ *"Use Saga whenever you need to save two entities into the same PostgreSQL database."* (Use standard `@Transactional` for single-database operations).
