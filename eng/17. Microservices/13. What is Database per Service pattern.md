# What is Database per Service Pattern?

---

## 🟢 Junior Level

The **Database per Service** pattern is a foundational architectural rule in microservices stating that **every microservice must own and encapsulate its own private database**. 

Under no circumstances is an outside microservice permitted to connect directly to another service's database, query its tables, or execute cross-service SQL queries:

```
  [Order Service] ──► (Private Orders DB: PostgreSQL)
         │
         │ (Communication ONLY via REST / gRPC / Kafka)
         ▼
  [User Service]  ──► (Private Users DB: PostgreSQL)
```

```
  Apartment Kitchens Analogy:
  • Monolithic Shared DB: A communal kitchen in a hostel. If one resident leaves the stove burning or locks 
    the refrigerator door, nobody else in the building can eat.
  • Database per Service: Private individual apartments where each tenant has their own private kitchen. 
    You cannot open your neighbor's fridge; if you need milk, you must knock on their door and ask (API request)!
```

```
  Core Benefits:
  1. 🔓 Loose Coupling: Teams can alter database schemas (`ALTER TABLE`) without coordinating with 10 other teams.
  2. 🛡️ Fault Isolation: A database crash in Product Catalog does not bring down Order Checkout or Auth.
  3. 🚀 Polyglot Persistence: Each microservice picks the optimal database engine for its workload.
```

### How to Query Data Without SQL `JOIN`s

Because relational `JOIN`s across independent databases are physically impossible, distributed architectures use three proven communication patterns:

```
  1. API Composition (Gateway / BFF Aggregation):
     • Client requests `GET /orders/1042`.
     • API Gateway calls `Order Service` for order details and `User Service` for customer name, 
       merging the two JSON payloads before returning to the frontend.

  2. Event-Driven Data Replication (Kafka Projections):
     • When a user updates their shipping address, `User Service` emits `UserAddressUpdatedEvent`.
     • `Order Service` consumes the event and updates its local denormalized `customer_address` column.

  3. CQRS (Command Query Responsibility Segregation):
     • Multiple services publish state change events to Kafka.
     • A dedicated **Read-Model Service** aggregates events and populates an **Elasticsearch** or 
       **ClickHouse** cluster optimized for complex multi-table search queries and dashboards.
```

## 🔴 Senior Level

### Polyglot Persistence in Enterprise Microservices

Decoupling databases allows architects to choose the exact right storage paradigm for each domain:

```
  ┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────────────────────────┐
  │ Microservice Domain          │ Storage Technology           │ Architectural Rationale                          │
  ├──────────────────────────────┼──────────────────────────────┼──────────────────────────────────────────────────┤
  │ **User & Billing Service**   │ **PostgreSQL** (Relational)  │ Strict ACID transactions, foreign keys, audits.  │
  │ **Product Catalog**          │ **MongoDB** (Document)       │ Flexible schemas for diverse product categories. │
  │ **Shopping Cart & Sessions** │ **Redis Cluster** (Key-Value)│ Sub-millisecond in-memory lookups, native TTLs.  │
  │ **Full-Text Product Search** │ **Elasticsearch / OpenSearch**│ Fuzzy matching, faceted search, typo-tolerance.  │
  │ **Fraud & Social Graph**     │ **Neo4j** (Graph Database)   │ High-speed multi-hop relational graph traversals.│
  │ **Real-Time Analytics**      │ **ClickHouse** (Columnar)    │ High-throughput append-only aggregations.        │
  └──────────────────────────────┴──────────────────────────────────────────────────────────────────────────────────┘
```

### The Inevitable Architectural Consequences

Adopting Database per Service requires the implementation of several supporting patterns:
1. **Abandonment of 2PC (Two-Phase Commit):** Synchronous distributed transactions are replaced with the **Saga Pattern** (Choreography/Orchestration with compensating transactions).
2. **Transactional Outbox Pattern:** To guarantee that database writes and Kafka event emissions occur atomically without dual-write race conditions.
3. **Anti-Corruption Layer (ACL):** Translating foreign service payloads into local domain aggregates to prevent external schema leakage.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Every microservice owns its private database; direct database access from other services is strictly forbidden.
- **Pillars:** Enables autonomous schema migrations, fault isolation, and polyglot persistence.
- **Querying Without Joins:** Solved via **API Composition**, **Kafka Event Replication**, and **CQRS Read-Models**.
- **Polyglot Storage:** Pick the right tool for the job (Postgres for ACID, Redis for cache, Elasticsearch for search).
- **Required Supporting Patterns:** **Saga Pattern** (distributed consistency) and **Transactional Outbox** (dual-write prevention).

**Common Follow-up Questions:**
- *"Is Schema per Service an acceptable stepping stone toward Database per Service?"* → Yes; starting with separate schemas on a shared PostgreSQL instance keeps hosting costs low while strictly enforcing table separation before splitting into separate RDS instances later.
- *"How do you handle data consistency when a customer deletes their account?"* → `User Service` publishes `UserDeletedEvent`; downstream services consume the event and anonymize/archive their local private customer data asynchronously.
- *"What is the main downside of Database per Service?"* → High operational complexity, loss of instant SQL `JOIN`s, eventual consistency delays, and overhead of managing multiple database servers.

**Red Flags (DO NOT Say):**
- ❌ *"It is fine for Service A to read directly from Service B's database as long as it uses a read-only SQL connection."* (Violates encapsulation; schema changes in Service B will silently break Service A).
- ❌ *"Just execute cross-database SQL JOINs if both databases are on the same PostgreSQL host."* (Creates hidden runtime coupling).
- ❌ *"Database per Service is mandatory for tiny prototypes with only 1 developer."* (A monolithic single database is often faster for early-stage MVP discovery).
