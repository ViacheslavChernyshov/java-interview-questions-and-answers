# How to Refactor God Object?

---

## 🟢 Junior Level

A **God Object** (also known as **The Blob Anti-Pattern**) is a monolithic class that knows too much, does too much, and accumulates dozens of unrelated responsibilities (e.g. 50+ fields, 3,000+ lines of code, and 80 methods):

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ ❌ THE GOD OBJECT (THE BLOB):                                                   │
  │ `AppManager.java` (3,500 lines) handles:                                        │
  │ • User authentication & token creation                                          │
  │ • Direct JDBC SQL queries & connection pooling                                  │
  │ • SendGrid email & Twilio SMS dispatch                                          │
  │ • Payment gateway charging & currency conversion                                │
  │ • PDF report generation & CSV exports                                           │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```
  Broken Windows Theory:
  • No developer creates a 3,500-line God Object on Day 1.
  • It starts as a clean 100-line service. Then developers say: *"It's faster to just add one more 
    helper method here than create a new file."* Repeated 50 times over 3 years, a monster is born!
```

---

## 🟡 Middle Level

### The 5-Step Safe Refactoring Protocol (Zero-Downtime Migration)

Senior engineers **never** perform a "Big Bang" rewrite of a God Object. Instead, they apply Martin Fowler's incremental refactoring recipe:

```
  Step 1: Characterization Tests  ──► Write regression safety net (assert existing behavior).
  Step 2: Group by Cohesion (LCOM)──► Cluster methods and fields into domain buckets.
  Step 3: Extract Role Interfaces ──► Create focused capability interfaces.
  Step 4: Extract Classes & Facade──► Convert God Object into a delegating Facade.
  Step 5: Migrate Callers & Delete──► Gradually redirect callers to new services; delete facade.
```

```
                                  ┌───────────────────────────┐
                                  │      LEGACY CALLERS       │
                                  └─────────────┬─────────────┘
                                                │ (Calling legacy methods)
                                                ▼
                               ┌─────────────────────────────────┐
                               │   LEGACY GOD OBJECT (FACADE)    │
                               │   (Delegates work to new svcs)  │
                               └───────┬───────────────┬─────────┘
                                       │               │
                        ┌──────────────┴──────┐ ┌──────┴──────────────┐
                        ▼                     ▼ ▼                     ▼
              ┌───────────────────┐ ┌───────────────────┐ ┌───────────────────┐
              │    USER SERVICE   │ │   EMAIL SERVICE   │ │   REPORT SERVICE  │
              │  (Domain Core)    │ │ (Infrastructure)  │ │ (Infrastructure)  │
              └───────────────────┘ └───────────────────┘ └───────────────────┘
```

## 🔴 Senior Level

### Concrete Refactoring Walkthrough

#### Step 1: Write Characterization (Golden Master) Tests
Before touching any production code, write end-to-end tests that lock down the exact inputs and outputs of the God Object methods so any unintended regression is caught instantly.

#### Step 2: Cluster Responsibilities (LCOM Matrix)

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Responsibility Cluster       │ Methods Identified               │ Target Extracted Class                           │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **User Core Domain**         │ `registerUser`, `updateProfile`  │ `UserService`                                    │
  │ **Email Notifications**      │ `sendWelcomeEmail`, `sendReset`  │ `EmailNotificationService`                       │
  │ **Reporting & Exports**      │ `generatePdfReport`, `exportCsv` │ `UserReportExporter`                             │
  │ **Security / Passwords**     │ `hashPassword`, `verifyPassword` │ `PasswordEncoderService`                         │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

#### Step 3 & 4: Extract New Classes & Convert God Object into a Delegating Facade

```java
// 1. New, focused SRP-compliant service:
@Service
@RequiredArgsConstructor
public class EmailNotificationService {
    private final JavaMailSender mailSender;

    public void sendWelcomeEmail(String email, String username) {
        // Clean, isolated email logic
    }
}

// 2. Legacy God Object converted into a temporary Delegating Facade (Non-Breaking!):
@Service
@Deprecated // Signal to team to stop adding new methods here!
@RequiredArgsConstructor
public class LegacyUserManager {

    private final UserService userService;
    private final EmailNotificationService emailService;
    private final UserReportExporter reportExporter;

    // Delegate legacy method calls to the new specialized beans:
    public void sendWelcomeEmail(String email, String username) {
        emailService.sendWelcomeEmail(email, username); // 👈 DELEGATION
    }

    public void registerUser(UserDTO dto) {
        userService.registerUser(dto);
    }
}
```

#### Step 5: Migrate Callers and Decommission
Update client classes one by one to inject `EmailNotificationService` directly. Once all callers are updated, delete `LegacyUserManager.java`!

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A God Object (The Blob) is an anti-pattern class that concentrates excessive responsibilities, fields, and control logic.
- **The Golden Rule:** Never do a "Big Bang" rewrite. Use **Characterization Tests + Delegating Facade** for safe, incremental refactoring.
- **The 5 Steps:** 1. Write tests $\to$ 2. Cluster responsibilities $\to$ 3. Extract interfaces $\to$ 4. Delegate from God Facade $\to$ 5. Delete God Object.
- **Root Cause:** Violating the Single Responsibility Principle (SRP) repeatedly over time.
- **Outcome:** Transforms an unmaintainable 3,500-line monster into 4–5 cohesive, testable services.

**Common Follow-up Questions:**
- *"What is a Characterization Test?"* → A test written against legacy code to document and verify its existing behavior (even quirks or edge cases) prior to refactoring, ensuring zero accidental behavioral changes.
- *"How do you prevent a new God Object from forming in the future?"* → Establish CI/CD automated quality gates in **SonarQube** (e.g. failing builds if a class exceeds 400 lines of code, Cyclomatic Complexity > 15, or LCOM4 > 1).
- *"What is the risk of extracting too many micro-classes during refactoring?"* → Creating anemic 1-line classes increases project navigation overhead. Group methods around cohesive **Domain Bounded Contexts**, not arbitrary 1-method files.

**Red Flags (DO NOT Say):**
- ❌ *"The best way to fix a God Object is to delete it and rewrite everything from scratch over a weekend."* (Massive risk of introducing severe business regressions).
- ❌ *"A God Object is fine if all its methods are marked `synchronized`."* (Synchronization addresses thread safety, not architectural coupling and maintainability).
- ❌ *"Break a God Object into an Entity with 50 getters and setters and put all logic into static utility functions."* (Creates an Anemic Domain Model; encapsulate behavior into domain services).
