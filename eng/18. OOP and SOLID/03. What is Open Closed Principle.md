# What is Open Closed Principle?

---

## 🟢 Junior Level

The **Open/Closed Principle (OCP)** is the second principle of SOLID, stating that:

> **"Software entities (classes, modules, functions) should be OPEN for extension, but CLOSED for modification."**

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ • Open for Extension: You can easily add new behavior to the system.           │
  │ • Closed for Modification: You do NOT have to modify, recompile, or re-test     │
  │   existing, working source code to add that new behavior!                       │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```
  Smartphone USB-C Port Analogy:
  • You can plug in headphones, flash drives, keyboards, or external monitors (Open for Extension).
  • You do NOT have to unscrew the phone's case and solder new internal wires to support a new accessory 
    (Closed for Modification)!
```

```java
// ❌ VIOLATION (Adding a Triangle requires modifying calculateArea()):
public class AreaCalculator {
    public double calculateArea(Object shape) {
        if (shape instanceof Circle c) {
            return Math.PI * c.getRadius() * c.getRadius();
        } else if (shape instanceof Rectangle r) {
            return r.getWidth() * r.getHeight();
        }
        // 💥 Adding Triangle requires modifying this class, risking bugs in Circle/Rectangle!
        throw new IllegalArgumentException("Unknown shape");
    }
}
```

```java
// ✅ OCP COMPLIANT (Polymorphic Abstraction):
public interface Shape {
    double calculateArea();
}

public record Circle(double radius) implements Shape {
    @Override public double calculateArea() { return Math.PI * radius * radius; }
}

public record Rectangle(double width, double height) implements Shape {
    @Override public double calculateArea() { return width * height; }
}

// 🚀 Adding a new shape (Triangle) requires writing a NEW class; zero edits to AreaCalculator!
public record Triangle(double base, double height) implements Shape {
    @Override public double calculateArea() { return 0.5 * base * height; }
}
```

## 🟡 Middle Level

### The Core Mechanism: Strategy Pattern + Dependency Injection

In production Spring Boot backends, OCP is implemented using the **Strategy Pattern** with Spring's automatic map-based dependency injection:

```java
// 1. Common Strategy Interface:
public interface PaymentStrategy {
    PaymentMethod getMethod(); // e.g. CREDIT_CARD, PAYPAL, CRYPTO
    PaymentReceipt process(PaymentRequest request);
}

// 2. Extensible Implementations:
@Component
public class CreditCardPaymentStrategy implements PaymentStrategy {
    @Override public PaymentMethod getMethod() { return PaymentMethod.CREDIT_CARD; }
    @Override public PaymentReceipt process(PaymentRequest req) { /* Stripe API */ }
}

@Component
public class CryptoPaymentStrategy implements PaymentStrategy {
    @Override public PaymentMethod getMethod() { return PaymentMethod.CRYPTO; }
    @Override public PaymentReceipt process(PaymentRequest req) { /* Blockchain */ }
}
```

```java
// 3. OCP-Compliant Service (Closed for modification):
@Service
public class PaymentService {

    private final Map<PaymentMethod, PaymentStrategy> strategies;

    // Spring automatically discovers and maps all Strategy beans at startup!
    public PaymentService(List<PaymentStrategy> strategyList) {
        this.strategies = strategyList.stream()
            .collect(Collectors.toMap(PaymentStrategy::getMethod, Function.identity()));
    }

    public PaymentReceipt executePayment(PaymentRequest request) {
        PaymentStrategy strategy = strategies.get(request.paymentMethod());
        if (strategy == null) {
            throw new UnsupportedOperationException("Unsupported payment: " + request.paymentMethod());
        }
        return strategy.process(request); // Zero if/else or switch statements!
    }
}
```

## 🔴 Senior Level

### Design Patterns That Enable OCP

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Design Pattern               │ How It Satisfies the Open/Closed Principle                                      │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Strategy Pattern**         │ Encapsulates swappable algorithms behind an interface.                          │
  │ **Decorator Pattern**        │ Adds dynamic responsibilities to objects without modifying base class code.    │
  │ **Template Method Pattern**  │ Fixes the algorithm skeleton while allowing subclasses to override steps.      │
  │ **Observer / Event Pub-Sub** │ Producers emit domain events without knowing what downstream listeners exist.   │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### The Java 21 Sealed Hierarchy Exception

> [!NOTE]
> In functional programming and modern Java 21, developers sometimes intentionally choose **Closed Exhaustive Hierarchies** over OCP when the set of domain variants is fixed and known (e.g. Algebraic Data Types / AST nodes):

```java
// Intentionally closed hierarchy (Exhaustive Pattern Matching):
public sealed interface OrderStatus permits Pending, Shipped, Delivered, Cancelled {}

public String getStatusBadge(OrderStatus status) {
    return switch (status) {
        case Pending p   -> "badge-yellow";
        case Shipped s   -> "badge-blue";
        case Delivered d -> "badge-green";
        case Cancelled c -> "badge-red";
        // Compiler guarantees 100% exhaustiveness; no default needed!
    };
}
```
**Senior Insight:** Use **OCP (Polymorphism)** when the set of behaviors is unbounded and extensible (plugins, payment processors, tax rules); use **Sealed Hierarchies** when data variants are strictly closed and exhaustive.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Classes should be open for extension (adding new features) but closed for modification (not touching existing code).
- **Core Mechanism:** Polymorphism, Interfaces, and Abstraction.
- **Code Smell:** Long `if-else if-else` or `switch` statements checking `instanceof` or type strings.
- **Primary Pattern:** **Strategy Pattern** combined with Spring `List<Strategy>` or `Map<Type, Strategy>` injection.
- **Benefits:** Eliminates regression bugs; new features are added via new classes without re-testing old ones.

**Common Follow-up Questions:**
- *"How does OCP reduce regression testing overhead?"* → When you add a new class, existing classes are untouched, guaranteeing that existing unit tests continue to pass without risk of newly introduced regression defects.
- *"Can a system be 100% closed to all possible modifications?"* → No; 100% closure against every theoretical future change is impossible. Senior architects design extension points around anticipated vectors of change (e.g. payment methods, export formats, notification channels).
- *"How does the Decorator pattern support OCP?"* → Decorators wrap existing components (e.g. `BufferedInputStream` wrapping `FileInputStream`), adding functionality (buffering, compression, encryption) without modifying the original stream class.

**Red Flags (DO NOT Say):**
- ❌ *"OCP means you can never edit an existing class even if you find a critical security bug in it."* (OCP applies to adding *new features*, not fixing bugs or refactoring).
- ❌ *"Whenever you need a new feature, use inheritance to subclass everything."* (Inheritance creates tight coupling; prefer composition and interfaces).
- ❌ *"A 10-case switch statement over string payment types is completely fine and scalable."* (Violates OCP; adding a payment type requires modifying the switch).
