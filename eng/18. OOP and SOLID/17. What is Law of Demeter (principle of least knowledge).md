# What is Law of Demeter (Principle of Least Knowledge)?

---

## 🟢 Junior Level

The **Law of Demeter (LoD)**, also known as the **Principle of Least Knowledge**, is a software design guideline that states:

> **"Talk only to your immediate friends, never to strangers."**

An object should only invoke methods on its direct collaborators. It should never navigate through an object to reach internal sub-objects (avoiding the **"Train Wreck" Code Smell**):

```
  Paperboy & Wallet Analogy:
  • Violating LoD: When the paperboy collects money, he reaches into your pocket, pulls out your wallet, 
    opens the zipper, extracts $5, and puts the wallet back into your pants!
  • Following LoD: The paperboy tells you: "Payment is $5." You open your wallet, take out $5, 
    and hand it to him. The paperboy knows nothing about the internal structure of your pockets or wallet!
```

```java
// ❌ "TRAIN WRECK" CODE SMELL (Violates Law of Demeter):
// Navigating 4 levels deep into internal object graphs!
String city = order.getCustomer().getProfile().getAddress().getCity();

// ✅ LAW OF DEMETER COMPLIANT (Delegation):
// Order delegates internally; caller talks only to its direct friend `order`!
String city = order.getDeliveryCity();
```

## 🟡 Middle Level

### The 4 Formal Rules of Method Invocation

A method `m` of class `A` may **only** call methods belonging to:

```
  ┌───┬─────────────────────────────────────────────────────────────────┬─────────────────────────────┐
  │ # │ Permitted Method Target                                         │ Java Syntax Example         │
  ├───┼─────────────────────────────────────────────────────────────────┼─────────────────────────────┤
  │ 1 │ The object `A` itself (`this`).                                 │ `this.calculateSubtotal()`  │
  │ 2 │ Any object passed as an argument to `m`.                        │ `param.process()`           │
  │ 3 │ Any object instantiated / created within `m`.                   │ `new Helper().format()`     │
  │ 4 │ Any direct instance field (collaborator) of `A`.                │ `this.repository.save()`    │
  └───┴─────────────────────────────────────────────────────────────────┴─────────────────────────────┘
  ❌ FORBIDDEN: Calling methods on objects returned by other methods (`a.getB().getC().doAction()`).
```

### The "Tell, Don't Ask" Principle

The Law of Demeter is closely tied to the **"Tell, Don't Ask"** design philosophy:

```java
// ❌ "ASK" ANTI-PATTERN (Violates LoD & Encapsulation):
// Caller interrogates wallet internals to make a business decision:
if (customer.getWallet().getBalance().compareTo(price) >= 0) {
    customer.getWallet().deduct(price);
}

// ✅ "TELL, DON'T ASK" (Adheres to LoD):
// Caller instructs customer to purchase; Customer manages internal wallet encapsulation!
customer.debit(price);
```

## 🔴 Senior Level

### When is Method Chaining NOT a Violation?

A common misconception is that *every* line containing multiple dots (`.`) violates the Law of Demeter. Senior engineers distinguish between structural navigation and functional fluent pipelines:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Chaining Paradigm            │ Example                          │ LoD Evaluation                                   │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Train Wreck (Domain Hop)** │ `order.getUser().getCar().start()`│ 🔴 **Violation**: Peeking into unrelated domain  │
  │                              │                                  │ internal structures and private dependencies.    │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Fluent Builder Pattern**   │ `User.builder().name("A").build()`│ 🟢 **Compliant**: Fluent DSL operating on a single│
  │                              │                                  │ builder instance to construct an aggregate.      │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Stream API Pipelines**     │ `list.stream().filter().toList()`│ 🟢 **Compliant**: Monadic data transformation    │
  │                              │                                  │ pipeline operating on immutable stream context.  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Data Records / DTOs**      │ `record.customer().address()`    │ 🟢 **Compliant**: Pure data carriers without     │
  │                              │                                  │ business behavior or encapsulation guarantees.   │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Architectural Cost of Over-Delegation: "Middleman" Code Smell

Blindly enforcing LoD across every single class can produce the **Middleman Anti-Pattern**, where classes become bloated with dozens of 1-line forwarding methods:

```java
// ⚠️ MIDDLEMAN CODE SMELL (Bloated forwarding pass-throughs):
public class Order {
    private Customer customer;

    public String getCustomerName() { return customer.getName(); }
    public String getCustomerEmail() { return customer.getEmail(); }
    public String getCustomerPhone() { return customer.getPhone(); }
    public String getCustomerCity() { return customer.getAddress().getCity(); }
    public String getCustomerZip() { return customer.getAddress().getZip(); }
    // ... 20 more pass-through delegators!
}
```
**Senior Balance:** For pure read-only data transfer, return a flat **Java Record DTO** (`OrderDeliveryDTO(orderId, customerName, city, zip)`) rather than writing 20 forwarding methods on domain entities.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Talk only to your immediate friends; do not reach through objects to talk to strangers.
- **Code Smell:** **"Train Wreck"** method chaining (`a.getB().getC().getD().execute()`).
- **Philosophy:** Closely paired with **"Tell, Don't Ask"** (instruct objects to do work rather than inspecting their internals).
- **Legitimate Chaining:** Builders (`UserBuilder`), Fluent APIs, Java Stream API, and Method Cascading do NOT violate LoD.
- **Trade-off:** Over-applying LoD can create the **Middleman** anti-pattern (classes filled with useless 1-line forwarding methods).

**Common Follow-up Questions:**
- *"Why does the 'Train Wreck' pattern cause production bugs?"* → It creates tight coupling to distant object hierarchies (a schema change in `Address` breaks 20 unrelated services) and creates multiple points of failure for `NullPointerException`.
- *"How does Law of Demeter help unit testing?"* → When code adheres to LoD, unit tests only need to mock direct dependencies (`mockOrder`). When code violates LoD, tests must construct complex deeply nested mock chains (`when(order.getCustomer().getAddress()...)`).
- *"Is navigating a JSON / GraphQL response in a frontend client an LoD violation?"* → No; JSON payloads and Java Records are **Data Structures**, not encapsulated Object-Oriented Domain Entities. LoD applies to behaviors and encapsulated domain objects.

**Red Flags (DO NOT Say):**
- ❌ *"Any Java code that has more than one dot (`.`) is an automatic Law of Demeter violation."* (Stream API, String operations, and Builders are completely compliant).
- ❌ *"To fix Demeter violations, make all private fields public so you don't need getters."* (Completely destroys encapsulation).
- ❌ *"The Law of Demeter means classes should never have helper dependencies."* (Classes should interact with their direct dependencies; they just shouldn't navigate *through* them).
