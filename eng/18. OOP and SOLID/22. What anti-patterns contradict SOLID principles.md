# What Anti-Patterns Contradict SOLID Principles?

---

## 🟢 Junior Level

An **Anti-Pattern** is a common software design approach that seems convenient at first glance but leads to severe architectural degradation, bugs, fragility, and maintenance bottlenecks:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ THE STUPID MNEMONIC (THE OPPOSITE OF SOLID):                                    │
  │ • S — Singleton (Overused global mutable state)                                 │
  │ • T — Tight Coupling (Classes hardwired to concrete details)                    │
  │ • U — Untestability (Cannot write fast, isolated unit tests)                    │
  │ • P — Premature Optimization (Sacrificing clean design for theoretical speed)   │
  │ • I — Indescriptive Naming (`AppManager`, `CommonHelper`, `DataProcessor`)      │
  │ • D — Duplication (Violating DRY and creating shotgun surgery)                  │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

### The Comprehensive SOLID vs. Anti-Pattern Taxonomy

```
  ┌───────────┬──────────────────────────────────┬─────────────────────────────────────────────────┐

  ├───────────┼──────────────────────────────────┼─────────────────────────────────────────────────┤
  │ **SRP**   │ **1. God Object (The Blob)**     │ 3,500-line class bundling SQL, HTTP, and math.  │
  │           │ **2. Feature Envy**              │ Method in Class A reaches into Class B's data.  │
  │           │ **3. Shotgun Surgery**           │ 1 business change forces edits across 15 files. │
```

## 🔴 Senior Level

### Deep-Dive on Subtle Architectural Anti-Patterns

#### 1. Shotgun Surgery vs. Divergent Change (The SRP Dualities)

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Divergent Change (1 Class, Many Changes) │ Shotgun Surgery (Many Classes, 1 Change)         │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • You make changes to 1 class for 5      │ • Making 1 single business change (e.g. adding a │
  │   different business reasons (Violates   │   tax rule) forces small edits across 15 classes!│
  │   **Cohesion**).                         │ • Violates **Coupling & SRP**.                   │
  │ • Solution: **Extract Class**.           │ • Solution: **Move Method / Inline into Domain**.│
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

#### 2. Anemic Domain Model vs. Rich Domain Model (Martin Fowler)

In an **Anemic Domain Model**, entity classes are reduced to dumb bags of getters and setters, while external procedural services manipulate their private fields directly:

```java
// ❌ ANEMIC DOMAIN MODEL (Procedural code masquerading as OOP):
public class BankAccount {
    private BigDecimal balance;
    public BigDecimal getBalance() { return balance; }
    public void setBalance(BigDecimal balance) { this.balance = balance; }
}

@Service
public class BankAccountService {
    public void withdraw(BankAccount acc, BigDecimal amount) {
        // Business invariants leaked outside the entity:
        if (acc.getBalance().compareTo(amount) >= 0) {
            acc.setBalance(acc.getBalance().subtract(amount)); // Encapsulation destroyed!
        }
    }
}
```

```java
// 🟢 RICH DOMAIN MODEL (OOP Encapsulation & High Cohesion):
public class BankAccount {
    private BigDecimal balance;

    // Encapsulates state mutation and business invariants:
    public void withdraw(BigDecimal amount) {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Withdrawal amount must be positive");
        }
        if (this.balance.compareTo(amount) < 0) {
            throw new InsufficientFundsException("Insufficient account balance");
        }
        this.balance = this.balance.subtract(amount);
    }
}
```

#### 3. Circular Dependencies ($A \to B \to A$)

When two Spring services inject each other, it violates DIP and prevents Spring Boot from determining the bean creation order:

```java
// ❌ CIRCULAR DEPENDENCY HAZARD:
@Service public class OrderService {
    private final PaymentService paymentService; // OrderService depends on PaymentService
}

@Service public class PaymentService {
    private final OrderService orderService; // 💥 PaymentService depends on OrderService!
}
```
**Senior Fix:** Break the cycle by extracting a shared domain interface, introducing an **Event Publisher (ApplicationEventPublisher)**, or creating a third coordinating service (`OrderCheckoutCoordinator`).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **STUPID vs SOLID:** Singleton (overuse), Tight Coupling, Untestability, Premature Optimization, Indescriptive Naming, Duplication.
- **Top Anti-Patterns:**
  - **God Object:** Class that does everything (SRP).
  - **Shotgun Surgery:** 1 change forces edits across 15 files (SRP/Coupling).
  - **Refused Bequest:** Subclass throws `UnsupportedOperationException` (LSP).
  - **Fat Interface:** Monolithic interface with unused methods (ISP).
  - **Hardcoded `new`:** Inability to mock or swap dependencies (DIP).
- **Anemic Domain Model:** Entities with only getters/setters and zero encapsulated behavior.
- **Circular Dependencies:** Break $A \leftrightarrow B$ cycles via Domain Events or coordinating mediator services.

**Common Follow-up Questions:**
- *"Why is the Singleton pattern often considered an anti-pattern?"* → When overused, Singletons introduce global mutable state, tightly couple classes to a concrete implementation, prevent dependency injection, and make parallel unit testing flaky due to shared cross-test state.
- *"How does Feature Envy violate OOP principles?"* → Feature Envy occurs when a method in Class A spends most of its time reading and manipulating fields in Class B. It indicates that the method is in the wrong place and should be moved inside Class B (high cohesion).
- *"How do you fix Shotgun Surgery?"* → Use **Move Method** and **Move Field** to consolidate related logic that was scattered across 15 classes into a single cohesive domain component.

**Red Flags (DO NOT Say):**
- ❌ *"God Objects are acceptable if the team has strong code documentation."* (Documentation does not fix runtime fragility and merge conflicts).
- ❌ *"An Anemic Domain Model with 100% getters/setters is the best way to write Java backends."* (It is procedural programming disguised as OOP; prefer rich domain entities).
- ❌ *"Enable `@Lazy` on circular dependencies instead of refactoring the design."* (`@Lazy` is a temporary hack that masks a fundamental architectural design flaw).
