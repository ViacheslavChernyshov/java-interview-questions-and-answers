# What is Interface Segregation Principle?

---

## 🟢 Junior Level

The **Interface Segregation Principle (ISP)** is the fourth principle of SOLID, formulated by Robert C. Martin (Uncle Bob):

> **"Clients should not be forced to depend upon interfaces that they do not use."**

In plain English: It is far better to create **many small, highly focused, capability-based interfaces** than a single giant, bloated "Fat Interface" that forces implementers to write empty dummy methods or throw `UnsupportedOperationException`:

```
  Swiss Army Knife vs. Specific Kitchen Tools Analogy:
  • Fat Interface: Handing a diner a heavy 50-tool Swiss Army Knife with saws, screwdrivers, and pliers 
    when all they asked for was a spoon to eat soup.
  • Segregated Interfaces: Giving the diner a Spoon (`Spoonable`), a Chef a Knife (`Cuttable`), 
    and a Carpenter a Saw (`Sawable`). Each person receives only the exact tool they need!
```

```java
// ❌ FAT INTERFACE VIOLATION (Forces implementations to carry baggage):
public interface MultiFunctionDevice {
    void print(Document doc);
    void scan(Document doc);
    void fax(Document doc);
}

public class BasicOfficePrinter implements MultiFunctionDevice {
    @Override public void print(Document doc) { System.out.println("Printing..."); }

    // 💥 Forced to implement methods the hardware physically does NOT possess!
    @Override public void scan(Document doc) { throw new UnsupportedOperationException("No scanner!"); }
    @Override public void fax(Document doc) { throw new UnsupportedOperationException("No fax!"); }
}
```

```java
// ✅ ISP COMPLIANT (Role / Capability Interfaces):
public interface Printable { void print(Document doc); }
public interface Scannable { void scan(Document doc); }
public interface Faxable   { void fax(Document doc); }

// Simple hardware implements only what it supports:
public class BasicOfficePrinter implements Printable {
    @Override public void print(Document doc) { System.out.println("Printing..."); }
}

// Advanced all-in-one hardware implements multiple interfaces:
public class EnterpriseCopier implements Printable, Scannable, Faxable {
    @Override public void print(Document doc) { /* Print */ }
    @Override public void scan(Document doc)  { /* Scan */ }
    @Override public void fax(Document doc)   { /* Fax */ }
}
```

## 🟡 Middle Level

### Role Interfaces vs. Header Interfaces

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Interface Style              │ Architecture Paradigm            │ Evaluation & Impact                              │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Header Interface**         │ A 1-to-1 mirror of a service     │ 🔴 **Anti-Pattern**: 30-method interface that    │
  │ (e.g. `IOrderService`)       │ class (`IUserService`).          │ forces test mocks and callers to depend on all 30│
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Role Interface**           │ Small, cohesive, capability-based│ 🏆 **Gold Standard**: Client consumes only the   │
  │ (e.g. `OrderFinder`)         │ interface (`AutoCloseable`).     │ exact 1–2 methods it needs (`OrderCanceller`).   │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The JDK: A Masterclass in ISP Design

The Java Standard Library is renowned for its elegant application of the Interface Segregation Principle:

```java
// The JDK defines single-purpose, highly composable capability interfaces:
public interface AutoCloseable { void close() throws Exception; }
public interface Comparable<T> { int compareTo(T o); }
public interface Runnable      { void run(); }
public interface Flushable     { void flush() throws IOException; }
public interface Readable      { int read(CharBuffer cb) throws IOException; }
```
Because these interfaces are segregated into single responsibilities, any class can implement `AutoCloseable` to participate in Java's `try-with-resources` without being forced to implement unrelated stream or file methods!

## 🔴 Senior Level

### ISP in Spring Boot Controller & Service Layer Architecture

In enterprise microservices, client components often need only a small slice of an aggregate service:

```java
// Segregated Role Interfaces:
public interface OrderReader {
    Optional<OrderDTO> findById(Long orderId);
    List<OrderDTO> findByCustomerId(Long customerId);
}

public interface OrderCanceller {
    void cancelOrder(Long orderId, String reason);
}

public interface OrderCreator {
    OrderConfirmationDTO createOrder(OrderRequestDTO request);
}
```

```java
// 1. Single cohesive implementation:
@Service
public class OrderService implements OrderReader, OrderCanceller, OrderCreator {
    // Implements all methods
}

// 2. Read-Only Controller depends ONLY on OrderReader:
@RestController
@RequiredArgsConstructor
public class OrderQueryController {

    private final OrderReader orderReader; // 🛡️ Cannot accidentally invoke mutate/cancel methods!

    @GetMapping("/api/v1/orders/{id}")
    public ResponseEntity<OrderDTO> getOrder(@PathVariable Long id) {
        return orderReader.findById(id).map(ResponseEntity::ok).orElseGet(() -> ResponseEntity.notFound().build());
    }
}
```

```
  Why This Matters to Senior Architects:
  1. **Security & Principle of Least Privilege:** `OrderQueryController` has zero access to `cancelOrder()` or `createOrder()`.
  2. **Mocking Speed:** Unit tests for `OrderQueryController` only need to mock 2 reader methods instead of 25 order methods.
  3. **Refactoring Safety:** Modifying the order creation workflow does not cause recompilation or test invalidation in query controllers!
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Clients should not be forced to depend on methods they do not use.
- **Core Rule:** Prefer many small, specific **Role Interfaces** over one large general-purpose "Fat Interface".
- **LSP Connection:** Violating ISP (forcing classes to implement unwanted methods) almost always leads to an LSP violation (`UnsupportedOperationException`).
- **JDK Role Models:** `AutoCloseable`, `Comparable`, `Runnable`, `Flushable`.
- **Testing Benefit:** Small interfaces make unit test mocking dramatically simpler and faster.

**Common Follow-up Questions:**
- *"How many methods should an ideal interface have?"* → There is no hard number, but adhering to the **Single Responsibility Principle** means an interface should represent a single cohesive capability (often 1 to 4 methods). Single-method interfaces can also be annotated as `@FunctionalInterface` (e.g. `Runnable`, `Callable`).
- *"What is the difference between SRP and ISP?"* → **SRP** is about the *cohesion of a class* (a class should have only one reason to change); **ISP** is about the *granularity of interfaces for clients* (an interface should not force clients to know about methods they don't call).
- *"Does creating many small interfaces violate clean architecture?"* → No; interfaces are cheap in Java, and composing multiple interfaces (`implements Printable, Scannable`) provides maximum flexibility without coupling.

**Red Flags (DO NOT Say):**
- ❌ *"Create a single `IGeneralService` interface with 50 methods for all controller operations."* (Textbook Fat Interface anti-pattern).
- ❌ *"If an interface has methods you don't need, just implement them with empty braces `{}`."* (Violates ISP and leads to silent bugs).
- ❌ *"ISP only applies to user interfaces (UI), not backend Java code."* (ISP is a fundamental object-oriented code design principle).
