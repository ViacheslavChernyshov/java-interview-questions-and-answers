# What is Liskov Substitution Principle?

---

## 🟢 Junior Level

The **Liskov Substitution Principle (LSP)** is the third principle of SOLID, formulated by computer scientist Barbara Liskov in 1987:

> **"Subtypes must be substitutable for their base types without altering the correctness of the program."**

In plain English: If class `B` is a subclass of class `A`, you should be able to pass an object of `B` anywhere `A` is expected, and the application must continue to work correctly **without unexpected runtime exceptions, broken assumptions, or type checks**:

```
  Standard Electrical Outlet Analogy:
  • An electrical wall socket expects any device with a standard 2-prong plug (Base Type).
  • If you plug in a lamp, laptop charger, or fan (Subtypes), they all work seamlessly.
  • If a manufacturer sells a "smart plug" that blows the fuse or throws an explosion when plugged in, 
    it violates the contract (LSP Violation)!
```

```java
// ❌ LSP VIOLATION (Ostrich violates the contract of Bird):
public class Bird {
    public void fly() { System.out.println("Flying high in the sky!"); }
}

public class Ostrich extends Bird {
    @Override
    public void fly() {
        // 💥 Ostrich cannot fly, throwing an unexpected runtime exception!
        throw new UnsupportedOperationException("Ostriches cannot fly!");
    }
}

// Caller code crashes when iterating over a list of birds:
public void migrateBirds(List<Bird> birds) {
    for (Bird b : birds) {
        b.fly(); // 💥 CRASHES with UnsupportedOperationException when an Ostrich is present!
    }
}
```

```java
// ✅ LSP COMPLIANT (Segregated Hierarchy based on actual capabilities):
public interface Bird { void eat(); }
public interface FlyingBird extends Bird { void fly(); }

public class Sparrow implements FlyingBird {
    @Override public void eat() { System.out.println("Eating seeds"); }
    @Override public void fly() { System.out.println("Flying!"); }
}

public class Ostrich implements Bird {
    @Override public void eat() { System.out.println("Eating plants"); }
    // Does NOT implement FlyingBird; zero invalid methods!
}
```

## 🟡 Middle Level

### The 4 Formal Rules of Design by Contract (LSP Invariants)

LSP is strictly defined through Bertrand Meyer's **Design by Contract** rules:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Contract Rule                │ Subtype Requirement & Violation Example                                         │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Preconditions**         │ **Cannot be strengthened** in a subtype. (If base accepts numbers $-100 \dots +100$,│
  │ (Input requirements)         │ a subclass cannot demand only positive numbers $> 0$).                          │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. Postconditions**        │ **Cannot be weakened** in a subtype. (If base guarantees returning a non-null    │
  │ (Output promises)            │ object, subclass cannot return `null`).                                         │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. Class Invariants**      │ **Must be preserved** by the subtype. (Base class state guarantees must never   │
  │ (Internal consistency)       │ be corrupted by child method overrides).                                        │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **4. Exception Rule**        │ Subclass methods **cannot throw new or broader checked exceptions** than those │
  │ (Failure modes)              │ declared by the base method.                                                    │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### The Classic Mathematical Trap: The Square / Rectangle Paradox

In real-world mathematics, *"A Square is a Rectangle"*. However, in Object-Oriented Design, modeling a Square as a subclass of Rectangle **violates LSP**:

```java
// ❌ THE CLASSIC SQUARE / RECTANGLE LSP TRAP:
public class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    public int getArea() { return width * height; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        this.width = width;
        this.height = width; // ⚠️ Enforcing square geometry mutates both dimensions!
    }

    @Override
    public void setHeight(int height) {
        this.width = height;
        this.height = height;
    }
}
```

```java
// 💥 THE CALLER'S ASSUMPTION IS BROKEN:
public void verifyRectangleArea(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);

    // Caller expects 5 * 10 = 50.
    // If r is a Square, r.setHeight(10) sets width to 10 ➔ Area is 100!
    assert r.getArea() == 50 : "LSP Violation! Expected 50, but got " + r.getArea();
}
```

#### Senior Solution:
Replace inheritance with **Composition** or a shared immutable `Shape` interface:

```java
// ✅ Clean, immutable solution:
public interface Shape { int getArea(); }

public record Rectangle(int width, int height) implements Shape {
    @Override public int getArea() { return width * height; }
}

public record Square(int side) implements Shape {
    @Override public int getArea() { return side * side; }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** Subtypes must be substitutable for their base types without breaking client expectations.
- **Contract Rules:** Preconditions cannot be strengthened; postconditions cannot be weakened; invariants must be preserved.
- **Code Smells:** `UnsupportedOperationException`, empty no-op method overrides, or `if (obj instanceof Subclass)` checks.
- **Rectangle / Square Trap:** Proves that real-world "IS-A" relationships do not automatically map to Object-Oriented inheritance.
- **Remedy:** **Favor Composition over Inheritance** or split broad interfaces into narrow, capability-based interfaces.

**Common Follow-up Questions:**
- *"Why is `instanceof` a symptom of an LSP violation?"* → If client code must check `if (bird instanceof Ostrich)` to avoid calling `fly()`, the subtype is not transparently substitutable, proving an architectural defect in the hierarchy.
- *"How does Java's type system enforce parts of LSP at compile time?"* → Java enforces that overridden methods cannot declare broader checked exceptions, and return types must be covariant (subtypes of the base return type).
- *"Does Java's `Collections.unmodifiableList()` violate LSP?"* → Yes, technically! It implements `List<T>`, but calling `add()` throws `UnsupportedOperationException` at runtime instead of adding an element.

**Red Flags (DO NOT Say):**
- ❌ *"LSP means subclasses can override methods to do whatever they want, including throwing `UnsupportedOperationException`."* (Throwing unexpected exceptions on base methods is the #1 violation of LSP).
- ❌ *"Square should always extend Rectangle because a square is a rectangle in math."* (Behavioral subtyping differs from mathematical classification).
- ❌ *"Fixing LSP violations requires adding `instanceof` checks in all caller methods."* (`instanceof` is a workaround that proves the abstraction is broken).
