# Give an Example of Liskov Substitution Principle Violation

---

## 🟢 Junior Level

A **Liskov Substitution Principle (LSP) Violation** occurs when a subclass cannot fulfill the behavioral promises of its parent class, forcing the subclass to either throw unexpected runtime exceptions, ignore method calls, or corrupt business state:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ ❌ COMMON LSP VIOLATION ARCHETYPES:                                             │
  │ 1. **The "Refused Bequest"**: Subclass throws `UnsupportedOperationException`.  │
  │ 2. **The "Silent State Corruptor"**: Subclass alters unexpected side-effects.   │
  │ 3. **The "Strengthened Precondition"**: Subclass rejects valid base parameters. │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

### Archetype 1: The "Refused Bequest" (Banking Account Example)

```java
// ❌ BASE CLASS (Establishes the contract: Any Account can withdraw funds):
public class BankAccount {
    protected BigDecimal balance = BigDecimal.ZERO;

    public void deposit(BigDecimal amount) {
        this.balance = this.balance.add(amount);
    }

    public void withdraw(BigDecimal amount) {
        if (balance.compareTo(amount) >= 0) {
            this.balance = this.balance.subtract(amount);
        }
    }
}

// ❌ VIOLATION (FixedTermDepositAccount refuses the withdraw bequest!):
public class FixedTermDepositAccount extends BankAccount {
    @Override
    public void withdraw(BigDecimal amount) {
        // 💥 Cannot withdraw before term maturity; breaks base class contract!
        throw new UnsupportedOperationException("Withdrawals locked until maturity date!");
    }
}
```

```java
// 💥 SYSTEM CRASH (Caller cannot safely substitute FixedTermDepositAccount):
public void processMonthlyFees(List<BankAccount> accounts) {
    for (BankAccount account : accounts) {
        account.withdraw(new BigDecimal("10.00")); // 💥 CRASHES ENTIRE BATCH on FixedTerm account!
    }
}
```

## 🟡 Middle Level

### Clean Refactoring: Segregating Capability Interfaces

To fix the banking violation, separate read and write capabilities into distinct interfaces:

```java
// ✅ 1. Read-Only Account Contract:
public interface Account {
    BigDecimal getBalance();
    void deposit(BigDecimal amount);
}

// ✅ 2. Withdrawable Capability Contract:
public interface WithdrawableAccount extends Account {
    void withdraw(BigDecimal amount);
}

// ✅ 3. Standard Checking Account (Withdrawable):
public class CheckingAccount implements WithdrawableAccount {
    private BigDecimal balance = BigDecimal.ZERO;

    @Override public BigDecimal getBalance() { return balance; }
    @Override public void deposit(BigDecimal amount) { balance = balance.add(amount); }
    @Override public void withdraw(BigDecimal amount) { balance = balance.subtract(amount); }
}

// ✅ 4. Fixed Term Account (Only implements Account, zero invalid methods!):
public class FixedTermDepositAccount implements Account {
    private BigDecimal balance = BigDecimal.ZERO;

    @Override public BigDecimal getBalance() { return balance; }
    @Override public void deposit(BigDecimal amount) { balance = balance.add(amount); }
}
```

```java
// 🛡️ The fee processor now demands ONLY WithdrawableAccount (100% Compile-Time Safe!):
public void processMonthlyFees(List<WithdrawableAccount> accounts) {
    for (WithdrawableAccount account : accounts) {
        account.withdraw(new BigDecimal("10.00")); // Guaranteed to never throw UnsupportedOperationException!
    }
}
```

## 🔴 Senior Level

### Real-World JDK LSP Violations

Even the official Java Standard Library contains famous historical LSP violations created before design patterns were codified:

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ JDK Class & Superclass       │ Why It Violates the Liskov Substitution Principle                               │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`java.sql.Date`**          │ Subclasses `java.util.Date`. However, `java.sql.Date` represents a date without │
  │ `extends java.util.Date`     │ a time component. Calling `getHours()` or `setMinutes()` throws                │
  │                              │ 💥 `IllegalArgumentException`!                                                  │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`Collections`**            │ `Collections.unmodifiableList(list)` implements `List<T>`. However, calling     │
  │ **`unmodifiableList()`**     │ `list.add("item")` throws 💥 `UnsupportedOperationException`!                   │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **`java.util.Properties`**   │ `Properties extends Hashtable<Object, Object>`. However, it only supports       │
  │ `extends Hashtable`          │ `String` keys/values. Calling `put(123, new Date())` corrupts `getProperty()`.  │
  └──────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Strengthened Preconditions Violation

An LSP violation occurs when a subclass arbitrarily tightens validation rules that the parent class relaxed:

```java
public class UserRegistrationValidator {
    // Contract: Accepts any non-null username between 3 and 50 characters:
    public void validate(String username) {
        if (username == null || username.length() < 3 || username.length() > 50) {
            throw new IllegalArgumentException("Invalid length");
        }
    }
}

// ❌ LSP VIOLATION (Strengthens precondition by rejecting valid underscores!):
public class StrictCorporateValidator extends UserRegistrationValidator {
    @Override
    public void validate(String username) {
        super.validate(username);
        // 💥 Extra strict constraint: Breaks callers who pass valid usernames with underscores!
        if (username.contains("_")) {
            throw new IllegalArgumentException("Underscores not permitted in corporate names!");
        }
    }
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Violation:** Subclass throwing `UnsupportedOperationException` on an inherited method.
- **Root Cause:** Misusing inheritance for code reuse ("IS-A" trap) when behavioral contracts do not match.
- **JDK Examples:** `java.sql.Date extends java.util.Date`, `Collections.unmodifiableList()`.
- **Refactoring:** Break broad base classes into **Capability Interfaces** (`WithdrawableAccount` vs `Account`).
- **Precondition Rule:** Subclasses cannot demand stricter validation than the parent class.

**Common Follow-up Questions:**
- *"Why did the JDK designers make `Properties` extend `Hashtable` if it violates LSP?"* → It was created in Java 1.0 (1996) before modern OOP design guidelines were established. Today, Joshua Bloch explicitly cites this as a design mistake in *Effective Java*.
- *"How does Interface Segregation Principle (ISP) help prevent LSP violations?"* → By splitting fat interfaces into small, single-purpose interfaces, subclasses only implement methods they actually support, eliminating the need to throw `UnsupportedOperationException`.
- *"How can you detect LSP violations during automated code analysis?"* → Static analysis tools (SonarQube, SpotBugs) detect empty method overrides, methods that only throw `UnsupportedOperationException`, and `instanceof` checks over parent types.

**Red Flags (DO NOT Say):**
- ❌ *"Throwing `UnsupportedOperationException` in a subclass is standard Java practice and does not violate SOLID."* (It is the textbook violation of LSP).
- ❌ *"Whenever a subclass cannot do what the parent does, catch the exception with `try/catch` in the caller."* (Defeats polymorphism; callers should not know concrete subtype quirks).
- ❌ *"Subclasses can safely tighten input validation rules to whatever they want."* (Strengthening preconditions violates Liskov substitution).
