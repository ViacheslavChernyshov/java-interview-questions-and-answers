# What is Composition and Inheritance?

---

## 🟢 Junior Level

**Inheritance** and **Composition** are the two primary mechanisms in Object-Oriented Programming for structuring code relationships and reusing functionality:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🧬 INHERITANCE ("IS-A" Relationship)                     │ 🧩 COMPOSITION ("HAS-A" Relationship)                   │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • A subclass extends a parent class to inherit its      │ • A class contains a reference to an object and         │
  │   state and behaviors.                                  │   delegates work to it.                                 │
  │ • **Static & Compile-Time**: Fixed at compilation.      │ • **Dynamic & Runtime**: Swappable at runtime.          │
  │ • Example: `Dog IS-A Animal` (`class Dog extends Animal`)│ • Example: `Car HAS-A Engine` (`class Car { Engine e; }`)│
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```java
// 1. INHERITANCE EXAMPLE (IS-A):
public class Animal {
    public void eat() { System.out.println("Eating food..."); }
}

public class Dog extends Animal {
    public void bark() { System.out.println("Woof!"); }
}

// 2. COMPOSITION EXAMPLE (HAS-A):
public class Engine {
    public void ignite() { System.out.println("Vroom!"); }
}

public class Car {
    private final Engine engine; // Composed dependency

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start() {
        engine.ignite(); // Delegation
    }
}
```

## 🟡 Middle Level

### Comprehensive Comparison Matrix

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architectural Metric         │ Inheritance (IS-A)               │ Composition (HAS-A)                              │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Binding Time**             │ Static (Compile-time)            │ Dynamic (Runtime / Polymorphic)                  │
  │ **Encapsulation**            │ 🔴 **Breaks Encapsulation**      │ 🟢 **Preserves Encapsulation**                   │
  │                              │ (White-box reuse: sees protected)│ (Black-box reuse: interacts via public API only) │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Coupling Level**           │ High (Tight coupling to parent)  │ Low (Decoupled via interfaces)                   │
  │ **Flexibility**              │ Rigid (Cannot change parent)     │ High (Swap strategies dynamically at runtime)   │
  │ **Testability**              │ Hard (Requires testing hierarchy)│ Trivial (Inject mock objects via constructor)    │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Composition vs. Aggregation

Within Object-Oriented modeling, object containment has two distinct lifecycle semantics:

```
  • Composition (Strong Ownership): The parent object manages the complete lifecycle of the child. 
    If `Car` is garbage collected, its dedicated `CarChassis` is destroyed with it.
  • Aggregation (Loose Association): The child object has an independent lifecycle. 
    A `Department` has `Employees`; if the `Department` is dissolved, the `Employees` still exist.
```

## 🔴 Senior Level

### The Fragile Base Class Problem

Joshua Bloch's classic rule in *Effective Java* (Item 18) states: **"Favor Composition over Inheritance."**

The greatest danger of inheritance is the **Fragile Base Class Problem**, where modifying the parent class silently breaks subclass invariants without any compiler errors:

```java
// ❌ THE FRAGILE BASE CLASS TRAP:
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0; // Tracks total items added

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c); // 💥 BUG: HashSet.addAll() internally calls add()!
    }

    public int getAddCount() { return addCount; }
}

// 💥 addAll(List.of("A", "B", "C")) results in addCount = 6 (Double counting!), not 3!
```

#### Senior Solution (The Forwarding Wrapper / Decorator Pattern):

```java
// ✅ SAFE COMPOSITION (Zero dependence on internal HashSet implementation details):
public class InstrumentedSet<E> implements Set<E> {
    private final Set<E> delegate; // Black-box composition
    private int addCount = 0;

    public InstrumentedSet(Set<E> delegate) {
        this.delegate = delegate;
    }

    @Override
    public boolean add(E e) {
        addCount++;
        return delegate.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c); // Safe: delegate manages its own mechanics
    }

    public int getAddCount() { return addCount; }
    // Forward remaining Set methods to delegate...
}
```

### JVM Performance: VTable Inlining & Devirtualization

- **Inheritance** relies on **Virtual Method Tables (VTables)** (`invokevirtual`). Deep hierarchies (5+ levels) make JIT compiler profiling difficult.
- If a call-site is **Monomorphic** (1 concrete class executed), the HotSpot JIT compiler applies **Devirtualization and Inlining** (zero method call overhead).
- If a call-site is **Megamorphic** (3+ concrete subclasses), the JIT compiler cannot inline, forcing a VTable lookup on every invocation.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Inheritance:** "IS-A" compile-time relationship; white-box reuse; breaks encapsulation.
- **Composition:** "HAS-A" runtime relationship; black-box reuse; preserves encapsulation.
- **Joshua Bloch Rule:** *"Favor composition over inheritance"* (Effective Java Item 18).
- **Fragile Base Class:** Modifying superclass internal implementation details silently breaks subclasses.
- **When Inheritance is OK:** Real polymorphic hierarchies (`IOException` $\to$ `SocketException`) or Framework Template Methods.

**Common Follow-up Questions:**
- *"What is the difference between Composition and Aggregation?"* → In Composition, the child cannot exist without the parent (strong lifecycle coupling); in Aggregation, the child exists independently of the container.
- *"Why does inheritance break encapsulation?"* → A subclass depends on the implementation details of its parent (e.g. knowing whether `addAll()` calls `add()`); if the parent changes its internal methods in a minor update, child classes break.
- *"How does composition improve unit testing?"* → Composition allows injecting mock interfaces (`MockEngine`) into the constructor, whereas inheritance forces tests to execute the real parent class code.

**Red Flags (DO NOT Say):**
- ❌ *"Inheritance is always better than composition because you write fewer lines of code."* (Inheritance creates tight coupling and severe maintenance fragility).
- ❌ *"Composition is slower than inheritance because of extra pointer dereferencing."* (JIT compiler optimizes composed delegates through escape analysis and method inlining).
- ❌ *"Subclassing `ArrayList` is the best way to create a custom business collection."* (Wrap `List<T>` via composition/delegation instead of extending concrete collection classes).
