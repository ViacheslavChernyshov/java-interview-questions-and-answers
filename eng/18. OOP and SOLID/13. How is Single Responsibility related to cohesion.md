# How is Single Responsibility Related to Cohesion?

---

## 🟢 Junior Level

**Cohesion** and the **Single Responsibility Principle (SRP)** are two closely related concepts that define the internal focus and organization of a class:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 🎯 COHESION (Internal Attribute)                         │ 🏛️ SINGLE RESPONSIBILITY (Architectural Rule)           │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Measures how closely related the methods and fields   │ • The rule stating a class should have one, and only    │
  │   of a class are to each other.                         │   one, reason to change (one business actor).           │
  │ • **High Cohesion**: All methods work toward one goal.  │ • **Applying SRP naturally produces High Cohesion!**    │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

```
  Surgical Medical Team Analogy:
  • High Cohesion (SRP Compliant): A Cardiac Surgery Team where every member (Surgeon, Anesthesiologist, 
    Perfusionist) focuses entirely on performing the heart operation.
  • Low Cohesion (SRP Violation): A "Hospital Staffer" who performs heart surgery, cleans hospital hallways, 
    manages the payroll database, and repairs the parking lot gates.
```

```java
// 🟢 HIGH COHESION (All methods operate strictly on Order state):
public class OrderService {
    public Order createOrder(CreateOrderRequest req) { /* ... */ }
    public void cancelOrder(Long orderId) { /* ... */ }
    public BigDecimal calculateOrderTotal(Order order) { /* ... */ }
}

// 🔴 LOW COHESION (Unrelated operations bundled in a God class):
public class GeneralManager {
    public void saveToDatabase(Object o) { /* DB */ }
    public void sendEmail(String to) { /* Networking */ }
    public void calculateEmployeeSalary() { /* Payroll */ }
}
```

## 🟡 Middle Level

### The 7 Levels of Cohesion (Myers Taxonomy)

In computer science, Glenford Myers classified cohesion into 7 levels, from best to worst:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Cohesion Level               │ How Elements Are Grouped         │ Real-World Java Example                          │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. Functional (Best 🟢)**  │ All elements perform 1 task.     │ `BCryptPasswordEncoder.encode()`                 │
  │ **2. Sequential (🟢)**       │ Output of Step 1 is input to 2.  │ `ImageTransformer.resize().compress().watermark()`│
  │ **3. Communicational (🟡)**  │ Operate on the same shared data. │ `UserRepository` (CRUD on `User` entity)         │
  │ **4. Procedural (🟡)**       │ Grouped by execution order.      │ `ApplicationStartupInitializer`                  │
  │ **5. Temporal (🟠)**         │ Grouped by execution time.       │ `NightlyBatchCleanupJob`                         │
  │ **6. Logical / Utility (🔴)**│ Grouped by broad category.       │ `CommonUtils`, `StringUtils`                     │
  │ **7. Coincidental (Worst 🔴)│ Arbitrary random grouping.       │ `GeneralHelper`, `MiscManager`                   │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### High Cohesion + Low Coupling: The Holy Grail

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Architectural Approach                   │ Evaluation & Impact                              │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Low Cohesion + High Coupling**         │ 💥 **Spaghetti / God Object**: Fragile, impossible│
  │ (God Classes)                            │ to test, frequent merge conflicts.               │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **High Cohesion + High Coupling**        │ ⚠️ **Atomic Dust (Over-granularity)**: Hundreds  │
  │ (Micro-classes with tight dependencies)  │ of 3-line classes that depend tightly on each oth│
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **High Cohesion + Low Coupling**         │ 🏆 **Clean Architecture**: Highly focused classes│
  │ (SRP + Dependency Inversion)             │ communicating across clean, decoupled interfaces.│
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

## 🔴 Senior Level

### Mathematical Measurement: LCOM4 (Lack of Cohesion in Methods)

Static analysis tools (SonarQube, JDepend) mathematically measure class cohesion using the **LCOM4 metric** (Henderson-Sellers formulation):

```
  LCOM4 Graph Model:
  • Vertices ($V$): Methods and Fields of the class.
  • Edges ($E$): An edge exists between Method A and Method B if they access the same field 
    or call each other.
```

```
  [Method 1: calculateTax] ────── (Accesses field: `orderTotal`) ────── [Method 2: applyDiscount]
                               (CONNECTED GRAPH: LCOM4 = 1 🟢)

  [Method 1: hashPassword] ── (Uses `salt`)        [Method 2: sendEmail] ── (Uses `smtpPort`)
              ▲                                                   ▲
              └─────────────── (DISJOINT SUBGRAPHS: LCOM4 = 2 🔴) ─┘
```

```
  LCOM4 Interpretation:
  • LCOM4 = 1: 🟢 Ideal Cohesion. All methods belong to a single connected component.
  • LCOM4 > 1: 🔴 SRP Violation! The class contains $N$ disjoint subgraphs and MUST be refactored 
    into $N$ separate classes!
```

### Package Cohesion: Package-by-Layer vs. Package-by-Feature

Cohesion applies not just to classes, but to directory structure:

```
  1. Package-by-Layer (Low Architectural Cohesion):
     ├── controllers/ (UserController, OrderController, PaymentController)
     ├── services/    (UserService, OrderService, PaymentService)
     └── repositories/(UserRepository, OrderRepository, PaymentRepository)
     (Editing an "Order" feature requires touching 3 separate distant packages!)

  2. Package-by-Feature / Domain (High Architectural Cohesion):
     ├── order/       (OrderController, OrderService, OrderRepository, OrderDTO)
     ├── user/        (UserController, UserService, UserRepository, UserDTO)
     └── payment/     (PaymentController, PaymentService, PaymentRepository)
     (Everything related to "Order" is co-located inside 1 cohesive bounded package!)
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Cohesion vs SRP:** Cohesion is the *measurement* of internal method/field focus; SRP is the *design rule* that produces High Cohesion.
- **Universal Goal:** **High Cohesion + Low Coupling**.
- **Top Cohesion Levels:** Functional (1 task) and Sequential (pipeline).
- **Worst Cohesion Levels:** Logical (Utility classes) and Coincidental (Misc helpers).
- **LCOM4 Metric:** $LCOM4 = 1$ is ideal; $LCOM4 \ge 2$ mathematically indicates disjoint responsibilities that should be split into separate classes.
- **Package Cohesion:** Prefer **Package-by-Feature** over Package-by-Layer for maximum domain cohesion.

**Common Follow-up Questions:**
- *"Are static `StringUtils` utility classes an acceptable violation of functional cohesion?"* → Yes, stateless string/math utility classes have Logical Cohesion. They are acceptable pragmatically as long as they remain stateless and do not hold domain business logic.
- *"How does High Cohesion impact the JVM JIT compiler?"* → Highly cohesive classes have small, frequently executed methods operating on a compact set of fields, maximizing CPU L1/L2 cache locality and enabling aggressive JIT method inlining.
- *"What happens if cohesion is too high (over-granularization)?"* → Breaking code into thousands of 1-line classes increases cognitive navigation overhead and inter-class coupling without adding architectural value.

**Red Flags (DO NOT Say):**
- ❌ *"Cohesion and Coupling mean the exact same thing."* (Cohesion is internal module focus; Coupling is inter-module dependency).
- ❌ *"A class that has 30 unrelated methods is fine as long as it has unit tests."* (Fails cohesion and SRP; high maintenance hazard).
- ❌ *"LCOM4 is a database query optimization tool."* (LCOM4 is an object-oriented code cohesion metric).
