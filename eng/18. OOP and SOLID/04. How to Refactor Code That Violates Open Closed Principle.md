# How to Refactor Code That Violates Open Closed Principle?

---

## 🟢 Junior Level

Code that violates the **Open/Closed Principle (OCP)** is easily recognized by long chains of `if-else if-else` or `switch` statements inspecting types, string flags, or enums:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ ❌ THE OCP CODE SMELL:                                                           │
  │ Every time a new business requirement is introduced (e.g. adding Telegram SMS): │
  │ 1. You must open `NotificationService.java`.                                    │
  │ 2. You must add another `else if ("TELEGRAM".equals(channel))` branch.          │
  │ 3. You risk accidentally breaking existing Email and SMS logic!                 │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```java
// ❌ BEFORE (Violates OCP):
public class NotificationSender {
    public void sendNotification(String channel, String recipient, String message) {
        if ("EMAIL".equalsIgnoreCase(channel)) {
            // 30 lines of JavaMail SMTP code...
        } else if ("SMS".equalsIgnoreCase(channel)) {
            // 30 lines of Twilio REST API code...
        } else if ("PUSH".equalsIgnoreCase(channel)) {
            // 30 lines of Firebase Cloud Messaging code...
        } else {
            throw new IllegalArgumentException("Unsupported channel: " + channel);
        }
    }
}
```

## 🟡 Middle Level

### The 4-Step Systematic Refactoring Recipe

```
  Step 1: Identify the Variation Point ──► Branching condition over type/channel.
  Step 2: Extract Common Interface     ──► `public interface NotificationChannel`
  Step 3: Implement Strategy Classes   ──► `EmailChannel`, `SmsChannel`, `PushChannel`
  Step 4: Inject Strategy Map          ──► Replace conditional with `map.get(channel).send(...)`
```

#### Step 1 & 2: Define Common Strategy Interface

```java
public interface NotificationChannel {
    String getChannelType();
    void send(String recipient, String message);
}
```

#### Step 3: Implement Dedicated Strategy Classes

```java
@Component
public class EmailNotificationChannel implements NotificationChannel {
    @Override public String getChannelType() { return "EMAIL"; }
    @Override public void send(String recipient, String message) {
        // Isolated JavaMail SMTP logic
    }
}

@Component
public class SmsNotificationChannel implements NotificationChannel {
    @Override public String getChannelType() { return "SMS"; }
    @Override public void send(String recipient, String message) {
        // Isolated Twilio SMS logic
    }
}
```

#### Step 4: Refactor Caller to Use Dynamic Map Dispatch

```java
@Service
public class NotificationSender {

    private final Map<String, NotificationChannel> channels;

    // Spring auto-discovers all NotificationChannel beans in the application context:
    public NotificationSender(List<NotificationChannel> channelList) {
        this.channels = channelList.stream()
            .collect(Collectors.toMap(c -> c.getChannelType().toUpperCase(), Function.identity()));
    }

    public void sendNotification(String channel, String recipient, String message) {
        NotificationChannel targetChannel = channels.get(channel.toUpperCase());
        if (targetChannel == null) {
            throw new IllegalArgumentException("Unsupported notification channel: " + channel);
        }
        targetChannel.send(recipient, message); // Polymorphic dispatch in 1 line!
    }
}
```

## 🔴 Senior Level

### Adding New Features with Zero Existing Code Edits

To prove compliance with OCP, add **Telegram Notification** support:

```java
// 🚀 ADDING TELEGRAM REQUIRES 100% NEW CODE IN A NEW FILE:
@Component
public class TelegramNotificationChannel implements NotificationChannel {
    @Override public String getChannelType() { return "TELEGRAM"; }
    @Override public void send(String recipient, String message) {
        // Telegram Bot API HTTP call...
    }
}
```
**The Result:** `NotificationSender.java`, `EmailNotificationChannel.java`, and `SmsNotificationChannel.java` are **completely untouched**. Existing unit tests pass with 0% risk of regression!

### Lightweight Alternative: Enums with Constant-Specific Methods

For local, fixed mathematical algorithms where Spring beans are unnecessary, use **Enums with Abstract Methods**:

```java
public enum DiscountTier {
    REGULAR {
        @Override public BigDecimal applyDiscount(BigDecimal total) { return total.multiply(new BigDecimal("0.95")); }
    },
    VIP {
        @Override public BigDecimal applyDiscount(BigDecimal total) { return total.multiply(new BigDecimal("0.85")); }
    },
    PLATINUM {
        @Override public BigDecimal applyDiscount(BigDecimal total) { return total.multiply(new BigDecimal("0.70")); }
    };

    public abstract BigDecimal applyDiscount(BigDecimal total);
}
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Refactoring Strategy:** Replace `switch`/`if-else` conditionals with the **Strategy Pattern + Factory / Map Injection**.
- **The 4 Steps:** Identify variation $\to$ Extract interface $\to$ Create concrete classes $\to$ Inject map.
- **Spring Boot Magic:** Injecting `List<StrategyInterface>` automatically collects all Spring beans implementing that interface.
- **Regression Safety:** Adding a new feature creates a brand new `.java` file, leaving existing classes untouched.
- **Enum Option:** For small, fixed algorithmic strategies, use Java Enums with constant-specific abstract methods.

**Common Follow-up Questions:**
- *"What happens if two Strategy classes return the same channel type string?"* → `Collectors.toMap` will throw an `IllegalStateException: Duplicate key`. Prevent this by enforcing unique enums or using a merge function in the collector.
- *"How do you handle a default fallback strategy?"* → Use `channels.getOrDefault(channel, defaultFallbackChannel)`.
- *"Is using `switch` statements always a violation of OCP?"* → No; simple `switch` expressions on closed enums (where all cases are within the same cohesive domain) are acceptable. It becomes a violation when every new system feature forces you to locate and edit the switch.

**Red Flags (DO NOT Say):**
- ❌ *"Refactor OCP violations by creating a deep 5-level inheritance hierarchy."* (Deep inheritance creates fragile base classes; use composition and interfaces).
- ❌ *"Using Spring `@Autowired` in every if-branch fixes OCP."* (The branching logic still violates OCP; use map injection).
- ❌ *"OCP refactoring makes code slower because of interface method calls."* (JIT compiler optimizes interface calls via monomorphic/bimorphic inline caching with negligible overhead).
