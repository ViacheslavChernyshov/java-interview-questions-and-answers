# How to Determine If a Class Has Single Responsibility?

---

## 🟢 Junior Level

Determining whether a class adheres to the **Single Responsibility Principle (SRP)** requires evaluating whether it has only **one reason to change** (serving one specific business actor).

Senior engineers use **The "AND" Elevator Pitch Test**:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ ❓ THE "AND" ELEVATOR PITCH TEST:                                               │
  │ Describe what your class does in a single sentence without using the words:      │
  │ • "AND"                                                                         │
  │ • "OR"                                                                          │
  │ • "ALSO"                                                                        │
  │ • "AS WELL AS"                                                                  │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```
  Evaluating Class Responsibilities:
  • ❌ `OrderManager`: "It validates the shopping cart **AND** saves it to Postgres **AND** 
       sends an email **AND** generates a PDF invoice." (4 Responsibilities ➔ SRP Violation!)
  • 🟢 `OrderValidator`: "It verifies that the order contains valid items and shipping addresses." (1 Responsibility)
  • 🟢 `PdfInvoiceGenerator`: "It renders an order into a downloadable PDF binary document." (1 Responsibility)
  • 🟢 `EmailNotifier`: "It sends transactional email confirmations to customers." (1 Responsibility)
```

## 🟡 Middle Level

### The 5 Diagnostic Tests for Single Responsibility

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Diagnostic Test              │ What to Inspect                  │ Red Flag / SRP Violation Signal                  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **1. The Actor Test**        │ Who requests changes to this     │ CFO (Finance), DBA (Database), and CMO (Marketing│
  │ (Robert C. Martin)           │ class?                           │ all request changes to the same class!           │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **2. The Import List Test**  │ Look at package `import` headers.│ Imports `java.sql.*`, `jakarta.mail.*`,          │
  │                              │                                  │ `com.fasterxml.jackson.*`, and `org.pdfbox.*`!   │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **3. The Constructor Test**  │ Count injected constructor args. │ Injects 8+ dependencies into the constructor.    │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **4. The Test Friction Test**│ Look at unit test setup code.    │ Testing a 2-line calculation requires 40 lines of│
  │                              │                                  │ Mockito `when().thenReturn()` across 6 systems.  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **5. The Git Churn Test**    │ Check `git log` commit history.  │ The file is modified in 70% of all pull requests.│
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### The Import Smell Example

```java
// ❌ THE IMPORT SMELL (Class mixing 4 unrelated technological domains):
package com.example.service;

import java.sql.Connection;                   // 1. Persistence Concern (DBA)
import jakarta.mail.internet.MimeMessage;     // 2. Notification Concern (Operations)
import com.fasterxml.jackson.databind.ObjectMapper; // 3. Serialization Concern (API)
import org.apache.pdfbox.pdmodel.PDDocument;  // 4. Document Formatting Concern (HR/Billing)

public class OrderManager {
    // 💥 An obvious God Class violating SRP!
}
```

## 🔴 Senior Level

### Automated Mathematical Heuristics: LCOM4 & Static Analysis

In enterprise CI/CD pipelines, teams rely on objective mathematical metrics to enforce SRP automatically:

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Static Analysis Metric       │ Target Threshold                 │ Meaning When Breached                            │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **LCOM4** (Lack of Cohesion  │ $\mathbf{LCOM4 = 1}$ (Clean)     │ $\mathbf{LCOM4 \ge 2}$ proves mathematically     │
  │ in Methods - Henderson)      │                                  │ that methods operate on disjoint subgraphs.      │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Cognitive Complexity**     │ $\mathbf{< 15}$ per method       │ $\mathbf{> 15}$ indicates deeply nested branching│
  │ (SonarQube)                  │                                  │ doing too many conditional tasks.                │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Lines of Code (LOC)**      │ $\mathbf{< 350}$ lines per class │ $\mathbf{> 1,000}$ lines strongly correlates     │
  │                              │                                  │ with accumulating multiple responsibilities.     │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

```
  LCOM4 Disjoint Subgraph Visualization:
  [Method: calculateTax] ── (Uses `taxRate`) ── [Method: applyExemption] (Subgraph 1)
  
  [Method: sendSmtp] ────── (Uses `smtpHost`) ─ [Method: parseEmail]     (Subgraph 2)
  
  🔴 LCOM4 = 2 (Two completely disjoint graphs sharing zero state! Must be split into 2 classes).
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **The "AND" Test:** If describing what a class does requires using "AND", it violates SRP.
- **The Actor Test:** A class should be responsible to one, and only one, business stakeholder/actor.
- **Top 4 Code Smells:** Mixed import packages (SQL + Mail + PDF), 8+ constructor dependencies, testing friction, and high Git churn.
- **Automated Verification:** Use **SonarQube** (Cognitive Complexity $< 15$) and **LCOM4 = 1** in CI/CD quality gates.

**Common Follow-up Questions:**
- *"Does a class with 10 methods automatically violate SRP?"* → No! If all 10 methods operate on the same private fields toward a single cohesive goal (e.g. `StringBuilder` or `OrderAggregate`), it has high cohesion ($LCOM4 = 1$) and adheres to SRP.
- *"How do you distinguish an Orchestrator class from a God class?"* → An **Orchestrator** coordinates high-level business steps by delegating to specialized services (`validator.validate()`, `repo.save()`, `notifier.send()`). A **God class** attempts to execute the raw low-level logic (raw SQL, SMTP sockets, JSON parsing) directly inside its own methods.
- *"Can a package violate SRP?"* → Yes! A package that bundles unrelated domain classes violates package cohesion. Prefer **Package-by-Feature** over Package-by-Layer.

**Red Flags (DO NOT Say):**
- ❌ *"A class has single responsibility only if it has exactly one method."* (A class can have multiple methods as long as they all serve the same responsibility).
- ❌ *"If all methods in a class are private, SRP doesn't matter."* (Private methods sharing state still cause fragility and testing friction).
- ❌ *"You can only determine SRP by subjective opinion, not through metrics."* (LCOM4, Git churn, and Cognitive Complexity provide objective mathematical proof).
