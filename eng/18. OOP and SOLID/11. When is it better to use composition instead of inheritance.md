# When is It Better to Use Composition Instead of Inheritance?

---

## 🟢 Junior Level

In modern software development, **Composition is almost always preferred over Inheritance** (the *"Favor Composition over Inheritance"* rule).

Use this simple decision test:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ ❓ THE DECISION TEST:                                                           │
  │ • Is it a pure "IS-A" relationship where the subclass can ALWAYS be substituted │
  │   for the parent in 100% of scenarios without breaking invariants?              │
  │   👉 If YES ➔ **Inheritance may be acceptable** (`Cat IS-A Mammal`).            │
  │ • Do you just want to reuse code, wrap functionality, or change algorithms?     │
  │   👉 If YES ➔ **Use COMPOSITION!** (`Car HAS-A Engine`).                        │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```
  Tattoo vs. Backpack Analogy:
  • Inheritance is like a **Tattoo**: Permanent, fixed at creation, and impossible to remove or change later.
  • Composition is like a **Backpack**: You can swap your laptop, water bottle, or books whenever needed!
```

## 🟡 Middle Level

### The 5 Architectural Scenarios Where Composition Wins

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Scenario                        │ Why Composition is Superior                                                     │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. Hiding / Limiting APIs**   │ Inheritance forces the subclass to expose **every single public method** of the │
  │                                 │ parent class. Composition lets you expose only the exact methods you want!      │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. Dynamic Runtime Swapping** │ Subclass parents are statically locked at compile time. Composition allows      │
  │                                 │ swapping strategies dynamically at runtime (`service.setStrategy(...)`).        │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. Multiple Behaviors**       │ Java does not support multiple class inheritance. With composition, a class can │
  │                                 │ compose 10 different delegates effortlessly.                                    │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **4. Third-Party Class Reuse**  │ You cannot safely extend third-party library classes you don't control. Wrap    │
  │                                 │ them in a composite adapter instead.                                            │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **5. Unit Test Mockability**    │ Composed dependencies are easily replaced by Mockito mocks in unit tests.       │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### Classic JDK Blunder: `Stack extends Vector`

The JDK's legacy `java.util.Stack` is a famous architectural anti-pattern created before design patterns were codified:

```java
// ❌ THE STACK EXTENDS VECTOR DESIGN MISTAKE:
public class Stack<E> extends Vector<E> {
    public E push(E item) { addElement(item); return item; }
    public synchronized E pop() { ... }
}

// 💥 A Stack MUST be strictly LIFO (Last-In, First-Out).
// However, because it extends Vector, clients can call Vector methods directly:
Stack<String> stack = new Stack<>();
stack.push("Bottom");
stack.push("Top");

stack.add(0, "ILLEGAL_MIDDLE_INSERTION!"); // 💥 Corrupts LIFO invariant!
stack.clear(); // 💥 Bypasses pop mechanics!
```

#### The Clean Composition Fix (Wrapper / Adapter):

```java
// ✅ Clean Composition (Strict LIFO invariant protected):
public class ModernStack<E> {
    private final Deque<E> internalStorage = new ArrayDeque<>(); // Composed private delegate

    public void push(E item) { internalStorage.push(item); }
    public E pop() { return internalStorage.pop(); }
    public E peek() { return internalStorage.peek(); }
    public boolean isEmpty() { return internalStorage.isEmpty(); }
    // 🛡️ Callers CANNOT invoke random index insertion!
}
```

## 🔴 Senior Level

### Joshua Bloch's Rule: "Design and Document for Inheritance, or Else Prohibit It"

In *Effective Java* (Item 19), Joshua Bloch establishes the enterprise standard:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ INHERITANCE GOVERNANCE RULES:                                                                 │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 1. **Default to `final`:** If a class is not specifically engineered for extension, mark it   │
  │    `final` (or make its constructors private with static factories) to prohibit subclassing.  │
  │ 2. **Never Call Overridable Methods in Constructors:** If a parent constructor calls an        │
  │    overridable method, the child's overridden method executes BEFORE child fields initialize! │
  │ 3. **Document Hook Points:** If designing for inheritance, document every self-use of methods │
  │    using `@implSpec` (e.g. "This method internally calls `add()`").                           │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Design Patterns Powered by Composition

```
  ┌──────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Design Pattern               │ Composition Mechanism                                                           │
  ├──────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **Strategy Pattern**         │ Class composes a `PaymentStrategy` interface and delegates execution.           │
  │ **Decorator Pattern**        │ Class wraps an existing interface (`new BufferedReader(new FileReader(...))`).  │

```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Golden Rule:** *"Favor composition over inheritance"* (Effective Java Item 18).
- **Core Advantage:** Composition is black-box reuse (preserves encapsulation, enables runtime swapping, and hides unwanted methods).
- **The JDK Flaw:** `Stack extends Vector` and `Properties extends Hashtable` broke encapsulation by exposing parent methods that violated child invariants.
- **When to Use Inheritance:** Only for true, immutable semantic subtyping (`RuntimeException` $\to$ `IllegalStateException`) or well-documented Template Methods.
- **Prohibiting Subclassing:** Mark classes `final` if they are not explicitly engineered for inheritance.

**Common Follow-up Questions:**
- *"What happens if a parent constructor calls an overridable method?"* → The subclass's overridden method runs *before* the subclass constructor has initialized its fields, resulting in `NullPointerException`s or reading zeroed default primitives!
- *"How does composition solve the multiple inheritance limitation in Java?"* → A Java class can only `extend` one superclass, but it can compose references to as many classes/interfaces as needed (`private final Engine e; private final Gps g; private final Radio r;`).
- *"Is composition always zero-cost?"* → Composition adds a minor memory reference (8 bytes for the object pointer) and a layer of indirection, which HotSpot JIT eliminates in high-frequency loops via escape analysis and inlining.

**Red Flags (DO NOT Say):**
- ❌ *"Always use inheritance when you want to save lines of code by sharing a method."* (Inheritance for mere code sharing leads to the Fragile Base Class trap).
- ❌ *"Stack extending Vector is good Java design."* (It is universally acknowledged as a historical design flaw).
- ❌ *"Composition cannot achieve polymorphism."* (Composition combined with interfaces achieves superior, dynamic polymorphism).
