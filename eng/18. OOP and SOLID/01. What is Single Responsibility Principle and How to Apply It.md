# What is Single Responsibility Principle and How to Apply It?

---

## 🟢 Junior Level

The **Single Responsibility Principle (SRP)** is the first principle of SOLID, formulated by Robert C. Martin (Uncle Bob):

> **"A class should have one, and only one, reason to change."**

A "reason to change" corresponds directly to a specific **business stakeholder or user role (Actor)**. If changes requested by Accounting (CFO), DBAs (Operations), and Marketing (CMO) all require modifying the same Java class, SRP is violated:

```
  Restaurant Kitchen Analogy:
  • No SRP (The Overloaded Chef): One person cooks the steak, washes the dishes, repairs the plumbing, 
    manages the financial accounting, and designs the website. If the plumbing breaks, food stops being served!
  • With SRP: Specialized roles (Head Chef, Dishwasher, Accountant, Plumber). Each person does one job well.
```

```java
// ❌ VIOLATION (Employee does too many unrelated jobs):
public class Employee {
    public BigDecimal calculatePay() { /* Accounting rule (CFO) */ }
    public void saveToDatabase() { /* Persistence rule (DBA) */ }
    public String generatePdfReport() { /* HR Reporting rule (COO) */ }
}

// ✅ COMPLIANT (Split into focused, single-purpose classes):
public class Employee {
    private Long id;
    private String name;
    private BigDecimal hourlyRate;
}

public class PayrollCalculator {
    public BigDecimal calculatePay(Employee emp) { /* Pay logic */ }
}

public class EmployeeRepository {
    public void save(Employee emp) { /* Database SQL logic */ }
}

public class EmployeeReportGenerator {
    public byte[] generatePdfReport(Employee emp) { /* PDF formatting */ }
}
```

## 🟡 Middle Level

### The "AND" Test & Code Smells

```
  ┌─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │ Code Smell                      │ Diagnostic Signal                                                               │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **1. The "AND" Description**    │ If you describe what a class does using "AND" ("It validates input **AND**      │
  │                                 │ saves to Postgres **AND** sends emails"), it violates SRP!                      │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **2. Git Merge Conflicts**      │ Multiple developers on different feature tracks constantly get merge conflicts  │
  │                                 │ on the exact same class file.                                                   │
  ├─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ **3. Massive Constructor**      │ A class requires 8+ injected dependencies in its constructor.                   │
  │ **4. Testing Friction**         │ Testing a simple calculation requires mocking 6 database repositories and HTTP  │
  │                                 │ clients.                                                                        │
  └─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘
```

### High Cohesion vs. Low Coupling

```
  • Cohesion (Internal Alignment): How closely related the methods and fields are within a class. 
    High cohesion = All methods operate on the same private fields toward one goal.
  • Coupling (External Dependency): How tightly bound a class is to outside classes. 
    Low coupling = Changing class A has zero side effects on class B.
```

```java
// Orchestrator adhering to SRP through Composition and Delegation:
@Service
@RequiredArgsConstructor
public class OrderCheckoutService {

    private final OrderValidator validator;
    private final PaymentProcessor paymentProcessor;
    private final OrderRepository repository;
    private final NotificationService notifier;

    // Has ONE responsibility: Orchestrating the high-level checkout flow!
    @Transactional
    public OrderResponseDTO checkout(OrderRequestDTO request) {
        validator.validate(request);
        PaymentReceipt receipt = paymentProcessor.charge(request.paymentInfo());
        Order order = repository.save(Order.from(request, receipt));
        notifier.sendOrderConfirmation(order);
        return OrderResponseDTO.from(order);
    }
}
```

## 🔴 Senior Level

### The Senior Balance: Avoiding "Class Explosion" (Over-Granularization)

Applying SRP dogmatically to an extreme leads to the **Class Explosion Anti-Pattern** (thousands of 3-line classes, single-method interfaces, and unnavigable folder hierarchies):

```
  ┌──────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │ ❌ Dogmatic Over-Granularity (Anti-Pattern)│ 🏆 Pragmatic Domain Cohesion (Senior Standard)   │
  ├──────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ • Creating `OrderValidator`,             │ • A cohesive `Order` aggregate that encapsulates │
  │   `OrderTaxCalculator`, `OrderPriceSetter`,│   domain invariants, delegating infrastructure I/O│
  │   `OrderIdGenerator` for 2-line methods. │   (Repositories, Gateway clients) externally.    │
  │ • Fractured code navigation and overhead.│ • High cohesion within clear Domain Boundaries.  │
  └──────────────────────────────────────────┴──────────────────────────────────────────────────┘
```

```
  Pragmatic Rule of Thumb:
  • Keep Domain Business Logic together within cohesive Domain Aggregates (DDD).
  • Separate Infrastructure Concerns (I/O, SQL, JSON parsing, Third-Party SDKs, Messaging) into dedicated adapters.
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** A class should have one, and only one, reason to change (one business actor).
- **Goal:** Maximizes **High Cohesion** (focused internal logic) and **Low Coupling** (minimal dependencies).
- **The "AND" Rule:** If a class does $X$ AND $Y$, split it.
- **Benefits:** High testability, minimal merge conflicts, safe refactoring, and clear ownership.
- **Senior Pitfall:** Beware of "Class Explosion"; do not split cohesive domain methods into hundreds of trivial classes.

**Common Follow-up Questions:**
- *"How is SRP related to the Open/Closed Principle (OCP)?"* → Classes with single responsibilities are small and focused, making them significantly easier to extend via polymorphism without modifying existing source code.
- *"Does a Service class that calls 4 other services violate SRP?"* → No; its single responsibility is **high-level workflow orchestration** (coordinating the steps), while delegating the specific tasks (validation, charging, persistence) to dedicated services.
- *"How does SRP impact unit testing?"* → Classes with single responsibilities have small dependency graphs, allowing you to write fast, focused unit tests with minimal mocking.

**Red Flags (DO NOT Say):**
- ❌ *"SRP means every Java class must only contain exactly one single method."* (A class can have multiple methods as long as they all serve the same cohesive responsibility).
- ❌ *"Place database queries, email sending, and JSON formatting inside the JPA `@Entity` class."* (Classic God-Object SRP violation).
- ❌ *"SRP is only important in huge enterprise projects, not in standard web backends."* (SRP is fundamental to maintaining clean, bug-free software at any scale).
