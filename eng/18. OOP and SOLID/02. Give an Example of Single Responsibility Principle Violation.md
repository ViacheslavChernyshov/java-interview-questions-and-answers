# Give an Example of Single Responsibility Principle Violation

---

## 🟢 Junior Level

A **Single Responsibility Principle (SRP) Violation** occurs when a class takes on multiple unrelated duties, becoming a **God Object** that mixes business calculations, database persistence, external networking, and UI/formatting logic:

```
  ┌─────────────────────────────────────────────────────────────────────────────────┐
  │ ❌ THE "GOD OBJECT" VIOLATION:                                                  │
  │ `UserManager` handles:                                                          │
  │ 1. Password hashing (Security concern)                                          │
  │ 2. SQL INSERT queries (Persistence concern)                                     │
  │ 3. SendGrid Email dispatch (Notification concern)                               │
  │ 4. CSV Export generation (Reporting concern)                                    │
  └─────────────────────────────────────────────────────────────────────────────────┘
```

```java
// ❌ CLASSIC SRP VIOLATION:
public class UserManager {

    public void registerUser(String username, String password, String email) {
        // 1. Validation Concern:
        if (username == null || password.length() < 8) {
            throw new IllegalArgumentException("Invalid input");
        }

        // 2. Cryptographic Concern:
        String passwordHash = BCrypt.hashpw(password, BCrypt.gensalt());

        // 3. Database Persistence Concern (Raw SQL):
        try (Connection conn = DriverManager.getConnection("jdbc:postgresql://localhost/db")) {
            PreparedStatement stmt = conn.prepareStatement("INSERT INTO users VALUES (?, ?, ?)");
            stmt.setString(1, username);
            stmt.setString(2, passwordHash);
            stmt.setString(3, email);
            stmt.executeUpdate();
        } catch (SQLException e) {
            throw new RuntimeException("Database error", e);
        }

        // 4. External Email Networking Concern:
        SendGridEmailClient client = new SendGridEmailClient("API_KEY");
        client.send(email, "Welcome to our platform!");
    }
}
```

```
  Why This Breaks in Production:
  • If the marketing team changes the welcome email, you must modify and re-deploy `UserManager`.
  • If you migrate from PostgreSQL to MongoDB, you must modify and re-deploy `UserManager`.
  • Writing a unit test for password validation requires a live PostgreSQL database and SendGrid internet access!
```

## 🟡 Middle Level

### The Refactored Clean Architecture Solution

```java
// ✅ 1. Pure Domain Model:
public record User(Long id, String username, String passwordHash, String email) {}

// ✅ 2. Dedicated Validation Component:
@Component
public class UserRegistrationValidator {
    public void validate(RegistrationRequest request) {
        if (request.username() == null || request.password().length() < 8) {
            throw new IllegalArgumentException("Invalid registration parameters");
        }
    }
}

// ✅ 3. Dedicated Security Component:
@Component
public class PasswordEncoderService {
    public String encode(String rawPassword) {
        return BCrypt.hashpw(rawPassword, BCrypt.gensalt());
    }
}

// ✅ 4. Dedicated Persistence Component:
@Repository
public interface UserRepository extends JpaRepository<UserEntity, Long> {}

// ✅ 5. Dedicated Notification Component:
@Service
public class WelcomeNotificationService {
    public void sendWelcomeEmail(String email) { /* SendGrid API */ }
}
```

```java
// ✅ 6. Cohesive Orchestrator (Single Responsibility = Coordinating User Registration):
@Service
@RequiredArgsConstructor
public class UserRegistrationService {

    private final UserRegistrationValidator validator;
    private final PasswordEncoderService passwordEncoder;
    private final UserRepository userRepository;
    private final WelcomeNotificationService notificationService;

    @Transactional
    public User register(RegistrationRequest request) {
        validator.validate(request);
        String hash = passwordEncoder.encode(request.password());
        User savedUser = userRepository.save(User.create(request.username(), hash, request.email()));
        notificationService.sendWelcomeEmail(savedUser.email());
        return savedUser;
    }
}
```

## 🔴 Senior Level

### The "Spring Monster Service" Anti-Pattern

In enterprise Spring Boot backends, the most prevalent SRP violation is the **Monster Service** containing 20+ injected repositories:

```java
// ❌ THE "MONSTER SERVICE" CODE SMELL:
@Service
public class GeneralEcommerceService {
    @Autowired private UserRepository userRepository;
    @Autowired private ProductRepository productRepository;
    @Autowired private OrderRepository orderRepository;
    @Autowired private PaymentRepository paymentRepository;
    @Autowired private CouponRepository couponRepository;
    @Autowired private InventoryRepository inventoryRepository;
    @Autowired private ShippingRepository shippingRepository;
    @Autowired private AuditLogRepository auditLogRepository;
    @Autowired private EmailService emailService;
    @Autowired private PdfGenerator pdfGenerator;
    // ... 15 more dependencies!

    // 💥 3,000 lines of mixed code handling login, searching, checkout, refunds, and PDF exports!
}
```

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────┐
  │ TECHNICAL CATASTROPHES CAUSED BY THE MONSTER SERVICE:                                         │
  ├───────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 1. **Git Merge Hell:** 10 developers on different feature tracks constantly trigger merge      │
  │    conflicts on `GeneralEcommerceService.java`.                                               │
  │ 2. **Fragile Transaction Boundaries:** A bug in PDF generation triggers an unintended         │
  │    rollback of the financial payment transaction!                                             │
  │ 3. **Testing Impossibility:** Instantiating `GeneralEcommerceService` in a unit test requires │
  │    mocking 25 dependencies and writing 300 lines of Mockito boilerplate.                      │
  └───────────────────────────────────────────────────────────────────────────────────────────────┘
```

#### Senior Refactoring Protocol:
Decompose the monster service into focused, domain-bounded services:
- `OrderCheckoutService` (Checkout workflow orchestration only).
- `InventoryReservationService` (Stock allocation and warehouse locks).
- `PaymentCaptureService` (Payment gateway transaction integration).
- `OrderInvoiceService` (PDF generation and asynchronous email dispatch).

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Violation Signs:** Mixing validation, persistence (SQL), encryption, notifications, and formatting in one class.
- **Root Cause:** Failing to separate **Domain Logic** from **Infrastructure Concerns**.
- **Refactoring Strategy:** Extract classes using **Composition and Dependency Injection**.
- **The Monster Service:** A `@Service` with 10+ injected repositories is a clear sign of an SRP violation.
- **Testability Benefit:** Splitting classes allows unit tests to test business logic in $< 5\text{ms}$ with zero database or network mocks.

**Common Follow-up Questions:**
- *"How do you test a class that violates SRP versus one that follows SRP?"* → Testing a class that violates SRP requires configuring complex integration test contexts, in-memory databases, and mock network servers; testing an SRP-compliant class requires only pure JUnit 5 unit tests with 1–2 simple mocks.
- *"Can an SRP violation cause concurrency and performance bugs?"* → Yes; when multiple unrelated operations are bundled in one transactional method, locks on the database are held for unnecessary lengths (e.g. holding a database row lock while waiting for a slow SendGrid HTTP email response).
- *"How do you convince a team to refactor an existing 2,000-line God Class?"* → Highlight git merge conflict frequency, high defect rates when fixing unrelated bugs, and the inability to write reliable automated tests.

**Red Flags (DO NOT Say):**
- ❌ *"It is fine to put JDBC database code inside your Spring REST `@RestController`."* (Severe layering and SRP violation).
- ❌ *"Putting everything into one giant Service class is faster because Spring creates fewer beans."* (Bean instantiation overhead is negligible; monolithic classes destroy maintainability).
- ❌ *"If a class is under 500 lines of code, it can never violate SRP."* (A 50-line class that does 3 unrelated tasks still violates SRP).
