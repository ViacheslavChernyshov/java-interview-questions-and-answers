# Are Record Fields final?

---

## 🟢 Junior Level

**YES, absolutely!** All component fields declared in a `record` header are **implicitly `private final`**:

```java
public record User(String name, int age) {}

User user = new User("Alice", 28);

// ❌ COMPILE ERROR: Cannot assign a value to final variable:
// user.name = "Bob";
// user.age = 30;
```

```
  Key Invariants:
  • You do not need to write the `final` keyword in the header; it is automatically added by the compiler.
  • No setters are generated.
  • Once instantiated, the reference pointers stored in the record cannot be changed.
```

---

## 🟡 Middle Level

### Shallow Immutability vs. Deep Immutability

> [!WARNING]
> While record field references are `final`, **Records are only SHALLOWLY immutable by default**!
>
> If a record component holds a mutable object (such as an `ArrayList`, `HashMap`, or `Date`), an external caller can still mutate the internal elements of that object!

```java
// ⚠️ SHALLOW IMMUTABILITY HAZARD:
public record UserAccount(String username, List<String> roles) {}

List<String> mutableRoles = new ArrayList<>(List.of("USER"));
UserAccount account = new UserAccount("alice", mutableRoles);

// 💥 External mutation breaks immutability:
mutableRoles.add("ADMIN");                   // Mutated via external reference!
account.roles().add("SUPERUSER");            // Mutated via record getter!

System.out.println(account.roles());         // Prints: [USER, ADMIN, SUPERUSER]!
```

#### Senior Solution: Deep Immutability via Compact Constructor

```java
public record UserAccount(String username, List<String> roles) {

    // 🛡️ Compact constructor guarantees DEEP immutability via List.copyOf():
    public UserAccount {
        roles = (roles == null) ? List.of() : List.copyOf(roles); // Unmodifiable snapshot!
    }
}

// account.roles().add("HACKER"); -> Throws UnsupportedOperationException!
```

## 🔴 Senior Level

### Reflection Protection: Records are Immune to Reflection Hacks

In regular Java classes, developers could historically bypass `final` using `setAccessible(true)`:

```java
// On a Regular Java Class:
Field field = RegularClass.class.getDeclaredField("name");
field.setAccessible(true);
field.set(instance, "Hacked"); // Allowed in legacy Java!
```

In **Java 16+**, the JVM explicitly **prohibits mutating Record fields via Reflection**:

```java
Field field = User.class.getDeclaredField("name");
field.setAccessible(true);

// 💥 THROWS IllegalAccessException: "cannot assign instance field of a record class"!
field.set(user, "Hacked");
```

### Java Memory Model (JMM) Freeze Barrier

Because all record components are `final`, the HotSpot JVM enforces **JMM §17.5 Final Field Freeze semantics**:
- As soon as the record constructor finishes, a `StoreStore` memory barrier guarantees that all fields are visible to all CPU cores.
- Records can be shared safely across concurrent threads without locks, synchronization, or `volatile` modifiers.

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Implicitly Final:** All record components are automatically `private final`.
- **Shallow vs Deep:** Records are only shallowly immutable by default; mutable members (`List`, `Map`, arrays) must be defended using `List.copyOf()` or array cloning in compact constructors.
- **Reflection Immunity:** Java 16+ explicitly forbids modifying record fields via reflection (`IllegalAccessException`).
- **Thread Safety:** Because fields are final, records are inherently thread-safe and safe to publish across threads without locks.

**Common Follow-up Questions:**
- *"Can you declare a record field as `non-final` or `volatile`?"* → No; record header components are unconditionally `private final`; keywords like `volatile` or `transient` are illegal in record headers.
- *"How do you handle defensive copying for arrays in records?"* → In compact constructor: `payload = (payload == null) ? new byte[0] : payload.clone();` and override accessor: `public byte[] payload() { return this.payload.clone(); }`.
- *"Can a record contain a mutable static variable?"* → Yes, static fields can be mutable (e.g. `public static int counter`), but this should be avoided to preserve architectural purity.

**Red Flags (DO NOT Say):**
- ❌ *"Records are deeply immutable automatically even if they contain an ArrayList."* (They are only shallowly immutable; collections require `List.copyOf()`).
- ❌ *"You can change record fields at runtime using reflection with `setAccessible(true)`."* (The JVM explicitly blocks reflection field assignment on records).
- ❌ *"You must explicitly write `final` before every component in `record User(final String name)`."* (The `final` keyword is redundant and implicitly applied).
