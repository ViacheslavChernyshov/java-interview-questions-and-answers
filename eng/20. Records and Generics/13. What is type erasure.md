# What is Type Erasure?

---

## 🟢 Junior Level

**Type Erasure** is the process by which the Java compiler (`javac`) **removes all generic type parameters and type arguments** during compilation into bytecode:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 💻 Developer Source Code (.java)                        │ ⚙️ Compiled JVM Bytecode (.class)                       │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ `List<String> strings = new ArrayList<>();`             │ `List strings = new ArrayList();`                       │
  │ `List<Integer> numbers = new ArrayList<>();`            │ `List numbers = new ArrayList();`                       │
  │ `strings.add("Hello");`                                 │ `strings.add("Hello");`                                 │
  │ `String s = strings.get(0);`                            │ `String s = (String) strings.get(0);`                   │
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

> [!NOTE]
> At runtime inside the JVM, **`List<String>` and `List<Integer>` are the EXACT same class (`List.class`)**! The JVM does not know or preserve the generic type argument.

## 🟡 Middle Level

### The 3 Rules of Type Erasure Execution

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────┐
  │ # │ Compilation Step                 │ Compiler Bytecode Transformation                                │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 1 │ **Unbounded Parameters `<T>`**   │ Replaced with `java.lang.Object`.                               │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 2 │ **Bounded Parameters `<T extends │ Replaced with the **first bound** (`Number` or `Comparable`).   │
  │   │  Bound>`**                       │                                                                 │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 3 │ **Synthetic Bridge Methods**     │ Synthesized in subclasses to preserve polymorphism in bytecode. │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────┘
```

```java
// Source Code:
public class NumberBox<T extends Number> {
    private T value;
    public T getValue() { return value; }
}

// Bytecode after Type Erasure (T erased to Number):
public class NumberBox {
    private Number value;
    public Number getValue() { return value; }
}
```

### Why Did Java Choose Type Erasure?

When Generics were added in **Java 5 (2004)**, the primary goal was **100% backward compatibility**:
- Legacy code compiled on Java 1.4 had to run without recompilation on the Java 5 JVM.
- New generic collections had to seamlessly accept and interact with legacy raw collection libraries without duplicating entire bytecode runtime classes (unlike C++ templates or C# reified generics).

## 🔴 Senior Level

### The 7 Compile-Time Consequences of Type Erasure

Because type arguments are erased at runtime, the Java compiler strictly prohibits several operations:

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────┐
  │ # │ Prohibited Operation             │ Why It Is Banned / Compiler Error                               │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 1 │ ❌ `new T()`                     │ Type `T` is unknown at runtime; JVM cannot know constructor.    │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 2 │ ❌ `new T[10]`                   │ Cannot allocate typed array without knowing exact reified type. │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 3 │ ❌ `obj instanceof List<String>` │ Erased to `List`; must use `instanceof List<?>` instead.        │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 4 │ ❌ `T.class`                     │ `T.class` does not exist; pass `Class<T> clazz` token instead.  │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 5 │ ❌ `static T item;`              │ Static state is shared across all instances; `T` is per-instance│
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 6 │ ❌ Overloading with same erasure │ `void sort(List<String> l)` vs `void sort(List<Integer> l)`     │
  │   │                                  │ both erase to `void sort(List l)` (Duplicate Method Error).     │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 7 │ ❌ `catch (T ex)`                │ Cannot catch generic exception types because type is erased.    │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────┘
```

### Type Tokens: How to Recover Erased Types at Runtime

When frameworks (Jackson, Spring, Guice) need to know generic types at runtime, they use **Super Type Tokens** (anonymous subclasses that preserve signature metadata in class bytecode tables):

```java
// Jackson TypeReference retains erased generic type in Class Signature attribute:
TypeReference<List<UserDTO>> typeRef = new TypeReference<List<UserDTO>>() {};
List<UserDTO> users = objectMapper.readValue(json, typeRef);
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** The compiler strips away all generic type parameters and arguments during compilation to bytecode.
- **Erasure Targets:** Unbounded `<T>` erases to `Object`; bounded `<T extends Number>` erases to `Number`.
- **Reason:** 100% backward compatibility with pre-Java 5 libraries and JVM runtimes.
- **Runtime Identity:** `new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` (Both return `ArrayList.class`).
- **Forbidden:** `new T()`, `new T[]`, `T.class`, `instanceof List<String>`, static `T` fields, and same-erasure method overloading.

**Common Follow-up Questions:**
- *"Is all generic type information lost after compilation?"* → Generic type information is erased from *executable code*, but class/method signatures and field declarations retain generic metadata in the **`Signature` attribute** of the `.class` file (which can be read via Reflection via `getGenericSuperclass()`).
- *"What is a Bridge Method?"* → A synthetic method generated by `javac` when a generic class is extended or implements a generic interface, ensuring polymorphic dispatch still works after type erasure.
- *"How does C# generics differ from Java generics?"* → C# uses **Reified Generics** (types are preserved at runtime in the CLR and specialized for value types), whereas Java uses Type Erasure.

**Red Flags (DO NOT Say):**
- ❌ *"The JVM allocates a different class in memory for `ArrayList<String>` and `ArrayList<Integer>`."* (Both share the exact same `ArrayList.class` raw runtime type).
- ❌ *"Type erasure was introduced in Java 8."* (It was introduced in Java 5 alongside Generics).
- ❌ *"You can check if an object is `instanceof Map<String, Integer>` at runtime."* (Type parameters are erased; `instanceof Map<?, ?>` is the only legal syntax).
