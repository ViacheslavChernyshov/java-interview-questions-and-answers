# Can You Use Record as a Key in HashMap?

---

## 🟢 Junior Level

**YES! Java Records are the industry GOLD STANDARD for composite keys in `HashMap` and `HashSet`:**

```java
// 🚀 Clean, type-safe composite cache key:
public record CacheKey(String tenantId, String entityType, Long entityId) {}

Map<CacheKey, UserData> cache = new HashMap<>();

CacheKey key1 = new CacheKey("tenant-A", "USER", 1001L);
cache.put(key1, new UserData("Alice"));

// Lookup with a new instance containing identical values succeeds immediately:
CacheKey key2 = new CacheKey("tenant-A", "USER", 1001L);
UserData result = cache.get(key2); // 🟢 Returns UserData("Alice")!
```

```
  Why Records are Ideal Map Keys:
  • 🔒 Reference Immutability: Header fields are `private final`, protecting hash bucket placement.
  • ⚖️ Auto Contract: Compiler-generated `equals()` and `hashCode()` strictly obey the Java hashCode contract.
  • 🧼 Type Safety: Eliminates hacky string concatenations like `tenantId + ":" + type + ":" + id`.
```

## 🟡 Middle Level

### The 2 Critical Production Hazards with Record Keys

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────┐
  │ # │ Key Hazard                       │ Cause & Solution                                                │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 1 │ 💥 **Mutable Collection Member** │ If a record holds an `ArrayList`, mutating the list alters the  │
  │   │                                  │ record's `hashCode()`, **orphaning the entry** in the Map!      │
  │   │                                  │ 🟢 **Solution:** `List.copyOf()` in compact constructor.        │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 2 │ 💥 **Array Component Member**    │ Array components use reference identity (`==`) in auto-generated│
  │   │                                  │ `equals()`, causing lookups with identical arrays to fail!      │
  │   │                                  │ 🟢 **Solution:** Override `equals` using `Arrays.equals()`.     │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────┘
```

### Hazard 1: Mutable Collection Key Mutation

```java
// ❌ DANGEROUS: Record key with mutable list:
public record FilterKey(String category, List<String> tags) {}

List<String> tags = new ArrayList<>(List.of("java", "spring"));
FilterKey key = new FilterKey("tech", tags);
map.put(key, "Cached Article");

// 💥 External mutation changes the hash code:
tags.add("microservices"); 

// The map searches the WRONG BUCKET because hashCode() changed!
System.out.println(map.get(key)); // 💥 NULL! (Ghost memory leak!)
```

```java
// 🟢 SENIOR FIX: Defensive copying in compact constructor:
public record FilterKey(String category, List<String> tags) {
    public FilterKey {
        tags = (tags == null) ? List.of() : List.copyOf(tags); // Truly immutable!
    }
}
```

## 🔴 Senior Level

### Performance: HotSpot JIT Hash Code Inlining

In high-throughput key lookups (e.g. 1,000,000 lookups/second in local in-memory caches):
- Because record classes are **implicitly `final`**, the HotSpot JIT compiler performs **Class Hierarchy Analysis (CHA)**.
- Method calls to `key.hashCode()` and `key.equals()` are **monomorphically inlined** directly into machine assembly without virtual method table (vtable) pointer lookups, achieving near-native struct comparison speeds.

```
  [HashMap.get()] ──(JIT Inlined)──► [Direct primitive & object comparison in CPU registers!]
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Answer:** Yes, records are the premier choice for composite keys in `HashMap` and `HashSet`.
- **Requirements Satisfied:** Immutability (`final` fields) and rigorous `equals()` / `hashCode()` contract synchronization.
- **Collection Hazard:** If the record contains a collection, enforce deep immutability using `List.copyOf()` or `Set.copyOf()` in a compact constructor.
- **Array Hazard:** If the record contains an array, manually override `equals()` and `hashCode()` with `Arrays.equals` and `Arrays.hashCode`.

**Common Follow-up Questions:**
- *"What happens if a record's `hashCode()` mutates after being inserted into a HashMap?"* → The entry remains in its original bucket based on the old hash code; future `map.get()` calls compute the new hash code, look in the wrong bucket, and return `null`, creating a memory leak.
- *"Does a record cache its `hashCode()` like `java.lang.String` does?"* → No; records recompute `hashCode()` on each call by default. If the record has many fields and is hashed millions of times, you can override `hashCode()` with a cached field if necessary.
- *"Can records be used as keys in `TreeMap`?"* → Yes, provided the record implements `Comparable<T>` or a custom `Comparator` is passed to the `TreeMap`.

**Red Flags (DO NOT Say):**
- ❌ *"Records cannot be used as HashMap keys because they don't have getters."* (HashMap uses `equals()` and `hashCode()`, not getters).
- ❌ *"A record key is always 100% immutable regardless of what components it holds."* (If it holds a mutable list or array, the key can be mutated from outside unless defensive copying is used).
- ❌ *"You must always write custom `equals` and `hashCode` for every record used in a Map."* (Compiler-generated `equals` and `hashCode` are already optimal unless arrays are involved).
