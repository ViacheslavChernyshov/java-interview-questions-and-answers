# What Are the Main Differences Between Record and Regular Class?

---

## 🟢 Junior Level

The core difference between a `record` and a regular Java class is that a **Record is a transparent, immutable data carrier**, whereas a **Regular Class is a general-purpose abstraction that encapsulates mutable state and behavior**:

```
  ┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────┐
  │ 📦 Java Record                                          │ 🏛️ Regular Java Class                                   │
  ├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────┤
  │ • Declared in 1 line: `record Point(int x, int y) {}`   │ • Requires 30+ lines of field, constructor, and method  │
  │ • Implicitly **`final`** (cannot be subclassed).        │   boilerplate.                                          │
  │ • All state components are strictly **`private final`**.│ • Can be extensible or mutable.                         │
  │ • Component accessors have **no `get` prefix** (`x()`). │ • Typically uses JavaBean conventions (`getX()`).       │
  │ • Automatic value-based `equals`, `hashCode`, `toString`│ • Must manually override `equals`, `hashCode`, `toString│
  └─────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────┘
```

## 🟡 Middle Level

### The Definitive Comparison Matrix

```
  ┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────────────────┐
  │ Characteristic               │ Java Record (`record`)           │ Regular Java Class (`class`)                     │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Direct Superclass**        │ Strictly `java.lang.Record`      │ `java.lang.Object` (or any custom class)         │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Class Extensibility**      │ Implicitly `final`               │ Extensible by default (unless marked `final`)    │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Instance Fields**          │ Only header components permitted │ Can declare arbitrary instance fields            │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Field Mutability**         │ Implicitly `private final`       │ Can be `public`, `private`, `volatile`, mutable  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Accessor Convention**      │ Component name directly (`id()`) │ JavaBean convention (`getId()`, `isDone()`)      │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Constructors**             │ Auto-synthesized **Canonical**   │ Default no-arg constructor if none defined       │
  │                              │ and **Compact Constructor**      │                                                  │
  ├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────────────────┤
  │ **Custom Secondary Ctors**   │ **MUST** delegate via `this(...)`│ Can directly initialize fields                   │
  └──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────────────────┘
```

### Constructor Delegation Invariant

In a record, any secondary constructor **must explicitly delegate** to the canonical constructor:

```java
public record User(String username, int age, String status) {

    // 🟢 Secondary constructor MUST delegate to canonical constructor:
    public User(String username) {
        this(username, 0, "ACTIVE"); // Valid delegation
    }

    // ❌ COMPILE ERROR: Cannot bypass canonical constructor or set fields directly!
    // public User(int age) { this.age = age; }
}
```

## 🔴 Senior Level

### Safe Serialization Architecture

Regular Java classes have a major security and consistency flaw in classic Java serialization: deserialization (`readObject`) uses native memory allocation that **bypasses all constructors**, allowing malicious byte streams to inject corrupted state.

In contrast, **Records cannot bypass constructors during deserialization**:
1. Java Object Serialization extracts components from the stream.
2. It passes them directly through the **Canonical Constructor**!
3. All validation and defensive copying rules defined in your compact constructor are **guaranteed to execute during deserialization**, eliminating an entire class of security vulnerabilities.

```
  Classic Deserialization vs Record Deserialization:
  • Regular Class ➔ Allocates memory via Unsafe ➔ Injects fields directly (Bypasses validation constructor!)
  • Java Record   ➔ Reads components ➔ Invokes Canonical Constructor (Executes validation & defensive copies!)
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Core Role:** Records are pure, transparent, immutable data carriers subclassing `java.lang.Record`.
- **Extensibility:** Records cannot extend other classes and cannot be inherited (always `final`).
- **Fields:** Only header components are allowed as instance fields; all are `private final`.
- **Accessors:** Named without `get` (e.g. `order.id()`).
- **Constructor Delegation:** Custom constructors must invoke `this(...)` to reach the canonical constructor.
- **Serialization Safety:** Deserialization is guaranteed to invoke the canonical constructor, preventing constructor bypass attacks.

**Common Follow-up Questions:**
- *"Can a record contain static fields and static methods?"* → Yes; records can declare static constants (`public static final String DEFAULT = "X"`) and static utility factory methods.
- *"Can a record implement multiple interfaces?"* → Yes; while multiple class inheritance is impossible, records can implement any number of interfaces (e.g. `implements Serializable, Comparable<T>`).
- *"Why does a record prohibit extra instance fields outside the header?"* → Because a record's entire contract (identity, constructor, equals, serialization) must be 100% defined by its component header.

**Red Flags (DO NOT Say):**
- ❌ *"Records can declare additional non-static instance fields in the body."* (Records strictly forbid non-static instance fields outside the header).
- ❌ *"Records generate setters so you can mutate fields."* (Records are strictly immutable and have no setters).
- ❌ *"A record can extend an abstract class like `BaseEntity`."* (All records already extend `java.lang.Record` and cannot extend another class).
