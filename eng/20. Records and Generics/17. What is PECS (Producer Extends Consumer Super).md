# What is PECS (Producer Extends Consumer Super)?

---

## 🟢 Junior Level

**PECS** is the golden mnemonic created by **Joshua Bloch** (*Effective Java*, Item 31) to guide when to use `extends` versus `super` wildcards in method signatures:

```
  ┌───────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │                                    🎯 THE PECS PRINCIPLE                                                  │
  ├───────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │  • 📥 **P**roducer **E**xtends ➔ If the parameter **PRODUCES / SUPPLIES** data to your method,            │
  │                                   use `<? extends T>`. (You only READ from it).                           │
  │  • 📤 **C**onsumer **S**uper   ➔ If the parameter **CONSUMES / RECEIVES** data from your method,          │
  │                                   use `<? super T>`. (You WRITE into it).                                 │
  └───────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

```java
// 1. PRODUCER: Reads numbers out of the list to calculate a sum:
public static double sumOfList(List<? extends Number> producer) {
    double total = 0.0;
    for (Number n : producer) { // 🟢 Read operation
        total += n.doubleValue();
    }
    return total;
}

// 2. CONSUMER: Writes generated integers into the destination list:
public static void generateNumbers(List<? super Integer> consumer, int count) {
    for (int i = 1; i <= count; i++) {
        consumer.add(i); // 🟢 Write operation
    }
}
```

## 🟡 Middle Level

### The API Flexibility Test: Why PECS is Critical

Without PECS, generic collections are **strictly invariant**, making client code needlessly rigid:

```java
// ❌ RIGID API (No wildcards):
public class InventoryService {
    public void restock(List<Product> products) { ... }
}

List<ElectronicProduct> electronics = List.of(new Laptop(), new Phone());
// inventoryService.restock(electronics); // 🛑 COMPILE ERROR! List<ElectronicProduct> is NOT a List<Product>!
```

```java
// 🟢 FLEXIBLE SENIOR API (With PECS Producer Extends):
public class InventoryService {
    public void restock(List<? extends Product> products) { // 🚀 Producer: Reads products
        for (Product p : products) {
            database.save(p);
        }
    }
}

// Now works seamlessly with any product subclass:
inventoryService.restock(electronics); // 🟢 Compiles cleanly!
```

## 🔴 Senior Level

### The Masterpiece Signature: `Collections.max()`

The most sophisticated demonstration of PECS in the JDK standard library is `java.util.Collections.max()`:

```java
// JDK Standard Library Declaration:
public static <T extends Comparable<? super T>> T max(Collection<? extends T> coll)
```

```
  Deconstructing the Signature:
  1. `Collection<? extends T> coll`:
     • The input collection is a PRODUCER of elements to compare.
     • By PECS, it uses `? extends T`, allowing you to find the max of a `List<Integer>` or `List<Double>`.

  2. `<T extends Comparable<? super T>>`:
     • The elements must be comparable.
     • Why `Comparable<? super T>` instead of `Comparable<T>`?
     • Because a subclass `T` (e.g. `java.sql.Timestamp`) might inherit its `compareTo()` implementation 
       from an ancestor class (e.g. `java.util.Date implements Comparable<Date>`).
     • `Timestamp` implements `Comparable<Date>` (which is `Comparable<? super Timestamp>`)!
     • Without `? super T`, `Collections.max(timestamps)` would fail compilation!
```

### When NOT to Use Wildcards

```
  ┌───┬──────────────────────────────────┬─────────────────────────────────────────────────────────────────┐
  │ # │ Scenario                         │ Recommended Signature Rule                                      │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 1 │ **Both Read AND Write**          │ Do not use wildcards! Use exact type: `List<T> list`.           │
  ├───┼──────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ 2 │ **Method Return Types**          │ **NEVER** use wildcards in return types (`List<? extends User>`)│
  │   │                                  │ as it forces callers to deal with wildcards in their own code.  │
  └───┴──────────────────────────────────┴─────────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Cheat Sheet

**Must Know:**
- **Definition:** **P**roducer **E**xtends, **C**onsumer **S**uper.
- **Producer (`? extends T`):** Use when your method reads values out of the collection.
- **Consumer (`? super T`):** Use when your method writes/pushes values into the collection.
- **Both Read & Write:** Use exact parameterized type `<T>` without wildcards.
- **Return Types Rule:** Never return wildcard types (`List<?>` or `List<? extends T>`); always return concrete types (`List<T>`).

**Common Follow-up Questions:**
- *"Why should you never use wildcards in method return types?"* → Returning `List<? extends Product>` forces the caller to write wildcarded variables and forbids them from adding items to the returned list, polluting their API and codebase.
- *"Why is `Comparable<? super T>` used instead of `Comparable<T>`?"* → It allows types that inherit their `Comparable` implementation from a superclass (like `ScheduledFuture` inheriting from `Delayed`) to be compared without compilation errors.
- *"How does PECS relate to the Liskov Substitution Principle (LSP)?"* → PECS is the direct application of LSP to generic types: Covariant return types (producers) and Contravariant parameter types (consumers).

**Red Flags (DO NOT Say):**
- ❌ *"PECS stands for Parameter Extends Class Super."* (It stands for **Producer Extends, Consumer Super**).
- ❌ *"Always use `? extends` when you want to add elements to a collection."* (Adding elements requires `? super`).
- ❌ *"Return `List<? extends T>` from your service methods to make them more flexible."* (Return types should always be concrete, never wildcards).
