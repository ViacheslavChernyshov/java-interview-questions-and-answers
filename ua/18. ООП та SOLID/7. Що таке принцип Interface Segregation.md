# Що таке принцип Interface Segregation?

---

## 🟢 Junior Level

### Просте визначення

**Принцип розділення інтерфейсів (Interface Segregation Principle, ISP)** — це літера «I» в абревіатурі SOLID. Він стверджує:
> **Клієнти не повинні залежати від методів, які вони не використовують.**

**Клієнт** — це будь-який клас, який реалізує інтерфейс або викликає його методи. Якщо інтерфейс змушує клас створювати методи-заглушки, викидати `UnsupportedOperationException` або залежати від непотрібних йому функцій — принцип ISP порушено.

### Аналогія з реального життя

Уявіть **багатофункціональний швейцарський ніж** та **звичайну кухонну виделку**:
- Якщо вам в їдальні потрібна тільки виделка, щоб пообідати, але вам видають 5-кілограмову валізу з пилкою, штопором, ліхтариком і лазерною указкою — це незручно і надлишково.
- У програмуванні краще надати вузький інтерфейс `Eatable` з методом `eat()`, ніж гігантський інтерфейс `MultiTool`, що змушує кожного клієнта реалізовувати `sawWood()` та `openWine()`.

### Приклад порушення та виправлення

**❌ Погано (Fat / Жирний інтерфейс):**
```java
// Жирний інтерфейс змушує реалізовувати все підряд
public interface Worker {
    void work();
    void eat();
    void sleep();
}

// Робот не їсть і не спить, але змушений реалізувати методи!
public class RobotWorker implements Worker {
    @Override
    public void work() {
        System.out.println("Робот працює");
    }

    @Override
    public void eat() {
        // Заглушка або виняток — явна ознака порушення ISP!
        throw new UnsupportedOperationException("Роботи не їдять");
    }

    @Override
    public void sleep() {
        throw new UnsupportedOperationException("Роботи не сплять");
    }
}
```

**✅ Добре (Розділені інтерфейси):**
```java
// Вузькі, сфокусовані інтерфейси (Role Interfaces)
public interface Workable {
    void work();
}

public interface Feedable {
    void eat();
}

// Людина реалізує обидва інтерфейси:
public class HumanWorker implements Workable, Feedable {
    @Override
    public void work() { System.out.println("Людина працює"); }

    @Override
    public void eat() { System.out.println("Людина обідає"); }
}

// Робот реалізує тільки те, що реально виконує:
public class RobotWorker implements Workable {
    @Override
    public void work() { System.out.println("Робот працює без зупинок"); }
}
```

## 🟡 Middle Level

### Механіка на рівні JVM та вплив на Constant Pool

На рівні байт-коду та JVM великий інтерфейс (Fat Interface) створює зайві залежності в **Constant Pool** кожного класу-реалізатора:
- **Constant Pool**: таблиця посилань у `.class` файлі. Кожен метод інтерфейсу додає запис.
- **vtable / itable**: таблиці віртуальних методів та інтерфейсів. Більше методів = більша таблиця = повільніший пошук при поліморфному виклику (`invokeinterface`).
- Головна проблема — архітектурна: «забруднення» коду методами-заглушками та зайві залежності між модулями.

### Role Interfaces проти Header Interfaces

#### 1. Header Interfaces (Антипатерн)
Створення інтерфейсу `IMyService` для класу `MyService`, який просто сліпо дублює всі його публічні методи.
- **Проблема**: Це не абстракція, а просте дублювання. При додаванні методу в сервіс він додається в інтерфейс, і всі клієнти змушені перекомпілюватися.

#### 2. Role Interfaces (Senior-підхід)
Інтерфейс повинен описувати **роль** об'єкта в конкретному контексті взаємодії:
- Один клас може реалізовувати 10 маленьких інтерфейсів-ролей (`Serializable`, `Cloneable`, `Comparable`, `AutoCloseable`).
- Клієнт (наприклад, принтер) вимагає тільки контракт `Printable`, і йому байдуже, чи вміє об'єкт зберігатися в БД або серіалізуватися в JSON.

### Ознаки порушення ISP

1. **`UnsupportedOperationException`**: Метод реалізовано тільки тому, що інтерфейс змусив, але реальної логіки для нього немає.
2. **Порожні методи-заглушки**: Метод нічого не робить (`// do nothing`), повертає `null` або `0`.
3. **Роздуті тестові моки**: Для тестування одного методу доводиться налаштовувати 20 моків у `when(...).thenReturn(...)`, хоча тестований код викликає тільки одну функцію.

### Рішення через патерн Adapter

Якщо ви працюєте зі сторонньою бібліотекою з «жирним» інтерфейсом, який неможливо змінити, використовуйте **Adapter**:

```java
// Сторонній жирний інтерфейс
public interface ThirdPartyCloudStorage {
    void uploadFile(byte[] data);
    void deleteFile(String id);
    void listFiles();
    void billingReport(); // Нашому додатку це не потрібно
}

// Наш чистий вузький інтерфейс
public interface DocumentUploader {
    void upload(byte[] data);
}

// Адаптер ізолює систему від жирного інтерфейсу
public class CloudStorageAdapter implements DocumentUploader {
    private final ThirdPartyCloudStorage cloudStorage;

    public CloudStorageAdapter(ThirdPartyCloudStorage cloudStorage) {
        this.cloudStorage = cloudStorage;
    }

    @Override
    public void upload(byte[] data) {
        cloudStorage.uploadFile(data);
    }
}
```

## 🔴 Senior Level

### Продуктивність і Highload

- **Binary Compatibility**: ISP безпосередньо захищає бінарну сумісність модулів. Якщо додано метод у вузький інтерфейс `PaymentProcessor`, це зачіпає тільки модулі еквайрингу, а не модулі каталогу, доставки та аналітики.
- **Megamorphic Call Sites**: Якщо інтерфейс занадто широкий і має сотні різнорідних реалізацій, JVM JIT-компілятор не зможе виконати інлайнінг у точках виклику `invokeinterface`, переходячи в режим `megamorphic dispatch`. Вузькі інтерфейси підвищують імовірність мономорфних/біморфних викликів, дозволяючи JIT генерувати прямий машинний код.

### Default Methods та функціональні інтерфейси

1. **Default Methods (Java 8+)**: Дозволяють додавати методи в інтерфейси без зламу наявних реалізацій, але **не вирішують проблему ISP**. Інтерфейс однаково залишається перевантаженим, засмічуючи підказки IDE та API клієнта.
2. **Single Abstract Method (SAM)**: Інтерфейси з одним методом (`Runnable`, `Callable`, `Function`, `Consumer`) ідеально відповідають ISP і підтримують лямбда-синтаксис.

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- ISP: клієнти не повинні залежати від методів, які вони не використовують.
- Жирний інтерфейс (Fat Interface) змушує писати заглушки та кидати `UnsupportedOperationException`.
- Role Interfaces > Header Interfaces: інтерфейс описує роль (`Printable`, `AutoCloseable`), а не копіює методи одного класу.
- Інтерфейси належать викликаючому коду (клієнту), а не сервісу-реалізації.
- Патерн Adapter допомагає ізолювати сторонні жирні контракти.
- Default Methods у Java 8+ не усувають порушення ISP, а лише приховують помилки компіляції.

**Часті уточнюючі запитання:**
- **У чому різниця між Header Interface та Role Interface?** — Header сліпо дублює методи класу (антипатерн), Role описує конкретну роль об'єкта у взаємодії.
- **Як ISP полегшує тестування?** — Зменшує кількість моків: мокається тільки 1 необхідний метод, а не 20 непотрібних.
- **Чи потрібно розділяти інтерфейс з 2 методами?** — Ні, якщо методи семантично пов'язані (наприклад, `hasNext()` і `next()`).

**Червоні прапорці (НЕ говорити):**
- ❌ *«Для кожного класу обов'язково треба створити інтерфейс IMyClass»* (це Header Interface).
- ❌ *«Default methods повністю вирішують проблему ISP»* (інтерфейс усе одно залишається перевантаженим).
- ❌ *«Якщо метод інтерфейсу не потрібен, достатньо просто кинути UnsupportedOperationException»*.
