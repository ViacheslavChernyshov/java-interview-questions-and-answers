# Навіщо взагалі потрібні принципи SOLID?

---

## 🟢 Junior Level

### Що таке SOLID простими словами

**SOLID** — це акронім із п'яти фундаментальних принципів об'єктно-орієнтованого проектування, сформульованих Робертом Мартіном (Дядьком Бобом):
- **S** — Single Responsibility Principle (Принцип єдиної відповідальності)
- **O** — Open/Closed Principle (Принцип відкритості / закритості)
- **L** — Liskov Substitution Principle (Принцип підстановки Лісков)
- **I** — Interface Segregation Principle (Принцип розділення інтерфейсів)
- **D** — Dependency Inversion Principle (Принцип інверсії залежностей)

### Навіщо вони потрібні

Уявіть, що ви будуєте будинок із модульних блоків LEGO або склеюєте його намертво смолою:
- **Без SOLID (спагеті-код)**: Усі деталі намертво зчеплені. Якщо потрібно замінити лампочку в кімнаті, доводиться ламати перекриття та перекладати половину фундаменту.
- **З SOLID**: Кожна деталь автономна, з'єднується через стандартизовані інтерфейси. Ви можете замінити перегорілий блок за 5 секунд, не ризикуючи обвалити всю будівлю.

### 4 симптоми «поганого дизайну», з якими бореться SOLID

1. **Rigidity (Жорсткість)**: Систему важко змінювати. Одне невелике виправлення спричиняє лавину правок у десятках інших класів.
2. **Fragility (Крихкість)**: Зміна в одному модулі несподівано ламає роботу зовсім не пов'язаної частини програми.
3. **Immobility (Нерухомість)**: Неможливо перевикористати модуль в іншому проекті, оскільки він намертво приріс до поточного оточення.
4. **Viscosity (В'язкість)**: Розробнику простіше й швидше написати «милицю» (костиль) в обхід архітектури, ніж зробити правильне масштабоване рішення.

## 🟡 Middle Level

### Економічний сенс SOLID: Total Cost of Ownership (TCO)

У комерційній розробці SOLID — це передусім **інструмент зниження фінансових витрат**:
- Написання першої версії коду займає лише ~20% від загальних витрат на проект.
- Решта 80% — це супровід, розвиток, виправлення багів і рефакторинг упродовж наступних років.
- SOLID вимагає трохи більше часу на старті (проектування інтерфейсів, композиція), але багаторазово окупається, суттєво знижуючи вартість додавання кожної нової фічі.

### SOLID у мікросервісах та розподілених системах

| Принцип | На рівні класів | На рівні мікросервісів |
|---|---|---|
| **SRP** | Клас вирішує одну задачу | Сервіс відповідає за один Bounded Context (DDD) |
| **OCP** | Нова логіка = новий клас (Strategy) | Розширення API через нові ендпоінти без зламу старих клієнтів |
| **LSP** | Підклас не ламає контракт предка | Нова версія сервісу суворо дотримується зворотної сумісності контракту API |
| **ISP** | Вузькі спеціалізовані інтерфейси | Клієнти не отримують зайвих полів (BFF, GraphQL, Consumer-Driven Contracts) |
| **DIP** | Залежність від інтерфейсів через DI | Сервіси спілкуються через стабільні контракти (OpenAPI, gRPC Protobuf, Events) |

## 🔴 Senior Level

### Метрики якості коду та діагностика

1. **LCOM (Lack of Cohesion in Methods)**: Вимірює ступінь згуртованості методів класу з його полями. Значення `LCOM > 0.8` вказує на те, що клас є God Object і грубо порушує SRP.
2. **Afferent (Ca) та Efferent (Ce) Coupling**: Визначають вхідні та вихідні залежності. Показник нестабільності $I = Ce / (Ca + Ce)$ демонструє стійкість модуля до змін.
3. **Cognitive & Cyclomatic Complexity**: Вимірюються в SonarQube. Складність методів $> 15$ свідчить про спагеті-логіку та порушення SRP/OCP.

### Запобігання догматизму: Противаги SOLID (KISS, YAGNI, DRY)

Сліпе застосування SOLID без оцінки контексту веде до **Over-engineering**:
- **Interface Explosion**: Створення десятків одноразових інтерфейсів із 1 методом порушує **YAGNI**.
- **Over-Abstraction**: 10 шарів маперів і DTO для простої операції створюють оверхед на CPU та пам'ять (GC pressure).
- **Свідомі винятки з SOLID**: Прототипи, MVP для швидкої перевірки гіпотез, разові міграційні скрипти та екстрені Production Hotfix-патчі.

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- SOLID бореться з 4 вадами поганого дизайну: Rigidity (жорсткість), Fragility (крихкість), Immobility (нерухомість), Viscosity (в'язкість).
- SOLID знижує Total Cost of Ownership (TCO) системи, спрощуючи підтримку коду на довгій дистанції.
- Принципи масштабуються з ООП на рівень мікросервісної архітектури (Bounded Contexts, API contracts).
- Противаги SOLID для захисту від over-engineering: **KISS**, **YAGNI**, **DRY**.
- Метрики якості: LCOM (cohesion), Cyclomatic Complexity (SonarQube), Coupling.

**Часті уточнюючі запитання:**
- **Коли SOLID — це over-engineering?** — Для простих скриптів, короткоживучих прототипів, MVP або коли кількість класів/інтерфейсів невиправдано ускладнює читання без очевидної бізнес-вигоди.
- **Який принцип SOLID найважливіший?** — SRP (Single Responsibility) та DIP (Dependency Inversion), оскільки вони формують фундамент модульності й тестування.

**Червоні прапорці (НЕ говорити):**
- ❌ *«Я завжди створюю інтерфейси для 100% класів у будь-якому проекті, навіть для простих утиліт»* (ознака over-engineering).
- ❌ *«SOLID потрібен лише для того, щоб код виглядав красиво»* (це передусім інженерний інструмент зниження вартості змін).
