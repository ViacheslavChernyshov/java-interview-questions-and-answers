# Як SOLID допомагає в тестуванні коду?

---

## 🟢 Junior Level

### Просте пояснення

Принципи SOLID часто називають **«Design for Testability» (Проектування для тестованості)**.
- Якщо код написаний без дотримання SOLID (спагеті з викликами `new` всередині методів, статичні зв'язки, класи на 2000 рядків), написати для нього швидкий ізольований модульний тест (Unit Test) майже неможливо.
- Якщо код спроектовано за SOLID, кожен клас ізольований, залежності передаються ззовні (DI), а логіка розбита на невеликі передбачувані блоки. Тестувати такий код легко і швидко.

### Аналогія з реального життя

Уявіть перевірку працездатності **двигуна автомобіля**:
- **Без SOLID**: Двигун намертво вварений усередину кузова, з'єднаний безпосередньо з коробкою передач і баком. Щоб перевірити одну свічку запалювання, потрібно виїжджати на полігон і розганяти всю машину.
- **З SOLID**: Двигун зібраний із модульних блоків. Ви можете зняти стартер, поставити його на лабораторний тестовий стенд, подати струм і за 5 секунд перевірити окремо від решти авто.

### Приклад коду до та після SOLID

**❌ Погано (Неможливо протестувати ізольовано):**
```java
public class OrderService {
    // Пряме створення залежностей: реальна БД та реальний SMS-шлюз!
    public void createOrder(String userPhone, BigDecimal amount) {
        DatabaseConnection db = new DatabaseConnection("prod-db.host"); // Реальне підключення!
        db.saveOrder(userPhone, amount);

        SmsGateway sms = new SmsGateway("api-secret-key"); // Відправка реального SMS зі списанням грошей!
        sms.send(userPhone, "Order created!");
    }
}
// Щоб протестувати цей метод, потрібна піднята робоча база даних і гроші на балансі SMS-сервісу!
```

**✅ Добре (Легко протестувати з мок-об'єктами):**
```java
public class OrderService {
    private final OrderRepository orderRepository;
    private final NotificationService notificationService;

    // Залежності передаються ззовні (DIP / DI)
    public OrderService(OrderRepository orderRepository, NotificationService notificationService) {
        this.orderRepository = orderRepository;
        this.notificationService = notificationService;
    }

    public void createOrder(String userPhone, BigDecimal amount) {
        orderRepository.save(userPhone, amount);
        notificationService.notify(userPhone, "Замовлення створено!");
    }
}

// Unit-тест виконується за мілісекунди без зовнішніх систем:
class OrderServiceTest {
    @Test
    void shouldCreateOrderSuccessfully() {
        OrderRepository mockRepo = mock(OrderRepository.class);
        NotificationService mockNotify = mock(NotificationService.class);
        OrderService service = new OrderService(mockRepo, mockNotify);

        service.createOrder("+380501112233", BigDecimal.valueOf(100));

        verify(mockRepo).save("+380501112233", BigDecimal.valueOf(100));
        verify(mockNotify).notify("+380501112233", "Замовлення створено!");
    }
}
```

## 🟡 Middle Level

### Внесок кожного з 5 принципів у тестованість

| Принцип | Роль у тестуванні | Практична вигода |
|---|---|---|
| **SRP** | **Ізоляція тестів** | У класу одна відповідальність ➔ один компактний тестовий клас без роздутих сценаріїв. |
| **OCP** | **Регресійна стабільність** | Новий функціонал = новий клас і нові тести. Не потрібно переписувати 100 старих тестів. |
| **LSP** | **Контрактна взаємозамінність** | Базовий набір тестів інтерфейсу гарантовано проходить для будь-якої його реалізації (Contract Tests). |
| **ISP** | **Мінімалістичні моки** | Вузькі інтерфейси позбавляють потреби мокати десятки непотрібних методів заради одного виклику. |
| **DIP** | **Підміна реальності** | Дозволяє миттєво підставити Mock-об'єкт замість реальної БД, сокета чи стороннього API. |

## 🔴 Senior Level

### Архітектурні індикатори та антипатерни тестування

1. **Mock-to-Assertion Ratio**: Якщо кількість рядків налаштування моків (`when(...).thenReturn(...)`) у 3 рази перевищує кількість перевірок (`assertEquals`, `verify`), тестований клас перевантажений обов'язками (порушення SRP).
2. **Test Fragility (Крихкість тестів)**: Якщо додавання одного поля в DTO ламає 40 тестів у непов'язаних модулях, це свідчить про порушення ISP та наявність паразитної зв'язаності (Tight Coupling).
3. **Піраміда тестування**: Дотримання SOLID зміщує баланс на користь швидких **Unit-тестів** (виконуються за секунди в пам'яті), мінімізуючи потребу у важких та повільних Integration/E2E тестах із підняттям Spring Context і Testcontainers.

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- SOLID перетворює закритий монолітний код на модульну систему, придатну для швидкого юніт-тестування (Design for Testability).
- **DIP** дозволяє підміняти важкі інфраструктурні залежності (БД, мережа) на Mock-об'єкти (Mockito).
- **ISP** мінімізує обсяг коду налаштування моків, виключаючи методи-пустишки.
- **SRP** гарантує, що тестовий клас буде сфокусованим і не ламатиметься від змін у сторонній бізнес-логіці.
- **OCP** захищає стару тестову базу від масової регресії при додаванні нових можливостей.

**Часті уточнюючі запитання:**
- **Як зрозуміти, що код погано спроектований, пишучи юніт-тести?** — Якщо для тесту одного простого методу потрібно налаштовувати 10 моків та ініціалізувати складне дерево об'єктів.
- **Як LSP допомагає у тестуванні?** — Дозволяє писати абстрактні контрактні тести (Contract Tests), які автоматично валідують усі підкласи та реалізації інтерфейсу.

**Червоні прапорці (НЕ говорити):**
- ❌ *«Якщо код важко протестувати, треба використовувати PowerMock для мокання приватних і статичних методів»* (це ознака поганої архітектури, яку слід рефакторити за SOLID).
- ❌ *«Усі тести обов'язково мають піднімати реальну базу даних і повний Spring Context»*.
