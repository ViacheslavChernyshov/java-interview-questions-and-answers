# Чи можна перевантажувати методи, що відрізняються лише дженерик-параметрами?

---

## 🟢 Junior Level

### Проста відповідь

**Ні, не можна.** Спроба оголосити такі методи призведе до помилки компіляції:
> *"name clash: methods have the same erasure"* (конфлікт імен: методи мають однакове стирання типів).

### Приклад проблеми

```java
public class Printer {
    // ❌ ПОМИЛКА КОМПІЛЯЦІЇ!
    public void print(List<String> list) {
        System.out.println("Рядки: " + list);
    }

    // ❌ ПОМИЛКА КОМПІЛЯЦІЇ: name clash!
    public void print(List<Integer> list) {
        System.out.println("Числа: " + list);
    }
}
```

### Чому так відбувається?

У Java дженерики існують тільки на етапі компіляції для суворої перевірки типів. У процесі компіляції працює механізм **Type Erasure (стирання типів)**:
- `List<String>` перетворюється на необроблений `List`
- `List<Integer>` перетворюється на необроблений `List`

Для віртуальної машини (JVM) у скомпільованому байт-коді обидва методи виглядають абсолютно однаково:
```java
void print(List list)
void print(List list)
```
Оскільки Java забороняє мати два методи з однаковим ім'ям та однаковим набором параметрів в одному класі, компілятор відхиляє такий код.

## 🟡 Middle Level

### Внутрішня будова: Байт-код і дескриптори методів

1. **Сигнатура в байт-коді**: У JVM методи ідентифікуються іменем та дескриптором (типами параметрів і повертаваного значення).
   - Дескриптор для `void print(List<String>)` після стирання — `(Ljava/util/List;)V`.
   - Дескриптор для `void print(List<Integer>)` після стирання — `(Ljava/util/List;)V`.
2. **Атрибут `Signature`**: Компілятор зберігає інформацію про дженерики у спеціальному атрибуті `Signature` в метаданих `.class` файлу.
   - Цей атрибут використовується компілятором для перевірки типів викликаючого коду і доступний через Reflection API (`Method.getGenericParameterTypes()`).
   - Однак JVM **не використовує** атрибут `Signature` для поліморфної диспетчеризації викликів (`invokevirtual`).

---

### Способи вирішення проблеми

#### 1. Різні, зрозумілі назви методів (Clean Code — Рекомендовано)
```java
public void printStrings(List<String> list) { /* ... */ }
public void printIntegers(List<Integer> list) { /* ... */ }
```

#### 2. Використання обгорток (Strongly Typed Wrappers)
Замість `List<String>` та `List<Integer>` створити окремі типи:
```java
public record StringBatch(List<String> items) {}
public record IntegerBatch(List<Integer> items) {}

public void print(StringBatch batch) { /* ... */ }
public void print(IntegerBatch batch) { /* ... */ }
```

## 🔴 Senior Level

### Bridge Methods та Synthetic-код

Коли клас успадковує параметризований generic-інтерфейс із конкретним типом, компілятор сам генерує спеціальний синтетичний метод — **Bridge Method**:

```java
public interface Consumer<T> {
    void accept(T t);
}

public class StringConsumer implements Consumer<String> {
    // Наш метод:
    public void accept(String s) { System.out.println(s); }

    // Згенерований компілятором Bridge Method у байт-коді:
    // public synthetic bridge void accept(Object obj) {
    //     this.accept((String) obj);
    // }
}
```
**Навіщо потрібен Bridge Method:** Щоб зберегти поліморфізм для викликів через базовий інтерфейс `Consumer raw = new StringConsumer(); raw.accept("test");`.

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- Перевантажувати методи, що відрізняються лише дженерик-параметрами, **не можна** через механізм **Type Erasure**.
- Помилка компіляції: `name clash: methods have the same erasure`.
- У байт-коді обидва методи отримують однаковий дескриптор `(Ljava/util/List;)V`.
- Найкраще рішення — дати методам різні смислові назви (`printStrings()`, `printIntegers()`) або створити Record-обгортки.
- **Bridge Methods** генеруються компілятором автоматично для збереження поліморфізму при наслідуванні generic-типів.

**Часті уточнюючі запитання:**
- **Чому інформація про generics зберігається в .class файлі, але методи все одно не можна перевантажити?** — Інформація про generics зберігається в атрибуті `Signature` для компілятора та Reflection, але диспетчеризація методів у JVM (`invokevirtual`) спирається виключно на стертий дескриптор.
- **Що таке Bridge Method?** — Синтетичний метод, що генерується компілятором для зв'язування стертого методу інтерфейсу (`Object`) з конкретним типом реалізації.

**Червоні прапорці (НЕ говорити):**
- ❌ *«У Java можна перевантажити метод, якщо один приймає `List<String>`, а інший `List<Integer>`»*.
- ❌ *«Generics існують у рантаймі JVM так само, як і в C#»* (у C# працює reification, у Java — type erasure).
