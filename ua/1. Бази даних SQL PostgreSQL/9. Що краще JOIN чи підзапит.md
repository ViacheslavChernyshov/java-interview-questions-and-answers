# Що краще: JOIN чи підзапит?

## 🟢 Junior Level

**Однозначної відповіді немає** — залежить від ситуації. У більшості сучасних баз даних (включаючи PostgreSQL) оптимізатор часто перетворює підзапити на JOIN, тому продуктивність може бути однаковою.

**Просте правило:**
- **JOIN** — коли потрібні дані з обох таблиць
- **Підзапит (EXISTS/IN)** — коли потрібно лише перевірити існування

**Приклад:**
```sql
-- JOIN: отримати користувачів І їхні замовлення
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id;

-- EXISTS: перевірити, чи є замовлення у користувача
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```

**Коли що використовувати:**
- Потрібні колонки з обох таблиць → **JOIN**
- Потрібна лише фільтрація → **EXISTS/IN**
- Складна логіка з агрегацією → **підзапит**

## 🟡 Middle Level

### Як оптимізатор обробляє підзапити

PostgreSQL вміє **Unnesting** (розгортання) — перетворює підзапити на JOIN на рівні плану виконання. Це означає, що написаний вами підзапит фізично виконується як з'єднання таблиць, що зазвичай швидше.

При цьому часто використовується **Semi-Join** — особливий тип з'єднання: для кожного рядка лівої таблиці перевіряє, чи є хоча б один збіг у правій, і повертає рядок лівої таблиці ОДИН РАЗ (без дублів).

```sql
-- Підзапит у WHERE
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 100);

-- Оптимізатор перетворює на:
SELECT * FROM users
INNER JOIN (SELECT user_id FROM orders WHERE amount > 100) o 
ON users.id = o.user_id;
-- Plan: Hash Semi-Join (дуже ефективно)
```

### Semi-Join vs JOIN

**Проблема JOIN: Join Amplification**
```sql
-- ❌ Якщо у користувача 10 замовлень, він з'явиться 10 разів!
SELECT DISTINCT u.* FROM users u
JOIN orders o ON u.id = o.user_id;

-- ✅ EXISTS використовує Semi-Join (немає дублів!)
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
-- Зупиняється після першого збігу → швидше
```

### Оптимізаційні бар'єри (Optimization Fences)

| Бар'єр                | Що відбувається                  |
| --------------------- | -------------------------------- |
| `LIMIT` / `OFFSET`    | Підзапит виконується окремо      |
| `DISTINCT`            | Не може бути витягнутий у JOIN   |
| `GROUP BY` / Агрегати | Підзапит матеріалізується        |
| `UNION` / `INTERSECT` | Окремий вузол у плані            |

### Скалярні підзапити в SELECT

```sql
-- ❌ ПОГАНО: підзапит виконується для кожного рядка
SELECT u.name, 
       (SELECT SUM(amount) FROM orders o WHERE o.user_id = u.id) as total
FROM users u;
-- Plan: SubPlan (1,000,000 підзапитів для 1,000,000 користувачів!)

-- ✅ ДОБРЕ: JOIN + GROUP BY
SELECT u.name, SUM(o.amount) as total
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.name;
-- Plan: Hash Join + HashAggregate (набагато швидше!)
```

### CTE (WITH) та матеріалізація

**PostgreSQL 12+:** CTE за замовчуванням вбудовуються (Inlined):

```sql
-- PG 12+: цей CTE буде вбудований в основний запит
WITH active_users AS (
    SELECT * FROM users WHERE status = 'ACTIVE'
)
SELECT * FROM active_users u
JOIN orders o ON u.id = o.user_id;
```

**Керування матеріалізацією:**
```sql
-- Примусова матеріалізація (обчислити CTE один раз)
WITH c AS MATERIALIZED (
    SELECT user_id, SUM(amount) as total FROM orders GROUP BY user_id
)
SELECT * FROM users u JOIN c ON u.id = c.user_id;

-- Примусове вбудовування
WITH c AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE amount > 100
)
SELECT * FROM c JOIN users u ON c.user_id = u.id;
```

### Типові помилки

1. **Скалярний підзапит у SELECT на великих даних**
   ```sql
   -- ❌ Катастрофа продуктивності
   SELECT u.name, (SELECT COUNT(*) FROM orders WHERE user_id = u.id)
   FROM users u;  -- 1 млн рядків → 1 млн підзапитів!
   ```

2. **NOT IN з NULL**
   ```sql
   -- ❌ Поверне порожній результат, якщо є NULL!
   SELECT * FROM users
   WHERE id NOT IN (SELECT user_id FROM orders);
   
   -- ✅ Використовуйте NOT EXISTS
   SELECT * FROM users u
   WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
   ```

### Практичне порівняння

| Ситуація                    | Кращий інструмент   | Чому                              |
| --------------------------- | ------------------- | --------------------------------- |
| Дані з обох таблиць         | **JOIN**            | Максимум стратегій виконання      |
| Перевірка існування         | **EXISTS**          | Hash Semi-Join, немає дублів      |
| Залежна вибірка (топ-N)     | **LATERAL**         | Використовує індекси всередині    |
| Агрегація для кожного рядка | **JOIN + GROUP BY** | Один прохід замість N підзапитів  |

## 🔴 Senior Level

### Unnesting та Decorrelation

**Як оптимізатор "розгортає" підзапити:**

```sql
-- Вихідний запит
SELECT * FROM users u
WHERE u.id IN (
    SELECT o.user_id FROM orders o 
    WHERE o.amount > (SELECT AVG(amount) FROM orders)
);

-- Кроки трансформації:
-- 1. Скалярний підзапит AVG → InitPlan (обчислюється один раз)
-- 2. IN підзапит → Hash Semi-Join
-- 3. Фінальний план:
--    InitPlan: AVG(amount)
--    → Hash Semi-Join (users ↔ orders)
```

### SubPlan vs InitPlan

**SubPlan:** Виконується для кожного рядка зовнішнього запиту
```sql
EXPLAIN SELECT u.name,
       (SELECT SUM(amount) FROM orders o WHERE o.user_id = u.id)
FROM users u;
-- ⚠️ Виконується 1,000,000 разів!
```

**InitPlan:** Виконується один раз перед основним запитом
```sql
EXPLAIN SELECT * FROM users
WHERE amount > (SELECT AVG(amount) FROM orders);
-- ✅ Виконується 1 раз!
```

### Memoize Node (PostgreSQL 14+)

**Memoize** — вузол у плані виконання, який кешує результати підзапиту. Якщо підзапит викликається з тими ж параметрами повторно, результат береться з кешу.

```sql
SELECT u.name, o.amount
FROM users u
LEFT JOIN LATERAL (
    SELECT amount FROM orders o
    WHERE o.user_id = u.id
    ORDER BY created_at DESC
    LIMIT 1
) o ON true;
-- PostgreSQL 14+: Memoize кешує результати
-- 🚀 Прискорення в 10-100 разів на даних з повторами
```

### LATERAL JOIN: Коли і чому

```
LATERAL майже завжди → Nested Loop
→ Чудово, якщо зовнішня таблиця мала (< 10,000 рядків)
→ Катастрофа, якщо зовнішня таблиця велика (> 1,000,000 рядків)
```

**Альтернативи для великих даних:**
```sql
-- ✅ Window Function → Hash Join
SELECT name, amount
FROM (
    SELECT u.name, o.amount,
           ROW_NUMBER() OVER(PARTITION BY u.id ORDER BY o.created_at DESC) as rn
    FROM users u
    INNER JOIN orders o ON u.id = o.user_id
) sub
WHERE rn = 1;

-- ✅ DISTINCT ON → Sort + Unique
SELECT DISTINCT ON (u.id) u.name, o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id
ORDER BY u.id, o.created_at DESC;
```

### Edge Cases

1. **Підзапит в UPDATE/DELETE**
   ```sql
   -- ✅ FROM синтаксис → JOIN
   UPDATE orders o SET status = 'VIP'
   FROM users u
   WHERE o.user_id = u.id AND u.vip = true;
   ```

2. **Порожній підзапит**
   ```sql
   -- IN () → FALSE
   -- NOT IN () → TRUE (обережно з NULL!)
   -- EXISTS () → FALSE
   -- NOT EXISTS () → TRUE
   ```

### Performance Comparison

| Підхід                   | Складність           | Коли використовувати              |
| ------------------------ | -------------------- | --------------------------------- |
| **JOIN**                 | O(N + M) з Hash Join | Дані з обох таблиць               |
| **EXISTS/IN**            | O(N + M) з Semi-Join | Перевірка існування               |
| **Scalar Subquery**      | O(N × M)             | **Уникайте** на великих даних     |
| **LATERAL**              | O(N × log M)         | Залежні вибірки, малі зовнішні    |
| **CTE MATERIALIZED**     | O(M) + O(N)          | CTE використовується > 1 разу    |

### Production Experience

**Реальний сценарій #1: SubPlan вбиває API**
- REST API: скалярний підзапит у SELECT для 10,000 користувачів
- Час: 45 секунд → Замінили на JOIN + GROUP BY → 200ms (прискорення у 225 разів)

**Реальний сценарій #2: Memoize рятує від LATERAL**
- LATERAL без Memoize: > 5 хвилин → Після PG 14 з Memoize: 3 секунди
- Hits/Misses ratio: 95%/5%

### Резюме для Senior

- Оптимізатор вміє **Unnesting** та **Decorrelation** підзапитів
- **SubPlan** на кожний рядок → катастрофа; замінюйте на JOIN
- **Memoize (PG 14+)** кешує результати LATERAL → перевіряйте Hits/Misses
- **CTE в PG 12+** за замовчуванням вбудовується; керуйте через MATERIALIZED
- **EXISTS = Semi-Join** (немає Join Amplification)

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- PostgreSQL вміє Unnesting — перетворює підзапити на JOIN (Hash Semi-Join)
- SubPlan = виконується для кожного рядка → O(N × M) → КАТАСТРОФА
- InitPlan = виконується один раз → O(M) + O(N) → чудово
- EXISTS = Semi-Join: немає Join Amplification, зупиняється після 1-го збігу
- NOT EXISTS > NOT IN: NOT IN з NULL поверне порожній результат
- Memoize (PG 14+): кешує результати LATERAL → Hit rate > 80% = чудово
- CTE в PG 12+: за замовчуванням вбудовується (NOT MATERIALIZED)

**Часті уточнюючі запитання:**
- «Чому EXISTS краще за DISTINCT JOIN?» → Semi-Join не створює дублів
- «Коли Memoize не допомагає?» → Усі ключі унікальні → 0% Hits
- «CTE MATERIALIZED чи NOT MATERIALIZED?» → MATERIALIZED якщо > 1 разу

**Червоні прапорці (НЕ говорити):**
- ❌ «Підзапит завжди повільніший за JOIN» (декорельований EXISTS може бути швидше)
- ❌ «NOT IN безпечний» (NULL поверне порожній результат!)
- ❌ «CTE завжди матеріалізується» (PG 12+ вбудовує за замовчуванням)
