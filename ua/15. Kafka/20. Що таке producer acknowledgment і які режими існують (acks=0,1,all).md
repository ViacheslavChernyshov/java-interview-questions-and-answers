# Що таке producer acknowledgment і які режими існують?

---

## 🟢 Junior Level

**Producer Acknowledgment (acks)** — це параметр конфігурації продюсера, який визначає, скільки підтверджень від реплік брокера повинен отримати продюсер, щоб вважати запис повідомлення успішним. Це головний важіль управління балансом між **надійністю (Durability)** та **швидкістю (Latency)**.

| Режим | Підтвердження | Швидкість | Надійність |
|---|---|---|---|
| `acks=0` | Ніякого (Fire & Forget) | Максимальна | Нульова |
| `acks=1` | Тільки від Leader репліки | Середня | Середня |
| `acks=all` (`-1`) | Від Leader та всіх ISR реплік | Низька | Максимальна |

### Проста аналогія

- **acks=0** — відправив листа і пішов, не перевіряючи чи дійшов
- **acks=1** — відправив листа і дочекався, що поштове відділення прийняло
- **acks=all** — відправив листа і дочекався підтвердження, що копії зберігаються у кількох відділеннях

## 🟡 Middle Level

### Детальний розбір режимів ACKS

#### acks = 0 (Fire and Forget)
Продюсер не чекає ніякого підтвердження від брокера. Повідомлення вважається успішно відправленим, як тільки воно потрапило в мережевий буфер.
- **Latency**: Мінімальна.
- **Reliability**: Нульова. Якщо брокер впав або в мережі стався збій — дані втрачено назавжди.
- **Use Case**: Збір логів або метрик, де втрата 1-2% даних допустима.

#### acks = 1 (Leader Only)
Продюсер чекає підтвердження тільки від Лідера партиції. Лідер записує дані у свій локальний лог і одразу відповідає продюсеру.
- **Latency**: Середня.
- **Reliability**: Середня. Якщо Лідер впав **одразу** після відповіді продюсеру, але **до того**, як Фоловери встигли скопіювати дані — вони будуть втрачені.
- **Use Case**: Загальні бізнес-події, що не вимагають екстремальної надійності.
- *Примітка: За замовчуванням до Kafka 3.0. Починаючи з Kafka 3.0 (KIP-316) дефолт змінено на acks=all.*

#### acks = all (або -1)
Продюсер чекає підтвердження від Лідера та **всіх синхронних реплік (ISR)**.
- **Latency**: Максимальна (обмежена найповільнішою реплікою в ISR).
- **Reliability**: Максимальна. Дані гарантовано збережені на кількох вузлах.
- **Use Case**: Фінансові транзакції, критичні дані.

### Зв'язок з min.insync.replicas

Параметр `acks=all` сам по собі не гарантує запис на кілька вузлів. Якщо в ISR залишився тільки один Лідер, `acks=all` перетвориться на `acks=1`. Щоб гарантувати реальну надлишковість, потрібно використовувати `min.insync.replicas >= 2`.

```java
// Конфігурація продюсера для максимальної надійності
Properties props = new Properties();
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
// На рівні топіка: min.insync.replicas=2, replication.factor=3
```

## 🔴 Senior Level

### Вплив на ретраї (Retries)

При використанні `acks=1` або `all` продюсер може отримувати помилки (наприклад, `NotLeaderForPartitionException`). В цьому випадку він буде автоматично робити повторні спроби (`retries`). При `acks=0` ретраї неможливі, оскільки продюсер не знає про помилку.

### acks=all + min.insync.replicas: Формула надійності

```
Гарантія = acks=all + min.insync.replicas >= 2 + replication.factor >= 3
```

Якщо ISR < min.insync.replicas → `NotEnoughReplicasException`, запис відхиляється. Це захищає від silent data loss, але знижує доступність.

### Production Best Practices

| Сценарій | acks | min.insync.replicas | replication.factor |
|---|---|---|---|
| Логи/метрики | 0 або 1 | 1 | 2 |
| Бізнес-події | 1 | 1 | 3 |
| Фінанси/критичне | all | 2 | 3 |
| Аудит/комплаєнс | all | 2 | 3 + rack awareness |

### Моніторинг

```
# Ключові метрики продюсера
kafka.producer:type=producer-metrics,client-id=*
  record-error-rate          # Помилки запису → якщо зростає, перевірте ISR
  request-latency-avg        # Середня затримка → порівняйте acks=1 vs acks=all
  record-retry-rate          # Частота повторів → якщо висока, проблеми з кластером
```

### Резюме для Senior

- `acks=0`: Швидкість за будь-яку ціну.
- `acks=1`: Баланс (небезпечно при падінні лідера).
- `acks=all`: максимальна надійність, але вища latency та нижча доступність.
- Завжди використовуйте `acks=all` разом з `min.insync.replicas >= 2` для критичних даних.
- `acks=all` захищає від втрати даних, але не від дублікатів (для цього потрібна ідемпотентність).

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- `acks=0` — fire and forget, мінімальна latency, нульова reliability
- `acks=1` — підтвердження від лідера, середня reliability; при падінні лідера дані втрачені
- `acks=all` — підтвердження від усіх ISR, максимальна reliability; вища latency
- `acks=all` без `min.insync.replicas>=2` = `acks=1` якщо ISR=1
- Дефолт змінився: до Kafka 3.0 — acks=1; з Kafka 3.0 (KIP-316) — acks=all
- Retries можливі при acks=1/all; при acks=0 продюсер не знає про помилку
- `acks=all` захищає від втрати, але не від дублікатів (потрібна ідемпотентність)

**Часті уточнюючі запитання:**
- *Чому acks=all без min.insync.replicas недостатньо?* — Якщо ISR=1, acks=all = acks=1
- *Який дефолт в Kafka 3.0+?* — acks=all (KIP-316), раніше був acks=1
- *Що буде при acks=all і ISR < min.insync.replicas?* — NotEnoughReplicasException

**Червоні прапорці (НЕ говорити):**
- ❌ «acks=0 для production даних» — нульова гарантія доставки
- ❌ «acks=all гарантує запис на кілька вузлів без min.insync.replicas» — якщо ISR=1, то на один
- ❌ «acks=0 підтримує retries» — продюсер не знає про помилку
- ❌ «acks=all захищає від дублікатів» — ні, потрібна ідемпотентність
