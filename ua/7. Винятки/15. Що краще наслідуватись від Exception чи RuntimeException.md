# Що краще: наслідуватись від Exception чи RuntimeException?

## 🟢 Junior Level

**Ключове питання:** чи повинен викликаючий код бути **зобов'язаний** обробити цю помилку?

**Decision Tree:**
1. Помилка введення/валідації → `IllegalArgumentException` (unchecked)
2. Помилка бізнес-правила → `BusinessException` (unchecked)
3. Помилка зовнішньої системи → залежить:
   - Якщо відновлювано (retry допоможе) → checked
   - Якщо ні (сервіс впав) → unchecked

В Java є два основних типи винятків:

- **Checked Exception** (наслідуються від `Exception`, але не від `RuntimeException`) — компілятор **вимагає** їх обробки. Навіщо: щоб розробник на етапі написання коду свідомо вирішив, що робити з цією помилкою.
- **Unchecked Exception** (наслідуються від `RuntimeException`) — компілятор **не вимагає** їх обробки. Чому: JVM спроектована так, що ці винятки представляють помилки програмування (баги), які не можна відновити на льоту.

```java
// Checked — потрібно оголошувати throws або ловити
public class DatabaseException extends Exception {
    public DatabaseException(String msg) { super(msg); }
}

// Unchecked — не потрібно оголошувати
public class ValidationException extends RuntimeException {
    public ValidationException(String msg) { super(msg); }
}
```

**Рекомендація:**
- Помилки **користувача** (невірне введення, порушення бізнес-правил) → зазвичай `RuntimeException`
- Помилки **зовнішньої системи** (мережа, БД, файлова система) → часто `Exception`, бо можна повторити запит

## 🟡 Middle Level

### Коли наслідуватись від Exception (Checked)

**Використовуй checked exception, коли:**

1. **Викликаючий може відновити ситуацію**
```java
public Connection getConnection() throws ConnectionPoolExhaustedException {
    // Викликаючий може зачекати і спробувати знову
}
```

2. **Це очікувана ситуація**, а не баг
```java
public Document readDocument(String path) throws FileNotFoundException {
    // Файл може не існувати — це нормально
}
```

3. **API вимагає обов'язкової обробки**
```java
public void transferMoney(Account from, Account to, BigDecimal amount)
        throws InsufficientFundsException {
    // Викликаючий ЗОБОВ'ЯЗАНИЙ обробити недостатність коштів
}
```

### Коли наслідуватись від RuntimeException (Unchecked)

1. **Помилка програмування**
```java
public void setAge(int age) {
    if (age < 0) throw new IllegalArgumentException("Age < 0");
}
```

2. **Бізнес-правила** (сучасний підхід Spring)
```java
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long id) {
        super("Order not found: " + id);
    }
}
```

3. **Коли неможливо відновитися**
```java
public class ConfigurationException extends RuntimeException {
    // Невірна конфігурація → перезапуск, а не retry
}
```

### Spring підхід

Spring послідовно використовує unchecked exceptions:
- `DataAccessException` (замість `SQLException`)
- `HttpClientErrorException`
- `NoSuchBeanDefinitionException`

```java
// Spring перетворює checked → unchecked
@Repository
public class UserRepository {
    // SQLException (checked) → DataAccessException (unchecked)
    public User findById(Long id) {
        return jdbcTemplate.queryForObject(
            "SELECT * FROM users WHERE id = ?", rowMapper, id);
    }
}
```

### Ієрархія власних винятків

```java
// Базовий для всіх бізнес-винятків
public abstract class BusinessException extends RuntimeException {
    private final String errorCode;
    
    protected BusinessException(String errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }
    
    public String getErrorCode() { return errorCode; }
}

// Конкретні винятки
public class OrderNotFoundException extends BusinessException {
    public OrderNotFoundException(Long id) {
        super("ORDER_NOT_FOUND", "Order not found: " + id);
    }
}

public class InsufficientFundsException extends BusinessException {
    public InsufficientFundsException(BigDecimal required, BigDecimal available) {
        super("INSUFFICIENT_FUNDS", 
              String.format("Required: %s, Available: %s", required, available));
    }
}
```

### Типові помилки

1. **Порожній catch блок**
```java
// ❌ Найгірший антипатерн
try { riskyOperation(); } catch (Exception e) { }

// ✅ Мінімум — логування
try { riskyOperation(); } catch (Exception e) { log.error("Failed", e); }
```

2. **Ловити Exception замість конкретного типу**
```java
// ❌ Ловить ВСЕ, включаючи NullPointerException
try { ... } catch (Exception e) { ... }

// ✅ Конкретний тип
try { ... } catch (IOException e) { ... }
```

## 🔴 Senior Level

### Checked vs Unchecked: Архітектурне рішення

**Checked Exceptions порушують Open/Closed Principle:**
```java
// Якщо додати нову checked exception в нижній шар:
public void processOrder() throws OrderException, PaymentException,
        ShippingException, InventoryException { // список зростає!
    // Кожен новий виняток → зміна сигнатури всього ланцюжка
}
```

**Unchecked + @ControllerAdvice (Spring підхід):**
```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(BusinessException e) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ErrorResponse(e.getErrorCode(), e.getMessage()));
    }
    
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
        log.error("Unexpected error", e);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ErrorResponse("INTERNAL_ERROR", "Internal server error"));
    }
}
```

### Exception Translation Pattern

```java
@Repository
public class JpaUserRepository implements UserRepository {
    @Override
    public User findById(Long id) {
        try {
            return entityManager.find(User.class, id);
        } catch (PersistenceException e) {
            // Перетворення інфраструктурного виключення в доменне
            throw new UserRepositoryException("Failed to find user: " + id, e);
        }
    }
}
```

### Performance: вартість винятків

```java
// Створення виключення з stack trace: ~5-10 мікросекунд
// Кидання та ловлення: ~1-5 мікросекунд
// Виключення БЕЗ stack trace:
public class FastException extends RuntimeException {
    public FastException(String msg) {
        super(msg, null, true, false); // writableStackTrace = false
    }
}
```

### Резюме для Senior

- **Сучасний підхід (Spring):** unchecked для всього, крім справді відновлюваних ситуацій
- Checked exceptions порушують Open/Closed Principle → каскадне оновлення сигнатур
- Exception Translation Pattern — перетворення інфраструктурних у доменні
- Stack trace коштує ~5-10 мкс → для hot path використовуйте `writableStackTrace=false`
- Ієрархія: `BusinessException` → конкретні бізнес-винятки з error codes

## 🎯 Шпаргалка для інтерв'ю

**Обов'язково знати:**
- Checked = компілятор вимагає обробки; Unchecked = не вимагає
- Сучасний підхід (Spring): unchecked для бізнес-логіки
- Checked порушують OCP → каскадне оновлення throws
- Spring перетворює checked (SQLException) → unchecked (DataAccessException)
- Ієрархія: базовий BusinessException (unchecked) → конкретні підкласи з errorCode

**Часті уточнюючі запитання:**
- «Коли все ж використовувати checked?» → Коли retry реально допоможе
- «Як Spring обробляє винятки?» → @ControllerAdvice + @ExceptionHandler
- «Скільки коштує throw?» → ~5-10 мкс (stack trace), мінімізуйте для hot path

**Червоні прапорці (НЕ говорити):**
- ❌ «Завжди checked для безпеки» (порушує OCP, засмічує сигнатури)
- ❌ «Порожній catch — нормально» (найгірший антипатерн)
- ❌ «Ловлю Exception скрізь» (ковтає NPE та інші баги)
