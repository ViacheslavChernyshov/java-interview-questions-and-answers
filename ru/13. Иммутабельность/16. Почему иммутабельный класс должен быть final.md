# Почему иммутабельный класс должен быть final?

---

## 🟢 Junior Level

### Простой ответ

Иммутабельный класс обязан быть объявлен со спецификатором **`final`**, чтобы **полностью запретить наследование**.

Если класс не пометить как `final`, любой другой разработчик (или злоумышленник) может создать подкласс, добавить в него мутабельные поля с сеттерами и переопределить методы так, чтобы они возвращали изменяемые данные:

```java
// ❌ НЕБЕЗОПАСНО: Класс не final
public class Coordinates {
    private final int x;
    private final int y;

    public Coordinates(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }
}

// 💥 Коварный подкласс ломает неизменяемость:
public class MutableCoordinates extends Coordinates {
    private int mutableX;

    public MutableCoordinates(int x, int y) {
        super(x, y);
        this.mutableX = x;
    }

    public void setX(int newX) { this.mutableX = newX; }

    @Override
    public int getX() { return mutableX; } // Переопределили геттер!
}
```

### Аналогия из жизни

Представьте **запечатанный сургучной печатью конверт**:
- `final class` — это сургучная печать. Никто не может вскрыть конверт, дописать в него текст или подменить листок бумаги.
- Если сургучной печати нет, кто-то может вложить внутрь поддельный листок и передать конверт дальше от имени автора.

## 🟡 Middle Level

### Опасности отсутствия `final` для бизнес-логики и инфраструктуры

| Риск | Механизм сбоя | Последствия в Production |
| :--- | :--- | :--- |
| **Уязвимость TOCTOU (Time-of-Check to Time-of-Use)** | Валидатор проверяет объект `Coordinates`, а подкласс меняет координаты перед сохранением в БД | Обход проверок безопасности, запись некорректных данных |
| **Повреждение хеш-таблиц (`HashMap`)** | Подкласс переопределяет `hashCode()` и `equals()` с опорой на изменяемые поля | Потеря элементов в бакетах `HashMap`, утечка памяти |
| **Потеря потокобезопасности (Thread Safety)** | Поля родителя защищены `final freeze`, а поля наследника — нет | Гонки данных, чтение `null` или полу-инициализированных полей |

### Примеры из стандартной библиотеки Java (JDK)

Все фундаментальные иммутабельные типы в Java объявлены как `final`:
- `java.lang.String`
- `java.lang.Integer`, `java.lang.Long`, `java.lang.Double` (все обёртки примитивов)
- `java.math.BigDecimal`, `java.math.BigInteger`
- `java.time.LocalDate`, `java.time.LocalDateTime`, `java.time.Instant`
- Все классы `java.lang.Record` (Java 16+) **неявно являются `final`**.

### Прокси-фреймворки и Mockito (Spring & CGLIB)

Исторически `final` классы создавали сложности для библиотек:
- **CGLIB / Spring AOP**: Не может создать CGLIB-прокси для `final` класса (решается переходом на JDK Dynamic Proxies через интерфейсы).
- **Mockito 2/3**: Не мог мокать `final` классы. Начиная с **Mockito 5+** (Spring Boot 3), мокирование `final` классов и методов работает «из коробки» благодаря `mock-maker-inline` (на базе ByteBuddy агента).

## 🔴 Senior Level

### JIT Оптимизации: Devirtualization и Monomorphic Inlining

Объявление класса как `final` — это мощнейшая подсказка для JIT C2-компилятора:

1. **Устранение таблицы виртуальных методов (Devirtualization)**:
   - Если класс `final`, компилятор на 100% уверен, что у его методов **нет и никогда не будет подклассов и переопределений** (Hierarchy Analysis).
   - Инструкция байт-кода `invokevirtual` мгновенно преобразуется в прямой статический вызов без обращения к `vtable` в памяти.
2. **Агрессивный Inlining**:
   - Методы-геттеры (`getX()`) инлайнятся в машинный код вызывающего метода: вызов метода заменяется прямым чтением регистра процессора за $0$ тактов.
3. **Escape Analysis**:
   - JIT легко доказывает, что объект не утекает за пределы метода, и может разложить его на скаляры в регистрах CPU (Scalar Replacement), полностью исключая аллокацию в Heap!

### Способы запрета наследования без слова `final`

По правилам книги Joshua Bloch «Effective Java» (Item 17):
> *«Проектируйте и документируйте для наследования, либо запрещайте его.»*

Если по архитектурным причинам нельзя объявить весь класс `final`, наследование можно заблокировать через **приватный конструктор**:

```java
public class SecureValue {
    private final String value;

    // Приватный конструктор — внешний класс не сможет вызвать super()!
    private SecureValue(String value) {
        this.value = value;
    }

    public static SecureValue of(String value) {
        return new SecureValue(value);
    }
}
```

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Иммутабельный класс обязан быть `final`, чтобы предотвратить добавление мутабельного состояния и переопределение методов в подклассах.
- Без `final` нарушается контракт Liskov Substitution Principle (LSP) и разрушается потокобезопасность.
- `final` позволяет JIT C2-компилятору выполнять девиртуализацию (Devirtualization) и мономорфный инлайнинг методов.
- Все Record (Java 16+) неявно являются `final`.
- Альтернатива запрета наследования: приватные конструкторы со статическими фабриками (`of()`).

**Частые уточняющие вопросы:**
- **Что произойдёт, если класс не пометить final?** — Подкласс сможет переопределить геттеры, сломать `hashCode()` в `HashMap` и подменить данные в обход валидации.
- **Как JIT компилятор использует final у класса?** — Выполняет девиртуализацию вызовов и агрессивный инлайнинг методов без проверок vtable.
- **Можно ли мокать final-классы в современных тестах?** — Да, Mockito 5+ поддерживает `mock-maker-inline` через Java Agent.

**Красные флаги (НЕ говорить):**
- ❌ «Если все поля помечены `final`, делать сам класс `final` необязательно».
- ❌ «`final` замедляет компиляцию и не даёт преимуществ в производительности».
- ❌ «`Record` можно наследовать от другого класса».
