# Что произойдёт, если переопределить геттер в подклассе иммутабельного класса?

---

## 🟢 Junior Level

### Простой ответ

Если класс, задуманный как иммутабельный, **не объявлен как `final`**, класс-наследник может переопределить его методы-геттеры и возвращать динамически изменяемые значения. 

В результате **гарантия иммутабельности полностью уничтожается**: сторонний код, принимающий базовый тип, будет считать объект неизменяемым, но в реальности получать разные значения при каждом вызове.

### Наглядный пример нарушения:

```java
// ❌ ОШИБКА АРХИТЕКТУРЫ: Класс забыли пометить final
public class Money {
    private final long amount; // Поле неизменяемо

    public Money(long amount) {
        this.amount = amount;
    }

    public long getAmount() {
        return amount;
    }
}

// Коварный мутабельный наследник:
public class CheatingMoney extends Money {
    private long dynamicAmount;

    public CheatingMoney(long initial) {
        super(initial);
        this.dynamicAmount = initial;
    }

    public void setAmount(long amount) {
        this.dynamicAmount = amount;
    }

    @Override
    public long getAmount() {
        return this.dynamicAmount; // 💥 Подмена неизменяемого значения!
    }
}
```

### Как это ломает логику программы:

```java
Money cash = new CheatingMoney(100);
System.out.println(cash.getAmount()); // 100

((CheatingMoney) cash).setAmount(500);
System.out.println(cash.getAmount()); // 500! (Хотя тип переменной Money)
```

## 🟡 Middle Level

### Нарушение принципа подстановки Барбары Лисков (LSP)

Это классический пример нарушения **Liskov Substitution Principle (LSP)** из SOLID:
- Базовый класс `Money` декларирует инвариант: *«Значение экземпляра константно на протяжении всей жизни объекта»*.
- Подкласс `CheatingMoney` нарушает контракт предка, делая поведение непредсказуемым для любого клиентского кода.

### Последствия для инфраструктуры и коллекций

1. **Разрушение структуры `HashMap` и `HashSet`**:
   - Если объект `CheatingMoney` положить в `HashMap` в качестве ключа, его `hashCode()` и `equals()` (опирающиеся на `getAmount()`) изменятся после мутации.
   - Попытка выполнить `map.get(cash)` вернет `null`, а объект навсегда застрянет в памяти (Memory Leak).

2. **Потеря потокобезопасности (Thread Safety)**:
   - Базовое поле `amount` благодаря `final` безопасно публиковалось в памяти (JMM §17.5).
   - Поле наследника `dynamicAmount` не является `final` или `volatile` $\rightarrow$ параллельные потоки столкнутся с гонками данных и чтением устаревших значений из L1-кэша CPU.

## 🔴 Senior Level

### Байт-код: `invokevirtual` и динамическая диспетчеризация

В Java вызов любого нестатического и неприватного метода компилируется в байт-код инструкцию **`invokevirtual`**:
```
invokevirtual #4 // Method Money.getAmount:()J
```
- JVM в рантайме использует таблицу виртуальных методов (**vtable**) фактического класса объекта в Heap.
- Поскольку объект в памяти имеет тип `CheatingMoney`, JVM вызывает реализацию подкласса, игнорируя реализацию `Money`.
- **Вывод для Senior**: Спецификация Java Memory Model (JMM) гарантирует неизменяемость полей в памяти, но **не может защитить от полиморфного переопределения методов**.

### 3 архитектурных паттерна защиты иммутабельности

#### 1. Использование ключевого слова `final` для класса (Рекомендуется)
```java
public final class ImmutableMoney { ... } // Наследование физически запрещено
```

#### 2. Приватный конструктор + Static Factory Method (Joshua Bloch Pattern)
Если класс нельзя объявить `final` (например, для внутренних подклассов в одном файле), конструкторы делают `private`:
```java
public class SafeMoney {
    private final long amount;

    private SafeMoney(long amount) {
        this.amount = amount;
    }

    public static SafeMoney of(long amount) {
        return new SafeMoney(amount);
    }
}
```
*Внешний класс не сможет отнаследоваться, так как не имеет доступа к конструктору `super()`.*

#### 3. Sealed Classes и Records (Java 16/17+)
- **Records**: автоматически являются `final`, а их компоненты-геттеры нельзя переопределить через наследование.
- **Sealed Types**: строго ограничивают круг наследников списком доверенных иммутабельных классов:
  ```java
  public sealed class SafeData permits EncryptedData, PlainData {}
  ```

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Переопределение геттера в не-`final` классе полностью уничтожает гарантии иммутабельности из-за полиморфизма (`invokevirtual`).
- Нарушает **Liskov Substitution Principle (LSP)**: клиентский код ожидает неизменяемый контракт, но получает мутабельный объект.
- Разрушает потокобезопасность (поля наследника не защищены JMM `final` freeze действием) и ломает хеш-таблицы (`HashMap`).
- Способы защиты:
  1. Объявить класс `final`.
  2. Сделать конструкторы `private` и использовать статические фабрики.
  3. Использовать `record` (Java 16+) или `sealed class` (Java 17+).

**Частые уточняющие вопросы:**
- **Почему final-поля родителя не спасают от мутации?** — Поля в памяти не меняются, но переопределенный метод возвращает значение другого мутабельного поля подкласса.
- **Как это ломает HashMap?** — Изменение возвращаемого значения геттера меняет `hashCode()`, объект попадает не в ту корзину и теряется.
- **Как запретить наследование без слова final?** — Сделать все конструкторы `private`.

**Красные флаги (НЕ говорить):**
- ❌ «Если все поля помечены `final`, класс автоматически становится защищенным от наследования».
- ❌ «Переопределение геттера никак не влияет на многопоточность».
- ❌ «Полиморфизм в Java не работает для методов-геттеров».
