# Почему класс String является иммутабельным?

---

## 🟢 Junior Level

### Простое определение

В Java объект класса **`String` является неизменяемым (Immutable)**: после создания строкового объекта его содержимое в памяти изменить невозможно.

Любые методы, которые кажутся «модифицирующими» строку (`concat()`, `replace()`, `substring()`, `toUpperCase()`), на самом деле **создают и возвращают абсолютно новый объект `String`** в куче (Heap), оставляя исходную строку неизменной:

```java
String original = "Java";
original.concat(" Developer"); // Результат игнорируется!

System.out.println(original); // Выведет "Java"

// Чтобы сохранить результат, нужно присвоить ссылку:
String updated = original.concat(" Developer");
System.out.println(updated); // Выведет "Java Developer" (новый объект)
```

### Аналогия из жизни

Представьте **отпечатанную типографскую книгу**:
- Вы не можете стереть текст со страницы отпечатанной книги. Если вам нужно внести правку в главу, типография должна напечатать **новый тираж** (новую книгу).
- В отличие от книги, школьная доска с мелом — это мутабельный объект (`StringBuilder`), где можно стирать и дописывать буквы на том же месте.

### 4 главные причины иммутабельности String:
1. **Экономия памяти (String Pool)**: одинаковые строки-литералы разделяются между всеми модулями приложения.
2. **Безопасность (Security)**: строки используются для хранения URL, путей к файлам, логинов и сетевых сокетов.
3. **Потокобезопасность (Thread Safety)**: строку можно безопасно читать из десятков потоков без блокировок и `synchronized`.
4. **Быстрый кэшированный `hashCode`**: делает строки идеальными ключами для `HashMap` и `HashSet`.

## 🟡 Middle Level

### 1. Архитектура String Pool (Паттерн Flyweight)

Благодаря иммутабельности JVM экономит до 30–50% оперативной памяти:
```java
String s1 = "interview";
String s2 = "interview";

System.out.println(s1 == s2); // true — обе переменные указывают на ОДИН И ТОТ ЖЕ объект в String Pool
```
Если бы строки были мутабельными, изменение `s1.setCharAt(0, 'I')` привело бы к незаметной порче данных в переменной `s2` и во всех сторонних библиотеках, использующих этот литерал.

### 2. Защита от атак Time-of-Check to Time-of-Use (TOCTOU)

Строки передаются в качестве параметров в системные вызовы операционной системы и фреймворки безопасности:

```java
public void deleteUserFile(String filePath) {
    if (!securityManager.isPathAllowed(filePath)) { // 1. Проверка прав (Time of Check)
        throw new SecurityException("Access Denied");
    }

    // Если бы String был мутабельным, другой поток мог бы изменить filePath прямо здесь!
    fileSystem.deleteFile(filePath); // 2. Выполнение действия (Time of Use)
}
```
Если бы `filePath` был мутабельным, злоумышленник мог бы передать валидный путь `/tmp/log.txt`, дождаться проверки `isPathAllowed`, в параллельном потоке подменить символы на `/etc/passwd` и удалить критический системный файл.

### 3. Кэширование `hashCode()` для коллекций

Внутри класса `String` хеш-код вычисляется лениво ровно один раз и кэшируется в `private int hash;`:
- Сложность первого вызова `hashCode()` — $O(N)$.
- Все последующие вызовы `hashCode()` для того же объекта — мгновенные $O(1)$.
- Это обеспечивает максимальную производительность поиска в `HashMap<String, V>`.

### 4. Почему пароли нельзя хранить в String?

Поскольку строки иммутабельны, объект пароля `"secret123"` останется в Heap до срабатывания Garbage Collector. При снятии аварийного дампа памяти (Heap Dump) пароль в открытом виде может быть извлечён злоумышленником. Для паролей используют `char[]`, который можно перезаписать нулями сразу после авторизации (`Arrays.fill(password, '0')`).

## 🔴 Senior Level

### Внутренняя реализация и эволюция Compact Strings (Java 9+)

- **Java 8 и старше**:
  ```java
  public final class String {
      private final char[] value; // UTF-16, каждый символ ВСЕГДА занимает 2 байта
      private int hash;
  }
  ```
- **Java 9+ (JEP 254 Compact Strings)**:
  ```java
  public final class String {
      private final byte[] value; // 1 байт на символ для Latin-1 (ASCII/ISO-8859-1)
      private final byte coder;   // 0 = LATIN1, 1 = UTF16
      private int hash;
  }
  ```
Сжатие строк экономит до 50% размера строковых массивов в куче без изменения публичного API.

### Модель памяти Java (JMM) и Safe Publication (§17.5 JLS)

Спецификация Java Memory Model предоставляет особые гарантии для `final`-полей:
- **Freeze-действие**: по завершении конструктора `String` все `final`-поля (`value`, `coder`) «замораживаются».
- Гарантируется, что любой поток, получивший ссылку на `String`, увидит корректно инициализированный массив байтов **без необходимости явной синхронизации (Safe Publication)**.

### JIT Intrinsics и векторные инструкции SIMD

JVM C2-компилятор знает об иммутабельности `String` и заменяет стандартные циклы в методах `equals()`, `compareTo()`, `indexOf()` низкоуровневыми процессорными интринсиками (HotSpot Intrinsics), использующими векторные инструкции **AVX-2 / AVX-512** для побайтового сравнения целых блоков памяти за 1 такт CPU.

### Автоматическая дедупликация в G1 GC (`-XX:+UseStringDeduplication`)

В Garbage Collector G1 встроен фоновый механизм поиска одинаковых массивов `byte[]` у разных объектов `String`. Если два объекта имеют одинаковое содержимое, G1 перенаправляет ссылку `value` второго объекта на массив первого, освобождая дубликат из памяти. Это возможно **исключительно благодаря неизменяемости строк**.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `String` иммутабелен: `final` класс, приватный `final byte[] value` (Java 9+), отсутствие сеттеров.
- Любая модификация строки создаёт новый объект в памяти.
- Иммутабельность обеспечивает: **String Pool** (переиспользование литералов), **Thread Safety** (безопасный доступ без блокировок), **Security** (защита от TOCTOU атак) и **кэширование `hashCode`**.
- Java 9+ Compact Strings: хранит `byte[]` + `coder` (1 байт для Latin-1, 2 байта для UTF-16), экономя до 50% памяти.
- Пароли хранят в `char[]`, а не в `String`, чтобы занулить массив в памяти сразу после использования.

**Частые уточняющие вопросы:**
- **Что такое TOCTOU атака применительно к String?** — Подмена пути к файлу или URL другим потоком между моментом проверки прав безопасности и моментом непосредственного выполнения операции.
- **Где хранится String Pool?** — Начиная с Java 7, String Pool перенесён из PermGen в основную кучу (Heap) и очищается сборщиком мусора.
- **Как G1 GC дедуплицирует строки?** — Флаг `-XX:+UseStringDeduplication` объединяет ссылки на идентичные массивы `byte[]` разных объектов `String`.
- **Почему `hashCode` в String кэшируется?** — Строка неизменяема, её хеш не меняется; ленивый кэш ускоряет поиск в `HashMap` до $O(1)$.

**Красные флаги (НЕ говорить):**
- ❌ «Метод `s.concat("abc")` изменяет исходную строку `s` на месте».
- ❌ «String Pool находится в PermGen» (в Java 8+ PermGen удалён, пул находится в Heap).
- ❌ «Иммутабельность сделана только ради удобства программиста» (это фундаментальное требование безопасности и JVM JMM).
