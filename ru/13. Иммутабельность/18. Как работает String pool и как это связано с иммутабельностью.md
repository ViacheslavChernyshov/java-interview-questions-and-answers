# Как работает String pool и как это связано с иммутабельностью?

---

## 🟢 Junior Level

### Что такое String Pool?

**String Pool (Пул строк)** — это специальная область в куче (Heap) JVM, предназначенная для хранения уникальных экземпляров строковых литералов по паттерну **Flyweight (Приспособленец)**.

Когда вы объявляете строку через литерал (`"Java"`), JVM сначала ищет такую строку в пуле:
- Если строка уже есть в пуле — возвращается ссылка на существующий объект.
- Если строки нет — создаётся новый объект, помещается в пул, и возвращается ссылка на него.

```java
String s1 = "Hello";
String s2 = "Hello"; // Ссылка из String Pool

System.out.println(s1 == s2); // true — обе переменные указывают на ОДИН И ТОТ ЖЕ объект!

String s3 = new String("Hello"); // Явное создание нового объекта в Heap вне пула
System.out.println(s1 == s3); // false — разные ссылки в памяти
```

### Почему String Pool невозможен без иммутабельности?

Представьте, что строки были бы **мутабельными**:
1. Переменная `s1` («Имя пользователя») и `s2` («Пароль по умолчанию») указывают на один строковый объект `"admin"` в пуле.
2. Пользователь меняет своё имя: `s1.set("john")`.
3. Если бы объект мутировал, пароль по умолчанию `s2` и все системные роли во всех остальных потоках **незаметно изменились бы на `"john"`**.
4. **Вывод**: переиспользование одного объекта миллионами потоков возможно **исключительно потому, что его значение гарантированно неизменно**.

## 🟡 Middle Level

### Байт-код: Constant Pool и инструкция `ldc`

На этапе компиляции все строковые литералы помещаются в таблицу констант `.class` файла (`Constant_Utf8_info`):

```
0: ldc           #2                  // String Hello (загружает ссылку из String Pool)
2: astore_1
3: new           #3                  // class java/lang/String
6: dup
7: ldc           #2                  // String Hello
9: invokespecial #4                  // Method java/lang/String."<init>":(Ljava/lang/String;)V
```

### Метод `String.intern()`

Метод `intern()` переносит строку, созданную динамически в рантайме (например, вычитанную из БД или JSON), в String Pool:

```java
String dynamic = new String("custom"); // В обычном Heap
String interned = dynamic.intern();    // Помещает в String Pool (или возвращает существующий)

System.out.println(interned == "custom"); // true
```

### Эволюция расположения String Pool в памяти

| Версия Java | Где находился String Pool | Поведение GC и риски |
| :--- | :--- | :--- |
| **Java 6 и старше** | **PermGen** (Permanent Generation) | Ограниченный размер (обычно 64–128 МБ). Активный вызов `intern()` быстро приводил к фатальному `java.lang.OutOfMemoryError: PermGen space`. |
| **Java 7+** | **Основная куча (Heap Space)** | Пул перенесён в основную кучу. Неиспользуемые интернированные строки могут безопасно удаляться стандартным Garbage Collector. |

## 🔴 Senior Level

### Внутреннее устройство: Native `StringTable` в C++ HotSpot

Под капотом String Pool реализован в JVM как нативная C++ хеш-таблица `StringTable`:
- Это хеш-таблица с фиксированным количеством бакетов (Buckets) и разрешением коллизий цепочками (Chaining).
- **Параметр тюнинга**: `-XX:StringTableSize=N` (по умолчанию $65536$ в Java 11/17/21).
- Если приложение интернирует миллионы уникальных строк (например, UUID), бакеты `StringTable` переполняются длинными связными списками, и метод `intern()` деградирует из $O(1)$ в тяжелое линейное сканирование $O(N)$, сжигая процессорное время.

### String.intern() vs G1 String Deduplication

В современных высоконагруженных системах ручной вызов `intern()` считается антипаттерном. Для экономии памяти используется автоматическая дедупликация в G1 GC:

```bash
# Включение фоновой дедупликации массивов byte[] без загрязнения StringTable:
java -XX:+UseG1GC -XX:+UseStringDeduplication -jar app.jar
```

| Характеристика | `String.intern()` | G1 String Deduplication |
| :--- | :--- | :--- |
| **Как работает** | Добавляет ссылки в C++ `StringTable` | GC в фоне объединяет одинаковые массивы `byte[]` |
| **Нагрузка на CPU** | Блокирующий синхронный вызов в коде | Асинхронный фоновый поток сборщика мусора |
| **Сравнение по `==`** | ✅ Допустимо (один объект `String`) | ❌ Недопустимо (объекты `String` разные, общий только массив) |

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- String Pool — пул строк в Heap, реализующий паттерн Flyweight для экономии памяти.
- Работает **только благодаря иммутабельности**: если бы строки были мутабельными, изменение одного литерала ломало бы все переменные приложения.
- Литералы помещаются в пул автоматически, метод `.intern()` позволяет вручную поместить динамическую строку в пул.
- В Java 7+ String Pool перенесен из PermGen в основную кучу (Heap) и очищается GC.
- Ручной `intern()` опасен: миллионы уникальных строк переполняют бакеты нативной таблицы `StringTable`.
- В Java 8u20+ альтернатива — флаг `-XX:+UseStringDeduplication` в G1 GC.

**Частые уточняющие вопросы:**
- **Сколько объектов создаст `new String("abc")`?** — Два объекта: один строковый литерал `"abc"` в String Pool (если его там не было) и второй объект `String` в основной куче.
- **Очищается ли String Pool сборщиком мусора?** — Да, начиная с Java 7, неиспользуемые интернированные строки удаляются обычным GC.
- **Что такое параметр `-XX:StringTableSize`?** — Размер хеш-таблицы пула строк в JVM; увеличение размера помогает избежать коллизий при большом числе интернированных строк.

**Красные флаги (НЕ говорить):**
- ❌ «String Pool находится в PermGen в Java 17».
- ❌ «Вызов `intern()` на миллионах случайных UUID ускоряет приложение».
- ❌ «`new String("a") == "a"` вернёт true».
