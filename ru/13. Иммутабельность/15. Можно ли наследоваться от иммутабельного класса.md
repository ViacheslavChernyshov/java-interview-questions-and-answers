# Можно ли наследоваться от иммутабельного класса?

---

## 🟢 Junior Level

### Короткий ответ

Технически в Java вы **можете** унаследоваться от класса, если он явно не объявлен как `final`. Однако с точки зрения архитектуры и безопасности это **грубейшая ошибка и антипаттерн**.

Если класс не защищён от наследования, дочерний класс может добавить изменяемые (mutable) поля и методы, полностью разрушив гарантию неизменяемости:

```java
// ❌ ОШИБКА ПРОЕКТИРОВАНИЯ: забыли final
public class Money {
    private final long amount;

    public Money(long amount) { this.amount = amount; }
    public long getAmount() { return amount; }
}

// 💥 Дочерний класс превращает объект в мутабельный:
public class FraudulentMoney extends Money {
    private long extraAmount;

    public FraudulentMoney(long amount) { super(amount); }
    public void setExtraAmount(long extra) { this.extraAmount = extra; }

    @Override
    public long getAmount() {
        return super.getAmount() + extraAmount; // Данные меняются на лету!
    }
}
```

### Аналогия из жизни

Представьте **паспорт гражданина**:
- Настоящий паспорт — иммутабельный документ. Никто не может доклеить в него свои страницы или изменить дату рождения.
- Если разрешить свободное «наследование» паспорта, любой человек сможет вклеить дополнительные листы с фальшивыми штампами и предъявлять его в банке под видом государственного документа.

## 🟡 Middle Level

### Нарушение принципа подстановки Лисков (LSP)

Принцип **Liskov Substitution Principle** гласит: *объекты подкласса должны иметь возможность заменять объекты суперкласса без нарушения корректности программы*.

Когда система ожидает иммутабельный `Money`, она рассчитывает на следующие инварианты:
1. Значение `getAmount()` **детерминировано и никогда не изменится**.
2. Объект можно безопасно кэшировать в `ConcurrentHashMap` и отдавать десяткам параллельных потоков без синхронизации.
3. `hashCode()` константен.

Если в метод передать `FraudulentMoney`, все эти гарантии рушатся: потоки получают гонки данных (Race Conditions), а кэши возвращают искаженные значения.

### 2 правильные альтернативы наследованию

#### 1. Композиция вместо наследования (Item 18 Effective Java)
Вместо наследования оберните иммутабельный объект как `private final` поле нового класса:
```java
public final class LabeledMoney {
    private final Money money;
    private final String currency;

    public LabeledMoney(Money money, String currency) {
        this.money = money;
        this.currency = currency;
    }
}
```

#### 2. Приватный конструктор и фабричные методы
Если по какой-то причине класс нельзя пометить `final`, заблокируйте наследование через конструктор:
```java
public class SecureMoney {
    private final long amount;

    // Конструктор закрыт — сторонний класс не сможет вызвать super()!
    private SecureMoney(long amount) {
        this.amount = amount;
    }

    public static SecureMoney of(long amount) {
        return new SecureMoney(amount);
    }
}
```

## 🔴 Senior Level

### Современный стандарт: Sealed Hierarchy (Java 17+) и Algebraic Data Types

Если архитектура **действительно требует иерархии типов**, в современном Java используется механизм **`sealed` классов и интерфейсов**:

```java
// Корневой контракт жестко ограничивает список возможных наследников:
public sealed interface TransactionResult permits Success, Failure {}

// Все реализации обязаны быть строго иммутабельными (Records неявно final):
public record Success(String txId, long timestamp) implements TransactionResult {}
public record Failure(String errorCode, String reason) implements TransactionResult {}
```

**Преимущества для Senior:**
1. **Строгий контроль**: сторонний код не может создать свой неконтролируемый подкласс.
2. **Exhaustive Pattern Matching (Java 21+)**: компилятор проверяет полноту покрытия веток в `switch` без блока `default`:
   ```java
   String message = switch (result) {
       case Success s -> "OK: " + s.txId();
       case Failure f -> "Error: " + f.reason();
   };
   ```

### Уязвимости безопасности (Security Exploits)

В библиотеках безопасности и криптографии (JDK Security Providers) отсутствие `final` у классов ключей или сертификатов позволяло внедрять вредоносные классы, переопределяющие методы проверки цифровой подписи (Time-of-Check to Time-of-Use / TOCTOU атаки). Именно поэтому все классы в `java.lang.*` и `java.time.*` закрыты модификатором `final`.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Наследование от иммутабельного класса — антипаттерн, так как подкласс может добавить мутабельное состояние и переопределить методы.
- Нарушает контракт Liskov Substitution Principle (LSP) и разрушает потокобезопасность.
- Защита: объявление класса как **`final`** или закрытие конструктора (**`private constructor`** + static factory).
- Все базовые классы JDK (`String`, `Integer`, `LocalDate`, `BigDecimal`) объявлены как `final`.
- В Java 17+ для построения безопасных иерархий используются **`sealed` классы** в связке с `record`.

**Частые уточняющие вопросы:**
- **Почему нельзя просто сделать поля подкласса final?** — Подкласс всё равно может переопределить геттер суперкласса и возвращать динамические или случайные значения.
- **Как расширить функционал иммутабельного класса без наследования?** — Через паттерн «Композиция» (вложить иммутабельный объект внутрь нового класса).
- **В чём преимущество Sealed Classes перед final?** — Sealed позволяет создать закрытую иерархию типов (например, `Result = Success | Failure`), не допуская произвольных наследников из внешних библиотек.

**Красные флаги (НЕ говорить):**
- ❌ «Наследоваться от иммутабельного класса абсолютно безопасно, если не добавлять сеттеры».
- ❌ «`final` классы ухудшают объектно-ориентированный дизайн и их следует избегать».
- ❌ «В Java 17 `Record` можно унаследовать от обычного класса».
