# Как иммутабельность влияет на производительность?

---

## 🟢 Junior Level

### Главный баланс: Память vs Скорость многопоточности

Влияние иммутабельности на производительность нельзя охарактеризовать однозначно как «быстрее» или «медленнее». Это классический инженерный компромисс (Trade-off):

- **Минусы для производительности (CPU & Memory)**:
  - Любая «модификация» требует создания нового объекта в куче (Heap) и копирования данных.
  - Увеличивается нагрузка на Garbage Collector (GC pressure) при создании миллионов временных объектов.
- **Плюсы для производительности (Concurrency & Optimization)**:
  - **Нулевые затраты на блокировки (Lock-Free)**: чтение иммутабельных данных из десятков параллельных потоков не требует `synchronized`, `ReentrantLock` или `volatile`.
  - Отсутствие расходов на создание защитных копий (Zero Defensive Copying).
  - Глубокие оптимизации JIT-компилятора.

### Простое эмпирическое правило:

```
Интенсивная сборка / цикл в 1 потоке  ──► Мутабельность быстрее (StringBuilder, ArrayList)
Передача данных между 10+ потоками    ──► Иммутабельность быстрее (Records, String, Immutable Collections)
```

**Пример:**
```java
// ❌ МЕДЛЕННО (Создает 10 000 объектов String в цикле):
String text = "";
for (int i = 0; i < 10_000; i++) {
    text += i; // $O(N^2)$ по времени и памяти!
}

// ✅ БЫСТРО (Мутабельный буфер для сборки):
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10_000; i++) {
    sb.append(i);
}
String finalImmutableText = sb.toString(); // Зафиксировали в иммутабельный String
```

## 🟡 Middle Level

### 1. Lock-Free масштабируемость в Highload

В многопоточных веб-сервисах (Spring Boot, Netty) наибольшие задержки вызывают не вычисления, а **конкуренция за блокировки (Lock Contention)**:
- Потоки, пытающиеся прочитать мутабельный объект, блокируются на мьютексах, вызывая системные вызовы ядра ОС (`park()` / `unpark()`) и переключение контекста процессора (Context Switch $\approx 1000$–$2000$ тактов CPU).
- **Иммутабельные объекты читаются без блокировок**: производительность системы масштабируется линейно с добавлением ядер процессора.

### 2. JIT Оптимизации: Constant Folding & Scalar Replacement

Компилятор JVM HotSpot (C2) активно использует `final`-поля:
1. **Constant Folding**: Значения, вычисленные от иммутабельных констант, вычисляются один раз на этапе JIT-компиляции.
2. **Escape Analysis & Scalar Replacement**: Если JIT доказывает, что временный иммутабельный объект не покидает пределы метода, он вообще **не выделяет память в Heap**: объект раскладывается на простые регистры процессора CPU (Scalar Replacement), работая со скоростью языка C.

## 🔴 Senior Level

### Стоимость аллокаций: TLAB и Bump-the-Pointer

Senior разработчик должен понимать, почему создание короткоживущих иммутабельных объектов в Java происходит чрезвычайно быстро:

1. **TLAB (Thread-Local Allocation Buffer)**:
   - Каждому потоку в области памяти **Eden (Young Generation)** выделяется персональный буфер памяти.
   - Аллокация нового объекта не требует синхронизации между потоками и сводится к единственной процессорной инструкции **Bump-the-Pointer**:
     ```asm
     add r10, size   ; просто сдвигаем указатель свободной памяти вперед
     ```
   - Создание объекта в TLAB занимает **всего 1–2 такта CPU** (так же быстро, как выделение памяти на стеке).
2. **Бесплатная очистка в Minor GC**:
   - Согласно Generational Hypothesis, 98% временных иммутабельных объектов умирают в Eden space до первого вызова сборщика мусора.
   - Сборщик мусора копирует только *выжившие* объекты, поэтому мертвые объекты очищаются мгновенным сбросом указателя TLAB без накладных расходов.

### Отсутствие GC Write Barriers

В современных сборщиках мусора (G1, ZGC) перезапись ссылки в существующем мутабельном объекте вызывает накладные расходы **GC Write Barrier** (обновление таблицы Card Table / Remembered Sets для отслеживания ссылок из Old Gen в Young Gen).
- Иммутабельные объекты **никогда не изменяют свои ссылки** после конструирования, освобождая процессор от непрерывных проверок Write Barriers.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Иммутабельность замедляет однопоточные мутации (создание новых объектов, $O(N)$ копирование), но ускоряет многопоточное чтение (отсутствие блокировок, context switches).
- Паттерн «Мутабельный сборщик $\rightarrow$ Иммутабельный результат»: использовать `StringBuilder`/`ArrayList` для локальной сборки, а отдавать в систему `String`/`Record`/`List.copyOf()`.
- Выделение памяти под короткоживущие объекты в Java происходит мгновенно благодаря **TLAB** (Bump-the-pointer за 1-2 такта CPU).
- `final` поля позволяют JIT выполнять **Scalar Replacement** (раскладка объекта в регистры CPU без аллокации в Heap).
- Иммутабельные объекты устраняют накладные расходы на **GC Write Barriers**.

**Частые уточняющие вопросы:**
- **Почему конкатенация String в цикле медленная?** — Каждый `+` создает новый объект и копирует массив символов, порождая квадратичную сложность $O(N^2)$.
- **Что такое Scalar Replacement?** — JIT-оптимизация, заменяющая создание объекта в куче хранением его полей непосредственно в регистрах процессора или стеке.
- **Как TLAB ускоряет создание иммутабельных объектов?** — Потоки аллоцируют объекты в локальных буферах памяти без блокировок простым сдвигом указателя.

**Красные флаги (НЕ говорить):**
- ❌ «Иммутабельность всегда снижает производительность из-за создания объектов».
- ❌ «В Java создание любого объекта требует системного вызова `malloc()` ядра ОС».
- ❌ «Для оптимизации многопоточности лучше всегда использовать мутабельные объекты с `synchronized`».
