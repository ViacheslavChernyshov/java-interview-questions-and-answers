# Что произойдёт, если изменить мутабельный ключ в HashMap?

---

## 🟢 Junior Level

### Простой ответ

Если изменить объект, который уже используется в качестве ключа в `HashMap`, **этот элемент станет «невидимым» и потеряется**: вы не сможете извлечь его через `map.get(key)` или удалить через `map.remove(key)`.

Объект **физически останется лежать в памяти** внутри внутренней таблицы `HashMap`, но для всех стандартных операций поиска он превратится в «зомби-запись».

### Наглядный пример:

```java
// Мутабельный список в роли ключа:
List<String> userRoles = new ArrayList<>(List.of("USER"));

Map<List<String>, String> permissions = new HashMap<>();
permissions.put(userRoles, "READ_ONLY_ACCESS");

// Проверяем — всё работает:
System.out.println(permissions.get(userRoles)); // "READ_ONLY_ACCESS"

// 💥 КАТАСТРОФА: Изменяем мутабельный ключ после добавления в карту!
userRoles.add("ADMIN");

// Пытаемся получить значение по тому же самому объекту:
System.out.println(permissions.get(userRoles)); // ❌ вернёт null!
System.out.println(permissions.containsKey(userRoles)); // ❌ вернёт false!
System.out.println(permissions.size()); // вернёт 1 (объект всё ещё в карте!)
```

### Аналогия из жизни

Представьте **камеру хранения на вокзале**:
- Вы сдали чемодан синего цвета. Автомат вычислил номер ячейки по цвету: «Синий $\rightarrow$ Ячейка №5» и положил чемодан туда.
- Ночью чемодан перекрасили в красный цвет.
- Утром вы подходите к автомату и говорите: «Найди мой красный чемодан». Автомат вычисляет «Красный $\rightarrow$ Ячейка №10», открывает ячейку №10 — она пуста, и сообщает: «Вашего чемодана нет». Чемодан остался заперт в ячейке №5 навсегда.

## 🟡 Middle Level

### Внутреннее устройство `HashMap`: Двойная точка отказа

Чтобы понять, почему объект теряется, разберём исходный код метода `HashMap.getNode()`:

```java
final Node<K,V> getNode(Object key) {
    Node<K,V>[] tab; Node<K,V> first, e; int n, hash; K k;
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (first = tab[(n - 1) & (hash = hash(key))]) != null) { // 1. Вычисление индекса бакета
        
        // 2. Проверка первого узла в бакете:
        if (first.hash == hash && // ⚠️ Сравнение кэшированного хеша!
            ((k = first.key) == key || (key != null && key.equals(k))))
            return first;
        
        // 3. Обход цепочки/дерева в бакете...
    }
    return null;
}
```

Когда ключ мутирует, происходят **два критических сбоя**:

1. **Сбой 1: Поиск не в том бакете (Bucket Mismatch)**:
   - При `put()` вычислен старый хеш $\rightarrow$ элемент помещен в `table[5]`.
   - При `get()` вычисляется новый `key.hashCode()` $\rightarrow$ мапа ищет в `table[12]`. В бакете №12 ячейка пуста $\rightarrow$ возврат `null`.
2. **Сбой 2: Поломка даже при коллизии бакетов (`first.hash != hash`)**:
   - Даже если из-за совпадения остатка от деления `(n - 1) & hash` новый хеш укажет на тот же бакет №5, внутри `Node<K,V>` хранится **кэшированное значение `hash`**, вычисленное при вставке!
   - Условие `first.hash == hash` вернет `false`, и `HashMap` проигнорирует найденный узел, даже если `first.key == key` вернет `true`!

### Дубликаты в `HashSet`

Поскольку `HashSet` внутри использует `HashMap<E, Object>`, мутация элемента в сете позволяет добавить его **повторно**:
```java
Set<List<String>> set = new HashSet<>();
List<String> list = new ArrayList<>(List.of("A"));
set.add(list);

list.add("B"); // Изменили
set.add(list); // Успешно добавится второй раз!

System.out.println(set.size()); // 2 одинаковых объекта по ссылке в одном Set!
```

## 🔴 Senior Level

### Утечка памяти (Memory Leak) и аварийный Resize

1. **Zombie Entry Leak**:
   - Потерянный элемент удерживается сильной ссылкой из массива `Node<K,V>[] table`.
   - Garbage Collector **не может удалить ни ключ, ни значение**, даже если в коде больше нет ссылок на эти объекты.
   - Освободить память можно только полной очисткой `map.clear()` или перебором `entrySet().iterator().remove()`.
2. **Катастрофа при рехешировании (`resize()`)**:
   - Когда размер карты превышает порог `threshold` (`capacity * 0.75`), `HashMap` удваивает массив `table`.
   - При переносе узлов `HashMap` использует **старый кэшированный `node.hash`**, распределяя узел по битовой маске `hash & oldCap`.
   - В результате потерянный элемент перемещается в новый бакет на основе своего *старого* хеша, делая его поиск через новые методы `get()` окончательно невозможным.

### 3 архитектурных решения проблемы

#### 1. Использование иммутабельных ключей (Default Rule)
Всегда использовать `String`, `UUID`, `Long` или `Record`:
```java
public record UserKey(String tenantId, String userId) {} // Иммутабелен из коробки!
```

#### 2. Паттерн «Remove $\rightarrow$ Mutate $\rightarrow$ Put»
Если объект обязан измениться, его необходимо **извлечь из карты до изменения**:
```java
String value = map.remove(key); // 1. Удалили по СТАРОМУ хешу
key.addRole("ADMIN");           // 2. Изменили объект
map.put(key, value);            // 3. Добавили по НОВОМУ хешу
```

#### 3. `IdentityHashMap`
Если ключи должны сравниваться строго по ссылке (`==`), а не по содержимому:
- `IdentityHashMap` использует `System.identityHashCode(key)` (адрес в памяти), который никогда не меняется при мутации полей объекта.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- При мутации ключа его `hashCode()` меняется $\rightarrow$ `HashMap.get()` ищет элемент в другом бакете и возвращает `null`.
- Даже если бакет совпал, поиск упадет из-за несовпадения сохраненного `node.hash` и нового `hash`.
- Потерянный элемент остаётся в памяти карты, вызывая **тихую утечку памяти (Memory Leak)**.
- В `HashSet` мутация приводит к появлению одинаковых дубликатов.
- Единственный способ найти потерянный элемент — полный перебор `entrySet()` за $O(N)$.
- Правило: ключи `HashMap` обязаны быть строго **иммутабельными** (`String`, `Record`, `UUID`).

**Частые уточняющие вопросы:**
- **Удаляется ли объект из памяти при изменении ключа?** — Нет, объект остаётся в старом бакете массива `table`, удерживая память до вызова `map.clear()`.
- **Почему не помогает проверка `first.key == key`?** — Перед сравнением ключей `HashMap` всегда сравнивает хеши `first.hash == hash`. При мутации это условие вернет `false`.
- **Как безопасно изменить мутабельный ключ?** — `map.remove(key)` $\rightarrow$ изменить объект $\rightarrow$ `map.put(key, value)`.
- **Чем отличается IdentityHashMap?** — Сравнивает ключи через `==` и использует `System.identityHashCode()`, не зависящий от мутации полей.

**Красные флаги (НЕ говорить):**
- ❌ «HashMap автоматически пересчитывает хеши ключей при их изменении».
- ❌ «При изменении ключа объект автоматически удаляется сборщиком мусора».
- ❌ «В качестве ключа HashMap можно спокойно использовать `ArrayList` или мутабельные DTO».
