# Если два объекта имеют одинаковый hashCode(), обязательно ли они равны по equals()?

---

## 🟢 Junior Level

### Простой и категоричный ответ

**НЕТ, НЕ ОБЯЗАТЕЛЬНО!**

Совпадение `hashCode()` у двух разных объектов называется **коллизией хеш-функции (Hash Collision)**. Это абсолютно нормальная, штатная ситуация при работе с хеш-таблицами в Java.

### Золотое правило контракта `equals` и `hashCode`:

```
1. Если a.equals(b) == true   ──► a.hashCode() == b.hashCode()  (ОБЯЗАТЕЛЬНО!)
2. Если a.hashCode() == b.hashCode() ──► a.equals(b) может быть как true, так и false (КОЛЛИЗИЯ!)
```

### Наглядный пример коллизии строк:

```java
String s1 = "Aa";
String s2 = "BB";

System.out.println(s1.hashCode()); // 2112
System.out.println(s2.hashCode()); // 2112

System.out.println(s1.equals(s2)); // false — строки абсолютно разные!
```

### Аналогия из жизни

Представьте **однофамильцев в телефонном справочнике**:
- **`hashCode()`** — это фамилия («Иванов»). На букву «И» в справочнике зарегистрированы сотни людей.
- **`equals()`** — это полные паспортные данные (ФИО, серия и номер паспорта).
- Тот факт, что у двух людей одинаковая фамилия «Иванов», **не делает их одним и тем же человеком**!

## 🟡 Middle Level

### Математическое обоснование: Принцип Дирихле (Pigeonhole Principle)

Почему совпадение `hashCode()` неизбежно:
1. Метод `hashCode()` возвращает примитивный 32-битный тип **`int`**.
2. Максимальное количество уникальных значений `int` ограничено: $2^{32} \approx 4{,}294{,}967{,}296$ (около 4.3 миллиарда).
3. Количество возможных строковых комбинаций или состояний бизнес-объектов **бесконечно** (даже строка из 10 латинских букв имеет $26^{10} \approx 141$ триллион вариантов).
4. **По принципу Дирихле**: если разложить бесконечное число объектов в 4.3 млрд ячеек, неизбежно найдутся разные объекты, попадающие в одну ячейку.

### Пример коллизии для типа `Long`

В классе `java.lang.Long` хеш-код вычисляется как свёртка 64-битного числа в 32 бита:
```java
public static int hashCode(long value) {
    return (int)(value ^ (value >>> 32)); // XOR старших и младших 32 бит
}
```
Из-за этого числа `1L` и `4294967297L` ($1 + 2^{32}$) имеют **абсолютно одинаковый `hashCode() == 1`**, но `equals()` вернёт `false`.

### Двухступенчатый фильтр поиска в `HashMap`

`HashMap` использует `hashCode()` и `equals()` как многоуровневый фильтр:

```
Запрос get(key):
   │
   ▼
[Шаг 1: hashCode()] ──► Вычисляет бакет за O(1), мгновенно отсекая 99.9% остальных элементов
   │
   ▼
[Шаг 2: equals()]   ──► Поэлементно сравнивает только те немногие объекты, которые попали в этот бакет
```

## 🔴 Senior Level

### Hash Spreader в Java 8+

Чтобы уменьшить вероятность коллизий младших бит в небольших массивах бакетов, `HashMap` в Java 8+ применяет функцию подмешивания (Hash Spreader):

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```
Сдвиг `h >>> 16` и операция `XOR` подмешивают старшие 16 бит хеша в младшие, предотвращая коллизии при малых размерах таблицы (`table.length = 16, 32, 64`).

### Hash-Flooding DoS-атака и древовидная трансформация (Treeification)

В Java 7 злоумышленник мог отправить на сервер HTTP POST-запрос с 10 000 JSON-полей, специально подобранных так, чтобы их `hashCode()` совпадал (например, строки вида `"AaAa"`, `"AaBB"`, `"BBAa"`).
- В Java 7 это превращало бакет в связный список длиной 10 000 элементов. Вставка каждого поля занимала $O(N)$, приводя к квадратичной сложности $O(N^2)$ и **100% загрузке CPU (Denial of Service)**.
- **Защита в Java 8+ (JEP 180)**: При превышении порога `TREEIFY_THRESHOLD = 8` в бакете список преобразуется в **красно-черное дерево (`TreeNode`)**, снижая худшую сложность поиска и вставки с $O(N)$ до **$O(\log N)$**.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Одинаковый `hashCode()` **НЕ означает** равенство по `equals()`. Это называется **коллизией**.
- Равенство по `equals()` **СТРОГО гарантирует** одинаковый `hashCode()`.
- Классический пример коллизии строк: `"Aa".hashCode() == "BB".hashCode() == 2112`.
- Коллизии неизбежны из-за принципа Дирихле: диапазон `int` (32 бита $\approx 4.3$ млрд) ограничен, а число возможных объектов бесконечно.
- В `HashMap` `hashCode()` определяет номер бакета ($O(1)$ грубый фильтр), а `equals()` находит точный ключ внутри бакета.
- В Java 8+ при коллизиях от 8 элементов бакет превращается в красно-черное дерево (`TreeNode`, $O(\log N)$) для защиты от Hash-Flooding DoS атак.

**Частые уточняющие вопросы:**
- **Почему класс String использует множитель 31 в формуле hashCode?** — Число 31 — нечетное простое число, а умножение `31 * h` оптимизируется процессором в быстрый сдвиг `(h << 5) - h`.
- **Что происходит в HashMap, если два ключа имеют одинаковый hashCode?** — Они помещаются в один бакет (связный список или красно-черное дерево) и различаются через `equals()`.
- **Как Long генерирует hashCode?** — `(int)(value ^ (value >>> 32))` — сворачивает 64 бита в 32 через XOR.

**Красные флаги (НЕ говорить):**
- ❌ «Если у двух объектов одинаковый хеш-код, они 100% равны».
- ❌ «Качественный алгоритм hashCode обязан исключать любые коллизии».
- ❌ «При возникновении коллизии в HashMap один из объектов перезаписывает другой».
