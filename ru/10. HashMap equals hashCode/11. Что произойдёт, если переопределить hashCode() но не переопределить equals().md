# Что произойдёт, если переопределить hashCode(), но не переопределить equals()?

---

## 🟢 Junior Level

### Простой ответ

Если вы переопределите только **`hashCode()`**, но забудете переопределить **`equals()`**:
1. Объекты с одинаковым содержимым попадут в **один и тот же бакет** `HashMap`.
2. Однако при проверке внутри бакета `HashMap` использует стандартный `Object.equals()`, который сравнивает **ссылки в памяти (`==`)**, а не поля объектов.
3. В результате `HashMap` посчитает два логически одинаковых объекта **совершенно разными ключами**.

### Наглядный пример:

```java
public class Product {
    private final String sku;

    public Product(String sku) { this.sku = sku; }

    @Override
    public int hashCode() {
        return sku.hashCode(); // Хеш переопределен!
    }
    // equals() ЗАБЫЛИ! Осталась реализация Object.equals (сравнение по ссылке)
}

Map<Product, Integer> stock = new HashMap<>();
stock.put(new Product("SKU-100"), 50); // Положили в бакет

// Пытаемся достать по новому объекту с тем же SKU:
Integer count = stock.get(new Product("SKU-100"));

System.out.println(count); // ❌ вернёт null!
System.out.println(stock.size()); // 1
```

### Аналогия из жизни

Представьте **камеру хранения на вокзале**:
- Вы сдали посылку с кодом `SKU-100`. Робот положил её на полку №5 (`hashCode` совпал).
- Вы приходите за посылкой с тем же кодом `SKU-100`. Робот подходит к полке №5, но просит предъявить паспорт с отпечатком пальца (`equals`).
- Так как вы принесли новый бланк (`new Product(...)`), отпечаток пальца не совпадает с оригиналом. Робот говорит: «Посылка на полке лежит, но я вам её не отдам, это не вы».

## 🟡 Middle Level

### Сравнение двух фатальных ошибок контракта `equals / hashCode`

| Ситуация | Поиск бакета при `get()` | Поиск внутри бакета | Результат `get()` | Поведение `HashSet` |
| :--- | :--- | :--- | :--- | :--- |
| **Переопределен `equals`, забыт `hashCode`** | ❌ **Ищет не в том бакете** (рандомный `hashCode`) | Не доходит до проверки | `null` | Дубликаты в разных бакетах |
| **Переопределен `hashCode`, забыт `equals`** | ✅ **Ищет в правильном бакете** | ❌ **Падает проверка `equals`** (сравнивает `this == obj`) | `null` | Дубликаты в одном бакете |

### Пошаговая трассировка выполнения `map.get(new Product("SKU-100"))`

```java
// 1. Вычисляется хеш ключа: hash = "SKU-100".hashCode()
// 2. Определяется индекс бакета: index = (n - 1) & hash -> например, бакет 5
// 3. HashMap берет первый узел table[5]:
if (first.hash == hash && 
   ((k = first.key) == key || (key != null && key.equals(k)))) // ⚠️ key.equals(k)
```
- `first.hash == hash` $\rightarrow$ `true` (хеши совпали).
- `(k = first.key) == key` $\rightarrow$ `false` (разные ссылки в куче: `0x100 != 0x200`).
- `key.equals(k)` $\rightarrow$ вызывается `Object.equals()`, который выполняет `this == obj` $\rightarrow$ `false`!
- Итог: `HashMap` перебирает весь бакет и возвращает **`null`**.

## 🔴 Senior Level

### Утечка памяти при десериализации (JSON / Kafka / REST DTOs)

Самый опасный сценарий в Production — использование таких DTO в кэшах дедупликации:

```java
@Service
public class EventDeduplicator {
    private final Set<EventDto> processedEvents = new HashSet<>();

    public void process(EventDto event) {
        // EventDto десериализуется из Jackson JSON на каждый HTTP/Kafka запрос:
        if (!processedEvents.add(event)) { 
            log.warn("Дубликат события: {}", event.getId());
            return;
        }
        businessLogic(event);
    }
}
```

**Катастрофа в Production:**
- Каждый входящий запрос создает **новый экземпляр `EventDto`** в памяти.
- `processedEvents.add(event)` всегда возвращает `true`, так как `equals()` сравнивает ссылки.
- **Итог**:
  1. Дедупликация **не работает вообще** (дубликаты обрабатываются многократно).
  2. Коллекция `processedEvents` раздувается в одном бакете до миллионов объектов $\rightarrow$ **`OutOfMemoryError: Java heap space`**.

### Деградация производительности и раздувание `TreeNode`

1. Все создаваемые объекты скапливаются в одном бакете хеш-таблицы.
2. При превышении `TREEIFY_THRESHOLD = 8` связный список бакета превращается в красно-черное дерево (**`TreeNode`**).
3. Так как класс не реализует `Comparable<Product>`, дереву приходится прибегать к запасному компаратору **`tieBreakOrder(a, b)`** с вызовом нативного `System.identityHashCode()` на каждом поиске/вставке, что полностью уничтожает кэш-локальность CPU и замедляет работу сервиса в тысячи раз.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Переопределение только `hashCode()` направляет объекты в правильный бакет, но `Object.equals()` сравнивает их по ссылке (`this == obj`).
- `map.get(new Key(...))` вернёт `null`, так как новый экземпляр не равен старому по ссылке.
- `HashSet` будет бесконечно расти, сохраняя логические дубликаты в одном бакете.
- В кэшах и дедупликаторах это приводит к `OutOfMemoryError` и повторной обработке событий.
- Золотое правило Java: **всегда переопределять `equals()` и `hashCode()` парой** (или использовать `Record` / `@EqualsAndHashCode`).

**Частые уточняющие вопросы:**
- **В чём разница между забытым equals() и забытым hashCode()?** — При забытом `hashCode` поиск идёт не в том бакете; при забытом `equals` поиск идёт в правильном бакете, но объект не признаётся равным.
- **Что вернёт `set.contains(new Key("A"))`, если в сете уже есть `new Key("A")`?** — Вернёт `false`, так как ссылки разные.
- **Как автоматизировать соблюдение контракта?** — Использовать Java 16+ `Record`, Lombok аннотацию `@EqualsAndHashCode`, либо генераторы IDE.

**Красные флаги (НЕ говорить):**
- ❌ «Если hashCode одинаковый, то `equals()` вызывать необязательно».
- ❌ «HashMap сравнивает ключи только по их хеш-коду».
- ❌ «Ошибка без `equals` менее критична, чем ошибка без `hashCode`».
