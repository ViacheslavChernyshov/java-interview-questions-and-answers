# Какие проблемы возникают при использовании общей базы данных

---

## 🟢 Junior Level

### Что такое Shared Database в микросервисах

**Shared Database (Общая база данных)** — это архитектурный антипаттерн, при котором несколько независимых микросервисов обращаются напрямую к одной и той же физической или логической базе данных, читая и изменяя одни и те же таблицы.

```
       ┌───────────────────┐       ┌────────────────────┐
       │   Order Service   │       │    User Service    │
       └─────────┬─────────┘       └─────────┬──────────┘
                 │                           │
                 └─────────────┬─────────────┘
                               ▼
                    ┌─────────────────────┐
                    │   SHARED DATABASE   │ ◄── ❌ АНТИПАТТЕРН!
                    │ (users, orders, ...)│
                    └─────────────────────┘
```

### Аналогия из реальной жизни

Представьте **несколько независимых квартир в доме с одной общей кухней и холодильником**:
- Жильцы одной квартиры решают переставить все полки в холодильнике или выбросить просроченные продукты, не предупредив соседей.
- Соседи приходят готовить ужин и обнаруживают, что их продуктов нет на привычном месте — весь процесс парализован.
- В микросервисах каждый сервис должен иметь свою изолированную «кухню» (Database per Service) и общаться с другими через официальные протоколы (REST/gRPC/Kafka).

### Основные проблемы для начинающих:
1. **Жесткая связанность по схеме (Schema Coupling)**: переименование или удаление столбца ломает другие сервисы.
2. **Потеря независимости релизов**: невозможно задеплоить один сервис без согласования с другими командами.
3. **Единая точка отказа (Single Point of Failure)**: падение СУБД останавливает работу всех микросервисов компании.

## 🟡 Middle Level

### Технические последствия использования Shared DB

| Проблема | Механизм возникновения | Последствия для продакшена |
| :--- | :--- | :--- |
| **Schema Coupling** | Сервис А выполняет `ALTER TABLE users DROP COLUMN phone;` | Сервис Б падает с `SQLException: column phone does not exist`. |
| **Connection Pool Starvation** | Сервис аналитики забирает все 100 соединений из HikariCP для тяжелого отчета. | Сервис авторизации не может получить соединение $\rightarrow$ отказ в обслуживании (HTTP 503). |
| **Lock Contention & Escalation** | Сервис заказов обновляет 10 000 строк в транзакции $\rightarrow$ СУБД эскалирует построчную блокировку до блокировки всей таблицы (Table Lock). | Сервис пользователей зависает на простом `SELECT ... WHERE id = ?`. |
| **Data Ownership & Migration Conflict** | Две команды пишут свои миграции через Liquibase/Flyway в одну БД. | Конфликты `schema_version`, deadlocks при миграциях во время деплоя. |

### Наглядный пример поломки в коде

```java
// Сервис А (Order Service) ожидает поле address:
@Entity
@Table(name = "customers")
public class CustomerEntity {
    @Id
    private Long id;
    private String address; // Связан с колонкой 'address'
}

// Сервис Б (User Service) в новом релизе нормализовал адрес в отдельную таблицу:
// Migration V2__split_address.sql:
// ALTER TABLE customers DROP COLUMN address;

// РЕЗУЛЬТАТ: Сервис А моментально падает при первом же запросе!
```

## 🔴 Senior Level

### Процесс разделения Shared DB: Strangler Fig Pattern

Переход от Shared DB к Database per Service — одна из самых сложных задач в архитектуре распределённых систем.

```
Этап 1: Shared DB ──► Этап 2: CDC / Dual-Write ──► Этап 3: Database per Service
```

#### Шаги безопасной миграции без простоя (Zero Downtime):

1. **Определение владельца данных (Bounded Context)**:
   - Таблица `users` принадлежит только `User Service`.
   - Всем остальным сервисам **запрещается прямой SQL-доступ** к таблице `users`. Доступ переводится на REST/gRPC API сервиса-владельца.
2. **Выделение физической БД**:
   - Создаётся новая изолированная база данных `user_db`.
3. **Репликация данных через Change Data Capture (CDC)**:
   - Инструменты типа **Debezium + Kafka Connect** вычитывают WAL/Binlog старой БД и в реальном времени переносят изменения в новую `user_db`.
4. **Shadow Traffic / Dark Launching**:
   - `User Service` начинает читать из новой `user_db`, но в фоне сравнивает ответы со старой БД для проверки целостности.
5. **Окончательное переключение**:
   - Запись переводится на новую `user_db`.
   - Старая таблица в общей БД удаляется.

### Поддержание консистентности между разделенными БД

Когда общая БД распадается на независимые сервисы, исчезает возможность выполнять межбазовые ACID-транзакции и прямые SQL JOIN.

**Инструменты решения на уровне Senior:**
1. **Transactional Outbox Pattern**: гарантирует атомарную запись сущности в БД и отправку события в Kafka без распределённых транзакций (XA/2PC).
2. **Saga Pattern (Оркестрация / Хореография)**: для распределённых бизнес-транзакций с компенсирующими действиями.
3. **CQRS & Read Models**: для сложных выборок, которые раньше делались через `JOIN`, создаётся отдельный агрегирующий сервис с материализованным представлением (Read Model в Elasticsearch или PostgreSQL).

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Shared DB — антипаттерн, превращающий микросервисы в «распределённый монолит» (Distributed Monolith).
- Главные проблемы: Schema Coupling (миграции ломают чужой код), Connection Pool Exhaustion (конкуренция за пулы соединений), Lock Contention (тяжёлые транзакции блокируют чужие таблицы).
- Отсутствие владельца данных: размывается ответственность за целостность и миграции (Flyway/Liquibase).
- Паттерн решения: **Database per Service**. Доступ к данным только через публичные API или асинхронные события.
- Миграция: Strangler Fig + CDC (Debezium / Kafka Connect) для переноса данных без простоя.
- Замена межбазовых транзакций: Outbox Pattern + Saga Pattern.

**Частые уточняющие вопросы:**
- **Почему нельзя делать JOIN между таблицами разных сервисов?** — Это жестко привязывает сервисы к схеме данных друг друга, делая невозможным независимое масштабирование и рефакторинг.
- **Что делать, если одному сервису постоянно нужны данные другого?** — Репликация через события (Event-Driven Data Replication), кэширование или CQRS Read-модель.
- **В чём опасность миграций Flyway в общей БД?** — Одновременный запуск миграций разными сервисами приводит к конфликту блокировок таблицы `flyway_schema_history` и рассинхронизации версий.
- **Когда Shared DB допустима?** — На ранней стадии стартапа (MVP/PoC), но при условии разделения на уровне схем (Postgres Schemas) как временный шаг к разделению.

**Красные флаги (НЕ говорить):**
- ❌ «Shared DB — отличный способ сэкономить ресурсы и легко делать JOIN между сервисами».
- ❌ «Мы разделили код на микросервисы, но БД оставили общей — это полноценная микросервисная архитектура».
- ❌ «Проблему изменения схемы в общей БД можно решить рассылкой писем разработчикам перед деплоем».
