# Что такое паттерн Strangler Fig?

---

## 🟢 Junior Level

### Происхождение названия и суть паттерна

Паттерн **Strangler Fig (Удушающий инжир)** был описан Мартином Фаулером (Martin Fowler) после поездки в тропические леса Австралии. В природе семечко этого растения прорастает в кроне взрослого дерева, пускает корни к земле, оплетает ствол и со временем полностью заменяет собой старое дерево, которое постепенно отмирает.

В IT-архитектуре **Strangler Fig** — это проверенная стратегия **постепенной, безопасной миграции крупного монолитного приложения на микросервисы**.

```
Фаза 0:  [═════════════════ Монолит ═════════════════]

Фаза 1:  [══════════════ Монолит ══════════════] + [User Service]
Фаза 2:  [═══════════ Монолит ═══════════] + [User Service] + [Order Service]
Фаза 3:  [═══ Монолит ═══] + [User Service] + [Order Service] + [Payment Service]
Фаза 4:  [User Service] + [Order Service] + [Payment Service] + [Notification Service] (Монолит выключен!)
```

### Почему «Big Bang Rewrite» — это антипаттерн?

- **Big Bang (Переписать всё с нуля заново за 2 года)**: команда 2 года пишет новую систему «в вакууме», пока бизнес развивает старый монолит. В день релиза новая система не готова к 50% скрытых требований и проект закрывается с миллионными убытками.
- **Strangler Fig**: каждый спринт (2-4 недели) отделяется один изолированный кусок (например, модуль уведомлений), сразу выкатывается в Production и начинает приносить пользу бизнесу без остановки монолита.

## 🟡 Middle Level

### 4 шага миграционного цикла (Intercept $\rightarrow$ Transform $\rightarrow$ Coexist $\rightarrow$ Eliminate)

```
                       ┌───────────────────────────────┐
                       │      API Gateway / Ingress    │
                       └───────┬───────────────┬───────┘
            /api/v1/orders     │               │  /api/v1/users (мигрировано!)
                               ▼               ▼
                      ┌────────────────┐ ┌─────────────────┐
                      │    Монолит     │ │  User Service   │
                      └────────────────┘ └─────────────────┘
```

1. **Intercept (Перехват)**: Перед монолитом ставится **API Gateway** (Spring Cloud Gateway, Kong, Nginx). Все клиенты шлют запросы только на Gateway.
2. **Transform (Реализация)**: Новый изолированный Bounded Context (например, `User Service`) разрабатывается с отдельной базой данных.
3. **Coexist (Сосуществование)**: Gateway начинает маршрутизировать `/api/v1/users` на новый микросервис, а все остальные запросы оставляет на монолите.
4. **Eliminate (Удаление)**: Старый код работы с пользователями внутри монолита удаляется, очищая кодовую базу.

## 🔴 Senior Level

### Проблема синхронизации данных: Dual Writing vs CDC (Change Data Capture)

При миграции сервиса его данные должны быть перенесены из монолитной БД в изолированную БД микросервиса.

#### ❌ Почему наивный Dual Writing ломает согласованность:
Если монолит одновременно делает `UPDATE monolith_db` и шлет HTTP/Kafka событие в `new_service_db`:
- При сбое сети монолит запишет данные, а микросервис нет.
- При двух одновременных запросах возникнет гонка (Race Condition), и в новой БД останется устаревшая версия (Out-of-order write).

#### ✅ Архитектурный стандарт Senior: CDC (Debezium + Kafka Connect)
```
[Monolith PostgreSQL] ──(WAL / Binlog)──► [Debezium CDC] ──► [Kafka Topic] ──► [New Microservice DB]
```
- Изменения вычитываются напрямую из транзакционного журнала БД (WAL) с гарантией Exactly-Once / At-Least-Once.
- Монолит даже не знает о том, что данные реплицируются в новый сервис.

### Теневой трафик (Traffic Shadowing / Dark Launching)

Перед тем как переключить реальных пользователей на новый микросервис:
1. **Shadowing**: API Gateway дублирует 100% входящих запросов в новый микросервис асинхронно в фоне.
2. **Diff Engine**: Специальный прокси сравнивает HTTP-ответы монолита и микросервиса на 1 000 000 реальных запросов:
   - Если расхождений $0\%$, а задержки (p99 latency) в норме — переключается рабочий трафик через Feature Flag (1% $\rightarrow$ 10% $\rightarrow$ 50% $\rightarrow$ 100%).

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Strangler Fig — паттерн пошаговой миграции монолита на микросервисы без остановки работы системы (Zero Downtime).
- API Gateway ставится перед монолитом и перехватывает роуты, перенаправляя трафик на новые сервисы.
- Big Bang Rewrite (переписать с нуля за 2 года) — классический антипаттерн с огромным риском провала.
- Для переноса данных вместо ненадежного Dual Writing используется **CDC (Change Data Capture)** через Debezium и Kafka.
- Проверка корректности проводится через **Traffic Shadowing** (теневое дублирование запросов) и постепенный канареечный релиз через Feature Flags.

**Частые уточняющие вопросы:**
- **С какого функционала лучше начинать миграцию?** — С наименее связанного и наименее критичного для бизнеса модуля (например, генерация PDF, отправка email/SMS или сервис статических страниц).
- **Что такое Dual Write Problem?** — Нарушение консистентности данных при попытке приложения параллельно писать в две независимые базы данных без распределенной транзакции.
- **Как помогает Feature Flag?** — Позволяет мгновенно откатить трафик на монолит за 1 секунду без повторного деплоя при обнаружении бага в новом микросервисе.

**Красные флаги (НЕ говорить):**
- ❌ «Лучший способ перейти на микросервисы — остановить разработку фич и переписать всю систему с нуля».
- ❌ «Синхронизировать базы монолита и микросервиса можно обычным вызовом REST API внутри контроллера монолита».
- ❌ «Новый микросервис должен ходить напрямую в базу данных монолита».
