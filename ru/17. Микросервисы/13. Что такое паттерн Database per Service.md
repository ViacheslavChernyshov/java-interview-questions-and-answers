# Что такое паттерн Database per Service?

---

## 🟢 Junior Level

### Простое определение

**Database per Service (База данных на микросервис)** — это фундаментальный архитектурный паттерн микросервисной архитектуры, при котором **каждый сервис владеет своей собственной закрытой базой данных**.

Ни один другой сервис не имеет права напрямую подключаться к чужой базе, читать из её таблиц или выполнять SQL-запросы:

```
[Order Service] ──────► (Order Database)
      ▲                        │
      │ REST / Kafka           │ (Прямой доступ к чужой БД СТРОГО ЗАПРЕЩЁН!)
      ▼                        ▼
[User Service]  ──────► (User Database)
```

### Зачем это нужно:
1. **Свобода изменения схем (Loose Coupling)**: Разработчики сервиса пользователей могут переименовать колонку `phone` в `phone_number` или добавить миграцию Liquibase/Flyway в любой момент, не согласуя это с 10 другими командами.
2. **Изоляция сбоев (Fault Tolerance)**: Если база данных сервиса каталога товаров упадет от нагрузки, сервис оформления заказов и сервис платежей продолжат работать.
3. **Главная цена**: В микросервисах **невозможно сделать SQL `JOIN`** между таблицами разных сервисов.

## 🟡 Middle Level

### 3 стратегии физической изоляции данных

В зависимости от бюджета и зрелости инфраструктуры паттерн реализуется на трех уровнях:

| Уровень изоляции | Как устроен | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **1. Database Server per Service** | У каждого сервиса свой отдельный физический/облачный кластер (AWS RDS) | 🟢 100% аппаратная изоляция CPU, RAM и дискового I/O | Дорого, сложнее обслуживать 30 кластеров |
| **2. Database Schema per Service** | Один общий кластер PostgreSQL, но у каждого сервиса своя схема (`orders.*`, `users.*`) | 🟢 Дешево, легко настраивать бэкапы | 🔴 Noisy Neighbor: один тяжелый запрос в `users` может перегрузить CPU всей БД |
| **3. Private Tables with separate credentials** | Разные пользователи СУБД с правами доступа только к своим таблицам | Минимальный старт | Риск случайного `JOIN` |

### Как сервисы получают данные друг друга без `JOIN`

1. **API Composition (Синхронный сбор через Gateway/BFF)**:
   - Клиент запрашивает страницу заказа.
   - API Gateway делает параллельные вызовы `GET /orders/1` и `GET /users/42`, объединяя JSON в один ответ.
2. **Event-Driven Data Replication (Асинхронная репликация через Kafka)**:
   - При смене адреса пользователя `User Service` публикует событие `UserAddressChangedEvent`.
   - `Order Service` сохраняет копию адреса в своей локальной таблице для мгновенного чтения.
3. **CQRS / Materialized View**:
   - Специальный аналитический сервис слушает события из Kafka и строит денормализованные представления в Elasticsearch или ClickHouse для быстрых поисковых выборок.

## 🔴 Senior Level

### Полиглотная персистентность (Polyglot Persistence)

Паттерн Database per Service снимает ограничение на использование единой СУБД для всей компании. Каждый сервис выбирает инструмент, идеально оптимизированный под его профиль нагрузки:

```
User Service        ──► PostgreSQL       (Строгие ACID-транзакции, реляционная модель)
Product Catalog     ──► MongoDB          (Гибкая документная модель для разных категорий товаров)
Shopping Cart       ──► Redis            (In-Memory Key-Value со сверхбыстрым TTL)
Product Search      ──► Elasticsearch    (Полнотекстовый поиск, нечеткий поиск Typo-Tolerance)
Fraud Detection     ──► Neo4j            (Графовая СУБД для поиска связей между мошенниками)
Analytics Service   ──► ClickHouse       (Колоночная СУБД для агрегации миллиардов событий в секунду)
```

### Неизбежные архитектурные следствия и Trade-offs

Принимая решение о переходе на Database per Service, архитектор обязан внедрить сопутствующие паттерны:
1. **Отказ от 2PC (Two-Phase Commit)**: Распределенные транзакции XA медленны и блокируют ресурсы.
2. **Паттерн Saga (Оркестрация / Хореография)**: Для обеспечения согласованности бизнес-процесса между несколькими БД (с компенсационными транзакциями при сбоях).
3. **Transactional Outbox Pattern**: Чтобы атомарно сохранить бизнес-сущность в своей БД и гарантированно отправить событие в Kafka без потери сообщений.
4. **Anti-Corruption Layer (ACL)**: Защитный слой маппинга DTO во избежание проникновения чужих структур данных во внутреннюю доменную модель сервиса.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Database per Service — каждый микросервис владеет своей БД; прямой доступ других сервисов к БД запрещен.
- Обеспечивает слабую связность (Loose Coupling), независимые миграции и независимый деплой.
- Делает невозможным классический SQL `JOIN` между таблицами разных сервисов.
- Доступ к чужим данным реализуется через: API Composition, Event-Driven репликацию (Kafka) или CQRS.
- Позволяет использовать **Polyglot Persistence** (PostgreSQL, Redis, Mongo, ClickHouse).
- Требует перехода на **Eventual Consistency**, паттерны **Saga** и **Transactional Outbox**.

**Частые уточняющие вопросы:**
- **В чём разница между Database per Service и Schema per Service?** — Schema per Service использует один сервер СУБД с логическим разделением прав по схемам; это дешевле, но создает риск Noisy Neighbor по ресурсам CPU/диска.
- **Как сформировать сложный отчет по заказам и пользователям без JOIN?** — Использовать CQRS: агрегировать события в отдельное аналитическое хранилище (ClickHouse / Elasticsearch).
- **Что делать, если при создании заказа нужно проверить баланс пользователя?** — Использовать паттерн Saga с резервированием баланса или вызов Payment Service.

**Красные флаги (НЕ говорить):**
- ❌ «Сервисы могут подключаться к базам друг друга в режиме Read-Only».
- ❌ «Для отчетов можно сделать `JOIN` между таблицами сервисов, если они на одном PostgreSQL сервере».
- ❌ «Database per Service обязателен даже для стартапа из двух разработчиков».
