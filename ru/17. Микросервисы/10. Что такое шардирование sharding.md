# Что такое шардирование (sharding)?

---

## 🟢 Junior Level

### Простое определение

**Шардирование (Sharding / Горизонтальное секционирование)** — это архитектурный метод разделения одной гигантской базы данных на **несколько независимых физических серверов (шардов)**, где каждый сервер хранит только **свою уникальную часть данных**.

```
                           [Шардированная база данных]
                                       │
            ┌──────────────────────────┼──────────────────────────┐
            ▼                          ▼                          ▼
       [Шард 1]                   [Шард 2]                   [Шард 3]
  Пользователи A–H           Пользователи I–P           Пользователи Q–Z
  (Сервер 1: 30 млн)         (Сервер 2: 30 млн)         (Сервер 3: 30 млн)
```

### Разница: Репликация vs Шардирование

- **Репликация (Read Replicas)**: Каждый сервер хранит **100% полную копию** всей базы данных. Используется для отказоустойчивости и распределения нагрузки на чтение (`SELECT`).
- **Шардирование**: Серверы хранят **разные куски данных**. Используется, когда объем данных или поток записей (`INSERT / UPDATE`) физически не помещается на один даже самый мощный сервер.

### Аналогия из жизни

Представьте **многотомную энциклопедию из 26 томов (от А до Я)**:
- Если бы вся энциклопедия была в одной книге толщиной в 10 метров, её невозможно было бы поднять и открыть.
- Разделив её на 26 отдельных томов (шардов), 26 человек могут одновременно читать и делать записи в разных томах, не мешая друг другу.

## 🟡 Middle Level

### 3 стратегии шардирования и выбор Shard Key

Ключ шардирования (**Shard Key**) — это поле сущности (например, `user_id` или `tenant_id`), по значению которого маршрутизатор определяет, на какой именно сервер отправить SQL-запрос.

| Стратегия | Как вычисляется | Плюсы | Минусы / Риски |
| :--- | :--- | :--- | :--- |
| **1. Range-based (По диапазону)** | `ID 1..1M -> Shard 1`, `1M..2M -> Shard 2` | Легко делать Range-запросы (`BETWEEN`) | 🔴 **Hot Spotting**: Все новые записи идут только в последний шард! |
| **2. Hash-based (По хешу ключа)** | `shard_id = hash(user_id) % num_shards` | 🟢 Идеально равномерное распределение записей | Range-запросы требуют опроса всех шардов |
| **3. Directory-based (По справочнику)** | Центральная таблица соответствия: `Tenant_A -> Shard 3` | Максимальная гибкость (крупных клиентов на отдельные серверы) | Таблица маршрутизации становится SPOF и узким горлышком |

### Проблемы, возникающие при шардировании

1. **Cross-Shard Queries (Запросы между шардами)**:
   - Если сделать `SELECT * FROM orders WHERE amount > 1000`, маршрутизатору приходится выполнять паттерн **Scatter-Gather**: отправить запрос на все 100 шардов, дождаться 100 ответов и объединить их в памяти приложения.
2. **Отсутствие внешних ключей (No Cross-Shard Foreign Keys)**:
   - СУБД физически не может проверить `FOREIGN KEY` между таблицей `orders` на Шарде 1 и `users` на Шарде 2. Контроль целостности переносится в Java-код.
3. **Cross-Shard Transactions**:
   - Транзакции между несколькими шардами требуют протокола **2PC (Two-Phase Commit)**, который увеличивает задержки в 10–50 раз.

## 🔴 Senior Level

### Проблема ребалансировки: Consistent Hashing (Консистентное хеширование)

При наивном хешировании `hash(key) % N`:
- Если у вас было $N=3$ шарда и вы добавили 4-й шард ($N=4$), формула изменится для **75% всех существующих ключей**.
- Придется остановить базу и переместить сотни терабайт данных между всеми серверами.

**Решение для Senior: Consistent Hashing (Кольцо хешей + Virtual Nodes)**:
```
                                 [0 / 2^32 - 1]
                              .----------------.
                           .'     Shard A        '.
                         .'                        '.
                   Shard C                           Shard B
                         '.                        .'
                           '.                    .'
                              '----------------'
```
- Пространство хешей замыкается в кольцо от $0$ до $2^{32}-1$.
- При добавлении нового шарда перемещается только **$\frac{1}{N+1}$** часть данных от соседнего узла, а остальные шарды продолжают работать без перерывов.

### Инструменты шардирования в Enterprise

В современной практике шардирование редко пишут вручную в коде на Java:
1. **Vitess**: Прокси-кластер над MySQL, созданный YouTube для прозрачного шардирования петабайтных баз.
2. **Citus Data**: Расширение для PostgreSQL, превращающее Postgres в распределенную СУБД с шардированием таблиц по `tenant_id`.
3. **Distributed SQL (NewSQL)**: СУБД со встроенным автоматическим шардированием из коробки (**CockroachDB**, **YugabyteDB**, **Google Cloud Spanner** на базе Raft/Paxos).

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Шардирование — горизонтальное разделение базы данных по строкам на несколько независимых серверов.
- Репликация копирует все данные для чтения; шардирование разделяет данные для масштабирования записи и объема.
- **Shard Key** определяет, на какой сервер попадут данные (выбирается поле с высокой кардинальностью, например `user_id`).
- Стратегии: Range-based (риск Hot Spots), Hash-based (равномерно), Directory-based.
- Главные трудности: потеря внешних ключей (FK), медленные межшардовые `JOIN` и запросы Scatter-Gather.
- Для безопасного добавления шардов без полной миграции данных применяется **Consistent Hashing**.

**Частые уточняющие вопросы:**
- **Что такое Hot Shard (Hot Spotting)?** — Ситуация, когда один шард получает 90% всей нагрузки (например, при range-шардировании по дате или при попадании аккаунта популярного блогера на один узел).
- **Что такое Scatter-Gather?** — Паттерн, когда координатор рассылает запрос по всем шардам параллельно, а затем собирает и сортирует результаты в памяти.
- **Когда пора внедрять шардирование?** — Только тогда, когда база данных превышает пределы вертикального масштабирования (обычно от 1-2 ТБ) или упирается в лимиты дискового IOPS при записи.

**Красные флаги (НЕ говорить):**
- ❌ «Шардирование и Read-репликация — это взаимозаменяемые вещи».
- ❌ «Шардирование нужно подключать в каждый проект с первого дня разработки».
- ❌ «Межшардовые JOIN работают так же быстро, как обычные в одной базе данных».
