# Как SOLID помогает в тестировании кода?

---

## 🟢 Junior Level

### Простое объяснение

Принципы SOLID часто называют **«Design for Testability» (Проектирование для тестируемости)**.
- Если код написан без соблюдения SOLID (спагетти с `new` внутри методов, статические вызовы, классы на 2000 строк), написать для него простой модульный тест (Unit Test) практически невозможно.
- Если код написан по SOLID, каждый класс изолирован, зависимости передаются снаружи, а логика разбита на маленькие предсказуемые блоки. Тестировать такой код легко и быстро.

### Аналогия из жизни

Представьте проверку работоспособности **двигателя автомобиля**:
- **Без SOLID**: Двигатель намертво заварен внутри кузова, приварен к коробке передач и топливному баку. Чтобы проверить одну свечу зажигания, нужно выезжать на полигон и разгонять всю машину.
- **С SOLID**: Двигатель собирается из стандартных модулей. Вы можете снять стартер, поставить его на тестовый стенд в лаборатории, подать питание и проверить за 5 секунд отдельно от машины.

### Пример: код до и после SOLID

**Плохо (Невозможно протестировать изолированно):**
```java
public class OrderService {
    // Внутри создаются реальные зависимости: обращение к БД и реальная отправка SMS!
    public void createOrder(String userPhone, BigDecimal amount) {
        DatabaseConnection db = new DatabaseConnection("prod-db.host"); // Подключение к БД!
        db.saveOrder(userPhone, amount);

        SmsGateway sms = new SmsGateway("api-secret-key"); // Отправка реального SMS!
        sms.send(userPhone, "Order created!");
    }
}
// Чтобы протестировать createOrder, нам нужна реальная работающая БД и деньги на балансе SMS-шлюза!
```

**Хорошо (Легко протестировать с моками):**
```java
public class OrderService {
    private final OrderRepository orderRepository;
    private final NotificationService notificationService;

    // Зависимости передаются снаружи (DIP / DI)
    public OrderService(OrderRepository orderRepository, NotificationService notificationService) {
        this.orderRepository = orderRepository;
        this.notificationService = notificationService;
    }

    public void createOrder(String userPhone, BigDecimal amount) {
        orderRepository.save(userPhone, amount);
        notificationService.notify(userPhone, "Order created!");
    }
}

// В unit-тесте подменяем зависимости за 1 секунду:
class OrderServiceTest {
    @Test
    void shouldCreateOrderSuccessfully() {
        OrderRepository mockRepo = mock(OrderRepository.class);
        NotificationService mockNotify = mock(NotificationService.class);
        OrderService service = new OrderService(mockRepo, mockNotify);

        service.createOrder("+123456789", BigDecimal.valueOf(100));

        verify(mockRepo).save("+123456789", BigDecimal.valueOf(100));
        verify(mockNotify).notify("+123456789", "Order created!");
    }
}
```

## 🟡 Middle Level

### Как каждый из 5 принципов помогает в тестах

| Принцип | Роль в тестировании | Практическая польза |
| :--- | :--- | :--- |
| **SRP** | **Изоляция тестов** | У класса одна ответственность → один компактный тестовый класс. Тесты не падают из-за правок в посторонних модулях. |
| **OCP** | **Регрессионная стабильность** | Новая фича = новый класс и новые тесты. Не нужно переписывать и актуализировать 100 старых тестов. |
| **LSP** | **Контрактная взаимозаменяемость** | Тест для базового интерфейса обязан проходить для любой его реализации (Contract / Abstract Tests). |
| **ISP** | **Минималистичные моки** | Узкие интерфейсы избавляют от необходимости мокать 20 неиспользуемых методов ради одного нужного. |
| **DIP** | **Подмена реальности** | Позволяет подсунуть Mock-объект вместо реальной БД, сети или внешнего HTTP API. |

### SOLID и Test-Driven Development (TDD)

TDD выступает лакмусовой бумажкой качества архитектуры:
- Если вам **больно и неудобно** писать unit-тест для класса — архитектура нарушает SRP или DIP.
- Если для проверки одного условия требуется проинициализировать 15 других объектов — нарушен принцип связности (Tight Coupling).

## 🔴 Senior Level

### Метрики качества тестов и архитектурные индикаторы

1. **Mock-to-Assertion Ratio**:
   - Если количество строк настройки моков (`when(...).thenReturn(...)`) превышает количество строк логики и проверок (`assertEquals`), класс перегружен зависимостями (нарушение SRP).
2. **Test Fragility (Хрупкость тестов)**:
   - Если добавление нового поля или изменение формата одного ответа ломает 50 тестов в несвязанных пакетах, в системе отсутствует разделение интерфейсов (ISP) и есть паразитные прямые связи.
3. **Execution Speed & Context Overhead**:
   - SOLID-код позволяет запускать тысячи Unit-тестов на чистом JUnit/Mockito за сотни миллисекунд без поднятия `SpringExtension` (`@SpringBootTest`). Интеграционные тесты с полным контекстом оставляются только для проверки связки со слоем данных (Testcontainers).

### Abstract Test Pattern для проверки LSP

```java
// Базовый контрактный тест для любого хранилища ключей
public abstract class KeyValueStoreContractTest {
    protected abstract KeyValueStore createStore();

    @Test
    void shouldStoreAndRetrieveValue() {
        KeyValueStore store = createStore();
        store.put("key", "value");
        assertEquals("value", store.get("key"));
    }
}

// Тест для Redis-реализации
class RedisStoreTest extends KeyValueStoreContractTest {
    @Override
    protected KeyValueStore createStore() { return new RedisKeyValueStore(); }
}

// Тест для InMemory-реализации
class InMemoryStoreTest extends KeyValueStoreContractTest {
    @Override
    protected KeyValueStore createStore() { return new InMemoryKeyValueStore(); }
}
```

### Когда SOLID НЕ является главным приоритетом для тестирования

1. **Чисто функциональные утилиты**: Статические методы вида `StringUtils.isBlank()` тестируются тривиально без создания моков и интерфейсов.
2. **Прототипы и Spike Solutions**: Код для проверки концепции на 1–2 дня не требует изоляции слоёв.
3. **Black-box End-to-End тесты**: При тестировании всей системы целиком через REST API внутреннее устройство сервисов не влияет на структуру системного теста.

### Резюме для Senior

- Высокая тестируемость — главный индикатор чистоты архитектуры.
- Детерминированность тестов достигается через DIP (инъекция `Clock` для контроля времени, инъекция генераторов случайных чисел).
- Unit-тесты должны проверяться без поднятия Spring-контекста.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- SOLID = «Design for Testability»: без DIP и SRP изолированное unit-тестирование невозможно.
- SRP: один тестовый класс, отсутствие лишних моков для проверки изолированной бизнес-логики.
- OCP: регрессионная стабильность — новые фичи покрываются новыми тестами, старые тесты не модифицируются.
- LSP: Contract Tests / Abstract Test Pattern — гарантия прохождения базовых тестов всеми потомками.
- ISP: компактные моки — мокаются только вызываемые методы.
- DIP: король тестирования — изоляция от БД, сети, диска и времени через интерфейсы.
- Mock Ratio: преобладание строк моков над строками ассертов — признак запаха кода (code smell).

**Частые уточняющие вопросы:**
- **Как проверить SOLID без Spring?** — Написать чистый JUnit тест без `@SpringBootTest` и `@MockBean`; если это легко сделать — архитектура чистая.
- **Что такое Abstract Test паттерн?** — Базовый абстрактный тестовый класс для проверки соответствия контракту всех реализаций интерфейса (LSP).
- **Почему важно инжектировать `Clock`?** — Позволяет детерминированно тестировать логику с таймаутами, сроками годности и временными окнами.
- **В чём опасность избыточного мокирования?** — Моки связывают тест с деталями реализации, делая тесты хрупкими при рефакторинге.

**Красные флаги (НЕ говорить):**
- «Для любого unit-теста в Spring нужно всегда использовать `@SpringBootTest`».
- «Чем больше моков настроено в тесте, тем выше качество теста».
- «Если код сложно протестировать, надо сделать приватные методы публичными».
