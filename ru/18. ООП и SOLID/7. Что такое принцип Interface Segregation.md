# Что такое принцип Interface Segregation?

---

## 🟢 Junior Level

### Простое определение

**Принцип разделения интерфейсов (Interface Segregation Principle, ISP)** — это буква «I» в аббревиатуре SOLID. Он гласит:
> **Клиенты не должны зависеть от методов, которые они не используют.**

**Клиент** — это любой класс, который реализует интерфейс или вызывает его методы. Если интерфейс заставляет класс реализовывать методы-пустышки, выбрасывать `UnsupportedOperationException` или зависеть от ненужных функций — принцип ISP нарушен.

### Аналогия из реальной жизни

Представьте **многофункциональный швейцарский нож** и **обычную кухонную вилку**:
- Если вам в столовой нужна только вилка, чтобы пообедать, но вам выдают огромный 5-килограммовый чемодан с пилой, штопором, фонариком и лазерной указкой — это неудобно и избыточно.
- В программировании лучше предоставить узкий интерфейс `Eatable` с методом `eat()`, чем гигантский интерфейс `MultiTool`, заставляющий каждого едока реализовывать `sawWood()` и `openWine()`.

### Пример нарушения и исправления

**Плохо (Fat / Жирный интерфейс):**
```java
// Жирный интерфейс — заставляет реализовывать всё подряд
public interface Worker {
    void work();
    void eat();
    void sleep();
}

// Робот не ест и не спит, но обязан реализовать методы!
public class RobotWorker implements Worker {
    @Override
    public void work() {
        System.out.println("Robot working");
    }

    @Override
    public void eat() {
        // Заглушка или исключение — явный признак нарушения ISP!
        throw new UnsupportedOperationException("Robots do not eat");
    }

    @Override
    public void sleep() {
        throw new UnsupportedOperationException("Robots do not sleep");
    }
}
```

**Хорошо (Разделённые интерфейсы):**
```java
// Узкие, сфокусированные интерфейсы (Role Interfaces)
public interface Workable {
    void work();
}

public interface Feedable {
    void eat();
}

// Человек реализует оба интерфейса
public class HumanWorker implements Workable, Feedable {
    @Override
    public void work() { System.out.println("Human working"); }

    @Override
    public void eat() { System.out.println("Human eating lunch"); }
}

// Робот реализует только то, что умеет
public class RobotWorker implements Workable {
    @Override
    public void work() { System.out.println("Robot working non-stop"); }
}
```

## 🟡 Middle Level

### Детальная механика и влияние на JVM

На уровне байт-кода и виртуальной машины Java большой интерфейс (Fat Interface) создаёт лишние зависимости в **Constant Pool** каждого класса-реализатора.
- **Constant Pool**: таблица ссылок в `.class` файле. Каждый объявленный метод интерфейса добавляет записи в Constant Pool.
- **vtable / itable**: таблицы виртуальных методов и интерфейсов. Больше методов = больше таблица = больше памяти и медленнее поиск при полиморфном вызове (invokeinterface).
- Главная проблема — архитектурная: загрязнение кодовой базы методами-заглушками, потеря бинарной совместимости и усложнение тестирования.

### Role Interfaces vs Header Interfaces

#### 1. Header Interfaces (Антипаттерн)
Создание интерфейса `IMyService` для класса `MyService`, который просто слепо копирует все его публичные методы.
- **Проблема**: Это не абстракция, а дублирование. При добавлении метода в сервис интерфейс разрастается, и все клиенты вынуждены перекомпилироваться и подстраиваться под новые методы.

#### 2. Role Interfaces (Senior-подход)
Интерфейс должен описывать **роль** объекта в конкретном контексте взаимодействия:
- Один класс может реализовывать 10 маленьких интерфейсов-ролей (`Serializable`, `Cloneable`, `Comparable`, `AutoCloseable`).
- Клиент (например, принтер) требует контракт `Printable`, и ему безразлично, умеет ли передаваемый объект сохраняться в БД или сериализоваться в JSON.

### Признаки нарушения ISP

1. **`UnsupportedOperationException`**: Самый яркий маркер. Метод реализован только потому, что интерфейс заставил, но реального поведения нет.
2. **Пустые методы-заглушки**: Метод ничего не делает (`// do nothing`), возвращает `null` или `0`.
3. **Раздутые тестовые моки**: Для тестирования одного метода приходится настраивать 20 моков в `when(...).thenReturn(...)`, хотя тестируемый код вызывает только один метод.

### Решение через паттерн Adapter

Когда вы работаете со сторонней библиотекой с «жирным» интерфейсом, который вы не можете изменить, используйте **Adapter**:

```java
// Сторонний жирный интерфейс из внешней библиотеки
public interface ThirdPartyCloudStorage {
    void uploadFile(byte[] data);
    void deleteFile(String id);
    void listFiles();
    void generateBillingReport(); // Нашему сервису это не нужно
}

// Наш чистый узкий интерфейс под конкретную задачу
public interface DocumentUploader {
    void upload(byte[] data);
}

// Адаптер изолирует приложение от жирного интерфейса
public class CloudStorageAdapter implements DocumentUploader {
    private final ThirdPartyCloudStorage cloudStorage;

    public CloudStorageAdapter(ThirdPartyCloudStorage cloudStorage) {
        this.cloudStorage = cloudStorage;
    }

    @Override
    public void upload(byte[] data) {
        cloudStorage.uploadFile(data);
    }
}
```

## 🔴 Senior Level

### Производительность и Highload

- **Binary Compatibility**: ISP напрямую защищает бинарную совместимость модулей. Если вы добавили метод в узкий интерфейс `PaymentProcessor`, это затронет только модули эквайринга, а не модули каталога, доставки и аналитики.
- **Megamorphic Call Sites**: Если интерфейс слишком широкий и имеет сотни разнородных реализаций, JVM JIT-компилятор (C2) не сможет выполнить devirtualization (инлайнинг) в точках вызова `invokeinterface`, переходя в режим `megamorphic dispatch` через просмотр `itable`. Узкие интерфейсы повышают вероятность мономорфных/биморфных вызовов, позволяя JIT генерировать прямой машинный код.

### Edge Cases и тонкости

1. **Default Methods (Java 8+)**:
   - Позволяют добавлять методы в интерфейсы без поломки существующих реализаций.
   - **Опасность**: Default-методы **не спасают от нарушения ISP**. Интерфейс остаётся раздутым, засоряя автодополнение IDE и API клиента методами, которые ему не требуются.
2. **Single Method Interfaces (SAM / Функциональные интерфейсы)**:
   - Интерфейсы с одним методом (`Runnable`, `Callable`, `Function`, `Consumer`) идеально соответствуют ISP и могут использоваться как лямбды.
   - Однако не стоит впадать в догматизм: интерфейс с 2-3 тесно связанными методами (например, `Iterator`: `hasNext()` и `next()`, или `AutoCloseable`: `close()`) абсолютно валиден.

### Когда НЕ стоит дробить интерфейсы

1. **Интерфейс с 1-2 методами**: Дальнейшее дробление приведёт к бессмысленному раздуванию файлов (interface explosion).
2. **Все реализации используют все методы**: Если во всех 100% сценариев методы используются совместно (например, `getX()` и `getY()` у двумерной точки).
3. **Внутренний (package-private) интерфейс**: Не публичный API, влияние на сторонние модули отсутствует.

### Резюме для Senior

- Интерфейсы принадлежат **клиентам**, а не реализациям (Client-Driven Design).
- Предпочитайте множество узких интерфейсов-ролей одному монолитному.
- ISP снижает зацепление (Coupling), упрощает модульное тестирование и исключает методы-пустышки.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- ISP: клиенты не должны зависеть от методов, которые они не используют.
- Fat Interface заставляет классы реализовывать методы-заглушки и бросать `UnsupportedOperationException`.
- Role Interfaces > Header Interfaces: интерфейс описывает роль (`Printable`, `AutoCloseable`), а не класс.
- Интерфейсы принадлежат вызывающему коду (клиенту), а не сервису-реализации.
- Adapter паттерн помогает изолировать сторонние «жирные» интерфейсы.
- Default Methods в Java 8+ не устраняют нарушение ISP, а лишь скрывают ошибки компиляции.

**Частые уточняющие вопросы:**
- **Header Interface vs Role Interface?** — Header слепо дублирует методы класса (антипаттерн), Role задаёт конкретную роль для взаимодействия.
- **Как ISP упрощает тестирование?** — Уменьшает число моков: класс мокает только 1 нужный метод, а не 20 ненужных.
- **Нужно ли дробить интерфейс с 2 методами?** — Нет, если методы семантически связаны (например, `hasNext()` и `next()`).
- **Как ISP связан с DIP?** — Узкие интерфейсы являются более стабильными и предсказуемыми абстракциями.

**Красные флаги (НЕ говорить):**
- «Для каждого класса обязательно нужно создавать интерфейс IMyClass» (это Header Interface).
- «Default methods полностью решают проблему ISP» (интерфейс всё равно остаётся перегруженным).
- «Если метод не нужен, достаточно просто бросить UnsupportedOperationException».
