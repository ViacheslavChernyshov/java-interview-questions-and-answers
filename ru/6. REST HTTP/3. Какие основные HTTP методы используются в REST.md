# Какие основные HTTP методы используются в REST?

---

## 🟢 Junior Level

### Что такое HTTP-методы?

**HTTP-методы (HTTP Verbs / Глаголы HTTP)** — это стандартные команды протокола HTTP, которые указывают серверу, **какое действие** клиент хочет выполнить над указанным ресурсом (URI):

| HTTP Метод | Аналог в CRUD | Назначение | Пример URI |
| :--- | :--- | :--- | :--- |
| **`GET`** | **R**ead | Получить представление ресурса (чтение) | `GET /api/v1/users/42` |
| **`POST`** | **C**reate | Создать новый подчиненный ресурс или выполнить действие | `POST /api/v1/users` |
| **`PUT`** | **U**pdate (Replace) | Полностью заменить ресурс по указанному адресу | `PUT /api/v1/users/42` |
| **`PATCH`** | **U**pdate (Partial) | Частично обновить отдельные поля ресурса | `PATCH /api/v1/users/42` |
| **`DELETE`** | **D**elete | Удалить указанный ресурс | `DELETE /api/v1/users/42` |

### Базовые правила для начинающих:
1. **URI идентифицирует ресурс (существительное)**: `/orders`, а метод указывает действие: `POST /orders` (создать), `GET /orders/1` (прочитать).
2. **`GET` никогда не должен менять данные**: если вы открываете ссылку в браузере, ничего не должно удаляться или списываться со счёта.

## 🟡 Middle Level

### Классификация методов: Безопасность (Safe) и Идемпотентность (Idempotent)

По спецификации **RFC 9110 (HTTP Semantics)** методы классифицируются по двум ключевым свойствам:

```
                          ┌─── Safe (Не меняет состояние сервера): GET, HEAD, OPTIONS
            ┌─── Свойства ┤
            │             └─── Idempotent (Повтор не меняет состояние): GET, PUT, DELETE, HEAD
HTTP Методы ┤
            │             ┌─── PUT: Полная замена (все поля обязательны)
            └─── Мутации  ┼─── PATCH: Частичное обновление (RFC 6902 / RFC 7386)
                          └─── POST: Создание / Запуск бизнес-операции (Не идемпотентен!)
```

### Сравнение свойств методов

| Метод | Тело запроса? | Safe? | Idempotent? | Cacheable? (Кэшируемый) |
| :--- | :---: | :---: | :---: | :---: |
| **`GET`** | ❌ Нет | ✅ **Да** | ✅ **Да** | ✅ **Да** |
| **`HEAD`** | ❌ Нет | ✅ **Да** | ✅ **Да** | ✅ **Да** |
| **`OPTIONS`** | ❌ Нет | ✅ **Да** | ✅ **Да** | ❌ Нет |
| **`POST`** | ✅ Да | ❌ Нет | ❌ **Нет** | ⚠️ Только с явным Cache-Control |
| **`PUT`** | ✅ Да | ❌ Нет | ✅ **Да** | ❌ Нет |
| **`PATCH`** | ✅ Да | ❌ Нет | ⚠️ Зависит от операции | ❌ Нет |
| **`DELETE`** | ⚠️ Редко | ❌ Нет | ✅ **Да** | ❌ Нет |

### Вспомогательные методы: `HEAD` и `OPTIONS`
- **`HEAD`**: возвращает точно такие же HTTP-заголовки, как и `GET`, но **без тела ответа** (используется для быстрой проверки размера файла `Content-Length` или актуальности кэша `ETag` перед тяжелой загрузкой).
- **`OPTIONS`**: используется браузерами для **CORS Preflight** запросов. Сервер возвращает заголовок `Access-Control-Allow-Methods: GET, POST, PUT, DELETE`, сообщая фронтенду, какие операции разрешены.

## 🔴 Senior Level

### Тонкости PUT vs PATCH в Enterprise-архитектуре

1. **Строгий контракт `PUT` (Полная замена)**:
   - Если клиент отправил `PUT /users/42` с телом `{"name": "Ivan"}`, а в базе у пользователя было поле `email: "ivan@test.com"`, бэкенд **обязан затереть email в `null`**, так как `PUT` заменяет ресурс целиком.
2. **Реализация `PATCH` (JSON Merge Patch vs JSON Patch)**:
   - **JSON Merge Patch (RFC 7386)**: передаются только измененные поля (`{"email": "new@test.com"}`). Проблема: сложно различить «поле не передано» и «поле нужно явно занулить» (решается через `JsonNullable<T>` в Jackson).
   - **JSON Patch (RFC 6902)**: передается массив атомарных операций:
     ```json
     [
       { "op": "replace", "path": "/email", "value": "new@test.com" },
       { "op": "remove", "path": "/temporaryToken" }
     ]
     ```

### Автоматические повторы (Retries) в Service Mesh (Istio / Envoy / Linkerd)

Senior архитектор учитывает идемпотентность при настройке сетевых политик:
- **Безопасные ретраи**: При получении `503 Service Unavailable` или сетевого тайм-аута Sidecar-прокси (Envoy) может **автоматически повторить** запросы `GET`, `PUT`, `DELETE` без риска испортить данные.
- **Опасность для `POST`**: Повтор `POST`-запроса при тайм-ауте категорически запрещен (риск двойного списания денег или дублирования заказа). Для `POST` обязателен заголовок **`Idempotency-Key`**.

### Method Tunneling (`X-HTTP-Method-Override`)

Некоторые корпоративные фаерволы и корпоративные WAF блокируют методы `PATCH` и `DELETE`.
- **Решение**: отправка обычного `POST` с заголовком:
  ```http
  POST /api/v1/users/42 HTTP/1.1
  X-HTTP-Method-Override: PATCH
  ```
  Spring Boot автоматически обрабатывает этот заголовок при включении `HiddenHttpMethodFilter`.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- 5 основных методов: `GET` (чтение), `POST` (создание/действие), `PUT` (полная замена), `PATCH` (частичное обновление), `DELETE` (удаление).
- `GET` и `HEAD` являются **Safe** (не меняют состояние сервера) и **Idempotent**.
- `POST` — единственный принципиально **неидемпотентный** метод.
- `PUT` и `DELETE` **идемпотентны**: многократный вызов приводит к тому же конечному состоянию сервера, что и однократный.
- `OPTIONS` используется браузером для CORS Preflight проверок.
- `PUT` требует передачи всех полей объекта, иначе опущенные поля должны быть обнулены.

**Частые уточняющие вопросы:**
- **В чём разница между Safe и Idempotent?** — Safe методы вообще не имеют права менять состояние сервера; Idempotent методы могут менять состояние (например, `DELETE`), но повторные вызовы не производят новых изменений.
- **Чем HEAD отличается от GET?** — `HEAD` возвращает только заголовки (Headers) без тела ответа (Body).
- **Почему нельзя использовать GET для удаления пользователей?** — `GET` обязан быть безопасным; браузеры, поисковые боты и CDN могут выполнять предзагрузку (prefetching) ссылок `GET`, что приведет к случайному удалению данных.

**Красные флаги (НЕ говорить):**
- ❌ «`PUT` и `PATCH` — это абсолютно одно и то же».
- ❌ «`GET` может удалять записи в БД, если передать параметр `?action=delete`».
- ❌ «`DELETE` не является идемпотентным, потому что второй раз он возвращает 404 вместо 200».
