# Что означает Stateless в контексте REST?

---

## 🟢 Junior Level

### Простое определение

**Stateless (Отсутствие состояния)** — это одно из фундаментальных архитектурных ограничений REST, сформулированных Роем Филдингом.

Оно означает, что **сервер не сохраняет контекст сессии клиента между последовательными HTTP-запросами**. Каждый входящий запрос должен содержать абсолютно всю информацию, необходимую серверу для его полного понимания, аутентификации и обработки:

```
[Клиент] ─── Запрос 1: "Дай профиль пользователя" (Токен: ABC) ───► [Сервер 1]
[Клиент] ─── Запрос 2: "Дай список заказов"        (Токен: ABC) ───► [Сервер 2] ◄── Другой сервер легко обработает запрос!
```

### Аналогия из жизни

Представьте **окошко паспортного контроля в международном аэропорту**:
- Офицер пограничной службы не обязан помнить вас в лицо или сохранять в блокноте запись о том, что вы подходили к нему 2 минуты назад.
- Каждый раз, когда вы подходите к окошку, вы предъявляете паспорт и посадочный талон (всю необходимую информацию). 
- Благодаря этому вас может проверить **абсолютно любой свободный офицер** в любой кабинке.

### Главные преимущества для начинающих:
1. **Любой сервер может обработать любой запрос**: балансировщик нагрузки (Nginx, AWS ALB) может направить второй запрос клиента на абсолютно другой инстанс бэкенда.
2. **Надёжность**: если один сервер упадёт, клиентские сессии не «сгорят» — следующий запрос без проблем примет соседний сервер.

## 🟡 Middle Level

### Разделение состояний: Session State vs Resource State

Критически важно не путать два типа состояния:

| Тип состояния | Где хранится | Разрешено в REST? | Примеры |
| :--- | :--- | :--- | :--- |
| **Session State (Состояние сессии)** | **Строго на клиенте** | ❌ **Запрещено** на сервере | Корзина покупок до оформления, текущий шаг визарда, токен авторизации, выбранная страница пагинации. |
| **Resource State (Состояние ресурсов)** | **На сервере (в БД)** | ✅ **Разрешено** | Записи о пользователях в PostgreSQL, созданные заказы, остатки товаров на складе. |

### Stateful vs Stateless на практике

#### ❌ Stateful подход (Классический сервлетный подход с `HttpSession`):
```http
// 1-й запрос: логин (сервер выделяет память в Heap под сессию и шлет Cookie):
POST /login
<-- Set-Cookie: JSESSIONID=node0198273645.node01

// 2-й запрос: клиент шлет cookie, запрос ОБЯЗАН попасть на node01 (Sticky Session):
GET /cart
--> Cookie: JSESSIONID=node0198273645.node01
```
*Если сервер node01 перезагружается, вся корзина клиента исчезает.*

#### ✅ Stateless подход (REST + JWT Bearer Token):
```http
// 1-й запрос: логин
POST /api/v1/auth/login
<-- {"accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."}

// 2-й запрос: передача токена в заголовке на ЛЮБОЙ доступный сервер:
GET /api/v1/cart
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

## 🔴 Senior Level

### Архитектурный парадокс Stateless и отзыва токенов (JWT Revocation)

Хотя JWT позиционируется как эталонный Stateless-инструмент, в Enterprise-системах возникает жесткое требование безопасности: **мгновенный отзыв доступа (Revocation)** при компрометации токена или смене пароля.

**Парадокс архитектуры:**
- Чтобы проверить, не отозван ли Stateless JWT, сервер вынужден при **каждом запросе** обращаться к общему Redis/БД (Blacklist / Token Introspection RFC 7662).
- В этот момент система де-факто вновь становится зависимой от внешнего централизованного хранилища состояний сессий.

```
                      ┌─────────────────────────┐
                      │  Stateless REST Server  │
                      └────────────┬────────────┘
                                   │ При КАЖДОМ запросе:
                                   ▼
                      ┌─────────────────────────┐
                      │   Redis Token Blacklist │ ◄── Узкое горлышко и SPOF
                      └─────────────────────────┘
```

**Решение для Senior:**
1. Короткоживущие Access Token (5–15 минут) + длинноживущие Refresh Token.
2. Проверка отзыва только при обновлении Refresh Token через Auth Service.

### Масштабирование и Multi-Region Anycast Routing

Stateless-архитектура раскрывает максимальную мощь в глобально распределенных облаках:
1. **Anycast BGP Routing**: Запрос от клиента в Сингапуре попадает на сервер в дата-центре Сингапура, а запрос из Франкфурта — в Германию. Никакой синхронизации сессий между континентами не требуется.
2. **Kubernetes Auto-scaling (HPA / KEDA)**: Поды микросервиса могут масштабироваться от 2 до 200 экземпляров за секунды без переноса или прогрева сессий.
3. **Optimistic Concurrency Control (ETag + If-Match)**: В условиях отсутствия серверной сессии конкурентные обновления одного и того же ресурса предотвращаются через HTTP-заголовки `ETag` и `If-Match: "v2"`, возвращая `412 Precondition Failed` при коллизиях.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Stateless означает, что сервер не сохраняет состояние сессии между запросами.
- Каждый запрос обязан содержать всю необходимую информацию для выполнения (токен, параметры).
- Resource State (данные в БД) хранится на сервере; Session State (состояние диалога) хранится строго на клиенте.
- Преимущества: легкое горизонтальное масштабирование, отсутствие необходимости в Sticky Sessions, отказоустойчивость при падении серверов.
- JWT — стандартный механизм Stateless-аутентификации, но мгновенный отзыв токенов требует проверки в кэше (Redis), создавая централизованную точку зависимости.

**Частые уточняющие вопросы:**
- **В чём разница между Session State и Resource State?** — Session State относится к взаимодействию клиента с сервером (токен, фильтры); Resource State — это сами бизнес-данные в БД.
- **Почему Sticky Sessions — антипаттерн в REST?** — Привязка клиента к конкретному инстансу ломает балансировку нагрузки и приводит к обрывам сессий при автоскейлинге подов.
- **Как предотвратить перезапись данных двумя клиентами в Stateless REST?** — Через Optimistic Locking с использованием HTTP-заголовков `ETag` и `If-Match`.

**Красные флаги (НЕ говорить):**
- ❌ «Stateless означает, что сервер не имеет базы данных и ничего не сохраняет на диск».
- ❌ «В REST сессии хранятся в `HttpSession` на бэкенде».
- ❌ «JWT делает систему на 100% безопасной без необходимости обновления токенов».
