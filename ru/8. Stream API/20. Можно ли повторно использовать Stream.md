# Можно ли повторно использовать Stream?

---

## 🟢 Junior Level

### Простой ответ

**Нет, категорически нельзя.** В Java объект `Stream` является **одноразовым конвейером**. 

Как только на стриме была вызвана любая **терминальная операция** (например, `forEach`, `collect`, `count`, `reduce`, `findFirst`), стрим считается полностью закрытым и исчерпанным (consumed).

### Что произойдёт при попытке повторного вызова:

```java
List<String> names = List.of("Alice", "Bob", "Charlie");
Stream<String> stream = names.stream();

// 1-й вызов терминальной операции — выполнится успешно:
stream.forEach(System.out::println);

// 2-й вызов терминальной операции на том же объекте stream:
long count = stream.count(); // ❌ ВЫБРОСИТ ИСКЛЮЧЕНИЕ!
```

**Исключение в рантайме:**
```
java.lang.IllegalStateException: stream has already been operated upon or closed
```

### Аналогия из реальной жизни

Представьте **поток воды в реке** или **киноплёнку в старом проекторе**:
- Вы не можете войти в одну и ту же воду дважды — вода утекла через конвейер.
- Стрим — это не хранилище данных (не контейнер), а последовательность вычислений над потоком данных.

### Как правильно решать задачу:

Чтобы обработать данные повторно, нужно **создать новый стрим** из исходной коллекции:
```java
// ✅ ПРАВИЛЬНО: каждый раз вызываем .stream() заново
names.stream().forEach(System.out::println);
long count = names.stream().count();
```

## 🟡 Middle Level

### Внутреннее устройство: Флаг `linkedOrConsumed` в `AbstractPipeline`

В исходном коде OpenJDK (`java.util.stream.AbstractPipeline`) каждый узел стрима хранит внутреннее состояние:

```java
// Фрагмент реализации AbstractPipeline.java
private boolean linkedOrConsumed;

final <R> R evaluate(TerminalOp<E_OUT, R> terminalOp) {
    assert getOutputShape() == terminalOp.inputShape();
    if (linkedOrConsumed)
        throw new IllegalStateException(MSG_STREAM_LINKED);
    linkedOrConsumed = true; // Стрим помечается как сожжённый/использованный

    return isParallel()
           ? terminalOp.evaluateParallel(this, sourceSpliterator(terminalOp.getOpFlags()))
           : terminalOp.evaluateSequential(this, sourceSpliterator(terminalOp.getOpFlags()));
}
```

**Почему архитектор Java (Brian Goetz) сделал стримы одноразовыми:**
1. **Потоки из внешних небуферизуемых источников**: Источник стрима может быть сокетом (`SocketChannel`), генератором случайных чисел или строками из сетевого сокета, которые физически невозможно перемотать назад.
2. **Сложность управления памятью**: Чтобы поддержать повторные проходы, стриму пришлось бы буферизовать все промежуточные элементы в оперативной памяти (Heap), превращая Stream в тяжелую коллекцию и уничтожая его главное преимущество — низкий memory footprint.
3. **Безопасность параллелизма (`parallelStream`)**: Отсутствие возможности повторного использования защищает от race condition при разделении состояния между потоками в ForkJoinPool.

### Способы обхода ограничения

#### 1. Паттерн `Supplier<Stream<T>>` (для коллекций в памяти)
Если вам нужно передавать фабрику стримов в методы:
```java
Supplier<Stream<String>> streamSupplier = () -> names.stream().filter(s -> s.startsWith("A"));

// Каждый вызов get() возвращает чистый, готовый к вычислениям стрим:
streamSupplier.get().forEach(System.out::println);
long total = streamSupplier.get().count();
```

> [!WARNING]
> Не используйте `Supplier<Stream>`, если источником является внешний ресурс (запрос к БД, HTTP-клиент, чтение большого файла с диска). В таких случаях стрим нужно один раз вычитать в коллекцию (`.toList()`).

#### 2. Промежуточное кэширование в коллекцию
```java
List<String> filteredList = names.stream()
    .filter(s -> s.length() > 3)
    .toList(); // Вычислили 1 раз

filteredList.forEach(System.out::println);
long count = filteredList.size();
```

## 🔴 Senior Level

### Архитектура API: Stream как параметр метода (Anti-pattern)

В дизайне библиотек и сервисов передача `Stream<T>` в качестве аргумента публичного метода считается антипаттерном:

```java
// ❌ АНТИПАТТЕРН в публичном API
public void processUsers(Stream<User> userStream) {
    long count = userStream.count(); // Стрим исчерпан!
    // userStream.forEach(...); // Упадёт в рантайме!
}

// ✅ ПРАВИЛЬНЫЙ ДИЗАЙН:
public void processUsers(Collection<User> users) { /* ... */ }
// Или, если данных слишком много для памяти:
public void processUsers(Supplier<Stream<User>> userStreamSupplier) { /* ... */ }
```

### Утечки ресурсов (Resource Leaks) и AutoCloseable

Некоторые стримы захватывают системные ресурсы (файловые дескрипторы, базы данных). Такие стримы реализуют интерфейс `AutoCloseable`:
- `Files.lines(Path)`
- `Files.walk(Path)`
- `Files.list(Path)`

Попытка повторного использования или незакрытие такого стрима приводит к **утечке дескрипторов файлов ОС (File Descriptor Leak)**:

```java
// ✅ ОБЯЗАТЕЛЬНО: Обернуть в try-with-resources
try (Stream<String> lines = Files.lines(Paths.get("app.log"))) {
    lines.filter(line -> line.contains("ERROR"))
         .forEach(System.out::println);
} // Автоматический вызов lines.close() освободит дескриптор ОС
```

### Аллокации памяти в Highload

Один пайплайн Stream API создает цепочку из 4–8 промежуточных служебных объектов (`ReferencePipeline$Head`, `StatelessOp`, `TerminalOp`, `Spliterator`).
- При нагрузке **>100K RPS** создание и мгновенный сброс стримов приводит к сильному давлению на Young Generation (Eden space GC pressure).
- В ультра-низколатентном коде (Highload / FinTech) в циклических критических секциях предпочтительнее классический цикл `for` без промежуточных аллокаций.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `Stream` — строго одноразовый объект. Повторный вызов терминальной операции бросает `IllegalStateException: stream has already been operated upon or closed`.
- Причина: стрим — это ленивый конвейер (pipeline), а не хранилище данных; буферизация для повторного прохода разрушила бы концепцию низкого расхода памяти.
- Внутренняя реализация: флаг `linkedOrConsumed` в `AbstractPipeline` переводится в `true` при первом запуске `evaluate()`.
- Обход: паттерн `Supplier<Stream<T>>` (для in-memory данных) или сборка в коллекцию через `.toList()`.
- Стримы с системными ресурсами (`Files.lines()`) реализуют `AutoCloseable` и требуют закрытия через `try-with-resources`.

**Частые уточняющие вопросы:**
- **Что происходит под капотом при повторном запуске?** — Проверяется boolean-флаг `linkedOrConsumed`, при `true` выбрасывается `IllegalStateException`.
- **Почему метод не должен принимать `Stream<T>` в аргументах?** — Вызываемый метод не может гарантировать, что стрим не был частично или полностью исчерпан снаружи, и не сможет сделать два прохода.
- **В чём разница между `Stream` и `Iterable`?** — `Iterable` можно обходить неограниченное число раз через вызовы `.iterator()`, а `Stream` можно обойти ровно один раз.

**Красные флаги (НЕ говорить):**
- ❌ «У стрима есть метод `reset()` для сброса указателя».
- ❌ «Стрим можно клонировать через `stream.clone()`».
- ❌ «`parallelStream` можно использовать повторно, потому что там несколько потоков».
