# Что делают операции distinct(), sorted(), limit(), skip()?

---

## 🟢 Junior Level

### Краткий обзор 4 ключевых промежуточных операций

Все четыре метода являются **промежуточными (intermediate)** операциями и возвращают новый `Stream<T>`, но в отличие от простых `map()` и `filter()`, они изменяют состав, порядок или количество элементов:

| Метод | Что делает | Пример входных данных $\rightarrow$ Результат |
| :--- | :--- | :--- |
| **`distinct()`** | Удаляет все дубликаты (на основе `equals()` и `hashCode()`) | `[1, 2, 2, 3, 1] ──► [1, 2, 3]` |
| **`sorted()`** | Сортирует элементы (по `Comparable` или `Comparator`) | `[3, 1, 4, 2] ──► [1, 2, 3, 4]` |
| **`limit(n)`** | Оставляет не более первых $n$ элементов | `[1, 2, 3, 4, 5].limit(3) ──► [1, 2, 3]` |
| **`skip(n)`** | Пропускает первые $n$ элементов стрима | `[1, 2, 3, 4, 5].skip(2) ──► [3, 4, 5]` |

### Базовый пример:

```java
List<Integer> numbers = List.of(5, 2, 8, 2, 9, 1, 5, 8);

List<Integer> result = numbers.stream()
    .distinct()            // [5, 2, 8, 9, 1]
    .sorted()              // [1, 2, 5, 8, 9]
    .skip(1)               // [2, 5, 8, 9] (пропустили наименьшее)
    .limit(3)              // [2, 5, 8]    (взяли топ-3)
    .toList();

System.out.println(result); // [2, 5, 8]
```

## 🟡 Middle Level

### Stateless vs Stateful операции

В архитектуре Stream API промежуточные операции делятся на две принципиальные категории:

1. **Stateless (Без сохранения состояния)** — `filter()`, `map()`, `flatMap()`, `peek()`:
   - Каждый элемент обрабатывается изолированно, стрим не помнит предыдущие элементы.
   - Элементы «пролетают» конвейер вертикально на лету без буферизации.
2. **Stateful (С сохранением состояния)** — `distinct()`, `sorted()`, `limit()`, `skip()`:
   - Требуют сохранения внутреннего состояния при обработке потока данных:
     - `distinct()`: наполняет внутренний `LinkedHashSet` для фильтрации дубликатов ($O(N)$ памяти).
     - `sorted()`: является **полным барьером конвейера (Pipeline Barrier)** — не может отдать ни одного элемента downstream-узлам, пока не соберет **абсолютно все элементы** источника в массив и не отсортирует их (Dual-Pivot Quicksort / TimSort).
     - `limit(n)` / `skip(n)`: сохраняют счетчики просмотренных элементов.

### Оптимизации Stream Flags (`StreamOpFlag`)

JVM отслеживает метаданные потока. Если источник уже обладает нужными свойствами, операция оптимизируется:

```java
Set<String> treeSet = new TreeSet<>(List.of("B", "A", "C"));

// ОПТИМИЗАЦИЯ: JVM видит флаги DISTINCT и SORTED у источника TreeSet:
treeSet.stream()
    .distinct() // Пропускается (no-op), так как Set гарантирует уникальность!
    .sorted()   // Пропускается (no-op), так как TreeSet уже отсортирован!
    .toList();
```

## 🔴 Senior Level

### 3 критические ловушки производительности в Production

#### 1. Антипаттерн «Top-N через sorted().limit()»
Сортировка всей базы ради первых 5 элементов:
```java
// ❌ ПЛОХО на 1 000 000 элементов: Сортирует ВСЕ элементы $O(N \log N)$
List<User> top5 = users.stream()
    .sorted(Comparator.comparing(User::getScore).reversed())
    .limit(5)
    .toList();
```
**Решение для Senior**: На больших объемах использовать **PriorityQueue (Min-Heap)** фиксированного размера 5 — сложность **$O(N \log K)$** вместо $O(N \log N)$ и $O(K)$ памяти вместо $O(N)$ аллокаций массива.

#### 2. Пагинация через `skip(N).limit(M)`
- Использование `stream.skip(100_000).limit(20)` для пагинации в коде вынуждает стрим поштучно протянуть 100 000 элементов через все фильтры.
- Пагинация должна выполняться на уровне СУБД (`LIMIT/OFFSET` или Keyset Pagination).

#### 3. Бесконечные стримы (Infinite Stream Hangs)
```java
// 💥 OutOfMemoryError: sorted() ждёт завершения бесконечного стрима!
Stream.iterate(0, i -> i + 1)
    .sorted()  // Барьер зависнет навсегда, пытаясь буферизовать бесконечность!
    .limit(10)
    .toList();

// ✅ ПРАВИЛЬНО: limit() ОБЯЗАН стоять ДО sorted()!
Stream.iterate(0, i -> i + 1)
    .limit(10)
    .sorted()
    .toList();
```

### Поведение в `parallelStream()`

- **`distinct()` в параллелизме**: требует распределенной дедупликации через `ConcurrentHashMap` или слияния частичных сетов, создавая ощутимый contention.
- **`sorted()` в параллелизме**: использует `Arrays.parallelSort()`, который эффективен только на массивах от $\approx 100{,}000$ элементов.
- **`limit()` и `skip()` в параллелизме**: требуют сохранения порядка обхода (Encounter Order), что принуждает потоки буферизовать чанки и синхронизироваться.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `distinct()` и `sorted()` — **stateful операции**, требующие выделения $O(N)$ дополнительной памяти в Heap.
- `sorted()` — барьер конвейера: стрим накапливает ВСЕ элементы перед тем, как отдать первый элемент дальше.
- На бесконечных стримах `sorted()` вызывает зависание и `OutOfMemoryError` (если `limit()` не вызван ДО него).
- `distinct()` использует `equals()` и `hashCode()`. Для мутабельных объектов мутация полей после `distinct()` разрушает инвариант уникальности.
- Если источник уже отсортирован (`TreeSet`), JVM оптимизирует и пропускает этапы `distinct()` и `sorted()`.
- `skip(N)` для пагинации на миллионах записей — антипаттерн ($O(N)$ холостой проход).

**Частые уточняющие вопросы:**
- **Чем stateful операции отличаются от stateless?** — Stateless (`filter`, `map`) обрабатывают элементы независимо на лету; Stateful (`sorted`, `distinct`) накапливают состояние/буфер в памяти.
- **Почему `stream.sorted().limit(5)` неэффективен на 10M записях?** — Сортирует все 10M элементов ($O(N \log N)$) ради 5 записей; лучше использовать `PriorityQueue` ($O(N \log 5)$).
- **Как `distinct()` определяет дубликаты?** — Через внутренний `HashSet`/`LinkedHashSet`, используя `hashCode()` и `equals()`.

**Красные флаги (НЕ говорить):**
- ❌ «`sorted()` сортирует элементы по одному на лету, не накапливая их в памяти».
- ❌ «`distinct()` можно вызвать на бесконечном стриме без `limit()` и он отработает мгновенно».
- ❌ «`distinct()` сравнивает объекты только по ссылке `==`».
