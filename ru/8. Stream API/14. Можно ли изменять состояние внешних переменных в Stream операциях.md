# Можно ли изменять состояние внешних переменных в Stream операциях?

---

## 🟢 Junior Level

### Простой ответ

**Прямо изменять локальные переменные нельзя**, так как Java требует, чтобы все переменные, используемые внутри лямбда-выражений, были **`final` или `effectively final`** (переменная, значение которой не меняется после инициализации).

Попытка изменить примитивную переменную приведёт к **ошибке компиляции**:

```java
int sum = 0;
List<Integer> numbers = List.of(1, 2, 3, 4, 5);

// ❌ ОШИБКА КОМПИЛЯЦИИ: Variable used in lambda expression should be final or effectively final
numbers.stream().forEach(n -> sum += n);
```

### «Грязные хаки», которые пишут новички (и почему так делать нельзя):

Иногда разработчики пытаются обойти проверку компилятора через массивы или атомики:
```java
// ❌ ПЛОХОЙ ХАК (Массив из одного элемента):
int[] sumWrapper = new int[1];
numbers.stream().forEach(n -> sumWrapper[0] += n);

// ❌ АНТИПАТТЕРН (AtomicInteger):
AtomicInteger atomicSum = new AtomicInteger();
numbers.stream().forEach(atomicSum::addAndGet);
```

### Как делать правильно (Функциональный подход):

Вместо мутации внешнего состояния нужно позволить Stream API собрать или свернуть результат:
```java
// ✅ ПРАВИЛЬНО: через специализированный IntStream
int sum = numbers.stream()
    .mapToInt(Integer::intValue)
    .sum();
```

## 🟡 Middle Level

### Почему Java требует `Effectively Final`?

В Java переменные метода живут в **стек-фрейме (Stack)** потока. Лямбда-выражение компилируется в синтетический метод и может быть выполнено асинхронно или в другом потоке (когда оригинальный стек-фрейм метода уже уничтожен).

1. **Захват по значению (Capture by Value)**: Java копирует значение локальной переменной внутрь объекта лямбды в куче (Heap).
2. **Запрет рассинхронизации**: Если бы Java разрешала менять локальную переменную, возникла бы иллюзия синхронизации между стеком метода и копией в Heap, что привело бы к скрытым ошибкам видимости памяти.

### Почему мутация внешнего состояния разрушает `parallelStream`

Если в последовательном стриме хак с `AtomicInteger` или `List.add` ещё может вернуть ожидаемый результат, то при переходе на `.parallelStream()` код ломается:

| Метод мутации | Поведение в `parallelStream()` | Последствия |
| :--- | :--- | :--- |
| **`list.forEach(resultList::add)`** | Одновременный `add()` в `ArrayList` | `ArrayIndexOutOfBoundsException`, потеря элементов, `null` в середине списка |
| **`list.forEach(map::put)`** | Запись в обычный `HashMap` | Зацикливание бакетов, повреждение структуры хеш-таблицы |
| **`list.forEach(atomicSum::addAndGet)`** | Постоянные гонки CAS-операций | Сильная деградация производительности из-за конкуренции за ячейку памяти |

## 🔴 Senior Level

### Аппаратный уровень: Cache Coherence Traffic и Cache Line Bouncing

Когда множество потоков ForkJoinPool обновляют один общий `AtomicInteger` или `AtomicReference` внутри `parallelStream()`:

```java
AtomicLong counter = new AtomicLong();
transactions.parallelStream().forEach(t -> counter.addAndGet(t.getAmount()));
```

1. **Протокол когерентности кэшей (MESI/MOESI)**:
   - Переменная `counter` лежит в одной кэш-линии процессора (64 байта).
   - Как только ядро CPU выполняет инструкцию `LOCK CMPXCHG` (CAS), оно отправляет по межъядерной шине сигнал **Invalidate** всем остальным ядрам CPU.
2. **Cache Line Bouncing**:
   - Кэш-линия непрерывно скачет между L1/L2 кэшами разных процессорных ядер.
   - 90% процессорного времени тратится не на вычисления, а на ожидание синхронизации кэш-памяти (Memory Bus Saturation).
3. **Решение для Senior**: Использовать `LongAdder` (шардинг счетчика по ячейкам) или чистую редукцию:
   ```java
   long total = transactions.parallelStream()
       .mapToLong(Transaction::getAmount)
       .sum(); // Сложение происходит независимо в локальных регистрах потоков!
   ```

### Статический анализ и правила линтеров

Для защиты кодовой базы на уровне CI/CD:
- **SonarQube Rule `S2674` / `S3864`**: запрещает побочные эффекты и мутацию внешних структур в стримах.
- **ErrorProne / ArchUnit**: проверка на отсутствие захвата мутабельных ссылок в лямбдах.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Локальные переменные внутри лямбд обязаны быть `final` или `effectively final`.
- Причина: Java копирует значение переменной со стека в кучу (Capture by Value) для обеспечения живучести данных после закрытия стек-фрейма.
- Мутация внешних коллекций (`list::add`) в `parallelStream` приводит к потере данных и гонкам памяти.
- Использование `AtomicInteger` в параллельных стримах устраняет гонки, но убивает производительность из-за конфликтов на шине памяти (Cache Line Bouncing).
- Всегда заменяйте мутацию внешних переменных стандартными операциями редукции (`sum()`, `reduce()`, `collect()`).

**Частые уточняющие вопросы:**
- **Что такое effectively final?** — Переменная, которая явно не помечена словом `final`, но её значение ни разу не переназначается после инициализации.
- **Почему массив `int[1]` компилируется внутри лямбды?** — Ссылка на массив остаётся неизменной (`effectively final`), меняется только содержимое ячейки памяти. Это антипаттерн.
- **Почему mapToInt().sum() быстрее AtomicInteger в параллельном стриме?** — Потоки суммируют числа независимо в своих регистрах CPU, объединяя результаты только в конце (без постоянных CAS-блокировок).

**Красные флаги (НЕ говорить):**
- ❌ «Обернуть переменную в массив `int[]` — стандартный и рекомендуемый способ накопления суммы в стриме».
- ❌ «Лямбда держит прямую ссылку на стек-фрейм вызывающего метода».
- ❌ «В `parallelStream` можно безопасно писать в обычный `ArrayList`».
