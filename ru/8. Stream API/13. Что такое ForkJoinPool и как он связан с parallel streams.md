# Что такое ForkJoinPool и как он связан с parallel streams?

---

## 🟢 Junior Level

### Простое определение

**ForkJoinPool** — это специализированный пул потоков, появившийся в Java 7 (JSR 166y), разработанный специально для выполнения задач по принципу **«Разделяй и властвуй» (Divide and Conquer)**:
1. **Fork (Разделение)**: большая задача рекурсивно делится на более мелкие независимые подзадачи.
2. **Join (Объединение)**: результаты выполнения подзадач агрегируются в единый финальный результат.

### Аналогия из реальной жизни

Представьте **бригаду рабочих, разбирающих склад коробок**:
- **Обычный пул потоков (ThreadPoolExecutor)**: Все рабочие толпятся у одной общей двери склада (одна блокирующая очередь задач). Каждый рабочий подходит к двери, берёт коробку и уходит распаковывать. Если коробок много, возникает давка у двери.
- **ForkJoinPool (Work-Stealing)**: Каждому рабочему сразу выделяют свою собственную стопку коробок (персональная двухсторонняя очередь — Deque). Если один рабочий закончил свою стопку быстрее других, он не простаивает, а подходит сзади к стопке соседа и «крадёт» (steals) у него коробку, чтобы помочь.

### Связь с Parallel Streams

Когда в Java вы вызываете `.parallelStream()` у коллекции или `.parallel()` у любого стрима, среда выполнения Java под капотом использует **ForkJoinPool.commonPool()** для параллельного вычисления:

```java
List<Integer> numbers = List.of(1, 2, 3, 4, 5, 6, 7, 8);

// Автоматически выполняется в ForkJoinPool.commonPool()
long sumOfSquares = numbers.parallelStream()
    .mapToLong(n -> (long) n * n)
    .sum();

System.out.println("Сумма квадратов: " + sumOfSquares);
```

**Размер пула по умолчанию:** равен `Runtime.getRuntime().availableProcessors() - 1` (один поток резервируется для текущего вызывающего потока).

## 🟡 Middle Level

### Механика Work-Stealing (Кража работы)

Архитектура ForkJoinPool коренным образом отличается от стандартного `ThreadPoolExecutor`:

| Характеристика | ThreadPoolExecutor | ForkJoinPool |
| :--- | :--- | :--- |
| **Очереди задач** | Одна общая `BlockingQueue` на все потоки | Отдельная `WorkQueue` (двусторонняя очередь — Deque) для каждого worker-потока |
| **Конкуренция (Contention)** | Высокая: все потоки блокируются на одной очереди | Минимальная: потоки работают со своими очередями |
| **Характер задач** | Независимые, часто разнородные задачи | Рекурсивно делимые подзадачи (CPU-bound) |
| **Поведение при простое** | Поток блокируется в ожидании задачи | Поток ищет работу в чужих очередях (**Work-Stealing**) |

```
Worker 1 Queue (Deque):  [Task A3] [Task A2] ◄── Worker 1 берёт с головы (LIFO)
Worker 2 Queue (Deque):  [Task B2] [Task B1]
                                      ▲
                                      └── Worker 1 крадёт с хвоста (FIFO), если освободился
```

### Как Parallel Stream использует ForkJoinPool

1. **Spliterator (`trySplit`)**: Источник данных делится на фрагменты с помощью `Spliterator`. Если коллекция поддерживает случайный доступ (`ArrayList`), деление происходит идеально пополам за $O(1)$.
2. **Оборачивание в задачи**: Фрагменты оформляются как `ForkJoinTask`.
3. **Параллельная обработка**: Задачи распределяются по worker-потокам пула.
4. **Сведение результатов (Combiner)**: Терминальная операция (например, `reduce` или `collect`) объединяет частичные результаты в единое целое.

### Запуск Parallel Stream в собственном ForkJoinPool

Хотя Parallel Streams по умолчанию используют общий `ForkJoinPool.commonPool()`, можно принудительно запустить параллельный стрим в изолированном пуле:

```java
ForkJoinPool customPool = new ForkJoinPool(4);

try {
    List<String> results = customPool.submit(() ->
        users.parallelStream()
            .map(this::heavyCpuCalculation)
            .toList()
    ).get(); // get() блокирует только ожидание завершения задачи в customPool
} finally {
    customPool.shutdown();
}
```

> [!NOTE]
> В ранних версиях Java использование стримов внутри кастомного ForkJoinPool опиралось на деталь реализации. Начиная с Java 8u40+, это официально поддерживаемый и документированный паттерн.

## 🔴 Senior Level

### Внутреннее устройство: Lock-Free Deque и LIFO/FIFO диспетчеризация

Внутри ForkJoinPool каждая очередь `WorkQueue` реализована в виде кольцевого массива:
- **LIFO (Last-In, First-Out) для потока-владельца**: Поток заталкивает (`push`) и забирает (`pop`) задачи с **головы** очереди. Это обеспечивает великолепную **локальность данных в кэше CPU (L1/L2)**, так как недавно созданные подзадачи содержат горячие данные в регистрах и кэше.
- **FIFO (First-In, First-Out) для ворующих потоков**: Сторонний поток крадет (`poll`) задачи с **хвоста** очереди. В хвосте находятся самые крупные, ещё не расщепленные подзадачи. Это минимизирует количество краж и предотвращает конфликты блокировок между владельцем и «ворами» на уровне CAS (`Unsafe` / `VarHandle`).

### Опасность Common Pool в Production и Enterprise (Spring Boot)

`ForkJoinPool.commonPool()` является **глобальным статическим ресурсом** всей виртуальной машины Java (JVM). Его делят:
- Все вызовы `collection.parallelStream()`
- Асинхронные цепочки `CompletableFuture.supplyAsync(task)` (когда Executor не передан явно)
- Ряд внутренних механизмов JDK

**Катастрофический сценарий (Thread Starvation):**
Если один разработчик напишет параллельный стрим с блокирующим I/O:
```java
// ❌ АНТИПАТТЕРН: Блокирующий HTTP-запрос внутри parallelStream
orders.parallelStream()
    .map(order -> restTemplate.getForObject("/payment/" + order.getId(), Payment.class)) // Блокировка!
    .toList();
```
Все потоки `commonPool` окажутся заблокированы в ожидании ответа по сети. В результате во всём микросервисе «встанут» все остальные параллельные стримы и асинхронные `CompletableFuture`.

### Механизм `ManagedBlocker`

Для смягчения проблемы блокировок в ForkJoinPool предусмотрен интерфейс `ForkJoinPool.ManagedBlocker`:
- Если задача обязана заблокироваться (например, ожидает `Phaser` или блокирующий лок), она регистрируется в `ManagedBlocker`.
- ForkJoinPool **компенсирует** блокировку: он временно спавнит дополнительный поток-компенсатор, поддерживая целевой уровень параллелизма.
- По умолчанию стандартные операции ввода-вывода (IO/Socket) **не реализуют** `ManagedBlocker`, поэтому блокировать потоки в FJP категорически не рекомендуется.

### Тюнинг и мониторинг

- **Параметр JVM**: `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N` — переопределяет число потоков в common pool.
- **Программные метрики**:
  ```java
  ForkJoinPool pool = ForkJoinPool.commonPool();
  int parallelism = pool.getParallelism();
  long stealCount = pool.getStealCount();      // Общее число краж задач (индикатор балансировки)
  int activeThreads = pool.getActiveThreadCount();
  int queuedTasks = pool.getQueuedSubmissionCount();
  ```

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `ForkJoinPool` — пул потоков для декомпозируемых CPU-bound задач по принципу «разделяй и властвуй».
- Главное отличие от `ThreadPoolExecutor` — алгоритм **Work-Stealing** и персональные очереди (Deque) у каждого потока.
- `parallelStream()` по умолчанию всегда выполняется в общем статическом `ForkJoinPool.commonPool()`.
- Размер commonPool = `availableProcessors() - 1`. Вызывающий поток также участвует в расчётах.
- Поток-владелец работает со своей очередью по принципу **LIFO** (кэш-локальность CPU), а ворующие потоки берут задачи с хвоста по **FIFO** (забирают самые крупные подзадачи без contention).
- Блокирующий ввод-вывод (I/O, HTTP, JDBC) в `parallelStream` — критический антипаттерн, приводящий к глобальному голоданию потоков (Thread Starvation) во всей JVM.

**Частые уточняющие вопросы:**
- **Почему поток крадет из хвоста (FIFO), а владелец берет из головы (LIFO)?** — Владелец берет горячие мелкие данные из кэша CPU; вор забирает крупную задачу, минимизируя гонки за ячейки памяти.
- **Как изолировать параллельный стрим?** — Запустить стрим через `customPool.submit(() -> stream.parallel()...).get()`.
- **Что делит commonPool в JVM?** — Parallel Streams, `CompletableFuture.supplyAsync()` без своего Executor, системные задачи JDK.
- **Что такое `getStealCount()`?** — Метрика количества украденных задач; высокий рост свидетельствует о качественной балансировке неравномерной нагрузки.

**Красные флаги (НЕ говорить):**
- ❌ «ForkJoinPool устроен так же, как обычный ThreadPoolExecutor с одной очередью».
- ❌ «В параллельных стримах отлично делать вызовы внешних REST API или базы данных».
- ❌ «Каждый parallelStream() создаёт новый отдельный пул потоков».
- ❌ «Размер commonPool всегда строго равен числу ядер процессора» (на 1 меньше, так как текущий поток включается в работу).
