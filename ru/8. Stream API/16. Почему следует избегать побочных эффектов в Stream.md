# Почему следует избегать побочных эффектов в Stream?

---

## 🟢 Junior Level

### Простое определение

**Побочный эффект (Side Effect)** — это любое действие функции, которое выходит за рамки вычисления возвращаемого значения:
- Изменение внешних переменных или полей класса
- Модификация переданных в стрим коллекций
- Запись в файлы, базу данных или отправка сетевых запросов

Стримы в Java спроектированы на принципах **функционального программирования**: функции, передаваемые в промежуточные операции (`map`, `filter`, `flatMap`), должны быть **чистыми (Pure Functions)** — детерминированными и не изменяющими окружающее состояние.

### Наглядный пример: Плохо vs Хорошо

**Плохо (Накопление через побочный эффект):**
```java
List<String> rawNames = List.of("anna", "bob", "charlie");
List<String> upperNames = new ArrayList<>(); // Внешнее мутабельное состояние

// ❌ АНТИПАТТЕРН: модификация внешней коллекции изнутри стрима
rawNames.stream()
    .map(String::toUpperCase)
    .forEach(upperNames::add); // Побочный эффект!
```

**Хорошо (Чистый сбор через Collectors):**
```java
// ✅ ПРАВИЛЬНО: стрим сам создаёт и возвращает результат
List<String> upperNames = rawNames.stream()
    .map(String::toUpperCase)
    .toList(); // Чистая функция без побочных эффектов
```

### Почему побочные эффекты опасны для Junior:
1. **Гонка данных (Race Condition)**: при переключении на `.parallelStream()` код с `upperNames::add` приведёт к потере элементов или `ArrayIndexOutOfBoundsException` внутри `ArrayList`.
2. **Непредсказуемость**: промежуточные операции ленивы — если терминальная операция не вызвана, побочные эффекты вообще не произойдут.

## 🟡 Middle Level

### Принцип Non-Interference (Невмешательство)

Спецификация Java Stream API прямо требует соблюдения правила **Non-Interference**:
> Функции в конвейере стрима **не должны модифицировать источник данных стрима** во время его обхода.

Если нарушить это правило, итерирование приведёт к `ConcurrentModificationException` или непредсказуемому зацикливанию:

```java
List<String> list = new ArrayList<>(List.of("one", "two", "three"));

// ❌ ОШИБКА: Модификация источника данных во время выполнения стрима!
list.stream()
    .filter(s -> {
        if (s.equals("two")) {
            list.add("four"); // Выбросит ConcurrentModificationException
        }
        return true;
    })
    .forEach(System.out::println);
```

### Ловушка ленивых вычислений и оптимизаций JVM

Поскольку стримы ленивы (Lazy), вы не можете рассчитывать на гарантированный вызов операций с побочными эффектами.

**Пример 1: Short-circuiting отсекает побочные эффекты:**
```java
List<String> names = List.of("Alice", "Bob", "Charlie");

// Мы ожидаем, что в лог запишутся все 3 имени, но запишется только "Alice"!
names.stream()
    .peek(name -> log.info("Processing: {}", name)) // ❌ Побочный эффект для логики
    .findFirst();
```

**Пример 2: Java 9+ Stream.count() Optimization:**
Начиная с Java 9, операция `.count()` на стримах с известным размером (`SIZED`) полностью оптимизирует и **вырезает промежуточные вызовы**:
```java
long count = names.stream()
    .peek(name -> auditService.log(name)) // ❌ В Java 9+ peek вообще НЕ БУДЕТ ВЫЗВАН!
    .count();
```

### Когда побочные эффекты допустимы?

Побочные эффекты допустимы **исключительно на терминальном этапе**:
1. `forEach(System.out::println)` — терминальный вывод во внешний поток.
2. `forEach(emailService::send)` — целевое действие над готовым отфильтрованным набором.

## 🔴 Senior Level

### Проблемы многопоточности и ThreadLocal / Transaction Context

В Enterprise-приложениях (Spring Boot, Hibernate, Security) контексты авторизации и транзакций привязаны к текущему потоку через `ThreadLocal` (`SecurityContextHolder`, `@Transactional` Session):

```java
// ❌ КАТАСТРОФА В ENTERPRISE:
@Transactional
public void processOrders(List<Order> orders) {
    orders.parallelStream()
        .forEach(order -> {
            // Воркер-потоки ForkJoinPool не имеют контекста @Transactional!
            // Каждая запись пойдёт в отдельной неконтролируемой транзакции или упадёт с LazyInitializationException
            orderRepository.save(order);
        });
}
```

**Последствия:**
- Потеря контекста безопасности (`SecurityContext` пуст у worker-потоков).
- Нарушение изоляции транзакций и невозможность rollback.
- Быстрое исчерпание пула соединений БД (HikariCP connection pool exhaustion).

### The Atomic Reference & False Sharing Trap

Попытка обойти ограничения многопоточности через атомики внутри параллельного стрима создаёт аппаратные просадки:

```java
AtomicInteger counter = new AtomicInteger();
list.parallelStream().forEach(item -> counter.incrementAndGet()); // ❌ Конкуренция за кэш-линию CPU
```
- **False Sharing и Cache Invalidation**: Постоянные CAS-операции на одном адресе памяти приводят к инвалидации L1/L2 кэша всех ядер CPU (Cache Coherency Traffic по шине памяти).
- **Решение**: Использовать `LongAdder` или сведение через чистый `mapToInt().sum()` / `reduce()`.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Стримы спроектированы для чистых функций без побочных эффектов (Pure Functions).
- Non-interference: стрим никогда не должен модифицировать собственный источник данных (`ConcurrentModificationException`).
- Ленивость (Laziness) и оптимизации (например, Java 9 `Stream.count()`) могут полностью отменить выполнение промежуточных операций (`peek()`, `map()`).
- Побочные эффекты в `parallelStream` приводят к гонкам данных, потере элементов и сбоям в несинхронизированных структурах.
- В Spring Boot вызов транзакций и баз данных в `parallelStream` ломает `ThreadLocal`-контексты (`SecurityContext`, `@Transactional`).

**Частые уточняющие вопросы:**
- **Почему `peek()` нельзя использовать для бизнес-логики?** — Он предназначен только для отладки; JVM имеет право пропустить вызов `peek()` при оптимизациях конвейера.
- **Что такое Non-interference?** — Запрет на модификацию исходной коллекции во время работы стрима.
- **Как `parallelStream` влияет на `@Transactional`?** — Потоки ForkJoinPool не наследуют транзакционный контекст вызывающего потока.
- **Как безопасно собирать результат без побочных эффектов?** — Использовать `Collectors` (`toList()`, `toMap()`, `groupingBy()`) или редукцию `reduce()`.

**Красные флаги (НЕ говорить):**
- ❌ «Можно накапливать элементы в `ArrayList` через `stream.forEach(list::add)`».
- ❌ «`peek()` гарантированно вызывается для каждого элемента перед `count()`».
- ❌ «Если обернуть переменную в `AtomicReference`, побочные эффекты в parallel stream становятся полностью безопасными».
