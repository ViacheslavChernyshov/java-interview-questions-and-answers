# Что такое операция peek() и когда её использовать?

---

## 🟢 Junior Level

### Простое определение

**`peek(Consumer<T>)`** — это **промежуточная (intermediate)** операция в Stream API, которая применяет переданное действие к каждому проходящему элементу и **без изменений передаёт его дальше** вниз по конвейеру.

Официальная документация Java прямо указывает:
> *«Этот метод существует в основном для поддержки отладки, позволяя увидеть элементы в процессе их движения по конвейеру.»*

### Аналогия из жизни

Представьте **смотровое окошко на конвейерной ленте завода**:
- Бутылки с напитком едут по ленте. На определенном этапе установлено прозрачное стекло со сканером (операция `peek`), которое фотографирует бутылку для инженера-контролера.
- Само окошко не меняет форму бутылки и не наливает в неё жидкость (для этого существуют операции `map`), а просто наблюдает.

### Базовый пример для отладки:

```java
List<String> names = List.of("anna", "bob", "alexander", "clark");

List<String> result = names.stream()
    .filter(name -> name.length() > 3)
    .peek(filtered -> System.out.println("[DEBUG After filter]: " + filtered))
    .map(String::toUpperCase)
    .peek(mapped -> System.out.println("[DEBUG After map]: " + mapped))
    .toList();
```

**Вывод в консоль:**
```
[DEBUG After filter]: anna
[DEBUG After map]: ANNA
[DEBUG After filter]: alexander
[DEBUG After map]: ALEXANDER
[DEBUG After filter]: clark
[DEBUG After map]: CLARK
```

## 🟡 Middle Level

### Внутренняя реализация: `Sink.ChainedReference`

В архитектуре реализации Stream API (`ReferencePipeline.java`) операция `peek()` оборачивает downstream-потребитель в цепочку `Sink`:

```java
// Упрощённый фрагмент внутренней реализации OpenJDK:
@Override
public void accept(T t) {
    action.accept(t);       // 1. Выполняем Consumer действие
    downstream.accept(t);   // 2. Передаем элемент следующей операции в пайплайне
}
```

### peek() vs map() vs forEach()

| Операция | Тип операции | Назначение | Возвращает |
| :--- | :--- | :--- | :--- |
| **`peek(Consumer)`** | Intermediate | Наблюдение / логирование в процессе конвейера | `Stream<T>` (тот же тип) |
| **`map(Function)`** | Intermediate | Преобразование / трансформация элементов | `Stream<R>` (новый тип) |
| **`forEach(Consumer)`** | **Terminal** | Завершающее целевое действие над элементами | `void` (завершает стрим) |

### Антипаттерн: Мутация объектов внутри `peek()`

Частая ошибка Junior/Middle разработчиков — изменение полей объектов внутри `peek()`:

```java
// ❌ ГРУБЫЙ АНТИПАТТЕРН: Мутация бизнес-сущностей внутри peek()
users.stream()
    .peek(user -> user.setActive(true)) // Побочный эффект!
    .collect(Collectors.toList());

// ✅ ПРАВИЛЬНО: Использовать map() или forEach()
List<User> activeUsers = users.stream()
    .map(user -> user.toActiveCopy()) // Чистая трансформация
    .toList();
```

## 🔴 Senior Level

### Ловушка оптимизации в Java 9+ (JDK-8075056)

В Java 9+ метод `.count()` был кардинально оптимизирован: если источник стрима обладает характеристикой **`SIZED`** (например, `ArrayList`, массив, `List.of()`) и в пайплайне **нет операций фильтрации**, JVM вычисляет количество элементов напрямую через размер коллекции, **полностью минуя обход элементов**:

```java
List<String> list = List.of("a", "b", "c");

long total = list.stream()
    .peek(item -> auditService.log(item)) // ❌ В Java 9+ этот peek ВООБЩЕ НЕ ВЫПОЛНИТСЯ!
    .count(); // Оптимизация вернет 3 мгновенно без вызова элементов!
```

> [!WARNING]
> Если бизнес-логика (например, аудит, списание денег или отправка метрик) помещена в `peek()`, она будет незаметно пропущена в рантайме.

### Влияние Short-Circuiting операций

Операции короткого замыкания (`findFirst()`, `findAny()`, `anyMatch()`, `limit()`) прерывают обработку стрима в произвольный момент:

```java
List<String> items = List.of("A", "B", "C", "D", "E");

// peek() сработает ТОЛЬКО для элементов "A" и "B", остальные 3 элемента не будут обработаны!
items.stream()
    .peek(item -> metricRegistry.counter("processed").increment())
    .filter(item -> item.equals("B"))
    .findFirst();
```

### Highload и накладные расходы

В критических по латентности системах (FinTech, Highload):
- Каждый `peek()` добавляет дополнительный виртуальный вызов (`invokevirtual` / `invokeinterface`) на каждый элемент.
- При обработке миллионов записей в секунду это создает нагрузку на стек вызовов процессора.
- **Production Best Practice**: для отладки вместо `peek()` использовать встроенный **Java Stream Debugger** в IDE или логировать батчами на терминальной стадии.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `peek(Consumer)` — промежуточная операция, предназначенная **исключительно для отладки и трассировки**.
- Не меняет элементы и передает их дальше по цепочке.
- Без вызова терминальной операции `peek()` не выполнится вовсе (ленивость Stream API).
- В Java 9+ при вызове `.count()` на `SIZED` коллекциях без `filter` вызов `peek()` полностью вырезается оптимизатором JVM.
- Short-circuiting операции (`findFirst`, `limit`) обрывают выполнение `peek()` для оставшихся элементов.
- Использование `peek()` для бизнес-мутаций — грубый архитектурный антипаттерн.

**Частые уточняющие вопросы:**
- **Почему peek() нельзя использовать для бизнес-логики?** — JVM не гарантирует его вызов из-за ленивости, шорт-циркуитов и оптимизаций `count()`.
- **В чём разница между peek() и forEach()?** — `peek()` возвращает `Stream<T>` и продолжает конвейер, `forEach()` возвращает `void` и завершает работу стрима.
- **Как peek() ведёт себя в parallelStream?** — Обрабатывается разными потоками ForkJoinPool в непредсказуемом порядке.

**Красные флаги (НЕ говорить):**
- ❌ «`peek()` — отличный метод для сохранения записей в базу данных перед сбором списка».
- ❌ «`peek()` всегда вызывается для каждого элемента независимо от терминальной операции».
- ❌ «`peek()` изменяет тип стрима так же, как `map()`».
