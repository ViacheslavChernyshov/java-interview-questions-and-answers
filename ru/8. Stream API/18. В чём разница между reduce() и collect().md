# В чём разница между reduce() и collect()?

---

## 🟢 Junior Level

### Простое объяснение

Обе операции — **`reduce()`** и **`collect()`** — являются **терминальными операциями редукции (свёртки)**: они проходят по всем элементам стрима и объединяют их в одно финальное значение.

Главная разница заключается в **способе формирования результата**:

| Критерий | `reduce()` (Immutable Reduction) | `collect()` (Mutable Reduction) |
| :--- | :--- | :--- |
| **Принцип работы** | На каждом шаге создаёт **новый объект** | Модифицирует **один существующий контейнер** |
| **Аналогия** | **Лепка снежка**: каждый слой снега прессуется в новый, увеличивающийся ком | **Корзина для покупок**: вы берете одну корзину и складываете в неё товары |
| **Основное назначение** | Примитивы, иммутабельные значения (числа, строки, Boolean) | Коллекции (`List`, `Set`, `Map`), сложные DTO |

### Базовые примеры

**1. Использование `reduce()` (Числовая свёртка):**
```java
List<Integer> numbers = List.of(1, 2, 3, 4, 5);

// Складываем числа: (0 + 1) -> 1, (1 + 2) -> 3, (3 + 3) -> 6 ...
int sum = numbers.stream()
    .reduce(0, (subtotal, element) -> subtotal + element);
```

**2. Использование `collect()` (Сборка в коллекцию):**
```java
List<String> words = List.of("apple", "banana", "cherry");

// Наполняем существующий ArrayList без пересоздания списка на каждом шаге
List<String> upperList = words.stream()
    .map(String::toUpperCase)
    .collect(Collectors.toList());
```

## 🟡 Middle Level

### Сигнатуры и внутреннее устройство

#### Сигнатура `reduce()`:
```java
T reduce(T identity, BinaryOperator<T> accumulator);
<U> U reduce(U identity, BiFunction<U, ? super T, U> accumulator, BinaryOperator<U> combiner);
```
- **`identity`**: нейтральный начальный элемент ($0$ для сложения, $1$ для умножения).
- **`accumulator`**: функция, принимающая частичный результат и следующий элемент, возвращающая **новое значение**.

#### Сигнатура `collect()`:
```java
<R> R collect(Supplier<R> supplier, BiConsumer<R, ? super T> accumulator, BiConsumer<R, R> combiner);
<R, A> R collect(Collector<? super T, A, R> collector);
```
- **`supplier`**: фабрика, создающая мутабельный контейнер (например, `ArrayList::new`).
- **`accumulator`**: процедура (`BiConsumer`), которая **добавляет** элемент в контейнер на месте (`List::add`).
- **`combiner`**: процедура слияния двух контейнеров в параллельном режиме (`List::addAll`).

### Почему `reduce()` для коллекций — катастрофический антипаттерн?

Попытка собрать коллекцию через `reduce()` порождает грубейшие ошибки:

```java
// ❌ АНТИПАТТЕРН: Использование reduce() для мутации коллекции
List<String> badList = words.parallelStream()
    .reduce(new ArrayList<>(), 
            (list, word) -> { list.add(word); return list; }, 
            (list1, list2) -> { list1.addAll(list2); return list1; });
```

**Что здесь сломано:**
1. **Нарушение многопоточности в `parallelStream()`**: `identity` (`new ArrayList<>()`) создаётся один раз. Несколько потоков ForkJoinPool одновременно вызывают `.add()` на одном и том же несинхронизированном `ArrayList`, что приводит к потере данных и `ArrayIndexOutOfBoundsException`.
2. **Алгоритмическая сложность $O(N^2)$ при создании копий**: Если пытаться создавать новый список на каждом шаге (`new ArrayList<>(list)`), копирование элементов на каждой итерации дает квадратичную сложность $O(N^2)$ и гигантский расход памяти.

## 🔴 Senior Level

### Анатомия интерфейса `Collector<T, A, R>`

Для `collect()` Java предоставляет мощную абстракцию `Collector`:
- **`A` (Accumulator type)**: внутренний мутабельный тип аккумулятора (например, `StringBuilder` или `List`).
- **`R` (Result type)**: финальный возвращаемый тип.
- **`finisher()`**: функция финального преобразования (например, `StringBuilder::toString` или `Collections::unmodifiableList`).

### Оптимизации `Characteristics` в Parallel Stream

Коллекторы могут иметь флаги `Characteristics`, кардинально меняющие поведение в `parallelStream()`:

```java
public enum Characteristics {
    CONCURRENT,  // Аккумулятор потокобезопасен (ConcurrentHashMap). Все потоки пишут в ОДИН контейнер без combiner!
    UNORDERED,   // Порядок элементов не важен
    IDENTITY_FINISH // Функция finisher() является тождественной (каст без трансформации)
}
```

```
При обычном collect() в parallelStream:
Thread 1 ──► Container A ──┐
                           ├──► Combiner ──► Итоговый List
Thread 2 ──► Container B ──┘

При Characteristics.CONCURRENT в parallelStream:
Thread 1 ──┐
           ├──► ЕДИНЫЙ ConcurrentMap (без накладных расходов на слияние контейнеров!)
Thread 2 ──┘
```

### Сравнение производительности и Memory Footprint

| Операция | Конкатенация строк 100K элементов | Сборка 100K объектов в `List` |
| :--- | :--- | :--- |
| **`reduce((a, b) -> a + b)`** | $O(N^2)$, создание сотен тысяч промежуточных `String` объектов в Eden space | $O(N^2)$ при копировании списков, огромная нагрузка на GC |
| **`collect(joining())` / `collect(toList())`** | $O(N)$, единый расширяемый буфер `char[]`/`byte[]` | $O(N)$, единый `ArrayList` с амортизированным расширением |

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `reduce()` предназначен для **иммутабельной свёртки** (числа, математические операции, boolean flag) — порождает новое значение на каждом шаге.
- `collect()` предназначен для **мутабельной свёртки** (коллекции, строки, мапы) — изменяет состояние существующего контейнера.
- Использование `reduce()` для накопления в мутабельные структуры (`ArrayList`) ломает `parallelStream` из-за общего `identity` между потоками.
- Конкатенация строк через `reduce()` имеет сложность $O(N^2)$, через `collect(joining())` — $O(N)$.
- `Collector` с флагом `CONCURRENT` позволяет нескольким потокам писать в единый потокобезопасный контейнер без этапа объединения (combiner).

**Частые уточняющие вопросы:**
- **Почему нельзя мутировать identity в reduce?** — В параллельном стриме `identity` расшаривается между потоками, что при мутации приведет к race conditions.
- **В чём разница между BiFunction в reduce и BiConsumer в collect?** — `BiFunction` возвращает новый объект, а `BiConsumer` мутирует переданный контейнер (возвращает `void`).
- **Когда оправдан кастомный Collector?** — Когда стандартных фабрик `Collectors` недостаточно (например, сборка в кольцевой буфер или специфическую структуру графа).

**Красные флаги (НЕ говорить):**
- ❌ «`reduce()` и `collect()` взаимозаменяемы и отличаются только синтаксисом».
- ❌ «`reduce()` работает быстрее `collect()`, потому что у него меньше параметров».
- ❌ «Сборка в `List` через `reduce` работает абсолютно безопасно в параллельных стримах».
