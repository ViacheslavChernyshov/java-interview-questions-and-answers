# Что такое побочные эффекты (side effects) в Stream?

---

## 🟢 Junior Level

### Простое определение

**Побочный эффект (Side Effect)** — это любое действие функции внутри стрима, которое **изменяет внешнее состояние программы** или взаимодействует с внешним миром помимо вычисления возвращаемого значения.

### Примеры побочных эффектов:
1. Изменение внешних переменных или добавление элементов во внешний список (`list.add()`).
2. Модификация полей объектов, проходящих через стрим (`user.setName(...)`).
3. Запись в консоль (`System.out.println`), логирование, запись в файл.
4. Выполнение сетевых запросов или транзакций в базе данных.

### Аналогия из жизни

Представьте **калькулятор**:
- **Чистая функция (без побочных эффектов)**: Вы вводите $2 + 2$ и получаете ответ $4$ на экране. Калькулятор не отправляет SMS вашему банку и не меняет обои на рабочем столе.
- **Функция с побочным эффектом**: Каждый раз при нажатии кнопки «+» калькулятор параллельно списывает 1 рубль с вашей карты и звонит в колокол.

### Наглядный пример: Плохо vs Хорошо

```java
// ❌ ПЛОХО (Побочный эффект — наполнение внешнего списка):
List<String> upperNames = new ArrayList<>();
names.stream()
    .map(String::toUpperCase)
    .forEach(upperNames::add); // Побочный эффект!

// ✅ ХОРОШО (Чистый стрим — результат возвращается как значение):
List<String> upperNames = names.stream()
    .map(String::toUpperCase)
    .toList();
```

## 🟡 Middle Level

### 3 столпа функциональной чистоты Stream API

Для безопасного и детерминированного выполнения (особенно в `parallelStream()`) функции в Stream API должны удовлетворять 3 требованиям:

1. **Non-interference (Невмешательство)**: функции конвейера **не должны изменять исходную коллекцию** во время работы стрима (иначе `ConcurrentModificationException`).
2. **Statelessness (Отсутствие состояния)**: результат обработки элемента не должен зависеть от состояния, накопленного при обработке предыдущих элементов.
3. **Side-effect-freedom (Отсутствие побочных эффектов)**: функции не должны мутировать разделяемые ресурсы без синхронизации.

### Почему побочные эффекты ломают параллелизм

```
Sequential Stream:  [Element 1] ──► [Element 2] ──► [Element 3] (Порядок детерминирован)

Parallel Stream:    Worker 1: [Element 2] ──┐
                    Worker 2: [Element 1] ──┼──► Доступ к общему ресурсу одновременно!
                    Worker 3: [Element 3] ──┘
```

- **Race Conditions**: одновременная запись в несинхронизированные структуры памяти.
- **Непредсказуемость порядка**: побочные эффекты сработают в случайном порядке потоков.
- **Visibility Issues**: изменения переменной в одном потоке не видны другим ядрам CPU без барьеров памяти (`volatile` / `synchronized`).

## 🔴 Senior Level

### Логгеры и блокировки в Highload (`peek(log::info)`)

Популярная ошибка — логирование элементов через `peek()` в высоконагруженных стримах:

```java
stream.parallel()
    .peek(item -> log.info("Processing item: {}", item.getId()))
    .map(this::heavyTransform)
    .toList();
```

**Аппаратная проблема:**
- Аппендеры логирования (Logback `FileAppender` / `ConsoleAppender`) используют внутренний `ReentrantLock` или `synchronized` для предотвращения перемешивания строк в файле.
- В результате 16 потоков `ForkJoinPool` выстраиваются в одну очередь за монитором логгера, вызывая **массовые context switches и падение производительности в 50–100 раз**.

### Риск взаимных блокировок (Deadlocks in ForkJoinPool)

Если побочный эффект внутри задачи стрима пытается захватить внешний монитор (`synchronized`), который в это же время удерживается другим потоком, ожидающим завершения параллельного стрима, возникает классический **Deadlock пула потоков**.

### Пропуск побочных эффектов при оптимизациях JVM

В Java 9+ метод `.count()` оптимизирован для `SIZED` источников:
```java
long count = users.stream()
    .peek(user -> auditService.register(user)) // ❌ БУДЕТ ПРОПУЩЕН ОПТИМИЗАТОРОМ!
    .count();
```
JIT-компилятор и Stream API вправе выбросить промежуточные узлы, так как считает стрим чистым конвейером без побочных эффектов.

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- Побочный эффект — мутация внешнего состояния или выполнение внешнего ввода-вывода (I/O, логи, БД) внутри стрима.
- Стримы спроектированы для **чистых функций (Pure Functions)**.
- В параллельных стримах побочные эффекты приводят к гонкам данных, нарушению порядка и взаимоблокировкам (Deadlocks).
- Логирование (`peek(log::info)`) в `parallelStream` блокирует потоки на мониторах аппендера, убивая параллелизм.
- Единственные легитимные места для побочных эффектов: `forEach()` (терминальное действие) и `peek()` (только локальная отладка).

**Частые уточняющие вопросы:**
- **Что такое Pure Function в контексте Stream?** — Функция, результат которой зависит только от переданных аргументов, не имеющая побочных эффектов и детерминированная при каждом вызове.
- **Что произойдет, если в parallelStream мутировать HashMap?** — Повреждение структуры связных списков/красно-черных деревьев в бакетах мапы, бесконечный цикл или потеря данных.
- **В чём разница между мутацией в forEach() и в map()?** — `forEach` — терминальная операция, предназначенная для вывода результатов; `map` — промежуточная чистая трансформация.

**Красные флаги (НЕ говорить):**
- ❌ «Внутри `map()` отлично отправлять HTTP-запросы и сохранять записи в базу данных».
- ❌ «Побочные эффекты в `peek()` гарантированно выполняются для всех элементов».
- ❌ «Побочные эффекты опасны только в Python, а в Java они полностью изолируются JVM».
