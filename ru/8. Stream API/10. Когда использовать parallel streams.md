# Когда использовать parallel streams?

---

## 🟢 Junior Level

### 3 главных условия для включения параллелизма

Использовать **`parallelStream()`** целесообразно **ТОЛЬКО** при одновременном выполнении 3 условий:

1. **Большой объём данных**: в коллекции тысячи или миллионы элементов.
2. **Тяжелые вычисления процессора (CPU-Bound)**: математика, криптография, обработка графики, сложный парсинг.
3. **Полная независимость элементов**: обработка одного элемента не зависит от других и не мутирует внешние переменные.

```java
// ✅ ХОРОШО: CPU-нагрузка, большой массив, чистая функция
List<BigInteger> primes = numbers.parallelStream()
    .filter(BigInteger::isProbablePrime)
    .toList();

// ❌ КАТАСТРОФА: Блокирующий ввод-вывод (I/O) в parallelStream
List<User> users = userIds.parallelStream()
    .map(id -> restTemplate.getForObject("/users/" + id, User.class)) // Парализует весь сервер!
    .toList();
```

### Аналогия из жизни

- **Однопоточный стрим (`stream`)** — один рабочий копает яму. Если яма маленькая (100 элементов), он выкопает её за 2 минуты.
- **Параллельный стрим (`parallelStream`)** — вы вызываете 8 рабочих с экскаватором. На их сбор, инструктаж и координацию уходит 15 минут. Это выгодно только для рытья котлована под небоскрёб ($100{,}000$ элементов), но бессмысленно для посадки одного цветка.

## 🟡 Middle Level

### Чек-лист принятия решения (Модель $N \times Q$)

Перед вызовом `.parallelStream()` Middle-разработчик обязан оценить формулу Брайана Гетца:
$$N \times Q > 10{,}000$$
- **$N$**: число элементов в коллекции.
- **$Q$**: количество машинных инструкций процессора на 1 элемент.

#### Оценка структуры данных (Spliterator Efficiency):
1. **🟢 Отлично ($O(1)$)**: `ArrayList`, примитивные массивы `int[]`, `IntStream.range()`. Они имеют точный размер и мгновенно делятся пополам по индексам.
2. **🟡 Средне**: `HashSet`, `TreeSet` (деревья и хеш-таблицы делятся сбалансированно, но создают больше накладных расходов).
3. **🔴 Ужасно ($O(N)$)**: `LinkedList`, `Stream.iterate()`. Для деления связного списка пополам нужно обойти $N/2$ ссылок в памяти — параллелизм сделает код **медленнее** обычного `for`.

#### Опасность Stateful и Order-dependent операций:
- Операции `sorted()`, `distinct()`, `limit()`, `skip()` требуют межпоточной синхронизации и сбора данных в промежуточные буферы. В `parallelStream` они теряют до 80% эффективности.

## 🔴 Senior Level

### Архитектурный выбор: `parallelStream()` vs `Virtual Threads` (Java 21) vs `CompletableFuture`

В современных Java-архитектурах инструменты многопоточности строго разграничены по профилю нагрузки:

| Задача | Рекомендуемый инструмент | Почему НЕ `parallelStream()` |
| :--- | :--- | :--- |
| **CPU-Bound над коллекцией** (математика, ML, сжатие) | 🟢 **`parallelStream()`** / ForkJoinPool | Идеально нагружает все физические ядра CPU |
| **I/O-Bound задачи** (HTTP-запросы, SQL, чтение файлов) | 🟢 **Virtual Threads (Java 21+)** / `ExecutorService` | `parallelStream` блокирует воркеры общего `ForkJoinPool.commonPool()` |
| **Асинхронные цепочки и Event-Driven** | 🟢 **`CompletableFuture`** | Поддерживает неблокирующие коллбэки и таймауты |

### Изоляция выполнения: паттерн Custom ForkJoinPool

Чтобы тяжелый параллельный стрим не заблокировал системные задачи приложения в Spring Boot, его изолируют в выделенном пуле потоков:

```java
ForkJoinPool customPool = new ForkJoinPool(Runtime.getRuntime().availableProcessors());
try {
    List<Report> reports = customPool.submit(() ->
        largeDataList.parallelStream()
            .map(this::generateReport)
            .toList()
    ).get();
} finally {
    customPool.shutdown();
}
```

### JMH (Java Microbenchmark Harness)

Senior инженер никогда не делает выводов об ускорении на основе «интуиции»:
- JIT C2-компилятор по-разному оптимизирует параллельный и последовательный код (инлайнинг, векторизация AVX, развертывание циклов).
- Единственное объективное доказательство выигрыша от `parallelStream` — это **микробенчмарк JMH** с фазами прогрева (Warmup).

## 🎯 Шпаргалка для интервью

**Обязательно знать:**
- `parallelStream` предназначен **исключительно для CPU-интенсивных задач** над большими коллекциями ($N \times Q > 10{,}000$).
- Категорически запрещено использовать `parallelStream` для I/O (БД, сетевые вызовы), так как он блокирует общий `ForkJoinPool.commonPool()`.
- Идеально делятся: массивы, `ArrayList`, `IntStream.range`. Ужасно делятся: `LinkedList`, `Stream.iterate`.
- Для I/O-задач в современной Java (21+) используются **Virtual Threads** или `CompletableFuture`.
- Проверять ускорение обязательно через бенчмарки **JMH**.

**Частые уточняющие вопросы:**
- **Почему parallelStream не подходит для LinkedList?** — Чтобы разделить `LinkedList` пополам, `Spliterator` вынужден последовательно перебирать ссылки $N/2$ элементов, нивелируя всю выгоду.
- **Что такое формула $N \times Q$?** — Произведение числа элементов ($N$) на объем работы процессора на элемент ($Q$). Параллелизм выгоден, если $N \times Q > 10{,}000$.
- **Как изолировать параллельный стрим от остального приложения?** — Запустить стрим через `customForkJoinPool.submit(() -> stream.parallel()...).get()`.

**Красные флаги (НЕ говорить):**
- ❌ «Если добавить `.parallel()` к любому стриму в Spring REST контроллере, сервер будет быстрее отвечать».
- ❌ «Параллельные стримы отлично подходят для сохранения сущностей в базу данных».
- ❌ «`LinkedList` параллелится так же быстро, как `ArrayList`».
